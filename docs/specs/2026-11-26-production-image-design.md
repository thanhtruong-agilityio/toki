# Production image and Compose design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/production-image.md (Thanh Truong)
Ticket: TOKI-084

## Goal
Toki needs one installable unit. Today the server runs through `tsx`, the web app through the Vite dev server, and the development Compose file only starts Postgres, MinIO and Mailpit on the builder's machine. This work builds the production images and the Compose file that runs the whole of Toki on one machine: Caddy with automatic TLS, the app server, the worker, the migration step, Postgres and MinIO. It also fixes how each process gets its configuration, which commands the operator can run, and which headers the browser sees. The installation guide, the automated deploy, the performance measurement and the security review (TOKI-087, TOKI-085, TOKI-089, TOKI-091) build on it.

## Scope
- In: `Dockerfile` (stages `build`, `server`, `web`); `.dockerignore`; the `build` script of `apps/server` (`apps/server/scripts/build.mjs`); the command `src/cli/healthcheck.ts`; `docker-compose.prod.yml`; `infra/Caddyfile`; the list of configuration areas of each process (`entryAreas` in `apps/server/src/config.ts`); the new rows of `docs/environment-config.md` and lines of `.env.example`; the check of the whole stack (`tools/stack/`, the root scripts `image:build` and `stack:check`), one CI job that runs it, and the two rows of `CLAUDE.md` "Common commands" for the two scripts. This ticket edits `docs/environment-config.md` and `.env.example` itself (R26); the Dockerfile and Compose lines for the build id of TOKI-104 are this ticket's too (R1, R10).
- Out (not now):
  - Backup and restore: deferred (D-092). Nothing here copies, snapshots or restores a volume.
  - Building and pushing the image on merge, the registry, the deploy trigger, the SSH or runner access, how `.env` reaches the server and is updated: TOKI-085. D-190 (automatic or by hand) is open there; nothing here depends on it (concern 11). The first installation builds on the machine with the two `docker build` commands of R10.
  - The step-by-step installation guide, the firewall and operating-system steps, DNS records: TOKI-087, which points to `.env.example` and writes no second list (plan, TOKI-087).
  - The content of the Content-Security-Policy, rate limits, cookie review and dependency review: TOKI-091 (concern 7). This work sets the headers that cannot break a feature.
  - The performance script and its 200-person load: TOKI-089. It runs against this stack.
  - The code of the commands themselves (`emergency-link`, `jobs-status`, `vapid-keys`, `backfill-join-lines`, `seed`), of `worker.ts`, of `main.ts` beyond its list of areas, and of the web app: their own tickets. This work builds the ones that exist into the image and leaves `seed` out.
  - A health check or a readiness route that reads the database (`/readyz`): not built (TOKI-004 concern 3).
  - Several copies of the server, a second machine, a managed database: not phase 1 (technical design).

## Requirements
- R1. One `Dockerfile` at the root has three stages and two targets. `build` installs every dependency of the workspace from the lock file (`--frozen-lockfile`), including the devDependencies of `apps/web` and the `sharp` platform package for the image's platform; then declares `ARG TOKI_BUILD_ID=dev` (the build id of TOKI-104 R2: a public commit hash, no secret; the only `ARG` of the file); then runs `pnpm --filter ./apps/web build` and `pnpm --filter @toki/server build` as two separate `RUN` lines in that order, so the layer that installs the dependencies stays cached when only the id changes. `server` (a target) is the runtime of the server, the worker and the commands (R4 to R8). `web` (a target) is Caddy with the built `apps/web/dist` and `infra/Caddyfile` inside it (R14). Both targets are built from the same commit and the same `TOKI_BUILD_ID`, so one tag names a server and a web app that belong together (concern 4). Check: `docker build --target server` and `--target web` both succeed; the control of R2 fails the build; R22 builds with `TOKI_BUILD_ID=check` and finds that value in both images and `dev` when the argument is absent.
- R2. A failed check of the web build fails the image build. The `build` script of `apps/web` today ends with `check:no-dev-pages` and `check:fonts`, and `check:pwa` joins it with TOKI-077 R10 (TOKI-016, TOKI-010); the `build` stage runs that script as it is and no `|| true`, `--ignore-scripts` or copy of a pre-built `dist` skips it. Check, on a temporary copy of the tracked files (R22), never in the checkout: (a) a copy whose `apps/web/package.json` `build` script has `&& node -e "process.exit(1)"` appended fails the build of the target `web` with a non-zero exit; (b) when `check:pwa` exists, a copy with `display` changed to `browser` in `apps/web/public/manifest.webmanifest` fails with the text `check:pwa` in the output; the same build of the unchanged copy exits 0.
- R3. The Node of every stage is one exact version of the line in `.nvmrc` (22), at 22.12 or later (the queue library needs it, TOKI-064 R1), on the Debian slim variant (glibc), so the `sharp` platform package is the standard one (concern 3). `pnpm` is the version of `packageManager` in the root `package.json`, activated with `corepack`. Check: the script reads the `FROM` lines and fails when the Node major differs from `.nvmrc`, when the minor is below 12, or when a tag is `latest` or has no patch version; `docker run <server image> node --version` agrees with the Dockerfile.
- R4. `apps/server` gets a `build` script, `apps/server/scripts/build.mjs`. It uses `esbuild` (a devDependency at the exact version already in the lock file for `tsx`) with `outbase: "src"` stated in the options (esbuild otherwise takes the common ancestor of the entries, which is `src/` only while `main.ts` or `db/migrate-cli.ts` is an entry) to write `apps/server/dist/` with the same folder structure as `src/` (`dist/main.js`, `dist/worker.js` once TOKI-064 adds it, `dist/db/migrate-cli.js`, `dist/cli/<name>.js`). Workspace packages (`@toki/*`, which are TypeScript source) are bundled into each file; every other dependency of `apps/server/package.json` stays external and is loaded from `node_modules` at run time. The entries are `src/main.ts`, `src/worker.ts` (when the file exists), `src/db/migrate-cli.ts`, and every `.ts` file directly in `src/cli/` except the helpers (a constant list in the script: `config.ts`, `operator.ts`) and the development-only `seed.ts`. The script also exports a function `define(buildId)` that returns the esbuild `define` map for the build id (TOKI-104 R2: the global that holds `TOKI_BUILD_ID`, read from `process.env.TOKI_BUILD_ID`, default `dev`); the build calls that same function, so the one test of TOKI-104 covers the one the image uses. `migrationsFolder` is `../../migrations` from the file that calls it, so it is right only in an entry that sits at the depth `dist/<folder>/` and inlines `db/migrate.ts`: today that is `dist/db/migrate-cli.js` alone (`/app/dist/db/` gives `/app/migrations`), and no other entry may call it. The root `build` script (`pnpm -r --if-present run build`) therefore builds it in CI. Check: after the build a test lists `dist/` and compares it with an expected list that is written out in the test, not made by the rule of the script: the entries of `src/cli/` known today (`emergency-link`, `healthcheck`, and, when they exist, `vapid-keys`, `jobs-status`, `backfill-join-lines`), the helpers `config.ts` and `operator.ts`, the development-only `seed.ts`; a `.ts` file in `src/cli/` that is in none of these three lists fails the test and names the file, so its owner decides entry or helper (a helper added without the decision would otherwise become an entry silently); the string `../../migrations` is in `dist/db/migrate-cli.js` and in no other file of `dist/`; `node dist/main.js` started with no environment exits 1 and names variables on standard error (the check of TOKI-004 R3, now on the built file).
- R5. The seed stays out of the image. The runtime stage copies only what R6 lists, so no file of `src/seed/` and no `dist/cli/seed.js` is in the image, and `seed.ts` is not an entry (R4). Check, on the built `server` image: no path under `/app` contains `seed`; the string `hugepig.example` (the sample addresses of TOKI-081 R21) is in no file under `/app`; `docker run <image> node dist/cli/seed.js` fails because the file does not exist. The build stage may hold the seed's source: only the runtime stage matters.
- R6. The runtime stage `server` holds, under `/app`: `dist/`, `migrations/` (the SQL and `meta/` of `apps/server/migrations`), `package.json` and `node_modules` with the production dependencies of `apps/server` only. The `build` stage makes `node_modules` with `pnpm deploy --prod --filter @toki/server /deploy/server` (pnpm 12 asks for its `--legacy` form when the workspace does not inject workspace packages; the choice is the one that works with the lock file, and the Dockerfile says which). The `@toki/*` packages are `workspace:*` dependencies: the deploy copies them into `node_modules/@toki/`, but R4 bundles them and nothing loads them at run time, so the Dockerfile deletes `node_modules/@toki` in the `build` stage and copies from the deploy folder only `node_modules` and `package.json`. `dist/` and `migrations/` are copied from the build of R4, so the deploy folder's other files (its `src/`, scripts, tests) never reach the image. It holds no `src/`, no source map, no test, no `.env` or `.env.*` file, and none of the devDependencies (`tsx`, `esbuild`, `drizzle-kit`, `vitest`, `typescript`, `@playwright/test`). The migration folder is found by the code as it is on main (R4 keeps the depth of `src/`). The process runs as the user `node`, with the working directory `/app`, and the image sets no `ENV` that holds a configuration value. Check: `docker run --rm --entrypoint sh` lists `/app` and finds exactly `dist`, `migrations`, `package.json` and `node_modules` at its top, none of the names above, no `node_modules/@toki`, and finds `migrations/meta/_journal.json`; `node dist/main.js` still starts as far as the configuration check (exit 1, a variable named, no "cannot find package"); `id -u` is not 0; `docker image inspect` shows no variable of `docs/environment-config.md`; a build in a temporary copy (R22) whose context holds a `.env` with a marker value leaves the marker in no file of the image (the `.dockerignore` of R7 keeps it out of the context).
- R7. A root `.dockerignore` keeps out of the build context: `.git`, every `node_modules`, `.env` and `.env.*` except `.env.example`, `apps/web/dist`, `apps/server/dist`, `e2e`, `docs`, test reports and the root `playwright*` files. The development MinIO build keeps its own file `Dockerfile.minio.dockerignore`, which BuildKit prefers for that Dockerfile; this work does not change it. Check, in a temporary copy of the tracked files (R22), where the script adds a file for each name of the list (including a `.env` with a marker value) and never touches the checkout: a `docker build` of a Dockerfile whose only step is `COPY . /ctx` and `find /ctx` finds none of them, and the context size is printed.
- R8. The server image runs the processes and the commands of the server with `node` on the built files, never `tsx` or `pnpm` (they are development tools, TOKI-026 concern 12). The default command is `node dist/main.js`. The worker is the same image with the command `node dist/worker.js`; the migration step is the same image with `node dist/db/migrate-cli.js`. Operator commands are run with `docker compose -f docker-compose.prod.yml exec -T server node dist/cli/<name>.js <args>` (`-T`: with a terminal attached Docker merges standard output and standard error, and the output contract of `emergency-link` keeps them apart, TOKI-026 R19; TOKI-087 R12 uses the same form); `emergency-link` needs `DATABASE_URL` and `APP_ORIGIN` (TOKI-026 R22), which the server service has. A command that needs no configuration, such as `vapid-keys`, is run before the first start with `docker run --rm toki-server:local node dist/cli/vapid-keys.js` (the image the first installation builds, R10), because `compose` would stop on the first value not yet in `.env` (concern 9). Check: R22.
- R9. The health check. `apps/server/src/cli/healthcheck.ts` takes an optional port as its first argument (default 3000), asks `GET http://127.0.0.1:<port>/healthz` and exits 0 only on a status 200 whose body is `{"status":"ok"}`, and exits 1 on anything else, a refused connection and a wait of more than 3 seconds included. It reads no environment variable and prints nothing on success. The `server` service of Compose uses it (`interval` 10 s, `timeout` 5 s, `retries` 3, `start_period` 30 s). `/healthz` is not routed by Caddy (TOKI-004 concern 3; R15). Check: a unit test of the exit codes against a local server that answers 200 with the right body, 200 with another body, 500, and a closed port; the 3-second limit is an `AbortSignal` that the command takes as a parameter, and the test passes one that is already aborted (no timer runs); R22 checks the container becomes `healthy`.
- R10. `docker-compose.prod.yml` (project name `toki`) has these services: `caddy` (the target `web`), `server`, `worker` and `migrate` (the target `server`), `postgres`, `minio`, `storage-init`. Images are named `${TOKI_REGISTRY:-}toki-server:${TOKI_TAG:-local}` and `${TOKI_REGISTRY:-}toki-web:${TOKI_TAG:-local}`, each with a `build` section of the matching target whose `args` hold `TOKI_BUILD_ID: ${TOKI_BUILD_ID:-dev}` (the build id of TOKI-104 R2; the same value in both sections), so `docker compose pull` takes them from a registry when `TOKI_REGISTRY` and `TOKI_TAG` name one (the registry and the tags are TOKI-085's) and `docker compose build` builds them on the machine once `.env` is filled. Compose reads every `${NAME:?...}` of the file when it loads it, `build` included, so the first installation, which builds before `.env` exists, builds with the two `docker build` commands `docker build --target server -t toki-server:local .` and `docker build --target web -t toki-web:local .` (with `--build-arg TOKI_BUILD_ID=<id>` to set the id); `docker compose up` then finds both images and builds nothing. `pnpm image:build` (R22) runs those two commands. Two networks: `edge` (Caddy, server, minio; subnet `172.29.0.0/24`, `ip_range` `172.29.0.128/25` so automatic addresses never use `.2`, Caddy at the fixed `ipv4_address` `172.29.0.2`) and `internal` (server, worker, migrate, storage-init, postgres, minio). Only `caddy` has `ports`: `${HTTP_PORT:-80}:${HTTP_PORT:-80}` and `${HTTPS_PORT:-443}:${HTTPS_PORT:-443}`, the same number inside and outside, because Caddy listens on the port of its site address. Postgres has no `ports` and is on `internal` only. `postgres` is the image `postgres:17.12`, the tag that `docker-compose.dev.yml` uses, with the health check `pg_isready -U "$${POSTGRES_USER}" -d "$${POSTGRES_DB}"` (`interval` 5 s, `timeout` 5 s, `retries` 10). `minio` has the health check of the development file (`wget -q -O /dev/null http://127.0.0.1:9000/minio/health/live`, `interval` 5 s, `timeout` 5 s, `retries` 10). `caddy` `depends_on` `server` with `service_healthy`, so a failed migration or a server that does not start never lets Caddy be recreated with the new web image (R13). `storage-init` overrides the image's `entrypoint` (it is `minio`) with `/bin/sh -c`, takes `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` and `MINIO_BUCKET` in its `environment`, and runs `mc alias set` then `mc mb --ignore-existing` (R24). `migrate` and `storage-init` have `mem_limit` 256 MB. Every service has `restart: unless-stopped` except `migrate` and `storage-init` (`restart: "no"`). The forms `${NAME:?message}` and `${HTTP_PORT:-80}` and the service names are the ones the guide's check reads as text (TOKI-087 R16); they stay in these forms. Check: `docker compose config --format json` (with the generated values of R22) is parsed by a test: the set of services, that `caddy` is the only service with `ports`, that `postgres` is on no network but `internal`, the restart values, the Postgres tag equal to the one in `docker-compose.dev.yml`, the health checks, the `depends_on` conditions (including `caddy` on `server`), the `edge` `ip_range` not containing `172.29.0.2`, and the `TOKI_BUILD_ID` argument in both build sections; R22 builds with the two `docker build` commands and starts the stack without a build.
- R11. Each service receives exactly the values its process reads, listed under its own `environment`, and never an `env_file` (concern 2). `apps/server/src/config.ts` exports `entryAreas`, `{ server: [...], worker: [...] }`, the configuration areas that `main.ts` and `worker.ts` load (the areas that exist when this ticket is built; the ticket that adds an area adds it to the list and its names to the service in its own change, and R22 fails when it does not); `main.ts` calls `loadProcessConfig(entryAreas.server)` and `worker.ts` calls `loadProcessConfig(entryAreas.worker)` (the areas of TOKI-064 R17 and TOKI-074 R1: the server loads `webPushPublic`, the worker `webPush`). A name is on a service when its area is in the list of that service's process; a name of another area is not. Names that have a default (`SERVER_PORT`, `SERVER_HOST`, `LOG_LEVEL`, `SMTP_TLS`, `MAIL_FROM_NAME`, `STORAGE_REGION`, `FIRST_ADMIN_NAME`) may be left out. The `migrate` service holds `DATABASE_URL` alone (the area `database`). A name that Compose gives a fixed value (R12) is never read from `.env`; a name the operator supplies is written `${NAME:?NAME is missing in .env}`, so Compose stops and names the first one missing. Check: R22 resolves the environment of every service with the generated values (the pure tests make the same values with `crypto.randomBytes` and `makeVapidPair()`) and asserts, with `loadConfig` of `config.ts`, that the resolved names of `server` load `entryAreas.server`, those of `worker` load `entryAreas.worker`, that no resolved name of a service is outside the names of its areas (`configVariableNames`), and that `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` are on `worker` and on no other service while `VAPID_PUBLIC_KEY` is on `server` and `worker`. Removing one operator name from the generated file makes `docker compose config` fail with that name.
- R12. Values the Compose file fixes, so the operator does not write them and cannot get them wrong: `NODE_ENV=production`; `SERVER_PORT=3000`; `SERVER_HOST=0.0.0.0` (TOKI-004 R18); `DATABASE_URL=postgres://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}`; `APP_ORIGIN=https://${APP_DOMAIN}`; `TRUSTED_PROXY=172.29.0.2` (the address of Caddy, so the per-address limit of TOKI-022 R56 counts the visitor's address and not Caddy's; Caddy sets `X-Forwarded-For` itself and does not trust one that arrives); `STORAGE_ENDPOINT=http://minio:9000`; `STORAGE_PUBLIC_URL=https://${STORAGE_DOMAIN}`; `STORAGE_BUCKET=${MINIO_BUCKET}`; `STORAGE_ACCESS_KEY=${MINIO_ROOT_USER}` and `STORAGE_SECRET_KEY=${MINIO_ROOT_PASSWORD}` (the root account of MinIO, concern 5); `STORAGE_DISK_PATH=/storage-data` (R17, when the area exists); and, on `minio` only, `MINIO_BROWSER=off` and `MINIO_API_CORS_ALLOW_ORIGIN=https://${APP_DOMAIN}` (R19). The password of Postgres goes into a URL, so the guide asks for letters, digits and `-._~` only (a generated hex string); a password with another character makes the `migrate` service fail with exit 1 (an invalid URL or an authentication error, with the text of the library; `migrate-cli.ts` prints "The database cannot be reached" only for connection errors, TOKI-005 R14) before anything else starts. Check: R22 (the resolved values), and the config tests of the server accept the resolved set.
- R13. Migrations run on every `docker compose up`, before the server and the worker. `migrate` runs `node dist/db/migrate-cli.js` and exits; `server` and `worker` `depends_on` it with `condition: service_completed_successfully`, and `migrate` depends on `postgres` with `service_healthy`; `caddy` depends on `server` with `service_healthy` (R10). The migrate command now also creates the queue schema (TOKI-064 R3), so no second step exists. The server does not migrate itself (TOKI-005 concern 4). When `migrate` fails, `docker compose up` stops with its log, and the `server`, `worker` and `caddy` containers of the running release are not recreated (they keep running the old images). If the failure is in the Drizzle step, the database is unchanged (the Drizzle migrator applies all pending migrations in one transaction, TOKI-005 R7); the queue schema step runs after that transaction and is not part of it, so a failure there leaves the new tables in place and the queue schema as it was (it is created idempotently, so the next `migrate` completes it). A rollback to an older tag runs the older `migrate`, which finds nothing pending and changes nothing, because migrations are forward-only and each one stays compatible with the previous image (TOKI-005 concern 10). Check: R22 starts the stack and reads that `migrate` exited 0 before `server` started (the `StartedAt` times); it runs `migrate` a second time and expects exit 0; it starts the stack with a `DATABASE_URL` password the database refuses and expects `docker compose up` to fail with `migrate` in the output and `server` and `caddy` never started.
- R14. The target `web` is the `caddy` image at one exact version (`caddy:2.<minor>.<patch>`, the newest at least two weeks old when the build starts, as for the other libraries) with `/srv` holding `apps/web/dist` and `/etc/caddy/Caddyfile` holding `infra/Caddyfile`. The Caddyfile reads the two host names and the two ports from the environment of the container (`APP_DOMAIN`, `STORAGE_DOMAIN`, `HTTP_PORT`, `HTTPS_PORT`, passed by Compose) and sets Caddy's `http_port` and `https_port` from the last two. Check: `docker run --rm -e APP_DOMAIN=localhost -e STORAGE_DOMAIN=storage.localhost <web image> caddy validate --config /etc/caddy/Caddyfile` exits 0; the same with `APP_DOMAIN` unset exits non-zero.
- R15. Routing for the app host (`{$APP_DOMAIN}`): `/api/*` and `/ws` go to `server:3000`, with the WebSocket upgrade and the `Origin` header passed; everything else is the web app from `/srv`. Caddy sets no read, write or idle timeout below 60 seconds on the server that holds the app host, so it cannot close a connection that is idle for 30 seconds before the 25-second `ping` of TOKI-038 R24 and the 30-second rule of TOKI-038 concern 8 have run. `/healthz` is not routed: it answers 404 from the web app's rule (R16). The server's own 404 and 500 bodies (TOKI-004 R8) reach the browser unchanged for `/api/*`. Check: `caddy adapt` of the Caddyfile gives a configuration whose timeouts are all absent or at least 60 seconds (no timer runs); R22 over HTTPS: `GET /api/v1/nope` returns the JSON `not_found` body of TOKI-004 with status 404; `GET /healthz` returns 404; a WebSocket upgrade at `/ws` with another `Origin` is refused with 403 `origin_not_allowed` (TOKI-038 R4), which proves the upgrade request and the `Origin` header reach the server; an upgrade with the app's `Origin` and no cookie is refused with the error body of TOKI-038 R2, not by Caddy.
- R16. Serving the web app. Rules, in this order: (1) `/api/*` and `/ws` (R15); (2) `/healthz` and `/readyz` (the second is not built): status 404 with an empty body, never `index.html`, decided before the fallback below; (3) `/manifest.webmanifest`: `Content-Type: application/manifest+json`, `Cache-Control: no-cache` (TOKI-077 R1, concern 8); (4) `/icons/*`: `Cache-Control: public, max-age=86400`; (5) `/push-sw.js`: `Cache-Control: no-cache` and a JavaScript content type (TOKI-074 R19); (6) `/assets/*`, the hashed files Vite writes, fonts included: `Cache-Control: public, max-age=31536000, immutable` (TOKI-010 concern 8); (7) `index.html`: `Cache-Control: no-store`, so with the network off a reload shows the browser's own error and never an old page (NFR-06, TOKI-077 R12 and R13; concern 6). A path under (3), (4), (5) or (6) that names no file answers 404 with no body of the app: never `index.html`. Any other `GET` or `HEAD` whose last path segment has no `.` (`/c/<id>`, `/emergency`, `/login`) answers `index.html` with status 200 (the single-page app routes it); one whose last segment has a `.` and names no file answers 404. Rule (2) comes first, so `/healthz` has no `.` and still answers 404 and not the app page. Responses are compressed (`zstd`, `gzip`). Check: R22 and a unit test of `dist`: every file of the built `apps/web/dist` falls in exactly one of the classes (3) to (7) (a file in none fails the test and names the file, so its owner adds a rule); a test of the adapted Caddy configuration that the matcher of rule (2) comes before the fallback; then over HTTPS: the five headers above on a real file of each class; `/icons/missing.png`, `/assets/missing.js`, `/missing.webmanifest` and `/x.js` give 404 and a body that is not `index.html`; `/c/0190aaaa-0000-7000-8000-000000000000` gives 200 and `index.html`; `/healthz` and `/readyz` give 404 and an empty body.
- R17. The server container measures the disk that holds file storage (TOKI-103 R5, when that area exists): Compose mounts the volume `minio-data` read-only into `server` at `/storage-data` and fixes `STORAGE_DISK_PATH=/storage-data`; the same volume is mounted read-write into `minio` at `/data`. Which disk is measured is a proposal: D-191 is Open in the decision log and TOKI-103 concern 1 is not decided (its proposal is the filesystem that holds the file storage); R17 follows that proposal until D-191 is answered, and the mount and the one value are the one line to change if the answer is another disk. A read-only mount of a volume reports the figures of the file system under it. Check: R22 reads `/storage-data` inside `server` and writes a file there, which fails; `df` of `/storage-data` and of `/data` in `minio` report the same size and device.
- R18. TLS and ports. With a real domain Caddy gets and renews its certificates by itself (the ACME HTTP and TLS challenges on 80 and 443) and sends `http://` to `https://`; with `localhost` (and `storage.localhost`) it uses its own local authority, so the stack can be tried on a laptop. HTTP/3 is switched off (`h1` and `h2` only), so exactly the two TCP ports are used (technical design: the firewall opens 80 and 443). The volumes `caddy-data` (certificates and account) and `caddy-config` persist: losing the first would ask the authority for a new certificate on every start and hit its rate limit. Check: R22 opens `https://localhost:<HTTPS_PORT>` and reads a certificate that does not match the system's trust but matches the name; `curl http://localhost:<HTTP_PORT>/` answers 308 or 301 to the `https://` address; after `docker compose restart caddy` the certificate has the same serial number (the volume was kept).
- R19. The storage host (`{$STORAGE_DOMAIN}`, concern 1). Caddy proxies every request to `minio:9000` with the `Host` header unchanged (the signature of an address covers it, TOKI-058 concern 10), and adds to every answer `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox` (TOKI-058 R13, TOKI-062). - R21. Logs. Caddy writes one access log line per request to standard output as JSON, and the line holds no query string and none of the request headers that can carry one or a credential, on either host and on any path. ## Design
### Runtime view
```
Internet ─80/443─▶ caddy (toki-web) ──/api, /ws──▶ server (toki-server) ──▶ postgres
                     │   └─ static files from /srv   worker (same image)  ──▶ postgres
                     │                                 migrate (same image, once) ─▶ postgres
                     └──storage host──▶ minio ◀── storage-init (once: creates the bucket)
networks: edge = caddy, server, minio      internal = server, worker, migrate, storage-init, postgres, minio
```
Only `caddy` publishes ports. Postgres is on `internal` and has no port, so the firewall of the machine cannot be bypassed by Docker for it (Docker publishes ports around a host firewall, so the rule "no `ports` on anything but Caddy" is what keeps Postgres and MinIO private, and R10 tests it).

### Images and stages
```
build   (node:22.<minor>-bookworm-slim, corepack pnpm)
  pnpm install --frozen-lockfile            all workspaces, devDependencies, sharp platform package
  ARG TOKI_BUILD_ID=dev                     one build id for both images (TOKI-104)
  pnpm --filter ./apps/web build            vite build, check:no-dev-pages, check:fonts, check:pwa
  pnpm --filter @toki/server build          esbuild → apps/server/dist
  pnpm deploy --prod --filter @toki/server  production node_modules; node_modules/@toki removed
server  (node:22.<minor>-bookworm-slim)     /app = dist/ migrations/ package.json node_modules(prod)
web     (caddy:2.x.y)                       /srv = apps/web/dist   /etc/caddy/Caddyfile = infra/Caddyfile
```
- The server is compiled and not run through `tsx`: every package of the repository is TypeScript source with `.js` import names (TOKI-004 concern 13), so Node cannot run it as it is, and `tsx` and `pnpm` are development tools. `esbuild` is already in the lock file through `tsx`; bundling the `@toki/*` packages into each entry removes the need to compile them as packages, and leaving the other dependencies external keeps native packages (`sharp`) and the Postgres client loadable from `node_modules`.
- The output keeps the depth of `src/` (`outbase: "src"`, R4), which is what keeps `migrationsFolder` (`../../migrations` from the migrate command) right without a change of that file.
- `sharp` loads its platform package from `node_modules`. The image's platform is the platform of the machine that builds it (`linux/amd64` for the VPS); the lock file must hold the package for it (TOKI-077 R7 says it holds Linux). The check runs `node -e "import('sharp')"` in the image when `apps/server` declares `sharp` (TOKI-060 R13) and fails when it cannot load.

### Errors
- A required name missing from `.env` -> `docker compose` stops before it starts anything and names the first missing name (`${NAME:?…}`).
- A bad value of a name the server checks (R11) -> the server exits 1 with the name on standard error (TOKI-004 R3 and R4); with `restart: unless-stopped` Compose restarts it, so the log shows the name again at each try; `docker compose ps` shows it restarting. Fix `.env`, then `up -d`.
- A migration fails -> `up` stops with the log of `migrate`; the running release is left running, and the database is unchanged when the Drizzle step failed (R13).
- `POSTGRES_PASSWORD` is changed in `.env` after the first start -> the password inside the existing `postgres-data` volume does not change, so `migrate` fails with an authentication error; change it in the database too, or start with an empty volume (which deletes the data).
- Caddy cannot get a certificate (DNS not pointing at the machine, port 80 or 443 closed) -> the site answers no HTTPS and the Caddy log names the failed challenge; nothing else is affected.
- A missing file under `/icons/`, `/assets/` or the manifest -> 404 (R16). A page opened with an old `index.html` after an update asks for a hashed file that the new image no longer holds and gets 404: the client's update notice and reload (D-107, TOKI-104) cover it.

## Testing
- Tests are written first. Pure checks run in the normal `pnpm test` with no Docker: the `dist` classes (R16, from a real `apps/web/dist` built in the test run, or a fixture tree), the shape of the resolved Compose file (R10, R11, R27) made from the YAML with the fake values, the `build.mjs` entry list against a temporary `src/` tree (R4), the `entryAreas` lists (R11), the Node and Caddy tags (R3, R14), the three MinIO tags (R24), the Postgres tag (R10), the memory sum (R23), the inventory against the Compose reads (R26), no secret value in `tools/stack/` (R27), the health check exit codes (R9), the order of the `/healthz` rule in the adapted Caddy configuration (R16), `changed.sh` (R28).
- `pnpm stack:check` is the one check that needs Docker. It builds the images from the commit, so it proves the real image, not a picture of it: the content (R5, R6, R7), the checks of the web build (R2 with its negative control), the stack (R10 to R13, R15 to R21, R23 to R25). It uses the ports 18080 and 18443 and the project `toki-stack-check`, and removes its volumes at the end.
- The negative controls are part of the checks: a broken manifest fails the image build (R2); a missing name makes Compose stop (R11); a refused database password stops `up` at `migrate` (R13); a stale `index.html` header lets the offline reload succeed (R25). Each shows the check can fail.
- No check waits on a timer of the code under test: the idle limit (R15) is read from the adapted Caddy configuration, not measured with a wait; the only waits are the polling of the `server` health status (up to 180 seconds, bounded) and the browser's own load events. Nothing here uses `Date.now()` or a timer in `apps/`.
- Generated values only: no password and no key pair is in a committed file. `tools/stack/names.env` holds names that are not secrets (ports, tag, `example.test` addresses); the script makes every secret at run time into a file of a temporary directory and removes it (R22). The SMTP host points at nothing (the first admin's link is printed by the command, not mailed). The stack check sends no real mail, uses no real domain and never reads or creates the `.env` of the checkout.
- Without Docker only the pure checks run; every requirement that reads "R22" in its check (R5 to R7, R13 to R21 and R23 to R25) is tested by `pnpm stack:check` alone, which needs Docker (and the CI job). That is accepted for an image, and the pull request says it.
- Not proved here: certificates from a real authority (the check uses Caddy's local one); the firewall of a real machine; a real registry pull; the load of 200 people (TOKI-089). The first real install by the guide proves the first (NFR-07, TOKI-087).

## Data safety
- No secret is in an image, an `ARG`, an `ENV`, the Compose file or the repository (R6, R7, R27). A container holds only the values its process reads; the server never holds the private VAPID key (R11).
- Postgres and MinIO have no published port and sit on `internal` (R10). MinIO's console is off (R19). The only exposed ports are 80 and 443 on Caddy.
- The access log holds no query string and no `Referer`, `Cookie` or `Authorization` header (R21), so a signed storage address, a search text or a sign-in token never reaches it; the server's own logger already hides the query (TOKI-004 R7). Docker logs are capped (R21).
- Uploaded files are served from another host with `nosniff`, `sandbox` and `attachment`, and the session cookie does not reach that host (R19).
- Storage uses the MinIO root account (concern 5). The sample data of the prototype is not in the image (R5).
- Nothing in this work backs up the volumes `postgres-data` and `minio-data`: a lost disk loses the data. This is the state D-092 accepts for phase 1.

## Areas of concern
1. The host of file storage. TOKI-058 concern 10 and TOKI-062 require that files are served from a host that is not the origin of the app, and the Blueprint gives no name for it. Decided in this spec: a second host name in the same domain, `STORAGE_DOMAIN` (for example `storage.<domain>`), served by the same Caddy with its own certificate, set as `STORAGE_PUBLIC_URL` by Compose. Reason: a different host is a different origin; the session cookie is host-only (`__Host-`), so it never goes to it; one Caddy and one machine are enough. The operator needs two DNS records pointing at the machine: that is one more line in the existing list of external values (domain, owner Thanh Truong, `docs/environment-config.md`), not a new product question. A sibling host is a different origin and the `__Host-` cookie never goes to it, but it is the same site, so SameSite gives no protection against a request that starts there: the protection rests on `nosniff`, `sandbox` and `attachment` alone, which is what TOKI-058 asks. A separate registrable domain for file storage is the stronger option, left for TOKI-091 to weigh; the Content-Security-Policy of the app (TOKI-091) must allow the storage host for form posts and image loads. Decided in this spec. Owner: Thanh Truong.
2. Where the production values live and who reads what. `docs/environment-config.md` says the place of the production `.env` and where the deploy gets its values are decided in TOKI-085. Decided in this spec, for the part that the images define: Compose reads `.env` and gives each service the names of its own process through `environment` (R11, R27); no `env_file`, because that would give the server the private VAPID key and every secret (TOKI-074 asks that the server container holds only the public key). Reason: least exposure, and the rule is testable. TOKI-085 decides how the file reaches the machine, who may read it and how it is changed; it must not change the names or the rule. The place (next to the Compose file), the mode 600 and the owner are this spec's proposal to TOKI-085 and TOKI-087 (R27), not a decision here. Decided in this spec. Owner: Thanh Truong.
3. Image base. The technical design names no base image. Decided in this spec: Debian slim with Node 22 for the runtime, not Alpine. Reason: `sharp` and its native libraries have the standard platform package for glibc, and the image is the same Linux the builder's CI uses; Alpine saves about 100 MB the 80 GB disk does not need. Caddy uses its own official image. Owner: Thanh Truong.
4. One tag, two images. Decided in this spec: the server image and the web image are built from one commit and carry one tag; Compose starts both from `TOKI_TAG`. Reason: a rollback then restores the web app and the API that were tested together (the client and the server share the data contract, `packages/shared`), and the old hashed files are in the old web image. The cost: a deploy replaces the web files at once, so a tab with the old page may ask for a file that is gone (Errors; TOKI-104's notice). Owner: Thanh Truong.
5. The storage account. Decided in this spec: the server and the worker use MinIO's root account as `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY`, which Compose derives from `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD`. Reason: one MinIO, reachable only on the private network, used by the app alone; a separate service account needs an extra provisioning step (`mc admin`) that a one-person operation would have to remember, and gives no protection while the app is the only client. A later change to a narrower account changes the Compose file and `storage-init` only. Owner: Thanh Truong.
6. Offline and the HTTP cache. NFR-06 asks that with the network off no stale page is served, and TOKI-077 left the production case to this work. Decided in this spec: `index.html` is `no-store`, not `no-cache`, so a browser never keeps a page to show offline; the hashed files and icons may be cached because they are never a page. R25 proves it with a real browser and a negative control. Owner: Thanh Truong.
7. The line with the security review. Decided in this spec: this work owns the Caddyfile, the Compose file and the headers of R20 (the ones no feature depends on: HSTS without sub-domains, `nosniff`, `Referrer-Policy`, `X-Frame-Options`); TOKI-091 owns the Content-Security-Policy, the rate limits, the cookies and the dependency review, and edits the Caddyfile and the app through its own change; the TOKI-091 plan line today reads "Headers, cookies, rate limits, dependencies", so the split is a request to TOKI-091 (Plan changes) until its spec says the same. Reason: a policy for scripts, styles, connections and form targets can only be written with the screens in front of it (the browser posts forms to the storage host and opens a WebSocket), and a wrong one breaks the app. Owner: Thanh Truong.
8. Starting limits. Decided in this spec: the memory limits and stop periods of R23 are a proposal of starting values, each one line, taken from the 4 GB machine of the technical design and from the facts of the merged specs (the worker's decode needs headroom, TOKI-060 concern 5; its grace is 30 seconds, TOKI-064 R15). They are not product figures. The long-running services add up to 3200 MB, which leaves 800 MB for the host, the Docker daemon and a Compose build on the machine; the one-shot services exit before the others start. TOKI-089 replaces them with its measure, and the by-hand measure of TOKI-060 sets the worker's. Owner: Thanh Truong.
9. A command that needs no configuration. Compose stops on the first missing name of `.env` (R11), so the tool that makes the VAPID pair, which has to run before `.env` is complete, cannot run through Compose. Decided in this spec: it runs with `docker run` on the image (Commands table); TOKI-087 writes it in the guide. The image holds no key pair and the private key is not printed to a log. Owner: Thanh Truong.
10. Worker health. The worker has no HTTP port (TOKI-064 concern 8). Decided in this spec: no Docker health check for it; `restart: unless-stopped` restarts it when it exits, and it exits 1 only when it cannot start (TOKI-064 R17); a worker that hangs is seen in `jobs:status` as a growing age of the oldest ready job (TOKI-064 R20). Reason: a check that does not read the queue would say "healthy" for a hung worker, and one that reads it adds a command and a connection for a risk the operator can already read in one command. If the first install shows hangs, a heartbeat check is a later change to the Compose file. Owner: Thanh Truong.
11. The trigger of a deploy. D-190 is open and belongs to TOKI-085. Decided in this spec: nothing here depends on it; the same `docker compose up -d` runs by hand or from a workflow, and the same `TOKI_TAG` selects the release. TOKI-085 owns the build on merge, the registry, the tags, the access to the machine and how `.env` is delivered; this work owns the Dockerfile, the Compose file, the Caddyfile, TLS, the headers, the migration step, the health check, the commands under `src/cli/` and the rule for secrets in the stack. Owner: Thanh Truong.
12. Downtime during an update. One copy of each service runs (technical design, NFR-04), so `up -d` stops and starts `server`, `worker` and, when its image changed, `caddy`: a gap of seconds in which open pages lose their WebSocket and reconnect (the reconnect recovery of TOKI-039). No decision gives an availability target, and the downtime question was deferred with backup (D-092). Accepted as deferred with D-092: no zero-downtime update and no target is promised here, and nothing here sets an availability figure; a migration that is not compatible with the previous image breaks the rollback rule of TOKI-005 and is refused there, not here. Owner: Thanh Truong.
13. Order of the first start. Several services start together: the first admin's set-up runs inside the server after it listens and retries while the tables do not exist (TOKI-020 R18), and `migrate` runs first anyway (R13). Decided in this spec: `migrate` before `server` and `worker`, `storage-init` before them, `postgres` and `minio` healthy before both; a worker that cannot start exits 1 and is restarted (TOKI-064 R17). Owner: Thanh Truong.
14. HTTP/3. R18 switches it off. This is this spec's proposal, not a product decision: with it off, exactly two TCP ports (80 and 443) are used, so the firewall needs one rule pair and no UDP port, which matches the firewall of the technical design (80 and 443) and the guide of TOKI-087 (R4 there). The cost is a little latency on a bad network; turning it on later is the `h3` protocol in the Caddyfile and one UDP 443 rule. Decided in this spec as the proposal until the owner says otherwise. Owner: Thanh Truong.
