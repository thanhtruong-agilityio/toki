# Messages and events tables design

Date: 2026-11-20 · Status: draft for review
Intent: docs/intents/messages-events-tables.md (Thanh Truong)
Ticket: TOKI-036

## Goal
The message API, the gateway, reconnect, file storage and the search index all need the same two things in the database before they can be built: a table of messages that can be read page by page in both directions, and a numbered log of events that a client can use to ask for what it missed.
This ticket builds them: the tables `messages`, `events` and `event_counters`, the two indexes that serve the main list of a conversation and the list of one thread, the one function that writes an event and sends the signal for it (`recordEvent`), the reads of the log (the last number, the oldest number, the events after a number), and the removal of events older than 7 days. The last-number read is used by the bootstrap call, so its `eventNumber` becomes real.
The hard rule is the event number. A client that holds a number that is too high loses an event and gets no error, so the number is taken inside the transaction of the change, from a counter row that stays locked until the commit; events then become visible in number order with no gap (R14 to R19). The second rule is that one function writes every event, so the numbering and the signal cannot be skipped by a caller (Design, "The event contract"). The sibling tickets TOKI-037 and TOKI-038 take their event names, order and signatures from that section.
Nothing on screen changes and no request is added.

## Requirements
- R1. The table `messages` exists after the migrations run on an empty database and is empty. It has exactly these columns: `id`, `workspace_id`, `conversation_id`, `author_id`, `kind`, `system_type`, `system_user_ids`, `body`, `parent_id`, `also_in_channel`, `edited_at`, `deleted_at`, `deleted_by`, `created_at`. Check: a test applies the migrations to a throwaway database and reads the column names, types, nullability and defaults from the Postgres catalog, and counts zero rows.
- R2. `messages.id` is a `uuid` primary key. When the caller passes no id the database client makes a UUIDv7 with the generator that `conversations.id` uses. A caller may pass its own id (the client makes the id of a message it sends, TOKI-037); the table takes it as given and checks no version, because no ordering depends on the id (R12, concern 4). A second insert of an existing id is refused with the unique violation of `messages_pkey`, so a caller can use `ON CONFLICT (id) DO NOTHING` and read the stored row. Check: insert without an id and the 13th hex digit is `7`; insert with an id and it is stored unchanged; insert the same id twice and the second fails with `messages_pkey`; `INSERT ... ON CONFLICT (id) DO NOTHING` leaves one row and the first row unchanged.
- R3. `kind` is required and is `user` or `system` (`messages_kind_check`). A `user` message has a null `system_type` and a null `system_user_ids`. A `system` message has a `system_type` of 1 to 64 characters matching `^[a-z][a-z0-9_]*$` and a `system_user_ids` that is an array of ids (`uuid[]`, possibly empty: "the topic changed" is about nobody); it has an empty `body`, no `parent_id`, `also_in_channel` false, and no `edited_at`, `deleted_at` or `deleted_by` (`messages_system_shape_check`, `messages_user_shape_check`). The table does not hold the list of system types: the system-message writer of TOKI-037 owns it (concern 8). `author_id` is required for both kinds: for a system line it is the person who acted. Check: a valid user message and a valid system line are accepted; each of these is refused by its named check, one at a time: a user message with a `system_type`, a user message with `system_user_ids`, a system line with no type, with a type `Joined`, with no `system_user_ids` (null), with a body `hi`, with a parent, with `also_in_channel` true, with an `edited_at`, with a `deleted_at`; a kind `other`.
- R4. `body` is required text, 0 to 10,000 characters counted in code points like `char_length` (D-042; `MESSAGE_TEXT_MAX`, R22). The empty string is allowed: a message may carry only files, and the table does not know the files; whether a message needs a text or a file is TOKI-037's rule (concern 9). Check: a body of 10,000 characters is accepted; 10,001 is refused (`messages_body_check`); 10,000 emoji (each outside the Basic Multilingual Plane) are accepted and 10,001 refused; the empty string is accepted; no body (null) is refused.
- R5. A thread is one level deep and stays in one conversation. `parent_id` is null for a root message and a system line, and the id of a root message of the same conversation for a reply. The pair (`parent_id`, `conversation_id`) references (`id`, `conversation_id`) of `messages` (`messages_parent_id_fkey`, made possible by the unique constraint `messages_id_conversation_id_key`), so a reply cannot point to another conversation's message. A trigger on insert refuses a reply whose parent is itself a reply or a system line (`messages_thread_depth_trg`). `also_in_channel` is true only for a reply (`messages_also_in_channel_check`): a reply sent also to the channel is one row shown in both places (D-160). Check: a root and a reply are accepted; a reply to a reply, a reply to a system line, a reply whose parent is in another conversation and a reply to an id that does not exist are each refused, with the name of the constraint or trigger; `also_in_channel` true on a root is refused and true on a reply accepted.
- R6. The lifecycle columns. `edited_at` is null or the time of the last edit. `deleted_at` and `deleted_by` are both null or both set (`messages_deleted_check`): a soft delete sets them and keeps the row, so the thread stays (D-013); `deleted_by` is the person who deleted it, equal to `author_id` for the author and another person for an admin, which is how "Message deleted by an admin" is told apart (D-049). `deleted_by` references `users.id`. The table does not decide who may edit or delete (the permission functions of TOKI-027 and TOKI-047 do) and does not empty `body` on delete (TOKI-047). Check: a message with `deleted_at` and no `deleted_by`, and the reverse, are refused; both set is accepted for `deleted_by` equal to the author and for another user; an update that sets `edited_at`, then `deleted_at` and `deleted_by`, succeeds and keeps the row, its thread and its replies; a `deleted_by` that is no user is refused (`messages_deleted_by_fkey`).
- R7. The columns that fix a message's place and origin never change. A trigger refuses an update of `workspace_id`, `conversation_id`, `author_id`, `kind`, `system_type`, `system_user_ids`, `parent_id` or `created_at` (`messages_immutable_trg`); `body`, `also_in_channel`, `edited_at`, `deleted_at` and `deleted_by` may change. Check: for each of the eight columns, an update to a different valid value fails and the row is unchanged; an update that sets a column to the value it has succeeds; an update of the five editable columns succeeds. Each refusal names the trigger.
- R8. A message row is never deleted: a trigger refuses every `DELETE` on `messages` (`messages_no_delete_trg`), because history is kept indefinitely (technical design, data model notes; D-029) and a deletion is the soft delete of R6. `TRUNCATE` is not blocked (R24 needs it). Check: a delete of a user message, of a system line and of a reply is refused and the rows stay.
- R9. Every key is enforced and refuses to delete the row it points to (`ON DELETE RESTRICT`, as in TOKI-019): `messages.workspace_id` references `workspaces.id`; (`conversation_id`, `workspace_id`) references (`id`, `workspace_id`) of `conversations` through `conversations_id_workspace_id_key` of TOKI-028, so a message carries the workspace of its conversation; `author_id` and `deleted_by` reference `users.id`; the parent key of R5. The keys that leave the module are written as SQL in the migration, because a schema file may not import another module's table (TOKI-019 convention 6); the parent key is declared in the schema file. Check: an insert with an unknown workspace, an unknown conversation, a workspace that is not the conversation's and an unknown author is refused, and each error names its key; a read of `pg_constraint` finds every key with `ON DELETE RESTRICT`.
- R10. `created_at` is required, `timestamptz`, written by the server from the clock of TOKI-008, with no database default and no `updated_at` (TOKI-019 convention 3). `edited_at` and `deleted_at` are `timestamptz` with no default. Check: the catalog shows the three columns as `timestamptz` with no default and `created_at` not null; an insert that omits `created_at` fails with a not-null error.
- R11. Two indexes serve the two reads, and the reads need no sort. `messages_conversation_main_idx` is on (`conversation_id`, `created_at`, `id`) where `parent_id is null or also_in_channel`: the main list of a conversation, which holds roots, system lines and replies also sent to the channel. `messages_thread_idx` is on (`parent_id`, `created_at`, `id`) where `parent_id is not null`: the replies of one thread. Both are btree indexes read forward or backward. Check, on a throwaway database holding 20,000 messages over 40 conversations with 2,000 replies: for each of the queries below the test runs `EXPLAIN (FORMAT JSON)` with `enable_seqscan` and `enable_bitmapscan` off and asserts that the plan uses the named index and holds no `Sort` node: the 50 newest of the main list (`order by created_at desc, id desc limit 50`); the 50 before a cursor (`(created_at, id) < ($1, $2)`, same order); the 50 after a cursor (`(created_at, id) > ($1, $2)`, `order by created_at, id`); the same three for one thread with `parent_id = $1`. A query whose `where` leaves out the predicate of the partial index is not tested: the index cannot serve it, and the spec of TOKI-037 must use the predicate as written (Design, "The two reads").
- R12. The order of messages is (`created_at`, `id`), the time the server stored the message and then the id as the tie-break, not the id alone (concern 4). Check: on the database of R11 rows are inserted with only three different `created_at` values and ids in random order; reading the main list of one conversation in pages of 7 with the cursor of R11, first from the newest backward and then from the oldest forward, returns every row exactly once, and the two walks give the same sequence reversed; a message inserted with an id whose time part is in 2001 and a `created_at` of today comes in the place of today's `created_at`, not in 2001. The table does not make the order follow the commit order: a message whose `created_at` is earlier can commit after a message whose `created_at` is later, and that is not decided here (concern 12).
- R13. The table `events` has exactly these columns: `workspace_id`, `number`, `scope`, `conversation_id`, `user_id`, `type`, `payload`, `created_at`; its primary key is (`workspace_id`, `number`) (`events_pkey`). `number` is a `bigint` that the server reads as a JavaScript number, from 1 to 9,007,199,254,740,991 (`events_number_check`), so no number is ever larger than a number the client can hold. `scope` is `workspace`, `conversation` or `user` (`events_scope_check`) and says who the event is for (Design, "Events"): `workspace` has no `conversation_id` and no `user_id`; `conversation` has a `conversation_id` and no `user_id`; `user` has a `user_id` and no `conversation_id` (`events_scope_shape_check`). `type` matches `^[a-z][a-z0-9_.]{0,63}$` (a dot is allowed: the kinds of the gateway read `member.joined`) (`events_type_check`) and `payload` is a JSON object (`events_payload_check`); the list of types and the shape of each payload are the contract of TOKI-038 (concern 2), and the table holds neither. `created_at` is `timestamptz`, written by the server, with no default. The keys: `workspace_id` to `workspaces.id`; (`conversation_id`, `workspace_id`) to `conversations (id, workspace_id)`, which is not checked when `conversation_id` is null; `user_id` to `users.id`; all `ON DELETE RESTRICT`, as SQL in the migration. A trigger refuses every update of an event (`events_no_update_trg`); a delete is allowed, because pruning needs it (R20). There is one more index, `events_created_at_idx` on (`created_at`), for pruning. Check: a test reads the columns and the primary key from the catalog; each scope with each wrong combination of the two columns is refused by `events_scope_shape_check`, and each right one accepted; a number of 0, of -1 and of 9,007,199,254,740,992 is refused; types `Message`, `message created` and a 65-character type are refused and `member.joined` accepted; a payload that is an array, a string or null is refused; an update of any column of an event fails and names the trigger; the foreign keys and their `ON DELETE RESTRICT` are read from `pg_constraint`.
- R14. The table `event_counters` has one row per workspace: `workspace_id` (primary key, references `workspaces.id`, `ON DELETE RESTRICT`) and `last_number` (`bigint`, from 1 to 9,007,199,254,740,991). No migration inserts a row: the row of a workspace is made by its first event, so before it `getLastEventNumber` answers 0, "no event", and the first event is numbered 1 (the rule of TOKI-031 R11). Two triggers keep the numbering from being bypassed. `event_counters_step_trg` refuses an insert whose `last_number` is not 1, an update that does not raise `last_number` by exactly 1, and every delete. `events_number_trg`, before each insert into `events`, refuses a row whose `number` is not the current `last_number` of its workspace's counter row, and a row of a workspace that has no counter row. Check: the migrations leave `event_counters` empty; a counter inserted with 5, an update from 1 to 3, an update from 3 to 2, an update that leaves 3 as it is, and a delete are each refused by `event_counters_step_trg`; an update from 3 to 4 succeeds; an insert into `events` with a number that is not the counter's, with no counter row and with a number lower than the counter's is refused by `events_number_trg`, and an insert whose number equals the counter's is accepted.
- R15. `recordEvent(tx, input)` of `modules/realtime/` is the only function that writes an event. It runs, on the transaction it is given, `appendEvent(tx, input)` (internal to the module, file `append.ts`, not exported) and then `select pg_notify('toki_events', <workspaceId>)`, and returns the event. `input` is `{ workspaceId, scope, conversationId?, userId?, type, payload, at }`, with `at` a `Date` from the clock; the names are the ones of the table (`scope`, `type`, `payload`) and the gateway's frame is the only place that calls them `kind` and `data` (Design, "The event contract"). The notification is sent by Postgres when the transaction commits and is dropped when it rolls back, so a listener learns of an event only when it can read it; the channel is `toki_events` and the payload is the workspace id as text. Both functions take a transaction (the type `Tx` of `db/client.ts`) and not the database: a call with the database does not type-check (a type test with `@ts-expect-error`). `appendEvent` runs two statements: the counter is raised by one with `insert ... on conflict (workspace_id) do update set last_number = event_counters.last_number + 1 returning last_number`, then the event is inserted with that number; `recordEvent` adds the third, the notification. The writing transaction runs at the default `READ COMMITTED`: under `REPEATABLE READ` the raise of a counter row changed by another transaction after the snapshot fails with SQLSTATE `40001`, so every writer of events keeps the default level, and a caller that opens its transaction in another level gets that error and not a wrong number. It returns `{ workspaceId, number, scope, conversationId, userId, type, payload, createdAt }`, `number` a JavaScript number: Postgres returns a `bigint` as a string, so the code converts it with `Number` after the statement, and the column of the schema file is read with the same conversion (`bigint` in `number` mode); the table keeps the number at or below 9,007,199,254,740,991 (R13), so the conversion loses nothing. `conversationId` and `userId` are null when the scope has none. It checks the combination of `scope`, `conversationId` and `userId` as R13 does and throws a plain error before it sends any statement when it is wrong, so no counter is raised for a refused event. It opens no transaction and logs nothing. Check: three calls of `recordEvent` in one transaction return 1, 2, 3 and the rows exist; a first call for a workspace creates its counter row with 1; the returned object has the fields above; a call with `scope` `conversation` and no conversation id throws before a statement is sent (the test counts the statements on the connection) and leaves the counter as it was; the type test fails to compile when the database is passed; a connection that ran `LISTEN toki_events` receives nothing while the transaction is open, receives one notification with the workspace id after the commit, and none after a rollback; a counter row set to 3,000,000,000 and to 9,007,199,254,740,990 returns the next number as a JavaScript number equal to that value plus one (not a string); a transaction opened at `REPEATABLE READ` that read the counter, after which another transaction committed an event, fails in its call with `40001`, and no event is written.
- R16. Events become visible in number order and the last number has no gap. The counter row stays locked from the moment of the first `appendEvent` of a transaction until its commit or rollback, so a second transaction that appends for the same workspace waits, takes the next number only after the first has ended, and a rollback gives its number back. Check, with two real connections and no timer: transaction A appends (number 1) and does not commit; transaction B starts to append and the test waits, by reading `pg_stat_activity` until B's backend shows a lock wait (`wait_event_type = 'Lock'`), not by sleeping; in that state a third connection that reads the counter and the events sees 0 and no event; A commits, B's call returns 2, and a reader sees 1 and event 1 only; B commits, and a reader sees 2 and events 1 and 2. A second case: A appends and rolls back; B's call then returns 1 and the events hold 1 alone. A stress case: 24 transactions on 8 connections each append 1 to 3 events and commit or roll back by a fixed pseudo-random rule with a fixed seed; at the end the numbers of `events` are exactly 1 to M with no gap and no repeat, and the counter is M; and a reader that reads the counter and then all events in one `REPEATABLE READ` transaction, repeated 200 times while the writers run, always finds every number from 1 to the counter it read.
- R17. An event is written in the transaction of its change and in no other. `appendEvent` writes on the transaction it is given, so a rollback removes the change, the event and the raise of the counter together, and a commit keeps all three. Check: in one transaction a row of `messages` is inserted and an event appended, then the transaction rolls back: no message, no event and no counter row remain (and the counter keeps the value it had if it had one); the same with a commit leaves the message, the event and the counter; a failure of the insert of the message after `appendEvent` (a check violation) rolls back the event too.
- R18. A transaction that writes more than one event keeps its numbers together. The calls of one transaction take consecutive numbers, and no other transaction takes a number between them, because the counter row is held (R16). This is what a channel restore by an Admin who is not a member (two changes), a leave that empties a private channel (two changes), and the first message of a direct message (the reveal and the message, Design, "The event contract") need. The ordering rule for locks: `recordEvent` takes the counter row lock and that lock is held until the end, so a transaction takes every other lock first (the account row, the conversation row, the member rows, as TOKI-024 R39 and TOKI-029 R15 order them) and writes its events last. After the first event the transaction takes no lock that can wait, because a transaction that took the counter lock and then waited for a conversation row would wait for one that holds that row and waits for the counter, which is a deadlock. Two things after the counter lock are not locks of that kind and are allowed: the insert of an event takes `FOR KEY SHARE` locks on the `workspaces`, `conversations` and `users` rows through its foreign keys, and the insert of a system line does the same for its own keys. `FOR KEY SHARE` waits only for a transaction that holds `FOR UPDATE` on the row or changes its key. The rule that keeps this true: no ticket takes `FOR UPDATE` on a row of `workspaces`, `conversations` or `users` and no ticket changes the key of those rows (member management R39 already forbids `FOR UPDATE`; `FOR NO KEY UPDATE` and `FOR SHARE` are the allowed levels). Check: A appends twice with a statement of another connection's `recordEvent` started between the two calls: the other call waits and returns 3 only after A's commit, while A's two calls returned 1 and 2; two transactions that each lock the same conversation row with `for no key update` and then append, started together, both finish, with 1 and 2 as numbers and no deadlock error (SQLSTATE `40P01`); and a test that shows where the rule stops being true: transaction B locks the conversation row `for update` and then appends while transaction A has appended, so that A's event insert waits for B and B waits for the counter, and the database ends one of them with `40P01`. That test passes only while the deadlock happens; its name says it documents the rule "no `FOR UPDATE` on these rows".
- R19. `getLastEventNumber(client, workspaceId)` returns `last_number` of the counter row, or 0 when the workspace has no row, with one statement, on the database or on a transaction (`client` is a `DbClient`). It reads the counter, not the largest number in `events`, because pruning can empty `events` while the numbers go on (R20). `readEventNumber` of `apps/server/src/bootstrap/event-number.ts` becomes `readEventNumber(tx, workspaceId)` and returns what `getLastEventNumber` returns for the transaction of the snapshot of TOKI-031 R10, with the workspace id that the handler has already read for its answer (TOKI-031 R4). This is an amendment of TOKI-031 R11 (the function takes the transaction only) and of R14 (the transaction has 7 statements), made by this ticket in code and in tests; the text of those merged specs is not edited (concern 13). The code that changes: the type of the dependency `readEventNumber` in `bootstrap/build.ts` and its call, and `event-number.ts`. The test lines that change: in `tests/bootstrap/build.db.test.ts` the fake `readEventNumber: async (tx) => {...}` takes `(tx, workspaceId)` and records both; in `tests/bootstrap/bounds.db.test.ts` the assertion `toBeLessThanOrEqual(7)` becomes 8, `toHaveLength(7)` becomes 8, the comment that lists the seven statements lists eight (begin, account, accounts by ids, workspace, people, conversations, event number, commit), and a line is added to the reads that matches `from "event_counters"`. The answer holds the real number: `eventNumber` is 0 for a workspace with no event and the last number otherwise. Because numbers are visible in order (R16) and the read is in the snapshot, the answer holds every event up to its number and none after it. Check: a fresh workspace answers `"eventNumber": 0`; after three `recordEvent` calls committed the answer holds 3; the fake of TOKI-031 R11 returns 41 and records its arguments, which are the transaction object and the workspace id; with the seam of TOKI-031 R10 a second connection appends and commits an event after the account read and the answer still holds the number from before (the snapshot), while the next call holds the new one; the statements of the transaction of the route counted by TOKI-031 R14 are 8 for the two fixtures, equal for both.
- R20. `getOldestEventNumber(client, workspaceId)` returns the smallest number still in `events`, or null when there is none. `pruneEvents(db, { before, batchSize? })` removes, for every workspace, the events whose `created_at` is earlier than `before` and every event with a smaller number (the oldest kept events are a whole run up to the last number, with no hole), returns how many rows it removed, never touches `event_counters`, and is safe to run twice or from two copies of the server at once. It works in two steps: one statement reads, for each workspace, the largest number whose `created_at` is earlier than `before`; then, for each workspace, it deletes the numbers up to that one in batches of `batchSize` (default 5,000, a constant of `prune.ts`), each batch its own statement, until a batch removes fewer rows than `batchSize`. So the first run after a long stop does not hold one delete over every row, and a run that is cut off leaves the oldest kept events a whole run. The numbers go on from the counter after a prune. Check: with events created at six different times, a prune with a `before` between the third and the fourth removes the first three and keeps the other three, `getOldestEventNumber` returns 4, `getLastEventNumber` returns 6, and the next `recordEvent` returns 7; a prune that removes every event leaves the counter at 6 and `getOldestEventNumber` returns null; an event with a lower number and a later `created_at` than a removed one (the clock was read before the lock, R18) is removed with it and the kept numbers have no hole; a second prune with the same `before` removes 0; two prunes started together leave the same rows as one; with 7 old events and a `batchSize` of 2 the prune removes 7 and the test counts 4 delete statements on the connection (2, 2, 2, 1), and with a `batchSize` of 7 it counts 2 (7, 0); events of two workspaces are pruned each by its own cut.
- R21. The pruning runs by itself. `startEventPruning({ db, clock, schedule, log })` of the `realtime` module calls `pruneEvents` with `before` = `clock.now()` minus `EVENT_RETENTION_DAYS` (R22), once at the start and then every `EVENT_PRUNE_INTERVAL_MS` (one hour), through the function `schedule(run, intervalMs)` that it is given and that returns a function that cancels it, and returns `stop`, a function that cancels the schedule and resolves when a run in progress has ended. A run that throws is logged with the error and the count 0, never with an event, and does not stop the later runs. `apps/server/src/main.ts` does not run any migration (that is `migrate-cli`); it starts the pruning after `app.listen`, in the way it starts `ensureFirstAdmin` (TOKI-020), with a `schedule` built on `setInterval` whose timer does not keep the process alive (`unref`), and awaits `stop()` in the existing `onClose` hook, before `connection.close()`, so no run uses a closed connection. ## Design
### Data model
`messages` (module `messages`; "Messages" row of the technical design: roots and replies in one table, a client-generated id):
- `id` uuid primary key (R2). `workspace_id` uuid, required: every table carries it (D-004). `conversation_id` uuid, required: the pair with `workspace_id` references `conversations`.
- `author_id` uuid, required, references `users.id`. A deactivated person's messages stay with them (F41).
- `kind` text: `user` or `system` (R3). A direct message, a channel message and a reply are all `user`; the conversation's own kind is in `conversations`, so a message has no copy of it.
- `system_type` text and `system_user_ids` uuid[]: only for `system` lines (R3). A line is stored as a type and the ids of the people it is about, never as English text, so every language gets its own words from translation keys (NFR-05): "Lan added Minh" is `system_type` `members_added`, `author_id` Lan, `system_user_ids` the ids of the people added. The list of types is TOKI-037's, in `packages/shared` (concern 8). Which changes write a line, and which write none, is also theirs: the flows list creation, join, add, leave, a topic or description change and a pin (F22 to F24, D-100, D-165) and no line for an unpin.
- `body` text, required, up to 10,000 code points (R4).
- `parent_id` uuid, null for a root message and for a system line; `also_in_channel` boolean, default false (R5). Reply rows are in the same table, so a reply is a message like any other for the send, the edit and the delete, and the thread's list is one index (R11). The stored reply count is not here (concern 7).
- `edited_at`, `deleted_at` timestamptz, `deleted_by` uuid (R6).
- `created_at` timestamptz, required (R10).
- Constraint, trigger and index names, which the tests assert: `messages_pkey`; checks `messages_kind_check`, `messages_system_shape_check`, `messages_user_shape_check`, `messages_body_check`, `messages_also_in_channel_check`, `messages_deleted_check`; unique `messages_id_conversation_id_key`; keys `messages_workspace_id_fkey`, `messages_conversation_id_fkey` (composite), `messages_author_id_fkey`, `messages_deleted_by_fkey`, `messages_parent_id_fkey` (composite); indexes `messages_conversation_main_idx`, `messages_thread_idx`; triggers `messages_thread_depth_trg`, `messages_immutable_trg`, `messages_no_delete_trg`.

`events` (module `realtime`):
- `workspace_id` and `number` are the primary key. One number runs through the whole workspace, not per conversation, because the client keeps one number (TOKI-031 R2) and asks for everything after it.
- `scope`, `conversation_id`, `user_id` say who the event is for. Decided in this spec (concern 10): `workspace` is for everyone signed in to the workspace; `conversation` is for the people who are members of that conversation at the moment the event is delivered or replayed (membership is the access rule, D-077, D-116, BR-09); `user` is for that person only, on every device. An event for a person who has just been removed from a conversation is a `user` event, because the person is no longer a member when it is delivered. The table stores the scope; applying it, live and on replay, is TOKI-038 and TOKI-039.
- `type` and `payload`: see R13; TOKI-038 owns them.
- `created_at`: the time of the change, from the clock. Pruning reads it (R20).
- Names: `events_pkey`; checks `events_number_check`, `events_scope_check`, `events_scope_shape_check`, `events_type_check`, `events_payload_check`; keys `events_workspace_id_fkey`, `events_conversation_id_fkey` (composite), `events_user_id_fkey`; index `events_created_at_idx`; triggers `events_no_update_trg`, `events_number_trg`.

`event_counters`: `workspace_id` (primary key `event_counters_pkey`, key `event_counters_workspace_id_fkey`), `last_number` (check `event_counters_last_number_check`); trigger `event_counters_step_trg`.

### How the event number stays free of gaps
Bootstrap R11 names two conditions that this ticket owns: (a) an event is written in the transaction of its change; (b) the number a reader sees has no gap that an open transaction can fill. A Postgres sequence fails (b): it hands out numbers in order, but two transactions commit in the other order, so a reader can see number 12 while number 11 is still in flight, and a client that holds 12 would never ask for 11.
The design: a counter row per workspace, raised with a single `insert ... on conflict do update ... returning` inside the transaction of the change. The row lock taken by that statement is held until the transaction ends, so the next transaction that wants a number waits for the commit or the rollback of this one. Therefore numbers are taken one transaction at a time, commit in the order they were taken, and a rollback gives its number back (the raise is rolled back with it). At every instant the committed events are the numbers 1 to N with no hole, and a reader at `REPEATABLE READ` that reads `last_number` sees an N for which all events up to N are visible. Decided in this spec; the alternatives and the cost are in concern 5.
`getLastEventNumber` reads the counter and not `max(number)` of `events` because pruning can leave `events` empty. `events_number_trg` and `event_counters_step_trg` make the database refuse a number that did not come from the counter, so a later ticket that inserts an event by its own SQL cannot break the rule.
The cost: transactions that write an event wait for each other, for the time from the first event to the commit. This is why the lock-order rule of R18 matters, and why a ticket calls `appendEvent` as the last step before the commit and does no slow work (a call to another system, a file) after it. At one server and 200 people (NFR-04) this is short; TOKI-089 measures the 150 ms target (NFR-13) with it in place.

### The event contract
This section is the contract that TOKI-037 (message API) and TOKI-038 (gateway) follow; where their specs say otherwise they change, as listed in "Plan changes". Decided in this spec (concerns 2, 14, 15).

**One path.** Code that changes data does not write events. It calls `recordChange(tx, change)` of `modules/conversations/changes.ts` inside its transaction, after its writes and before the commit, once for each thing that changed. `recordChange` runs a list of handlers in order; each handler is `(tx, change) => Promise<void | { message }>`, and a handler that returns a `message` (the system line of TOKI-037) gives it to the handlers after it as `change.message`. The handler of TOKI-038, which lives in `modules/realtime/`, decides the events of a change and writes each with `recordEvent`. So `conversations`, `members` and `messages` import no `realtime` code and `realtime` imports nothing of them: the list is a parameter, and the one place that builds it and passes it down is `apps/server/src/app.ts`. The list is written by the ticket that first needs it (TOKI-037 changes `changes.ts` into the list and the type `ChangeHandler`; this ticket does not touch the file, R25) and the order is fixed here: first the system-line handler of TOKI-037, which inserts the line row and returns it; last the event handler of TOKI-038, which writes the events of the change and then the `message.created` of the line. A handler added later goes between them or after them by the same rule: a handler that takes a lock runs before the event handler, because the event handler takes the counter lock and no lock follows it (R18). The messages module gets `recordChange` as a dependency from `app.ts` (it is the same function that the channel and member routes get) and calls it for a sent message with the change `message_created`.

**One writer.** `recordEvent(tx, input)` of `modules/realtime/index.ts` (R15) is the only function that writes an event: it numbers the event under the counter lock (`appendEvent`, internal, not exported) and sends the signal `pg_notify('toki_events', <workspaceId>)`, which Postgres delivers at the commit. Nothing outside `modules/realtime/` calls either (R25, tested).

**Field names.** The columns of the log and the input of `recordEvent` are `workspaceId`, `number`, `scope` (`workspace`, `conversation` or `user`), `conversationId`, `userId`, `type` (lower case, dots allowed, `message.created`), `payload` (a JSON object), `createdAt`. The frame the gateway sends to a client calls `type` `kind` and `payload` `data` (TOKI-038 R12; `type` is already the name of the frame itself); the gateway maps them in one place and no other code uses `kind` or `data` for an event.

**One read.** `readEventsAfter(client: DbClient, workspaceId: string, after: number, limit: number): Promise<StoredEvent[]>` (R26), `getLastEventNumber(client, workspaceId): Promise<number>` and `getOldestEventNumber(client, workspaceId): Promise<number | null>` (R19, R20). `readEventNumber(tx: Tx, workspaceId: string): Promise<number>` of the bootstrap code calls the first of these (R19). `StoredEvent` is what `recordEvent` returns.

**The first message of a direct message.** The other person must receive the first message, so the conversation is in their map before the message is delivered. The send calls `recordChange` twice in its transaction, in this order: `direct_conversation_appeared` first, then `message_created`. The event handler writes, for the first, one `conversation.appeared` event with scope `user` for each of the two people (TOKI-038 R20), and for the second one `message.created` with scope `conversation`; the three events have consecutive numbers (R18) and the gateway, which reads the log in number order and updates its map before it delivers an event (TOKI-038 R9), delivers the message to the other person. A group, a channel and every later message write only `message_created`. Nothing else writes `conversation.created` for a direct message.

### The two reads
Both are written by TOKI-037 and must keep the predicate of the index, because a partial index serves a query only when the query implies it.
- Main list: `where conversation_id = $1 and (parent_id is null or also_in_channel)`, ordered by `created_at, id`; older page `(created_at, id) < ($c, $i) order by created_at desc, id desc limit n`; newer page `(created_at, id) > ($c, $i) order by created_at, id limit n`. "Loading around one message" is one older and one newer page from that message's own (`created_at`, `id`).
- Thread: `where parent_id = $1`, same order.
The cursor is the pair, and the pair is compared as a row. Its text form, the page size and the limits are TOKI-037's.
Why not the id alone: a message sent offline is created on the client at one time and stored by the server hours later (D-097, D-132), and the client's clock may be wrong. If the id (UUIDv7, with the client's time in it) were the order, that message would appear in the past, behind messages that arrived since, and a client with a wrong clock could put messages years away. The server's `created_at` is the order everyone sees, and the id only breaks a tie (concern 4).

### What the later tickets get
- TOKI-037: the table and the two reads for send and paging. For the rule that hides a new direct message until its first message (concern 1) it needs "does this conversation have a `user` message" and "the time of the last one", and the main index answers both with one index probe per conversation (`kind = 'user'` added to the probe). The send is `insert ... on conflict (id) do nothing`, and a repeat is told from a clash of ids by comparing the stored row's author and conversation (the same way as TOKI-029 R5 does for channels). It writes the message rows and the system lines of a change, and writes no event itself: it calls `recordChange` with `message_created` (and `direct_conversation_appeared` before it for the first message of a direct message), as the last step before the commit, and the handler of TOKI-038 writes the events through `recordEvent` ("The event contract").
- TOKI-038: it builds the event handler behind `recordChange`, the scope of each event, the event types and payloads and the mapping from a change to its events, in `packages/shared/src/realtime/` and the `realtime` module. It uses `recordEvent` and `readEventsAfter` as they are here and writes neither (its drain reads the log after its position, in batches, in number order, and listens on `toki_events`). Pushing happens after the commit, with the event the call returned. Events become visible in number order, but two pushes after commit can still reach a client in another order, so every event carries its number and the client asks for a missing one (TOKI-039, TOKI-040).
- TOKI-039: `getOldestEventNumber` and `EVENT_RETENTION_DAYS`, to answer a request for events after a number that has been pruned with "reload everything", and `readEventsAfter` for the range read. It adds the audience filter and an index of its own if its query needs one; this ticket adds only the primary key and `events_created_at_idx`, because there is no query yet to measure.
- TOKI-053: it adds the read pointer to `conversation_members`, pointing to a message, and compares positions by (`created_at`, `id`) of the message the pointer names. Its count is the `user` messages of the main list after the pointer whose author is not the person: system lines (D-100, D-165) are `system` and a reply that is not also sent to the channel is outside the list (F14), so both fall out by the predicate of `messages_conversation_main_idx`. A message that commits after another message with a later `created_at` is not counted by a pointer that has already moved past it, and the pointer does not come back; see concern 12, which is open and asks TOKI-053 and TOKI-037.
- TOKI-045: the reply count and the last reply time as columns of `messages` or a view, with its own migration. TOKI-069: the search column and its GIN index. TOKI-058: the `files` and `attachments` tables, which point to `messages.id`. TOKI-047: what a deleted message's `body` becomes. TOKI-050: mentions.

### Errors
No request exists, so there are no HTTP errors. `recordEvent` throws a plain error for a wrong combination of scope and ids (R15). A violation of a table rule reaches the caller as the database error with the name of the constraint, for the request that owns the write to turn into its own answer (as TOKI-029 does for the channel name).

## Open questions from the intent
- Who writes the system lines, the events and the Activity items of a channel change, and what must this ticket give them? Answered: TOKI-037, TOKI-038 and TOKI-065 through `recordChange` (channel API R16, concern 4, decided by Thanh Truong on 2026-11-19); this ticket gives them the system-line columns of R3, `recordEvent` (R15), the scope of an event (R13) and the contract of "The event contract", and edits no code of `recordChange` (concern 2).
- Which ticket hides a new direct message until its first message, and what does it need from the messages table? Answered: TOKI-037 (bootstrap concern 1 and DM API concern 7, decided by Thanh Truong on 2026-11-19); it needs a "has a `user` message" probe and the time of the last message, which `messages_conversation_main_idx` serves (R11; concern 1).
- Which ticket owns the unread data, and what does it need? Answered: TOKI-053 (bootstrap concern 7, decided by Thanh Truong on 2026-11-19); it adds the read pointer to `conversation_members` and needs the order of R12 and the predicate of R11 (concern 3).
- By which order are messages paged? Answered: (`created_at`, `id`), R12 and concern 4.
- How does the event number stay free of gaps when transactions commit out of order? Answered: a counter row locked until the commit, R14 to R19 and concern 5.
- Who removes events older than 7 days? Answered: `pruneEvents` of this ticket, started by the server itself every hour (R20, R21, concern 11).

## Areas of concern
1. Which ticket hides a new direct message from the other person until its first message, and returns the latest message time. Decided: TOKI-037, by Thanh Truong (product owner) on 2026-11-19 in `docs/specs/2026-11-17-bootstrap-endpoint-design.md` (concern 1) and `docs/specs/2026-11-17-dm-api-design.md` (concern 7). This ticket does not build it and puts nothing in the way: the main index gives the probe and the last time per conversation (R11). Whether the rule also covers a group is left by DM API concern 8 to the spec of TOKI-037. Owner: Thanh Truong (product owner, plan).
2. Who writes the system lines, the Activity items and the events of a change, and who writes the event of a message. Decided for a channel change: TOKI-037 (system lines), TOKI-065 (Activity items) and TOKI-038 (events), each as a handler of `recordChange`, by Thanh Truong (product owner) on 2026-11-19 in `docs/specs/2026-11-17-channel-api-design.md` (concern 4). Decided in this spec for the rest: this ticket edits none of the three; one function writes events, `recordEvent`, and nothing outside `realtime` calls it or `appendEvent`; the event of a sent message is written by the same handler, because the send calls `recordChange` with `message_created` (the send does not call `appendEvent`, which the spec of TOKI-037 asked for and now changes), so the call comes last in the transaction (R18) because `recordChange` is called after the writes and before the commit. Reason: the numbering and the signal must live in one place or two writers would number or signal differently, and a writer that skips `pg_notify` would leave the gateway deaf to its event. The event types and payload shapes are one contract in `packages/shared`, owned by TOKI-038. Owner: Thanh Truong (product owner, plan).
3. Who owns the unread data. Decided: TOKI-053, which adds the read pointer to `conversation_members` and the counts to the bootstrap answer or to the store (bootstrap concern 7, decided by Thanh Truong on 2026-11-19; conversation tables, Scope). This ticket holds no pointer and no count; it gives the order (R12), the list predicate (R11) and `kind` (R3) that a count needs. Owner: Thanh Truong (product owner, plan).
4. The order of messages. Decided in this spec: (`created_at`, `id`), with `created_at` written by the server (R12), not the id alone. Reason: the id is made by the client, which may be offline for hours (D-097, D-132) or have a wrong clock; ordering by it would put a late message in the past. The id stays a UUIDv7 for the locality of its primary key and for the server-made ids of system lines, and the table checks no version (R2). TOKI-037 may still check the version of a client's id, as TOKI-029 R4 does for a channel. Owner: Thanh Truong.
5. How the event number avoids gaps. Decided in this spec: a counter row per workspace, raised in the transaction and locked until the commit (R14 to R19). Reason: it is the condition (b) of TOKI-031 R11 and a sequence cannot meet it. Alternatives refused: reading the largest number of `events` under a table lock (the same serialisation, a heavier lock, and pruning empties the table); a sequence with a reader that stops at the first hole (needs the reader to know which numbers are in flight, which it cannot). Cost, accepted: transactions that write an event take turns, and the lock-order rule of R18 follows; TOKI-089 measures it. If one server stops being enough, the counter is the place that changes. Owner: Thanh Truong.
6. Where the tables live. Decided in this spec: `messages` in a new module `messages`, `events` and `event_counters` in a new module `realtime`, as the technical design's module list and its "Realtime: events" group place them; the pruning starter is in `realtime` as well. Reason: the gateway (TOKI-038) belongs to `realtime` and reads `events`; the message API (TOKI-037) belongs to `messages`. The foreign keys to `conversations` and `users` are SQL in the migration (R9, R13), as in TOKI-028. Owner: Thanh Truong.
7. Which columns `messages` has now and which later tickets add. Decided in this spec: the columns that set a message's place, author, text, kind, thread and lifecycle, because the indexes, the checks and the triggers need them (R1). Left to the ticket that keeps them correct, each with its own migration: the reply count and last reply time (TOKI-045: they change with replies, deletes and "also send to the channel"), the search column (TOKI-069), mentions (TOKI-050), the read pointer (TOKI-053, on another table), and the file rows (TOKI-058, on their own tables). Reason: a column nobody writes yet has no test that proves it. The technical design lists the reply count and the search column among the table's contents; they arrive with their tickets, not with this one. Owner: Thanh Truong.
8. How a system line is stored. Decided in this spec: a `kind` of `system`, a `system_type` and a `system_user_ids` array, with no text (R3, Design). Reason: every text goes through i18n (NFR-05), the line's words depend on the viewer's language, and a stored English sentence would never be translated. The table checks the shape, not the list of types, because the writer of TOKI-037 owns the list and a list in a check would force it to edit this migration. Which changes produce a line is TOKI-037's; the wording of each ("Lan added Minh") is a proposal until D-139's rule is met by the screens ticket, TOKI-042. Owner: Thanh Truong.
9. The length of a message and an empty message. Decided: 10,000 characters (D-042). Decided in this spec: counted in code points, like the topic of TOKI-028 R6, and an empty body is allowed by the table (R4). Reason: a message that is only a file has no text, and the table does not see files; the rule "a text or a file" is TOKI-037's. The 10 files per message (D-042) is TOKI-037's and TOKI-058's. Owner: Thanh Truong.
10. Who an event is for, and who reads it back. Decided in this spec: the event holds a scope, `workspace`, `conversation` or `user`, and a conversation or user id (R13); a conversation event goes to the members at the time it is delivered or replayed, and an event for a person who has just left or been removed is a `user` event. The live audience is TOKI-038's; the request that returns the events after a number, its audience filter, its limit and its answer for a pruned number are TOKI-039's, on the unfiltered `readEventsAfter` of R26 (the plan line "fetching what was missed"), which this ticket gives `getOldestEventNumber` for (R20). Reason: the scope is a fact about the event that only its writer knows at the time, and the table must hold it; applying it needs the gateway and the reconnect, which come later. Owner: Thanh Truong.
11. The retention of events and who runs the pruning. Decided in this spec: 7 days, the figure of the technical design ("pruned after 7 days", "after more than 7 days away, the client reloads"), as `EVENT_RETENTION_DAYS`, and `pruneEvents` removes a whole run of the oldest numbers (R20), in batches of 5,000 so that a first run after a long stop does not hold one delete over every row. The run is started by the server every hour (R21), after it listens, because no ticket before the job queue (TOKI-064, M4, needs only TOKI-005) could run it and an unpruned log grows without limit; when TOKI-064 exists it may replace the starter by a queued job without changing `pruneEvents`. Reason for the hour: the retention is in days, and an hourly run is small. Owner: Thanh Truong.
12. A message can commit after a message with a later `created_at`. Not decided; a proposal is marked below, and the word "Accepted" is withdrawn because neither the decision log nor a merged spec decides the trade. The fact: `created_at` is read before the transaction commits, so two sends at nearly the same moment can commit in the other order. The consequence is not for a moment. A client that holds the cursor of the later message never pages to the earlier one until a full reload, and a read pointer that has moved to the later message (TOKI-053) puts the earlier one before the pointer for good, so it is never counted as unread. A connected client still receives both, because the events are numbered in commit order (R16), and a full page load reads the table at one moment; the loss is in the cursor and in the count. Proposal, not decided: the writer of a message takes the counter lock before it reads the clock, so that `created_at` follows the commit order of the workspace; this needs `realtime` to export one more function that takes the lock (a no-op raise is refused by `event_counters_step_trg`, so it would be a `select ... for no key update` of the counter row and a first-event case for a workspace with no row) and a send that takes that lock after its other locks and before it reads the clock; the cost is that sends of one workspace take turns for the whole transaction, which the event write already makes true. The other way is to keep the gap and to give the pointer and the cursor of TOKI-053 and TOKI-037 a rule of their own, for example a pointer that names the event number of the message. Question for Thanh Truong (product owner) with TOKI-053 and TOKI-037: take the clock under the lock, or keep the gap and handle it in the pointer. Owner: Thanh Truong (product owner).
13. The bootstrap function changes its arguments. Decided in this spec: `readEventNumber(tx, workspaceId)` (R19), an amendment of TOKI-031 R11 and R14, which name the function with the transaction only and count 7 statements. Reason: the counter is per workspace (every table carries `workspace_id`, D-004) and the handler already holds the id (TOKI-031 R4), so no second statement is needed to find it; the other way, reading the workspace inside the function, would add a statement and keep the signature. TOKI-031's test that records the argument records both. The builder's code and the lines of the two bootstrap tests that change are listed in R19 and edited by this ticket; the text of the merged spec is not. Owner: Thanh Truong.
14. The one path for events and the handler list. Decided in this spec: "The event contract" of the Design: `recordChange` runs a list of handlers built in `apps/server/src/app.ts`, in the order system lines then events; the event handler of TOKI-038 calls `recordEvent`; `appendEvent` is internal and nothing outside `realtime` calls either. Reason: a rule "every caller of `appendEvent` also sends the signal" cannot be kept by review in three tickets, and the lint rule `toki/module-entry` lets a module import another only through its `index.ts`, so the handler list is the way that `conversations`, `members` and `messages` reach the events without importing `realtime`. Alternative refused: each module calls `appendEvent` itself (TOKI-037 R10 as written), which spreads the lock rule of R18 over every caller. The field names are fixed there (`type`, `payload`, `scope` in the log; `kind` and `data` in the frame) and `readEventsAfter` is built here with one signature (R26). Owner: Thanh Truong.
15. The order of events when a direct message is revealed. Decided in this spec: `conversation.appeared` for each of the two people, then `message.created`, written by the event handler for the changes `direct_conversation_appeared` and `message_created` that the send calls in that order, with consecutive numbers (R18). Reason: the gateway updates its map of a person's conversations when it reads `conversation.appeared`, before it delivers the event after it, so the other person receives the first message; the order `message_created` first would deliver it to nobody who has not got the conversation yet. TOKI-037 R20 (which appends `conversation.created` itself) and TOKI-038 concern 6 (which writes the message first) change to this order. Owner: Thanh Truong.
16. The trigger of the counter accepts a number equal to the counter's. Decided in this spec: `events_number_trg` checks that the number of an inserted event equals the current `last_number` of its workspace and no more. The database cannot tell an insert after a raise in the same transaction from an insert after a raise in an older one, and a later SQL insert that does not raise the counter could reuse the current number only when `events` holds no row of that number, which happens only after a prune removed every event of the workspace. The guard is the rule of R25 (only `recordEvent` writes events, tested by a search of the source) and not the database. Alternatives refused: a check that the counter row was changed in the current transaction (`xmin` against the transaction id) is not stable across the wraparound of transaction ids; keeping the newest event of every workspace in the prune would keep a message copy beyond 7 days. The tests of R14 cover the gap (a number that is not the counter's) and the equal number, and not the reuse. Owner: Thanh Truong.
