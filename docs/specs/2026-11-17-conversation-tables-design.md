# Conversation tables design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/conversation-tables.md (Thanh Truong)
Ticket: TOKI-028

## Goal
The builder needs tables that say which conversations exist and who belongs to them, before the channel API, the direct-message API, the bootstrap call and the messages table are built, a small set of reads so that every other module can ask "is this person a member" and "what are the facts of this conversation" without touching the tables, and the two writes of #general's rows (create it, add a person to it) so that no other module writes these tables.
The tables hold by themselves the rules that application code can get wrong under load or by mistake: unique channel names, one #general (the row named `general`), a kind and privacy that never change, channels that are never deleted, and, for direct messages and groups, one conversation per set of people (a key that is sorted, has no repeated person and has 2 to 8 people) whose member rows are exactly the people in the key, added together and never removed. The group limit of 8 follows from the key.
Some rules stay with the requests that carry them, and the spec says which: who may create a channel or remove a person, the last-member archive (D-051), not leaving #general, and refusing a guest as a member of a direct message (D-050) belong to TOKI-029 and TOKI-030, because they depend on a person's role or on a count of members that the tables do not hold (Design, "What the tables hold and what the requests hold").

## Scope
- In:
  - The tables `conversations` and `conversation_members`, their constraints, indexes and the migrations that create them.
  - The module `apps/server/src/modules/conversations/` with the table definitions and its public functions: one builds the key of a direct message or group (R10, R11), three read membership and the facts that the permission functions of TOKI-027 need (R18, Design, "Reads for other modules"), and two write the rows of #general: `createGeneralChannel` and `addMemberToGeneral` (R25, R26; requested by TOKI-020 and TOKI-024, Design, "Plan changes").
  - The limits, the channel-name pattern, the notification levels and the rule for the level that applies to a member, in `packages/shared`, so server and web use one set of values (R15).
  - The per-member columns for notification level, mute and star (R13, R14), because the Blueprint lists them with these tables and a decision defines each (D-046, D-103, D-143).
  - The database rules for direct messages and groups, for #general and against deleting a conversation (R9, R10, R21, R22), and a test that every table of the accounts and conversation tables can be emptied in one statement (R23).
- Out (not now):
  - The first workspace row and the first Admin, and the call that creates #general at set-up: TOKI-020, which calls `createGeneralChannel` of this ticket and so needs it. The call that adds a person who accepts an invitation to #general: TOKI-024 (`acceptInvitation`), which calls `addMemberToGeneral`; TOKI-097 reaches it through TOKI-024 (Design, "Plan changes"). The migrations create the tables empty.
  - Every request that creates, lists, joins, leaves, edits, archives, restores or adds people to a channel, and the check that only an Admin creates a channel or removes a person: TOKI-029. The last-member rule (D-051) is carried out by the leave request of TOKI-029; see the hand-off in Design.
  - Opening a direct message or group, refusing a guest and handling two people who open the same one at the same moment: TOKI-030.
  - The bootstrap call (TOKI-031). It lists conversations and members with its own read, `listConversationSummaries`, which it adds to this module with its own ticket. It carries no unread count until the read pointer exists: this table holds nothing to count from, so TOKI-031 returns no unread field and TOKI-053 adds it with the pointer. Moving the count from the plan line of TOKI-031 to TOKI-053 is a change to the plan that is not made yet (TOKI-031 concern 7).
  - The read pointer (the message each person has read up to): TOKI-053 adds its column to `conversation_members`, and with it the unread counts and the badge; the New divider is TOKI-054. It points to a message, and the `messages` table (TOKI-036) does not exist when this ticket is built, so TOKI-053 needs TOKI-028 and TOKI-036 (Design, "Plan changes").
  - The request that saves a person's notification level, mute and star, and the Details panel that shows them (TOKI-035): the request is built by TOKI-029, for channels and for direct messages (concern 2). TOKI-031 returns the three values in the bootstrap call (its R7, R8).
  - The messages, events and pins tables: TOKI-036 and later. The accounts tables: TOKI-019.
  - A role per conversation: none exists (concern 7).

## Requirements
- R1. The tables `conversations` and `conversation_members` exist after the migrations are applied to an empty database, and are empty. `conversations` has exactly these columns: `id`, `workspace_id`, `kind`, `name`, `topic`, `description`, `is_private`, `is_general`, `dm_key`, `created_by`, `created_at`, `archived_at`. Check: a test applies the migrations to a throwaway database and reads the column names, types and nullability from the Postgres catalog, and counts zero rows in both tables.
- R2. `conversations.id` is a `uuid` primary key holding a UUIDv7. When a caller passes no id, the database client makes one, with the same default and the same generator as `workspaces.id` (TOKI-005 R8): TOKI-030 and `createGeneralChannel` pass none. A caller may pass its own id: the create-channel request of TOKI-029 (R3, R4) takes a UUIDv7 made by the client, which makes a repeated create the same request (D-111), and checks its version itself. The table checks no version and takes the value as given. Check: insert a conversation without passing an id; the 13th hex digit of the stored id is `7`; insert one with an id passed in, and it is stored unchanged.
- R3. `kind` is required and is one of `channel`, `dm`, `group_dm`. A channel has a name that matches `^[a-z0-9-]{1,80}$` (D-040). Check: insert channels named `qa-team` (accepted), `a` (accepted), a name of exactly 80 characters (accepted), a name of 81 characters, an empty name, `Q&A Team!`, `qa team`, `QA` and no name (each refused by a check constraint; the error names the constraint), and a row with kind `other` (refused).
- R4. Channel names are unique within a workspace, archived channels included (D-040, D-128), and the database refuses the second row also when two transactions insert the same name at the same moment (D-115). Check: (a) insert `launch`, then insert `launch` again: unique violation; (b) archive `launch`, then insert `launch`: unique violation; (c) open two connections, insert `release` in the first without committing, start the same insert in the second, commit the first: exactly one `release` row exists and the second insert fails with the unique violation, not with another error.
- R5. A direct message or group has no name, topic or description, is private, and is never archived: for kind `dm` and `group_dm` the columns `name`, `topic` and `description` are null, `is_private` is true and `archived_at` is null. A channel has no `dm_key`. Check: inserts that break each part (a DM with a name, with a topic, with a description, not private, with an archive time; a channel with a `dm_key`) are each refused by a check constraint, and a valid DM is accepted.
- R6. `topic` is null or 1 to 250 characters (D-101). Check: a topic of 250 characters is accepted; one of 251, and an empty string, are refused; a null topic is accepted. The limit counts code points, as Postgres `char_length` does, not bytes and not UTF-16 units: a topic of 250 characters of Vietnamese text and a topic of 250 emoji (each outside the Basic Multilingual Plane) are accepted, and 251 emoji are refused.
- R7. `description` is null or 1 to 500 characters (concern 1), counted in code points like the topic (R6). Check: a description of 500 characters is accepted; one of 501, and an empty string, are refused; a null description is accepted; 500 emoji are accepted and 501 are refused.
- R8. `kind`, `is_private`, `is_general`, `dm_key` and `workspace_id` cannot be changed after the row is created (D-040, D-045): an update that changes any of them is refused. An update of `topic`, `description` and `archived_at` is accepted. Check: for each of the five columns, an update to a different valid value fails and the row is unchanged; updating the topic, the description and `archived_at` to a time and back to null succeeds; an update that sets a column to the value it already has succeeds. Each refusal names the trigger `conversations_immutable_trg`.
- R9. #general is the conversation with `is_general` true, and it is the channel named `general`. A row with `is_general` true is a public, active channel named `general`, and a channel row named `general` has `is_general` true (D-034). Because the name is unique per workspace (R4), a workspace has at most one such row, and no other channel can take the name first. Check: a general row that is a DM, that is private, that has an archive time, or whose name is not `general` is refused (`conversations_general_shape_check`, `conversations_general_name_check`); a channel named `general` with `is_general` false is refused (`conversations_general_name_check`); an update that sets `archived_at` on the general row is refused (so #general cannot be archived); a second general row in the same workspace is refused (`conversations_workspace_id_name_key`); a general row in a second workspace is accepted; a channel that is not general may be archived. A later ticket that allows renaming changes the name check in its own migration; phase 1 has no rename (D-105).
- R10. A direct message or group has a `dm_key`, a channel has none. The key is the people's ids: lowercase UUID text, sorted in byte order (collation "C"), each id once, joined by commas (D-045, D-086, F25). Kind `dm` has a key of 2 ids, kind `group_dm` of 3 to 8 ids. The database checks the shape, the order, that no id repeats and the count (`conversations_dm_key_shape_check`, `conversations_dm_key_order_check`, `conversations_dm_key_size_check`); the order check calls an immutable SQL function written in the migration. `dm_key` is unique within a workspace. Check: a DM with a key of 2 sorted ids is accepted; the same two ids in the other order (`b,a`) is refused by the order check; `a,a` is refused (a DM with oneself, and a repeated id); `a,b` next to `a,b` is refused by the unique constraint, also when the two inserts run in two transactions at the same moment (as in R4 (c)); a DM with 3 ids and a group with 2 ids are refused; a group with 8 ids is accepted and one with 9 ids is refused; ids in upper case, ids that are not UUIDs, an empty id, a trailing comma and spaces are refused; a channel with a key and a DM or group with a null key are each refused. Sorting in byte order agrees with the default sort of JavaScript for lowercase UUID text (all characters are ASCII), which R11 proves.
- R11. A function `buildDmKey(userIds)` of the module returns `{ kind, key }` for a list of ids: the kind is `dm` for 2 people and `group_dm` for 3 to 8, and the key is the one R10 describes. The same people in any order, in upper or lower case, give the same result. It refuses a list with fewer than 2 different ids (messaging yourself is not supported, F25), a list with a repeated id, a list with more than 8 ids, and a value that is not a UUID. Check: unit tests for each case, including that `[a, b]` and `[b, a]` give one key, that `[a, b]` and `[a, b, c]` give different keys, and that a key of 8 people passes while 9 is refused; and a database test that inserts the DM built from `[a, b]`, then tries `[b, a]` and fails with the unique violation of R10; and a test that builds the key of 200 random sets of 2 to 8 ids and inserts each (with its member rows, R21) without a constraint error, so the sort in the function and the sort in the database agree.
- R12. `conversation_members` has exactly these columns: `conversation_id`, `user_id`, `workspace_id`, `notification_level`, `is_muted`, `is_starred`, `created_at`. The primary key is (`conversation_id`, `user_id`), so a person is a member of a conversation at most once; the table only joins two others, so it uses the composite key that convention 1 of TOKI-019 allows instead of an `id` (concern 8 (g)). A person is a member exactly while a row exists: leaving deletes the row (concern 5). There is an index on `user_id` for "the conversations of this person". Check: a test reads the columns and the primary key from the catalog and finds `conversation_members_pkey` on the two columns; inserting the same pair twice is refused; the index `conversation_members_user_id_idx` is listed.
- R13. `is_muted` and `is_starred` are required booleans, false by default (D-143, D-103). They belong to one row, so one person's value does not change another member's. Check: insert two members of one conversation, set `is_muted` and `is_starred` on the first; the second row still holds false for both.
- R14. `notification_level` is null or one of `all`, `mentions`, `none` (the labels 'All messages', 'Mentions only', 'Nothing'; the stored values are the keys of the prototype's Details panel). Null means "the default for the conversation's kind": `mentions` for a channel, `all` for a direct message or group (D-046). The function that turns the stored value into the level that applies is in `packages/shared` (R15), because the web app needs it too. Check: a database test refuses the value `loud` and the value `nothing`, accepts the three values and null (`conversation_members_notification_level_check`).
- R15. `packages/shared` exports `CHANNEL_NAME_MAX` (80), `CHANNEL_NAME_PATTERN`, `CHANNEL_TOPIC_MAX` (250), `CHANNEL_DESCRIPTION_MAX` (500), `GROUP_DM_MAX_PEOPLE` (8), `NOTIFICATION_LEVELS` (`all`, `mentions`, `none`), `isValidChannelTopic(value)`, `isValidChannelDescription(value)` and `effectiveNotificationLevel(kind, level)`. `isValidChannelTopic` accepts null or a string of 1 to `CHANNEL_TOPIC_MAX` code points (it counts with `Array.from(value).length`, never `.length`). `effectiveNotificationLevel` returns the stored level when there is one and the default of R14 otherwise. The server and the web app use these, and the server does not re-export them. The database constraints and these values agree. Check: unit tests: `('channel', null)` gives `mentions`, `('dm', null)` and `('group_dm', null)` give `all`, and `('channel', 'none')` and `('dm', 'mentions')` give the stored value; one database test runs the same list of names, topics and group sizes through the exported values and through inserts, and both accept and refuse the same items, with the boundary cases 80 and 81, 250 and 251 and 500 and 501 (letters and emoji), 8 and 9.
- R16. Every foreign key is enforced and refuses to delete the row it points to (`ON DELETE RESTRICT`, as in TOKI-019): `conversations.workspace_id` references `workspaces.id`; `conversations.created_by` and `conversation_members.user_id` reference `users.id` (the table `users` of TOKI-019, in `modules/members`); `conversation_members.workspace_id` references `workspaces.id`; and (`conversation_members.conversation_id`, `conversation_members.workspace_id`) references (`conversations.id`, `conversations.workspace_id`), which a unique constraint `conversations_id_workspace_id_key` on those two columns makes possible, so a member row always carries the workspace of its conversation. The constraints are named `<table>_<column>_fkey`. Check: for each of the five, an insert with an id that does not exist is refused with a foreign-key violation naming the constraint and with existing ids is accepted; a member row whose `workspace_id` is another existing workspace than the conversation's is refused by `conversation_members_conversation_id_fkey`; a test reads `pg_constraint` and finds all five with `confdeltype = 'r'` and these names; deleting a `users` row and a `workspaces` row that a member row points to fail with the constraint name. The same copy for the user's workspace is not checked by a key, because the `users` table of TOKI-019 has no key on (`id`, `workspace_id`) and this ticket does not change it: the writer copies it, phase 1 has one workspace, and the gap is accepted (concern 8 (h)).
- R17. Both tables have `created_at`, a timestamp with time zone, required. Following the server-table conventions of TOKI-019 (Design, "Conventions for server tables") the server writes it from the clock of TOKI-008 and the database gives no default; the same holds for `conversations.archived_at`, a nullable timestamp with time zone that the server sets when a channel is archived and clears when it is restored (D-029). There is no `updated_at`. Every table has `workspace_id` (Blueprint data model notes). Check: a test reads the catalog: the three time columns are `timestamptz`, have no column default, and `created_at` is not null; an insert that omits `created_at` fails with a not-null error naming the column.
- R18. The table definitions are in `apps/server/src/modules/conversations/schema.ts` and are not exported from the module's `index.ts`. This ticket exports six names and their types: `buildDmKey`, `getConversationFacts`, `isConversationMember`, `listMemberIds`, `createGeneralChannel` and `addMemberToGeneral`, so no other module reads or writes these tables (TOKI-002 rules 2 and 17). Other tickets add their own names to the same module (`channelRoutes`, `directRoutes`, `listConversationSummaries`), so the export test is one list of names in one file, `exports.test.ts`, that every ticket extends in its own change: it checks that each name of the list is exported and that no export is a table definition of `schema.ts`; it does not check that nothing else is exported. The reads and the mapping to the facts of TOKI-027 are in Design, "Reads for other modules"; the two writes are R25 and R26. Check: the export test passes with the six names of this ticket and still passes when another ticket adds a name to the list; a test that adds `conversations` or `conversationMembers` (the table objects) to the exports fails it; `pnpm lint` exits 0; database tests of the three reads: `getConversationFacts` returns the facts of the mapping table for each of the kinds (public channel, private channel, DM, group, #general, archived channel) with the actor a member and not a member, and null for an id that does not exist; `isConversationMember` is true and false; `listMemberIds` returns every member id of a conversation and an empty list for none.
- R19. One migration, `<number>_conversation_tables.sql` made with `pnpm db:generate --name conversation_tables` (TOKI-019 convention 8; the file name is exactly `<number>_<slug>.sql`), creates both tables, the functions and the triggers of R10, R21 and R22, and no other table. It changes no existing table and no row. It applies to a database that already holds the TOKI-005 and TOKI-019 migrations and keeps the TOKI-005 rules: forward-only, nothing that the previous release cannot run on. Check: the TOKI-005 test of applying all migrations to an empty database passes with the new file, the tables exist afterwards (R1), a test reads the migration file and finds two `CREATE TABLE` statements with these names (it does not say that no other table exists, as in TOKI-019 R1), and the tests of TOKI-019 pass unchanged after this migration.
- R20. No row is inserted by the migrations. In particular #general is not created here (TOKI-020). Check: the R1 count of rows is zero after a migration run.
- R21. The members of a direct message or group are exactly the people in its key, and they never change. A trigger on `conversation_members` refuses an insert for a `dm` or `group_dm` conversation when `user_id` is not one of the ids in its `dm_key`, refuses every delete of such a row, and refuses an update of `conversation_id`, `user_id` or `workspace_id` of any row; and a constraint trigger that runs at the end of the transaction (deferred) refuses a `dm` or `group_dm` conversation whose number of member rows is not the number of ids in its key. The group limit of 8 follows from R10. A channel's member rows are not limited by these triggers (a channel has any number of members). Check: with a DM of `a,b`: inserting a member row for `c` is refused; inserting `a` and `b` in one transaction and committing is accepted; inserting only `a` and committing is refused at commit; deleting the row of `a` is refused; an update of `user_id` is refused; an update of `is_muted` is accepted; a group of 8 with its 8 rows commits and a group of 8 with 7 rows does not; deleting a member row of a channel and changing its `notification_level` are accepted. Each refusal names its trigger (`conversation_members_fixed_trg`, `conversations_members_complete_trg`).
- R22. A conversation is never deleted: a trigger refuses every `DELETE` on `conversations` (D-029), for a channel with members, a channel with none (the channel whose last member left) and a DM; `TRUNCATE` is not blocked, which R23 needs. Check: each of the three deletes is refused and names `conversations_no_delete_trg`; the rows are still there.
- R23. All tables of the accounts and conversation tables can be emptied by one `TRUNCATE` that names them (`workspaces`, `users`, `login_codes`, `sessions`, `devices`, `conversations`, `conversation_members`) with no `CASCADE`, because Postgres refuses a `TRUNCATE` of a table that other tables point to unless they are all named. Check: insert one row in each (the helper of R24 for the first five) and run that statement; all seven are empty. The emptying step of the test harness (TOKI-008 R6) must empty every table of the `public` schema except the migration journal in one statement, or list these two names; see "Plan changes".
- R24. No test of this ticket imports another module's table. Rows of `workspaces` and `users` come from the helper `apps/server/src/db/test-rows.ts` of TOKI-019 (R26 of that spec), which inserts by SQL, and rows of `conversations` and `conversation_members` are inserted by SQL text in the tests. Check: a search of the files of this change finds no import of `modules/members` or of another module's `schema.ts`.
- R25. `createGeneralChannel(tx, { workspaceId, createdBy, createdAt })` inserts the #general row and the member row of its creator in the caller's transaction, and returns the conversation id. It is the only code that writes the fixed values of #general: kind `channel`, name `general`, public, `is_general` true, no topic, no description, no archive time, no key, the id from the database default (R2); the member row has `notification_level` null, not muted, not starred, `created_at` = `createdAt`. It opens no transaction of its own. A second call for a workspace that has a #general fails with the unique violation `conversations_workspace_id_name_key` and leaves no member row. Check: a database test calls it with a row of `workspaces`, a row of `users` and a fixed time, and reads back both rows column by column; a second call for the same workspace fails with the constraint named and the member count stays 1; a call for a second workspace succeeds; an unknown `createdBy` fails with `conversations_created_by_fkey` and nothing is written; the first Admin's row makes `isConversationMember` true and `getConversationFacts` report `isGeneral` true (the check of TOKI-020 R17).
- R26. `addMemberToGeneral(tx, { workspaceId, userId, createdAt })` inserts a member row for `userId` in the #general of `workspaceId`, with the same defaults as R25, and returns `true` when it added the row and `false` when the person already was a member (an insert with `ON CONFLICT (conversation_id, user_id) DO NOTHING`; the row that exists is not changed). It throws a plain error naming the workspace when the workspace has no #general, and writes nothing then. It opens no transaction of its own. Check: a database test adds a person (`true`, the row has the defaults and `created_at` = `createdAt`); a second call returns `false` and the row, including its `created_at`, is unchanged and still one; the member row of another person is untouched; a workspace with no #general throws and writes nothing; an unknown `userId` fails with `conversation_members_user_id_fkey`; two calls for the same person on two connections at the same moment leave one row and no error; the person is in #general of their workspace and not in another workspace's.

## Design
### Data model
`conversations` (server module `conversations`, Blueprint "Conversations" row: kind, private flag, archive time):
- `id` uuid primary key, UUIDv7 (R2).
- `workspace_id` uuid, required, references `workspaces.id`. There is one workspace in phase 1; the column keeps the path to several (D-004).
- `kind` text, required: `channel`, `dm`, `group_dm`. A direct message and a group are different kinds because the Blueprint draws them differently (a DM row has an avatar, a group a group icon) and because the group limit is not the DM size. Text with a check constraint, not a Postgres enum: adding a kind later is a one-line constraint change, while an enum value cannot be removed.
- `name` text. Channels only (R3, R5). Unique per workspace with one plain unique constraint on (`workspace_id`, `name`); the pattern allows lowercase only, so no case-folding index is needed (R4). Null names do not collide.
- `topic` text, null or 1 to 250 characters (R6). Channels only (R5). The server maps an emptied topic to null.
- `description` text, null; shown under About in the Details panel next to the topic and edited by any member (D-105, F24). Null or 1 to 500 characters, with a check constraint (R7, concern 1); the server maps an emptied description to null.
- `is_private` boolean, required, default false. A channel is public or private from creation (D-040); a DM and a group are always private (R5), which matches "visible only to members" (BR-09).
- `is_general` boolean, required, default false. It marks #general (D-034). Always a public, active channel named `general`, and the only channel with that name (R9). The unique name (R4) makes it at most one per workspace, so there is no separate unique index for it. The flag is kept next to the name because the lists and the permission facts read the flag (`isGeneral`), and because a later rename ticket then changes one named check instead of every reader.
- `dm_key` text, null for channels, required for DMs and groups (R10). Rule: the ids of the people, in lowercase, sorted in byte order, each once, joined by `,` (R10). Decided in this spec: plain text and not a hash, so constraints can check its shape, order and size, and a person can read it when debugging (at most 8 ids, 295 characters). The database refuses a key that is not sorted or repeats an id, so `b,a` cannot sit next to `a,b` and a DM with oneself cannot exist whatever the caller does. The key is built by `buildDmKey` (R11) in the same transaction that inserts the member rows, and the database checks at commit that the member rows match it (R21).
- `created_by` uuid, required, references `users.id`: the Admin who created the channel or the person who started the DM; shown as "creator" under About (F24).
- `created_at` timestamptz, required, written by the server (R17). Shown as the creation date under About.
- `archived_at` timestamptz, null while active; written by the server. Only channels are archived (R5); #general never (R9). A channel archived keeps its name (R4) and its members, and its messages stay readable (D-029, F26).
- Constraints (names listed under "Constraint and index names"): kind values, channel shape, direct-message shape, name pattern, topic length, description length, general shape and general name, `dm_key` shape, order and size by kind, unique (`workspace_id`, `name`), unique (`workspace_id`, `dm_key`), unique (`id`, `workspace_id`) for the member foreign key.
- A trigger on update refuses a change of `kind`, `is_private`, `is_general`, `dm_key` and `workspace_id` (R8). The server has no request that changes them (TOKI-029, TOKI-030); the trigger holds the rule if a later change forgets it. The name has no trigger: "no rename" is a phase-1 choice of the API (D-105), not a rule of the data.
- A trigger refuses every delete of a conversation (R22): channels are archived, never deleted (D-029). Without it the foreign key from the member rows would protect only a channel that still has members, and a channel whose last member left has none.

`conversation_members`:
- `conversation_id` uuid; `user_id` uuid references `users.id`; together the primary key (R12). `conversation_id` and `workspace_id` together reference `conversations (id, workspace_id)` (R16).
- `workspace_id` uuid, required, references `workspaces.id`. A copy of the conversation's workspace, kept because every table carries it; the composite key makes the database refuse a copy that differs from the conversation's (R16); the code that inserts a row copies it from the conversation.
- `notification_level` text, null or `all` / `mentions` / `none` (R14). Null follows the default of the conversation's kind (D-046) and is turned into a value by `effectiveNotificationLevel` of `packages/shared`. Decided in this spec: null and not a stored default, because the default depends on another table's `kind` (a column default cannot read it) and because the rule then lives in one function instead of in every insert path (TOKI-029, TOKI-030, #general at set-up, accepting an invitation).
- `is_muted` boolean, default false: hides the unread badge and bold, and stops toast, push and sound (D-103). The level `nothing` only stops toast, push and sound. `is_starred` boolean, default false: moves the conversation to Starred in that person's list (D-143). Both are personal (D-143, AC-138).
- `created_at` timestamptz, required, written by the server (R17): when the person joined. No `updated_at`.
- Indexes: the primary key serves "members of this conversation" and its count; the index `conversation_members_user_id_idx` on `user_id` serves "conversations of this person" (the bootstrap call of TOKI-031).
- Triggers (R21): for a direct message or group the member rows are exactly the people of the key, are inserted together and are never deleted or moved.
- Membership is the access rule: a person reads and writes a conversation only while a row exists (D-077, D-116, BR-09). Leaving deletes the row (concern 5). Private channels need no other flag for this; a public channel is not readable without a row either (D-116).
- No role column: the capability table has roles per workspace, not per conversation (D-090, concern 7).

### Foreign keys across modules
Drizzle's `references()` needs the other table's definition, and lint stops a module importing another module's table file (R18). The key inside the module (the composite key from `conversation_members` to `conversations`) uses Drizzle's `foreignKey`. Decided in this spec: this keeps one rule for every module and needs no table exported across modules. The snapshot does not list the hand-written statements, so the next `db:generate` does not remove them; R8, R9 and R16 prove they exist. See concern 8.

### Reads for other modules
No other module imports the tables (R18), so this module exports the reads that the others need, and the two writes of #general's rows (R25, R26). Each takes the database client or transaction of TOKI-005 as its first argument and returns plain values.
- `getConversationFacts(db, actorId, conversationId)` returns the facts that the permission functions of TOKI-027 need, as its type `ConversationFacts` (imported from `packages/shared`), or `null` when the conversation does not exist. One query reads the conversation and the actor's member row. The caller answers `null` as "not found". The mapping is written once here, in `facts.ts`, and tested:

| :---- | :---- |

### Hand-offs
- TOKI-029 (channel API): the leave request deletes the member row and, for a private channel (concern 3), sets `archived_at` when none is left, in the same transaction. It first locks the conversation row (`select ... for no key update`, as TOKI-029 R15 does), because two last members leaving together would otherwise each see the other and archive nothing. The mode is `for no key update` and not `for update`: the foreign key of a member row takes `for key share` on the conversation row, which `for update` blocks, so `addMemberToGeneral` for a newcomer would wait on an unrelated edit; `for no key update` still excludes another writer of the same channel. A public channel is not archived when it empties (concern 3). Any Admin restores an archived channel that has no member, or no Admin among its members, and becomes its member (concern 10).
- TOKI-029 maps the unique violation of R4 to the "name exists" answer to the second person (D-115) and turns an emptied topic into null.
- TOKI-030 (DM API): builds the key with `buildDmKey` and inserts the conversation and all member rows in one transaction (R21 checks them at commit); it inserts with `ON CONFLICT (workspace_id, dm_key) DO NOTHING` and then reads the row, so two people who open the same DM at the same moment get the same conversation and nothing is inserted twice, and it treats a unique violation of the key as "open the existing one". It refuses a guest (D-050) and a list that `buildDmKey` refuses.
- A DM appears in the other person's list only after the first message (F25). Both member rows are written when the DM is opened (decided in this spec, concern 6); the rule that hides an empty DM from the other person needs `messages` (TOKI-036), so TOKI-031 and TOKI-033 cannot build it first. No ticket owns it yet; TOKI-037 (the message API, whose first send makes the DM appear) is proposed and not decided (TOKI-030 concern 7, TOKI-031 concern 1). Until then M2 shows a new DM to both people from the moment it is opened.
- A deactivated person keeps their member rows: the same account returns with its channels (D-094, F41). Nothing here removes them; the read-only DM is a rule of the DM and message tickets. Member counts and the last-member rule ignore them (concern 9).
- TOKI-020 (first Admin and #general) calls `createGeneralChannel` (R25), which inserts the #general row and the member row of the first Admin. TOKI-024 calls `addMemberToGeneral` (R26) inside `acceptInvitation` (its R20 step 8) for each person who accepts an invitation; TOKI-097 calls `acceptInvitation`. Both callers need this ticket (Plan changes).
- TOKI-031 (bootstrap) reads the person's conversations with its own `listConversationSummaries`, which it adds to this module, and returns no unread field until TOKI-053 (Scope). It does not use a read of this ticket for the list.

### Errors

## Data safety
- The tables hold no message text and no personal data beyond the ids of people. Membership is the access rule for private channels, direct messages and groups, so every later query that returns a conversation or its content goes through `isConversationMember`, `getConversationFacts` or a join on `conversation_members` inside this module (BR-09); the table and the index on `user_id` are made for that. The facts of a conversation are read together with the actor's membership, so a caller cannot get the first without the second.
- A private channel's name, topic and description are visible to its members only: the tickets that list channels (TOKI-034) must filter on membership; nothing here lists them.
- Tests use fake ids and names and never touch the development database (TOKI-008 R4, R16).
