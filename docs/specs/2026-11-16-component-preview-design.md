# Component preview page design

Date: 2026-11-16 · Status: draft for review
Intent: docs/intents/component-preview.md (Thanh Truong)
Ticket: TOKI-016

## Goal
The builder needs one page that shows every component, icon, font and token of the design system together, in Calm and in Focus, so that the milestone M1 exit check "the component preview page matches the prototype in Calm and Focus at all three layouts" can be done by a person who did not build the components, and can be repeated after any later change. For this page "all three layouts" is read as in Design, "The three layouts": the components are compared on this page at the window widths of R16 and R21, and the layouts of the AppShell on the fixture of TOKI-015.
After this change `apps/web` has a second page, served in development only, that renders what `@toki/ui-web/examples` lists (the components of TOKI-012, TOKI-013 and TOKI-014), the 43 icons, the seven font faces and the 32 tokens; a browser test checks what a machine can check; and the pull request records the rest, which is compared with the prototype by eye, state by state.

  - Keeping the page out of the production build, and a check that proves it: the script `check:no-dev-pages` that this ticket and TOKI-015 share (R2).
  - The list of what the page must show, counted from the specs of TOKI-009 to TOKI-014 (Tables A, A2, B1 and B2), and the record of where each piece is in the prototype (`references.ts`).

Two `devDependencies` for `apps/web` (R7).
- Out (not now):
  - The components, the icons, the fonts and the tokens: TOKI-012, TOKI-013 and TOKI-014 (components and their `examples` files), TOKI-011 (icons), TOKI-010 (fonts), TOKI-009 (tokens). This ticket adds no file under `packages/` and edits no shared file of theirs (R19).   - The AppShell, its three layouts and the bottom tabs: TOKI-015. The page is drawn beside the shell, not inside it (Design, "Beside the shell"). The page does not load the shell's `app.css` or `utilities.css` (Table E).
  - Placement of toasts above the composer and the bars: TOKI-013 R29 and the tickets that register those elements. The page does not register any.
  - Test harness, Playwright configuration and CI workflow: TOKI-008 and TOKI-007. This ticket adds one test file that those pick up (TOKI-008 R12) and edits no configuration.
  - Comparing screenshots with the prototype, Storybook or any other new tool. The one screenshot test of this ticket, R24, compares the page with its own committed images and not with the prototype (concern 5, Design, "What 'matches the prototype' means here").
  - Copying the prototype into the repository: the Blueprint stays outside the repository (TOKI-095 spec, concern 4).
  - A text catalogue for the page (R18).

- R4. The page has three controls, each a native `select`: look (`calm`, `focus`), accent (`teal`, `indigo`, `clay`, `violet`) and density (the look's own, `comfortable`, `compact`), with the values of `looks`, `accents` and `densities` of `@toki/tokens` (TOKI-009 R1). The page sets `data-eff` and `data-accent` on the root element to the chosen look and accent, and `data-density` to the chosen density, with its own function `applyControls` in `controls.ts`: it does not call the `applyAppearance` of TOKI-015 R28, as TOKI-015's Scope says ("TOKI-016 has its own function for its controls and does not call it"), and the attribute rules are the same in both (an unknown value gives the default; a missing density removes `data-density`); for "the look's own" it sets no `data-density` (TOKI-009 R14: Calm then shows Comfortable and Focus Compact). It sets `data-eff` always, so the device's light or dark setting never decides the look. Changing a control changes the attributes at once with no reload and writes the three values to the address as `?look=&accent=&density=` with `history.replaceState`. Opening an address with those values applies them; a missing or unknown value gives `calm`, `teal` and "the look's own". The page writes nothing to `localStorage`, `sessionStorage` or a cookie. Check: a Vitest test of the pure function `readControls(search)` (valid, missing, unknown and repeated values) and the browser test (change each control and read the three attributes and the address; open `?look=focus&accent=clay&density=compact` and read them).

### What "matches the prototype" means here
Decided in this spec. The prototype is a single HTML file outside the repository (TOKI-095, concern 4), it draws no sheet of components, and no spec in this repository sets up a screenshot tool: TOKI-008 brings Vitest and Playwright (one sample test, Chromium) and says nothing of screenshots. (Concern 5 later adds R24, a screenshot test of the page against its own committed images; it guards against later change and is not the comparison with the prototype.) A screenshot comparison with the prototype would also need a reference image that does not exist, and a baseline made from this page would only prove that the page does not change. So "matches" is made of two checks, each with its limit.

1. The machine check (R2, R6 to R16, R20, R23). It runs in CI in the end-to-end job of TOKI-008. It proves: the page lists every component and every state that the specs oblige the examples to draw (Table B1 is the prototype's own class names and attributes); the 13 overlay examples open and close (R23); nothing on the page fails or logs an error; in both looks the browser draws the colours that the specs resolved from the prototype (Table C), through the real load order of the style sheets; accent and density reach the components; the narrow-screen rules of TOKI-012 hold at 719 and 720 px; the seven declared font faces are loaded by the browser on this page (R10); the page does not scroll sideways at the six window sizes of R16. It does not prove: that the tables of TOKI-009 and TOKI-012 equal the prototype (those tests prove the CSS equals the tables, and the tables equal the prototype only by review, TOKI-012 concern 11); anything about a property that Table C does not list (spacing, type size, shadow, line height); hover, active and focus-visible states; Safari and Firefox.
2. The by-eye comparison (R21). The reviewer, a person who did not write the component compared, opens the page and the prototype side by side in the same window size, Calm then Focus (the prototype's Look control is on its demo bar, D-145), and walks through Table A with Table D's lines open: the components at 360 by 560, 720 and 1100 px, the overlays opened at five widths, the accents and densities, and one run in Safari and one in Firefox for D-108. The result goes in the pull request in the four tables of R21, each row saying "matches" or naming the difference and whether it is accepted. The main comparison is done in Chrome, which the machine check also uses; a native `select` and a focus ring look different in each browser and are accepted (TOKI-012 concern 15). It proves that a person looked at each named state; it does not prove pixel equality.

States the prototype does not draw cannot be compared with it, only with the specs: the error box under a field and the invalid, disabled and read-only controls (TOKI-012 concern 1), the disabled link button, the disabled chip, switch, icon button and select, the Away dot's grey ring on a profile (TOKI-013 Design, PresenceDot), the one-word initials, and the toast at 360 px. ### Beside the shell
Decided in this spec. The page does not render inside the AppShell. The shell fills the window, needs the router, the sign-in state and the data of the app, and sets layout rules (`#root`, the content area, `--tabh`) that would change how the components are placed; the page's job is to show components alone, on a `--surface` panel, so that what differs from the prototype is the component. The page therefore needs from TOKI-015 nothing at all. TOKI-015 agrees and says it once (its Scope): "The page and this ticket do not depend on each other: the page keeps its own function for the look controls (TOKI-016 R4 and R19 list only five imports from `@toki/ui-web`, none of them `applyAppearance`), and `applyAppearance` here serves the app. A later change may make the page call it; that is not asked of either ticket." So the page sets `data-eff`, `data-accent` and `data-density` itself, with `applyControls` in `controls.ts` (a few lines), under the attribute rules of TOKI-015 R28 and TOKI-009. If a later change makes the page call `applyAppearance`, that change adds the need on TOKI-015 and the import to R19. The shell mounts the one `ToastProvider` of the app (TOKI-013); the page mounts its own, because it has no shell (R12). The page registers no toast anchor and no element to avoid, so its toasts sit 20 px above the window's bottom edge (TOKI-013 R27); the placement against a composer and the tab bar is checked by TOKI-013 R29 and the tickets that register them.

### The three layouts
Decided in this spec, adopting TOKI-015 (Design, "The three layouts"), which says what "three layouts" means once: Calm (the wide sidebar), Focus (an icon rail, and on Home a conversation column) and the narrow layout under 720 px (one pane at a time and the bottom tabs), the technical design's "Three layouts, one component set" (D-068 gives the widths, not the three names). "The widths at which the shell changes are 719/720 and 1099/1100; the shell is measured at 360 by 560, 719, 720, 800, 956, 1099, 1100 and 1400 px (R33), and TOKI-016 may quote this paragraph for its own reading of the exit check ...: the layouts are checked on the fixture of this ticket, the components on the preview page." This spec reads the exit check of the plan ("the component preview page matches the prototype in Calm and Focus at all three layouts") the same way: the exit check is met by two comparisons together, the components on this page (R14 to R16, R21) and the shell's layouts on the fixture of TOKI-015 (its R18 to R22, its by-eye record). No single place covers the sentence, so the plan line is reworded (plan change, concern 4). Components change only at 719 px (TOKI-012 R8), and the overlays place themselves by the window (TOKI-014 R29), so the sizes of this page are the shell's widths that matter for components: 360 by 560, 719, 720, 1099, 1100 and 1400 px by machine (R16), and 360 by 560, 720 and 1100 px by eye, with the overlays also at 719 and 1099 (R21).
The page has one look at a time, chosen by a control, and not two looks side by side: the tokens select a look by an attribute on the root element (TOKI-009), so two looks cannot share a document, and two frames of the page would add a second mode for the same result. The width is the browser window's, and has no control, because the component CSS reads the viewport (TOKI-012, Table I note) and not a container.

### Dev only
The page is a builder's tool and is not in the production build (R2). The mechanism: Vite builds only the inputs it is given, and `apps/web` gives it `index.html` only (TOKI-006 sets no `input`); `preview.html` sits in the project root next to `index.html`, so the dev server serves it and the build ignores it, with no flag, no route and no change to the code-defined router of TOKI-006 R3. Nothing that the app imports imports the page (R19), so its code and `@toki/ui-web/examples` never enter a chunk of the app. `check:no-dev-pages` (R2) proves it on every build, for this page and for the fixture page of TOKI-015.
Whether the page ships is not decided by the Blueprint (concern 1); this spec builds to the proposal that it does not.
