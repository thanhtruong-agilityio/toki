# Threads design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/threads.md (Thanh Truong)
Ticket: TOKI-045

## Goal
A member needs to answer one message without adding a line to the whole conversation, and to see at a glance which messages have answers. The message tables already have `parent_id` and `also_in_channel` (TOKI-036), and the message API sends and lists top-level messages only (TOKI-037, TOKI-040). This work adds the reply: the server side (send a reply, list the replies of one message, keep the reply count, the last reply time and the first three repliers on the root message, tell the other screens), the client side (the thread windows and the reply send in the sync engine) and the screen (the thread panel with its address, the reply box with "Also send to #name", and the reply line under a message).
The hard rules are three. A reply that is not also sent to the channel never enters the main list and never moves a direct message in the list. A reply is sent exactly once, with the same id rules as any message. The reply count is stored, and changes in the transaction of the reply, so a list of 50 messages needs no count query (technical design: "stored reply count").

  - `apps/web`: the thread route and its address, the shell slot, the thread panel, the reply box, the reply line `.tlink`, the root deleted state, the texts (R16 to R24).
- Out (not now), with the owner:

The sync engine's windows, queue and outbox: TOKI-040 (this work extends them additively, R12, R13; concern 7). The gateway: TOKI-038 (this work adds one row to its table of events, R8).

  - Edit, delete and the "Message deleted" line and its admin variant: TOKI-047, which also decides what a deleted reply does to the thread (concern 2). Pins: TOKI-048 (only messages of the main list can be pinned, D-166). Reactions: TOKI-046 (they work on a reply in the panel through `patchMessage`, R15). Mentions: TOKI-050. Text formatting: TOKI-049.
  - Who follows a thread, the thread items of Activity, their badge, and a muted conversation's rule (D-174): TOKI-065. This work stores nothing about followers (Design, "What the later tickets get").
  - Unread counts and the read pointer: TOKI-053 (it counts the main list only, so a reply that is not also sent to the channel is outside by the index predicate). Drafts that sync across devices and the "Draft" label: TOKI-051. Thread summary by AI and every phase 6 item.
  - Page size of the lists: TOKI-037 concern 1 (this work reads the same two constants).

## Requirements
Server: the stored summary
- R1. The table `messages` gains three columns in one migration made with `pnpm db:generate --name thread_summary` (TOKI-019 convention 8): `reply_count` (`integer`, not null, default 0, `messages_reply_count_check`: 0 or more), `last_reply_at` (`timestamptz`, null, no default) and `reply_user_ids` (`uuid[]`, not null, default empty array, `messages_reply_user_ids_check`: at most 3 elements). The check `messages_thread_summary_shape_check` says: `reply_count` is 0 exactly when `last_reply_at` is null; and a row with a `parent_id` (a reply) has `reply_count` 0, no `last_reply_at` and an empty `reply_user_ids`, so only a root carries a summary. The migration inserts no row and changes no other table; `messages_immutable_trg` (TOKI-036 R7) is not changed and does not list these columns, so they stay writable. It is forward-only (TOKI-005). Check: the migration test of TOKI-005 passes; the catalog shows the three columns with their types, nullability and defaults; each check refuses a bad row (a count of -1, a count of 1 with no time, a time with a count of 0, four ids, a reply with a count of 1) and accepts a good one; an update of the three columns of a root succeeds, and an update of `body`, `parent_id` and the other columns keeps the rules of TOKI-036 R7; `pnpm db:generate` run again reports no change; exactly three `ADD COLUMN` statements and no `CREATE TABLE` are in the file.

Server: send a reply
- R2. The send of TOKI-037 (`POST /api/v1/conversations/{id}/messages`) accepts two more keys, as TOKI-037 R4 allows: `parentId` (a lower-case UUID; optional) and `alsoInChannel` (a boolean; optional, `false` when absent). The body stays strict: every other key is 400 `validation_failed`. `alsoInChannel: true` with no `parentId` is 400 `validation_failed`. `alsoInChannel: true` in a conversation that is not a channel (a `dm` or a `group_dm`) is 400 `validation_failed` (proposal, concern 1: D-161 is open, and its proposal is "channels only, as in the prototype"; if the owner answers otherwise only this sentence changes). The text rules of TOKI-037 R4 (1 to 10,000 code points, white space only, U+0000, lone surrogates) apply to a reply unchanged, and the stored text is the text as sent. Check: a body with `parentId` and `alsoInChannel` is accepted; `alsoInChannel: true` without `parentId` is 400 and stores nothing; with `parentId` in a `dm`, a `group_dm` and a channel the answers are 400, 400 and 201 (this check follows the proposal of concern 1); `alsoInChannel: "yes"`, `parentId` in upper case or not a UUID, and an unknown key are 400; the boundary texts of TOKI-037 R4 give the same results for a reply.
- R3. The rules of a reply, in the order of TOKI-037 R1. Steps 1 to 5 (schema, facts, `canReadConversation`, the locks, the lookup of the id) are those of TOKI-037. A repeat is a repeat as TOKI-037 R5 says (same conversation, same author, a message): it answers 200 with the stored row and writes nothing, whatever `parentId` and `alsoInChannel` the repeated request carries (they are not compared, as the text is not). For a new id, step 6 is: (a) the post rule and the read-only rule of TOKI-037 R6 and R7, so a reply into an archived channel is 409 `channel_archived` for everybody and into a direct message with a deactivated person is 409 `conversation_read_only`; (b) then, when `parentId` is given, the lookup of the parent inside the same locks: `select id, conversation_id, kind, parent_id from messages where id = $parentId and conversation_id = $conversation`. A parent that does not exist in this conversation (no row, or a row of another conversation) is 404 `not_found` with the body of an unknown conversation (nothing about the other conversation is confirmed). A parent that is itself a reply, or a system line, is 400 `validation_failed` (a thread is one level deep, FR-33; the screen never offers it, so this is a guard; Decided in this spec, concern 5). A parent that is deleted (`deleted_at` set) is accepted: the reply is stored, and the thread keeps its place under the "Message deleted" line (D-013, D-096). Check, in a channel: a reply to a root is 201 and the row has `parent_id` and `also_in_channel` as sent; a reply to a reply is 400; a reply to a system line is 400; a reply to an id with no row and to a message of another conversation are each 404 with the same body as an unknown conversation; a reply to a root that was soft-deleted (set by SQL) is 201; an archived channel gives 409 for a reply; a repeat of a reply sent with other flags gives 200 and the stored row; a person who is not a member gets the refusals of TOKI-037 R2 before any parent lookup (the statement log shows no read of `messages` for the parent).
- R4. The thread summary is kept in the transaction of the reply. After the insert of a reply and before any call of `recordChange`, one statement updates the root row: `reply_count = reply_count + 1`, `last_reply_at = greatest(last_reply_at, $at)` with `$at` the `created_at` of the reply (the time of TOKI-037 R3), and `reply_user_ids` with the author appended when the author is not in it and it holds fewer than 3 (so it lists the first three different people who replied, in the order of their first reply; the prototype's reply line shows the same people). The statement takes the root row `FOR NO KEY UPDATE` through the update itself; it is the only lock this work adds, it comes after the conversation lock of TOKI-037 R8 and before the first `recordChange` (the counter lock of TOKI-036 R18, after which no lock may follow), and no code of this work locks a `messages` row before the conversation row. A rollback after it leaves the old summary. Check, with real connections and no sleep: ten replies by three people give `reply_count` 10, `last_reply_at` the latest `created_at`, and `reply_user_ids` the first three authors in order; two replies to one root at the same moment give 2 and both answer 201, with no deadlock (SQLSTATE `40P01`); a reply and a soft delete of the root (an update of `deleted_at` and `deleted_by` by SQL on a second connection) at the same moment end with both applied and a count of 1; a handler that throws after the update leaves the root's summary as it was and no reply row; the statement log of a reply shows the update after the insert and before the first call of the recording handler, and no locking statement after that call.
- R5. A reply and the main list. A reply with `alsoInChannel` false is not in the main list of TOKI-036 R11: `GET .../messages` of TOKI-037 does not return it, `listLastMessageTimes` (TOKI-037 R19) does not count it, and the unread predicate of TOKI-053 leaves it out, all by the predicate `parent_id is null or also_in_channel` that this work does not change. A reply with `alsoInChannel` true is in the main list as one message (D-160): `GET .../messages` returns it in its place by `created_at`, with its `parentId` and `alsoInChannel: true`; `lastMessageAt` of a `dm` or `group_dm` counts it; the message component draws it as a normal message with no mark (the prototype posts it as a plain message, line 2234; D-160). Check, with replies inserted through the route: a reply with the flag false is absent from the history of the conversation and `listLastMessageTimes` returns the time as before; with the flag true it is present, once, and the time becomes its `created_at`; the same reply is in the replies of R6 in both cases; the row count of `messages` after a reply sent with the flag true is one more than before (one message, not two).
- R6. `GET /api/v1/conversations/{id}/messages/{rootId}/replies` lists one thread. Steps 1 to 3 of TOKI-037 R1 apply (schema, facts, `canReadConversation`); no lock. The query keys are those of TOKI-037 R11: `limit` (the same constants `MESSAGE_PAGE_DEFAULT` and `MESSAGE_PAGE_MAX`) and at most one of `before`, `after` and `around`, each the id of a reply of this thread. The answer is 200 `{ "root": MessageEntry, "messages": MessageEntry[], "hasOlder": boolean, "hasNewer": boolean }`, `messages` oldest first, ordered by (`created_at`, `id`) and paged exactly as TOKI-037 R12 and R13 say, with `where parent_id = $root` so that `messages_thread_idx` serves it with no sort (TOKI-036 R11). `root` is the entry of the root as the table holds it now, summary included, deleted or not. `rootId` must be a user message of this conversation with no `parent_id`: a system line, a reply, another conversation's message and an id with no row are 404 `not_found` with the body of an unknown conversation. An anchor that is not a reply of this thread is 404. A deleted root still answers, with its replies. Archived channels answer for members (reading is allowed). Check: a thread of 120 replies read backward by pages of 20 gives every reply once and ends with `hasOlder` false, and forward with `after` the same; `around` follows the two-sided rule of TOKI-037 R13; a thread with no reply answers an empty list with both flags false; a reply to the root that was also sent to the channel is in the thread once; two cursors, an unknown key and `limit` 0 are 400; the four 404 cases; the replies of a deleted root load; the `EXPLAIN` of the three queries uses `messages_thread_idx` with no `Sort` node (as TOKI-036 R11 tests them); a person who is not a member of a private channel gets 404 and of a public channel 403 before any read of replies.
- R7. The entry and the send answer. `MessageEntry` of TOKI-037 R15 gains four keys, as it says later work may: `alsoInChannel` (boolean, true only for a reply), `replyCount` (integer, 0 or more), `lastReplyAt` (`null` or ISO 8601 UTC) and `replyUserIds` (an array of 0 to 3 ids). They are read from the columns of R1 and `also_in_channel`, so a root carries its summary in every answer that returns it (history, the replies route, the answer of a send) and a reply carries 0, `null` and an empty array. `packages/shared` also exports `ThreadSummarySchema` (`{ rootId, replyCount, lastReplyAt, replyUserIds }`, strict) and the response schema of R6. The send answer of a reply (201 and 200) is `{ "message": MessageEntry, "thread": ThreadSummary }`, with the root's summary as it stands when the answer is made; the answer for a root message stays `{ "message": MessageEntry }` with no `thread` key. Check: schema tests accept a root with a summary, a reply and a thread answer, and refuse an added key, a missing key, four user ids and a `replyCount` of -1; every 200 and 201 body of the tests of R2 to R6 is parsed with the response schema; a send of a root has no `thread` key; the tests of TOKI-037 that built a `MessageEntry` are updated with the four keys in this change and pass.
- R8. Telling the other screens. A reply calls `recordChange` twice in its transaction, as the last statements and in this order: first `message_created` (TOKI-037 R10, `message` the entry of the reply, which TOKI-038 turns into `message.created` with `{ message }` and the reply's `parentId`), then `thread_updated`, a new change type of `conversations/changes.ts` with the fields `conversationId`, `actorId`, `at` and `thread` (a `ThreadSummary`). The event handler of TOKI-038 gains one row in its table of changes: `thread_updated` writes one event `thread.updated`, scope `conversation`, payload `{ conversationId, rootId, replyCount, lastReplyAt, replyUserIds }`, whose schema this work adds to the registry of event kinds in `packages/shared/src/realtime/` (TOKI-038 R12 allows a kind added within a version). The two events have consecutive numbers (TOKI-036 R18). A repeat, a refusal and a reply that rolls back call `recordChange` zero times. The change `thread_updated` is also what R9's function is meant to be used with. Check, with a recording handler as in TOKI-037 R10: a reply makes two calls in this order with the fields above and `thread` equal to the `thread` of the 201 body; a repeat and every refusal make none; with the real event handler (the test of this work, as TOKI-038 R20 tests its own rows) the log holds `message.created` then `thread.updated` with consecutive numbers, and the payload of the second parses with its schema; a rolled-back reply leaves no event.
- R9. `recomputeThreadSummary(tx, rootId)` of the `messages` module (exported from its `index.ts`) sets the three columns of a root from the replies that exist and are not deleted: `reply_count` is the number of replies with `deleted_at` null, `last_reply_at` the latest `created_at` among them (null when there are none) and `reply_user_ids` the first three different authors in order of their first reply, and returns the `ThreadSummary`. It is for TOKI-047 (a delete of a reply) and for a repair; this work's own send does not call it (R4 is incremental). It takes the root row `FOR NO KEY UPDATE`, as R4 does. Check: after ten replies by the send, the function returns the same values as the incremental columns; after a reply is soft-deleted by SQL it returns a count of 9 and the new last time and authors; with no replies it returns 0, null and an empty array; a property test of 200 random sequences of replies and deletes by SQL compares it with a direct count query.
- R10. Safety and shared values. A reply and the replies route log no text and no id list beyond the request line (TOKI-037 R23). The registry of error codes gains no code (`validation_failed`, `not_found`, `forbidden`, `channel_archived`, `conversation_read_only`, `message_id_in_use` are reused). `packages/shared/src/messages/` exports the new keys and schemas of R7 and the response schema of R6. Nothing of this work calls `appendEvent` or `recordEvent` (TOKI-036 R25). Check: a forced constraint failure on a reply with a known text leaves that text out of the captured log; a grep test finds no call of `recordEvent` or `appendEvent` in the files of this work; a type test imports every new name from `@toki/shared`.

Client: windows and sending
- R11. The API client (TOKI-032 R9, TOKI-040 R2) gains two things. `api.messages.send(conversationId, body, signal?)` takes `body` `{ id, text, parentId?, alsoInChannel? }`, sends exactly the keys it is given, and returns `{ status, message, thread? }` read with the schema of R7 in the form that drops unknown keys. `api.messages.replies(conversationId, rootId, query?, signal?)` sends `GET /conversations/{id}/messages/{rootId}/replies` with `limit`, `before`, `after` or `around` only when given (never two positions) and returns `{ root, messages, hasOlder, hasNewer }`. The path parts are encoded; the 10-second rule and the error kinds are those of the existing core. Check: with the fake `fetch` of the API tests, each call sends the method, path, query and body as written; a send with no reply keys sends exactly `{ id, text }` as before; an answer with an extra key keeps it; a failed answer ends as an `ApiError`.
- R12. Thread windows. The sync engine (TOKI-040) keeps, next to its windows of main lists, one window for each thread that a screen has loaded, keyed by the id of the root. `getThread(rootId)` returns a `ThreadWindow`: the `MessageWindow` of TOKI-040 R3 (`status`, `error`, `items`, `hasOlder`, `hasNewer`, `isLoadingOlder`, `isLoadingNewer`, `stale`) plus `conversationId` and `root` (`MessageEntry` or `null` until the first answer); the empty window of an unknown thread is one frozen object with `root` null. `subscribeThread(rootId, listener)` is called for the changes of that thread only. `loadThread(conversationId, rootId)`, `loadThreadOlder(rootId)`, `loadThreadNewer(rootId)` and `loadThreadAround(conversationId, rootId, replyId)` call `api.messages.replies` with no position, `before` the oldest held reply, `after` the newest, and `around`; they never reject and obey TOKI-040 R5 and R6 for order, duplicates, identity, the merge table, flags, the "no request for a ready window with `hasNewer` false" rule and the events kept aside during a head load; every answer also sets `root`. The code is the windows module of TOKI-040 given a key and a loader, not a copy. `reload()` of TOKI-040 R19 marks thread windows `stale` with the others, and `reset` drops them. Check: the tests of TOKI-040 R3 to R5 are run again on a thread window (shuffled input, duplicates, 120 replies in pages of 20, a deferred page with an event in flight, a stale window replaced and not merged, the model test of the contiguous range); `getThread` twice gives `===` objects; a change in thread `a` calls the listener of `a` only; `root` is set by the first answer and replaced by the next one; a second `loadThread` on a ready window sends no request.
- R13. Sending a reply. `send(conversationId, text, reply?)` of TOKI-040 R7 gains the optional third argument `reply` `{ parentId, alsoInChannel }`; with none it behaves as before. The pending item gains `parentId` (`string | null`) and `alsoInChannel` (boolean). A pending reply is an item of the thread window of its `parentId` (after the confirmed replies, in press order), not of the main window; when that window does not exist it is made (status `idle`, root null) so the item shows, and when it is `stale` or has `hasNewer` true `send` starts `loadThread` as TOKI-040 R7 does for the main list. The queue of TOKI-040 R8 is one queue for each conversation, replies and top-level messages together, in press order; the request is `api.messages.send(conversationId, { id, text, parentId, alsoInChannel })`; the states, Retry, Delete and the single automatic try (TOKI-040 R10, R11) are those of any message. The stored text of TOKI-040 R12 gains the optional keys `parentId` and `alsoInChannel` on an item (an item without them is a top-level message, so a text written by an earlier build is valid; the `version` stays 1), and a restored reply goes back to its thread window. Check: with the fake `api`, a reply sent with `alsoInChannel` true calls it with exactly those keys; the pending item is in the thread window synchronously and not in the main window; a top-level `send` calls it with `{ id, text }` as before; two sends in one conversation, one a reply, are sent in press order one at a time; an offline reply waits and is sent when the status is `online`; the outbox text of a waiting reply holds its keys and restores it into the thread window after a new engine starts; a stored text with no reply keys is restored as a top-level message; a 409 `channel_archived` makes the reply `failed` with that error.
- R14. What confirms and what an event does. (a) A send answer for a reply (201 or 200) replaces the pending item by the message in the thread window (TOKI-040 R4 placement rule: a window that is `stale` or has `hasNewer` true keeps the item while the `loadThread` runs), and applies the answer's `thread` to the root (rule (c)). When `alsoInChannel` is true it also places the message in the main window by the rule of TOKI-040 R16 step 3, and calls `setLastMessageAt` with its `createdAt` (a no-op for a channel, TOKI-040 R18). (b) An event `message.created` whose message has a `parentId` is not placed in the main window by the engine (TOKI-040 R16, concern 9 there). The handler of this work, registered with `registerEventHandler("message.created", ...)` (TOKI-040 R18), acts as follows: a pending item with the id of the message is replaced; the message is placed in the thread window of its `parentId` by the same rule (it fills an empty place and never replaces a held message; an event that comes while a `loadThread` or `loadThreadAround` runs is kept aside and put through the rule afterwards, as TOKI-040 R5 says); when `alsoInChannel` is true it calls `tools.placeMessage(conversationId, message)` and `tools.setLastMessageAt(conversationId, message.createdAt)`. A reply with `alsoInChannel` false never touches the main window or the list time. (c) An event `thread.updated`, registered the same way, sets `replyCount`, `lastReplyAt` and `replyUserIds` on the root: through `tools.patchMessage(conversationId, rootId, update)` for the main window and on `root` of the thread window; it is applied only when `replyCount` is not lower than the held one (an event older than a page that already holds a newer count changes nothing, and a repeated event changes nothing); a root that is not held anywhere changes nothing. Check: a reply from another person in a ready thread window and a ready main window is placed in the thread window and not in the main window; the same with `alsoInChannel` true is placed in both and raises the list time of a `dm` entry and not of a channel entry; a replay of the same event leaves one message; an event for an unloaded thread changes no window; the answer of the own send replaces the item, and the event after it changes nothing (one reply in the window); the event before the answer does the same; `thread.updated` raises the count on the main window's root and on the thread's `root`, with one listener call each; an event with a lower count and an equal one change nothing; during a deferred `loadThread` an arriving reply is in the window after the page; the `api` is not called for any of these events.
- R15. Other tickets' tools reach threads, and leaving drops them. `patchMessage`, `placeMessage` and `removeMessage` of TOKI-040 R18, which take a conversation id and a message id, look for the message in the main window of the conversation and in every thread window of that conversation (as `root` and among the items), and change it wherever it is held, so an edit, a reaction or a pin reaches the same message in the panel (TOKI-046, TOKI-047, TOKI-048 call them as they are); the handlers of TOKI-047 for `message.edited` and `message.deleted` (with its `isFresher` rule) therefore reach a reply held in a thread window and a root held as `root` without a second handler here. `conversation.left` and `reset` drop the thread windows of the conversation, and its waiting replies become `failed` as TOKI-040 R14 says for the others. Check: `patchMessage` on a message held in the main window and as the thread's `root` changes both and calls each window's listener once; on a reply held in a thread window it changes that reply; on a message that is held nowhere it does nothing; `conversation.left` for a conversation with a thread window empties the window and makes a waiting reply `failed`; a window of another conversation is `===` before and after.

Web: the screen
- R16. The thread's address and Back (D-089). A route `threadRoute` (`apps/web/src/routes/thread.tsx`, path `/c/$conversationId/t/$messageId`, a child of `conversationRoute` of TOKI-033 R21; `$messageId` is the id of the root) is added to the route tree in `router.tsx`. Its `validateSearch` returns `reply` (an id, optional; R18) and no other key, dropping `panel`. Opening a thread (a press on the reply line, or `useOpenThread(conversationId)(rootId)` from the action bar) navigates to the thread address with a new history entry and `state: { threadPushed: true }`; when the address already is a thread it replaces the entry (keeping the state), so Back from the second thread closes the panel, not the first thread. Closing (the panel's Close button from 720 px, its Back button under 720 px, Escape, TOKI-015 R11) calls `closeThread`: when the current entry's `state.threadPushed` is true it calls `history.back()`; otherwise it navigates to `/c/{conversationId}` with `replace: true`. So browser Back, the panel's own buttons and Escape all end on `/c/{conversationId}` with no panel, one entry back, and Back never leaves the conversation while the panel is open. A thread address opened in a new tab shows the conversation with the same thread open. Opening Details from a thread leaves the thread (TOKI-035 R8); choosing another conversation in the list goes to its address and the panel closes. The thread panel is drawn only when the conversation page is drawn, so a person who is not a member of the conversation never loads the thread (TOKI-033 R21). Check, on a memory history: open a thread then Close, open then `history.back()`, open then Escape: each ends on `/c/{id}` with no panel and the history one entry back; a page opened on the thread address and closed leaves the history length unchanged and no panel; opening thread B from thread A leaves one entry for both and Back closes the panel; `?panel=details` on a thread address is dropped; the browser test pastes the thread address into a new tab and finds the same thread open; a non-member's address draws the view of TOKI-033 R21 and makes no request for replies.
- R17. The shell slot. `ConversationPage` (TOKI-033's file, filled by TOKI-035 R10) is changed here to call `useShellPanel` once, with this choice: when the address is a thread (`useParams({ strict: false }).messageId` is set) the content is the `ThreadPanel`, otherwise `DetailsPanel` while `panel=details`, otherwise `null`; `label` is `t("thread.panel.label")` for a thread. This is a change to one expression of that file and to its test (Decided in this spec: the child route's effects run before the parent's, so two calls would let the parent clear the thread; one call has one owner). `threadRoute` renders nothing in the main area. Check: a page test with the real `AppShellRoute` provider: on a thread address the shell has `data-panel` and the panel's accessible name is the thread label; after closing, the slot is cleared; on `?panel=details` the Details panel shows; the existing Details tests of TOKI-035 still pass.
- R18. The panel. `ThreadPanel({ conversationId, rootId, replyId? })` renders a `SidePanel` (TOKI-015 R11) with `title` `t("thread.title")` ("Thread") and `subtitle` the conversation's name, `#name` for a channel and the name as the conversation list shows it for a direct message or a group (the prototype's `sideHead`, line 1437), `labels.back` and `labels.close` from the `common` keys that TOKI-035 R11 uses. ## Design
### Data model
`messages` (TOKI-036) gains `reply_count`, `last_reply_at` and `reply_user_ids` (R1). They are the technical design's "stored reply count", with the last time and the first three repliers that the reply line needs. A reply row has them at their defaults. Nothing else changes: `parent_id`, `also_in_channel`, the thread-depth trigger and the two indexes are TOKI-036's.

Why stored and not counted: the main list returns 50 roots per page and each needs its count; a count by `parent_id` would cost one index range for each root on every page and on every event. The stored values are changed inside the reply's transaction under a row lock (R4), so they are right whenever the reply is visible. The cost is one row update for each reply and a lock on the root that makes two replies to one root wait for each other, for the time of one transaction. Decided in this spec (concern 4).

### API
| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/conversations/{id}/messages` | members, a conversation that is not archived | The send of TOKI-037, with `parentId` and `alsoInChannel` (R2, R3); answers 201 or 200 with `thread` for a reply |
| GET | `/api/v1/conversations/{id}/messages/{rootId}/replies` | members, any state | The root and a page of its replies (R6) |

Errors are those of TOKI-037's table; this work adds a reading of `validation_failed` (a bad parent, `alsoInChannel` outside a channel) and of `not_found` (a parent or root that is not in the conversation). A 409 means the screen was out of date: the client reloads (D-131).

### The event path
The reply calls `recordChange` with `message_created` and then `thread_updated` (R8). The handler list of TOKI-037 R18 runs: the system-line handler does nothing for either (no line), the event handler writes `message.created` and `thread.updated`. A client applies them in number order: the reply goes to the thread window (and the main window when `alsoInChannel`), then the root's summary changes (R14). Both events are for the members of the conversation, because a person who can read the conversation can read its threads.

### The client
Thread windows are the windows of TOKI-040 under a second key, so the order, merge and stale rules are written once (R12). A reply's pending item lives in its thread window; the queue is the conversation's one queue (R13). The handlers use only the seams TOKI-040 R18 gives (`registerEventHandler`, `patchMessage`, `placeMessage`, `setLastMessageAt`), plus the extension of `patchMessage` and the others to reach thread windows (R15).

### What the later tickets get
- TOKI-065: the facts for followers are in the rows and events: the root author is `author_id` of the root, the repliers are the authors of rows with that `parent_id` (and `reply_user_ids` holds only the first three, so it is not the list of followers), and the event `message.created` with a `parentId` is the trigger of a thread item. This work creates no follower row. The address for an item is `/c/{conversationId}/t/{rootId}?reply={replyId}` (R16, R18).
- TOKI-047 (its spec on PR branch `spec/edit-delete-messages`): its `replyCount` input for `deletedDisplay` is the `replyCount` key of R7, which counts replies that are not deleted when set by R9 and counts every reply sent until a delete calls R9; the lock order it states (conversation, then the message row `FOR NO KEY UPDATE`) is the one R4 uses. `recomputeThreadSummary` (R9) after a soft delete of a reply, and `patchMessage` (R15) for the root's and replies' changes; it decides what a deleted reply is (concern 2). It takes message-row locks after the conversation lock and before `recordChange`, as R4 does.
- TOKI-042 and TOKI-052: `ThreadLink`, `canOpenThread`, `useOpenThread` (R20).
- TOKI-043: the box (R19). From it this work needs: a draft key, a placeholder, a slot above its tools for the checkbox, and a send callback that receives the text and returns whether it was accepted. If the composer offers less, the difference is a change in TOKI-043's pull request, not a second box here.
- TOKI-053: it counts the main list only; replies that are not also sent to the channel fall out by the predicate (R5).

## Areas of concern
1. Whether "Also send to #name" is offered in a thread of a direct message or a group. Not decided. D-161 is open: the prototype shows the box only in channels (line 1437), and a reply sent also to a direct message or group would be a second line in a conversation that is already the whole of one exchange. Proposal, not a decision: channels only; R2 refuses `alsoInChannel: true` elsewhere and R19 hides the checkbox. If the owner answers "offer it", R2's refusal and R19's rule are removed; nothing else changes, because the list time and the main-window placement already handle a reply sent also to the channel in a `dm` or `group_dm` (R5, R14). Owner: Thanh Truong (product owner).
2. What a deleted reply does. Not decided. D-013 and the journeys decide that deleting a root keeps its thread; the log says nothing about deleting a reply: whether it leaves the thread, whether the count drops, and whether a "Message deleted" line stays in the thread in its place. Proposal, not a decision: a deleted reply with no replies of its own is removed from the thread list and from the count, as a deleted message with no replies disappears in the channel (AC-031's rule), and the count is set by `recomputeThreadSummary` (R9). The build of delete is TOKI-047, so only its use of R9 depends on the answer. Owner: Thanh Truong (product owner).
3. Which constants page the replies. Decided in this spec: the thread uses the two constants of TOKI-037 (`MESSAGE_PAGE_DEFAULT`, `MESSAGE_PAGE_MAX`, whose values are TOKI-037's concern 1), so the page size of a thread and of a conversation are one answer. Reason: the lists have the same shape and two numbers for one question would drift. Owner: Thanh Truong.
4. Where the reply summary lives. Decided in this spec: three stored columns on the root, changed incrementally in the reply's transaction under the root's row lock (R1, R4). Reason: the technical design says "stored reply count"; a count per root on every page costs a range read for each of 50 roots. The cost is that two replies to one root, and a reply and a delete of that root's row, serialise for one short transaction, and that the lock comes before the counter lock (the order of TOKI-036 R18). Alternatives, a trigger or a materialised count, were not chosen because the send already holds the row and needs the new values for its answer. Owner: Thanh Truong.
5. A bad parent. Decided in this spec: a parent that is a reply or a system line is 400 `validation_failed`, a parent that is not in the conversation is 404 `not_found`; a deleted parent is accepted (D-096). Reason: the screen never sends the first, so it is a guard; the second must not confirm another conversation's message (BR-10). Owner: Thanh Truong.
6. How the other screens learn of a reply. Decided in this spec: two events in one transaction, `message.created` (the reply) and `thread.updated` (the absolute summary of the root), and the client applies the second only when it does not lower the count (R14). Reason: absolute values make a repeated event harmless, and one event for each purpose keeps `message.created` the same shape as in TOKI-038. The known limit: a replayed older `thread.updated` after a reply was deleted could raise the count again until the next page or the next `thread.updated`; a delete by TOKI-047 patches the held root directly, and the rule's cost is that edge. Owner: Thanh Truong.
7. Where the reply send and thread windows live. Decided in this spec: in the sync engine of TOKI-040, added by this work (R12, R13). Reason: the queue, the outbox, the single automatic try and Retry and Delete are written once there, and a second sender would duplicate them and could send a reply and a message of one conversation out of press order. The cost is that this work edits the engine's files after TOKI-040 (additive, the existing tests unchanged), which Plan changes says. Owner: Thanh Truong.
8. The ConversationPage change. Decided in this spec: one `useShellPanel` call with a choice between thread, Details and none (R17). Reason: effects of a child route run before the parent's, so two callers could clear each other and the last-call-wins rule would depend on the order of effects. Owner: Thanh Truong.
9. The panel list is not virtualised. Decided in this spec: the panel renders the loaded replies as plain rows and loads older ones when scrolled to the top (R18). Reason: a thread is read by the people who follow it and the 10,000-message target is for the channel list (TOKI-041); a virtual list would need a second source and a header slot in that component. The cost: a very long thread that was scrolled all the way back keeps all its rows in the DOM. Owner: Thanh Truong.
