# Threads design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/threads.md (Thanh Truong)
Ticket: TOKI-045

## Goal
A member needs to answer one message without adding a line to the whole conversation, and to see at a glance which messages have answers. The message tables already have `parent_id` and `also_in_channel` (TOKI-036), and the message API sends and lists top-level messages only (TOKI-037, TOKI-040). This work adds the reply: the server side (send a reply, list the replies of one message, keep the reply count, the last reply time and the first three repliers on the root message, tell the other screens), the client side (the thread windows and the reply send in the sync engine) and the screen (the thread panel with its address, the reply box with "Also send to #name", and the reply line under a message).
The hard rules are three. A reply that is not also sent to the channel never enters the main list and never moves a direct message in the list. A reply is sent exactly once, with the same id rules as any message. The reply count is stored, and changes in the transaction of the reply, so a list of 50 messages needs no count query (technical design: "stored reply count").

## Requirements
Server: the stored summary
- R1. The table `messages` gains four columns in one migration made with `pnpm db:generate --name thread_summary` (TOKI-019 convention 8): `reply_count` (`integer`, not null, default 0, `messages_reply_count_check`: 0 or more), `last_reply_at` (`timestamptz`, null, no default), `reply_user_ids` (`uuid[]`, not null, default empty array, `messages_reply_user_ids_check`: at most 3 elements) and `summary_version` (`integer`, not null, default 0, `messages_summary_version_check`: 0 or more). `summary_version` rises by 1 on every change of the other three (R4, R9) and is the number that a client compares to decide which of two summaries is newer (R14). The check `messages_thread_summary_shape_check` says: `reply_count` is 0 exactly when `last_reply_at` is null; and a row with a `parent_id` (a reply) has `reply_count` 0, no `last_reply_at`, an empty `reply_user_ids` and `summary_version` 0, so only a root carries a summary. The migration inserts no row and changes no other table; `messages_immutable_trg` (TOKI-036 R7) is not changed and does not list these columns, so they stay writable. It is forward-only (TOKI-005). The test of TOKI-036 R1 reads the column names after the migrations and expects exactly its fourteen, so it fails once this migration adds four; this change edits that test (Plan changes, TOKI-036, gives its line). Check: the migration test of TOKI-005 passes; the catalog shows the four columns with their types, nullability and defaults; each check refuses a bad row (a count of -1, a count of 1 with no time, a time with a count of 0, four ids, a version of -1, a reply with a count of 1 or a version of 1) and accepts a good one; an update of the four columns of a root succeeds, and an update of `body`, `parent_id` and the other columns keeps the rules of TOKI-036 R7; the edited test of TOKI-036 R1 passes with the eighteen names; `pnpm db:generate` run again reports no change; exactly four `ADD COLUMN` statements and no `CREATE TABLE` are in the file.

Server: send a reply
- R2. The send of TOKI-037 (`POST /api/v1/conversations/{id}/messages`) accepts two more keys, as TOKI-037 R4 allows: `parentId` (a lower-case UUID; optional) and `alsoInChannel` (a boolean; optional, `false` when absent). The body stays strict: every other key is 400 `validation_failed`; the one key that TOKI-058 R14 adds, `attachmentIds`, and its change of the text rule (an empty text is allowed when the message has a file) apply to a reply as to any message. Two rules refuse `alsoInChannel: true`, and they fall at different steps of TOKI-037 R1. (a) `alsoInChannel: true` with no `parentId` is 400 `validation_failed` at step 1, as a refinement of the body schema (it needs no fact). (b) `alsoInChannel: true` in a conversation that is not a channel (a `dm` or a `group_dm`) is 400 `validation_failed` at step 6, for a new id only (R3 (a)), because it needs the kind of the conversation, which step 2 reads; this rule is a proposal (concern 1: D-161 is open, and its proposal is "channels only, as in the prototype"; if the owner answers otherwise only this sentence and its checks change). So a person who is not a member of a private direct message still gets 404 and a non-member of a public channel 403 before rule (b), and a repeat is answered as R3 says. The text rules of TOKI-037 R4 (1 to 10,000 code points, white space only, U+0000, lone surrogates) apply to a reply unchanged, and the stored text is the text as sent. Check: a body with `parentId` and `alsoInChannel` is accepted; `alsoInChannel: true` without `parentId` is 400 and stores nothing, also for a person who is not a member (step 1 comes first); with `parentId` in a `dm`, a `group_dm` and a channel the answers are 400, 400 and 201 (this check follows the proposal of concern 1); a non-member of a private `dm` who sends `alsoInChannel: true` with a `parentId` gets 404, and a non-member of a public channel gets 403 (not 400); `alsoInChannel: "yes"`, `parentId` in upper case or not a UUID, and an unknown key are 400; the boundary texts of TOKI-037 R4 give the same results for a reply.
- R3. The rules of a reply, in the order of TOKI-037 R1. Steps 1 to 5 (schema, facts, `canReadConversation`, the locks, the lookup of the id) are those of TOKI-037. A repeat is a repeat as TOKI-037 R5 says (same conversation, same author, a message): it answers 200 with the stored row and writes nothing, whatever `parentId` and `alsoInChannel` the repeated request carries (they are not compared, as the text is not), so a repeat that carries `alsoInChannel: true` in a direct message is 200, and one that carries it with no `parentId` is 400 at step 1 as any body is. For a new id, step 6 is, in this order: (a) the post rule and the read-only rule of TOKI-037 R6 and R7, so a reply into an archived channel is 409 `channel_archived` for everybody and into a direct message with a deactivated person is 409 `conversation_read_only`; then the kind rule of R2 (b); (b) then, when `parentId` is given, the lookup of the parent inside the same locks: `select id, conversation_id, kind, parent_id from messages where id = $parentId and conversation_id = $conversation`. A parent that does not exist in this conversation (no row, or a row of another conversation) is 404 `not_found` with the body of an unknown conversation (nothing about the other conversation is confirmed). A parent that is itself a reply, or a system line, is 400 `validation_failed` (a thread is one level deep, FR-33; the screen never offers it, so this is a guard; Decided in this spec, concern 5). A parent that is deleted (`deleted_at` set) is accepted: the reply is stored, and the thread keeps its place under the "Message deleted" line (D-013, D-096). Check, in a channel: a reply to a root is 201 and the row has `parent_id` and `also_in_channel` as sent; a reply to a reply is 400; a reply to a system line is 400; a reply to an id with no row and to a message of another conversation are each 404 with the same body as an unknown conversation; a reply to a root that was soft-deleted (set by SQL) is 201; an archived channel gives 409 for a reply; a repeat of a reply sent with other flags gives 200 and the stored row, and a repeat with `alsoInChannel: true` in a `dm` is 200 (not 400); a person who is not a member gets the refusals of TOKI-037 R2 before any parent lookup (the statement log shows no read of `messages` for the parent); a deactivated person's `dm` with `alsoInChannel: true` gives 409, not 400.
- R4. The thread summary is kept in the transaction of the reply, and only when the insert stored a row. TOKI-037 R5 inserts with `ON CONFLICT (id) DO NOTHING`, and the conversation lock is `FOR SHARE`, so two sends of one id can run together: when the insert returns no row, the statement below and both `recordChange` calls are skipped and the request answers as a repeat (R7). When it stored a row, it first calls the `saveMentions` that `app.ts` injects into the send (TOKI-050 R6; the reply is the same route and gets the same call, after the insert of the reply and before the entry is built; the default does nothing and returns an empty delta, so the tests of this work that pass none stay valid), then, when the body has `attachmentIds`, the `linkAttachments` of TOKI-058 R14 (in the same transaction, after `saveMentions`; it locks only the file rows of this reply and none of another message), and then, before any call of `recordChange`, one statement updates the root row: `reply_count = reply_count + 1`, `last_reply_at = greatest(last_reply_at, $at)` with `$at` the `created_at` of the reply (the time of TOKI-037 R3), `reply_user_ids` with the author appended when the author is not in it and it holds fewer than 3 (so it lists the first three different people who replied, in the order of their first reply; the prototype's reply line shows the same people) and `summary_version = summary_version + 1`, and it returns the new values for the answer and for R8. The statement takes the root row `FOR NO KEY UPDATE` through the update itself; it is the only lock this work adds, it comes after the conversation lock of TOKI-037 R8 and before the first `recordChange` (the counter lock of TOKI-036 R18, after which no lock may follow), and the send locks no reply row and no message row before the conversation row (R9 states the order for the whole module). A rollback after it leaves the old summary. The incremental values are in commit order under the root lock, while `created_at` is read before the transaction waits for the lock (TOKI-037 R3), so two replies at one moment can commit in the other order of their `created_at`: `last_reply_at` is the same (it is a `greatest`), and `reply_user_ids` may then list the two first-time authors in the other order. The truth is the order of `created_at` that R9 computes, and a difference is allowed until a recompute (concern 12). Check, with real connections and no sleep: ten replies by three people give `reply_count` 10, `last_reply_at` the latest `created_at`, `summary_version` 10 and `reply_user_ids` the first three authors in order; two replies to one root at the same moment give 2 and both answer 201, with no deadlock (SQLSTATE `40P01`); two sends of one id at the same moment on two connections give one 201 and one 200, one stored row, a count of 1, a version of 1 and one pair of `recordChange` calls; a reply and a soft delete of the root (an update of `deleted_at` and `deleted_by` by SQL on a second connection) at the same moment end with both applied and a count of 1; a handler that throws after the update leaves the root's summary as it was and no reply row; the statement log of a reply shows the update after the insert and before the first call of the recording handler, and no locking statement after that call; with a fake `saveMentions`, a reply calls it once with the id and the text of the reply after the insert and before the update of the root, a repeat and a send whose insert stored no row call it zero times, and a rollback after it leaves no mention row and no change of the summary; with a fake `linkAttachments`, a reply with `attachmentIds` calls it once after `saveMentions` and before the update of the root, a repeat calls it zero times, and a refusal by it (400 `validation_failed`) leaves no reply row and the root's summary as it was.
- R5. A reply and the main list. A reply with `alsoInChannel` false is not in the main list of TOKI-036 R11: `GET .../messages` of TOKI-037 does not return it, `listLastMessageTimes` (TOKI-037 R19) does not count it, and the unread predicate of TOKI-053 leaves it out, all by the predicate `parent_id is null or also_in_channel` that this work does not change. A reply with `alsoInChannel` true is in the main list as one message (D-160): `GET .../messages` returns it in its place by `created_at`, with its `parentId` and `alsoInChannel: true`; `lastMessageAt` of a `dm` or `group_dm` counts it; the message component draws it as a normal message with no mark (the prototype posts it as a plain message, line 2234; D-160). Check: through the route, in a channel: a reply with the flag false is absent from the history of the conversation, with the flag true it is present, once, and the same reply is in the replies of R6 in both cases; the row count of `messages` after a reply sent with the flag true is one more than before (one message, not two). For the `dm` half the route cannot be used while the proposal of concern 1 refuses the flag in a `dm`, so the test writes the rows by SQL (TOKI-036 R5 allows it) and asks `listLastMessageTimes`: a `dm` with a reply row with the flag false returns the time as before, and with the flag true returns the reply's `created_at`. A channel does not ask `listLastMessageTimes`, so the channel half proves the history rule only.
- R6. `GET /api/v1/conversations/{id}/messages/{rootId}/replies` lists one thread. Steps 1 to 3 of TOKI-037 R1 apply (schema, facts, `canReadConversation`); no lock. The query keys are those of TOKI-037 R11: `limit` (the same constants `MESSAGE_PAGE_DEFAULT` and `MESSAGE_PAGE_MAX`) and at most one of `before`, `after` and `around`, each the id of a reply of this thread. The answer is 200 `{ "root": MessageEntry, "messages": MessageEntry[], "hasOlder": boolean, "hasNewer": boolean }`, `messages` oldest first, ordered by (`created_at`, `id`) and paged exactly as TOKI-037 R12 and R13 say, with `where parent_id = $root` so that `messages_thread_idx` serves it with no sort (TOKI-036 R11). `root` is the entry of the root as the table holds it now, summary included, deleted or not. Every entry of the answer, `root` included, is made by `buildMessageEntry` of TOKI-037 (the one function that turns rows into entries, Design "The entry builder"), so each key that a later ticket adds (`reactions`, `pinned`, `mentions`, files) is filled here as in the history, and this route reads no reaction, pin or mention itself. `rootId` must be a user message of this conversation with no `parent_id`: a system line, a reply, another conversation's message and an id with no row are 404 `not_found` with the body of an unknown conversation. An anchor that is not a reply of this thread is 404. A deleted root still answers, with its replies. Archived channels answer for members (reading is allowed). Check: a thread of 120 replies read backward by pages of 20 gives every reply once and ends with `hasOlder` false, and forward with `after` the same; `around` follows the two-sided rule of TOKI-037 R13; a thread with no reply answers an empty list with both flags false; a reply to the root that was also sent to the channel is in the thread once; two cursors, an unknown key and `limit` 0 are 400; the four 404 cases; the replies of a deleted root load; the `EXPLAIN` of the three queries uses `messages_thread_idx` with no `Sort` node (as TOKI-036 R11 tests them); a person who is not a member of a private channel gets 404 and of a public channel 403 before any read of replies; with test readers injected for `reactions`, `pinned` and `mentions` (the shapes of TOKI-046 R10, TOKI-048 R3 and TOKI-050 R8), the root and every reply of the answer carry what they returned, each reader is called once for the whole answer, and the answer parses with the strict schema that has those keys.
- R7. The entry and the send answer. `MessageEntry` of TOKI-037 R15 gains five keys, as it says later work may: `alsoInChannel` (boolean, true only for a reply), `replyCount` (integer, 0 or more), `lastReplyAt` (`null` or ISO 8601 UTC), `replyUserIds` (an array of 0 to 3 ids) and `summaryVersion` (integer, 0 or more). They are read from the columns of R1 and `also_in_channel`, so a root carries its summary in every answer that returns it (history, the replies route, the answer of a send, the answers and events of edit and delete) and a reply carries 0, `null`, an empty array and 0. `packages/shared` also exports `ThreadSummarySchema` (`{ rootId, replyCount, lastReplyAt, replyUserIds, summaryVersion }`, strict) and the response schema of R6. The send answer of a reply (201 and 200) is `{ "message": MessageEntry, "thread": ThreadSummary }`; the answer for a root message stays `{ "message": MessageEntry }` with no `thread` key. For a 201, `thread` is the row the statement of R4 returned. For a 200 (a repeat, or a send whose insert stored no row), the entry and `thread` come from the stored row: its `parent_id` (never the request's) says whether there is a `thread` key and whose summary is read, as it stands now (a read with no lock), so a repeat of a reply that carries another `parentId` answers the thread of the stored parent, and a repeat of a root that carries a `parentId` has no `thread` key. The entry of a send answer is made by `buildMessageEntry` as every entry is. Check: schema tests accept a root with a summary, a reply and a thread answer, and refuse an added key, a missing key, four user ids, a `replyCount` of -1 and a `summaryVersion` of -1; every 200 and 201 body of the tests of R2 to R6 is parsed with the response schema; a send of a root has no `thread` key; a repeat of a reply with another `parentId` gives the `thread` of the stored parent; a repeat of a root with a `parentId` has no `thread` key; a repeat after two more replies gives a `thread` with the newer count; the tests of TOKI-037 that built a `MessageEntry` are updated with the five keys in this change and pass.
- R8. Telling the other screens. A reply calls `recordChange` twice in its transaction, as the last statements and in this order: first `message_created` (TOKI-037 R10, `message` the entry of the reply, which TOKI-038 turns into `message.created` with `{ message }` and the reply's `parentId`), then `thread_updated`, a new change type of `conversations/changes.ts` with the fields `conversationId`, `actorId`, `at` and `thread` (a `ThreadSummary`). The event handler of TOKI-038 gains one row in its table of changes: `thread_updated` writes one event `thread.updated`, scope `conversation`, payload `{ conversationId, rootId, replyCount, lastReplyAt, replyUserIds, summaryVersion }`, whose schema this work adds to the registry of event kinds in `packages/shared/src/realtime/` (TOKI-038 R12 allows a kind added within a version), and one row in `apps/server/src/modules/realtime/kinds.ts` saying that the kind changes no map (TOKI-038 checks that every kind of the registry has a row there and the reverse, so without the row that test fails; TOKI-047 R10 adds its two rows the same way). The two events have consecutive numbers (TOKI-036 R18). A repeat, a refusal, a send whose insert stored no row and a reply that rolls back call `recordChange` zero times. The change `thread_updated` is also sent by TOKI-047 after it deletes a reply (R9). Check, with a recording handler as in TOKI-037 R10: a reply makes two calls in this order with the fields above and `thread` equal to the `thread` of the 201 body; a repeat and every refusal make none; with the real event handler (the test of this work, as TOKI-038 R20 tests its own rows) the log holds `message.created` then `thread.updated` with consecutive numbers, and the payload of the second parses with its schema; a rolled-back reply leaves no event; the registry test of TOKI-038 (every kind has a row in `kinds.ts` and the reverse) passes with the new kind and its row.
- R9. `recomputeThreadSummary(tx, rootId)` of the `messages` module (exported from its `index.ts`) sets the four columns of a root from the replies that exist and are not deleted, and returns the `ThreadSummary`: `reply_count` is the number of replies with `deleted_at` null, `last_reply_at` the latest `created_at` among them (null when there are none), `reply_user_ids` the first three different authors in order of their first reply (by `created_at`, then `id`), and `summary_version` the held version plus 1, so a recompute that lowers the count still raises the version and a client applies it (R14). It runs three statements in this order: (1) the root row `select ... for no key update`, which waits for any send that holds the root; (2) one aggregate read of the replies; (3) the update. Because the lock is granted in statement 1 and the count is read in statement 2, which under `READ COMMITTED` takes its snapshot when it starts, the count sees every reply committed before the lock was granted, and a send that comes after waits for the lock and adds its own reply on top. It is the function TOKI-047 calls in the transaction of the delete of a reply, and it is the repair for a count that is wrong; this work's own send does not call it (R4 is incremental). It is called exactly when a reply is deleted by that route (TOKI-047 calls it after its update of the reply and before its first `recordChange`, and then sends `thread_updated` for the root with the returned summary and the actor and time of the delete); it is not called for a repeat of a delete, an edit, a delete of a root or a refused request. Lock order, for the whole module and for TOKI-047: a message row is locked before the root of its thread and never after it (the delete route locks the reply row, then this function locks the root); this work's own send locks no reply row and takes the root only through its update; so no cycle exists between a send, a delete and a root delete. What a deleted reply does to the count is concern 2 (not decided): this function implements the proposal there, and if the owner answers that a deleted reply stays counted, its `deleted_at` filter and the call from TOKI-047 are removed and nothing else changes. Check: after ten replies by the send, the function returns the same values as the incremental columns, with the version one higher; after a reply is soft-deleted by SQL it returns a count of 9, the new last time and authors, and a version again one higher; with no replies it returns 0, null and an empty array; a property test of 200 random sequences of replies and deletes by SQL compares it with a direct count query; with two real connections, a recompute and a send to one root at the same moment both end applied and the count equals the number of live replies; a delete of a reply (a row lock on the reply, then the recompute) and a send to the same root at the same moment end with no deadlock; the statement log of the function shows the lock before the aggregate read.
- R10. Safety and shared values. A reply and the replies route log no text and no id list beyond the request line (TOKI-037 R23). The registry of error codes gains no code (`validation_failed`, `not_found`, `forbidden`, `channel_archived`, `conversation_read_only`, `message_id_in_use` are reused). `packages/shared/src/messages/` exports the new keys and schemas of R7 and the response schema of R6. Nothing of this work calls `appendEvent` or `recordEvent` (TOKI-036 R25). Check: a forced constraint failure on a reply with a known text leaves that text out of the captured log; a grep test finds no call of `recordEvent` or `appendEvent` in the files of this work; a type test imports every new name from `@toki/shared`.

Client: windows and sending
- R11. The API client (TOKI-032 R9, TOKI-040 R2) gains two things. `api.messages.send(conversationId, body, signal?)` takes `body` `{ id, text, parentId?, alsoInChannel? }` (and the `attachmentIds?` that TOKI-040 gains from TOKI-059), sends exactly the keys it is given, and returns `{ status, message, thread? }` read with the schema of R7 in the form that drops unknown keys. `api.messages.replies(conversationId, rootId, query?, signal?)` sends `GET /conversations/{id}/messages/{rootId}/replies` with `limit`, `before`, `after` or `around` only when given (never two positions) and returns `{ root, messages, hasOlder, hasNewer }`. The path parts are encoded; the 10-second rule and the error kinds are those of the existing core. Check: with the fake `fetch` of the API tests, each call sends the method, path, query and body as written; a send with no reply keys sends exactly `{ id, text }` as before; an answer with an extra key keeps it; a failed answer ends as an `ApiError`.
- R12. Thread windows. The sync engine (TOKI-040) keeps, next to its windows of main lists, one window for each thread that a screen has loaded, keyed by the id of the root. `getThread(rootId)` returns a `ThreadWindow`: the `MessageWindow` of TOKI-040 R3 (`status`, `error`, `items`, `hasOlder`, `hasNewer`, `isLoadingOlder`, `isLoadingNewer`, `stale`) plus `conversationId` and `root` (`MessageEntry` or `null` until the first answer); the empty window of an unknown thread is one frozen object with `root` null. `subscribeThread(rootId, listener)` is called for the changes of that thread only. `loadThread(conversationId, rootId)`, `loadThreadOlder(rootId)`, `loadThreadNewer(rootId)` and `loadThreadAround(conversationId, rootId, replyId)` call `api.messages.replies` with no position, `before` the oldest held reply, `after` the newest, and `around`; they never reject and obey TOKI-040 R5 and R6 for order, duplicates, identity, the merge table, flags, the "no request for a ready window with `hasNewer` false" rule and the events kept aside during a head load. The code is the windows module of TOKI-040 given a key and a loader, not a copy (a change request to TOKI-040 asks it to be generic in its key now, so this work does not refactor it afterwards). Every window keeps the index of its message ids that the windows module has, so a message is found by id with no scan. An answer does not replace `root`. ## Design
### Data model
`messages` (TOKI-036) gains `reply_count`, `last_reply_at`, `reply_user_ids` and `summary_version` (R1). They are the technical design's "stored reply count", with the last time and the first three repliers that the reply line needs, and the version that tells a client which of two summaries is newer. A reply row has them at their defaults. Nothing else changes: `parent_id`, `also_in_channel`, the thread-depth trigger and the two indexes are TOKI-036's.

Why stored and not counted: the main list returns 50 roots per page and each needs its count; a count by `parent_id` would cost one index range for each root on every page and on every event. The stored values are changed inside the reply's transaction under a row lock (R4), so they are right whenever the reply is visible. The cost is one row update for each reply and a lock on the root that makes two replies to one root wait for each other, for the time of one transaction. Decided in this spec (concern 4).

### API
| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/conversations/{id}/messages` | members, a conversation that is not archived | The send of TOKI-037, with `parentId` and `alsoInChannel` (R2, R3); answers 201 or 200 with `thread` for a reply |
| GET | `/api/v1/conversations/{id}/messages/{rootId}/replies` | members, any state | The root and a page of its replies (R6) |

Errors are those of TOKI-037's table; this work adds a reading of `validation_failed` (a bad parent, `alsoInChannel` outside a channel) and of `not_found` (a parent or root that is not in the conversation). A 409 means the screen was out of date: the client reloads (D-131).

### The event path
The reply calls `recordChange` with `message_created` and then `thread_updated` (R8); the delete of a reply (TOKI-047) calls it with `message_deleted` and then `thread_updated` (R9). The handler list of TOKI-037 R18 runs: the system-line handler does nothing for either (no line), the event handler writes `message.created` and `thread.updated`. A client applies them in number order: the reply goes to the thread window (and the main window when `alsoInChannel`), then the root's summary changes when its version is higher than the held one (R14). Both events are for the members of the conversation, because a person who can read the conversation can read its threads.

### The client
Thread windows are the windows of TOKI-040 under a second key, so the order, merge and stale rules are written once (R12). A reply's pending item lives in its thread window; the queue is the conversation's one queue (R13). The handlers use only the seams TOKI-040 R18 gives (`registerEventHandler`, `patchMessage`, `placeMessage`, `setLastMessageAt`), plus the extension of `patchMessage`, `placeMessage`, `removeMessage` and `applyMessage` to reach thread windows by a parent key (R15). Several handlers may be registered for one kind and run in the order of registration, so this work, reactions, edit and delete, and pins each register their own.

### The entry builder
TOKI-037 R15 defines `MessageEntry`; this work needs every place that returns an entry to fill the same keys. It asks TOKI-037 for one function, `buildMessageEntry(db, row, readers?)` and its list form `buildMessageEntries(db, rows, readers?)`, exported from `messages`, with `readers` `{ listReactions?, listPinned?, listMentions? }` injected by `app.ts` (the shape of TOKI-046 R10 for reactions; TOKI-048 R3 for pins; TOKI-050 R8 for mentions). It reads the thread summary from the row itself (R7), so this work needs no reader. The history, the replies route (R6), the answer of a send (R7), the answers and the events of edit and delete (TOKI-047), and the answers of reactions and pins all build their entries through it, so a key that a later ticket adds is filled everywhere at once and an entry in an event is as complete as one in a page.

### Who depends on whom
This work needs TOKI-040 (the engine it extends), TOKI-035 (the page whose expression R17 changes), TOKI-042 (the panel draws the root and the replies with the message component) and TOKI-043 (the reply box); TOKI-033 and TOKI-041 come through TOKI-035. It does not need TOKI-047, TOKI-046 or TOKI-048: they need this work. TOKI-042 does not need this work, because `ThreadLink` reaches its row through the `footer` slot that the page fills (R17), so there is no needs cycle. TOKI-047 needs this work for `recomputeThreadSummary`, `thread_updated`, `replyCount` and the windows.

## Areas of concern
1. Whether "Also send to #name" is offered in a thread of a direct message or a group. Not decided. D-161 is open: the prototype shows the box only in channels (line 1437), and a reply sent also to a direct message or group would be a second line in a conversation that is already the whole of one exchange. Proposal, not a decision: channels only; R2 refuses `alsoInChannel: true` elsewhere and R19 hides the checkbox. If the owner answers "offer it", R2's refusal and R19's rule are removed; nothing else changes, because the list time and the main-window placement already handle a reply sent also to the channel in a `dm` or `group_dm` (R5, R14). Owner: Thanh Truong (product owner).
2. What a deleted reply does. Not decided. D-013 and the journeys decide that deleting a root keeps its thread; the log says nothing about deleting a reply: whether it leaves the thread, whether the count drops, and whether a "Message deleted" line stays in the thread in its place. Proposal, not a decision: a deleted reply is removed from the thread list and from the count. This follows F16 and TOKI-047 R20 ("a deleted reply is hidden in the panel and in the channel"); a reply never has replies of its own, so the condition of F16 for a deleted message with no replies always holds. The count is set by `recomputeThreadSummary` (R9), which TOKI-047 calls in the transaction of the delete, and the other screens learn it by `thread.updated` with a higher `summaryVersion` (R14). If the owner answers that a deleted reply stays counted, the filter of R9 and the call from TOKI-047 are removed and nothing else changes. Owner: Thanh Truong (product owner).
3. Which constants page the replies. Decided in this spec: the thread uses the two constants of TOKI-037 (`MESSAGE_PAGE_DEFAULT`, `MESSAGE_PAGE_MAX`), so the page size of a thread and of a conversation are one answer. This decides only that the two numbers are shared; their values are those of TOKI-037 concern 1, and this line does not answer the page size. Reason: the lists have the same shape and two numbers for one question would drift. Owner: Thanh Truong.
4. Where the reply summary lives. Decided in this spec: four stored columns on the root, changed incrementally in the reply's transaction under the root's row lock (R1, R4), and recomputed by R9. Reason: the technical design says "stored reply count"; a count per root on every page costs a range read for each of 50 roots. The cost is that two replies to one root, and a reply and a delete of that root's row, serialise for one short transaction, and that the lock comes before the counter lock (the order of TOKI-036 R18). Alternatives, a trigger or a materialised count, were not chosen because the send already holds the row and needs the new values for its answer. Owner: Thanh Truong.
5. A bad parent. Decided in this spec: a parent that is a reply or a system line is 400 `validation_failed`, a parent that is not in the conversation is 404 `not_found`; a deleted parent is accepted (D-096). Reason: the screen never sends the first, so it is a guard; the second must not confirm another conversation's message (BR-10). Owner: Thanh Truong.
6. How the other screens learn of a reply, and of a count that drops. Decided in this spec: two events in one transaction, `message.created` (the reply) and `thread.updated` (the absolute summary of the root with a `summaryVersion` that rises on every change), and the client applies a summary only when its version is higher than the held one (R14). Reason: absolute values make a repeated event harmless; the version, and not the count, decides which summary is newer, so a count that falls after a deleted reply is applied while an older event, an older page or a repeat answer cannot put an old count back; and one event for each purpose keeps `message.created` the same shape as in TOKI-038. The earlier rule "apply only when the count is not lower" is dropped because it made every decrease impossible. Owner: Thanh Truong.
7. Where the reply send, the thread windows and the handlers live. Decided in this spec: in the sync engine of TOKI-040, added by this work (R12, R13, R15), with handlers registered through `registerEventHandler`, which runs several handlers of one kind in registration order (change request to TOKI-040). Reason: the queue, the outbox, the single automatic try and Retry and Delete are written once there, and a second sender would duplicate them and could send a reply and a message of one conversation out of press order. The cost is that this work edits the engine's files after TOKI-040 and extends its contract table (a type test of its R22 gains rows): the edit is additive for callers and behaviour, and the contract test is edited in the pull request that makes the change (Plan changes, TOKI-040). Owner: Thanh Truong.
8. The ConversationPage change. Decided in this spec: one `useShellPanel` call with a choice between thread, Details and none (R17). Reason: effects of a child route run before the parent's, so two callers could clear each other and the last-call-wins rule would depend on the order of effects. Owner: Thanh Truong.
9. The panel list is not virtualised. Decided in this spec: the panel renders the loaded replies as plain rows and loads older ones when scrolled to the top (R18). Reason: a thread is read by the people who follow it and the 10,000-message target is for the channel list (TOKI-041); a virtual list would need a second source and a header slot in that component. The cost: a very long thread that was scrolled all the way back keeps all its rows in the DOM. Owner: Thanh Truong.

10. A reply sent with the tick while it waits. Decided in this spec: the pending item lives in the thread window only; the channel shows the message when the answer or the event arrives (R13). Reason: D-160 makes it one message, and a pending copy in two windows would be one item with two places and two ways to fail. The cost: offline, the person does not see a "Waiting to send" copy in the channel. Owner: Thanh Truong.
11. Back for a thread opened by address. Decided in this spec: Back closes the panel first for a panel opened from the app, and for a thread address opened in a new tab or from a link Back leaves to the page before it, while Close and Escape replace the entry with the conversation (R16). Reason: inserting a conversation entry under a direct address would rewrite the person's history, and `history.back()` cannot close a panel that has no entry of its own. Owner: Thanh Truong.
12. The order of the first three repliers. Decided in this spec: the order of `created_at`, computed by R9, is the truth; the incremental update of R4 follows commit order and may list two first-time authors in the other order until a recompute (R4). Reason: the time is read before the transaction waits for the root lock (TOKI-037 R3), so the two orders can differ only for replies at one moment, and a lock held to make them agree would serialise more of the send. Owner: Thanh Truong.
13. The stored text during a deploy. Decided in this spec: the schema of an item in the outbox text is not strict about keys, and the text keeps `version` 1 (R13). Reason: a strict schema would make a tab on an older build remove the whole text, with the waiting messages of the other tabs, the first time it saw a reply item; the cost is that an older build that writes the text back drops the two reply keys of the items it holds, for the short time two builds share a browser. Owner: Thanh Truong.
14. Who owns the delete of a reply and the one entry builder. Decided in this spec: this work owns `recomputeThreadSummary`, `ThreadSummary`, the `summaryVersion` and the change `thread_updated`, and TOKI-047's transaction calls the function and sends the change (R9, Plan changes); TOKI-037 owns `buildMessageEntry`, and every route and event builds its entries through it (R6, R7). Reason: one owner for each piece, and an entry in an answer or an event as complete as one in a page. Owner: Thanh Truong.
15. Which tools the thread box has. Not decided. The prototype draws the toolbar (bold, italic, code, emoji, attach, mention) in the thread box as in the conversation's box (`composerHtml`), and the edit field has none; TOKI-043 R17 builds `tools` in `ConversationComposer` only, and TOKI-049 concern 4 asks this ticket for it. Proposal, not a decision: the thread box builds `tools` from `composerTools` and calls `useMentions` (R19). If the owner answers that the thread box has no toolbar, the sentences (a) and (b) of R19 and their checks are removed, which also removes the paperclip (it is the `attach` tool), and nothing else changes: the drop zone and the paste of (d) still add files to the thread's set. Owner: Thanh Truong (product owner).
