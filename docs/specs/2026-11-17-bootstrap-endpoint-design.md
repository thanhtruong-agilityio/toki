# Bootstrap endpoint design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/bootstrap-endpoint.md (Thanh Truong)
Ticket: TOKI-031

## Goal
The app needs everything that draws its first screen in one answer: who the signed-in person is, the workspace name, the people, the person's own conversations with their star, mute and level, and the point in the event stream that this answer corresponds to. This work adds that request, `GET /api/v1/bootstrap`, reads all of it from one consistent view of the database, and leaves out whatever the person may not see. The client-core API client (TOKI-032) and the conversation list (TOKI-033) are built on its shape.

## Scope
- In:
  - The route `GET /api/v1/bootstrap` and the code that gathers its answer from the `workspace`, `members` and `conversations` modules (Design, "Where the code lives").
  - The response schemas in `packages/shared` (R2, R17).
  - One read added to `modules/members` and one to `modules/conversations` (R15).
  - The rule for which conversations and people come (R5, R6) and what each entry holds (R7, R8).
  - The event number field and the place where it is read (R11).
  - Server integration tests, including the size and the number of statements (R14, R20).
- Out (not now):
  - Unread counts, the "mention" dot and the New divider: the read pointer, TOKI-053, adds them to the conversation entries; the table has nothing to count from before messages exist (TOKI-028 Scope). The plan line of this ticket names "unread counts"; moving them to TOKI-053 is a change to the plan that the product owner has not made (concern 7).
  - The latest message of a conversation, the order of direct messages by it (F09) and hiding a DM from the other person until its first message (F25): they need `messages` (TOKI-036). Which ticket builds them is open (concern 1). Until it is decided, M2 ships with a known deviation from F25: a new DM is in both people's lists from the moment it is opened (TOKI-028 concern 6), so the other person sees an empty DM before any message. This ticket returns it as it is.
  - The numbered event log and its number: TOKI-036 builds the log; this ticket returns the number through one function that returns 0 until then (R11).
  - Messages, threads, files, drafts, reactions, pins, Activity, Later, presence (TOKI-055), job title, time zone, status text and the person's preferences: each belongs to its own ticket, which adds its field to this response when its data exists (R12).
  - The description of a conversation, its creator and creation date, the members of a channel and the list of channels to browse: TOKI-029 (the Details panel and Browse read them by their own requests; concern 2).
  - Saving a person's notification level, mute and star: not owned by any ticket in the plan (TOKI-028 concern 2). This ticket only returns them (concern 5).
  - The WebSocket, the reconnect and the sync engine that use the event number: TOKI-038, TOKI-039, TOKI-040.
  - Screens and texts: none. The response holds names and values, no display text, so nothing goes through i18n.

## Requirements
- R1. `GET /api/v1/bootstrap` exists, takes no body and no query, and needs a valid session of any role (TOKI-022 R24): a Member and an Admin get the same shape. Without a session it answers 401 `unauthenticated`, with an ended session 401 `session_ended`, with a deactivated account 401 `account_deactivated`, as TOKI-022 R27 and R44 say, and the body holds no workspace data. A query string is ignored. Check: with a session of each role, status 200; with no cookie, an ended session and a deactivated account, the three 401 codes and a body that passes the error schema of TOKI-004 and contains neither the workspace name nor any display name. The deactivated case is built as TOKI-022 R29 allows: a session is made with `createSession` while the account is active, then the account is set to `deactivated` by SQL, and the call is made with that session (`createSession` refuses a deactivated account).
- R2. A 200 answer is a JSON object with exactly these five keys: `user`, `workspace`, `members`, `conversations`, `eventNumber`. It passes the schema `BootstrapResponse` of R17, which rejects unknown keys at every level, `user` included. Check: a test parses the body of a rich fixture with `BootstrapResponse` (strict) and it passes; the same body with one added key at the top level, in `user`, in `workspace`, in a member and in a conversation entry (one of each kind) fails to parse, for each.
- R3. `user` is the signed-in account in the `User` shape of TOKI-022 R32 (`id`, `email`, `displayName`, `role`, `language`), read inside the transaction of R10, and is equal to the `user` of `GET /api/v1/auth/session` for the same session when no change happens between the two calls. It is the only place where an email address is returned. The schema of `user` in this response is the `User` schema of TOKI-022 R38 wrapped with `.strict()` (R17): TOKI-022 does not say that its `User` is strict, and a Zod object strips unknown keys by default, so the strictness is this schema's own and no change to TOKI-022 is needed. Check: both routes with one session give equal `user` objects; the body holds no other value of the form `x@y`; the strict parse of R2 rejects an added key in `user`.
- R4. `workspace` is `{ "id", "name" }` of the workspace read, inside the transaction of R10, through the `workspace` module read that TOKI-022 uses for the sign-in card (Module boundaries of that spec), which returns the id and name of the one workspace of the installation (D-004: one workspace now, `workspace_id` kept in the schema). The `workspaceId` that every other read filters on is not taken from that read: it is the `workspaceId` that `getAccountsByIds(tx, [account.id])` returns for the caller (TOKI-029 R19; the contract table of that spec), called without the `lock` option. The handler checks that the two ids are equal and answers 500 `internal_error` if they are not (not reachable while there is one workspace). Decided in this spec. Reason: TOKI-029 and TOKI-030 take the workspace from the account in the same way, the `User` shape has no workspace id, and the workspace read takes no account. Check: after `createWorkspace` with the name `Test Workspace`, the answer holds that name and the id of the row; a test that replaces the account read of the handler (the seam of R10) by one that returns another `workspaceId` gets 500 and a body with no workspace data. The route tests use one workspace row; the filtering by workspace is proved on two workspaces by the database tests of R15.
- R5. `members` holds every account of the workspace, active and deactivated, the signed-in person included, as `{ "id", "displayName", "role", "status" }` and nothing else: `role` is `member` or `admin`, `status` is `active` or `deactivated` (TOKI-019 R9, R10). It holds no email address, no sign-in or session data. It is ordered by `lower(displayName)` compared with the collation `"C"` (byte order), then by id in the same collation: a rule of this ticket, the same as the list of the Admin page orders by, written here so this ticket reads no code of TOKI-024. Check: a fixture of five accounts (one deactivated, two Admins, names in upper and lower case) is returned complete, in that order, with exactly those four keys each; a search of the body for the five email addresses finds only the one of `user`; the second workspace is covered by the database test of `listPeople` (R15).
- R6. `conversations` holds a conversation when, and only when, the signed-in person has a member row in it and it is not archived (`archived_at` is null). So it holds: every channel the person has joined (public or private), #general, every DM and every group the person is in, also with a deactivated person. It holds no public channel the person has not joined (D-116), no private channel, DM or group the person is not in, no archived conversation (F26), and nothing of another workspace (R15 proves this on two workspaces). Check: a fixture with a joined public channel, a joined private channel, #general, a DM, a group, a DM with a deactivated person, an unjoined public channel, a private channel without the person, a DM of two other people, and a joined channel that is archived returns exactly the first six ids; after the person leaves one joined channel (its member row deleted) and after another is archived, a second call omits both.
- R7. Each entry of `conversations` has one of two shapes, both strict. A `channel` entry is exactly `{ "id", "kind": "channel", "name", "topic", "isPrivate", "isGeneral", "notificationLevel", "isMuted", "isStarred", "memberIds": null }`: `name` is the channel name, `topic` the topic or null, `isPrivate` and `isGeneral` the two flags of TOKI-028. A `dm` or `group_dm` entry is the `DirectConversationEntry` that TOKI-030 defines in `packages/shared/src/direct-conversations.ts` (its R17 and R18) and this ticket adopts, not a copy: exactly `{ "id", "kind": "dm" | "group_dm", "name": null, "topic": null, "isPrivate": true, "isGeneral": false, "notificationLevel", "isMuted", "isStarred", "memberIds": string[] }` (`isPrivate` is true for every DM and group, TOKI-028 R5). Both shapes have the same keys, so the client reads one list; the response of TOKI-030 for a new or reopened DM is the same entry, so the picker adds it to the store with no mapping. `memberIds` of a DM or group is the ids of its people, the signed-in person included, which are the ids of its `dm_key`, in the order of the key: lowercase text in byte order (collation `"C"`, TOKI-028 R10), so the client names a DM by the other person and a group by its people (F09) and the key never changes (TOKI-028 R21). The entries are ordered by `id` in the same collation. The description, `createdBy`, `createdAt`, `archivedAt` and the key `dm_key` are not returned. Check: for each kind the entry has exactly these keys with these values, `isPrivate` true for a DM and a group, `memberIds` of a group of 8 holds 8 ids in the order of its key, and a channel has `memberIds` null; the list of ids is in ascending byte order, tested with a pair of ids whose order in byte order differs from their order in the default collation of the test database.
- R8. `notificationLevel` is the level that applies to the signed-in person, one of `all`, `mentions`, `none`: the stored value of the member row, or, when it is null, the default of the kind, which is the result of `effectiveNotificationLevel(kind, level)` of TOKI-028 R15 (`mentions` for a channel, `all` for a DM or group, D-046). `isMuted` and `isStarred` are the person's own booleans of the member row (D-103, D-143). Another member's values never appear. Check: two people in one channel, the first with `none`, muted and starred, the second with nothing set: each call returns its own values (`none`/true/true for the first, `mentions`/false/false for the second); a DM with a null level returns `all`; a stored `mentions` on a DM returns `mentions`; the body of the first call holds no value of the second person's row beyond what the second's own call returns.
- R9. There is no limit: every conversation that R6 selects comes in the one answer, in phase 1 (D-117). There is no pagination, no cursor and no `limit` query. Check: a fixture of 500 conversations (300 channels, 150 DMs, 50 groups) of one person returns all 500 and no `nextCursor` or similar key; the schema of R17 has no such key.
- R10. The six parts of the answer come from one consistent view. The handler opens one transaction, `READ ONLY` at `REPEATABLE READ`, and reads inside it, in this order: the caller's account (`user`, with the account read of TOKI-022 given the transaction), the caller's `workspaceId` (R4), the workspace, `members`, `conversations` and the event number. The account of `user` is therefore read inside the snapshot, not taken from the session check, which ran before the transaction and in another snapshot; the account on the request only tells the handler whose id to read. So `user.role` and the caller's own row in `members` come from one snapshot and agree, and a change committed by another request while the handler runs shows in none of the parts. If the account read inside the transaction shows the account as deactivated, the answer is 401 `account_deactivated` and nothing else. The handler takes no row lock (Design, "Locks"). Check: the builder has a test-only seam, an optional function called once with the transaction after the first read (the account); a test passes one that, through a second connection, commits the demotion of the caller from `admin` to `member`, a new account, a new channel with the caller as a member and a new member row: the answer holds none of the four changes, and `user.role` equals the role of the caller's row in `members`; a second call holds all four. Isolation level and access mode are shown by the database, not by a log: in the same seam call the test runs `show transaction_isolation` and `show transaction_read_only` on the transaction object and asserts `repeatable read` and `on`, and it runs an `update` of any row on the transaction and asserts that it fails with SQLSTATE `25006` (read-only transaction).
- R11. `eventNumber` is a non-negative integer: the number of the last event of the log at the moment of the view of R10. It is read by the function `readEventNumber(tx)` of `apps/server/src/bootstrap/event-number.ts`, which takes the transaction of R10. Until TOKI-036 builds the log, the function returns `0`, meaning "no event yet", and reads nothing. TOKI-036 replaces the body so that it reads the last event number with the transaction it is given; it owns the numbering (the first event is numbered 1 or higher, so `0` stays "none") and the test of it against a concurrent writer. The client keeps this number and asks for the events after it (TOKI-039). Two conditions are handed to TOKI-036 and go into its requirements and its tests, because a client that holds a number that is too high loses an event and gets no error: (a) every event is written in the same transaction as the change that causes it, so the snapshot of R10 holds both or neither (today `recordChange` of TOKI-029 R16 writes nothing, so no event exists); (b) the number that the read returns has no gap that a transaction still in flight can fill later: a sequence hands out numbers in order but they commit out of order, so a reader's highest number can pass a number whose row is not yet visible, and the numbering must be made so that this cannot happen (for example numbers taken under a lock that is held until the commit). Check: the answer holds `"eventNumber": 0` today; a test replaces `readEventNumber` by a fake that records its argument and returns 41, and the answer holds 41 and the recorded argument is the transaction object that the other reads used.
- R12. The answer holds no message, no unread count, no draft, no presence, no job title, time zone or status text, no preferences and no description of a conversation. A ticket that adds a field for a person or a conversation adds it to the schemas of R17, to the entry of R5 or R7, and to the tests of this ticket in its own change; the schema stays strict, so a field that is not in the schema is not returned. Check: the strict parse of R2 fails on every such key; a search of the body of the rich fixture finds none of the seeded description texts and none of the seeded display texts other than names.
- R13. The answer is sent with `Cache-Control: no-store` and a `Content-Type` whose media type is `application/json` (Fastify adds `; charset=utf-8`). The request changes nothing: after it, no row of any table has changed except `sessions.last_used_at` of the caller's session, which the session check sets (TOKI-022 R25), and the route is a `GET` that creates or ends no session (TOKI-022 R36). Check: the `Cache-Control` value and the media type of `Content-Type` (the text before the `;`) on a 200; a row count and a checksum of the rows of every table except `sessions` before and after a call are equal; the route-list test of TOKI-022 R36 passes with the route listed.
- R14. The number of SQL statements of the transaction of R10 does not grow with the size of the answer. What is counted: the statements sent on the connection that the handler checked out for its transaction, from `BEGIN` to `COMMIT` inclusive, counted by a wrapper around the database client that records each statement text on that connection. The statements of the session check of TOKI-022 (load the session, load the account, set `last_used_at`; its steps 2, 3 and 6) run before the handler and are not counted. At most 8 are counted, for a workspace of 3 conversations and for one of 500 conversations and 200 people: `BEGIN`, the account, the accounts by ids, the workspace, the people, the conversations, the event number, `COMMIT` is 8 once the log is read and 7 today (R11 reads nothing yet). Check: the test wraps the database client, calls the route on both fixtures, and asserts that the counted statements of the transaction are 7 or fewer today (8 once TOKI-036 reads the log) and that the two counts are equal; it also records the statements of the whole request and asserts that the two totals are equal, which proves that nothing in the route or the session check grows with the data. The seam of R10 is not used in this test.
- R15. Two reads are added to the modules, each taking the open transaction as its first argument and returning plain values. `modules/members/index.ts` exports `listPeople(tx, workspaceId)`, which returns the rows of R5 in the order of R5. `modules/conversations/index.ts` exports `listConversationSummaries(tx, workspaceId, userId)`, which returns the rows of R6, R7 and R8 in one statement: the conversations that have a member row of `userId` (a join on the caller's member row, in the query itself), the flags and the caller's stored level, mute and star (the stored level, not the one that applies, which the handler computes with the shared function), and, for a DM or group, `memberIds` made from the `dm_key` of the row by splitting it at the commas (the key holds exactly the ids of the members, in the order of R7, TOKI-028 R10 and R21), so no second statement and no list of ids is needed. Decided in this spec. The handler also uses two reads that other tickets build: `getAccountsByIds` (TOKI-029 R19) and the account read of TOKI-022 ("get an account by id"), which must accept a transaction as its client (Plan changes). The table definitions are not exported and no other module reads these tables. The export-list test of the `conversations` module is the one constant of names that each ticket extends (TOKI-030 concern 3); this ticket adds `listConversationSummaries` to it in its own change and does not use `listConversationIdsOfUser`, which returns archived conversations too and has no flags (Plan changes asks the owner of TOKI-028 to name a caller or drop it). Check: `pnpm lint` exits 0 with the boundary rules of TOKI-002; the export-list test lists the new name; database tests of each function on two workspaces (an account, a conversation and a member row of the second workspace are not returned) and on the fixtures of R5, R6 and R7, including a person with no conversation (an empty list) and a conversation whose member row was deleted.
- R16. The code that gathers the answer is in `apps/server/src/bootstrap/`, outside `modules/`, and imports only the `index.ts` files of `workspace`, `members` and `conversations` (TOKI-002 R17). The route is registered by `api/index.ts` under `/api/v1` (TOKI-004 R10). No module imports `bootstrap`. Check: `pnpm lint` exits 0; the route-list test of TOKI-004 R10 finds `GET /api/v1/bootstrap` and no path outside `/api/v1`; a search finds no import of `src/bootstrap` inside `modules/`.
- R17. `packages/shared/src/bootstrap/schemas.ts`, exported from the package index, exports the strict schemas `BootstrapUser`, `BootstrapPerson`, `BootstrapChannelEntry`, `BootstrapConversation` and `BootstrapResponse` (the shapes of R2, R3, R5, R7, R8) and the inferred types, written with the schema library TOKI-022 R38 uses. `BootstrapUser` is the `User` schema of TOKI-022 wrapped with `.strict()`, not a copy of its fields (R3). `BootstrapConversation` is the union of `BootstrapChannelEntry` and `DirectConversationEntry` imported from `packages/shared/src/direct-conversations.ts` (TOKI-030 R17), each strict. The server builds its answer as a value of these types and the client of TOKI-032 parses with the same schema. Check: type check: the builder returns `BootstrapResponse`; unit tests parse a valid body, and reject a missing key, a wrong `kind`, a `notificationLevel` of `loud`, a `memberIds` holding a string that is not a UUID, a null `memberIds` for a `dm`, a non-null `memberIds` for a `channel`, a `name` that is not null for a `dm`, an `isPrivate` of false for a `dm` or `group_dm`, an added key in `user`, and an `eventNumber` of -1 or 1.5.
- R18. The signed-in person sees everything they must and nothing else: the answer of one person never contains the id, name or topic of a conversation that R6 leaves out, and never contains a member id of a private conversation the person is not in. Check: a fixture where a private channel named `secret-plan` with topic `hidden topic`, a DM of two other people and an unjoined public channel `open-room` exist; the full text of the body of the person who is in none of them contains none of the three names, the topic or the ids; the body of a member of the private channel contains the channel.
- R19. A deactivated person appears in `members` with status `deactivated`, and the entries of the DMs and groups that include them stay in `conversations` with their `memberIds`, so the client can show the old DM with the person's name and the "deactivated" state (F25, F41, D-094); nothing is hidden by the server. Whether they are left out is a client rule of the screens that list people: the People screen (TOKI-079, which does not list deactivated people, F41, AC-116), the people picker (TOKI-034) and the mention suggestions (TOKI-050); TOKI-032 stores the list and TOKI-033 draws the conversation list, and neither filters people. Check: with a deactivated account in a DM with the caller, the DM is in `conversations`, its `memberIds` holds the account, and `members` holds the account with `deactivated`; after the account is reactivated the status is `active`.
- R20. With 200 people and 500 conversations (R9, R14), the JSON body is smaller than 250 KB before compression. The size depends on the lengths of the texts, so the fixture fixes them: ids are UUID text of 36 characters; the 300 channels have names of 20 characters and topics of 60 characters; the 150 DMs and 50 groups (3 people each) have no text; the 200 people have display names of 30 characters. At these lengths the body is about 176 KB. The bound is a regression guard chosen in this spec, not a product number (concern 6), and it is checked at these lengths only: with every channel name at its limit of 80 characters, every topic at its limit of 250 and every display name at 80 the body is about 251 KB, over the bound, so a second check on that fixture asserts a body under 400,000 bytes. Check: the two fixtures; the test reads the byte length of each body (UTF-8) and it is under 250,000 for the first and under 400,000 for the second.

## Design
### API
| Method | Path | Session | Purpose |
|---|---|---|---|
| GET | `/api/v1/bootstrap` | required, any role | The first load: the signed-in person, the workspace, the people, the person's conversations, the event number |

Shape (JSON). The example values are made up.
```
{
  "user": { "id", "email", "displayName", "role", "language" },
  "workspace": { "id", "name" },
  "members": [ { "id", "displayName", "role": "member" | "admin", "status": "active" | "deactivated" } ],
  "conversations": [ {
    "id", "kind": "channel" | "dm" | "group_dm",
    "name": string | null, "topic": string | null,
    "isPrivate": boolean, "isGeneral": boolean,
    "notificationLevel": "all" | "mentions" | "none",
    "isMuted": boolean, "isStarred": boolean,
    "memberIds": string[] | null
  } ],
  "eventNumber": 0
}
```
Decided in this spec: the key is `members` (the plan's word), the ids are strings, times are not returned (nothing in the first screen needs one), and the two shapes of an entry have the same keys, so the client reads one list. `members` is the list of people of the workspace, keyed `id` like the other people of this response; the member list of one channel (TOKI-029 R8) is a list of membership rows keyed `userId` with `joinedAt`, a different thing, and TOKI-032 reads each with its own schema. Decided in this spec.

### Where the code lives
`apps/server/src/bootstrap/` is a folder outside `modules/`, like `first-admin.ts` of TOKI-020. Reason: the answer needs `workspace`, `members` and `conversations`, and `members` already imports `workspace`; a module that called all three could make an import cycle, which fails at start-up when an export is used while a module loads. A file outside `modules/` may import each module's `index.ts` only (TOKI-002 R17), so no module reaches into another and nothing imports `bootstrap`. Decided in this spec.

### How an answer is built
1. The session check has already run and put the account on the request; the handler uses only its id (R10). It opens one transaction, `READ ONLY` at `REPEATABLE READ`.
2. It reads, with that transaction: the caller's account (R3), the caller's `workspaceId` with `getAccountsByIds` (R4), the workspace (R4), `listPeople` (R5), `listConversationSummaries` (R6 to R8), then `readEventNumber` (R11).
3. It computes `notificationLevel` for each conversation with `effectiveNotificationLevel` of `packages/shared` (R8) and builds the value of `BootstrapResponse` (R17). The schema is a strict type, not a runtime filter: the test parses the real body (R2).
4. It commits and sends the answer with the headers of R13.

Statements: `BEGIN`, the account, the accounts by ids, the workspace, the people, the conversations of the person (the member ids come from `dm_key` in the same statement, R15), the event number (none while it returns 0), `COMMIT`: 7 today, 8 once the log is read (R14 counts these, and only these, on the transaction; the three statements of the session check are outside it).

Why `REPEATABLE READ` and not separate reads: the client applies the events after `eventNumber` to the lists it got. If a channel were created between the read of conversations and the read of the number, the client would hold a number that already includes an event for a channel it never received. One snapshot makes the answer and the number agree. Decided in this spec.

Locks. The handler takes no row lock. A `READ ONLY` transaction cannot take `FOR SHARE` or `FOR UPDATE`, so `getAccountsByIds` is called without its `lock` option, and plain reads at `REPEATABLE READ` are never blocked by the row locks that the write operations take in the order of TOKI-024 R39 (`users` rows first, the invitation row last; TOKI-029 R15 the same). So a bootstrap never waits for an Admin's write and cannot take part in a lock cycle; a change that commits after the snapshot shows in the next call. Because it takes no lock, the role it reads is the committed role at the moment of its snapshot, as the reads of TOKI-029 do (their concern 13). Decided in this spec.

Why every person and every conversation come at once: D-117 for conversations (revisit past 500); for people, the app needs a name for every author, DM partner and mention, NFR-04 caps the first version at about 200 people, and a body of about 30 KB for them is cheaper than a request per name. Decided in this spec.

### What each part returns, and why
- Others' email addresses are not returned: the prototype's People card and profile panel show name, title, presence, local time and time zone and no address, and no decision shows an address to other members. The Admin page reads addresses through TOKI-024. The name of a newcomer is the part of their address before the `@` until they change it (D-150), so that part is returned to everyone as a name; the address itself is not. Decided in this spec.
- `notificationLevel` is the level that applies, not the stored value (null means the kind's default, TOKI-028 R14): the client needs one meaning, and nothing in phase 1 needs to tell "chose the default" from "never chose". When the request that saves the level is built (TOKI-028 concern 2), it sends one of the three values. Decided in this spec.
- Archived channels are not returned (F26: the channel "leaves everyone's list"; F09: when the last-viewed conversation was archived, #general opens). A member can still read one (F10) and TOKI-029 lists it in Browse with `isMember` true; how the client gets the name of an archived channel that a search result, an Activity or Later item or a file points to, when the store has no entry for it, is decided in concern 2.
- DMs of a person include every DM and group the person has a member row in, from the moment it is opened (TOKI-028 concern 6). Hiding one from the other person until its first message is concern 1.
- A channel entry carries no member count: F10's header shows the head count, and the count changes with every join and leave, so a number in the first load would be wrong until an event updated it, and no event exists before TOKI-036 to TOKI-040. For a DM or group the count is `memberIds.length`. For a channel the header reads `GET /api/v1/channels/{id}` (TOKI-029 R7, `memberCount`) when the channel is opened (TOKI-035). Decided in this spec.
- The entries of the three requests: this response, `GET /channels/{id}` and the join and create answers of TOKI-029 (`ChannelDetail`), and the answer of TOKI-030 (`DirectConversationEntry`, the entry of this response). The `DirectConversationEntry` is one shape. A `ChannelDetail` has no level, mute or star, so TOKI-032 builds the channel entry of its store from it: it keeps the level, mute and star it already holds for that id, and for a channel it does not hold (created or joined just now) it uses `effectiveNotificationLevel('channel', null)`, false and false, which are the values of a new member row. Decided in this spec; TOKI-032's spec is the place to repeat it.

### Errors
- No session, an ended session, a deactivated account: 401 with the codes of TOKI-022 (R1). An account that the session check found active and the snapshot shows as deactivated (R10): 401 `account_deactivated`.

- There is no 403 and no 404: every signed-in person is allowed, and the route has no id.
