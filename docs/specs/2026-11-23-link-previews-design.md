## Goal
Today an address in a message is only text, and, once TOKI-049 is built, a link. The journeys promise a card with the title, the description and the site name under the message a few seconds later, which the sender can remove (F12, AC-100). This work builds it: a job on the background queue opens the address from the server, reads the page, stores the card, and an event shows it to everyone who reads the message.
The hard part is that the server opens an address that a user chose. The rule of the technical design is "link previews refuse internal addresses". This spec turns it into checks that hold for an address written as a number, a name that points inside, a redirect, an address with a user name in front, and a name whose DNS answer changes between the check and the connection, and adds limits on time, size and rate (R2 to R10).

## Requirements
Which links, and the job
- R1. What gets a card. A message that is stored (`message_created`) or whose text changed (`message_edited`) gets a job when it is a `user` message with no `deletedAt` whose text holds at least one link by `findLinks` of TOKI-049 (R1 of that spec defines the function; its R3 defines the address: an `http://` or `https://` address, outside code, that `new URL` accepts, with no user name or password before the host). The candidates are the first `LINK_PREVIEWS_PER_MESSAGE` distinct `href` values in the order of the text (proposal: 1, concern 1; `packages/shared/src/link-previews/limits.ts`), after dropping each address longer than `LINK_URL_MAX` (2,048 characters). A message with no candidate gets no job. A system line and a deleted message get none. The function `linkCandidates(text): string[]` of `packages/shared/src/link-previews/` returns the candidates, and the change handlers (R17) and the job (R3) both call it. Check: a table test of `linkCandidates` and of the change handler (R12) with texts that hold no address, an address in code (`` `https://a.test` ``), `ftp://a.test`, `https://u@a.test`, an address of 2,049 characters, two addresses with the same `href`, and three different addresses: a job only where a candidate exists, and with the constant at 1 the first `href` only.
- R2. The job. `link-previews.fetch` is declared with `defineJob` (TOKI-064 R6) in `modules/link-previews/`: payload `z.strictObject({ messageId: z.uuid() })`, so no address, text or title is ever stored in the queue (TOKI-064 R7); `expireSeconds` 60, and the defaults of TOKI-064 R8 for the rest. A test checks `LINK_PREVIEWS_PER_MESSAGE * LINK_FETCH_DEADLINE_MS` is less than `expireSeconds * 1000`, so a job with the most candidates ends before the queue counts it as lost. It is added to `jobTypes` in `job-types.ts`, its handler is made by `createLinkPreviewHandler(deps)` and listed in `buildJobHandlers` of `job-handlers.ts`, as the contract table of TOKI-064 says. The handler needs four things besides `context`, so `JobDeps` (TOKI-064 R9) gains four fields, built in `buildJobDeps(config, db)`: `linkFetcher` (R6 to R8), `loadMessage`, `lockConversation` and `buildEntry` (R12). `buildEntry` is the one builder of TOKI-037 (`buildMessageEntry`) with every injected reader of the wave (reactions, pins, mentions, `readLinkPreviews`), because the entry that the job puts in its change must equal the entry of every other route; `buildJobDeps` therefore builds the same readers that `app.ts` gives the send route. The queue that adds the job is not a field of `JobDeps`: see R12 and Plan changes. The worker needs no new configuration area and no new environment variable (TOKI-064 R2). Check: the walking test of TOKI-064 R7 passes with the job in the registry; `buildJobHandlers` returns a handler for it; a search finds no `process.env` in the module; a built entry in the job equals the entry that the send route builds for the same message (one test with a reaction, a pin and a card).
- R3. What the handler does. In order: (1) read the message by id through the seam of R12; when it is missing, deleted or not a `user` message, finish with no write; (2) take the candidates of R1 from its text; (3) read the existing rows of the message (R14), delete each row whose `href` is no longer a candidate (the cards follow the text, concern 2), and drop each candidate that already has a row, whatever its status; (4) for each remaining candidate, in order: reuse a `ready` row of the same `href` made less than `LINK_PREVIEW_REUSE_HOURS` (24) hours ago (R10), which makes no request; else ask for a place under the limits of R10 (the short transaction of R10 that writes the row of `link_fetches`), and when it is refused write a `failed` row (R14) with the reason `rate_limited` or `host_limited` and no request; else fetch with the guarded fetcher (R4 to R8) and read the page (R9); (5) in one short transaction with the locks of R13, read the message again, do the deletes of step 3 (again, against the text as it is now) and, for each result whose `href` is still a candidate of the text now and whose message is not deleted, insert its row with `position` the largest `position` of the message plus 1 (0 when the message has no row), with `ON CONFLICT (message_id, href) DO NOTHING`; (6) when a `ready` row that is not removed was inserted or deleted, build the entry (R15) and call `recordChange` once with `message_link_previews_changed` (R16) as the last statement of the transaction. No network call is made inside a transaction. A failure of the fetch is an outcome, not an error: the fetcher never throws (R7), it returns `{ ok: false, reason }`, and the handler wraps the call of the fetcher and the reader of the page in one `try`: anything that is thrown there is logged as the outcome `failed` with the reason `fetch_error` and the handler goes on as for a failed fetch, so a bug in the guard code is never retried against the third-party site (concern 5). The one exception is the reason `aborted` (the signal of `context.signal` ended, TOKI-064 R13: the time of the job is over or the worker is stopping): nothing is known about the site, so the handler throws a plain error with the code `aborted` and the queue tries again; the retry is counted by the limits of R10 like any other fetch. Only a database error is thrown otherwise, from the database calls outside that `try`, so the queue retries it (TOKI-064 R8). The order of the cards after an edit that reorders the addresses is the order of `position`, which a reorder does not change (accepted: with the constant at 1 it cannot show). Check, with a fake fetcher and a real database: the six steps in turn; a job for a deleted message writes nothing; a message edited so that the address is gone between the read and the transaction writes no row; the same job run twice inserts the rows once and calls `recordChange` once; a fetch result is never written inside a transaction (the fake records the transaction state it is called in); a fake fetcher that throws a `TypeError` gives one call of the fetcher, a `failed` row with `fetch_error`, a completed job and no retry; a fake that returns `aborted` makes the handler throw; with the constant at 2, the edits `A B` to `C A` (B deleted, C inserted at position 1 while A keeps 0) and `A B` to `B A` finish with no unique violation.

The guard (the part that makes the fetch safe)
- R4. The address policy. `modules/link-previews/address-policy.ts` exports `isPublicAddress(ip: string): boolean`, `checkLinkUrl(href: string, policy): { ok: true } | { ok: false; reason }` and `LINK_POLICY` (`{ allowedPorts: [80, 443], isAllowedAddress: isPublicAddress }`). Nothing else decides whether an address may be fetched, and the fetcher takes the policy as an argument so a test can widen it (R25); the production wiring passes `LINK_POLICY` and a test checks that it does (R25). `checkLinkUrl` parses `href` with `new URL` once and applies these rules in this order, and the first that matches gives the reason: (1) `bad_url`: it does not parse; (2) `blocked_scheme`: the scheme is not `http` or `https`; (3) `blocked_userinfo`: `username` or `password` is not empty (so a name before the host is refused in a message and in a redirect, and the request never carries an `Authorization` header); (4) `blocked_port`: the port is not in `allowedPorts` (an explicit `:80` or `:443` is allowed on either scheme; `new URL` drops the default one); (5) `blocked_name`: the host is empty or longer than 253 characters, or is one of these names, before any lookup: `localhost`, a name that ends in `.localhost`, `.local`, `.internal`, `.lan`, `.home.arpa` or `.localdomain`, and a name with no dot (a single label such as `db`, `minio` or `server`, which is how a Compose service or a company host is written); the trailing dot of a fully qualified name is removed before these tests; (6) `blocked_address`: the host is an IP literal for which `isAllowedAddress` is false (`new URL` has already turned `http://2130706433/`, `http://0x7f.1/`, `http://0177.0.0.1/`, `http://127.1/` and full-width digits into `127.0.0.1`, and it keeps an IPv6 literal in brackets, which the check reads without them). A host that is a name and passes goes on to the guarded lookup (R6), whose refusal is also `blocked_address`. Check: Table A (R25), each row against `checkLinkUrl` with `LINK_POLICY`, the reason of the row and the order (a row with two faults gives the first of the order).
- R5. Which IP addresses are public. `isPublicAddress` is true only for an address that is a global unicast address, by exclusion for IPv4 and by inclusion for IPv6. IPv4 is refused in: `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10` (shared address space, which the company tailnet uses and where `100.100.100.200`, a cloud metadata address, sits), `127.0.0.0/8`, `168.63.129.16/32` (the Azure wire server, public in form and internal in use), `169.254.0.0/16` (link-local, with the cloud metadata address `169.254.169.254`), `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.31.196.0/24`, `192.52.193.0/24`, `192.88.99.0/24`, `192.168.0.0/16`, `192.175.48.0/24` (the last three of these four are the AS112 ranges, which are not a web), `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4` and `240.0.0.0/4` (which holds `255.255.255.255`). The deployment target is not stated, so the list names the addresses that a public cloud host exposes at a public-looking address; a ticket that learns of another adds it here. IPv6 is accepted only inside `2000::/3` (global unicast) and refused in `2001::/23` (protocol assignments, which holds Teredo `2001::/32`), `2001:db8::/32` and `3fff::/20` (documentation), `2002::/16` (6to4) and `2620:4f:8000::/48` (AS112). Everything outside `2000::/3` is therefore refused, which covers `::`, `::1`, `fc00::/7` (with the AWS IPv6 metadata address `fd00:ec2::254`), `fe80::/10`, `ff00::/8`, the IPv4-mapped form `::ffff:a.b.c.d` (so `::ffff:127.0.0.1`, `::ffff:10.0.0.1` and `::ffff:8.8.8.8` are all refused, a public IPv4 address in mapped form included, by design: write it as IPv4), the IPv4-compatible form `::a.b.c.d` (`new URL` writes `::127.0.0.1` as `::7f00:1`) and the NAT64 form `64:ff9b::/96`. A string that is not an IP address gives false. The tests compare against a table written from these ranges, not against the code under test. Check: Table A, address rows, with the first and last address of each range and one address just outside it.
- R6. Resolve once, connect to what was checked. The fetcher connects to a host name only through a `lookup` function of its own, `createGuardedLookup(resolve, isAllowedAddress, deadline)`, given to the socket (`lookup` option of `node:https` and `node:http`). In production `resolve` is made from `dns.promises.Resolver` (the c-ares resolver: `resolve4` and `resolve6` asked together, so there is no use of `getaddrinfo` and its four-thread pool, which cannot be aborted and which an attacker's slow DNS server could hold, no read of `/etc/hosts` and no search domains of the operating system); a name that gives no address of either kind is a failure with the reason `dns_error`. The lookup is raced against the deadline of R8 and against `context.signal`, and an answer that comes late is dropped, never used. The function asks the resolver for every address of the name, refuses the whole name with the reason `blocked_address` when any one of them is not allowed (a name with one public and one internal address is refused, so an attacker cannot make the choice), and otherwise answers with the checked addresses and nothing else. The socket connects to one of them; no second resolution is made for that request, so an answer that changes after the check cannot be used (DNS rebinding). The function honours the `all` option of Node's `autoSelectFamily`. A host that is an IP literal does not call `lookup`, so R4 checks it before the request is made. TLS keeps the host name for the certificate and the SNI, with the default validation: no option turns the validation off (a search of the module for `rejectUnauthorized` and `NODE_TLS_REJECT_UNAUTHORIZED` finds nothing); the fetcher takes one more option, `tls: { ca }`, that only adds a trusted authority and exists so a test can use its own. Check: a fake resolver that answers a public address the first time and `127.0.0.1` the second: the request connects to the first and the resolver is called once; a fake that answers `[public, 10.0.0.5]` gives the refusal and no connection; a resolver that answers after the deadline is dropped and gives `timeout`; a name with no answer is `dns_error`; the layers (b) and (c2) of R25 observe the sockets.
- R7. The request. Only `GET`, on a connection of its own: `agent: false` and `Connection: close` (Node's global agent keeps sockets alive, and a pooled socket would outlive the deadline). The request is built from the same parsed `URL` object that R4 checked, never from a string parsed again: its `hostname` (without the brackets of an IPv6 literal), its `port` and its `pathname + search`, so the host that was checked is the host that is connected; no `auth` option is ever given. The headers are `User-Agent: TokiLinkPreview/1.0` (a constant, with no workspace name, address or version of the server), `Accept: text/html,application/xhtml+xml;q=0.9`, `Accept-Language: en`, `Accept-Encoding: identity`, and the two that Node adds, `Host` and `Connection`. No cookie, no `Authorization`, no `Referer` and no header taken from the message or from the sender. A response with a `Content-Encoding` other than `identity` is a failure (`unsupported_encoding`), which is how a decompression bomb is refused. The status must be 200 to 299 after the redirects; any other status, 401 and 403 included, is a failure (`http_status`). The `Content-Type` must be `text/html` or `application/xhtml+xml` (any case, parameters allowed); any other is a failure (`not_html`). Nothing is requested besides the page: no image, favicon, script, stylesheet or `oembed` address is read from it (concern 4). The body of a redirect response is destroyed, not read. `createLinkFetcher` never throws: any error, a refused connection, a reset, a TLS error (`tls_error`), a stream error in the body, `ERR_INVALID_URL` or a refusal of the lookup, comes back as `{ ok: false, reason }`, with the reason `network_error` for an error that has no code of its own. Check: a real local server under the test policy records the request: method, exactly the six headers above, no body; one case for each failure above; a socket reset and a refused port give `network_error`; a fetcher run with `agent` unset is caught by a test that reads the request's `agent` option; the same HTTPS test as in R25 (b) for SNI and the certificate.
- R8. Redirects and limits. The fetcher follows a redirect by hand: for the statuses 301, 302, 303, 307 and 308 with a `Location`, it resolves the target against the current address, and then runs the whole of R4 to R7 for the new address (the scheme, the user name, the port, the name rules, the literal check, the guarded lookup), so every hop is checked as the first one was; a target with a user name or password is refused (`blocked_userinfo`) and no hop carries credentials. At most `LINK_MAX_REDIRECTS` (3) redirects are followed; a fourth, a loop, a `Location` that is missing or is not an `http` or `https` address, and a redirect to a refused address are failures (`too_many_redirects`, `bad_redirect`, and the reason of the refusal: `blocked_address`, `blocked_name`, `blocked_port`, `blocked_scheme` or `blocked_userinfo`). Time: one deadline of `LINK_FETCH_DEADLINE_MS` (8,000) from the start of the fetch of one address, for the lookup, the connection, the redirects and the body together; when it passes, the socket is destroyed and the result is `timeout`. The fetcher also takes the `AbortSignal` of `context.signal` (TOKI-064 R13): when it aborts the socket is destroyed and the result is `aborted`. Size: the fetcher reads at most `LINK_MAX_BYTES` (524,288) bytes of the body and then stops reading and closes the socket; what it has read is used (R9), a body longer than that is not a failure. The deadline uses the `timers` of the fetcher (an object with `after(ms, fn)` that returns a cancel function, the shape of `Timers` in `client-core`), never a global timer, so a test fires it by hand; the one file that gives the real `timers` (`timers.ts` of the module) is the one place of the module that calls `setTimeout`. Check: a redirect chain of 3 ends in a result and of 4 in `too_many_redirects`; the redirect targets `http://169.254.169.254/latest/meta-data/`, `http://localhost/`, `file:///etc/passwd`, `gopher://x`, `http://a:b@example.com/` and a name that the fake resolver maps to a private address are each refused with the reason of Table A at once (the first four need no server: the pure rule refuses them), and the redirect to a real local port and to a name mapped to `127.0.0.1` is proved by the layer (c2) of R25 with the reason `blocked_address` and zero connections on the second server; a server that never answers, and one that sends one byte at a time, end with `timeout` when the test fires the timer and the socket is destroyed (the server sees the close); an abort of the signal ends with `aborted`; a server that sends 5 MB reads at most 524,288 bytes of it (the server sees the connection closed before it finished) and gives the title found in the first bytes.
- R9. Reading the page. The reader of the page (`html.ts`) is the one place that turns bytes into text. The bytes are decoded as UTF-8 unless the `charset` of the `Content-Type`, or else a `<meta charset>` or `<meta http-equiv="Content-Type">` in the first 1,024 bytes, names another label that `TextDecoder` knows; an unknown label means UTF-8. The text is read by a tolerant HTML tokenizer (the dependency of R20), which never builds a document and never runs a script or loads a resource; the reader stops at `</head>` or at the end of what was read. It takes the first present value of each field: title: `og:title`, `twitter:title`, the `<title>` element; description: `og:description`, `twitter:description`, `<meta name="description">`; site name: the host of the card's own `href` (the parsed address the sender wrote, never the final address after a redirect and never a value that the page gives, so a page cannot name itself "Your Bank" in the one field that a reader trusts first; proposal, concern 11), without a leading `www.`. Each value is cleaned: character references decoded by the tokenizer, every run of white space made one space, every character removed that is a control (`\p{Cc}`), a lone surrogate (`\p{Cs}`; the character reference of a surrogate becomes U+FFFD, so the text is always valid UTF-8 for Postgres) or a format character (`\p{Cf}`) except U+200C and U+200D (the joiners that build emoji sequences and the letters of Persian and Indic scripts), which keeps the removal of the bidirectional controls U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069 and U+061C and of the invisible spaces such as U+200B, U+2060 and U+FEFF, then trimmed, and cut to `LINK_TITLE_MAX` (200), `LINK_DESCRIPTION_MAX` (300) and `LINK_SITE_MAX` (100) code points, with `…` as the last character of a cut value (the cut counts in the limit). A value that is empty after cleaning is absent. The result is `ready` when the title or the description is present; a missing title is then the site name. When both are absent the result is `failed` with the reason `no_text`. The values are text: they are stored and sent as text and drawn as text (R22), and no mark, link or mention of the formatting work is read in them. Check: Table B (R25) against the reader; a title with `<script>`, `<img src=x onerror=alert(1)>` and `&lt;b&gt;` stays as those characters; a title with U+202E and U+200B loses them and one with a family emoji (joined by U+200D) keeps it; a title with `&#xD800;` has U+FFFD; 200 and 201 characters, and 300 and 301, at the limits; a 5 MB page whose `<title>` is in the first 1,000 bytes; a page with the `<title>` after 600 KB has none (`no_text`); a page with `og:site_name` "Your Bank" gives the host.
- R10. Limits on the requests. The server sends a request only after it has written a row of the table `link_fetches` (R14: `id`, `workspace_id`, `author_id`, `host`, `started_at`), so the count includes the fetches in flight and does not fall when a message or a card is deleted. The step is one short transaction before the network call: it takes `pg_advisory_xact_lock` on a key made from the sender's `author_id` (so two jobs of one sender cannot both read 9 and both pass), deletes the rows of `link_fetches` older than one hour, counts the rows of that sender with `started_at` inside the last `LINK_SENDER_WINDOW_SECONDS` (60) seconds and the rows of that `host` (the host name of the parsed `href`) from every sender inside the same window, and, when both counts are below their caps, inserts its row with the time of the clock of TOKI-008 and commits. The caps are `LINK_SENDER_RATE` (5, proposal in concern 10) and `LINK_HOST_RATE` (10); a candidate that would pass either gets a `failed` row with the reason `rate_limited` (the sender's) or `host_limited` (the host's) and no request. Every fetch is counted when it starts, a retry of the job included, and a `failed` or a `ready` result does not change the count. This keeps one person from using the server to send a flood of requests to one site or many, and keeps a crowd of senders from sending more than `LINK_HOST_RATE` requests a minute to one site. A candidate whose `href` has a `ready` row less than `LINK_PREVIEW_REUSE_HOURS` (24) hours old, in any message, gets a copy of that row's title, description and site name with no request and no row of `link_fetches`; the reuse is an economy and not a limit, because a delete of the message removes the row that it would copy. Check: with the controllable clock of TOKI-008, 5 candidates of one sender in a minute are fetched and the 6th is `rate_limited` and one minute later fetches; the sequence post, delete the message, post again, repeated 6 times inside a minute gives `rate_limited` at the 6th post; an edit that swaps the address in a loop does the same; two jobs of one sender run together on two connections with 4 fetches already counted do not both fetch (one `rate_limited` at least: the advisory lock); 11 senders that post one address of one host in a minute give 10 fetches and one `host_limited`; the count includes a fetch that has not ended (the fake fetcher is held open); a second message with the same address within a day makes no request and has the same card; after 25 hours it makes one; rows of `link_fetches` older than an hour are gone after a job.
- R11. Logging. The handler logs one line for each address with the fields `job`, `jobId`, `attempt`, `host` (the host name only, as parsed), `outcome` (`ready`, `failed`, `skipped`) and `reason` (the codes of R4 to R10, and `fetch_error`). No line holds a path, query string, fragment, title, description or the message text, because an address can carry a token. The error of a thrown database failure holds identifiers and codes only (TOKI-064 R18). Check: a captured log of a ready, a refused and a timed-out address, with a path `/secret?token=abc` in each, holds none of that text.

Seams, the table and the entry
- R12. The module and its seams. `modules/link-previews/index.ts` is the only public entry: `linkPreviewJob`, `createLinkPreviewHandler`, `createLinkPreviewChangeHandlers`, `readLinkPreviews`, `createLinkFetcher`, `registerLinkPreviewRoutes`, `isPublicAddress` and `LINK_POLICY`, with their types. The module reads the table `messages` and the conversation row only through functions that the composition gives it: `loadMessage(tx, id, { lock })` (returns `{ id, conversationId, authorId, text, deleted }` or `null`), `buildEntry(tx, messageId)` (the `buildMessageEntry` of TOKI-037, R15) and `lockConversation(tx, conversationId)` (the conversation lock that TOKI-047 uses), supplied by `job-deps.ts` (the three of them and `linkFetcher` are the new fields of `JobDeps`, R2) and by `app.ts` for the route; the `messages` module gains the export of `loadMessage` and accepts `readLinkPreviews` as one more injected reader of its builder, as it does for reactions and pins. ### Why the guard is built this way
- Checking the name and then letting the HTTP client resolve it again is the classic hole: the first answer is public and the second is `127.0.0.1`. The fetcher therefore resolves once, in its own `lookup`, and the socket can only connect to an address that passed (R6). A check on the URL string alone is never enough, so there are three independent checks: the string (R4), the resolved addresses (R6) and the address of every redirect hop (R8). The tests keep them independent: each is proved in a layer where the others cannot refuse first (R25).
- The check is by what the address is, not by a list of names to refuse: `http://2130706433/` and `http://[::ffff:7f00:1]/` are the same machine as `127.0.0.1`, and the IPv6 rule accepts a small block and refuses everything else, so a form that nobody thought of is refused (R5).
- Everything that can be unbounded is bounded: time (one deadline, and the job's signal), size (one cap), redirects (3), compression (refused), the requests of one sender and to one host (R10, counted before the request, so a delete does not reset them) and no error is retried against the third-party site (R3). Concurrency is the job's 2 handlers (TOKI-064 R8): one sender can hold one of them for at most `LINK_SENDER_RATE` times 8 seconds a minute, which is accepted (concern 10). The result of a refusal is silent for the user, who sees no card and no error, so the app does not tell anyone which internal names exist (a person sees the same thing for an internal host, a dead host and a page with no title).
- The page is read with a tokenizer that makes no document and runs nothing, and its texts are stored as text and drawn as React children, so a hostile page can put characters in a card and nothing more (R9, R22).

## Testing
- Test-first. Pure tests need no database or network: Table A, Table B, the cleaning of texts, the candidate rule, the schema. Tests of the fetcher use a real local server and fake resolvers and timers (R25). Tests of the job, the change handlers, the route and the entry use a real database (`createJobsTestDb()` of TOKI-064 R5 for the job tests, the shared test database for the rest) and a recording `recordChange`.
- Every requirement has a check in its text; the guard's checks name what the test must observe on the other side of the socket (zero connections, the closed socket) and the reason that came back, and each guard rule has a layer in which it is the only one that can refuse (R25), so a check cannot pass by a function that returns "refused" for everything or by another rule refusing first. The allowed rows of Table A pass the pure check, and the real-server tests fetch from a mapped fake name under a test policy.
- No real timer and no real network. The real `timers.ts` is covered by one test that its `after` returns a cancel function that stops the callback, run with a fake timer host as TOKI-032 R25 does.

## Data safety
- The server sends one request to an address that a user chose. The three layers of R4 to R8 keep it to public web servers on ports 80 and 443; the request carries no cookie and no identity (R7); the only thing sent about the app is the constant `User-Agent`.
- The job queue holds the message id only (R2), and no log line holds an address path, a title or a text (R11).
- The stored title, description and site name are third-party text (the site name is the host that the sender wrote). They are limited in length, cleaned of control and bidirectional characters, stored and drawn as text (R9, R22), and removed when the message is deleted (R17). They are readable by the people who can read the message only (R15, R16).
- The server reads a page on behalf of a person; the site sees the server's address and the constant `User-Agent`, never the person, the workspace or the conversation. Whether a link in a direct message or a private channel may be read at all is concern 3.
- A page may not be what its sender saw: the card shows what the server read at one moment (concern 5).

## Areas of concern
1. How many cards one message gets. Not decided. The log gives no number: the journeys say "a preview card appears" (AC-100) and the prototype's `att` list can hold several. The build reads one constant, `LINK_PREVIEWS_PER_MESSAGE`. Proposal, not a decision of the product owner: 1, the first address of the text, because every extra card is another request to another site and another block under a short message. Owner: Thanh Truong (product owner).
2. The cards when a message is edited. Not decided. The log says nothing: F16 and the edit work say the edit changes the text, and a card is not text. R17 builds this proposal: a card whose address is no longer in the text goes away, a card the sender removed stays removed, and an address that becomes the first candidate gets a card. The alternative is that a card never changes after the first fetch. Owner: Thanh Truong (product owner).
3. Links in direct messages and private channels. Not decided. D-014 and AC-100 do not exclude any kind of conversation, and the server reads the page on every one, so a site hears from the server that someone posted its address. Proposal: the same rule for every kind of conversation, as the journeys do not distinguish them. A stricter rule (no previews in a DM or a private channel) is one condition in R1. Owner: Thanh Truong (product owner).
4. No image in the card. Decided in this spec: the card has no image, no favicon and no embed. Reason: D-014 and the journeys name title, description and site name, and the prototype's card (line 1380) has none; an image means the server reads a second address from a page it does not trust, and the browser of every reader loads a remote resource, which tells the other site who is reading. Owner: Thanh Truong.
5. A failed fetch is not retried. Decided in this spec. A site that is down, slow or refuses gives no card and the job ends in success (R3), and so does an error that nobody mapped (the reason `fetch_error`); the queue's retries are for database errors and for an abort by shutdown only. Reason: the card is a convenience, a retry minutes later arrives long after the person has read the message, and repeated requests to a site that said no are what the limits of R10 exist to prevent. A person who wants another try posts the address again. Owner: Thanh Truong.
6. Who removes the card and when it disappears. Not decided for an Admin. F12 says "the sender", and the log gives no rule for removing a card. D-047 does not give an Admin an extra right: it says that deleting messages, removing people and archiving apply only where the Admin is a member, so an Admin who is a member can delete another person's message. R19 builds the proposal, the author only, by `canEditMessage`; a hostile or phishing card in someone's message then stays until the whole message is deleted, and an Admin who is a member can delete it. The alternative is the author and an Admin who is a member of the conversation, as `canDeleteMessage` gives, which changes R19 step 5 and R23. The card goes when the server answers, not before (R23), because a card that comes back after a failure is worse than a short wait. Owner: Thanh Truong (product owner).
7. Who draws the card, and where. Decided in this spec: TOKI-062 owns `.card`, `LinkCard`, the block `.att`, the place under the text, the order and the rule that a message with a card is not grouped; this work owns the data, the job, the event, the removal and the body of the seam file `link-cards.tsx` (`LinkCards`, `hasLinkCards`), with the remove button in the `action` slot of `LinkCard`. This work adds no member to `messageExtensions` and asks nothing of TOKI-042. Owner: Thanh Truong.
8. The Vietnamese wording of the button, and the English too. Not decided. The prototype has no button for removing a card and D-139 treats a wording that the prototype lacks as a proposal. Proposal: English "Remove preview" and "Could not remove the preview"; Vietnamese "Xóa bản xem trước" and "Không thể xóa bản xem trước". Owner: Thanh Truong (product owner).
9. Network limits outside the code, and no off switch. Not decided. Proposal: the three layers of R4 to R8 are the defence, and a firewall rule on the machine that runs the worker, which refuses the worker's traffic to the cloud metadata address `169.254.169.254` and to the machine's own private networks except the database host, is a second one; that rule, the worker's network in Compose and any outbound proxy are TOKI-084's (Plan changes holds the line for it); this ticket adds no environment variable and no switch to turn previews off, and an operator who must stop them removes the job from `job-types.ts` in a release. The technical design says "refuse internal addresses" and does not ask for an off switch; whether there is none is a product and configuration choice that the log does not make. Owner: Thanh Truong (product owner).
10. The figures of the guard. Decided in this spec, with no product figure to follow: 8 seconds in all, 512 KiB, 3 redirects, ports 80 and 443, 5 fetches a minute for each sender and 10 a minute to one host for all senders, reuse for 24 hours, texts of 200, 300 and 100 characters. Reasons: 8 seconds is long enough for a slow but honest site and keeps the card within about 10 seconds of the message once the queue's 2-second poll is added (the journeys say "a few seconds"); 512 KiB holds the head of almost every page and bounds memory for two handlers; 3 redirects cover `http` to `https` and `www`; 80 and 443 keep the server from probing other services on a public machine; 5 a minute for a sender is more than a person writes and bounds the time one sender can hold a handler to 40 seconds a minute of the two handlers' 120; 10 a minute to one host keeps a crowd of senders from sending a site more than that; many senders posting many different slow hosts can still fill the queue, which is accepted for a company of about 200 people; a day of reuse keeps one popular address from being read for every message. Each is one constant in `limits.ts` that the owner may change with no other change. Owner: Thanh Truong.
11. What the card says about the site. Not decided. The card shows what a page says about itself in the title and the description, and a hostile page can name itself anything ("Your bank"). The defences are that the title link opens the address the sender wrote, in its parsed form (the row's `href`, not the final address after a redirect, so a redirect cannot change where the card's link goes), that the texts are plain text, and that control and bidirectional characters are removed (R9). The site name is the field a reader trusts first, and the page's own `og:site_name` can differ from the host. Proposal, built in R9: the site name is the host of the `href`, never a page value. The alternative is the page's `og:site_name`, else the host, as the prototype's card (`Tailnet only`) suggests, which is one change in R9. Owner: Thanh Truong (product owner).
