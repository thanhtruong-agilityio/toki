# Performance measurement design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/performance-measurement.md (Thanh Truong)
Ticket: TOKI-089

## Goal
The product owner accepted six speed figures with 200 people online as the load (D-113, NFR-13), and the technical design says a load script "creates 200 people, 50 channels and 1 million messages to measure the performance targets before release". The tests of the earlier tickets read plans and count statements and never time anything, and the merged specs of the message tables, the gateway, the search index, the search request, the client engine and the message list each hand the real measure to this ticket.
This ticket builds that script: one command that fills a fresh production stack of TOKI-084 with the load, one command that keeps 200 people connected and measures the six figures through Caddy, and one result file that names, for each figure, the target and its source, how it was measured, the samples, the value and whether it is under the target. It changes no code of the app.
The measure is a decision of a person on a machine of the first VPS, not a check of the pull-request pipeline: its result depends on the machine, and a shared runner would make the figures noise.

## Scope
- In:
  - `tools/performance/`: the load command, the measure command, the file of targets, the file of the scenario, the readers and the writers of the result, and their tests (R1 to R3).
  - The data: 200 people, 50 channels, 1,000,000 messages, two extra readers with 501 and 1,001 conversations, 203 sessions made for the run (R4 to R8).
  - The load of 200 connected people and the six measures, each with its method (R9 to R15).
  - The result file and the page that tells a person how to run it and read it (R16, R19).
  - The rule about timing: the script uses real time, its tests never wait for a timer (R17, R18).
- Out (not now):
  - The production image, the stack, its memory limits and its Caddyfile: TOKI-084 owns them. This ticket reports the memory each service used (R16) so a person can tune TOKI-084's starting limits; it changes none of them.
  - Fixing a figure that is over its target. A figure over its target is a finding with its numbers; the fix is a ticket of the owner of that part (concern 5 says who decides about the milestone).
  - A run in the pull-request pipeline, a nightly run, a threshold that fails a build: not built (R16, concern 4).
  - The seed of TOKI-081. It is for development, refuses a database that holds other data and writes 8 people (TOKI-081 R2, R14, R15); this load is separate and shares nothing with it (R3).
  - Replies, reactions, pins, mentions, files and unread counts in the loaded data (R6, concern 8 says why).
  - The fold of the shared-items list of TOKI-063 (computed per row with no index, left by that spec to this measurement): the loaded data has no files (R6, concern 8), so it is not measured here; it needs a load with files, a later ticket of the owner of TOKI-063.
  - Load of other kinds (many sign-ins, mail, uploads, the worker's image work): not a target of D-113.
  - The sign-in path (codes and mail): the people of the run get sessions directly (R8).

## Requirements
- R1. Place and commands. The code is in `tools/performance/` as ES modules (`.mjs`), as `tools/bundle-size/` is. Plain `node` cannot import `@toki/shared`: its `exports` point to `src/index.ts` and the files inside import each other with `.js` specifiers for `.ts` files, and no file under `tools/` imports an `@toki/*` package today. This ticket needs three things from the package (`ACTIVITY_SEND_INTERVAL_MS`, R9; `createUuidV7Generator`, R10; `createTestClock`, R17), so `measure.mjs` and the tests run through `tsx`, as `apps/server` already does (its `package.json` pins `tsx` 4.23.15): the root `package.json` gains `tsx` (the same exact version) and `@toki/shared` (`workspace:*`) in `devDependencies`, and the scripts `perf:load` (`tsx tools/performance/load.mjs`), `perf:measure` (`tsx tools/performance/measure.mjs`) and `test:performance` (`tsx --test tools/performance/*.test.mjs`), which the root `test` script runs after its own `node --test` list. `load.mjs` and `load-sql.mjs` import no workspace package (R6 builds the ids in SQL), so the database test of R18 starts them with `node`. No job is added to `.github/workflows/ci.yml` and `changed.sh` is not edited. The folder is not copied into either image (TOKI-084 R6, R7 copy only what they list). Check: a test reads the root scripts and `ci.yml`: the three scripts exist, `tsx` and `@toki/shared` are in the root `devDependencies` at exact versions, no step of `ci.yml` names `perf:`; a test that imports `@toki/shared` from `tools/performance/` runs under `pnpm test:performance`. That the pull request edits neither `ci.yml` nor `changed.sh` is a review item, not a test (a test cannot see the diff of the pull request).
- R2. The six targets are written once, in `tools/performance/targets.json`: for each, `id`, `text`, `number`, `unit`, `statistic`, `source`, `statisticIsProposal` (true when the log gives no statistic, see concern 2) and, for `delivery`, `measuringPointIsProposal` (true: the log does not say whether the judged figure is the time on a socket or on a screen, concern 9). The numbers and sources are:
  `delivery`: 150 ms, p95, D-113, NFR-13; `firstLoad4g`: 2,000 ms, D-113, NFR-13; `initialJs`: 200,000 bytes gzip, D-113, TOKI-006 R10, TOKI-007 R7; `switchOpened`: 100 ms, D-113, NFR-13; `scroll60`: 60 frames per second, D-113, NFR-13; `search`: 200 ms, p95, D-113, NFR-13.
  The `statistic` of `firstLoad4g`, `switchOpened` and `scroll60` is the proposal of R12 to R14 and carries `statisticIsProposal` true. The result file (R16) copies the entry of each target; no number of a target is written anywhere else. A percentile of `n` values is the nearest-rank one: the value at position `ceil(p × n)` of the sorted list. Check: a test reads the file and compares each id, number, unit, source and the two flags with the list above (so a changed number fails a test and must be a change of this spec); a second test reads `lib/verdict.mjs`, `lib/page-probes.mjs` and `measure.mjs` and finds in them no numeric literal other than 0 and 1 and no literal equal to a target number: the verdict takes its number from its parameter, and R14's frame limit is `Math.ceil(1000 / targets.scroll60.number)`. The scenario's own numbers (200 people, 100 switches, 60 seconds of wait) live in `scenario.json` or in named constants and are not searched.
  `delivery`: 150 ms, p95, D-113, NFR-13; `firstLoad4g`: 2,000 ms, D-113, NFR-13; `initialJs`: 200,000 bytes gzip, D-113, TOKI-006 R10, TOKI-007 R7; `switchOpened`: 100 ms, D-113, NFR-13; `scroll60`: 60 frames per second, D-113, NFR-13; `search`: 200 ms, p95, D-113, NFR-13.
  The `statistic` of `firstLoad4g`, `switchOpened` and `scroll60` is the proposal of R12 to R14 and carries `statisticIsProposal` true. The result file (R16) copies the entry of each target; no number of a target is written anywhere else. Check: a test reads the file and compares each id, number, unit and source with the list above (so a changed number fails a test and must be a change of this spec), and a search of the other files of the folder finds none of the six numbers as a literal used for a verdict.
- R3. The load command is separate from the seed. `load.mjs` imports nothing from `apps/server/src/seed/`, writes no account named in `PROTOTYPE_SEED` and never uses the domain `hugepig.example`; its 199 added accounts are `perf-002@perf.test` to `perf-200@perf.test` (the domain `.test` is reserved and routes nowhere). Check: a test reads the import lines and the address list of the generated SQL (R7).
- R4. Where it works and what it refuses. The load runs on the machine of the stack, with Docker, and reaches Postgres through the stack: by default `docker compose -f docker-compose.prod.yml exec -T postgres psql -v ON_ERROR_STOP=1 -U <POSTGRES_USER> -d <POSTGRES_DB>` with the SQL on standard input, because Postgres has no published port (TOKI-084 R10); the environment variable `PERF_PSQL` replaces that command line for a database that is reachable some other way (the development Compose file, a test database). Before it writes anything it reads and refuses, with exit code 1 and one line naming the condition, when any of these holds: the table `messages` holds a row; the table `users` holds other than one row (the first administrator of TOKI-020, who is person number 1 of the scenario, R5); the table `workspaces` holds other than one row; the conversation `#general` is missing; the index `messages_search_idx` of TOKI-069 R4 is missing (the search figure would mean nothing without it). There is no flag that overrides a refusal. To measure again from scratch a person removes the volumes (`docker compose down -v`) and starts the stack. Check: a database test (R18) runs the load against a database that fails each condition in turn and finds exit 1, the named condition and no row written; a run on a database that meets them loads.
- R5. People and channels. The load adds 199 accounts to the 1 first administrator, so 200 active accounts exist: `role` `member`, `status` `active`, `language` `en`, the `display_name` `Perf 002` to `Perf 200`, an address `perf-NNN@perf.test` (`perf-002` to `perf-200`); the first administrator keeps their account and address and is the person number 1 of the scenario. It creates 49 public channels named `perf-01` to `perf-49` (lower-case letters, digits and hyphen, the rule of TOKI-029 R3), so with `#general` there are 50 channels (technical design, Testing). Every account is a member of `#general`; the other channels have between 5 and 100 members each, chosen by a fixed rule from the seed of R6 and listed in the result (R16), so the same seed gives the same membership; the two readers of R7 are members of all 50. Each row is one the real tables accept: creation times from the clock of the run, the keys and checks of TOKI-019, TOKI-028 and TOKI-024 hold. Check: the database test counts 200 accounts, 50 channels, the member counts of `#general` (200) and of every other channel (5 to 100), and that every member row has its account and conversation.
- R6. Messages. The load inserts exactly 1,000,000 rows into `messages`, all `kind` `user`, top-level (no `parent_id`, `also_in_channel` false, no `edited_at`, no `deleted_at`). The split is fixed by the seed: `#general` and each of the 49 channels have at least 10,000 messages (so a channel of 10,000 exists for R14 and R15), the remaining messages are spread by a fixed weight, and the 951 small private channels of the readers (R7) hold 20 each (19,020 in all, part of the million). The author of a message is a member of its conversation. `body` is Vietnamese-like text of 3 to 40 words, built from a seed so a given seed gives the same text on every run. The words come from a vocabulary of 2,000 made by a fixed rule from a list of 150 syllables (about half with diacritics), and each word of a message is drawn by rank with a weight of 1 ÷ rank (a Zipf shape); the 20 words of rank 1 to 20 are the "common" words of R13, the words of rank above 1,500 are its "rare" words, and the starts of R13's `short` group are the two-letter starts of the syllables. This distribution is a proposal (concern 7), written in `scenario.json` and in the result; it exists so that "rare", "common" and "short" mean a number of matching rows, which R13 reports for each query. `created_at` is spread evenly over the 730 days that end one hour before the run starts, taken from the clock the command is given (it never reads the machine's time in a way a test cannot replace). `id` is a UUID version 7 built in the statement from the row's own `created_at` (48 bits of the time in milliseconds, then random bits, with the version and variant bits set: `gen_random_uuid()` bytes with the first six replaced and the version nibble set to 7), the shape the app writes (TOKI-037 R4), so the primary-key index measured has the locality of the real one and not that of a version-4 key; TOKI-036 R2 takes any id. Check: the database test counts the rows (at the small scale of R18: the count asked for), the minimum per channel, the author membership, that every row satisfies the real checks of `messages` because the real table took them, that every `id` has version nibble 7 and sorts in the order of `created_at` to the millisecond, and that two runs with one seed give the same bodies and counts; a test of the word rule checks the rank weights and that each of R13's groups matches at least one row at the small scale.
- R7. The two readers and the bulk write. The account `perf-199` (reader A) is a member of the 50 channels and of the small private channels `perf-s-001` to `perf-s-451`, so it belongs to 501 conversations, one past the number at which D-117 says the first load is to be reconsidered ("revisit past 500 conversations"); the account `perf-198` (reader B) is a member of the 50 channels and of `perf-s-001` to `perf-s-951`, so it belongs to 1,001 conversations, the size that takes the group-of-1,000 branch of `searchMessageIds` (TOKI-069 R11, TOKI-070 concern 6). Each small channel has reader B and one other person (and the first 451 also have reader A). The counts 501 and 1,001 are proposals (concern 11). The messages are written by the database from a statement `INSERT … SELECT … FROM generate_series(…)` in batches of 50,000 rows, each batch one statement `BEGIN; … COMMIT;` of its own, so no row passes through the script (the 1,000,000 take about 20 batches of the big conversations plus one for the small ones). It is outside the app: it writes through no route, calls no `recordChange` and writes no event, so `events` and `event_counters` stay as the first start left them and no live frame is sent; the first send of R10 is event number 1 (TOKI-036 R14). Triggers and constraints stay on (`session_replication_role` is not changed), so the rows are exactly what the app could have written. The indexes stay in place while the rows go in, the btree indexes of TOKI-036 R11, the GIN index of TOKI-069 R4 (`fastupdate = off`), the primary key and every later index of `messages`: the structure measured is the one the real database has, built the way production builds it (a row at a time, no pending list), and not a fresh index built after the load, which is smaller and faster than any index that grew. After the last batch the load runs `VACUUM (ANALYZE) messages` and `ANALYZE` on the other tables it filled, each as a statement of its own outside any transaction (`VACUUM` cannot run inside one), so the planner has the figures a database with that many rows has. Check: the database test (R18) runs the statements one at a time and proves the batches (the text of each starts `BEGIN` and ends `COMMIT`, and the counts after each), the unchanged `session_replication_role`, the absence of events, that the maintenance statements run, and that an index created by the migrations is still there after the load; the by-hand run of Testing proves the million.
- R8. Sessions. The load creates 200 `token` sessions, one per account, and three `cookie` sessions, for `perf-002` (the browser measures of R10 to R14) and for the two readers (R12), each with a secret of 32 random bytes in base64url whose `sha256` hex is `secret_hash` (the rule of `createSession` of the `auth` module), `created_at` and `last_used_at` from the clock of the run. The secrets are written once to `tools/performance/out/secrets.json`, mode 600; the folder `tools/performance/out/` is in `.gitignore`. `measure.mjs` reads the file named by `--secrets <file>` (default `out/secrets.json`); when it runs on another machine than the load (concern 4), the person copies the file there with a tool of their choice and keeps mode 600 (R19 lists the step). No secret is printed, logged or put in the result file. Check: the database test makes a request with each kind through the real session check (`checkSession` of TOKI-022 R44, imported through the public entry of the `auth` module as it is on the day; TOKI-038 R2 moves it from `sessions.ts` to `api.ts`) and gets the account; a test reads the output of a run and the result file and finds no secret value; the file mode is 600; `.gitignore` names the folder.
- R9. 200 people online. `measure.mjs` reads `APP_DOMAIN` as Compose does (it may carry a port, as `localhost:18443` of TOKI-084 R22) and opens 200 WebSocket connections, one for each account, to `wss://<APP_DOMAIN>/ws` through Caddy (the whole value, port included) with the header `Authorization: Bearer <secret>` and no `Origin` (TOKI-038 R2, R4), waits for the `ready` frame of each (TOKI-038 R7) for at most 60 seconds, and keeps them open to the end. Each connection answers a `ping` with a `pong` (TOKI-038 R24) and sends the frame `{"type":"activity","idleMs":0}` every `ACTIVITY_SEND_INTERVAL_MS` of `@toki/shared` (TOKI-055 R1, R13; the import is why the commands run through `tsx`, R1), so the server sees 200 people who are active. These 200 are idle apart from that: they load no bootstrap, save no draft, move no read pointer and type nothing, a lighter load than 200 people at work (R19 states it as a limit). The command then calls `GET /api/v1/presence` with one of the sessions (TOKI-055 R8) and records how many people are `active`. If fewer than 200 connections are ready within the 60 seconds, the run stops with exit code 1 and says how many were. At the end of each phase the command records how many connections are still open; a phase that ends with fewer than 200 is marked `invalid` in the result with that count, and its figure is kept but not judged. The WebSocket client is the library `ws`, declared in the root `devDependencies` at one exact version (the library under `@fastify/websocket` of TOKI-038; `ws` is not in the lock file on main because the gateway is not built, so a test that the version equals the one the gateway uses is added when TOKI-038 lands, and until then the version is one released at least two weeks before, TOKI-091 R19), so the lock file gets no second WebSocket library. The timeout and the activity interval go through the injected `timers` of R17. Check: a test with a local fake server (R17) shows that the command waits for 200 `ready`, answers `ping`, sends `activity` at the interval it is given, stops with exit 1 when it is short, strips the port when it tests the host name, and marks a phase `invalid` when a connection closes during it; the presence count and the open count are fields of the result.
- R10. Message delivery (`delivery`). The command sends messages with `POST /api/v1/conversations/{id}/messages` (TOKI-037 R3) and a UUIDv7 `id` it makes with `createUuidV7Generator` of `@toki/shared`, with the session of the sender as a Bearer token and the header `Origin: https://<APP_DOMAIN>` and `Content-Type: application/json` (TOKI-022 R46, R45), so the real path runs: the commit, the signal, the read of the batch and the send (TOKI-038 concern 4; a run that fakes the signal does not check the target). A send counts as a sample only when the answer is `201`; any other status (a `429` above all) is listed with its code and marks the phase `invalid` (R16). The start of a sample is the reading of the monotonic clock just before the request is written; the end is the reading when the `message.created` frame with that message's `id` is read by a receiving connection (TOKI-038 R20). There is one sample for each pair (message, receiving person other than the sender). The send phase is 1,000 messages at the pace of R11 (one every 500 ms): 300 into `#general` (each reaches 199 people, 59,700 pairs) and 700 spread over the other 49 channels, 14 or 15 each, from a sender that is a member, the senders taking turns so no account sends more than a few a minute. The run is therefore expected to produce 59,700 pairs for `#general` plus, for each of the 700 others, the members of its channel minus one; the command computes the expected number from the membership it loads and writes it next to the observed number. The socket figure is the 95th percentile of all the pairs. Because a person sees a message on the screen and not on a socket, a second figure is taken on the browser person `perf-002` (R12's browser, signed in with the cookie session, `#general` open): for the 300 messages sent into `#general`, the page notes the wall-clock time at which the row with the message's text enters the list, and the figure `onScreen` is that time minus the wall-clock time at which the script wrote the request. `perf-002` is never the sender of any message of the send phase. The two clocks are tied before the phase: the script and the page run on one machine, the page reads `performance.timeOrigin + performance.now()` (sub-millisecond, not the whole-millisecond `Date.now()`), and the command takes 20 readings of the page's clock and of its own around each call, keeps the offset of the reading with the shortest round trip, and writes the offset and the spread of the 20 in the result; a spread above 5 ms (a proposal) marks the phase `invalid`. The figure judged against 150 ms is, as a proposal (concern 9), the 95th percentile of `onScreen` (300 samples, the 285th of the sorted list); the socket figure and the median, 99th percentile and maximum of both go in the result next to it, and `targets.json` carries `measuringPointIsProposal`. Check: a test with a controllable clock (R17) feeds known arrival times and gets the exact percentile, the pairs per message, the exclusion of the sender, the expected pair count, the offset choice, a status other than 201 marking the phase `invalid`, and a message that never arrives counted as a sample over the target and listed as lost, not dropped from the count.
- R11. The scenario, one file. `tools/performance/scenario.json` holds the numbers of the run that are not targets: the seed, the counts of R5 to R7, the pace of R10 (one message every 500 ms), the word distribution of R6, the sample counts of R10 to R14, the spacings of R12 and R13, the network profile of R12 and the search queries of R13. Every number in it except the log's "200 people online" is a proposal (concern 7), and the file says so in a `proposals` list that the result copies. The pace is a starting value, not a measured limit: the counter row of TOKI-036 R16 is held from the first append to the commit, which is milliseconds, so two sends a second are not expected to queue; the result records the duration of each send request, so a run in which the sends themselves queue shows it. Every run copies the file whole into the result. A command-line option overrides the counts for a smaller run and the override is written in the result; the targets cannot be overridden (R2). Check: a test reads the file and the result and compares; a run with an override shows it; the `proposals` list names every key but `people`.
- R12. First load on 4G (`firstLoad4g`). A browser run: Chromium through Playwright (`@playwright/test` is already a devDependency; TOKI-008 R10), a new context for each run with an empty cache and a cookie session set as `__Host-toki_session` (TOKI-084 R12, TOKI-022 R21), network emulation with the profile of `scenario.json`, the page `https://<APP_DOMAIN>/`; the load ends when the first row of the conversation list is on the screen. The time is read in the page from the navigation start. There are 20 runs for each of three people: `perf-002` (about a dozen conversations), reader A (501) and reader B (1,001), the last two being the case D-117 is about, because the first load carries every conversation. The runs of one person are at least `firstLoadGapMs` (5,000) apart, because `GET /bootstrap` is in the `heavy` class of TOKI-091 R12 (60 a minute for each account) and the browser makes other requests too. The figure of a person is the 95th percentile of its 20 runs (the 19th), judged against 2,000 ms; which person's figure is judged is part of concern 1 (proposal: all three must be under). Any answer to `/api/v1/` with a status of 400 or more during a run (a `429` above all) is listed with its code and the run is not a sample; the phase is `invalid` (R16). The profile (download, upload, round trip) and the moment that ends the load are proposals (concern 1); the file `scenario.json` holds them and the result prints them, so changing an answer is one edit. Check: a test of the page-side code with a fake timer (R17) shows the time taken from the navigation start, the choice of the 19th of 20 for each person and a run with a non-2xx answer left out of the samples and marking the phase; the by-hand run of Testing shows the 60 runs.
- R13. Search (`search`). The command sends `GET /api/v1/search?q=<text>&kind=messages` (TOKI-070 R1) with the session of a person, over Caddy, one request at a time (latency, not throughput), while the 200 are connected. The time is from writing the request to reading the whole answer. A request counts as a sample only when the answer is `200`; any other status is listed with its code and marks the phase `invalid`, and is never timed into a figure (a `429` is a fast answer and would lower the percentile). The route belongs to the `heavy` class of TOKI-091 R12 (60 requests in 60 seconds for each account), so the command spaces the requests of one account by at least `heavyMinGapMs` (1,100 ms, so at most 54 a minute), takes the 1,000 requests from 20 people in turn, and sends the reader requests below at that spacing (100 requests, 110 seconds); once TOKI-091 is built a test derives the spacing from the class table of `packages/shared/src/limits/classes.ts` instead of a stored number. This run asks no exemption from the limiter; it must stay under it, and it reports the number of `429` it still gets (R16). The queries are listed in `scenario.json` in three groups, each with at least 10 queries: `ordinary` (one rare word, two rare words in any order, a word with diacritics typed without them, the cases of TOKI-069 R12), `common` (single words of rank 1 to 20, R6) and `short` (two-letter starts that match many rows: `ha`, `ng`, `nh`, `tr`, `th`, ...). The route cannot run a one-letter query: under `SEARCH_MESSAGE_MIN_LENGTH` (2, TOKI-070 R7) `messages` is an empty page and no statement is sent, so the 335 ms of TOKI-069 R11 for `n:*` is a figure of the database function on 1,000,000 rows, not of the route, and the route's own figure for a two-letter start is what this phase measures. 1,000 requests in all, 400 `ordinary`, 300 `common`, 300 `short`, and 100 more from each reader of R7 (501 and 1,001 conversations, the second takes the group-of-1,000 branch). A fourth, report-only group measures `GET /api/v1/conversations/:id/search` (TOKI-072; it is also `heavy`) in `#general` with 100 requests of the `common` and `short` queries, at the same spacing, as TOKI-072 asks of this ticket; it is not part of `search` (concern 3). For every query the result gives its time and the number of rows that match it, taken from a `count(*)` over the same predicate through the Postgres path of R4 (`null` when unreachable), so a slow group can be tied to the number of matches. The result gives, for each group and for each reader, the count, median, 95th percentile and maximum, and `search` is judged, as the log says, on the 95th percentile; which groups count toward it is concern 3, so the result carries the 95th percentile of `ordinary` + `common` and of all three groups side by side and `met` for both. Check: a test with a controllable clock (R17) feeds a known list and gets the group figures and both `met` values, leaves a non-200 answer out and marks the phase, and finds the spacing between the requests of one account never under `heavyMinGapMs`; a test of `scenario.json` finds every `short` query at two code points or more and at least 10 in each group.
- R14. Switching to a channel opened before (`switchOpened`) and scrolling (`scroll60`). Two browser runs with the cookie session of `perf-002` on the same `https://<APP_DOMAIN>` page, with no network emulation (the log gives none). Switching: the page opens 10 channels once each (so each held its window, TOKI-040 R6), then makes 100 switches to one of them chosen at random but never the same twice in a row, at least 500 ms apart (so the `read` class of TOKI-091 R12 is not reached), by pressing its row in the conversation list; a sample is the time from the press to the frame in which the newest message text of that channel is in the list. The figure is the 95th percentile, judged against 100 ms (the log gives the number and no statistic: concern 2). Scrolling: the page opens `#general` (at least 10,000 messages, R6) and, as a preparation that is not timed, loads history until 10,000 messages are in the list (counted from the history answers the page receives, TOKI-037 R11), then scrolls the message list (`role="list"`, TOKI-041 R24) from the bottom up through the loaded messages with the browser's own scroll gesture (`Input.synthesizeScrollGesture` through the Chrome protocol), recording the duration of every frame with `requestAnimationFrame` during the gesture. A second scroll, from a fresh page, that loads history while it scrolls is recorded in the same way and reported next to the first, not judged. Which of the two is the case of "scrolls 10,000 messages" is concern 12. The result has, for each, the average frame rate, the 95th percentile of the frame duration and the share of frames longer than the limit; the target is judged as met when the 95th percentile of the frame duration is at most the limit, `Math.ceil(1000 / targets.scroll60.number)` (17 ms), read from `targets.json` and never written in the code, a proposal (concern 2). Any answer to `/api/v1/` with a status of 400 or more during the runs is listed and marks the phase `invalid`. Check: a test of the page-side code with a controllable clock (R17) feeds known frame times and switch times and gets the percentiles, the derived limit and `met`; the by-hand run shows the browser runs.

## Design
### What a run does, in order
1. A fresh stack of TOKI-084 is up and healthy; the first administrator exists (TOKI-020), `#general` exists.
2. `pnpm perf:load` (R4 to R8): guard, accounts and sessions, channels and members, the 1,000,000 messages in batches, `VACUUM (ANALYZE)`; writes `out/secrets.json`.
3. `pnpm perf:measure` (R9 to R16): the 200 connect; the bundle figure (R15, needs no load); the send phase (R10) with the browser person watching; the search phase (R13); the browser phases (R12, R14); the memory and queue readings; the file.
4. The person reads the table, pastes it in the ticket, and removes the stack and its volumes.

### The load, and why each choice
| Choice | Reason |
| :---- | :---- |
| 200 people, 50 channels, 1,000,000 messages | The technical design says exactly this load script; D-113 sets 200 people online |
| Accounts `perf-NNN@perf.test`, direct session rows | The sign-in path sends mail and has its own limits (TOKI-022); the targets are not about sign-in and 200 mails would measure the mail layer |
| Created outside the app, by one SQL statement per batch | 1,000,000 sends through the route would take hours and would also fill the event log and the job queue with work that is not part of the figure |
| Indexes stay while rows go in | The measured structure must be the one production grows (R7) |
| Version-7 ids built in the statement from `created_at` | The app writes version 7 (TOKI-037 R4); a random version-4 key would make a larger, scattered primary-key index than the real one (R6) |
| Text with and without diacritics, a ranked vocabulary, seed-fixed | TOKI-069 searches through a fold of diacritics, and its cost follows the number of matches, so the words need a stated frequency (R6) |
| No replies, reactions, files in the data | The targets concern the main list, search and delivery; the reply index (TOKI-036 R11) and the others are measured by their plan tests (concern 8) |

## Errors and edge cases
- The stack is not healthy, `APP_DOMAIN` does not answer or the certificate is not trusted -> exit 1 with the cause; for `localhost` Caddy's own authority is used and the commands accept its certificate only for a host name ending in `.localhost` or equal to `localhost`.
- A guard of R4 fails -> the guard statement raises `perf_guard: <condition>`, the command stops at it, exit 1 with one line naming the condition, nothing written.
- A batch fails -> the load stops with the batch number, rolls back that batch and exits 1; the guard refuses a second run (messages are not empty), so the person removes the volumes and starts again.
- A connection closes during a phase -> the phase is `invalid` (R9), its figure is printed and not judged.
- An answer that is not the expected status (a `429` above all) in the send, search, first-load or switch phase -> it is never a sample; it is listed with its code and the phase is `invalid` (R10, R12 to R14), and the `429` count goes in the result (R16).
- A sent message never arrives within 10 seconds -> a lost sample counted as over the target (R10).
- Docker or the Postgres path is not reachable from the measuring machine -> memory and queue fields are `null`, the six figures are still measured.

## Data safety
- Every account, message and secret is made for the run and is throwaway; the stack that holds them is removed afterwards (R19). No real person's data is ever loaded.
- `secrets.json` has mode 600 and sits in a git-ignored folder; no secret is printed or put in the result (R8).
- The load refuses a database that holds anything but the first administrator (R4), so it cannot be run by mistake against a database that people use.
- No log line of the commands holds a message text or a secret.

Facts: plain `node` cannot import `@toki/shared` (R1); the production image holds no `tsx` and no `tools/` (TOKI-084 R6, R8); `apps/server` already runs `.ts` with `tsx` 4.23.15; a process boundary keeps the database test from importing `tools/` into `apps/server` (TOKI-002 rules). Proposal, not a decision: `.mjs` files run through `tsx` (added to the root `devDependencies`, with `@toki/shared`), `load.mjs` importing nothing from the workspace so the database test starts it with `node`, and the load proved against the real tables by one database test that runs it as a process and executes its printed statements one at a time (R18). The alternative is three small local copies (the interval, a UUIDv7 generator, a test clock) with a test that compares them with the package; it keeps plain `node` and risks drift. Owner: Thanh Truong.
