# Performance measurement design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/performance-measurement.md (Thanh Truong)
Ticket: TOKI-089

## Goal
The product owner accepted six speed figures with 200 people online as the load (D-113, NFR-13), and the technical design says a load script "creates 200 people, 50 channels and 1 million messages to measure the performance targets before release". The tests of the earlier tickets read plans and count statements and never time anything, and the merged specs of the message tables, the gateway, the search index, the search request, the client engine and the message list each hand the real measure to this ticket.
This ticket builds that script: one command that fills a fresh production stack of TOKI-084 with the load, one command that keeps 200 people connected and measures the six figures through Caddy, and one result file that names, for each figure, the target and its source, how it was measured, the samples, the value and whether it is under the target. It changes no code of the app.
The measure is a decision of a person on a machine of the first VPS, not a check of the pull-request pipeline: its result depends on the machine, and a shared runner would make the figures noise.

## Scope
- In:
  - `tools/performance/`: the load command, the measure command, the file of targets, the file of the scenario, the readers and the writers of the result, and their tests (R1 to R3).
  - The data: 200 people, 50 channels, 1,000,000 messages, the extra reader with 500 conversations, 200 sessions made for the run (R4 to R8).
  - The load of 200 connected people and the six measures, each with its method (R9 to R15).
  - The result file and the page that tells a person how to run it and read it (R16, R19).
  - The rule about timing: the script uses real time, the tests of it do not (R17, R18).
- Out (not now):
  - The production image, the stack, its memory limits and its Caddyfile: TOKI-084 owns them. This ticket reports the memory each service used (R16) so a person can tune TOKI-084's starting limits; it changes none of them.
  - Fixing a figure that is over its target. A figure over its target is a finding with its numbers; the fix is a ticket of the owner of that part (concern 5 says who decides about the milestone).
  - A run in the pull-request pipeline, a nightly run, a threshold that fails a build: not built (R16, concern 4).
  - The seed of TOKI-081. It is for development, refuses a database that holds other data and writes 8 people (TOKI-081 R2, R14, R15); this load is separate and shares nothing with it (R3).
  - Replies, reactions, pins, mentions, files and unread counts in the loaded data (R6, concern 8 says why).
  - Load of other kinds (many sign-ins, mail, uploads, the worker's image work): not a target of D-113.
  - The sign-in path (codes and mail): the people of the run get sessions directly (R8).

## Requirements
- R1. Place and commands. The code is in `tools/performance/` as ES modules (`.mjs`), as `tools/bundle-size/` is. The root `package.json` gains `perf:load` (`node tools/performance/load.mjs`) and `perf:measure` (`node tools/performance/measure.mjs`), and the `node --test` list of the root `test` script gains the test files of the folder (R17). No job is added to `.github/workflows/ci.yml` and `changed.sh` is not edited. The folder is not copied into either image (TOKI-084 R6, R7 copy only what they list). Check: a test reads the root scripts and `ci.yml`; the two scripts exist, no step of `ci.yml` names `perf:`, and a `git diff` of the pull request touches neither `ci.yml` nor `changed.sh`.
- R2. The six targets are written once, in `tools/performance/targets.json`: for each, `id`, `text`, `number`, `unit`, `statistic`, `source`, and `statisticIsProposal` (true when the log gives no statistic, see concern 2). The numbers and sources are:
  `delivery`: 150 ms, p95, D-113, NFR-13; `firstLoad4g`: 2,000 ms, D-113, NFR-13; `initialJs`: 200,000 bytes gzip, D-113, TOKI-006 R10, TOKI-007 R7; `switchOpened`: 100 ms, D-113, NFR-13; `scroll60`: 60 frames per second, D-113, NFR-13; `search`: 200 ms, p95, D-113, NFR-13.
  The `statistic` of `firstLoad4g`, `switchOpened` and `scroll60` is the proposal of R12 to R14 and carries `statisticIsProposal` true. The result file (R16) copies the entry of each target; no number of a target is written anywhere else. Check: a test reads the file and compares each id, number, unit and source with the list above (so a changed number fails a test and must be a change of this spec), and a search of the other files of the folder finds none of the six numbers as a literal used for a verdict.
- R3. The load command is separate from the seed. `load.mjs` imports nothing from `apps/server/src/seed/`, writes no account named in `PROTOTYPE_SEED` and never uses the domain `hugepig.example`; its 199 added accounts are `perf-002@perf.test` to `perf-200@perf.test` (the domain `.test` is reserved and routes nowhere). Check: a test reads the import lines and the address list of the generated SQL (R7).
- R4. Where it works and what it refuses. The load runs on the machine of the stack, with Docker, and reaches Postgres through the stack: by default `docker compose -f docker-compose.prod.yml exec -T postgres psql -v ON_ERROR_STOP=1 -U <POSTGRES_USER> -d <POSTGRES_DB>` with the SQL on standard input, because Postgres has no published port (TOKI-084 R10); the environment variable `PERF_PSQL` replaces that command line for a database that is reachable some other way (the development Compose file, a test database). Before it writes anything it reads and refuses, with exit code 1 and one line naming the condition, when any of these holds: the table `messages` holds a row; the table `users` holds other than one row (the first administrator of TOKI-020, who is person number 1 of the scenario, R5); the table `workspaces` holds other than one row; the conversation `#general` is missing; the index `messages_search_idx` of TOKI-069 R4 is missing (the search figure would mean nothing without it). There is no flag that overrides a refusal. To measure again from scratch a person removes the volumes (`docker compose down -v`) and starts the stack. Check: a database test (R18) runs the load against a database that fails each condition in turn and finds exit 1, the named condition and no row written; a run on a database that meets them loads.
- R5. People and channels. The load adds 199 accounts to the 1 first administrator, so 200 active accounts exist: `role` `member`, `status` `active`, `language` `en`, the `display_name` `Perf 002` to `Perf 200`, an address `perf-NNN@perf.test` (`perf-002` to `perf-200`); the first administrator keeps their account and address and is the person number 1 of the scenario. It creates 49 public channels named `perf-01` to `perf-49` (lower-case letters, digits and hyphen, the rule of TOKI-029 R3), so with `#general` there are 50 channels (technical design, Testing). Every account is a member of `#general`; the other channels have between 5 and 100 members each, chosen by a fixed rule from the seed of R6 and listed in the result (R16), so the same seed gives the same membership. Each row is one the real tables accept: creation times from the clock of the run, the keys and checks of TOKI-019, TOKI-028 and TOKI-024 hold. Check: the database test counts 200 accounts, 50 channels, the member counts of `#general` (200) and of every other channel (5 to 100), and that every member row has its account and conversation.
- R6. Messages. The load inserts exactly 1,000,000 rows into `messages`, all `kind` `user`, top-level (no `parent_id`, `also_in_channel` false, no `edited_at`, no `deleted_at`). The split is fixed by the seed: `#general` and each of the 49 channels have at least 10,000 messages (so a channel of 10,000 exists for R14 and R15), the remaining messages are spread by a fixed weight, and 450 small private channels of the extra reader (R7) hold 20 each (9,000 in all, part of the million). The author of a message is a member of its conversation. `body` is Vietnamese-like text of 3 to 40 words from a list of words with and without diacritics, built from a seed, so a given seed gives the same text on every run; about one message in 50 holds a word of the common starts of R13. `created_at` is spread evenly over the 730 days that end one hour before the run starts, taken from the clock the command is given (it never reads the machine's time in a way a test cannot replace); `id` is `gen_random_uuid()` (TOKI-036 R2 takes any id and checks no version; no order depends on it, R12 there). Check: the database test counts the rows (at the small scale of R18: the count asked for), the minimum per channel, the author membership, that every row satisfies the real checks of `messages` because the real table took them, and that two runs with one seed give the same bodies and counts.
- R7. The extra reader and the bulk write. The account `perf-199` (the reader) is a member of the 50 channels and of 450 small private channels `perf-s-001` to `perf-s-450` of two members each (the reader and one other), so the reader belongs to 500 conversations, the number past which D-117 says the first load is to be reconsidered; the reader is the person TOKI-070 concern 6 wants measured. The messages are written by the database from a statement `INSERT … SELECT … FROM generate_series(…)` in batches of 50,000 rows, each batch its own transaction, so no row passes through the script and the 1,000,000 take 20 batches of the big conversations plus the small ones. It is outside the app: it writes through no route, calls no `recordChange` and writes no event, so `events` and `event_counters` stay as the first start left them and no live frame is sent; the first send of R10 is event number 1 (TOKI-036 R14). Triggers and constraints stay on (`session_replication_role` is not changed), so the rows are exactly what the app could have written. The indexes stay in place while the rows go in, the btree indexes of TOKI-036 R11, the GIN index of TOKI-069 R4 (`fastupdate = off`), the primary key and every later index of `messages`: the structure measured is the one the real database has, built the way production builds it (a row at a time, no pending list), and not a fresh index built after the load, which is smaller and faster than any index that grew. After the last batch the load runs `VACUUM (ANALYZE) messages` and `ANALYZE` on the other tables it filled, so the planner has the figures a database with that many rows has. Check: the database test (R18) proves the statement, the batches, the unchanged `session_replication_role`, the absence of events, and that an index created by the migrations is still there after the load; the by-hand run of Testing proves the million.
- R8. Sessions. The load creates 200 `token` sessions, one per account, and one `cookie` session for `perf-002` (the browser measures of R12 to R14), each with a secret of 32 random bytes in base64url whose `sha256` hex is `secret_hash` (the rule of `createSession` of the `auth` module), `created_at` and `last_used_at` from the clock of the run. The secrets are written once to `tools/performance/out/secrets.json`, mode 600; the folder `tools/performance/out/` is in `.gitignore`. No secret is printed, logged or put in the result file. Check: the database test makes a request with each kind through the real session check (`checkSession` of TOKI-022 R44) and gets the account; a test reads the output of a run and the result file and finds no secret value; the file mode is 600; `.gitignore` names the folder.
- R9. 200 people online. `measure.mjs` opens 200 WebSocket connections, one for each account, to `wss://<APP_DOMAIN>/ws` through Caddy with the header `Authorization: Bearer <secret>` and no `Origin` (TOKI-038 R2, R4), waits for the `ready` frame of each (TOKI-038 R7) for at most 60 seconds, and keeps them open to the end. Each connection answers a `ping` with a `pong` (TOKI-038 R24) and sends the frame `{"type":"activity","idleMs":0}` every `ACTIVITY_SEND_INTERVAL_MS` of `@toki/shared` (TOKI-055 R1, R13), so the server sees 200 people who are active. The command then calls `GET /api/v1/presence` with one of the sessions (TOKI-055 R8) and records how many people are `active`. If fewer than 200 connections are ready within the 60 seconds, the run stops with exit code 1 and says how many were. At the end of each phase the command records how many connections are still open; a phase that ends with fewer than 200 is marked `invalid` in the result with that count, and its figure is kept but not judged. The WebSocket client is the library `ws` at one exact version (the library under `@fastify/websocket` of TOKI-038, so the lock file gets no second WebSocket library). Check: a test with a local fake server (R17) shows that the command waits for 200 `ready`, answers `ping`, sends `activity` at the interval it is given, stops with exit 1 when it is short, and marks a phase `invalid` when a connection closes during it; the presence count and the open count are fields of the result.
- R10. Message delivery (`delivery`). The command sends messages with `POST /api/v1/conversations/{id}/messages` (TOKI-037 R3) and a UUIDv7 `id` it makes, with the session of the sender as a Bearer token and the header `Origin: https://<APP_DOMAIN>` and `Content-Type: application/json` (TOKI-022 R46, R45), so the real path runs: the commit, the signal, the read of the batch and the send (TOKI-038 concern 4; a run that fakes the signal does not check the target). The start of a sample is the reading of the monotonic clock just before the request is written; the end is the reading when the `message.created` frame with that message's `id` is read by a receiving connection (TOKI-038 R20). There is one sample for each pair (message, receiving person other than the sender): a message into `#general` has 199. The send phase is 1,000 messages at the pace of R11 (one every 500 ms): 200 into `#general` and 800 spread evenly over the other 49 channels, from a sender that is a member. The figure is the 95th percentile of all the samples. Because a person sees a message on the screen and not on a socket, a second figure is taken on the browser person `perf-002` (R12's browser, signed in with the cookie session, `#general` open): for 300 of the 1,000 sent into `#general`, the page notes the wall-clock time at which the row with the message's text enters the list, and the figure `onScreen` is that time minus the wall-clock time at which the script wrote the request, valid because the script and the browser run on one machine (R11, R16 name it). The figure judged against 150 ms is the 95th percentile of `onScreen` (it is what D-113's word "seen" says); the socket figure and the median, 99th percentile and maximum of both go in the result next to it. Check: a test with a controllable clock (R17) feeds known arrival times and gets the exact percentile, the pairs per message, the exclusion of the sender, and a message that never arrives counted as a sample over the target and listed as lost, not dropped from the count.
- R11. The scenario, one file. `tools/performance/scenario.json` holds the numbers of the run that are not targets: the seed, the counts of R5 to R7, the pace of R10 (one message every 500 ms, a technical choice with its reason: the counter row of TOKI-036 R16 makes two sends of a workspace take turns, so a faster pace would measure the queue of the test and not a person's message), the sample counts of R10 to R14, the network profile of R12 and the search queries of R13. Every run copies it whole into the result. A command-line option overrides the counts for a smaller run and the override is written in the result; the targets cannot be overridden (R2). Check: a test reads the file and the result and compares; a run with an override shows it.
- R12. First load on 4G (`firstLoad4g`). A browser run: Chromium through Playwright (`@playwright/test` is already a devDependency; TOKI-008 R10), a new context for each run with an empty cache and the cookie session of `perf-002` set as `__Host-toki_session` (TOKI-084 R12, TOKI-022 R21), network emulation with the profile of `scenario.json`, the page `https://<APP_DOMAIN>/`; the load ends when the first row of the conversation list is on the screen. The time is read in the page from the navigation start. There are 20 runs, and the figure is the 95th percentile (so the 19th of 20), judged against 2,000 ms. The profile (download, upload, round trip) and the moment that ends the load are proposals (concern 1); the file `scenario.json` holds them and the result prints them, so changing an answer is one edit. Check: a test of the page-side code with a fake timer (R17) shows the time taken from the navigation start and the choice of the 19th of 20; the by-hand run of Testing shows the 20 runs.
- R13. Search (`search`). The command sends `GET /api/v1/search?q=<text>&kind=messages` (TOKI-070 R1) with the session of a person, over Caddy, one request at a time (latency, not throughput), while the 200 are connected. The time is from writing the request to reading the whole answer. The queries are listed in `scenario.json` in three groups, each with at least 10 queries: `ordinary` (one rare word, two rare words in any order, a word with diacritics typed without them, the cases of TOKI-069 R12), `common` (single common words), and `short` (the starts of one or two letters that match many rows: `n`, `ha`, `ng`, `nh`; TOKI-069 R11 measured 335 ms for `n:*` on 1,000,000 rows). 1,000 requests in all, 400 `ordinary`, 300 `common`, 300 `short`, from 20 different people, and 100 more from the reader of R7 (500 conversations). The result gives, for each group and for the reader, the count, median, 95th percentile and maximum, and `search` is judged, as the log says, on the 95th percentile; which groups count toward it is concern 3, so the result carries the 95th percentile of `ordinary` + `common` and of all three groups side by side and `met` for both. Check: a test with a controllable clock (R17) feeds a known list and gets the group figures and both `met` values.
- R14. Switching to a channel opened before (`switchOpened`) and scrolling (`scroll60`). Two browser runs with the cookie session of `perf-002` on the same `https://<APP_DOMAIN>` page, with no network emulation (the log gives none). Switching: the page opens 10 channels once each (so each held its window, TOKI-040 R6), then makes 100 switches to one of them chosen at random but never the same twice in a row, by pressing its row in the conversation list; a sample is the time from the press to the frame in which the newest message text of that channel is in the list. The figure is the 95th percentile, judged against 100 ms (the log gives the number and no statistic: concern 2). Scrolling: the page opens `#general` (at least 10,000 messages, R6), and scrolls the message list (`role="list"`, TOKI-041 R24) from the bottom up with the browser's own scroll gesture (`Input.synthesizeScrollGesture` through the Chrome protocol) until the list has loaded and passed 10,000 messages (counted from the history answers the page receives, TOKI-037 R11), recording the duration of every frame with `requestAnimationFrame` during the gesture. The result has the average frame rate, the 95th percentile of the frame duration and the share of frames longer than 17 ms; the target is judged as met when the 95th percentile of the frame duration is at most 17 ms (1000 ÷ 60 rounded up), a proposal (concern 2). Check: a test of the page-side code with a controllable clock (R17) feeds known frame times and switch times and gets the percentiles and `met`; the by-hand run shows the browser runs.
- R15. The 200 KB figure (`initialJs`). The command copies `/srv` of the running `caddy` service (`docker compose cp`, which is what the image serves, built from the commit under test) to a folder under `out/`, calls `measure(distDir)` of `tools/bundle-size/check.mjs` on it and compares the number with `bytes` of `tools/bundle-size/limit.json` through `verdict(size, limit)` of that file; it does not build the web app and has no second implementation of the rule (gzip, every script and `modulepreload` of `index.html` and what they import statically, a total at or above 200,000 bytes fails: TOKI-007 R7). The option `--dist <folder>` measures a folder instead, for a stack that is not on this machine. Check: a test runs the step on a small folder of fixture files and gets the same number as `measure` called directly, and a test that renames or removes `measure` from `check.mjs` fails; the by-hand run reports the figure of the real image.
- R16. The result. Each run writes `tools/performance/out/result-<UTC time>.json` and prints a table of the six lines. The file has: a header (the commit of the run, the time from the clock of the command, the host name of `APP_DOMAIN`, the description of the stack machine that the person gives with `--machine "2 vCPU, 4 GB"` and a note that the script ran on the same or another machine, the versions of Node, Chromium and Postgres, `select version()`); the data (the counts of R5 to R7, the member count of each channel, the list of the indexes of `messages` with their definition, `reloptions` and size from the catalog, the size of the table); the 200 (R9: connected, active in the presence snapshot, still open at the end of each phase); for each target the entry of R2 and `measured`, `samples`, `met` (`true`, `false`, or `null` for an `invalid` phase), `invalid` with its reason, and the details of R10 to R15; the memory of each service of the stack from `docker stats --no-stream` at the end of the send phase and of the search phase, next to the `mem_limit` of TOKI-084 R23 (`null` when the command cannot reach Docker); the job queue state at the end of the send phase from the queue schema `pgboss` (TOKI-064 R2), counts by state through the same Postgres path as R4 (`null` when unreachable); and the scenario copy of R11. The command exits 0 when it completed, whether or not a target is met, and 1 only when it could not measure (R4, R9, a stack that does not answer); it never turns a figure over its target into a failing exit, because a figure is a finding and the verdict belongs to the person (concern 5). `out/` is in `.gitignore`; a person may paste the printed table into the ticket. Check: a test builds a result from fixtures with a controllable clock and checks every field, the `null` cases, that no secret and no address of a person is in it, and the exit codes.
- R17. Why this one script uses real time, and how its tests do not. The rule is that a test never waits for a real timer and takes time from the controllable clock of TOKI-008 (`createTestClock`, TOKI-008 R19). This ticket's two commands are the exception, and only they: what they measure is the elapsed real time of a real server, a real network path and a real browser; a controllable clock would measure nothing, and an assertion about a time inside a unit test would be a test of the machine. Everything the commands do that is not the clock is a function that takes the time as a parameter: `percentile(values, p)`, the scheduler of R10's pace (`nextSendAt(now, paceMs)`), the sample records, the verdicts (`met`), the result builder (R16), and the page-side code of R12 and R14, each taking `now: () => number` (the commands pass `performance.now`; a test passes the clock of TOKI-008). The tests in this folder never assert a measured duration and never wait: they feed fixed times and read exact results, and use a fake WebSocket server that answers at once (R9). `scripts/check-clock-use.sh` reads `apps/server/src` and `packages/client-core/src` only, so `tools/performance/` is outside it; a test of this folder confirms that nothing under `apps/` or `packages/` imports from `tools/performance/`. Check: a test reads every `*.test.mjs` of the folder and finds no `setTimeout`, `setInterval`, `sleep` or `Date.now(`; the clock used in them is `createTestClock`; and no assertion compares a value with a duration taken from a run.
- R18. The load is proved against the real tables, at a small scale. `perf:load` takes `--people`, `--channels`, `--small-channels`, `--messages` and `--print-sql` (print the SQL and exit) and `PERF_PSQL`; its defaults are the numbers of R5 to R7. One database test of `apps/server` (`apps/server/tests/performance-load.db.test.ts`, run by the database project of TOKI-008, on a throwaway migrated database as `migrate.db.test.ts` does) makes a first administrator and `#general` with the existing writers, calls `node tools/performance/load.mjs --print-sql --people 12 --channels 5 --small-channels 4 --messages 3000` as a child process, runs the SQL it prints with the test database client, and checks the counts of R5 to R7, the refusals of R4, the sessions of R8 through `checkSession`, the absence of events, and that the migrations' indexes are still present. Because the real table takes the rows, a later migration that adds a required column fails this test and the load is brought up to date in that change, so the load cannot drift from the schema unnoticed. The test imports nothing from `tools/` (it starts a process), so the import rules of TOKI-002 are not touched. Check: the test is part of `pnpm test`; removing a required column from the generated SQL makes it fail.
- R19. The page and the command list. `docs/performance-measurement.md` (English) holds, in this order: what the run measures and the six targets with their sources (copied from `targets.json` by a test that fails when they differ), the machine to use (the size of TOKI-084's stack: 2 vCPU, 4 GB, 80 GB), the steps (start a fresh stack with TOKI-084's Compose file; run `pnpm perf:load` on that machine; run `pnpm perf:measure --machine "…"`), how long each takes (stated from the by-hand run), what the files in `out/` are, how to read a result and that a stack is thrown away afterwards (`docker compose down -v`; the data is throwaway and is not to be kept or restored), and the three limits of what is measured (R6 and concern 8; one machine; no sign-in). "Common commands" of `CLAUDE.md` gains one row each for `pnpm perf:load` and `pnpm perf:measure` (the rule that the ticket which adds a command adds it there), which say they need the production stack and are not part of `pnpm test`. Check: a test compares the target table of the page with `targets.json`; a test finds both commands in `CLAUDE.md` and `package.json`.
- R20. Nothing else changes. No file of `apps/server/src`, `apps/web/src` or `packages/` is edited; no route, event, test hook, environment variable of the app or flag is added to make the app measurable; the two commands read the app only through its public entries (HTTP and `/ws` through Caddy) and the database through the Postgres path of R4. New environment names of the commands (`PERF_PSQL`, `APP_DOMAIN` read from the same name Compose uses, `PERF_SECRETS`) are listed in `docs/environment-config.md` in a new section "Performance measurement" with the note that they are read by the commands in `tools/performance/` and by no process of the app (TOKI-096's inventory rule). Check: the diff of the pull request shows no file under `apps/` or `packages/` except the one test of R18; the inventory test of TOKI-096 passes with the new rows.

## Design
### What a run does, in order
1. A fresh stack of TOKI-084 is up and healthy; the first administrator exists (TOKI-020), `#general` exists.
2. `pnpm perf:load` (R4 to R8): guard, accounts and sessions, channels and members, the 1,000,000 messages in batches, `VACUUM (ANALYZE)`; writes `out/secrets.json`.
3. `pnpm perf:measure` (R9 to R16): the 200 connect; the bundle figure (R15, needs no load); the send phase (R10) with the browser person watching; the search phase (R13); the browser phases (R12, R14); the memory and queue readings; the file.
4. The person reads the table, pastes it in the ticket, and removes the stack and its volumes.

### The load, and why each choice
| Choice | Reason |
| :---- | :---- |
| 200 people, 50 channels, 1,000,000 messages | The technical design says exactly this load script; D-113 sets 200 people online |
| Accounts `perf-NNN@perf.test`, direct session rows | The sign-in path sends mail and has its own limits (TOKI-022); the targets are not about sign-in and 200 mails would measure the mail layer |
| Created outside the app, by one SQL statement per batch | 1,000,000 sends through the route would take hours and would also fill the event log and the job queue with work that is not part of the figure |
| Indexes stay while rows go in | The measured structure must be the one production grows (R7) |
| Random `gen_random_uuid()` ids | The table takes any id (TOKI-036 R2); the order is `created_at`, `id` (R12 there) |
| Text with and without diacritics, seed-fixed | TOKI-069 searches through a fold of diacritics; ordinary and common words need to exist in the data (R13) |
| No replies, reactions, files in the data | The targets concern the main list, search and delivery; the reply index (TOKI-036 R11) and the others are measured by their plan tests (concern 8) |

### What is measured through what
| Figure | Where it starts and ends | Load present |
| :---- | :---- | :---- |
| `delivery` | write of the send request, to the row on the screen of `perf-002` (and to the frame on each socket) | 200 connected, activity frames, the paced sends |
| `firstLoad4g` | navigation start, to the first row of the conversation list | 200 connected |
| `initialJs` | the files `/srv` of the running Caddy, through `measure()` | none needed |
| `switchOpened` | press on the row, to the frame with the channel's newest text | 200 connected |
| `scroll60` | frame durations during one scroll through 10,000 messages | 200 connected |
| `search` | write of the request, to the whole answer read | 200 connected |

### Layout
```
tools/performance/
```

## Errors and edge cases
- The stack is not healthy, `APP_DOMAIN` does not answer or the certificate is not trusted -> exit 1 with the cause; for `localhost` Caddy's own authority is used and the commands accept its certificate only for a host name ending in `.localhost` or equal to `localhost`.
- A guard of R4 fails -> exit 1, nothing written.
- A batch fails -> the load stops with the batch number, rolls back that batch and exits 1; the guard refuses a second run (messages are not empty), so the person removes the volumes and starts again.
- A connection closes during a phase -> the phase is `invalid` (R9), its figure is printed and not judged.
- A sent message never arrives within 10 seconds -> a lost sample counted as over the target (R10).
- Docker or the Postgres path is not reachable from the measuring machine -> memory and queue fields are `null`, the six figures are still measured.

## Data safety
- Every account, message and secret is made for the run and is throwaway; the stack that holds them is removed afterwards (R19). No real person's data is ever loaded.
- `secrets.json` has mode 600 and sits in a git-ignored folder; no secret is printed or put in the result (R8).
- The load refuses a database that holds anything but the first administrator (R4), so it cannot be run by mistake against a database that people use.
- No log line of the commands holds a message text or a secret.

## Areas of concern
1. What "first load on 4G" means. Not decided. D-113 and NFR-13 say "first load on 4G under 2 seconds" and the log gives no network speed, no cache state, no sign-in state and no ending moment. Proposal, not a decision (R12): a cold cache, the signed-in person of the run, the profile "Fast 4G" (about 9 Mbps down, 1.5 Mbps up, 60 ms round trip) set in `scenario.json`, ending when the first row of the conversation list is on the screen, no CPU slowdown. A slower profile (Lighthouse's mobile one is 1.6 Mbps and 150 ms) would not leave 2 seconds for 200 KB of script and the fonts and would need the target or the budget to change. The prototype has no loader to learn it from. Owner: Thanh Truong (product owner).
2. The statistic of the three figures that have only a number. Not decided. D-113 says p95 for delivery and search and gives "under 100 ms" for switching, "60 frames per second" for scrolling and "under 2 seconds" for the load, with no statistic. Proposal, not a decision (R12, R14): switching and the first load are judged on the 95th percentile of 100 and of 20 runs; scrolling is met when the 95th percentile of the frame duration is at most 17 ms; the median, the maximum and the share of long frames are in the result as well. Stricter (every switch, no dropped frame) or looser (the median) is the owner's choice and changes `targets.json` and R12, R14. Owner: Thanh Truong (product owner).
3. Which searches count toward the 200 ms p95. Not decided. TOKI-069 measured 335 ms for the one-letter start `n` over 1,000,000 messages and says `ha`, `ng` or `nh` can also be over (TOKI-069 concern 11, TOKI-070 concern 6); their 2-letter minimum does not prevent it. The log says "search across 1 million messages p95 under 200 ms" and does not say which searches. R13 measures three groups and reports `met` for ordinary and common words and for all three; it does not choose. Proposal, not a decision: count all three groups, and if the short starts are over, take one option of TOKI-069 R11 (a cap on the matches read, a 3-letter minimum, which changes F29, or `btree_gin`). Owner: Thanh Truong (product owner).
4. The machine and the place of the script. Not decided. The technical design gives the first VPS as 2 vCPU, 4 GB RAM, 80 GB and says Singapore or Vietnam, and D-113 does not say on what the figures are taken. The 200 clients and the browser use CPU, and on the same 2 vCPU they would slow the server. Proposal, not a decision: the stack on a machine of that size, the script and the browser on another machine of the same network (the on-screen time of R10 needs the script and the browser together on that second machine); a run on a laptop is a trial and its result says so in `--machine`. Which provider and region is the VPS choice of TOKI-087 and the open log row on the VPS. Owner: Thanh Truong (product owner).
5. What a figure over its target does. Not decided. The plan's milestone check says the 6 performance targets pass with 200 people online, and the log does not say who decides, or what is done, when a figure is over (a fix ticket, a changed target or a changed budget). This ticket reports and never fails a build (R16). Proposal, not a decision: each figure over its target becomes a ticket of the part's owner and the milestone waits for it or for a new decision by the product owner. Owner: Thanh Truong (product owner).
6. The 200 KB figure is measured on the files the image serves. Decided in this spec: R15 copies `/srv` of the running `caddy` and calls `measure` and `verdict` of `tools/bundle-size/check.mjs` with `limit.json`, so the rule is the one decided in TOKI-006 concern 4 and TOKI-007 concern 3 (gzip, first-load set, 200,000 bytes) and cannot drift. Reason: it is the bytes a person downloads, from the same commit as the stack, and no second implementation exists. Owner: Thanh Truong.
7. The workload while measuring. Decided in this spec, as technical choices the Blueprint leaves to the builder (they are not product figures and live in `scenario.json`): the 200 people send `activity` frames and answer pings; sends are paced one every 500 ms (the counter row takes turns for a workspace's events, TOKI-036 R16, so a faster pace would measure a queue); 1,000 sends for delivery (950th of the sorted samples is the p95 of the sockets), 300 of them watched on the screen; 20 first loads, 100 switches, 1,000 searches. The log gives only "200 people online". Reason: a stated, repeatable load is better than none; a different rate is a one-line change. Owner: Thanh Truong.
8. What the loaded data leaves out. Decided in this spec: the million are top-level user messages in 50 channels and 450 small ones, with no replies, reactions, pins, mentions, files or unread pointers, and no event in the log. Reason: the six targets concern the main list, delivery and search; the reply index has its own plan test (TOKI-036 R11) and the Activity items and mentions have a cost of their own noted by TOKI-065 concern 12 and TOKI-073 concern 7 (a 199-event `@channel` is not part of these figures). The result page says so (R19). Owner: Thanh Truong.
9. The `delivery` figure is the time on the screen. Decided in this spec: D-113 says "seen by another person", so the judged figure is the 95th percentile of the time until the message is in the list of a browser person (R10), with the socket figure beside it; the time of a real phone's rendering is not measured. Reason: the socket figure alone would leave out the client's work (TOKI-040 R20, TOKI-041 R9) which the person feels. Cost: the script and the browser must be on one machine so one wall clock serves both (R10, concern 4). Owner: Thanh Truong.
10. Where the load code lives and how it stays correct. Decided in this spec: plain `.mjs` in `tools/performance/`, run with `node` like `tools/bundle-size/`, and proved against the real tables by one database test that runs the load as a process and executes its printed SQL (R18). Reason: the production image holds no `tsx` and no `tools/` (TOKI-084 R6, R8), the commands run from a checkout, and a process boundary keeps the test from importing `tools/` into `apps/server` (TOKI-002 rules). Owner: Thanh Truong.
11. The reader with 500 conversations. Decided in this spec: one person (`perf-199`) belongs to 500 conversations, the figure D-117 names ("all of them in phase 1; revisit past 500 conversations"). Reason: TOKI-070 concern 6 asks that a person with many conversations be measured; a person with more than 1,000 conversations is beyond what D-117 plans for, so it is not built. Owner: Thanh Truong.
