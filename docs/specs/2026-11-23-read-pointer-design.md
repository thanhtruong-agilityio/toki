# Read pointer design

Date: 2026-11-23 · Status: draft for review (concerns 1 to 4 are open for the product owner)
Intent: docs/intents/read-pointer.md (Thanh Truong)
Ticket: TOKI-053

## Goal
A person needs to see which conversations hold something they have not read, how much, and whether it mentions them, and to see it go away once they have read it, on every device. The store of TOKI-032 has a slot for this (`unread`, `setUnread`, `clearUnread`) and the rows of TOKI-033 draw it, but nothing fills it. This work builds the server side (one pointer for each person and conversation, the count, the requests, the bootstrap field, a notice to the person's other devices) and the client side (a tracker that counts arriving messages, decides when a conversation is read, sends the pointer and fills the slot).
The hard rule is that a count must stay right while messages arrive, while the person reads on another device and after a lost connection. The design (Design, "How the number stays right") gives every server answer the event number it was computed at (`asOf`), and the client adds to it only the messages with a higher number. Then the same reducer is right for the bootstrap answer, a reply to a request, a live notice that arrives before or after the message events, and a re-read after a lost connection. The second rule is privacy: the pointer is read and written only for the signed-in person and is never part of an answer about someone else (D-048).

## Requirements
- R1. The pointer column. `conversation_members` (TOKI-028 R12) gains `last_read_message_id` (`uuid`, null): the message the person has read up to; null means nothing was read since the person joined (R4, concern 2). One migration, `<number>_read_pointer.sql`, made with `pnpm db:generate --name read_pointer` (TOKI-019 convention 8), adds the column to the existing table, the composite key `conversation_members_last_read_fkey` on (`last_read_message_id`, `conversation_id`) to (`id`, `conversation_id`) of `messages` through `messages_id_conversation_id_key` of TOKI-036 (so a pointer cannot name a message of another conversation), `ON DELETE RESTRICT` and not checked when the column is null, and, on `message_mentions` (TOKI-050 R4), the index `message_mentions_conversation_created_idx` on (`conversation_id`, `created_at`). The key and the index are written as SQL in the migration (a schema file may not import another module's table, TOKI-019 R22); the column is declared in `modules/conversations/schema.ts` and the index in `modules/mentions/schema.ts`, so `pnpm db:generate` run again reports no change. The migration inserts no row and changes no row; the column is null for every existing member row. The column is not part of the primary key and no trigger changes. Check: the catalog test of TOKI-028 R12 expects eight columns (the seven of R12 and this one); the key is read from `pg_constraint` with `ON DELETE RESTRICT`; a pointer to a message of another conversation is refused by name; a delete of the member row succeeds with the pointer set; the migration test of TOKI-005 passes; the migration file has no `CREATE TABLE`.
- R2. Position and forward-only. The position of a message is the pair (`created_at`, `id`) of its row (TOKI-036 R12), compared as a row. `messages` exports `getMainListPositions(client, conversationId, messageIds)`, which returns, for the ids that are rows of that conversation in the main list (`parent_id is null or also_in_channel`, TOKI-036 R11; a system line is in it), a map from id to `{ createdAt, id }`, in one statement; an id that is not there is absent. `conversations` exports `lockReadState(tx, conversationId, userId)`, which runs `select last_read_message_id, created_at from conversation_members ... for no key update` and returns `{ lastReadMessageId, joinedAt }` or null when the person has no member row, and `setReadPointer(tx, conversationId, userId, messageId)`, which sets the column. The rule that decides a move is one pure function of `packages/shared`, `isForward(held, next)` (`held` a position or null, `next` a position): true when `held` is null or `next` is later than `held` by the order of TOKI-036 R12. A move to the same message, or to an earlier one, changes nothing. Check: unit tests of `isForward` for null, equal, earlier, later by time, and equal time with a greater id; a database test of `getMainListPositions` with a root, a system line, a reply also sent to the channel (all present), a reply that is not (absent), an id of another conversation (absent) and an unknown id (absent); `lockReadState` returns null for a person who is not a member and the two fields for a member; the module export tests list the new names.
- R3. The request that moves the pointer. `PUT /api/v1/conversations/{id}/read` takes `{ "messageId": string }` (strict; a lower-case UUID) and answers 200 with `{ "unread": UnreadRecord }` (R12) for that conversation as it stands after the request. It needs a session (401), and then runs the steps of TOKI-037 R1 that apply: (1) the schemas (400 `validation_failed`); (2) `getConversationFacts`: `null` and a private channel, DM or group of which the person is not a member are 404 `not_found`; (3) `canReadConversation` (TOKI-027 R5): a person who is not a member of a public channel is 403 `forbidden`. An archived channel may be read, so the request is allowed there. Inside one transaction at the default level, in the lock order of TOKI-037 R8: the account row `FOR SHARE`, the conversation row `FOR SHARE`, then `lockReadState`; a person with no member row after the locks is answered by step 2 or 3 again. A `messageId` that `getMainListPositions` does not return is 404 `not_found`, with the same body as an unknown conversation and with no id in it. The pointer is moved when `isForward(position of the held pointer, position of messageId)` is true (the held pointer's position is read with the same function) and left alone otherwise; the answer is 200 in both cases, so a repeat, a late request from a slow tab and a move to an older message are all 200 and change nothing (D-111). The route writes no event and takes no event lock, so it never waits for the counter row (concern 5). After the commit the record of R7 for that conversation is read (R10) and returned, and the live notice of R9 is sent. The `Origin` and media-type rules of TOKI-022 R45 and R46 cover it. No log line holds a message id list or a person's id beyond the usual request line. Check: a table test of each status and code; a move forward stores the id and returns the new record; the same request twice stores once and answers the same; a move to an older message and to the same one change nothing and answer 200; two requests at once on two connections, the second waiting, end at the later of the two ids whatever the order they commit in; a thread reply that is not also sent to the channel, a message of another conversation and an unknown id are 404 with equal bodies; an Admin who is not a member of a private channel gets 404; a person who left gets 404 or 403 by the kind of channel; the statement log shows no write to `events` or `event_counters`.
- R4. The count. `messages` exports `readUnread(client, input, readers)` (`input` `{ workspaceId, userId, rows: [{ conversationId, lastReadMessageId, joinedAt }] }`, built by the caller from the member rows; `readers` `{ listMentionCandidates }`, R5) that returns the record of R12, without `asOf`, for each conversation that has a count above 0 or a mention. For one conversation the position `after` is the position of its pointer message, or, when the pointer is null, (`joinedAt`, the smallest uuid) (concern 2). A message is unread when all hold: its position is later than `after`; `kind` is `user` (a system line, D-100, D-165, is out); it is in the main list (`parent_id is null or also_in_channel`: a thread reply is out, F14, a reply also sent to the channel is in, D-160); `author_id` is not the person (a person's own message is never unread); `deleted_at` is null (concern 3). `count` is how many; `firstUnreadId` is the id of the earliest of them by the order of R2, or null. The count has no cap (the prototype's badge sets none, TOKI-012 concern 4). It makes no change to any row. The query is written so that the partial index `messages_conversation_main_idx` (TOKI-036 R11) serves it: it keeps the predicate as the index writes it and bounds the range by the row comparison on (`created_at`, `id`). One statement reads all conversations of the call, with the rows passed as arrays (`unnest`), and the cost is by conversation and by unread message, not by the length of the history (R10). A muted conversation, and a conversation of notification level `nothing`, keep their count (D-103; TOKI-054 hides it). Check, with rows inserted by SQL: counts for a pointer in the middle, at the end, null, and set to a system line; a system line, a thread reply, the person's own message and a deleted message are not counted; a reply also sent to the channel is; two messages with one `created_at` are split by the id; `firstUnreadId` is the earliest counted one and null for a count of 0; a conversation with nothing unread is absent from the result; 1,000 unread messages count 1,000; a conversation of another person's pointer is unaffected.
- R5. The mention mark. A conversation has `mention` true when a message that passes the tests of R4 except "in the main list" mentions the person: it is later than `after`, of kind `user`, not by the person, not deleted, in the main list or in a thread (F13: a mention in a thread reply raises the @ mark and not the count), and it names the person or `@channel` (TOKI-050 R19 `isMentioned`: `@channel` counts for every member but its sender). `mentions` exports `listMentionCandidates(client, { userId, ranges: [{ conversationId, after: Date }] })`, one statement over `message_mentions` (TOKI-050 R4) that returns, for each range, the `message_id` of the rows with `created_at` not earlier than `after` and either `user_id = userId` or `is_channel`, served by the index of R1; `readUnread` takes it as `readers.listMentionCandidates` (the `messages` module imports nothing of `mentions`; `app.ts` passes it, as TOKI-037 R18 does for `readers`) and then checks the returned ids against `messages` in one statement for the rest of the tests (position, kind, author, deleted). So the mark costs two statements for all conversations. A message that mentions the person and is unread but not counted (a thread reply) gives `mention` true and no count. Check: a message naming the person, one naming `@channel` by another person and one in a thread give `mention` true; the person's own `@channel` message, a deleted message, a message before the pointer and a message naming another person give false; a thread reply that names the person gives `mention` true and `count` 0, and the record is present; the reader is called once for all conversations; with no reader given the mark is false for every conversation.
- R6. What is not read. No code of this work reads a conversation of which the person is not a member, a conversation that is archived (they are not in the list, TOKI-031 R17; R7 and R8 pass only the rows of `listConversationSummaries`), or the pointer of another person. `readUnread` computes only for the person of its input. Check: a fixture with an archived channel and a channel the person left returns neither; the argument is always the signed-in person in each caller (a search finds no call with another id).
- R7. The request that returns every record. `GET /api/v1/unread` answers 200 with `{ "eventNumber": number, "unread": { [conversationId]: UnreadRecord } }` (R12) for the signed-in person: every conversation of their list with a count above 0 or a mention, and nothing for the rest. It reads in one snapshot, as `buildBootstrap` does (`inReadSnapshot`, TOKI-031 R10: a read-only transaction at `REPEATABLE READ`): the member rows (the same read that gives the bootstrap conversations, R8), the counts (R4, R5) and `readEventNumber(tx, workspaceId)` (TOKI-036 R19). `asOf` of every record is that `eventNumber`, so every record in the answer is the state at that number and no message with a higher number is in any count (TOKI-036 R16: committed events have no gap). It takes no lock. A person with no conversation gets `{ eventNumber, unread: {} }`. The answer never holds a message text, a name or an id other than the person's own conversations and message ids. Check: a person with three conversations (two unread) gets two records; the answer parses with the strict response schema; a second connection that commits a message after the first read (the seam of TOKI-031 R10) is in neither the counts nor the number, and the next call has both; the transaction shows `repeatable read` and read-only; the statements are the bound of R10.
- R8. The bootstrap field. `BootstrapResponse` (TOKI-031 R17) gains `unread`, the same map as R7, and its `eventNumber` is the `asOf` of every record. It is built by the same function as R7 in the transaction of TOKI-031 R10, after the event number is read, with the member rows that `listConversationSummaries` now also returns (`lastReadMessageId`, `joinedAt`: the existing statement reads `conversation_members` and gains two columns, so no extra statement for the rows). This amends TOKI-031 R12 ("no unread count") and its R14 (the bound of statements, 8 after TOKI-036 R19, becomes 10: the counts and the mention candidates), made by this ticket in code and in tests; the merged text is not edited (concern 6). `readEventNumber`, `BootstrapDeps` and the two bootstrap tests that count statements change as TOKI-036 R19 lists, with `10` for `8`, and the fixture of 500 conversations and 200 people must still give an equal count to the fixture of 3. The schema stays strict. Check: the rich fixture's answer has `unread` with the expected records; a person with nothing unread has `{}`; the strict parse rejects a record with an added key and a count of -1; the statement count is 10 or fewer and equal for both fixtures; the snapshot test of TOKI-031 R10 shows a message committed after the account read in neither `unread` nor `eventNumber`.
- R9. The live notice. After the commit of a move that changed the pointer (R3), the route calls `publishLive({ userId }, "read.changed", data)` of TOKI-038 R27 with `data` `{ "conversationId": string, "record": UnreadRecord }` (R12; the record has the `asOf` of its own read, R3). It goes to every open connection of the person and to nobody else, and writes no event and no log row (the reason is concern 5: an event takes the counter row lock until the commit, TOKI-036 R16 to R18, and a pointer moves after every message a person reads, so it would queue every person's read behind every other write and fill the log). A move that changed nothing sends no notice. The schema of the notice is in `packages/shared/src/realtime/read.ts`; it is a live kind and is in neither the registry of event kinds nor `kinds.ts` of TOKI-038 R12 (as TOKI-051 R7 does for `draft.changed`). A lost notice costs nothing that stays: the client reads every record again when the connection returns (R17). The route takes the function through a `publishLive` option of `messageRoutes` (TOKI-037 R18), a no-op without the gateway. Check: with a recording `publishLive`, a move forward sends one notice with audience `{ userId }` and the record of the answer; a repeat, an older id and a refusal send none; a real socket test shows the person's second connection receiving the frame and another person receiving nothing; the log has no `events` row.
- R10. Cost. The number of statements of R3 after the commit, of R7 and of R8's addition does not grow with the number of conversations or messages: R7 sends at most 2 for the counts and the candidates, plus the snapshot's own (`BEGIN`, the member rows, the event number, `COMMIT`); R3 sends the locks and reads of R3 plus the same two. Check, on a database of 20,000 messages over 40 conversations with 5,000 unread in one: the counts are right; `EXPLAIN (FORMAT JSON)` of the count statement with `enable_seqscan` off uses `messages_conversation_main_idx` with the row comparison as an index condition and holds no `Sort` node; the statements counted on the connection are equal for 3 and for 500 conversations; the 5,000-message count is read with a bounded number of buffers: the test asserts that the buffers read for a conversation with 5,000 unread are lower than for the whole table (`EXPLAIN (ANALYZE, BUFFERS)`, a ratio, not a time).
- R11. Leaving, privacy. The pointer lives in the member row, so a leave, a removal and the last-member archive of TOKI-029 (which delete the row) remove it with no code of their own (D-133, TOKI-029 hand-off); the person who joins again has a new row with a null pointer. No route and no event shows a pointer, a count or the time of a move to anyone but the person: the member list (TOKI-029, TOKI-035), the details, the message entry (TOKI-037 R15) and every event carry none of `lastReadMessageId`, `unread`, `asOf` or `firstUnreadId`; the sender sees no mark (D-048, AC-023). Check: a leave deletes the row and the next `GET /unread` has no record for the channel; a rejoin starts with a null pointer; the schemas of the member list, the details, the message entry and every event kind in the registry of TOKI-038 are parsed in a test that finds none of the four names; a search of `apps/server/src` finds `last_read_message_id` only in the files this work names (Layout); the live notice reaches one person only (R9).
- R12. The shared shapes. `packages/shared/src/unread/` (exported from the package index) holds: `UnreadRecordSchema`, a strict object `{ count: integer >= 0, mention: boolean, firstUnreadId: uuid | null, asOf: integer >= 0 }` and its type `UnreadRecord`; `UnreadSnapshotSchema` `{ eventNumber, unread: record by conversation id }` (R7); `ReadRequestSchema` `{ messageId }` and `ReadResponseSchema` `{ unread: UnreadRecord }` (R3); `ReadChangedSchema` (R9, in `src/realtime/read.ts`); `isForward` (R2); and the constant `READ_ADVANCE_DELAY_MS` 500 and `READ_ADVANCE_MAX_WAIT_MS` 2000 (R15). The bootstrap `unread` is a record by conversation id of `UnreadRecordSchema`. Check: schema tests accept a valid record and refuse a count of -1, a non-integer, a missing key, an added key and a `firstUnreadId` that is not a uuid or null; a type test imports each name from `@toki/shared`.
- R13. The tracker. `createUnreadTracker(options)` of `packages/client-core/src/unread/`, exported from the package index with its types. `options`: `conversations` (the store of TOKI-032, with the additions of R20), `sync` (the engine of TOKI-040: `getMessages`, `registerEventHandler`, `subscribeEvents`), `api` (the two calls of R17), `windowUse` (the port of R21), `timers` (`Timers`, TOKI-032), `getUserId` and `isMentioned` (`isMentioned(message, userId)` of TOKI-050 R19). It keeps, for each conversation, `base` (an `UnreadRecord`, or none: a zero record with `asOf` 0) and `local` (a map from message id to `{ number, createdAt, counts, mention }`), and the store's slot shows `count` = `base.count` plus the entries of `local` with `counts` true, `mention` = `base.mention` or any entry with `mention` true, `firstUnreadId` = `base.firstUnreadId` or, when that is null, the entry of `local` with `counts` true that is earliest by (`createdAt`, id). Every change goes through one pure function `reduce(state, action)` in `reducer.ts`, with the actions `snapshot` (R14), `record` (R14), `message` (R14), `read` (R15). It uses no DOM or browser global and no timer of its own (client-core rules, TOKI-032 R25, TOKI-008 R19). Check: reducer tests of R14 and R15; the package has no DOM reference; `createUnreadTracker` with fakes needs no timer other than `timers`.
- R14. How a number stays right. (a) `snapshot({ eventNumber, unread })` (the bootstrap answer, a refresh, the answer of R7): for every conversation of the store, `base` becomes the record of the map or a zero record, both with `asOf` `eventNumber`, only when `eventNumber` is not lower than the held `base.asOf`; and every entry of `local` with `number` not above `eventNumber` is dropped, because the answer already holds it. (b) `record(r)` (the answer of R3, a live notice of R9): `base` becomes `r` when `r.asOf` is higher than the held `base.asOf`, or equal and (`r.count` lower, or equal with `r.mention` false and the held true) (a pointer only moves forward, so at one number a later pointer has no larger count); otherwise it is ignored; then the entries of `local` with a number not above `r.asOf` are dropped. (c) `message(event)` (an event `message.created`, read through `registerEventHandler`, TOKI-040 R18, after the engine's own effect): nothing when `data.message.kind` is not `user`, when the author is the person, or when `event.number` is not above `base.asOf` (already counted) or the id is already in `local`; otherwise an entry with `counts` true when the message is in the main list (`parentId` null or `alsoInChannel` true) and `mention` true when `isMentioned(message, userId)` (TOKI-050 R19), kept only when `counts` or `mention` is true. When the conversation is being read (R15) a main-list message is not added to `local` and the pointer is moved to it instead (R15), but a thread reply that mentions the person is added (a mention in a thread is not read by reading the main list, F13). The unread slot of a conversation the store does not hold is not made. (d) The numbers need no consecutive order and no cursor: the reducer is the same for events in any order and for a repeat, because each entry is keyed by the message id and each record by `asOf`. Check: a table of cases: a record with `asOf` 10 and then a `message` of number 9 changes nothing, of number 11 adds one; a live record arriving after the message event it already contains (`asOf` at or above the event's number) does not count it twice; a live record arriving before a message event whose number is above its `asOf` is followed by +1; two records at one `asOf` with counts 3 then 2 end at 2, and 2 then 3 at 2; a stale record (lower `asOf`) is ignored; a snapshot lowers a count that another device cleared; replaying the same events twice gives the same result; events in a random order give the same result as in order; a reply that is not also sent to the channel adds no count and a mention gives `mention` true; a system line and the person's own message add nothing; a reply also sent to the channel adds one.
- R15. Reading and sending the pointer. A conversation is being read when the tracker has been told that the list of that conversation is at the bottom (`setAtBottom(conversationId, atBottom)`, the function the page gives to `onAtBottomChange` of TOKI-041 R19, which calls it with `false` on unmount), and `windowUse.isInUse()` is true (R21), and the conversation is the one shown (a person is at the bottom of one list at a time: a `setAtBottom(other, true)` replaces the earlier id). On the change to "being read", and for each `message.created` that places a main-list message at the end of a conversation that is being read, the tracker takes as its target the newest confirmed message of the main window (`sync.getMessages(id).items`: the last item of kind `message`; a waiting item is not a target), and: (1) at once, locally, empties the count and the first unread id of that conversation and the `mention` unless an entry of `local` that is a thread reply later than the target holds it (the dot may flash and is then set by the answer: R14); (2) sends `PUT /read` (R3) with the target, after `READ_ADVANCE_DELAY_MS` of quiet and at most `READ_ADVANCE_MAX_WAIT_MS` after the first target of a burst, with the newest target at the time, one request in flight for each conversation, and the answer goes to `record` (R14 (b)). A pending target is sent at once when the conversation stops being read, so a person who leaves does not lose it. No request is sent when the target is not later than the last target sent or the position that the held `base` names; a failed request is not retried by itself (the next target or the next resync repairs it; D-079: nothing is shown for it); a 404 or 403 drops the target. The person's own sent message needs no move to count as read (it is never counted, R4) but the list goes to the end after a send (TOKI-041 R17), which calls `setAtBottom(id, true)`. The tracker marks nothing read when the conversation is not at the bottom, when the window is not in use, or when no window is held (TS-033, TS-034). Check, with a fake `windowUse` and the recording `timers` (no real timer): at the bottom in use with 3 unread, the count is 0 at once and one request is sent after the delay with the id of the newest message; ten messages in a burst send one request with the last id, and one more at the maximum wait when they never stop; the window not in use sends nothing and keeps the count; scrolled up (`setAtBottom` false), a message raises the count and sends nothing; a switch of conversation sends the pending target at once; a request that fails leaves the local zero and sends nothing more; an old target is not sent; the answer of an earlier request does not undo a later one (R14 (b)).
- R16. Events that need the server. For `message.deleted` and `message.edited` (TOKI-047 R10) of a conversation whose slot shows a count above 0 or a mention, the tracker removes the entry of `local` with that id (the edit: when the new entry no longer qualifies by R14 (c)) and asks for every record again (R17), because a message that the base counted may have left the count (concern 3). For `conversation.restored` (TOKI-038 R20) and for a `member.joined` event of the signed-in person it asks the same way (the pointer survives an archive; a joiner starts at null, concern 2). For `conversation.left` (TOKI-040 R14) it drops the conversation's state (the store already removed the slot, D-133). A request for every record is made with at most one in flight and one queued, however many events ask. Check: a delete of an unread message in a conversation with a count 3 sends one `GET /unread` and the new snapshot lowers the count; two deletes together send one and one more; a delete in a conversation with no count sends none; a left conversation has no state and no slot; a restored channel asks once.
- R17. Resync. The tracker asks `GET /api/v1/unread` (R7) through `api.unread.read(signal?)` (a method of `createApiClient`, TOKI-032 R9, same rules: 10 seconds, no retry), applies the answer as `snapshot` (R14 (a)), and does it: when the connection's status becomes `online` after a time it was not (read through `sync.attachConnection`'s state, TOKI-040 R19; the first `online` after the page loaded is skipped, the bootstrap has just given the same), and for the cases of R16. A failed read changes nothing and is repeated at the next such moment. `api.unread.advance(conversationId, messageId, signal?)` sends R3 and reads its answer with `ReadResponseSchema` in the form that drops unknown keys (TOKI-032 R3). The live frame is read through `sync.registerLiveHandler("read.changed", ...)` (TOKI-040 R18) and parsed with `ReadChangedSchema`; a frame that does not parse is ignored. Check: a fake connection going `offline` then `online` triggers one read and the first `online` after the start none; a snapshot answer ends the state of a conversation that another device cleared; a frame for a conversation the store does not hold is ignored; the 10-second and error rules are those of the core.
- R18. The store slot is filled, and by whom. After every change of the state of R13 the tracker calls `conversations.setUnread(id, { count, mention, firstUnreadId })` for each conversation whose shown value changed (the store ignores an equal value, TOKI-032 R20), and `clearUnread(id)` when the shown value is `{ 0, false, null }`; it is the one caller of both, as TOKI-032 R20 says, and no other code writes the slot. - R19. The contract for TOKI-054. ## Design
### The pointer and the count
One column on the member row. A person's state for a conversation already lives in `conversation_members` (level, mute, star), a leave deletes the row, and so the pointer is removed with it (D-133) with no code. The pointer names a message and not a time: the message is always there (TOKI-036 R8, a row is never deleted), the key stops a pointer from naming another conversation's message, and the order is read from the message (`created_at`, `id`), so a change of the order rule is one place (R2, R4). Alternatives refused: a time column (copies the order, and two messages with one time need the id too); the event number of the message (`messages` has no such column and the sender does not write one).
The count is computed, never stored: a stored count would have to change with every message, edit and delete of every conversation, and would be wrong after the first missed write. Counting from the pointer costs by what is unread, not by the history (R10). The prototype shows no cap, so the count has none (TOKI-012 concern 4).
Which messages count follows the predicate of the index of TOKI-036 R11: roots, system lines and replies also sent to the channel are in the main list; `kind = 'user'` leaves the system lines out (D-100, D-165); the author test leaves out the person's own messages; `deleted_at is null` leaves out deleted ones (concern 3).

### How the number stays right
Three things can disagree: the count the server computed, the messages that arrived since, and another device's reading. A record carries `asOf`, the event number the server read in the same snapshot as the count (R7: a read-only `REPEATABLE READ` transaction, the same as the bootstrap's; TOKI-036 R16: every message with a number up to it is in the count and none above it). The client keeps the record as `base` and adds one for every counted message event with a higher number (R14). This one rule gives, with no ordering between channels of data: a record that arrives before or after the message events it overlaps; a repeated event; a replay after a reconnect (TOKI-039); and a record from another device. A stale record (lower `asOf`) is ignored, and two records at one `asOf` end at the smaller count, because a pointer only moves forward (R14 (b)).
The cases that cannot be done by adding one (a delete, an edit that removes a mention, a restored channel) ask for every record again (R16, R17).

### The request, the notice and the other device
A move is `PUT /conversations/{id}/read` with the id of the newest message the person saw. It is idempotent and forward-only (R3): the answer is 200 whether or not the pointer moved, so a repeat or a late request from a slow tab is harmless, and the pointer cannot go back. The move takes the member row `FOR NO KEY UPDATE` after the conversation row `FOR SHARE`, the order of TOKI-037 R8, and takes no event lock.
The other devices are told by a live notice (R9), not by an event of the log, as TOKI-051 does for drafts (concern 5): a pointer moves after every message a person reads, and an event would hold the counter row lock of the whole workspace for each (TOKI-036 R16 to R18). Because every record has its `asOf` (above), a notice that arrives early, late or never leaves nothing wrong that stays: a device reads every record again when its connection returns (R17).

### Reading
Reading is decided in the client. The server cannot know that a window is in use or that a list is at the bottom. The tracker joins three facts (R15): the list is at the bottom (`onAtBottomChange`, TOKI-041 R19: the window holds the newest message, `hasNewer` false, within 32 px of the end), the window is in use (visible and focused, R21), and a message to read exists. The count falls at once on the screen and the request follows after a short wait, so a person scrolling or a busy channel sends one request for a burst, not one for each message (R15: 500 ms of quiet and at most 2,000 ms, the numbers of concern 10). A message that arrives while the person is at the bottom of an open, used window is never counted: it is placed by the engine (TOKI-040 R16) and the pointer is moved to it.
At the opening the first unread id is there before the list reports the bottom (R19), so TOKI-054 keeps the New divider on the first unread message, by id, while the pointer moves on.

## Data safety
The pointer is a message id of the person's own conversation: no text, no name. `GET /unread` and the notice hold ids of the person's own conversations and messages only. No log line holds a message id list (R3). A pointer is never shown to another person (R11).

## Areas of concern
1. A message can commit after a message with a later `created_at`. Not decided, and it is TOKI-036 concern 12, which is still open and asks this ticket. The fact: a pointer that has moved to the later message puts the earlier one before it, so the earlier one is never counted, for any device that reads the table afterwards. The window is short (a person at the bottom of an open list sees the earlier message arrive by event and it is placed above), but it exists whenever the person's pointer moves between the two commits and the person does not see the earlier message. This spec builds the position rule in one place (`isForward`, `getMainListPositions`, the row comparison of R4), so either answer of TOKI-036 changes that place only. Proposal, not decided: take the answer of TOKI-036 concern 12 as it is given; if the writer takes the counter lock before it reads the clock, nothing changes here; if the gap stays, a pointer that names the event number of the message is the other way, and needs a column on `messages` and a change of R2 to R4. Question for the product owner, with TOKI-036 and TOKI-037. Owner: Thanh Truong (product owner).
2. Whether the history that was there before a person joined a channel is unread. Not decided. D-029, D-116 and FR-20 give the full history to a joiner and no rule for its count; D-100 says only that the line "Minh joined" raises none. Counting every old message would show a new member a count of thousands. Proposal, not decided: a person's start point is the time they joined (`conversation_members.created_at`), so only messages after it count, and a rejoin starts again at its own time; R4 and R16 are built on it, and a different answer changes the start point of R4 only (for example, the newest message at the time of the join, written by the join code of TOKI-029, which this work would then have to edit). Owner: Thanh Truong (product owner).
3. Whether a deleted message leaves the count, and an edit that removes the person's mention leaves the @ mark. Not decided for a message with no mention. F13 says that when the message is deleted or the mention is edited out, the Activity item is removed and "the badges fall back", which covers the mention case; the log says nothing for a plain message. Proposal, not decided: a deleted message is not counted and a message that no longer mentions the person gives no @ mark, for every message (R4, R5, R16); the other reading is that a deleted message stays in the count until the pointer passes it, which would leave a count that opens to nothing (D-049: a message deleted by its author with no replies is not drawn). Owner: Thanh Truong (product owner).
4. Whether a window that is visible and focused but not used for a long time still reads a conversation. Not decided. D-052 says "the window is in use" and does not say how it is known; the platform gives visibility and focus (R21), and presence gives "Away after 5 minutes without activity" to other people (TOKI-055), which is a different thing. Proposal, not decided: visibility and focus only, with no idle time, so that a person who walks away from a focused window at the bottom of a conversation reads what arrives; the stricter reading adds a last-input time to `WindowUse` and changes R21 only. Owner: Thanh Truong (product owner).
5. How the other devices learn of a move: a live notice and not an event of the log. Decided in this spec. Reason: every event takes the counter row lock of the workspace until its commit (TOKI-036 R16 to R18); a pointer moves after every message a person reads, so each message in a busy channel would queue one write for each reader behind every send, and the log would fill with them. The same reason and the same route as TOKI-051 concern 4 for drafts. The cost, a lost notice, is repaired because every record carries `asOf` and the client reads every record again when its connection returns (R14, R17). Alternative refused: a `user`-scope event with the count, which would replay by itself but adds the lock and the volume, and would still need the `asOf` rule because the count is read before the event is numbered. Owner: Thanh Truong.
6. Where the counts reach the store, which TOKI-031 concern 7 and TOKI-032 concern 7 left to this ticket. Decided in this spec: both ways, for different jobs. The bootstrap answer carries `unread` (R8), so the first paint of the list has counts and a refresh replaces them (R20); the tracker is the one caller of `setUnread` and `clearUnread` and handles every change between two loads (R18). Reason: one source for a load and one for a change, with the `asOf` rule (R14) making them agree. The amendment of TOKI-031 R12 and R14 is made in code and tests and not in the merged text, as TOKI-036 concern 13 did. Owner: Thanh Truong.
7. How the pointer is represented. Decided in this spec: the id of the last message read, on the member row, with a composite key to the message (R1); the position is read from the message (R2). Reasons and the alternatives refused are in Design, "The pointer and the count". Owner: Thanh Truong.
8. D-052 says a conversation is read at the bottom of the list; F13 step 5 says the @ mark and the count clear "once the message is on screen". Decided: D-052, a Confirmed decision, is the rule for the count and the mark alike (R15); a mention message that is on screen but above the bottom keeps its mark until the person reaches the bottom (TS-034). F13's step is the wording of a journey and D-091 accepts what the journeys do, not their wording. Owner: Thanh Truong.
9. Where the window-in-use rule lives. Decided in this spec: a small port in `client-core` (`WindowUse`) with its web adapter in `apps/web`, and not a new member of `Platform` of TOKI-018. Reason: `Platform` holds what the shared interface asks of a device (storage, files, sound, notifications, tabs); the phone app will give its own adapter of the same port, and TOKI-055 may need a member for activity, so the two can be joined then (Hand-offs). Owner: Thanh Truong.
10. The wait before the pointer is sent. Decided in this spec, as a technical choice the Blueprint leaves to the builder: 500 ms of quiet and at most 2,000 ms from the first target of a burst (R12, R15). Reason: the count must fall at once on the screen (done locally) while the server need not hear every message of a busy channel, and 2,000 ms bounds how long another device shows a stale count; a pending target is sent at once when the person leaves. TOKI-089 may tune the numbers. Owner: Thanh Truong.
11. The count has no cap. Decided: the prototype's badge sets none (TOKI-012 concern 4, TOKI-033 R7) and the log sets none; the query costs by what is unread (R10). Owner: Thanh Truong.
12. Who owns the first unread message. Decided: this work gives `firstUnreadId` (R4, R19); TOKI-054 draws the New divider, keeps it while the conversation is open and drops it at the next opening (TOKI-041 R8, D-052). Owner: Thanh Truong.
13. A conversation restored after an archive, and a new direct message. Decided in this spec: a restored channel and a joiner read their record from the server (R16), because the pointer survives an archive and a joiner's start is the server's; a direct message that appears has no record and is counted from the events that follow it (`conversation.appeared` and `message.created` have consecutive numbers, TOKI-036 "The event contract"). Owner: Thanh Truong.
