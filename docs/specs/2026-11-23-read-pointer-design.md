# Read pointer design

Date: 2026-11-23 · Status: draft for review (concerns 2 to 4 and the `@` dot rule of concern 8 are open for the product owner)
Intent: docs/intents/read-pointer.md (Thanh Truong)
Ticket: TOKI-053

## Goal
A person needs to see which conversations hold something they have not read, how much, and whether it mentions them, and to see it go away once they have read it, on every device. The store of TOKI-032 has a slot for this (`unread`, `setUnread`, `clearUnread`) and the rows of TOKI-033 draw it, but nothing fills it. This work builds the server side (one pointer for each person and conversation, the count, the requests, the bootstrap field, a notice to the person's other devices) and the client side (a tracker that counts arriving messages, decides when a conversation is read, sends the pointer and fills the slot).
The hard rule is that a count must stay right while messages arrive, while the person reads on another device and after a lost connection. The design (Design, "How the number stays right") gives every server answer the event number it was computed at (`asOf`) and the version of the pointer it was computed with (`pointerVersion`), and the client adds to it only the messages with a higher number. Two answers about one conversation then have an order even when no event separates them, because a pointer move writes no event. Then the same reducer is right for the bootstrap answer, a reply to a request, a live notice that arrives before or after the message events, and a re-read after a lost connection. The second rule is privacy: the pointer is read and written only for the signed-in person and is never part of an answer about someone else (D-048).

## Requirements
Requirements that rest on an open concern are proposals until the product owner decides it: R4 and R19 on concern 2 (the start point); R4, R5, R14 (c) and R16 on concern 3 (deleted and edited messages); R15 and R21 on concern 4 (no idle time) and, for the `@` dot, concern 8.
- R1. The pointer columns. `conversation_members` (TOKI-028 R12) gains two columns: `last_read_message_id` (`uuid`, null), the message the person has read up to, where null means nothing was read since the person joined (R4, concern 2); and `pointer_version` (`bigint`, not null, default 0), the number of moves of this pointer, which `setReadPointer` raises by 1 at each move that changes the pointer (R2) and which orders two answers about one conversation when no event separates them (R14, concern 14). One migration, `<number>_read_pointer.sql`, made with `pnpm db:generate --name read_pointer` (TOKI-019 convention 8), adds the two columns to the existing table and the composite key `conversation_members_last_read_fkey` on (`last_read_message_id`, `conversation_id`) to (`id`, `conversation_id`) of `messages` through `messages_id_conversation_id_key` of TOKI-036 (so a pointer cannot name a message of another conversation), `ON DELETE RESTRICT` and not checked when the column is null. The key is written as SQL in the migration (a schema file may not import another module's table, TOKI-019 R22); the columns are declared in `modules/conversations/schema.ts`, so `pnpm db:generate` run again reports no change. The migration inserts no row and changes no existing value (the pointer is null and the version 0 for every existing member row). Neither column is part of the primary key and no trigger changes. This ticket changes nothing of `message_mentions`: the index that the mention read needs is asked of TOKI-050 (R5, Plan changes). Check: the catalog test of TOKI-028 R12 (amended by this ticket) expects nine columns, the seven of R12 and these two in this order; the key is read from `pg_constraint` with `ON DELETE RESTRICT`; a pointer to a message of another conversation is refused by name; a delete of the member row succeeds with the pointer set; the migration test of TOKI-005 passes; the migration file has no `CREATE TABLE`.
- R2. Position and forward-only. The position of a message is the pair (`created_at`, `id`) of its row (TOKI-036 R12), compared as a row. `messages` exports `getMainListPositions(client, conversationId, messageIds)`, which returns, for the ids that are rows of that conversation in the main list (`parent_id is null or also_in_channel`, TOKI-036 R11; a system line is in it), a map from id to `{ createdAt, id }`, in one statement; an id that is not there is absent. `conversations` exports three functions on the member row. `lockReadState(tx, conversationId, userId)` runs `select last_read_message_id, created_at from conversation_members ... for no key update` and returns `{ lastReadMessageId, joinedAt }` or null when the person has no member row. `readReadState(client, conversationId, userId)` runs the same select with no lock, adds `pointer_version`, and returns `{ lastReadMessageId, joinedAt, pointerVersion }` or null; it is the read of a read-only snapshot (R7). `setReadPointer(tx, conversationId, userId, messageId)` sets the column and `pointer_version = pointer_version + 1` in one statement. The rule that decides a move is one pure function of `packages/shared`, `isForward(held, next)` (`held` a position or null, `next` a position): true when `held` is null or `next` is later than `held` by the order of TOKI-036 R12. A move to the same message, or to an earlier one, changes nothing, and so does not raise the version. Check: unit tests of `isForward` for null, equal, earlier, later by time, and equal time with a greater id; a database test of `getMainListPositions` with a root, a system line, a reply also sent to the channel (all present), a reply that is not (absent), an id of another conversation (absent) and an unknown id (absent); `lockReadState` returns null for a person who is not a member and the two fields for a member; `readReadState` returns the three fields, takes no lock (a second connection holding `for no key update` on the row does not make it wait) and returns null for a non-member; `setReadPointer` called twice leaves the version at 2; the module export tests list the new names.
- R3. The request that moves the pointer. `PUT /api/v1/conversations/{id}/read` takes `{ "messageId": string }` (strict; a lower-case UUID) and answers 200 with `{ "unread": UnreadRecord }` (R12) for that conversation as it stands after the request. It needs a session (401), and then runs the steps of TOKI-037 R1 that apply: (1) the schemas (400 `validation_failed`); (2) `getConversationFacts`: `null` and a private channel, DM or group of which the person is not a member are 404 `not_found`; (3) `canReadConversation` (TOKI-027 R5): a person who is not a member of a public channel is 403 `forbidden`. An archived channel may be read, so the move is allowed there and stored (the pointer survives an archive, concern 13), and its record and notice are sent like any other; the client tracker holds no state for an archived channel and sends none (R15, R16). Inside one transaction at the default level, in the lock order of TOKI-037 R8: the account row `FOR SHARE`, the conversation row in the mode TOKI-037 R8 gives its kind (`FOR SHARE` for a channel and a group, `FOR NO KEY UPDATE` for a `dm`), then `lockReadState`; a person with no member row after the locks is answered by step 2 or 3 again. A `messageId` that `getMainListPositions` does not return is 404 `not_found`, with the same body as an unknown conversation and with no id in it. The pointer is moved with `setReadPointer` when `isForward(position of the held pointer, position of messageId)` is true (the held pointer's position is read with the same function) and left alone otherwise; the answer is 200 in both cases, so a repeat, a late request from a slow tab and a move to an older message are all 200 and change nothing (the rule of this request, not a general one). The route writes no event and takes no event lock, so it never waits for the counter row (concern 5). After the commit the route calls `readRecord` (an option of `messageRoutes`, TOKI-037 R18, given by `app.ts` from `readUnreadRecord` of `bootstrap`, R7), which reads the person's count, pointer, pointer version and the event number in one read-only snapshot of its own. It must not be a read in the transaction of the move or two reads at the default level: a count and an event number read apart are two moments and `asOf` would not be true for the count (R14). The record it returns is the answer, and when the pointer moved the live notice of R9 is sent. The `Origin` and media-type rules of TOKI-022 R45 and R46 cover it. No log line holds a message id list or a person's id beyond the usual request line. Check: a table test of each status and code; a move forward stores the id, raises `pointerVersion` by one and returns the new record; the same request twice stores once, leaves the version and answers the same; a move to an older message and to the same one change nothing and answer 200; two requests at once on two connections, the second waiting, end at the later of the two ids whatever the order they commit in; a thread reply that is not also sent to the channel, a message of another conversation and an unknown id are 404 with equal bodies; an Admin who is not a member of a private channel gets 404; a person who left gets 404 or 403 by the kind of channel; a move on an archived channel is stored and answered 200, with a record of `{ 0, false, null }`, the person's `pointerVersion` and an `asOf` (R7); a move to the newest message of a conversation answers the zero record, not an absent one; a read in a `dm` takes the conversation row `FOR NO KEY UPDATE` and in a channel `FOR SHARE` (read from `pg_locks` by a second connection); the statement log shows no write to `events` or `event_counters`; the record read after the commit is the one of a snapshot (the transaction shown is `repeatable read` and read-only; a message committed by a second connection between the move and the read is counted only when its number is not above the answer's `asOf`, so the count and `asOf` are one state).
- R4. The count. `messages` exports `readUnread(client, input, readers)` (`input` `{ workspaceId, userId, rows: [{ conversationId, lastReadMessageId, joinedAt, pointerVersion }] }`, built by the caller from the member rows; `readers` `{ listMentionCandidates }`, R5) that returns the `UnreadEntry` of R12 (the record without `asOf`) for each conversation that has a count above 0 or a mention, and `pointerVersion` is the one of its input row. For one conversation the position `after` is the position of its pointer message, or, when the pointer is null, (`joinedAt`, the smallest uuid) (concern 2). A message is unread when all hold: its position is later than `after`; `kind` is `user` (a system line, D-100, D-165, is out); it is in the main list (`parent_id is null or also_in_channel`: a thread reply is out, F14, a reply also sent to the channel is in, D-160); `author_id` is not the person (a person's own message is never unread); `deleted_at` is null (concern 3). `count` is how many; `firstUnreadId` is the id of the earliest of them by the order of R2, or null. The server counts exactly and sets no cap: the prototype's badge sets none and the screen decides what it shows (TOKI-012 concern 4, TOKI-054; concern 11). It makes no change to any row. The query is written so that the partial index `messages_conversation_main_idx` (TOKI-036 R11) serves it: it keeps the predicate as the index writes it and bounds the range by the row comparison on (`created_at`, `id`). One statement reads all conversations of the call, with the rows passed as arrays (`unnest`). For each row of its input it returns `count`, `firstUnreadId` and the time of `after` (R5 needs it). `firstUnreadId` is read by a `lateral` subquery ordered by (`created_at`, `id`) with `limit 1`, which the same index serves with no `Sort` node, and not by an ordered aggregate. The cost is by conversation and by unread message, not by the length of the history (R10). A muted conversation and a conversation of notification level `none` (TOKI-028 R15) both keep their count: D-103 says only Mute hides the badge, and what the list shows is TOKI-054's. Check, with rows inserted by SQL: counts for a pointer in the middle, at the end, null, and set to a system line; a system line, a thread reply, the person's own message and a deleted message are not counted; a reply also sent to the channel is; two messages with one `created_at` are split by the id; `firstUnreadId` is the earliest counted one and null for a count of 0; a conversation with nothing unread and no mention is absent from the result; 1,000 unread messages count 1,000; a conversation of another person's pointer is unaffected; the entry carries the `pointerVersion` of its row.
- R5. The mention mark. A conversation has `mention` true when a message that passes the tests of R4 except "in the main list" mentions the person: it is later than `after`, of kind `user`, not by the person, not deleted, in the main list or in a thread (F13: a mention in a thread reply raises the @ mark and not the count), and it names the person or `@channel` (TOKI-050 R19 `isMentioned`: `@channel` counts for every member but its sender). `mentions` exports `listMentionCandidates(client, { userId, ranges: [{ conversationId, after: Date }] })`, one statement over `message_mentions` (TOKI-050 R4) that returns, for each range, the `message_id` of the rows with `created_at` not earlier than `after` and either `user_id = userId` or `is_channel`. It and the index `message_mentions_conversation_created_idx` on (`conversation_id`, `created_at`) that serves its range belong to TOKI-050, which is asked to carry both (Plan changes); this ticket builds neither. The index serves the range by conversation and time, and `user_id = userId or is_channel` is a filter over the mention rows of that range, which are bounded by the messages after `after`. `readUnread` takes the function as `readers.listMentionCandidates` (the `messages` module imports nothing of `mentions`; the caller passes it, and the caller is `bootstrap`, R7, which imports both modules through their `index.ts`). The calls are in this order: the count statement of R4 returns the time of `after` for each conversation; the candidates statement takes those times as its ranges; one more statement checks the returned ids against `messages` for the rest of the tests (position, kind, author, deleted). So the mark costs two statements for all conversations, the count one, and a call of `readUnread` three in all (R10). A message that mentions the person and is unread but not counted (a thread reply) gives `mention` true and no count. Check: a message naming the person, one naming `@channel` by another person and one in a thread give `mention` true; the person's own `@channel` message, a deleted message, a message before the pointer and a message naming another person give false; a thread reply that names the person gives `mention` true and `count` 0, and the entry is present; the reader is called once for all conversations, with the times that the count statement returned; with no reader given the mark is false for every conversation.
- R6. What is not read. No code of this work reads a conversation of which the person is not a member, or the pointer of another person. The lists (R7 and R8) pass only the rows of `listConversationSummaries`, so an archived channel, which is not in the list (TOKI-031 R17), has no entry in them. The one read of an archived channel is the record that follows a move on it (R3): the person is a member, the history is readable, and the record is the person's own. `readUnread` computes only for the person of its input. The tracker keeps no state for a conversation the store does not hold (R14, R15), so the record or the notice of an archived channel is dropped there, and its `conversation.archived` event removes the state as `conversation.left` does (R16). Check: a fixture with an archived channel and a channel the person left returns neither in the answers of R7 and R8; a move on the archived channel answers 200 with the person's record; the argument is always the signed-in person in each caller (a search finds no call with another id).
- R7. The request that returns every record, and where it lives. `GET /api/v1/unread` answers 200 with `{ "eventNumber": number, "unread": { [conversationId]: UnreadEntry } }` (R12) for the signed-in person: every conversation of their list with a count above 0 or a mention, and nothing for the rest. `asOf` of every entry is that `eventNumber`. The builder and the route are in `apps/server/src/bootstrap/` (`unread.ts`, `unread-routes.ts`), the folder outside `modules/` that already reads the modules through their `index.ts` and that no module imports, so there is no cycle: `inReadSnapshot` and `readEventNumber` are here, `messages` stays free of `bootstrap`, and the route and the bootstrap use one function. `bootstrap/index.ts` exports `unreadRoutes` (registered by `app.ts` next to `bootstrapRoutes`) and `readUnreadRecord`. The builder is `buildUnread(tx, { workspaceId, userId, rows }, deps)`, which calls `readUnread` of `messages` with `listMentionCandidates` of `mentions` and returns the map of entries. The route reads in one snapshot (`inReadSnapshot`, TOKI-031 R10: a read-only transaction at `REPEATABLE READ`), these statements in this order: `BEGIN`, the account (`getAccountById`: a deactivated account is 401 `account_deactivated`, and its `workspaceId` is the one every other read filters on), `listConversationSummaries` (the member rows with `lastReadMessageId`, `joinedAt` and `pointerVersion`, R8), the count (R4), the candidates and the check (R5), `readEventNumber(tx, workspaceId)` (TOKI-036 R19) and `COMMIT`: 8 statements. So every entry is the state at that number and no message with a higher number is in any count (TOKI-036 R16: committed events have no gap). It takes no lock. `readUnreadRecord(db, { workspaceId, userId, conversationId }, deps)` is the one-conversation read of R3: in its own snapshot it runs `BEGIN`, `readReadState`, the count, the candidates, the check, `readEventNumber` and `COMMIT` (7 statements) and returns an `UnreadRecord`: the entry, or when the conversation has nothing unread an entry of `{ 0, false, null }` with the person's `pointerVersion`, with `asOf` the event number read; for a person with no member row (a leave that came between the commit and the read) it returns `{ 0, false, null, 0 }` and no notice is sent. A person with no conversation gets `{ eventNumber, unread: {} }`. The answer never holds a message text, a name or an id other than the person's own conversations and message ids. Check: a person with three conversations (two unread) gets two entries; the answer parses with the strict response schema; a second connection that commits a message after the first read (the seam of TOKI-031 R10) is in neither the counts nor the number, and the next call has both; the transaction shows `repeatable read` and read-only; `readUnreadRecord` returns the zero record with `asOf` for a conversation with nothing unread, for an archived channel and, with version 0, for a person with no member row; the statements are 8 for the route and 7 for `readUnreadRecord`, equal for 3 and for 500 conversations; a search shows that `messages` imports nothing from `bootstrap`.
- R8. The bootstrap field. `BootstrapResponse` (TOKI-031 R17) gains `unread`, the same map of entries as R7, and its `eventNumber` is the `asOf` of every entry. It is built by `buildUnread` of R7 in the transaction of TOKI-031 R10, after the event number is read, with the member rows that `listConversationSummaries` now also returns (`lastReadMessageId`, `joinedAt`, `pointerVersion`: the existing statement reads `conversation_members` and gains three columns, so no extra statement for the rows). The entries carry no `asOf` because it is equal to `eventNumber` for every one (R12); that keeps the body smaller. This amends TOKI-031 R12 ("no unread count"), R14 (the bound of statements: 7 today, 8 after TOKI-036 R19, becomes 11: the counts statement and the two statements of the mention mark add 3) and R20 (the size bound and the key list), made by this ticket in code and in tests; the merged text is not edited (concern 6). The tests it changes, by name: in `tests/bootstrap/bounds.db.test.ts` the two statement assertions (`toBeLessThanOrEqual` and `toHaveLength`, 8 after TOKI-036 R19, become 11) and the comment that lists the statements (it lists eleven: begin, account, accounts by ids, workspace, people, conversations, event number, counts, candidates, check, commit), the exact key list `conversations, eventNumber, members, user, workspace`, which gains `unread`, and the two size bounds, which now run on a fixture in which every one of the 500 conversations holds an entry (about 144 bytes each, about 72 KB in all, on the 176 KB of TOKI-031 R20): the first bound, 250,000, becomes 275,000, and the second, 400,000, stays (the fixture at the text limits is then about 323 KB); both are regression guards chosen here, as TOKI-031 concern 6 chose them, and the writer measures the two bodies and says the figures in the pull request; in `tests/bootstrap/build.db.test.ts` the fake `readEventNumber` and the first test, whose valid answer gains `unread: {}`. `readEventNumber`, `BootstrapDeps` and the code that change for the event number are as TOKI-036 R19 lists. The schema stays strict. Check: the rich fixture's answer has `unread` with the expected entries; a person with nothing unread has `{}`; the strict parse rejects an entry with an added key and a count of -1; the statement count is 11 or fewer and equal for the fixtures of 3 and of 500 conversations; the snapshot test of TOKI-031 R10 shows a message committed after the account read in neither `unread` nor `eventNumber`; the two size bounds hold on the fixtures above.
- R9. The live notice. After the commit of a move that changed the pointer (R3), the route calls `publishLive({ userId }, "read.changed", data)` of TOKI-038 R27 with `data` `{ "conversationId": string, "record": UnreadRecord }` (R12; the record has the `asOf` of its own read, R3). It goes to every open connection of the person and to nobody else, and writes no event and no log row (the reason is concern 5: an event takes the counter row lock until the commit, TOKI-036 R16 to R18, and a pointer moves after every message a person reads, so it would queue every person's read behind every other write and fill the log). A move that changed nothing sends no notice. The schema of the notice is in `packages/shared/src/realtime/read.ts`; it is a live kind and is in neither the registry of event kinds nor `kinds.ts` of TOKI-038 R12 (as TOKI-051 R7 does for `draft.changed`). A lost notice costs nothing that stays: the client reads every record again when the connection returns (R17). The route takes the function through a `publishLive` option of `messageRoutes` (TOKI-037 R18), a no-op without the gateway. Check: with a recording `publishLive`, a move forward sends one notice with audience `{ userId }` and the record of the answer; a repeat, an older id and a refusal send none; a real socket test shows the person's second connection receiving the frame and another person receiving nothing; the log has no `events` row.
- R10. Cost. The number of statements does not grow with the number of conversations or messages. `GET /unread` sends 8 (R7). The addition of R8 to the bootstrap is 3 (the count, the candidates, the check), which makes the transaction 11 with the 8 of TOKI-036 R19. `readUnreadRecord` sends 7 (R7), and R3 adds to it the statements of its own transaction (the account lock, the conversation lock, the member row, the positions, the update). Check, on a database of 20,000 messages over 40 conversations with 5,000 unread in one: the counts are right; `EXPLAIN (FORMAT JSON)` of the count statement with `enable_seqscan` off uses `messages_conversation_main_idx` with the row comparison as an index condition and holds no `Sort` node, `firstUnreadId` included; the statements counted on the connection are equal for 3 and for 500 conversations; the 5,000-message count is read with a bounded number of buffers: the test asserts that the buffers read for a conversation with 5,000 unread are lower than for the whole table (`EXPLAIN (ANALYZE, BUFFERS)`, a ratio, not a time). The cost that remains is stated in concern 11: one heap row for each unread message, because `kind`, `author_id` and `deleted_at` are not in the index; the fixture reads 5,000 rows for the conversation with 5,000 unread.
- R11. Leaving, privacy. The pointer lives in the member row, so a leave, a removal and the last-member archive of TOKI-029 (which delete the row) remove it with no code of their own (D-133, TOKI-029 hand-off); the person who joins again has a new row with a null pointer and version 0. - R12. The shared shapes. `packages/shared/src/unread/` (exported from the package index) holds: `UnreadEntrySchema`, a strict object `{ count: integer >= 0, mention: boolean, firstUnreadId: uuid | null, pointerVersion: integer >= 0 }` and its type `UnreadEntry` (the shape of the bootstrap and of `GET /unread`, where `asOf` is the answer's `eventNumber`); `UnreadRecordSchema`, the same object with `asOf: integer >= 0` and its type `UnreadRecord` (the shape of the answer of R3 and of the notice of R9, which have no answer-level number); `UnreadSnapshotSchema` `{ eventNumber, unread: entry by conversation id }` (R7); `ReadRequestSchema` `{ messageId }` and `ReadResponseSchema` `{ unread: UnreadRecord }` (R3); `ReadChangedSchema` (R9, in `src/realtime/read.ts`); `isForward` (R2); `isNewerState(a, b)` (R14); and the constants `READ_ADVANCE_DELAY_MS` 500 and `READ_ADVANCE_MAX_WAIT_MS` 2000 (R15). Check: schema tests accept a valid entry and record and refuse a count of -1, a non-integer, a missing key, an added key (an `asOf` in an entry too) and a `firstUnreadId` that is not a uuid or null; a type test imports each name from `@toki/shared`.
- R13. The tracker. `createUnreadTracker(options)` of `packages/client-core/src/unread/`, exported from the package index with its types. `options`: `conversations` (the store of TOKI-032, with the additions of R20), `sync` (the engine of TOKI-040: `getMessages`, `registerEventHandler`, `registerLiveHandler`, `subscribeEvents`), `api` (the two calls of R17), `windowUse` (the port of R21), `timers` (`Timers`, TOKI-032), `getUserId` and `isMentioned` (`isMentioned(message, userId)` of TOKI-050 R19). The tracker also has `attachConnection(connection)` (R17, R19), which is not an option because the connection is made in a file that imports the one that makes the tracker. It keeps, for each conversation, `base` (an `UnreadRecord`, or none: a zero record with `asOf` 0 and `pointerVersion` 0) and `local` (a map from message id to `{ number, createdAt, counts, mention }`), and the store's slot shows `count` = `base.count` plus the entries of `local` with `counts` true, `mention` = `base.mention` or any entry with `mention` true, `firstUnreadId` = `base.firstUnreadId` or, when that is null, the entry of `local` with `counts` true that is earliest by (`createdAt`, id). Every change goes through one pure function `reduce(state, action)` in `reducer.ts`, with the actions `snapshot` (R14), `record` (R14), `message` (R14), `read` (R14 (e)). It also keeps, for each conversation, a flag `pendingRead` (R14 (e)). It uses no DOM or browser global and no timer of its own (client-core rules, TOKI-032 R25, TOKI-008 R19). - R14. How a number stays right. ## Design
### The pointer and the count
One column on the member row. A person's state for a conversation already lives in `conversation_members` (level, mute, star), a leave deletes the row, and so the pointer is removed with it (D-133) with no code. The pointer names a message and not a time: the message is always there (TOKI-036 R8, a row is never deleted), the key stops a pointer from naming another conversation's message, and the order is read from the message (`created_at`, `id`), so a change of the order rule is one place (R2, R4). Alternatives refused: a time column (copies the order, and two messages with one time need the id too); the event number of the message (`messages` has no such column and the sender does not write one).
The count is computed, never stored: a stored count would have to change with every message, edit and delete of every conversation, and would be wrong after the first missed write. Counting from the pointer costs by what is unread, not by the history (R10). The prototype shows no cap, so the server count has none and the screen decides what to show (TOKI-012 concern 4, concern 11).
Which messages count follows the predicate of the index of TOKI-036 R11: roots, system lines and replies also sent to the channel are in the main list; `kind = 'user'` leaves the system lines out (D-100, D-165); the author test leaves out the person's own messages; `deleted_at is null` leaves out deleted ones (concern 3).

### How the number stays right
Three things can disagree: the count the server computed, the messages that arrived since, and another device's reading. A record carries `asOf`, the event number the server read in the same snapshot as the count (R7: a read-only `REPEATABLE READ` transaction, the same as the bootstrap's; TOKI-036 R16: every message with a number up to it is in the count and none above it). The client keeps the record as `base` and adds one for every counted message event with a higher number (R14). This one rule gives, with no ordering between channels of data: a record that arrives before or after the message events it overlaps; a repeated event; a replay after a reconnect (TOKI-039); and a record from another device. A record whose state, the pair (`asOf`, `pointerVersion`), is older than the held one is ignored (R14). The pair is needed because a pointer move writes no event: the answer of a move and a slower answer of `GET /unread` can have one `asOf`, and only the version tells which of the two is later (concern 14). The same rule orders the bootstrap, a refresh, the answer of a request and a notice.
The cases that cannot be done by adding one (a delete, an edit that removes a mention, a restored channel) ask for every record again (R16, R17).

### The request, the notice and the other device
A move is `PUT /conversations/{id}/read` with the id of the newest message the person saw. It is idempotent and forward-only (R3): the answer is 200 whether or not the pointer moved, so a repeat or a late request from a slow tab is harmless, and the pointer cannot go back. The move takes the member row `FOR NO KEY UPDATE` after the conversation row (`FOR SHARE`, or `FOR NO KEY UPDATE` for a `dm`: the mode TOKI-037 R8 gives each kind), and takes no event lock. The answer is read after the commit in a snapshot of its own, so its count, pointer and `asOf` are one state (R3).
The other devices are told by a live notice (R9), not by an event of the log, as TOKI-051 does for drafts (concern 5): a pointer moves after every message a person reads, and an event would hold the counter row lock of the whole workspace for each (TOKI-036 R16 to R18). Because every record has its `asOf` (above), a notice that arrives early, late or never leaves nothing wrong that stays: a device reads every record again when its connection returns (R17).

### Reading
Reading is decided in the client. The server cannot know that a window is in use or that a list is at the bottom. The tracker joins three facts (R15): the list is at the bottom (`onAtBottomChange`, TOKI-041 R19: the window holds the newest message, `hasNewer` false, within 32 px of the end), the window is in use (visible and focused, R21), and a message to read exists. The count falls at once on the screen and the request follows after a short wait, so a person scrolling or a busy channel sends one request for a burst, not one for each message (R15: 500 ms of quiet and at most 2,000 ms, the numbers of concern 10). A message that arrives while the person is at the bottom of an open, used window is never counted: it is placed by the engine (TOKI-040 R16) and the pointer is moved to it.
At the opening the first unread id is there before the list reports the bottom (R19), so TOKI-054 keeps the New divider on the first unread message, by id, while the pointer moves on.

## Data safety
The pointer is a message id of the person's own conversation: no text, no name. `GET /unread` and the notice hold ids of the person's own conversations and messages only. No log line holds a message id list (R3). A pointer is never shown to another person (R11).

## Open questions from the intent

- A message that commits after a message with a later time: is it counted by a pointer that has moved past it? Answered: the writer of a user message takes the event counter lock before it reads the clock, so a user message that commits later does not get an earlier time. See concern 1.

## Areas of concern
1. A message can commit after a message with a later `created_at`. This is the question of TOKI-036 concern 12. Without a rule, a pointer that has moved to the later message puts the earlier one before it, so the earlier one is never counted for any device that reads the table afterwards, and the count of the client, which follows the event number (R14 (c)), differs from the count of the server, which follows the position (R4). Decided: the writer of a user message takes the event counter lock before it reads the clock, so the time of a user message that commits later is not earlier than the time of one that has committed, while the server clock does not go back. Decided by Thanh Truong (product owner) on 2026-11-27. Nothing changes in this ticket: the position stays (`created_at`, `id`), R2 to R4 stand as written and `messages` gets no column. The rule is built by the writer of messages (TOKI-036 and TOKI-037), and this ticket relies on it and does not test it. A system line does not take the lock; it is never counted (R4), so the time it is given changes no count. Two messages that get the same `created_at` are ordered by their ids, whatever order they commit in; whether the clock read under the lock must also be later than the one before it belongs to the spec of TOKI-036. Alternative refused: keep the gap and let the pointer name the event number of the message, which needs a column on `messages` and a change of R2 to R4. Owner: Thanh Truong (product owner).
2. Whether the history that was there before a person joined a channel is unread. Not decided. D-029 and FR-20 give the full history to a joiner and no rule for its count (D-116 says only that a person cannot read a channel they have not joined); D-100 says only that the line "Minh joined" raises none. Counting every old message would show a new member a count of thousands. Proposal, not decided: a person's start point is the time they joined (`conversation_members.created_at`), so only messages after it count, and a rejoin starts again at its own time; R4 and R16 are built on it, and a different answer changes the start point of R4 only (for example, the newest message at the time of the join, written by the join code of TOKI-029, which this work would then have to edit). Owner: Thanh Truong (product owner).
3. Whether a deleted message leaves the count, and an edit that removes the person's mention leaves the @ mark. Not decided for a message with no mention. F13 says that when the message is deleted or the mention is edited out, the Activity item is removed and "the badges fall back", which covers the mention case; the log says nothing for a plain message. Proposal, not decided: a deleted message is not counted and a message that no longer mentions the person gives no @ mark, for every message (R4, R5, R16); the other reading is that a deleted message stays in the count until the pointer passes it, which would leave a count that opens to nothing (D-049: a message deleted by its author with no replies is not drawn). Owner: Thanh Truong (product owner).
4. Whether a window that is visible and focused but not used for a long time still reads a conversation. Not decided. D-052 says "the window is in use" and does not say how it is known; the platform gives visibility and focus (R21), and presence gives "Away after 5 minutes without activity" to other people (TOKI-055), which is a different thing and gives this ticket no source. Proposal, not decided: visibility and focus only, with no idle time, so that a person who walks away from a focused window at the bottom of a conversation reads what arrives; the stricter reading adds a last-input time to `WindowUse` and changes R21 only. Owner: Thanh Truong (product owner).
5. How the other devices learn of a move: a live notice and not an event of the log. Decided in this spec. Reason: every event takes the counter row lock of the workspace until its commit (TOKI-036 R16 to R18); a pointer moves after every message a person reads, so each message in a busy channel would queue one write for each reader behind every send, and the log would fill with them. The same reason and the same route as TOKI-051 concern 4 for drafts. The cost, a lost notice, is repaired because every record carries `asOf` and the client reads every record again when its connection returns (R14, R17). Alternative refused: a `user`-scope event with the count, which would replay by itself but adds the lock and the volume, and would still need the `asOf` rule because the count is read before the event is numbered. Owner: Thanh Truong.
6. Where the counts reach the store, which TOKI-031 concern 7 and TOKI-032 concern 7 left to this ticket. Decided in this spec: both ways, for different jobs. The bootstrap answer carries `unread` (R8), so the first paint of the list has counts and a refresh replaces them (R20); the tracker is the one caller of `setUnread` and `clearUnread` and handles every change between two loads (R18). Reason: one source for a load and one for a change, with the `asOf` rule (R14) making them agree. The amendment of TOKI-031 R12, R14 and R20 is made in code and tests and not in the merged text, as TOKI-036 concern 13 did. Owner: Thanh Truong.
7. How the pointer is represented. Decided in this spec: the id of the last message read, on the member row, with a composite key to the message (R1); the position is read from the message (R2). Reasons and the alternatives refused are in Design, "The pointer and the count". Owner: Thanh Truong.
8. Two rules about the bottom of the list. (a) The count: Decided, by D-052 (Confirmed) and TS-034: a conversation is read when it is open, the window is in use and the person is at the bottom of the list, and a message on screen above the bottom does not lower the count (R15). (b) The `@` dot: Not decided. F13 step 5 says "Once the message is on screen the @ dot and count clear", and D-091 accepts the phase-1 journeys as the baseline (with the four choices of D-156 to D-159); no decision says that this step changed. Proposal, not decided: apply D-052 to the dot too, so a mention message that is on screen but above the bottom keeps its dot until the person reaches the bottom, and the dot clears with the count (R15). That departs from the wording of a journey step, and a person can see the difference. The other reading, that the dot clears when the mention message is on screen, needs the list to report which messages are visible (TOKI-041 reports only the bottom) and changes R15 and R19. A consequence for the owner: a mention inside a thread reply gives the dot and no count (F13), and the pointer moves only through the main list, so that dot clears only when a later main-list message is read; opening the Activity item at that reply or reading the thread panel (TOKI-065) does not clear it here. Whether opening that reply should clear it is also open. Owner: Thanh Truong (product owner).
9. Where the window-in-use rule lives. Decided in this spec: a small port in `client-core` (`WindowUse`) with its web adapter in `apps/web`, and not a new member of `Platform` of TOKI-018. Reason: `Platform` holds what the shared interface asks of a device (storage, files, sound, notifications, tabs); the phone app will give its own adapter of the same port. TOKI-055 keeps its own activity source and exports none for this ticket (its Scope and Hand-offs), so the two adapters stay separate. Owner: Thanh Truong.
10. The wait before the pointer is sent. Decided in this spec, as a technical choice the Blueprint leaves to the builder: 500 ms of quiet and at most 2,000 ms from the first target of a burst (R12, R15). Reason: the count must fall at once on the screen (done locally) while the server need not hear every message of a busy channel, and 2,000 ms bounds how long another device shows a stale count; a pending target is sent at once when the person leaves. TOKI-089 may tune the numbers. Owner: Thanh Truong.
11. How many unread messages the server counts. Decided: all of them, with no server cap. The display cap is the screen's: the merged TOKI-012 concern 4 says no cap and no hiding of zero in the component, so what a badge shows is TOKI-054's, and the log sets no cap. The cost is accepted and stated: the query is bounded by the unread messages, not by the history, but not by anything else, so a person who was away from busy channels pays one heap row for each unread message (the filters `kind`, `author_id` and `deleted_at` are not in the index) on every bootstrap, every reconnect and every delete event of R16; the fixture of R10 reads 5,000 rows for its conversation with 5,000 unread. `firstUnreadId` is read by a `lateral` subquery with `limit 1`, which costs one index probe for each conversation (R4). A server bound (count up to a limit plus one) is the alternative, and needs a product answer on what the badge shows at the limit. Owner: Thanh Truong.
12. Who owns the first unread message. Decided: this work gives `firstUnreadId` (R4, R19); TOKI-054 draws the New divider, keeps it while the conversation is open and drops it at the next opening (TOKI-041 R8, D-052). Owner: Thanh Truong.
13. A conversation restored after an archive, and a new direct message. Decided in this spec: a restored channel and a joiner (`member.joined`, `members.added`) read their record from the server (R16), because the pointer survives an archive and a joiner's start is the server's; a direct message that appears has no record and is counted from the events that follow it (`conversation.appeared` and `message.created` have consecutive numbers, TOKI-036 "The event contract"), and a created channel has no message yet. Owner: Thanh Truong.
14. How two answers about one conversation are ordered. Decided in this spec: by the pair (`asOf`, `pointerVersion`), `asOf` first (R14), with `pointer_version` a counter on the member row that each move of the pointer raises by one (R1, R2). Reason: a move writes no event, so a slow `GET /unread` and the answer of a move can have one `asOf`, and a rule on `asOf` alone, or one that compares counts, cannot tell the later one; the version can, because moves of one row are serialized by the row lock. A conversation that no entry names counts as zero at the highest version of its `asOf`, so a slower answer at that number never raises it. Alternative refused: ordering by the count at one `asOf` (it holds only while a later pointer can never have a larger count, and gives no order for a record against an absent entry). The cost is one `bigint` column and one small key in each entry (R8 measures it). Owner: Thanh Truong.
