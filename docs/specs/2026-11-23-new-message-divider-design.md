# New divider, badges and filters design

Date: 2026-11-23 · Status: draft for review (concerns 2 to 6 are open for the product owner)
Intent: docs/intents/new-message-divider.md (Thanh Truong)
Ticket: TOKI-054

## Goal
After the read pointer (TOKI-053) the client knows, for every conversation, how many messages are unread, whether one mentions the person, and which message is the first unread. Nothing yet turns that into what a person sees as a whole. This work does it: the New divider and the opening at the first unread message, the @ mark of a row with the rule for a muted conversation, the Home number in the navigation, the unread count in the browser tab title, and the Unread and Mentions filters, which the device still keeps switched off.
The hard rule is that the divider is anchored by message id at the opening and never moves, whatever arrives later. The conversation page reads the first unread message once, in the first render that has the store ready, and keeps it for as long as the conversation is open (R7, R8). The second rule is that every number comes from one set of pure functions in `client-core` (technical design: what to show lives there), so the web interface and a phone interface cannot disagree (R1).

## Design
### Where the decisions live
Every number and every rule is a pure function in `packages/client-core/src/badges/`, called by the store (`getList`, `getBadges`) so that every reader of the store, the sidebar, the shell and the title, sees the same value. `apps/web` holds only wiring: one hook for the divider, one for the title, and one prop of the shell. That is the technical design's rule that "what to show" lives in `client-core`.

### The data it reads
- The slot of TOKI-032 R20, filled by the tracker of TOKI-053 (`{ count, mention, firstUnreadId }`). `count` is the main-list messages of other people after the pointer, with no system line and no thread reply (TOKI-053 R4); `mention` is the @ mark, which a mention inside a thread reply also raises (F13).
- `isMuted` and the level of the conversation entry (TOKI-031 R8).
- `mentionsInMuted`, set from outside (R2).

### The divider
The first unread message comes from the tracker, which empties it when the list has reported the bottom. The page must therefore read it at the mount, before the list has reported anything, and keep it. The hook keeps it in state; the page gives it to the list as an `openAt` of kind `new`. The list draws the divider before that message and opens there. Because the list receives an id and not an index, a message loaded above it, a day divider or a hidden message cannot move it.

```
tracker.getUnread(id).firstUnreadId --once--> useNewDivider --> openAt { messageId, kind: "new" }
                                                                   |
                       ConversationPage (messageList.openAt) -------+--> MessageList: New row before message, open there
store.getList / getBadges --> ConversationListPane rows ; AppShellRoute badge ; useTabTitle -> document.title
```

### The tab title
D-122 gives the form `(3) Toki` for mentions and direct messages and a dot for anything else. A mention is known as a mark and not as a number of messages, so the count of R1 (c) is a proposal: a direct message adds its unread messages and a channel with a mark adds one. The dot and the rule for when it shows are proposals too (concern 2, concern 3). The title never shows a number that no row shows, because every term is a row of the list.

### Layout
```
packages/client-core/src/badges/{shown-mention.ts,home-badge.ts,title-badge.ts,index.ts} + tests
packages/client-core/src/conversations/{store.ts,selectors.ts,types.ts}   (R2, R4, edited)
apps/web/src/conversation/useNewDivider.ts + test
apps/web/src/conversation/ConversationPage.tsx                             (R8, edited)
apps/web/src/shell/useTabTitle.ts + test
apps/web/src/routes/app-layout.tsx                                         (R4, R6, edited)
apps/web/src/conversation-list/device-memory.ts                            (R3, edited)
packages/i18n/src/messages/{en,vi}/nav.ts                                  (R11)
e2e/new-message-divider.spec.ts
```

## Areas of concern
1. The rule for a muted conversation and the switch. The rule is Decided by D-088 (Confirmed, "a personal switch in Preferences, on by default"), D-103 and F08: no count, no bold, out of the Home badge, and the @ mark only while the switch is on. Where the value comes from is Decided in this spec: the store holds `mentionsInMuted`, default true, and a setter; the preference's own ticket (TOKI-102 server, TOKI-078 screen) calls it. Reason: the saved preference does not exist yet, and the default of D-088 is the value until it does. Owner: Thanh Truong.
2. What number the tab title shows. Not decided. D-122 says `(3) Toki` "counts mentions and DMs" and does not say whether it counts messages, conversations or mentions, nor whether a muted conversation counts. The data holds a mention as a mark and not as a number. Proposal, not a decision: the unread messages of unmuted direct messages and groups, plus one for each channel that shows an @ mark (R1 (c)); a muted direct message adds nothing; a muted channel adds one only while the switch for mentions in muted conversations is on. The other readings (the number of conversations, or the sum of all counts of Home) change `titleBadge` only. Owner: Thanh Truong (product owner).
3. The dot of the tab title. Not decided. D-122 says "a dot for anything else" and gives neither the character nor what "anything else" is. Proposal, not a decision: the character `•` before the name, shown when the number is 0 and an unmuted conversation has unread messages; Activity and Later items are not looked at here, because their lists belong to other tickets. A page that also shows the Activity badge would need a source from TOKI-065. Owner: Thanh Truong (product owner).
4. The largest number a badge shows. Not decided. The prototype draws the number as it is, the component has no cap (TOKI-012 concern 4) and TOKI-053 concern 11 leaves the cap to this work; no decision sets one. Proposal, not a decision: no cap, as the prototype does; a cap such as `99+` would be one change in the wiring (R4) and in the row label of TOKI-033. Owner: Thanh Truong (product owner).
5. Whether the Mentions filter keeps a muted conversation whose @ mark is hidden by the switch. Not decided. D-074 says a count on a chip equals the rows shown, which argues for keeping only rows that draw the mark; no decision says it for this case. Proposal, not a decision: the filter keeps the rows that draw the mark (R3 (b)). The other reading, that the filter keeps every row with a mention regardless of the switch, changes one line of the store. The Unread filter keeps a muted conversation with a count, decided in TOKI-032 concern 7. Owner: Thanh Truong (product owner).
6. Which wins when a conversation opens with unread messages and a target message. Not decided. D-052 says opening a conversation with unread messages scrolls to the divider; the journeys of Activity, Pins and Search say the conversation opens at that message. The list takes one `openAt`. Proposal, not a decision: the target wins and no divider is drawn in that mount (R10 (a)); the count stays until the person reaches the bottom. The other reading draws the divider and puts the target in view, which needs the list to take both. Owner: Thanh Truong (product owner).
7. Who turns the Unread and Mentions filters on. Decided in this spec: this ticket, by setting `readStateAvailable` to true (R3 (c)). Reason: TOKI-033 R18 says TOKI-053 sets it, and TOKI-053's scope leaves the filters to this ticket and lists no such change, so without an owner the filters would stay empty. Owner: Thanh Truong.
8. How the divider outlives the opening. Decided in this spec: the list keeps the id it is given for its mount, and the page may drop its `openAt` at `onOpened` as TOKI-041 R4 has it (R9). Reason: D-052 says the divider "stays while viewing" and TOKI-041 R4 needs the drop so that a return to the Messages tab opens at the end; the two meet in the list, which is the only place that holds a mounted state. If the built list does not keep the id, the change is made in its file by this ticket. Owner: Thanh Truong.
9. Where the first unread message is read. Decided in this spec: once, in the first render with a ready store, and kept by the hook (R7). Reason: TOKI-053 R19 empties the value after the list reports the bottom, so a later read would lose the divider, and a read at every render would move it. Owner: Thanh Truong.
10. Pause and Focus time. Decided by D-072: "Badges still update", so the Home number and the tab title follow the counts during both, and the hook of R5 reads neither. Owner: Thanh Truong.
