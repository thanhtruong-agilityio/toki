# Typing indicator design

Date: 2026-11-20 · Status: draft for review (concerns 1, 2 and 3 are open for the product owner)
Intent: docs/intents/typing-indicator.md (Thanh Truong)
Ticket: TOKI-044

## Goal
A person who has a conversation open must see that someone is writing in it, as the prototype does with the line "Lan is typing…" under the message list. This work adds the signal: the frame the browser sends while a person types, the relay that passes it to the other members of the conversation and keeps nothing, the limit that stops a long text from flooding the server, the store that shows who is typing now and forgets them by itself, and the line that draws it.

## Scope
- In:
  - The client frame `typing` and the live frame of the same kind, with their schemas and three numbers, in `packages/shared` (R1, R2).
  - The relay on the server: who may send, who hears, the limit, nothing stored (R3 to R7).
  - In `packages/client-core`: the sender that limits the signal (R8, R9) and the store of who is typing, with the expiry, the clearing by message and the own-typing rule (R10 to R14).
  - The typing line in `packages/ui-web` and its texts in `@toki/i18n` (R15, R16).
  - The creation of the store and the sender in `apps/web/src/client.ts`, and the one call that resets the store when the person changes (R17).
- Out (not now):
  - The socket, its frames in and out, the retry and the offline banner: TOKI-039. Its wiring file `apps/web/src/realtime.ts` calls `typing.receive` for each live frame and `typingSender.setSend` with `connection.send` (R17).
  - Applying events to the cache: TOKI-040. It calls `typing.clear` when it applies a message of another person (R12).
  - Where the line sits and the scroll of the list: TOKI-041. It places `TypingLine` under the message list (R15) and reads `getTypingLabel` (R16).
  - The composer: TOKI-043. It calls `typingSender.notify` and `typingSender.reset` as R9 says. No composer code is written here.
  - The gateway, its frame limits, `onClientFrame`, `publishLive` and `canListen`: TOKI-038. This work only uses them.
  - Presence (Active, Away): TOKI-055.
  - The wording and the name for two or more people typing (concern 2), the name that is shown (concern 1) and the thread reply box (concern 3): not decided.

## Requirements
Shared definitions
- R1. `packages/shared/src/realtime/typing.ts` exports the constants `TYPING_EXPIRY_MS` (5,000), `TYPING_SEND_INTERVAL_MS` (3,000) and `TYPING_RELAY_MIN_INTERVAL_MS` (2,000), the schema `typingClientFrameSchema` of the client frame `{ "type": "typing", "conversationId" }` and the type made from it. `conversationId` is a conversation id as `packages/shared` defines it (a UUID). The frame has no other field: it holds no text of the message and no name. Check: the schema accepts the frame above, and rejects a frame with a missing or non-UUID `conversationId`, with a number for the id, and with an extra field; the three constants have the values written here; a test builds a frame of the longest valid shape and finds it under 100 bytes (the gateway accepts 4,096, TOKI-038 R25).
- R2. The same file exports `typingLiveFrameSchema`, the schema of the `live` frame of TOKI-038 R12 with `kind` equal to `"typing"` and `data` equal to `{ "conversationId", "userId" }` (both ids). It has no event number. `packages/shared/src/realtime/index.ts` exports both schemas, the type and the constants. Check: the schema accepts that frame and rejects a frame with a `number`, a missing `userId`, or another `kind`; the export-list test of `packages/shared` lists the new names.

The relay on the server
- R3. `apps/server/src/modules/realtime/typing.ts` exports `registerTyping({ onClientFrame, publishLive, clock, maxPaceKeys })`, which calls `onClientFrame("typing", handler)` of TOKI-038 R27; `maxPaceKeys` is the bound of R6 and defaults to 1,000. `app.ts` calls it once, right after it registers the gateway, and only when the gateway exists (TOKI-038 R29 registers it when `db` and `listen` are given), with the two functions of the `realtime` module and the clock of TOKI-008 R19; the file imports no other module (TOKI-038 R29). Check: an app built with the gateway answers a `typing` frame (R5); an app built without `listen` has no registration and starts without error; a search of `typing.ts` for an import of another module finds none; a spy on `onClientFrame` sees one registration of the type `typing`.
- R4. The handler is called as `handler(accountId, frame, canListen)`: the account id of the connection that sent the frame, the frame as the client sent it, and `canListen`, the check of TOKI-038 R25 as R27 there hands it over. TOKI-038 R27 words it as "the connection's account id and the frame, and `canListen(connection, conversationId)`" and does not fix the parameter list; this is the form this spec uses (TOKI-038 is merged with R27 as quoted, so no change of it is asked). If TOKI-038 passes the connection and not a bound function, only the call `canListen(conversationId)` here changes. The handler checks the frame, then who sent it. A frame that does not pass `typingClientFrameSchema` is ignored: it is not relayed, it is not answered and the connection stays open (a frame that is not a JSON object is already refused by TOKI-038 R25). A frame whose `conversationId` the connection does not listen to (`canListen` of TOKI-038 R27 is false: a conversation the person is not a member of, one that does not exist, a DM that the person has not yet been shown) is dropped with no answer and no difference from a missing conversation, so the signal never tells a person that a conversation exists. Check: one case for each of the four frames (invalid shape, a private channel the person is not in, a public channel not joined, a made-up id); each leaves every other connection with no frame and the sender's connection open and unanswered. The check is membership only, so a Guest who is a member of an invited channel sends and hears the signal like a Member or an Admin; the permission suite of D-090 expects that.
- R5. A valid frame from a member is relayed with `publishLive({ conversationId }, "typing", { conversationId, userId })`, where `userId` is the account id of the connection that sent it, never a value read from the frame. The frame reaches every open connection of every member of that conversation, the sender's own connections included (R13 says where the own typing is removed), and no other connection. Nothing is written: no event number, no log row, no table. Check: with Lan, Minh and Sam in a channel, an Admin who is not in it, and a person in another conversation, all connected, and Lan in two tabs, a `typing` frame from Lan reaches Minh, Sam and both tabs of Lan, each with `data.userId` of Lan, and does not reach the Admin or the other person; the recorded frames of the two outsiders hold no id of the channel; the count of rows of the event log is the same before and after; a frame whose body names another user id in an extra field is rejected by R4.
- R6. A frame from the same account for the same conversation that arrives less than `TYPING_RELAY_MIN_INTERVAL_MS` after the last frame that was relayed for that pair is dropped, with no answer and no close. The time is read from the injected clock. The record of the last relay is a map keyed by account id and conversation id; when it holds more than `maxPaceKeys` keys (R3, 1,000 by default), the keys older than the interval are removed at the next relay, so it does not grow without limit. A person typing in two conversations has two keys. Check, with the `TestClock`: a frame at 0 s is relayed; a second at 1.9 s is not; a third at 2.0 s is; a frame for another conversation at 0.1 s is relayed; a frame of another account at 0.1 s is relayed; with `maxPaceKeys` set to 3 in the test, after 4 distinct keys and 2 s, the next relay leaves the map smaller than 4 (the default of 1,000 is read from the constant, not tested with 1,001 accounts).
- R7. The relay logs nothing about a typing frame and keeps no copy: no log line holds a conversation id, user id or frame of kind `typing` at the default log level. Check: a test with the captured log of the app sends ten frames and finds no line that holds the conversation id.

The sender in the browser
- R8. `createTypingSender({ clock })` in `packages/client-core` returns `{ notify(conversationId), reset(conversationId), setSend(fn | null) }`. `setSend` sets the function that puts a frame on the socket; `fn(frame)` returns `true` when the frame was put on an open socket and `false` otherwise. `notify(conversationId)` builds the frame of R1 and calls the function when no frame for that conversation was sent in the last `TYPING_SEND_INTERVAL_MS` (read from the clock), and remembers the time only when the function returned `true`. With no function set, or when it returns `false`, nothing is queued and nothing is remembered, so the next `notify` tries again. Check, with the `TestClock`: ten `notify` calls in one second send one frame; the next frame goes at 3.0 s and not at 2.9 s; during 60 seconds of a call every 100 ms (the last call at 59.9 s) at most 20 frames are sent (at 0, 3, ... 57 s); a function that returns `false` makes every call try again and sends no frame later by itself; with no function set, `notify` does nothing and throws nothing.
- R9. The contract for the composer (TOKI-043, which builds the call): `notify(conversationId)` is called when a change of the field leaves it with text (a typed character, a paste), not when the field is emptied, not when a draft is restored, and, as the interim default that concern 3 may change, not for the thread reply box. `reset(conversationId)` is called when the message is sent and when the field is emptied, so the first character of the next message sends a frame at once. `setSend` is called by the wiring file of TOKI-039 (R17), with `connection.send` when the connection starts and with `null` when it stops (status `idle` or `stopped`); `connection.send` returns false until the `ready` frame has come, so `notify` sends nothing before that (R8). A signal that cannot be sent is lost on purpose: phase 1 has no offline mode (D-079) and a signal that arrives late says something false. Check: `reset` after a sent frame lets the next `notify` send at once; `reset` of one conversation does not change another; the composer's tests (TOKI-043) check the calls of this contract.

The store of who is typing
- R10. `createTypingStore({ clock, timers, getOwnUserId })` in `packages/client-core` returns `{ receive(frame), clear(conversationId, userId), reset(), getTypers(conversationId), subscribe(listener), getState() }`. `timers` is the `Timers` type of `createApiClient` (`after(ms, fn)` returns a function that cancels) and `getOwnUserId()` returns the signed-in person's id or `null`. `receive(frame)` takes any value: it ignores a value that does not pass `typingLiveFrameSchema`. For a valid frame it records the entry `{ userId, expiresAt }` for that conversation, with `expiresAt` equal to `clock.now() + TYPING_EXPIRY_MS`, and schedules a check with `timers.after(TYPING_EXPIRY_MS)`. `getTypers(conversationId)` returns the user ids whose `expiresAt` is after `clock.now()`, in the order of the first signal of each, and `[]` for an unknown conversation. Check: a valid frame gives `["u1"]`; a frame with an invalid shape, with an unknown kind and with a number gives no change and no listener call; two people give two ids in the order of their first signals.
- R11. Expiry. An entry is removed 5 seconds after its last signal: a signal for a person who is already listed moves `expiresAt` forward and keeps the person's place in the order; the check of an earlier signal does not remove an entry that a later signal has renewed; when an entry is removed, every listener is called once. A check also removes every entry that is already due. Check, with the `TestClock` and a manual `Timers` that runs its callbacks when the test advances the clock: after a frame at 0 s the person is listed at 4.999 s and gone at 5.0 s with one listener call; a second frame at 3 s keeps the person until 8 s; a conversation with two people where one stops loses only that one; `getTypers` at 5.0 s returns `[]` even when no timer has run (R14 says what that read does to the snapshot).
- R12. Clearing by a message. `clear(conversationId, userId)` removes that person from that conversation at once and calls the listeners once if something was removed; it does nothing for an unknown pair. The sync engine (TOKI-040 R16) calls it, as its optional `typing` option, when it applies a `message.created` of kind `user` from a person other than the signed-in one (concern 4), so the line goes before the message shows, as the prototype does. Check: after `clear`, `getTypers` no longer holds the person and a listener was called once; `clear` for a person who is not listed calls no listener; a signal that arrives after `clear` lists the person again.
- R13. The own typing is never kept. A frame whose `data.userId` equals `getOwnUserId()` is ignored whatever tab sent it, so the signed-in person never sees their own typing, not even from another tab or device. With `getOwnUserId()` equal to `null`, a frame is ignored. Check: a frame with the own id gives no change and no listener call; the same frame from a second store whose own id is another person is kept.
- R14. Snapshots and reset. `getState()` returns an immutable snapshot, the same object while nothing changes (the rule of client-core R12 and R22: `getTypers` returns the same array for the same conversation until the list of that conversation changes). The time filter of R11 is applied on read and keeps the old array when the filtered list equals it: a read that drops nothing returns the same array; a read that drops an entry whose timer has not yet run returns a new array, replaces the held entry and the snapshot of `getState()`, and calls no listener (the pending timer of that entry still calls the listeners once when it runs, and finds nothing to remove). An expired entry is therefore never in `getState()` after any read. `reset()` drops every entry, cancels the pending checks and calls the listeners once; `apps/web` calls it when the person changes (R17), so nothing of the earlier person stays. Check: two calls of `getTypers` with no change between return the same array; a read at a time when nothing has expired returns the same array, and a read after an entry expired with no timer run returns a new array without a listener call; a change in another conversation does not change the array of this one; after `reset` every `getTypers` returns `[]` and a check that was pending does not call a listener.

The line
- R15. `packages/ui-web` exports `TypingLine({ label })`, in the folder `components/TypingLine/` (`TypingLine.tsx`, `TypingLine.css`, `TypingLine.examples.tsx`, `index.ts`, as `components/Chip/` is). It renders nothing when `label` is empty, and otherwise a `div` with the class of the prototype's `.typing`: three dots and the `label`. It has no `role` and no `aria-live`: the prototype has none, and a live region would announce the line each time it appears for a few seconds, which is noise for a screen reader (a technical choice; the line is a courtesy and the message itself is announced where messages are). The look is the prototype's: padding `4px 16px 4px 60px` (left 16px on a narrow screen, as in the prototype's mobile block), muted colour, 12.5px text, a row with a 6px gap, dots of 5px, round, in the muted colour, blinking to 25% opacity over 1.2 s with the second dot delayed 0.2 s and the third 0.4 s; with `prefers-reduced-motion` the dots do not move (the global rule of `base.css` covers it). The values come from the tokens where a token exists. The component holds no text. TOKI-041 places it under the message list of the open conversation, in the main list only. Check: a render test finds the three dots and the label, nothing for an empty label, and no `role` or `aria-live` attribute; the export-list test `packages/ui-web/tests/components/exports.test.ts` lists `TypingLine`; the stylesheet test of `ui-web` finds the padding, the size, the delay values; a search of the component for a quoted English word finds none.
- R16. The text is one key of `@toki/i18n`, `typing.one`, with the parameter `name`: English "{name} is typing…" (the prototype's text, `msgsHtml`; the same in a channel and in a DM, as the prototype does not tell them apart) and a Vietnamese text, a proposal (D-139; the form of address is D-188, open): "{name} đang nhập…" (a neutral form with no pronoun, so the answer to D-188 does not change it). The key is added to both languages: the new file `typing.ts` in each and one import and one entry in `packages/i18n/src/messages/en/index.ts` and `vi/index.ts`, as the comment of `en/index.ts` says, so the `i18n` check passes. `getTypingLabel(typers, getName, t)` in `apps/web` returns the text of `typing.one` for the first typer, in the order of `getTypers`, whose name `getName(userId)` knows, and an empty string for no typer and when no typer has a known name. The name `getName` returns is concern 1 and the text for two or more typers is concern 2. Interim behaviour for two or more typers, a proposal and not a decision: the label names the first typer in the order of first signal and says nothing about the others, so the result is defined and testable; the answer to concern 2 replaces it and the test for it. The product owner decides whether this is acceptable until then. Check: one typer with a known name gives "Lan is typing…" in English; no typer gives `""`; an unknown name gives `""`; two typers (Lan first, Minh second) give "Lan is typing…", and the same two with Lan's name unknown give "Minh is typing…"; the `i18n` check exits 0; the Vietnamese key exists.

This work adds no socket and no file for that wiring.
  The reset. ## Design
### The path of one signal
1. The composer calls `typingSender.notify(id)` when the field has text. At most one frame in 3 seconds per conversation goes out (R8).
2. The gateway reads the frame, and its limits of 4,096 bytes and 50 frames in 10 seconds apply first (TOKI-038 R25). A frame of this kind is under 100 bytes (R1) and a person sends at most 4 in 10 seconds per conversation, so the limit of the gateway is not reached by typing.
3. The handler of R4 to R6 checks the shape, the membership and the pace, then calls `publishLive` with the conversation (R5). The gateway sends one string to every connection of the members (TOKI-038 R18).
4. The wiring file of TOKI-039 hands each `live` frame to `typing.receive` through `subscribeLive` (R10, R17). The store ignores the own id (R13), records the person with an expiry of 5 seconds (R11) and tells its listeners.
5. TOKI-041 reads `getTypers(conversationId)`, builds the label (R16) and draws `TypingLine` (R15). The line clears when 5 seconds pass without a signal, when TOKI-040 calls `clear` for a message of that person (R12), or at `reset`.

There is no "stopped typing" frame: the line clears by expiry, as the journey says ("it clears after 5 seconds without typing"). A person who closes the tab, loses the connection or is removed from the conversation stops sending, and the line goes by itself. Nothing on the server needs to notice it.

### Who hears
The audience is the map of TOKI-038 and its reverse index from a conversation to its connections (R8, R9, R15, R18): the members of the conversation at the moment of the frame, and only a connection that has the conversation in its person's map. A person who is removed from a channel loses the conversation from their map before the next frame, so they hear nothing after it. An archived channel keeps its members in the map, but its composer is replaced by "This channel has been archived" (F10), so the composer sends no signal there.

### What exists on main and what this work extends
- On `main` today: `@toki/shared` has the clock (`Clock`, `createTestClock`); `@toki/client-core` has `createApiClient`, `Timers` and the conversation store with `getUser()` and `getPerson(id)` (client-core R23); `apps/web/src/client.ts` holds the one client and the one store. The wiring file `apps/web/src/realtime.ts`, `connection.subscribeLive` and `connection.send` are defined by the spec of TOKI-039 as revised in its open pull request (PR 210); they do not exist yet either. The `realtime` module, `packages/shared/src/realtime/` and the socket do not exist yet: they are built by TOKI-036 and TOKI-038 (the spec of TOKI-038, merged to `main`, defines `publishLive`, `onClientFrame` and `canListen` in its R27 and the live frame with no number in its R12). This work uses those names as that spec gives them; if they change there, R3 to R5 change.
- The typing store is separate from the conversation store, because the conversation store holds server data and has no clock (client-core R24), while this state is short-lived and is made of time.

## Data safety
- The signal holds two ids and no text: the sender sends a conversation id, the server adds the account id of the connection, the receivers get both. It is not stored, not numbered and not logged (R5, R7).
- A person learns that someone types only in a conversation they are a member of (R4, R5), whatever their role.

## How each constraint in the intent is met
| Constraint | Met by |
| :---- | :---- |

## Open questions from the intent
- Who sees the signal, and how often is it sent? Answered: the members of the conversation only (R4, R5), one frame in 3 seconds per conversation (R8), at most one relayed in 2 seconds (R6); the numbers are concern 5.
- What does the line say when two or more people type at the same time, and which name does it show? Not answered. Carried forward as concern 1 (the name) and concern 2 (the text).
- Does a thread reply box send the signal? Not answered. Carried forward as concern 3.
- Who clears the line when the typing person's message arrives, and who connects the socket to the store? Answered: the store clears at expiry and `clear` (R12), which TOKI-040 calls; the wiring file of TOKI-039 calls `receive` and `setSend` (R9, R17); concern 4.

## Areas of concern
1. The name in the line. Not decided. The prototype shows the first name ("Lan is typing…", the `first` field of its sample people). The people the client holds (client-core R23) have `displayName` and no first name, and the product has no rule that cuts a Vietnamese full name into a first name (the given name is the last word of a name such as "Nguyễn Văn Lan"). Proposal, not a decision: show the `displayName` as it is. Question for the product owner: full name, or a first name that the person sets. Owner: Thanh Truong (product owner).
2. Two or more people typing at once. Not decided. The prototype has one typing person per conversation (`S.typing[cid]` holds one id), so it shows no text for two. Proposal, not a decision: "{a} and {b} are typing…" for two and "Several people are typing…" for three or more, as plural forms of `@toki/i18n`. Question for the product owner: what the line says, and how many names it shows. R16 builds only the case of one person until this is answered. Owner: Thanh Truong (product owner).
3. The thread reply box. Not decided. The prototype draws the line in the main list only (`msgsHtml`) and nowhere in the thread panel; whether a person who writes a reply in a thread is shown as typing, and where, is not in the log or in the journeys. As an interim default, not a decision, this work sends no signal from a thread box (R9) and the frame has no field for a thread; the answer may change R9 without a change of TOKI-043. Question for the product owner: whether typing in a thread is shown at all, and under the thread or in the channel. Owner: Thanh Truong (product owner).
4. The line must clear when the person's message arrives, not wait 5 seconds. Decided in this spec (a technical choice): the prototype clears the typing person before it adds the message, and a line that stays under the message it announces would look wrong; the store offers `clear` (R12) and the sync engine of TOKI-040, which applies the message, calls it. Reason: the store does not read events, so only the code that applies them knows that a message was created. Owner: Thanh Truong.
5. The numbers 3 seconds (send), 2 seconds (relay) and the 1,000 keys of the pace map. Decided in this spec (technical choices; only the 5 seconds is in the Blueprint, F11): a send interval below the expiry keeps the line steady while a person types, with 2 seconds of margin for one lost or late frame; the relay minimum is below the send interval so network jitter does not drop a good frame; both are constants of `packages/shared` and change without a design change. Owner: Thanh Truong.
6. The sender's own tabs receive their own signal. Decided in this spec (a technical choice): the relay does not leave out the sender, because `publishLive` of TOKI-038 has no way to leave a person out, and the client removes the own id (R13), which also covers a second tab or device. The cost is one small frame per tab. The alternative, an option to leave out a person in `publishLive`, would change TOKI-038 R27. Owner: Thanh Truong.
7. A signal is not sent when the socket is not open. Decided in this spec: no queue and no retry (R8, R9), as phase 1 has no offline mode (D-079) and a delayed signal is false. Owner: Thanh Truong.
