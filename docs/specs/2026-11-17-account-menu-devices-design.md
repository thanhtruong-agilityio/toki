# Account menu, Sign out and signed-in devices (screens) design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/account-menu-devices.md (Thanh Truong)
Ticket: TOKI-099

## Goal
The builder (Thanh and Claude) needs the screens that let a person leave Toki and see where they are signed in. The prototype has no sign-out and no list of devices (D-158); its account card opens a menu of Set status, Pause notifications, Focus time and Preferences (line 2129). The server calls exist (TOKI-022, TOKI-026) and the shell already draws the account card as a button that can open a menu (TOKI-015, "Contract for TOKI-014 and TOKI-099"). Nothing uses them.
After this change the account card shows the signed-in person and opens a Menu with a Preferences entry and a Sign out entry, and with the entries of Set status, Pause and Focus time as those tickets register them. Sign out ends the session on this device, shows the sign-in page and tells the other tabs of the browser to leave at once. A page at `/prefs` holds the section "Signed-in devices": one row per device with its kind, browser and last use, "This device" on the one in use, a Sign out beside each other device and "Sign out all other devices", each after a confirmation that names its target.

Sign out
- R7. `useSignOut()` (`apps/web/src/account/sign-out.ts`) returns `signOut`, a function that returns a promise that never rejects and resolves `"done"`, `"failed"`, `"blocked"` or `"busy"`. The steps, in this order, and nothing else: (1) while a sign-out is running a second call returns `"busy"` and does nothing (D-111); (2) `ensureOnline()` of TOKI-093 R17: when it returns `false` the call returns `"blocked"`, the helper has shown its explanation, and nothing else happens (D-079); (3) the tasks of R8 run; (4) the client call `signOut` of R13 is made; (5) when it succeeds the signal of R10 is sent, then `markSignedOut()` of TOKI-023 R39 is called, and the call returns `"done"`; (6) when the call fails (kind `network`, `timeout`, or any `http` error) the session state does not change, no signal is sent, one plain toast shows `t("common.error.actionFailed")` and the call returns `"failed"`, so the person is still signed in and can press again. Tasks run while the session is still valid, so they can call the server. Nothing is registered by this ticket. Check: tests with three fake tasks (one slow, one that throws, one fast) and fake timers: the call is made after the slow one settles; with a task that never settles it is made at 10 000 ms and not before; the throwing task changes nothing; a removed task is not run.

### The order of Sign out and why
Tasks first, then the call, then the signal, then the state. The tasks (drafts, push registration) need a session that is still valid, so they run before the call. The call comes before the state change because a failed call must leave the person signed in (R7 (6)): a sign-out that shows `/login` while the server session lives on would be a false success on a shared computer. The signal is sent after the call succeeded, so the other tabs never leave on a sign-out that failed. The state is set last, so this tab changes only when everything has been done.

### The signal between tabs
One `BroadcastChannel`, no storage key, no polling. A received message only asks the tab to go to `/login`; a forged message from another page of the same origin can sign a tab out of the interface but cannot read or change anything on the server (the session is not touched by it). Without the channel the other tab learns at its next request, which the server answers 401 (TOKI-022 R28) and TOKI-023 turns into its modal (R24 there); TS-210 accepts "a notice that the session has ended with the content covered". This is why no fallback through `localStorage` events is built (concern 6).

### Reading the list
Read when the section mounts and after each confirmation; no timer and no event. A row can therefore be older than the server (a device that signed itself out); the next read shows it. Rows have no keys other than the session `id`.
