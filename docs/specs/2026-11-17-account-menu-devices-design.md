# Account menu, Sign out and signed-in devices (screens) design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/account-menu-devices.md (Thanh Truong)
Ticket: TOKI-099

## Goal
The builder (Thanh and Claude) needs the screens that let a person leave Toki and see where they are signed in. The prototype has no sign-out and no list of devices (D-158); its account card opens a menu of Set status, Pause notifications, Focus time and Preferences (line 2129). The server calls exist (TOKI-022, TOKI-026) and the shell already draws the account card as a button that can open a menu (TOKI-015, "Contract for TOKI-014 and TOKI-099"). Nothing uses them.
After this change the account card shows the signed-in person and opens a Menu with a Preferences entry and a Sign out entry, and with the entries of Set status, Pause and Focus time as those tickets register them. Sign out ends the session on this device, shows the sign-in page and tells the other tabs of the browser to leave at once. A page at `/prefs` holds the section "Signed-in devices": one row per device with its kind, browser and last use, "This device" on the one in use, a Sign out beside each other device and "Sign out all other devices", each after a confirmation that names its target.

  - The section "Signed-in devices", its confirmations and its states (R14 to R20), and the page at `/prefs` that holds it, the Preferences row of the section list (R21).
  - The `tabs` part of `platform`, which sends and receives the signal between the tabs of one browser (R10; TOKI-018 left it to this ticket).
  - The namespace `account` in both languages and the five `common` keys (R22), the date context of the section (R15), the browser test, the tests (Testing).
- Out (not now), with the owner of each:
  - The More sheet itself, its layout and its closing when a destination is chosen: TOKI-092. This ticket gives it the entries (R4) and the sign-out function (R7); TOKI-092 draws them in its account section.

  - The server side: sign-out of the device in use (TOKI-022 R28, R33), the list and the ending of other sessions (TOKI-026 R1 to R16), ending every session on deactivation (TOKI-024).

The reset of the conversation store for the states other than this ticket's sign-out (`ended`, another person's id): TOKI-033 (its R32); TOKI-097 resets it itself before `markSignedIn` when it replaces a signed-in person (its R33), as this ticket does for Sign out. For Sign out and for the signal of another tab this ticket resets the store itself (R9, concern 14).

Sign out
- R7. `useSignOut()` (`apps/web/src/account/sign-out.ts`) returns `signOut`, a function that returns a promise that never rejects and resolves `"done"`, `"failed"`, `"blocked"` or `"busy"`, and `useSigningOut()` returns whether a sign-out is running. The running flag is one value at module level (read through `useSyncExternalStore`), not a value per hook instance, so the menu, the More sheet and a test that calls the hook twice all see one sign-out. The steps, in this order, and nothing else: (1) while a sign-out is running a second call returns `"busy"` and does nothing (D-111); (2) `ensureOnline()` of TOKI-093 R17: when it returns `false` the call returns `"blocked"`, the helper has shown its explanation, and nothing else happens (D-079); (3) the flag is set and the tasks of R8 run; (4) the client call `signOut` of R13 is made; (5) when it succeeds, in this order: the signal of R10 is sent, `conversations.reset()` of TOKI-032 R11 is called, `markSignedOut()` of TOKI-023 R39 is called, the router replaces the address with `/login` with no `next` (R9), the flag is cleared and the call returns `"done"`; (6) when the call fails (kind `network`, `timeout`, or any `http` error) the flag is cleared, the session state does not change, no signal is sent, one plain toast shows `t("common.error.actionFailed")` and the call returns `"failed"`, so the person is still signed in and can press again. There is no confirmation dialog and no Undo (R11). While the flag is set the person sees it (the rule of the wait): the card's second line reads `t("account.signingOut")` and the card has `aria-busy` (R1), the `signOut` entry is disabled (R4), and a visually hidden element with `role="status"` drawn by `AccountMenu` holds the same text, so a screen reader hears it. Decided in this spec: the wait is stated as two limits, up to 10 000 ms for the tasks (R8) and up to 10 000 ms for the call (TOKI-032 R2, D-126), 20 seconds at most; the indicator is shown for the whole of it, no progress bar or count is drawn, and a second press during it is answered by the disabled entry and returns `"busy"`. The router is read by the hook when it is called and used after the component has unmounted. Check: tests with a fake API client, a fake `ensureOnline`, a recording `markSignedOut`, a recording platform and a recording router for each of the six paths, including the order of calls in (5); a second call during (3) and (4) from the same hook and from a second hook instance (one call is made to the API, the second returns `"busy"`); the card, the entry and the status element during a slow call and after it.
- R8. Before the call, tasks that other tickets ask to run. `registerBeforeSignOut(task)` (same folder) returns a function that removes the task; `task` is `() => void | Promise<void>`. Journey F06 says unsynced drafts are saved to the server and the device's push registration is removed: TOKI-051 and TOKI-074 each register a task for that. The tasks run together, each started once, and the step of R7 (3) ends when all have settled or after 10 000 ms, whichever is first; the 10 000 ms is counted with the `timers` instance of the web app (`timers.after`, TOKI-032 R25), which `apps/web/src/client.ts` exports for it (R13), not with `setTimeout`. A task that throws or rejects, and a task still running at 10 000 ms, never stops the sign-out: step (4) is made all the same (Decided in this spec, concern 7). Tasks run while the session is still valid, so they can call the server. Nothing is registered by this ticket. The client task is a convenience, not the guarantee: the push registration of a device must also be removed on the server for every ended session by the listener that TOKI-074 registers through TOKI-022 R50, which receives the ids of sessions ended by any route (decided in this spec as a request to TOKI-074, concern 7), so a late or failed task cannot leave a signed-out device receiving notifications (AC-132, TS-212, which TOKI-074 carries). Check: tests with three fake tasks (one slow, one that throws, one fast) and a recording fake `timers` of the form TOKI-032 uses (no Vitest fake time, TOKI-008 R19): the call is made after the slow one settles; with a task that never settles it is made when the recorded 10 000 ms timer is fired and not before; the throwing task changes nothing; a removed task is not run.
- R9. After a sign-out the state is `signedOut` and `/login` is shown with no modal and with no `next` in the address (TOKI-023 R39; the guard of TOKI-023 sends a person with no session to `/login?next=<path>`, which would keep the address of the conversation that was open in the URL of a shared computer, so step (5) of R7 replaces the address with `/login` itself). This ticket also empties the conversation store (Decided in this spec, concern 14): `conversations.reset()` is step (5) of R7 and is also made in R12, through one function `endLocalSession()` of `sign-out.ts` that does the reset, then `markSignedOut()`, then the replace to `/login`. The reason is the order: once the state is `signedOut` the guard sends the router to `/login` and `AppShellRoute` is unmounted, so an effect of `AppShellRoute` that reacts to the state change (TOKI-033 R32) is not certain to run, and on a shared computer the next person to sign in must not find the first person's conversations in the store (D-132). TOKI-033 R32 stays as it is and is a second line of defence for the other ways the state leaves `signedIn` (`ended`, another person's id; TOKI-097 R33 already resets before `markSignedIn` for a person who accepts an invitation while another is signed in); `reset()` of an empty store changes nothing (TOKI-032 R11), so the two do not collide. `AppShellRoute` is unmounted, so the account menu and the section of R14 are gone. Pressing the browser's Back button, or opening the address of a conversation that was showing, ends on `/login` (the guard may add `?next=` for an address typed or restored by the browser, concern 15) and shows no channel name and no message (FR-46 AC-130, TS-208; the guard is TOKI-023 R1). Check: a test that uses the real `createConversationStore` of `client-core` filled through a fake API client, the real session store of TOKI-023 and a memory router with the real guard, mounts the real `AppShellRoute`, calls `signOut()` and asserts that the store's state is the first one (`status` `idle`, no conversation, no person) and the address is `/login` with no search; the same test with `AppShellRoute` unmounted before `markSignedOut()` is called gives the same result, so it does not depend on the order of the unmount and of any effect; the same for a `signedOut` message of R12. The browser test of R21 asserts the address after Sign out.
- R10. The signal between tabs. `@toki/platform` gains a fifth member `tabs` of `Platform` (TOKI-018, Scope, Out, leaves "telling other tabs" to this ticket, and its R1 says a later ticket updates the test that counts the members): `tabs.post(message)` sends a `TabMessage` to every other tab and window of the same browser and origin, and `tabs.subscribe(listener)` calls `listener(message)` for each message that another tab sends and returns a function that stops it. `TabMessage` is `{ type: "signedOut" }` and nothing else; it carries no name, no address and no id. The web implementation uses one `BroadcastChannel` named `toki:tabs`, opened when the first listener subscribes or the first message is posted and closed when the last listener has gone and no message is pending; a tab does not receive its own message (the channel's own rule). No method throws: where `BroadcastChannel` does not exist, or it throws, `post` does nothing and `subscribe` returns a function that does nothing (R9 of TOKI-018 gives the same promise to storage). A received message whose shape is not `{ type: "signedOut" }` is dropped before it reaches a listener. The interface file adds no browser global (TOKI-018 R24). Check: unit tests with two `createWebPlatform()` instances in jsdom or in the browser test, a fake `BroadcastChannel` for the absent and the throwing cases, and a malformed message.

- R12. Receiving. While `AppShellRoute` is mounted (the person is signed in in this tab) it subscribes to `tabs` and, for a `signedOut` message, calls `endLocalSession()` of R9 (the store is reset, `markSignedOut()` of TOKI-023 R39 is called, the address becomes `/login` with no `next`), with no request to the server; it unsubscribes when it unmounts. This tab is then at `/login` with no modal, as the tab that signed out is. The other devices of the person are not told: they stay signed in (D-093, FR-46 AC-132, TS-211). A tab that is already at `/login` has no listener. Check: a unit test with a fake `tabs` that emits `signedOut` (the state becomes `signedOut` and the store is empty), a malformed message and a message after unmount (no change); the browser test of R21 with two pages of one browser context, which asserts that the second page shows `/login` within 2 seconds of the press in the first and that it sent no request in that time.

The client calls
- R13. `packages/client-core/src/auth/sessions.ts` exports `createSessionsApi(api)`, which takes the client of TOKI-032 and returns four functions, all through `api.request`, with `credentials` and the 10-second rule of that client and no text of their own: `list()` is `GET /auth/sessions`, whose body is `{ sessions: [...] }` (TOKI-026 R1), and returns the array `{ id, current, deviceKind, browser, lastUsedAt }[]` in the order the server sent (TOKI-026 R1, R4), always with exactly one item whose `current` is true (TOKI-026 R3); `endOne(id)` is `DELETE /auth/sessions/{id}` with `id` put in the path by `encodeURIComponent`; `endOthers()` is `DELETE /auth/sessions`; `signOut()` is `DELETE /auth/session` (TOKI-022 R28). The three `DELETE` calls answer 204 and return nothing; they pass `schema: z.undefined()` (the schema library of `@toki/shared`, TOKI-032 R1), because `request` takes `schema` as a required field (TOKI-032 R2) and TOKI-032 R3 returns `undefined` on a 204 without running it; any other answer is an `ApiError`. Decided in this spec (the reading of an unknown code): `list()` reads `deviceKind` and `browser` as strings and maps a value that is not in the value lists of TOKI-026 R37 (the constants of `packages/shared/src/auth/devices.ts`, TOKI-026 R37) to `unknown`, so the list that `list()` returns always holds codes of TOKI-026 R6. Reason: TOKI-032 R3 fails on a value outside an enum, so reading the list with the shared schema would turn one new browser code, which TOKI-026 R6 can grow and TOKI-032 R3 treats as a compatible change, into "Could not load the devices" with a Retry that fails every time; the other fields are read as TOKI-032 R3 reads any answer (an unknown key is dropped; a missing key, including a missing `sessions`, or a wrong type is `invalid_response`), and the value lists and the codes of the server are not changed. `apps/web/src/client.ts` (TOKI-032 R25, which exports `api` and `conversations` and makes `createTimers()` for `api`) gains two exports: `sessions = createSessionsApi(api)` and `timers`, the one instance that file already passes to `createApiClient`, held in a named constant so that R8 has an instance to use (a change of one line in a file that TOKI-032 owns; when TOKI-032 has already named and exported it, nothing is added). Neither export makes a second client or a second timer. The package keeps its rules: no DOM, no `@toki/i18n`, no clock (TOKI-032 R1, R24). Check: tests with a fake `fetch`: the four methods and paths, the encoded id, a 204, a 404 `not_found`, a 400 `current_session`, a 401 `session_ended` (the hook of TOKI-032 R7 is called), a body `{ sessions: [...] }` read to its array, a body with no `sessions` (an `invalid_response` error), a list answer with an unknown key (dropped), one with a `browser` of `brave` (read as `unknown`, the list still returned), and one with a missing `id` (an `invalid_response` error).

### The order of Sign out and why
Tasks first, then the call, then the signal, then the store and the state. The tasks (drafts, push registration) need a session that is still valid, so they run before the call. The call comes before the state change because a failed call must leave the person signed in (R7 (6)): a sign-out that shows `/login` while the server session lives on would be a false success on a shared computer. The signal is sent after the call succeeded, so the other tabs never leave on a sign-out that failed. The store is emptied just before the state is set, by this ticket and not by an effect of a layout that the state change unmounts (R9), and the state is set last, so this tab changes only when everything has been done. The person sees the wait: up to 20 seconds (R7), shown on the card from the press to the end.

### The signal between tabs
One `BroadcastChannel`, no storage key, no polling. A received message only asks the tab to go to `/login`; a forged message from another page of the same origin can sign a tab out of the interface but cannot read or change anything on the server (the session is not touched by it). Without the channel the other tab learns at its next request, which the server answers 401 (TOKI-022 R28) and TOKI-023 turns into its modal (R24 there); TS-210 accepts "a notice that the session has ended with the content covered". This is why no fallback through `localStorage` events is built (concern 6).

### Reading the list
Read when the section mounts, after each confirmation and when "Sign out all other devices" is pressed; no timer and no event. A re-read keeps the rows on screen and marks the list busy (R14). A row can therefore be older than the server (a device that signed itself out); the next read shows it. Rows have no keys other than the session `id`.
