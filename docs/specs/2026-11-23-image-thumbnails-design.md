# Image thumbnails design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/image-thumbnails.md (Thanh Truong)
Ticket: TOKI-060

## Goal
A file is stored as an opaque download and the browser never draws it (D-095). A picture in a message has to be seen, so the server makes one small image from it, a thumbnail, that the browser may draw. The card in the message and the viewer window of TOKI-062 both draw this one image. This ticket builds that: the background job that makes the thumbnail, the reader of images that does it safely, the columns that record the result, the route that serves it, and the event that tells every open client that it is ready.
Two rules are hard. The server decodes bytes that a person chose, so the decoder runs only in the worker process, with a limit on the size of the file, on the number of pixels and on the time, and an image that cannot be read ends in a state that says so, never in a placeholder that waits for ever (R4, R5, R9). The thumbnail is served only to people who can read the conversation, by the same rule as the file (R8).
The job starts when the upload finishes, not when the message is sent, so in the usual case the thumbnail is ready before the message exists and travels in the message from the first moment; a thumbnail that finishes after the send reaches the readers as one small event (R3, R6, R10).
This ticket builds: three columns of `files` (`thumb_state`, `thumb_width`, `thumb_height`) and one migration; the `thumbnail` key of the file entry; the job `files.thumbnail` and a recurring sweep `files.thumbnail-sweep`; `image.ts`, the one file that touches the image library; two methods of the storage client; the route `GET /api/v1/files/{id}/thumbnail`; the change `thumbnail_updated` and the event `message.thumbnail_updated`; the handler in `client-core` that puts the finished thumbnail into the held message; and the body of the one function, `fileImage`, through which the cards of TOKI-062 read the thumbnail (R15). Nothing else on screen is built here: the card, the placeholder and the viewer are TOKI-062 (Scope).

## Requirements
- R1. Columns of `files`, in `modules/files/schema.ts`, added by one migration `<number>_file_thumbnails.sql` made with `pnpm db:generate --name file_thumbnails` (forward-only, it changes only the table `files` and inserts no row): `thumb_state` (text, not null, default `none`; one of `none`, `pending`, `ready`), `thumb_width` and `thumb_height` (integer, null unless `thumb_state` is `ready`). Checks: `thumb_state` is one of the three; `thumb_state` is `ready` exactly when both sizes are not null; when set, each size is between 1 and `THUMBNAIL_MAX_SIDE` (1040); `thumb_state` is `none` or `ready_at` is not null (a file that was never completed has no job). Index `files_thumb_pending_idx` on (`ready_at`, `id`) where `thumb_state` = `pending` and `state` in (`ready`, `attached`) (the sweep, R7; a removed file is not in it). The thumbnail has no storage-key column: the key is always `files/<id>/thumb.webp`, built from the `id` as Postgres stores it, as TOKI-058 R5 does for the original. The migration writes no backfill: a file completed before it stays `none` and shows as a file card; no code of this ticket queues a job for it. Check: SQL-text tests, each refusal naming its constraint, each "must fail" next to a "must pass": `ready` with sizes 1×1 and 1040×1040 passes and 0×5 and 1041×5 fail; `ready` with a null size fails; `none` with a size fails; `pending` with a null `ready_at` fails and with a time passes; a state `other` fails; the migration touches only `files` and a database with rows of TOKI-058 gets `none` on every one; `explain` of the query of R7 shows the index, with `SET enable_seqscan = off` in the test and a few hundred rows inserted and analysed first, so that the check cannot fail because the planner prefers to scan a tiny table.
- R2. `packages/shared/src/files/thumbnails.ts` (re-exported by the index of `files` and of the package) exports: `THUMBNAIL_MAX_SIDE` = 1040, `THUMBNAIL_QUALITY` = 80, `THUMBNAIL_MAX_INPUT_PIXELS` = 50,000,000, `THUMBNAIL_MAX_INPUT_BYTES` = 52,428,800 (50 MiB, half of `FILE_MAX_BYTES` of TOKI-058 R3; concern 5), `THUMBNAIL_DECODE_TIMEOUT_SECONDS` = 30, `THUMBNAIL_RETRY_LIMIT` = 3, `THUMBNAIL_PENDING_MAX_AGE_MS` = 1,800,000 (30 minutes, R7), `THUMBNAIL_CONTENT_TYPE` = `image/webp`, `thumbnailPath(fileId)` returning `/api/v1/files/<fileId>/thumbnail` (the id as given; the server accepts a lower-case id only, R8), `FileThumbnail` (a strict discriminated union on `status`: `{ status: "none" }`, `{ status: "pending" }`, `{ status: "ready", width, height }` with integers from 1 to 1040) and `ThumbnailUpdatedData` (a strict object `{ conversationId, messageId, parentId (null or id), fileId, thumbnail }` where `thumbnail` is `{ status: "none" }` or a ready one, never `pending`), the `data` of the event of R10. `FileEntry` of TOKI-058 R3 (`id`, `name`, `size`, `contentType`) gains the key `thumbnail` (a `FileThumbnail`), with the default `{ status: "none" }` on read only (as TOKI-037 R15 does for the keys that later work adds), so an entry stored or received before the key existed still parses; the server always writes it (R11). The entry holds no address and no storage key; its `size` stays the byte size of the original file (the card of TOKI-062 prints it), and the thumbnail has no byte size on the entry: it has `width` and `height` only. Check: schema tests accept the three shapes and refuse a ready one without a size, a `pending` with a size, an extra key, a size of 0 and one of 1041, and a `ThumbnailUpdatedData` with `pending`; an old `FileEntry` without the key parses to `none`; a `FileEntry` with `size` still parses and one with a `url`, a `key` or a `thumbnailSize` key is refused (strict); a type test imports every name from `@toki/shared`; `thumbnailPath` of an id gives the exact path.
- R3. The job starts when the upload is completed. The route `POST /api/v1/files/{id}/complete` of TOKI-058 R10 changes in one way. The statement that moves a `pending` row to `ready` also sets `thumb_state` to `pending` when the stored `content_type` begins with `image/` and is not `image/svg+xml` and `size_bytes` is more than 0 (the same rule as `fileImage` of TOKI-062 R8 uses today), and leaves `none` otherwise (the declared type is only a hint that saves reading every file; the content decides, R5; a file with an empty or `application/octet-stream` type is stored as such, TOKI-058 R3, and stays a file card, concern 1). In the same transaction, only when this statement changed the row, it calls `jobs.enqueue(thumbnailJob, { fileId }, { key: "thumbnail:<id>", tx })` of TOKI-064 R11 and R12. The queue reaches `fileRoutes` as the option `jobs` that `app.ts` fills with `app.jobs`; `files` imports `jobs` through its `index.ts` (TOKI-064 R24). The route holds no row lock while it calls storage (TOKI-058 R10) and opens the transaction only for the update and the enqueue. When `enqueue` throws, the transaction rolls back, the row stays `pending` (the file) and the answer is 500 `internal_error`, so the client's next `complete` tries again. A repeat of `complete` on a `ready` or `attached` file changes no row and enqueues nothing. The 200 body is `{ file: FileEntry, state: "ready", upload: null }` and its `file.thumbnail` is the one the row holds, `{ status: "pending" }` for an image (the entry is built by the one function of R11). No file of any other kind is read by this ticket. Check: a PNG completed gives `pending` and one job with `fileId` and the key; a text file, an `image/svg+xml` file, a file of 0 bytes with `image/png` and a file with `application/octet-stream` give `none` and no job; a repeat enqueues nothing (a spy on the queue); a queue that throws leaves the file `pending` (its upload state) and the answer 500, and a real transaction test on a jobs database shows a rollback leaves neither the `ready` state nor a job and a commit leaves both; the 200 body parses with the response schema.
- R4. The job and its handler. The job type is declared in `modules/files/thumbnail-jobs.ts` (no image library, exported by `index.ts` so that the API process can queue it): `thumbnailJob = defineJob({ name: "files.thumbnail", payload: z.strictObject({ fileId: <uuid> }), retry: { retryLimit: THUMBNAIL_RETRY_LIMIT }, expireSeconds: 120, concurrency: 2 })` (the option names of TOKI-064 R6; the rest of R8 there stays: backoff, delay, one attempt more than the limit, so four attempts). The handler is `createThumbnailHandler(deps: JobDeps)` in `modules/files/thumbnails.ts`, which returns `defineHandler(thumbnailJob, (context, data) => ...)` (TOKI-064 R9, R13) and is exported only by the worker entry of R13. It needs `deps.fileStore` (TOKI-058 R18 adds it), `deps.recordChange`, `deps.loadMessage` (the seam of TOKI-061 R12, R10 here) and `context.db`. The job types go to `job-types.ts` and the factory calls to `buildJobHandlers` in `job-handlers.ts`, in this ticket's change. A run does, in this order: (1) read the row of `data.fileId` (the key is built from the `id` that the row returns, never from the string of the payload, so an upper-case spelling makes no second key); a missing row, a `removed` row, or a `thumb_state` other than `pending` ends the run at once as completed (safe to run twice, TOKI-064 R13); (2) open the original with `getObject` (R9): when its `size` is above `THUMBNAIL_MAX_INPUT_BYTES` the body is destroyed unread and the outcome is `none` with the reason `too_large`; otherwise call `makeThumbnail` with the body (R5); (3) when the result is a thumbnail and `context.signal` has not aborted, write it with `putObject({ key, body })` at `files/<id>/thumb.webp`; (4) finish the row (R6). A run whose signal has aborted before step 3 or 4 writes nothing and throws, so the queue tries again. The handler never reads the file name, never logs it and puts no storage key in an error. Check, with the controllable clock of TOKI-008 and the fake store: the declaration is read back (name, payload shape, `retryLimit` 3, `expireSeconds` 120, `concurrency` 2); the walking test of TOKI-064 R7 passes for the payload; a payload with an extra key is refused by `enqueue`; a run for a missing, a `removed`, a `ready` and a `none` row completes and calls storage zero times; a run for a file whose `size` is one byte above the cap calls `getObject` once, reads no byte of the body (the body is destroyed), writes nothing and ends `none` with `too_large`, and a file of exactly the cap goes on to `makeThumbnail`; an upper-case `fileId` reads the same row and writes `files/<lower-case id>/thumb.webp`; a run whose signal is aborted before the write writes no object and no row and throws; `buildJobHandlers` with fake deps returns the handler, and the registry holds both new types (R7).
- R5. The reader of images, `modules/files/image.ts`, the only file that imports the image library (R13). It exports `makeThumbnail(source: Readable, options?): Promise<ThumbnailResult>` where the result is `{ kind: "ready", bytes: Buffer, width, height }` or `{ kind: "none", reason: "unsupported_format" | "too_many_pixels" | "too_large" | "unreadable" }`, and `options` holds only `maxInputPixels` and `maxInputBytes` (defaults `THUMBNAIL_MAX_INPUT_PIXELS` and `THUMBNAIL_MAX_INPUT_BYTES`), for tests. The library gets a finished buffer and never a stream, because with a stream its `metadata()` waits until the whole input has arrived (tested on `sharp` 0.34.5: a valid PNG header written to an open stream left `metadata()` unresolved after 1.5 seconds), so no check of the header could run before the whole file had been read and held. The checks therefore happen in this order, each before the next costs anything: (a) the format is read from the first bytes by this file, never from the declared type or the name: JPEG (`FF D8 FF`), PNG (the 8-byte signature), GIF (`GIF87a` or `GIF89a`), WebP (`RIFF`, 4 bytes, `WEBP`) and AVIF (a `ftyp` box at byte 4 whose major or compatible brands include `avif` or `avis`); anything else (SVG, HEIC, TIFF, BMP, text, an empty stream) destroys the source after the first chunk and gives `unsupported_format`, so a 100 MB text file named `a.png` costs one chunk, not a read; (b) the rest is read into one buffer while the bytes are counted: above `maxInputBytes` the source is destroyed and the result is `too_large` (a body longer than its stated size is caught here too); (c) the header is read with `sharp(buffer, { limitInputPixels: false, failOn: "error" }).metadata()`: its `format` must agree with (a) (`jpeg`, `png`, `gif`, `webp`; for AVIF `heif` with `compression` `av1`, so a HEIC file, whose compression is `hevc`, is `unsupported_format`), and `width` × `height` of the first frame (the option `animated` is not set, so a GIF or WebP with many frames reports the size of one frame; tested: a 30-frame GIF reports 40 × 30) must be at most `maxInputPixels`, otherwise `too_many_pixels` and nothing is decoded (tested: a PNG whose header says 20,000 × 20,000 is refused in about 2 ms; the comparison is made here and not by matching the text of the library's error); a header that cannot be read gives `unreadable`; (d) the loaders: when the module loads it calls `sharp.block({ operation: ["VipsForeignLoad"] })` and then `sharp.unblock` for the five buffer loaders (`VipsForeignLoadJpegBuffer`, `VipsForeignLoadPngBuffer`, `VipsForeignLoadNsgifBuffer`, `VipsForeignLoadWebpBuffer`, `VipsForeignLoadHeifBuffer`), so the library cannot reach its SVG, TIFF or other loaders even when a file lies about itself (tested: with these calls an SVG and a TIFF give "unsupported image format" and the five formats load); (e) the decode is `sharp(buffer, { limitInputPixels: maxInputPixels, failOn: "error" })` and fails on an error or a truncated file (tested: a truncated JPEG, GIF, WebP and PNG all fail with `failOn: "error"`, while `none` would give half a picture), which gives `unreadable`; warnings are not failures; (f) the orientation of the photo is applied (`rotate()`), so a picture taken sideways is upright and the sizes of the result are those of the upright picture; (g) the result fits inside `THUMBNAIL_MAX_SIDE` × `THUMBNAIL_MAX_SIDE` with the proportions kept and is never larger than the original (`fit: "inside"`, `withoutEnlargement: true`; a picture of 100 × 50 stays 100 × 50); only the first frame of an animation is read; (h) the output is WebP at quality `THUMBNAIL_QUALITY` with the transparency kept and no metadata at all (no EXIF, no place, no camera, no profile that names a person: `withMetadata` is never called); (i) the decode has `.timeout({ seconds: THUMBNAIL_DECODE_TIMEOUT_SECONDS })`, which stops the library's work itself (tested: it ends the pipeline with an error that starts with "timeout", where the abort of `context.signal` alone cannot stop a decode that runs in the library's own threads); a timeout is not an image result: `makeThumbnail` throws, and R6 c treats it as a failure to retry; (j) `sharp.cache(false)` is called once when the module loads (the setting is process-wide), so no call keeps anything between calls. `makeThumbnail` never throws for a bad image (those are the four reasons), and throws only for a failure that is not about the image (memory, a closed stream, the timeout). Check, with files of a few hundred bytes made by the test (the fixtures of Testing): each of the five formats gives `ready` with a decodable WebP; a JPEG with orientation 6 gives the sizes swapped and the pixels upright (a corner pixel moved to the expected place); a 2000 × 1000 image gives 1040 × 520, a 1040 × 600 image stays as it is, and one of 100 × 50 gives 100 × 50; a PNG with a half-transparent pixel keeps an alpha value in the result; an animated GIF of three different frames gives the first frame, and a GIF of 60 tiny frames gives one frame's size and a single frame out; an SVG, a HEIC sample, a TIFF, a text file named `a.png` and an empty stream give `unsupported_format` as listed in the test table, and the source is destroyed after its first chunk (a counting source shows at most one chunk read); a source that starts with a JPEG header and never ends gives `too_large` after the cap plus one chunk and is destroyed; a PNG with a header of 20,000 × 20,000 and a tiny valid data chunk gives `too_many_pixels` with no decode, and a header with no data gives `unreadable`; `maxInputPixels` 100 with an image of 10 × 10 passes and of 10 × 11 gives `too_many_pixels`; a JPEG with a GPS tag gives output with no EXIF (read back with the library's metadata); a truncated PNG and a truncated JPEG give `unreadable`; a file that holds SVG text after a PNG signature gives `unreadable` and the SVG loader is never run (a blocked loader); a test that sets the timeout to its smallest value on a large generated image sees the throw; two calls in a row return equal results for equal input.
- R6. How a run ends. After step 2 or 3 of R4 the handler finishes the row in one transaction through `finishThumbnail(tx, { fileId, thumbnail, at, recordChange })`, which is also what R7 calls. It runs `UPDATE files SET thumb_state = $1, thumb_width = $2, thumb_height = $3 WHERE id = $4 AND thumb_state = 'pending' AND state IN ('ready', 'attached') RETURNING state, conversation_id, uploader_id`; the answer, including the uploader, comes from the row it changed (one source). Outcomes: (a) a thumbnail was made: the row becomes `ready` with its sizes; (b) `makeThumbnail` or step 2 said `none`: the row becomes `none`, the object is not written, the run completes (no retry, no `jobs.dead`: an image that cannot be read is an expected end, not a fault), and one log line says which reason (R14); (c) a failure that is not about the image (storage unreachable, the database, memory, the decode timeout of R5 i): the handler throws and the queue retries (TOKI-064 R8); on the last attempt (`context.attempt` greater than `THUMBNAIL_RETRY_LIMIT`, so the fourth) it first finishes the row as `none` in its own transaction (an error of that write is logged and does not hide the first error) and then throws, so the job ends in `jobs.dead` for the operator and the file does not wait for ever; (d) the update changed no row (the file was dropped, removed with its message or already finished while the handler worked): when the handler had written the object it removes it with `deletePrefix("files/<id>/thumb.webp")` of TOKI-058 R5, and ends as completed, so no object stays that no row owns; the removal of the original and of everything under `files/<id>/` by TOKI-058 R18 covers the rest; (e) when the update changed a row whose `state` is `attached`, the same transaction reads the message of the file and calls `recordChange` as R10 says, after the update and as the last statement (TOKI-036 R18); when it is `ready` (not sent yet) nothing is recorded, because there is no message and the entry of the message will carry the thumbnail from its first moment (R11). The handler holds no row lock while it reads, decodes or writes; the lock is taken by the update and held to the commit. Check, with the fake store and the controllable clock: a run for a good PNG ends `ready` with sizes and one object; a run for an SVG ends `none`, writes no object, completes and leaves no dead job; a store that throws on `getObject` fails the first attempt and the row stays `pending`; with the clock moved through the retries the fourth attempt ends the row `none` and the job in `jobs.dead` with its source queue; a failure of that last write is logged and the first error is the one thrown; a file removed between step 1 and the update leaves no object (the spy on the fake shows the delete) and the run completes; a file attached before the update gets one recorded change, a file not attached gets none; two runs of one job (the same message delivered twice) leave one object, one change and the same row; a transaction that fails after the update rolls the row back to `pending`; `finishThumbnail` takes no uploader argument (a type test) and the change carries the uploader of the row.
- R7. The sweep. `fileThumbnailSweepJob = defineJob({ name: "files.thumbnail-sweep", payload: <empty strict object>, schedule: { cron: "*/10 * * * *" } })` is declared in `thumbnail-jobs.ts` and `createThumbnailSweepHandler(deps)` in `thumbnails.ts` (TOKI-064 R16: only the worker creates the schedule; the cron text is the only place where the interval is written). It needs `deps.jobs`, the queue of TOKI-064 R11 (`JobDeps` has the field `jobs` already: TOKI-064 R9 and R17 give the worker's own queue to `buildJobDeps(config, db, jobs)`, and the queue takes `tx`; this ticket adds nothing for it). One run: (1) reads at most 100 ids with a plain `SELECT id FROM files WHERE thumb_state = 'pending' AND state IN ('ready', 'attached') AND ready_at <= $now - THUMBNAIL_PENDING_MAX_AGE_MS ORDER BY ready_at, id LIMIT 100` (the index of R1; no lock is taken; a row of a removed file is never selected, so it cannot fill the batch); (2) for each id, in its own transaction, calls `jobs.cancelByKey(thumbnailJob, "thumbnail:<id>", { tx })` of TOKI-064 R14, which cancels a job that is waiting (created or waiting for a retry) and returns how many it cancelled: when it returns more than 0 the job was still in the queue, so the row is not closed: the same transaction enqueues the job again with the same payload and key (`enqueue(..., { key, tx })`) and the row stays `pending`; when it returns 0 no job is waiting for this file, and the transaction calls `finishThumbnail` with `none` (R6; the guarded `UPDATE ... WHERE thumb_state = 'pending'` makes a row that the worker finished a moment ago change nothing, and a row that the worker is updating at that moment makes the sweep wait for the lock and then change nothing). A file closed here that is attached sends the event of R10. So a job that was lost (the queue was emptied by hand, a dead job of an older run) leaves no placeholder behind, and a job that is only waiting behind a backlog after an outage is not discarded. A job that is still alive after 30 minutes and meets a `none` row ends as completed (R4 step 1). Thirty minutes is longer than the whole retry life of a job (four attempts of at most 120 seconds each and the waits of TOKI-064 R8, under 15 minutes). A job that was running when the worker was killed is not waiting, so a sweep that runs before the library's supervision has expired it may close that row; this is the one loss left and it is named in concern 9. The run logs the two counts (R14). Check, with the controllable clock and a real queue on a jobs database: a `pending` row of 29 minutes 59 seconds is not selected and at 30 minutes with no job is `none`; a `pending` row of 31 minutes whose job is waiting is kept `pending`, its job is replaced by one new job with the same key and payload, and a second run does the same and creates no second extra job; a row of another state is never touched; a row of a `removed` file with `pending` is never selected and 100 of them in front of one good row do not stop that row from being closed in the same run; 150 rows with no job take two runs; an attached file gets the event and an unsent one does not; a row finished by the worker between the select and the update stays as the worker left it (two connections, the sweep waits on the row lock and changes nothing); a second run does nothing; the cron text is parsed by a test and gives a 10-minute step; the registry holds `files.thumbnail` and `files.thumbnail-sweep` and the walking test of TOKI-064 R7 passes for both payloads.
- R8. `GET /api/v1/files/{id}/thumbnail` serves the thumbnail. A valid session is needed (401). It is registered in the same plugin as the routes of TOKI-058 and uses the one decision that TOKI-058 R12 makes for the open route: a file is readable by the actor when it is `attached` and the actor can read its conversation (`getConversationFacts` and `canReadConversation`, TOKI-027 R5: a member of the conversation, an archived channel included, D-170; an Admin has no extra right, D-047; a person who left reads nothing, D-116), or when it is `pending` or `ready` and the actor is its uploader. This ticket owns the one function that holds the decision, `readableFile(db, actorId, row)` in `modules/files/access.ts`, and the open route and this route both call it: if TOKI-058 wrote the decision inline in its route, this ticket moves it into the function with no change of behaviour; if TOKI-058 already built a function for it, this ticket gives it this name and place and changes no behaviour. The module does not export the function. The answer is 404 `not_found`, with the body that the open route gives (compared as bytes), when: the id is unknown or not a lower-case UUID; the state is `removed`; the file is not readable by the actor; or `thumb_state` is not `ready`. Otherwise the route sets the strong `ETag: "<id>"` (the thumbnail of a file is written once and never changes, so the id is its version); when the request's `If-None-Match` holds that value (alone, in a list, or in its weak form), the answer is 304 with the `ETag` and the `Cache-Control` below and no read of storage; otherwise it reads `files/<id>/thumb.webp` with `getObject` and answers 200 with the bytes, `Content-Type: image/webp`, `Content-Length`, `Content-Disposition: inline; filename="thumbnail.webp"`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, the `ETag` and `Cache-Control: private, no-cache`. So the browser keeps the picture but asks again each time, and the answer is 304 after the access check: a scrolling list costs one small request per picture and no bytes, and a person who lost access gets 404 at the next request (concern 6 proposes a longer cache and leaves it undecided). The content type is fixed by the route and not read from storage, and the bytes are those that `makeThumbnail` made (a new image, not the upload), so the rule that a file never runs in the browser (D-095) stays true: what the browser draws is never the file the person chose. A `ready` row whose object is missing (a reset of the development bucket) is 404 and one error line with the file id (TOKI-058's own note on resets). The route writes no row and no event, and logs no name and no address. ## Design
### How a thumbnail goes
```
 composer        server (Fastify)                 queue / worker                      MinIO
    |-- POST /files/{id}/complete -->|  row `ready`, thumb_state `pending`, job queued (one transaction)
    |<-- 200 file.thumbnail pending -|
    |                                |     worker: files.thumbnail { fileId }
    |                                |       open original (size known) ---------------------->|  stream
    |                                |       sniff format, read into one buffer (at most 50 MiB)
    |                                |       header: format, pixels (at most 50,000,000)
    |                                |       decode, upright, fit 1040, WebP (30 s limit)
    |                                |       write files/<id>/thumb.webp -------------------->|
    |                                |       UPDATE files ... ready (one transaction)
    |                                |       attached? -> recordChange -> message.thumbnail_updated
    |-- POST /conversations/{id}/messages { attachmentIds } -->|  entry carries `thumbnail` (ready, or pending)
    |<-- event message.thumbnail_updated  (only when the file was already in a message) ---|
    |-- GET /files/{id}/thumbnail ->|  session, may read the conversation
    |<-- 200 image/webp + ETag, private, no-cache (304 on a repeat) ---------------------|
```
Both orders are covered. The usual order is the upper one: the picture is made while the person types, and the message carries it. The other order, a send before the worker finishes, is the event. The file row is the one place where the two meet: the worker's update and the send's link both lock the row, so a send either sees the finished thumbnail in its entry or the worker sees the file attached and sends the event, never neither (R6 e, R11).

### Choices made here
- **The job starts at `complete`, not at the send** (concern 4). Work that starts when the upload finishes runs while the person types, so for most messages there is nothing to wait for and no second event. The cost is a thumbnail for an image that is never sent: at most 20 unsent files per person exist (TOKI-058 R9), each is removed after at most 24 hours with its thumbnail (TOKI-058 R18), and the work of one is a fraction of a second, so the waste has a bound. The start is in the same transaction as the state change, so a file that is `ready` and an image always has its job (R3).
- **A narrow event, not the whole message** (concern 4). The events of edit, delete and pin carry the entry and the client chooses the fresher copy by `editedAt` (TOKI-047 R14). A thumbnail does not change `editedAt`, so a whole entry would look equal in age to the held one and could put back an older text or older reactions. A patch of one file is applied the same way twice (TOKI-040 R18) and can only move a thumbnail from `pending` to its final state.
- **The server draws the picture, the browser draws the server's picture** (concern 6). The upload stays opaque and downloaded (D-095). What the browser draws is a WebP that the worker made: new pixels, no metadata, a type fixed by the route. A hostile file cannot reach the browser as the thumbnail, only as a download.
- **Through the server, not a signed address** (concern 6). A signed address changes at every request and carries `attachment`, so the browser could not cache it and, with the headers of TOKI-058 R13, may not draw it. The route streams the WebP and answers a repeat with a 304 after the access check, so the browser keeps the picture without the server giving up the check.
- **One rendition, 1040 pixels, WebP, no metadata** (concern 3, concern 7). The prototype's image box is 300 pixels wide (`.imgph`: `width: min(300px, 100%)`, `aspect-ratio: 4/3`) and its viewer is up to 520 wide (`.imgph.big`). 1040 is twice the viewer and covers the card at more than three times the density, so the card and the viewer window of TOKI-062 draw the same file and nothing is made twice. The price is that a card downloads a picture larger than its box needs (concern 7). WebP draws in the last two versions of Chrome, Edge, Safari and Firefox (NFR-14 of the requirements names those browsers), keeps transparency and is smaller than JPEG at the same look. Dropping the metadata removes the place and the camera of a photo (the original keeps them; the person chose to share it, not to share it as a picture on a list).
- **One library, one file, read from a buffer** (concern 5). `sharp` (libvips) decodes JPEG, PNG, GIF, WebP and AVIF, reads the size from the header, limits the pixels, applies the orientation, writes WebP and can be told to stop after a time and to refuse every loader that is not one of the five; it is the common choice for Node and is fast (a 49-megapixel PNG was read and reduced in about 0.13 seconds in the author's test on a laptop; not a gate). It does not check a stream before the end, so this ticket reads the original into one buffer after its own check of the first bytes and of the size (R5), and pays for that with a cap on the size of the original (concern 5). Pure-JavaScript decoders are slow and have no AVIF or WebP encoder; an external converter (ImageMagick) would add a process and a policy file. The cost is native code per platform (concern 5). `image.ts` is the only file that knows it, like `store.ts` and the SDK, so a different library is one file.
- **The library stays out of the API process** (R13). The API process only queues the job, so it needs the job's name and nothing else. The handlers and the reader of images are behind a second entry that only the worker loads, so a crash or a stall of the decoder, and the memory of a decode, cannot reach the process that answers requests.
- **An unreadable image is a normal end** (R6 b). A person can send any file with an `image/` label. The job ends `none` and the file shows as a file card with a download; it is not a retry and not a dead job. Only a failure that has nothing to do with the image is retried and, after the last attempt, lands in `jobs.dead` for the operator.
- **The sweep exists because a placeholder that never ends is worse than none** (concern 9). A lost job or a worker that was down for an hour must not leave `pending` on a screen. One recurring job looks at every row still `pending` after 30 minutes: it keeps a row whose job is still waiting and closes a row that has none.
- **No new table.** Three columns of `files` hold the result (R1). The key is derived, like the key of the original.

### The state of a thumbnail
| `thumb_state` | Meaning | Set by |
| :---- | :---- | :---- |
| `none` | no thumbnail: not an image, a format the server does not draw, too many pixels, too large to read, unreadable, failed for good | `complete` (not `image/`), the worker (R6), the sweep |
| `pending` | the image is complete and its job has not finished | `complete` (R3) |
| `ready` | `files/<id>/thumb.webp` exists and has the sizes | the worker (R6) |

`pending` goes to `ready` or `none`, and nothing goes back to `pending`. The entry shows the same three words. Only `ready` has sizes.

### Errors
- The decoder cannot read the image, the format is not in the list, the picture has too many pixels or the file is above the size cap -> `none`, the job completes, one log line (R6 b).
- Storage or the database fails, or a decode runs past its 30 seconds -> the job is retried (TOKI-064 R8); after the fourth attempt the row is `none` and the job is in `jobs.dead` (R6 c).
- The queue cannot take the job at `complete` -> the transaction rolls back and the answer is 500; the client's next `complete` repeats it (R3).
- The object is missing when the route serves it -> 404 and one error line (R8).
- The worker is down -> `pending` stays until the worker returns; the sweep, which runs in the worker, then keeps the rows whose jobs are waiting and closes the others; messages and uploads are not affected.

## Data safety
- The worker decodes bytes that a person chose. Limits, each checked before the next costs anything: the size of the original is read from storage and refused above 50 MiB before a byte is read (R4); the format is read from the first bytes and only five formats go on, a source of any other kind is destroyed after its first chunk (R5 a); the bytes are counted and the source is destroyed at the cap (b); the pixel count is read from the header of the finished buffer and capped at 50,000,000 before anything is decoded (c); the library can load only the five formats (d); the decode fails on an error (e) and has a 30-second limit that stops the library's work (i); two jobs run at a time (R4); a job has 120 seconds (R4); the library cache is off (j). The most that one run holds is the original (at most 50 MiB) plus the decoded picture (at most 50,000,000 pixels, a few hundred megabytes when the format is not read in a stream), so two runs hold under about 600 MB at the worst; the by-hand measure in Testing replaces this estimate with a number (concern 5).
- The decoder runs only in the worker process: the API process does not load the library (R13). A decoder that crashes the process takes down the worker, which also runs the timers and the link previews of other tickets, and not the API; the queue then retries the job after its `expireSeconds` and the sweep closes a row whose job is gone (R7, concern 9). A separate process for the decode is not built.
- A thumbnail carries no metadata (R5 h), so a photo shared as a picture does not publish its place or its camera.
- A thumbnail is readable only through R8, by the rule of the file: a member who can read the conversation, or the uploader of an unsent file. The answer for everyone else is the 404 of the open route, so nothing confirms that a file exists.
- What the browser draws is the worker's output with a fixed type and `nosniff`, a sandboxed content-security header and a cross-origin policy (R8); the uploaded bytes are still served only as a download (TOKI-058 R13).
- File names are data: never in a key, a log line or an error (R4, R14). The key is derived from the id.
- A removed file loses its thumbnail with everything under `files/<id>/` (TOKI-058 R18), and a thumbnail that is written after the file was removed is deleted by the worker (R6 d). No object stays that no row owns.
- The browser keeps a thumbnail but asks again for each use, and the answer is checked against the access rule every time (R8). A person removed from a private channel gets nothing new at their next request; a copy their browser already holds stays in its cache until it is cleared, which the server cannot reach (concern 6).

## Open questions from the intent
- Which kinds of image get a thumbnail, and what do the others show? Not answered: the log does not say what counts as an image; this spec proposes JPEG, PNG, GIF, WebP and AVIF, and shows every other file as a file card with a download. See concern 1.
- How big is a thumbnail, in what format, and does it keep the details of the photo? Answered in this spec: 1040 pixels on the long side, WebP at quality 80, no metadata (R5). See concern 3.
- When does the job start and how does the message learn? Answered in this spec: at `complete`, in the same transaction; a ready thumbnail travels in the entry, a late one in the event `message.thumbnail_updated` (R3, R6, R10). See concern 4.
- How does the server read an image that a user chose without being brought down by it? Answered in this spec: `sharp` in the worker only, after a check of the format, the size and the pixels, with a limit on the time and the concurrency (R4, R5, R13). See concern 5.
- What does the screen show while the thumbnail is not ready, and where do the proportions of the placeholder come from? Not answered: the entry has no size while `pending`, so a placeholder cannot have the right proportions until the worker has read the image. See concern 2.
- What if the job fails for good, or is lost? Answered in this spec: the row ends `none` after the last attempt and a sweep closes any row still `pending` after 30 minutes whose job is gone (R6, R7). See concern 9.
- How does the browser get a thumbnail, who may, and for how long may it keep it? Not answered: who may is the rule of the file and the route is built (R8), but how long a browser may keep a thumbnail is a trade that the log does not decide; the code revalidates every time and a longer cache is a proposal. ## Areas of concern
1. What counts as an image. The log says the previews include image thumbnails (D-014) and that "Documents" in the Files page is every file that is not an image, and does not say which formats are images. Proposal, not a decision: JPEG, PNG, GIF (the first frame), WebP and AVIF are images and get a thumbnail; SVG, HEIC, TIFF, BMP and every other type are files, shown as a file card with a download and listed under Documents. Reason: those five are what a browser draws and what the library reads with limits; SVG is a document that can hold scripts and links and the server would have to render it (D-095 says files are never opened in the page); HEIC needs a decoder that the prebuilt library does not include, and a phone usually gives a JPEG to a browser. If the owner wants HEIC or TIFF, the set is one list in `image.ts` (the sniff, the loaders and the format check) and the library build, and the proportions of the cost are in concern 5. A related point of the same proposal: the job is queued from the declared type (R3), so a picture that a browser or a drag from the desktop hands over with an empty or `application/octet-stream` type is stored as such (TOKI-058 R3) and stays a file card; the alternative is to read the first bytes at `complete`, which costs one more read of storage on every upload. Not decided. Owner: Thanh Truong (product owner).
2. The proportions of the placeholder before the thumbnail is ready. F18 says the placeholder has the right proportions so the layout does not jump. The server knows the size of an image only after the worker has read it, and the job starts when the upload finishes, so in the usual case the size is known before the message exists. When a message is sent before the worker has finished, the entry says `pending` with no size, and this spec gives the screen only what it knows: the prototype's box (`.imgph`, 4 : 3) until the event arrives, and then the real proportions, which can make that one message change height. Proposal A, what R2 builds: accept that single change. Proposal B: the composer reads the size of the picture in the browser and sends it with the start of the upload (two integers on the request of TOKI-058 R6, kept on the row as a hint and replaced by the real size), so a `pending` entry has a size and the layout never jumps; it costs two columns, a request field, a check of the numbers and a change to TOKI-058 and TOKI-059. Not decided. Owner: Thanh Truong (product owner).
3. Size, format and metadata of the thumbnail. Decided in this spec: 1040 pixels on the long side, never enlarged, WebP at quality 80 with transparency, the first frame of an animation, the orientation applied and every piece of metadata dropped. Reason: the prototype's image box is 300 pixels wide and its viewer 520; 1040 is twice the viewer and serves the card and the viewer with one file (concern 7); WebP draws in the browsers of NFR-14 and keeps alpha; the original keeps its metadata. The numbers are constants of `packages/shared` (R2): another value changes one constant and its tests. A technical choice of this spec. Owner: Thanh Truong.
4. When the job starts and how the message is told. Decided in this spec: the job is queued by `complete`, in the transaction that makes the file `ready`, so it runs while the person types; the message carries a finished thumbnail in its entry, and a late one is told by one narrow event, `message.thumbnail_updated`, through `recordChange` as TOKI-036 requires. Reason: no second event for the usual message, no work for an image that is dropped before it is complete, and a patch of one file cannot put back older text or reactions (Design). The alternative, queueing at the send, works for the plan's wording but makes every image message show a placeholder first. The cost is a thumbnail for an image that is never sent, bounded by the cap of 20 unsent files and the 24-hour removal (TOKI-058 R9, R18). Owner: Thanh Truong.
5. Reading images safely, and the library. Decided in this spec: `sharp` behind one file, in the worker process only and never loaded by the API process, with the limits of R4 and R5. The numbers are choices of this spec, not figures from the Blueprint, and each is one constant: the original may be at most 52,428,800 bytes (50 MiB), 50,000,000 pixels (a 45-megapixel camera passes), a decode time of 30 seconds, two jobs at a time, and the library cache off. Reason for the size cap: the library cannot check a stream before the whole of it has arrived (tested on 0.34.5), so the original is read into one buffer; the upload limit is 100 MiB (TOKI-058 `FILE_MAX_BYTES`), and two jobs at once at that size would hold 200 MiB of originals before any decode, so the cap is half of it. A photo of 50 megapixels is 10 to 25 MB as a JPEG and passes; a lossless PNG or TIFF of that size can be above the cap and then stays a file card with a download. If the owner wants every uploaded image to get a thumbnail, the constant is raised to `FILE_MAX_BYTES`, at the price of the memory above. Other costs and unknowns, for the owner and for TOKI-084: it is native code, so the production image needs its platform package (about 15 to 20 MB installed); decoding 50 million pixels can use several hundred megabytes at the peak, so the worker needs headroom, and the by-hand measure in Testing gives the real number before it is set; a native crash of the decoder takes down the worker process, which also runs other tickets' timers and jobs (Data safety), and a separate process for the decode is not built; and there is no rate per person: at most 20 unsent files exist at once (TOKI-058 R9), and 200 people sending 20 images each would be a few minutes of work for the worker at the speed measured by the author (about 0.1 to 0.3 seconds an image), so the queue absorbs a burst, and a rate is added only if the by-hand measure or the logs show a problem. It departs from a sentence of TOKI-058 (uploaded content is never read by the server): the worker reads images to make the thumbnail, which D-014 requires. A technical choice of this spec. Owner: Thanh Truong.
6. How the browser gets a thumbnail, and for how long it may keep it. The route is built: `GET /api/v1/files/{id}/thumbnail` streams the WebP through the server by the rule of the file and answers 404 to everyone else, with a fixed type. Reason for the route: a signed address changes each time and carries `attachment`, so the browser could neither cache nor draw it; the thumbnail is small. What the log does not decide is how long a browser may keep the picture. The log says nothing is visible to a person who left a private channel (D-116) and that Admins have no extra right (D-047), and it does not say how much speed may be traded against that. The code does the safe thing: `Cache-Control: private, no-cache` with a strong `ETag` that is the file id, and a 304 after the access check, so the browser keeps the bytes, a scrolling list costs one small request per picture, and access ends at the next request. Proposal, not a decision: `Cache-Control: private, max-age=3600`, which saves those requests and means that a picture that a browser already holds stays readable from its cache for up to an hour after the person loses access (a removal from a private channel); it changes one header value and one test. Not decided. Owner: Thanh Truong (product owner).
7. The large image of the viewer. Decided in this spec: there is one rendition of an image, the thumbnail of up to 1040 pixels on the long side, and both the card and the viewer window of TOKI-062 draw it; no second image, no size parameter. Reason: F18 says an image opens large, and the original cannot be drawn in the page (D-095; TOKI-058 R13 leaves the check of an `<img>` on a signed address to a by-hand trial), so the large image must be one the server made; 1040 is twice the 520 pixels of the window, sharp on a screen at twice the density, and one file means one job, one key, one route and no parameter. The cost is that a card, whose box is 300 pixels wide, downloads the same file, which holds about 2.6 times the pixels of a 640-pixel picture; a smaller second rendition for the card can be added later as another key and is not built. TOKI-062 is changed to match (Plan changes). A technical choice of this spec. Owner: Thanh Truong.
8. Edits that other work needs. Decided in this spec: this ticket edits no other spec, and the requests are in "Plan changes": the entry key and its one builder, two methods of the storage client, the change to `complete`, the sentence of TOKI-058's Data safety, the use of the `loadMessage` field of `JobDeps` (TOKI-061 R12), the second import path of the module, the row of the event handler and the registry, and the merge rule of TOKI-045 and TOKI-047. As code it changes `modules/files/`, `changes.ts` and `modules/realtime/` by a row each, `job-types.ts`, `job-handlers.ts`, `job-deps.ts` and `client.ts`. Owner: Thanh Truong.
9. A thumbnail that never finishes. Decided in this spec: an image that cannot be read ends `none` at once (R6 b); a failure that is not about the image is tried four times (four attempts) and then ends `none` and in `jobs.dead` (R6 c); a recurring sweep looks at every row still `pending` 30 minutes after the upload completed, keeps a row whose job is still waiting in the queue and closes a row whose job is gone (R7). Reason: a placeholder that never ends is the worst of the three states, a lost job, a queue emptied by hand or a worker that was down must not leave one, and a worker that comes back to a backlog must not throw the backlog away. One loss is left: a job that was running when the worker was killed is not waiting, and a sweep tick that falls before the library's supervision has expired it closes that row; the picture then shows as a file card. A file that ended `none` has no retry button: it is a download. Owner: Thanh Truong.
