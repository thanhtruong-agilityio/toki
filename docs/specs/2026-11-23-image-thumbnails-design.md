# Image thumbnails design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/image-thumbnails.md (Thanh Truong)
Ticket: TOKI-060

## Goal
A file is stored as an opaque download and the browser never draws it (D-095). A picture in a message has to be seen, so the server makes a second, small image from it, a thumbnail, that the browser may draw. This ticket builds that: the background job that makes the thumbnail, the reader of images that does it safely, the columns that record the result, the route that serves it, and the event that tells every open client that it is ready.
Two rules are hard. The server decodes bytes that a person chose, so the decoder runs only in the worker, with a limit on the size of the picture and on the time, and an image that cannot be read ends in a state that says so, never in a placeholder that waits for ever (R4, R5, R9). The thumbnail is served only to people who can read the conversation, by the same rule as the file (R8).
The job starts when the upload finishes, not when the message is sent, so in the usual case the thumbnail is ready before the message exists and travels in the message from the first moment; a thumbnail that finishes after the send reaches the readers as one small event (R3, R6, R10).
This ticket builds: three columns of `files` (`thumb_state`, `thumb_width`, `thumb_height`) and one migration; the `thumbnail` key of the file entry; the job `files.thumbnail` and a recurring sweep `files.thumbnail-sweep`; `image.ts`, the one file that touches the image library; two methods of the storage client; the route `GET /api/v1/files/{id}/thumbnail`; the change `thumbnail_updated` and the event `message.thumbnail_updated`; the handler in `client-core` that puts the finished thumbnail into the held message; and the body of the one function, `fileImage`, through which the cards of TOKI-062 read the thumbnail (R15). Nothing else on screen is built here: the card, the placeholder and the viewer are TOKI-062 (Scope).

## Requirements
- R1. Columns of `files`, in `modules/files/schema.ts`, added by one migration `<number>_file_thumbnails.sql` made with `pnpm db:generate --name file_thumbnails` (forward-only, it changes only the table `files` and inserts no row): `thumb_state` (text, not null, default `none`; one of `none`, `pending`, `ready`), `thumb_width` and `thumb_height` (integer, null unless `thumb_state` is `ready`). Checks: `thumb_state` is one of the three; `thumb_state` is `ready` exactly when both sizes are not null; when set, each size is between 1 and `THUMBNAIL_MAX_SIDE` (640); `thumb_state` is `none` or `ready_at` is not null (a file that was never completed has no job). Index `files_thumb_pending_idx` on (`ready_at`, `id`) where `thumb_state` = `pending` (the sweep, R7). The thumbnail has no storage-key column: the key is always `files/<id>/thumb.webp`, built from the `id` as Postgres stores it, as TOKI-058 R5 does for the original. Check: SQL-text tests, each refusal naming its constraint, each "must fail" next to a "must pass": `ready` with sizes 1×1 and 640×640 passes and 0×5 and 641×5 fail; `ready` with a null size fails; `none` with a size fails; `pending` with a null `ready_at` fails and with a time passes; a state `other` fails; the migration touches only `files` and a database with rows of TOKI-058 gets `none` on every one; `explain` of the query of R7 shows the index.
- R2. `packages/shared/src/files/thumbnails.ts` (re-exported by the index of `files` and of the package) exports: `THUMBNAIL_MAX_SIDE` = 640, `THUMBNAIL_QUALITY` = 80, `THUMBNAIL_MAX_INPUT_PIXELS` = 50,000,000, `THUMBNAIL_RETRY_LIMIT` = 3, `THUMBNAIL_PENDING_MAX_AGE_MS` = 1,800,000 (30 minutes, R7), `THUMBNAIL_CONTENT_TYPE` = `image/webp`, `thumbnailPath(fileId)` returning `/api/v1/files/<fileId>/thumbnail` (the id as given; the server accepts a lower-case id only, R8), `FileThumbnail` (a strict discriminated union on `status`: `{ status: "none" }`, `{ status: "pending" }`, `{ status: "ready", width, height }` with integers from 1 to 640) and `ThumbnailUpdatedData` (a strict object `{ conversationId, messageId, parentId (null or id), fileId, thumbnail }` where `thumbnail` is `{ status: "none" }` or a ready one, never `pending`), the `data` of the event of R10. `FileEntry` of TOKI-058 R3 gains the key `thumbnail` (a `FileThumbnail`), with the default `{ status: "none" }` on read only (as TOKI-037 R15 does for the keys that later work adds), so an entry stored or received before the key existed still parses; the server always writes it. The entry holds no address, no storage key and no byte size. Check: schema tests accept the three shapes and refuse a ready one without a size, a `pending` with a size, an extra key, a size of 0 and one of 641, and a `ThumbnailUpdatedData` with `pending`; an old `FileEntry` without the key parses to `none`; a type test imports every name from `@toki/shared`; `thumbnailPath` of an id gives the exact path.
- R3. The job starts when the upload is completed. The route `POST /api/v1/files/{id}/complete` of TOKI-058 R10 changes in one way. The statement that moves a `pending` row to `ready` also sets `thumb_state` to `pending` when the stored `content_type` begins with `image/` and is not `image/svg+xml` and `size_bytes` is more than 0 (the same rule as `fileImage` of TOKI-062 R8 uses today), and leaves `none` otherwise (the declared type is only a hint that saves reading every file; the content decides, R5). In the same transaction, only when this statement changed the row, it calls `jobs.enqueue(thumbnailJob, { fileId }, { key: "thumbnail:<id>", tx })` of TOKI-064 R11 and R12. The queue reaches `fileRoutes` as the option `jobs` that `app.ts` fills with `app.jobs`; `files` imports `jobs` through its `index.ts` (TOKI-064 R24). The route holds no row lock while it calls storage (TOKI-058 R10) and opens the transaction only for the update and the enqueue. When `enqueue` throws, the transaction rolls back, the row stays `pending` (the file) and the answer is 500 `internal_error`, so the client's next `complete` tries again. A repeat of `complete` on a `ready` or `attached` file changes no row and enqueues nothing. The 200 body is `{ file: FileEntry, state: "ready", upload: null }` and its `file.thumbnail` is the one the row holds, `{ status: "pending" }` for an image. No file of any other kind is read by this ticket. Check: a PNG completed gives `pending` and one job with `fileId` and the key; a text file, an `image/svg+xml` file and a file of 0 bytes with `image/png` give `none` and no job; a repeat enqueues nothing (a spy on the queue); a queue that throws leaves the file `pending` (its upload state) and the answer 500, and a real transaction test on a jobs database shows a rollback leaves neither the `ready` state nor a job and a commit leaves both; the 200 body parses with the response schema.
- R4. The job and its handler, in `modules/files/thumbnails.ts`. `thumbnailJob = defineJob({ name: "files.thumbnail", payload: z.strictObject({ fileId: <uuid> }), retry: { retryLimit: THUMBNAIL_RETRY_LIMIT }, expireSeconds: 120, concurrency: 2 })` (the option names of TOKI-064 R6; the rest of R8 there stays: backoff, delay, one attempt more than the limit, so four attempts). `createThumbnailHandler(deps: JobDeps)` returns `defineHandler(thumbnailJob, (context, data) => ...)` (TOKI-064 R9, R13). It needs `deps.fileStore` (TOKI-058 R18 adds it), `deps.recordChange` and the application database; it adds no field to `JobDeps`. The job type goes to `job-types.ts` and the factory call to `buildJobHandlers` in `job-handlers.ts`, in this ticket's change. A run does, in this order: (1) read the row of `data.fileId` (the key is built from the `id` that the row returns, never from the string of the payload, so an upper-case spelling makes no second key); a missing row, a `removed` row, or a `thumb_state` other than `pending` ends the run at once as completed (safe to run twice, TOKI-064 R13); (2) read the original from storage as a stream (`getObject`, R9) and call `makeThumbnail` (R5); (3) when the result is a thumbnail and `context.signal` has not aborted, write it with `putObject` at `files/<id>/thumb.webp`; (4) finish the row (R6). A run whose signal has aborted before step 3 or 4 writes nothing and throws, so the queue tries again. The handler never reads the file name, never logs it and puts no storage key in an error. Check, with the controllable clock of TOKI-008 and the fake store: the declaration is read back (name, payload shape, `retryLimit` 3, `expireSeconds` 120, `concurrency` 2); the walking test of TOKI-064 R7 passes for the payload; a payload with an extra key is refused by `enqueue`; a run for a missing, a `removed`, a `ready` and a `none` row completes and calls storage zero times; an upper-case `fileId` reads the same row and writes `files/<lower-case id>/thumb.webp`; a run whose signal is aborted before the write writes no object and no row and throws; `buildJobHandlers` with fake deps returns the handler, and the registry holds both new types (R7).
- R5. The reader of images, `modules/files/image.ts`, the only file that imports the image library (R13). It exports `makeThumbnail(source: Readable, options?): Promise<ThumbnailResult>` where the result is `{ kind: "ready", bytes: Buffer, width, height }` or `{ kind: "none", reason: "unsupported_format" | "too_many_pixels" | "unreadable" }`, and `options` holds only `maxInputPixels` (default `THUMBNAIL_MAX_INPUT_PIXELS`), for tests. The rules: (a) the format is read from the content, never from the declared type or the name, and must be one of `THUMBNAIL_INPUT_FORMATS` = JPEG, PNG, GIF, WebP and AVIF (concern 1; the library reports AVIF as `heif`, so a file is AVIF only when its compression is `av1`, and HEIC stays unsupported); SVG, HEIC, TIFF, BMP and every other format give `unsupported_format` and the reading of the stream stops at once; (b) the number of pixels (width × height of the first frame) is read from the header before a pixel is decoded and must be at most `maxInputPixels`, otherwise `too_many_pixels` and nothing is decoded; (c) a file that the decoder cannot read, a truncated one or a header that lies, gives `unreadable`; the library is told to fail on an error and not to continue on a warning; (d) the orientation of the photo is applied, so a picture taken sideways is upright and the sizes of the result are those of the upright picture; (e) the result fits inside 640 × 640 with the proportions kept, and is never larger than the original (a picture of 100 × 50 stays 100 × 50); (f) only the first frame of an animation is read; (g) the output is WebP at quality 80 with the transparency kept, and no metadata at all (no EXIF, no place, no camera, no profile that names a person); (h) a call reads one image and keeps nothing between calls: the library cache is off. It never throws for a bad image (those are the three reasons), and it throws only for a failure that is not about the image (memory, a closed stream), which the handler treats as a try again (R6). Check, with files of a few hundred bytes made by the test (the fixtures of Testing): each of the five formats gives `ready` with a decodable WebP; a JPEG with orientation 6 gives the sizes swapped and the pixels upright (a corner pixel moved to the expected place); a 2000 × 1000 image gives 640 × 320 and one of 100 × 50 gives 100 × 50; a PNG with a half-transparent pixel keeps an alpha value in the result; an animated GIF of three different frames gives the first frame; an SVG, a HEIC sample, a TIFF, a text file named `a.png` and an empty stream give `unsupported_format` or `unreadable` as listed in the test table, and the reading stops (the source is destroyed); a header of 20,000 × 20,000 with no data gives `too_many_pixels` quickly, and `maxInputPixels` 100 with an image of 10 × 10 passes and of 10 × 11 gives `too_many_pixels`; a JPEG with a GPS tag gives output with no EXIF (read back with the library's metadata); a truncated PNG gives `unreadable`; two calls in a row return equal results for equal input.
- R6. How a run ends. After step 2 or 3 of R4 the handler finishes the row in one transaction through `finishThumbnail(tx, { fileId, thumbnail, at, uploaderId, recordChange })`, which is also what R7 calls. It runs `UPDATE files SET thumb_state = $1, thumb_width = $2, thumb_height = $3 WHERE id = $4 AND thumb_state = 'pending' AND state IN ('ready', 'attached') RETURNING state, conversation_id, uploader_id`; the answer comes from the rows it changed. Outcomes: (a) a thumbnail was made: the row becomes `ready` with its sizes; (b) `makeThumbnail` said `none`: the row becomes `none`, the object is not written, the run completes (no retry, no `jobs.dead`: an image that cannot be read is an expected end, not a fault), and one log line says which reason (R14); (c) a failure that is not about the image (storage unreachable, the database, memory): the handler throws and the queue retries (TOKI-064 R8); on the last attempt (`context.attempt` greater than `THUMBNAIL_RETRY_LIMIT`) it first finishes the row as `none` in its own transaction (an error of that write is logged and does not hide the first error) and then throws, so the job ends in `jobs.dead` for the operator and the file does not wait for ever; (d) the update changed no row (the file was dropped, removed with its message or already finished while the handler worked): when the handler had written the object it removes it with `deletePrefix("files/<id>/thumb.webp")` of TOKI-058 R5, and ends as completed, so no object stays that no row owns; the removal of the original and of everything under `files/<id>/` by TOKI-058 R18 covers the rest; (e) when the update changed a row whose `state` is `attached`, the same transaction reads the message of the file and calls `recordChange` as R10 says, after the update and as the last statement (TOKI-036 R18); when it is `ready` (not sent yet) nothing is recorded, because there is no message and the entry of the message will carry the thumbnail from its first moment (R11). The handler holds no row lock while it reads, decodes or writes; the lock is taken by the update and held to the commit. Check, with the fake store and the controllable clock: a run for a good PNG ends `ready` with sizes and one object; a run for an SVG ends `none`, writes no object, completes and leaves no dead job; a store that throws on `getObject` fails the first attempt and the row stays `pending`; with the clock moved through the retries the fourth attempt ends the row `none` and the job in `jobs.dead` with its source queue; a failure of that last write is logged and the first error is the one thrown; a file removed between step 1 and the update leaves no object (the spy on the fake shows the delete) and the run completes; a file attached before the update gets one recorded change, a file not attached gets none; two runs of one job (the same message delivered twice) leave one object, one change and the same row; a transaction that fails after the update rolls the row back to `pending`.
- R7. The sweep. `fileThumbnailSweepJob = defineJob({ name: "files.thumbnail-sweep", payload: <empty strict object>, schedule: { cron: "*/10 * * * *" } })` and `createThumbnailSweepHandler(deps)` (TOKI-064 R16: the worker creates the schedule; the cron text is the only place where the interval is written). One run reads at most 100 rows `WHERE thumb_state = 'pending' AND ready_at <= $now - THUMBNAIL_PENDING_MAX_AGE_MS ORDER BY ready_at, id FOR UPDATE SKIP LOCKED` (the index of R1) and, for each, calls `finishThumbnail` with `none` in its own transaction, so a job that was lost (the queue was emptied by hand, a dead job of an older run) and a job that waited too long leave no placeholder behind, and each such file that is attached sends the event of R10. A job that is still alive after 30 minutes finds its row `none` and ends as completed (R4 step 1). Thirty minutes is longer than the whole retry life of a job (four attempts of at most 120 seconds each and the waits of TOKI-064 R8, under 15 minutes). Both job types are added to `job-types.ts` and the second factory to `buildJobHandlers`. Check, with the controllable clock: a `pending` row at 29 minutes 59 seconds is kept and at 30 minutes is `none`; a row of another state is never touched; 150 rows take two runs; an attached file gets the event and an unsent one does not; a locked row is skipped and stays; a second run does nothing; the cron text is parsed by a test and gives a 10-minute step; the registry holds `files.thumbnail` and `files.thumbnail-sweep` and the walking test of TOKI-064 R7 passes for both payloads.
- R8. `GET /api/v1/files/{id}/thumbnail` serves the thumbnail. A valid session is needed (401). It is registered in the same plugin as the routes of TOKI-058 and uses the one decision that TOKI-058 R12 makes for the open route: a file is readable by the actor when it is `attached` and the actor can read its conversation (`getConversationFacts` and `canReadConversation`, TOKI-027 R5: a member of the conversation, an archived channel included, D-170; an Admin has no extra right, D-047; a person who left reads nothing, D-116), or when it is `pending` or `ready` and the actor is its uploader. If that decision is written inline in the route of TOKI-058 when this ticket is built, this ticket moves it to one function, `readableFile(db, actorId, row)` in `modules/files/access.ts`, that both routes call, with no change of behaviour (so the two cannot drift). The answer is 404 `not_found`, with the body that the open route gives (compared as bytes), when: the id is unknown or not a lower-case UUID; the state is `removed`; the file is not readable by the actor; or `thumb_state` is not `ready`. Otherwise it reads `files/<id>/thumb.webp` with `getObject` and answers 200 with the bytes, `Content-Type: image/webp`, `Content-Length`, `Content-Disposition: inline; filename="thumbnail.webp"`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: private, max-age=3600`. The content type is fixed by the route and not read from storage, and the bytes are those that `makeThumbnail` made (a new image, not the upload), so the rule that a file never runs in the browser (D-095) stays true: what the browser draws is never the file the person chose. A `ready` row whose object is missing (a reset of the development bucket) is 404 and one error line with the file id (TOKI-058's own note on resets). The route writes no row and no event, and logs no name and no address. Check: a member of a public channel, a private channel, a DM and a group gets 200 and the bytes decode as WebP of the stored sizes; every 404 case above with one body, including an unknown id, a `removed` row, a `pending`, a `none`, an upper-case id, a non-member of a public channel, an Admin outside a private channel and a person removed from a private channel on the next request; an unsent `ready` thumbnail opens for its uploader and is 404 for a member of the conversation; an archived channel's thumbnail opens for a member; a file whose message was deleted is 404 (TOKI-058 R17); a request with no session is 401 with no read; the headers are exactly those above (the cache header read back); a test shows the open route and this route are given the same function and the table of TOKI-058 R12 passes through both.
- R9. Two methods are added to `ObjectStore` of TOKI-058 R5, one implementation in `store.ts` and one in the fake. `getObject(key): Promise<{ body: Readable; size: number } | null>` (null when there is no object; the body is a stream, never a whole file in memory) and `putObject({ key, body, contentType })` which writes one object of at most 5 MB in one request and stores it with `Content-Type: application/octet-stream` and `Content-Disposition: attachment` like every object of the bucket (TOKI-058 R7, R13), whatever `contentType` the caller names (the caller's value is not stored; the route of R8 fixes the type it answers with). The thumbnail is written with `contentType` `image/webp` only so the fake can record what was asked. A body above 5 MB is refused before any request. The S3 implementation is in `store.ts`, the only file that imports the SDK; no route or job imports the SDK. Check: a unit test of the fake against the interface; against MinIO (TOKI-058 R20): a put of a thumbnail and a get return equal bytes and the size; a get of a missing key is null; the stored object has the two headers above and not `image/webp`; a put of 5 MB passes and of 5 MB + 1 is refused with no request; `deletePrefix("files/<id>/")` removes the thumbnail with the original (the cleanup of TOKI-058 R18 then leaves nothing under the prefix).
- R10. The message learns that the thumbnail is ready through the contract of TOKI-036 ("The event contract"): the worker writes no event; it calls `recordChange`. `Change` of `conversations/changes.ts` gains the type `thumbnail_updated` and the optional fields `fileId`, `messageId`, `parentId` and `thumbnail` (the shapes of R2). The call has `actorId` = the uploader of the file (the person whose files these are; the field cannot be empty and no person did something now), `conversationId` of the file, `userIds` empty, `at` = `context.clock.now()` and the four fields; `messageId` and `parentId` come from the `attachments` row of the file and its message (`parentId` is the root of a reply, `null` for the main list). The `recordChange` that the worker uses is the same one the server uses: it is built by `buildChangeHandlers` of TOKI-064 R17, so the handler list is the same in both processes. The event handler of TOKI-038 gains one row (as TOKI-038 "Rows of later tickets" says each ticket does): `thumbnail_updated` writes `message.thumbnail_updated`, scope `conversation`, with `data` = `ThumbnailUpdatedData` (R2), one event for one call; `EventChange` gains the four optional fields; the kind and its schema go to the registry of `packages/shared/src/realtime/events.ts` and a row to `kinds.ts` (no change of any map). The line handler of TOKI-037 R16 does nothing for this type and the handler of TOKI-038 writes no extra `message.created`. The event carries the file and its new thumbnail only, not the whole message, so it cannot replace a newer text or newer reactions that the client already holds. A change is made only when the file is attached when the row is updated (R6 e); nothing is recorded for an unsent file, a file of a deleted message or a file that ended `none` before it was sent. Check: with a recording handler standing in for the event handler, a finished thumbnail of an attached file gives one change with the fields of the test and `actorId` the uploader; of an unsent file none; of a file of a reply `parentId` is the root; the worker's change list equals the server's (one builder); with the real handler a `message.thumbnail_updated` event is written with its schema parsed and a number after the counter lock, and a made-up change type still writes nothing; the kind has its row in `kinds.ts` (the test of TOKI-038 R12 fails without it); a change that rolls back leaves no event and no counter step; two connected people of the conversation receive the frame and a person outside it does not.
- R11. The entry carries the thumbnail. `listFiles(db, messageIds)` of TOKI-058 R15 selects `thumb_state`, `thumb_width` and `thumb_height` with the file columns it reads already and builds `thumbnail` as R2 says, in the same one statement for all the ids of the call. A `ready` row gives `{ status: "ready", width, height }`, `pending` gives `{ status: "pending" }` and `none` gives `{ status: "none" }`. The send builds its entry with `listFiles` too (TOKI-058 R15), so a message sent after the thumbnail is ready carries it from the 201 body, the history, the replies, the `message` of the change and the event of `message.created`, and the four bodies are equal. A file that ended `none` shows `none`. The same file is served by the same value to everyone who can read the message. Check: a history page of 50 messages with files costs one extra statement as before (a statement count); the 201 body, the 200 of a repeat, the history item and the `message` of the recorded change are equal for one message with 3 files in the three states; a file made `ready` after the send shows `ready` in the next history page; a message that is deleted has `files: []` (TOKI-058 R15); an entry holds no `url`, no `key` and no byte size (a schema test).
- R12. The client puts the thumbnail into the held message, in `packages/client-core/src/messages/thumbnails.ts`. It exports `applyThumbnail(message, fileId, thumbnail)` (pure: the message with the one file's `thumbnail` replaced, the same object when nothing changes, the same result when applied twice), `mergeFileThumbnails(held, incoming)` (pure: the `files` of `incoming` where, for a file that `held` has, a `ready` or `none` thumbnail of `held` is kept when the `incoming` one is `pending`; every other key comes from `incoming`), and `createThumbnailHandlers({ sync })`, built once in `apps/web/src/client.ts` after `sync` as `createMessageActions` of TOKI-047 R15 is, which registers through `sync.registerEventHandler` (TOKI-040 R18: several handlers for one kind, run in the order registered) one handler for `message.thumbnail_updated`. The handler parses `data` with `ThumbnailUpdatedData` (an unparsable one is dropped and logged once, and does not stop the other handlers) and calls `tools.patchMessage(conversationId, messageId, held => applyThumbnail(held, fileId, thumbnail), parentId)`, so a message held in a main window, or a reply held in a thread window (TOKI-045, by `parentId`), changes and a message that is not held changes nothing. A `pending` thumbnail never replaces a `ready` or `none` one: no event carries `pending` (R2) and `mergeFileThumbnails` covers a page that was requested before the event and answered after it. No text is added: the placeholder, its proportions and the image are TOKI-062's. Check: a table test of `applyThumbnail` and `mergeFileThumbnails` over (held, incoming) pairs, among them `ready` held and `pending` incoming (kept), `pending` held and `ready` incoming (taken), a file the held message does not have, and an unrelated key that comes from `incoming`; an event for a held message changes only that file and calls the listener of the window once; an event for an unheld message changes nothing; an event for a reply held in a thread window changes it by `parentId`; applying the event twice leaves the window `===` the second time; a handler registered next to another for `message.edited` is not disturbed; a bad `data` is dropped without throwing.
- R13. ## Design
### How a thumbnail goes
```
 composer        server (Fastify)                 queue / worker                      MinIO
    |-- POST /files/{id}/complete -->|  row `ready`, thumb_state `pending`, job queued (one transaction)
    |<-- 200 file.thumbnail pending -|
    |                                |     worker: files.thumbnail { fileId }
    |                                |       read original ----------------------------------->|  stream
    |                                |       makeThumbnail (format, pixels, upright, 640, WebP)
    |                                |       write files/<id>/thumb.webp -------------------->|
    |                                |       UPDATE files ... ready (one transaction)
    |                                |       attached? -> recordChange -> message.thumbnail_updated
    |-- POST /conversations/{id}/messages { attachmentIds } -->|  entry carries `thumbnail` (ready, or pending)
    |<-- event message.thumbnail_updated  (only when the file was already in a message) ---|
    |-- GET /files/{id}/thumbnail ->|  session, may read the conversation
    |<-- 200 image/webp, private, 1 hour ---------------------|
```
Both orders are covered. The usual order is the upper one: the picture is made while the person types, and the message carries it. The other order, a send before the worker finishes, is the event. The file row is the one place where the two meet: the worker's update and the send's link both lock the row, so a send either sees the finished thumbnail in its entry or the worker sees the file attached and sends the event, never neither (R6 e, R11).

### Choices made here
- **The job starts at `complete`, not at the send** (concern 4). Work that starts when the upload finishes runs while the person types, so for most messages there is nothing to wait for and no second event. The cost is a thumbnail for an image that is never sent: at most 20 unsent files per person exist (TOKI-058 R9), each is removed after at most 24 hours with its thumbnail (TOKI-058 R18), and the work of one is a fraction of a second, so the waste has a bound. The start is in the same transaction as the state change, so a file that is `ready` and an image always has its job (R3).
- **A narrow event, not the whole message** (concern 4). The events of edit, delete and pin carry the entry and the client chooses the fresher copy by `editedAt` (TOKI-047 R14). A thumbnail does not change `editedAt`, so a whole entry would look equal in age to the held one and could put back an older text or older reactions. A patch of one file is applied the same way twice (TOKI-040 R18) and can only move a thumbnail from `pending` to its final state.
- **The server draws the picture, the browser draws the server's picture** (concern 6). The upload stays opaque and downloaded (D-095). What the browser draws is a WebP that the worker made: new pixels, no metadata, a type fixed by the route. A hostile file cannot reach the browser as the thumbnail, only as a download.
- **Through the server, not a signed address** (concern 6). A signed address changes at every request and carries `attachment`, so the browser could not cache it and, with the headers of TOKI-058 R13, may not draw it. The thumbnail is small (a few tens of kilobytes at 640 pixels), so the route streams it and lets the browser keep it for an hour: a message list that scrolls does not ask for the same picture again.
- **WebP at 640 pixels, no metadata** (concern 3). The prototype's image box is 300 pixels wide (`.imgph`: `width: min(300px, 100%)`, `aspect-ratio: 4/3`) and its viewer is up to 520 wide (`.imgph.big`). 640 covers the box at twice the density with room to spare. WebP draws in the last two versions of Chrome, Edge, Safari and Firefox (NFR-14 of the requirements names those browsers), keeps transparency and is smaller than JPEG at the same look. Dropping the metadata removes the place and the camera of a photo (the original keeps them; the person chose to share it, not to share it as a picture on a list).
- **One library, one file** (concern 5). `sharp` (libvips) decodes JPEG, PNG, GIF, WebP and AVIF, reads the size from the header, limits the pixels, streams, applies the orientation and writes WebP; it is the common choice for Node and is fast. Pure-JavaScript decoders are slow and have no AVIF or WebP encoder; an external converter (ImageMagick) would add a process and a policy file. The cost is native code per platform (concern 5). `image.ts` is the only file that knows it, like `store.ts` and the SDK, so a different library is one file.
- **An unreadable image is a normal end** (R6 b). A person can send any file with an `image/` label. The job ends `none` and the file shows as a file card with a download; it is not a retry and not a dead job. Only a failure that has nothing to do with the image is retried and, after the last attempt, lands in `jobs.dead` for the operator.
- **The sweep exists because a placeholder that never ends is worse than none** (concern 9). A lost job or a worker that was down for an hour must not leave `pending` on a screen. One recurring job closes every `pending` row after 30 minutes.
- **No new table.** Three columns of `files` hold the result (R1). The key is derived, like the key of the original.

### The state of a thumbnail
| `thumb_state` | Meaning | Set by |
| :---- | :---- | :---- |
| `none` | no thumbnail: not an image, a format the server does not draw, too many pixels, unreadable, failed for good | `complete` (not `image/`), the worker (R6), the sweep |
| `pending` | the image is complete and its job has not finished | `complete` (R3) |
| `ready` | `files/<id>/thumb.webp` exists and has the sizes | the worker (R6) |

`pending` goes to `ready` or `none`, and nothing goes back to `pending`. The entry shows the same three words. Only `ready` has sizes.

### Errors
- The decoder cannot read the image, the format is not in the list or the picture is too large -> `none`, the job completes, one log line (R6 b).
- Storage or the database fails -> the job is retried (TOKI-064 R8); after the fourth attempt the row is `none` and the job is in `jobs.dead` (R6 c).
- The queue cannot take the job at `complete` -> the transaction rolls back and the answer is 500; the client's next `complete` repeats it (R3).
- The object is missing when the route serves it -> 404 and one error line (R8).
- The worker is down -> `pending` stays until the worker returns or the sweep closes the row; messages and uploads are not affected.

## Data safety
- The worker decodes bytes that a person chose. Limits: the format is read from the content and only five formats are decoded (R5 a); the pixel count is read from the header and capped at 50,000,000 before anything is decoded (b); the stream is read once and destroyed when the format is refused; two jobs run at a time (R4); a job has 120 seconds (R4); the library cache is off. The decoder runs only in the worker process, never in the process that answers requests, so a crash or a stall of a decoder does not take the API down.
- A thumbnail carries no metadata (R5 g), so a photo shared as a picture does not publish its place or its camera.
- A thumbnail is readable only through R8, by the rule of the file: a member who can read the conversation, or the uploader of an unsent file. The answer for everyone else is the 404 of the open route, so nothing confirms that a file exists.
- What the browser draws is the worker's output with a fixed type and `nosniff`, a sandboxed content-security header and a cross-origin policy (R8); the uploaded bytes are still served only as a download (TOKI-058 R13).
- File names are data: never in a key, a log line or an error (R4, R14). The key is derived from the id.
- A removed file loses its thumbnail with everything under `files/<id>/` (TOKI-058 R18), and a thumbnail that is written after the file was removed is deleted by the worker (R6 d). No object stays that no row owns.
- The browser may keep a thumbnail for an hour. A person removed from a private channel keeps a copy that their own browser already held for up to that hour and gets nothing new (concern 6).

## Areas of concern
1. What counts as an image. The log says the previews include image thumbnails (D-014) and that "Documents" in the Files page is every file that is not an image, and does not say which formats are images. Proposal, not a decision: JPEG, PNG, GIF (the first frame), WebP and AVIF are images and get a thumbnail; SVG, HEIC, TIFF, BMP and every other type are files, shown as a file card with a download and listed under Documents. Reason: those five are what a browser draws and what the library reads from a stream with limits; SVG is a document that can hold scripts and links and the server would have to render it (D-095 says files are never opened in the page); HEIC needs a decoder that the prebuilt library does not include, and a phone usually gives a JPEG to a browser. If the owner wants HEIC or TIFF, the set is one constant (`THUMBNAIL_INPUT_FORMATS`) and the library build, and the proportions of the cost are in concern 5. Not decided. Owner: Thanh Truong (product owner).
2. The proportions of the placeholder before the thumbnail is ready. F18 says the placeholder has the right proportions so the layout does not jump. The server knows the size of an image only after the worker has read it, and the job starts when the upload finishes, so in the usual case the size is known before the message exists. When a message is sent before the worker has finished, the entry says `pending` with no size, and this spec gives the screen only what it knows: the prototype's box (`.imgph`, 4 : 3) until the event arrives, and then the real proportions, which can make that one message change height. Proposal A, what R2 builds: accept that single change. Proposal B: the composer reads the size of the picture in the browser and sends it with the start of the upload (two integers on the request of TOKI-058 R6, kept on the row as a hint and replaced by the real size), so a `pending` entry has a size and the layout never jumps; it costs two columns, a request field, a check of the numbers and a change to TOKI-058 and TOKI-059. Not decided. Owner: Thanh Truong (product owner).
3. Size, format and metadata of the thumbnail. Decided in this spec: 640 pixels on the long side, never enlarged, WebP at quality 80 with transparency, the first frame of an animation, the orientation applied and every piece of metadata dropped. Reason: the prototype's image box is 300 pixels wide and its viewer 520; 640 covers the box at twice the density; WebP draws in the browsers of NFR-14 and keeps alpha; the original keeps its metadata. The numbers are constants of `packages/shared` (R2): another value changes one constant and its tests. Owner: Thanh Truong.
4. When the job starts and how the message is told. Decided in this spec: the job is queued by `complete`, in the transaction that makes the file `ready`, so it runs while the person types; the message carries a finished thumbnail in its entry, and a late one is told by one narrow event, `message.thumbnail_updated`, through `recordChange` as TOKI-036 requires. Reason: no second event for the usual message, no work for an image that is dropped before it is complete, and a patch of one file cannot put back older text or reactions (Design). The alternative, queueing at the send, works for the plan's wording but makes every image message show a placeholder first. The cost is a thumbnail for an image that is never sent, bounded by the cap of 20 unsent files and the 24-hour removal (TOKI-058 R9, R18). Owner: Thanh Truong.
5. Reading images safely, and the library. Decided in this spec: `sharp` behind one file, in the worker process only, with the limits of R4 and R5 (five formats read from the content, 50,000,000 pixels, 120 seconds, two jobs at a time, no cache). Reason: it reads the size from the header, limits pixels, streams, applies the orientation and writes WebP, and it is fast; the alternatives are slower or add a process (Design). It departs from a sentence of TOKI-058 (uploaded content is never read by the server): the worker reads images to make the thumbnail, which D-014 requires. Owner: Thanh Truong.
6. How the browser gets a thumbnail. Decided in this spec: the route `GET /api/v1/files/{id}/thumbnail`, which streams the WebP through the server by the rule of the file and answers 404 to everyone else, with `Cache-Control: private, max-age=3600` and a fixed type. Reason: a signed address changes each time and carries `attachment`, so the browser could neither cache nor draw it; the thumbnail is small. The cost is that a thumbnail that was fetched is kept for up to an hour by that browser after the person loses access (a removal from a private channel), and the bytes go through Node; both are small and are the price of caching. The hour is a number of this spec. Owner: Thanh Truong.
7. The large image of the viewer. The journeys say an image opens large (F18). TOKI-062 draws the thumbnail in its window and never the original, because the original cannot be assumed drawable (TOKI-058 R13 leaves the check of an `<img>` on a signed address to a by-hand trial), and it asks this ticket for a preview of at least 1040 pixels on the long edge, twice the 520 pixels of its window. This spec makes the thumbnail 640 pixels (concern 3), which is sharp for the card (300 pixels wide) and soft in the window on a screen at twice the density; the two specs do not yet agree. Proposal, not a decision: the same job also writes a second image of up to 1040 pixels on the long side, `files/<id>/large.webp`, served by the same route with a size parameter, and the window draws it; it costs a second encode, a few hundred kilobytes per image, one more key on the entry and one more route parameter. A single thumbnail of 1040 pixels would also serve both and would make every card in a list about three times heavier than it needs to be. Nothing in this ticket builds either; until the owner decides, the window of TOKI-062 draws the 640-pixel thumbnail. Not decided. Owner: Thanh Truong (product owner), with TOKI-062.

9. A thumbnail that never finishes. Decided in this spec: an image that cannot be read ends `none` at once (R6 b); a failure that is not about the image is retried four times and then ends `none` and in `jobs.dead` (R6 c); a recurring sweep closes any row still `pending` 30 minutes after the upload completed (R7). Reason: a placeholder that never ends is the worst of the three states, and a lost job, a queue emptied by hand or a worker that was down must not leave one. A file that ended `none` has no retry button: it is a download. Owner: Thanh Truong.
