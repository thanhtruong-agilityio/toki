# Message API design

Date: 2026-11-20 · Status: draft for review
Intent: docs/intents/message-api.md (Thanh Truong)
Ticket: TOKI-037

## Goal
A member of a conversation needs to send a message and to read what was written, in a channel, a direct message or a group. Today the server has the conversation tables, the permission functions and the channel and direct-message requests, and (with TOKI-036) the table of messages, but no request stores or returns a message. This work adds the two requests: send, and load history. It also takes the two jobs that earlier specs gave it: the grey system lines that a channel change causes, and the rule that a new direct message stays out of the other person's list until its first message. The server fixes, whatever the screen shows: only a member writes and reads; an archived channel takes no new message; a repeat of a send stores one message; a joiner reads the whole history.

## Scope
- In:
  - Two routes under `/api/v1` (Design, "API"): send a message, and load history in four ways (latest, older, newer, around one message).
  - The send rules: membership, archived channel, read-only direct message, the text limits, the repeat of the same id, the locks that keep a send correct when it meets a leave, an archive or a deactivation.
  - The shape of a message as the API returns it (`MessageEntry`), the limits and the two new error codes, in `packages/shared`.
  - The system-line writer: the grey lines that the changes of TOKI-029 cause, written in the transaction of the change (R16, R17), and the plumbing that lets the newcomer line of #general be written (R17).
  - The rule that hides a new direct message from the other person until its first message, with the field `lastMessageAt` and the event that makes the direct message appear (R19 to R21; decided by the product owner in TOKI-031 concern 1).
  - The seam `recordChange` as the one place where an effect of a message is attached (R10, R18).
  - Server integration tests, including tests with two real connections.
- Out (not now), with the owner:
  - The tables `messages` and the event log, their indexes and the event numbering: TOKI-036. This ticket adds no table, no column and no migration (R24); what it needs from the tables is in Design, "What this ticket needs from TOKI-036".
  - The WebSocket gateway, who listens to which conversation, and what is pushed: TOKI-038. This ticket gives it the changes and the message entry (R10, R18); it opens no socket.
  - Reconnect and the fetching of what was missed by event number: TOKI-039. The routes here load history by position, not by event number.
  - Reactions: TOKI-046. Edit and delete of a message, the "(edited)" label, the deleted line and the deleted-by-admin line: TOKI-047 (this ticket returns the fields it will fill, R15). Pins and the Pinned tab: TOKI-048. Threads, replies and "Also send to channel": TOKI-045 (this ticket sends and lists top-level messages only, R4, R14). Text formatting and links: TOKI-049 (the server stores the text as sent, R4). Mentions and `@channel`: TOKI-050. Drafts: TOKI-051.
  - Files: the files and attachments tables, the signed addresses and the link between a file and a message: TOKI-058, the composer side: TOKI-059. The limit of 10 files per message is held here as a shared constant, and enforced by TOKI-058 where the files are linked (R22, concern 5).
  - The read pointer, unread counts, the New divider and badges: TOKI-053, TOKI-054. Activity items, push and sound: TOKI-065 and the notification work. Search of messages: TOKI-069. Link previews: TOKI-062.
  - The client: the sync engine and the optimistic send (TOKI-040), the message list (TOKI-041), the message component and the text of every system line (TOKI-042), the composer (TOKI-043). The server sends data and codes, never the words of a system line.
  - The routes that create, edit or archive a conversation: TOKI-029 and TOKI-030. This ticket changes none of them, except the one call that its system lines need (R17).

## Requirements
Access and order of checks
- R1. Two routes: `POST /api/v1/conversations/{id}/messages` (send) and `GET /api/v1/conversations/{id}/messages` (history). Both need a valid session (TOKI-022 R24, 401). After it, each route runs these steps in this order: (1) the schemas of the path, query and body (400 `validation_failed`); (2) `getConversationFacts(db, actor.id, id)` of TOKI-028: `null` is 404 `not_found`; a `private_channel`, a `dm` or a `group_dm` of which the actor is not a member is 404 `not_found`, before any permission function runs, so a private conversation is never confirmed (BR-10, D-045); (3) the permission function: `canReadConversation` for history, `canPostInConversation` for send (TOKI-027 R5); (4) for send, the locks of R8, after which the facts are read again and the functions are called again with the locked actor. Unlike the channel routes, the two routes accept the id of a direct message or a group. The actor of steps 1 to 3 is the account of the session; no route compares a role (TOKI-027 R16). Check: a table test sends each case to each route and checks status and code; a request without a session is 401 with no read of conversations.
- R2. A refusal of a permission function is answered by reason: `not_a_member` of a public channel is 403 `forbidden` (a person who has not joined cannot read it, D-116, and cannot write to it, D-077); `channel_archived` is 409 `channel_archived` (send only: reading an archived channel is allowed for a member, TOKI-027 R5); `fact_missing` and `unknown_role` are 500 `internal_error`, logged at error level (TOKI-027, "How the server uses them"). `not_a_member` of a private channel, a DM or a group is 404 `not_found`, which step 2 of R1 has already answered. The error body holds no text of a message and no name. Check: a table test drives each reachable reason through a route, and `fact_missing` and `unknown_role` through a stubbed function (a real request cannot reach them while `users.role` holds only `member` or `admin`, TOKI-019 R9). A positive case for each route in each kind of conversation, so a loader that always refuses fails.

Send
- R3. `POST /api/v1/conversations/{id}/messages` takes `{ "id": string, "text": string }` and answers 201 with `{ "message": MessageEntry }` (R15). The message is stored with the `id` of the request, the conversation of the path, the actor as author, the text as sent, and `created_at` read from the clock of TOKI-008 once for the request; the client sends no time, so a client with a wrong clock cannot place a message in the past or the future. Check: after a send the row holds those values column by column; the answer parses with the response schema; a request that carries a time field is refused by R4.
- R4. Validation of send. The body is strict: a key other than `id` and `text` (`parentId`, `attachmentIds`, `createdAt`, `authorId`) is 400 `validation_failed` and stores nothing; TOKI-045 and TOKI-058 add their keys in their own changes (concern 5). `id` is a lower-case UUID of version 7, made by the client with the generator of `packages/shared` (`createUuidV7Generator`, TOKI-032 concern 11 and TOKI-099): a version-4 id and an upper-case id are 400. `text` is a string of 1 to `MESSAGE_TEXT_MAX` (10,000) code points, counted with `Array.from(text).length` and never `.length` (D-042, FR-09, AC-024); a text of 10,000 characters is accepted and one of 10,001 is refused, with letters and with emoji outside the Basic Multilingual Plane (10,000 emoji accepted, 10,001 refused). A text with no character other than white space (spaces, tabs, line breaks) is 400: nothing is stored and no empty message appears (AC-024, TS-038). A text that contains the character U+0000 is 400, because the database cannot store it and the failure would otherwise be a 500. The text is stored as sent: no trimming, no change of line breaks, no markup is read or removed (TOKI-049 renders; message content is never rendered as raw HTML, technical design). Check: each case; the stored text of a text with leading and trailing spaces and a line break is equal to the sent text; a text of 10,000 code points whose UTF-8 length is over 10,000 bytes is accepted.
- R5. A repeat of a send stores nothing (D-111, technical design: resending the same id returns the stored message). The insert uses `ON CONFLICT (id) DO NOTHING`. When a row of `id` exists, the request is a repeat only when that row is in the conversation of the path, was written by the actor, and is a message (not a system line); the answer is then 200 with `{ "message": MessageEntry }` as the row stands now (edited or deleted since, TOKI-047), and nothing is written and `recordChange` is not called. The text of the request is not compared, because the stored text can have been edited since the first answer, so a retry after an edit gets the answer it lost; a client that sends one id with another text gets the stored message and nothing changes (it makes one id for each press, so that is a client error, not a case to repair). Every other case where a row of `id` exists (another conversation, another author, or a system line) is 409 `message_id_in_use` with no `details`, the same body whatever the row is, so it confirms that the id is taken and nothing about it. A repeat needs only the right to read the conversation: it is answered before the post rule of R6, so a retry that arrives after the channel was archived still gets its stored message (200), and one that arrives after the person left gets 403 or 404 like any non-member. Check: the same body twice gives one row, one `recordChange` call and the answers 201 then 200; the same id with another text gives 200 and the first text; the same body after an edit of the row (set by SQL) gives 200 with the edited text; the same id in another conversation and from another author each give 409 `message_id_in_use`; a retry after the channel was archived (set by SQL) gives 200; a retry by a person who left gives 403 in a public channel and 404 in a private one; with two real connections, two requests with one id and one body at the same moment leave one row and answer one 201 and one 200, and two requests with one id from two members leave one row, one 201 and one 409.
- R6. Who may send. After step 2 of R1, `canPostInConversation(actor, conv)` decides (TOKI-027 R5): a member of a conversation that is not archived may send, a Member and an Admin alike; an Admin who is not a member of a private channel or a DM gets 404 and has no extra right (D-047). An archived channel is 409 `channel_archived` for every member, an Admin included (F26, BR-11). A person who is not a member of a public channel gets 403 `forbidden`: the send is refused whatever the screen showed (TS-039), and after the person joins, the same request works (TS-040). Check: a member of a public, a private channel, a DM and a group sends (201); a non-member of a public channel gets 403 and no row; an Admin who is not in a private channel gets 404; an archived channel gets 409 for a Member and for an Admin; a person who joined after a refusal then sends; each refusal leaves the table of messages unchanged.
- R7. A direct message with a deactivated person is read-only (F25, F41, D-091). When the conversation is a `dm` and the other person has status `deactivated`, a send is 409 `conversation_read_only` with no `details`, and nothing is stored; a repeat of R5 is still answered. A group is not read-only when one of its members is deactivated, and a send into it works for the others (TOKI-030 concern 1, decided by the product owner on 2026-11-19). The other person's id comes from `listMemberIds` of TOKI-028 (the members of a direct message never change, TOKI-028 R21) and their status from the injected `getAccountsByIds` read inside the lock of R8, so a person who is deactivated while the request waits is seen. A direct message whose other person is Active again sends again. Reading the history of such a direct message stays allowed. Check: a DM whose other person is deactivated (row update by SQL) refuses a send with 409 `conversation_read_only` and stores nothing, and its history loads; after reactivation the send works; a group of three in which one person is deactivated accepts a send; with two real connections, a deactivation that holds the person's row while a send into their DM waits gives 409 after it commits.
- R8. Locks (the order of TOKI-024 R39, which TOKI-029 R15 and TOKI-030 R22 follow). A send runs in one transaction: (1) `getAccountsByIds(tx, ids, { lock: "share" })` for the actor and, in a direct message, the other person, in id order in one statement; the actor's status comes from this read, so a deactivated actor gets 401 `account_deactivated`, and the permission function is called again with the locked role (R1 step 4); (2) the conversation row, `SELECT ... FOR SHARE` for a channel and a group, `FOR NO KEY UPDATE` for a `dm` (concern 8), before any member row or message row is read or written; (3) the facts are read again and R6, R7 are checked again; a result that differs from the first is answered by R2. `FOR SHARE` on the conversation row excludes a leave, an archive and a removal (they take `FOR NO KEY UPDATE`, TOKI-029 R15), so a message is never stored after the archive committed or by a person whose member row is already deleted, and it does not exclude another send, so sends into one channel do not wait on each other. It does not conflict with the `FOR KEY SHARE` that the member row of a newcomer takes when `addMemberToGeneral` runs, nor with the `FOR KEY SHARE` that the message row takes on the conversation row. Reading history takes no lock and runs in one statement per page. Check with two real connections, the second waiting and the result checked after the first commits, never by sleeping: a send and an archive at the same moment end either with the message stored in the still active channel before the archive, or with the send refused 409; a send and the leave of the same person end with the message stored (leave second) or with the send refused (leave first), never with a message by a person who has no member row after both; a Member whose account is deactivated while the send waits gets 401; two sends and a join of #general by `addMemberToGeneral` finish without a deadlock; the isolation level read back inside the transaction is `read committed`.
- R9. The order of messages and the clock. Messages are ordered by `created_at` and then by `id` (concern 4). `created_at` is the time at which the server handled the send, so a message sent from a queue after a reconnect is placed at the time it arrived, as the person sees it (D-097). Check: with the controllable clock, three sends at three times load in that order whatever the order of their ids; two sends at the same clock time load in the order of their ids; a message whose UUIDv7 time part is one year in the past is placed at the clock time, not by its id.
- R10. The effect seam. A send that stores a message calls `recordChange(tx, change)` of `modules/conversations/changes.ts` once, inside its transaction, after the insert and before the commit, with `type: "message_created"`, the actor, the conversation id, the people affected (the members of the conversation, read with `listMemberIds`), the time and the `MessageEntry` of the stored message in the field `message`. It writes no event and pushes nothing: the event rows are written behind `recordChange` by the work of TOKI-036 and TOKI-038, and the push of what was written is the gateway's (Design, "Lines with TOKI-036 and TOKI-038"). A repeat and every refusal call it zero times. When the send is the first message of a `dm` the call of R20 follows. Check: a spy counts one call per stored message, two for the first message of a `dm`, none per repeat and per refusal; the calls are inside the transaction (a rollback after them leaves no message); a failing `recordChange` leaves no message and the answer is 500.

History
- R11. `GET /api/v1/conversations/{id}/messages` takes `limit` (1 to `MESSAGE_PAGE_MAX`, default `MESSAGE_PAGE_DEFAULT`; the values are concern 1) and at most one of `before`, `after` and `around`, each the id of a message (a lower-case UUID); two of them, a value outside these and a key other than these four are 400 `validation_failed`. It answers 200 with `{ "messages": MessageEntry[], "hasOlder": boolean, "hasNewer": boolean }`, the messages in ascending order (R9, oldest first). With none of the three, it returns the newest messages (`hasNewer` is false). `before` returns the messages older than that message, the newest of them last; `after` returns the messages newer than that message, the oldest of them first; the message named is not in the answer. `around` returns the message named and the messages on both sides (R13). A message id that is not a row of this conversation (another conversation, or no row; a system line is a valid anchor) is 404 `not_found` with the same body as for an unknown conversation. `hasOlder` and `hasNewer` say whether a message exists beyond the first and the last of the answer, so the client knows when to stop loading. Check: a conversation of 120 messages read in pages of 50 backwards with `before` gives every message once and ends with `hasOlder` false; the same forwards with `after`; the latest page holds the newest `limit`; an empty conversation answers an empty list with both flags false; two cursors, an unknown key, `limit` 0 and `limit` one above the maximum are 400; a cursor of another conversation and a cursor with no row are 404.
- R12. Paging is exact. The query compares the pair (`created_at`, `id`) of the anchor message with the pair of the rows, so a page never repeats or skips a message when several share a `created_at`, and `hasOlder` and `hasNewer` come from reading one row more than the limit. A message that commits after a page was read is not in that page; the client gets it by event (TOKI-038, TOKI-039). Check: 30 messages with the same `created_at` and ids in any order are read in pages of 7 in both directions and each message appears once, in the order of R9; a message inserted between two page requests is seen by the next request that reaches its place and is never duplicated.
- R13. `around` returns the message named, then up to `floor((limit - 1) / 2)` older messages and up to `ceil((limit - 1) / 2)` newer ones, in one answer, with `hasOlder` and `hasNewer` computed for the two ends. It is the request for a jump to a message (TOKI-068) and for opening a conversation at a place (TOKI-041, TOKI-054). The two sides are not redistributed when one is short; the client loads more with `before` and `after`. Check: with limit 5, a message in the middle of 20 returns 2 older and 2 newer; the oldest message returns itself and 2 newer with `hasOlder` false; the newest returns itself and 2 older with `hasNewer` false; with limit 4 a middle message returns 1 older and 2 newer.
- R14. What history holds. For a person who may read the conversation (`canReadConversation`, TOKI-027 R5: a member of any kind of conversation, an archived channel included), every top-level message of the conversation since its first, however long ago: a joiner and a person added later read the whole history because no code and no column limits it (D-029, D-116, FR-20; TS-080 is a test of this ticket). Replies of a thread (rows that have a parent, TOKI-045) are not in the list: only messages of the main list are (FR-33). System lines (R16) are in it, in their place by time. A deleted message stays in the list as a row with no text (TOKI-047 fills the state; this ticket returns it as the table holds it, R15). A person who left or was removed has no member row and reads nothing; a person who is not a member of a public channel gets 403 and of a private one 404 (R2), so there is no preview (D-116, TS-083). Check: a member added to a channel after 40 messages reads all 40 (TS-080); a person who left gets 403 or 404; a thread reply inserted by SQL is not in the list and a system line is; an archived channel's history loads for a member and is refused to a non-member; an Admin who is not a member of a private channel gets 404.
- R15. `MessageEntry` is one strict Zod object in `packages/shared`, exported from the package index, with these keys and no other: `id`, `conversationId`, `kind` (`"user"` or `"system"`), `authorId` (the author of a user message, the person who acted for a system line), `text` (a string for a user message, `null` for a system line and for a deleted message), `system` (`null` for a user message, `{ "type": string, "userIds": string[] }` for a system line, R16), `createdAt` (ISO 8601 UTC), `editedAt` (`null` or ISO 8601) and `deletedAt` (`null` or ISO 8601). `editedAt` and `deletedAt` are read from the table and are always `null` until TOKI-047 writes them; TOKI-045, TOKI-046, TOKI-048 and TOKI-058 add their own keys to the entry in their own changes (reply count, reactions, pinned, files), each with its tests, so the keys of other work are not guessed here. The server and its tests use the strict schema; the client of TOKI-032 derives a form that drops unknown keys (TOKI-032 R3). The response schemas of both routes are exported too. Check: a schema test accepts a user message and a system line and refuses an added key, a missing key, a `kind` of `other`, a non-ISO time and a user message with `system` set; every 200 and 201 body of the route tests is parsed with the response schema.

System lines
- R16. The system lines. A change of TOKI-029 that is effective writes one message row of `kind` `system` in the conversation, in the transaction of the change, through `recordChange` (R18), with the id made by the server (UUIDv7), the person who acted as author, `created_at` equal to the time of the change, `system.type` and `system.userIds` as follows. `channel_created` writes `channel_created` (userIds: the first members); `member_joined` writes `member_joined` (the person); `members_added` writes `members_added` (the people added); `member_left` writes `member_left` (the person); a topic edit writes `topic_changed` (no people). These five come from the journeys F20, F21, F22, F23 and F24 (the baseline accepted in D-091); their wording is the client's (TOKI-042). The server sends no wording. A system line is never counted as unread and notifies nobody: its `kind` is how the read pointer and the notification work tell it apart (D-100, TOKI-053); this ticket counts and notifies nothing. The changes `member_removed`, `channel_archived`, `channel_restored`, `settings_changed` and a change of the description only write no line in this ticket, because no journey gives them one (concern 3, undecided). A request that changes nothing writes no line (TOKI-029 R16: zero calls). A leave that empties a private channel writes `member_left` and no line for the archive. `Change` gains the optional field `fields` (`["topic"]`, `["description"]` or both) set by the edit route of TOKI-029, so the writer knows what changed; that is the only change this ticket makes to a route of TOKI-029 (concern 12). Check: for each of the five changes, a real request of TOKI-029 leaves one system line with the type, author and people above; a restore by an Admin who is not a member leaves a `member_joined` line and no line for the restore; an edit of the description only leaves no line (until concern 3 is decided); a repeat or `changed: false` leaves none; a rollback after the line leaves none; the lines are in the history in order of time.
- R17. A newcomer in #general (D-100, F03: "Minh joined", no notification). `addMemberToGeneral(tx, input)` of TOKI-028 R26 takes an optional `recordChange` in `input`; when it adds the row (it returns `true`) it calls it with `member_joined`, the newcomer as actor and as the only person, and the time `createdAt`; when it returns `false` it calls it zero times. `acceptInvitation` of TOKI-024 passes the `recordChange` of the app, which the `members` module receives from `apps/server/src/app.ts` like it receives its other dependencies, so the `members` module imports no file of `messages` and `conversations`. `createGeneralChannel` (the first Admin) writes no line (concern 3). Check: accepting an invitation leaves one `member_joined` line in #general by the newcomer, in the transaction of the accept (a rollback of the accept leaves none); accepting again leaves one; the existing tests of TOKI-024 and TOKI-028 pass with the default `recordChange`; the first Admin's set-up leaves no line.
- R18. Modules and wiring. The `messages` module (`apps/server/src/modules/messages/`) owns the routes and the writer; it imports the `conversations` module (`getConversationFacts`, `listMemberIds`) and receives `getAccountsByIds` from outside; the `conversations` module imports nothing of `messages`, so there is no cycle (the rule of TOKI-029 R18). `recordChange` in `changes.ts` is built from a list of handlers run in order inside the caller's transaction: first the system-line writer of this ticket (it sets `change.message` when it writes a line), then the handlers that TOKI-038 adds (events). `apps/server/src/app.ts` composes the list and passes the one `recordChange` to `channelRoutes`, `directRoutes`, `messageRoutes` and `members` (the `channelDeps.recordChange` seam already exists for tests). `messageRoutes({ db, clock, getAccountsByIds, recordChange })` is exported from `modules/messages/index.ts` and registered in `apps/server/src/app.ts`. Check: `pnpm lint` exits 0; a test starts the app through `buildApp` with the real wiring and finds the two routes registered; a test that makes a handler throw shows the whole change rolled back; the export test lists the new names.

Hidden direct message
- R19. A new direct message stays out of the other person's list until its first message (F25, D-091; TOKI-031 concern 1). `listConversationSummaries(tx, workspaceId, userId)` returns a conversation of kind `dm` to `userId` only when `userId` is its `created_by` or the conversation has at least one message (any row of `messages`, a user message; a `dm` has no system line). A channel and a group are not filtered (concern 2). The bootstrap answer and the answer of `POST /api/v1/direct-conversations` gain the key `lastMessageAt` on every `dm` and `group_dm` entry: the `created_at` of the newest message of the conversation as ISO 8601 UTC, or `null` when it has none; `DirectConversationEntrySchema` (`packages/shared/src/direct-conversations.ts`) gains the key, so the strict entry has eleven keys and the tests of TOKI-030 R17 and R18 and of TOKI-031 R2, R7 and R17 are updated in this ticket's change. The two reads are in one statement each and the statement count of TOKI-031 R14 does not grow. A person who is not the creator and who opens the direct message with `POST /api/v1/direct-conversations` gets it (200) and sends in it, but a reload of the bootstrap call does not list it for them until its first message. Check: a DM opened by `a` is listed for `a` and not for `b`; after `a` or `b` sends, it is listed for both, with `lastMessageAt` equal to that message's time; a group opened by `a` is listed for `b` at once; `lastMessageAt` is `null` for a new DM and is the newest message's time afterwards; the opening request returns the key; the statement counts of TOKI-031 R14 are equal for the two fixtures.
- R20. The appearance event. When a send stores the first message of a `dm`, `recordChange` is called a second time, after `message_created`, with `type: "direct_conversation_appeared"`, the sender as actor and, as the people affected, the members of the conversation other than its `created_by` (the people for whom the direct message was hidden). It is called in the same transaction, once, even when two members send their first messages at the same moment, because a `dm` is locked `FOR NO KEY UPDATE` (R8) and the second send finds a message. TOKI-038 turns it into the event that adds the entry to those people's lists (Design, "Lines with TOKI-036 and TOKI-038"). Check: the first message of a DM by its creator calls `direct_conversation_appeared` once with the other person; the first message by the other person calls it with that person (the creator already sees it); the second message calls it zero times; two first messages from two connections at the same moment call it once in all.
- R21. `compareDirect` of `packages/client-core/src/conversations/selectors.ts` orders direct messages and groups by `lastMessageAt`, newest first, and a conversation with `lastMessageAt` `null` after those that have one, by name among them (F09; TOKI-031 concern 1, TOKI-032 concern 10); channels keep their order by name. The store keeps `lastMessageAt` as the server sent it and does not compute it. Check: a selector test with entries whose times are in a different order from their names and with a `null`; the order of channels is unchanged; the parse form of TOKI-032 R3 accepts the new key.

Structure and safety
- R22. `packages/shared/src/messages/` exports the Zod schemas of the two requests and responses (R3, R11, R15), `MESSAGE_TEXT_MAX` (10,000, D-042), `MESSAGE_FILES_MAX` (10, D-042) and `MESSAGE_PAGE_DEFAULT` and `MESSAGE_PAGE_MAX` (the values of concern 1). `MESSAGE_FILES_MAX` is used by no route of this ticket (R4, concern 5): it is exported so that TOKI-058 and TOKI-059 read one number. The registry of error codes gains `message_id_in_use` (409) and `conversation_read_only` (409); `forbidden`, `not_found`, `validation_failed`, `channel_archived`, `account_deactivated` and `internal_error` are reused. Check: schema tests at the boundaries 1, 10,000 and 10,001 characters; the registry has the two codes and no duplicate; a type test imports every name from `@toki/shared`.
- R23. No log line of this work holds the text of a message, or id list of people beyond the usual request line (TOKI-004 R7: no query string). A Postgres error carries the offending value in its detail, so the 500 handler of this work logs the Postgres code and the constraint name only, never the error object or its `detail`, as TOKI-029 R20 does. Check: a forced constraint failure on a send with a known text leaves that text out of the captured log; a send with a text and a request of history leave the text out of the log.
- R24. This ticket adds no table, no column and no migration. It writes only rows of `messages` (user messages and system lines) and, through `recordChange`, whatever the handlers of TOKI-036 and TOKI-038 write; it changes no row of `conversations` and `conversation_members`. It stores no unread count, sends no notification, push or mail, makes no search entry and fetches no link. Check: the migration folder is unchanged; after a send the row counts of every table other than `messages` (and the event table through its handler) are unchanged.
- R25. The routes are in `apps/server/src/modules/messages/` as in Design, "Layout". The `Origin` rule and the media-type rule of TOKI-022 (R45, R46) cover the `POST`: a foreign `Origin` is 403 `origin_not_allowed`, a body that is not `application/json` is 415. A send with no body is 400 `validation_failed`. Check: each case.

## Design
### API
All routes need a session (R1). Bodies are JSON.

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/conversations/{id}/messages` | members, a conversation that is not archived | Send a message; 201 stored, 200 the same id again (R3 to R8) |
| GET | `/api/v1/conversations/{id}/messages` | members, any state | Latest messages, or `before`, `after`, `around` a message (R11 to R14) |

Outcomes common to the routes (the error format is TOKI-004's; a client acts on `error.code`, D-131):

| Status | `error.code` | When |
|---|---|---|
| 200 / 201 | none | Stored message returned (200: the same id again, R5); a page of history |
| 400 | `validation_failed` | A path, query or body fails its schema, including 10,001 characters, only white space and U+0000 (R4, R11) |
| 401 | as TOKI-022 (`account_deactivated` when the locked sender was deactivated) | No valid session |
| 403 | `forbidden` | A person who is not a member of a public channel (R2) |
| 404 | `not_found` | Unknown conversation; a private channel, DM or group the person is not in; a message id that is not in the conversation (R1, R11) |
| 409 | `channel_archived` | Send into an archived channel |
| 409 | `conversation_read_only` | Send into a DM with a deactivated person (R7) |
| 409 | `message_id_in_use` | The id belongs to another message (R5) |
| 500 | `internal_error` | A server failure, or `fact_missing` or `unknown_role` from a function |

A 409 means the screen was out of date; the client reloads the conversation (D-131). A request with no answer after 10 seconds counts as failed on the client (D-126) and is sent again with the same id, which R5 makes safe.

### Decisions in the flow of a request
- The id is made by the client (UUIDv7), so the optimistic message and the stored one are the same message and a retry cannot duplicate it (technical design). The server checks only the shape and that the id is free or its own.
- A send answers 201 for a new message and 200 for a repeat, with the same body, as TOKI-030 does for a direct message; a client treats both as "stored".
- History is read by position (a message id) and not by an opaque cursor, so the same request serves "load older", "load newer" and "jump to this message" (TOKI-068), and the flags say when to stop.
- Reading history changes nothing: no read pointer moves (TOKI-053) and no unread count changes.

### Lines with TOKI-036 and TOKI-038
Written from this side; each line is read again against the two specs at the end.
- Message ids: client-made for user messages (R4); server-made UUIDv7 for system lines (R16). TOKI-036's table takes both, with no database default needed for a message.
- Event emission: one seam, `recordChange(tx, change)`. This ticket calls it with `message_created` (R10), `direct_conversation_appeared` (R20) and the changes of TOKI-029, and its system-line handler runs first and sets `change.message`, so that an event for a change that caused a line also carries the line (the line is a new message of the conversation: clients must receive it). TOKI-036 owns the event table, the numbering and its two conditions (written in the same transaction as the change; no gap that a transaction in flight can fill, TOKI-031 R11); TOKI-038 adds the handler that writes the events and the push. This ticket writes no event row and allocates no number.
- What the gateway pushes: the events written for the changes above, to the members of the conversation (`userIds`, with the members read by `listMemberIds`), after the commit. The payload of `message_created` is the `MessageEntry` of R15, so one shape serves the list and the event. For `direct_conversation_appeared` the payload is the `DirectConversationEntry` of R19, for each person, with their own level, mute and star.
- What this ticket needs from the tables of TOKI-036 (names are what this spec assumes; a different name changes the code and no requirement): table `messages` with `id` (uuid primary key, no version check), `workspace_id`, `conversation_id`, `author_id`, `kind` (`user` or `system`), `system_type`, `system_user_ids`, `parent_id` (null for a top-level message), `body`, `created_at`, `edited_at`, `deleted_at`; a unique primary key on `id`; an index on (`conversation_id`, `created_at`, `id`) for R12, whose order is the one of R9; a foreign key to `conversations` and to `users` with `ON DELETE RESTRICT`; no delete of a message row by this ticket.

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- Order by `created_at` then `id`, not by `id` alone, because the client makes the id and its time part is the client's clock (concern 4).
- Position cursors (a message id) and two flags, not `nextCursor` (above).
- `FOR SHARE` on the conversation row for a send, `FOR NO KEY UPDATE` for a `dm` (concern 8).
- A repeat is a read: answered with only the right to read (R5, concern 11).
- The text is counted in code points and stored as sent (R4, concern 9).

## Data safety
- A message is visible to the members of its conversation only. A private channel, a DM and a group answer 404 to anyone else, with the same body as for an id that does not exist (BR-09, BR-10); a public channel answers 403 to a non-member and returns nothing of it, so there is no preview (D-116).
- Every read of history goes through `getConversationFacts` and the permission function, never through a query on messages alone, so a caller cannot read without the check.
- The text is stored as sent and returned as data; the server never builds markup from it.
- The log holds no text, name or id list (R23). A 409 `message_id_in_use` confirms only that a UUIDv7 is taken.
- Tests use made-up texts and generated ids.

## Open questions from the intent
- How many messages does one page of history hold? Not answered. The log has the first 50 and more on scroll for lists of people and channels (D-109), and none for messages. Carried forward as concern 1.
- Does the rule that hides a new direct message until its first message also cover a group? Not answered. TOKI-030 concern 8 leaves it to this spec; F25 words the rule for a DM. Carried forward as concern 2.
- Which channel changes write a system line, and does a change of the description? Answered in part: the five lines of F20 to F24 are written (R16). The description, a removal, an archive and a restore have no line in a journey. Carried forward as concern 3.
- Which ticket stores the files of a message and enforces the limit of 10? Answered: TOKI-058 links and enforces; this ticket ships the constant (R22, concern 5).

## Areas of concern
1. The page size of history. Not decided. The Blueprint plan lists it as open for TOKI-037; the log decides 50 rows and more on scroll for the lists of people and channels (D-109) and nothing for messages. Proposal, not a decision: a default of 50 and a maximum of 100, as for the channel lists of TOKI-029 R6. Until it is answered, the values `MESSAGE_PAGE_DEFAULT` and `MESSAGE_PAGE_MAX` are the ones the owner gives, and every test reads the constants, not a number. The 60 frames per second target for 10,000 messages (the acceptance criteria) is for the list of TOKI-041 and does not depend on this number. Owner: Thanh Truong (product owner).
2. Whether a new group stays out of the other people's lists until its first message. Not decided. F25 says "A DM appears in the other person's list only when the first message is sent" and TOKI-031 concern 1 and TOKI-030 concern 7 name a direct message; TOKI-030 concern 8 says the group case is looked at when this ticket is specified, because a group can put seven people in a conversation they never agreed to. Proposal, not a decision: the rule of R19 covers a `dm` only (the wording of F25), and a group appears at once; extending it to a group is one condition in the read of R19 and one more case in R20. Also noted for the owner: a person who is not the creator and opens a hidden DM does not see it after a reload until its first message (R19). Owner: Thanh Truong (product owner).
3. Which changes write a system line. Not decided for four cases. Written (R16): created, joined, added, left and a topic change, from F20 to F24 and D-100. No journey gives a line to: a change of the description only (F24 says that a change of the topic and description adds a line, and does not say whether the description alone does), the removal of a person by an Admin, the archive and the restore of a channel (F26 gives a strip to the members who have the channel open, not a line), and the first Admin creating #general (no journey). Proposal, not a decision: no line for the four, except that a description change writes the same line as a topic change with the field named; each is one more case of the writer. Owner: Thanh Truong (product owner).
4. The order of messages. Decided in this spec: by the server's `created_at`, then by `id`. Reason: the Blueprint has the client make the message id, so the time inside a UUIDv7 is the client's clock, and an ordering by id would let a wrong clock place a message in the past. The cost: two messages sent in the same millisecond are ordered by their random ids, so the client sends the queue of one conversation one after another and waits for each answer (the sync engine of TOKI-040, D-097 one automatic try). The pagination index of TOKI-036 follows this order. Owner: Thanh Truong.
5. The ten files of a message. Decided in this spec: this ticket ships `MESSAGE_FILES_MAX` and the text rules; the body of a send has no file key, and a key other than `id` and `text` is refused (R4). TOKI-058 owns the tables of files and attachments and so adds `attachmentIds` to the body, enforces the 10 and the rule that a message may then have no text, and adds the files to the entry (R15); TOKI-059 holds the 10 on the screen. Reason: the plan gives this ticket the number but the link needs a table that exists only after TOKI-058; checking ids of files here would test nothing real. The plan line of TOKI-037 ("10 files per message") then reads as the constant. Owner: Thanh Truong.
6. Module layout and the wiring of `recordChange`. Decided in this spec: a `messages` module, the `conversations` module importing nothing of it, and one composed `recordChange` passed from `app.ts` (R18), so that `members` calls it for the newcomer line (R17) and no import cycle is made. The cost is a small change to `addMemberToGeneral` and `acceptInvitation` (TOKI-028 R26, TOKI-024 R20). Owner: Thanh Truong.
7. Where the event of a message is written. Decided in this spec: behind `recordChange`, by the handler of TOKI-038 on the event table of TOKI-036; this ticket calls the seam in the transaction of the message and writes no event (R10, Design, "Lines with TOKI-036 and TOKI-038"). The payload of `message_created` is the `MessageEntry`. If the two other specs draw the line elsewhere (for example the event writer is a function that the send calls directly), only R10 and R18 change. Owner: Thanh Truong.
8. The locks of a send. Decided in this spec: `FOR SHARE` on the account rows and then on the conversation row, so sends do not wait on each other and a send waits for a leave or an archive; `FOR NO KEY UPDATE` for a `dm`, so that the first message of a DM is found by exactly one request (R8, R20). This rests on the lock-mode table of PostgreSQL and the two-connection tests of R8 prove it when built. Owner: Thanh Truong.
9. How text is counted and stored. Decided in this spec: 10,000 code points (D-042 says characters; the topic of TOKI-028 R6 counts the same way); a text with only white space or with U+0000 is refused; the text is stored as sent with no trimming (R4). Whether the composer trims is the composer's. Owner: Thanh Truong.
10. The status for a send into a read-only DM. Decided in this spec: 409 `conversation_read_only`; the refusal itself comes from F41 and TOKI-030 concern 1. The screen shows its own line ('This account has been deactivated', F25); D-131 maps 409 to a fresh copy. If the owner prefers another status only R7 and the table change. Owner: Thanh Truong.
11. What a repeat answers. Decided in this spec: the stored message as it stands, with only the right to read, and 409 `message_id_in_use` for an id that is another message's (R5), as TOKI-029 R5 does for a channel id. Reason: "nothing lost" (D-132) needs a retry after an archive or an edit to return the stored message. Owner: Thanh Truong.
12. Changes that other specs and code need. Decided in this spec: this ticket edits no other spec. As code it changes: `recordChange` and `Change` (TOKI-029 R16; the handler list, `message`, `fields`), the call of `recordChange` by the topic edit route to name its fields (R16), `addMemberToGeneral` and `acceptInvitation` (R17), `listConversationSummaries`, the bootstrap and the opening answer and `DirectConversationEntrySchema` with their tests (R19, TOKI-031 concern 1), and `compareDirect` (R21, TOKI-032 concern 10). What stays a request until its owner edits the text: the plan lines of TOKI-037 (the 10 files, concern 5), TOKI-058 (it adds `attachmentIds`) and TOKI-038 (it handles `message_created` and `direct_conversation_appeared`); TOKI-036 (the columns and the index of Design); TOKI-045, TOKI-046, TOKI-047 and TOKI-048 (their keys on `MessageEntry`, the filter of replies, `editedAt` and `deletedAt`). Owner: Thanh Truong.
