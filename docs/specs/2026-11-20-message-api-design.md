# Message API design

Date: 2026-11-20 · Status: draft for review
Intent: docs/intents/message-api.md (Thanh Truong)
Ticket: TOKI-037

## Goal
A member of a conversation needs to send a message and to read what was written, in a channel, a direct message or a group. Today the server has the conversation tables, the permission functions and the channel and direct-message requests, and (with TOKI-036) the table of messages, but no request stores or returns a message. This work adds the two requests: send, and load history. It also takes the two jobs that earlier specs gave it: the grey system lines that a channel change causes, and the rule that a new direct message stays out of the other person's list until its first message. The server fixes, whatever the screen shows: only a member writes and reads; an archived channel takes no new message; a repeat of a send stores one message; a joiner reads the whole history.

## Scope
- In:
  - Two routes under `/api/v1` (Design, "API"): send a message, and load history in four ways (latest, older, newer, around one message).
  - The send rules: membership, archived channel, read-only direct message, the text limits, the repeat of the same id, the locks that keep a send correct when it meets a leave, an archive or a deactivation.
  - The shape of a message as the API returns it (`MessageEntry`), the limits and the two new error codes, in `packages/shared`.
  - The system-line writer: the grey lines that the changes of TOKI-029 cause, written in the transaction of the change (R16, R17), the plumbing that lets the newcomer line of #general be written (R17), and the one-time command that writes the line of the people who joined #general before the writer existed (R26).
  - The rule that hides a new direct message from the other person until its first message, with the field `lastMessageAt` and the change that makes the direct message appear (R19 to R21; decided by the product owner in TOKI-031 concern 1).
  - The calls to `recordChange` for a sent message and for the reveal of a direct message (`message_created`, `direct_conversation_appeared`, R10, R20), the handler list that `recordChange` becomes and the system-line handler (R16, R18). This ticket writes no event: the events are written by the handler of TOKI-038 through `recordEvent` of TOKI-036 (TOKI-036, Design, "The event contract").
  - Server integration tests, including tests with two real connections.
- Out (not now), with the owner:

  - Reconnect and the fetching of what was missed by event number: TOKI-039. The routes here load history by position, not by event number.
  - Reactions: TOKI-046. Edit and delete of a message, the "(edited)" label, the deleted line and the deleted-by-admin line: TOKI-047 (this ticket returns the fields it will fill, R15). ## Requirements
Access and order of checks
- R1. Two routes: `POST /api/v1/conversations/{id}/messages` (send) and `GET /api/v1/conversations/{id}/messages` (history). Both need a valid session (TOKI-022 R24, 401). After it, each route runs these steps in this order: (1) the schemas of the path, query and body (400 `validation_failed`); (2) `getConversationFacts(db, actor.id, id)` of TOKI-028: `null` is 404 `not_found`; a `private_channel`, a `dm` or a `group_dm` of which the actor is not a member is 404 `not_found`, before any permission function runs, so a private conversation is never confirmed (BR-10, D-045); (3) `canReadConversation` (TOKI-027 R5), for both routes: a person who is not a member of a public channel gets 403 `forbidden`; (4) for send only, the locks of R8, after which the facts are read again and `canReadConversation` is called again with the locked actor; (5) for send only, inside the locks: the lookup of the id of the request (R5); a repeat is answered 200 here and the steps below do not run; (6) for send only, when the id is not a repeat: `canPostInConversation` (R6, TOKI-027 R5) and the read-only rule of a direct message (R7), then the insert. So the post rule runs only for a new message and a repeat needs only the right to read. Unlike the channel routes, the two routes accept the id of a direct message or a group. The actor of steps 1 to 3 is the account of the session; no route compares a role (TOKI-027 R16). Check: a table test sends each case to each route and checks status and code; a request without a session is 401 with no read of conversations; the statement log of a send shows the lock statements before the lookup of the id, and the lookup before the insert.
- R2. A refusal of a permission function is answered by reason: `not_a_member` of a public channel is 403 `forbidden` (a person who has not joined cannot read it, D-116, and cannot write to it, D-077); `channel_archived` is 409 `channel_archived` (send only, a new message only, step 6 of R1: reading an archived channel is allowed for a member, TOKI-027 R5); `fact_missing` and `unknown_role` are 500 `internal_error`, logged at error level (TOKI-027, "How the server uses them"). `not_a_member` of a private channel, a DM or a group is 404 `not_found`, which step 2 of R1 has already answered. The error body holds no text of a message and no name. Check: a table test drives each reachable reason through a route, and `fact_missing` and `unknown_role` through a stubbed function (a real request cannot reach them while `users.role` holds only `member` or `admin`, TOKI-019 R9). A positive case for each route in each kind of conversation, so a loader that always refuses fails.

Send
- R3. `POST /api/v1/conversations/{id}/messages` takes `{ "id": string, "text": string }` and answers 201 with `{ "message": MessageEntry }` (R15). The message is stored with the `id` of the request, the conversation of the path, its workspace (`workspace_id`, not null in TOKI-036 R1), the actor as author, the text as sent, and `created_at` read from the clock of TOKI-008 once for the request; the client sends no time, so a client with a wrong clock cannot place a message in the past or the future. Check: after a send the row holds those values column by column, `workspace_id` included; the answer parses with the response schema; a request that carries a time field is refused by R4.
- R4. Validation of send. The body is strict: a key other than `id` and `text` (`parentId`, `attachmentIds`, `createdAt`, `authorId`) is 400 `validation_failed` and stores nothing; TOKI-045 and TOKI-058 add their keys in their own changes (concern 5). `id` is a lower-case UUID of version 7, made by the client with the generator of `packages/shared` (`createUuidV7Generator`, TOKI-032 concern 11 and TOKI-098): a version-4 id and an upper-case id are 400. `text` is a string of 1 to `MESSAGE_TEXT_MAX` (10,000, TOKI-036 R22) code points, counted with `Array.from(text).length` and never `.length` (D-042, FR-09, AC-024); a text of 10,000 characters is accepted and one of 10,001 is refused, with letters and with emoji outside the Basic Multilingual Plane (10,000 emoji accepted, 10,001 refused). A text with no character other than white space is 400, where white space is what `String.prototype.trim` of JavaScript removes (spaces, tabs, line breaks, U+00A0 and the other Unicode space characters and line terminators; U+200B, the zero-width space, is not white space): nothing is stored and no empty message appears (AC-024, TS-038). A text that contains the character U+0000, or a lone surrogate (`text.isWellFormed()` is false), is 400, because the database cannot store the first and would store the second as U+FFFD, so "stored as sent" would be false; without the refusal the first would be a 500. The text is stored as sent: no trimming, no change of line breaks, no markup is read or removed (TOKI-049 renders; message content is never rendered as raw HTML, technical design). Check: each case; the stored text of a text with leading and trailing spaces and a line break is equal to the sent text; a text of 10,000 code points whose UTF-8 length is over 10,000 bytes is accepted; a text of only U+00A0 and tabs is 400, a text of only U+200B is accepted; a text with a lone surrogate is 400 and stores nothing.
- R5. A repeat of a send stores nothing (D-111, technical design: resending the same id returns the stored message). Inside the lock of R8 (R1 step 5) the send reads the row of `id`; when there is none it goes on (R1 step 6) and inserts with `ON CONFLICT (id) DO NOTHING`, and when that insert returns no row (another request stored the id between the read and the insert) it reads the row and decides as follows. When a row of `id` exists, the request is a repeat only when that row is in the conversation of the path, was written by the actor, and is a message (not a system line); the answer is then 200 with `{ "message": MessageEntry }` as the row stands now (edited or deleted since, TOKI-047), and nothing is written and `recordChange` is not called. The text of the request is not compared, because the stored text can have been edited since the first answer, so a retry after an edit gets the answer it lost; a client that sends one id with another text gets the stored message and nothing changes (it makes one id for each press, so that is a client error, not a case to repair). Every other case where a row of `id` exists (another conversation, another author, or a system line) is 409 `message_id_in_use` with no `details`, the same body whatever the row is, so it confirms that the id is taken and nothing about it. A repeat needs only the right to read the conversation: it is answered before the post rule of R6 and the read-only rule of R7, so a retry that arrives after the channel was archived, or after the other person of a direct message was deactivated, still gets its stored message (200), and one that arrives after the person left gets 403 or 404 like any non-member. Check: the same body twice gives one row, one `recordChange` call and the answers 201 then 200; the same id with another text gives 200 and the first text; the same body after an edit of the row (set by SQL) gives 200 with the edited text; the same id in another conversation and from another author each give 409 `message_id_in_use`; a retry after the channel was archived (set by SQL) gives 200 and a new id in that channel gives 409 `channel_archived`; a retry into a direct message whose other person was deactivated gives 200; a retry by a person who left gives 403 in a public channel and 404 in a private one; with two real connections, two requests with one id and one body at the same moment leave one row and answer one 201 and one 200, and two requests with one id from two members leave one row, one 201 and one 409.
- R6. Who may send. For an id that is not a repeat (step 6 of R1), `canPostInConversation(actor, conv)` decides (TOKI-027 R5): a member of a conversation that is not archived may send, a Member and an Admin alike; an Admin who is not a member of a private channel or a DM gets 404 and has no extra right (D-047). An archived channel is 409 `channel_archived` for every member, an Admin included (F26, BR-11). A person who is not a member of a public channel gets 403 `forbidden`: the send is refused whatever the screen showed (TS-039), and after the person joins, the same request works (TS-040). Check: a member of a public, a private channel, a DM and a group sends (201); a non-member of a public channel gets 403 and no row; an Admin who is not in a private channel gets 404; an archived channel gets 409 for a Member and for an Admin; a person who joined after a refusal then sends; each refusal leaves the table of messages unchanged.
- R7. A direct message with a deactivated person is read-only (F25, F41, D-091). When the conversation is a `dm` and the other person has status `deactivated`, a send is 409 `conversation_read_only` with no `details`, and nothing is stored; a repeat of R5 is still answered. A group is not read-only when one of its members is deactivated, and a send into it works for the others (TOKI-030 concern 1, decided by the product owner on 2026-11-19). The rule runs at step 6 of R1, for a new id only. The other person's id comes from `listMemberIds` of TOKI-028, read before the lock (the members of a direct message never change, TOKI-028 R21, so this one read does not need it), and their status from the injected `getAccountsByIds` read inside the lock of R8, so a person who is deactivated while the request waits is seen. A direct message whose other person is Active again sends again. Reading the history of such a direct message stays allowed. Check: a DM whose other person is deactivated (row update by SQL) refuses a send with 409 `conversation_read_only` and stores nothing, and its history loads; after reactivation the send works; a group of three in which one person is deactivated accepts a send; with two real connections, a deactivation that holds the person's row while a send into their DM waits gives 409 after it commits.
- R8. Locks (the order of TOKI-024 R39, which TOKI-029 R15 and TOKI-030 R22 follow). A send runs in one transaction: (1) `getAccountsByIds(tx, ids, { lock: "share" })` for the actor and, in a direct message, the other person, in id order in one statement; the actor's status comes from this read, so a deactivated actor gets 401 `account_deactivated`, and the permission function is called again with the locked role (R1 step 4); (2) the conversation row, `SELECT ... FOR SHARE` for a channel and a group, `FOR NO KEY UPDATE` for a `dm` (concern 8), before any member row or message row is read or written, except the `listMemberIds` of R7 that finds the other person of a `dm` (a read that cannot change, R7); (3) the facts are read again and `canReadConversation` is checked again, then the lookup of the id (R5), then, for a new id, R6 and R7; a result that differs from the first is answered by R2. `FOR SHARE` on the conversation row excludes a leave, an archive and a removal (they take `FOR NO KEY UPDATE`, TOKI-029 R15), so a message is never stored after the archive committed or by a person whose member row is already deleted, and it does not exclude another send, so sends into one channel do not wait on each other. It does not conflict with the `FOR KEY SHARE` that the member row of a newcomer takes when `addMemberToGeneral` runs, nor with the `FOR KEY SHARE` that the message row takes on the conversation row. Reading history takes no lock and runs in one statement per page. Check with two real connections, the second waiting and the result checked after the first commits, never by sleeping: a send and an archive at the same moment end either with the message stored in the still active channel before the archive, or with the send refused 409; a send and the leave of the same person end with the message stored (leave second) or with the send refused (leave first), never with a message by a person who has no member row after both; a Member whose account is deactivated while the send waits gets 401; two sends and a join of #general by `addMemberToGeneral` finish without a deadlock; the isolation level read back inside the transaction is `read committed`.
- R9. The order of messages and the clock. Messages are ordered by `created_at` and then by `id` (concern 4). `created_at` is the time at which the server handled the send, so a message sent from a queue after a reconnect is placed at the time it arrived, as the person sees it (technical design; the retry after a reconnect is D-097). Check: with the controllable clock, three sends at three times load in that order whatever the order of their ids; two sends at the same clock time load in the order of their ids; a message whose UUIDv7 time part is one year in the past is placed at the clock time, not by its id.
- R10. The event of a message. This ticket writes no event: a send never calls `appendEvent` or `recordEvent`, which are TOKI-036's and are called only by the event handler of TOKI-038 (TOKI-036, Design, "The event contract"). A send that stores a message calls `recordChange(tx, change)` (R18) once, as the last statement of its transaction, after the insert and after every lock, with `type` `message_created`, `actorId` the author, `conversationId`, `userIds` empty, `at` the time of R3 and `message` the `MessageEntry` of R15 for the stored row. The event handler of TOKI-038, last in the list, writes from it the event `message.created` (scope `conversation`, payload `{ message }`); TOKI-038 adds the kind and its schema to its registry and imports `MessageEntry` from `@toki/shared`. A repeat and every refusal call `recordChange` zero times. When the send is the first message of a `dm`, the call of R20 comes first. Check, with a recording handler as the only handler (the real event handler and its events are tested by TOKI-038): one call per stored message with the fields above, and a `message` equal to the 201 body; two calls for the first message of a `dm` (R20); none for a repeat and for a refusal; a statement log shows no write after the call; a handler that throws leaves no message row and the answer is 500; a rollback after the call leaves no row; no file of `messages` imports `realtime` or calls `appendEvent` or `recordEvent` (a grep test).

History
- R11. `GET /api/v1/conversations/{id}/messages` takes `limit` (1 to `MESSAGE_PAGE_MAX`, default `MESSAGE_PAGE_DEFAULT`; the values are concern 1) and at most one of `before`, `after` and `around`, each the id of a message (a lower-case UUID); two of them, a value outside these and a key other than these four are 400 `validation_failed`. It answers 200 with `{ "messages": MessageEntry[], "hasOlder": boolean, "hasNewer": boolean }`, the messages in ascending order (R9, oldest first). With none of the three, it returns the newest messages (`hasNewer` is false). `before` returns the messages older than that message, the newest of them last; `after` returns the messages newer than that message, the oldest of them first; the message named is not in the answer. `around` returns the message named and the messages on both sides (R13). A message id that is not a row of the main list of this conversation (another conversation, no row, or a reply of a thread that is not also sent to the channel; a system line is a valid anchor) is 404 `not_found` with the same body as for an unknown conversation. `hasOlder` and `hasNewer` say whether a message exists beyond the first and the last of the answer, so the client knows when to stop loading; when the answer is empty they are about the anchor: `before` the oldest message gives an empty list with `hasOlder` false and `hasNewer` true, and `after` the newest gives an empty list with `hasNewer` false and `hasOlder` true. Check: a conversation of 120 messages read in pages of a `limit` of 20 backwards with `before` gives every message once and ends with `hasOlder` false; the same forwards with `after`; the latest page, with no `limit`, holds the newest `MESSAGE_PAGE_DEFAULT` (the fixture is larger than that); an empty conversation answers an empty list with both flags false; two cursors, an unknown key, `limit` 0 and `limit` `MESSAGE_PAGE_MAX + 1` are 400 (the check reads the constants, concern 1); a cursor of another conversation, a cursor with no row and the id of a thread reply that is not in the main list are 404; the two empty cases above.
- R12. Paging is exact. The query compares the pair (`created_at`, `id`) of the anchor message with the pair of the rows, so a page never repeats or skips a message when several share a `created_at`, and `hasOlder` and `hasNewer` come from reading one row more than the limit. A message that commits after a page was read is not in that page; the client gets it by event (TOKI-038, TOKI-039). Check: 30 messages with the same `created_at` and ids in any order are read in pages of 7 in both directions and each message appears once, in the order of R9; a message inserted between two page requests is seen by the next request that reaches its place and is never duplicated.
- R13. `around` returns the message named, then up to `floor((limit - 1) / 2)` older messages and up to `ceil((limit - 1) / 2)` newer ones, in one answer, with `hasOlder` and `hasNewer` computed for the two ends. It is the request for a jump to a message (TOKI-068) and for opening a conversation at a place (TOKI-041, TOKI-054). The two sides are not redistributed when one is short; the client loads more with `before` and `after`. Check: with limit 5, a message in the middle of 20 returns 2 older and 2 newer; the oldest message returns itself and 2 newer with `hasOlder` false; the newest returns itself and 2 older with `hasNewer` false; with limit 4 a middle message returns 1 older and 2 newer.
- R14. What history holds. For a person who may read the conversation (`canReadConversation`, TOKI-027 R5: a member of any kind of conversation, an archived channel included), every top-level message of the conversation since its first, however long ago: a joiner and a person added later read the whole history because no code and no column limits it (D-029, D-116, FR-20; TS-080 is a test of this ticket). The list is the main list of the conversation as TOKI-036 defines it (roots, system lines, and replies that were also sent to the channel, which TOKI-045 writes); other replies of a thread are not in it (FR-33). System lines (R16) are in it, in their place by time. A deleted message stays in the list as a row with no text (TOKI-047 fills the state; this ticket returns it as the table holds it, R15). A person who left or was removed has no member row and reads nothing; a person who is not a member of a public channel gets 403 and of a private one 404 (R2), so there is no preview (D-116, TS-083). Check: a member added to a channel after 40 messages reads all 40 (TS-080); a person who left gets 403 or 404; a thread reply that is not also sent to the channel, inserted by SQL, is not in the list, and a system line and a reply also sent to the channel are; an archived channel's history loads for a member and is refused to a non-member; an Admin who is not a member of a private channel gets 404.
- R15. `MessageEntry` is one strict Zod object in `packages/shared`, exported from the package index, with these keys and no other: `id`, `conversationId`, `kind` (one of `MESSAGE_KINDS` of TOKI-036 R22, `"user"` or `"system"`), `authorId` (the author of a user message, the person who acted for a system line), `parentId` (`null` for a message of the main list; the id of the root for a reply that was also sent to the channel, which TOKI-045 writes and so a row that R14 can return), `text` (the `body` for a user message; `null` for a system line, whose body is empty, and for a message with `deleted_at` set), `system` (`null` for a user message, `{ "type": SystemLineType, "userIds": string[] }`, `SystemLineType` being one of `SYSTEM_LINE_TYPES` (R22) from `system_type` and `system_user_ids` for a system line, R16), `createdAt` (ISO 8601 UTC), `editedAt` (`null` or ISO 8601) and `deletedAt` (`null` or ISO 8601). `editedAt` and `deletedAt` are read from the table and are always `null` until TOKI-047 writes them; TOKI-045, TOKI-046, TOKI-048 and TOKI-058 add their own keys to the entry in their own changes (reply count, reactions, pinned, files), each with its tests, so the keys of other work are not guessed here. The server and its tests use the strict schema; the client of TOKI-032 derives a form that drops unknown keys (TOKI-032 R3). The response schemas of both routes are exported too. Check: a schema test accepts a user message and a system line and refuses an added key, a missing key, a `kind` of `other`, a `system.type` that is not in the list, a non-ISO time and a user message with `system` set; every 200 and 201 body of the route tests is parsed with the response schema.

System lines
- R16. The system lines. A change of TOKI-029 that is effective writes one message row of `kind` `system` in the conversation, in the transaction of the change, through `recordChange` (R18): the system-line handler, first in the list, inserts the row, with the id made by the server (UUIDv7), the person who acted as author, `created_at` equal to the time of the change, `system.type` and `system.userIds` as follows, and returns `{ message }` (the `MessageEntry` of the line), which the handlers after it read as `change.message`; the event handler of TOKI-038, last in the list, writes the events of the change and then the `message.created` of the line (TOKI-036, Design, "The event contract"). The line handler writes no event. `channel_created` writes `channel_created` (userIds: the first members); `member_joined` writes `member_joined` (the person); `members_added` writes `members_added` (the people added); `member_left` writes `member_left` (the person); a topic edit writes `topic_changed` (no people). These five come from the journeys F20, F21, F22, F23 and F24 (the baseline accepted in D-091); their wording is the client's (TOKI-042). The server sends no wording. A system line is never counted as unread and notifies nobody: its `kind` is how the read pointer and the notification work tell it apart (D-100, TOKI-053); this ticket counts and notifies nothing. The changes `member_removed`, `channel_archived`, `channel_restored`, `settings_changed` and a change of the description only write no line in this ticket, because no journey gives them one (concern 3, undecided: this is its proposal). A request that changes nothing writes no line (TOKI-029 R16: zero calls). A leave that empties a private channel writes `member_left` and no line for the archive. `Change` gains the optional field `fields` (`["topic"]`, `["description"]` or both) set by the edit route of TOKI-029 in its call of `details_changed`, so the handler writes `topic_changed` when `topic` is in it; that is the only change this ticket makes to a route of TOKI-029 (concern 12). Check: for each of the five changes, a real request of TOKI-029, with a recording handler after the line handler, leaves one system line with the type, author and people above and the recording handler receives it as `change.message`; a restore by an Admin who is not a member leaves a `member_joined` line and no line for the restore; an edit of the description only leaves no line (this follows concern 3); an edit of the topic and the description leaves one `topic_changed` line; a repeat or `changed: false` leaves none; a rollback after the line leaves none; the lines are in the history in order of time. That each line has its `message.created` event numbered after the event of its change is a test of TOKI-038 R20, with the real event handler.
- R17. A newcomer in #general (D-100, F03: "Minh joined", no notification). `addMemberToGeneral(tx, input)` of TOKI-028 R26 takes an optional `recordChange` in `input`; when it adds the row (it returns `true`) it calls it with `member_joined`, the newcomer as actor and as the only person, and the time `createdAt`; when it returns `false` it calls it zero times. `acceptInvitation(tx, { token, now }, deps?)` of TOKI-024 gains an optional third parameter `deps: { recordChange?: RecordChange }` that it passes on to `addMemberToGeneral`; the default does nothing, so the callers and tests that exist stay valid. The route that calls it, TOKI-097, passes the `recordChange` of the app, which `app.ts` gives to the `members` module like its other dependencies, so `members` imports only the type `RecordChange` from the `conversations` index and no file of `messages` (Plan changes). `createGeneralChannel` (the first Admin) writes no line (concern 3). The event handler of TOKI-038 also writes `member.joined` for #general from the same change, for every accept, and the accept holds the counter lock to its commit; that is intended: an accept is rare, and the contract of TOKI-036 R18 allows it because no statement of the accept after the first call of `recordChange` takes a lock. The people who joined before this writer existed get their line from R26. ## Design
### API
All routes need a session (R1). Bodies are JSON.

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/conversations/{id}/messages` | members, a conversation that is not archived | Send a message; 201 stored, 200 the same id again (R3 to R8) |
| GET | `/api/v1/conversations/{id}/messages` | members, any state | Latest messages, or `before`, `after`, `around` a message (R11 to R14) |

Outcomes common to the routes (the error format is TOKI-004's; a client acts on `error.code`, D-131):

| Status | `error.code` | When |
|---|---|---|
| 200 / 201 | none | Stored message returned (200: the same id again, R5); a page of history |
| 400 | `validation_failed` | A path, query or body fails its schema, including 10,001 characters, only white space and U+0000 (R4, R11) |
| 401 | as TOKI-022 (`account_deactivated` when the locked sender was deactivated) | No valid session |
| 403 | `forbidden` | A person who is not a member of a public channel (R2) |
| 404 | `not_found` | Unknown conversation; a private channel, DM or group the person is not in; a message id that is not in the conversation (R1, R11) |
| 409 | `channel_archived` | Send into an archived channel |
| 409 | `conversation_read_only` | Send into a DM with a deactivated person (R7) |
| 409 | `message_id_in_use` | The id belongs to another message (R5) |
| 500 | `internal_error` | A server failure, or `fact_missing` or `unknown_role` from a function |

A 409 means the screen was out of date; the client reloads the conversation (D-131). A request with no answer after 10 seconds counts as failed on the client (D-126) and is sent again with the same id, which R5 makes safe.

### Decisions in the flow of a request
- The id is made by the client (UUIDv7), so the optimistic message and the stored one are the same message and a retry cannot duplicate it (technical design). The server checks only the shape and that the id is free or its own.
- A send answers 201 for a new message and 200 for a repeat, with the same body, as TOKI-030 does for a direct message; a client treats both as "stored".
- History is read by position (a message id) and not by an opaque cursor, so the same request serves "load older", "load newer" and "jump to this message" (TOKI-068), and the flags say when to stop.
- Reading history changes nothing: no read pointer moves (TOKI-053) and no unread count changes.

### Lines with TOKI-036 and TOKI-038
Read against the revised event contract of TOKI-036 (PR 198, "The event contract") and the spec of TOKI-038 on 2026-11-20; where those say otherwise, they change (Plan changes).
- Message ids: client-made for user messages (R4), server-made UUIDv7 for system lines (R16). The table of TOKI-036 takes both and checks no version (its R2), so this ticket checks the version of the client's id (R4).
- Events: TOKI-036 owns the event table, the numbering and its one writer, `recordEvent` (with the internal `appendEvent`), which only the event handler inside `realtime` calls. Code that changes data calls `recordChange` (TOKI-036, "The event contract"). This ticket calls it with `message_created` for a sent message, with `direct_conversation_appeared` first for the first message of a direct message, and its line handler, first in the list, inserts the system line and returns it as `change.message`; the event handler of TOKI-038, last, writes `message.created` for the message and for the line, and `conversation.appeared` for the reveal. This ticket writes no event, adds nothing to the registry of event kinds (TOKI-038 R12) and does not call `appendEvent` or `recordEvent`. The field names of an event are `scope`, `type` and `payload`; the gateway's frame says `kind` and `data`.
- What the gateway pushes: each event after its commit, to the members of the conversation, in number order (TOKI-038 R13, R14, R15). The `payload` of `message.created` is `{ message: MessageEntry }`, the same shape as the list, so one shape serves both. The reveal of a direct message is `conversation.appeared`, scope `user`, one for each of the two people, written before the `message.created` (R20).
- What this ticket uses of the tables of TOKI-036 (names as in its spec): table `messages` with `id`, `workspace_id`, `conversation_id`, `author_id`, `kind` (`user` or `system`), `system_type`, `system_user_ids` (a line is a type and the ids of its people, never text; the list of types is `SYSTEM_LINE_TYPES` of R22), `body` (empty for a line), `parent_id`, `also_in_channel`, `edited_at`, `deleted_at`, `deleted_by`, `created_at`; the main-list index (`conversation_id`, `created_at`, `id`) where `parent_id is null or also_in_channel`, which every query of R11 to R14 states with that predicate as written, so the index serves it with no sort (TOKI-036 R11); the primary key on `id` for `ON CONFLICT (id) DO NOTHING` (its R2); `MESSAGE_TEXT_MAX`. A message row is never deleted and its place never changes (its R7, R8). `created_at` of a message can commit after a later one (its concern 12, accepted), which R12 states.
- Both specs expect from this ticket: the idempotent send (R5), the page size and the cursor (R11), the refusal of a post into an archived channel and into a read-only direct message (R6, R7), the rule that a message needs a text or a file (R4, concern 5), the list of system types and which changes write a line (R16, concern 3), the hiding of a new direct message with `lastMessageAt` (R19 to R21), the handler list in `recordChange` (R18), and the two reads of TOKI-036 "The two reads" (R11 to R14). The DM condition in `listConversationIdsOfUser` is TOKI-038's, with the injected read of R19.

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- Order by `created_at` then `id`, not by `id` alone, because the client makes the id and its time part is the client's clock (concern 4).
- Position cursors (a message id) and two flags, not `nextCursor` (above).
- `FOR SHARE` on the conversation row for a send, `FOR NO KEY UPDATE` for a `dm` (concern 8).
- A repeat is a read: answered with only the right to read, before the post rule (R1, R5, concern 11).
- The text is counted in code points and stored as sent; white space is what `trim` removes, and a lone surrogate is refused (R4, concern 9).

## Data safety
- A message is visible to the members of its conversation only. A private channel, a DM and a group answer 404 to anyone else, with the same body as for an id that does not exist (BR-09, BR-10); a public channel answers 403 to a non-member and returns nothing of it, so there is no preview (D-116).
- Every read of history goes through `getConversationFacts` and the permission function, never through a query on messages alone, so a caller cannot read without the check.
- The text is stored as sent and returned as data; the server never builds markup from it.
- The log holds no text, name or id list (R23). A 409 `message_id_in_use` confirms only that a UUIDv7 is taken.
- Tests use made-up texts and generated ids.

3. Which changes write a system line. Not decided for five cases. Written (R16): created, joined, added, left and a topic change, from F20 to F24 and D-100. 4. The order of messages. Decided in this spec: by the server's `created_at`, then by `id`. Reason: the Blueprint has the client make the message id, so the time inside a UUIDv7 is the client's clock, and an ordering by id would let a wrong clock place a message in the past. The cost: two messages sent in the same millisecond are ordered by their random ids, so the client sends the queue of one conversation one after another and waits for each answer (the sync engine of TOKI-040, D-097 one automatic try). The pagination index of TOKI-036 follows this order. Owner: Thanh Truong.
5. The ten files of a message. Reason: the plan gives this ticket the number but the link needs a table that exists only after TOKI-058; checking ids of files here would test nothing real. The plan line of TOKI-037 ("10 files per message") then reads as the constant. Owner: Thanh Truong.

8. The locks of a send.
