# File storage design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/file-storage.md (Thanh Truong)
Ticket: TOKI-058

## Goal
A message can carry text only. This ticket lets it carry up to 10 files of any type, each up to 100 MB, kept in MinIO (D-014).
The hard rules are three. The size limit holds on the server even though the browser sends the bytes straight to storage. Only people who can read the conversation can open its files, and a file always arrives as a download and is never run in the browser (D-095). A file that was uploaded and never sent, and the files of a deleted message, do not stay in storage (D-130, D-043).
This ticket builds: the tables `files` and `attachments`; four routes (start an upload, finish it, drop an unsent file, open a file); the storage client; the link between a file and a message at send time; the `files` key of the message entry; the handler that removes the files of a deleted message; one recurring cleanup job; the storage configuration; and the test setup against a real MinIO.
Nothing on screen changes: the composer cards, the message cards and the Files page are other tickets (Scope).

## Requirements
- R1. Table `files`, in `modules/files/schema.ts`: `id` (uuid, primary key, made by the client with the UUIDv7 generator of `packages/shared`, as a message id is), `workspace_id`, `conversation_id`, `uploader_id` (`users.id`), `name` (text, 1 to 255 code points), `size_bytes` (bigint, 0 to `FILE_MAX_BYTES`), `content_type` (text, 1 to 255), `state` (one of `pending`, `ready`, `attached`, `removed`), `created_at`, `ready_at` (null until `ready`), `removed_at` (null until `removed`). The key in storage is not a column: it is always `files/<id>/original` (R5). Keys that leave the module (`workspaces`, `conversations` through (`conversation_id`, `workspace_id`) as TOKI-036 R9 does, `users`) are `ON DELETE RESTRICT` and written as SQL in the migration. Checks: the length of `name`; `size_bytes` between 0 and 104,857,600; `ready_at` is not null exactly when `state` is `ready` or `attached`; `removed_at` is not null exactly when `state` is `removed`. Index `files_unsent_idx` on (`created_at`, `id`) where `state` in (`pending`, `ready`) (the cleanup, R18); index `files_removed_idx` on (`removed_at`, `id`) where `state` = `removed`; index `files_conversation_idx` on (`conversation_id`, `created_at` desc, `id` desc) where `state` = `attached` (the lists of TOKI-063); index on (`uploader_id`) where `state` in (`pending`, `ready`) (the cap of R9). Check: SQL-text tests, each refusal naming its constraint, each "must fail" next to a "must pass": 104,857,600 passes and 104,857,601 and a negative size fail; a name of 255 emoji passes and 256 fails; `state` `ready` with a null `ready_at` fails; a row of another workspace than its conversation fails; deleting a conversation, a workspace or a user that a file points to is refused; `explain` of each query of R9, R18 and R1's list shows its index.
- R2. Table `attachments`, in the same schema file: `id` (uuid), `message_id` (references `messages.id`, `ON DELETE RESTRICT`), `kind` (text, only `file` now), `file_id` (references `files.id`, `ON DELETE RESTRICT`), `position` (smallint, 0 to 9), `created_at`. Unique on `file_id` (a file is in one message), unique on (`message_id`, `position`) and the check `position` between 0 and 9, so the database itself holds at most 10 attachments for a message (`MESSAGE_FILES_MAX`, D-042). The check `kind = 'file'` is written so that a later kind (link cards, TOKI-061; the technical design says the table is built to extend) changes the check and makes `file_id` optional in its own migration. Index on (`message_id`, `position`) is the unique one. The migration of R1 and R2 is one file, `<number>_file_storage.sql`, made with `pnpm db:generate --name file_storage` (TOKI-019 convention 8), forward-only, with the cross-module keys written by hand; it changes no existing table and inserts no row. Check: a message with 10 attachments passes and an 11th (position 10, or a repeated position) fails; a file in two messages fails; a `kind` of `link` fails; the migration touches only the two tables.
- R3. `packages/shared/src/files/` (file `limits.ts`, re-exported by `index.ts` of the package) exports: `FILE_MAX_BYTES` = 104,857,600 (100 MB read as 100 × 1024 × 1024, concern 2; D-014, FR-10), `FILE_NAME_MAX` = 255, `FILE_UPLOAD_URL_SECONDS` = 900, `FILE_DOWNLOAD_URL_SECONDS` = 60 (concern 4), `FILE_UNSENT_MAX_AGE_MS` = 86,400,000 (D-130), `FILE_CLEANUP_INTERVAL_MS` = 600,000, `FILE_UNSENT_MAX_PER_PERSON` = 20 (concern 6), `STORED_CONTENT_TYPE` = `application/octet-stream`; `FileEntry` (a strict Zod object: `id`, `name`, `size`, `contentType`); `StartUploadRequest` (`id`, `conversationId`, `name`, `size`, `contentType` optional); `UploadTicket` (`url`, `fields` as a record of strings, `expiresAt` ISO 8601); and the responses of R6, R10 and R11. `MESSAGE_FILES_MAX` stays where TOKI-037 R22 put it. `name` follows the text rules of TOKI-037 R4 for characters that cannot be stored (no U+0000, no lone surrogate) and is not trimmed or changed, and an empty name is refused; `size` is an integer from 0 to `FILE_MAX_BYTES`; `contentType`, when given, is cut to its media type (no parameters), lower-cased, and replaced by `application/octet-stream` when it is not of the form `type/subtype` or is longer than 255, and is never a reason to refuse a file (D-095). Check: schema tests at 0, 104,857,600 and 104,857,601 bytes, at 1, 255 and 256 code points of name (letters and emoji), the missing and the odd content types, and a type test that imports every name from `@toki/shared`.
- R4. Configuration. `apps/server/src/config.ts` gains an area `storage` read by `loadConfig` like `mail`: `STORAGE_ENDPOINT` (URL the server calls, required), `STORAGE_PUBLIC_URL` (URL the browser calls and the signed addresses carry; default: the value of `STORAGE_ENDPOINT`), `STORAGE_REGION` (default `us-east-1`), `STORAGE_BUCKET` (required), `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY` (required, secret). The area is optional in the `Config` type, so a test of another area builds the app without it, and the server entry requires it. A missing or invalid name stops the start-up with the name only, never a value. The names are added to `configVariableNames` and the module exports `storageConfigSchema` and `storageVariableNames`. Check: the config tests of TOKI-096 style: each missing name is reported, `STORAGE_PUBLIC_URL` falls back to the endpoint, a value never appears in the error, and the names equal the names in `.env.example` (R21).
- R5. The storage client. `modules/files/store.ts` exports the interface `ObjectStore` and `createS3Store(config, clock)`. The interface has: `presignUpload({ key, size, expiresInSeconds })` returning `{ url, fields }`; `presignDownload({ key, name, expiresInSeconds })` returning a URL; `head(key)` returning `{ size } | null`; `deletePrefix(prefix)` (lists and deletes every object under it, success when there is none). The implementation uses the AWS SDK for JavaScript v3 (`@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`, `@aws-sdk/s3-presigned-post`, one exact version for the three, pinned like every dependency of the repository, concern 3), path-style addressing, and a second client built on `STORAGE_PUBLIC_URL` that only signs (signing makes no network call), so the address a browser gets points where the browser can go while the server keeps calling the internal endpoint. No route or job imports the SDK; they receive an `ObjectStore`, and `buildApp` takes an optional `objectStore` so a test passes a fake. Keys: `files/<fileId>/original` for the uploaded bytes; later tickets (thumbnails, TOKI-060) write other objects under `files/<fileId>/`, and `deletePrefix("files/<fileId>/")` removes them all (R18). The signing time comes from the clock given to `createS3Store`. Check: a unit test of the fake against the interface; the real client is tested against MinIO (R20).
- R6. `POST /api/v1/files` starts an upload. Body: `StartUploadRequest` (strict). A valid session is needed (401). Steps in order: (1) the body schema (400 `validation_failed`; a `size` above `FILE_MAX_BYTES` is refused here, before any byte is sent, AC-027); (2) the conversation is read like the send of TOKI-037 R1 steps 2 and 3: unknown id, or a private channel, DM or group the actor is not in, is 404 `not_found`; a person who is not a member of a public channel is 403 `forbidden`; (3) `canPostInConversation` (an archived channel is 409 `channel_archived`, as TOKI-037 R6); (4) the repeat rule of R8; (5) for a new file, `assertUploadsAllowed(app.diskSpace)` of TOKI-103 R10, before anything is signed or written, so a refusal (507 `storage_full`) leaves no row; (6) the cap of R9; (7) one row is inserted in state `pending` with `created_at` from the clock and the sanitized values of R3, and the answer is 201 `{ file: FileEntry, state: "pending", upload: UploadTicket }` (R7). The uploader of the row is the actor. No role is compared (TOKI-027 R16). Check: a table test sends each case and checks status, code and rows: a member of a public channel, a private channel, a DM and a group gets 201; a non-member of a public channel 403; an Admin outside a private channel 404; an archived channel 409; a size of 100 MB + 1 is 400 and no row; a refused disk (the fake of TOKI-103 at `full`) is 507 and no row and no signature call; a request without a session is 401 with no read.
- R7. The upload ticket makes the size and the stored headers a rule of storage, not of the browser. `presignUpload` builds a presigned POST policy (not a presigned PUT, concern 5) with these conditions: the bucket, the exact key `files/<id>/original`, `content-length-range` from the declared size to the declared size, `Content-Type` equal to `application/octet-stream`, `Content-Disposition` equal to `attachment`, and an expiry of `FILE_UPLOAD_URL_SECONDS` from the clock. The real type of the file is kept only in the column `content_type`. `UploadTicket.fields` holds every field the policy needs and the browser sends them in the form before the field `file`. Check, against MinIO (R20): the bytes of the declared size are accepted; one byte more and one byte less are refused by storage with no object created; a different `key`, a different `Content-Type` and a different `Content-Disposition` field are each refused; a ticket signed with a time older than its lifetime is refused (signed in the past, not waited for); exactly 104,857,600 bytes are accepted and 104,857,601 declared are refused by R6 and, sent anyway against a ticket for a smaller size, by storage (TS-042, TS-043); a stored object has the content type and disposition above.
- R8. A repeat of the start. The client makes the id, so the same request twice, and the Retry of a failed upload, are one rule: when a row of `id` exists and its uploader, conversation, name, size and normalized content type are those of the request, the answer is 200 with the same shape: for `pending` a new `UploadTicket` for the same key (the earlier one is not revoked and the key is written once, a second POST of the same key replaces the object), for `ready` or `attached` `upload` is `null` and nothing is signed. A row of `id` in state `removed`, a row of another person or another conversation, and a row whose values differ are 409 `file_id_in_use` with no `details`, the same body whatever the row is. A repeat needs only that its person may still post (R6 steps 2 and 3); it is not counted by the cap of R9 and, when it signs, it passes the disk rule of R6 step 5. Check: the same body twice gives one row and the answers 201 then 200 with a different `expiresAt`; a repeat of a `ready` file gives `upload` null; the same id from another person, in another conversation, with another size, and after the removal each give 409 with one body; two requests with one id at the same moment leave one row (two real connections).
- R9. The cap of unsent files. A person may hold at most `FILE_UNSENT_MAX_PER_PERSON` (20) files in `pending` or `ready` that were not removed. A new row beyond that is 409 `too_many_unsent_files` and writes nothing. It is not a quota of storage (D-106): such files are removed after 24 hours (R18), and the number is twice the ten of a message. Check: 20 rows pass and the 21st is 409; after one of the 20 is removed (R11) or attached (R14) a new start passes; another person is not counted.
- R10. `POST /api/v1/files/{id}/complete` tells the server that the bytes are stored. Only the uploader (any other person, an unknown id and a `removed` row are 404 `not_found`). For `pending`: `head("files/<id>/original")`; no object is 409 `upload_incomplete` and the row stays `pending` (the client retries); an object whose size is not `size_bytes` (storage should never allow it, R7) is deleted, the row becomes `removed` and the answer is 409 `file_rejected`; an object of the declared size sets the state to `ready` and `ready_at` from the clock, and the answer is 200 `{ file: FileEntry, state: "ready", upload: null }`. For `ready` or `attached` the answer is 200 with the same body and no call to storage, so a retry after a lost answer is safe. The route calls storage once and holds no row lock while it does (the row is read, the call is made, the update is conditional on `state = 'pending'`). Check: with MinIO, upload then complete gives `ready`; complete with nothing stored gives 409 `upload_incomplete` and the row is `pending`; an object put by hand with another size gives 409 `file_rejected`, no object and a `removed` row; a repeat gives 200 and no `head` call (a spy on the fake); another person gets 404.
- R11. `DELETE /api/v1/files/{id}` drops an unsent file (the × on a composer card). Only the uploader, only while the state is `pending` or `ready`: the row becomes `removed` with `removed_at` from the clock, the answer is 204, and the object is removed by the next run of R18 (not by this request). An `attached` file is 409 `file_attached` and is not touched (a file leaves a message only with the message, R17); another person and an unknown id are 404; a `removed` row answers 204 and changes nothing. Check: each case, with the rows read back.
- R12. `GET /api/v1/files/{id}/download` opens a file. A valid session is needed (401). The file is read with its row; the answer is 404 `not_found`, with one body, when: the id is unknown; the state is `removed`; the state is `pending` or `ready` and the actor is not its uploader (an unsent file is visible to its uploader only); the state is `attached` and the actor cannot read the conversation of the file, decided by `getConversationFacts` and `canReadConversation` (TOKI-027 R5: a member of the conversation, an archived channel included, D-170; an Admin has no extra right, D-047); a person who left or was removed has no member row and so reads nothing (D-116). So a public channel the actor has not joined is 404 here, not the 403 of the message routes, because an id of a file is not a thing a person can browse and nothing may confirm it (concern 7; the plan line of TOKI-088 asks that file lists and direct links answer like not found). Otherwise the answer is 302 with `Location` a signed GET address valid `FILE_DOWNLOAD_URL_SECONDS`, `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. The address is made for each request and is never stored or logged, and the route writes no message or event. The stable file link is this route's path, not the signed address (the signed address ends in 60 seconds), so TOKI-062's Copy link copies the path, and it opens only for people who can read the conversation (F18, AC-029). Check: a member gets 302 and the address fetches the bytes; every 404 case above with the same body; a member of a private channel who is removed gets 404 on the next request; an unsent file opens for its uploader and 404 for a member of the conversation; an archived channel's file opens for a member; a file whose message was deleted is 404 (R17); the log of the request holds no address.
- R13. A file never runs in the browser (D-095), by three layers. (1) The object is stored with `Content-Type: application/octet-stream` and `Content-Disposition: attachment` (R7), whatever the file is. (2) The signed GET address asks storage to answer with `response-content-disposition` = `attachment; filename="<ascii name>"; filename*=UTF-8''<percent-encoded name>` and `response-content-type` = `application/octet-stream`; the ascii name replaces every character outside printable ASCII, and the quote, the backslash, the path separators and control characters (line breaks included) with `_`, and the encoded name is the stored `name` complete, so no name can end the header or add one. (3) Every answer of this server for a file carries `X-Content-Type-Options: nosniff` (R12); the same header for the storage host is asked of the proxy (TOKI-084, concern 10), because storage does not let a signed address set it. An `<img>` that uses the address still draws, as the disposition applies to a page that opens the address and not to a picture inside a page; whether TOKI-062 shows the original that way is its choice. Check, against MinIO and with real requests: the reply of the signed address has `Content-Disposition` starting `attachment` and `Content-Type` `application/octet-stream` for an HTML file, an SVG file, a file named `a"b\n.html` and a name with Vietnamese letters (the decoded `filename*` equals the name); the object read straight from storage with no override has the same two headers; the answer of R12 has `nosniff`.
- R14. The send links the files. The body of `POST /api/v1/conversations/{id}/messages` (TOKI-037 R3, R4) gains the optional key `attachmentIds`: an array of 0 to `MESSAGE_FILES_MAX` (10) lower-case UUIDs with no repeat; 11 ids, a repeat and an id that is not a UUID are 400 `validation_failed` (TS-041, AC-026). The text rule changes: with no attachment the text is as before (1 to 10,000 code points, not only white space); with at least one attachment the text may be the empty string or omitted, and when it is given and not empty it follows the same rule as before (a text of only white space is 400). A message with no text and no file is 400. The empty text is stored as the empty body, which TOKI-036 R4 allows. The key is added to the shared schemas of TOKI-037 R22 by this ticket. In the transaction of the send, after the insert and after `saveMentions` and before the entry is built and before `recordChange`, the option `linkAttachments(tx, { messageId, conversationId, workspaceId, actorId, fileIds })` of `messageRoutes` (given by `app.ts`, the default does nothing, so the tests of TOKI-037 stay valid; `messages` imports nothing of `files`) runs once, only for a message that is stored (not for a repeat, R5 of TOKI-037, and not for a refusal), and only when `fileIds` is not empty. It locks the file rows `FOR UPDATE` in id order in one statement, and then every id must be a file that: exists, was uploaded by the actor, belongs to this conversation and workspace, and is in state `ready`. When any is not, the whole send is refused with 400 `validation_failed` whose `details.issues` carries `{ path: ["attachmentIds", index], code: "attachment_unavailable" }` for each such id, one code for every cause so a refusal confirms nothing about the file of another person, and no message row is left. Otherwise each file becomes `attached` and one `attachments` row is inserted with `position` the index in the array. A send whose message is later refused or rolled back leaves the files `ready`. Check: a send with 10 files stores 10 rows in the order given and an 11th id is 400 and stores nothing; each failing cause (unknown, another person's, another conversation's, `pending`, `removed`, already attached) gives the same issue code and no message; a send with no text and one file is 201 with an empty text; a send with only white space and a file is 400; a repeat of a send with files answers 200 and links nothing; two sends with the same file at the same moment (two connections) store one message with the file and refuse the other; a rollback after the link leaves the file `ready`; a send into an archived channel is 409 and leaves the file `ready`.
- R15. The entry carries the files. `MessageEntry` of TOKI-037 R15 gains the key `files`: an array of `FileEntry` in `position` order, default `[]` on read only (TOKI-037 R15, so an entry written before the key exists still parses). The reader `listFiles(db, messageIds): Promise<Map<string, FileEntry[]>>` is written in `modules/files/` and given to the builder `buildMessageEntry` and `buildMessageEntries` through the `readers` of `messageRoutes` (TOKI-037 R27), one statement for all the ids of the call. The builder gives `[]` to a system line, to a row with `deleted_at` set (without calling the reader) and to a message absent from the map. The send builds its entry with `listFiles` too (a new message that has files is no longer built with no reader, TOKI-037 R27), so the 201 body, a repeat's 200 body, the history item and the `message` of the change and of the event are equal. The entry holds no address and no storage key. Check: a unit test of the builder with a fake reader (once for a page, not for deleted or system rows); a history page of 50 messages with files costs one extra statement; the four bodies are equal for one message with 3 files; an entry has no `url` or `key`.
- R16. Edit of a message that has files. TOKI-047 R3 says the text of an edit follows the rule of a send and that this ticket changes it for messages with files. The edit route takes the option `hasAttachments(tx, messageId): Promise<boolean>` of `messageRoutes` (given by `app.ts`; default `false`): an empty text is accepted only when it returns true for the message, otherwise the rule of TOKI-037 R4 applies. Writing the function is this ticket's; calling it in the edit route is a line in TOKI-047's code, noted in Plan changes. A text equal to the stored text is still no change (TOKI-047 R3). Check: an edit to the empty string of a message with a file is 200 and the text is empty; the same for a message with no file is 400; an edit to white space only is 400 in both.
- R17. A deleted message loses its files (D-043, AC-033). `modules/files/` exports a change handler, given to `createRecordChange` (TOKI-037 R18) before the event handler of TOKI-038 (the seam of TOKI-047 R12). For the change `message_deleted` it runs in the transaction of the delete: it deletes the `attachments` rows of the message and sets its files to `removed` (`removed_at` from the change's time), in one statement each. After it, the open route answers 404 for those files (R12) and no list reads them, and the stored objects are removed by the next run of R18. It does nothing for any other change, and nothing for a message with no files. A deleted message's other attachment rows, which TOKI-047 R7 leaves, are the ones removed here. A handler that throws rolls the delete back (TOKI-047 R12). Check (TS-051, AC-033): after a delete the file is 404 on R12 for a member who could open it before, the rows are gone, the entry has `files: []`, the file is `removed`, and after a run of R18 the object is gone from MinIO; a delete rolled back after the handler leaves the attachment and the open route working; a message with no files is deleted with the handler doing no write (a statement log).
- R18. The cleanup job. `modules/files/cleanup.ts` exports `cleanupFiles({ db, store, clock })`, the job type `fileCleanupJob = defineJob({ name: "files.cleanup", payload: <empty strict object>, schedule: { cron: "*/10 * * * *" } })` of TOKI-064 R6 (every `FILE_CLEANUP_INTERVAL_MS`, ten minutes), and `createFileCleanupHandler(store)`, which returns `defineHandler(fileCleanupJob, (context) => cleanupFiles({ db: context.db, store, clock: context.clock }))` (TOKI-064 R13). The job type is added to `job-types.ts` and the handler to `job-handlers.ts` (TOKI-064 R9), and `worker.ts` adds the area `storage` to its configuration list and builds the store there (TOKI-064 R17); the server process, which only adds jobs, needs no store for this job. The clock is the one of the handler context, so a test moves it (TOKI-064 R19). One run does, in this order: (1) in one statement, every file in `pending` or `ready` whose `created_at` is at least `FILE_UNSENT_MAX_AGE_MS` before the clock becomes `removed` (D-130: 24 hours from the start of the upload; the statement skips locked rows, so a send that has locked a file wins and the file stays attached); (2) for the `removed` rows, oldest first, at most 100 a run: `deletePrefix("files/<id>/")` and, when it succeeded, delete the row. A failure of storage for one file is logged with the id (no name) and leaves the row for the next run, and the other files are still tried. A file that is `attached` is never touched. Check, with the controllable clock and no real wait (TOKI-008 R8, R9): a file at 23 h 59 min 59 s is kept and at 24 h is removed (storage and row), for `pending` and for `ready`; an attached file of any age stays; a `removed` row whose storage call fails is kept, logged once and removed by the run after the store recovers; 150 removed rows take two runs; a file locked by a send (two connections) is skipped and stays; a second run does nothing and calls storage zero times; the objects under `files/<id>/` other than `original` go with it.
- R19. Error codes in `packages/shared/src/error.ts`: `fileIdInUse` (`file_id_in_use`, 409, R8), `tooManyUnsentFiles` (`too_many_unsent_files`, 409, R9), `uploadIncomplete` (`upload_incomplete`, 409, R10), `fileRejected` (`file_rejected`, 409, R10) and `fileAttached` (`file_attached`, 409, R11). Reused: `forbidden`, `not_found`, `validation_failed`, `channel_archived`, `unauthorized`, `account_deactivated`, `internal_error`; `storage_full` is TOKI-103's. No body carries a name, a key, a path or an address. Check: the registry test lists each code once and keeps the older codes; every 4xx body of the routes parses with the error schema and has no `details` except the `issues` of R14.

## Design
### How a file goes
```
 composer                 server (Fastify)                         MinIO
    |-- POST /files ---------->|  session, may post, disk rule, cap
    |<-- 201 { file, upload } -|  row `pending`, signed POST policy (size, key, headers)
    |-- POST form + bytes ----------------------------------------->|  refused by storage when size or fields differ
    |-- POST /files/{id}/complete -->|  head the object, size must match
    |<-- 200 state `ready` ---|
    |-- POST /conversations/{id}/messages { attachmentIds } -->|  row `attached` + `attachments`
    |-- GET /files/{id}/download ->|  session, can read the conversation
    |<-- 302 signed GET (60 s, attachment) ------------------|--> bytes, always a download
```
The bytes never pass through Node: the upload goes from the browser to storage and the download comes from storage. A body of 100 MB would also be refused by the JSON-only body rule of the server (TOKI-022 R45), which is one more reason for the direct path.

### Choices made here
- **Presigned POST, not presigned PUT, and not through the server** (concern 5). A presigned PUT cannot set a size limit in the policy of the standard S3 interface: the size of the body is whatever the browser sends, and the technical design asks that the size be enforced by the server. A POST policy carries `content-length-range`, so storage itself refuses a body of another size, and fixes the key and the stored headers. Through the server would put 100 MB through Node and the JSON-only rule and is what the technical design rejects.
- **Two checks of size.** Storage refuses at upload (R7), and `complete` reads the stored size (R10). The second one is what makes "the file is rejected when it completes" (TS-043) true even if the policy is changed by mistake, and a file counts as uploaded only after it.
- **The type is data, not a rule.** Every type is accepted (D-095). The declared type is kept as text for the card and the Files filter ("Documents" is every file that is not an image, as the log answers for the Files page) and is never used to decide how the file is served: storage always has `application/octet-stream` and `attachment`.
- **A file belongs to one conversation from the start.** The start names the conversation, so "can the person upload here" is decided once, an unsent file cannot be moved to another conversation (R14), and the rule of R12 has one place to look.
- **The link is made inside the send.** The send already locks the conversation and inserts the message (TOKI-037 R8); the files are locked last and in id order, so no lock cycle is made and a send and the cleanup of R18 cannot both take a file.
- **Delete uses the seam of TOKI-047.** The handler of R17 runs in the delete's transaction and marks; the cleanup removes the objects. One recurring job does both D-043 and D-130, so a failed storage call is retried by the next run and no job is lost with a lost queue entry (concern 9).
- **Tables.** `files` holds the file and its state; `attachments` holds the link to a message and the position, and is the table the technical design says is built to extend. `state` is stored, not derived from `attachments`, so the cleanup and the list index read one table; only R14 and R17 change it, each in the transaction that changes `attachments`, and their tests read both tables back.

### Errors
- Storage unreachable on `complete`, on the signing of a download or in the cleanup -> the request is 500 `internal_error` (the shared handler logs it), a `pending` row stays `pending`, and the cleanup retries the row on the next run. A start of upload needs no call to storage (signing is local), so it works while storage is down and the upload fails at the browser.
- A signed address that expired -> storage refuses it; the client asks again (R8 for an upload, R12 for a download).
- The object of an `attached` file is missing from storage (a reset of the development bucket, `dev:reset:files`, leaves rows) -> R12 still answers 302 and storage answers 404 at the address. This is a development state, not handled (TOKI-003 names it).

## Data safety
- A file is readable only through R12: the signed address is made per request after the access check, lives 60 seconds, is never stored or logged, and no entry, event or log line holds a storage key or an address. The bucket has no public access: the signed addresses are the only way in.
- The upload ticket is for one key, one size and fixed headers, for 15 minutes, and is only given to a person who may post in the conversation.
- File names are data: they are never put in a key, in a path or in a log line, and the header of R13 cannot be broken by one.
- Uploaded content is never read, rendered or scanned by the server (D-186), and is never served with its own type.
- The storage credentials are secrets: they are read only by the configuration module, never written in a log or an error (R4), and the development values are throwaway.

## Areas of concern
1. File types and virus scanning. Answered: the plan line lists "whether any file types are blocked" and "virus scanning" as open, and the log has decided both since: every type is accepted up to 100 MB and a file is always downloaded and never run in the browser (D-095, Confirmed); no scanning in phase 1 (D-186, Confirmed). This spec blocks no type and scans nothing, and makes "never run in the browser" a rule of the stored object and of every address (R13). Owner: Thanh Truong (product owner).
2. What "100 MB" is. Decided in this spec: 100 × 1024 × 1024 bytes, 104,857,600 (`FILE_MAX_BYTES`), so a file that any file manager calls 100 MB passes and one byte more than 100 MiB does not (R3, R7). Reason: the log gives the number without a unit base, and the larger reading never refuses a file that looks like 100 MB. The card text "Over 100 MB" (F18) is unchanged. Every test reads the constant. If the owner wants 100,000,000, only the constant and the two boundary tests change. Owner: Thanh Truong.
3. The S3 client library. Decided in this spec: the AWS SDK for JavaScript v3 (three packages, one exact version), behind `ObjectStore` (R5). Reason: the repository's own `Dockerfile.minio` says MinIO publishes no image and its sources are archived, so the store may change one day; the SDK speaks the S3 interface of any store and has the presigned POST that R7 needs, and only `store.ts` knows it. The alternative, the `minio` package, is smaller but ties the code to that one server. The cost is more installed packages on the server. Owner: Thanh Truong.
4. How long a signed address lives. Decided in this spec: 900 seconds for the upload ticket, 60 seconds for a download address (R3). Reason: storage checks the time only when a request starts, so a long transfer that began in time is not cut, and the browser uses a download address at once after the redirect; a short life limits a leaked address, and every new use goes through the access check again. The signing time comes from the clock. Owner: Thanh Truong.
5. Presigned POST, presigned PUT, or through the server. Decided in this spec: presigned POST with a policy (R7). Reason: only the policy form lets storage itself refuse a body of another size and fix the key and the headers; a presigned PUT leaves the size to the browser, and through the server puts 100 MB through Node. The cost: the browser sends a form, not a bare PUT, with the fields of the ticket (TOKI-059), and storage must allow the browser's origin, which MinIO does by default and TOKI-084 must keep (concern 10). Owner: Thanh Truong.
6. The cap of unsent files. Decided in this spec: 20 files in `pending` or `ready` for each person (R9). Reason: D-106 has no quota, but without any bound one person could fill the disk with starts of 100 MB in 24 hours before the cleanup of D-130 runs; the cap does not limit what a person may send (an attached file is not counted) and is twice the ten of a message. It is a protection, not a quota, and the number is a builder's choice that the owner may change in one constant. Owner: Thanh Truong.
7. What a person gets who opens a file they cannot see. Decided in this spec: 404 `not_found` with one body for an unknown id, a removed file, an unsent file of another person, and a conversation the person cannot read, including a public channel not joined (R12). Reason: BR-10 and D-116 say no access reads as not found, the plan line of TOKI-088 asks the same of file lists and direct links, and an id of a file is not something a person browses, so the 403 that the message routes give for a public channel would confirm a file for nothing. The cost: the start of an upload names a conversation and so follows the message routes (403 for a public channel not joined, R6). Owner: Thanh Truong.
8. The list of files. Decided in this spec: this ticket builds no list route; the Files tab and the Files page (TOKI-063) read the `files` and `attachments` tables through the module and the index of R1, and apply D-170 (members of the conversation, an archived channel included) with the same rule as R12. Reason: the lists have their own filters, search and paging, which TOKI-063 specifies. Owner: Thanh Truong.
9. Who removes a stored file, and how. Decided in this spec: one recurring job, `files.cleanup`, on the cron `*/10 * * * *`, declared with the tools of TOKI-064 (R18): it removes the unsent files after 24 hours (D-130) and the files marked `removed` by a delete (D-043) or by R11. Reason: access is cut at once by the state (R12, R17), and the removal of bytes is a later, repeatable step; a job for each message would be lost if its queue entry were lost, and the state is in the database, so a run that fails is repeated. The cost: a deleted file's bytes stay for up to about 10 minutes. TOKI-047 R12 words it as "queues the removal"; this is the recurring form of it. Owner: Thanh Truong.
10. The test bucket, CI, and the production path to storage. Decided in this spec: tests use a separate bucket that is emptied at the start of each run and guarded like the test database (R20). CI builds MinIO from `Dockerfile.minio` because no image is published; the first run is slow (the build needs about 3 GB of free disk, see that file) and later runs use the layer cache. If the cost proves too high, the fallback is to run the storage project in a separate job; this changes the workflow and no requirement. In production the browser must reach `STORAGE_PUBLIC_URL`, the proxy must pass the host unchanged (the signature covers it) and add `nosniff`, and storage must allow the app's origin: all of that is TOKI-084's. Owner: Thanh Truong.
11. A file-only message. Decided in this spec: a message may have no text when it has at least one file; its body is the empty string (R14), allowed by TOKI-036 R4, and its entry `text` is the empty string, not `null` (which means deleted or a system line, TOKI-037 R15). Reason: AC-024 forbids an empty message with no file, and a file alone is a message in F18. The rule for an edit is R16. Owner: Thanh Truong.
