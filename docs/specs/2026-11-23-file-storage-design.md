# File storage design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/file-storage.md (Thanh Truong)
Ticket: TOKI-058

## Goal
A message can carry text only. This ticket lets it carry up to 10 files of any type, each up to 100 MB, kept in MinIO (D-014).
The hard rules are three. The size limit holds on the server even though the browser sends the bytes straight to storage. Only people who can read the conversation can open its files, and a file always arrives as a download and is never run in the browser (D-095). A file that was uploaded and never sent, and the files of a deleted message, do not stay in storage (D-130, D-043).
This ticket builds: the tables `files` and `attachments`; five routes (start an upload, finish it, drop an unsent file, list a person's unsent files, open a file); the storage client; the link between a file and a message at send time; the `files` key of the message entry; the handler that removes the files of a deleted message; one recurring cleanup job; the storage configuration; and the test setup against a real MinIO.
Nothing on screen changes: the composer cards, the message cards and the Files page are other tickets (Scope).

## Requirements
- R1. Table `files`, in `modules/files/schema.ts`: `id` (uuid, primary key, made by the client with the UUIDv7 generator of `packages/shared`, as a message id is), `workspace_id`, `conversation_id`, `uploader_id` (`users.id`), `name` (text, 1 to 255 code points), `size_bytes` (bigint, 0 to `FILE_MAX_BYTES`), `content_type` (text, 1 to 255), `state` (one of `pending`, `ready`, `attached`, `removed`), `created_at`, `ready_at` (null while `pending`, set when the file becomes `ready` and kept after), `removed_at` (null until `removed`). The key in storage is not a column: it is always `files/<id>/original`, built from the `id` as Postgres stores it (R5). Keys that leave the module (`workspaces`, `conversations` through (`conversation_id`, `workspace_id`) as TOKI-036 R9 does, `users`) are `ON DELETE RESTRICT` and written as SQL in the migration. Checks: the length of `name`; `size_bytes` between 0 and 104,857,600; `ready_at` is not null when `state` is `ready` or `attached` and is null when `state` is `pending` (free when `removed`: a file removed from `pending` has none and one removed from `ready` or `attached` keeps the time it was ready); `removed_at` is not null exactly when `state` is `removed`. Index `files_unsent_idx` on (`created_at`, `id`) where `state` in (`pending`, `ready`) (the cleanup, R18); index `files_removed_idx` on (`removed_at`, `id`) where `state` = `removed`; index `files_conversation_idx` on (`conversation_id`, `created_at` desc, `id` desc) where `state` = `attached` (the lists of TOKI-063); index on (`uploader_id`, `created_at` desc, `id` desc) where `state` in (`pending`, `ready`) (the cap of R9 and the list of R23). Check: SQL-text tests, each refusal naming its constraint, each "must fail" next to a "must pass": 104,857,600 passes and 104,857,601 and a negative size fail; a name of 255 emoji passes and 256 fails; `state` `ready` with a null `ready_at` fails, `pending` with a `ready_at` fails, and `removed` passes with and without one; a row of another workspace than its conversation fails; deleting a conversation, a workspace or a user that a file points to is refused; `explain` of each query of R9, R18, R23 and R1's list shows its index.
- R2. Table `attachments`, in the same schema file: `id` (uuid), `message_id` (references `messages.id`, `ON DELETE RESTRICT`), `kind` (text, only `file` now), `file_id` (references `files.id`, `ON DELETE RESTRICT`), `position` (smallint, 0 to 9), `created_at`. Unique on `file_id` (a file is in one message), unique on (`message_id`, `position`) and the check `position` between 0 and 9, so the database itself holds at most 10 attachments for a message (`MESSAGE_FILES_MAX`, D-042). The check `kind = 'file'` is written so that a later kind (link cards, TOKI-061; the technical design says the table is built to extend) changes the check and makes `file_id` optional in its own migration. Index on (`message_id`, `position`) is the unique one. The migration of R1 and R2 is one file, `<number>_file_storage.sql`, made with `pnpm db:generate --name file_storage` (TOKI-019 convention 8), forward-only, with the cross-module keys written by hand; it changes no existing table and inserts no row. Check: a message with 10 attachments passes and an 11th (position 10, or a repeated position) fails; a file in two messages fails; a `kind` of `link` fails; the migration touches only the two tables.
- R3. `packages/shared/src/files/` (file `limits.ts`, re-exported by `index.ts` of the package) exports: `FILE_MAX_BYTES` = 104,857,600 (100 MB read as 100 × 1024 × 1024, concern 2; D-014, FR-10), `FILE_NAME_MAX` = 255, `FILE_UPLOAD_URL_SECONDS` = 900, `FILE_DOWNLOAD_URL_SECONDS` = 60 (concern 4), `FILE_UNSENT_MAX_AGE_MS` = 86,400,000 (D-130: a `ready` file that is not sent), `FILE_PENDING_MAX_AGE_MS` = 3,600,000 (a `pending` file whose bytes never arrived, concern 6), `FILE_REMOVED_KEEP_MS` = 2,700,000 (the 15 minutes of an upload ticket plus a grace of 30 minutes, concern 9), `FILE_UNSENT_MAX_PER_PERSON` = 20 (concern 6); the cleanup runs every 10 minutes, a number that lives only in the cron text of R18, `STORED_CONTENT_TYPE` = `application/octet-stream`; `FileEntry` (a strict Zod object: `id`, `name`, `size`, `contentType`; later work adds keys to it, TOKI-060 adds `thumbnail`, with a default on read as TOKI-037 R15 does for its keys, so the schema is written to take one); `StartUploadRequest` (`id`, `conversationId`, `name`, `size`, `contentType` optional; `id` is a lower-case UUID of version 7, the rule of TOKI-037 R4, so a version-4 id and an upper-case id are 400); `UploadTicket` (`url`, `fields` as a record of strings, `expiresAt` ISO 8601); and the responses of R6, R10, R11 and R23. The server builds the key only from the `id` that the insert returns (`RETURNING id`), never from the string of the request, because Postgres compares uuid values without case and a second spelling must not make a second key. `MESSAGE_FILES_MAX` stays where TOKI-037 R22 put it. `name` follows the text rules of TOKI-037 R4 for characters that cannot be stored (no U+0000, no lone surrogate) and is not trimmed or changed, and an empty name is refused; `size` is an integer from 0 to `FILE_MAX_BYTES`; `contentType`, when given, is cut to its media type (no parameters), lower-cased, and replaced by `application/octet-stream` when it is not of the form `type/subtype` or is longer than 255, and is never a reason to refuse a file (D-095). Check: schema tests at 0, 104,857,600 and 104,857,601 bytes, at 1, 255 and 256 code points of name (letters and emoji), the missing and the odd content types, and a version-4 id and an upper-case id are 400, and the key built after an insert of `ABC...` equals the key built for `abc...`; a type test that imports every name from `@toki/shared`. Every producer of a `FileEntry` (R6, R8, R10, R15 and R23) builds it through one function, `fileEntryFromRow(row)` in `modules/files/entries.ts`, written here as the mapping of the four keys, so that a key added later (TOKI-060 R11) is added in one place and no producer leaves it at its default; check: each producer's test reads the entry it returns, and a grep test finds no other construction of a file entry.
- R4. Configuration. `apps/server/src/config.ts` gains an area `storage` read by `loadConfig` like `mail`: `STORAGE_ENDPOINT` (URL the server calls, required), `STORAGE_PUBLIC_URL` (URL the browser calls and the signed addresses carry; default: the value of `STORAGE_ENDPOINT`), `STORAGE_REGION` (default `us-east-1`), `STORAGE_BUCKET` (required), `STORAGE_ACCESS_KEY` and `STORAGE_SECRET_KEY` (required, secret). The area is optional in the `Config` type, so a test of another area builds the app without it, and the server entry and the worker entry require it. A missing or invalid name stops the start-up with the name only, never a value. The names are added to `configVariableNames` and the module exports `storageConfigSchema` and `storageVariableNames`. Every process that starts the real server entry now needs the six names or throwaway values (a start only signs, so it needs no running MinIO): `apps/server/tests/main.test.ts`, `apps/server/tests/e2e-real-launch.ts`, `apps/server/tests/e2e-sign-in-launch.ts`, `playwright.real-server.config.ts`, `playwright.sign-in.config.ts`, the `e2e` job and the `tests` job of `.github/workflows/ci.yml`, and a developer's existing `.env` (copy the new names from `.env.example`). They are edited in this ticket's change (Plan changes, TOKI-007). Check: the config tests of TOKI-096 style: each missing name is reported, `STORAGE_PUBLIC_URL` falls back to the endpoint, a value never appears in the error, and the names equal the names in `.env.example` (R21); the process tests of the real server entry and the launchers pass with the throwaway values and fail with the name of the missing one.
- R5. The storage client. `modules/files/store.ts` exports the interface `ObjectStore` and `createS3Store(config, options?)`. The interface has: `presignUpload({ key, size, expiresInSeconds })` returning `{ url, fields, expiresAt }`; `presignDownload({ key, name, expiresInSeconds })` returning a URL; `head(key)` returning `{ size } | null`; `deletePrefix(prefix)` (lists and deletes every object under it, in as many pages of 1,000 as it takes, success when there is none). TOKI-060 adds two methods to the interface, to the S3 implementation and to the fake: `getObject(key)` and `putObject({ key, body })` (its R9); this ticket builds neither, and the keys and the stored headers of R7 and R13 are the same for them. The implementation uses the AWS SDK for JavaScript v3 (`@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`, `@aws-sdk/s3-presigned-post`, one exact version for the three, pinned like every dependency of the repository, concern 3), path-style addressing, and a second client built on `STORAGE_PUBLIC_URL` that only signs (signing makes no network call), so the address a browser gets points where the browser can go while the server keeps calling the internal endpoint. No route or job imports the SDK; they receive an `ObjectStore`, and `buildApp` takes an optional `objectStore` so a test passes a fake. Keys: `files/<fileId>/original` for the uploaded bytes; later tickets (thumbnails, TOKI-060) write other objects under `files/<fileId>/`, and `deletePrefix("files/<fileId>/")` removes them all (R18). The signing time is the system time: `createPresignedPost` of the SDK reads `Date.now()` plus the `systemClockOffset` of its client (read in version 3.1175.0, the version at the time of writing), and takes no signing date, so the injected clock of the application does not reach it. `expiresAt` is the expiry the store signed. The option `systemClockOffsetMs` of `createS3Store` sets that offset and is used only by the storage test of an expired ticket (R7); the fake of a unit test computes `expiresAt` from the clock it is given. Check: a unit test of the fake against the interface; the real client is tested against MinIO (R20), including `deletePrefix` over more than 1,000 objects.
- R6. `POST /api/v1/files` starts an upload. Body: `StartUploadRequest` (strict). A valid session is needed (401). Steps in order: (1) the body schema (400 `validation_failed`; a `size` above `FILE_MAX_BYTES` is refused here, before any byte is sent, AC-027); (2) the conversation is read like the send of TOKI-037 R1 steps 2 and 3: unknown id, or a private channel, DM or group the actor is not in, is 404 `not_found`; a person who is not a member of a public channel is 403 `forbidden`; (3) `canPostInConversation` (an archived channel is 409 `channel_archived`, as TOKI-037 R6); (4) the repeat rule of R8; (5) for a new file, the option `assertUploadsAllowed: () => void | Promise<void>` of `fileRoutes` (`app.ts` fills it with a call of `assertUploadsAllowed(app.diskSpace)` of TOKI-103 R10, because `files` imports nothing of `disk-space`), before anything is signed or written, so a refusal (507 `storage_full`) leaves no row; (6) in one transaction: the lock and the cap of R9, then the insert; the row has state `pending`, `created_at` from the clock and the sanitized values of R3, and the answer is 201 `{ file: FileEntry, state: "pending", upload: UploadTicket }` (R7). The uploader of the row is the actor. No role is compared (TOKI-027 R16). Check: a table test sends each case and checks status, code and rows: a member of a public channel, a private channel, a DM and a group gets 201; a non-member of a public channel 403; an Admin outside a private channel 404; an archived channel 409; a size of 100 MB + 1 is 400 and no row; a refused disk (the fake of TOKI-103 at `full`, passed through the option) is 507 and no row and no signature call; a request without a session is 401 with no read; the route test of TOKI-103 and this one pass the same option name, and a test of `app.ts` shows the option calls `assertUploadsAllowed(app.diskSpace)`.
- R7. The upload ticket makes the size and the stored headers a rule of storage, not of the browser. `presignUpload` builds a presigned POST policy (not a presigned PUT, concern 5) with these conditions: the bucket, the exact key `files/<id>/original`, `content-length-range` from the declared size to the declared size (0 to 0 for an empty file), `Content-Type` equal to `application/octet-stream`, `Content-Disposition` equal to `attachment`, and an expiry of `FILE_UPLOAD_URL_SECONDS` from the signing time (R5). The real type of the file is kept only in the column `content_type`. `UploadTicket.fields` holds every field the policy needs and the browser sends them in the form before the field `file`. The ticket is not single-use: until it expires the uploader can post again to the same key, which replaces the bytes (concern 5 states this limit). Check, against MinIO (R20): the bytes of the declared size are accepted; a file of 0 bytes with a size of 0 is accepted; one byte more and one byte less are refused by storage with no object created; a different `key`, a different `Content-Type` and a different `Content-Disposition` field are each refused; a form with a field the policy does not list (`x-amz-meta-note`, `Cache-Control`, `Content-Encoding`, `tagging`, `x-amz-storage-class`, `success_action_redirect`) is refused, one at a time, and a form with no `Content-Type` field is refused; an expired ticket is refused (a store built with a `systemClockOffsetMs` of minus 16 minutes, not waited for); exactly 104,857,600 bytes are accepted and 104,857,601 declared are refused by R6 and, sent anyway against a ticket for a smaller size, by storage (TS-042, TS-043); a stored object has the content type and disposition above; a preflight `OPTIONS` request with the origin of the app and the method `POST` is answered with the origin allowed (the browser's `XMLHttpRequest` upload listener makes the form post non-simple, TOKI-059 R3, so the preflight is part of the path). These are checks of the behaviour of MinIO `RELEASE.2025-10-15` for POST policies that no one has run yet: they are written as build-time checks, and where MinIO accepts a field the policy does not list, R7's wording "the stored headers are a rule of storage" is cut back to the four conditions and the finding goes in the pull request.
- R8. A repeat of the start. The client makes the id, so the same request twice, and the Retry of a failed upload, are one rule: when a row of `id` exists and its uploader, conversation, name, size and normalized content type are those of the request, the answer is 200 with the same shape: for `pending` a new `UploadTicket` for the same key (the earlier one is not revoked and the key is written once more by a second POST of the same key, which replaces the object), for `ready` or `attached` `upload` is `null` and nothing is signed. A `pending` row older than `FILE_PENDING_MAX_AGE_MS` minus `FILE_UPLOAD_URL_SECONDS` (45 minutes) is not signed again: it is answered like a `removed` row, so no ticket is ever live after the cleanup removes the row (R18, concern 9). A row of `id` in state `removed`, a row of another person or another conversation, and a row whose values differ are 409 `file_id_in_use` with no `details`, the same body whatever the row is (the client makes a new id and retries). A repeat needs only that its person may still post (R6 steps 2 and 3); it is not counted by the cap of R9 and, when it signs, it passes the disk rule of R6 step 5. The insert is `INSERT ... ON CONFLICT (id) DO NOTHING` followed by a read, so two requests with one id at the same moment give one row. Check: the same body twice gives one row and the answers 201 then 200 with a different `expiresAt`; a repeat of a `ready` file gives `upload` null; the same id from another person, in another conversation, with another size, after the removal, and for a `pending` row at 45 minutes each give 409 with one body, and a `pending` row at 44 minutes 59 seconds is signed again (the controllable clock); two requests with one id at the same moment leave one row (two real connections).
- R9. The cap of unsent files. A person may hold at most `FILE_UNSENT_MAX_PER_PERSON` (20) unsent files: the rows in `ready`, and the rows in `pending` created less than `FILE_PENDING_MAX_AGE_MS` (1 hour) before the clock. A `pending` row whose upload never finished stops counting after an hour, and the cleanup removes it within 10 minutes more (R18); a `ready` file counts until it is sent, dropped (R11) or removed after 24 hours. A new row beyond that is 409 `too_many_unsent_files` and writes nothing, and its text is the screen's (concern 6). The count and the insert are one unit: the transaction of R6 first runs `SELECT 1 FROM users WHERE id = $1 FOR NO KEY UPDATE` on the uploader, so two starts of one person at the same moment are taken one after the other and cannot both read 19. A person who lost the ids after a reload (D-168: a draft restores text only) recovers through R23 and R11: the list gives the ids, and a drop frees a place. It is not a quota of storage (D-106); it is a protection and the numbers are proposals (concern 6). Check: 20 rows pass and the 21st is 409; after one of the 20 is removed (R11) or attached (R14) a new start passes; a `pending` row of 59 minutes counts and one of 60 does not; another person is not counted; two starts at the same moment by one person with 19 rows give one 201 and one 409 (two real connections).
- R10. `POST /api/v1/files/{id}/complete` tells the server that the bytes are stored. Only the uploader (any other person, an unknown id and a `removed` row are 404 `not_found`). For `pending`: `head("files/<id>/original")`; no object is 409 `upload_incomplete` and the row stays `pending` (the client retries); an object whose size is not `size_bytes` (storage should never allow it, R7) marks the row `removed` and the answer is 409 `file_rejected` (the object is removed by the cleanup, R18); an object of the declared size sets the state to `ready` and `ready_at` from the clock, and the answer is 200 `{ file: FileEntry, state: "ready", upload: null }`. The route calls storage once and holds no row lock while it does. TOKI-060 R3 changes the first statement for an image: the same update also sets the thumbnail state and, in the same transaction, queues the job `files.thumbnail`; for that `fileRoutes` takes one more option, `jobs` (the queue of TOKI-064, given by `app.ts`), and the answer of this route keeps the shape above with the entry of `fileEntryFromRow`. This ticket builds neither the column nor the job. Both updates are one statement each, `UPDATE files SET ... WHERE id = $1 AND state = 'pending' RETURNING ...`, and the answer comes from the rows it changed. When it changed none, the row is read again: `ready` or `attached` answers 200 with the same body (a retry after a lost answer, or two completes at once); `removed` (the cleanup or a drop won) or no row answers 404 `not_found`, and the object, if there is one, is the cleanup's (a `removed` row keeps its object for `FILE_REMOVED_KEEP_MS`, R18). For `ready` or `attached` at the first read the answer is 200 with the same body and no call to storage. Check: with MinIO, upload then complete gives `ready`; complete with nothing stored gives 409 `upload_incomplete` and the row is `pending`; an object put by hand with another size gives 409 `file_rejected`, a `removed` row, and no object after the next run of R18 past the keep time; a repeat gives 200 and no `head` call (a spy on the fake); another person gets 404; complete against the cleanup of R18 (two connections, the row removed between the read and the update) is 404 and leaves the row `removed`; complete against a drop (R11) at the same moment ends with one winner and a consistent row.
- R11. `DELETE /api/v1/files/{id}` drops an unsent file (the × on a composer card). One statement: `UPDATE files SET state = 'removed', removed_at = $now WHERE id = $1 AND uploader_id = $2 AND state IN ('pending', 'ready') RETURNING id`, and the answer comes from the rows it changed, so a file that a send has just attached cannot be turned to `removed` by a drop that read it earlier. One row changed: 204, and the object is removed by a run of R18 at least `FILE_REMOVED_KEEP_MS` after (not by this request, R18). No row changed: the row is read; `attached` is 409 `file_attached` and is not touched (a file leaves a message only with the message, R17); `removed` of this uploader is 204 and changes nothing; another person's row and an unknown id are 404. Check: each case, with the rows read back; a drop against a send of the same file at the same moment (two connections): the send wins and the file stays `attached`, or the drop wins and the send is 400 `attachment_unavailable`, and never an `attached` file that ends `removed`.
- R12. `GET /api/v1/files/{id}/download` opens a file. A valid session is needed (401). The file is read with its row; the answer is 404 `not_found`, with one body, when: the id is unknown; the state is `removed`; the state is `pending` or `ready` and the actor is not its uploader (an unsent file is visible to its uploader only); the state is `attached` and the actor cannot read the conversation of the file, decided by `getConversationFacts` and `canReadConversation` (TOKI-027 R5: a member of the conversation, an archived channel included, D-170; an Admin has no extra right, D-047); a person who left or was removed has no member row and so reads nothing (D-116). So a public channel the actor has not joined is 404 here, not the 403 of the message routes, because an id of a file is not a thing a person can browse and nothing may confirm it (concern 7; the plan line of TOKI-088 asks that file lists and direct links answer like not found). The decision is one function, `readableFile(db, actorId, row)` in `modules/files/access.ts`, which TOKI-060 R8 owns (the thumbnail route of that ticket applies the same rule and gets the same 404 body): this ticket states the rule and writes it inline in the route, and TOKI-060 moves it into the function with no change of behaviour; the module does not export it. Otherwise the answer is 302 with `Location` a signed GET address valid `FILE_DOWNLOAD_URL_SECONDS`, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer` (the page leaves the app for the storage host, and the address must not travel in a `Referer`) and `X-Content-Type-Options: nosniff`. The address is made for each request and is never stored or logged, and the route writes no message or event. The stable file link is this route's path, not the signed address (the signed address ends in 60 seconds), so TOKI-062's Copy link copies the path, and it opens only for people who can read the conversation (F18, AC-029). Check: a member gets 302 and the address fetches the bytes; every 404 case above with the same body; a member of a private channel who is removed gets 404 on the next request; an unsent file opens for its uploader and 404 for a member of the conversation; an archived channel's file opens for a member; a file whose message was deleted is 404 (R17); the log of the request holds no address, and the answer has `Referrer-Policy: no-referrer`. The access log of the proxy is TOKI-084's: Plan changes asks it to log no query string for the storage host, because the signed address is in the query.
- R13. A file never runs in the browser (D-095), by three layers. (1) The object is stored with `Content-Type: application/octet-stream` and `Content-Disposition: attachment` (R7), whatever the file is. (2) The signed GET address asks storage to answer with `response-content-disposition` = `attachment; filename="<ascii name>"; filename*=UTF-8''<encoded name>` and `response-content-type` = `application/octet-stream`; the ascii name replaces every character outside printable ASCII, and the quote, the backslash, the path separators and control characters (line breaks included) with `_`, and the encoded name is the stored `name` complete, encoded with the set of RFC 5987 (`encodeURIComponent` and then `'`, `(`, `)` and `*` percent-encoded too), so no name can end the header or add one. (3) Every answer of this server for a file carries `X-Content-Type-Options: nosniff` (R12); the same header for the storage host, and `Content-Security-Policy: sandbox`, are asked of the proxy (TOKI-084, concern 10), because storage does not let a signed address set them. A fourth rule needs no header: the storage host must not share the origin of the app (scheme, host and port), so that a file served from it, if it ever ran, would have none of the app's cookies or browser storage. This ticket states it in the inventory row of `STORAGE_PUBLIC_URL` (R21; the development value is on another port) and TOKI-084 enforces it in the production proxy and Compose (concern 10); no route of this ticket changes for it. Whether an `<img>` that uses the address draws is not claimed by this spec: browsers apply opaque-response blocking to a cross-origin image whose answer has `nosniff` and a type that is not an image, so it may not. Before TOKI-062 relies on showing an original that way, the by-hand trial below opens an `<img>` on a signed address in Chrome and Safari and records the result in the pull request; TOKI-062 owns the choice (a build-time check, not a requirement of this ticket). ## Design
### How a file goes
```
 composer                 server (Fastify)                         MinIO
    |-- POST /files ---------->|  session, may post, disk rule, cap
    |<-- 201 { file, upload } -|  row `pending`, signed POST policy (size, key, headers)
    |-- POST form + bytes ----------------------------------------->|  refused by storage when size or fields differ
    |-- POST /files/{id}/complete -->|  head the object, size must match
    |<-- 200 state `ready` ---|
    |-- POST /conversations/{id}/messages { attachmentIds } -->|  row `attached` + `attachments`
    |-- GET /files/{id}/download ->|  session, can read the conversation
    |<-- 302 signed GET (60 s, attachment) ------------------|--> bytes, always a download
```
The bytes never pass through Node: the upload goes from the browser to storage and the download comes from storage. A body of 100 MB would also be refused by the JSON-only body rule of the server (TOKI-022 R45), which is one more reason for the direct path.

### Choices made here
- **Presigned POST, not presigned PUT, and not through the server** (concern 5). A presigned PUT cannot set a size limit in the policy of the standard S3 interface: the size of the body is whatever the browser sends, and the technical design asks that the size be enforced by the server. A POST policy carries `content-length-range`, so storage itself refuses a body of another size, and fixes the key and the stored headers. Through the server would put 100 MB through Node and the JSON-only rule and is what the technical design rejects.
- **Two checks of size.** Storage refuses at upload (R7), and `complete` reads the stored size (R10). The second one is what makes "the file is rejected when it completes" (TS-043) true even if the policy is changed by mistake, and a file counts as uploaded only after it.
- **The type is data, not a rule.** Every type is accepted (D-095). The declared type is kept as text for the card and the Files filter ("Documents" is every file that is not an image, as the log answers for the Files page) and is never used to decide how the file is served: storage always has `application/octet-stream` and `attachment`.
- **A file belongs to one conversation from the start.** The start names the conversation, so "can the person upload here" is decided once, an unsent file cannot be moved to another conversation (R14), and the rule of R12 has one place to look.
- **The link is made inside the send.** The send already locks the conversation and inserts the message (TOKI-037 R8); the files are locked last and in id order, so no lock cycle is made and a send and the cleanup of R18 cannot both take a file.
- **Delete uses the seam of TOKI-047.** The handler of R17 runs in the delete's transaction and marks; the cleanup removes the objects. One recurring job does both D-043 and D-130 and the abandoned uploads, so a failed storage call is retried by the next run and no job is lost with a lost queue entry (concern 9).
- **A removed row outlives its upload ticket.** A ticket is valid for 15 minutes and storage checks the time only when a request starts, so a transfer can finish after the ticket's expiry. The cleanup therefore keeps a `removed` row, and its object, for `FILE_REMOVED_KEEP_MS` (45 minutes: ticket life plus 30 minutes), and no ticket is signed for a `pending` row that the cleanup could remove before the ticket expires (R8). The answers of R12 and R10 come from the state at once, so access is cut when the row is marked, and only the bytes wait.
- **Tables.** `files` holds the file and its state; `attachments` holds the link to a message and the position, and is the table the technical design says is built to extend. `state` is stored, not derived from `attachments`, so the cleanup and the list index read one table; only R14 and R17 change it, each in the transaction that changes `attachments`, and their tests read both tables back.

### Errors
- Storage unreachable on `complete`, on the signing of a download or in the cleanup -> the request is 500 `internal_error` (the shared handler logs it), a `pending` row stays `pending`, and the cleanup retries the row on the next run. A start of upload needs no call to storage (signing is local), so it works while storage is down and the upload fails at the browser.
- A signed address that expired -> storage refuses it; the client asks again (R8 for an upload, R12 for a download).
- The object of an `attached` file is missing from storage (a reset of the development bucket, `dev:reset:files`, leaves rows) -> R12 still answers 302 and storage answers 404 at the address. This is a development state, not handled (TOKI-003 names it).

## Data safety
- A file is readable only through R12: the signed address is made per request after the access check, lives 60 seconds, is never stored or logged, and no entry, event or log line holds a storage key or an address. The bucket has no public access: the signed addresses are the only way in.
- The upload ticket is for one key, one size and fixed headers, for 15 minutes, and is only given to a person who may post in the conversation. It can be used more than once until it expires (concern 5); the bytes of a removed file stay until the keep time of R18 has passed, so a live ticket cannot write an object that nothing will remove.
- File names are data: they are never put in a key, in a path or in a log line, and the header of R13 cannot be broken by one.
- Uploaded content is never read, rendered or scanned by the API process (D-186), and is read in the worker only to make a thumbnail of an image (TOKI-060); it is never served with its own type.
- The storage host is not the origin of the app, so a file served from it never has the app's cookies (R13).
- The storage credentials are secrets: they are read only by the configuration module, never written in a log or an error (R4), and the development values are throwaway.

## Areas of concern
1. File types and virus scanning. Answered: the plan line lists "whether any file types are blocked" and "virus scanning" as open, and the log has decided both since: every type is accepted up to 100 MB and a file is always downloaded and never run in the browser (D-095, Confirmed); no scanning in phase 1 (D-186, Confirmed). This spec blocks no type and scans nothing, and makes "never run in the browser" a rule of the stored object and of every address (R13). Owner: Thanh Truong (product owner).
2. What "100 MB" is. Proposal for the owner (D-014 gives "100 MB" with no unit): 100 × 1024 × 1024 bytes, 104,857,600 (`FILE_MAX_BYTES`), so a file that any file manager calls 100 MB passes and one byte more than 100 MiB does not (R3, R7). Reason: the log gives the number without a unit base, and the larger reading never refuses a file that looks like 100 MB. The card text "Over 100 MB" (F18) is unchanged, and TOKI-059's `formatFileSize` divides by 1,024 so that the limit reads "100 MB" (its R4); if the owner picks 100,000,000, the step there changes with the constant. Every test reads the constant. If the owner wants 100,000,000, only the constant and the two boundary tests change. Owner: Thanh Truong.
3. The S3 client library. Decided in this spec: the AWS SDK for JavaScript v3 (three packages, one exact version: all three are released with one common version, 3.1175.0 at the time of writing), behind `ObjectStore` (R5). Reason: the SDK has the presigned POST that R7 needs and speaks the S3 interface of any store, and only `store.ts` knows it; the repository's own `Dockerfile.minio` says MinIO publishes no image and its sources are archived, so the store may change one day, though the `minio` package also speaks S3 and that is not the deciding reason. The cost is size: the three packages with their dependencies are about 30 packages and about 19 MB installed (measured with `npm install` of the three), added to the server image and to `pnpm install --frozen-lockfile` in CI. The SDK is ESM-ready, which the server (`"type": "module"`) needs. Owner: Thanh Truong.
4. How long a signed address lives. Decided in this spec: 900 seconds for the upload ticket, 60 seconds for a download address (R3). Reason: storage checks the time only when a request starts, so a long transfer that began in time is not cut, and the browser uses a download address at once after the redirect; a short life limits a leaked address, and every new use goes through the access check again. The ticket's life also sets the keep time of a removed file (R18, concern 9). The signing time is the system time, not the injected clock (R5). Owner: Thanh Truong.
5. Presigned POST, presigned PUT, or through the server. Decided in this spec: presigned POST with a policy (R7). Reason: only the policy form lets storage itself refuse a body of another size and fix the key and the headers; a presigned PUT leaves the size to the browser, and through the server puts 100 MB through Node. The cost: the browser sends a form, not a bare PUT, with the fields of the ticket (TOKI-059), and storage must allow the browser's origin and answer its preflight `OPTIONS` request (TOKI-059 sends the form with an `XMLHttpRequest` whose `upload` listener makes the cross-origin `POST` non-simple), which MinIO does by default and TOKI-084 must keep (concern 10). Limit of this design: the ticket is not single-use, so for 15 minutes after `complete` or after the send the uploader can post again to the key and replace the bytes of the file with other bytes of the same size, and the message that everyone sees then shows the new bytes. Only the uploader of a file in a conversation they may post in can do this, to their own file, and it adds no storage (the size is fixed). It is kept for phase 1 as a proposal for the owner; the stronger options are a shorter life (storage checks the time only at the start of a request, so 300 seconds still allows a long transfer) or the ETag stored at `complete` and compared by `head` at R12, which this ticket does not build. Owner: Thanh Truong.
6. The cap of unsent files and how a person recovers. Proposal for the owner (no decision of the log covers it: D-106 says no quota, D-130 gives 24 hours for an unsent file, D-168 says a draft restores text only and not files): at most 20 unsent files for each person (R9); a `pending` file whose bytes never arrived counts for 1 hour and is then removed (R3, R18); a person who reloaded and lost the ids gets them from `GET /api/v1/files/unsent` and frees places with the drop of R11 (R23); the start counts and inserts under a lock on the person's row (R9). Reason: without a bound one person could fill the disk with starts of 100 MB before the cleanup runs, and a cap with no way to recover would lock a person out for 24 hours after a reload or a few failed uploads. The cap does not limit what a person may send (an attached file is not counted). The numbers (20, 1 hour) and the choice of a list route over removing the oldest files silently are the builder's proposal; a different owner choice changes R9, R18 and R23 only. The text of the 409 `too_many_unsent_files` is a screen text for TOKI-059 (an i18n key it adds); this ticket adds no key. Owner: Thanh Truong.
7. What a person gets who opens a file they cannot see. Decided in this spec: 404 `not_found` with one body for an unknown id, a removed file, an unsent file of another person, and a conversation the person cannot read, including a public channel not joined (R12). Reason: BR-10 and D-116 say no access reads as not found, the plan line of TOKI-088 asks the same of file lists and direct links, and an id of a file is not something a person browses, so the 403 that the message routes give for a public channel would confirm a file for nothing. The cost: the start of an upload names a conversation and so follows the message routes (403 for a public channel not joined, R6). Owner: Thanh Truong.
8. The list of files. Decided in this spec: this ticket builds no list route for the Files tab or page (its only list is the person's own unsent files, R23); the Files tab and the Files page (TOKI-063) read the `files` and `attachments` tables through the module and the index of R1, and apply D-170 (members of the conversation, an archived channel included) with the same rule as R12. Reason: the lists have their own filters, search and paging, which TOKI-063 specifies. Owner: Thanh Truong.
9. Who removes a stored file, and how. Proposal for the owner (the log decides D-043 and D-130, not the delay or the form): one recurring job, `files.cleanup`, on the cron `*/10 * * * *`, declared with the tools of TOKI-064 (R18): it marks the unsent files `removed` after 24 hours for `ready` and 1 hour for `pending` (D-130) and removes the bytes and the row of every `removed` file (a delete by D-043, a drop by R11, or the cleanup) 45 minutes after it was marked. Reason: access is cut at once by the state (R12, R17), and the removal of bytes is a later, repeatable step; a job for each message would be lost if its queue entry were lost, and the state is in the database, so a run that fails is repeated. The 45 minutes are the 15 minutes of an upload ticket plus a grace of 30 minutes for a transfer that began before the ticket expired: an earlier delete of the prefix and the row would let a live ticket store up to 100 MB that no row owns and no run removes, which with the cap not counting it would let a person fill the disk until the 95% rule of TOKI-103 refuses everyone. The cost: a deleted file's bytes stay for up to about an hour. Left out, as a stronger later step: a periodic sweep of `files/` objects that have no row (and are older than the keep time); this ticket's rule closes the hole for a transfer shorter than the grace, and a transfer longer than 45 minutes after the ticket's expiry is not covered. TOKI-047 R12 words it as "queues the removal"; this is the recurring form of it (Plan changes). Owner: Thanh Truong.
10. The test bucket, CI, and the production path to storage. Decided in this spec: tests use a separate bucket that is emptied at the start of each run and guarded like the test database (R20). CI builds MinIO from `Dockerfile.minio` because no image is published; the first run is slow (the build needs about 3 GB of free disk, see that file) and later runs use the layer cache. If the cost proves too high, the fallback is to run the storage project in a separate job; this changes the workflow and no requirement. In production the browser must reach `STORAGE_PUBLIC_URL`, the proxy must pass the host unchanged (the signature covers it), add `nosniff` and `Content-Security-Policy: sandbox`, and log no query string for that host, and storage must allow the app's origin and answer its preflight `OPTIONS` request, and the storage host must not share the origin of the app (R13): all of that is TOKI-084's. Owner: Thanh Truong.
11. A file-only message. Decided in this spec: a message may have no text when it has at least one file; its body is the empty string (R14), allowed by TOKI-036 R4, and its entry `text` is the empty string, not `null` (which means deleted or a system line, TOKI-037 R15). Reason: AC-024 forbids an empty message with no file, and a file alone is a message in F18. The rule for an edit is R16. Owner: Thanh Truong.
