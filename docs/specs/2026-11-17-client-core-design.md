# client-core: API client and conversation store design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/client-core.md (Thanh Truong)
Ticket: TOKI-032
Needs: TOKI-031, and for the checks TOKI-002 (lint, boundaries), TOKI-004 (error schema), TOKI-008 (Vitest, the search script) and TOKI-007 (size check); see Plan changes.

## Goal
The screens of the sidebar, Browse channels, the people picker and the conversation header all need the same data and the same rules: one way to call the server and read an error, and one list of conversations with its groups, filters, names and settings. This work builds both in `packages/client-core`: an API client typed from the shared schemas, and a conversation store that takes the first load (`GET /api/v1/bootstrap`, TOKI-031), applies the answers of the channel and direct-message requests (TOKI-029, TOKI-030) and gives screens the list already grouped, filtered and named. It holds no text and uses no browser API, so a React hook now and a phone screen later read the same code.

## Scope
- In:
  - The API client: the request core, the error type, the reading of answers with the shared schemas, the 10-second timeout, the report of unauthenticated answers, the mapping of an error to a kind of screen (D-131), and one typed method for each route of the bootstrap, channel and direct-conversation requests (R1 to R9).
  - The conversation store: state, subscription, the first load and its refresh, the merge of channel answers into entries, the commands that change the list, and reset (R10 to R16, R26).
  - The selectors: names, the grouped list, order, search, filters, lookups (R17 to R23).
  - A small wiring file in `apps/web` that creates the one client and the one store (R25).
  - Unit tests in `packages/client-core` (Vitest, no browser, no database, fake `fetch`).
- Out (not now):
  - Any screen, hook, text or style: TOKI-033 (the list), TOKI-034, TOKI-035. This ticket adds no file in `packages/ui-web`, `packages/i18n` or `packages/tokens`.
  - Where the open collapsed groups, the chosen filter and the search text are kept, and their storage per device (F09): TOKI-033. The store takes the filter and the search text as arguments of a selector and keeps neither.
  - The session state, `reportUnauthenticated` and the sign-in screens: TOKI-023 (`packages/client-core/src/auth/`). This ticket owns the connection of the API client's 401 hook to it (R7, R25): Decided in this spec, because the wiring file is this ticket's. The client does not import `auth/`; only `apps/web/src/client.ts` does.
  - The WebSocket, events, optimistic send, the queue of unsent messages and the saved cache for offline use: TOKI-038, TOKI-040. The store is in memory only.
  - Unread counts and the mention mark: the read pointer, TOKI-053. This ticket defines the slot they fill and the filter rules over it (R20).
  - Who calls `setUnread`: TOKI-053 (R20).
  - Saving the person's notification level, mute and star: no ticket owns the request (TOKI-031 concern 5); no client method or store command exists for it here (concern 9).
  - Messages, threads, files, drafts, reactions, presence: each belongs to its own ticket.
  - A generator of UUIDv7 ids for the client: not built here (concern 11).
  - Token sessions and the `Authorization` header for the phone app: phase 3. The client sends the browser's cookie and nothing else.

## Requirements
- R1. Package. `@toki/client-core` declares `@toki/shared` as a `workspace:*` dependency (TOKI-001 left every internal link but two to the ticket that needs it) and the schema library of `@toki/shared` at the same version, and exports from `src/index.ts`: `createApiClient`, `ApiError`, `classifyApiError`, `createConversationStore` and the types of this spec. No file of the package uses a global outside the allow list of TOKI-002 rule 1 (`fetch`, `AbortController`, `AbortSignal`, `URL`, `URLSearchParams`, `Headers`, `Response` and the language built-ins, `Intl` included), imports `@toki/platform/web`, or calls `Date.now()`, `new Date()`, `setTimeout` or `setInterval` (TOKI-008 R19). Check: `pnpm typecheck` exits 0, and so do `pnpm lint` and `pnpm lint:boundaries` once TOKI-002 is in the tree (TOKI-002 was reverted and is landing again; this ticket needs it, see Plan changes); the R19 search script of TOKI-008 finds no match in `packages/client-core/src`; `pnpm ls --filter @toki/client-core` lists `@toki/shared`.
- R2. Request core. `createApiClient(options)` takes `{ timers, baseUrl?, fetch?, requestTimeoutMs?, onUnauthenticated? }`; `timers` is required (R5). `baseUrl` defaults to `/api/v1`; `fetch` defaults to the global `fetch` read when a request is sent, not when the client is made; `requestTimeoutMs` defaults to 10 000 (D-126). The core method `request({ method, path, query?, body?, schema, signal? })` (the methods of R9 also take an optional `signal`) sends `baseUrl + path`, the query with every `undefined` value left out and values written with `URLSearchParams`, with the credentials mode `same-origin` and the header `Accept: application/json`. When `body` is given it sends the JSON text and `Content-Type: application/json`; when it is not given it sends no body and no `Content-Type` (TOKI-022 R45 refuses other types; the POST routes join, leave, archive and restore and the DELETE route of TOKI-029 take no body). It sets no `Origin` header (TOKI-022 R46: the browser sets it). Check: with a fake `fetch` that records its arguments: a `GET` with `{ search: "a b", limit: undefined }` sends `?search=a+b`; a `POST` with a body sends the text and the JSON type; a `POST` with no body sends neither a body nor a `Content-Type`; no sent header is named `Origin`; a client made before `globalThis.fetch` is replaced uses the replacement.
- R3. Reading a good answer. A 2xx answer whose body is JSON is parsed with `schema` (a shared schema). A 204 answer, and an answer to a route declared with no body, returns `undefined`. A key that the schema does not know is dropped and does not fail the parse, at every level, `workspace`, `user`, a conversation entry and a member included; a missing key, a value of the wrong type or a value outside an enum (a `notificationLevel` of `loud`) fails with an `ApiError` of kind `invalid_response` (R4) that holds the status and no body text. Decided in this spec (concern 1): the shared schemas of TOKI-031 are strict, which is right for the server's tests and wrong for a client that must keep working when the API adds a field (technical design: within a version, fields are only added). The schemas exported by `packages/shared` are not changed and not re-exported in a non-strict form; the dropping is done in `packages/client-core/src/api/parse.ts` and works on any object schema, so it does not depend on whether TOKI-029's schemas are strict. For an answer that is a union (`channels.get` answers `ChannelDetail | ChannelSummary`, `BootstrapConversation` is a channel entry or a direct entry), the branch is chosen by the keys that identify it, not by the first branch that parses: the branch with the most required keys is tried first (`ChannelDetail` before `ChannelSummary`), and `kind` selects the entry of a conversation, so a detail with an added key is never read as a summary that silently loses `description`, `createdBy` and `createdAt`. Check: the body of a rich fixture parses; the same body with one added key at the top level, in `user`, in `workspace`, in a `members` item, in a channel entry and in a direct entry parses and the result has none of the added keys; a body with a missing `eventNumber`, a `notificationLevel` of `loud`, a `memberIds` that is null for a `dm`, and a body that is not JSON each give kind `invalid_response`; the check is made on `BootstrapResponse`, on `ChannelDetail` and on the direct-conversation response; `channels.get` with a detail plus an added key returns a detail that still has `description`, `createdBy` and `createdAt`, and with a summary plus an added key returns a summary; the exported schemas of `packages/shared` still reject an added key (the test imports them).
- R4. The error type. `ApiError` extends `Error` and has `kind` (`http`, `network`, `timeout`, `aborted`, `invalid_response`), `status` (a number for `http` and `invalid_response`, else null), `code` (the `error.code` of the body for `http`, else null), `message` (the English developer text of the body, else a fixed English text), `details` (the `details` of the body or null) and `requestId` (the string `details.requestId` when it is one, else null; the error ID that D-131 shows with Retry). A non-2xx answer whose body passes the error schema of TOKI-004 is kind `http` with those fields. A non-2xx answer whose body does not pass it (an HTML page from a proxy, an empty body, text) is kind `http` with `code` null and `details` null, and the body is not copied into the error. `ApiError` never holds the request body, the cookie or the response headers. Check: one test for each kind; a 502 with an HTML body gives kind `http`, status 502, code null; a 409 with `{ error: { code: "channel_archived", message, details: { x: 1 } } }` gives code and details; a 500 with `details.requestId` gives `requestId`; `JSON.stringify` of an error holds none of the strings of a request body sent in the test.
- R5. Network and timeout. When `fetch` rejects, the request ends with kind `network` and status null. When no answer has arrived after `requestTimeoutMs`, counted with the injected `timers.after(ms, fn)` (returns a function that cancels), the request is aborted through an `AbortController` and ends with kind `timeout`; the timer is cancelled when the answer arrives or the request fails. When the caller's `signal` aborts, the request ends with kind `aborted` and no other kind. `timers` is required: `createApiClient` does not type-check without it, so no host gets the timeout by forgetting it. Check, with a fake `fetch` that never answers and a fake `timers` that records the delay and fires on demand: the delay is 10 000, firing it ends the request with kind `timeout` and the fetch's signal is aborted; an answer before the fire cancels the timer (the fake counts one cancel); a rejecting `fetch` gives `network`; aborting the caller's signal gives `aborted`; with a `requestTimeoutMs` of 8 000 the delay is 8 000; a type test shows `createApiClient({})` does not compile. Reason for `timers`: TOKI-008 R19 allows no timer function in `client-core` and its clock has `now()` only, so the web app lends the one timer function (R25).
- R6. No automatic retry. The client sends each request once and does not repeat one after an error. Retry belongs to the screen after D-131 (a button) and to the sync engine for messages (TOKI-040). Check: a fake `fetch` that fails once is called once; the error reaches the caller.
- R7. Unauthenticated answers. When an answer is 401 with the code `unauthenticated`, `session_ended` or `account_deactivated` (TOKI-022 R24, R27), the client calls `onUnauthenticated(code)` once and then ends the request with the `ApiError` as for any error. The client has a method `setOnUnauthenticated(fn | null)` to set or replace the hook after it was made. A throwing hook does not change the error that the caller receives. No other code, and no other status, calls the hook, and a 200 never does. The sign-in calls of TOKI-023 go through `request` too (R25); a 401 with the code `invalid_code` or any other is not one of the three, so it does not call the hook. Check: three 401 answers with the three codes call the hook with each code, once each, and each request still rejects with the `ApiError`; a 401 with another code, a 403 and a 500 do not call it; a hook that throws leaves the rejection as the `ApiError`; a hook set with `setOnUnauthenticated` after the client was made is called, and `null` removes it.
- R8. Which kind of screen an error leads to (D-131). `classifyApiError(error)` returns one of `unauthenticated` (a 401 of R7), `field` (400), `no_access` (403 and 404, the one shared page), `fresh_copy` (409 and 410), `wait` (429), `retry` (5xx, `network` and `timeout`; the error ID that D-131 shows with it is `requestId` of an `http` error, and there is none for `network` and `timeout`), `unreadable` (`invalid_response`: a 2xx answer that does not fit the schema has no error body and the server sends no ID in a header, so there is no error ID, and a repeat fails the same way, so it gets no Retry; the screen shows a message that asks for a reload, the page being too old, NFR-17; Decided in this spec), `ignore` (`aborted`) and `unknown` (any other status, including a 401 with another code, and an `http` error with a status below 400). It reads the status and the kind, and the code only for R7's three codes. Check: a table test of every row above, and `classifyApiError` of a value that is not an `ApiError` returns `unknown`. Source: D-131 (400 field message, 403 and 404 one shared page, 409 and 410 fresh copy, 429 wait, 5xx Retry with an error ID), D-126 (no answer counts as failed and shows Retry).
- R9. Typed methods. The client has these methods, each calling `request` with the schema of the response from `packages/shared` and sending exactly what the route of the other spec takes:

  | Method | Request | Answer |
  | :---- | :---- | :---- |
  | `bootstrap(signal?)` | `GET /bootstrap` | `BootstrapResponse` (TOKI-031 R17) |
  | `channels.create(body)` | `POST /channels` with `{ id, name, isPrivate?, topic?, memberIds? }` | `{ channel: ChannelDetail, created }`, `created` true for status 201 and false for the 200 of a repeat (TOKI-029 R3, R5) |
  | `channels.list({ search?, limit?, cursor? })` | `GET /channels` | `{ channels: ChannelSummary[], nextCursor }` (R6) |
  | `channels.get(id)` | `GET /channels/{id}` | `{ channel: ChannelDetail \| ChannelSummary }` (R7) |
  | `channels.members(id, { limit?, cursor? })` | `GET /channels/{id}/members` | `{ members: { userId, joinedAt }[], nextCursor }` (R8) |
  | `channels.update(id, { topic?, description? })` | `PATCH /channels/{id}` | `{ channel: ChannelDetail, changed }` (R9) |
  | `channels.join(id)` | `POST /channels/{id}/join`, no body | `{ channel: ChannelDetail, changed }` (R10) |
  | `channels.addMembers(id, userIds)` | `POST /channels/{id}/members` with `{ userIds }` | `{ added, alreadyMembers }` (R11) |
  | `channels.leave(id)` | `POST /channels/{id}/leave`, no body | `{ changed, archived }` (R12) |
  | `channels.removeMember(id, userId)` | `DELETE /channels/{id}/members/{userId}` | `{ changed }` (R13) |
  | `channels.archive(id)`, `channels.restore(id)` | `POST /channels/{id}/archive` or `/restore`, no body | `{ channel: ChannelDetail, changed }` (R14) |
  | `directConversations.open(userIds)` | `POST /direct-conversations` with `{ userIds }` | `{ conversation: DirectConversationEntry }`, status 200 or 201 (TOKI-030 R18) |

  The schemas are the ones TOKI-029 R17 and TOKI-030 R17 export; this ticket writes none of its own, and does not re-check the rules of the server (a name pattern, a limit) before sending: the server's answer is the rule. A path part (`id`, `userId`) is put in the address with `encodeURIComponent`. `directConversations.open` returns `created` in the same way (status 201). The methods that send no body take an optional `signal` as their last argument, which the store uses (R11). Check: one test per row with a fake `fetch`: the method, the path, the query, the body and the use of the right response schema (a valid body is returned, an invalid one is `invalid_response`); an `id` of `a/b` is sent as `a%2Fb`; `open` and `channels.create` return `created` true for 201 and false for 200.
- R10. Store state, first load and refresh. `createConversationStore({ api })` returns a store whose state holds: `status` (`idle`, `loading`, `ready`, `failed`), `isRefreshing` (a boolean), `error` (an `ApiError` or null), `user`, `workspace`, `people` (by id, in the order the server sent), `conversations` (by id), `details` (R14), `unread` (R20) and `eventNumber`. It starts `idle`, empty, with `isRefreshing` false. `status` is about the data: `loading` only while the store holds no data, that is the first load, a load after `reset()` and a load after a failed first load; `ready` as soon as data is held, and it stays `ready` during a refresh and after a failed refresh; `failed` only when no data is held. `isRefreshing` is true while a request runs with data held. So a refresh never empties the list, the details or the slot, and a screen can tell "loading for the first time" (show a skeleton) from "refreshing" (show the list, maybe a small mark). `load()` and `refresh()` are the same function and both are named in the contract (R27): with no data held it is a first load, otherwise a refresh. It calls `api.bootstrap(signal)` and on success replaces `user`, `workspace`, `people`, `conversations` and `eventNumber` with the answer, applies R14 to `details` and R20 to `unread`, empties `error` and sets `ready`; on failure it sets `error` and `failed` (no data held) or keeps all data and `ready` (data held). It never rejects: the returned promise resolves when the request has ended and the outcome is read from `status` and `error` (Decided in this spec: a screen that calls it from an effect has no rejection to handle, and the Retry of D-131 is a button that calls `refresh()` when `error` is set). While one request is running, another `load()` or `refresh()` returns the same promise and sends no second request, unless `reset()` was called in between (R11). `getEventNumber()` is kept for TOKI-039 and TOKI-040; this ticket changes it only by a load or a refresh. Check: states in order (`idle`, `loading`, `ready`) with a fake `api`; an answer with 3 channels, 2 DMs, a group, 4 people and `eventNumber` 41 gives exactly those entries, people in the server's order and 41; two `load()` calls in a row give one `bootstrap` call and one promise; a failed first load gives `failed`, the error and a promise that resolves; a refresh after a good load shows `status` `ready` and `isRefreshing` true while it runs, with the list unchanged at every moment; a failed refresh keeps the data, `ready` and sets the error; a second good load clears the error.
- R11. Reset and stale answers. `reset()` returns the store to its first state and drops the whole state, so nothing of the earlier person stays. It also forgets the request in flight: it aborts it through the `signal` it gave to `api.bootstrap`, discards the stored promise, and raises a generation number, so the next `load()` sends a new request and never reuses the promise of the earlier person. The promise of an abandoned `load()` resolves and changes no state. An answer that arrives from a request begun before a `reset()` is ignored in every case (a first load, a refresh, a command of R15, a read), also when the abort did not stop it. Reason: D-132 sets the same principle for the message kept in the browser (nothing of an earlier person stays when someone else signs in), and the store holds every person's email address and role (Data safety); the caller of `reset` is the wiring of TOKI-033 (R25). Check: start a load with a fake `api` that answers late, call `reset()`, let the answer arrive: the state is the first state and no listener was called with data; the same for a `joinChannel` begun before the reset; load, reset, load again (the second call sends a second `bootstrap` request and signals abort on the first), let both answers arrive in either order: the state holds the answer of the second request only.
- R12. Subscription and snapshots. `getState()` returns an immutable snapshot (a frozen object tree is not required, but no code mutates a snapshot already given out, and two calls with no change in between return the same object). `subscribe(listener)` returns an unsubscribe function; every change of state calls each listener once, after the state is replaced; a command or a refresh whose answer changes no state (a join of a channel already held with the same entry and detail) calls no listener. This is the shape that `useSyncExternalStore` takes. Check: a listener counts calls over `load`, a join, a join again with the same answer (no call) and `reset`; an unsubscribed listener is not called; a snapshot kept before a change is not altered by it.
- R13. The entry merge rule. The conversations of the list are `BootstrapConversation` entries (TOKI-031 R17). The answers of the channel routes carry a `ChannelDetail`, which has no level, mute or star, so a channel entry is made from it so (decided in TOKI-031, Design, "What each part returns"; this ticket owns the rule): `id`, `name`, `topic`, `isPrivate` and `isGeneral` come from the detail, `kind` is `channel`, `memberIds` is null, and `notificationLevel`, `isMuted` and `isStarred` are those the store already holds for that `id`; for an id it does not hold they are `effectiveNotificationLevel('channel', null)` of `@toki/shared` (`mentions`), false and false, the values of a new member row (D-046). The description, `createdBy`, `createdAt`, `archived` and `memberCount` are not part of the entry. A direct entry (the answer of `directConversations.open`) is stored as it is: its own level, mute and star are the stored ones of the caller's member row (TOKI-030 R18), and replace what the store held. Check: a store holding channel `c` with `all`, muted, starred receives a detail of `c` with a new topic: the entry has the new topic and `all`, true, true; a detail of an id the store does not hold gives `mentions`, false, false; a direct entry replaces the held one with its own three values; a detail with a description holds no `description` in the entry.
- R14. Details and the rule of the fresher answer. The store keeps the last answer of `channels.get` and of the commands for each channel in `details` (by id, the `ChannelDetail` or the `ChannelSummary`), so the header and Details panel (TOKI-035) read the description, creator, date and `memberCount`, and a person who opens an archived channel or a channel that is not joined reads its name and topic (TOKI-031 concern 2: such a channel is not added to the list). An answer that says the person is not a member (`isMember` false) or that the channel is archived (`archived` true) removes the entry of that id from `conversations`; an answer that says the person is a member of an active channel adds or updates the entry by R13. A `ChannelSummary` of a channel that is not joined holds no description and the store invents none. Details across a refresh (Decided in this spec): `load()` and `refresh()` keep `details`. A held detail is dropped only when the answer contradicts it: its id is in the answer's `conversations` and the detail says `isMember` false or `archived` true, or its id is not in the answer and the detail says the person is a member of an active channel (the person is no longer one); the details of archived channels and of channels the person has not joined stay. A kept detail may show an old `memberCount` until the next `readChannel` or the events of TOKI-040. So a detail stored by `restoreChannel` or kept for an archived channel survives the refresh that follows. Check: `readChannel(id)` (the store command that calls `channels.get`) with a detail of an archived channel the person is a member of: `details` has it, the list has no entry for it; the same call for a public channel that is not joined with a summary: `details` has the summary, the list has none; a held entry whose later detail says `isMember` false is removed; an active member detail adds the entry with the defaults of R13; a held detail survives a refresh whose answer agrees with it; a detail of a channel the person is no longer a member of, and a detail of a channel that the refresh lists as joined while the detail says not a member, are dropped.
- R15. Commands. The store has these commands; each calls the matching method of R9 and applies the answer when it comes (never before: there is no optimistic change here), and on an error it changes no state, calls no listener and rejects with the `ApiError`:
  Command `openDirect(userIds)`: stores the entry (R13) and resolves with `{ id, created }`.
  Command `createChannel(body)`: stores the entry and the detail from the answer (R13, R14) and resolves with `{ id, created }`; a repeat (status 200) gives `created` false and changes nothing that was not already so.
  Command `joinChannel(id)`: stores the entry and the detail from the answer (R13, R14); a new entry has the defaults.
  Command `leaveChannel(id)`: removes the entry and the detail of `id` from the state when the answer arrives (a `changed` of false also removes it, the person is not in the channel); a repeat is harmless (TOKI-029 R12).
  Command `editChannel(id, { topic?, description? })`: stores the entry and the detail from the answer (R13, R14).
  Command `archiveChannel(id)`: removes the entry (R14) and keeps the detail (`archived` true).
  Command `restoreChannel(id)`: stores the entry and the detail from the answer (the entry with the defaults) and then calls `refresh()` (R10), because the member row of a restored channel was kept by the server with its level, mute and star (TOKI-029 R14: members, files and history are kept) and the client no longer holds them; the detail stays in `details` through that refresh (R14). The command resolves when the refresh has ended. It rejects only when the restore request itself failed: a failed refresh does not reject (the restore happened), it leaves the entry with the defaults and sets `error` as R10 says, and the next `refresh()` corrects the three values. Decided in this spec: a caller (TOKI-101) must not read a rejection as "the restore failed" when it did not.
  Command `readChannel(id)`: calls `channels.get`, applies the answer by R14 and resolves with the answer (a `ChannelDetail` or a `ChannelSummary`).
  No command is given for `addMembers`, `removeMember`, `members` or `list`: they change no entry of the list, and their screens (TOKI-034, TOKI-035, TOKI-100) call the methods of R9 directly. A command applies the answer to the state as it is when the answer arrives, and R26 says what an older read or refresh does to a later command. Check: each command with a fake `api` for success (the state after, and one listener call, two for `restoreChannel`: its own answer and the refresh's) and for an error (state equal to before, no listener call, rejection with the error); each of create, join, edit and restore leaves the detail in `details`; a `leaveChannel` whose answer has `changed` false; `restoreChannel` sends `POST .../restore` and then `GET /bootstrap`, and the entry then has the level, mute and star of the bootstrap answer; a failed refresh after a restore resolves the command, keeps the entry with the defaults and sets `error`; a failed restore request rejects; the detail is still in `details` after the refresh.
- R16. Hand-offs of what the store does not do. The store has no method that saves a level, mute or star, and no method that sets a read state other than `setUnread` (R20). A request that ends the membership of the signed-in person made by another person (an Admin removes them, someone archives the channel) is seen only at the next `refresh()` or `readChannel` until TOKI-040 applies events; the store offers `refresh()` for the caller to use, and calls it by itself nowhere except R15 (`restoreChannel`). Check: a search of the package for `refresh(` finds the definition, the one call of R15 and the tests.
- R17. Names. `getConversationName(id)` returns the text a row shows: the `name` of a channel; for a `dm` the `displayName` of the other person in `memberIds` (the one that is not `user.id`); for a `group_dm` the `displayName` of every person in `memberIds` except the signed-in person, ordered by the collator of R18 and joined with `, `. The name is made from the `displayName` of the members, the only name data that `BootstrapPerson` carries (TOKI-031 R5: `id`, `displayName`, `role`, `status`): a group of Alex Phạm and Thu Hoàng is named `Alex Phạm, Thu Hoàng`. The prototype shows `Alex, Thu`, but it writes that name as a literal and keeps a separate short name (`first`) for each person, and F09 says only "the members' names"; the store has no short name and does not claim to reproduce the prototype's text. Whether a group is named by short names, and how a short name is made, is not decided (concern 12); a screen shortens a long name with an ellipsis. TOKI-035 R2 and TOKI-033 expect what this function returns, so their examples and tests use the full names until concern 12 is answered. A person who is not in `people` adds no part, and a conversation with no known person has the name `""` (the server returns every person of every conversation it returns, TOKI-031 R10, so this is not reached with a real answer; the screen shows nothing rather than an id). A deactivated person's name stays as it is (TOKI-031 R19). The comma and the space are not translated text. Check: a channel, a DM, a group of three with names given out of order, a group whose second person is missing from `people`, and a DM with a deactivated person.
- R18. Order. One collator `Intl.Collator('vi', { sensitivity: 'accent' })` compares names (it ignores case and keeps accents, so `Anh` and `Ánh` are different people and are ordered, not left to the id); a tie is broken by `id` in code-point order, so the order is the same on every run. Channels are ordered alphabetically by `name` (F09). Direct conversations (a `dm` and a `group_dm` together) are ordered by their name from R17 until the latest message of a conversation exists: F09 says "most recent message" and the response of TOKI-031 has no such field (its concern 1 is open), so the comparator is one function, `compareDirect`, that the ticket delivering the field changes. The Starred group is ordered by name, channels and direct conversations mixed (concern 6; F09 does not say). ## Design
### Where the code lives
```
packages/client-core/
├─ package.json                  adds @toki/shared and the schema library
└─ src/
   ├─ index.ts                   exports (R1)
   ├─ api/
   │  ├─ client.ts               createApiClient, request, the typed methods (R2, R5 to R7, R9)
   │  ├─ errors.ts               ApiError (R4)
   │  ├─ parse.ts                the reading of a good answer, unknown keys dropped (R3)
   │  ├─ classify.ts             classifyApiError (R8)
   │  └─ *.test.ts
   └─ conversations/
      ├─ store.ts                state, subscribe, load, reset, commands (R10 to R16)
      ├─ merge.ts                the entry merge rule (R13, R14)
      ├─ names.ts                getConversationName, collator (R17, R18)
      ├─ selectors.ts            getList and the lookups (R19 to R23)
      └─ *.test.ts
apps/web/src/client.ts           the one client and the one store (R25)
```
The two folders do not import each other except `conversations` importing the types of `api`. `auth/` (TOKI-023) is a third folder that imports neither.

### Why a store of our own
The conversation data lives in this store and not in the Query cache of `apps/web` (TOKI-006 R5). Reason: the technical design says "server data in the `client-core` cache" and that the decisions about what to show live in `client-core`; the store must run in React Native, where TanStack Query is not a dependency of `client-core`; and the list is built from several answers (the first load, a join, an archive) that must merge by one rule (R13), which a cache keyed by request does not do. The store is plain TypeScript with `subscribe` and `getState`, so `ui-web` reads it with `useSyncExternalStore` and adds no dependency to `client-core`. TOKI-006's concern 6, where the Query client lives for other server data (messages, search), stays open; this ticket decides only the data above. Decided in this spec.

### Reading an answer
The schemas of TOKI-031 are strict and say that unknown keys fail. The client turns the strictness off for an answer it receives (R3): the web app and the server ship together and a page that is too old is reloaded (NFR-17), but a phone app of phase 3 will lag behind the server, and the API only adds fields within a version. The exported schemas are not touched: `api/parse.ts` derives the lenient reading, and the builder chooses the mechanism (a walk over the schema that turns each object into a non-strict one, or a helper that removes the keys named in the `unrecognized_keys` issues and parses again, taking care that for a union those issues are nested in the union's errors and not at the top), and the tests of R3 decide. For a union the branch is chosen by its identifying keys (R3), never by the first branch that happens to parse. A wrong or missing known key still fails, so a change that breaks the contract is seen. Decided in this spec.

### The entry merge, in a table
| Answer | Entry in `conversations` | Entry in `details` |
| :---- | :---- | :---- |
| Bootstrap (load or refresh) | Every entry of the answer replaces the earlier list, except ids a command touched meanwhile (R26) | Kept; only a detail the answer contradicts is dropped (R14) |
| `directConversations.open` | The entry, with its own level, mute, star | none (a DM has no detail) |
| Channel detail, member, active | Added or updated by R13 | The detail |
| Channel detail, archived | Removed | The detail |
| Channel summary, not a member | Removed if held | The summary |
| `leave` | Removed | Removed |
| `restore` | Added with defaults, then refreshed | The detail, kept through the refresh |

### Errors
| Case | Result |
| :---- | :---- |
| A 401 with `unauthenticated`, `session_ended`, `account_deactivated` | The hook is called, the request rejects, kind `http` (R7) |
| 4xx and 5xx with a conforming body | `ApiError` with `code`, `message`, `details` (R4) |
| 4xx and 5xx with a body that is not the error format | `ApiError` with `code` null (R4) |
| No answer in 10 seconds, no connection | `timeout`, `network` (R5) |
| A 2xx body that does not fit the schema | `invalid_response` (R3) |

The meaning of a code (`channel_name_taken` under the name field, `group_too_large` as the limit message of F25) is the screen's, which maps `error.code` to an `@toki/i18n` key (TOKI-017 Design). The client only gives the `code` and the kind of screen (R8).

## Data safety
- The store holds the caller's email address (`user`) and every person's name and role, and lives in memory only; nothing is written to browser storage by this ticket (an offline cache is TOKI-040's, and `reset()` at a change of person, R11, follows the principle of D-132).
- `ApiError` never holds a request body, a cookie or a header (R4). Nothing in the package logs.
- A private channel or DM of another person is never in the store, because the server never sends it (TOKI-031 R18); the store adds nothing from another source.

Decided in this spec: the client takes a `timers` object and the web app lends it (R5, R25), because TOKI-008 R19 bans timer functions in `client-core` and its clock has no timer. 4. Where the connection of the unauthenticated answer lives. Decided in this spec: this ticket owns it. The client has a hook and a setter (R7), `apps/web/src/client.ts` is this ticket's file and calls `api.setOnUnauthenticated(reportUnauthenticated)` (R25), and TOKI-023 supplies `reportUnauthenticated` and moves its sign-in calls to `api.request`. TOKI-023 R39 and its concern 12 say that whichever ticket builds the shared client must report every 401; this is that ticket. If TOKI-023 is not yet in the tree, the line is left to it as R25 says, and the hand check of TOKI-023 includes "a 401 on `bootstrap` shows the modal". The status codes of `validation_error` (TOKI-022) and `validation_failed` (TOKI-004) differ in name for the same case: the client reads no such code (R8 uses the status), so it is not affected; the two specs need one name. Owner: Thanh Truong.

12. The name of a group direct message. Not decided. The prototype shows `Alex, Thu` for Alex Phạm and Thu Hoàng, written as a literal with a separate short name per person; `BootstrapPerson` has no short name and F09 says only "the members' names", and no decision in the log sets the rule. R17 uses the full `displayName` of each member, so the group of the prototype reads `Alex Phạm, Thu Hoàng`. Proposal only, not a decision: shorten each name to its first word, which gives `Alex, Thu` here; a Vietnamese name usually puts the given name last, so for many people the first word is the family name, and a stored short name (a field TOKI-031 adds to `BootstrapPerson`) would be more exact.
