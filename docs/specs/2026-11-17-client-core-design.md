# client-core: API client and conversation store design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/client-core.md (Thanh Truong)
Ticket: TOKI-032

## Goal
The screens of the sidebar, Browse channels, the people picker and the conversation header all need the same data and the same rules: one way to call the server and read an error, and one list of conversations with its groups, filters, names and settings. This work builds both in `packages/client-core`: an API client typed from the shared schemas, and a conversation store that takes the first load (`GET /api/v1/bootstrap`, TOKI-031), applies the answers of the channel and direct-message requests (TOKI-029, TOKI-030) and gives screens the list already grouped, filtered and named. It holds no text and uses no browser API, so a React hook now and a phone screen later read the same code.

## Scope
- In:
  - The API client: the request core, the error type, the reading of answers with the shared schemas, the 10-second timeout, the report of unauthenticated answers, the mapping of an error to a kind of screen (D-131), and one typed method for each route of the bootstrap, channel and direct-conversation requests (R1 to R9).
  - The conversation store: state, subscription, the first load and its refresh, the merge of channel answers into entries, the commands that change the list, and reset (R10 to R16).
  - The selectors: names, the grouped list, order, search, filters, lookups (R17 to R23).
  - A small wiring file in `apps/web` that creates the one client and the one store (R25).
  - Unit tests in `packages/client-core` (Vitest, no browser, no database, fake `fetch`).
- Out (not now):
  - Any screen, hook, text or style: TOKI-033 (the list), TOKI-034, TOKI-035. This ticket adds no file in `packages/ui-web`, `packages/i18n` or `packages/tokens`.
  - Where the open collapsed groups, the chosen filter and the search text are kept, and their storage per device (F09): TOKI-033. The store takes the filter and the search text as arguments of a selector and keeps neither.
  - The session state, `reportUnauthenticated` and the sign-in calls: TOKI-023 (`packages/client-core/src/auth/`). This ticket gives its API client a hook for unauthenticated answers (R7) and does not import `auth/`.
  - The WebSocket, events, optimistic send, the queue of unsent messages and the saved cache for offline use: TOKI-038, TOKI-040. The store is in memory only.
  - Unread counts and the mention mark: the read pointer, TOKI-053. This ticket defines the slot they fill and the filter rules over it (R20).
  - Saving the person's notification level, mute and star: no ticket owns the request (TOKI-031 concern 5); no client method or store command exists for it here (concern 9).
  - Messages, threads, files, drafts, reactions, presence: each belongs to its own ticket.
  - A generator of UUIDv7 ids for the client: not built here (concern 11).
  - Token sessions and the `Authorization` header for the phone app: phase 3. The client sends the browser's cookie and nothing else.

## Requirements
- R1. Package. `@toki/client-core` declares `@toki/shared` as a `workspace:*` dependency (TOKI-001 left every internal link but two to the ticket that needs it) and the schema library of `@toki/shared` at the same version, and exports from `src/index.ts`: `createApiClient`, `ApiError`, `classifyApiError`, `createConversationStore` and the types of this spec. No file of the package uses a global outside the allow list of TOKI-002 rule 1 (`fetch`, `AbortController`, `AbortSignal`, `URL`, `URLSearchParams`, `Headers`, `Response` and the language built-ins, `Intl` included), imports `@toki/platform/web`, or calls `Date.now()`, `new Date()`, `setTimeout` or `setInterval` (TOKI-008 R19). Check: `pnpm lint`, `pnpm lint:boundaries` and `pnpm typecheck` exit 0; the R19 search script of TOKI-008 finds no match in `packages/client-core/src`; `pnpm ls --filter @toki/client-core` lists `@toki/shared`.
- R2. Request core. `createApiClient(options)` takes `{ baseUrl?, fetch?, timers?, requestTimeoutMs?, onUnauthenticated? }`. `baseUrl` defaults to `/api/v1`; `fetch` defaults to the global `fetch` read when a request is sent, not when the client is made; `requestTimeoutMs` defaults to 10 000 (D-126). The core method `request({ method, path, query?, body?, schema, signal? })` sends `baseUrl + path`, the query with every `undefined` value left out and values written with `URLSearchParams`, with the credentials mode `same-origin` and the header `Accept: application/json`. When `body` is given it sends the JSON text and `Content-Type: application/json`; when it is not given it sends no body and no `Content-Type` (TOKI-022 R45 refuses other types; the four body-less routes of TOKI-029 accept none). It sets no `Origin` header (TOKI-022 R46: the browser sets it). Check: with a fake `fetch` that records its arguments: a `GET` with `{ search: "a b", limit: undefined }` sends `?search=a+b`; a `POST` with a body sends the text and the JSON type; a `POST` with no body sends neither a body nor a `Content-Type`; no sent header is named `Origin`; a client made before `globalThis.fetch` is replaced uses the replacement.
- R3. Reading a good answer. A 2xx answer whose body is JSON is parsed with `schema` (a shared schema). A 204 answer, and an answer to a route declared with no body, returns `undefined`. A key that the schema does not know is dropped and does not fail the parse, at every level, a conversation entry and a member included; a missing key, a value of the wrong type or a value outside an enum (a `notificationLevel` of `loud`) fails with an `ApiError` of kind `invalid_response` (R4) that holds the status and no body text. Decided in this spec (concern 1): the shared schemas of TOKI-031 are strict, which is right for the server's tests and wrong for a client that must keep working when the API adds a field (technical design: within a version, fields are only added). Check: the body of a rich fixture parses; the same body with one added key at the top level, in `user`, in a `members` item, in a channel entry and in a direct entry parses and the result has none of the added keys; a body with a missing `eventNumber`, a `notificationLevel` of `loud`, a `memberIds` that is null for a `dm`, and a body that is not JSON each give kind `invalid_response`; the check is made on `BootstrapResponse`, on `ChannelDetail` and on the direct-conversation response.
- R4. The error type. `ApiError` extends `Error` and has `kind` (`http`, `network`, `timeout`, `aborted`, `invalid_response`), `status` (a number for `http` and `invalid_response`, else null), `code` (the `error.code` of the body for `http`, else null), `message` (the English developer text of the body, else a fixed English text), `details` (the `details` of the body or null) and `requestId` (the string `details.requestId` when it is one, else null; the error ID that D-131 shows with Retry). A non-2xx answer whose body passes the error schema of TOKI-004 is kind `http` with those fields. A non-2xx answer whose body does not pass it (an HTML page from a proxy, an empty body, text) is kind `http` with `code` null and `details` null, and the body is not copied into the error. `ApiError` never holds the request body, the cookie or the response headers. Check: one test for each kind; a 502 with an HTML body gives kind `http`, status 502, code null; a 409 with `{ error: { code: "channel_archived", message, details: { x: 1 } } }` gives code and details; a 500 with `details.requestId` gives `requestId`; `JSON.stringify` of an error holds none of the strings of a request body sent in the test.
- R5. Network and timeout. When `fetch` rejects, the request ends with kind `network` and status null. When no answer has arrived after `requestTimeoutMs`, counted with the injected `timers.after(ms, fn)` (returns a function that cancels), the request is aborted through an `AbortController` and ends with kind `timeout`; the timer is cancelled when the answer arrives or the request fails. When the caller's `signal` aborts, the request ends with kind `aborted` and no other kind. If no `timers` is given there is no timeout. Check, with a fake `fetch` that never answers and a fake `timers` that records the delay and fires on demand: the delay is 10 000, firing it ends the request with kind `timeout` and the fetch's signal is aborted; an answer before the fire cancels the timer (the fake counts one cancel); a rejecting `fetch` gives `network`; aborting the caller's signal gives `aborted`; with a `requestTimeoutMs` of 8 000 the delay is 8 000. Reason for `timers`: TOKI-008 R19 allows no timer function in `client-core` and its clock has `now()` only, so the web app lends the one timer function (R25).
- R6. No automatic retry. The client sends each request once and does not repeat one after an error. Retry belongs to the screen after D-131 (a button) and to the sync engine for messages (TOKI-040). Check: a fake `fetch` that fails once is called once; the error reaches the caller.
- R7. Unauthenticated answers. When an answer is 401 with the code `unauthenticated`, `session_ended` or `account_deactivated` (TOKI-022 R24, R27), the client calls `onUnauthenticated(code)` once and then ends the request with the `ApiError` as for any error. The client has a method `setOnUnauthenticated(fn | null)` to set or replace the hook after it was made. A throwing hook does not change the error that the caller receives. No other code, and no other status, calls the hook, and a 200 never does. Check: three 401 answers with the three codes call the hook with each code, once each, and each request still rejects with the `ApiError`; a 401 with another code, a 403 and a 500 do not call it; a hook that throws leaves the rejection as the `ApiError`; a hook set with `setOnUnauthenticated` after the client was made is called, and `null` removes it.
- R8. Which kind of screen an error leads to (D-131). `classifyApiError(error)` returns one of `unauthenticated` (a 401 of R7), `field` (400), `no_access` (403 and 404, the one shared page), `fresh_copy` (409 and 410), `wait` (429), `retry` (5xx, `network`, `timeout`, and `invalid_response`, whose error ID is `requestId` when present), `ignore` (`aborted`) and `unknown` (any other status, including a 401 with another code, and an `http` error with a status below 400). It reads the status and the kind, and the code only for R7's three codes. Check: a table test of every row above, and `classifyApiError` of a value that is not an `ApiError` returns `unknown`. Source: D-131 (400 field message, 403 and 404 one shared page, 409 and 410 fresh copy, 429 wait, 5xx Retry with an error ID), D-126 (no answer counts as failed and shows Retry).
- R9. Typed methods. The client has these methods, each calling `request` with the schema of the response from `packages/shared` and sending exactly what the route of the other spec takes:

  | Method | Request | Answer |
  | :---- | :---- | :---- |
  | `bootstrap()` | `GET /bootstrap` | `BootstrapResponse` (TOKI-031 R17) |
  | `channels.create(body)` | `POST /channels` with `{ id, name, isPrivate?, topic?, memberIds? }` | `{ channel: ChannelDetail }` (TOKI-029 R3; 200 for a repeat, R5 there) |
  | `channels.list({ search?, limit?, cursor? })` | `GET /channels` | `{ channels: ChannelSummary[], nextCursor }` (R6) |
  | `channels.get(id)` | `GET /channels/{id}` | `{ channel: ChannelDetail \| ChannelSummary }` (R7) |
  | `channels.members(id, { limit?, cursor? })` | `GET /channels/{id}/members` | `{ members: { userId, joinedAt }[], nextCursor }` (R8) |
  | `channels.update(id, { topic?, description? })` | `PATCH /channels/{id}` | `{ channel: ChannelDetail, changed }` (R9) |
  | `channels.join(id)` | `POST /channels/{id}/join`, no body | `{ channel: ChannelDetail, changed }` (R10) |
  | `channels.addMembers(id, userIds)` | `POST /channels/{id}/members` with `{ userIds }` | `{ added, alreadyMembers }` (R11) |
  | `channels.leave(id)` | `POST /channels/{id}/leave`, no body | `{ changed, archived }` (R12) |
  | `channels.removeMember(id, userId)` | `DELETE /channels/{id}/members/{userId}` | `{ changed }` (R13) |
  | `channels.archive(id)`, `channels.restore(id)` | `POST /channels/{id}/archive` or `/restore`, no body | `{ channel: ChannelDetail, changed }` (R14) |
  | `directConversations.open(userIds)` | `POST /direct-conversations` with `{ userIds }` | `{ conversation: DirectConversationEntry }`, status 200 or 201 (TOKI-030 R18) |

  The schemas are the ones TOKI-029 R17 and TOKI-030 R17 export; this ticket writes none of its own, and does not re-check the rules of the server (a name pattern, a limit) before sending: the server's answer is the rule. A path part (`id`, `userId`) is put in the address with `encodeURIComponent`. `directConversations.open` also returns whether the conversation was created (`created`: status 201). Check: one test per row with a fake `fetch`: the method, the path, the query, the body and the use of the right response schema (a valid body is returned, an invalid one is `invalid_response`); an `id` of `a/b` is sent as `a%2Fb`; `open` returns `created` true for 201 and false for 200.
- R10. Store state and first load. `createConversationStore({ api })` returns a store whose state holds: `status` (`idle`, `loading`, `ready`, `failed`), `error` (an `ApiError` or null), `user`, `workspace`, `people` (by id, in the order the server sent), `conversations` (by id), `details` (R14), `unread` (R20) and `eventNumber`. It starts `idle` and empty. `load()` sets `loading`, calls `api.bootstrap()` and on success replaces `user`, `workspace`, `people`, `conversations` and `eventNumber` with the answer, empties `error` and sets `ready`; on failure it sets `error`, and `failed` when it never loaded, or keeps the earlier data and `ready` when it did (the screen then offers Retry from `error`). `load()` and `refresh()` are the same call: while one is running, another returns the same promise and sends no second request. `load()` returns the promise of the end of the load and rejects with the `ApiError`. The store keeps `eventNumber` for TOKI-039 and TOKI-040 to read (`getEventNumber()`); this ticket does not change it afterwards. Check: states in order (`idle`, `loading`, `ready`) with a fake `api`; an answer with 3 channels, 2 DMs, a group, 4 people and `eventNumber` 41 gives exactly those entries, people in the server's order and 41; two `load()` calls in a row give one `bootstrap` call and one promise; a failed first load gives `failed` and the error; a failed refresh after a good load keeps the data, `ready` and the error; a second good load clears the error.
- R11. Reset and stale answers. `reset()` returns the store to its first state and drops the whole state, so nothing of the earlier person stays (D-132 says the data kept in the browser is dropped when someone else signs in; the caller of `reset` is the wiring, R25). An answer that arrives from a request begun before a `reset()` is ignored: it changes no state, also when it is a first load, a command (R15) or a refresh. Check: start a load with a fake `api` that answers late, call `reset()`, let the answer arrive: the state is the first state and no listener was called with data; the same for a `joinChannel` begun before the reset.
- R12. Subscription and snapshots. `getState()` returns an immutable snapshot (a frozen object tree is not required, but no code mutates a snapshot already given out, and two calls with no change in between return the same object). `subscribe(listener)` returns an unsubscribe function; every change of state calls each listener once, after the state is replaced; a command whose answer changes no entry (a join of a channel already held with the same values) calls no listener. This is the shape that `useSyncExternalStore` takes. Check: a listener counts calls over `load`, a join, a join again with the same answer (no call) and `reset`; an unsubscribed listener is not called; a snapshot kept before a change is not altered by it.
- R13. The entry merge rule. The conversations of the list are `BootstrapConversation` entries (TOKI-031 R17). The answers of the channel routes carry a `ChannelDetail`, which has no level, mute or star, so a channel entry is made from it so (decided in TOKI-031, Design, "What each part returns"; this ticket owns the rule): `id`, `name`, `topic`, `isPrivate` and `isGeneral` come from the detail, `kind` is `channel`, `memberIds` is null, and `notificationLevel`, `isMuted` and `isStarred` are those the store already holds for that `id`; for an id it does not hold they are `effectiveNotificationLevel('channel', null)` of `@toki/shared` (`mentions`), false and false, the values of a new member row (D-046). The description, `createdBy`, `createdAt`, `archived` and `memberCount` are not part of the entry. A direct entry (the answer of `directConversations.open`) is stored as it is: its own level, mute and star are the stored ones of the caller's member row (TOKI-030 R18), and replace what the store held. Check: a store holding channel `c` with `all`, muted, starred receives a detail of `c` with a new topic: the entry has the new topic and `all`, true, true; a detail of an id the store does not hold gives `mentions`, false, false; a direct entry replaces the held one with its own three values; a detail with a description holds no `description` in the entry.
- R14. Details and the rule of the fresher answer. The store keeps the last answer of `channels.get` and of the commands for each channel in `details` (by id, the `ChannelDetail` or the `ChannelSummary`), so the header and Details panel (TOKI-035) read the description, creator, date and `memberCount`, and a person who opens an archived channel or a channel that is not joined reads its name and topic (TOKI-031 concern 2: such a channel is not added to the list). An answer that says the person is not a member (`isMember` false) or that the channel is archived (`archived` true) removes the entry of that id from `conversations`; an answer that says the person is a member of an active channel adds or updates the entry by R13. A `ChannelSummary` of a channel that is not joined holds no description and the store invents none. Check: `readChannel(id)` (the store command that calls `channels.get`) with a detail of an archived channel the person is a member of: `details` has it, the list has no entry for it; the same call for a public channel that is not joined with a summary: `details` has the summary, the list has none; a held entry whose later detail says `isMember` false is removed; an active member detail adds the entry with the defaults of R13.
- R15. Commands. The store has these commands; each calls the matching method of R9 and applies the answer when it comes (never before: there is no optimistic change here), and on an error it changes no state, calls no listener and rejects with the `ApiError`:
  Command `openDirect(userIds)`: stores the entry (R13) and returns `{ id, created }`.
  Command `createChannel(body)`: stores the entry from the detail (R13) and returns the id; a repeat (status 200) changes nothing that was not already so.
  Command `joinChannel(id)`: stores the entry from the detail (R13); a new entry has the defaults.
  Command `leaveChannel(id)`: removes the entry and the detail of `id` from the state when the answer arrives (a `changed` of false also removes it, the person is not in the channel); a repeat is harmless (TOKI-029 R12).
  Command `editChannel(id, { topic?, description? })`: stores the entry and the detail from the answer (R13, R14).
  Command `archiveChannel(id)`: removes the entry (R14) and keeps the detail (`archived` true).
  Command `restoreChannel(id)`: stores the entry from the detail with the defaults and then calls `refresh()` (R10), because the member row of a restored channel was kept by the server with its level, mute and star (TOKI-029 R14: members, files and history are kept) and the client no longer holds them; the command ends when the refresh has ended, and a failed refresh leaves the entry with the defaults and rejects with its error. Decided in this spec.
  Command `readChannel(id)`: R14.
  No command is given for `addMembers`, `removeMember`, `members` or `list`: they change no entry of the list, and their screens (TOKI-034, TOKI-035, TOKI-100) call the methods of R9 directly. A command applies the answer to the state as it is when the answer arrives, so two commands in flight apply in the order of their answers. A command answered while a `load()` is running is applied; when the load's answer then arrives, it replaces the state and an entry that was in no snapshot is lost until the next `refresh()` (a known limit, closed by the events of TOKI-040; Decided in this spec because the alternative, holding commands behind the load, delays a person's own action). Check: each command with a fake `api` for success (the state after, and one listener call) and for an error (state equal to before, no listener call, rejection with the error); a `leaveChannel` whose answer has `changed` false; `restoreChannel` sends `POST .../restore` and then `GET /bootstrap`, and the entry then has the level, mute and star of the bootstrap answer; a failed refresh after a restore.
- R16. Hand-offs of what the store does not do. The store has no method that saves a level, mute or star, and no method that sets a read state other than `setUnread` (R20). A request that ends the membership of the signed-in person made by another person (an Admin removes them, someone archives the channel) is seen only at the next `refresh()` or `readChannel` until TOKI-040 applies events; the store offers `refresh()` for the caller to use, and calls it by itself nowhere except R15 (`restoreChannel`). Check: a search of the package for `refresh(` finds the definition, the one call of R15 and the tests.
- R17. Names. `getConversationName(id)` returns the text a row shows: the `name` of a channel; for a `dm` the `displayName` of the other person in `memberIds` (the one that is not `user.id`); for a `group_dm` the `displayName` of every person in `memberIds` except the signed-in person, ordered by the collator of R18 and joined with `, ` (the prototype's group is named "Alex, Thu" for Alex and Thu). A person who is not in `people` adds no part, and a conversation with no known person has the name `""` (the server returns every person of every conversation it returns, TOKI-031 R10, so this is not reached with a real answer; the screen shows nothing rather than an id). A deactivated person's name stays as it is (TOKI-031 R19). The comma and the space are not translated text. Check: a channel, a DM, a group of three with names given out of order, a group whose second person is missing from `people`, and a DM with a deactivated person.
- R18. Order. One collator `Intl.Collator('vi', { sensitivity: 'base' })` compares names; a tie is broken by `id` in code-point order, so the order is the same on every run. Channels are ordered alphabetically by `name` (F09). Direct conversations (a `dm` and a `group_dm` together) are ordered by their name from R17 until the latest message of a conversation exists: F09 says "most recent message" and the response of TOKI-031 has no such field (its concern 1 is open), so the comparator is one function, `compareDirect`, that the ticket delivering the field changes. The Starred group is ordered by name, channels and direct conversations mixed (concern 6; F09 does not say). Check: a list of channels `b`, `a-1`, `a`, `10`, `9` gives `10`, `9`, `a`, `a-1`, `b` under the rule stated by the collator (the test writes the expected list by running no code of the store); direct names `Trần`, `Tran`, `Ánh`, `Anh` with different ids give the same order on two runs and on a shuffled input; a tie of two names is broken by id.
- R19. Search. A query keeps the conversations whose name from R17 contains the query, ignoring case, as the prototype's search does (`toLowerCase` and `includes`). Both sides are put in Unicode form NFC first (a name typed on one device in a decomposed form still matches), and the query is trimmed of white space at both ends, so a trailing space typed after a name does not hide it (Decided in this spec; the prototype does not trim). An empty query keeps everything. Diacritics are not folded: `an` does not find `Ánh` (concern 8). Check: `Pro` finds `project-launch`; `PRO` finds it; `  launch ` finds it; a decomposed `Trần` equivalent query finds `Trần`; `anh` finds `Anh` and not `Ánh`; a query that matches nothing gives empty groups.
- R20. Filters and the unread slot. The state holds `unread`, a record by conversation id of `{ count: number, mention: boolean }`; an id with no record counts as `{ 0, false }`. `setUnread(id, value)` sets one record and `clearUnread(id)` removes it; they are the way the read pointer (TOKI-053) fills the slot, and no other code writes it. The filter `all` keeps everything, `unread` keeps a conversation whose `count` is above 0, `mentions` keeps one whose `mention` is true; these are the prototype's rules (`unread>0`, `mention`). A conversation that is muted is kept or not by the same rule: whether the muted ones are left out of Unread is not decided (concern 7). With no record in the slot, which is the case until TOKI-053, `unread` and `mentions` keep nothing. Check: with records for three conversations (count 2, count 0, mention true) the three filters give the expected ids; without records `unread` and `mentions` give empty groups; a muted conversation with count 3 is kept by `unread` (the interim rule of concern 7); `reset()` empties the slot.
- R21. The list. `getList({ query?, filter? })` (defaults: empty query, `all`) returns `{ starred, channels, direct, isEmpty }`: `starred` holds every kept conversation with `isStarred` true, of any kind; `channels` every kept channel that is not starred; `direct` every kept `dm` and `group_dm` that is not starred; each array is ordered by R18; `isEmpty` is true when the three are empty (the screen then shows its empty state, F09, D-074) and `false` otherwise. A group is an empty array when nothing is in it; hiding an empty group is the screen's (F09). A row is `{ id, kind, name, isPrivate, isGeneral, isStarred, isMuted, notificationLevel, unreadCount, hasMention, otherPersonId }`: `name` from R17, `unreadCount` and `hasMention` from the slot of R20 (raw, so the screen applies the rules of mute, D-103: "Mute also hides the unread badge and bold"), and `otherPersonId` the id of the other person for a `dm` and null for the rest, so the screen reads the person (presence, status, the deactivated state, TOKI-079 and TOKI-035) with `getPerson`. A row holds no description, no topic, no member list and no time. Check: a fixture of 3 channels (one private, one starred), 2 DMs (one starred), 1 group and #general gives the expected ids in each array; a starred DM is in `starred` and not in `direct`; a filter or a query that matches nothing gives `isEmpty` true and three empty arrays; the keys of a row equal the list above; a deactivated person's DM stays in `direct` with `otherPersonId` set.
- R22. Stable results. `getList` and the other selectors return the same object, by reference, when called again with equal arguments and with no change of state in between, and a new object after a change of state; a change that does not touch the conversations, people or slot (for example `error`) keeps the result of `getList`. Check: two calls give `===` results; after `setUnread` the result is a new object; after a state change that only sets `error` the result of `getList` is the same object; changing the query gives a new result and does not make the names compute again (a counter on the person lookup shows the names are worked out once per state).
- R23. Lookups. The store exposes: `getConversation(id)` (the entry, or undefined), `hasConversation(id)`, `getGeneralId()` (the id of the entry with `isGeneral` true, or null), `getPerson(id)` (`{ id, displayName, role, status }` or undefined, also for a deactivated person), `getPeople()` (all of them, in the server's order: no filter on status, which the screens that list people apply, TOKI-031 R19), `getUser()`, `getWorkspace()`, `getChannelDetail(id)` (R14), `getMemberCount(id)` (for a `dm` or `group_dm` the length of `memberIds`, for a channel the `memberCount` of its detail, undefined when the detail is not held) and `getEventNumber()`. These read the state and send no request. Check: a test of each against the fixture, including a deactivated person in `getPeople()` and `getMemberCount` for a group of 8, a channel with a held detail and a channel without one.
- R24. No text and no time. The package holds no sentence that a person reads, no key of `@toki/i18n` and no call of it, and reads no clock (the store has no timestamp). Check: a search of `packages/client-core/src` outside tests for a quoted string with a space and a letter that is not an English developer message of R4 or the `", "` of R17 finds nothing the review cannot explain; `packages/client-core/package.json` has no dependency on `@toki/i18n`.
- R25. The wiring in the web app. `apps/web/src/client.ts` exports one `api` (made with `createApiClient` and a `timers` object whose `after(ms, fn)` calls `setTimeout` and returns a function that calls `clearTimeout`), one `conversations` store made with it, and `setOnUnauthenticated` that calls the client's. ## Design
### Where the code lives
```
packages/client-core/
├─ package.json                  adds @toki/shared and the schema library
└─ src/
   ├─ index.ts                   exports (R1)
   ├─ api/
   │  ├─ client.ts               createApiClient, request, the typed methods (R2, R5 to R7, R9)
   │  ├─ errors.ts               ApiError (R4)
   │  ├─ parse.ts                the reading of a good answer, unknown keys dropped (R3)
   │  ├─ classify.ts             classifyApiError (R8)
   │  └─ *.test.ts
   └─ conversations/
      ├─ store.ts                state, subscribe, load, reset, commands (R10 to R16)
      ├─ merge.ts                the entry merge rule (R13, R14)
      ├─ names.ts                getConversationName, collator (R17, R18)
      ├─ selectors.ts            getList and the lookups (R19 to R23)
      └─ *.test.ts
apps/web/src/client.ts           the one client and the one store (R25)
```
The two folders do not import each other except `conversations` importing the types of `api`. `auth/` (TOKI-023) is a third folder that imports neither.

### Why a store of our own
The conversation data lives in this store and not in the Query cache of `apps/web` (TOKI-006 R5). Reason: the technical design says "server data in the `client-core` cache" and that the decisions about what to show live in `client-core`; the store must run in React Native, where TanStack Query is not a dependency of `client-core`; and the list is built from several answers (the first load, a join, an archive) that must merge by one rule (R13), which a cache keyed by request does not do. The store is plain TypeScript with `subscribe` and `getState`, so `ui-web` reads it with `useSyncExternalStore` and adds no dependency to `client-core`. TOKI-006's concern 6, where the Query client lives for other server data (messages, search), stays open; this ticket decides only the data above. Decided in this spec.

### Reading an answer
The schemas of TOKI-031 are strict and say that unknown keys fail. The client turns the strictness off for an answer it receives (R3): the web app and the server ship together and a page that is too old is reloaded (NFR-17), but a phone app of phase 3 will lag behind the server, and the API only adds fields within a version. The mechanism (a helper that removes the keys named in the `unrecognized_keys` issues of the strict parse and parses again, or a derived non-strict schema) is the builder's choice; the tests of R3 decide. A wrong or missing known key still fails, so a change that breaks the contract is seen. Decided in this spec.

### The entry merge, in a table
| Answer | Entry in `conversations` | Entry in `details` |
| :---- | :---- | :---- |
| Bootstrap | Every entry of the answer replaces the earlier list | none; the list of details is emptied |
| `directConversations.open` | The entry, with its own level, mute, star | none (a DM has no detail) |
| Channel detail, member, active | Added or updated by R13 | The detail |
| Channel detail, archived | Removed | The detail |
| Channel summary, not a member | Removed if held | The summary |
| `leave` | Removed | Removed |
| `restore` | Added with defaults, then refreshed | The detail |

### Errors
| Case | Result |
| :---- | :---- |
| A 401 with `unauthenticated`, `session_ended`, `account_deactivated` | The hook is called, the request rejects, kind `http` (R7) |
| 4xx and 5xx with a conforming body | `ApiError` with `code`, `message`, `details` (R4) |
| 4xx and 5xx with a body that is not the error format | `ApiError` with `code` null (R4) |
| No answer in 10 seconds, no connection | `timeout`, `network` (R5) |
| A 2xx body that does not fit the schema | `invalid_response` (R3) |

The meaning of a code (`channel_name_taken` under the name field, `group_too_large` as the limit message of F25) is the screen's, which maps `error.code` to an `@toki/i18n` key (TOKI-017 Design). The client only gives the `code` and the kind of screen (R8).

## Testing
- Written test-first, with Vitest in `packages/client-core` (TOKI-008 R1, R12): no browser, no database, no real network. The `fetch` is a function made by the test that records the request and returns a `Response` built by the test; the `timers` is a fake that records the delay and fires on demand; the `api` of the store tests is a fake object with the methods of R9. No test reads the system clock.
- Fixtures: a rich bootstrap body (3 channels with one private and one starred, #general, 2 DMs, a group, 4 people with a deactivated one), written with made-up names and ids, and parsed in the test with the schema of `@toki/shared` so that a change of the contract fails here. The fixture is the one value that TOKI-031's own tests also use if that ticket exports a builder; otherwise this ticket writes its own.
- R1: lint, boundaries, typecheck and the search script. R2 to R9: one test per row as stated. R10 to R16: the store with the fake `api`, including the late answer after `reset()`. R17 to R23: the selectors on the fixture, including the shuffled-input check for order and the reference-equality checks. R24: the search. R25: the search, the timer unit test and the build.
- The collator check does not depend on the machine: Node 22 is pinned (TOKI-001) and its ICU holds the `vi` data; the test states the expected order as literal arrays.
- Hand check once, output in the pull request: with the server and the web app of `pnpm dev` and the first Admin signed in, call `conversations.load()` from the browser console through a temporary import and read `getList()`: one group, `channels`, with #general.

## Data safety
- The store holds the caller's email address (`user`) and every person's name and role, and lives in memory only; nothing is written to browser storage by this ticket (an offline cache is TOKI-040's, and D-132 says what happens at a change of person: `reset()`, R11).
- `ApiError` never holds a request body, a cookie or a header (R4). Nothing in the package logs.
- A private channel or DM of another person is never in the store, because the server never sends it (TOKI-031 R18); the store adds nothing from another source.

## Areas of concern
1. Strict shared schemas against additive API. Decided in this spec: the client drops unknown keys and fails on a wrong or missing known key (R3). TOKI-031 R17 says the client parses "with the same schema" and that the schemas reject unknown keys at every level; both stay true for the server's tests, but a client built on the strict parse breaks on the first field the API adds. TOKI-031's sentence needs the words "or a non-strict form of it". Owner: Thanh Truong.
2. Store of our own against the Query cache. Decided in this spec (Design, "Why a store of our own"), for the conversation data only. TOKI-006 concern 6 (where the Query client lives for other server data) stays open. Owner: Thanh Truong.
3. Timers and the clock. Decided in this spec: the client takes a `timers` object and the web app lends it (R5, R25), because TOKI-008 R19 bans timer functions in `client-core` and its clock has no timer. If TOKI-008 later gives the clock a timer, `timers` becomes that. Owner: Thanh Truong.
4. Where the connection of the unauthenticated answer lives. Decided in this spec: the client has a hook and a setter (R7), `apps/web/src/client.ts` exists after this ticket, and TOKI-023 calls `setOnUnauthenticated(reportUnauthenticated)`. Plan change asked: TOKI-023 and this ticket do not depend on each other in the plan, so whichever is built second makes the call or the hand check shows it missing; the hand check of TOKI-023 should include "a 401 on `bootstrap` shows the modal". The status codes of `validation_error` (TOKI-022) and `validation_failed` (TOKI-004) differ in name for the same case: the client reads no such code (R8 uses the status), so it is not affected; the two specs need one name. Owner: Thanh Truong.
5. Which ticket opens the last viewed conversation and falls back to #general when it was archived or left (D-035, flow 2.3, TS-030). Not decided. No plan line owns it. The store gives what it needs (`hasConversation`, `getGeneralId`, R23). Proposal only, not a decision: TOKI-033, which owns the address of each conversation, keeps the last viewed id per device and applies the fallback. Owner: Thanh Truong (product owner, plan).
6. The order of the Starred group. Not decided. F09 orders channels alphabetically and DMs by latest message and says nothing about Starred, which mixes both. R18 uses the name, as an interim rule. Proposal only, not a decision: keep it alphabetical by name. Owner: Thanh Truong (product owner).
7. Whether a muted conversation with unread messages is kept by the Unread filter. Not decided. The prototype keeps it (`unread>0` with no check of mute); D-103 says Mute hides the badge and the bold, and says nothing about the filter. R20 follows the prototype as an interim rule. Where the unread data comes from is TOKI-031 concern 7 (proposal: TOKI-053). Owner: Thanh Truong (product owner).
8. Whether the search of the list ignores diacritics (typing `an` for `Ánh`). Not decided. D-015 decides it for Ctrl+K only and D-177 for People is Open. R19 does not fold them, as the prototype does not. Proposal only, not a decision: fold them as Ctrl+K does. Owner: Thanh Truong (product owner).
9. Saving the person's level, mute and star. Not decided (TOKI-031 concern 5, TOKI-028 concern 2). The store returns the three values and cannot change them; when the request exists its owner adds a client method and a store command that follows R13 and R15. Owner: Thanh Truong (product owner, plan).
10. The order of direct messages by latest message. Not decided (TOKI-031 concern 1: the field and its ticket are open). R18 orders by name through one function, `compareDirect`, so the change is one place. Owner: Thanh Truong (product owner, plan).
11. The ids that the client makes. Decided in this spec: `channels.create` takes the `id` from the caller (TOKI-029 R4: a lower-case UUIDv7 made by the client) and this ticket builds no generator; the first ticket that needs one, the Admin page's Create channel (TOKI-098), adds it to `packages/shared` so that message sending (TOKI-040) reuses it. Owner: Thanh Truong.
