# Base components, group 2 design

Date: 2026-11-16 · Status: draft for review
Intent: docs/intents/base-components-2.md (Thanh Truong)
Ticket: TOKI-013

## Goal
The builder (Thanh and Claude) needs four small pieces of the prototype as components before the shell, the lists, the profile and the Undo pattern are built: the avatar with initials, the presence dot, the empty-list message and the toast. Today `packages/ui-web` holds only the icons (TOKI-011), so each screen would copy these pieces from the prototype by hand.
After this change `ui-web` exports `Avatar`, `PresenceDot`, `EmptyState` and `Toast` (with a provider, hooks and a region that keeps toasts above the composer, the bottom bar and the sidebar, as far as the layout registers them: Scope and concern 8 say which). Each looks as in the prototype in Calm and Focus. The prototype's toast sits over the composer on a wide screen, over the sidebar at some widths, and at the top of the frame on a narrow screen, which D-078 forbids or which is a defect; this change builds a measured placement instead of copying it (Design, Toast).

## Requirements
Shared
- R1. `packages/ui-web/src/components/` holds one folder for each of `Avatar`, `PresenceDot`, `EmptyState` and `Toast`. Each folder has `<Name>.tsx`, `<Name>.css`, `<Name>.test.tsx`, `<Name>.examples.tsx` and `index.ts`, and no file other than those and the helper files named in Design, Layout (`getInitials.ts`, `ToastProvider.tsx`, `ToastRegion.tsx`, `toastPlace.ts`). `src/components/index.ts` (created by TOKI-012) holds one `export * from "./<Name>"` line for each of the four folders, and `src/index.ts` is not changed by this ticket. A folder's `index.ts` names its exports.
- R2. `@toki/ui-web` exports at least these names from group 2, and the test checks that each is present; it does not require that nothing else is exported, because group 1 adds its own (TOKI-012 R1): `Avatar`, `AvatarProps`, `getInitials`, `PresenceDot`, `PresenceDotProps`, `PresenceState`, `presenceStates`, `EmptyState`, `EmptyStateProps`, `Toast`, `ToastProps`, `ToastProvider`, `ToastRegion`, `useToasts`, `useToastAvoid`, `useToastAnchor`, `computeToastBottom`, `computeToastExtent`, `TOAST_MS_WITH_ACTION` and `TOAST_MS_PLAIN`.
- R3. No source file of group 2 (test and examples files excepted) imports `@toki/i18n`, `@toki/tokens` or `@toki/platform`, holds a visible text, or uses a notification, storage, service worker or audio API. The four `.css` files contain no colour literal (`#`, `rgb(`, `rgba(`, `hsl(` with a number as its first argument) and no custom property name that is not one of the 32 names of TOKI-009 R10 or one that the component defines itself (`--h`, `--s`).
- R4. Every component of this group (`Avatar`, `PresenceDot`, `EmptyState`, `Toast` and `ToastRegion`) is made with `forwardRef` and forwards `ref` to its root element. Each passes `className` (appended after its own classes) and the other attributes of its root element through, except the attributes it owns (named in each requirement below). The owned attributes are applied after the spread, so a caller cannot replace them even with a cast; the props type does not accept an owned attribute, so passing one without a cast fails `pnpm typecheck` (TOKI-012 R2 c, d).
- R5. `ui-web` gains no dependency: the test set-up, `jsdom` included, is TOKI-012's (R27). `pnpm install`, `pnpm typecheck`, `pnpm lint`, `pnpm lint:boundaries`, `pnpm format:check` and `pnpm --filter @toki/ui-web test` exit 0 at the end of this work.

Avatar
- R6. `<Avatar name="Lan Nguyễn" hue={172} />` renders one `span` with class `av`, `aria-hidden="true"`, the style `--h:172` and the text `LN` as its only child. With `size={46}` the style also holds `--s:46px`. Without `size` it holds no `--s`, so the size is the density value `--av` (36 px comfortable, 30 px compact; TOKI-009 Table C). The owned attributes are `aria-hidden` and `children`; `aria-label`, `aria-labelledby` and `title` are removed before the spread, and the props type does not accept them, `src` or `alt`: an avatar has no name of its own (the button or row around it has, D-075) and shows no picture (D-118). A caller's `style` is merged with the component's: the caller's keys win, except `--h` and `--s`, which are the component's (R10 says on which element the style lands). `ref` points at the root.
- R7. `getInitials(name)` normalises the name to NFC, trims it, splits it on runs of white space, takes the first code point of the first word and of the last word, upper-cases each with `toUpperCase()` and keeps only the first code point of that result, and joins them. So `Lan Nguyễn` gives `LN`, `Khoa Đỗ` gives `KĐ`, `Toki Automations` gives `TA`, `Minh Trần Quang` gives `MQ` and `ß Test` gives `ST` (`ß` upper-cases to `SS`, and one letter is kept). A name written with combining marks, `"O\u0302ng Ba"` (`O` and U+0302), gives `ÔB` (U+00D4), which is only so after the NFC step. A name of one word gives its one letter (`Lan` gives `L`). An empty name or one of only white space gives the empty string. It never throws.
- R8. The hue is taken modulo 360 into the range 0 to 359 (`-30` gives `330`, `360` gives `0`); a value that is not a finite number gives `0`. `size` must be a finite number above `0`; any other value is treated as no `size`.
- R9. `Avatar.css` holds the rule `.av` with the declarations of the prototype's rule: `--s:var(--av)`, `width` and `height` of `var(--s)`, `flex:none`, `border-radius:30%`, `display:inline-grid`, `place-items:center`, `font-weight:700`, `font-size:calc(var(--s)*.38)`, `letter-spacing:.01em`, a background of `hsl(var(--h) var(--av-s) var(--av-l))`, a colour of `hsl(var(--h) var(--av-ts) var(--av-tl))`, `position:relative` and `user-select:none`. The two colours therefore follow the look through `--av-s`, `--av-l`, `--av-ts` and `--av-tl` (TOKI-009 Table A) and need no look selector.
- R10. `<Avatar name hue presence="away" />` renders a wrapper `span` with class `pdw` around the avatar of R6 and a `PresenceDot` of that state as its second child. `className`, `style`, `ref` and the other attributes go to the wrapper in this case, and `--h` and `--s` stay on the `.av` element (without `presence` the caller's `style` and the rest go to the `.av`, as in the prototype's stacks, which put a margin and a border on it). `Avatar.css` holds the prototype's two rules, `.av .pd{position:absolute;right:-3px;bottom:-3px}` (line 115) and `.pdw{position:relative;display:inline-grid;flex:none}` (line 599) with `.pdw .pd{position:absolute;right:-3px;bottom:-3px}` (line 600). Without `presence`, no wrapper and no dot are rendered. The dot has no `label` unless `presenceLabel` is given (R14).

PresenceDot
- R11. `presenceStates` is `["active", "away", "dnd"]` and `PresenceState` is its union. There is no `meet` state and no offline state (D-036; Scope).
- R12. `<PresenceDot state="active" />` renders one `span` with class `pd`; state `away` adds the class `away` and state `dnd` adds the class `dnd`. The state is required; there is no default.
- R13. `PresenceDot.css` holds the prototype's declarations: `.pd` with width and height of 11px, `border-radius:50%`, `border:2px solid var(--surface)`, `background:var(--accent)`, `display:inline-block`, `flex:none` and `box-sizing:border-box`; `.pd.away` with `background:var(--surface)` and `border-color:var(--muted)` (the prototype also has `border-width:2px`, which repeats the shorthand and is left out); `.pd.dnd` with `background:var(--danger)`. So Active is a solid dot in the accent colour, Away is a hollow dot with a grey ring, and Do not disturb is a red dot, in both looks and all four accents.
- R14. `PresenceDot` takes an optional `label` (text). With a `label` it renders `role="img"` and `aria-label` set to it; without one it renders `aria-hidden="true"`. `role`, `aria-label` and `aria-hidden` are owned (R4). The colour of the dot is never the only carrier of the state where a `label` or a visible word is shown next to it; which places must pass a label is concern 7. `Avatar` takes `presenceLabel` and passes it on.

EmptyState
- R15. `<EmptyState icon="users" title="Nobody matches" description="Try a name or a job title." />` renders `div.empty` holding, in this order: `div.eic` with the icon `users` at `size={26}`; `b` with the title; `span` with the description; and, only when `action` is given, the `action` node. `icon` has the type `IconName` of TOKI-011; `title` and `description` are required strings; `action` is an optional `ReactNode`.
- R16. `EmptyState.css` holds the declarations of the prototype's rules. `.empty`: `display:flex`, `flex-direction:column`, `align-items:center`, `justify-content:center`, `text-align:center`, `gap:10px`, `padding:56px 24px`, `color:var(--muted)`, `flex:1`. `.empty .eic`: width and height 56px, `border-radius:18px`, `background:var(--accent-soft)`, `color:var(--accent-text)`, `display:grid`, `place-items:center`. `.empty .eic .ic`: width and height 26px. `.empty b`: `color:var(--ink)`, `font-size:15px`.
- R17. In a parent that is a flex column with a height, the empty state takes the free height of the parent and its content is centred horizontally and vertically in it (D-074): checked in a browser at 360, 720 and 1100 px wide, in both looks, with the centre of the `.empty` block's content (the `.eic` and the text) within 1 px of the centre of the parent. In a parent that is not a flex column the component does not centre vertically, as in the prototype (Design, EmptyState); the parent's side of this contract is a hand-off (concern 8).
- R18. `EmptyState` holds no text of its own and draws no button of its own (R3). Its props type omits the native `title` and `children` (`title` is the prop of R15) and `ref` points at `div.empty`.

Toast
- R19. `<Toast text="Left #design" />` renders `div.toast` holding `span` with the text, and no `role`: the live region is the `ToastRegion` (R21; Decided in this spec, the prototype also puts `role="status"` on each toast, and a role added together with the node is not announced as a change and can make a screen reader read the toast twice; Testing has a manual check, concern 15). With `action={{ label, onPress }}` it also renders `button` of `type="button"` with the label after the span. `Toast` is the presentational part: it holds no timer and no state, and `ref` points at `div.toast`.
- R20. `Toast.css` holds the declarations of the prototype's rules. `.toast`: `pointer-events:auto`, `display:flex`, `align-items:center`, `gap:12px`, `background:var(--ink)`, `color:var(--surface)`, `padding:9px 12px 9px 14px`, `border-radius:var(--radius-sm)`, `box-shadow:var(--pop)`, `animation:tin .18s ease-out`, `font-weight:500`. `.toast button`: `color:var(--accent-soft)`, `font-weight:700`, `padding:2px 6px`. `[data-eff="focus"] .toast button`: `color:var(--accent)`. `@keyframes tin` from `transform:translateY(8px);opacity:0`. The text of a toast wraps; it is not cut. The colours are the prototype's in each look (Calm `--accent-soft`, Focus `--accent`), written the other way round: the prototype has the default `--accent` and the exception `[data-eff="calm"]`. Decided in this spec: a page with no `data-eff` attribute (TOKI-009 R12 gives it the Calm values on a light device) then gets the Calm label, not teal on the toast's `--ink`. The selector is the one look selector of group 2, because no existing token has `--accent-soft` in Calm and `--accent` in Focus (concern 14). Whether the colours are readable is concern 3.
- R21. `ToastProvider` renders its children and, after them, one `ToastRegion`. `ToastRegion` renders a `div.toasts` with `aria-live="polite"` (the one live region of the toasts, R19) that is in the document from the first render, also when there is no toast, so that a screen reader announces a toast added later. `.toasts` holds the declarations `position:fixed`, `left:50%`, `transform:translateX(-50%)`, `display:flex`, `flex-direction:column`, `gap:8px`, `align-items:center`, `pointer-events:none`, `z-index:40`, `width:min(480px,92%)`. Decided in this spec: `fixed` replaces the prototype's `absolute`, because the prototype's frame is a demo device and the real page is the window.
- R22. `useToasts()` returns `{ show, dismiss }`. `show({ text, action? })` adds a toast at once and returns its id; `dismiss(id)` removes it and does nothing for an unknown id. Called outside a `ToastProvider`, `useToasts()` throws an error whose message contains `ToastProvider`. `show` and `dismiss` keep the same identity for the life of the provider, and the list of toasts is in a separate context that only the region reads, so a component that calls `useToasts()` does not render again when a toast is added or removed, and a caller can put `show` in a dependency list without a loop.
- R23. A toast with an `action` is removed 5000 ms after it was shown (`TOAST_MS_WITH_ACTION`, D-069); a toast without one is removed after 2800 ms (`TOAST_MS_PLAIN`, the prototype's value; no decision gives one, concern 1). Each toast has its own timer. A toast is still in the document 1 ms before its time and gone at its time.
- R24. Pressing the button of a toast removes the toast first and then calls `onPress` once. A second press cannot happen, because the toast is gone; the timer of a removed toast does not call anything.
- R25. Several toasts show in the order of `show`, the oldest on top and the newest at the bottom, nearest to the composer, as in the prototype. There is no limit on their number and no merging of equal texts (concern 4).
- R26. When the provider unmounts, every timer is cleared; no state is set afterwards (no React warning, checked with fake timers).
- R27. `computeToastBottom(viewportHeight, obstacles, extent?)` returns the distance in pixels from the bottom of the window to the bottom of the toasts. An obstacle is `{ top, left, right }`; `extent` is `{ left, right }`, the horizontal span of the region (R31). With no obstacle it returns `20`. An obstacle counts only if its span overlaps `extent` by more than 0 (with no `extent` every obstacle counts). For each counting obstacle with `top < viewportHeight` the clearance is `viewportHeight - top + 14`; the result is the largest clearance, and never less than `20`. An obstacle with `top >= viewportHeight` (below the window), one with a `NaN` value, and one with `right <= left` is ignored. The numbers are the prototype's intended ones (20 px with nothing to avoid; 14 px above a bar), not its behaviour on a narrow screen, where its rule does not work (Design, Toast, Place).
- R28. `useToastAvoid(ref)` registers the element of `ref` as one that toasts must stay above, for as long as the calling component is mounted. `ToastRegion` sets its inline `bottom` to `computeToastBottom` of the rectangle (`getBoundingClientRect`) of every registered element that is in the document and has a width and a height above 0, with the region's span from R31 as `extent`. It measures again (a) when a registered element changes size (`ResizeObserver`, when the browser has it), (b) when the window is resized, (c) when an element is registered or removed, (d) whenever a toast is added or removed, and (e) on `transitionend` and `transitioncancel` of a registered element, because an element that moves by `transform` (the prototype hides its tab bar with `translateY(100%)` and a 0.18 s transition, lines 515 and 516) changes no size and fires no `ResizeObserver`. With no `ToastProvider` above, `useToastAvoid` does nothing. A registered element that is hidden, or moved off the window, no longer counts. This keeps toasts off every registered composer and bar; an element that nobody registers is not protected (concern 8).
- R29. An element registered by `useToastAvoid` stays clickable and visible while a toast is shown: in a browser, at 360, 720, 800, 1099 and 1100 px, in both looks, with a registered test composer at the bottom, a registered test bar that is hidden by a `transform` while a flag is set, a test sidebar at the left of the window (a column 272 px wide, or 68 px wide in the Focus form) and the main area beside it as the anchor (R31), and three toasts shown (one of them with a text long enough to fill the region), the bounding box of every toast ends above the top of the composer and of the bar while it is shown, and the toasts do not intersect the composer's box, the bar's box (while shown) or the sidebar's box; after the bar is hidden by the transform the toasts come down to the composer or to 20 px.
- R30. Each component folder holds `<Name>.examples.tsx` exporting `examples: Example[]` (R1; the type is TOKI-012's). Together they show: Avatar with no `size`, with `size={46}` and with `size` 18, 24, 30 and 64 (the sizes that the screens of the lists, the header and the profile use, Design, Avatar; asked by the preview page spec, TOKI-016 concern 6 (a)), with `presence` in each of the three states and with a one-word and a long name; PresenceDot in each state with and without `label`; EmptyState with and without `action` (the action is a TOKI-012 `Button`); Toast without and with an action, and with a long text. `src/examples.ts` gains the entries `Avatar`, `PresenceDot`, `EmptyState` and `Toast`, in that order, after group 1's. The `id`s are unique within a component. TOKI-012's test of R31 passes with the four folders.
- R31. `useToastAnchor(ref)` registers the element of `ref` as the area that the toasts are centred in, for as long as the calling component is mounted; the last element registered wins, and with none the area is the window. `computeToastExtent(viewportWidth, anchor?)` returns `{ left, width }` with `width = min(480, 0.92 × (anchor width or viewportWidth))` and `left` the centre of the anchor (or `viewportWidth / 2`) minus half of the width; the region's inline `left` is the centre and its inline `width` the width in pixels, so the prototype's `translateX(-50%)` stays. The span `{ left, left + width }` is the `extent` of R27. The anchor is measured at the times listed in R28 (a, b, c, d, e). With no `ToastProvider` above, `useToastAnchor` does nothing.
- R32. Narrow screens: `Toast.css` holds one `@media (max-width: 719px)` block with `.toast button{min-height:40px}` (journey F38, TOKI-012 R8 and Scope: the Toast button is a control). The prototype's button is about 24 px tall.
- R33. The Undo button's keyboard focus ring is visible on the toast: `Toast.css` holds `.toast button:focus-visible{outline-color:var(--surface)}`; the width, style and offset stay those of `base.css` (Table J of TOKI-012). The shared ring is `var(--accent)`, which on the toast's `--ink` is the same colour as the Focus label (R20, concern 3) and so would not show.

### Layout

### Where each look and size comes from
- Both looks: the components hold one look selector, `[data-eff="focus"] .toast button` (R20; Scope says why). Colours come from the variables of TOKI-009, so Calm and Focus differ by the values of `--ink`, `--surface`, `--accent` and the rest. The `data-eff` attribute is the one TOKI-009 decided.
- Density: only the default avatar size follows it (`--av`). `--gap` and `--row` are used by lists, not by these four.
- Avatar sizes the phase 1 screens use, from the prototype's `av()` and `avp()` calls and its CSS: the density size, and 18, 20, 22, 24, 28, 30, 32, 36, 46 and 64 px from the calls, and 34 px from the narrow layout's rule `.cr .av{--s:34px}` (line 529). The component accepts any positive number; it keeps no list of sizes, because the prototype sets them in pixels at each place. Two prototype sizes, the Meet tile (56 to 104 px) and the Mail sender (38 px), belong to phases that are not built.
- The font size of the initials is 0.38 times the size (R9), the weight 700 (the 700 face of TOKI-010). The initials of Vietnamese names (`KĐ`) are inside the character set of TOKI-010.

### Avatar
- The initials rule is the prototype's `av()` function (first letter of the first word and of the last word, upper-cased) with these changes, each Decided in this spec. The prototype splits on one space, takes UTF-16 units, and throws a `TypeError` for an empty name or one with a leading space (checked). (1) The name is trimmed and split on runs of white space, so a leading, trailing or double space changes nothing and an empty or white-space-only name gives no letters instead of an error. (2) The name is normalised to NFC and a letter is one code point, so a name typed with combining marks (`O` and U+0302) gives `Ô` and not `O`, and a letter outside the first 65536 code points is not cut in half. (3) A one-word name gives one letter; the prototype shows the same letter twice (`LL` for `Lan`), an accident of its code and not a drawn design (concern 6). (4) Each letter is cut to one code point after `toUpperCase()`, so `ß` gives `S` and not `SS`. `Đ` has no decomposition, so the prototype's `Khoa Đỗ` proves nothing about step (2); the test uses `O` and U+0302 (Testing).
- The hue is a prop, not derived inside the component. The prototype stores one number per person (`h:172`) and makes one up for guests and mail senders. The decision log does not say where the real number comes from (concern 5). Whatever the answer, the component needs only the number.
- `Avatar` is hidden from screen readers, like the icons (TOKI-011 R7). The prototype does the same (`aria-hidden="true"`) and puts the person's name on the button around the avatar (`aria-label` on `avbtn`). A screen that shows an avatar with no name next to it adds the name to the button or row.

### PresenceDot
- The dot has a 2 px ring of `var(--surface)`, so on a row whose background is not `--surface` (a hovered row) the ring shows as a light edge; the prototype is the same.
- The prototype draws the dot as `<i class="pd …">`; a `span` is used here so that the element carries no italic meaning. The class names are the prototype's.
- Found in the prototype: on the profile panel and the People card the dot is given an inline `border-color:var(--surface)`, which would hide the grey ring of an Away dot. The context table says Away is a hollow dot with a grey ring, so R13 follows that, not the inline style.
- Size: 11 px. The prototype makes it 10 px in a conversation row (`.cr .pdw .pd`); that rule belongs to the conversation list, which passes a `className` or its own CSS.

### EmptyState
- The look is the prototype's `emptyHtml()` function and its `.empty` rules. The texts in the prototype are written by each list (for example 'Nobody matches' with 'Try a name or a job title.'; 'You are all caught up' with 'Mentions, thread replies and reactions will show up as they happen.' and the button 'Open your conversations'). D-074 asks for a text written for each list, so the texts belong to the screens (Scope).
- The component fills the free height of a parent that is a flex column (`flex:1`). The prototype is not centred in two of its three kinds of parent: I measured `.msgs` (the Pinned tab) and `.secbody` (Activity) in headless Chrome at 360 and 1300 px in both looks, and both are `display:block`, so `flex:1` does nothing; the block is centred across but sits at the top, 114 to 154 px above the vertical centre of the parent. D-074 says 'centred in the content area'. Decided in this spec: the CSS stays the prototype's (R16) and does not hide the defect with a `min-height`, which depends on the parent having a height; the parent's side is a hand-off. TOKI-015 (the content area and the panes it builds) and every screen ticket that puts an empty state in `.msgs` or `.secbody` make that parent a flex column with a height and `min-height:0` (concern 8). The plan lines of those tickets do not say so.
- Decided in this spec: the title is a `b`, not a heading, as in the prototype. The component gives the region no live role; announcing an empty result to a screen reader is not decided (concern 11).

### Toast
- Pieces: `Toast` (one box), `ToastProvider` (holds the list and the timers, renders the region), `ToastRegion` (the container and its position), `useToasts` (`show`, `dismiss`), `useToastAvoid` (R28), `useToastAnchor` (R31). The provider is mounted once, by the AppShell (TOKI-015); screens only call `useToasts()`. The provider has three contexts: the stable `{ show, dismiss }` (R22), the list (read by the region only), and the registry of avoided elements and the anchor (stable, so a registering component does not render again).
- How long: 5000 ms when the toast has a button, from D-069 ('Undo for 5 seconds'); the prototype's 5200 ms adds 200 ms that no decision asks for. 2800 ms without a button is the prototype's number only. Nothing in the log or the prototype sets a different time for other cases (a mention toast with 'View' has a button, so it gets 5000 ms, which agrees with the journey 'closes after 5 seconds'). There is no `duration` prop: the two numbers are exported constants, so the rule is in one place.
- The button: after a press the toast is removed, then `onPress` runs (the prototype's `toastact` order). A toast has no close button and no swipe; the prototype has neither. The button's focus ring has its own colour (R33).
- Announcing: the region is the live region (R19, R21); the toast has no role of its own. Concern 15.
- Place. What the prototype does, measured in headless Chrome (window widths 360, 800 and 1100 px; at 360 the window reported 500 px; three toasts shown): (a) `.toasts` is centred on the device frame and is `min(480px,92%)` wide, so at 800 px in Calm its box is x 160 to 640 and the sidebar's user card is x 12 to 260, and in Focus at 800 and 1100 px it overlaps the conversation-list column (x 68 to 356). The three short toasts I used are as wide as their text (54 to 200 px), so they did not touch the card; a toast wider than twice the distance from the centre to the sidebar's edge (280 px at 800 px in Calm, 388 px in Focus at 1100 px) does. (b) The narrow rule `.toasts{bottom:calc(var(--tabh) + 14px)}` (line 562) does nothing: `--tabh` is set on `.app` (line 506) and `.ov`, which holds the toasts, is a sibling of `.app`, so `var(--tabh)` is invalid, `bottom` computes to `auto` and the toasts sit at the top of the frame (y 45 to 180 in a frame that starts at 45). The prototype is wrong here and a by-eye comparison at 360 px will not match it; the intended value, 14 px above the tab bar, is what this spec builds (R27). (c) It hides the tab bar with `transform:translateY(100%)` and a 0.18 s transition (lines 515, 516) and, while a chat or a side pane is open, sets the toasts' `bottom` back to 20 px with a sibling selector (line 563) that does work; the toasts do not follow the bar in any other case.
  Decided in this spec: the region does not know the layout; the layout tells it, by two registrations. `useToastAnchor(ref)` names the area that the toasts are centred in (the main area, which on a wide screen excludes the sidebar and the navigation rail), so a toast never lands on the sidebar or the conversation list whatever the width. `useToastAvoid(ref)` names a composer or a bar that the toasts must stay above; the region keeps its bottom edge 14 px above the highest of those whose span overlaps its own (R27, R28, R31), measured again when a toast is added or removed and when a registered element finishes a transition. The prototype's two numbers stay (20 px with nothing to avoid, 14 px above an obstacle). The alternative, a CSS variable that the shell and the composer keep in step, was not chosen: the composer grows with its text and with attachments, and a variable would need each owner to measure itself and write it (the prototype's `--tabh` failure is the example). The other alternative, obstacles with no span (tops only), was dropped: the region is wider than a sidebar's gap, so a tops-only rule cannot say 'stay out of this column'. Hand-offs: TOKI-043 (Composer) calls `useToastAvoid` on its outer element; TOKI-015 mounts the provider, calls `useToastAnchor` on the main area and `useToastAvoid` on the bottom tabs (the bar stays registered while hidden: R28 e makes the hidden bar stop counting), and chooses what the anchor is while a side panel overlays the chat at 720 to 1099 px; a floating bar that D-078 also protects (the Meet bar, phase 4) does the same. Until they do, the toast sits at 20 px, centred in the window.
  What the claim covers. True: a toast never covers an element that is registered with `useToastAvoid`, and never covers anything outside the anchor, at any width. Not covered: an element nobody registers; the on-screen keyboard (below); the conversation list is also covered when the layout registers no anchor. The claim 'toasts stay above the composer and the navigation' is therefore true as far as TOKI-015 and TOKI-043 register (concern 8).
- Narrow width: `width:min(480px,92%)` of the anchor (the window when there is none), as in the prototype, so on a 360 px window the region is 331 px wide (92% of 360); a toast is as wide as its text, up to the region's width, and a long text wraps. Nothing else is decided for narrow screens beyond D-078 and R32.
- On-screen keyboard: the prototype does nothing and no decision covers it. The region follows the layout viewport only (R28 does not listen to the visual viewport). Concern 4.
- Pause and Focus time (D-072) are not handled here: a caller that is not allowed to show a toast does not call `show` (TOKI-073).
- The timer lives in the provider, in `setTimeout` calls, and each toast keeps its own handle; unmounting clears them (R26). The list is React state in the provider, so a toast shown from an event handler appears on the next render. `ResizeObserver` does not exist in jsdom and may not in a very old browser: when it is missing the hooks rely on the window resize, the toast changes and the transition events only (R28).
- `Toast` is exported on its own so the preview page and tests can draw one without a provider.

### Errors
- `useToasts()` outside a provider -> an error that names `ToastProvider` (R22). No silent loss of a toast.
- `dismiss` of an unknown id, a second `dismiss`, or a timer of a removed toast -> nothing happens (R22, R24).
- A `size` that is 0, negative or not a number -> the density size (R8). A `hue` that is not a number -> 0 (R8).
- An empty name -> an avatar with no letters (R7); the screen is responsible for names (concern 6).
