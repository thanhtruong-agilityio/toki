# Base components, group 2 design

Date: 2026-11-16 · Status: draft for review
Intent: docs/intents/base-components-2.md (Thanh Truong)
Ticket: TOKI-013

## Goal
The builder (Thanh and Claude) needs four small pieces of the prototype as components before the shell, the lists, the profile and the Undo pattern are built: the avatar with initials, the presence dot, the empty-list message and the toast. Today `packages/ui-web` holds only the icons (TOKI-011), so each screen would copy these pieces from the prototype by hand.
After this change `ui-web` exports `Avatar`, `PresenceDot`, `EmptyState` and `Toast` (with a provider, a hook and a region that keeps toasts above the composer and the navigation). Each looks as in the prototype in Calm and Focus. The prototype's toast sits over the composer on a wide screen, which D-078 forbids; this change fixes that instead of copying it.

## Scope

  - `Avatar`, with the helper `getInitials`; `PresenceDot`; `EmptyState`; `Toast`, `ToastProvider`, `useToasts`, `ToastRegion` and `useToastAvoid`.
  - The CSS of these four, carried over from the prototype, one file each.
  - The shared rules of group 1 and group 2 for `ui-web` components (next bullet).
  - Tests, and an examples file per component for the preview page.
- Shared with group 1 (TOKI-012: Button, IconButton, Chip, Switch, Field, Select, Tag, Badge). Both specs are written at the same time. Decided in this spec, from the side of group 2; the group 1 spec must agree, and where it does not, the difference is a review comment on both:
  - Folder layout: `packages/ui-web/src/components/<Name>/` with `<Name>.tsx`, `<Name>.css`, `<Name>.test.tsx`, `<Name>.examples.tsx` and `index.ts`; `src/components/index.ts` re-exports each folder; `src/index.ts` re-exports `./icons` and `./components` (R1).
  - Styling: one plain CSS file per component, imported by its `.tsx`; the class names, the CSS custom property names and the declarations are the prototype's; no CSS module, no Tailwind, no styling library (the technical design; TOKI-009 R10). `ui-web` already has `"sideEffects": ["**/*.css"]` (TOKI-011 R11).
  - Props: a size that the prototype gives as a named step is a string union (`size="sm"`); a size that the prototype sets in pixels is a number of pixels (`size={46}`, group 2 only). A variant or tone is a string union of the prototype's modifier names. A state is a boolean with the name of the HTML or ARIA attribute (`disabled`, `checked`). Every component accepts `className`, which is appended after the prototype's class names, and the other attributes of its root element, except those it owns (the same rule as `IconProps`, TOKI-011 R5, R15). No component takes `ref` yet.
  - Texts: no component in `ui-web` imports `@toki/i18n` or holds a text. Every visible word and every accessible name comes in as a prop, which the screen fills from i18n. This keeps `ui-web` free of a text catalogue and follows TOKI-018 R25.
  - Tests: a test file next to each component, run by Vitest with `pnpm --filter @toki/ui-web test`. Markup is checked with `renderToStaticMarkup` (as TOKI-011). A test that needs a DOM (clicks, timers, observers) starts with the line `// @vitest-environment jsdom`, renders with `react-dom/client` inside `act`, and uses `vi.useFakeTimers()`. No testing library is added. `jsdom` is a dev dependency of `ui-web`, at the exact version `packages/platform` uses (TOKI-018), or its own exact pin if that package does not exist when this is built. CSS is tested by reading the `.css` file (declarations and variable names); what jsdom cannot do (layout, colour) is checked by eye (Testing).
  - "Stories": there is no Storybook. TOKI-016 builds the one preview page. Each component folder has `<Name>.examples.tsx` exporting `examples`, a list of `{ id: string; title: string; element: ReactElement }`, which the page imports and shows in both looks. The examples hold texts copied from the prototype; they are preview data and are imported only by the preview page.
  - Page-wide rules that the prototype's CSS has once are owned by TOKI-012, the first ticket that carries component CSS over (TOKI-010, Scope): `*{box-sizing:border-box}`, the `button` reset, `button,input,select,textarea{font:inherit;color:inherit}`, `:focus-visible`, `.sr`, the `prefers-reduced-motion` rule, and the one import of `@toki/tokens/tokens.css` in `apps/web`. The CSS here relies on them and repeats none (concern 10).
- Out (not now):
  - Everything that group 1 builds. `EmptyState` does not draw its own button: the screen passes a Button of TOKI-012 as `action` (R20).
  - Menu, Modal and Sheet: TOKI-014. The AppShell, the bottom tabs and the content area: TOKI-015. The preview page itself: TOKI-016.
  - The Undo pattern: the line with TOKI-093 is below.
  - Where presence comes from: the line is below.
  - Avatar stacks (the overlapping faces of the thread line and the poll voters), the person's profile picture, the group icon of a group DM, and the Meet tile avatar: the ticket that draws each one. They use `Avatar` with `size`, `className` and `style`.
  - The decision who gets a toast (conversation level, Mute, Pause, Focus, whether the conversation is on screen: D-072, D-088, D-103): TOKI-073. The sound with a toast: TOKI-075.
  - The texts of toasts and empty lists and their Vietnamese versions: the screen that shows them (D-074 asks for a text written for each list; D-139). Dates and times: no component here shows one.
  - The notification, storage, service worker and audio APIs: none is used here, so `platform` is not imported. TOKI-013 needs TOKI-018 in the plan, but no requirement here calls it; the lint rule 3 of TOKI-002 stays satisfied.
- The line with TOKI-093, stated once. This ticket builds the Toast: its look, its place, its timer (5 seconds when it has a button), the button and what a press does, the stack, and `useToasts().show`. TOKI-093 builds the pattern on top of it: the helper that runs a reversible action at once and shows a toast whose button reverses it (it calls `show` with `action`), the text key for 'Undo', the confirmation dialog that names its target, the guard against closing a form that has content (D-070), and the check that no action shows both a confirmation and an Undo (AC-077). TOKI-093 adds no timer and no second toast component. Any screen that needs a toast with a button before TOKI-093 exists can call `show` itself.
- The line with the presence data, stated once. `PresenceDot` only draws a state it is given. The state comes from the server's `presence` module (TOKI-055): Active while a device has Toki open and was used in the last 5 minutes, Away after 5 minutes without activity or with no device connected, Do not disturb during Focus time, and no Offline state (D-036, FR-32, context states table, F34). Presence is held in memory on the server, not in the database (technical design), and a person cannot set it by hand (AC-129). TOKI-055 decides the values on the wire and maps them to the three names of R13; if it uses the same three names, no mapping is needed. The colours come from the prototype's CSS (R14) and the context states table (Active: solid dot in the accent colour; Away: hollow dot with a grey ring; Do not disturb: red dot). No D-row sets a colour: D-036 sets only the time. The fourth prototype state, 'In a Meet', arrives with Meet in phase 4 and is not built (R13).

## Requirements
Shared
- R1. `packages/ui-web/src/components/` holds one folder for each of `Avatar`, `PresenceDot`, `EmptyState` and `Toast`. Each folder has `<Name>.tsx`, `<Name>.css`, `<Name>.test.tsx`, `<Name>.examples.tsx` and `index.ts`, and no file other than those and the helper files named in Design, Layout (`getInitials.ts`, `ToastProvider.tsx`, `ToastRegion.tsx`, `computeToastBottom.ts`). `src/components/index.ts` re-exports every component folder and `src/index.ts` re-exports `./components` besides `./icons`.
- R2. `@toki/ui-web` exports exactly these new names, and no other from `src/components` of group 2: `Avatar`, `AvatarProps`, `getInitials`, `PresenceDot`, `PresenceDotProps`, `PresenceState`, `presenceStates`, `EmptyState`, `EmptyStateProps`, `Toast`, `ToastProps`, `ToastProvider`, `ToastRegion`, `useToasts`, `useToastAvoid`, `computeToastBottom`, `TOAST_MS_WITH_ACTION` and `TOAST_MS_PLAIN`.
- R3. No source file of group 2 (test and examples files excepted) imports `@toki/i18n`, `@toki/tokens` or `@toki/platform`, holds a visible text, or uses a notification, storage, service worker or audio API. The four `.css` files contain no colour literal (`#`, `rgb(`, `rgba(`, `hsl(` with a number as its first argument) and no custom property name that is not one of the 32 names of TOKI-009 R10 or one that the component defines itself (`--h`, `--s`).
- R4. Every component passes `className` (appended after its own classes) and the other attributes of its root element through, except the attributes it owns (named in each requirement below); the props type does not accept an owned attribute, so passing one fails `pnpm typecheck`.
- R5. `ui-web` gains no dependency other than the dev dependency `jsdom` (Scope). `pnpm install`, `pnpm typecheck`, `pnpm lint`, `pnpm lint:boundaries`, `pnpm format:check` and `pnpm --filter @toki/ui-web test` exit 0 at the end of this work.

Avatar
- R6. `<Avatar name="Lan Nguyễn" hue={172} />` renders one `span` with class `av`, `aria-hidden="true"`, the style `--h:172` and the text `LN` as its only child. With `size={46}` the style also holds `--s:46px`. Without `size` it holds no `--s`, so the size is the density value `--av` (36 px comfortable, 30 px compact; TOKI-009 Table C). `aria-hidden` cannot be changed, and the props type does not accept `aria-label`, `title`, `children`, `src` or `alt`: an avatar has no name of its own (the button or row around it has, D-075) and shows no picture (D-118).
- R7. `getInitials(name)` splits the trimmed name on runs of white space, takes the first character of the first word and the first character of the last word, joins them and upper-cases the result, so `Lan Nguyễn` gives `LN`, `Khoa Đỗ` gives `KĐ` (the name is normalised to NFC first and a character is one code point), `Toki Automations` gives `TA` and `Minh Trần Quang` gives `MQ`. A name of one word gives its one first letter (`Lan` gives `L`). An empty name or one of only white space gives the empty string. It never throws.
- R8. The hue is taken modulo 360 into the range 0 to 359 (`-30` gives `330`, `360` gives `0`); a value that is not a finite number gives `0`. `size` must be a finite number above `0`; any other value is treated as no `size`.
- R9. `Avatar.css` holds the rule `.av` with the declarations of the prototype's rule: `--s:var(--av)`, `width` and `height` of `var(--s)`, `flex:none`, `border-radius:30%`, `display:inline-grid`, `place-items:center`, `font-weight:700`, `font-size:calc(var(--s)*.38)`, `letter-spacing:.01em`, a background of `hsl(var(--h) var(--av-s) var(--av-l))`, a colour of `hsl(var(--h) var(--av-ts) var(--av-tl))`, `position:relative` and `user-select:none`. The two colours therefore follow the look through `--av-s`, `--av-l`, `--av-ts` and `--av-tl` (TOKI-009 Table A) and need no look selector.
- R10. `<Avatar name hue presence="away" />` renders a wrapper `span` with class `pdw` around the avatar of R6 and a `PresenceDot` of that state as its second child. `className` and the other attributes go to the wrapper in this case, and `--h` and `--s` stay on the `.av` element. `Avatar.css` holds `.pdw{position:relative;display:inline-grid;flex:none}` and `.av .pd,.pdw .pd{position:absolute;right:-3px;bottom:-3px}`. Without `presence`, no wrapper and no dot are rendered. The dot has no `label` unless `presenceLabel` is given (R14).

PresenceDot
- R11. `presenceStates` is `["active", "away", "dnd"]` and `PresenceState` is its union. There is no `meet` state and no offline state (D-036; Scope).
- R12. `<PresenceDot state="active" />` renders one `span` with class `pd`; state `away` adds the class `away` and state `dnd` adds the class `dnd`. The state is required; there is no default.
- R13. `PresenceDot.css` holds the prototype's declarations: `.pd` with width and height of 11px, `border-radius:50%`, `border:2px solid var(--surface)`, `background:var(--accent)`, `display:inline-block`, `flex:none` and `box-sizing:border-box`; `.pd.away` with `background:var(--surface)` and `border-color:var(--muted)`; `.pd.dnd` with `background:var(--danger)`. So Active is a solid dot in the accent colour, Away is a hollow dot with a grey ring, and Do not disturb is a red dot, in both looks and all four accents.
- R14. `PresenceDot` takes an optional `label` (text). With a `label` it renders `role="img"` and `aria-label` set to it; without one it renders `aria-hidden="true"`. The colour of the dot is never the only carrier of the state where a `label` or a visible word is shown next to it; which places must pass a label is concern 7. `Avatar` takes `presenceLabel` and passes it on.

EmptyState
- R15. `<EmptyState icon="users" title="Nobody matches" description="Try a name or a job title." />` renders `div.empty` holding, in this order: `div.eic` with the icon `users` at `size={26}`; `b` with the title; `span` with the description; and, only when `action` is given, the `action` node. `icon` has the type `IconName` of TOKI-011; `title` and `description` are required strings; `action` is an optional `ReactNode`.
- R16. `EmptyState.css` holds the declarations of the prototype's rules. `.empty`: `display:flex`, `flex-direction:column`, `align-items:center`, `justify-content:center`, `text-align:center`, `gap:10px`, `padding:56px 24px`, `color:var(--muted)`, `flex:1`. `.empty .eic`: width and height 56px, `border-radius:18px`, `background:var(--accent-soft)`, `color:var(--accent-text)`, `display:grid`, `place-items:center`. `.empty .eic .ic`: width and height 26px. `.empty b`: `color:var(--ink)`, `font-size:15px`.
- R17. In a parent that is a flex column with a height, the empty state takes the free height of the parent and its content is centred horizontally and vertically in it (D-074): checked in a browser at 360, 720 and 1100 px wide, in both looks, with the centre of the `.eic` and the text block within 1 px of the centre of the parent. The parent's side of this contract is in Design (hand-off to TOKI-015).
- R18. `EmptyState` holds no text of its own and draws no button of its own (R3).

Toast
- R19. `<Toast text="Left #design" />` renders `div.toast` with `role="status"` holding `span` with the text. With `action={{ label, onPress }}` it also renders `button` of `type="button"` with the label after the span. `Toast` is the presentational part: it holds no timer and no state.
- R20. `Toast.css` holds the declarations of the prototype's rules. `.toast`: `pointer-events:auto`, `display:flex`, `align-items:center`, `gap:12px`, `background:var(--ink)`, `color:var(--surface)`, `padding:9px 12px 9px 14px`, `border-radius:var(--radius-sm)`, `box-shadow:var(--pop)`, `animation:tin .18s ease-out`, `font-weight:500`. `.toast button`: `color:var(--accent)`, `font-weight:700`, `padding:2px 6px`. `[data-eff="calm"] .toast button`: `color:var(--accent-soft)`. `@keyframes tin` from `transform:translateY(8px);opacity:0`. The text of a toast wraps; it is not cut.
- R21. `ToastProvider` renders its children and, after them, one `ToastRegion`. `ToastRegion` renders a `div.toasts` with `aria-live="polite"` that is in the document from the first render, also when there is no toast, so that a screen reader announces a toast added later. `.toasts` holds the declarations `position:fixed`, `left:50%`, `transform:translateX(-50%)`, `display:flex`, `flex-direction:column`, `gap:8px`, `align-items:center`, `pointer-events:none`, `z-index:40`, `width:min(480px,92%)`. Decided in this spec: `fixed` replaces the prototype's `absolute`, because the prototype's frame is a demo device and the real page is the window.
- R22. `useToasts()` returns `{ show, dismiss }`. `show({ text, action? })` adds a toast at once and returns its id; `dismiss(id)` removes it and does nothing for an unknown id. Called outside a `ToastProvider`, `useToasts()` throws an error whose message contains `ToastProvider`.
- R23. A toast with an `action` is removed 5000 ms after it was shown (`TOAST_MS_WITH_ACTION`, D-069); a toast without one is removed after 2800 ms (`TOAST_MS_PLAIN`, the prototype's value; no decision gives one, concern 1). Each toast has its own timer. A toast is still in the document 1 ms before its time and gone at its time.
- R24. Pressing the button of a toast removes the toast first and then calls `onPress` once. A second press cannot happen, because the toast is gone; the timer of a removed toast does not call anything.
- R25. Several toasts show in the order of `show`, the oldest on top and the newest at the bottom, nearest to the composer, as in the prototype. There is no limit on their number and no merging of equal texts (concern 4).
- R26. When the provider unmounts, every timer is cleared; no state is set afterwards (no React warning, checked with fake timers).
- R27. `computeToastBottom(viewportHeight, tops)` returns the distance in pixels from the bottom of the window to the bottom of the toasts. With no obstacle it returns `20`. For each obstacle top `t` with `viewportHeight - t > 0` the clearance is `viewportHeight - t + 14`; the result is the largest clearance, and never less than `20`. An obstacle with `t >= viewportHeight` (below the window) is ignored. `NaN` is ignored. The numbers are the prototype's (20 px; 14 px above the tab bar).
- R28. `useToastAvoid(ref)` registers the element of `ref` as one that toasts must stay above, for as long as the calling component is mounted. `ToastRegion` sets its inline `bottom` to `computeToastBottom` of the `top` of every registered element that is in the document and has a height above 0, measured with `getBoundingClientRect`. It measures again when an element changes size (`ResizeObserver`), when the window is resized, and when an element is registered or removed. With no `ToastProvider` above, `useToastAvoid` does nothing. So a registered composer or tab bar is never covered, at any width (D-078, NFR-09); an element that is hidden or moved off the window (the tab bar while a chat is open on a narrow screen) no longer counts.
- R29. An element registered by `useToastAvoid` stays clickable and visible while a toast is shown: in a browser, at 360 px and at 1100 px, with a registered test composer at the bottom and three toasts shown, the bounding box of every toast ends above the top of the composer, and the toasts do not intersect the composer's box.

## Design
### Layout
```
packages/ui-web/src/
├─ index.ts                     adds: export * from "./components"
└─ components/
   ├─ index.ts                  re-exports the folders (group 1 adds its own lines)
   ├─ Avatar/                   Avatar.tsx, getInitials.ts, Avatar.css, Avatar.test.tsx, Avatar.examples.tsx, index.ts
   ├─ PresenceDot/              PresenceDot.tsx, PresenceDot.css, PresenceDot.test.tsx, PresenceDot.examples.tsx, index.ts
   ├─ EmptyState/               EmptyState.tsx, EmptyState.css, EmptyState.test.tsx, EmptyState.examples.tsx, index.ts
   └─ Toast/                    Toast.tsx, ToastProvider.tsx, ToastRegion.tsx, computeToastBottom.ts, Toast.css,
                                Toast.test.tsx, Toast.examples.tsx, index.ts
```
The extra files in `Avatar` and `Toast` exist because one function or one provider each has its own file.

### Where each look and size comes from
- Both looks: the components hold no look selector except the one the prototype has (`[data-eff="calm"] .toast button`). Colours come from the variables of TOKI-009, so Calm and Focus differ by the values of `--ink`, `--surface`, `--accent` and the rest. The prototype's `[data-eff="calm"]` and `[data-eff="focus"]` attributes are the ones TOKI-009 decided.
- Density: only the default avatar size follows it (`--av`). `--gap` and `--row` are used by lists, not by these four.
- Avatar sizes the phase 1 screens use, from the prototype's `av()` and `avp()` calls and its CSS: the density size, and 18, 20, 22, 24, 28, 30, 32, 36, 46 and 64 px. The component accepts any positive number; it keeps no list of sizes, because the prototype sets them in pixels at each place. Two prototype sizes, the Meet tile (56 to 104 px) and the Mail sender (38 px), belong to phases that are not built.
- The font size of the initials is 0.38 times the size (R9), the weight 700 (the 700 face of TOKI-010). The initials of Vietnamese names (`KĐ`) are inside the character set of TOKI-010.

### Avatar
- The initials rule is the prototype's `av()` function (first letter of the first word and of the last word, upper-cased) with two changes, both Decided in this spec: the name is normalised to NFC so that a decomposed `Đỗ` still gives one letter, and a one-word name gives one letter. The prototype would show the same letter twice (`LL` for `Lan`). The reason: a doubled letter is an accident of the prototype's code, not a drawn design (concern 6).
- The hue is a prop, not derived inside the component. The prototype stores one number per person (`h:172`) and makes one up for guests and mail senders. The decision log does not say where the real number comes from (concern 5). Whatever the answer, the component needs only the number.
- `Avatar` is hidden from screen readers, like the icons (TOKI-011 R7). The prototype does the same (`aria-hidden="true"`) and puts the person's name on the button around the avatar (`aria-label` on `avbtn`). A screen that shows an avatar with no name next to it adds the name to the button or row.

### PresenceDot
- The dot has a 2 px ring of `var(--surface)`, so on a row whose background is not `--surface` (a hovered row) the ring shows as a light edge; the prototype is the same.
- The prototype draws the dot as `<i class="pd …">`; a `span` is used here so that the element carries no italic meaning. The class names are the prototype's.
- Found in the prototype: on the profile panel and the People card the dot is given an inline `border-color:var(--surface)`, which would hide the grey ring of an Away dot. The context table says Away is a hollow dot with a grey ring, so R13 follows that, not the inline style.
- Size: 11 px. The prototype makes it 10 px in a conversation row (`.cr .pdw .pd`); that rule belongs to the conversation list, which passes a `className` or its own CSS.

### EmptyState
- The look is the prototype's `emptyHtml()` function and its `.empty` rules. The texts in the prototype are written by each list (for example 'Nobody matches' with 'Try a name or a job title.'; 'You are all caught up' with 'Mentions, thread replies and reactions will show up as they happen.' and the button 'Open your conversations'). D-074 asks for a text written for each list, so the texts belong to the screens (Scope).
- The component fills the free height of its parent (`flex:1`), as in the prototype. Hand-off to TOKI-015: the content area of the AppShell, and every pane body that holds an empty state, is a flex column that has a height and `min-height:0`. Without that, `flex:1` has nothing to fill and the message is not centred.
- Decided in this spec: the title is a `b`, not a heading, as in the prototype. The component gives the region no live role; announcing an empty result to a screen reader is not decided (concern 11).

### Toast
- Pieces: `Toast` (one box), `ToastProvider` (holds the list and the timers, renders the region), `ToastRegion` (the container and its position), `useToasts` (`show`, `dismiss`), `useToastAvoid` (R28). The provider is mounted once, by the AppShell (TOKI-015); screens only call `useToasts()`.
- How long: 5000 ms when the toast has a button, from D-069 ('Undo for 5 seconds'); the prototype's 5200 ms adds 200 ms that no decision asks for. 2800 ms without a button is the prototype's number only. Nothing in the log or the prototype sets a different time for other cases (a mention toast with 'View' has a button, so it gets 5000 ms, which agrees with the journey 'closes after 5 seconds'). There is no `duration` prop: the two numbers are exported constants, so the rule is in one place.
- The button: after a press the toast is removed, then `onPress` runs (the prototype's `toastact` order). A toast has no close button and no swipe; the prototype has neither.
- Place: the prototype puts the toasts at `bottom:20px` of its frame, and on a narrow screen at `calc(var(--tabh) + 14px)`, back to 20 px when a chat or a side pane is open. On a wide screen that sits over the composer, and with a chat open on a narrow screen too. D-078 and NFR-09 forbid that. Decided in this spec: the region does not know the layout; the layout tells it. A component that must not be covered calls `useToastAvoid(ref)`, and the region keeps its bottom edge 14 px above the highest of them (R27, R28). The prototype's two numbers stay (20 px with nothing to avoid, 14 px of space above an obstacle). The alternative, a CSS variable that the shell and the composer keep in step, was not chosen: the composer grows with its text and with attachments, and a variable would need each owner to measure itself and write it. Hand-offs: TOKI-043 (Composer) calls `useToastAvoid` on its outer element, TOKI-015 (BottomTabs) calls it on the tab bar and mounts the provider, and a floating bar that D-078 also protects (the Meet bar, phase 4) does the same. Until they do, the toast sits at 20 px.
- Narrow width: `width:min(480px,92%)`, centred, as in the prototype, so at 360 px a toast is 331 px wide and the text wraps. Nothing else is decided for narrow screens beyond D-078.
- On-screen keyboard: the prototype does nothing and no decision covers it. The region follows the layout viewport only (R28 does not listen to the visual viewport). Concern 4.
- Pause and Focus time (D-072) are not handled here: a caller that is not allowed to show a toast does not call `show` (TOKI-073).
- The timer lives in the provider, in `setTimeout` calls, and each toast keeps its own handle; unmounting clears them (R26). The list is React state in the provider, so a toast shown from an event handler appears on the next render.
- `Toast` is exported on its own so the preview page and tests can draw one without a provider.

### Errors
- `useToasts()` outside a provider -> an error that names `ToastProvider` (R22). No silent loss of a toast.
- `dismiss` of an unknown id, a second `dismiss`, or a timer of a removed toast -> nothing happens (R22, R24).
- A `size` that is 0, negative or not a number -> the density size (R8). A `hue` that is not a number -> 0 (R8).
- An empty name -> an avatar with no letters (R7); the screen is responsible for names (concern 6).

## Testing
- Tests are written first and seen to fail, then made to pass, in the four test files. Markup tests use `renderToStaticMarkup`; the Toast tests use jsdom (Scope).
- R1, R2: a test lists `src/components/*` and the exports of `src/index.ts` and compares them with the lists above (the exports of group 1 are added to its own list; the test checks the group 2 names are present and that no name outside both groups appears).
- R3: a test reads the non-test, non-examples source files and the four CSS files and fails on `@toki/i18n`, `@toki/tokens`, `@toki/platform`, a colour literal, or a variable name outside the allowed set. A second check: no JSX text child holds letters.

## Areas of concern
1. How long a toast without a button stays is not decided. The prototype uses 2.8 seconds and D-069 fixes only the 5 seconds of an Undo toast. This spec uses the prototype's number (R23). Proposal, not a decision: keep 2.8 seconds. Owner: Thanh Truong.
2. A 5-second button is short for a keyboard or screen reader user, and for a person who does not look at the screen: the toast is also not in the tab order before it goes. The decision log gives no accessibility rule for toasts beyond D-075. The prototype has no pause. Proposal, not a decision: stop the timer while the pointer is over the toast or focus is inside it, and restart it afterwards. Not built. Owner: Thanh Truong.
3. In the Focus look the toast button takes the accent colour (`#5EEAD4` for teal) on a toast background of `--ink` (`#E8EDEB`), a ratio of about 1.2 to 1, so the button is hard to read. The prototype does this, and TOKI-009 concern 5 says there is no contrast target, so R20 copies it. Proposal, not a decision: in Focus use `--accent-text` on a darker button background, or `--bg` for the label. Owner: Thanh Truong.
4. Not decided: a limit on how many toasts show at once, whether equal texts merge, the order when the limit is reached, and what a toast does with the on-screen keyboard (the keyboard may cover the toasts and the composer on a phone). The prototype stacks without limit and has no keyboard rule. R25 follows the prototype. Proposal, not a decision: at most three at once, the oldest leaving first; a toast follows the visual viewport. Owner: Thanh Truong.
5. The hue of a person's avatar is not decided. The prototype stores one number per person and invents one for guests. The Avatar takes the number as a prop (R6). Proposal, not a decision: a stable number from 0 to 359 made from the account id, the same on every device, so that no new field is stored. Owner: Thanh Truong (the accounts and People tickets apply it).
6. Decided in this spec: a one-word name shows one letter and the name is normalised to NFC (R7). The prototype shows a doubled letter for one word. Not decided: what to show for a name that is empty or has no letter (for example only an emoji or digits), and whether names with titles or a bracket (for example the prototype's 'Jordan (guest)' style suffix) should be skipped. R7 returns the first character as it is. Owner: Thanh Truong.
7. Presence words and labels. The prototype has the English words Active, Away and Do not disturb (and 'In a Meet'); none has a Vietnamese wording in the prototype (D-139: any other wording is a proposal; proposal for Vietnamese, to be reviewed in TOKI-080: Đang hoạt động, Vắng mặt, Không làm phiền). The text keys follow the i18n rule that the first ticket that needs a text creates its namespace: the first screen that shows presence in words (the plan names TOKI-035 header, TOKI-057 Profile, TOKI-079 People) adds the `presence` namespace; this ticket adds none. Also not decided: which places must pass a `label` to the dot. Active and Do not disturb differ by colour only (both solid), so a dot with no word beside it is not usable for a person who cannot tell the two colours apart. Proposal, not a decision: every dot that is not next to the word gets a `label`. Owner: Thanh Truong.
8. The toast stays above the composer and the navigation only if TOKI-043 (Composer) and TOKI-015 (BottomTabs) call `useToastAvoid`, and TOKI-015 mounts the provider. The plan does not say so in those tickets; they must be told. Until then the toast sits at 20 px and can cover them. Owner: Thanh Truong.

The plan also gives TOKI-013 the need TOKI-018, which nothing here uses. Plan change to make; TOKI-016 reads the `examples` lists (Scope). Owner: Thanh Truong.
