# Text formatting design

Date: 2026-11-23 · Status: draft for review

## Goal
Today the message component draws the text of a message exactly as stored. This work makes the marks of the journeys real: text between two `*` is bold, between two `_` italic, between two backticks code, an `http://` or `https://` address is a link that opens in a new tab, and the composer gets the Bold, Italic and Code buttons. Formatting is made when a message is drawn, from the plain string that is stored, and it is safe by construction: the result is React elements, never markup.

## Requirements
- R1. The reader of marks. `packages/shared/src/text/marks.ts` exports `parseMarks(text: string): MarkNode[]` and `findLinks(text: string): { start: number; end: number; url: string; href: string }[]`, from `packages/shared/src/index.ts` (one line). `MarkNode` is `{ type: "text"; value: string } | { type: "code"; value: string } | { type: "link"; value: string; href: string } | { type: "bold"; children: MarkNode[] } | { type: "italic"; children: MarkNode[] }`, and every node also has `start` and `end`, the offsets in UTF-16 code units of the text it was given (`end` exclusive), covering the marks themselves (for `` `a` `` at the start: `start` 0, `end` 3, `value` `a`). The functions are pure, use no DOM global and never throw for any string: the empty string gives `[]`, and a text with no mark gives one `text` node holding the whole text. Joining the source slices `text.slice(start, end)` of the top-level nodes gives back the input exactly (nothing is dropped). `findLinks` lists, in order, every `link` node at any depth, with `url` the text as it appears and `href` the address after R3. Build-time check, not verified here: `@toki/shared` may be loaded by a native client (React Native, Hermes), where the `URL` class may not implement `username` or `hostname` (from memory, not tested), so "never throws" holds on the web and in Node only until the first native ticket runs the table of R1 and Table T on Hermes; that ticket must do so before it imports the reader. Check: a property test over a table of strings, including the empty string, lone surrogates, U+0000, 10,000 code points of `*`, of `_`, of a backtick and of `a`, and random strings of the characters `*_` backtick, `h`, `t`, `p`, `s`, `:`, `/`, `.`, space and line break: no throw, the slices join to the input, offsets are inside the text and ascending; `findLinks` equals the `link` nodes of `parseMarks`.
- R2. Code. A backtick, then one or more characters that are not a backtick and not a line break, then a backtick, is a `code` node whose `value` is what lies between. The value is literal: a `*`, an `_` or an address inside it is plain text. When the first backtick has no such partner (no second backtick, a line break first, or the next character is a backtick) it is plain text and the scan goes on from the next character. The scan goes left to right and a backtick that closes a node never opens another. This is the prototype's rule (`rich()`), with the content kept literal (concern 1). Check: the cases of Table T.
- R3. Links. An address starts at `http://` or `https://` (the scheme in any letter case), anywhere in a text that is not inside code. It is read in one pass and ends at the first character that is white space (a tab and a line break included), a control or format character (`\p{Cc}`, `\p{Cf}`: U+0000, bidirectional marks), `<`, `>`, `"`, a backtick or a backslash `\`. The backslash ends the address because the URL parser reads `\` as `/` in an `http(s)` address, so `https://evil.example\.trusted.example/` would open `evil.example` while its tail shows another name; ending at `\` leaves the link `https://evil.example` and the rest as text, which is what the link opens. Then these are cut from its end, repeatedly: `.` `,` `;` `:` `!` `?` `'` `*` `_` `~`, and a `)`, `]` or `}` that has more closers than openers of its kind inside the address (the counts are made once, and decremented as characters are cut). What is left is the `value` (the text as typed). The `link` node exists only when all of these hold: the characters right after `://` are the authority, that is the characters up to the first `/`, `?` or `#`, and it is not empty and holds no `@` (an address with a name or password before the host, as in `https://trusted.example@other.example`, is plain text: Decided in this spec, concern 6); `new URL(value)` parses; its protocol is `http:` or `https:`; its `username` and `password` are empty; its hostname is not empty. `href` is `new URL(value).href`. Because of the rules above the host that `new URL(value)` gives is the host that follows `://` in the typed text (apart from letter case, a default port and the encoding of a non-ASCII name): what a person sees is what the link opens. Any other scheme (`javascript:`, `data:`, `ftp:`, `mailto:`) is plain text, and so are `www.example.com` and a bare domain (D-167). An address ends at an `&` only if a character above ends it: the `&` of a query string stays in the address (concern 2). A failed candidate (no host, a name before an `@`) is skipped as a whole: the scan goes on after its end, so an `https://` inside it is not read again (R7). The rules for the trailing characters, the scheme in any case and the `&` are the proposal of concern 2; the end at a backslash, a control character and the refusal of a name before the host are safety rules (concern 6). Check: Table T, including the rows with a backslash, a tab or line break, a control character, mixed-case schemes, `javascript:`, `data:` and a name before the host; and a property test that for every `link` node whose typed address is ASCII, `new URL(value).hostname` equals the text between `://` and the first `/`, `?`, `#` or `:` of `value`, lower-cased, over the table and the random strings of R1 with `\`, `@`, tab and `:` added to their characters.
- R4. Bold. A `*`, then one or more characters (not `*`, not a line break; a code node or a link counts as one character), then a `*`, is a `bold` node. The rule is the prototype's: there is no condition on the characters beside the marks (concern 1). An unpaired `*` is plain text. Check: Table T.
- R5. Italic. A `_`, then one or more characters (not `_`, not a line break), then a `_`, is an `italic` node when the character before the first `_` is the start of the text, white space or `(`, and the character after the second `_` is the end of the text, white space, `)`, `.`, `,`, `!` or `?`. A code node, a link or the mark of a bold node is not such a character, so `snake_case_name` and `a_b_c` are plain text, and an italic that would start or end at the edge of a bold node is plain text (the prototype's behaviour, which reads the text after it made bold; concern 1). The start and the end of the text are boundaries only at the top level; inside a bold node they are not. Check: Table T.
- R6. Order and nesting. The scan finds code first, then links, then bold, then italic, each on what the earlier ones left, so a code node and a link are opaque: a mark is never found inside them, and an address is never cut by an `_` or `*` in it. Bold may hold italic, code and links; italic may hold bold, code and links; bold never holds bold and italic never holds italic; code and link hold only their text. A candidate italic that would cross the edge of a bold node (only one end inside it) is not made, so the nodes are always properly nested. The depth is at most 2 below the top. Check: Table T, and a property test that no `bold` holds `bold` and no `italic` holds `italic`, at any depth.
- R7. Cost. `parseMarks` reads a text of `n` code units in a number of steps that grows linearly with `n`: it is a left-to-right scan with no regular expression that can backtrack, no recursion deeper than the depth of R6 and no search that restarts for each mark or for each failed candidate. In particular a failed address candidate is skipped to its end (R3) and the bracket counts of R3 are made once. `marks.ts` also exports `parseMarksCounted(text): { nodes: MarkNode[]; steps: number }` (not from `index.ts`, used by tests only) where `steps` counts one for each code unit examined by any scan and each code unit cut from an address; `parseMarks` returns its `nodes`. The bound is `steps <= 16 * n + 100`. A text longer than the 10,000-code-point limit (TOKI-037 R4, D-042) is read the same way; the limit is the server's, and this function does not refuse. A second bound keeps the row small: at most 500 nodes of the types `bold`, `italic`, `code` and `link` (counted together, at any depth) are made for one text; from the next mark on, the rest of the text is one `text` node (this keeps a 10,000-character `*a*a*a...` from making about 3,300 `strong` elements in one row, TOKI-041 R25 measures rows; the number 500 is a proposal of this spec, the owner may change it with no other change). Check: the adversarial strings, at `n` = 5,000 and 10,000 code points: `*`, `_` and a backtick repeated, `*a ` repeated, a backtick and `a` repeated, `https://` repeated, `https://a@` repeated, `https://[` repeated, `https://a.com/` followed by `)` repeated, `https://a.com/` followed by `_` repeated, `_ ` repeated and `*a*a` repeated. For each: the result equals the expected nodes (all plain, or the expected count, never more than 500 marks), `steps <= 16 * n + 100`, and `steps(2n) <= 2.5 * steps(n)` with `n` = 5,000. A 10,000-code-point message of each string is one test case. The test counts operations, uses no timer and no wall time.
- R8. The link component. `packages/ui-web/src/components/TextLink/` (`TextLink.tsx`, `TextLink.css`, `TextLink.test.tsx`, `TextLink.examples.tsx`, `index.ts`, one line in `components/index.ts` and one entry in `componentExamples`, TOKI-012 R31) exports `TextLink({ href, children })`. It accepts an `href` only when it is a string that starts with `http://` or `https://` (any letter case), holds no white space, no control character and no backslash, parses with `new URL`, has the protocol `http:` or `https:`, an empty `username` and `password` and a non-empty `hostname`. Then it renders `<a class="lnk" href={u.href} target="_blank" rel="noopener noreferrer">{children}</a>` with `u.href` the PARSED form, never the string it was given. For any other `href` (not a string, empty, another scheme, a name or password in it, not an address) it renders `<span class="lnk">{children}</span>` with no `href`: the component refuses `javascript:` and `data:` itself, so a caller's mistake does not make an unsafe link. `TextLink.css` holds the prototype's rule for `.lnk` (line 254) and nothing else: `color: var(--accent-text); text-decoration: underline; text-underline-offset: 2px`. `rel` has `noopener` so the page cannot be reached from the new tab and `noreferrer` so the address of this workspace is not sent to the other site (Decided in this spec, concern 6). `ui-web` holds no text (R14). Check: `href` `https://example.com/a` gives an anchor with the three attributes and the class, and `HTTP://A.com` gives an anchor whose `href` is `http://a.com/`; these give a span with no `href`, no `target` and no `rel`: `javascript:alert(1)`, `JaVaScRiPt:alert(1)`, a leading space or U+0001 before `javascript:`, `java` + tab + `script:alert(1)`, `data:text/html,x`, `ftp://x`, `//x`, empty, `undefined`, `https:`, `https:foo`, `https://a.com` + line break + `@evil.com`, `https://a.com\@evil.com`, `https://evil.example\.trusted.example/`, `https://user@host.example/` and `https://user:pw@host.example/`; the computed style has the underline and the colour of `--accent-text`; the examples show the link in both looks and on a `--mention-bg` background (the row and the tint belong to TOKI-042 and TOKI-050, and the link inside a mentioned row is checked in the browser test R16).
- R9. The elements of bold, italic and code. Bold is `<strong>`, italic is `<em>` and code is `<code class="fmt-code">` (Decided in this spec, concern 6: they carry the meaning for a screen reader, the prototype's `<b>` and `<i>` do not). `apps/web/src/conversation/formatting/formatting.css` holds: `.fmt-code { font-family: "JetBrains Mono", ui-monospace, "SF Mono", Menlo, monospace; font-size: .92em; background: var(--hover); padding: 1px 5px; border-radius: 5px; }` (prototype line 251, the stack of `.mono` of `utilities.css`) and no rule for `strong` and `em`: bold is the browser's weight 700, which the fonts of TOKI-020 hold, and italic is the style the browser makes, because the app adds no italic file (the fonts spec, concern 3, decided). No colour literal. Long text inside a mark wraps like the text around it (`overflow-wrap: anywhere` of TOKI-042 R8 is inherited). Check: in the browser test (R16) a code mark has the computed font family that starts with `"JetBrains Mono"` and the `--hover` background, a bold mark has weight 700, an italic mark has style italic, and a 300-character word in each does not widen the row. A bold code mark (``*`x`*``) is a `code` in a `strong`: the fonts of TOKI-020 hold JetBrains Mono at weight 500 only, so its bold is made by the browser; this is accepted (the weight of 700 is checked on it too) until a later fonts change adds the file.
- R10. The stage. `apps/web/src/conversation/formatting/` holds `stage.tsx`, which exports `createFormattingStage(options?: { mapText?: (text: string, ctx: TextContext) => ReactNode[] }): TextStage` and `formattingStage = createFormattingStage()`. `TextStage` and `TextContext` are those of TOKI-042 R14. The stage takes each part that is a string, reads it with `parseMarks`, and returns in its place, in order: the text of a `text` node as a string; for `code` the element of R9 with the value as its only child; for `link` a `TextLink` with `href` and the `value` as its child; for `bold` a `strong` and for `italic` an `em` whose children are made the same way, a string child going through `options.mapText` when it is given (default: the string itself). Parts that are elements are returned as they are (TOKI-042 R15), an empty string is dropped, and every element in the returned array has a `key` made from the index of the part and `start` of its node, so a message that is drawn again keeps its elements. Each child of a `strong` or `em` is wrapped in a fragment keyed by its index and `start`, so a `mapText` that returns several elements gives no key warning. The stage builds elements with `createElement`/JSX only. It does not use `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`, `DOMParser` or a markup string, and it does not read `ctx` except to pass it to `mapText`. That rule is kept by one block of `eslint.config.js` for `apps/web` and `packages/ui-web` (in the pattern of the lint rules of `docs/specs/2026-11-12-lint-format-boundary-rules-design.md`), with `no-restricted-syntax` selectors for the JSX attribute `dangerouslySetInnerHTML`, an assignment to `innerHTML` or `outerHTML`, and a call of `insertAdjacentHTML`, so it covers `TextLink` and every later file, not one folder. Check: a probe text with every kind gives the expected elements and strings in order; a part that is an element is returned unchanged and unread; with `mapText` that wraps `@Lan` in a probe element, the probe appears inside the bold and italic elements and not inside code or a link, and the top-level strings are untouched; a lint test runs ESLint on probe files with each forbidden form (in a file of `apps/web` and one of `ui-web`) and gets an error for each, and on the real files of this work gets none; keys are unique and the same for the same text on a second render, and a `mapText` that returns two elements gives no React key warning.
- R11. Where the stage is registered. `apps/web/src/conversation/message/extensions.ts` (TOKI-042 R14) gets one import and one entry: `textPipeline: [formattingStage]`; TOKI-050 adds `mentionStage` after it (TOKI-042 R15). The stage runs for a confirmed message, for a pending, waiting and failed item and for a reply in the thread panel, with the same result, because the component uses one pipeline for all (TOKI-042 R8, R15); a message that is edited is drawn from its new text with the new marks, because the text is the only input. Formatting is made when the message is drawn: the stored text, the text sent and the text of the edit field are the plain string with its marks, never a copy with elements. Check: a probe `Message` test renders a confirmed entry, a pending item and an entry with `editedAt` with the same text and finds the same elements; the edit-field text of the same entry is the string with its marks; the server's `MessageEntry` of the text is unchanged (no key is added).
- R12. Marks and mentions (the part of the agreement with TOKI-050 concern 6 that this work can fix). (a) The stage never gives a chip itself and leaves top-level strings to the stage after it. (b) A string inside code, and inside a link, is never given to `mapText`, so the stage after it cannot tint or chip a name there; the markup of code and links is opaque to it (the proposal of both concerns, concern 3). (c) A string inside bold or italic is given to `mapText` when one is passed, with the string as `parseMarks` returns it. This is written for the answer "a name in a mark is a mention" of concerns 3 and TOKI-050 concern 6, which stay undecided together. The function it takes is `(text: string, ctx: TextContext) => ReactNode[]`, exported by TOKI-050 and owned by TOKI-050 (it is the one place that knows what a name is; this work only calls it): TOKI-050 R19 builds a `TextStage` that reads strings only, so a change request for it is in Plan changes. Until TOKI-050 exports that function and its owner answers, `mapText` is not passed and a name in bold or italic has no chip (the build follows the proposal of TOKI-050 concern 6 for code and the opposite of its second half for bold and italic; the second half is one argument). (d) `parseMarks` and `findLinks` give the ranges of code and links (`start`, `end`), so the server rule of TOKI-050 can skip them if the owner decides that a name in code is plain text for both; this work changes no line of TOKI-050. The opening characters of TOKI-050 R2 (a) (`*`, `_`, a backtick, `(`, `[`, `{`, `"`, `'`) are the marks of this grammar: the three marks are the ones in R2, R4 and R5, and TOKI-050's list is a superset. Check: the tests of R10 for `mapText`; a test with the text `@Lan *@Lan* _@Lan_ ` plus a backtick and `@Lan` in code and `https://example.com/@Lan` gives a probe only inside bold and italic when `mapText` is given and nowhere when it is not.

One reader of marks lives in `packages/shared`, not in the web app, for two reasons: the link previews of TOKI-061 must find the same addresses that the message draws as links (the server worker would otherwise carry a second rule), and TOKI-050 may need the ranges of code and links on the server (R12 d). It has no DOM and no React, so both sides can import it. The cost is that a change to the rule is a change to a shared package; the tests of R1 to R7 are the guard. Decided in this spec (concern 5).

### What formatting is, and what it is not
- It is made when a message is drawn, from the stored plain string. The server, the sync engine, the outbox, the draft, the edit field and the copy of a text hold the text with its marks as typed. Reason: TOKI-037 stores the string as sent; a later change of the rules (a new mark) then changes every old message too, and a draft or an edit never holds two forms of one text.
- It is never markup. The input is a string, the output is a list of React elements and strings, and React sets text as text. No string is turned into HTML at any step, so `<b>`, an `onerror` attribute or an entity in the text can only be shown, never run. This is the whole safety rule and the reason there is no list of allowed or forbidden tags to keep up to date. The server also never builds markup (TOKI-037 Data safety).
- It is the prototype's `rich()` made safe and made correct where `rich()` was an accident of its order. `rich()` escapes first and then substitutes, so an address stops at `&` (its query string is cut), a mark inside code is still applied, an address inside code is still a link and an italic can cross the edge of a bold. The rules above keep what the prototype draws and change these four accidents of its order, each in concern 1 or 2, and also apply the address rules of concern 2: the scheme is read in any letter case (the prototype reads lower case only), the trailing `. , ; : ! ? ' * _ ~` and an unmatched closing bracket are cut from an address, an address ends at a backslash, a control or format character, and a value is a link only when `new URL` accepts it as `http` or `https` with a host and no name before it (in the prototype `https://` alone and `https://user@host` are links).
- The grammar, in the order the scan applies it, with `[x]` for the nodes it makes:

  | Order | Looks for | Makes | Inside it |
  | :---- | :---- | :---- | :---- |
  | 1 | backtick, text, backtick (one line) | code | literal |
  | 2 | `http://` or `https://` up to R3's end | link | literal |
  | 3 | `*`, text, `*` (one line) | bold | italic, code, link |
  | 4 | `_`, text, `_` with the boundaries of R5 | italic | bold, code, link |

### How a pending item and the thread are drawn
The pipeline of TOKI-042 runs for every message the component draws, so a message that waits, one that failed, a reply in the thread panel and the same message in the main list show the same marks. `ctx.mentions` does not matter to this stage.

### The toolbar
The prototype's three buttons wrap the selection and put the caret after it, or between two inserted markers when nothing is selected (line 2388). They sit in the composer's toolbar row before the emoji, attach and mention tools, in the prototype's order (TOKI-043 R17). A person can also type the marks; a button is a convenience, and there is no shortcut (Scope). The composer of the thread box is the same `Composer`; whether it builds its `tools` from `composerTools` is for TOKI-045 and TOKI-043 (Plan changes).

## Data safety
- A text is never turned into markup: no `dangerouslySetInnerHTML`, no `innerHTML`, no markup string (R10), forbidden by one ESLint rule for all of `apps/web` and `packages/ui-web`, with a test of the rule. HTML in a text, inside a mark too, is shown as characters (TS-157, TS-158).
- A link is made only for `http:` and `https:` (D-167), rebuilt by `new URL`, never with a name or password in it, ends at a backslash or a control character so that the host shown is the host opened, and is opened with `noopener noreferrer`; `TextLink` renders the parsed address and refuses any other scheme, a name or password, a backslash and a control character itself (R3, R8).
- The component logs nothing and writes nothing to storage. The reader keeps no state between calls.
- Opening a link sends the person's browser to a site outside Toki; `noreferrer` keeps the address of the workspace from it. The link preview, which makes the server fetch an address, is TOKI-061's and brings its own limits (it refuses internal addresses).

## Areas of concern
1. How the marks are read where the prototype is loose, and what is nested. Not decided. The log gives the three marks and says "text between two" of them (AC-099) and nothing about the rest. The prototype's `rich()` applies bold to any text between two `*` on a line, including `2 * 3 * 4` (bold " 3 "), makes an italic only after white space or `(` and before white space or `)`, `.`, `,`, `!`, `?`, applies marks inside code, and can cross the edge of a bold. The build follows the prototype for what it draws (R4, R5) and changes four things that its order of work makes by accident: content of code is literal (R2), an address is never cut by a mark and is not made inside code (R3, R6), nodes are always properly nested (R6) and a mark never reaches over a line break (R2, R4, R5, which is the prototype's too). Proposal, not a decision: those rules as built; a variant that the owner may prefer is to require that a `*` has no white space after its first and none before its last (so `2 * 3 * 4` stays plain), and the same for `_`. A selection that holds a line break gets its marks anyway, and the result is plain text: the proposal is that the button wraps each line of the selection, a change to R13 only. Owner: Thanh Truong (product owner).
2. Where an address ends. Not decided. D-167 says which schemes. It does not say whether the full stop that ends a sentence, a comma, a closing bracket or the mark that follows (`*https://a.com*`) belongs to it, whether the scheme may be in capitals, or whether a query string with `&` is whole. The prototype keeps the full stop and the closing bracket in the link and, through the order of its escaping, cuts the address at the first `&`, which an address with a query string would not survive. Proposal, not a decision, built as R3: cut `. , ; : ! ? ' * _ ~` from the end (so `https://a.com/x_` loses its `_`), cut a closing bracket only when it has no opener in the address, keep `&`, read the scheme in any case. The prototype differs from this in more than the four accidents of concern 1: it reads the scheme in lower case only, keeps the trailing characters, validates nothing (`https://` alone and `https://user@host` are links) and does not stop at a backslash or a control character. The end at a backslash or a control character is not part of this proposal: it is a safety rule (concern 6), because the URL parser reads `\` as `/`. Owner: Thanh Truong (product owner).
3. A mention inside code, bold, italic or a link. Not decided. TOKI-050 concern 6 is the same question from its side: the server reads the whole string and finds a name anywhere, while the chip stage of TOKI-042 R15 cannot read inside an element. The log does not say whether a name inside a mark is a mention. Proposal, not a decision, and the build as far as this work can make it (R12): a name inside code or a link is plain text for the chip; a name inside bold or italic gets a chip when TOKI-050 exports one function `(text, ctx) => ReactNode[]` and passes it as `mapText` (one line in `extensions.ts` and no change to TOKI-042 R15, which keeps its rule that a stage never reads inside an element). The function is owned by TOKI-050, and until it exists and the owner answers, the build gives no chip inside a mark (R12 c is written for the answer yes); the server, which stores who is named, skips code and links only if the owner chooses the same for both sides, with the ranges of `parseMarks`. A name made of `_` or `*` (a display name such as `ha_tran`) can have its first characters read as a mark before the chip stage sees it; the proposal does not solve it, because the name is cut only when two `_` fall in one line at the boundaries of R5 and a name has one. Owner: Thanh Truong (product owner), with TOKI-050.
4. Which composers have the three buttons. Not decided. The prototype draws the toolbar for every composer it builds (`composerHtml`, line 1400), thread box included, and the edit field has no toolbar. TOKI-043 R17 builds `tools` from `composerTools` in `ConversationComposer`, and TOKI-045 R19 says its box adds nothing but the checkbox, so as written the thread box would have no buttons. Proposal, not a decision: the thread box builds `tools` from the same `composerTools`, so the buttons are there as in the prototype; the edit field of TOKI-047 stays without a toolbar. Owner: Thanh Truong (product owner), with TOKI-043 and TOKI-045.
5. Where the reader lives, and that it is shared. Decided in this spec (a technical choice the Blueprint leaves to the builder): one pure function in `packages/shared` (R1), a stage in the web app (R10), the link in `ui-web` (R8). Reason: the link previews and, possibly, the mention rule must agree with what is drawn as a link or as code, and a rule in the web app would be copied. The cost is a shared package that the server also loads, though it uses nothing of the reader today. Owner: Thanh Truong.
6. The safety choices. Decided in this spec (technical choices): no markup is ever built (R10); `<strong>`, `<em>` and `<code>` in place of `<b>` and `<i>` (R9); `rel="noopener noreferrer"` (R8); an address with a name or password before the host is not a link (R3, and `TextLink` refuses it too); an address ends at a backslash or a control character, and `TextLink` renders the parsed address (R3, R8). Reason: the log requires that a message is never raw HTML (technical design, AC-101) and says nothing of these; an address of the form `https://trusted.example@other.example` shows a trusted-looking name and opens another site, and as the link shows the typed text, refusing it is the one way not to build a deceiving link; `noreferrer` keeps the workspace's address from other sites. Owner: Thanh Truong.
7. The Vietnamese names of the three buttons. Not decided. The English names "Bold", "Italic" and "Code" are the prototype's; there is no Vietnamese text in the prototype or the log, and D-139 treats a wording the prototype lacks as a proposal. Proposal: "In đậm", "In nghiêng", "Mã". Owner: Thanh Truong (product owner).
8. What other places show of a text, and the new tab. Not decided. The prototype applies `rich()` to the text of a message row only (line 1362); the other places it draws a message text (the Pinned tab, Activity, Later, search results, the preview in the list) show the characters as they are. So the marks appear there as `*Friday*` in the prototype. The log does not say whether they should show the formatting, the plain text with the marks removed, or the raw text. Proposal, not a decision: those places keep the raw text as the prototype does, and nothing in this work reads them; a function that removes the marks can be built from `parseMarks` when an owner asks. Also not decided: a link opens in a new tab (D-167) and the page does not say so to a screen reader; proposal: no announcement now (a visually hidden text would be copied with the address), the `title` attribute is the alternative. Owner: Thanh Truong (product owner).
