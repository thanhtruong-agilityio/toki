# Message component design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/message-component.md (Thanh Truong)
Ticket: TOKI-042
Needs: TOKI-017 (i18n), TOKI-041 (the list, in its open pull request 218: the row, `grouped`, `footer`, `target`), TOKI-093 (patterns: `deleteUnsentMessage`), TOKI-094 (`formatTime`) and TOKI-040 (`retry`, `discard`, `MessageItem`, in its open pull request 211). TOKI-037 is merged (`MessageEntry`, `system`).

## Goal
The list of TOKI-041 draws every message with a stand-in that shows the text and nothing else. This work builds the real message component: the avatar, the name and the time in 24 hours, the text, the states of a message that is not confirmed (faded, "Waiting to send", "Not sent" with Retry and Delete), the grey lines of the system messages, and the margin time of a grouped message. It also fixes, once, the places where the work that follows plugs into a message (formatting, mentions, reactions, files, the action bar, edit, delete, pins, the profile panel), so that none of them redraws the layout and each edits one named file.

## Scope
- In:
  - The folder `apps/web/src/conversation/message/`, its props and its use by the list and by the thread panel (R1, R2).
  - What is drawn for the four kinds of item: a user message, a message that is not confirmed, a system line, a deleted message (R3 to R13).
  - The measurements of the prototype, in both looks and at two widths (R4, R6, R20).
  - The places for other work: one typed object in one file (R14 to R17).
  - Texts, accessibility and tests (R18 to R20).
- Out (not now), each with its owner:
  - Day dividers, grouping, the New divider, the order of rows, scrolling, what is hidden: TOKI-041. This component receives `grouped` and draws it (R6); it never looks at a neighbour.
  - The words "Today", "Tomorrow" and "Yesterday" and the glue to the date formatter: they already exist (`common.today`, `common.tomorrow`, `common.yesterday`, and `useDateContext` in the list's `deps.ts`, TOKI-041 R6), so this work adds no `common` key and no glue; the plan line that names them is out of date (Plan changes).
  - Bold, italic, code and links: TOKI-049. Mentions and the tint rule: TOKI-050. Both fill the text pipeline (R15).
  - The action bar, the More menu, the tapped state of a message on narrow screens, copy: TOKI-052. The reaction chips, their picker and their requests: TOKI-046. The thread link and the thread panel: TOKI-045. The edit field, "(edited)", the line of a deleted message, the delete dialog: TOKI-047. The Pinned label, pins and the Pinned tab: TOKI-048. Files, images and link cards: TOKI-058. The profile panel that a press on a name opens: TOKI-057. This work gives each of them a place (R14) and draws none of them.
  - The Guest label and the Automation label beside a name (prototype `.tag`): no Guest exists in the bootstrap people (role is `member` or `admin`, TOKI-032) and automations are phase 5; the ticket that adds either adds its entry to the label row (R14).
  - Sending, the outbox and the states of delivery: TOKI-040. The composer: TOKI-043. The unsaved text of a failed message is not touched here.
  - The seed data: TOKI-081 (it needs nothing from this work).

## Requirements
Structure
- R1. Layout and contract. The component lives in `apps/web/src/conversation/message/`: `Message.tsx`, `UserMessage.tsx`, `SystemLine.tsx`, `DeliveryLabel.tsx`, `MessageHeader.tsx`, `extensions.ts` (R14), `deps.ts` (R2), `format.ts` (R5, R12), `message.css`, `index.ts`, and a test file next to each source. `Message` takes `{ item, grouped, conversationId, target, footer }` with the types of TOKI-041 R21 (`item` is the engine's `MessageItem`, `footer` a `ReactNode`), plus nothing else, so the thread panel of TOKI-045 draws the same component with `grouped` false and no `footer`. The file `apps/web/src/conversation/message-list/MessageRow.tsx` of TOKI-041 keeps its name, its props and its `React.memo`, and its body becomes `<Message {...props} />`; the root keeps `data-mid` (the item's `id`) and `data-testid="message-row"`, and gets `data-grouped`, `data-delivery` (`confirmed`, `sending`, `waiting` or `failed`) and, when `target` is true, `data-target="true"`. The root has no vertical margin and no fixed height (TOKI-041 R20, R21). `index.ts` exports `Message`, `MessageProps` and the types of R14. Check: the files and exports exist; a type test fixes the props; a test renders `MessageRow` and finds the test id and the attributes for each of the four delivery values and for `target`; a test reads `message.css` and finds no `margin-top`, `margin-bottom` or `height:` on the root class.
- R2. State and dependencies. `deps.ts` is the only file of the folder that imports `apps/web/src/client.ts` or the conversation store; it exports `sync` (only `retry` and `discard` are used), `useAuthor(personId)` (the person's `displayName` and `status` from the store of TOKI-032, or `null` for a person the store does not hold, re-read for that one person only), `useCurrentUserId()` and `useTimeZone()` (the browser's zone, `Intl.DateTimeFormat().resolvedOptions().timeZone`, the same rule as TOKI-041 R6 until TOKI-078 stores a person's zone). The component reads nothing else from a store; reactions, pins and replies come through R14. Tests of the folder replace `deps.ts` with `vi.mock`. Check: a test finds an import of `client` or the store outside `deps.ts` and fails on it; changing one person in a fake store re-renders only the rows whose author or system people include that person (a counting render).

What is drawn
- R3. Which layout. `Message` chooses by the item: an item of `kind` `pending` draws the user layout of R4 with the delivery state of R9; an item of `kind` `message` whose `message.kind` is `system` draws the system line of R11; one whose `message.deletedAt` is not `null` draws the deleted layout of R13; every other draws the user layout. A message drawn here is never hidden (TOKI-041 R5 removes those). Check: one test for each of the four paths with a fake item, including a system item that has `deletedAt` set (it draws the deleted layout).
- R4. The user layout, as the prototype draws it (`msgHtml`, `.msg`). One flex row of the width of the list: the avatar (`Avatar` of `@toki/ui-web`, `name` the person's name, `hue` from `personHue(authorId)` of `apps/web/src/people/person-hue.ts`, the size `var(--av)` that the look sets), then a column that takes the rest (`min-width: 0`). The column holds the header line (name, then the time, then the label row of R14), the text (R8) and, in this order, the places of R15. The numbers come from the prototype and were measured in headless Chrome at 1300 and 500 px wide, in both looks:

  | | Calm (`--av` 36, `--gap` 14) | Focus (`--av` 30, `--gap` 8) |
  | :---- | :---- | :---- |
  | Avatar | 36 x 36 | 30 x 30 |
  | Row padding (top, bottom, left) | 7, 7, 12 | 4, 4, 12 |
  | Space above a message that is not grouped | 7 | 4 |
  | Gap between avatar and column | 12 (10 at 500 px) | 12 (10 at 500 px) |
  | Text starts at | 60 px from the row's left edge (58 at 500 px) | 54 (52 at 500 px) |
  | Row height, one line of text, not grouped | 54.6 | 48.6 |
  | Row height, one line of text, grouped | 34.3 | 28.3 |

  Name: 14 px, weight 700, ink; time: 11.5 px, muted; text: 14 px, line height 20.3 px; the header line is a flex row with gap 8, `align-items: baseline` and `flex-wrap: wrap`. The row has a rounded radius (`--radius-sm`) and the background `--surface-2` on hover, on focus inside it and when it is the active message (R14); a message that mentions the person has the background `--mention-bg` (R16). The prototype's top margin of a message becomes padding of an outer wrapper that the list measures with the row (TOKI-041 R20), so the hover background does not cover it. The look is set by the existing tokens `--av` and `--gap`, so the component has no branch on the look. Check: in the browser test (R20) at 1300 and 500 px, in both looks, the avatar sizes, the text offset and the row heights above are read from the page within 1 px; a jsdom test checks the structure (avatar, name, `time`, text, in that order).
- R5. The time. The time beside the name is `formatTime(at, timeZone)` of `@toki/shared` (TOKI-094 R1), 24 hours `HH:mm` for every person and every language (D-123): `at` is `Date.parse(message.createdAt)` for a confirmed message and `localTime` for a waiting or failed one (TOKI-040 R7). It is drawn in a `<time>` element with `dateTime` the ISO form. When `formatTime` returns `null` (a time that is not a number) no time is drawn and the rest of the row is unchanged; the text `Invalid` never appears (D-073). Check: `2026-11-20T09:31:00Z` in `Asia/Ho_Chi_Minh` reads `16:31` and in `UTC` `09:31`; `00:05` reads `00:05`; a pending item reads its `localTime`; an invalid `createdAt` draws no `<time>` and no text with `Invalid`; the text never has `AM` or `PM`. No timer: the time is a function of the data (TOKI-008 R19).
- R6. A grouped message. When `grouped` is true the row has no avatar and no name. The column keeps its left edge: a spacer the width of the avatar (`var(--av)`) holds the time, right-aligned, 11 px, muted, with 3 px above, in a `<time>` element (the prototype's `.gut`). The time is in the page for a screen reader at all times. It is seen on hover of the row, when focus is inside the row, when the row is the active message (R14), and always on a device that cannot hover (`@media (hover: none)`), so the time is never hover-only (D-067; Decided in this spec, concern 3). A grouped row that has a state to show (R9 or a label of R14) draws a header line with no name: the time, then the labels, and the spacer is empty then, so the time is not drawn twice (Decided in this spec, concern 4). Check: jsdom: a grouped row has no avatar and no name, has one `<time>`, and has the same column offset as one that is not grouped (the browser test of R20 reads the x of the text); a grouped row with `editedAt`-style label from a test extension shows a header line with the time and the label and no gutter time; the stylesheet has the `hover: none` rule that sets the gutter time visible (a test reads `message.css`).
- R7. The author. The name is the `displayName` from `useAuthor`. A person the store does not hold shows the text of `message.unknownAuthor` and an avatar with the initials of that text and the hue of the id. A person whose `status` is `deactivated` has the label `message.deactivated` (`Tag` of `@toki/ui-web`) after the name; the old messages stay (F41). The name is plain text; when `extensions.openProfile` is set (R14) the avatar and the name are buttons that call it with the person's id and the avatar button has the person's name as its accessible name, and until then they are not buttons (a button that does nothing is not drawn). Check: a known person, an unknown one and a deactivated one each draw the expected name or label; with `openProfile` set a press on the name and on the avatar calls it with the id once each; without it neither is a button.
- R8. The text. The text of a confirmed message is `message.text`, of a pending item `item.text`; it goes through the text pipeline (R15) and is drawn in an element with `white-space: pre-wrap` and `overflow-wrap: anywhere` (the prototype's `.tx`), so a line break stays and a long word wraps inside the column. It is never set as markup: the default pipeline returns the string as a text node. An empty text or `null` draws no text element (a message may later hold only files, TOKI-058). Check: a text with `<b>x</b>` shows the characters and creates no element; a text with a newline keeps it (computed style); a 300-character word at 500 px does not make the row wider than the list (browser test); an empty text draws no text element.
- R9. The states of a message that is not confirmed (`item.kind` `pending`; F11, D-087, D-097). All three keep the avatar, the name and the time of the person, since the prototype draws a waiting message in full. Their text is drawn in the muted colour, the prototype's `.msg.pending .tx` (Decided in this spec: the one rule covers "faded until confirmed", concern 5).
  Sending: the faded text and `aria-busy="true"` on the root; no label. It becomes the confirmed message with the same key (TOKI-041 R5), so the row keeps its place and, apart from colour and the time, nothing moves.
  Waiting: the label `message.waiting`, "Waiting to send" (the prototype's text), in the header line after the time: the clock icon (`clock`, 12 px) and the text, 11.5 px, weight 600, colour `--mention-ink` on `--mention-bg`, radius 6, 0 6 px padding (the prototype's `.waiting`).
  Failed: the label `message.notSent`, "Not sent" (D-087; the wording is a proposal, D-139, concern 1), in the colour `--danger` on `--danger-soft`, the same shape as the waiting label, and after it two text buttons, `message.retry` "Retry" and `message.delete` "Delete" (`Button` with `variant="link"`). Retry calls `sync.retry(item.id)`. Delete calls `sync.discard(item.id)` with no dialog and no toast, which is the pattern `deleteUnsentMessage` of TOKI-093 (confirmation `none`); the focus, which is on the button that is about to leave the page, moves first to the nearest ancestor with `role="list"` (the list's scroller, `tabIndex` 0, TOKI-041 R24) when there is one, so it is not lost to the page (Decided in this spec, concern 6). Retry is offered offline too: the engine turns the item into `waiting` and sends it when the connection is back (TOKI-040 R11; D-079 lets messages wait), so it is not behind `useOnlineGate`. A press that the engine answers with `false` (the item is no longer failed) changes nothing.
  A message that confirms has no label. Check: a table of the three deliveries: the faded text colour, `aria-busy` only for `sending`, the label text for `waiting` and `failed`, the buttons only for `failed`; Retry calls `retry` with the id once; Delete calls `discard` once, opens no dialog (`queryByRole("dialog")` is null) and shows no toast, and the focus is on the scroller of a test list; a fake `sync` whose `retry` returns false changes nothing; a confirmed message with the same id has no label.
- R10. What a person's own message shows. A message of the signed-in person is drawn like any other: no "You", no different colour or side. Check: a test with `authorId` equal to the signed-in id draws the same structure as another person's.
- R11. System lines. A message with `kind` `system` is drawn by `SystemLine` from `message.system.type` and `message.system.userIds` (TOKI-037 R15, R16) and `message.authorId` (the person who acted). The data has no text: the words are keys of the namespace `message`, filled with display names (R12). The types are `channel_created`, `member_joined`, `members_added`, `member_left`, `topic_changed` (TOKI-037 R22) and `message_pinned` (TOKI-048 R9: a line with no people). A type that the client does not know draws nothing and no padding, so a newer server never shows a broken line. A system line is one grey line: no avatar, no name column, no time, no actions, no reactions and no footer; it is aligned with the text column of a message (the same left edge as R4) and uses the colour `--muted`, 13 px, line height 20.3 px, the same row padding as a message (R4) and no hover background; the names in it have weight 600. Its date is the day divider above it (D-100: "with the date"; TOKI-041 R6). It is never grouped (TOKI-041 R7) and it never raises an unread count or a notification (the server and TOKI-053 decide that, D-100, D-165; this work only draws). The look is a proposal, because the prototype draws no system line (concern 2). Check: each of the six types renders its text for a fake people store in English; an unknown type renders an empty element with no padding; the line has no `<time>`, no button and no avatar; `getComputedStyle` of the test row has the muted colour; the text column offset equals the user layout's in the browser test.
- R12. The words of a system line, and how people are named in them. `format.ts` builds the text: the actor is `message.authorId`, the people are `system.userIds`, each is the display name from the store, and a person the store does not hold is `message.system.someone`. The line always names the person, including the signed-in one (no "You"; concern 1). For `members_added` the people are listed with `Intl.ListFormat` in the interface language (`type: "conjunction"`, `style: "long"`): up to 4 people are all named; more than 4 name the first 3 followed by `message.system.others` with the count of the rest ("5 others"; a proposal, concern 1). A line of `members_added` with no known people reads with `message.system.someone`. The English texts: `member_joined` "{name} joined" (D-100), `channel_created` "{name} created this channel", `members_added` "{name} added {people}", `member_left` "{name} left the channel", `topic_changed` "{name} changed the topic", `message_pinned` "{name} pinned a message"; all but the first are proposals (journeys F20 to F24 and F17 accepted what the line does, D-091; D-139 makes the words a proposal). Check: a table over the six types with one, two and four people for `members_added`; five people read "Lan added A, B, C and 2 others"; an unknown person reads "Someone"; the Vietnamese catalog renders the same keys with the list joined by the Vietnamese conjunction of `Intl.ListFormat` (the test asserts the output of `Intl.ListFormat("vi")`, not a literal).
- R13. A deleted message that is drawn. A message with `deletedAt` set that the list did not hide (a message that an Admin deleted, or one the author deleted that has replies, TOKI-041 R5) draws, in place of the avatar, name, time and text, the result of `extensions.renderDeleted({ by })`, where `by` is `message.deletedBy` (`"author"` or `"admin"`, TOKI-047 R8), and then the `footer`, so a deleted root keeps its thread link (TOKI-047 R20). It draws no avatar, no name, no time, no labels, no editor, no reactions and no action bar. Until TOKI-047 fills the entry, `renderDeleted` is a function that returns `null` and the row draws nothing but the footer; no message can have `deletedAt` before TOKI-047 writes it (TOKI-037 R15), so nothing is lost. Check: with a test entry the deleted layout draws that node and the footer and none of the pieces above; with the default the row draws only the footer; a deleted item with a `by` of each value passes it.

- R15. The text pipeline and the order under the text. The text is made by `textPipeline.reduce((parts, stage) => stage(parts, ctx), [text])`: a stage receives the parts so far (strings and elements), returns parts, changes only the strings and keeps every element as it is, and builds elements, never markup strings (so TOKI-049 can turn `*x*` into an element and TOKI-050 can turn `@Lan` in what remains into a chip without reading inside a code span). The result is drawn inside the text element of R8. The pipeline runs for a pending item too, with its own id, so a message looks the same before and after confirmation. A stage that throws is caught for that one message: the plain text is drawn, so one bad message never blanks a list. Under the text the column draws, in this order: the result of `files`, the result of `reactions`, the `footer` (TOKI-041 R21). Check: a probe stage that wraps `x` in an element is applied; two stages apply in array order and the second cannot change an element made by the first; a throwing stage draws the plain text; the order text, files, reactions, footer is read from the DOM; the pending item goes through the pipeline.
- R16. The mention tint and the active row. When `isMentioned(message, meId)` is true the row has the class `mentioned` and the background `--mention-bg` that stays on hover (the prototype's `.msg.mentioned`); a chip with the class `mention` inside such a row has no background of its own (the prototype's rule), so the yellow is not doubled. The tint is this work's CSS; the rule that decides it, including "not my own message", is TOKI-050's. When `useActive(id)` is true the row has the class `act`. A system line, a deleted line and a pending item are never tinted. Check: a probe `isMentioned` returning true gives the class and the computed background `--mention-bg`; it is not called for a system line or a pending item; `useActive` true gives `act`.
- R17. The action bar's place. When `actions` returns a node it is the last child of the row root inside the measured box, and the root is `position: relative`, so the bar of TOKI-052 can be placed over the top right edge as the prototype does (`right: 12px; top: -16px`). The component calls `actions` for an item of `kind` `message` that is a user message with no `deletedAt`, and for a pending item, and not for a system line, a deleted message or a message whose editor is open; TOKI-052 decides what a pending or failed item offers. At widths under 720 px the root is `flex-wrap: wrap`, so a bar that TOKI-052 gives `flex-basis: 100%` sits below the message (the prototype's tapped-message rule); the rule for the bar itself is TOKI-052's. Check: a probe node is the last child for a user message and for a pending item, and absent for the other three cases; the computed `position` of the root is `relative`; `message.css` holds the narrow `flex-wrap` rule.

Texts, accessibility, tests
- R18. Texts. Every text goes through `@toki/i18n/react`: the namespace `message` in the files `message.ts` of `en` and `vi`, with one import and one entry in each `index.ts`: `waiting` ("Waiting to send", the prototype), `notSent` ("Not sent"), `retry` ("Retry"), `delete` ("Delete"), `deactivated` ("Deactivated"), `unknownAuthor` ("Unknown person"), and under `system`: `memberJoined`, `channelCreated`, `membersAdded`, `memberLeft`, `topicChanged`, `messagePinned`, `others`, `someone` (R12). Every English text the prototype does not contain, and every Vietnamese text, is a proposal (D-139); the Vietnamese form of address is D-188 (Open) and the texts use no pronoun. No text is in a component or in `packages/ui-web`. The key names are unique to this work: it uses no key of `messageActions`, `pins`, `thread` or `reactions`. Check: `pnpm i18n:check` exits 0; a test renders every state in English and in Vietnamese; a search of the folder for a quoted English word finds none outside the catalogs and tests.
- R19. Accessibility. The avatar is hidden from a screen reader (the component's own rule); the author's name is text in the row, so a screen reader reads name, time, then text. Retry and Delete are real buttons reachable with Tab, in that order, activated by Enter and Space, with a visible focus ring. The waiting and not-sent labels are text, not colour alone: the words and, for waiting, the clock icon. The faded text of a sending message keeps a contrast of at least 4.5 to 1 against the row background in both themes (the muted token against `--surface`; a test computes it from the tokens). Nothing animates, so `prefers-reduced-motion` needs no rule. The root is not a landmark and has no role; the list wrapper supplies `listitem` (TOKI-041 R24). One browser test file, `e2e/message.spec.ts`, run by `pnpm test:e2e` in Chromium with the stubs of `e2e/message-list.spec.ts` (TOKI-041 R25), at 1300 and at 500 px, in the Calm and the Focus look: it reads the numbers of the table of R4, the text offset of a grouped message equal to that of a message that is not grouped (R6), a 300-character word that does not widen the row (R8), a system line whose text starts at the same x as a message's text (R11), and, in a touch context (`isMobile`, `hasTouch`) where `(hover: none)` matches, the time of a grouped message visible without hover (R6). ## Design
### How a row is made
```
MessageRow (TOKI-041, memo)  ->  Message
  item.kind pending ------------------> UserMessage (+ DeliveryLabel)
  message.kind system ----------------> SystemLine (format.ts)
  message.deletedAt ------------------> renderDeleted + footer
  otherwise --------------------------> UserMessage
UserMessage:  [avatar | gutter time] [ header: name, time, labels | text pipeline | files | reactions | footer ]  [ actions ]
```
- The component is a function of its props and of `deps.ts`. It never reads the list, the window or a neighbour: `grouped`, `target` and `footer` are given. That is what lets the thread panel draw it too.
- The outer wrapper carries the prototype's top margin as padding; the inner box carries the padding, the radius and the background, so hover and tint do not cover the space between messages.

### Why a typed object and not props
Each of the nine tickets that add to a message would otherwise add a prop to `Message` and to `MessageRow`, to the list and to the thread panel, which draw the same component. One object read inside the component keeps the props of TOKI-041 R21 as they are and puts every later change in one file, with a type that a compiler checks and a default that draws nothing. It follows the rule that TOKI-040 R21 and TOKI-041 R4 already use: the ticket that lands second adds the one line.

### What the prototype does not draw
The prototype has no system line, no "Not sent", no deactivated label, no sending state other than a waiting message, no "(edited)" or Pinned label on a grouped message, and a time that a grouped message shows on hover only. The prototype also shows no way to see an unknown author. Each is built here as stated and marked: wording is concern 1, look is concern 2, the others are decisions of this spec (concerns 3 to 6).

### Known limits
- The time of a grouped message in the margin is not shown to a person on a hover device until they hover or focus the row (the prototype's behaviour).
- A message with a very large number of reactions or files is as tall as its parts; the list measures the row (TOKI-041 R20).
- A `Today` label on a day divider is the list's; this component never shows a date, only a time.
