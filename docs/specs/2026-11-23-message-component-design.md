# Message component design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/message-component.md (Thanh Truong)
Ticket: TOKI-042
Needs: TOKI-017 (i18n), TOKI-041 (the list, in its open pull request 218: the row, `grouped`, `footer`, `target`; it needs TOKI-040, so `retry`, `discard` and `MessageItem` of pull request 211 come through it), TOKI-093 (patterns: `deleteUnsentMessage`) and TOKI-094 (`formatTime`). TOKI-037 is merged (`MessageEntry`, `system`). The tickets that fill a place of R14 need this one (Plan changes).

## Goal
The list of TOKI-041 draws every message with a stand-in that shows the text and nothing else. This work builds the real message component: the avatar, the name and the time in 24 hours, the text, the states of a message that is not confirmed (muted text, "Waiting to send", "Not sent" with Retry and Delete), the grey lines of the system messages, and the margin time of a grouped message. It also fixes, once, the places where the work that follows plugs into a message (formatting, mentions, reactions, files, the action bar, edit, delete, pins, the profile panel), so that none of them redraws the layout and each edits one named file.

## Scope
- In:
  - The folder `apps/web/src/conversation/message/`, its props and its use by the list and by the thread panel (R1, R2).
  - What is drawn for the four kinds of item: a user message, a message that is not confirmed, a system line, a deleted message (R3 to R13).
  - The measurements of the prototype, in both looks and at two widths (R4, R6, R20).
  - The places for other work: one typed object in one file, whose places are components (R14 to R17).
  - Texts, accessibility and tests (R18 to R20).
- Out (not now), each with its owner:
  - Day dividers, grouping, the New divider, the order of rows, scrolling, what is hidden: TOKI-041. This component receives `grouped` and draws it (R6); it never looks at a neighbour.
  - The words "Today", "Tomorrow" and "Yesterday" and the glue to the date formatter: they already exist (`common.today`, `common.tomorrow`, `common.yesterday`, and `useDateContext` in the list's `deps.ts`, TOKI-041 R6), so this work adds no `common` key and no glue; the plan line that names them is out of date (Plan changes).
  - Bold, italic, code and links: TOKI-049. Mentions and the tint rule: TOKI-050. Both fill the text pipeline (R15).
  - The action bar, the More menu, the tapped state of a message on narrow screens, copy: TOKI-052. The reaction chips, their picker and their requests: TOKI-046. The thread link and the thread panel: TOKI-045. The edit field, "(edited)", the line of a deleted message, the delete dialog: TOKI-047. The Pinned label, pins and the Pinned tab: TOKI-048. Files, images and link cards (the `Files` place, the block `.att` and the grouping condition for files): TOKI-062; the file storage under them draws nothing: TOKI-058. The profile panel that a press on a name opens: TOKI-057. This work gives each of them a place (R14) and draws none of them.
  - The Guest label and the Automation label beside a name (prototype `.tag`): no Guest exists in the bootstrap people (role is `member` or `admin`, TOKI-032) and automations are phase 5; the ticket that adds either adds its entry to the label row (R14).
  - Sending, the outbox and the states of delivery: TOKI-040. The composer: TOKI-043. The unsaved text of a failed message is not touched here.
  - The seed data: TOKI-081 (it needs nothing from this work).

## Requirements
Structure
- R1. Layout and contract. The component lives in `apps/web/src/conversation/message/`: `Message.tsx`, `UserMessage.tsx`, `SystemLine.tsx`, `DeliveryLabel.tsx`, `MessageHeader.tsx`, `extensions.ts` (R14), `deps.ts` (R2), `format.ts` (R5, R12), `message.css`, `index.ts`, and a test file next to each source. `Message` takes `{ item, grouped, conversationId, target, footer }` with the types of TOKI-041 R21 (`item` is the engine's `MessageItem`, `footer` a `ReactNode`), plus nothing else, so the thread panel of TOKI-045 draws the same component with `grouped` false and no `footer`. A row is two elements (R4): the outer wrapper `.message-outer` and the inner box `.message`. The outer wrapper is the element that `MessageRow` of TOKI-041 and the list measure; it carries `data-mid` (the item's `id`), `data-testid="message-row"`, `data-grouped`, `data-delivery` (`confirmed`, `sending`, `waiting` or `failed`), `aria-busy` (R9) and, when `target` is true, `data-target="true"`. The inner box carries the classes `message`, `mentioned` and `act` (R16), `position: relative`, the props of `useRow` (R14) and the place of the action bar (R17). `MessageRow.tsx` of TOKI-041 keeps its name, its props and its `React.memo`, and its body becomes `<Message {...props} />`. The outer wrapper has no margin and no fixed height; its only vertical space is the top padding of R4 (TOKI-041 R20, R21). `index.ts` exports `Message`, `MessageProps` and the types of R14. Check: the files and exports exist; a type test fixes the props; a test renders `MessageRow` and reads the outer wrapper for the test id and the attributes for each of the four delivery values and for `target`, and the inner box for its classes; a test reads `message.css` and finds no `margin-top`, `margin-bottom` or `height:` on the outer class.
- R2. State and dependencies. `deps.ts` is the only file of the folder that imports `apps/web/src/client.ts` or the conversation store; it exports `sync` (only `retry` and `discard` are used), `useAuthor(personId)` (the person's `displayName` and `status` from the store of TOKI-032, or `null` for a person the store does not hold, re-read for that one person only), `useCurrentUserId()` and `useTimeZone()` (the browser's zone, `Intl.DateTimeFormat().resolvedOptions().timeZone`, the same rule as TOKI-041 R6 until TOKI-078 stores a person's zone). The component reads nothing else from a store; reactions, pins and replies come through R14. Tests of the folder replace `deps.ts` with `vi.mock`. Check: a test finds an import of `client` or the store outside `deps.ts` and fails on it; changing one person in a fake store re-renders only the rows whose author or system people include that person (a counting render).

What is drawn
- R3. Which layout. `Message` chooses by the item: an item of `kind` `pending` draws the user layout of R4 with the delivery state of R9; an item of `kind` `message` whose `message.kind` is `system` draws the system line of R11; one whose `message.deletedAt` is not `null` draws the deleted layout of R13; every other draws the user layout. A message drawn here is never hidden (TOKI-041 R5 removes those). Check: one test for each of the four paths with a fake item, including a system item that has `deletedAt` set (it draws the deleted layout).
- R4. The user layout, as the prototype draws it (`msgHtml`, `.msg`). One flex row of the width of the list: the avatar (`Avatar` of `@toki/ui-web`, `name` the person's name, `hue` from `personHue(authorId)` of `apps/web/src/people/person-hue.ts`, the size `var(--av)` that the look sets), then a column that takes the rest (`min-width: 0`). The column holds the header line (name, then the time, then the label row of R14), the text (R8) and, in this order, the places of R15. The inner box `.message` is this flex row: it holds the padding, the radius, the background, `position: relative` and the tint; the outer wrapper `.message-outer` holds only the space above a message that is not grouped, as top padding, so hover and tint never cover it and the list measures both with the row. The numbers come from the prototype and were measured in headless Chrome at 1300 and 500 px wide, in both looks:

  | | Calm (`--av` 36, `--gap` 14) | Focus (`--av` 30, `--gap` 8) |
  | :---- | :---- | :---- |
  | Avatar | 36 x 36 | 30 x 30 |
  | Row padding (top, bottom, left) | 7, 7, 12 | 4, 4, 12 |
  | Space above a message that is not grouped | 7 | 4 |
  | Gap between avatar and column | 12 (10 at 500 px) | 12 (10 at 500 px) |
  | Text starts at | 60 px from the row's left edge (58 at 500 px) | 54 (52 at 500 px) |
  | Row height, one line of text, not grouped | 54.6 | 48.6 |
  | Row height, one line of text, grouped | 34.3 | 28.3 |

  Name: 14 px, weight 700, ink; time: 11.5 px, muted; text: 14 px, line height 20.3 px; the header line is a flex row with gap 8, `align-items: baseline` and `flex-wrap: wrap`, and carries the `id` `message-header-<id>` (the item's `id`), so that `useRow` of TOKI-052 can name it in `aria-labelledby` (a request of TOKI-052 R9; the element is the header line of a row that has one, and for a grouped row with no header line it is the gutter `<time>` of R6, so the `id` is always in the page for a confirmed message). The row has a rounded radius (`--radius-sm`) and the background `--surface-2` on hover, on focus inside it and when it is the active message (R14); a message that mentions the person has the background `--mention-bg` (R16). The prototype's top margin of a message is the padding of the outer wrapper (7 or 4 px, none when `grouped`). The look is set by the existing tokens `--av` and `--gap`, so the component has no branch on the look. Check: in the browser test (R20) at 1300 and 500 px, in both looks, the avatar sizes, the text offset and the row heights above are read from the page within 1 px; a jsdom test checks the structure (outer wrapper, inner box, avatar, name, `time`, text, in that order) and that the header line has the `id` `message-header-<id>`, and that a grouped row without a header line has the same `id` on its gutter `<time>`. The font of the time (the mono, tabular face the prototype sets on `time`) comes from the global `time` rule of `packages/ui-web/src/styles/utilities.css`, so `message.css` adds none; the browser test reads the computed `font-family` and `font-variant-numeric` of a `<time>`.
- R5. The time. The time beside the name is `formatTime(at, timeZone)` of `@toki/shared` (TOKI-094 R1), 24 hours `HH:mm` for every person and every language (D-123): `at` is `Date.parse(message.createdAt)` for a confirmed message and `localTime` for a waiting or failed one (TOKI-040 R7). It is drawn in a `<time>` element with `dateTime` the ISO form, made only when `at` is a finite number (`Number.isFinite(at)`), because `new Date(NaN).toISOString()` throws a `RangeError`. When `formatTime` returns `null` (a time that is not a number) no `<time>` is drawn, `toISOString` is not called, and the rest of the row is unchanged; the text `Invalid` never appears (D-073). Check: `2026-11-20T09:31:00Z` in `Asia/Ho_Chi_Minh` reads `16:31` and in `UTC` `09:31`; `00:05` reads `00:05`; a pending item reads its `localTime`; an invalid `createdAt` and a pending item whose `localTime` is `NaN` draw no `<time>`, throw nothing and show no text with `Invalid`; the text never has `AM` or `PM`. No timer: the time is a function of the data (TOKI-008 R19).
- R6. A grouped message. When `grouped` is true the row has no avatar and no name. The column keeps its left edge: a spacer the width of the avatar (`var(--av)`) holds the time, right-aligned, 11 px, muted, with 3 px above, in a `<time>` element (the prototype's `.gut`). The time is in the page for a screen reader at all times. It is seen on hover of the row, when focus is inside the row, when the row is the active message (R14), and always on a device that cannot hover (`@media (hover: none)`), so the time is never hover-only (D-067; Decided in this spec, concern 3). A grouped row for which at least one entry of `labels` (R14) has `show(message)` true draws a header line with no name: the time, then those labels, and the spacer is empty then, so the time is not drawn twice (Decided in this spec, concern 4). A pending item is never grouped (TOKI-041 R7 requires both neighbours to be confirmed), so the states of R9 never reach a grouped row; `Message` still draws a pending item as not grouped if it is given `grouped` true. Check: jsdom: a grouped row has no avatar and no name, has one `<time>`, and has the same column offset as one that is not grouped (the browser test of R20 reads the x of the text); a pending item given `grouped` true draws the avatar and name; a grouped row whose test label has `show` true shows a header line with the time and the label and no gutter time; the stylesheet has the `hover: none` rule that sets the gutter time visible (a test reads `message.css`).
- R7. The author. The name is the `displayName` from `useAuthor`. A person the store does not hold shows the text of `message.unknownAuthor` and an avatar with the initials of that text and the hue of the id. A person whose `status` is `deactivated` has the label `message.deactivated` (`Tag` of `@toki/ui-web`) after the name; the old messages stay (F41). The name is plain text; when `useOpenProfile(conversationId)` (R14) returns a function the avatar and the name are buttons that call it with the person's id and the avatar button has the person's name as its accessible name, and while it returns `undefined` they are not buttons (a button that does nothing is not drawn). Check: a known person, an unknown one and a deactivated one each draw the expected name or label; with a probe `useOpenProfile` that returns a function a press on the name and on the avatar calls it with the id once each; with the default (it returns `undefined`) neither is a button.
- R8. The text. The text of a confirmed message is `message.text`, of a pending item `item.text`; it goes through the text pipeline (R15) and is drawn in an element with `white-space: pre-wrap` and `overflow-wrap: anywhere` (the prototype's `.tx`), so a line break stays and a long word wraps inside the column. It is never set as markup: the default pipeline returns the string as a text node. An empty text or `null` draws no text element (a message may later hold only files, TOKI-062 draws them). Check: a text with `<b>x</b>` shows the characters and creates no element; a text with a newline keeps it (computed style); a 300-character word at 500 px does not make the row wider than the list (browser test); an empty text draws no text element.
- R9. The states of a message that is not confirmed (`item.kind` `pending`; F11, D-087, D-097). All three keep the avatar, the name and the time of the person, since the prototype draws a waiting message in full. Their text is drawn in the muted colour: for a waiting message this is the prototype's rule `.msg.pending .tx` (Decided in this spec, concern 5); for a sending and a failed message it is the same colour, decided in concern 2, because the prototype draws only the waiting message and F11 says only "slightly faded" (concern 2).
  Sending: the muted text and `aria-busy="true"` on the outer wrapper; no label. It becomes the confirmed message with the same key (TOKI-041 R5), so the row keeps its place and, apart from colour and the time, nothing moves.
  Waiting: the label `message.waiting`, "Waiting to send" (the prototype's text), in the header line after the time: the clock icon (`clock`, 12 px) and the text, 11.5 px, weight 600, colour `--mention-ink` on `--mention-bg`, radius 6, 0 6 px padding (the prototype's `.waiting`).
  Failed: the label `message.notSent`, "Not sent" (D-087; the wording is decided, concern 1), in the colour `--danger` on `--danger-soft`, the same shape as the waiting label, and after it two text buttons, `message.retry` "Retry" and `message.delete` "Delete" (`Button` with `variant="link"`). Retry calls `sync.retry(item.id)`. Delete calls `sync.discard(item.id)` with no dialog and no toast, which is the pattern `deleteUnsentMessage` of TOKI-093 (confirmation `none`); the focus, which is on the button that is about to leave the page, moves first to the closest ancestor of the outer wrapper (the search starts at its parent, because the row itself is leaving) that has the attribute `data-focus-fallback`; the body of the thread panel is to set it with `tabIndex` 0 (a change request to TOKI-045 R18), and so is the list's scroller (a change request to TOKI-041 R24; the scroller already has `tabIndex` 0). When no ancestor has the attribute, the focus goes to the closest ancestor that has a `tabindex` attribute (today that is the list's scroller), and when there is none, to `document.body`; this is the only case where it is lost (Decided in this spec, concern 6). Retry is offered offline too: the engine turns the item into `waiting` and sends it when the connection is back (TOKI-040 R11; D-079 lets messages wait), so it is not behind `useOnlineGate`. A press that the engine answers with `false` (the item is no longer failed) changes nothing.
  A message that confirms has no label. Check: a table of the three deliveries: the muted text colour, `aria-busy` only for `sending`, the label text for `waiting` and `failed`, the buttons only for `failed`; Retry calls `retry` with the id once; Delete calls `discard` once, opens no dialog (`queryByRole("dialog")` is null) and shows no toast, and the focus is on the scroller of a test list in the main list and on the body of a test thread panel (each with `data-focus-fallback`), on the closest ancestor with a `tabindex` when no ancestor has the attribute, and on `document.body` when there is none; a fake `sync` whose `retry` returns false changes nothing; a confirmed message with the same id has no label.
- R10. What a person's own message shows. A message of the signed-in person is drawn like any other: no "You", no different colour or side. Check: a test with `authorId` equal to the signed-in id draws the same structure as another person's.
- R11. System lines. A message with `kind` `system` is drawn by `SystemLine` from `message.system.type` and `message.system.userIds` (TOKI-037 R15, R16) and `message.authorId` (the person who acted). The data has no text: the words are keys of the namespace `message`, filled with display names (R12). The types are `channel_created`, `member_joined`, `members_added`, `member_left`, `topic_changed` (TOKI-037 R22) and `message_pinned` (TOKI-048 R10: a line with no people). Main's `SYSTEM_LINE_TYPES` holds the first five; `message_pinned` is added by TOKI-048, which this ticket does not wait for, so `format.ts` takes `system.type` as a `string` and chooses with a `switch` whose `message_pinned` case is written against the string and whose default draws nothing: the code compiles on main and the six-type test uses a fake item typed through a cast. A type that the client does not know draws nothing and no padding, so a newer server never shows a broken line. A system line is one grey line: no avatar, no name column, no time, no actions, no reactions and no footer; it is aligned with the text column of a message (the same left edge as R4) and uses the colour `--muted`, 13 px, line height 20.3 px, the same row padding as a message (R4) and no hover background; the names are plain text in the same weight (the translator `t` returns strings only, so a bold name would need the template split at its placeholders; that is left out, concern 2). Its date is the day divider above it (D-100: "with the date"; TOKI-041 R6). It is never grouped (TOKI-041 R7) and it never raises an unread count or a notification (the server and TOKI-053 decide that, D-100, D-165; this work only draws). The look is decided in concern 2, because the prototype draws no system line. "With the date" (D-100) is read as the day divider above the line, not as a date or time on the line (concern 1). Check: each of the six types renders its text for a fake people store in English, `message_pinned` through a cast item; an unknown type renders an empty element with no padding; the line has no `<time>`, no button and no avatar; `getComputedStyle` of the test row has the muted colour; the text column offset equals the user layout's in the browser test.
- R12. The words of a system line, and how people are named in them. `format.ts` builds the text, as one string made by `t` with `{name}` and `{people}` (never markup): the actor is `message.authorId`, the people are `system.userIds`, each is the display name from the store, and a person the store does not hold is `message.system.someone`. The line always names the person, including the signed-in one (no "You"; concern 1). For `members_added` the people are listed with `Intl.ListFormat` in the interface language (`type: "conjunction"`, `style: "long"`): up to 4 people are all named; more than 4 name the first 3 followed by `message.system.others` with the count of the rest ("5 others"; concern 1). A line of `members_added` with no known people reads with `message.system.someone`. The English texts: `member_joined` "{name} joined" (D-100), `channel_created` "{name} created this channel", `members_added` "{name} added {people}", `member_left` "{name} left the channel", `topic_changed` "{name} changed the topic", `message_pinned` "{name} pinned a message"; all but the first are not in the prototype and are decided in concern 1 (journeys F20 to F24 and F17 accepted what the line does, D-091). Check: a table over the six types with one, two and four people for `members_added`; five people read "Lan added A, B, C, and 2 others" (this is the output of `Intl.ListFormat("en", { type: "conjunction", style: "long" })`, which writes the serial comma, checked in Node; the test asserts that output built from the same parts, and the English text follows the API); an unknown person reads "Someone"; the Vietnamese catalog renders the same keys with the list joined by the Vietnamese conjunction of `Intl.ListFormat` (the test asserts the output of `Intl.ListFormat("vi")`, not a literal).
- R13. A deleted message that is drawn. A message with `deletedAt` set that the list did not hide (a message that an Admin deleted, or one the author deleted that has replies, TOKI-041 R5) draws, in place of the avatar, name, time and text, the component `extensions.DeletedLine` rendered as `<DeletedLine by={by} />`, where `by` is `deletedBy(message)`, and then the `footer`, so a deleted root keeps its thread link (TOKI-047 R20). `deletedBy` is a helper of `format.ts` that returns `"author"` or `"admin"`: it reads the key `deletedBy` that TOKI-047 R8 adds to `MessageEntry`, through a check that works when the type does not have the key yet, and returns `"author"` when the key is missing; TOKI-047 replaces the helper body by the typed read (Plan changes), so this ticket compiles and is tested alone on main, where `deletedBy` does not exist. The mapping to the line of TOKI-047 R20 is: `by` `"author"` is `DeletedMessageLine kind="deleted"` and `by` `"admin"` is `kind="deletedByAdmin"`; that mapping is inside TOKI-047's `DeletedLine` fill, not here. It draws no avatar, no name, no time, no labels, no editor, no reactions and no action bar. Until TOKI-047 fills the entry, `DeletedLine` is a component that returns `null` and the row draws nothing but the footer; no message can have `deletedAt` before TOKI-047 writes it (TOKI-037 R15), so nothing is lost. Check: with a test component the deleted layout draws it and the footer and none of the pieces above; with the default the row draws only the footer; an item with `by` `"author"`, `"admin"` and with the key missing passes the expected value to it.

The places for other work
- R14. One object, one file; the places are components. `apps/web/src/conversation/message/extensions.ts` exports `messageExtensions`, the single place where other work plugs in. Its type is fixed here, and every member has a default that draws nothing or the plain behaviour, so the component is complete without any of them. A place that needs a hook (a store, the engine, the active row) is a React component that `Message` renders as an element, never a function that `Message` calls: each component owns its hooks and its re-renders, a place that is not drawn is simply not rendered, and a row re-renders only when its own parts change (TOKI-041 R21). Only the members that are pure are plain functions.

  The rules: (a) a later ticket edits only this file and its own folder, one import and one entry, and says so in its pull request, as TOKI-041 R4 does for `tabs.ts`; (b) no ticket edits `Message.tsx` or `UserMessage.tsx` to add a piece, and one that needs a place that is not in the table changes this requirement; (c) a member is read at render, so a test replaces it with `vi.spyOn` or a reset helper `resetMessageExtensions()` that the file exports for tests; (d) a member is stable (the same function or component between renders; for `useOpenProfile`, the function it returns) or every row renders again and remounts; (e) a member never reads the item's neighbours; (f) a component of the table may use hooks, and a function of the table (`show`, `isMentioned`, a stage) may not; (g) `useRow` and then `useOpenProfile` are called at the top of `UserMessage`, in that order, unconditionally on every render; `UserMessage` is the one component of the user layout for a pending and for a confirmed item, so a pending item that confirms keeps its row and its hooks. ## Design
### How a row is made
```
MessageRow (TOKI-041, memo)  ->  Message
  item.kind pending ------------------> UserMessage (+ DeliveryLabel)
  message.kind system ----------------> SystemLine (format.ts)
  message.deletedAt ------------------> DeletedLine + footer
  otherwise --------------------------> UserMessage
UserMessage:  [avatar | gutter time] [ header: name, time, labels | Body( text pipeline ) | Files | Reactions | footer ]  [ Actions ]
```
- The component is a function of its props and of `deps.ts`. It never reads the list, the window or a neighbour: `grouped`, `target` and `footer` are given. That is what lets the thread panel draw it too.
- The outer wrapper `.message-outer` carries the test id, the `data-*` attributes and the prototype's top margin as padding; the inner box `.message` carries the padding, the radius, the background, the classes `mentioned` and `act`, and `position: relative` for the bar, so hover and tint do not cover the space between messages and the bar's offsets are those of the prototype.

### Why a typed object and not props
Each of the tickets that add to a message would otherwise add a prop to `Message` and to `MessageRow`, to the list and to the thread panel, which draw the same component. One object whose places are components, read inside the component, keeps the props of TOKI-041 R21 as they are and puts every later change in one file, with a type that a compiler checks and a default that draws nothing. The places are components, not functions, so the real fills (the editor, the reaction chips, the bar) can use hooks without breaking the rules of hooks. It follows the rule that TOKI-040 R21 and TOKI-041 R4 already use: an entry is one line in an existing file; the file itself and its type are made by this ticket, which the others need (Plan changes).

### What the prototype does not draw
The prototype has no system line, no "Not sent", no deactivated label, no sending state other than a waiting message (and no grouped waiting message: `grp` requires both neighbours to be confirmed), no "(edited)" or Pinned label on a grouped message, and a time that a grouped message shows on hover only. The prototype also shows no way to see an unknown author, and its `.msg` has a `transition: background .15s` that this work does not keep (concern 2). Each is built here as stated and marked: wording is concern 1, look is concern 2, the others are decisions of this spec (concerns 3 to 6).

### Known limits
- The time of a grouped message in the margin is not shown to a person on a hover device until they hover or focus the row (the prototype's behaviour).
- A message with a very large number of reactions or files is as tall as its parts; the list measures the row (TOKI-041 R20).
- A `Today` label on a day divider is the list's; this component never shows a date, only a time.
- A message that waits with files and no text draws the avatar, the name, the time and the label, and no card, because `Files` is rendered for a confirmed message only (R14). How such a message should look, and what happens when its files expire while it waits, is open and is not decided here (concern 12 of the composer attachments spec, TOKI-040 R7 and R12).
