# DM and group DM API design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/dm-api.md (Thanh Truong)
Ticket: TOKI-030

## Goal
A Member or an Admin needs to start a conversation with one other person, or with up to seven others, and to find the same conversation again whenever the same people ask for it. TOKI-028 gives the tables and the database rules (a key per set of people, member rows equal to the key, no delete). Nothing yet takes a list of people, applies the rules that need a person's role or status, and writes the rows. This ticket adds one request that does it, with stable error codes for the people picker of TOKI-034.
The rules that belong to this request and not to the tables are: only a Member or an Admin may open one (a guest may not, D-050), nobody opens one with themselves (F25), a group holds 8 people at most counting its creator (D-017, D-086), a new conversation is not opened with a deactivated person (concern 2), and two requests for the same set at the same moment give one conversation.

## Scope
- In:
  - One route, `POST /api/v1/direct-conversations`, that opens a direct message (one other person) or a group (two to seven others) and returns it, created or already existing.
  - The pure rule that turns the list of people into the kind and the key, and the order of the checks.
  - The write of the conversation and its member rows in one transaction, safe against the same set arriving twice at once.
  - The use of the read `getAccountsByIds` of the `members` module, which TOKI-029 builds (its R19) and this ticket imports unchanged; this route must not read the `users` table. This ticket builds no read of accounts.
  - The request and response schemas and the three new error codes, in `packages/shared`.
  - Tests of the route and the write.
- Out (not now):
  - The tables, their constraints and triggers, the key builder `buildDmKey` and the five reads: TOKI-028. This ticket adds no migration and changes no table.
  - Listing conversations: TOKI-031 and TOKI-033. The rule that a direct message appears in the other person's list only after the first message (F25) needs `messages` (TOKI-036) and belongs to TOKI-037 (concern 7).
  - The people picker, the chips, the text of the refusals and the screen that opens the conversation: TOKI-034 and TOKI-033. The server sends codes and English developer messages only.
  - Sending, reading and loading messages, and refusing a message into a read-only direct message: TOKI-037 (Design, "Hand-offs").
  - Notification level, mute and star of a conversation: not here. TOKI-029 builds the request that saves them, for a direct message and a group too (TOKI-028 concern 2, decided by Thanh Truong as product owner on 2026-11-18).
  - Add, remove, leave, archive and restore requests. A direct message or group has none, and the channel routes of TOKI-029 refuse a direct conversation (R14).
  - Guests as people: phase 5. This ticket refuses a role that the permission functions do not know, as the caller and as a person to message, with a server error (R4, R7); the phase 5 ticket gives a guest its own result and the database-level test of D-050.
  - A limit on how many direct messages or groups one person may open: the log sets none (effect on the other people: concern 8).
  - Pushing an event when a direct message is opened: the other person sees it only after the first message (F25), and the event log (TOKI-036, TOKI-038) does not exist yet.

## Requirements
- R1. `POST /api/v1/direct-conversations` is registered under the `/api/v1` prefix and needs a valid session: the session check of TOKI-022 (R24) answers 401 first, for no cookie or token, an ended session and a deactivated account. The route takes the actor's id and role from the account that the session check puts on the request, never from the body, and passes them to a handler function `handleOpenDirect(deps, account, body)` that holds all the rules (Design, "How the route gets its dependencies"). Check: a request without a session returns 401 with the code of TOKI-022 and writes no row; the account of a signed-in request reaches the handler (a positive route test); the route list of the app contains this one `POST` path and no other path for direct conversations.
- R2. The body is `{ "userIds": string[] }`: the people to message, not counting the caller, who is added by the server (decided in this spec, Design). `userIds` has 1 or more items, each a UUID in any letter case, and no id twice once lower-cased. The schema is a Zod schema in `packages/shared`, and the route validates with it. A body that does not pass returns 400 `validation_failed` with `details.issues` as in TOKI-004 (no submitted value in it) and writes nothing. A request with no body, or with a body that is not JSON, is answered before the schema by the guards of TOKI-022 (R45 refuses a body that is not `application/json` with 415, and applies to a request "with a body" only), so a request with no body and no content type reaches the schema and gets 400 `validation_failed`. Check: tests send a missing body with no content type (400 `validation_failed`), a form-encoded body (415 `unsupported_media_type` of TOKI-022), a request with a foreign `Origin` (403 `origin_not_allowed`, TOKI-022 R46), and the invalid bodies below: `{}`, `{ "userIds": [] }`, `{ "userIds": "x" }`, a list with a number, a list with a value that is not a UUID, a list with the same id twice, and the same id in upper and lower case; each invalid body returns 400 `validation_failed` and the tables are unchanged in every case. A list with 1 id and a list with 7 ids pass the schema.
- R3. Order of the checks, each stops the request: (1) session (R1); (2) permission (R4); (3) body schema (R2); (4) the caller's own id in the list (R5); (5) more than 7 ids (R5); (6) accounts, read and locked in the transaction that steps 7 to 9 use (R22, R6, R7); (7) existing conversation (R9); (8) deactivated people (R10); (9) create (R11). Steps 2 to 5 read nothing from the database. Check: a list of 8 ids that do not exist returns `group_too_large`, not `not_found`; a list that holds the caller's own id and an unknown id returns `direct_with_self`; a request for a set that already exists and holds a deactivated person returns 200 (R9) and not the 409 of R10.
- R4. Permission. The route calls `canCreateDirectConversation(actor)` of TOKI-027 (R8 there) twice with the same rule: first on the account of the request (step 2), then on the role read under the lock (R22), which is the one that decides. `role_not_allowed` returns 403 `forbidden`. `unknown_role` and `fact_missing` return 500 `internal_error` and are logged at error level, as TOKI-027 asks ("How the server uses them") and as TOKI-024 R1, TOKI-029 R2 do, so that a loader bug or a bad migration does not pass as a quiet refusal. The route and the handler compare no role to a string (TOKI-027 R16). In phase 1 `users.role` holds only `member` or `admin` (TOKI-019 R9) and both are allowed, so a real request never reaches a refusal of this step; the guest that D-050 and AC-059 refuse in phase 5 becomes a `Role` value that gets `role_not_allowed`, hence 403, from the function in the phase 5 ticket (concern 6). Check, through the handler seam of Design, "How the route gets its dependencies": `handleOpenDirect` called with an account of role `member` and one of role `admin` (both pass, 201) and with accounts of role `"guest"` and `"owner"` (both 500 `internal_error`, no row, an error-level log line); a test that replaces `canCreateDirectConversation` by a stub returning `role_not_allowed` gets 403 `forbidden` and no row, and a stub returning `fact_missing` gets 500. The 403 for a guest is therefore proved by that stub only, because phase 1 cannot store a guest. A search `grep -rnE "(role|Role)\b.*['"](admin|member|guest)['"]"` over the non-test files of this change finds no line.
- R5. People and size. The route builds the list `[actor.id, ...userIds]` and uses `buildDmKey` of TOKI-028 (R11 there) for the kind and the key. An id equal to the caller's own id, with other ids or alone, returns 400 `direct_with_self` (messaging yourself is not supported, F25). A list of 8 or more ids in `userIds` (9 or more people with the caller) returns 400 `group_too_large` with `details` `{ "max": 8, "maxOthers": 7 }`: `max` is the number of people counting the caller and `maxOthers` is the longest `userIds` (D-017, D-086, BR-36). The 8 comes from `GROUP_DM_MAX_PEOPLE` of TOKI-028 (R15) and the 7 from `DIRECT_CONVERSATION_MAX_OTHERS` (R17). One id gives kind `dm`, 2 to 7 ids give `group_dm`. Check: unit tests of the pure rule for 1, 2, 7 (accepted) and 8 and 200 (refused) ids, for the caller's id alone, first, last and in the middle of a list, and for the same ids in other orders (one key); the route test sends 8 ids and receives 400 `group_too_large` with `details` `{ max: 8, maxOthers: 7 }`, and sends the caller's own id and receives 400 `direct_with_self`; both leave the tables unchanged.
- R6. Accounts. The route reads the accounts of the caller and of every id in `userIds` with `getAccountsByIds(tx, ids, { lock: "share" })` (R15, R22), in one call inside the transaction, and takes the workspace of the new conversation from the caller's account. An id that has no account, or an account of another workspace, returns 404 `not_found`, the same answer for both, with no `details` (BR-09: the answer does not tell whether the person exists elsewhere). Check: a test sends an id that is a UUID nobody has, and an id of an account in a second workspace (a row inserted by the helper of TOKI-019), and gets the same status, code and body for both, and no row is written.
- R7. A person who is put in the conversation must be one who may take part in direct conversations. There is no function of TOKI-027 for a target, so the route asks `canCreateDirectConversation({ id, role })` of TOKI-027 for each other person with the role read under the lock, which says the same thing: every Member and Admin, no guest (BR-37, D-050); no role is compared in this ticket (R4; request to TOKI-027 in concern 9). `role_not_allowed` answers as for an unknown id (R6: 404 `not_found`, so the existence of a guest is not shown, D-050); `unknown_role` and `fact_missing` answer 500 as in R4. In phase 1 neither is reachable by a real request (R4), so the rule is proved with an account read that the test injects through the handler seam and with the stub of R4. Check: a handler test with a read that returns the role `"guest"` for one id gets 500 `internal_error` and no row; with a stub that makes the function return `role_not_allowed` for that id it gets 404 `not_found` and no row; with the role `"member"` for the same id it gets 201.
- R8. A group is made only of accounts that exist and belong to the caller's workspace. Check: the same tests as R6 for a group (2 to 7 ids where one id is unknown or in another workspace); no row is written, not even for the valid ids.
- R9. Existing conversation. When a conversation of the caller's workspace has the key of R5, the route returns status 200 and that conversation, writes nothing, and does not look at the status of the other people in it (the caller's own status is checked, R22). The entry holds the caller's own stored level, mute and star, read from the caller's member row (R18). Check: open `[b]` as `a` (201); open `[a]` as `b` returns 200 with the same `id`, and `created_at` and the member rows are the ones of the first request; after `b` is deactivated (a row update by SQL), `a` opens `[b]` again and gets 200 with the same `id`; the count of rows of both tables is the same after each call.
- R10. A new conversation with a deactivated person is refused: when no conversation has the key and one or more of the other people have status `deactivated`, the route returns 409 `person_deactivated` with `details` `{ "userIds": [...] }` holding those ids, lower case, sorted, and writes nothing (F25, F41, D-091; the rule itself is concern 2, the status is concern 6). Check: a route test with one deactivated person in a DM and one among three in a group; each returns 409 with the right ids, and the tables are unchanged. A person who is Active again (a row update) can be opened in the same test.
- R11. Create. When no conversation has the key and the checks of R3 passed, the route inserts in one transaction the `conversations` row and one `conversation_members` row for each person in the key, and returns status 201 and the new conversation. The `conversations` row has: `kind` `dm` or `group_dm`; `name`, `topic`, `description` and `archived_at` null; `is_private` true; `is_general` false; `dm_key` the key of R5; `created_by` the caller; `workspace_id` of the caller's account; `created_at` from the injected clock (TOKI-008 R19), not from the database. The transaction is `READ COMMITTED` (R22). Each member row has the same `workspace_id`, `created_at` from the clock, `notification_level` null, `is_muted` and `is_starred` false (D-046; the level that applies is `effectiveNotificationLevel` of TOKI-028). The member rows are written in the same transaction as the conversation, as TOKI-028 R21 requires. Check: a database test reads both tables after a DM and after a group of 8 and compares every column; a test passes an account read that reports an id for which `users` has no row (a stub, since the real read would not), so the foreign key of `conversation_members.user_id` fails on the member insert; the request returns 500 `internal_error` and the `conversations` row is not there.
- R12. Same people, same conversation. For any set of people, every request that names the others of that set, from any member of it, in any order and in any letter case, returns the conversation with the same `id`. Check: a group of `a`, `b`, `c`: `a` opens `[b, c]`, `b` opens `[c, a]`, `c` opens `[A-in-upper-case, b]`; the first returns 201 and the other two 200 with one `id`; a fourth person `d` opening `[a, b, c]` gets a different conversation; `a` opening `[b]` gets a different one again.
- R13. Two requests at the same moment. When several requests for one set arrive together, one creates the conversation and the others return it: exactly one answers 201, the others 200 with the same `id`, the tables hold one `conversations` row and one member row for each person, and no request fails with a unique violation or an internal error. The insert uses `INSERT ... ON CONFLICT (workspace_id, dm_key) DO NOTHING` and then reads the row by the key (TOKI-028, Hand-offs); this relies on `READ COMMITTED` (R22). Check: a test sends the same DM from `a` and from `b` together, and a group of 4 from its four members together, and 10 requests of one person for one DM together, each on separate database connections and each through `handleOpenDirect`, the code the route runs; the counts above hold in every run, and the test repeats each case 20 times.
- R14. A group never gains or loses people. The only code in this ticket that writes `conversation_members` for a `dm` or `group_dm` is the insert of R11, and no route of this ticket adds, removes or changes a person. A request for a set that differs by one person gives another conversation and leaves the first unchanged. Check: open a group of `a`, `b`, `c`; then open `[b, c, d]` as `a` and `[b]` as `a`; the three conversations have three `id`s and the first still has exactly the member rows `a`, `b`, `c`; a search of the files of this change finds no `UPDATE` or `DELETE` on `conversation_members`. The refusal of "add people" and "remove people" for a direct conversation is in the channel routes (TOKI-029, Design, "Hand-offs"), which use the `not_a_channel` answer of TOKI-027 (R9).
- R15. Account read. This ticket uses `getAccountsByIds(client, ids, options?)` that TOKI-029 builds in the `members` module (its R19) and does not build or change it: `{ lock?: "share" }` makes the read `FOR SHARE` in id order, and for each id that has a row in `users` it returns `{ id, workspaceId, role: string, status }` with `status` `active` or `deactivated` and `role` the stored text, so a value other than `member` or `admin` reaches the permission functions as `unknown_role`; nothing for an id with no row; it filters nothing by workspace, so the route compares `workspaceId` with the caller's (R6); it returns no email address or display name. Decided in this spec: TOKI-030 needs TOKI-029 for it (concern 5, the plan change), and a field that is missing is a change to TOKI-029's function, made by whoever needs it first, not a second function. Check: the route and handler tests run on the real read (an active Admin, a deactivated Member, an unknown id, an account of a second workspace); this ticket adds no test of the read itself, which TOKI-029 owns.
- R16. Module boundaries, the same as TOKI-029 R18 so that the two route plugins of the module reach `members` one way. The `conversations` module does not import the `members` module, because `members` already imports `conversations` (`acceptInvitation` calls `addMemberToGeneral`, TOKI-024 R20 step 8) and a cycle would stop the server at start. The plugin is a function `directRoutes({ db, clock, getAccountsByIds })`: it receives the database client, the clock of TOKI-008 and the account read from outside, imports nothing of `members`, is exported from `modules/conversations/index.ts` and is registered in `apps/server/src/api/index.ts`, which imports the `index.ts` of both modules and passes the read in (TOKI-002 R17 allows this). No file of this change imports a table definition of another module. The export-list test of TOKI-028 R18 is changed in this ticket's own change into one constant of names that every ticket extends: this ticket adds `directRoutes` and its types to it, and the test checks that every name of the constant is exported, not that nothing else is (concern 3). Check: `pnpm lint` exits 0; the export-list test finds the five names of TOKI-028 R18, `directRoutes` and the types of this ticket, and still passes when another ticket adds its name to the constant; a test starts the app through `buildApp` with the real `api/index.ts` and finds the route registered.
- R17. The shared schemas are in `packages/shared/src/direct-conversations.ts`, exported from the package index of `@toki/shared`: the body of R2, the entry schema `DirectConversationEntry` and its inferred type, the response of R18, and the constant `DIRECT_CONVERSATION_MAX_OTHERS` (7, written as `GROUP_DM_MAX_PEOPLE - 1`, the constant of `packages/shared/src/conversations.ts`, TOKI-028 R15). `DirectConversationEntry` is one strict Zod object (`.strict()`) with exactly the ten keys of R18, `kind` being `dm` or `group_dm`, `name` and `topic` null, `isPrivate` true and `isGeneral` false; it is not a union. TOKI-031 imports it for the `dm` and `group_dm` entries of `BootstrapConversation` (its R7 and R17) and TOKI-032 uses it for the answer of `directConversations.open` (its R2), so no other spec writes these keys again. The server and its tests use the strict schemas. The web client of TOKI-032 derives from them a form that drops unknown keys, in `packages/client-core/src/api/parse.ts` (TOKI-032 R3), so that a field added to the API later does not break an old client; the schemas exported here are not changed and not re-exported in a non-strict form. Check: a type test imports each name from `@toki/shared`; the route test parses every 200 and 201 body with the response schema; the schema test of the entry rejects an added key, a missing key, a `kind` of `channel`, a non-null `name`, an `isPrivate` of false and a `notificationLevel` of `loud`.
- R18. Response. Status 200 or 201 with `{ "conversation": DirectConversationEntry }`. The entry is the entry of the bootstrap call of TOKI-031 (its R7) for a direct message or group, so the picker adds it to the client's store with no mapping and the same shape is written once: exactly `{ "id": string, "kind": "dm" | "group_dm", "name": null, "topic": null, "isPrivate": true, "isGeneral": false, "notificationLevel": "all" | "mentions" | "none", "isMuted": boolean, "isStarred": boolean, "memberIds": string[] }`. `notificationLevel`, `isMuted` and `isStarred` are the caller's own: the stored values of the caller's member row, the level turned into the one that applies by `effectiveNotificationLevel(kind, level)` of TOKI-028 R15 (`all` for a new direct message or group, D-046); another person's values never appear. `memberIds` are the ids of the people in the key, lower case, in ascending byte order (collation "C", the order of the key, TOKI-028 R10, and of TOKI-031 R7), the caller included. The entry has no `createdBy`, `createdAt`, description, last message or unread count; 201 against 200 says whether it was created. The schema `DirectConversationEntry` is defined here, in `packages/shared`, because this ticket is built before TOKI-031: TOKI-031 adopts it for the `dm` and `group_dm` entries of `BootstrapConversation` (its R7 and R17, which now name this schema and this file), so the two key sets are one; this spec edits no other spec (concern 5). Check: the schema test of R17; for a DM and a group the `memberIds` equal the member rows read from the table, sorted; the keys of the entry equal the key list of TOKI-031 R7 written out in the test; a caller with a stored level `none`, muted and starred gets `none`, true, true on the 200 and a new conversation gets `all`, false, false on the 201; a field not in the schema is absent.
- R19. Error codes. This ticket adds to the registry of error codes in `packages/shared` (TOKI-004): `direct_with_self` (400), `group_too_large` (400) and `person_deactivated` (409), and uses `validation_failed`, `not_found`, `internal_error`, `unsupported_media_type` and `origin_not_allowed` of TOKI-004 and TOKI-022 `forbidden` (403) of TOKI-024 R2, and `account_deactivated` (401) of TOKI-022; whichever of the tickets is built first adds `forbidden`. Every error body passes the error schema of TOKI-004. Check: a test finds the three new codes in the registry; every refusal test above also parses its body with the error schema.
- R20. No other effect. A request writes no message, no event, no notification and no row outside `conversations` and `conversation_members`; it logs the usual request line and no list of people. Check: after each outcome the row counts of every other table are unchanged; the test log holds no id from `userIds`.
- R21. A refusal never changes data. For every status other than 200 and 201, both tables hold exactly what they held before the request. Check: every route test of a refusal compares the full contents of both tables before and after.
- R22. The transaction, its locks and its isolation. Decided in this spec; it follows TOKI-024 R39 and TOKI-029 R15. Everything from the account read to the commit runs in one transaction at `READ COMMITTED`, set in the code and not left to a shared helper's default: the insert of R13 waits for a concurrent insert of the same key and the read that follows must see its row, which a `REPEATABLE READ` snapshot would not (it would fail with a serialization error, so the loser would answer 500). The first statement is `getAccountsByIds(tx, [actor.id, ...userIds], { lock: "share" })`, which is `SELECT ... FROM users WHERE id = ANY($1) ORDER BY id FOR SHARE`: the caller and the other people are locked in id order, the order of TOKI-024 R39 (`users` rows first, by id, and no conversation row is locked by this route), in the mode that waits for a role change or a deactivation that holds a row and then reads its result. `FOR SHARE` does not conflict with the `FOR KEY SHARE` that the foreign keys of the new rows take on the same `users` rows, and two requests of this kind never exclude each other. The caller's role and status come from the locked row and not from the account that the session check read before the transaction: a deactivated caller gets 401 `account_deactivated`, and `canCreateDirectConversation` is called again with the locked role (R4). The status of the other people is read from the same locked rows, so a person who is deactivated while this request waits is refused with 409 (R10) and no new conversation is made with a person who was deactivated before the commit. Check, with two real connections: a deactivation that holds the person's row while a create waits gives 409 `person_deactivated` after it commits; a caller who is deactivated while their own request waits gets 401; a create and a person route of TOKI-024 that locks every `users` row in id order, started at the same moment, finish without a deadlock; the concurrent cases of R13 pass with the isolation level read back from the transaction (`SHOW transaction_isolation` is `read committed`).

## Design
### API
| Method | Path | Session | Purpose |
|---|---|---|---|
| POST | `/api/v1/direct-conversations` | required | Open the direct message or group made of the caller and `userIds`; create it if it does not exist |

The path names the thing that is opened and is separate from the channel routes of TOKI-029. A `POST` that finds the existing conversation answers 200 and one that creates answers 201, so a client can tell them apart without a field; both bodies have the same shape (R18).

Body and response shapes are in R2 and R18.

### Outcomes
| Status | `error.code` | `details` | Meaning | The client is expected to |
|---|---|---|---|---|
| 201 | none | none | Created; body `conversation` | Open it; it is empty |
| 200 | none | none | The same people already had it; body `conversation` | Open it with its history |
| 400 | `validation_failed` | `issues` (TOKI-004) | Body not valid (R2) | Not reachable from a correct screen |
| 400 | `direct_with_self` | none | The caller's own id is in the list (R5) | Not reachable from a correct screen; the caller is never offered |
| 400 | `group_too_large` | `max` (8, people counting the caller), `maxOthers` (7) | 8 or more others (R5) | Show the limit message of F25 |
| 401 | `unauthenticated`, `session_ended`, `account_deactivated` | none | TOKI-022; `account_deactivated` also when the caller is deactivated while the request waits (R22) | As TOKI-023 and TOKI-099 |
| 403 | `forbidden` | none | Role not allowed (R4); not reachable in phase 1 | Show the shared no-access page (D-131) |
| 403 | `origin_not_allowed` | none | A foreign `Origin` header (TOKI-022 R46) | Not reachable from the app |
| 404 | `not_found` | none | An id is unknown, in another workspace or a person who may not take part (R6, R7) | The shared page of D-131 (403 and 404). TOKI-034 (its concern 6) keeps D-131: the 404 of a correct screen is not reachable, so the picker does not refresh its list on it, and until the shared page of TOKI-082 exists it shows its own plain line |
| 415 | `unsupported_media_type` | none | A body that is not `application/json` (TOKI-022 R45) | Not reachable from the app |
| 409 | `person_deactivated` | `userIds` | A person in a new conversation is deactivated (R10) | Refresh the people list and let the person choose again (D-131: 409 means a fresh copy) |
| 500 | `internal_error` | `requestId` | Server failure, or a permission function answered `fact_missing` or `unknown_role` (R4, R7) | Retry with the error ID (D-131) |

The texts a person reads, for example "Up to 8 people, counting you" in flow F25, are written by the screen ticket (TOKI-034, its text table, where they are proposals under D-139 because the prototype does not contain them), and no text is sent by this ticket.

### How a request runs
1. The session check (TOKI-022) puts the account on the request. The route takes `id` and `role` from it.
2. `canCreateDirectConversation(actor)` on the account of the request (R4), then the body schema (R2).
3. The pure rule `planDirectConversation(actorId, userIds)` in `direct.ts` lower-cases the ids, refuses the caller's id (`direct_with_self`) and a list that makes more than 8 people (`group_too_large`), and calls `buildDmKey`. It reads nothing. Its result is `{ kind, key, memberIds }` or the name of the refusal (R5).
4. One transaction at `READ COMMITTED` (R22), with the clock read once at its start. Its first statement is the one call to `getAccountsByIds` with the lock for the caller and the others. The caller's row is re-checked (R22). The pure rule `checkPeople(callerRow, rows, ids, canTakePart)` in `direct.ts` returns `not_found` for a missing id, another workspace, or a person that the permission function refuses (R6, R7), and otherwise the ids of the deactivated people; the permission function is passed in as `canTakePart`, so `direct.ts` is pure and compares no role.
5. In the same transaction:
   1. Look for the conversation: `SELECT ... WHERE workspace_id = $1 AND dm_key = $2`, with the caller's member row. Found: answer 200 (R9), whatever the status of the other people in it.
   2. Not found and one or more people are deactivated: answer 409 (R10), roll back and write nothing.
   3. Not found and nobody is deactivated: `INSERT INTO conversations (...) ON CONFLICT (workspace_id, dm_key) DO NOTHING RETURNING id`. A row came back: this request made it, so insert one member row for each person of the key and commit; the deferred trigger of TOKI-028 (R21 there) checks at commit that the member rows match the key; answer 201. No row came back: another request made the same conversation between 5.1 and 5.3 (the insert waited for it to commit), so read it by the key, with the caller's member row, and answer 200 (R13).

Why the existing conversation wins over a deactivated person: F25 says an existing direct message with a deactivated person keeps its history, and F41 says it becomes read-only, so the caller must still be able to open it.

### Decided in this spec
These are technical choices the Blueprint leaves to the builder.
- The path is `POST /api/v1/direct-conversations`. Reason: a direct message and a group are not channels, and TOKI-029 owns the channel routes.
- `userIds` are the other people, and the server adds the caller. Reason: the caller's id is already known from the session, so a client cannot name a different caller, and "up to 8 counting you" becomes 7 others (R5).
- 201 for created and 200 for existing, same shape. Reason: D-111 is about creating a channel, sending invitations and setting a reminder and names no direct message; its reason (a repeat of the same request is ignored) is applied here by analogy. The natural key (the set of people) does that, so no `Idempotency-Key` header is needed; a repeat returns the same conversation.
- The caller's id inside `userIds` is refused (`direct_with_self`), not ignored. Reason: F25 says messaging yourself is not supported; a request that names oneself is a mistake of the client, and ignoring it would turn a request for `[self]` into an empty list.
- A person that the permission function refuses as a target gives 404 `not_found` as an unknown id does. Reason: D-050 keeps a guest inside one channel, so the existence of a guest is not shown outside it.
- `role_not_allowed` of the caller gives 403 and `unknown_role` and `fact_missing` give 500, as TOKI-027, TOKI-024 R1 and TOKI-029 R2 do. Reason: D-050 says the server refuses a guest's start-DM request (AC-059, TS-092) and a refusal is 403 (D-131); a role the server does not know is a loader bug and must not pass as a quiet refusal. In phase 1 no guest can be stored, so the 403 for a guest comes with phase 5 (R4, concern 6).
- The status of a refusal of a new conversation with a deactivated person is 409. Reason: D-131 maps 409 to "fresh copy". That the request is refused is decided (concern 2); the status is a builder's choice.
- The plugin takes the account read as a parameter (R16). Reason: the dependency `members` to `conversations` already exists, and the other direction would be a cycle; TOKI-029 does the same.
- The `users` rows of the caller and of the other people are locked `FOR SHARE`, in id order, in the first statement of the transaction, and the transaction is `READ COMMITTED` (R22). Reason: the mode and order of TOKI-024 R39 and TOKI-029 R15; it removes the race in which a person deactivated at the moment of the request ends up in a new conversation, at the price of one row lock per person that does not block any other request of this kind.
- The route reads accounts through `getAccountsByIds` and not through the session's account, because it needs the status, role and workspace of other people and the locked state of the caller. The caller is read in the same call so that its workspace is the one the other accounts are compared with.
- The response is the bootstrap entry of TOKI-031 (R18), not a smaller or larger shape, so that one shape exists for the client.
- The key, kind and member rule come from TOKI-028 (`buildDmKey`, constraints and triggers); this ticket repeats none of them in SQL or in a second sorting function.

### How the route gets its dependencies
`api/index.ts` is a file outside `modules/`, so it may import the `index.ts` of both `conversations` and `members` and join them: `directRoutes({ db, clock, getAccountsByIds })`. The plugin does nothing but take `request.account` (put there by the session check), call `handleOpenDirect(deps, account, body)` and turn its result into a status and a body. `handleOpenDirect` is exported from `direct-routes.ts` and not from the module's `index.ts`. This is the seam of the tests: the account is an argument, so a test passes an account of role `"guest"` or `"owner"`, which `users.role` cannot hold and a session cannot produce, and the account read and `canCreateDirectConversation` can be replaced by stubs (R4, R7). The route test registers the plugin through `buildApp({ config, registerRoutes })` (TOKI-004 R16) with the real read and covers what a real request can reach; a test signs in a person with the session function of TOKI-022 (R29, token transport) on rows from the helper of TOKI-019 and sends the `Authorization` header.

### Hand-offs
- TOKI-029 (channel API): builds `getAccountsByIds` (its R19) and this ticket imports it (R15, concern 5). Its add, remove, join, leave, archive and restore routes answer the id of a direct message or group as "not a channel" through the permission functions of TOKI-027 (R9 there), so the request of AC-058 and TS-091 ("send an add-member request for the group") is refused there; the status and code are TOKI-029's. Request to TOKI-029: its Hand-offs say that TOKI-030 owns every route that creates or reads a direct message or group; this ticket has one `POST` and no read route, so the sentence should say that no route reads a direct conversation and that reading goes through the bootstrap call.
- TOKI-031 (bootstrap): builds its own read of conversations and members (`listConversationSummaries`, its R15), so this ticket exports no read of direct conversations. It adopts `DirectConversationEntry` of this ticket, imported from `packages/shared/src/direct-conversations.ts` (R17, R18), for its `dm` and `group_dm` entries (its R7 and R17), so that the two shapes are one; its text now says so. Both member rows exist from the moment of opening (TOKI-028 concern 6); TOKI-037 hides a new direct message from the other person until its first message (F25): concern 7 here and concern 1 of TOKI-031. The people picker takes its candidates from the people of the bootstrap call (no route of this ticket lists people, and `GET /members` of TOKI-024 is for Admins).
- TOKI-034 (picker): sends `userIds` in the order pressed, with no caller id, opens the returned conversation on 200 and on 201 alike (D-076), and turns `person_deactivated` and `group_too_large` into its messages (its R20 and R23); a `not_found`, `forbidden`, `direct_with_self` or `validation_failed` shows its generic line, since none is reachable from a correct screen. It enforces the limit on the chips with `DIRECT_CONVERSATION_MAX_OTHERS` (7) and shows `GROUP_DM_MAX_PEOPLE` (8) in its text, and does not read `max` from `details` as the length of `userIds` (R5). The texts are its proposals (D-139).
- TOKI-032 (client core): `directConversations.open(userIds)` returns the entry of R18 and `created` from the status (its R2), and the store keeps the entry as it is, with its own level, mute and star (its R13). Its client drops unknown keys while the schemas here stay strict (R17).
- TOKI-037 (messages): owner of the hiding rule and of its event (concern 7). It refuses a message into a direct message whose other person is deactivated (F41, D-091: "DMs with them become read-only"), reading the members with `listMemberIds` (TOKI-028) and the status with `getAccountsByIds` (TOKI-029). A group with a deactivated member stays writable for its other members (concern 1), so TOKI-037 refuses nothing there.
- TOKI-028: its export test lists the exports exactly. This ticket turns it into one constant that each ticket extends and adds `directRoutes` and its types (R16, concern 3).

## Data safety
- Membership is the access rule (TOKI-028): a direct message is visible only to the people in its key, and the route returns a conversation only to someone who is in its key, because the caller is always in the list it builds (R5). The route never returns a conversation the caller is not in.
- The answer for an unknown id, an id of another workspace and a person who may not take part is one answer (R6, R7), so the route cannot be used to find out who exists or who is a guest.
- The route reads no email address or display name (R15) and logs no ids of people (R20). A new group is made with no consent of the people in it and with no way out (D-045); see concern 8.
- Tests use fake data and never touch the development database (TOKI-008).

## Open questions from the intent
- Can a new direct message or group be opened with a person who is deactivated? Answered: no, the request is refused with 409 `person_deactivated` (R10, concern 2). The log gives the flows that such a person is not listed (F25) and that direct messages with them become read-only (F41), accepted as the baseline in D-091; the rule for a request that names one is the product owner's decision of 2026-11-19, and its status is a builder's choice (concern 6).
- When one member of a group is deactivated, does the whole group become read-only? Answered: no, only a direct message of two people does (concern 1).
- Which ticket stops a message being sent into a direct message with a deactivated person? Answered: TOKI-037, which writes the message and reads the status (Hand-offs). This is for a direct message of two people; a group stays writable (concern 1). Evidence: F41; TOKI-028, Hand-offs.

## Areas of concern
1. Whether a group direct message becomes read-only when one of its members is deactivated. Decided: no. Only a direct message of two people is read-only; a group stays writable for its other members, and the deactivated member keeps the label "Deactivated" (F41). Flow F41 says "DMs with them become read-only" and F25 says an existing direct message with a deactivated person keeps its history with the composer replaced; neither names groups, and D-094 is about invitations. The tables and this ticket are the same either way; TOKI-037 builds the refusal for the direct message of two people only. Decided by Thanh Truong (product owner) on 2026-11-19. Owner: Thanh Truong (product owner).
2. Whether a new direct message or group may be refused when it names a deactivated person. Decided: it is refused (R10, 409 `person_deactivated`), so no new conversation is born read-only; an existing conversation with that person still opens (R9). F25 says a deactivated person is not listed and F41 that existing direct messages with them become read-only; the log gives no rule for a request that names one (a hand-made request or a stale list), so this is the product owner's rule. Decided by Thanh Truong (product owner) on 2026-11-19. Owner: Thanh Truong (product owner).
