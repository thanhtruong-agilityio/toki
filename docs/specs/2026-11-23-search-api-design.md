# Search API design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/search-api.md (Thanh Truong)
Ticket: TOKI-070

## Goal
Ctrl+K needs one request that answers "what matches these words" for a signed-in person: their conversations, the public channels they could join, the people of the workspace and their messages. This ticket builds that request and the rule behind it: who may be found, how many are returned, and how a person asks for more.
The rule that cannot be wrong is the permission rule. Messages are searched only in conversations the person is a member of; a private channel or a direct message of other people is never returned, whatever the word and whatever the role; a channel that was not joined is returned as a name and a topic and never as a message; a deactivated person is not listed. The route does not decide this by filtering a wide result: each kind is built from a set that already holds only what the person may see (R4, R5, R7).
Names (conversations, channels, people) are matched here with the shared `foldText`, so the palette, the conversation list and the people picker apply one rule. Messages use the index, `buildSearchTsQuery` and `searchMessageIds` of TOKI-069. No table, column or migration is added.

## Scope
- In:
  - `GET /api/v1/search` with its request and response shapes, the 20 results per kind and the cursor that asks for more (R1 to R3, R8).
  - The sets each kind is read from, which are the permission rule (R4, R5, R7), and the rule that matches and orders names (R6).
  - The message part: the call of `searchMessageIds`, the entry that gives the text of a result, and the text cut (R7).
  - One read added to the `conversations` module and one to the `messages` module (R9), the module `search` (R13), the shared schemas and constants (R12).
  - The tests of who is found and who is not (R14).
- Out (not now):
  - The index, the fold of the stored text, `searchWords`, `buildSearchTsQuery` and `searchMessageIds`: TOKI-069. This ticket calls them and does not decide the word rule or the order of messages (concerns 4 and 5).
  - The palette, the actions group, the "recent" list before typing, the highlight, the debounce, the call from the web app and every text on screen ("No results for ..."): TOKI-071. The search inside one conversation, which also matches the sender: TOKI-072.
  - Opening a message from a result and the flash: TOKI-068. The Files search: TOKI-063. The search field of the conversation list, of Browse channels and of the people picker, which filter data the client holds: TOKI-033, TOKI-034.
  - The measurement with a million messages and 200 people online: TOKI-089 (R10).
  - The access-control suite across all routes: TOKI-088. This ticket writes the cases for its own route (R14) and the suite reuses them.

## Requirements
- R1. One route, `GET /api/v1/search`, in the module `search` (R13), registered in the `/api/v1` scope, so every request needs a valid session (TOKI-022 R24: 401 without one, 401 `account_deactivated` for a deactivated account). After the session, in this order: (1) `canUseWorkspaceViews(actor)` of TOKI-027 R10 (a Member and an Admin are allowed; a result other than allowed is answered 403 `forbidden`, the code that member management R1 gives to `canOpenAdminPage`, which no role reaches today); (2) the schema of the query (R2, 400 `validation_failed`); (3) the reads of R4 to R7. The route takes no body and no other parameter, and its answer has the header `cache-control: no-store` (the answer is personal). An Admin has no extra right: the sets of R4, R5 and R7 are built from the actor's own membership and role-free facts, and no code of the route reads the role (TOKI-027 R16). Check: a test of the route without a session (401, and no read of `conversations`, `users` or `messages`: the statement count is 0), with a Member and with an Admin (both 200, same shape), with a deactivated account (401 `account_deactivated`), and with a fake `canUseWorkspaceViews` that refuses (403 `forbidden`, statement count 0); a source search finds no comparison with `"admin"` or `"member"` in `modules/search/`.
- R2. The query. `q` is required, one string, and is trimmed of white space at both ends (`String.prototype.trim`); the trimmed text has 1 to `SEARCH_QUERY_MAX` (200) code points. `kind` is optional and one of `conversations`, `channels`, `people`, `messages`. `cursor` is optional, a non-empty string of at most `SEARCH_CURSOR_MAX` (512) characters (a name is at most 80 characters, so its cursor is shorter), and is accepted only with `kind` (R8). A repeated key (`q=a&q=b`), any other key, an empty or white-space-only `q`, a `q` over the limit, a `kind` outside the list, a `cursor` over the limit and a `cursor` with no `kind` are 400 `validation_failed` with the path of the key in `details.issues`, and no read is made. The values of `SEARCH_QUERY_MAX`, `SEARCH_CURSOR_MAX` and of the other limits are builder choices (concern 14): a name is at most 80 characters, and a longer query adds nothing, because the message query keeps its first 8 words (TOKI-069 R6). Check: a table test sends each refused case and `cursor` of 512 and of 513 characters (513 refused before any decoding), and `q` of 1 and of 200 code points (200 accepted, 201 refused, with 200 emoji so that code points and UTF-16 units differ) and compares status, code and `details.issues[0].path`; the statement count of every refused case is 0 after the session.
- R3. The answer is 200 with `{ conversations?, channels?, people?, messages? }`: without `kind` all four keys, with `kind` only that key. Each key is a page `{ items: T[], nextCursor: string | null }` with at most `SEARCH_PAGE_SIZE` (20, D-112) items, in the order of R6 (names) or R7 (messages), and `nextCursor` is not null exactly when more items exist after the position of the page (the server reads one more than it returns; for messages the position is the last id that `searchMessageIds` returned among the first 20, R7, R8). A kind with nothing to return is `{ items: [], nextCursor: null }`, never an error and never absent when it was asked for, so a refused case and a case with no match look the same. The items are strict objects: `SearchConversation` `{ id, kind ("channel" | "dm" | "group_dm"), name (the name of a channel, null for a direct message or a group), topic (string or null), isPrivate, isGeneral, archived, memberIds (string[] for a direct message or a group, null for a channel) }`; `SearchChannel` `{ id, name, topic }`; `SearchPerson` `{ id, displayName }`; `SearchMessage` (R7). A direct message or a group has no name: the client makes it from `memberIds` and the people it holds (`getConversationName`, TOKI-032 R17), as for the list. The key a later ticket adds to a person (the job title, with TOKI-057 or TOKI-078) is added to `SearchPerson` in that ticket's change. Check: a schema test accepts each item and refuses an added key, a missing key and a `kind` of `other`; the body of every 200 of the route tests is parsed with the response schema; with `kind=people` the answer has the key `people` only; a query with no match has four pages that are empty and have `nextCursor` null.
- R4. Which conversations and channels are read. The set is built by `listSearchableConversations` (R9) from the actor's own member rows, in one statement. (a) `conversations`: every conversation the actor is a member of, of any kind: a public channel, a private channel, a direct message, a group (D-116, F29), `#general` included, archived channels included (concern 3 is the proposal for them). Never a conversation without the actor's member row, so a private channel, a direct message or a group of other people cannot be in the set whatever its name; an Admin who is not a member has no row (D-047). A direct message that has no message and was not created by the actor is not in the set, by the same rule and the same function as the list (TOKI-037 R19; decided for a direct message by TOKI-031 concern 1; a group is not hidden, which is a proposal, concern 10). (b) `channels`: the public channels that are not archived and of which the actor is not a member, with their `name` and `topic` only (D-051: private channels never appear in Ctrl+K for outsiders; D-116: a person cannot read the content of a channel they have not joined, so no message; F29 "Channels you can join" and Browse channels, TOKI-029 R6, show its name and topic; `canJoinChannel` refuses an archived channel). The row of a channel that is not joined carries no description, creator, member count or id of a person, inside the module either (R9 a). Check, on one fixture of a workspace with: `#general`, a public channel joined, an archived public channel joined, a public channel not joined, an archived public channel not joined, a private channel joined, a private channel of which the actor is not a member (the actor is an Admin in one run and a Member in the other), a direct message of the actor, a direct message of two other people, a group of the actor, a group of other people: the `conversations` items are the six that the actor belongs to (`#general`, the public channel joined, the archived channel joined with `archived: true`, the private channel, the direct message and the group) and no other; the `channels` items are the public channel not joined and nothing else; the private channel of others, the direct message of others and the group of others are never in any answer, for either role, whatever the query (the names are chosen so that the query matches all of them); the id of a channel that was joined and then left moves from `conversations` to `channels`.
- R5. Which people. `listPeople(client, workspaceId)` of the `members` module (code on main: every account of the workspace with `id`, `displayName`, `role`, `status`; no address) gives the accounts, and the route keeps the accounts whose `status` is `active` and whose `id` is not the actor's. A deactivated person is not listed (F41, D-091); the signed-in person is not listed because the prototype's palette leaves them out (`p.id !== ME`, line 2177 of `index.html`; concern 13). Role is not used and not returned. Every other active person is listed whatever the conversations they share: the directory is the workspace's (People, F29 "People"). Check: a workspace with an active Admin, an active Member, the actor and a deactivated person: `people` holds the first two for the query `a` (names chosen to match), neither the actor nor the deactivated one; deactivating a person between two requests removes them from the second answer; the answer holds no `role`, `status` or address (the strict schema of R3).
- R6. Matching and ordering names (conversations, channels, people). The text compared is `foldText` of `@toki/shared` (TOKI-050 R2, the same fold as the list, TOKI-032 R19: NFD, marks removed, `đ` to `d`, lower case), applied to the name and to the trimmed query, so `nguyen` finds `Nguyễn`, `duong` finds `Đường`, `Ha Noi` finds `hà nội`, and a name stored in the decomposed form matches. A name matches when its folded text contains the folded query as one string (the rule of the lists, TOKI-032 R19, and of the prototype's `includes`). If the folded query is empty (a lone combining mark) nothing matches. What is compared: the `name` of a channel (a channel name holds only lower-case letters, digits and hyphens, so `Hà` finds `ha-noi`; the name is compared as stored and with its hyphens read as spaces, and the better rank counts, so `duong dan` finds `duong-dan` as it finds the words in a message; concern 1); the `displayName` of every other member of a direct message or a group, read from the unfiltered list of S3, so a direct message with a deactivated person is found by that person's name (the actor's own name is not compared, as the list does not name a direct message by it); the `displayName` of a person. The topic of a channel and the job title of a person are not compared (concern 1). The order is the proposal of concern 2, and the next sentence is its rule: by rank, `0` when the folded text equals the folded query, `1` when it starts with it, `2` when it contains it (a group takes the best rank of its members' names); then by the sort key, the folded name (for a group the folded names of the others in ascending order joined by `", "`) compared by code unit; then by `id` compared as text. This is a total order, so the pages of R8 never repeat or skip an item. The rank and the comparison are pure functions of `packages/shared/src/search/names.ts`: `nameRank(foldedName: string, foldedQuery: string): 0 | 1 | 2 | null`, `nameSortKey(foldedNames: string[]): string` (the folded names sorted ascending by code unit and joined by `", "`; one name gives itself) and `compareSearchNames(a: { rank: 0 | 1 | 2; sortKey: string; id: string }, b: { rank: 0 | 1 | 2; sortKey: string; id: string }): number` (rank, then sort key, then id, each ascending), so the palette can order what it holds in the same way. Matching and ordering run in the server's memory over the rows of R4 and R5 (concern 8). Check: table tests of `nameRank`, `nameSortKey` and `compareSearchNames` and of the order (`dat` against `Đạt`, `Dat`, `Nguyễn Văn Đạt`, `Mai Đạt`; equal names broken by id; a decomposed name; a lone combining mark); route tests: `nguyen` finds the person `Nguyễn` and so does `Nguyễn`, `dao` finds `Đào`, and `duong` finds the channel `duong-dan` (AC-082, TS-127, TS-128); a group is found by the name of any other member and not by the actor's own name; a direct message with a deactivated person is found by that person's name in `conversations` while the person is not in `people`; `duong dan` finds the channel `duong-dan` and `duong-dan` finds it too; `ha` finds the channel `ha-noi`; a topic word that is in no name finds nothing; with 45 people named `Test 01` to `Test 45` and the query `test`, three pages hold 20, 20 and 5 items, each person once, in the order of the names.
- R7. Messages. When the trimmed query has fewer than `SEARCH_MESSAGE_MIN_LENGTH` (2) code points (F29: messages from 2 characters; the prototype tests `q.trim().length >= 2`), or `buildSearchTsQuery(q)` is `null` (no word, for example `!!` or an emoji), `messages` is an empty page and no statement of messages is sent. Otherwise the route takes the ids of the actor's member conversations (the set of R4 (a), from the same statement, so the actor's membership is the only thing that decides which conversations are searched), asks `searchMessageIds` of TOKI-069 R9 for `limit` 21 (one more than the page) with `before` from the cursor, in groups of at most 1,000 ids (the limit of that function): with 1,000 ids or fewer one call; with more, one call for each group, one after the other, the results merged and sorted by (`createdAt`, `id`) newest first and cut to 21, which gives the same list as one call would for rows written with a whole millisecond (R8, concern 9). All the reads of the request run in one snapshot (R10), so the ids and the entries are read from the same state of the database. The order, the word rule and the cost are those of TOKI-069 (concerns 4, 5 and 11 of that spec and of this one); this route adds no order of its own. The text of a result is read through `buildMessageEntriesByIds` (R9), which is given the ids that the search returned for the first 20 and the ids of the actor's conversations, and the builder of TOKI-037 R27, so a result has the same hiding rules as a message in a list; an entry whose `deletedAt` is not null or whose `kind` is not `user` is dropped (the index already leaves them out, so this is a guard), and an id with no entry is dropped, so a page can hold fewer than 20 items, or none, while `nextCursor` is not null, and the client asks again. The cursor of a messages page is built from the last id that `searchMessageIds` returned among the first 20, the position read and not the position shown, so a page whose items were all dropped still advances. Replies are returned like any message (TOKI-069 R9), with their `parentId`. The messages of a person whose account is deactivated are returned (F41: old messages stay). A `SearchMessage` is `{ id, conversationId, conversationName (the name of the channel, null for a direct message or a group), authorId, parentId, createdAt, text, textTruncated }`: the six values come from the entry, `text` is its first `SEARCH_TEXT_MAX` (300) code points (counted with `Array.from`, so no pair of a surrogate is cut) and `textTruncated` is true when the text was longer. The entry's reactions, files, pins and mentions are not read and not returned (no reader is passed to the builder); the highlight and the choice of a window around the match are TOKI-071's (concern 11). Check: with the fixtures of TOKI-069 R12 in three conversations of the actor, one conversation of another workspace and the conversations of R4: only the actor's conversations give messages (a message of the private channel of others, of a direct message of others, of a public channel not joined and of a left channel is never in the answer, with the word in each); a message of an archived channel the actor belongs to is returned; `nguyen` finds `Nguyễn Văn Đạt` and `duong dan` finds `đường dẫn` (AC-082, TS-127), `Nguyễn` and `đường dẫn` find the same (TS-128); a word used only in a private channel (`bluebird`) gives no message and no channel for a non-member (AC-083, TS-129); a deleted message and a system line are not returned; a message deleted and committed through a second connection between the call of `searchMessageIds` and the read of the entries (a seam called between them) is still returned, because the request reads one snapshot, and the next request does not return it; with a fake `buildMessageEntriesByIds` that returns no entry for all 20 ids, the page is empty, `nextCursor` is not null and the call with it returns the next ids (the cursor advances); a text of 301 code points is cut to 300 with `textTruncated` true, and a text of 300 is not; a text with an emoji at the cut is not split; `a` (one code point) and `!!` give an empty page with no statement of messages; a person with 1,001 conversations (bulk SQL) finds a message in the first and in the last: two calls of `searchMessageIds` (the counting fake), the page equal to the one made by a fixture of the same messages in 10 conversations; the page after the one with 21 matches holds the 21st and `nextCursor` null.
- R8. The cursor. `nextCursor` is opaque to the client: base64url of the JSON array `[rank, sortKey, id]` for the three name kinds and `[createdAtIso, id]` for messages (the position of the last item returned for names; for messages the position of the last id read, R7). The next page is the items that follow that position in the same order (R6: after the position in the total order; R7: `before` of TOKI-069 R9, which compares the pair (`created_at`, `id`)). A cursor that is not base64url, not that JSON (the shapes differ, three elements for names and two for messages, so a cursor made for one kind never fits another), of the wrong shape for the kind (a rank other than 0, 1 or 2, an id that is not a lower-case UUID, a time that is not an ISO 8601 UTC time with a `Z`) is 400 `validation_failed` with the path `cursor` and the code `invalid_cursor` (the shape of TOKI-029 R6). A cursor made for one query and sent with another is a position in the other query's order and gives a valid page (it reveals nothing, because every page is built from the sets of R4 to R7). `created_at` of a message written by the application is a whole millisecond (TOKI-008 R19 clock, TOKI-037 R3), so the `Date` of `before` loses nothing, and "the same list as one call" (R7) holds for such rows; a row written by SQL, an import or the seed with microseconds can be ordered differently by the merge of R7 and skipped or repeated at a page boundary, so the seed of TOKI-081 writes whole milliseconds (Plan changes). Check: for each kind, 45 matching items read in three pages give each item once, in order, and the last `nextCursor` is null; with 25 messages sharing one `created_at`, the pages never repeat or skip (the ids break the tie); each malformed cursor is 400 with `invalid_cursor`; a cursor made for names and sent with `kind=messages`, and one made for messages sent with a name kind, are 400 `validation_failed` with `invalid_cursor`, never a 500; a cursor of 513 characters is 400 before decoding; a cursor that points past the end gives an empty page with `nextCursor` null.
- R9. Reads added to two modules. (a) `modules/conversations/search.ts`, exported by `index.ts` (no table is exported): `listSearchableConversations(client, workspaceId, userId, deps: { listLastMessageTimes })` returns `{ id, kind, name, topic, isPrivate, isGeneral, archived, createdBy, memberIds, isMember }[]`, where `createdBy` is set for a `dm` row only (its one use is `hideUnstartedDirects`) and is null for every other row, so a channel that is not joined leaves the function as id, name and topic and flags only: one statement over `conversations` left-joined to the actor's own `conversation_members` row, for the workspace, with the rows where the row exists (`isMember` true) or the conversation is a channel, is not private and is not archived (`isMember` false); `memberIds` is `string_to_array(dm_key, ',')` for a direct message or a group, null for a channel; then the filter of TOKI-037 R19 for the unstarted direct messages, using `deps.listLastMessageTimes` (one grouped statement, called only when the first one returned a direct message the actor did not create, and with those ids). That filter is the one function of `summaries.ts` (`hideUnstartedDirects`, extracted from `listConversationSummaries` by this ticket so that the list and the search apply one rule, with the tests of the list unchanged); a group is not filtered, which is a proposal and not a decision (concern 10). (b) `modules/messages/entry.ts` gains `buildMessageEntriesByIds(db, workspaceId, conversationIds, ids)`, which does not trust the ids: one statement `select ... from messages where workspace_id = $1 and conversation_id = any($2) and id = any($3)`, with `conversationIds` the conversations of S1, so a message outside the actor's set cannot be read even by a later change to the route; then `buildMessageEntries(db, rows)` of TOKI-037 R27 with no reader, and the entries in the order of `ids`, an id with no row dropped; exported by `index.ts`. The module `members` gains nothing: `listPeople` is used as it is. Check: `listSearchableConversations` is tested on the fixture of R4 (the rows, the flags, `memberIds` in the order of the key, the unstarted direct message hidden for the person who did not create it and shown to its creator, and shown to both after a message) and by one test that its direct and group ids equal those of `listConversationSummaries` for the same person on a fixture without an archived or an unjoined conversation; `buildMessageEntriesByIds` returns the entries in the order of the ids, drops an unknown id, an id of another workspace and an id of a conversation outside `conversationIds` (a message of a private channel of others, given by id), and sends one statement for 50 ids; `listSearchableConversations` returns `createdBy` null for a channel, joined or not, and for a group, and the creator for a `dm`; the export tests of both modules list the new names and no table.
- R10. Statements and cost. The route opens one transaction, `READ ONLY` at `REPEATABLE READ`, and runs all its reads inside it, so the member rows and the messages come from one snapshot and a person removed from a private channel while the request runs gets no message of it that the snapshot does not hold (D-051, AC-083). The route's service opens it itself with the database client, as the bootstrap handler does (bootstrap R10); it imports no helper of `bootstrap`, which no other module may do, and the five reads take the transaction as their `client`. `BEGIN` and `COMMIT` are not counted as statements. The route reads in this order, and only what the kinds asked for need: S1 `listSearchableConversations` (always, for the kinds `conversations`, `channels` and `messages`), S2 the unstarted-direct read of R9 (only inside S1's function), S3 `listPeople` (for `people` and for `conversations`, whose direct names come from it), S4 the calls of `searchMessageIds` (for `messages`), S5 `buildMessageEntriesByIds` (for `messages`, when S4 returned an id). The count of statements of a request is therefore at most 5 with no kind, and for `kind=people` it is 1, for `kind=channels` 1 or 2, for `kind=conversations` 2 or 3, for `kind=messages` at most 4. These per-kind numbers are for up to 1,000 conversations; each further group of 1,000 adds one S4 call to every request that asks for messages (so `kind=messages` with 1,001 conversations is at most 5 and no kind at most 6). Apart from those added calls, the count does not depend on the number of results or of conversations. Matching names in memory reads every conversation the actor belongs to and every public channel not joined (at most the 500 conversations of D-117, before it is reconsidered) and every account of the workspace (200 people, D-113), the sets that the first load already reads. The route runs no write and sends no event. The search of messages is as fast as TOKI-069 R11 says and no faster: for a very common short prefix the budget of D-113 can be missed, the cost of `searchMessageIds` is paid once for each group of 1,000 conversations, and the route adds the permission set and the entry read to it (concern 6); TOKI-089 measures the whole request. Check: the same seam as bootstrap R10 runs `show transaction_isolation` and `show transaction_read_only` on the transaction and asserts `repeatable read` and `on`; a member row removed through a second connection after S1 does not change the answer of that request and changes the next; a statement counter on the connection checks each count above for each `kind` and for no `kind`, with 5 conversations (the numbers above) and with 1,001 (the numbers above plus one for messages); the same count for a fixture of 40 conversations and one of 4; no test of this ticket uses a real timer or a clock.
- R11. Nothing is confirmed and nothing leaks. (a) The route answers 200 for any valid query, also when nothing matches or nothing is allowed, and it has no 403 and no 404 about data (the one 403 is the refusal of `canUseWorkspaceViews` in R1, which no role reaches): it never names a conversation, a person or a message the actor may not see, so "no access" and "no result" are the same answer (BR-10, TS-129). (b) An unexpected error is answered as 500 `internal_error` by the shared handler with no text of the query, of a name or of a message in the body; the server logs the Postgres code and the constraint name only, never the error object or its `detail` (TOKI-029 R20, TOKI-037 R23). (c) The log line of a request holds the method, the path without the query, the status and the duration (TOKI-004 R7), so the text typed is not in the log; the route adds no log line. (d) The query string is the text of a search, so it is not echoed in any answer. Check: a forced failure of each read (fakes) gives 500 with a body that holds no text of the query, and a captured log that holds neither the query, a conversation name, a person's name nor a message text; a captured log of a 200 holds no query text; a request for a word that exists only in a conversation of others and one for a word that exists nowhere give byte-equal bodies (both four empty pages).
- R12. The shared package. `packages/shared/src/search/` (which TOKI-069 R6 creates with `words.ts`) gains `limits.ts`: `SEARCH_KINDS` (`conversations`, `channels`, `people`, `messages`), `SEARCH_PAGE_SIZE` 20, `SEARCH_QUERY_MAX` 200, `SEARCH_CURSOR_MAX` 512, `SEARCH_MESSAGE_MIN_LENGTH` 2, `SEARCH_TEXT_MAX` 300; `schemas.ts`: the strict Zod objects of the query (R2), of the four items and of the response (R3); `names.ts`: `nameRank`, `nameSortKey` and `compareSearchNames` with the types of R6, pure with no DOM global. All are exported from the package index, so the palette (TOKI-071) parses with the same schemas. The error code `invalid_cursor` is a code of `details.issues` as in TOKI-029 R6 and is not a new entry of `ErrorCodes`. Check: the schema tests of R2 and R3, the table tests of R6, the export test of the package (it lists `SEARCH_CURSOR_MAX`, `nameRank`, `nameSortKey` and `compareSearchNames`), `pnpm lint` (the rule `toki/client-core-globals` for the shared package).
- R13. Module and wiring. The route is in `apps/server/src/modules/search/` (`routes.ts`, `service.ts`, `cursor.ts`, `safe-error.ts`, `index.ts` exporting `searchRoutes`); the module owns no table and no migration. It imports the public entries of `conversations` (`listSearchableConversations`), `members` (`listPeople`) and `messages` (`searchMessageIds`, `buildMessageEntriesByIds`, `listLastMessageTimes`) and no other file of them (lint rule 2, TOKI-002); none of those modules imports `search`. `searchRoutes({ db, ...overrides })` takes the reads as optional dependencies with the real ones as defaults, so a test can count calls or inject a failure (R7, R10, R11); `app.ts` registers it in the `/api/v1` scope next to the other routes and passes nothing else. The module's error handler follows TOKI-029 R20 (a file of its own, `safe-error.ts`; if a shared one exists when this is built it is used instead). No route, event, table, column or job other than `GET /api/v1/search` is added, `MessageEntry` and the send, edit and delete are unchanged, and no code outside `modules/messages/` reads `messages` for a search. - R14. The access matrix. ## Design
### One request, four sets
```
GET /api/v1/search?q=nguyen[&kind=people&cursor=...]
  session -> canUseWorkspaceViews -> query schema
  S1  listSearchableConversations ----+--> conversations  (member rows)
                                      +--> channels       (public, not archived, not joined)
                                      +--> ids of member conversations --+
  S3  listPeople  -> people (active, not the actor) -> also DM names      |   (all reads: one READ ONLY, REPEATABLE READ transaction)
  names: foldText + nameRank, in memory -> pages of 20                    |
  messages: buildSearchTsQuery -> searchMessageIds (TOKI-069) <-----------+
            -> buildMessageEntriesByIds -> cut the text -> page of 20
```
The permission rule is the shape of the sets, not a filter applied afterwards: a conversation the actor is not a member of has no row in S1 unless it is a public channel that is not archived, and then only its id, name and topic leave the module. A message query is never given an id that did not come from the actor's own member rows, and it has no way to widen that list; the read of the entries checks the conversation again.

### What each kind matches and returns
| Kind | Source | Matched | Returned | Cut at 20 |
|---|---|---|---|---|
| `conversations` | actor's member rows (R4 a) | name of a channel; names of the other members of a direct message or group | `SearchConversation` | by rank, name, id (R6) |
| `channels` | public, not archived, not joined (R4 b) | name | `SearchChannel` (id, name, topic) | by rank, name, id |
| `people` | active accounts but the actor (R5) | display name | `SearchPerson` (id, displayName) | by rank, name, id |
| `messages` | `searchMessageIds` in the actor's conversations (R7) | the words of the text, by the rule of TOKI-069 | `SearchMessage` | newest first (proposal, concern 5) |

The kind `channels` is separate from `conversations` because F29 lists "Channels you can join" as its own group and D-112 counts 20 per kind: a person with 30 matching conversations would otherwise never see a channel they could join. Whether the palette draws one group or two is TOKI-071's (concern 7).

### Why names are matched in memory
Decided in this spec (concern 8). Names are short, the sets are small (R10), and the rule of the lists is `foldText` on both sides with a contains test. Matching in memory with the same function means there is one fold in TypeScript for every list, no second SQL fold for names to keep equal to it, and the order of R6 (a rank computed from the folded name) is a plain sort. The cost is that each request reads the conversations and the people the first load reads; the member list of the Admin page already folds in SQL for its own reasons (member management R24), and that is not reused here. If a workspace passes the 500 conversations of D-117, this is where to look first (TOKI-089).

### Pages
`nextCursor` is the position of the last item returned for names and the position of the last id read for messages (R8). A page is read with one item more than it returns to know whether another exists. The kinds are paged separately, so asking for more of one kind (`kind=people&cursor=...`) does not read or return the others.

## Data safety
- The route reads conversations, names and message text and writes nothing. The answer is personal and is not cached (R1). The text of a search is in the query string and is never logged or echoed (R11).
- The permission rule is built into the sets (R4, R5, R7) and tested for four roles and memberships (R14). The function `searchMessageIds` trusts the ids it is given (TOKI-069 R9); this route is the one place that gives it ids, and it gives only the actor's own; the entries are read with the actor's conversation ids again (R9 b), and all reads run in one snapshot (R10).
- A channel that was not joined reveals its name and topic (F29) and no message (D-116). A private channel and a direct message of other people reveal nothing, not even that they exist (D-051, BR-10).
