# Database connection, migrations and the workspaces table design

Date: 2026-11-12 · Status: draft for review (decisions of 2026-11-16 recorded)
Intent: docs/intents/database-migrations.md (Thanh Truong)
Ticket: TOKI-005

## Goal
The builder (Thanh working with Claude) needs the server to reach Postgres and one repeatable way to change the database structure.
The first table, `workspaces`, must exist, because every later table carries `workspace_id`.
Later tickets then add their tables the same way, and the test harness can run against a real Postgres.

## Design
### Data model
`workspaces` (the only table in this change):
- `id`: `uuid`, primary key, UUIDv7, made in the server (R8). It is the workspace id: there is no separate `workspace_id` column, and other tables point to `workspaces.id` (Decided by Thanh, 2026-11-16, concern 2). Source: Blueprint data model notes.
- `name`: text, not null, not empty, at most 100 characters (R9). Source: flow F01 says the workspace name comes from an environment variable; the rules are Decided by Thanh, 2026-11-16.
- `created_at`: timestamp with time zone, required, set by the database on insert (R15). Decided by Thanh, 2026-11-16.
- No other column. Several rows are allowed: no single-row constraint (R15).
- The table is created empty. No row is inserted by this change.

### Errors
- Connection variable missing -> the server does not start and prints the variable name (Blueprint, flow F01 rule; TOKI-004 R3 through R2). `db:migrate` does the same (R14).
- A migration fails -> the apply command exits non-zero, prints the Postgres error and leaves the database as it was before the run (R7).
- Postgres unreachable when `db:migrate` runs -> it exits non-zero and says so, without a password (R14). A retry in the deploy step belongs to TOKI-085.
- Postgres unreachable at server start -> the server still starts, `/healthz` stays ok, and a request that needs the database fails with `internal_error` (R16).

### Layout
Assumption: the folder and script names below are proposals; the Blueprint fixes only `apps/server` and Drizzle. The table location follows TOKI-002 (design rule 2, concerns 1, 2 and 11).
```
apps/server/
├─ drizzle.config.ts        Drizzle Kit settings (table files: src/modules/*/schema.ts; migrations path)
├─ migrations/              generated SQL files and meta/ (_journal.json, snapshots), all committed to git
└─ src/
   ├─ config.ts             (TOKI-004) gains `DATABASE_URL` and a function that checks only that variable
   ├─ db/
   │  ├─ client.ts          createDb(connection): opens a connection from the value it is given; reads no environment
   │  ├─ migrate.ts         runMigrations(connection, folder); its command entry reads the value from config.ts
   │  └─ README.md          how to add a table
   └─ modules/workspace/
      └─ schema.ts          the workspaces table definition; not exported from the module's index.ts
package.json (root)         scripts db:generate and db:migrate; dev:reset:db (from TOKI-003) gains the db:migrate step
```
- The connection value is read in one place, the TOKI-004 configuration module, which stays the only reader of `process.env` in `apps/server/src` (TOKI-004 R2). `client.ts` and `migrate.ts` read no environment: they take the connection value as a parameter. The server builds its client once at startup from the value in `config.ts`; building it opens no connection, so an unreachable Postgres does not stop the start (R16). Tests and the TOKI-008 harness pass another value, from `TEST_DATABASE_URL` (TOKI-008 R18), so no rewrite is needed to reach a test or throwaway database.
- `db:migrate` runs outside the server. Its entry calls the function of `config.ts` that checks only the connection variable, so it does not fail because an unrelated required variable (mail, first admin, workspace name) is unset. How the command gets `.env` loaded follows the `dev` script of TOKI-004; in CI and in the deploy step the value is in the environment. Assumption: this is a small addition to `config.ts`, which TOKI-004 builds first.
- The table definition lives in `modules/workspace/schema.ts`, not in a shared folder, so lint rule 2 and rule 17 of TOKI-002 keep other modules and shared files from importing it. `client.ts` is built without any table definition; each module imports its own tables. Tests of the table (R8, R9) sit in the same module folder.
- The migration folder is `apps/server/migrations/`, outside `src/`. A migration is the whole folder content: the SQL file, `meta/_journal.json` and the snapshot. Leaving `meta/` out makes the migrator skip the new SQL file and makes the next `db:generate` diff against a stale snapshot.
- The database connection is one URL variable, `DATABASE_URL`; tests use `TEST_DATABASE_URL`. No separate host, port, user, password or database variables exist. Decided by Thanh, 2026-11-16 (replaces the earlier stand-in note of 2026-11-12). TOKI-096 lists both names in its inventory.
- Migrations are applied by command only, not at server start. Outside development the command runs as a step of the automated deploy (TOKI-085). See concern 4.
- The Postgres driver is chosen when the ticket is built and named in the PR (concern 3). It changes nothing in the requirements.

## Testing
- Written test-first, as the Blueprint asks for backend work.
- Integration tests with Vitest. The connect test (R1) reads the development Postgres from TOKI-003 through `DATABASE_URL` and writes nothing. Every other test runs on a throwaway database made on the server given by `TEST_DATABASE_URL` (CI has its own service, below): apply on an empty database (R4), apply twice (R5), broken migration (R7), id is UUIDv7 (R8), name rules (R9), `created_at` and several rows (R15), unreachable Postgres (R16), the loopback guard (R13). The tests of one file share one throwaway database; each file makes its own, so files cannot interfere even if they run in parallel.
- R2, R3, R6, R11, R12, R14 and the by-hand part of R16 are checked by hand once on the builder's machine by running the command or looking for the file; the output goes in the PR. R12 stays by hand because `dev:reset:db` only targets the development database (TOKI-003 R5, R12) and no test may touch it (TOKI-008 R16).
- In CI, the tests check of TOKI-007 starts a Postgres 17 service and gives the tests the connection value (TOKI-007 R15), so these tests run and pass there, not skipped. When Postgres is not reachable the database tests fail with a clear message; they are never skipped (TOKI-008 R7). The TOKI-004 tests stay free of any database (TOKI-004 R11); the Scope plan change records that the `apps/server` test command now also runs these tests.
- TOKI-008 later runs these tests under its harness against the test database (TOKI-008 R15, R16, R18). Nothing here changes for that: the tests already take the connection value as a parameter and already use `TEST_DATABASE_URL`.
- Fake data only.

## Data safety
- The connection value lives in `.env`, never in git. In `.env.example` (owned by TOKI-096) the rows for `DATABASE_URL` and `TEST_DATABASE_URL` are empty, not placeholders, as for every secret (TOKI-096 R9). The throwaway credentials of the CI Postgres service live in the workflow file and are not secrets (TOKI-007 R11).
- The tests never wipe the database that the connection value points at: they make and drop their own throwaway database on the server of `TEST_DATABASE_URL`, and refuse to run on a non-loopback host (R13), so a `.env` that points at a shared or production server is not touched; `DATABASE_URL` is only read by R1.
- The connection value is never written to logs or error output. The only parts printed are the variable name (when it is missing) and the host and database name (when Postgres is unreachable), never the password or the full URL (R14).
