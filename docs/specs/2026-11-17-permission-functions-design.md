# Shared permission functions design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/permission-functions.md (Thanh Truong)
Ticket: TOKI-027

## Goal
The builder needs one set of rules that says what a Member and an Admin may do, so the server can refuse what a role may not do and the web app can hide the same controls, with no second copy that drifts. This ticket puts those rules into `packages/shared` as pure functions: a role plus a few facts go in, a yes or no plus a reason code comes out. They follow the capability table that D-090 signed off. Later feature tickets call them and add the rows of their own features.

## Scope
- In: a module `packages/shared/src/permissions/` exported from `@toki/shared`: the types (role, actor, facts, decision, reason codes); one function for each phase 1 row of the capability table (Design, Table A) plus two rules that are in no row of the capability table: #general cannot be left (D-034), and any member edits the topic and description of a channel (D-105); the unit tests, including a matrix test of every function for both roles; the rule for what a function does when a fact is missing or a role is unknown.
- Out (not now):
  - Guest. Guest is a phase 5 role (D-090, D-152; technical design, phase 5: "a guest role added to the shared permission rules"). Phase 1 has no Guest function. The ticket that builds guests adds the role, its rows and the guest permission suite of D-050.
  - Capability rows of phase 5: "Invite a guest to a channel", "Create automations", "See Analytics". The ticket that builds each feature adds its function to this module and its row to the matrix test (R14).
  - Loading the facts (membership, channel kind, archived, author) from the database, and the HTTP status and error text for a refusal: the API ticket that owns the endpoint. The facts of a conversation are read by `getConversationFacts` of TOKI-028 (Design, "Facts of a conversation: who maps the columns"). The tickets that call the functions are TOKI-024 (members), TOKI-029 (channels), TOKI-030 (DMs), TOKI-037 (send), TOKI-045 (threads), TOKI-046 (reactions), TOKI-047 (edit and delete), TOKI-048 (pins) and TOKI-050 (@channel).
  - Hiding a control on a screen: the screen ticket (for example TOKI-035 Details panel, TOKI-034 Browse channels). This ticket gives them the function to call.
  - Account status and sessions. `users.status` is `active` or `deactivated` (TOKI-019 R10); an invited person has no `users` row (TOKI-019 concern 2). A deactivated person has no session (BR-29), so the server never reaches a permission function for them. Sign-in checks the status: TOKI-022. These functions read the role of an account, and for a target person of `canChangeRole` and `canDeactivateAccount` also its status.
  - Limits that are not permissions: a group DM holds up to 8 people (D-017), `@channel` asks for confirmation in a channel of 20 or more (D-041), channel name rules (D-040), a message holds up to 10,000 characters (D-042). The ticket of the feature owns each.
  - The role column and the table that stores it: TOKI-019. The first Admin from configuration: TOKI-020.
  - The record of administrative actions (D-110) and the repeat-request rule (D-111): TOKI-024. TOKI-024 also owns the transaction that locks the active Admin rows and then calls `canChangeRole` and `canDeactivateAccount` (R12, Design, "What a caller must pass"); the last-Admin and self-deactivation rules are functions of this ticket, called by TOKI-024.

## Requirements
- R1. `packages/shared/src/permissions/` exists and everything in R2 to R12 is exported from `@toki/shared` (`packages/shared/src/index.ts`). `pnpm typecheck` at the repository root exits 0 with an import of every exported name from `@toki/shared` in a test file.
- R2. The module exports the type `Role` with exactly the values `"member"` and `"admin"` (no Owner, D-152); the type `Actor` `{ id: string; role: Role }`; the type `ActorInput` `{ id: string; role: string }`, which every function takes in place of `Actor` for the person who acts (and, in `canCreateDirectConversation`, for any person; R8), so a caller passes the role as the table stores it (text) without a cast, and a value that is neither `"member"` nor `"admin"` reaches the function and gets `unknown_role` (R4); `Actor` is assignable to `ActorInput`; the type `ConversationFacts` `{ kind: "public_channel" | "private_channel" | "dm" | "group_dm"; isGeneral: boolean; archived: boolean; isMember: boolean }` (`isMember` is whether the actor is a member of that conversation); the type `MessageFacts` `{ authorId: string }`; and the result type `Decision`: `{ allowed: true }` or `{ allowed: false; reason: DenyReason }`. `canDeleteMessage` returns the type `DeleteDecision`: `{ allowed: true; as: "author" | "admin" }` or `{ allowed: false; reason: DenyReason }` (R7). `ConversationFacts` is defined here and imported by the conversations module of TOKI-028 for the return type of its `getConversationFacts`. Facts that contradict each other (`isGeneral` true with a `kind` other than `public_channel`) are malformed and give `fact_missing` (R4). `DenyReason` is exactly: `fact_missing`, `unknown_role`, `role_not_allowed`, `not_a_member`, `not_a_channel`, `private_channel`, `channel_is_general`, `channel_archived`, `not_author`, `self_target`, `last_admin`.
- R3. Every function is pure: it reads no database, clock, network, environment or global, it does not change its arguments (a test passes deeply frozen arguments), it does not throw, and it returns the same result for the same arguments. A function that gives a yes or no for several reasons returns the first reason in this order: `fact_missing`, `unknown_role`, `role_not_allowed`, `not_a_member`, `not_a_channel`, `private_channel`, `channel_is_general`, `channel_archived`, then the reasons about the message or the target person (`not_author`, `self_target`, `last_admin`).
- R4. Missing facts deny. When an argument a function needs is missing, `null`, of the wrong type, or (for `kind` or `role`) not one of the listed values, the function returns `{ allowed: false, reason: "fact_missing" }`; a `role` that is a string but is not `"member"` or `"admin"` (for example `"guest"` or `"owner"`) returns `unknown_role`. `actor.id`, `authorId` and `target.id` must be non-empty strings; an empty string is malformed and gives `fact_missing`, so two empty ids never match. Ids are compared as they are, case included (they are the ids of the tables, TOKI-019 convention). A function never defaults a missing fact to a permissive value. Each function checks only the facts it uses, as listed in Table A. Check: a table test calls every function with each of its facts removed in turn and with the role `"guest"`, and expects `fact_missing` or `unknown_role` every time, never `allowed: true`.
- R5. Reading and writing a conversation (D-077, D-116, BR-09, BR-11). `canReadConversation(actor, conv)` is allowed for a Member and an Admin who is a member of the conversation, whatever its kind and whether or not it is archived; otherwise `not_a_member`. `canPostInConversation(actor, conv)` is allowed when the actor is a member and `archived` is false; an archived conversation gives `channel_archived`. It answers sending, replying in a thread, reacting and attaching files. An Admin who is not a member of a private channel or a DM is refused both (`not_a_member`): an Admin has no extra right to read (D-047).
- R6. `canUseAtChannel(actor, conv)` is allowed for any Member or Admin who is a member of a channel (`public_channel` or `private_channel`) that is not archived (D-041, FR-17: any member of a channel); a `dm` or `group_dm` gives `not_a_channel`. `canPinMessage(actor, conv)` (pin and unpin) is allowed for any Member or Admin who is a member of a conversation of any kind that is not archived (FR-36); for both, a non-member gets `not_a_member` and an archived conversation `channel_archived`.
- R7. Messages (BR-24, FR-11, FR-12, FR-13). `canEditMessage(actor, conv, msg)` is allowed only when the actor is the author (`msg.authorId === actor.id`), is a member, and the conversation is not archived: a Member and an Admin alike; for another person's message it gives `not_author`, also for an Admin. `canDeleteMessage(actor, conv, msg)` is allowed for the author, and for an Admin who is a member of the conversation (`as: "admin"`); a Member who is not the author gets `not_author`. The allowed result is a `DeleteDecision` (R2) and carries `as: "author"` or `as: "admin"` (an Admin deleting their own message is `author`), so the caller can show 'Message deleted by an admin' and tell the author (D-049). In an archived conversation both give `channel_archived`; for a non-member both give `not_a_member`.
- R8. Creating conversations. `canCreateChannel(actor)` is allowed only for an Admin; a Member gets `role_not_allowed` (D-084, D-090). `canCreateDirectConversation(actor)` is allowed for a Member and an Admin (DMs and group DMs). Its argument is `{ id, role }` and not tied to the signed-in person, so a caller may also pass another person to ask whether that person may take part in a direct conversation: the answer is the same set of roles, and a role that is not `"member"` or `"admin"` (a guest, later) gives `unknown_role` (R4). No second function is added for that question.
- R9. Channel membership, state and details, for `public_channel` and `private_channel` only (a `dm` or `group_dm` gives `not_a_channel`, because people cannot be added to or removed from a group DM, D-045): `canJoinChannel(actor, conv)`: allowed for a Member or an Admin on a public channel that is not archived; a private channel gives `private_channel` (it is rejoined only when a member adds the person back, D-051); an archived one `channel_archived`. It needs no `isMember` fact. `canAddPeopleToChannel(actor, conv)`: allowed for a Member or an Admin who is a member of the channel, not archived (D-041, D-090). `canRemovePeopleFromChannel(actor, conv)`: allowed only for an Admin who is a member of the channel, never in #general (`channel_is_general`), not archived (D-085, D-047). A Member gets `role_not_allowed`. `canLeaveChannel(actor, conv)`: allowed for a member of a channel other than #general (D-034); in #general it gives `channel_is_general`. A leave from an archived channel is allowed. `canArchiveChannel(actor, conv)`: allowed only for an Admin who is a member of the channel, never #general (D-085, D-034, D-047). `canRestoreChannel(actor, conv)`: allowed for any Admin, a member of the channel or not, never #general (concern 1); a Member gets `role_not_allowed`. It needs no `isMember` fact and never returns `not_a_member`. Neither function checks whether the channel is already archived: that conflict belongs to the API (TOKI-029). That the Admin who restores becomes a member of the channel, and that a private channel stays hidden from a person who is not a member, is the work of the API too; a pure function writes nothing. `canEditChannelDetails(actor, conv)` (the topic and the description; the name and the privacy of a channel are never edited, D-105, D-040): allowed for a Member or an Admin who is a member of the channel, not archived (D-041, D-105); a non-member gets `not_a_member`, a `dm` or `group_dm` `not_a_channel`, an archived channel `channel_archived`, in the order of R3.
- R10. Workspace pages. `canUseWorkspaceViews(actor)` (Activity, Later, Files, People and Ctrl+K) is allowed for a Member and an Admin. `canOpenAdminPage(actor)` is allowed only for an Admin; a Member gets `role_not_allowed` (D-090). The Admin page lists members, so the member list endpoint of the Admin page uses `canOpenAdminPage`.
- R11. Invitations. `canInviteMember(actor, { role })` is allowed only for an Admin, for the invited role `"member"` or `"admin"` (D-153); an invited role that is not one of the two gives `unknown_role`. `canManageInvitations(actor)` (resend, revoke, list invitations) is allowed only for an Admin.
- R12. Accounts (D-153, BR-27, BR-28). `target` is `{ id: string; role: Role; status: "active" | "deactivated" }` (the two statuses of TOKI-019 R10) and `activeAdminCount` is the number of active Admins of the workspace, read by the caller after it locked the active Admin rows (Design, "What a caller must pass"); it includes the target when the target is an active Admin. The last Admin is an active Admin when `activeAdminCount` is 1 or less. `canChangeRole(actor, target, newRole, activeAdminCount)`: allowed only for an Admin. Making an Admin a Member (a demotion) when the target is an active Admin and `activeAdminCount` is 1 or less gives `last_admin`, also when the Admin demotes themselves; with two or more active Admins an Admin may demote any Admin, themselves included. Demoting a deactivated Admin is allowed whatever the count, because no active Admin is lost. Promoting, and setting the role a person already has, is allowed. `canDeactivateAccount(actor, target, activeAdminCount)`: allowed only for an Admin; the actor deactivating themselves gives `self_target`; deactivating an active Admin when `activeAdminCount` is 1 or less gives `last_admin`; deactivating a Member, or an Admin who is already deactivated, is allowed. `canReactivateAccount(actor)`: allowed only for an Admin. `activeAdminCount` that is not a whole number of 0 or more, or a `status` that is not one of the two, gives `fact_missing`. The function guarantees the rule only for the count it is given; that the count is true at the moment of the change is the caller's work (Design).

Both roles, every function: for each exported `can…` function a test states the expected result for a Member and for an Admin, including the reason code of every refusal in R5 to R12, in the matrix of R14. The orders of R3 are checked with arguments that break two rules at once (for example a Member, not a member of the channel, archived: `role_not_allowed` for `canArchiveChannel`; an Admin who is not a member of an archived channel: `not_a_member` for `canArchiveChannel`, and allowed for `canRestoreChannel`).

The module exports 22 `can…` functions: 20 appear in a row, `canLeaveChannel` in entry 18 and `canEditChannelDetails` in entry 19 (row 1 has no function; rows 3 and 7 reuse `canReadConversation` and `canPostInConversation`). The test fails when an exported `can…` function is in no entry or an entry names a function that does not exist. ## Design
### Table A. The capability table and the function that answers each row
The rows are the rows of the capability table in the Blueprint (reviewed in D-090). Phase 1 uses 17 of its 20 rows, plus entries 18 and 19; the three of phase 5 are in Out. Facts: A = actor (id, role); C = conversation facts; M = message facts; T = target person; N = active Admin count.

| # | Row of the capability table | Member / Admin / Guest (table) | Function | Facts |
|---|---|---|---|---|
| 1 | Sign in with an emailed code | yes / yes / yes | none here: no role decides it; the account status does (TOKI-022) | |
| 2 | Read and post in public channels | yes / yes / not allowed | `canReadConversation`, `canPostInConversation` | A, C |
| 3 | Read and post in private channels | if a member / if a member / invited channel only | the same two functions | A, C |
| 4 | Create public and private channels | not allowed / yes / not allowed | `canCreateChannel` | A |
| 5 | Join public channels; add people to a channel you are in | yes / yes / not allowed | `canJoinChannel`, `canAddPeopleToChannel` | A, C |
| 6 | Create DMs and group DMs | yes / yes / not allowed | `canCreateDirectConversation` | A |
| 7 | Threads, reactions, sending files | yes / yes / yes | `canPostInConversation` | A, C |
| 8 | Pin messages, use @channel | yes / yes / not allowed | `canPinMessage`, `canUseAtChannel` | A, C |
| 9 | Edit and delete your own messages | yes / yes / yes | `canEditMessage`, `canDeleteMessage` | A, C, M |
| 10 | Delete other people's messages | not allowed / where a member / not allowed | `canDeleteMessage` | A, C, M |
| 11 | Activity, Later, Files, People, Ctrl+K | yes / yes / not allowed | `canUseWorkspaceViews` | A |
| 12 | Remove people from a channel | not allowed / where a member / not allowed | `canRemovePeopleFromChannel` | A, C |
| 13 | Archive and restore channels | not allowed / where a member / not allowed | `canArchiveChannel`, `canRestoreChannel` | A, C (`canRestoreChannel` reads `kind` and `isGeneral` only) |
| 14 | Open the Admin page | not allowed / yes / not allowed | `canOpenAdminPage` | A |
| 15 | Invite members | not allowed / with any role / not allowed | `canInviteMember`, `canManageInvitations` | A, invited role |
| 16 | Deactivate and reactivate | not allowed / anyone but the last Admin and themselves / not allowed | `canDeactivateAccount`, `canReactivateAccount` | A, T, N |
| 17 | Change roles | not allowed / yes, except demoting the last Admin / not allowed | `canChangeRole` | A, T, new role, N |

Entry 18, outside the table: leave a channel. The capability table has no row for it. `canLeaveChannel` answers it by D-034 (#general cannot be left), D-051 and F23 (a member leaves a public or private channel). #general also cannot be archived (D-034): `canArchiveChannel` and `canRestoreChannel` (R9). Row 13 keeps the words of the capability table; for restore the rule is wider than "where a member": any Admin restores (R9, concern 1). Entry 19, outside the table: edit a channel's topic and description. `canEditChannelDetails` answers it by D-105 and D-041: a member of either role, in a channel that is not archived (R9); the Details panel (F24) and the channel API call it. The Guest column is not built (Out).

Guest in phase 1: none. Guests exist only from phase 5; until then a caller that passes `"guest"` is refused with `unknown_role` by every function (R4), which is the safe default.

### What a caller must pass, and what a function does when a fact is missing
- Actor: `id` and `role` of the signed-in person, from the session. The server reads the role from the account at each request, not from a value the client sent, and a write request reads it again from its locked account row (below). The caller passes the role as the account read returns it, as text, and does not narrow or cast it to `Role`, so that a stored value the module does not know is refused as `unknown_role` and reaches the server error ("How the server uses them"). The account read of the `members` module that TOKI-029 builds (`getAccountsByIds`, R19 there) returns `{ id, workspaceId, role, status }` with `role` as stored text; these functions use `id`, `role` and `status` and never `workspaceId`, so comparing the workspace stays the caller's work.
- Conversation facts: `kind`, `isGeneral`, `archived` and `isMember`. The server module that reads them owns the mapping from the stored columns; see "Facts of a conversation: who maps the columns" below. The client reads them from the data it already holds.
- Message facts: `authorId`.
- Target person: `id`, `role` and `status` from the account (also read from the locked rows, below). `activeAdminCount`: the number of rows with `role = 'admin'` and `status = 'active'` in the workspace.
- What TOKI-024 must do for the last Admin and the Admin who deactivates themselves. A pure function cannot stop two requests made at the same moment. Under the default read committed isolation, two Admins who demote each other at once both read a count of 2 and both pass, and the workspace is left with no Admin. So TOKI-024 runs the change in one transaction: first it reads every `users` row of the workspace in id order with `SELECT ... FOR NO KEY UPDATE` (the lock target named in TOKI-019 concern 7; TOKI-024 R27 and R39 give the mode and the order), then it builds the actor and the target from those locked rows and counts the active Admins from them, then it calls `canChangeRole` or `canDeactivateAccount`, then it writes, then it commits. The call comes after the lock, never before. A second request waits on the lock and then reads the new state, so an Admin who was demoted while waiting acts with the role it now has. Why every account row and `FOR NO KEY UPDATE`: under read committed a lock on only the active Admin rows would not see a person who another request has just promoted, so the count would be short; and `FOR UPDATE` conflicts with the `FOR KEY SHARE` that every row pointing to an account takes (an invitation, an admin action, a session), which can deadlock two requests. Another way that gives the same result (a serializable transaction with a retry) is allowed if TOKI-024 states it. What the function guarantees by itself: for the count and the target it is given, it refuses the last Admin and the person acting on themselves, and it gives the same result for the same arguments. What it cannot guarantee: that the count is true at the time of the write; that is the lock of TOKI-024. A writer that does not go through TOKI-024 (TOKI-020, a script) must keep the rule itself (TOKI-019 concern 7).
- A fact that is absent or malformed never turns into "allowed": the function returns `fact_missing` (R4). A caller that cannot supply a fact must refuse the request or hide the control.

### Facts of a conversation: who maps the columns
The mapping from the columns of TOKI-028 to `ConversationFacts` is written once, in `getConversationFacts(db, actorId, conversationId)` of the conversations module (TOKI-028, Design, "Reads for other modules"), and is owned by the server module that reads the facts. This ticket does not map any column and its functions do not read the tables. The mapping, with the names of that table: `kind` is `public_channel` when the column `kind` is `channel` and `is_private` is false, `private_channel` when `kind` is `channel` and `is_private` is true, `dm` or `group_dm` as the column says; `isGeneral` is `is_general`; `archived` is true when `archived_at` is not null; `isMember` is true when a `conversation_members` row exists for the conversation and the actor. `getConversationFacts` returns `null` when the conversation does not exist, and the endpoint answers that as "not found" and does not call a function. A mapping slip is therefore tested in TOKI-028 (its tests cover each kind, #general, an archived channel, a member and a non-member); a combination the mapping cannot name is refused by the functions as `fact_missing` (R2). Every API ticket that needs the facts calls `getConversationFacts` and does not map the columns again.

### How the server uses them
Each endpoint loads the facts, calls the function and, on `allowed: false`, refuses the request before any change. The reason code is for the server log and the response body's code; the status and text belong to the endpoint's ticket. When a person is not a member of a private conversation, the refusal reads the same as "not found" (BR-10, so a channel name does not leak): the endpoint maps `not_a_member` that way. `fact_missing` and `unknown_role` are not ordinary refusals: they mean that a loader forgot a fact or that a role the server does not know reached a function. The endpoint answers them with a server error (not 403 or 404) and logs them at error level, so a loader bug does not pass as a normal refusal. The check runs on every request, whatever the screen showed (BR-09). Tests in each API ticket send the forbidden request straight to the server and expect a refusal (the Member's edit request in FR-11, Mai's delete in FR-13, the Admin outside the private channel in FR-13); this ticket proves the rule, the API ticket proves that the endpoint calls it. Each API ticket also has a positive case: the allowed person succeeds, so a loader that always yields a refusal fails a test.

### How the client uses them
The web app calls the same functions with the signed-in person's role and the facts it holds, and hides or disables a control when the result is `allowed: false`. The `reason` lets a screen choose whether to hide the control (`role_not_allowed`) or show it disabled with a text where the screen design says so. The client check only shapes the screen: it is never the only check, because the server repeats every check (BR-09, D-050 for guests later). How `client-core` obtains the role and the facts is built with the bootstrap and the conversation store (TOKI-031, TOKI-032); the dependency of `client-core` on `shared` is declared by the first ticket that imports it (TOKI-001 concern 4).

### Adding a row later
The ticket that builds a new feature with a role rule adds, in the same change: a function in `packages/shared/src/permissions/`, its tests, its row in the matrix (R14), and the call on the server and in the client. No ticket writes a role comparison elsewhere (R16). Examples: guests, automations and analytics in phase 5; the ticket of each.

### Layout
```
packages/shared/src/permissions/
├─ types.ts          Role, Actor, ConversationFacts, MessageFacts, Decision, DenyReason
├─ checks.ts         the shared checks in the order of R3 (facts, role, member, archived)
├─ conversation.ts   read, post, @channel, pin, edit, delete
├─ channel.ts        create, join, add, remove, leave, archive, restore, edit details, direct conversations
├─ account.ts        workspace pages, invitations, roles, deactivate, reactivate
├─ index.ts          the exports
└─ *.test.ts         one file per source file, and capability-matrix.test.ts
```
Decided in this spec: the module is split by subject and not by role, because a rule such as "an Admin where a member" mixes a role and a fact; a function per question is easier to find and to call from both sides.

### Errors
- Missing or malformed fact -> `fact_missing`; unknown role -> `unknown_role`; neither throws (R4).

## Open questions from the intent
- Who restores an archived private channel that has no members left? The log has the question open (D-184): an Admin restores only a channel they belong to, so no Admin could restore a channel with no members. Answered: any Admin may restore an archived channel, a member or not, and becomes its member (R9, concern 1).
- Does Guest have any phase 1 behaviour? No: Guest is a phase 5 role (D-090, D-152; technical design, phase 5). A guest role passed in phase 1 is refused with `unknown_role` (R4). Answered here; see concern 4.

## Areas of concern
1. Restoring an archived channel in which no Admin is a member. The capability table and D-085 say an Admin restores and archives only where they are a member. As R9 was first written, `canRestoreChannel` needed membership, `canJoinChannel` and `canAddPeopleToChannel` refuse an archived channel, and `canLeaveChannel` allows leaving one, so any archived channel, public or private, with no Admin among its members could not be restored by anyone. It happens when the Admin who archived a channel leaves it afterwards, when its last member leaves (D-051 archives a private channel then), and for a public channel whose members are Members only. It also clashes with F26: Browse channels shows an Admin a 'Restore' button on an archived channel, and F21 says only members can open an archived channel; an Admin who is not a member would see a button that the rule refuses. D-184 asks only about a channel with no members. Decided by Thanh Truong (product owner) on 2026-11-19: any Admin may restore an archived channel and becomes its member. `canRestoreChannel` no longer needs `isMember` (R9, R13, Table A row 13, Testing); archiving still needs membership. Adding the member row, and keeping a private channel hidden from an Admin who is not a member, belong to the API (TOKI-029). Owner: Thanh Truong (product owner).
2. An Admin who is a member of a DM or group DM. The table and D-047 say an Admin deletes another person's message "where a member", with no exception for DMs, so `canDeleteMessage` allows it in any conversation the Admin belongs to (R7). Risk for the product owner (a risk to confirm, written here as a consequence): in a 1:1 DM an Admin can delete the other person's messages (shown as 'Message deleted by an admin', D-049), and a Member cannot delete the Admin's. D-047 and D-085 answer who sees and manages private conversations, not a DM in which the Admin takes part. The owner may confirm this or narrow the rule to channels; narrowing changes R7 only. Decided in this spec: follow the table literally, because the log makes no exception for DMs. Owner: Thanh Truong.
3. Archived conversations. The log decides that an archived channel is read-only with a locked composer and still searchable (F26, F21), and BR-11 requires a conversation that is not archived for writing (D-077). So reading stays allowed for a member and posting, replying in a thread, reacting and attaching files refuse with `channel_archived` (R5). The log does not decide the other cases, which R6, R7 and R9 write as refusals with `channel_archived`: editing and deleting one's own message, an Admin's delete, pinning, `@channel`, joining, adding people, removing people and editing the topic and description; and leaving, which R9 allows. Decided by Thanh Truong (product owner) on 2026-11-19: all of these are refused with `channel_archived` as R6, R7 and R9 write them, because they change content or members, and leaving stays allowed. The accepted cost is that nobody can remove a harmful message in an archived channel until it is restored; any Admin can restore it (concern 1). Owner: Thanh Truong. The functions follow the facts: AC-052 and TS-082 read as Sam still a member when the channel is archived; a person who left has no member row and cannot read it (D-116, D-170), and the log does not say that a past member may read.
4. Guest rules arrive later. Decided in this spec: phase 1 has no Guest function and refuses an unknown role (R4); the ticket that builds guests adds the role and the permission suite of D-050. Owner: Thanh Truong.
5. Race between two role changes. A pure function cannot see a change made at the same moment. Decided in this spec: TOKI-024 locks every `users` row of the workspace in id order with `SELECT ... FOR NO KEY UPDATE` (TOKI-024 R27, R39), reads the actor, the target and `activeAdminCount` from the locked rows, calls the function, and writes in the same transaction (Design, "What a caller must pass"); reading the count in a transaction without the lock does not stop two Admins demoting each other (TOKI-019 concern 7, which names `FOR UPDATE` on the active Admin rows and needs the same note). TOKI-024 owns the transaction and a test with two requests together. Owner: Thanh Truong.
