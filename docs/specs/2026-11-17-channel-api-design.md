# Channel API design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/channel-api.md (Thanh Truong)
Ticket: TOKI-029

## Goal
Members and Admins need to work with channels: an Admin creates them, everyone finds and joins public ones, people leave, add each other, edit the topic and description, and an Admin who belongs to a channel removes people, archives and restores it. Today the server has the conversation tables and the shared permission functions but no request that uses them. This work adds those requests. It also fixes, on the server, the rules that no screen may be trusted with: only an Admin creates; one name is never used twice; an outsider can neither read a channel nor learn that a private one exists; #general stays; a repeat of a request changes nothing.

## Scope
- In:
  - Eleven routes under `/api/v1` (Design, "API"): create, browse, details, member ids, edit topic and description, join, leave, add people, remove a person, archive, restore.
  - The functions of the `conversations` module behind them, the locks that keep them correct when two requests meet, and the last-member archive of a private channel (D-051).
  - One more permission function in `packages/shared`, `canEditChannelDetails` (R9), with its row in the matrix of TOKI-027.
  - The request and response schemas, the limits and the new error codes in `packages/shared`.
  - One read added to the `members` module, `getAccountsByIds` (R19), and the export of the route plugin (R18).
  - The seam where later work attaches the effects of a change (R16).
  - Server integration tests, including tests with two real connections.
- Out (not now):
  - The tables, constraints and the reads `getConversationFacts`, `isConversationMember`, `listMemberIds`, `listConversationIdsOfUser`: TOKI-028. #general and the first Admin: TOKI-020. The member row of #general for a newcomer: TOKI-024 and TOKI-097.
  - Direct messages and group DMs, their routes, their key and the refusal of a guest in them: TOKI-030. Adding or removing a person of a group DM is refused here (R2) and nowhere built.
  - The bootstrap call and what it returns for DMs, members, unread and the event number: TOKI-031. This work gives it the read of R18 and writes no event (R16).
  - System lines such as "Lan added Minh", Activity items, push, live events and the "This channel was just archived" strip: no ticket owns them yet (concern 4). R16 is the seam.
  - Saving a person's notification level, mute and star: no ticket owns it yet (concern 5).
  - Reading messages of a channel and the rule that joining gives the full history in the message list: TOKI-037 (messages); this work stores nothing that limits history (Design, "Hand-offs").
  - Every screen: TOKI-034, TOKI-035, TOKI-098, TOKI-100, TOKI-101.
  - Guests: phase 5. A guest role is refused as `unknown_role` by the functions (TOKI-027 R4).
  - Renaming, switching public and private, and deleting a channel: not built; the tables refuse the change of privacy and any delete (TOKI-028 R8, R22).

## Requirements
Access and order of checks
- R1. Every route needs a valid session (TOKI-022 R24, 401). After it, every route runs these steps in this order: (1) `POST /channels` only: `canCreateChannel(actor)`, which needs no body, so a Member gets 403 `forbidden` whatever the body (D-084, D-090); (2) the schemas of the path, query, body and header (400 `validation_failed`); (3) `getConversationFacts(db, actor.id, id)` of TOKI-028: `null` is 404 `not_found`; a `dm` or `group_dm` is 404 `not_found` for every route of this work, so a DM id is never confirmed and a group DM can neither gain nor lose a person here (D-045); a `private_channel` of which the actor is not a member is 404 `not_found`, before any permission function runs, because TOKI-027 R3 puts `role_not_allowed` before `not_a_member` and a Member who is not in a private channel would otherwise get 403 and so learn that it exists (BR-10, D-051); (4) the permission function of the route; (5) for a write, the lock of R15, then the facts are read again and the function is called again. The actor is the account of the session; no route compares a role itself (TOKI-027 R16).
- R2. A refusal of a permission function is answered by reason: `role_not_allowed` 403 `forbidden`; `not_a_member` of a public channel 403 `forbidden`; `not_a_member` of a private channel and `not_a_channel`, `private_channel` 404 `not_found`; `channel_is_general` 409 `channel_is_general`; `channel_archived` 409 `channel_archived`; `fact_missing` and `unknown_role` 500 `internal_error` (TOKI-027, "How the server uses them"). The error body is the format of TOKI-004 and holds no channel name, topic or description. Check: a table test drives each reason through the route that can produce it and checks status and code.

Create
- R3. `POST /api/v1/channels` takes `{ "id": string, "name": string, "isPrivate"?: boolean, "topic"?: string | null, "memberIds"?: string[] }` and answers 201 with `{ "channel": ChannelDetail }` (R7). `isPrivate` is false when absent (D-101). The channel is created with `created_by` the actor, `created_at` from the clock of TOKI-008, the workspace of the one workspace (the read of the `workspace` module that TOKI-022 uses), and no description. The actor and every id of `memberIds` get a member row with a null `notification_level`, false mute and false star (TOKI-028 R14), in the same transaction. Check: an Admin creates a public and a private channel; the rows exist; the actor and the chosen people are members; nobody else is.
- R4. Validation of create. `id` is a lower-case UUID of version 7, made by the client. `name` matches `CHANNEL_NAME_PATTERN` (1 to 80 of `a-z`, `0-9`, `-`; D-040): a name of 80 characters is accepted, one of 81, an empty one and `Q&A Team!`, `QA` and `qa team` are 400 `validation_failed` and the server does not convert them (the conversion of D-127 is the screen's). `topic` is null or 1 to 250 code points after the trim of R9 (`isValidChannelTopic`, D-101). `memberIds` has 0 to 200 entries (R11), repeated ids count once, and the actor's own id is allowed. A person who does not exist or is not active is 400 `invalid_member`, and nothing is created (Decided in this spec, concern 11). The name `general` is 409 `channel_name_taken` before any insert, whether or not #general exists yet, so the check constraint of TOKI-028 R9 is never what the person sees. Check: each case.
- R5. Name uniqueness and repeat (D-115, D-128, D-111). The insert uses `ON CONFLICT DO NOTHING` and so meets the unique name and the primary key without an error. When no row came back the route reads the row of `id`: if it exists, was made by the actor and has the same name, privacy and topic, the request is a repeat and answers 200 with the current `ChannelDetail`, creating, adding and recording nothing; if it exists with other content it is 409 `channel_id_in_use`; if no row has that id, the name belongs to another channel, archived or not, and the answer is 409 `channel_name_taken`. Check: the same body twice gives one channel, one set of member rows, one `recordChange` call (R16) and the second answer is 200; the same id with another name is `channel_id_in_use`; a name used by an archived channel is `channel_name_taken`; with two real connections, two Admins creating `release` at the same moment leave exactly one `release` row, one answer is 201 and the other 409 `channel_name_taken`; two requests with one id and one body at the same moment leave one row and answer 201 and 200.

Browse and details
- R6. `GET /api/v1/channels` takes `search`, `limit` (1 to 100, default 50, D-109) and `cursor` (opaque, from the last answer); a value outside these is 400 `validation_failed`. It answers 200 with `{ "channels": ChannelSummary[], "nextCursor": string | null }`. It lists every public channel, archived ones included, and the private channels of which the actor is a member (F21, prototype: the Browse list holds public channels and the private ones you are in). It never returns a private channel to a non-member. `search` keeps the channels whose name contains the text, ignoring case, as the prototype's search does; the characters `%` and `_` are plain characters, not wildcards. Order: by name in byte order (names are ASCII). Reading every page one after the other gives each channel once. `ChannelSummary` is `{ id, name, topic, isPrivate, isGeneral, archived, memberCount, isMember }`. Check: a Member sees public channels and only the private channels they are in; an Admin who is not in a private channel does not see it (concern 3); 120 channels in pages of 50; `search` with upper case, with `%` and with `_`.
- R7. `GET /api/v1/channels/{id}` answers 200 with `{ "channel": ChannelResponse }`. For a member `ChannelResponse` is `ChannelDetail`: the summary plus `description` (null or text), `createdBy` (the id of the creator) and `createdAt` (ISO 8601 UTC). For a person who is not a member of a public channel it is the `ChannelSummary` alone, with `isMember` false: name, topic and member count only, and no description, creator or message (D-116, AC-053). A private channel of which the person is not a member is 404 (R1). `memberCount` is the number of member rows (concern 9).
- R8. `GET /api/v1/channels/{id}/members` is for members of the channel (R1; a non-member of a public channel gets 403 `forbidden`). Query: `limit` (1 to 100, default 50) and `cursor`. It answers 200 with `{ "members": [{ "userId", "joinedAt" }], "nextCursor": string | null }`, ordered by `joinedAt` and then `userId`, every row once across pages. Names, status and presence come from the people list the client already holds (TOKI-031); this route returns no name, so it reads no other module's table.

Edit
- R9. `PATCH /api/v1/channels/{id}` takes `{ "topic"?: string | null, "description"?: string | null }` with at least one of the two, and no other key: a body with `name`, `isPrivate`, `kind` or any other key is 400 `validation_failed` and changes nothing (D-105, D-040, AC-050). A text is trimmed of white space at both ends and an empty result is stored as null (TOKI-028 R6). The topic follows R4. The description has no length limit here (concern 6). The change is made by `canEditChannelDetails(actor, conv)`, a function added to `packages/shared/src/permissions/` by this ticket: allowed for a member of a `public_channel` or `private_channel` that is not archived, of either role (D-041, D-105); a non-member `not_a_member`, a DM `not_a_channel`, an archived channel `channel_archived`, and the order of TOKI-027 R3. It adds entry 19 to the matrix test of TOKI-027 R14, "Edit a channel's topic and description" (it is in no row of the capability table; D-105, F24). A field that is absent is not touched, so two people changing the topic and the description at the same moment both keep their change; two changes of one field end with the last save (D-121). The answer is 200 with `{ "channel": ChannelDetail, "changed": boolean }`; setting the value that is already stored is 200 with `changed` false. Check: a Member and an Admin who are members edit; a non-member of a public channel gets 403; an archived channel gets 409 (concern 7); a 250-character and a 251-character topic; 250 emoji accepted and 251 refused; an emptied topic is null.

Join, add, leave, remove
- R10. `POST /api/v1/channels/{id}/join` (no body) is allowed by `canJoinChannel` for a public channel that is not archived. It inserts the actor's member row with `ON CONFLICT DO NOTHING`, and answers 200 with `{ "channel": ChannelDetail, "changed": boolean }`; a person who is already a member gets `changed` false. A private channel is 404 (R1: it is rejoined only by being added, D-051); an archived channel 409 `channel_archived`. Joining stores nothing that limits what the person may read afterwards (D-029, D-116).
- R11. `POST /api/v1/channels/{id}/members` takes `{ "userIds": string[] }` with 1 to 200 entries (the workspace has about 200 people, NFR-04) and is allowed by `canAddPeopleToChannel` for a member of either role, in a private channel too (D-090, F22). Every id must be an active account (R4, `invalid_member`, nothing added). People who are already members are skipped. The answer is 200 with `{ "added": string[], "alreadyMembers": string[] }`, ids in the order of the request. A person who left a private channel returns only this way (D-051, BR-23). The new rows are written in one transaction.
- R12. `POST /api/v1/channels/{id}/leave` (no body) is allowed by `canLeaveChannel`: #general is 409 `channel_is_general` (D-034). A person who is not a member of a public channel gets 200 `{ "changed": false, "archived": <the channel's state> }` and nothing is written, so a repeat of a leave, or a leave after Undo, is harmless (D-111); of a private channel 404. For a member, in one transaction with the lock of R15, the member row is deleted and the remaining rows are counted; when none remains and the channel is private, `archived_at` is set to now (D-051). The answer is 200 `{ "changed": true, "archived": boolean }`. Leaving a public channel needs no confirmation and Undo is a second call of `join` within 5 seconds (D-061, D-069; the 5 seconds are the screen's). Leaving an archived channel is allowed (TOKI-027 R9) and archives nothing more. Whether the last member leaving a public channel also archives it is not decided (concern 1): the function that says so, `archivesWhenEmptied(isPrivate)`, is one line in `channels.ts`, written to return true for a private channel only until concern 1 is answered, and the public case has no test until then.
- R13. `DELETE /api/v1/channels/{id}/members/{userId}` is allowed by `canRemovePeopleFromChannel`: an Admin who is a member, not in #general, not archived (D-085, D-047); a Member is 403 `forbidden`. Removing oneself is 409 `self_target`: leaving is its own route, which carries the last-member rule (Decided in this spec). A person who is not a member, or does not exist, answers 200 `{ "changed": false }`; otherwise the row is deleted and the answer is 200 `{ "changed": true }`. The remaining count is at least 1, because the actor stays.

Archive and restore
- R14. `POST /api/v1/channels/{id}/archive` and `/restore` (no body) are allowed by `canArchiveChannel` and `canRestoreChannel`: an Admin who is a member, never #general (D-034, D-085, D-047, F26); a Member is 403 `forbidden`; an Admin who is not a member of a private channel gets 404 and of a public channel 403 `forbidden`. Archive sets `archived_at` to now; restore sets it to null (D-029). Both answer 200 `{ "channel": ChannelDetail, "changed": boolean }`; archiving an archived channel and restoring an active one change nothing and answer `changed` false (the conflict that TOKI-027 R9 leaves to this API; D-111). Members, files and history are kept. Because the function needs membership, an archived channel without an Admin among its members cannot be restored (concern 2).

Safety and structure
- R15. Locks. Every write route of R10 to R14 and R9 starts its transaction with `SELECT ... FROM conversations WHERE id = $1 FOR NO KEY UPDATE`, then reads the facts again and calls the function again; a result that differs from the first is answered by R2. The lock is taken before any member row is read or written. `FOR NO KEY UPDATE` and not `FOR UPDATE`: the foreign key of a member row takes `FOR KEY SHARE` on the conversation row, which `FOR UPDATE` blocks, so a newcomer's `addMemberToGeneral` (TOKI-024 R20) would wait on an unrelated edit and two routes that take locks in a different order could deadlock (the reasoning of TOKI-024 R39); `FOR NO KEY UPDATE` still excludes another writer of the same channel. Check with two real connections: two last members of a private channel leave at the same moment and the channel ends archived, with no member (TOKI-028, Hand-offs); a join and an archive at the same moment end either with the member in an active channel or with the join refused, never with a member added after the archive was read as absent; a leave and an add of the same person; an edit of the topic and an archive; a join, an add and a leave in any channel finish without a deadlock while `addMemberToGeneral` adds a member to #general.
- R16. The seam for effects. Every effective write calls `recordChange(tx, change)` of `modules/conversations/changes.ts` once, inside its transaction, after the write and before the commit. `change` is one of `channel_created`, `member_joined`, `member_left`, `members_added`, `member_removed`, `details_changed`, `channel_archived`, `channel_restored`, each with the actor, the conversation id, the people affected and the time. A request that changes nothing (a repeat, `changed` false) calls it zero times. In this ticket `recordChange` does nothing: the system lines, Activity items, events and push of a change belong to the work that adds them, which edits only this function (concern 4). This ticket allocates no event number and writes no message. Check: a spy counts one call per effective write, none per no-op, and the call is inside the transaction (a rollback after it leaves nothing).
- R17. `packages/shared/src/channels/` exports the Zod schemas of every request and response above, `CHANNEL_BROWSE_PAGE_DEFAULT` (50, D-109), `CHANNEL_BROWSE_PAGE_MAX` (100), `CHANNEL_MEMBERS_ADD_MAX` (200) and the UUIDv7 pattern of `id`; the name and topic limits come from `packages/shared/src/conversations.ts` of TOKI-028 and are not repeated. The routes validate with these schemas. The registry of error codes gains `channel_name_taken` (409), `channel_id_in_use` (409), `channel_archived` (409), `channel_is_general` (409) and `invalid_member` (400); `forbidden`, `not_found`, `validation_failed`, `self_target` and `internal_error` are the codes of TOKI-004 and TOKI-024 and are reused, not added again.
- R18. The `conversations` module exports the route plugin of this work and its types, and adds them to the list of exports that the test of TOKI-028 R18 checks, in the same change, as TOKI-030 does for its routes; no other export is added. The bootstrap call reads the person's conversations with its own read, `listConversationSummaries` of TOKI-031, and not with a read of this work, so channels have one reader for the first load and one for Browse (R6). Check: the export test lists the names of TOKI-028, of the other tickets that add exports, and the plugin.
- R19. The `members` module exports `getAccountsByIds(db, ids)`, returning `{ id, status }` for each id that exists in the workspace; whichever of this ticket and TOKI-024 or TOKI-020 is built first adds it, with nothing else (the way TOKI-022 added its reads). The channel code uses it only to check R4 and R11, and imports no table of that module (TOKI-002 rules 2 and 17).
- R20. No log line of this work holds a channel name, topic, description or a person's id list. The request log holds no query string (TOKI-004 R7), so `search` is not logged.
- R21. This work adds no table, no column and no migration. Every database rule it relies on is in TOKI-028; a failing constraint that a request can reach (`conversations_workspace_id_name_key`, `conversations_general_name_check`) is mapped to `channel_name_taken`, and any other constraint error is a 500. Check: the migration folder is unchanged.

## Design
### API
All routes need a session (R1). Bodies are JSON.

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/channels` | Admin | Create a channel (R3 to R5) |
| GET | `/api/v1/channels` | any | Browse: public channels and your private ones (R6) |
| GET | `/api/v1/channels/{id}` | any, see R7 | Details; summary only for a non-member of a public channel |
| GET | `/api/v1/channels/{id}/members` | members | Member ids and join times, paged (R8) |
| PATCH | `/api/v1/channels/{id}` | members | Edit topic and description (R9) |
| POST | `/api/v1/channels/{id}/join` | any | Join a public channel (R10) |
| POST | `/api/v1/channels/{id}/members` | members | Add people (R11) |
| POST | `/api/v1/channels/{id}/leave` | any | Leave (R12) |
| DELETE | `/api/v1/channels/{id}/members/{userId}` | Admin who is a member | Remove a person (R13) |
| POST | `/api/v1/channels/{id}/archive` | Admin who is a member | Archive (R14) |
| POST | `/api/v1/channels/{id}/restore` | Admin who is a member | Restore (R14) |

Outcomes common to the routes (the error format is TOKI-004's; a client acts on `error.code`, D-131):

| Status | `error.code` | When |
|---|---|---|
| 400 | `validation_failed` | A path, query or body fails its schema (including a body with `name` or `isPrivate` on PATCH) |
| 400 | `invalid_member` | A person to add is unknown or not active |
| 401 | as TOKI-022 | No valid session |
| 403 | `forbidden` | A Member on an Admin route; a non-member of a public channel on a route that needs membership |
| 404 | `not_found` | Unknown id; a DM or group DM id; a private channel of which the person is not a member |
| 409 | `channel_name_taken`, `channel_id_in_use` | Create |
| 409 | `channel_archived`, `channel_is_general`, `self_target` | The conflicts of R2 and R13 |
| 500 | `internal_error` | A server failure, or `fact_missing` or `unknown_role` from a function |

A 409 means the screen was out of date; the client reloads the channel (D-131).

### Decisions in the flow of a request
- Create: the client makes the id (UUIDv7) and sends it, so a double press, a retry after a lost answer and two tabs are the same request and the second changes nothing (D-111). TOKI-028 R2 lets the database make the id when none is given; giving one is allowed and the route checks its shape. No separate table of stored answers is needed, unlike TOKI-024's invitations, because a channel has a natural key, its id.
- Browse and details answer only what a non-member may see (D-116): name, topic, member count. The member list and the description are for members.
- Every change that is a state the person already has (already a member, already archived, same topic) answers 200 with `changed` false, as TOKI-024 does (D-111).
- `DELETE` is used for removing a person because a membership is a resource that exists or does not; the other changes are `POST` actions, as in TOKI-024. The `Origin` rule of TOKI-022 R46 covers `POST` and `DELETE`; `PATCH` needs the same rule, and TOKI-024 concern 13 already asks that it cover every method except `GET`, `HEAD` and `OPTIONS` (concern 12).
- The role the permission functions see is the one the session check read at the start of the request. An Admin demoted while a request of theirs runs finishes that request; the next one is refused (TOKI-024 R26). Unlike TOKI-024's person routes, no invariant of the workspace depends on it, so the account is not locked here (Decided in this spec, concern 13).
- #general: every route that would change its state is refused by the function or the table: leave, archive, restore, remove (409 `channel_is_general`). Topic, description and adding people work in #general like in any channel.

### Hand-offs
- TOKI-037 (messages) reads and writes by `isConversationMember` or `getConversationFacts` and uses `canReadConversation`, `canPostInConversation`. Joining gives the full history because no code here, and no column of the member row, limits history; the test that a joiner reads messages from before the join (TS-080) belongs to TOKI-037, and a test that a non-joiner is refused (TS-083) too.
- TOKI-053 adds the read pointer as a column of `conversation_members`; leaving or removal deletes the row, so the person's unread state goes with it (D-133). The Activity items of that channel for that person are cleared by the Activity work (D-133); no code here touches them.
- TOKI-030 owns every route that creates or reads a DM or a group; TOKI-029 owns no conversation of those kinds. Both write `conversation_members` rows of their own kind: this ticket only channel rows. Both read through the `conversations` module.
- TOKI-031 reads the person's conversations with its own `listConversationSummaries`, omits archived channels and returns `memberIds` null for a channel, and owns the event number (the events table is TOKI-036) and the snapshot rule. A channel's members and an archived channel that a member opens come from this work: `GET /channels/{id}/members` (R8), and Browse, which lists an archived channel with `isMember` true for its members (R6, R7). TOKI-030 refuses no route here and has no channel route; this work answers the id of a DM or group on its routes with 404 `not_found` (R1), which is the "not a channel" refusal TOKI-030 relies on.
- TOKI-098, TOKI-100, TOKI-101, TOKI-034 and TOKI-035 call the routes above; each takes its error texts from `error.code`.

## Testing
- Written test first. Server integration tests with Vitest on the real Postgres, a signed-in Admin and Member made with the helpers of TOKI-019 and TOKI-022, the test clock of TOKI-008. Fake data only.
- Access (R1, R2): for each of the eleven routes, a request without a session is 401; a Member on create, remove, archive and restore is 403 (create: with a valid, an invalid and an empty body); every reason code of R2 reaches its status; a Member and an Admin who are not in a private channel get 404 on every route that names it, never 403; a DM id and a group DM id on every route are 404 (the add-person request of TS-091 included); a permission function stubbed to `fact_missing` gives 500. Each route also has a positive case, so a loader that always refuses fails.
- Create (R3 to R5, R21): Admin creates public and private, with and without `memberIds` and topic; Member refused (TS-074); names of 1, 80 (accepted), 81, empty, `Q&A Team!`, `QA`, `qa team` (refused); `general`; a name used by an archived channel; a repeat; the same id with other content; the two concurrent cases of R5 on two real connections; an unknown and a deactivated member id (`invalid_member`, nothing created); topic of 250 and 251; no constraint error reaches the client.
- Browse and details (R6 to R8): who sees what, with a Member in no private channel, a Member in one, an Admin outside one; archived channels listed with `archived`; paging of 120; `search` cases; `memberCount`; a non-member of a public channel gets the summary only; the member list pages and is refused to a non-member.
- Edit (R9): the cases of R9, both roles; a body with `name` or `isPrivate` or `kind` changes nothing (TS-079); the two-field concurrent edit keeps both; `canEditChannelDetails` unit tests (both roles, every refusal, missing fact, `guest`, frozen arguments) and the matrix entry 19, whose test counts 22 functions.
- Membership (R10 to R13): join public, join twice, join private (404), join archived (409); add by a Member in a public and a private channel; add of an active, an unknown and a deactivated person; add of an existing member; a person who left a private channel cannot join it and returns when added (BR-23); leave public then join again (Undo); leave private; leave twice; leave #general by a Member and an Admin (TS-024); the last member of a private channel leaves: archived, row gone, messages untouched; remove by an Admin member (TS-093), by a Member (TS-094), by an Admin outside the channel (TS-095), in #general, oneself, a non-member.
- Archive and restore (R14): both roles, #general, a non-member Admin, twice, restore of an active channel; members and rows kept; nothing deletes a channel (no route, and the table trigger refuses a delete, TOKI-028 R22).
- Locks (R15): the two-connection cases of R15, with the second connection waiting and the result checked after the first commits, never by sleeping.
- Seam (R16): the spy test of R16.
- Shared (R17): schemas accept and refuse the boundaries; the registry has the five codes and no duplicate.
- Safety (R20): the captured log is searched for a channel name, topic and description sent in the tests.
- Decisions that are still undecided (concerns 1 to 9) have no test until the owner answers; each concern says which requirement changes.

## Data safety
- A private channel's name, topic, description and member list are visible to its members only: browse, details, members and every other route answer 404 to anyone else, with the same body as for an id that does not exist (BR-09, BR-10). The log holds none of them (R20).
- A non-member of a public channel sees name, topic and member count, never a message or the description (D-116).
- The member list holds ids and join times only.

## Open questions from the intent
- Does the rule "archived when the last member leaves" apply to public channels too? Not answered. Carried forward as concern 1.
- Who restores an archived channel in which no Admin is a member? Not answered. Carried forward as concern 2.
- Which channels does the Admin page's "Channels" list show? Not answered. Carried forward as concern 3.
- Which ticket writes the system lines, the Activity items and the live events of a channel change? Not answered. Carried forward as concern 4.
- Which ticket builds the request that saves notification level, mute and star? Not answered. Carried forward as concern 5.
- Is there a limit on the length of a description? Not answered. Carried forward as concern 6.
- Can a deactivated person be added to a channel? Answered: no, an unknown or deactivated id is 400 `invalid_member` (R4, R11). Evidence: People lists and pickers do not list deactivated people (F25, F41); a person who cannot sign in cannot use the channel. See concern 11.

## Areas of concern
1. The last member leaving a public channel. Not decided. D-051 states "if the last member leaves, the channel is archived" inside its answer about private channels, FR-21 and AC-056 say "the channel", flow F23 shows the warning for private channels only and says a public channel can be rejoined any time, and D-184 (Open) says "a private channel". The same question is concern 3 of TOKI-028. R12 builds the private case; the public case waits for the product owner, and it changes one line (`archivesWhenEmptied`) and one test. Proposal only, not a decision: private channels only, because an empty public channel can still be joined by anyone while an archived one could not be restored (concern 2). Owner: Thanh Truong (product owner).
2. Who restores an archived channel in which no Admin is a member. Not decided. R14 follows TOKI-027 R9 (an Admin who is a member), so a private channel archived by its last member leaving, or a channel whose Admin members left, can never be restored; F26 also gives Admins a Restore button in Browse that the rule would refuse. D-184 (Open) asks it and its answer is only a proposal. Proposal only, not a decision: any Admin restores and becomes a member, which changes `canRestoreChannel`, R14 and the tests. Owner: Thanh Truong (product owner); the same as concern 1 of TOKI-027 and concern 10 of TOKI-028.
3. Which channels the Admin page's "Channels" list shows. Not decided. D-183 says "all channels with their member counts"; D-047 and BR-09 say an Admin does not see private channels they are not in, and D-148 never names private channels in analytics. R6 returns public channels and the private ones the person is in, so an Admin sees no other private channel and TOKI-098 can use `GET /channels` unchanged. If the owner wants every private channel listed to Admins, it is a new route with its own rule. Owner: Thanh Truong (product owner), with TOKI-098.
4. Who writes what a change causes: the system lines ("Lan created this channel", "Lan joined", "Lan added Minh", "Lan left the channel", a topic change), the Activity item "Lan added you to #name", the push, the live events that update open screens (including "This channel was just archived") and the numbered events. Not decided: no ticket in the plan owns the writing of system lines (TOKI-042 draws them, TOKI-053 and D-100 say they raise no count) and the tables for messages and events arrive with TOKI-036. This ticket cannot write them, so it gives the seam of R16: one function that the owning work replaces, called inside each transaction so a line or an event and its change commit together. Proposal only, not a decision: TOKI-037 adds the system-message writer, TOKI-038 the events, TOKI-065 the Activity item, each editing `recordChange` only. Owner: Thanh Truong (product owner, for the plan).
5. Who builds the request that saves a person's notification level, mute and star of a channel. Not decided (TOKI-028 concern 2). It is not in this spec's scope or requirements: the plan's description of TOKI-029 does not list it. Proposal only, not a decision: one more route in this ticket, `PATCH /channels/{id}/me`, which would add a requirement here. Owner: Thanh Truong (product owner).
6. The length limit of a description. Not decided (TOKI-028 concern 1). R9 accepts any text up to the request body limit of the server. Proposal only, not a decision: 500 characters, checked here and by a constraint in a later migration. Owner: Thanh Truong (product owner).
7. Which changes an archived channel refuses. Not decided (TOKI-027 concern 3). The log decides only that an archived channel is read-only with a locked composer. The functions refuse a topic or description edit, a join, adding and removing people with `channel_archived`, and allow leaving. `canEditChannelDetails` (R9) is a new case of the same question. Proposal only, not a decision: refuse as the functions do. Owner: Thanh Truong (product owner).
8. Whether notification level, mute and star come back when a person leaves and returns (Undo, rejoin, added again). Not decided (TOKI-028 concern 4). Join and add create a row with the defaults (R10, R11), so nothing comes back; the answer changes these two requirements and the Undo call. Owner: Thanh Truong (product owner).
9. Whether deactivated people count in the member count of Browse and in the last-member rule. Not decided (TOKI-028 concern 9). `memberCount` and R12 count member rows, deactivated people included, because the count cannot read the accounts of another module. Proposal only, not a decision: leave them out of both, which needs a read of the status through the `members` module. Owner: Thanh Truong (product owner).
10. Browse search. Decided in this spec: it matches the channel name only, containing the text, ignoring case, as the prototype's Browse does; the order is by name. The log has no rule for the order of Browse or for matching a topic; both are a builder choice and can change without a data change. Owner: Thanh Truong.
11. Technical choices the Blueprint leaves to the builder. Decided in this spec: (a) the client makes the id of a new channel, which is how a repeat of Create is ignored without a table of stored answers (R3, R5); (b) a deactivated or unknown person cannot be added (R4, R11); (c) a private channel of which the person is not a member, and any DM id, is answered 404 before any permission function runs (R1); (d) `DELETE` for removing a person, `PATCH` for the edit, `POST` for the other changes; (e) removing oneself is refused and leaving is its own route (R13); (f) a state already held answers 200 with `changed` false (R9 to R14); (g) the lock is `FOR NO KEY UPDATE` on the conversation row (R15); (h) the member list returns ids and not names (R8); (i) 200 as the largest number of people in one add or one create, from NFR-04 (about 200 people). Owner: Thanh Truong.
12. Changes that other specs need. Decided in this spec: this ticket edits none of them; each is a request to the owner. TOKI-027: `canEditChannelDetails` and matrix entry 19, 22 functions instead of 21 (R9). TOKI-028: the export list of R18 (TOKI-030 adds its own in the same way), the explicit id with UUIDv7 form in R3, and `FOR NO KEY UPDATE` where its Hand-offs say `select ... for update`. TOKI-022 and TOKI-024: the `Origin` rule covers `PATCH` (already asked by TOKI-024 concern 13). TOKI-004 registry: the five codes of R17, with `forbidden` from TOKI-024. The plan: TOKI-029 lists TOKI-027 and TOKI-028 as needs; it also needs TOKI-022 (the session check) and TOKI-024 (the shared error codes, `forbidden`). Owner: Thanh Truong.
13. The role during a request. Decided in this spec: the functions use the role that the session check read at the start of the request; the account is not locked, because no workspace-wide rule such as the last Admin is involved. A demotion takes effect on the next request. Owner: Thanh Truong.
