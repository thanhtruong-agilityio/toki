# Channel API design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/channel-api.md (Thanh Truong)
Ticket: TOKI-029

## Goal
Members and Admins need to work with channels: an Admin creates them, everyone finds and joins public ones, people leave, add each other, edit the topic and description, an Admin who belongs to a channel removes people and archives it, any Admin restores it, and each person saves their own notification level, mute and star. Today the server has the conversation tables and the shared permission functions but no request that uses them. This work adds those requests. It also fixes, on the server, the rules that no screen may be trusted with: only an Admin creates; one name is never used twice; an outsider can neither read a channel nor learn that a private one exists; #general stays; a repeat of a request changes nothing.

## Scope
- In:
  - Twelve routes under `/api/v1` (Design, "API"): create, browse, details, member ids, edit topic and description, join, leave, add people, remove a person, archive, restore, and the request that saves a person's own notification level, mute and star of a conversation (R22).
  - The functions of the `conversations` module behind them, the locks that keep them correct when two requests meet, and the last-member archive of a private channel (D-051).
  - The call of `canEditChannelDetails` for the edit (R9). TOKI-027 R9 defines that function and its matrix entry 19 (22 functions); this ticket writes no permission function and does not change the matrix test, with the one case of `canRestoreChannel` named in R14.
  - The request and response schemas, the limits and the new error codes in `packages/shared`.
  - One read added to the `members` module, `getAccountsByIds` (R19), with its four fields; this ticket builds it and TOKI-030 reuses it (Decided in this spec). The export of the route plugin `channelRoutes` and its registration in `apps/server/src/api/index.ts` (R18), which also adds `channelRoutes` to the export-list test of TOKI-028 R18.
  - This spec edits no other spec. The wording that other specs would need to change is listed as requests in concern 12.
  - The seam where later work attaches the effects of a change (R16).
  - Server integration tests, including tests with two real connections.
- Out (not now):
  - The tables, constraints and the reads `getConversationFacts`, `isConversationMember`, `listMemberIds`, `listConversationIdsOfUser`: TOKI-028. #general and the first Admin: TOKI-020. The member row of #general for a newcomer: TOKI-024 and TOKI-097.
  - Direct messages and group DMs, their routes, their key and the refusal of a guest in them: TOKI-030. Adding or removing a person of a group DM is refused here (R2) and nowhere built. The one request of this work that takes the id of a DM or a group is R22.
  - The bootstrap call and what it returns for DMs, members, unread and the event number: TOKI-031. It has its own read of conversations (R18); this work writes no event (R16).
  - System lines such as "Lan added Minh", Activity items, push, live events and the "This channel was just archived" strip: TOKI-037 (system lines), TOKI-038 (events) and TOKI-065 (Activity items), each through the seam of R16 (concern 4).
  - The client method and the store command that call the request of R22: TOKI-032.
  - Reading messages of a channel and the rule that joining gives the full history in the message list: TOKI-037 (messages); this work stores nothing that limits history (Design, "Hand-offs").
  - Every screen: TOKI-034, TOKI-035, TOKI-098, TOKI-100, TOKI-101.
  - Guests: phase 5. A guest role is refused as `unknown_role` by the functions (TOKI-027 R4).
  - Renaming, switching public and private, and deleting a channel: not built; the tables refuse the change of privacy and any delete (TOKI-028 R8, R22).

## Requirements
Access and order of checks
- R1. Every route needs a valid session (TOKI-022 R24, 401). After it, every route runs these steps in this order: (1) `POST /channels` only: `canCreateChannel(actor)`, which needs no body, so a Member gets 403 `forbidden` whatever the body (D-084, D-090); (2) the schemas of the path, query, body and header (400 `validation_failed`); (3) `getConversationFacts(db, actor.id, id)` of TOKI-028: `null` is 404 `not_found`; a `dm` or `group_dm` is 404 `not_found` for every route of this work except the settings route (R22, which has its own steps), so a DM id is never confirmed and a group DM can neither gain nor lose a person here (D-045); a `private_channel` of which the actor is not a member is 404 `not_found`, before any permission function runs, because TOKI-027 R3 puts `role_not_allowed` before `not_a_member` and a Member who is not in a private channel would otherwise get 403 and so learn that it exists (BR-10, D-051); (4) the permission function of the route; (5) for a write, the locks of R15: the account rows (the actor's and those of the people the request names), read again from the locked rows, then the conversation row; the facts are read again and the function is called again with the locked actor. A locked actor who is deactivated gets 401 `account_deactivated`; one whose role no longer allows the route gets the refusal of the function, 403 `forbidden` (the rule of TOKI-024 R1 step 5 and R39). The actor of steps 1 to 4 is the account of the session; no route compares a role itself (TOKI-027 R16).
- R2. A refusal of a permission function is answered by reason: `role_not_allowed` 403 `forbidden`; `not_a_member` of a public channel 403 `forbidden`; `private_channel` (a member of a private channel who calls `join`) 404 `not_found`; `not_a_member` of a private channel and `not_a_channel` are 404 `not_found` as well, but R1 step 3 has already answered that before a function runs; `channel_is_general` 409 `channel_is_general`; `channel_archived` 409 `channel_archived`; `fact_missing` and `unknown_role` 500 `internal_error` (TOKI-027, "How the server uses them"). The error body is the format of TOKI-004 and holds no channel name, topic or description. Reachable by a real request: `role_not_allowed`, `not_a_member` of a public channel, `private_channel`, `channel_is_general` and `channel_archived`. Not reachable by a real request: `not_a_channel` and `not_a_member` of a private channel (step 3 answers first), `fact_missing` and `unknown_role` (the facts are read by TOKI-028 and in phase 1 `users.role` holds only `member` or `admin`, TOKI-019 R9); those three are driven with a stub or an injected account read. Leave has one exception to this list (R12). Check: a table test drives each reachable reason through a route and checks status and code, and the other reasons through a stub.

Create
- R3. `POST /api/v1/channels` takes `{ "id": string, "name": string, "isPrivate"?: boolean, "topic"?: string | null, "memberIds"?: string[] }` and answers 201 with `{ "channel": ChannelDetail }` (R7). `isPrivate` is false when absent (D-101). The channel is created with `created_by` the actor, `created_at` from the clock of TOKI-008, the workspace of the actor's account (the locked read of R15, which carries `workspaceId`, as TOKI-030 R11 takes it from the caller's account; no import of the `workspace` module), and no description. The actor and every id of `memberIds` get a member row with a null `notification_level`, false mute and false star (TOKI-028 R14), in the same transaction. Check: an Admin creates a public and a private channel; the rows exist; the actor and the chosen people are members; nobody else is.
- R4. Validation of create. `id` is a lower-case UUID of version 7, made by the client; a version-4 id and an upper-case id are 400 `validation_failed`. `name` matches `CHANNEL_NAME_PATTERN` (1 to 80 of `a-z`, `0-9`, `-`; D-040): a name of 80 characters is accepted, one of 81, an empty one and `Q&A Team!`, `QA` and `qa team` are 400 `validation_failed` and the server does not convert them (the conversion of D-127 is the screen's). `topic` is trimmed as in R9: an empty or white-space-only text becomes null and is not an error, and a text is 1 to 250 code points after the trim (`isValidChannelTopic`, D-101). `memberIds` has 0 to 200 entries of the shape of R11 (lower-case UUIDs; an upper-case id is 400 `validation_failed`), repeated ids count once, and the actor's own id is allowed. Every id must be the account of an active person of the actor's workspace; an id with no account, an account of another workspace and a deactivated account all get the same 400 `invalid_member` with no detail, and nothing is created; the check reads the account rows locked by R15 (Decided in this spec, concern 11). The name `general` is 409 `channel_name_taken` before any insert, whether or not #general exists yet, so the check constraint of TOKI-028 R9 is never what the person sees. Check: each case.
- R5. Name uniqueness and repeat (D-115, D-128, D-111). The insert uses `ON CONFLICT DO NOTHING` and so meets the unique name and the primary key without an error. When no row came back the route reads the row of `id`. A request is a repeat only when that row exists, was made by the actor, has the same name and the same privacy (the fields that never change: no rename and fixed privacy, D-105, D-040) and the actor is still a member of it. A repeat answers 200 with the current `ChannelDetail` and creates, adds and records nothing; `topic` and `memberIds` are not compared, because they can change after the first answer (a topic edited, a person who left), so a retry after an edit still gets the answer it lost; a client that sends one id with other `memberIds` gets the channel as it is and nobody is added (it makes one id per press, so this is a client error, not a case to repair). Every other case where a row of `id` exists (another creator, another name or privacy, or the actor no longer a member) is 409 `channel_id_in_use` with no `details`, the same body whatever the channel is, so it confirms only that the id is taken, never what the channel is. If no row has that id, the name belongs to another channel, archived or not, and the answer is 409 `channel_name_taken`. The name of a private channel is told to any Admin who asks for the same name (D-115, D-128; see Data safety). Check: the same body twice gives one channel, one set of member rows, one `recordChange` call (R16) and the second answer is 200; the same id with another name is `channel_id_in_use`; the same id with the same name and other `memberIds` is 200 and adds nobody; the same body after the topic was edited is 200; an Admin who created a private channel, left it, and sends the same body gets 409 `channel_id_in_use` with no channel content, and so does the same call with a changed body; a name used by an archived channel is `channel_name_taken`; with two real connections, two Admins creating `release` at the same moment leave exactly one `release` row, one answer is 201 and the other 409 `channel_name_taken`; two requests with one id and one body at the same moment leave one row and answer 201 and 200.

Browse and details
- R6. `GET /api/v1/channels` takes `search`, `limit` (1 to 100, default 50, D-109) and `cursor` (opaque, from the last answer); a value outside these is 400 `validation_failed`. It answers 200 with `{ "channels": ChannelSummary[], "nextCursor": string | null }`. It lists every public channel, archived ones included, and the private channels of which the actor is a member (F21, prototype: the Browse list holds public channels and the private ones you are in). It never returns a private channel to a non-member. `search` keeps the channels whose name contains the text, ignoring case, as the prototype's search does; the characters `%` and `_` are plain characters, not wildcards. `search` is at most 80 characters (the longest name), longer is 400 `validation_failed`. Order: by name in byte order, which the query states as `ORDER BY name COLLATE "C"` and the cursor (the last name, which is unique in the workspace) compares with the same `COLLATE "C"`, as TOKI-028 R10 does, because with the usual collation of the database `-` and digits sort differently and a page could skip or repeat a channel. Reading every page one after the other gives each channel once. `ChannelSummary` is `{ id, name, topic, isPrivate, isGeneral, archived, memberCount, isMember }`. `memberCount` is the number of members whose account is active: a deactivated person keeps the member row and is not counted (Decided, concern 9). The route reads the member ids of the channels of the page in one statement of this module and their status with one call of the injected `getAccountsByIds` (R19, no lock), so the `conversations` module still reads no table of `members`. Check: a channel of three members of whom one is deactivated has `memberCount` 2 in Browse and in details; a Member sees public channels and only the private channels they are in; an Admin who is not in a private channel does not see it (concern 3); 120 channels in pages of 50; `search` with upper case, with `%` and with `_`.
- R7. `GET /api/v1/channels/{id}` answers 200 with `{ "channel": ChannelResponse }`. For a member `ChannelResponse` is `ChannelDetail`: the summary plus `description` (null or text), `createdBy` (the id of the creator) and `createdAt` (ISO 8601 UTC). For a person who is not a member of a public channel it is the `ChannelSummary` alone, with `isMember` false: name, topic and member count only, and no description, creator or message (D-116, AC-053). A member of an archived channel reads its `ChannelDetail` like any member (F10). A private channel of which the person is not a member is 404 (R1). `memberCount` is counted as in R6 (active people only, concern 9).
- R8. `GET /api/v1/channels/{id}/members` is for members of the channel, an archived one included (R1; a non-member of a public channel gets 403 `forbidden`). Query: `limit` (1 to 100, default 50) and `cursor`. It answers 200 with `{ "members": [{ "userId", "joinedAt" }], "nextCursor": string | null }`, ordered by `joinedAt` and then `userId`, every row once across pages. Names and status come from the people list the client already holds (TOKI-031); presence is not in that list and comes from TOKI-055. This route returns no name, so it reads no other module's table. `limit` goes to 100, so a channel of 200 people (NFR-04) is read in 2 requests and one of 201 in 3; the route has no search by name, so a client that searches the members reads every page.

Edit
- R9. `PATCH /api/v1/channels/{id}` takes `{ "topic"?: string | null, "description"?: string | null }` with at least one of the two, and no other key: a body with `name`, `isPrivate`, `kind` or any other key is 400 `validation_failed` and changes nothing (D-105, D-040, AC-050). A text is trimmed of white space at both ends and an empty result is stored as null (TOKI-028 R6). The topic follows R4. The description is null or 1 to 500 code points after the trim (`isValidChannelDescription`, `CHANNEL_DESCRIPTION_MAX` of `packages/shared`, the limit the check constraint of TOKI-028 R7 holds); a longer one is 400 `validation_failed` (Decided, concern 6). The change is allowed by `canEditChannelDetails(actor, conv)`, which TOKI-027 R9 defines and this ticket only calls: allowed for a member of a `public_channel` or `private_channel` that is not archived, of either role (D-041, D-105); a non-member `not_a_member`, a DM `not_a_channel`, an archived channel `channel_archived`, in the order of TOKI-027 R3. Its matrix entry 19 is in TOKI-027 R14. A field that is absent is not touched, so two people changing the topic and the description at the same moment both keep their change; two changes of one field end with the last save (D-121). The answer is 200 with `{ "channel": ChannelDetail, "changed": boolean }`; setting the value that is already stored is 200 with `changed` false. Check: a Member and an Admin who are members edit; a non-member of a public channel gets 403; an archived channel gets 409 (concern 7); a 250-character and a 251-character topic; a 500-character and a 501-character description; 250 emoji accepted and 251 refused; an emptied topic is null.

Join, add, leave, remove
- R10. `POST /api/v1/channels/{id}/join` is allowed by `canJoinChannel` for a public channel that is not archived. It takes no body, or `{ "settings"?: { "notificationLevel"?, "isMuted"?, "isStarred"? } }` with the values of R22 and no other key. It inserts the actor's member row with `ON CONFLICT DO NOTHING`: with a null level, false mute and false star when no `settings` is given or it is `{}`, and with the given values when it has any (an absent key keeps its default). This is how Undo of a leave gives the person their level, mute and star back: the screen keeps the three values for the 5 seconds and sends them with the join (Decided, concern 8); a join from Browse sends none and gets the defaults. The server does not check the 5 seconds: the values are the person's own and R22 could set them a moment later. When the person is already a member, `settings` is ignored and nothing is written. It answers 200 with `{ "channel": ChannelDetail, "changed": boolean }`; a person who is already a member gets `changed` false. A private channel is 404 (R1: it is rejoined only by being added, D-051); an archived channel 409 `channel_archived`. Joining stores nothing that limits what the person may read afterwards (D-029, D-116). Check: a join with no body gives the defaults; a leave and a join with `settings` `{ notificationLevel: "all", isMuted: true, isStarred: true }` gives a row with those three; a join with `settings` by a person who is already a member changes nothing; a `settings` with an unknown key or a level of `loud` is 400.
- R11. `POST /api/v1/channels/{id}/members` takes `{ "userIds": string[] }` with 1 to 200 entries (the workspace has about 200 people, NFR-04) and is allowed by `canAddPeopleToChannel` for a member of either role, in a private channel too (D-090, F22). `userIds` holds lower-case UUIDs (an upper-case id is 400 `validation_failed`, because TOKI-027 R4 compares ids as they are); an id repeated in the list counts once, at its first place. The two rules run in this order: first every id must be the account of an active person of the actor's workspace (R4, on the rows locked by R15; `invalid_member`, nothing added), whether or not the person is already a member, so a deactivated person who is already a member makes the whole request 400; then the people who are already members are skipped. The answer is 200 with `{ "added": string[], "alreadyMembers": string[] }`, ids in the order of the request after the removal of repeats. A person who left a private channel returns only this way (D-051, BR-23). The new rows are written in one transaction, each with the defaults: a person who is added again does not get the earlier level, mute and star back (concern 8).
- R12. `POST /api/v1/channels/{id}/leave` (no body) is allowed by `canLeaveChannel`: #general is 409 `channel_is_general` (D-034). A person who is not a member of a public channel, #general included, gets 200 `{ "changed": false, "archived": <the channel's state> }` and nothing is written, so a repeat of a leave, or a leave after Undo, is harmless (D-111); this overrides R2 for the reason `not_a_member` of this route only, and it is answered before `channel_is_general` (a person outside #general is not expected, D-034, and there is nothing to leave); of a private channel 404. For a member, in one transaction with the lock of R15, the member row is deleted and the remaining members are counted, leaving out the people whose account is deactivated (concern 9): the remaining ids are read after the lock on the conversation row and their status with the injected `getAccountsByIds` without a lock; when no active member remains and the channel is private, `archived_at` is set to now (D-051) and the rows of the deactivated people stay. The status read takes no lock because a `users` lock after the conversation lock would break the order of R15; a reactivation that commits after the read finds the channel archived, the same result as a reactivation a moment later (Decided in this spec). The answer is 200 `{ "changed": true, "archived": boolean }`. Leaving a public channel needs no confirmation and Undo is a second call of `join` within 5 seconds (D-061, D-069; the 5 seconds are the screen's). Leaving an archived channel is allowed (TOKI-027 R9) and archives nothing more. The last member leaving a public channel does not archive it: it stays active with no member and anyone can join it again (Decided, concern 1). The function that says so, `archivesWhenEmptied(isPrivate)`, is one line in `channels.ts` and returns true for a private channel only. Check: the last member of a public channel leaves and the channel is active with no member row; the last active member of a private channel whose other member is deactivated leaves and the channel is archived with that one row kept.
- R13. `DELETE /api/v1/channels/{id}/members/{userId}` is allowed by `canRemovePeopleFromChannel`: an Admin who is a member, not in #general, not archived (D-085, D-047); a Member is 403 `forbidden`. Removing oneself is 409 `self_target`: leaving is its own route, which carries the last-member rule (Decided in this spec). A person who is not a member, or does not exist, answers 200 `{ "changed": false }`; otherwise the row is deleted and the answer is 200 `{ "changed": true }`. The remaining count is at least 1, because the actor stays.

Archive and restore
- R14. `POST /api/v1/channels/{id}/archive` and `/restore` (no body) are allowed by `canArchiveChannel` and `canRestoreChannel`, never for #general (D-034, D-047, D-090, F26); a Member is 403 `forbidden`. Archive needs an Admin who is a member: an Admin who is not a member of a private channel gets 404 and of a public channel 403 `forbidden`. Restore is allowed for any Admin, a member or not (Decided, concern 2: any Admin restores and becomes its member; TOKI-027 R9 and its matrix row for restore drop the membership condition of `canRestoreChannel`, concern 12; TOKI-027 is not built yet and makes the change in its own spec and build, and if it was built as written, this ticket changes the function and that matrix row in its own pull request). An Admin who is not a member of a private channel still gets 404 from R1 step 3, for restore too, so the rule reaches public channels and the private channels the Admin is in. Archive sets `archived_at` to now; restore sets it to null (D-029), and when the Admin who restores is not a member it inserts their member row with the defaults in the same transaction and calls `recordChange` twice, `channel_restored` then `member_joined` (R16). A restore of a channel that is not archived changes nothing and adds no member row. Both answer 200 `{ "channel": ChannelDetail, "changed": boolean }`; archiving an archived channel and restoring an active one change nothing and answer `changed` false (the conflict that TOKI-027 R9 leaves to this API; D-111). Members, files and history are kept. A private channel that was archived with no Admin among its members stays archived: no Admin outside it can see or restore it (Decided, concern 2). Check: an Admin who is not a member restores an archived public channel: it is active, the Admin is a member with the defaults, and the answer is the `ChannelDetail` with `isMember` true; the same Admin on an archived private channel they are not in gets 404; a restore of an active channel by an Admin who is not a member is `changed` false and leaves no member row; the restore by an Admin who is not a member calls `recordChange` twice, in the order `channel_restored`, `member_joined`, and by a member once.

Safety and structure
- R15. Locks. Every write route of R3 to R5, R9 to R14 and R22 runs in one transaction that takes its locks in the order of TOKI-024 R39 (lock 1 `users` rows, lock 3 the `conversations` row, lock 4 the rows that belong to a conversation): (1) the account rows, read in one statement in id order with `getAccountsByIds(tx, ids, { lock: "share" })`, which is `SELECT ... FROM users WHERE id = ANY($1) ORDER BY id FOR SHARE`. `ids` is the actor and, for Create and for add people, every id of `memberIds` or `userIds`; the other routes lock the actor only. Role and status of the actor come from this read and R1 step 5 follows from it; the `invalid_member` check of R4 and R11 (no row, another workspace, deactivated) is made on these locked rows, so a person who is deactivated while the request waits is refused and a person cannot be deactivated between the check and the insert of the member row. (2) For every route except Create, `SELECT ... FROM conversations WHERE id = $1 FOR NO KEY UPDATE`, then the facts are read again and the function is called again; a result that differs from the first is answered by R2. The two locks come before any member row is read or written (lock 4). `FOR NO KEY UPDATE` and not `FOR UPDATE` on the conversation, as TOKI-024 R39 and TOKI-028 Hand-offs say: the foreign key of a member row takes `FOR KEY SHARE` on the conversation row, which `FOR UPDATE` blocks, so a newcomer's `addMemberToGeneral` (TOKI-024 R20) would wait on an unrelated edit; `FOR NO KEY UPDATE` still excludes another writer of the same channel. `FOR SHARE` on the accounts waits for a demotion or deactivation that holds a row and then reads its result (TOKI-024 R39), so no request acts with a role that was true only before it waited. The person routes of TOKI-024 lock every `users` row of the workspace in id order and take no conversation lock, and this transaction takes its `users` rows in id order in one statement and the conversation row after them, so the two cannot wait on each other in a cycle. Check with two real connections: two last members of a private channel leave at the same moment and the channel ends archived, with no member (TOKI-028, Hand-offs); a join and an archive at the same moment end either with the member in an active channel or with the join refused, never with a member added after the archive was read as absent; a leave and an add of the same person; an edit of the topic and an archive; an Admin whose archive waits on the conversation lock while another request demotes them: the archive is 403 `forbidden`; a Member who is deactivated while their join waits: 401 `account_deactivated`; an add of a person while that person is being deactivated: 400 `invalid_member` and no member row; a join, an add and a leave in any channel finish without a deadlock while `addMemberToGeneral` adds a member to #general.
- R16. The seam for effects. Every effective change calls `recordChange(tx, change)` of `modules/conversations/changes.ts` once for each thing that changed, inside its transaction, after the write and before the commit. `change` is one of `channel_created`, `member_joined`, `member_left`, `members_added`, `member_removed`, `details_changed`, `channel_archived`, `channel_restored`, `settings_changed` (R22), each with the actor, the conversation id, the people affected and the time. Create calls it once, `channel_created`, with the first members as the people affected. A leave that empties a private channel calls it twice, in this order: `member_left`, then `channel_archived` (the work that writes the "This channel was just archived" strip of F26 reads the second one). A restore by an Admin who is not a member calls it twice, `channel_restored` then `member_joined` (R14). A request that changes nothing (a repeat, `changed` false) calls it zero times. In this ticket `recordChange` does nothing: TOKI-037 adds the system lines, TOKI-038 the events and TOKI-065 the Activity item, each editing only this function (Decided, concern 4). This ticket allocates no event number and writes no message. Check: a spy counts one call per effective write, two for the emptying leave and for the restore by an Admin who is not a member, none per no-op, and the calls are inside the transaction (a rollback after them leaves nothing).
- R17. `packages/shared/src/channels/` exports the Zod schemas of every request and response of R3 to R14 and R22, `CHANNEL_BROWSE_PAGE_DEFAULT` (50, D-109), `CHANNEL_BROWSE_PAGE_MAX` (100), `CHANNEL_MEMBERS_ADD_MAX` (200) and the UUIDv7 pattern of `id`; the name, topic and description limits come from `packages/shared/src/conversations.ts` of TOKI-028 and are not repeated. The routes validate with these schemas. The registry of error codes gains `channel_name_taken` (409), `channel_id_in_use` (409), `channel_archived` (409), `channel_is_general` (409) and `invalid_member` (400); `forbidden`, `not_found`, `validation_failed`, `self_target`, `internal_error` and `account_deactivated` are the codes of TOKI-004, TOKI-022 and TOKI-024 and are reused, not added again.
- R18. Module boundaries. The `conversations` module does not import the `members` module, because `members` already imports `conversations` for `addMemberToGeneral` (TOKI-024 R20 step 8, TOKI-020), and a cycle would stop the server at start (the rule of TOKI-030 R16). The route plugin is a function `channelRoutes({ db, clock, getAccountsByIds })`, exported from `modules/conversations/index.ts` and registered in `apps/server/src/api/index.ts`, which imports the `index.ts` of both modules and passes the account read in (TOKI-002 R17 allows this). `clock` is the clock of TOKI-008 (R3, R12, R14). The module's exports are the names of TOKI-028 R18, `channelRoutes`, `directRoutes` (TOKI-030) and the types; `channelRoutes` is added to the list that the test of TOKI-028 R18 checks, in the same change. The bootstrap call reads the person's conversations with its own read, `listConversationSummaries(tx, workspaceId, userId)` of TOKI-031, and not with a read of this work, so channels have one reader for the first load and one for Browse (R6). Check: `pnpm lint` exits 0; the export test lists the names of TOKI-028, of the other tickets that add exports, and the plugin; a test starts the app through `buildApp` with the real `api/index.ts` and finds the twelve routes registered.
- R19. - R22. The route is registered by `channelRoutes` (R18), from `settings.ts`, so `api/index.ts` registers no new plugin. An effective change calls `recordChange` once with `settings_changed`, the actor as the only person affected (R16), so the event work can tell the person's other devices. Check: a member of a public channel, a private channel, a DM and a group each save the three values and read them back from the member row; a non-member of a public channel gets 403; a non-member of a private channel, a non-member of a DM and an unknown id get 404 with the same body; an archived channel and #general are allowed; an empty body, an unknown key and a level of `loud` are 400; saving `mentions` on a channel whose stored level is null answers `changed` false and writes nothing; saving only `isStarred` leaves the level and mute as they were; saving `mentions` and `isStarred` true on a channel whose stored level is null stores the star and leaves the level null; another member's row is unchanged.

## Design
### API
All routes need a session (R1). Bodies are JSON.

| Method | Path | Who | Purpose |
|---|---|---|---|
| POST | `/api/v1/channels` | Admin | Create a channel (R3 to R5) |
| GET | `/api/v1/channels` | any | Browse: public channels and your private ones (R6) |
| GET | `/api/v1/channels/{id}` | any, see R7 | Details; summary only for a non-member of a public channel |
| GET | `/api/v1/channels/{id}/members` | members | Member ids and join times, paged (R8) |
| PATCH | `/api/v1/channels/{id}` | members | Edit topic and description (R9) |
| POST | `/api/v1/channels/{id}/join` | any | Join a public channel (R10) |
| POST | `/api/v1/channels/{id}/members` | members | Add people (R11) |
| POST | `/api/v1/channels/{id}/leave` | any | Leave (R12) |
| DELETE | `/api/v1/channels/{id}/members/{userId}` | Admin who is a member | Remove a person (R13) |
| POST | `/api/v1/channels/{id}/archive` | Admin who is a member | Archive (R14) |
| POST | `/api/v1/channels/{id}/restore` | any Admin; becomes a member | Restore (R14) |
| PATCH | `/api/v1/conversations/{id}/settings` | members, any kind of conversation | Save one's own level, mute and star (R22) |

Outcomes common to the routes (the error format is TOKI-004's; a client acts on `error.code`, D-131):

| Status | `error.code` | When |
|---|---|---|
| 400 | `validation_failed` | A path, query or body fails its schema (including a body with `name` or `isPrivate` on PATCH) |
| 400 | `invalid_member` | A person to add is unknown or not active |
| 401 | as TOKI-022 (`account_deactivated` when the locked actor was deactivated, R1 step 5) | No valid session |
| 403 | `forbidden` | A Member on an Admin route; a non-member of a public channel on a route that needs membership |
| 404 | `not_found` | Unknown id; a DM or group DM id (on the settings route: one the person is not a member of); a private channel of which the person is not a member |
| 409 | `channel_name_taken`, `channel_id_in_use` | Create |
| 409 | `channel_archived`, `channel_is_general`, `self_target` | The conflicts of R2 and R13 |
| 500 | `internal_error` | A server failure, or `fact_missing` or `unknown_role` from a function |

A 409 means the screen was out of date; the client reloads the channel (D-131).

### Decisions in the flow of a request
- Create: the client makes the id (UUIDv7) and sends it, so a double press, a retry after a lost answer and two tabs are the same request and the second changes nothing (D-111). TOKI-028 R2 lets the database make the id when none is given; giving one is allowed and the route checks its shape. No separate table of stored answers is needed, unlike TOKI-024's invitations, because a channel has a natural key, its id.
- Browse and details answer only what a non-member may see (D-116): name, topic, member count. The member list and the description are for members.
- Every change that is a state the person already has (already a member, already archived, same topic) answers 200 with `changed` false, as TOKI-024 does (D-111).
- `DELETE` is used for removing a person because a membership is a resource that exists or does not; the other changes are `POST` actions, as in TOKI-024. The `Origin` rule of TOKI-022 R46 covers `POST` and `DELETE`; `PATCH` needs the same rule, and TOKI-024 concern 13 already asks that it cover every method except `GET`, `HEAD` and `OPTIONS` (concern 12).
- A write route reads the actor again from its locked account row after the lock waits, and calls the permission function again with it, so an Admin who was demoted or deactivated while the request waited is refused (R1 step 5, R15; the contract of TOKI-024 R1 and R39). A read route uses the account of the session check (concern 13).
- The four routes with no body (join, leave, archive, restore) accept a request with no body, an empty body with `Content-Type: application/json`, and `{}`; any other body is 400 `validation_failed`, except the `settings` of a join (R10). Fastify's JSON parser refuses an empty body that carries the JSON type, so `channelRoutes` registers, in its own scope only, a JSON parser that turns an empty body into no body (Decided in this spec; TOKI-022 R46's refusal of other media types is unchanged). A test sends each of the three forms and a body `{"x":1}` to each of the four routes.
- The five reasons of R2 that real requests reach, and the three that need a stub, are listed in R2.
- #general: every route that would change its state is refused by the function or the table: leave, archive, restore, remove (409 `channel_is_general`). Topic, description and adding people work in #general like in any channel.

### Hand-offs
- TOKI-037 (messages) reads and writes by `isConversationMember` or `getConversationFacts` and uses `canReadConversation`, `canPostInConversation`. Joining gives the full history because no code here, and no column of the member row, limits history; the test that a joiner reads messages from before the join (TS-080) belongs to TOKI-037, and a test that a non-joiner is refused (TS-083) too.
- TOKI-053 adds the read pointer as a column of `conversation_members`; leaving or removal deletes the row, so the person's unread state goes with it (D-133). The Activity items of that channel for that person are cleared by the Activity work (D-133); no code here touches them.
- TOKI-030 owns the one route that opens or creates a DM or a group, `POST /api/v1/direct-conversations`; no route reads a direct conversation, it is read through the bootstrap call (TOKI-031). TOKI-029 owns no conversation of those kinds. Both write `conversation_members` rows of their own kind: this ticket only channel rows, with one exception, the settings route of R22, which updates the caller's own row of any kind. Both read through the `conversations` module.
- TOKI-031 reads the person's conversations with its own `listConversationSummaries`, omits archived channels and returns `memberIds` null for a channel, and owns the event number (the events table is TOKI-036) and the snapshot rule. A channel's members and an archived channel that a member opens come from this work: `GET /channels/{id}/members` (R8), and Browse, which lists an archived channel with `isMember` true for its members (R6, R7). TOKI-030 refuses no route here and has no channel route; this work answers the id of a DM or group on its eleven channel routes with 404 `not_found` (R1); the settings route of R22 is the one that accepts such an id, for a member of it, which is the "not a channel" refusal TOKI-030 relies on.
- TOKI-098, TOKI-100, TOKI-101, TOKI-034 and TOKI-035 call the routes above; each takes its error texts from `error.code`.

## Data safety
- A private channel's name, topic, description and member list are visible to its members only: browse, details, members and every other route answer 404 to anyone else, with the same body as for an id that does not exist (BR-09, BR-10). The one accepted exception is Create: an Admin who asks for the name of a private channel is told 409 `channel_name_taken` (D-115, D-128 need it), and one who sends an id that is taken is told 409 `channel_id_in_use`, so the existence of a private channel's name or id can be learned by an Admin who guesses it; the channel's content and members are not. The log holds none of them (R20).
- A non-member of a public channel sees name, topic and member count, never a message or the description (D-116).
- The member list holds ids and join times only.
- Tests use made-up names and generated ids.

13. The role during a request. Decided in this spec: a write route reads the actor again from its locked account row (`FOR SHARE`, R15) and calls the permission function again with it, as TOKI-024 R1 step 5 and R39 do, so a demotion or deactivation that happened while the request waited takes effect for that request: 403 `forbidden` or 401 `account_deactivated`. Reason: a request can wait on the conversation lock for seconds, and the Admin routes (create, remove, archive, restore) must not run as an Admin who no longer is one. The cost is one more row lock per write. A read route uses the account of the session check, which is current at the start of the request. Owner: Thanh Truong.
