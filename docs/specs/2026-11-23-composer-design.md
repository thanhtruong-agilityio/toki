## Goal
The server stores messages and the sync engine sends them, but no screen lets a person write one. This work builds the composer: the field under the message list, with the Send button, Enter to send and Shift+Enter for a new line, no send while an input method is composing a word, a field that grows to 160 px and then scrolls, the counter near the 10,000-character limit, the draft that is kept for each conversation in the browser, the call to the typing indicator, the notice that replaces the composer of a direct message that is read-only, and the places that mentions, formatting, synced drafts, attachments and the thread box will use.

## Requirements
The text
- R1. The rule for the text that is sent. `packages/client-core/src/composer/text.ts` exports `countCodePoints(text)` and `prepareOutgoing(text, options?: { hasFiles?: boolean })`. `countCodePoints` counts with `Array.from(text).length` semantics (a character outside the Basic Multilingual Plane counts 1), without building an array. `prepareOutgoing(text, options)` does three things in this order: it removes every U+0000 and every lone surrogate (a high surrogate not followed by a low one, a low one not preceded by a high one); it trims with `String.prototype.trim`; it counts the result. It returns `{ text, count, problem }` with `text` the result, `count` its code points and `problem` `"empty"` when `count` is 0 and `options.hasFiles` is not true (when `hasFiles` is true an empty text is sendable and `problem` is `null`: a message with files and no text, TOKI-058 R14, TOKI-059), `"too_long"` when `count` is over `MESSAGE_TEXT_MAX` of `@toki/shared` (10,000, D-042, TOKI-036 R22) and `null` otherwise. The package uses no DOM global. The text that is sent is `prepareOutgoing(value, { hasFiles }).text`: the prototype trims before it sends (`sendKey`), and TOKI-037 stores what it receives (concern 3). Check: a table test: 10,000 letters and 10,000 emoji give `null`; 10,001 of each give `too_long`; "   " and a line break and tab give `empty`; a text of only U+00A0 gives `empty`; a text of only U+200B (not white space for `trim`) gives `null` and count 1; " a " gives text "a"; U+0000 inside "a\u0000b" is removed (text "ab"); a lone surrogate in "a\uD800b" is removed; a valid pair is kept and counts 1; a text whose UTF-8 length is over 10,000 bytes but whose code points are 10,000 gives `null`; the text is not changed in its middle (line breaks, double spaces); with `{ hasFiles: true }`, "" and "   " give `null` with text "" and count 0, 10,001 characters still give `too_long`, and " a " still gives "a"; with `{ hasFiles: false }` and with no options every case above is as before. The same table (without `hasFiles`) is run against the strict send-request schema that TOKI-037 R22 exports from `packages/shared`: every text with `problem` `null` is accepted by the schema and every text of `empty` and `too_long` is refused by it, so the two rules cannot drift; the case "U+0000 and lone surrogate" is run on the prepared text only (the schema refuses the raw text, which is why R1 removes them). The `hasFiles` cases are not run against that schema: the empty text with files is accepted by the send schema only once TOKI-058 R14 changes it, and its test is in that ticket.

Keys, button, counter and growth
- R2. Keys. In the field, a `keydown` of `Enter` with no Shift sends (R6) and calls `preventDefault`, so no line break is made, when the prop `enterSends` is true (its default; concern 4 says who passes false). `Shift+Enter` is not handled: the browser makes the line break. When `enterSends` is false, Enter is not handled either and only the Send button sends. A key that is part of an input method composition never sends: the event has `isComposing` true, or `keyCode` 229 (Safari reports the Enter that ends a composition after `compositionend`, with `isComposing` false and `keyCode` 229), or the field is between `compositionstart` and `compositionend`. Such an Enter is left to the input method and nothing else happens: no send, no `preventDefault`. An `Enter` whose text cannot be sent (the prop `problem` of R3, `empty` or `too_long`, or `sendGate.blocked` true, R19) calls `preventDefault` and does nothing else; the text stays as typed (journey F11: "the send button does nothing"). Enter with Ctrl, Alt or Meta is treated like Enter (the prototype does the same). The field has `enterkeyhint="send"` when `enterSends` is true and `"enter"` when it is false (concern 4). Before it acts, the composer offers the event to the key interceptors of R16 and does nothing if one consumes it.
  The composition rule needs state, so it is one small hook and two pure functions exported by `@toki/ui-web` (all three in `packages/ui-web/src/components/Composer/keys.ts`), for reuse by TOKI-045 (through `Composer`) and TOKI-047 R18 (its edit field):
  `isImeEvent(event: { isComposing?: boolean; keyCode?: number }): boolean` is pure: true for `isComposing` true or `keyCode` 229. `useComposition(): { handlers: { onCompositionStart; onCompositionEnd }; isImeKey(event): boolean }` keeps a ref that `compositionstart` sets and `compositionend` clears; `isImeKey(event)` is true when the ref is set or `isImeEvent(event)` is true; the caller spreads `handlers` on its `textarea`. `isSendKey(event: { key: string; shiftKey?: boolean }, ime: boolean): boolean` is pure: true for `Enter` with no Shift when `ime` is false.
  What TOKI-047 must write: `const composition = useComposition();` spread `composition.handlers` on the edit field; in `onKeyDown` call `composition.isImeKey(event)` first and do nothing for Esc and Enter when it is true, then `isSendKey(event, false)` for Enter. `Composer` itself does the same inside. Check: a Testing Library test with `userEvent.keyboard`: Enter sends once and the field is empty; Shift+Enter makes "a\nb" and sends nothing; a `keydown` created with `isComposing: true` sends nothing and is not default-prevented; one created with `keyCode: 229` and `isComposing: false` does the same; `compositionstart`, then Enter, then `compositionend`, then Enter sends only at the last one; Enter on "   " sends nothing and leaves "   "; Enter on 10,001 characters sends nothing; with `enterSends` false Enter makes a line break and sends nothing and the Send button sends; `renderHook(useComposition)` shows `isImeKey` false, true after `compositionstart` and false after `compositionend`, and `isImeEvent` and `isSendKey` as a table test. A browser test in Chromium drives the real input method through the CDP command `Input.imeSetComposition` (composition text "Việt" in the field), presses Enter and finds the field unchanged and no request; then `Input.insertText` commits the word and Enter sends it. The Safari case (composition ended before the Enter `keydown`, `keyCode` 229, `isComposing` false) is proved with a synthetic event only: the browser test runs in Chromium (TOKI-008 R10) and this work does not add a WebKit project; that is the limit of the proof.
- R3. The Send button, and what `Composer` gets from the controller. `Composer` cannot import `@toki/client-core` (R20), so the result of R1 comes in as props, computed by `useComposerController` (R18) from `prepareOutgoing(value)`: `count` (number), `max` (number, `MESSAGE_TEXT_MAX`), `problem` (`null`, `"empty"` or `"too_long"`; the controller computes it with the `hasFiles` of R18, so an empty text with files is `null`), `counterFrom` (number, R4) and `counterText` (the already translated and formatted text of `composer.counter`, for example "9,500 / 10,000"). The Send button is a `Button` of `variant` `primary` with the icon `send` and the visible text of `composer.send.label` in a `span`; its accessible name is the text of `composer.send.name`, which contains the visible text (the prototype: `aria-label="Send message"`). A press calls the prop `onSend()` (R6). The button is `disabled` only when `problem` is `"too_long"` or when a gate of R19 says so (the prototype: "beyond it the send button is locked"); when the field is empty or white space it is not disabled and a press does nothing and leaves the text, as F11 says ("the send button does nothing"). Under 720 px the `span` with the visible text is not drawn (the name stays), as in the prototype (`.sendg .btn span{display:none}`); `Composer` puts the text in that `span` itself, so the rule does not rely on what a caller puts in `children`. Mouse down on the button does not take the focus from the field. Check: tests of `Composer` with the props `problem` `null`, `"empty"` and `"too_long"`: the `disabled` attribute and the number of calls of `onSend`; a test of the controller with the field at 0, 3, 10,000 and 10,001 characters and with only spaces gives `problem` `"empty"`, `null`, `null`, `"too_long"` and `"empty"`; the accessible name equals `composer.send.name` and contains the visible text in English and in Vietnamese; at a narrow width in the browser test the text has no box and the button is 44 px wide and 40 px high (R13).
- R4. The counter. When `count` is at least `counterFrom` the composer draws `p.ccount` in the toolbar row, left of Send, with the text `counterText` it was given; when `problem` is `"too_long"` it also has the class `over` and the colour `var(--danger)`. `COMPOSER_COUNTER_FROM` is one constant exported by `apps/web/src/conversation/useComposerController.ts`, which the controller passes as `counterFrom` (so the thread box gets the same value); its value is concern 1, and the value that this work builds is the proposal there, 9,000. `counterText` is the text of `composer.counter` (`{count} / {max}`, the numbers written with `formatNumber` of `@toki/i18n`). The Send button has `aria-describedby` that names the counter's id (made with `useId`) while it is drawn, and the id of the reason of R19 while the gate is `blocked` and has a `reason`; when both apply the attribute holds the two ids joined by a space, the counter's first, so a person who hears "dimmed" hears why. The counter is not a live region (it would speak at every key). Check: a `Composer` test with `count` 4, then 5, `counterFrom` 5, `max` 10 and `counterText` "5 / 10": the counter appears at 5 and shows that text, has `over` when `problem` is `"too_long"`, and `aria-describedby` equals its id; no `aria-live`; with `sendGate` `{ blocked: true, reason: "Wait" }` and the counter drawn, `aria-describedby` holds the two ids in that order, and with only one of them it holds that one; a controller test gives `counterFrom` 9,000 and the text "9,500 / 10,000" for 9,500 characters; the browser test types 10,001 characters and finds Send disabled and the counter over.
- R5. Growth. The field is a `textarea` with `rows` 1, `min-height` 44 px and `max-height` 160 px, no `maxlength` (a person may paste more than the limit and then sees the counter, R4). After every change of the value (typed, pasted, restored, inserted by a tool, cleared by a send) its height is set to the smaller of its `scrollHeight` and 160 px, by first setting `height: auto`; above 160 px it scrolls inside (`overflow-y:auto`). The prototype's rule is `grow(t)`, line 1196. It is one hook, `useAutoGrow(ref, value, maxPx = 160)`, exported by `@toki/ui-web`, which the edit field of TOKI-047 R18 reuses. Check: a unit test with a stubbed `scrollHeight` of 30, 100, 400 gives heights 44 (the minimum), 100 and 160; the browser test (R13) types 1 to 8 lines and reads the heights of Table A.

Sending
- R6. What a send does. Pressing Send or Enter calls `prepareOutgoing(value, { hasFiles })`, with `hasFiles` from the `files` option of the controller (R18; false when it is not given). When `problem` is not `null`, or `files.blocked` is true, nothing happens (R2, R3, R19). Otherwise, when the controller has a `beforeSend` (R18) it calls `beforeSend(prepared)` and goes on only when that returns `true` (or a promise that settles to `true`); then it calls the `send` function of the controller (R18; for `ConversationComposer` it is `sync.send(conversationId, text)` of TOKI-040 R7) once with `prepared.text`. When that returns an id: the field is emptied, its height is set again (R5), the draft of the conversation is cleared (R9), `typingSender.reset(conversationId)` is called (R8), the focus is on the field (also when Send was pressed with the mouse or the keyboard), and the optional callback `onSent(id)` is called when given. The message list does not need it: TOKI-041 R17 goes to the end by itself when it sees the waiting item, and its page passes none (its Hand-offs, PR 218); `onSent` stays as a hook for another caller and nothing in this work depends on it. When it returns `null` (no signed-in person is held) the text stays in the field. The composer waits for nothing: the pending message is in the list before the request is answered (TOKI-040 R7); it is not blocked while a request is running, so two quick sends make two messages, in the order they were pressed (TOKI-040 R8). Offline it also calls `send`: the engine decides `waiting` (TOKI-040 R10); the composer has no state for it. The text is sent as the person sees it in the field after R1: its line breaks are kept; with `hasFiles` it may be the empty string, and `send` is called with it (the caller of R18 adds the file ids, R19). Check: with a fake `sync` that records calls: one call with the prepared text, after `beforeSend` when one is given (`false` leaves the text, the draft and the typing state as they are and calls `send` zero times; a second press while its promise is pending does not call it again; a promise that settles to `true` after the field was changed sends nothing and leaves the newer text); the id returned empties the field, clears the draft, calls `reset` once and `onSent` when given and leaves `document.activeElement` on the field; `null` leaves the text; two sends in a row call twice, in order; "  a  " sends "a"; with `files` `{ hasFiles: true, blocked: false }` and "  " the send function is called once with "", and with `blocked` true it is not called; the composer calls nothing else of the engine to send (R7 only reads `getMessages` and the store's `refresh`).
- R7. A send that fails with a stale page. After `send`, the connected composer watches the pending items of its conversation in `sync.getMessages(conversationId)`: only items with no `parentId` (the thread box is TOKI-045's, whose panel handles its own refusals, TOKI-045 R19). When an item of `kind` `pending` and `delivery` `failed` appears (or an item that was retried fails again with another `error` object) whose `error` has the `code` `channel_archived` or `conversation_read_only` (409s that a fresh copy changes), the composer asks the store for `refresh()` once for that item and that error (D-131: 409 and 410 get a fresh copy; TOKI-037 "Errors": "a 409 means the screen was out of date"), so the page redraws: a direct message whose other person was deactivated then shows the notice of R11, and an archived channel leaves the list and its page (TOKI-101). A 409 `message_id_in_use` is not in this list: a refresh does not change it and Retry returns the same error, so it is left as "Not sent". When `classifyApiError` of TOKI-032 R8 sorts the error as `no_access` (403, 404: the person left or was removed) the composer calls the `onNoAccess` prop, which `ConversationPage` gives it the way it gives it to the Details panel (TOKI-035 R14, the shared not-found view). Every other error (a `retry`, `wait`, `field`, a timeout) does nothing here: the message shows "Not sent" with Retry and Delete (TOKI-042, D-087) and the text of the person is not touched. The hook is `useSendFailures(conversationId, handlers)` in `apps/web/src/conversation/`; it keeps the ids it handled. Items that are already `failed` when the hook mounts are recorded as seen and ignored: a waiting message restored from the outbox after a reload (TOKI-040 R12) that fails later while the composer is mounted is handled like any other, and one that failed before is left as "Not sent". The hook forgets its ids when the conversation changes. A failure while the composer is not mounted (the person went to another conversation or to another tab) is left as "Not sent" by design: the engine's list shows it, and a Retry made there gets its own answer. Check: a fake `sync` that shows a failed item with a 409 `conversation_read_only` calls `refresh` once, also after a second render, and once more for a new item; `channel_archived` does the same; `message_id_in_use` calls nothing; a 404 calls `onNoAccess` once; a `timeout`, a 500 and a 400 call neither; an item that is already `failed` at mount calls neither; a failed item with a `parentId` calls neither; a window change in another conversation calls neither; a retried item that fails again with a new `ApiError` is handled again.
- R8. The typing sender. The connected composer calls `typingSender.notify(conversationId)` of TOKI-044 R9 for each change of the value that leaves it with at least one character and that comes from the person (a typed character, a paste, a deletion that leaves text, an insertion by a tool of R16); it does not call it for a change that empties the field, for a restored draft (R10) or when the thread reply box is the caller (R18, TOKI-044 concern 3). It calls `typingSender.reset(conversationId)` when a message is sent (R6) and when a change by the person leaves the field empty (a deletion, a cut). The emptying that a send makes is the send's own call: the controller sets the value after a send without running the change path, so a send calls `reset` once, not twice. It adds no timer: the pace of the signal is the sender's (TOKI-044 R8). Check: with a fake sender: typing "ab" calls `notify` twice; clearing the field calls `reset` once and not `notify`; mounting with a stored draft calls neither; a paste of text calls `notify` once; a send calls `reset` once in all (the empty-field path is not run for it); the thread variant (R18) with `typing: null` calls nothing.

Drafts
- R9. The browser draft store. `packages/client-core/src/composer/drafts.ts` exports `createDraftStore({ storage, getUserId })` and the type `DraftStore`: `get(key): string`, `set(key, text): void`, `clear(key): void`, `has(key): boolean` and `subscribe(listener): () => void`. A key is a string; the composer of a conversation uses `conversation:<conversationId>` and the thread box uses `thread:<rootId>` (the key TOKI-045 R19 names). `storage` is `{ read(): string | null; write(value: string): boolean; remove(): void }` (the same shape as the outbox of TOKI-040 R12; the web adapter is R20) and `getUserId` returns the id of the signed-in person or `null`. The stored text is one JSON text for the browser, `{ version: 1, userId, items: { [key]: string } }`, shared by every tab: each `set` and `clear` reads the text, changes only its own key and writes it back, so a draft of another conversation written by another tab is kept; the last write of one key wins. `get`, `set`, `clear` and `has` first compare `getUserId()` with the person the cache was loaded for: when the person changed, the memory is dropped; and when the stored `userId` is not the signed-in person's, the whole stored text is removed and nothing is restored (another person's draft is never shown: the decisions of the product owner of 2026-11-19, TOKI-023 concern 8 and TOKI-099 concern 10, which apply to drafts the pattern of D-132, a waiting message that is dropped when someone else signs in). While `getUserId()` is `null` (nobody is signed in) the store reads and writes nothing and returns "", and it leaves the stored text as it is, so the same person who signs in again finds their drafts (journey F07). A text that is blank (`trim` leaves nothing) is not a draft: `set(key, "   ")` removes the key, and `has` is false for it (FR-38: blank text produces no "Draft" label). A stored text that is not JSON, has another `version` or has a missing or wrongly typed key is removed and ignored. A `write` that returns false (TOKI-018 R9: the browser refused storage) leaves the draft in memory for the life of the page and shows no error. `subscribe` listeners are called once for each `set` or `clear` that changed a value. The text is kept as typed, with no trim and no limit on its length: the limit is applied when it is sent (R1). The cell is shared with the outbox (TOKI-040 R12) and a refused write is silent, so a text of more than `DRAFT_TEXT_MAX` code points (100,000, ten times the limit, a megabyte-sized paste; counted with `countCodePoints`, never with `.length`) is not written to the cell and stays in memory for the life of the page, like a refused write; every smaller text is written whole. `DRAFT_TEXT_MAX` is exported by `@toki/shared` from `packages/shared/src/drafts/limits.ts`, created by this work as the one constant; TOKI-051 adds its schemas beside it and keeps the name and the value, so the browser copy and the server copy cap at the same number (TOKI-051 R2, concern 7). Each change reads, parses, changes and writes the one JSON text once; the check counts the calls of `read` and `write` and asserts no time. A draft holds text only, never files (D-168). Check: tests with a fake storage cell: `set` then `get` returns the text and the cell holds the JSON of the form above; a blank text removes the key; two stores over one cell (two tabs) each keep the key of the other; another person's text is removed and `get` returns ""; `getUserId` returning `null` returns "" and leaves the cell; the same person after a `null` gets their text back; bad JSON, another version and a missing key are removed; a refusing `write` keeps the text readable by `get`; a listener is called once for a change and not for the same text set again; a text of 10,000 characters is written whole; 20 keys of 10,000 characters each make one `read` and one `write` for one change; a text of 100,001 code points is readable by `get` and is not written, and a text of 60,000 emoji (120,000 UTF-16 units, 60,000 code points) is written whole.
- R10. How the composer uses the store. The connected composer is mounted with `key` equal to the conversation id, so a change of conversation makes a new composer. On mount it reads `drafts.get("conversation:" + conversationId)` and puts it in the field as the first value (no `notify`, R8), and sets the height (R5); it does not take the focus (concern 5). On every change of the value it calls `drafts.set(key, value)` at once, with no debounce and no timer, so a text is in the store when the person leaves the conversation, closes the tab or the session ends under them (journey F07 and the decision of the product owner of 2026-11-19, TOKI-099 concern 10: a draft kept in the browser is enough). A send clears the key (R6). The composer of one conversation never reads another conversation's key. While the field is untouched the controller follows the store: it keeps a flag `touched`, false at mount, set true by the first change the person makes (typed, pasted, cut, or inserted by a tool, R16) and by a send; while `touched` is false it subscribes to `drafts.subscribe` and, at each notification, puts `drafts.get(key)` in the field (an empty text when the draft was removed), without `notify`, without calling `drafts.set`, without moving the focus and with the height set again (R5); once `touched` is true nothing from the store changes the field. With the browser store of this work the only notifications come from this page's own `set` and `clear`, which happen after `touched` is true, so the rule changes nothing until TOKI-051 notifies from another device; it is TOKI-051's rule (its R12), built here so that the controller needs no second change, and what two devices should do when both type is TOKI-051 concern 2, which is open. Check: type in conversation `a`, mount `b`, mount `a` again: `a` shows its text and `b` shows none; the store cell holds `conversation:a` after the first key; unmount and mount again as another person (the fake `getUserId` changed): the field is empty and the cell is removed; unmount with a text, `getUserId` goes to `null` and back to the same person, mount: the text is back; a send leaves no key; mounting does not call `notify` and does not focus; the test of R9 types 10,000 characters and reads them whole; with a fake store that notifies: an untouched field shows the text of a notification and the store gets no `set` from it, an emptied key empties an untouched field, a field in which one character was typed keeps its text when the store notifies, and after a send the field keeps its state.

When there is no composer
- R11. A conversation the person cannot write in. In the place of the composer, `ConversationPage` (TOKI-033 R21, TOKI-035) draws: (a) for a direct message (`kind` `dm`) whose other person has `status` `deactivated` in `getPerson`, `p.composer-notice` with `role="status"` and the text of `composer.readOnly.deactivated`, with the margins and border of the composer's box and no field, no button and no toolbar (journeys F25 and F41; TOKI-037 R7 refuses the send with 409). A group direct message is not read-only when one of its members is deactivated (TOKI-030 concern 1). The notice shows again as the person's status changes: it reads `getPerson` from the store, which the live frame `person.updated` changes (TOKI-040 R17). (b) For an archived channel the page of TOKI-101 has no composer and this work adds none: `ArchivedNotice` is what sits there (TOKI-101 R17). (c) For a conversation the person is not a member of, `UnjoinedView` (TOKI-033 R21, TOKI-032) is what the page draws, and it has no composer: `ConversationPage` draws the composer only inside the member page (R20), never in `UnjoinedView`. The composer is drawn for every other conversation of the person (a Guest included: the membership check is the same for every role, F11 and F12 list Guests). ### Why not a debounce or a timer
The draft is written at once and nothing waits. A debounce would lose the last characters when the tab is closed or the session ends, and it would need a timer that a test must fake (TOKI-008 R19); writing 10,000 characters as one small JSON text takes well under a frame.

## Data safety
- The draft text is kept in `localStorage` through the platform (R9) until it is sent or emptied. It stays after a sign-out of the same person, as journey F07 and the decision of 2026-11-19 say, and is removed when another person signs in on that browser (the decisions of the product owner of 2026-11-19, TOKI-023 concern 8 and TOKI-099 concern 10, which apply D-132 to drafts). The stored value holds the person's id, the key (a conversation id) and the text, no name and no address. A shared computer therefore keeps the unsent text of the last person until someone signs in; this is the cost of F07 and is accepted by that decision.
- No composer code logs the text, a draft or an error body. The text of a message is never turned into markup by the composer: it is a `textarea` value.
- The removal of U+0000 and lone surrogates (R1) keeps a text that the server would refuse from ending as an endless "Not sent".

## Areas of concern
1. The counter: when it appears, what it says and how it looks. Not decided. Journey F11 says "a counter appears near the limit; beyond it the send button is locked" and gives no threshold, no wording and no place; the prototype has no counter. Proposal, not a decision: it appears from 9,000 characters (90% of the limit), reads "{count} / {max}" in the toolbar row left of Send, and is red beyond the limit (R4, Table B). The value is one constant, so the answer changes one line and its test. Owner: Thanh Truong (product owner).
2. The Emoji button: which ticket builds it and what it inserts. Not decided. Journey F12 ("Formatting, emoji and mentions", the accepted baseline of D-091) lists the toolbar as "bold, italic, code, emoji, attach, mention", so the button's existence is stated; the plan line of TOKI-049 says only "Text formatting", no ticket owns the button, and what it inserts is open (D-017 keeps 8 fixed emoji and has no full picker; the prototype's button inserts one of the 8 reaction emoji with `insemoji`). Proposal, not a decision: build it after TOKI-046 as a tool in the `emoji` slot (R17) that lists the same 8 emoji and inserts one with `replaceRange`; until it is answered the slot is empty and no button is drawn. Owner: Thanh Truong (product owner).
3. What is sent: trimmed and cleaned text. Decided in this spec (a technical choice): the composer removes U+0000 and lone surrogates and trims leading and trailing white space with `trim`, as the prototype trims; the server stores what it receives (TOKI-037 R4 and concern 9, which leaves "whether the composer trims" to the composer). The limit and the counter apply to the text after this step, so a text of 10,000 characters and a final line break is sendable. Reason: the prototype does it, a message that starts or ends with an empty line is never wanted, and a text with U+0000 or a lone surrogate would be refused by the server and end as an endless "Not sent". Owner: Thanh Truong.
4. Enter on a phone. Not decided. Journey F11 says Enter sends and Shift+Enter makes a new line and says nothing about devices; no decision of the log or of a merged spec gives a rule for touch (D-068 makes 360 px a supported size and D-067 says no feature is desktop-only, which does not answer this). A phone's soft keyboard has no Shift+Enter and a long press on Enter does not make a line break on the usual keyboards, so if Enter sends there, a person on a phone cannot write two lines. Proposal, not a decision: when the pointer is coarse (`matchMedia("(pointer: coarse)")`), Enter makes a line break and only the Send button sends, with `enterkeyhint="enter"`; on a desktop Enter sends as F11 says, with `enterkeyhint="send"`. The build follows this proposal through one prop (`enterSends`, R2), so the answer, either way, changes one line in `ConversationComposer` and its test. Owner: Thanh Truong (product owner).
5. Where a draft lives and the focus on opening. Decided in this spec (the browser part): drafts live in the browser store of R9 with the person's id inside, which is what the product owner decided on 2026-11-19 for TOKI-043 and TOKI-051 (TOKI-023 concern 8, TOKI-099 concern 10), who applied the pattern of D-132; the server copy is TOKI-051. The cap of R9 (a text of more than `DRAFT_TEXT_MAX`, 100,000 code points, stays in memory only; the number is shared with TOKI-051's server copy) is a technical choice of this spec that protects the quota shared with the outbox. The composer does not take the focus when a conversation opens: on a phone it would raise the keyboard over the list, and the prototype uses `keepFocus` only to keep an existing focus. After a send the focus is on the field (F11). Reason: no decision names the focus on opening, and an unrequested keyboard is worse than one more press. Owner: Thanh Truong.
6. The composer under the overlay panel. Decided in this spec, within the decision of the product owner of 2026-11-18 that the layout belongs to this ticket (TOKI-015 concern 5): the composer is not squeezed and does not move; while a panel covers its right part from 720 to 1099 px the composer is `inert`, so no focus or typing goes to a control the person cannot see, and it is as left when the panel closes (R15). Reason: at 720 px the Calm main area is 436 px wide and the panel covers 360 of them, so a composer squeezed into the 76 px that stay visible could not be used, and the panel is a deliberate overlay (D-068, NR2); a covered control that keeps the focus is an accessibility failure, so it is taken out of the focus order, and the text, the width and the draft are kept (R15). The prototype squeezes the chat instead, which the product does not. Owner: Thanh Truong.
7. A send refused because the page is out of date. Decided in this spec: when a send ends with a 409 the composer asks the store for a fresh copy once, and with a 403 or 404 it takes the person to the shared not-found view, as D-131 maps them (R7). The message stays as "Not sent" with Retry and Delete. Reason: TOKI-037 says a 409 means the screen was out of date and the client reloads; only the composer knows that a send was refused, and without it a person of a deactivated peer's DM would see "Not sent" again after each Retry and no notice. The wording of the notice of R11 is a proposal (D-139, Table B). Owner: Thanh Truong.
8. The extension points. Decided in this spec (technical choices): a handle and interceptors on the field, four slots, a registry of six tool ids, one draft interface and one controller, a send gate (R16 to R19), the same toolbar for the composer and the thread box (R17, as the prototype's one `composerHtml` draws it), and one optional `beforeSend` on the controller and one `fieldProps` object on the field for mentions (R16, R18). Reason: mentions need the caret and the keys before send, formatting needs the selection, attachments need a place above the field and a gate on Send, synced drafts need to replace the store without changing the composer, and the thread box needs the same controller with its own key and no typing signal. What this work does not decide is how files travel in the send request (TOKI-058, TOKI-059, TOKI-040) and what the mention is stored as (TOKI-050). Owner: Thanh Truong.
