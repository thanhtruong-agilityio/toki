# Look and scheme in the app design

Date: 2026-11-27 · Status: draft for review
Intent: docs/intents/look-and-scheme-in-the-app.md (Thanh Truong, lead)
Ticket: TOKI-143

## Goal
The decided specs describe Toki with two independent choices, a look (Calm, Focus, Classic) and a colour scheme (light, dark, or the device's), and six supported states (`docs/specs/2026-11-26-look-and-scheme-model-design.md`, and the specs it amended). The prototype draws all six states (the merged prototype of PR #443). The code still has the old model: the attribute `data-eff` (`calm` or `focus`) that carries a layout and a set of colours together. This ticket changes the code to the decided model: the tokens, the function that sets the attributes on the page, the style sheets and screens that name the old attribute, and the tests and e2e helpers that read it. After it, Calm in dark and Focus in light work, Classic exists as a look whose frame the next tickets build, and no code reads `data-eff`.

## Scope
- In: `packages/tokens` (the types, the values of the six states, `getTheme`, the generated `tokens.css`, the tests); `applyAppearance` in `packages/ui-web` and its call in `apps/web/src/main.tsx`; the style sheets and tests of the shell, the conversation list, the toast, the conversation page and the archive notice that name `data-eff`; the controls of the preview page and of the shell fixture; the e2e helpers and specs that set or read the look.
- Out (not now): the Classic sidebar (its rail, column, header and quick links); the Look cards and the scheme control of Preferences; saving the look and the scheme to the account, the copy kept on the device, the first-paint script and the server rule for clients that still send the old value; the colours the Classic sidebar adds on top of the 32 properties (concern 3); the theme colour of the web app manifest (concern 4); reference images of the UI parity check for Classic.

## Requirements
- R1. The types. `@toki/tokens` exports `Look = "calm" | "focus" | "classic"` and `Scheme = "light" | "dark"`, with the lists `looks` (in that order) and `schemes` (`light`, `dark`). `Accent`, `Density`, `accents` and `densities` are as they are. Check: a type test and a value test of the two lists.
- R2. The values. The palettes, the accent values, the radii and the shadows are keyed by look and scheme, in the sizes of the 32 properties of TOKI-009 R10. Calm light and Focus dark keep every value they have today. The four new states are Table A. Check: a test of the 32 values of each of the six states, and of the teal and the three other accents of each.
- R3. `getTheme(look, scheme, accent, density?)` returns the 32 properties of that state. `density` left out is the look's own (`lookDensity`: Calm comfortable, Focus and Classic compact). The old call `getTheme(look, accent, density?)` is removed, so the compiler finds each caller. Check: tests of the calls in the six states, of a chosen density, and of the copy of the shadow layers (a caller that changes its theme does not change the tokens).
- R4. `tokens.css` (generated by `pnpm --filter @toki/tokens generate`) has, in this order: the six blocks `:root[data-look="<look>"][data-scheme="<scheme>"]`, the first of them `:root, :root[data-look="calm"][data-scheme="light"]`; the block `@media (prefers-color-scheme: dark) { :root:not([data-scheme]) { … } }` with the values and `color-scheme: dark` of Calm dark; the eighteen accent blocks `:root[data-look][data-scheme][data-accent]` for indigo, clay and violet; the two density blocks. Each look block declares the 32 properties and `color-scheme`. Check: a test of the order of the blocks and of their selectors; the file is as the generator writes it (the existing test of the generated file).
- R5. The states, 78 in all. Each of the 72 states with `data-look` and `data-scheme` set (3 looks, 2 schemes, 4 accents, 3 densities: comfortable, compact, or none chosen) shows the values that `getTheme` returns for it, for all 32 properties, whatever the device's setting is. Each of the 6 states with none of the attributes `data-look`, `data-scheme`, `data-accent` and `data-density` set (the device set to light or to dark: 2; with `data-density` comfortable or compact and the rest unset: 4) shows Calm in the scheme of the device, with the density chosen. Check: the existing test of the cascade, extended to these 78 states, in the browser engine that the token tests use.
- R6. `applyAppearance({ look, scheme, accent?, density? })` takes `look` (`calm`, `focus` or `classic`) and `scheme` (`light`, `dark` or `device`). It sets `data-look` to the look and `data-scheme` to `light` or `dark`; for `device` it sets the scheme the device has now and follows the device's setting until it is called again or its returned function is called. `accent` and `density` are as today (an unknown accent is teal; an unknown or absent density removes `data-density`). It sets no `data-eff`. A value that is not one of the three looks is `calm`; one that is not one of the three schemes is `device`. Check: the existing tests of the function, for the six states, for the device following a change of its setting, for the returned function, and for the unknown values.
- R7. The default of the app. `apps/web/src/main.tsx` calls `applyAppearance({ look: "calm", scheme: "device" })` before it mounts the app, so a person with nothing saved sees Calm in the scheme of the device, and a page where the call has not run yet shows the same (R4's device block). The call is the one TOKI-078 replaces with the saved values. Check: a test of `main.tsx`'s call, and the test of R5 for the page before the call.
- R8. The style sheets. In `shell.css`, `conversation-list.css`, `Toast.css`, `conversation.css` and `archive.css`, every `[data-eff="calm"]` is `[data-look="calm"]` and every `[data-eff="focus"]` is `:is([data-look="focus"], [data-look="classic"])`, because Classic has the frame of Focus (the shell spec, Table F, and its note). No rule changes anything else: the declarations, the order and the media queries stay. Check: a test that no file of `packages/` or `apps/` outside the specs has the text `data-eff`, and the existing tests of the style sheets (their lists of selectors) hold the new names.
- R9. The colours that a style sheet takes from a look. A rule that picks a colour by look (the toast under Calm, for example) picks it by scheme, not by look, when the reason is the colour. Check: a test of the rules in R8's files that sets `data-scheme` and not `data-look`; the toast keeps the colour it has in Calm light and Focus dark.
- R10. The preview page. Its controls are look (`calm`, `focus`, `classic`), scheme (`light`, `dark`), accent and density, in the address as `?look=`, `?scheme=`, `?accent=` and `?density=`; the defaults are `calm`, `light`, `teal` and the look's own. It sets `data-look`, `data-scheme`, `data-accent` and `data-density` directly (not through the device). The interim rule that Calm is light and Focus is dark is gone. Check: the existing test of the controls, for the new parameters and the defaults, and the preview e2e spec (it reads the new attributes).
- R11. The shell fixture. `apps/web/scripts/shell-fixture` takes `?look=calm|focus|classic` and `?scheme=light|dark|device` (the shell spec R32); with none, Calm and `device`. Check: the existing test of the fixture's entry, for the two parameters.
- R12. The e2e helpers. `e2e/support/tokens.ts` reads the property names from the block `:root, :root[data-look="calm"][data-scheme="light"]`; `e2e/support/sign-in.ts` has `setLook(page, look, scheme)` that sets the device's scheme to `scheme` and leaves the look to the app (Calm, until TOKI-078); the specs that read `data-eff` read `data-look` and `data-scheme`. Check: the tests of these helpers, and `pnpm test:e2e` for the specs that use them.
- R13. The UI parity check. The screens' declaration has `look` and `scheme` (the parity spec R2); the screens keep Calm light and Focus dark, and the check of the token values (`e2e/parity/tokens.spec.ts`) compares the 32 properties of the app with the prototype's in all six states and the four accents. Check: that spec passes, with a difference reported as it is today.
- R14. No other behaviour changes. Calm light and Focus dark look as they did before this change: a screen in these two states has the same computed styles as before. Check: the screenshot tests that exist (the preview and the parity check) show no new difference for these two states.

## Design
### Table A: the four new states
The values are those of the prototype as merged (PR #443); the palette of a look and a scheme is the 32 properties.

| State | Colours | Shadows |
| :---- | :---- | :---- |
| Calm dark | The palette of Focus dark, with `bg` `#0B0F10`, `surface2` `#1B2125`, `line` `#263035` | `shadow` `0px 1px 2px 0px rgba(0,0,0,0.4), 0px 8px 24px 0px rgba(0,0,0,0.3)`; `pop` as Focus dark |
| Focus light | The palette of Calm light, with `bg` `#EEF1EC`, `surface2` `#F4F6F2`, `line` `#DDE3DC` | `shadow` none; `pop` `0px 0px 0px 1px #DDE3DC, 0px 16px 40px 0px rgba(22,32,29,0.16)` |
| Classic light | The same as Focus light | The same as Focus light |
| Classic dark | The same as Focus dark | The same as Focus dark |

Sizes, radii, avatar tints and the density of a look do not depend on the scheme: Calm has the values of Calm today (radius 16 and 10, avatar 36, gap 14, row 36, tints 45, 88, 55, 28), and Focus and Classic have those of Focus (radius 10 and 8, avatar 30, gap 8, row 32, tints 35, 24, 70, 86). The accent values of a light state are Calm's today and those of a dark state are Focus's today (teal, indigo, clay, violet), for all three looks.

### The tokens
- `tokens.ts`: `palettes[look][scheme]`, `accentColors[look][scheme][accent]`, `shadows[look][scheme]`; `radii[look]`; `lookDensity[look]`. The values of Calm light and Focus dark are moved, not retyped, so a diff shows the move.
- `theme.ts`: `getTheme(look, scheme, accent, density?)`.
- `css.ts`: `toCss()` writes the blocks of R4 from the objects; it is the only writer of `tokens.css`.
- `index.ts` exports the new types and lists.

### The page
- `appearance.ts`: `Look = "calm" | "focus" | "classic"`, `Scheme = "light" | "dark" | "device"`; it sets the attributes of R6. It holds no text and reads no account.
- The reader of the device's setting is the one it already has (`matchMedia("(prefers-color-scheme: dark)")`), and its listener is removed by the returned function.

### Layout
```
packages/tokens/src/{tokens,theme,css,index}.ts, tokens.css, tests/tokens.test.ts
packages/ui-web/src/appearance.ts, layout/shell.css, conversation-list/…css, components/Toast/Toast.css
apps/web/src/main.tsx, preview/controls.ts, conversation/conversation.css, channel-archive/archive.css
apps/web/scripts/shell-fixture/main.tsx
e2e/support/{tokens,sign-in}.ts, e2e/parity/{screens…,tokens.spec}.ts, e2e/component-preview.spec.ts
```

## Testing
- Written first, each seen to fail for the right reason: the tokens tests (R1 to R5), then the tests of `applyAppearance` (R6, R7), then the selector tests of the style sheets (R8, R9), then the preview and fixture tests (R10, R11).
- The token test of the cascade runs in the browser engine the tokens already use, over the 78 states of R5.
- No new library, no network: the tests use fake data and the generated file.
- Before the pull request: `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm test:e2e` and `pnpm test:e2e:parity` (the last needs Docker) run, and their results are in the pull request.

## Data safety
- Nothing here stores or sends anything: the look and the scheme are attributes on the page. The account, the copy on the device and the server are out of scope.

## How each constraint in the intent is met
| Constraint | Met by |
| :---- | :---- |
| The model spec decided the attribute names, the six states, the default and the 78 states; the code follows it | R3 to R7 use its names and numbers; the design adds no value to the model |
| The values of the four new states come from the prototype; none is invented | Table A, taken from the merged prototype; R13 compares the app with the prototype in all six states |
| Calm light and Focus dark keep today's values; the narrow layout keeps its rules | R2 and R14; R8 changes only the selector, not a declaration |
| The UI parity check keeps working | R13 |
| The package that holds the tokens has no dependency on the UI packages | The design changes only files in `packages/tokens/src`, which imports nothing from `packages/ui-web` (the existing check of the package's dependencies stays) |

## Open questions from the intent
- What does `getTheme` return for Classic? Classic has the palette, the shadows, the radii and the density of Focus in the same scheme (Table A; the prototype draws the page of Classic with Focus's colours and adds the sidebar's own).
- Which tickets build the saved copy on the device and the first-paint script, and does this ticket have to put the default on the page before they exist? The saved copy and the first-paint script are the work of the Preferences ticket (TOKI-078 R8) and the web app ticket; this ticket puts the default on the page with the call of R7 and the device block of R4.
- The prototype draws extra colours for the Classic sidebar (`--side-*`): does the app carry them as properties of the Classic states, or does the ticket that draws the sidebar decide? Answered in concern 3: the ticket that builds the sidebar decides; this ticket adds none.
- The web app manifest's theme colour (`#0E1214`) was a Focus value: is it Calm dark's value now? Answered in concern 4: this ticket does not change it, the pwa ticket confirms the value.

## Areas of concern
1. The size of the change. It touches the tokens, a function, five style sheets, two controls and the e2e helpers, and it is not done in pieces because a half-renamed attribute would show the wrong colours. Decided: one ticket, in the order of R1 to R13, with a commit for each step. Owner: Thanh Truong.
2. The four new states are drawn by this run's prototype and the owner has not confirmed them one by one (the prototype pull request called them proposals). Accepted: the values of Table A are used as merged; a change of a value later is a change of the prototype, then of the tokens, with the test of R13 as the check. Owner: Thanh Truong.
3. Whether the colours the Classic sidebar adds (`--side-rail`, `--side-bg`, `--side-ink`, `--side-muted`, `--side-line`, `--side-hover`) are new custom properties of the tokens (which would make them more than 32) or belong to the style sheet of the sidebar. Not decided. The proposal is that the ticket that builds the sidebar decides, since only it uses them, and that this ticket adds none. Decided: the ticket that builds the Classic sidebar decides, and the tokens keep the 32 properties here. Decided by Thanh Truong (lead, as product owner) on 2026-11-27. Owner: Thanh Truong.
4. The theme colour of the web app manifest and the `theme-color` meta tag. They are one value and cannot follow the look or the scheme of a person; the pwa spec's value `#0E1214` is Focus dark's page colour and also Classic dark's. Not decided. The proposal is that this ticket changes none and the pwa ticket confirms the value. Decided: this ticket changes none, and the pwa ticket confirms the value. Decided by Thanh Truong (lead, as product owner) on 2026-11-27. Owner: Thanh Truong.
5. The parity check draws Classic only in the value check (R13), because the app has no Classic frame yet. Accepted: the screens of Classic are added by the tickets that build the sidebar, as the model spec's R11 says. Owner: Thanh Truong.
