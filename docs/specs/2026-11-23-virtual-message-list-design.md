# Virtualised message list design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/virtual-message-list.md (Thanh Truong)
Ticket: TOKI-041
Needs: TOKI-040 (the sync engine and its "Contract for the screens", as revised in its open pull request 211) and TOKI-101 (merged: `ArchivedHistory`); TOKI-033 and TOKI-035 (merged: `ConversationPage`, the shell slots, the header); TOKI-044 (typing line: see R22 for the build order). The page-level wiring of TOKI-045 (`renderFooter`) and TOKI-047 (`isHidden`) is by build order (R3, R5, R21), not by `needs`.

## Goal
After the sync engine the client holds the messages of each conversation, but nothing draws them: `ConversationPage` has a header and a Details panel, and an archived channel has an empty place called `ArchivedHistory`. This work builds the message list: a virtual list that draws only the rows near the screen so that 10,000 messages scroll at 60 frames per second (D-113), that opens at the latest message, at the New divider or at a given message, stays at the bottom while the person is there, holds the reading position when older messages load, shows a button with the number of new messages when the person has scrolled up, and goes to the end after the person sends. It also draws the day dividers, the New divider, the typing line, the tab row under the header and the readable history of an archived channel, and it fixes the contract that the message component (TOKI-042) will fill. The plan leaves the choice of the virtualisation library open: this spec makes it (R1).

## Scope
- In:
  - The library choice and its single point of use (R1, R2).
  - The place of the list in the conversation page and in the archived page, and the tab row with its one tab (R3, R4).
  - The row model: which rows exist and in what order, the messages that leave no row, the day dividers, the grouping, the New divider, the identity and the cost of rows (R5 to R9).
  - Loading: what the list asks of the engine and when, the states of a first load, failures, the loading of older and newer messages, a stale window (R10 to R13).
  - Scrolling: where the list opens, staying at the bottom, holding the position, the send, the new-messages button, the report of "at the bottom", what is kept mounted (R14 to R20).
  - The contract with the message component, the typing line, the texts and the accessibility of the list (R21 to R24).
- Out (not now), each with its owner:
  - What a message looks like (avatar, name, time, hover, send states, system lines, files): TOKI-042. This work gives it a stand-in and a contract (R21). The day dividers and the grouping are decided here, because only the list sees a message's neighbours and which of them are drawn (R5 to R7, concern 3); TOKI-042 draws what the row says and does no grouping of its own.
  - The composer, its limit and draft: TOKI-043. The page keeps room for it below the list (R3).
  - Which message is the first unread, when the New divider is set and when it is cleared, the unread counts and the read pointer: TOKI-053 and TOKI-054. This work draws the divider before the message whose id it is given as `newFromId`, for as long as it is given, and opens at it when `openAt` says so (R8, R14), and reports whether the person is at the bottom (R19).
  - The message action bar, the More menu, copy: TOKI-052. Threads, reactions, edits, deletes and pins: TOKI-045 to TOKI-048, which add keys to the message and their own parts of a row.
  - Jump to a message from Activity, Later or search, and the flash of the target: TOKI-068. This work opens at a message it is given (R14).
  - The mention rule and the `@` of the button: TOKI-050 gives the list the way to tell (R18); the tint of a mention in the row is painted by TOKI-042 (its R16).
  - The strip "Offline: showing saved messages", loading skeletons and the shared page for a failed first load: TOKI-082 (R10, R11 build plain stand-ins).
  - The engine, the cache, the order of messages and the optimistic send: TOKI-040. The history routes and the page size: TOKI-037. The frame rate and speed targets as measured with 1 million messages and 200 people: TOKI-089.
  - Search in a conversation and the browser's find-in-page: a virtual list does not hold the rows that are far from the screen, so the browser's own find cannot find them (Known limits).

The rows
- R5. The row model. `buildRows(items, options, previous?)` in `rows.ts` is a pure function from the `items` of the engine's `MessageWindow` (TOKI-040 R3) to an array of rows. First it drops the items that leave no row: the `message` items for which `options.isHidden(item.message)` is true (the list's one rule for a deleted message, below); a waiting item is never passed to it. Then, over the items that remain (the drawn items), in this order: (1) a row `retry-older` when R12 says so; (2) for each drawn item in order, a row `day` when its day is later than the running day (R6), then a row `new` when the item is the first drawn item at or after the message of `options.newFromId` (R8), then the row `item` for the item, with `grouped` (R7); (3) a row `typing` when `options.typingLabel` is not empty and the window's `hasNewer` is false (R22); (4) a row `retry-newer` when R12 says so. Every row has a `key`: the item's `id` for an `item` row (the same for a waiting item and for the message that confirms it, so React keeps the element and its measured height when the server confirms a message, TOKI-040 R9), `day:<YYYY-MM-DD>` for a day, `new`, `typing`, `retry-older`, `retry-newer`. Keys are unique in one result: the running day of R6 only grows, so no `day` key repeats. `options` is `{ timeZone, newFromId, typingLabel, olderFailed, newerFailed, hasNewer, isHidden, readTime }`; `readTime(item)` gives the time in milliseconds of R6 (the default reads `Date.parse(message.createdAt)` or `localTime`; the tests give a counting one).
  The rule for a hidden message. A hidden item has no row, no `day` row of its own, is never the neighbour of another item for the day or for the grouping (R6, R7), and never anchors the New divider (R8). The list does not know what a reply count is: `isHidden` is a prop of `MessageList` (R3), a pure function `(message: MessageEntry) => boolean` (the form of TOKI-047 R20), which TOKI-047 supplies as its `isHiddenMessage`, that is `deletedDisplay(message, message.replyCount) === "hidden"` of its R20, that is, a message deleted by its author that has no replies (F16, D-049). A message deleted by its author that has replies, and every message deleted by an Admin, is not hidden: it is a drawn item with a row, which TOKI-042's component draws as the grey line (F42, D-049). A waiting item is never hidden (the function is not called for it). With no `isHidden` given, nothing is hidden. TOKI-047 wires the prop in `ConversationPage` and in `ArchivedHistory` by the build-order rule of TOKI-040 R21: whichever of the two lands second adds the line and says so in its pull request. The grouping and the day dividers are this list's (R6, R7), computed over the drawn items only, so TOKI-047 R20 now says the same (Plan changes). A reply that arrives under a hidden root makes the root drawn (the count changes); R16 holds the position when it appears above the view. A window whose items are all hidden is drawn as the empty one (R10).
  Check: a table test for the empty window, one message, two days, a new message id in the middle, the first message, an id that is not in the window (no `new` row), a typing label with `hasNewer` true and false, the two failed flags, and the hidden cases: a hidden item between two messages of one author within 5 minutes leaves them grouped; the only message of a day being hidden leaves no `day` row for that day; a hidden first message leaves the next one with its own `day` row; `newFromId` of a hidden message puts `new` before the next drawn item and puts none when no item follows; a window of only hidden items gives no row; a deleted-by-admin item with no replies is drawn; keys are unique and a waiting item and its confirming message have the same key.
- R6. Day dividers. The day of an item is the calendar day of its time in `options.timeZone`: `Date.parse(message.createdAt)` for a confirmed message and `localTime` of TOKI-040 R7 for a waiting one (both through `options.readTime`), read with `zonedParts` of TOKI-094 R9 (`YYYY-MM-DD`). The list keeps a running day, the latest day seen so far over the drawn items. An item whose day is later than the running day starts a `day` row and becomes the running day; an item whose day is the same or earlier takes the running day and gets no row. So a waiting item, which follows the confirmed ones (TOKI-040 R4) but is dated by the device clock, never makes a second divider for a day or one out of order, whatever the skew of the clock; this running day is the day used by R7. Every `day` row is later than the one before it, so its key is unique. The time zone is the browser's (`Intl.DateTimeFormat().resolvedOptions().timeZone`), as TOKI-035 R12 uses until a person's own zone is stored (TOKI-078). `useDateContext` in `deps.ts` is a new small hook of this folder that builds the context of TOKI-094 from the four values that TOKI-035 builds inline: the browser's zone, `clock.now()` of `apps/web/src/clock.ts`, the language and the three words of `common`; it imports nothing from `apps/web/src/admin` or `apps/web/src/account`, which hold their own copies, and a later ticket may move all of them to one shared place. An item whose time is not a finite number, or for which `zonedParts` returns `null`, takes the running day and gets no day row (before any valid time there is no running day and no row). A `day` row is drawn by `DayDivider` in `Dividers.tsx`: the prototype's `.day` (a label between two lines, 12 px, 600, muted) with the text `formatDay(at, ctx)` of TOKI-094 R4, where `ctx` comes from `useDateContext` (the three day words are the existing `common.today`, `common.tomorrow` and `common.yesterday`; any other day is the date with the year only when it differs from the current one, D-073, D-123). The prototype's margins become padding of the row (R20). Check: messages at 23:59 and 00:01 in `Asia/Ho_Chi_Minh` (UTC+7) that are on one UTC day give two day rows; the same instants in `UTC` give one; a row for today, yesterday and an earlier date reads `Today`, `Yesterday` and `Mon 16 Nov` against a `TestClock`; an invalid time gives no row; the label never contains `Invalid`; a confirmed message on day 2 followed by a waiting item whose `localTime` is on day 1 gives one `day` row for day 2 and no second one, with unique keys; day 1, day 2, a waiting item on day 1 and one on day 2 give two `day` rows.
- R7. Grouping. Over the drawn items (R5), an `item` row is `grouped` (the message component draws no avatar and no name) when all hold: the item and the drawn item before it are messages with `kind` `user` and neither has `deletedAt` set (not a waiting item, not a system line, not a deleted line: the prototype never groups a waiting message, and a deleted line has no author), they have the same `authorId`, they are on the same running day (R6), the earlier one is no more than `GROUP_GAP_MS` (5 minutes) before the later one, and no `new` row sits between them. A system line or a deleted line is never grouped and the message after it is not grouped. A hidden item is skipped: the two messages around it are neighbours. The gap is measured between two consecutive messages, not from the first of the run, and exactly 5 minutes groups. This is the reading of journey F09 and F10 ("consecutive messages from one person within 5 minutes", D-091); the log fixes neither the consecutive reading nor the boundary (concern 7), and the break at the New divider departs from the prototype, whose `msgsHtml` keeps the previous message across the divider and resets it only on a new day. Both are decided (concern 7). A message with files is never grouped: the condition "the item is a confirmed message with `message.files.length > 0`" ends a group at that message, whatever the message before it is (the prototype breaks a group at a message with an attachment, `!(m.att||[]).length`); a waiting item has no files. The condition reads the message itself, not the one before it, so a message without files after one with files is grouped as before. A link card never changes grouping: a link preview arrives some seconds after the send (TOKI-061), and a message that lost its grouping then would gain an avatar and a name and move the message after it, so `grouped` reads `files` only and no link card field. This departs from the prototype's `m.att`, which counts cards, and is decided (concern 7). The edit of `rows.ts` for this condition is made by TOKI-062 (its R16), which draws the file cards; it is one condition in the function and it adds a case to the table below. A card or a file that arrives later changes the height of its row, which R20 measures again, and R16 holds the position of the first visible row. Check: a run of three messages 4 minutes apart is grouped from the second on, so is a run whose first and third are 8 minutes apart; a gap of exactly 5 minutes groups and 5 minutes 1 millisecond does not; another author, another day, a waiting item, a system line, a deleted line and a `new` row each end a group; a hidden item between two messages of one author does not end it; two messages of one author within 5 minutes where the second has a file are not grouped, and where the first has a file and the second has none the second is grouped; a message whose link cards turn from none to some after the first build keeps the same `grouped` value, and the row after it keeps its own.
- R8. The New divider. `options.newFromId` is the id of the first unread message, given to the list by the prop `newFromId`, separate from `openAt` (R14). The row `new` is drawn for as long as `newFromId` is given, whether or not `openAt` is, so it outlives `onOpened` and a return to the tab (D-052); it is placed before that message when it is in the window and drawn, after the day row of that message when it has one, as the prototype does (`msgsHtml`); when that message is hidden (R5) it is placed before the next drawn item, and when none follows there is no `new` row. `NewDivider` in `Dividers.tsx` draws it as the prototype does: the look of a day divider with the text `t("messageList.new")`, "New" (the prototype's text). The list does not decide which message is the first unread, when the divider is set, how long it stays, or that it is gone the next time the conversation opens: TOKI-054 (D-052) gives `newFromId` for as long as the conversation is viewed, drops it when a `jump` arrives, and gives none at the next opening of a conversation that was read. When `newFromId` becomes `undefined` while the list is mounted, the divider is drawn no more. Until TOKI-054 gives it, no divider is drawn and the list opens at the bottom, so TS-035 passes when TOKI-054 lands. A divider whose message is not in the window (for example the window was replaced by the latest page) is not drawn. Check: with `newFromId` of a held message a `new` row is before it and the label reads `New`; with an id not held there is none; a re-render with the same `newFromId` keeps one divider; a re-render with `openAt` gone (after `onOpened`) and the same `newFromId` keeps the divider where it was; `newFromId` going from an id to `undefined` removes it; the opening of R14 for this kind.
- R9. Identity and cost. When `buildRows` is given its previous result, a row whose item, `grouped` and neighbouring rows are unchanged is the same object as before (`===`), so a memoised row component does not render again (the engine keeps `item` objects the same when a window is replaced, TOKI-040 R4). One message added at the end changes the result by one `item` row, at most one `day` row and the `typing` row, and no other row; a prepended page changes the rows it adds and the row after them (its `grouped` may change). The function is linear in the number of items. Check: with 10,000 items, adding one at the end gives a result in which at most 3 rows are not `===` to the earlier ones, and adding 50 at the start gives at most 50 plus 3 new rows (counted by comparing the arrays); a counting `readTime` shows 10,000 time reads for the full build and at most 10 for the one-message update. `previous` is the earlier result of `buildRows` with what it kept: for each item (by object) its running day and whether it was hidden, and the `options` it was built with. A row, a day and a hidden flag are reused when the item object, the `isHidden` function and the options that they depend on are the same, so the times of the items that did not change are not read again. When `isHidden` or `timeZone` is another function or value, the whole result is built again.

Loading
- R10. Opening and states of the first load. On the mount of a list for a conversation the list calls `sync.loadLatest(conversationId)`, or, when `openAt` names a message that the held window does not contain (a window that was never loaded contains none), `sync.loadAround(conversationId, messageId)` and not `loadLatest` first (R14; the page of a conversation opened by a jump from another conversation gives this `openAt` at its first render, R4); the engine sends no request for a window that is ready, not stale and at the end (TOKI-040 R6), so a conversation that was open before shows at once (NFR-13: under 100 ms). The list reads the window through `useMessageWindow(conversationId)`, which is `useSyncExternalStore` over `sync.subscribeMessages` and `sync.getMessages` (the same object until a change, TOKI-040 R3). It calls the load once for each mount, also under React's strict mode (a ref holds the id), and never because a window went back to `idle`: a window that is dropped by `conversation.left` (TOKI-040 R14) is not loaded again, since the route moves away (TOKI-033 R21 (c)). While `status` is `idle` or `loading`, the list draws an empty region with `aria-busy="true"` and no text (a stand-in that TOKI-082's skeleton replaces; the wording of a loading text is not in the prototype, D-139). When `status` is `ready`, no drawn item remains (`items` is empty or every item is hidden, R5) and `hasOlder` is false, the list draws `EmptyState` (TOKI-013) with the icon `home`, `t("messageList.start.title", { name })` "This is the start of {name}" and `t("messageList.start.description")` "Say hello." (the prototype's `emptyHtml`, which writes the name without the `#`; Decided in this spec: the name given as `conversationName`, with `#` for a channel as the journey F09 and the prototype's composer placeholder write it). Check: with a fake `sync` the list calls `loadLatest` once for a mount and once more for a second mount, and not twice in strict mode; `status` `loading` shows the busy region and no text; a `ready` empty window shows the two texts; a window dropped to `idle` after being ready makes no call.
- R11. Failures of the first load. When `status` is `failed`, `classifyApiError(error)` (TOKI-032 R8, D-131) decides: `no_access` calls `onNoAccess()` (the page's, TOKI-035 R14) and draws nothing; `unauthenticated` and `ignore` draw nothing; `unreadable` draws `t("messageList.readFailed")` with no Retry (a repeat fails the same way); every other kind draws that text and a `Button` `t("messageList.retry")` that calls `sync.loadLatest` again. The text and the button are a plain stand-in for the shared page and Retry of TOKI-082 (D-126, D-131). A failed `loadAround` (the id is not a row of the main list, for example a reply that was not sent to the channel or an unknown id: the server answers 404 `not_found` as for an unknown conversation, TOKI-037 R11, so the list cannot tell the two apart; a deleted message is a row that `around` answers with 200, TOKI-037 R14, and the list hides it or draws it as a line, R5, R14; an offline failure is the same case) is first answered by one `loadLatest`, and only a failure of that is sorted as above. The engine leaves `status` `ready` with `error` set when it holds messages (TOKI-040 R5), so the list reads the end of its own `loadAround` from `error` as well as from `status` `failed`; after the `loadLatest` it opens at the end (R14 (b)), and a `loadLatest` that fails over a held window is the stale case of R12 (the end row with Retry). Check: each kind of error with a fake window `failed`; Retry calls `loadLatest` once; a `loadAround` that fails with 404 is followed by one `loadLatest` and `onNoAccess` is not called when that succeeds, and is called when it fails with 404; the same with a held `ready` window, where the failure is an `error` and not `status` `failed`.
- R12. Older and newer messages. The list calls `sync.loadOlder(conversationId)` when the scroll offset is within `PREFETCH` of the top of the content and `hasOlder` is true, and `sync.loadNewer(conversationId)` when the offset is within `PREFETCH` of the end and `hasNewer` is true; `PREFETCH` is one viewport height (Decided in this spec: a load that starts a screen early is done before the person arrives, whatever the height of the window). The engine ignores a load that is already running or has nothing to load (TOKI-040 R5), so the list needs no flag of its own. A load that failed leaves `error` set and the messages in place (TOKI-040 R5); the list then starts no load by itself in that direction: it remembers which direction it asked last and draws, at that end, a row `retry-older` or `retry-newer` holding `t("messageList.loadFailed")` and a `Button` `t("messageList.retry")` that calls the load again. The row goes when `error` is null again. A direction in which nothing is asked stays quiet. A window that is `stale` with `error` set (a failed `loadLatest` of R13) has no older or newer direction to remember: the list draws the `retry-newer` row at the end, whose Retry calls `sync.loadLatest`, so a person at the bottom of a stale window is told and can retry. A load makes no visible indicator (the position is held, R16). Check: a fake window with `hasOlder` true calls `loadOlder` when the offset is within one viewport of the top, and not when it is farther; with `hasOlder` false never; the same for the end and `loadNewer`; with `error` set after an older load, no second call is made on further scrolling and the row shows; pressing its Retry calls `loadOlder` once; the same for the end; a `stale` window with `error` set shows the end row and its Retry calls `loadLatest` once.
- R13. A stale window. After a reload of the engine the window is `stale` and takes no event (TOKI-040 R16, R19). The list calls `sync.loadLatest` for a stale window when the person is at the bottom (R19), at once when the window turns stale at the bottom and when the person next reaches the bottom otherwise, and not while the person is reading higher up, so that a latest page that replaces a far window (TOKI-040 R5) does not take the text from under them. A send starts its own `loadLatest` (TOKI-040 R7) and the list follows it (R17). If that load fails, `error` is set and `stale` stays true: the list draws the `retry-newer` row of R12 with its Retry, and calls nothing by itself until the person presses it. Check: with a `stale` window and the person at the bottom one `loadLatest` is called; with the person scrolled up none, and one when they reach the bottom; the messages shown stay while it runs; a failed `loadLatest` of a stale window at the bottom shows the end row with Retry and calls nothing more until Retry, which calls it once.

Scrolling
- R14. Where the list opens. For each mount the list opens at: (a) the row of `openAt.messageId` when `openAt` is given: for the kind `new` (the page gives `openAt` `{ messageId: newFromId, kind: "new" }` when it has a `newFromId`, TOKI-054 R8) that is the `new` row, which R8 draws before that message because `newFromId` is given with it (when `newFromId` is not given there is no `new` row and the list opens at the end), placed at the top of the visible area (Decided in this spec: the unread messages follow it, and when there are too few to fill the screen the browser's end of scroll leaves the divider higher, with older messages above it), for the kind `jump` (TOKI-068) the message, centred; the list sets no `data-target` and draws no flash: the flash is TOKI-068's, and the row reads it from its store (R21); when the message is hidden (R5) the next drawn row is centred and the id matches no row, so nothing flashes; when the message is not in the window (a mount over a conversation that was never loaded included) the list calls `loadAround` (R10), and no `loadLatest` first, and places itself when it is held; (b) otherwise the end of the content: this includes a mount that has `newFromId` and no `openAt` (a return to the Messages tab, R4), which opens at the end with the New divider drawn above and does not repeat the opening at the divider. - R15. Stay at the bottom. While the person is at the bottom (R19) the list keeps the end of the content in view when the content grows for any reason: a message arrives (also a system line), a waiting message becomes a confirmed one with a different height, the typing line appears or goes, a row is measured again (an image loads, a message is edited, a reaction row is added, TOKI-045 to TOKI-048), the window of the list is resized (the composer grows by a line, a panel opens, the window is resized, a keyboard opens). A person who is not at the bottom is not moved by any of these (R16). Check: the fake layout puts a row of 100 px at the end, then makes the last row 300 px, then shrinks the scroller by 80 px: the offset stays at the end each time; the same steps with the offset 500 px above the end change the offset by 0 (apart from R16).
- R16. Hold the position. Whatever changes in the rows above the first visible row, that row stays at the same distance from the top of the visible area: older messages loaded and put before it (R12), a row above it measured at another height, a message above it removed or changed (TOKI-045 to TOKI-048), a day row that appears. The list remembers the first visible row's key and its distance from the top before each change of the rows and, before the browser paints, sets the offset so that the distance is the same (a row is found by its key, which is why a measured height belongs to a key and not to a place). When that key is no longer among the rows (the window was replaced, TOKI-040 R5), the list goes to the end if the new window has `hasNewer` false and stays at the offset otherwise. The scroller sets `overflow-anchor: none`, so that the browser's own anchoring does not act a second time, and `virtual-rows.ts` turns off the library's own correction. `@tanstack/virtual-core` moves the scroll offset by itself when a row above the first visible row is measured at another size: its `shouldAdjustScrollPositionOnItemSizeChange` function (called with the row, the change in size and the virtualiser) is on by default for a row that lies entirely above the view when it is measured again (not while scrolling backward) and for the first measure of a row whose top is above the view. `virtual-rows.ts` sets that property of the virtualiser to a function that returns `false` for every row, so `holdOffset` is the only correction. - R17. After the person sends. A window that had `hasNewer` true is replaced by the latest page that `send` starts (TOKI-040 R7); the list follows that too, and the item stays in view when the confirmed message takes its place (the same key, R5). A scroll that the person makes (wheel, touch, keys, the scroll bar) ends the following; one that the list makes does not. Check: with the offset far above the end a new waiting item moves the offset to the end; a later change of the content keeps it there; a simulated person's scroll up ends it and the next message does not move it; with `hasNewer` true and a window replaced the end is shown.
- R18. The new-messages button. - R19. At the bottom. The list is at the bottom when the window has `hasNewer` false and the distance between the end of the visible area and the end of the content (the typing row included) is at most `AT_BOTTOM_PX` (32 px: a rounding of the browser's scroll must not decide; Decided in this spec). `onAtBottomChange(atBottom)` is called when the value changes, once after the opening of R14 has ended (not at the first measure, which can come before the opening passes have put the list at the New divider), and with `false` when the list unmounts (a tab change, a switch of conversation, leaving the page), so a reader of it never keeps `true` for a list that is gone; TOKI-053 uses it with "the window is in use" for the read rule of D-052 (a conversation is read when it is open, the window is in use and the person is at the bottom), and TOKI-073 uses the same value, passed on by the page, to tell whether the person is looking at the latest messages of the open conversation (no notice is shown for a message that is already in view). - R20. Virtualisation. The rows drawn are those that the library gives for the visible range plus `OVERSCAN_ROWS` (10) on each side, and the row that holds the keyboard focus, which stays mounted when it leaves the range, so a focused control in a message (TOKI-052) is not lost by a scroll (a `rangeExtractor` adds its index). Rows are placed at the offsets the library gives, in one scroller `div` with `role="list"` (R24) and `data-testid="message-list"`, `overflow-y: auto`, `overscroll-behavior: contain` and the prototype's padding (`8px 8px 12px`, `.msgs`, and its safe-area rule on narrow screens) carried over; each row sits in a wrapper that the list owns and the library measures with a `ResizeObserver`, so a row may change its height at any time. The spacing between rows is padding of the wrapper or of the component, never a vertical margin (a margin is outside what is measured): the prototype's margin on `.day` and `.msg` becomes padding. The estimates before measurement are `ESTIMATE_ITEM_PX` and `ESTIMATE_DIVIDER_PX`. The number of rows in the DOM does not grow with the length of the window: 10,000 messages in a viewport of 600 px put at most 60 row wrappers in the DOM. The library's options that jsdom cannot give (the size of the scroller, the scroll offset, the measure of an element, the scroll to an offset) are given by `useVirtualRows` from an optional `layout` argument that only the tests pass, so the real browser functions are the defaults (`test-support.ts` has `createFakeLayout({ viewportHeight, heights })`, which keeps an offset, answers the four calls from a table of heights and records every scroll). Check: with the fake layout and 10,000 items the wrappers in the DOM are at most 60 at the top, the middle and the end; the focused row stays mounted after the offset moves 5,000 px; a wrapper has no vertical margin in the stylesheet (a test reads `message-list.css`); a counting row component renders at most 25 rows for 100 one-row scroll steps (the rows are memoised, R9, R21).

## Design
### Why this library (Decided in this spec, concern 1)
The three candidates were measured for this spec: each bundled with esbuild (minified, React external) and compressed with gzip level 9, with the versions that were current: `@tanstack/react-virtual` 3.14.28 about 11 KB, `react-virtuoso` 4.18.24 about 21 KB, `react-window` 2.5.4 about 6.5 KB. The first-load budget is 200 KB (D-113, TOKI-007), so none is a problem alone; the choice rests on the other three reasons the plan names.
| | `@tanstack/react-virtual` | `react-virtuoso` | `react-window` 2 |
| :---- | :---- | :---- | :---- |
| Dependency size (gzip) | about 11 KB; the app already uses TanStack Query and Router | about 21 KB | about 6.5 KB |
| Tests in jsdom | the size of the scroller, the offset, the measure of an element and the scroll are options of the virtualiser, so a test passes a fake layout and checks every decision of this spec without a browser (R20) | measures inside the library; in our reading a test must mock the library's internals or give it an initial item count, so a scroll decision is proved in the browser | the heights and the scroll are the library's; in our reading a test can set a row height but not drive a scroll |
| Reverse scroll, stick to bottom, a prepend | none built in: the list decides (R14 to R17); stable keys per row (`getItemKey`) keep a measured height with a message when rows are added above | built in (`firstItemIndex`, `followOutput`, `initialTopMostItemIndex`); the rules are the library's, tuned for its own cases | none built in, and the dynamic height cache is kept by row index, so in our reading a prepend shifts every cached height and our code would rebuild it |
| Dynamic row height | measured through a `ResizeObserver` per row, cached by key | automatic | `useDynamicRowHeight`, by index |
The cost of the choice is that the list writes the reverse-scroll rules itself (R14 to R19). That cost buys rules that are ours, written as pure functions in `scroll-rules.ts` and `rows.ts` and tested in jsdom, and a browser test (R25) that proves what only a browser can. The library also corrects the offset by itself when a row above the view changes size; this is turned off so that the list's rule is the only correction (R16). We have not measured how much work the other two libraries would save. In our reading, `react-virtuoso` would remove that work at twice the size and would hide the decisions inside the library, where the position hold could be proved only by the browser; and `react-window` 2, which keeps its height cache by row index, would leave the position over a prepend to our own code and a cache that we would rebuild. These readings were not tested here and the choice does not depend on them: the size, the options that a test can give and the cache by key are the reasons.

### How the list works
```
window (TOKI-040)  ->  buildRows (R5..R9)  ->  virtual-rows.ts  ->  row wrappers  ->  MessageRow / dividers / typing / retry
                                  ^               ^   |
              typing label, newFromId, flags      |   +-- scroll-rules.ts: at bottom, hold, follow, button count (R14..R19)
                                                  +-- layout (real browser, or the fake of R20)
```
- `scroll-rules.ts` holds the decisions as pure functions over plain numbers: `isAtBottom(offset, viewport, total, hasNewer)`, `holdOffset(anchor, newStart)` (the new offset that keeps the first visible row where it was), `placeOffset(kind, rowStart, rowSize, viewport)` (R14), `countNew(counted, messages, me, isMention)` (R18), and `shouldLoad(direction, offset, viewport, flags)` (R12, R13). `virtual-rows.ts` is the one file that imports the library: it creates the virtualiser with the rows, `getItemKey` from the row keys, the `rangeExtractor` of R20 and the offsets, and applies the results of `scroll-rules.ts` in a layout effect, before the browser paints.
- A message that is added at the end while the person is at the bottom is placed by the engine (TOKI-040 R16), `buildRows` gives one more row, and R15 moves the offset by the row's height. A message that arrives while the person is scrolled up changes nothing on screen and raises the count of R18.
- A person who has scrolled up in a window that is not at the end (`hasNewer` true: after opening at the New divider or at a jumped-to message) reads down; `loadNewer` brings the rest (R12). New messages are not placed in such a window (TOKI-040 R16), so there is no count; the button "Latest messages" goes to the end (R18, concern 6).

## Data safety
- The list holds nothing of its own: the messages are the engine's, in memory (TOKI-040 R19), and are dropped by its `reset`. It writes nothing to storage and logs nothing; a message's text is rendered as text by the component (TOKI-042, TOKI-049) and never as markup.
