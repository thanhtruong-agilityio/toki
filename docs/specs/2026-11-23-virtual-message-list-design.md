# Virtualised message list design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/virtual-message-list.md (Thanh Truong)
Ticket: TOKI-041
Needs: TOKI-040 (the sync engine and its "Contract for the screens", as revised in its open pull request) and TOKI-101 (merged: `ArchivedHistory`); TOKI-033 and TOKI-035 (merged: `ConversationPage`, the shell slots, the header); TOKI-044 (typing line: see R22 for the build order).

## Goal
After the sync engine the client holds the messages of each conversation, but nothing draws them: `ConversationPage` has a header and a Details panel, and an archived channel has an empty place called `ArchivedHistory`. This work builds the message list: a virtual list that draws only the rows near the screen so that 10,000 messages scroll at 60 frames per second (D-113), that opens at the latest message, at the New divider or at a given message, stays at the bottom while the person is there, holds the reading position when older messages load, shows a button with the number of new messages when the person has scrolled up, and goes to the end after the person sends. It also draws the day dividers, the New divider, the typing line, the tab row under the header and the readable history of an archived channel, and it fixes the contract that the message component (TOKI-042) will fill. The plan leaves the choice of the virtualisation library open: this spec makes it (R1).

## Scope
- In:
  - The library choice and its single point of use (R1, R2).
  - The place of the list in the conversation page and in the archived page, and the tab row with its one tab (R3, R4).
  - The row model: which rows exist and in what order, the day dividers, the grouping, the New divider, the identity and the cost of rows (R5 to R9).
  - Loading: what the list asks of the engine and when, the states of a first load, failures, the loading of older and newer messages, a stale window (R10 to R13).
  - Scrolling: where the list opens, staying at the bottom, holding the position, the send, the new-messages button, the report of "at the bottom", what is kept mounted (R14 to R20).
  - The contract with the message component, the typing line, the texts and the accessibility of the list (R21 to R24).
- Out (not now), each with its owner:
  - What a message looks like (avatar, name, time, hover, send states, system lines, files): TOKI-042. This work gives it a stand-in and a contract (R21). The day dividers and the grouping are decided here, because only the list sees a message's neighbours (concern 3); TOKI-042 draws what the row says.
  - The composer, its limit and draft: TOKI-043. The page keeps room for it below the list (R3).
  - Which message is the first unread, when the New divider is set and when it is cleared, the unread counts and the read pointer: TOKI-053 and TOKI-054. This work draws the divider and opens at it when it is given the message id (R8, R14), and reports whether the person is at the bottom (R19).
  - The message action bar, the More menu, copy: TOKI-052. Threads, reactions, edits, deletes and pins: TOKI-045 to TOKI-048, which add keys to the message and their own parts of a row.
  - Jump to a message from Activity, Later or search, and the flash of the target: TOKI-068. This work opens at a message it is given (R14).
  - The mention tint and the `@` of the button: TOKI-050 gives the list the way to tell (R18).
  - The strip "Offline: showing saved messages", loading skeletons and the shared page for a failed first load: TOKI-082 (R10, R11 build plain stand-ins).
  - The engine, the cache, the order of messages and the optimistic send: TOKI-040. The history routes and the page size: TOKI-037. The frame rate and speed targets as measured with 1 million messages and 200 people: TOKI-089.
  - Search in a conversation and the browser's find-in-page: a virtual list does not hold the rows that are far from the screen, so the browser's own find cannot find them (Known limits).

## Requirements
Library and structure
- R1. The library is `@tanstack/react-virtual` (Decided in this spec, concern 1). It is added to `apps/web/package.json` only (an exact version of the 3.x line, chosen at build time); `packages/ui-web` and `packages/client-core` do not depend on it. Only one file imports it, `apps/web/src/conversation/message-list/virtual-rows.ts` (R2), so a later change of library changes one file. The bundle size check of TOKI-007 still passes, and the library adds no more than 15 KB gzip to the first-load JavaScript (about 11 KB when measured for this spec, concern 1). Check: a test reads the sources of `apps/web/src` and `packages` and finds the import in one file only; `pnpm build` and the bundle size script pass, and the pull request states the size before and after.
- R2. Layout. `apps/web/src/conversation/message-list/` holds `deps.ts`, `constants.ts`, `rows.ts`, `scroll-rules.ts`, `virtual-rows.ts`, `use-message-window.ts`, `use-typing-label.ts`, `MessageList.tsx`, `MessageRow.tsx` (the stand-in of R21), `Dividers.tsx` (the day and New dividers), `NewMessagesButton.tsx`, `message-list.css`, `index.ts`, `test-support.ts` (a fake layout, R20) and a test file next to each source. `deps.ts` is the only file of the folder that imports `apps/web/src/client.ts`; it exports `sync`, `typing` (when it exists, R22), `useCurrentUserId()` (`useConversationSelector((s) => s.getUser()?.id ?? null)` of TOKI-033 R29), `useDateContext` and `classifyApiError`. The tests of the screens replace `deps.ts` with `vi.mock`, as TOKI-101 R2 does. `constants.ts` holds the numbers named in this spec: `AT_BOTTOM_PX` 32, `GROUP_GAP_MS` 300000, `OVERSCAN_ROWS` 10, `ESTIMATE_ITEM_PX` 64 and `ESTIMATE_DIVIDER_PX` 40 (estimates that measurement replaces; correctness does not depend on them), `PREFETCH` (one viewport height, R12). `index.ts` exports `MessageList`, `MessageListProps`, `buildRows` and the row types. No file other than `deps.ts` imports `@toki/client-core` for a value. Check: the files exist and the names are exported; a test finds an import of `client` outside `deps.ts` and fails on it.
- R3. Placement. `ConversationPage` (TOKI-033 R21, TOKI-035 R10) keeps its file, props and test id, and its body becomes one column: `ConversationHeader`, the tab row (R4), and `MessageList` filling the rest of the height (`flex: 1; min-height: 0`). The page leaves the end of the column free for the composer of TOKI-043, which adds its own element after the list and changes nothing in it (the list copes with a composer that grows, R15). `ArchivedHistory({ channelId })` of TOKI-101 R14 keeps its file, its props and its test id, and its body becomes `<MessageList conversationId={channelId} conversationName={…} archived />`, where `archived` leaves out the typing line (R22); the name is `"#"` plus the detail's name from `getChannelDetail(channelId)`. The archived page's header, notice and `div.arch-body` are TOKI-101's and unchanged; it has no tab row (concern 2, decided). `MessageList` props: `conversationId`, `conversationName` (already worked out, with `#` for a channel), `archived?`, `openAt?` (R14), `onAtBottomChange?` (R19), `onNoAccess?` (R11) and `isMention?` (R18). The list reads `conversationId` once for each mount: the page gives it `key={conversationId}`, so a switch of conversation is a new list (R14). Check: a page test with a fake `deps` finds the header, the tab row and the list in that order in the column; the archived page holds the list in `div.arch-body`, no tab row and no composer element; both keep their test ids; a changed `conversationId` mounts a new list.
- R4. The tab row. `ConversationPage` draws the row under the header with `TabList` and `Tab` (TOKI-015 R13, R14), from the array `conversationTabs` in `apps/web/src/conversation/tabs.ts`. An entry is `{ id, labelKey, Panel }` (the form of `pinnedTab` of TOKI-048 R16), `Panel` being `({ conversationId, onOpenMessage }) => JSX` and `onOpenMessage(messageId)` the function of TOKI-048 R15; the tabs are drawn in the order of the array. This work's array has one entry, `messages` (`labelKey` `conversation.tabs.messages`, "Messages", the prototype's tab; its `Panel` draws `MessageList`). TOKI-048 adds `pinnedTab` after it and the later tickets for Files & links add their entries; they edit the array and nothing else of the page (TOKI-035 concern 7, decided by the product owner: TOKI-041 draws the row, the others add their tabs). The page translates `labelKey` with `t`. `onOpenMessage(messageId)` selects the `messages` tab and gives the list a new `openAt` `{ messageId, kind: "jump" }` (R14). The panel of a tab that is not selected is not mounted, so returning to Messages opens the list again by R14. The selected tab is state of the page, `messages` at every opening of a conversation (the prototype's `openConv` sets it); it is not in the address and Back leaves the conversation, not the tab (concern 2). Check: the row has one tab, selected, named `Messages` in English; an entry added to the array in a test shows a second tab, translated, and its `Panel` when selected; `onOpenMessage("m1")` from that panel selects Messages and the list gets a `jump` to `m1`; a switch of conversation selects `messages` again.

The rows
- R5. The row model. `buildRows(items, options, previous?)` in `rows.ts` is a pure function from the `items` of the engine's `MessageWindow` (TOKI-040 R3) to an array of rows, in this order: (1) a row `retry-older` when R12 says so; (2) for each item in order, a row `day` when the item's day differs from the previous item's day or it is the first item (R6), then a row `new` when the item is the message of `options.newFromId` (R8), then the row `item` for the item, with `grouped` (R7); (3) a row `typing` when `options.typingLabel` is not empty and the window's `hasNewer` is false (R22); (4) a row `retry-newer` when R12 says so. Every row has a `key`: the item's `id` for an `item` row (the same for a waiting item and for the message that confirms it, so React keeps the element and its measured height when the server confirms a message, TOKI-040 R9), `day:<YYYY-MM-DD>` for a day, `new`, `typing`, `retry-older`, `retry-newer`. Keys are unique in one result. `options` is `{ timeZone, newFromId, typingLabel, olderFailed, newerFailed, hasNewer }`. Check: a table test for the empty window, one message, two days, a new message id in the middle, the first message, an id that is not in the window (no `new` row), a typing label with `hasNewer` true and false, the two failed flags; keys are unique and a waiting item and its confirming message have the same key.
- R6. Day dividers. The day of an item is the calendar day of its time in `options.timeZone`: `Date.parse(message.createdAt)` for a confirmed message and `localTime` of TOKI-040 R7 for a waiting one, read with `zonedParts` of TOKI-094 R9 (`YYYY-MM-DD`). The time zone is the browser's (`Intl.DateTimeFormat().resolvedOptions().timeZone`), as TOKI-035 R12 uses until a person's own zone is stored (TOKI-078). An item whose time is not a finite number, or for which `zonedParts` returns `null`, is treated as being on the previous item's day and gets no day row. A `day` row is drawn by `DayDivider` in `Dividers.tsx`: the prototype's `.day` (a label between two lines, 12 px, 600, muted) with the text `formatDay(at, ctx)` of TOKI-094 R4, where `ctx` comes from `useDateContext` (the three day words are the existing `common.today`, `common.tomorrow` and `common.yesterday`; any other day is the date with the year only when it differs from the current one, D-073, D-123). The prototype's margins become padding of the row (R20). Check: messages at 23:59 and 00:01 in `Asia/Ho_Chi_Minh` (UTC+7) that are on one UTC day give two day rows; the same instants in `UTC` give one; a row for today, yesterday and an earlier date reads `Today`, `Yesterday` and `Mon 16 Nov` against a `TestClock`; an invalid time gives no row; the label never contains `Invalid`.
- R7. Grouping. An `item` row is `grouped` (the message component draws no avatar and no name) when all hold: the item and the one before it are messages with `kind` `user` (not a waiting item, not a system line: the prototype never groups a waiting message), they have the same `authorId`, they are on the same day (R6), the earlier one is no more than `GROUP_GAP_MS` (5 minutes) before the later one, and no `new` row sits between them. The gap is measured between two consecutive messages, not from the first of the run (Decided in this spec, concern 3: journey F09 says "consecutive messages from one person within 5 minutes"). A system line is never grouped and the message after it is not grouped. TOKI-058 adds the condition "the message has no files" here (the prototype breaks a group at a message with an attachment). Check: a run of three messages 4 minutes apart is grouped from the second on, so is a run whose first and third are 8 minutes apart; a gap of exactly 5 minutes groups and 5 minutes 1 millisecond does not; another author, another day, a waiting item, a system line and a `new` row each end a group.
- R8. The New divider. `options.newFromId` is the id of the first unread message, given to the list through `openAt` with the kind `new` (R14). The row `new` is placed before that message when it is in the window, after the day row of that message when it has one, as the prototype does (`msgsHtml`). `NewDivider` in `Dividers.tsx` draws it as the prototype does: the look of a day divider with the text `t("messageList.new")`, "New" (the prototype's text). The list does not decide which message is the first unread, when the divider is set, how long it stays, or that it is gone the next time the conversation opens: TOKI-054 (D-052) gives `openAt` at the opening and nothing at the next one. Until TOKI-054 gives it, no divider is drawn and the list opens at the bottom, so TS-035 passes when TOKI-054 lands. A divider whose message is not in the window (for example the window was replaced by the latest page) is not drawn. Check: with `newFromId` of a held message a `new` row is before it and the label reads `New`; with an id not held there is none; a re-render with the same `openAt` keeps one divider; the opening of R14 for this kind.
- R9. Identity and cost. When `buildRows` is given its previous result, a row whose item, `grouped` and neighbouring rows are unchanged is the same object as before (`===`), so a memoised row component does not render again (the engine keeps `item` objects the same when a window is replaced, TOKI-040 R4). One message added at the end changes the result by one `item` row, at most one `day` row and the `typing` row, and no other row; a prepended page changes the rows it adds and the row after them (its `grouped` may change). The function is linear in the number of items. Check: with 10,000 items, adding one at the end gives a result in which at most 3 rows are not `===` to the earlier ones, and adding 50 at the start gives at most 50 plus 3 new rows (counted by comparing the arrays); a counting `getTime` hook shows 10,000 time reads for the full build and at most 10 for the one-message update.

Loading
- R10. Opening and states of the first load. On the mount of a list for a conversation the list calls `sync.loadLatest(conversationId)`, or, when `openAt` names a message that the held window does not contain, `sync.loadAround(conversationId, messageId)` (R14); the engine sends no request for a window that is ready, not stale and at the end (TOKI-040 R6), so a conversation that was open before shows at once (NFR-13: under 100 ms). The list reads the window through `useMessageWindow(conversationId)`, which is `useSyncExternalStore` over `sync.subscribeMessages` and `sync.getMessages` (the same object until a change, TOKI-040 R3). It calls the load once for each mount, also under React's strict mode (a ref holds the id), and never because a window went back to `idle`: a window that is dropped by `conversation.left` (TOKI-040 R14) is not loaded again, since the route moves away (TOKI-033 R21 (c)). While `status` is `idle` or `loading`, the list draws an empty region with `aria-busy="true"` and no text (a stand-in that TOKI-082's skeleton replaces; the wording of a loading text is not in the prototype, D-139). When `status` is `ready`, `items` is empty and `hasOlder` is false, the list draws `EmptyState` (TOKI-013) with the icon `home`, `t("messageList.start.title", { name })` "This is the start of {name}" and `t("messageList.start.description")` "Say hello." (the prototype's `emptyHtml`, which writes the name without the `#`; Decided in this spec: the name given as `conversationName`, with `#` for a channel as the journey F09 and the prototype's composer placeholder write it). Check: with a fake `sync` the list calls `loadLatest` once for a mount and once more for a second mount, and not twice in strict mode; `status` `loading` shows the busy region and no text; a `ready` empty window shows the two texts; a window dropped to `idle` after being ready makes no call.
- R11. Failures of the first load. When `status` is `failed`, `classifyApiError(error)` (TOKI-032 R8, D-131) decides: `no_access` calls `onNoAccess()` (the page's, TOKI-035 R14) and draws nothing; `unauthenticated` and `ignore` draw nothing; `unreadable` draws `t("messageList.readFailed")` with no Retry (a repeat fails the same way); every other kind draws that text and a `Button` `t("messageList.retry")` that calls `sync.loadLatest` again. The text and the button are a plain stand-in for the shared page and Retry of TOKI-082 (D-126, D-131). A failed `loadAround` (the message id may be gone: the server answers 404 `not_found` as for an unknown conversation, TOKI-037 R11, so the list cannot tell the two apart) is first answered by one `loadLatest` and only a failure of that is sorted as above. Check: each kind of error with a fake window `failed`; Retry calls `loadLatest` once; a `loadAround` that fails with 404 is followed by one `loadLatest` and `onNoAccess` is not called when that succeeds, and is called when it fails with 404.
- R12. Older and newer messages. The list calls `sync.loadOlder(conversationId)` when the scroll offset is within `PREFETCH` of the top of the content and `hasOlder` is true, and `sync.loadNewer(conversationId)` when the offset is within `PREFETCH` of the end and `hasNewer` is true; `PREFETCH` is one viewport height (Decided in this spec: a load that starts a screen early is done before the person arrives, whatever the height of the window). The engine ignores a load that is already running or has nothing to load (TOKI-040 R5), so the list needs no flag of its own. A load that failed leaves `error` set and the messages in place (TOKI-040 R5); the list then starts no load by itself in that direction: it remembers which direction it asked last and draws, at that end, a row `retry-older` or `retry-newer` holding `t("messageList.loadFailed")` and a `Button` `t("messageList.retry")` that calls the load again. The row goes when `error` is null again. A direction in which nothing is asked stays quiet. A load makes no visible indicator (the position is held, R16). Check: a fake window with `hasOlder` true calls `loadOlder` when the offset is within one viewport of the top, and not when it is farther; with `hasOlder` false never; the same for the end and `loadNewer`; with `error` set after an older load, no second call is made on further scrolling and the row shows; pressing its Retry calls `loadOlder` once; the same for the end.
- R13. A stale window. After a reload of the engine the window is `stale` and takes no event (TOKI-040 R16, R19). The list calls `sync.loadLatest` for a stale window when the person is at the bottom (R19), at once when the window turns stale at the bottom and when the person next reaches the bottom otherwise, and not while the person is reading higher up, so that a latest page that replaces a far window (TOKI-040 R5) does not take the text from under them. A send starts its own `loadLatest` (TOKI-040 R7) and the list follows it (R17). Check: with a `stale` window and the person at the bottom one `loadLatest` is called; with the person scrolled up none, and one when they reach the bottom; the messages shown stay while it runs.

Scrolling
- R14. Where the list opens. For each mount the list opens at: (a) the row of `openAt.messageId` when `openAt` is given: for the kind `new` that is the `new` row, placed at the top of the visible area (Decided in this spec: the unread messages follow it, and when there are too few to fill the screen the browser's end of scroll leaves the divider higher, with older messages above it), for the kind `jump` (TOKI-068) the message, centred, and its row gets `data-target="true"` for as long as it is the target (the flash is TOKI-068's); when the message is not in the window the list calls `loadAround` (R10) and places itself when it is held; (b) otherwise the end of the content. There is no memory of the position of an earlier visit (the prototype scrolls to the end at every `openConv`; Decided in this spec, concern 4: the person who has no unread messages sees the latest). A new `openAt` object while the list is mounted starts a new opening of the same kind; the same object does nothing. The first paint of an opened conversation already shows the place: the list sets the offset before the browser paints and again after the first measurement of the rows (at most three passes), so no jump is seen (concern 5). Check: jsdom with the fake layout of R20: opening with no `openAt` puts the offset at the end; with `newFromId` of a held message the `new` row is at the top; with a `jump` id the row is centred and has `data-target`; with an id that is not held, `loadAround` is called and the place is taken when the window arrives; a second `openAt` object moves again, the same one does not. A browser test (R25): the first screenshot of a conversation shows the last message and the offset does not change in the next 500 ms.
- R15. Stay at the bottom. While the person is at the bottom (R19) the list keeps the end of the content in view when the content grows for any reason: a message arrives (also a system line), a waiting message becomes a confirmed one with a different height, the typing line appears or goes, a row is measured again (an image loads, a message is edited, a reaction row is added, TOKI-045 to TOKI-048), the window of the list is resized (the composer grows by a line, a panel opens, the window is resized, a keyboard opens). A person who is not at the bottom is not moved by any of these (R16). Check: the fake layout puts a row of 100 px at the end, then makes the last row 300 px, then shrinks the scroller by 80 px: the offset stays at the end each time; the same steps with the offset 500 px above the end change the offset by 0 (apart from R16).
- R16. Hold the position. Whatever changes in the rows above the first visible row, that row stays at the same distance from the top of the visible area: older messages loaded and put before it (R12), a row above it measured at another height, a message above it removed or changed (TOKI-045 to TOKI-048), a day row that appears. The list remembers the first visible row's key and its distance from the top before each change of the rows and, before the browser paints, sets the offset so that the distance is the same (a row is found by its key, which is why a measured height belongs to a key and not to a place). When that key is no longer among the rows (the window was replaced, TOKI-040 R5), the list goes to the end if the new window has `hasNewer` false and stays at the offset otherwise. The scroller sets `overflow-anchor: none`, so that the browser's own anchoring does not act a second time. A change of the width of the list is held the same way. Check: with the fake layout, prepending 20 rows of 50 px while the first visible row is 30 px from the top leaves it 30 px from the top (the offset grew by 1,000); removing a row of 70 px above it does the same; a row above it measured at 90 px instead of 64 does the same; a window replaced by another goes to the end; a browser test (R25) loads a page of older messages and finds the message that was at the top at the same y within 1 px.
- R17. After the person sends. When the list sees a new waiting item of the person (TOKI-040 R7) it goes to the end at once and keeps following the end (R15) until the person scrolls by hand, whatever the offset was before, so the sent message is seen (TOKI-040 Plan changes: the list scrolls to the end after `send`). A window that had `hasNewer` true is replaced by the latest page that `send` starts (TOKI-040 R7); the list follows that too, and the item stays in view when the confirmed message takes its place (the same key, R5). A scroll that the person makes (wheel, touch, keys, the scroll bar) ends the following; one that the list makes does not. Check: with the offset far above the end a new waiting item moves the offset to the end; a later change of the content keeps it there; a simulated person's scroll up ends it and the next message does not move it; with `hasNewer` true and a window replaced the end is shown.
- R18. The new-messages button. While the person is not at the bottom (R19) and the window has `hasNewer` false, the list counts the messages that arrive at the end of the window after the person left the bottom, counting messages of `kind` `user` written by someone else, not system lines and not the person's own (Decided in this spec: D-100 says a system line raises no unread count, and the button is the on-screen twin of that count; the journey F09 gives no rule for them). When the count is above 0 the list draws `NewMessagesButton` floating over the list, centred above its end, a `Button` (TOKI-012) with the icon `down` and the text `t("messageList.newMessages", { count })` ("{count} new message", "{count} new messages"; the journey F09 gives "↓ 3 new messages", and the prototype has no such button, so the wording is a proposal settled by D-139). When `isMention(message)` is given and true for one of the counted messages, the button also shows the `at` icon (the journey: "with @ if one is a mention"); TOKI-050 gives `isMention`, and until it does no `@` is drawn. Pressing the button goes to the end of the content and clears the count; reaching the bottom by hand clears it too. The count is kept by message id, so an event repeated after a catch-up is not counted twice. The button is not drawn at the bottom, and not for a window with `hasNewer` true, in which messages are not placed until the person reaches the end (TOKI-040 R16; concern 6). Check: at the bottom a new message gives no button; scrolled up, two messages of another person and one system line give "2 new messages"; one of the person's own gives none; `isMention` true on one shows the icon; the same id twice counts once; pressing the button moves the offset to the end and removes it; reaching the end by scrolling removes it; the English text for one and for 3.
- R19. At the bottom. The list is at the bottom when the window has `hasNewer` false and the distance between the end of the visible area and the end of the content (the typing row included) is at most `AT_BOTTOM_PX` (32 px: a rounding of the browser's scroll must not decide; Decided in this spec). `onAtBottomChange(atBottom)` is called when the value changes and once at the first measure; TOKI-053 uses it with "the window is in use" for the read rule of D-052 (a conversation is read when it is open, the window is in use and the person is at the bottom). A window with no rows is at the bottom. The list never calls it with the same value twice in a row. Check: the fake layout at the end, 32 px above the end and 33 px above it gives true, true, false; `hasNewer` true gives false at the last row; two renders at the same place call it once.
- R20. Virtualisation. The rows drawn are those that the library gives for the visible range plus `OVERSCAN_ROWS` (10) on each side, and the row that holds the keyboard focus, which stays mounted when it leaves the range, so a focused control in a message (TOKI-052) is not lost by a scroll (a `rangeExtractor` adds its index). Rows are placed at the offsets the library gives, in one scroller `div` with `role="list"` (R24), `overflow-y: auto`, `overscroll-behavior: contain` and the prototype's padding (`8px 8px 12px`, `.msgs`, and its safe-area rule on narrow screens) carried over; each row sits in a wrapper that the list owns and the library measures with a `ResizeObserver`, so a row may change its height at any time. The spacing between rows is padding of the wrapper or of the component, never a vertical margin (a margin is outside what is measured): the prototype's margin on `.day` and `.msg` becomes padding. The estimates before measurement are `ESTIMATE_ITEM_PX` and `ESTIMATE_DIVIDER_PX`. The number of rows in the DOM does not grow with the length of the window: 10,000 messages in a viewport of 600 px put at most 60 row wrappers in the DOM. ## Design
### Why this library (Decided in this spec, concern 1)
The three candidates were measured for this spec: each bundled with esbuild (minified, React external) and compressed with gzip level 9, with the versions that were current: `@tanstack/react-virtual` 3.14.28 about 11 KB, `react-virtuoso` 4.18.24 about 21 KB, `react-window` 2.5.4 about 6.5 KB. The first-load budget is 200 KB (D-113, TOKI-007), so none is a problem alone; the choice rests on the other three reasons the plan names.
| | `@tanstack/react-virtual` | `react-virtuoso` | `react-window` 2 |
| :---- | :---- | :---- | :---- |
| Dependency size (gzip) | about 11 KB; the app already uses TanStack Query and Router | about 21 KB | about 6.5 KB |
| Tests in jsdom | the size of the scroller, the offset, the measure of an element and the scroll are options of the virtualiser, so a test passes a fake layout and checks every decision of this spec without a browser (R20) | measures inside the library; a test must mock the library's own internals or give it an initial item count, and then no scroll decision can be proved | the heights and the scroll are the library's; the test can set a row height but not drive a scroll |
| Reverse scroll, stick to bottom, a prepend | none built in: the list decides (R14 to R17); stable keys per row (`getItemKey`) keep a measured height with a message when rows are added above | built in (`firstItemIndex`, `followOutput`, `initialTopMostItemIndex`); the rules are the library's, tuned for its own cases | none built in, and the dynamic height cache is kept by row index, so a prepend shifts every cached height and the position cannot be held without rebuilding it |
| Dynamic row height | measured through a `ResizeObserver` per row, cached by key | automatic | `useDynamicRowHeight`, by index |
The cost of the choice is that the list writes the reverse-scroll rules itself (R14 to R19). That cost buys rules that are ours, written as pure functions in `scroll-rules.ts` and `rows.ts` and tested in jsdom, and a browser test (R25) that proves what only a browser can. `react-virtuoso` would remove that work at twice the size and would hide the decisions inside the library, where the 60 frames per second and the position hold could be proved only by the browser. `react-window` cannot hold a position over a prepend.

### How the list works
```
window (TOKI-040)  ->  buildRows (R5..R9)  ->  virtual-rows.ts  ->  row wrappers  ->  MessageRow / dividers / typing / retry
                                  ^               ^   |
              typing label, newFromId, flags      |   +-- scroll-rules.ts: at bottom, hold, follow, button count (R14..R19)
                                                  +-- layout (real browser, or the fake of R20)
```
- `scroll-rules.ts` holds the decisions as pure functions over plain numbers: `isAtBottom(offset, viewport, total, hasNewer)`, `holdOffset(anchor, newStart)` (the new offset that keeps the first visible row where it was), `placeOffset(kind, rowStart, rowSize, viewport)` (R14), `countNew(counted, messages, me, isMention)` (R18), and `shouldLoad(direction, offset, viewport, flags)` (R12, R13). `virtual-rows.ts` is the one file that imports the library: it creates the virtualiser with the rows, `getItemKey` from the row keys, the `rangeExtractor` of R20 and the offsets, and applies the results of `scroll-rules.ts` in a layout effect, before the browser paints.
- A message that is added at the end while the person is at the bottom is placed by the engine (TOKI-040 R16), `buildRows` gives one more row, and R15 moves the offset by the row's height. A message that arrives while the person is scrolled up changes nothing on screen and raises the count of R18.
- A person who has scrolled up in a window that is not at the end (`hasNewer` true: after opening at the New divider or at a jumped-to message) reads down; `loadNewer` brings the rest (R12). New messages are not placed in such a window (TOKI-040 R16), so there is no count and no button (concern 6).

### Known limits
- The browser's find-in-page and a selection that crosses rows far apart do not reach the rows that are not drawn; a search in a conversation is TOKI-069 to TOKI-072.

- The estimate of a row's height is a guess until the row is measured; a row far above the screen that is measured later moves the content, which R16 absorbs.

## Data safety
- The list holds nothing of its own: the messages are the engine's, in memory (TOKI-040 R19), and are dropped by its `reset`. It writes nothing to storage and logs nothing; a message's text is rendered as text by the component (TOKI-042, TOKI-049) and never as markup.
- A list reads only conversations the person belongs to: the archived page is reached only by a member of the archived channel (TOKI-101 R13) and the history route refuses anyone else (TOKI-037 R1, TOKI-027 R5); a 403 or 404 draws nothing and calls `onNoAccess` (R11).

## Areas of concern
1. The virtualisation library. Decided in this spec (a technical choice the Blueprint leaves to the builder): `@tanstack/react-virtual`. Reasons: about 11 KB gzip against about 21 KB for `react-virtuoso` (measured with esbuild and gzip level 9); the size, the offset, the measure and the scroll of the virtualiser can be given by a test, so every decision of the list is proved in jsdom, which neither other library allows; it has no hidden reverse-scroll rules and a height cache by key, which a prepend needs and `react-window` 2 does not have (Design). The cost is that the list writes the reverse-scroll rules (R14 to R19) and that a browser test (R25) is needed for what jsdom cannot show. Owner: Thanh Truong.
2. The tab row. Decided: TOKI-035 concern 7, decided by the product owner on 2026-11-20, gives this ticket the row with the Messages tab and leaves the others to their tickets (R4). Decided in this spec (a reading): the selected tab is page state and not in the address, and the archived page has no tab row, because no decision puts the tab in the address or says that the other tabs open for an archived channel; if the owner wants either, it is a change of R4. Owner: Thanh Truong.
3. The day dividers, the grouping and who owns them. Decided in this spec: the list, because only it sees a message's neighbours and needs the rows to exist; TOKI-042 draws a message. The grouping reads F09 ("consecutive messages from one person within 5 minutes") as a gap of at most 5 minutes between two consecutive messages; the prototype groups by author and day only and never groups a waiting message, and R7 keeps the second rule. Reason: the rule must be one function that both the sequence of rows and the component read. Owner: Thanh Truong.
4. Where the list opens. Decided: with unread messages at the New divider (D-052); otherwise at the latest message, as the prototype does at every opening, and no position is remembered for a conversation that the person left; the divider at the top of the visible area and a jumped-to message at the centre (the prototype's `centerIn`) are technical placements. Owner: Thanh Truong.
5. Technical choices the Blueprint leaves to the builder. Decided in this spec: (a) the first paint already shows the place, by setting the offset before paint and after the first measure (R14), chosen over showing the top and scrolling, which a person would see as a jump; (b) a load starts one viewport height before the end (R12), chosen over a fixed number of pixels, which is too late on a tall window; (c) the list is `role="list"` and not a live region or `log` (R24); (d) scrolls are instant (R24); (e) a stale window is loaded only when the person is at the bottom (R13). Owner: Thanh Truong.
6. Reaching the latest message from a place that is not at the end. Not decided. A person who opens at the New divider with many unread messages, or at a message that TOKI-068 jumps to, has a window with `hasNewer` true: the journey F09 gives a button only for new messages that arrive while the person is scrolled up, which a window that is not at the end does not place (TOKI-040 R16), and the log has no rule for a way back. As it stands the person scrolls down and `loadNewer` brings the rest (R12), or sends a message, which goes to the end (R17); there is no control. Proposal, not a decision: show the same button with no count and the text "Latest messages", which calls `loadLatest` and goes to the end; it would be one more text and one more case of R18. Owner: Thanh Truong (product owner).
