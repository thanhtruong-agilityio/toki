# Installation guide design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/installation-guide.md (Thanh Truong)
Ticket: TOKI-087

## Goal
A person with a fresh server, a domain and a mail account needs one document that takes them to the sign-in page of their own Toki installation, and that says what to do when sign-in mail cannot be sent. This work writes that guide, `docs/install.md`, and a check that keeps it true: every command and every variable the guide names must exist. It adds no server or web code. It is the documented path that NFR-07 asks for ("a fresh server reaches a working sign-in page from the documented steps alone").

## Scope
- In: `docs/install.md` (the guide); the check `tools/install-guide/check.mjs` and its test `tools/install-guide/check.test.mjs`, added to the root `test` script; the vitest file `apps/server/tests/install-guide-sample.test.ts` that runs check 4 of R16 (it needs TypeScript, so it cannot be a node file); the `tests` list of `.github/scripts/changed.sh` (so a change to the guide or the inventory runs the check); one line in "Commands" of `CLAUDE.md` and one link in `README.md`.
- Out (not now):
  - A second list of variables, and any edit of `.env.example` or `docs/environment-config.md`: TOKI-096 owns the names and the development values, TOKI-084 adds the production rows (its R26). The guide points to them (R15).
  - Backup and restore: deferred (D-092). The guide has no backup step and says so (R14).
  - Updating to a new release, rolling back, the registry, the deploy trigger, the one-time installation of `toki-deploy.sh` and how `.env` reaches the machine when a workflow deploys: TOKI-085 (D-190 is open there), whose runbook is `docs/deploy.md`. The guide covers the first installation by hand and links to that runbook (R14).
  - The images, the Compose file, the Caddyfile and the commands themselves: TOKI-084, TOKI-026, TOKI-074. The guide names them; it does not build them.
  - The Content-Security-Policy, rate limits and the other items of the security review: TOKI-091.
  - The load measurement: TOKI-089.
  - A guide in Vietnamese: no ticket asks for it (English is the default, D-018).
- Depends on things that are not on `main` yet: `docker-compose.prod.yml` and `entryAreas` (TOKI-084, pull request 387), `apps/server/src/cli/vapid-keys.ts`, `makeVapidPair()` and the web push areas (TOKI-074), and `docs/deploy.md` (TOKI-085, pull request 396). Checks 3 to 5, check 4 and the link check of R16 run only after those merge; before that the test of this work runs them on text fixtures (Testing). The needs of the ticket change for this reason (Plan changes).

## Requirements
- R1. The guide is `docs/install.md`, in English, with these second-level headings in this order: `Before you start`, `1. The server`, `2. DNS`, `3. The firewall`, `4. Get the code and build the images`, `5. Fill in .env`, `6. Start Toki`, `7. Sign in as the first Admin`, `8. When mail cannot be sent`, `9. When something does not start`, `What this guide leaves out`. A new heading may be added between them by a later ticket; none of these may be removed or reordered. Check: the check (R16) reads the headings and fails with the missing or misplaced one.
- R2. `Before you start` and `1. The server` state what the operator needs: a VPS of 2 vCPU, 4 GB RAM and 80 GB disk with a public IPv4 address and root or `sudo` access (D-020, technical design); Ubuntu Server, a long-term-support release (concern 1: a proposal, not a decision); Docker Engine with the Compose plugin, installed by following Docker's own instructions for Ubuntu, then checked with `docker --version` and `docker compose version`; a domain the operator controls (two names, R3); a mail account that allows sending over SMTP (R7). It names no provider and no region. Check: the check finds `2 vCPU`, `4 GB` and `80 GB` in the guide and the two `docker` check commands in its code blocks.
- R3. `2. DNS`: two names, both pointing to the public address of the server: the name of the app (the value of `APP_DOMAIN`, for example `chat.example.com`) and the name of file storage (the value of `STORAGE_DOMAIN`, for example `storage.chat.example.com`), which must differ (TOKI-084 R26, concern 1 there). They are written without `https://` and without a port. The guide says to wait until `dig +short <name>` prints the server's address for both names before step 6, because Caddy asks for each certificate on the first start and a name that does not point to the server fails the challenge (TOKI-084, Errors). Check: the check finds both variable names, the sentence about the order, and the `dig` form.
- R4. `3. The firewall`: allow SSH on `22/tcp`, `80/tcp` and `443/tcp`, and nothing else; deny the rest of incoming traffic; UDP 443 stays closed because HTTP/3 is off (TOKI-084 R18). SSH stays on port 22 with key login and no password, because the deploy of TOKI-085 reaches the server by SSH from GitHub's runners, which have no fixed address (TOKI-085 R19 and concern 5); the guide says so in one sentence and links to `docs/deploy.md` for the key. The guide shows the `ufw` commands in this order: `ufw default deny incoming`, `ufw default allow outgoing`, `ufw allow 22/tcp`, `ufw allow 80/tcp`, `ufw allow 443/tcp`, then `ufw enable`, and says that `ufw enable` asks for a confirmation and that the SSH rule comes before it so that the operator is not locked out. It says why Postgres and MinIO stay private even though Docker publishes ports around `ufw`: only the `caddy` service has `ports` (TOKI-084 R10), so the operator must not add a `ports` entry to any other service. Check: the check reads the line `ufw allow 22/tcp` as the SSH line (any other `ufw allow` form fails check 5); the numbers of the other `ufw allow` lines equal the default numbers of `HTTP_PORT` and `HTTPS_PORT` read from `docker-compose.prod.yml`; every `ufw allow` line comes before `ufw enable`; the guide holds no `ufw allow` for 5432, 9000 or 3000.
- R5. `4. Get the code and build the images`: clone the repository into a build directory on the server (`git clone <repository-url> toki-build`, then `cd toki-build`), check out the commit the operator installs, and build the two images with the commands of TOKI-084 R10: `docker build --target server -t toki-server:local .` and `docker build --target web -t toki-web:local .` (with `--build-arg TOKI_BUILD_ID=<id>` to set the build id; the guide does not name that variable, which has no row of the inventory, TOKI-084 R26). The guide does not use `docker compose ... build` here: Compose reads every `${NAME:?...}` of the file when it loads it, `build` included, and `.env` does not exist until step 5, so it would stop at the first missing name (TOKI-084 R10). The guide says that `docker compose up` in step 6 then finds both images and builds nothing. What to check out: nothing in the repository is a named release that a person can check out (TOKI-085 R2 fixes only a tag `sha-<12 hex>` of a built image). The guide says to take a commit of `main` whose CI run passed (TOKI-085 R1), by its hash with `git checkout <hash>`, or the tip of `main`. The tag stays the default `local`, so the images are `toki-server:local` and `toki-web:local` (concern 2). The guide says that the build needs several minutes and memory, and that a build killed for lack of memory is the sign to add swap or to use TOKI-085's registry route. The directory where Toki runs is a second one: the guide makes it with `mkdir -p $HOME/toki`, copies `docker-compose.prod.yml` and `.env.example` into it and goes there with `cd`. It says, writing the directory as a path and not as a variable, that `.env`, the Compose file and `emergency-link.log` live in `$HOME/toki`, that this is the directory that TOKI-085's deploy calls its home (`$HOME/toki` by default, TOKI-085 R7), that it is not the checkout because the deploy replaces `docker-compose.prod.yml` in it, and that later updates go through the deploy of `docs/deploy.md`, not through a new clone. Check: the commands are in the allowed forms of R16; the two image names in the guide equal the images the Compose file names for its default tag; the guide holds no `docker compose` line with `build`.
- R6. `5. Fill in .env`: create the file next to `docker-compose.prod.yml`, in the directory made in step 4, with `cp .env.example .env`, then `chmod 600 .env`, and keep it owned by the user who runs `docker compose` (TOKI-084 R27). The guide then goes through the values the operator must set, in groups (domain, database, file storage, mail, first Admin, sign-in, Web Push), saying for each only what is specific to an installation: where the value comes from and any rule the inventory does not give in one line. It does not describe the meaning, default or secrecy of a variable: it points to `docs/environment-config.md` for that (R15). The values the Compose file sets itself (TOKI-084 R12: `DATABASE_URL`, `APP_ORIGIN`, `TRUSTED_PROXY`, `STORAGE_ENDPOINT`, `STORAGE_PUBLIC_URL`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`, `STORAGE_DISK_PATH`, `NODE_ENV`, `SERVER_PORT`, `SERVER_HOST`, each written out because the name rule of check 2 does not accept a wildcard) are named in one sentence as "set by Compose, leave them". Secrets are made on the server with `openssl rand -hex 32` and pasted into `.env` only; the Postgres password uses letters, digits and `-._~` only (TOKI-084 R12), which a hex string meets. The guide names no variable that has no row of the inventory: not `TOKI_BUILD_ID` and not the home directory of the deploy, which is written as a path (R5). The guide never shows a secret, never asks to paste one into a ticket, a chat or a pull request. Check: R16, checks 2, 3, 4 and 6.
- R7. Mail (D-027). The guide gives the seven mail variables of the inventory, `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM_ADDRESS` and `MAIL_FROM_NAME`, and says: `SMTP_TLS` must be `starttls` (usually port 587) or `tls` (usually port 465), because the server refuses `none` outside development and refuses a login sent in clear (TOKI-021 R4); `SMTP_USER` and `SMTP_PASSWORD` are both set or both empty (TOKI-021 R3); the sender address must be one the account is allowed to send from (a refusal shows as a failed send at the stage `mail_from`, TOKI-021 R14); the server does not test the account at start, so a wrong setting shows only at the first send (TOKI-021 R18). It shows, as an example and not as a requirement, the settings of a Gmail account with an app password (concern 3), written with the example address `admin@example.com`; one sentence beside the block says that `SMTP_USER` is the full address of the account (a Gmail login is the whole address, and `example.com` stands for it, not for a Google Workspace domain) and that `MAIL_FROM_ADDRESS` must be that address or one of its aliases. Check: R16 checks 2, 4 and 6; the sample block of `.env` in the guide holds all seven names and loads (R16 check 4).
- R8. The first Admin (D-028). The guide gives `FIRST_ADMIN_EMAIL`, `FIRST_ADMIN_NAME` and `WORKSPACE_NAME` and says: the server checks the first and the third at every start and stops naming the variable when one is missing or invalid (TOKI-020 R1); the values are used once, when the database is empty, to create the workspace, the first Admin and #general; after that they change nothing, and a later edit of `.env` only logs `first_admin_skipped` (TOKI-020 R7, R13); the first Admin signs in with a code like anyone else and then invites the others; there is no Owner role. Check: the sample block holds the three names; the sentences are present (the check looks for `used once` and for the log event name `first_admin_skipped`).
- R9. Web Push keys. In step 5, after the build of step 4, the operator makes the key pair with `docker run --rm toki-server:local node dist/cli/vapid-keys.js`, which prints two lines, `VAPID_PUBLIC_KEY=<value>` and `VAPID_PRIVATE_KEY=<value>` (TOKI-074 R2, TOKI-084 R8, concern 9 there), and puts the two values into `.env`; `VAPID_SUBJECT` is `mailto:` and the address of the operator. The guide says that the private key is a secret, that the command is run before `.env` is complete because Compose would stop at the first missing value, and that the pair must not be changed later: every registered device must register again (TOKI-074 concern 11). Check: the command is in the allowed forms of R16 and its file exists (R16 check 5).
- R10. `6. Start Toki`: in the run directory of step 4, `docker compose -f docker-compose.prod.yml up -d` (TOKI-084, Commands), then `docker compose -f docker-compose.prod.yml ps` until the `server` service shows `healthy` (about 30 seconds after its start, TOKI-084 R9). The guide says what happens on the first start in one short list: the database is migrated first and the step stops everything else when it fails (TOKI-084 R13); the first Admin, the workspace and #general are created once the server listens (TOKI-020 R12); Caddy gets the two certificates. It shows how to read a service's log with `docker compose -f docker-compose.prod.yml logs --tail=200 <service>`, where the service is one of the services of the Compose file. Check: R16 check 5 (the forms, the service names).
- R11. `7. Sign in as the first Admin`: open `https://<APP_DOMAIN>/login`, enter `FIRST_ADMIN_EMAIL`, read the 6-digit code from the mail (it works for 10 minutes, TOKI-021 R7), and enter it. When no mail arrives, the guide sends the operator to the `server` log, in this order, because `server` is `healthy` before the first Admin exists (the Admin is created after the server listens, with up to 10 tries 15 seconds apart, TOKI-084 R25 b, TOKI-020 R12, R18) and a sign-in for an address with no account sends no mail: first the line `first_admin_created`; when it is missing, the lines `first_admin_failed` (TOKI-020 R13); only when the account exists, the line `mail_send_failed`, whose `reason`, `cause`, `stage` and SMTP reply code say what the mail server refused (TOKI-021 R14); then step 8. Check: the check finds the three event names in that order in step 7 and the names `reason` and `stage`.
- R12. `8. When mail cannot be sent` (D-159). The guide gives the one-time link command in this exact form: `docker compose -f docker-compose.prod.yml exec -T server node dist/cli/emergency-link.js <email> 2>> emergency-link.log`. It explains: `-T` keeps standard output and standard error apart, which the command's output contract needs (TOKI-026 R19; with a terminal attached Docker merges the two); standard output holds exactly one line, `https://<APP_DOMAIN>/emergency#<token>`, to be given to that person only, by a way other than mail; the link works once and for 10 minutes (TOKI-026 R24, R27); the line written to standard error records who ran it and which link was issued and is kept in `emergency-link.log` next to `.env`, in the run directory of step 4 (TOKI-026 R35, concern 7 there), so each use leaves a record; exit code 1 means no link was issued and the line on standard error says why (no active account for that address, a concurrent issue, or a missing or invalid setting, whose name is printed), and exit code 2 a wrong call (TOKI-026 R20, R21, R22); the command needs no mail and no SMTP value (TOKI-026 R23). It says that this is the only sign-in without a code. Check: the form is in the allowed forms of R16 and `apps/server/src/cli/emergency-link.ts` exists; the check finds `-T`, `2>>`, `10 minutes` and `once`.
- R13. The first Admin's address was mistyped. TOKI-020 concern 16 decided the need and the approach only: change that one account's address in the database, or, on an installation that holds nothing else, start again with an empty database. The statement text and the `psql` form below are this spec's own proposal, not a decision of the log. Under step 8 the guide gives the fix: when the address is well-formed, `emergency-link` for the address written in `.env` still gives a link and the Admin enters; when it is wrong, the operator changes the address of that account with one statement. The guide shows these exact lines:
  ```bash
  docker compose -f docker-compose.prod.yml exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
  UPDATE users SET email = '<new address>' WHERE email = '<old address>';
  SQL
  ```
  The new address is in lower case with no space (the table refuses anything else, TOKI-019 R7); an address that holds a single quote is written with the quote doubled. For an installation that holds nothing else, starting again with an empty `postgres-data` volume is the alternative, and the guide says that this deletes the data. Check: the first line is the one `exec -T postgres` form that check 5 allows (R16 check 5); the lines between `<<'SQL'` and the closing `SQL` are not read as commands and are read by check 9 instead: they must be exactly one statement of the shape `UPDATE users SET email = '...' WHERE email = '...';`, and the table `users` and the column `email` must be in the SQL of `apps/server/migrations`.
- R14. `What this guide leaves out` lists, in one line each with the owner: backup and restore (D-092: nothing copies the volumes, so a lost disk loses the data); updating, rolling back, the installation of `toki-deploy.sh` and automated deploy (TOKI-085, with a link to `docs/deploy.md`, which holds the setup facts, the key, the Environment and the package visibility); the security review (TOKI-091); the load measurement (TOKI-089). The guide holds no backup or restore command. Check: no code block holds `pg_dump`, `pg_restore`, `rsync`, `tar`, `snapshot` or `restore`.
- R15. One list of variables. The guide has a sentence at the start of step 5 that points to `docs/environment-config.md` as the list of every variable, with its meaning and whether it is secret, and to `.env.example` as the file to copy. The guide contains no table with a column named `Required`, `Default`, `Secret` or `Purpose`, and no list of the variables of a process. Check: R16 check 7.

## Design
### Where the guide lives
`docs/install.md`: next to `docs/environment-config.md`, which it points to, and found from the `README.md`. One file, because the guide is short and a person follows it in order; a folder of pages would hide the order. It is a document, not a generated one: the check does the keeping-true.

### What each step contains
| Step | Contains | Source of the facts |
|---|---|---|
| Before you start, 1 | machine, OS, Docker | D-020, technical design, concern 1 |
| 2 DNS | two names, `dig` | TOKI-084 R26, Errors |
| 3 Firewall | `ufw` for SSH, 80, 443 | TOKI-084 R10, R18 |
| 4 Code and images | clone, checkout, the two `docker build` commands, the run directory | TOKI-084 R10, TOKI-085 R7, concern 2 |
| 5 .env | copy, `chmod 600`, groups, secrets, mail, first Admin, Web Push | TOKI-096, TOKI-084 R11, R12, R27, TOKI-021, TOKI-020, TOKI-074 |
| 6 Start | `up -d`, `ps`, `logs` | TOKI-084 R13, Commands |
| 7 First sign-in | `/login`, code, the three log lines in order | TOKI-022, TOKI-021 R14, TOKI-020 R13 |
| 8 Mail cannot be sent | `emergency-link`, record, typo fix | D-159, TOKI-026, TOKI-020 concern 16 |
| 9 Does not start | a short list: what the symptom is and where to look | TOKI-084 Errors, TOKI-004 R3 |

Step 9 holds only facts the other specs give: a service that restarts shows the variable it names on standard error (TOKI-004 R3, TOKI-084 Errors); `migrate` stopping with "The database cannot be reached" points to the Postgres password characters (TOKI-084 R12); no HTTPS points to DNS or a closed port and the `caddy` log names the failed challenge (TOKI-084 Errors); a server that listens but shows no `first_admin_created` line points to the `first_admin_failed` lines (TOKI-020 R13).

### The check
`tools/install-guide/check.mjs` exports `checkGuide(files)` (checks 1 to 3 and 5 to 11; check 4 is the vitest file of R16), where `files` is the text of the guide, the inventory, `.env.example`, the Compose file, the list of files under `apps/server/src/cli/` and the SQL of `apps/server/migrations`; it returns the list of failures, so the test calls it on real text and on changed copies. The command line reads the real files and prints the failures. It reads the Compose file as text (the `${NAME:?...}` references, the service names, the `ports` defaults) and does not run Docker: TOKI-084's `pnpm stack:check` already proves the stack in a real image, including the one-time link (its R25 b). The checks are complementary: that one proves the commands work, this one proves the guide names the same commands and variables.

### Order of the work on the first installation
