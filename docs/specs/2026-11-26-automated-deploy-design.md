# Automated deploy design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/automated-deploy.md (Thanh Truong)
Ticket: TOKI-085

## Goal
TOKI-084 makes one installable unit: two images and one Compose file. This work moves a release onto the machine and off it again. It builds and publishes the images from a commit of `main` whose CI run passed, puts a chosen release on the server with a script that checks the release before it touches the running one, runs the migrations first and alone, switches, waits for the server to be healthy, and returns to the previous release by itself when the new one does not become healthy. A bad release found later is rolled back with one command. The repository is public, so none of this may need a secret value in a workflow file or print a person's data in a run log: the application's secrets stay in the `.env` on the server. GitHub holds one SSH key that opens one script on the server, not a shell. That script runs Docker with a Compose file that the sender supplies, so a leaked key is not "the script and nothing else": without the checks of R22 it would be root on the machine, and with them it is still the means to stop the application, start any release from the project's registry with settings of the sender's choosing, and read the application's data and secrets through that. The key is therefore treated as being as sensitive as the `.env` and the database, and R22 and the Environment rules of R19 keep it from being worth more (concern 5 states this and what the owner is asked to accept).

## Scope
- In: `.github/workflows/release.yml` (build and publish); `.github/workflows/deploy.yml` (deploy and rollback); `tools/deploy/` (`release.sh`, `deploy-remote.sh`, `toki-deploy.sh` and their tests, the check of the whole flow `check.sh`); `docs/deploy.md`; the section "How secrets are kept, Production", the "Supplied by" of two rows and the rows of the GitHub values in "External values" of `docs/environment-config.md`; one new CI job and one new name in `.github/scripts/changed.sh`; the root scripts `deploy:test` and `deploy:check`, which are also added to "Common commands" in `CLAUDE.md`.
- Out (not now):
  - Whether a merge starts the deploy by itself: D-190, open (concern 1). Everything below is built and works with the deploy started by a person; the automatic start is one added job (concern 1).
  - The image, the Compose file, the Caddyfile, the health check, the migration service, the stop periods and the operator commands: TOKI-084. This work runs them and changes none.
  - Installing Docker, DNS, the firewall (it opens `22/tcp` for key login, TOKI-087 R4) and the run directory `$HOME/toki` with its `.env`: TOKI-087 (R4 to R6). The deploy user's `sshd` settings, `jq`, the registry file and the installation of `toki-deploy.sh` are in `docs/deploy.md` (R19), because TOKI-087 does not write them and asks this work to hold them.
  - A review of the key, the Docker group, the Actions permissions and the exposed SSH port: TOKI-091 (concern 5 lists what it receives).
  - Backup and restore of volumes or of `.env`: deferred (D-092). A rollback never restores data (R14).
  - Zero-downtime updates, several servers, blue-green or canary releases: not phase 1 (TOKI-084 concern 12; technical design).
  - The update strip and the server's "page too old" answer: TOKI-104 (R17, concern 11).
  - Signing or attesting images, scanning them for known flaws: not taken, a later decision (TOKI-091 concern 7 does not take it either).

## Requirements
- R1. The release workflow. `.github/workflows/release.yml` (name `Release`) has one trigger, `workflow_run` of the workflow named `CI` (`types: [completed]`), and its job `images` runs only when `github.event.workflow_run.conclusion == 'success'`, `github.event.workflow_run.head_branch == 'main'`, `github.event.workflow_run.event == 'push'` and `github.event.workflow_run.head_repository.full_name == github.repository` (a fork can have a branch named `main`); so an image is built only from a commit of this repository's `main` whose whole CI run (the `stack` job of TOKI-084 R28 included, which a push to `main` always runs) passed. It checks out `github.event.workflow_run.head_sha` with `persist-credentials: false`, and no step checks out anything else or runs code from a pull request. `permissions` is `{}` at the top of the file and `contents: read` and `packages: write` on the job `images` only. The `concurrency` group is `release-${{ github.event.workflow_run.head_sha }}` with `cancel-in-progress: false`: a re-run of one commit waits for the earlier run of that commit, and runs of different commits neither cancel nor wait for each other (a group shared by all commits would keep only one running and one pending run and cancel the older pending one, so a quick series of merges would lose releases). Every commit of `main` whose `CI` run passed therefore gets its release; a commit whose run failed has none, and a deploy that names it stops at R6. The workflow has no `pull_request`, `pull_request_target`, `issue_comment` or `workflow_dispatch` trigger (a failed release is started again with "Re-run" of its run). Check: `tools/deploy/workflows.test.mjs` (R20) reads the file and asserts each of these, including the four conditions, the group expression, that every `actions/checkout` has `persist-credentials: false` and a `ref` that is `github.event.workflow_run.head_sha` and nothing else, and that the `name` of `ci.yml` is `CI`, so a rename of that workflow fails the test and does not silently stop releases.
- R2. The release tag. The tag of a release is `sha-` followed by the first 12 characters of the commit's SHA-1 in lower case, for example `sha-0123456789ab`. `tools/deploy/release.sh <sha>` prints it; a SHA that is not 40 hexadecimal characters exits 2 and prints nothing else. The server image and the web image of one commit carry the same tag (TOKI-084 concern 4). No tag is `latest` and no moving tag is written. A tag is immutable: when `toki-server` and `toki-web` both already exist in the registry under the tag, `release.sh` builds and pushes nothing and exits 0 saying so (a re-run of a finished release changes no image); when only one exists, it builds and pushes both. Check: `tools/deploy/release.test.sh` with a fake `docker` on `PATH`: the tag of a known SHA; a short SHA, an upper-case SHA and an empty argument exit 2; with both images present the fake records no `build` and no `push`; with one missing it records both pushes; no recorded call carries the tag `latest`.
- R3. What a release publishes. The registry is the GitHub Container Registry, `ghcr.io/<owner>/`, with `<owner>` the repository owner in lower case; that string, ending in `/`, is `TOKI_REGISTRY` (TOKI-084 R10 and R26) (concern 2). `release.sh` logs in with the job's own `GITHUB_TOKEN` (no other credential, passed by `--password-stdin`, never as an argument) and builds the two Toki images with the two `docker build` commands of TOKI-084 R10, which read no env file and so need no secret value at all: `docker build --target server` and `docker build --target web`, each with `--build-arg TOKI_BUILD_ID=<the full 40-character commit SHA>` (the build id of TOKI-104 R2; the same value in both commands, so the two images of a release carry one), `--label org.opencontainers.image.source=https://github.com/<repository>` (so that the package is linked to the repository, concern 6) and `-t ${TOKI_REGISTRY}toki-server:<tag>` or `-t ${TOKI_REGISTRY}toki-web:<tag>`; then `docker push` of each. The names are the ones the Compose file names (the service `server` is `toki-server`, the service `caddy` is `toki-web`, TOKI-084 R10), and a test reads the `image:` of those services in `docker-compose.prod.yml` and fails when the names `release.sh` builds differ. The MinIO image of `Dockerfile.minio` is built and pushed too, as `${TOKI_REGISTRY}toki-minio:<the release tag named by the `minio` service of the Compose file>`, only when that tag is not yet in the registry (the image is rebuilt only when MinIO's release changes, and the server never compiles it, concern 12). This needs TOKI-084 R24 to name that image with `${TOKI_REGISTRY:-}` (Plan changes, concern 12): until that change is merged this work cannot be built, and R22 refuses a Compose file that does not carry the prefix with a text that names the cause. Check: `release.test.sh` with a fake `docker` on `PATH`: the recorded calls are the build and the push of the two images with the registry prefix and the tag, in that order; both builds carry the same `--build-arg TOKI_BUILD_ID` equal to the SHA given and the `--label`; no `docker compose` call is recorded; the login call has no password in its arguments; with the MinIO tag already present the fake records no MinIO build; a build that fails makes the script exit non-zero and records no push of the image it failed on.
- R4. The deploy workflow. `.github/workflows/deploy.yml` (name `Deploy`) has the trigger `workflow_dispatch` with one input `tag` (string, not required, default empty). In this ticket that is its only trigger (concern 1: D-190 is open). Its job `deploy` has `environment: production`, `timeout-minutes: 30` and `permissions` of `contents: read` and `packages: read`, and no job-level or step-level `if` that skips it; its `concurrency` group is `deploy-production` with `cancel-in-progress: false`, because stopping a deploy half way is worse than waiting (GitHub keeps one running and one pending run of a group and cancels an older pending one, so a third request cancels the second; the server's own lock of R7 is what makes two deploys safe). The first thing `deploy-remote.sh` does, before it reads its argument or runs any command, is to refuse a run whose `GITHUB_REF` is not `refs/heads/main`: it exits 1 and prints the reason, so the run is red and not skipped (R13). That guard is only a clear message: a `workflow_dispatch` run of another branch uses that branch's copy of `deploy.yml`, which can drop the guard, so the protection of the key is the deployment branch rule `main` of the Environment `production`, which is required (R19, concern 5). The input reaches the shell only through `env:` (the workflow rules) and is validated by R6 before any use. Check: `workflows.test.mjs`: the trigger set equals the constant `ALLOWED_DEPLOY_TRIGGERS` at the top of the test (`['workflow_dispatch']`; the owner's answer to concern 1 changes that one line and nothing else of the test); the three properties above; no `if:` on the job or its steps; no `${{ github.event.inputs` or `${{ inputs` inside a `run:` value; `deploy-remote.test.sh` with `GITHUB_REF=refs/heads/other` exits 1 with the reason and no fake command is called.
- R5. Only the key and four values. The job reads the GitHub Environment `production`: three secrets, `DEPLOY_SSH_KEY` (an ed25519 private key made for this purpose only), `DEPLOY_HOST` and `DEPLOY_USER` (secrets so that the run log masks them: the account behind an open SSH port is not for the public), and two variables that are not secrets, `DEPLOY_PORT` (default 22) and `DEPLOY_KNOWN_HOSTS` (the host key line of the server, in the form `[host]:port <type> <key>` when the port is not 22). The other credential in the job is the `GITHUB_TOKEN` of the run. The runner writes the key to a file in `RUNNER_TEMP` created under `umask 077`, calls ssh with `-p <DEPLOY_PORT> -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<a file made from DEPLOY_KNOWN_HOSTS>` and `-o ServerAliveInterval=30` and without `-v` (no `ssh-keyscan` and no first-use trust, which would accept an attacker's server), and removes both files in a step with `if: always()`; the run log shows the step names and the output of the script (R8) and, because host and user are secrets, only `***` for them. The key's public half sits in the deploy user's `authorized_keys` with the options `restrict,command="<path of toki-deploy>"` (R7), so the key can open that script and not a shell: no port forwarding, no agent forwarding, no terminal. What that script can be made to do with a Compose file and a tag of the sender's choosing is bounded by R22 and no further (Goal, concern 5). Check: `workflows.test.mjs`: every `secrets.` name in both workflows is `DEPLOY_SSH_KEY`, `DEPLOY_HOST`, `DEPLOY_USER` or `GITHUB_TOKEN`, and every `vars.` name is `DEPLOY_PORT` or `DEPLOY_KNOWN_HOSTS`; `deploy-remote.test.sh` with a fake `ssh`: the recorded arguments hold each option above and `-p` with the port (22 when the variable is empty) and no `-v`, the key file has mode 600 when the fake runs and does not exist after the script ends (also when the fake fails), and the key text is in no output.
- R6. Which release a run deploys. `tools/deploy/deploy-remote.sh` is what the job runs; it takes the input as an argument and starts with the guard of R4. (a) Empty: the release of the head commit of `main` (its R2 tag). (b) `sha-` and 12 lower-case hexadecimal characters: that release; the commit is found in the checkout (`fetch-depth: 0`) and must be an ancestor of `main`'s head, so no unmerged work can be deployed. (c) `previous`: the previous release on the server (R14). Anything else exits 2 before any command is run. For (a) and (b) it logs in to the registry with the run's token, checks that `toki-server` and `toki-web` exist under the tag and fails with exit 3 and the text "no image for this release; the Release workflow has not finished, failed, or never ran for this commit" when one is missing (a commit whose CI run failed has no release, R1), all before it connects to the server. It then connects once to ask `version` and compares the answer with the grammar number it was written for (`GRAMMAR` in `tools/deploy/`); a server script that is older or newer gives exit 3 and the text "update toki-deploy on the server (docs/deploy.md)" before anything is sent. It then sends the server `deploy <tag>` with the file `docker-compose.prod.yml` of that same commit as a tar stream on standard input (a release is the pair of its images and its Compose file, so a release that adds a name or a service brings the file that goes with it). The request holds no registry: the server uses its own (R7, R22). For (c) it sends `rollback` and nothing on standard input. An `ssh` that exits 255 (no connection, host key not matching, key refused) is mapped to exit 10 with that text, because 255 is not a code of the script. Check: `deploy-remote.test.sh` with fake `git`, `docker` and `ssh`: the three forms send the right command and, for (a) and (b), a tar that holds exactly `docker-compose.prod.yml` of the right commit (the fake `git` serves two different files for two commits); a commit that is not an ancestor of `main`, a tag of the wrong shape, `sha-0123456789AB`, `sha-0123456789ab; id` and `latest` exit 2 with no `ssh` call; a missing image exits 3 with no `ssh` call; a fake `ssh` that answers `version` with another number exits 3 and no tar is sent; a fake `ssh` that exits 255 gives exit 10.
- R7. The server script and its commands. `tools/deploy/toki-deploy.sh` runs on the server as the deploy user and is the forced command of R5. It is installed by the operator as a file owned by root and not writable by the deploy user (so the key cannot replace it, R19), and it reads its request from `SSH_ORIGINAL_COMMAND` when set and from its own arguments otherwise (so the operator can run it by hand, concern 4). It accepts exactly: `deploy <tag>`, `rollback`, `status` and `version` (which prints the grammar number, R6). `<tag>` matches `^sha-[0-9a-f]{12}$`; the request is split into words and never passed to a shell for evaluation; a request that is anything else, a registry word included, exits 2 before any other command runs. The registry is not part of a request: the script reads it from `TOKI_REGISTRY_FILE` (default `/etc/toki/registry`), a file that the operator makes once, owned by root and not writable by the deploy user, whose one line matches `^[a-z0-9.-]+(:[0-9]+)?(/[a-z0-9._-]+)*/$` (it ends with `/`, for example `ghcr.io/<owner>/`); a missing, unreadable or malformed file exits 3 (R22). `TOKI_HOME` (default `$HOME/toki`) is the run directory that the installation guide of TOKI-087 makes (its R5 and R6: `.env`, `docker-compose.prod.yml` and `emergency-link.log` live there, and the clone is a different directory, `toki-build`); it holds `.env` and `docker-compose.prod.yml` (TOKI-084 R27), and the deploy replaces the Compose file and writes `releases/`, `releases.log`, `deploy.log` and `.deploy.lock` there. The script exits 3 with the reason when `TOKI_HOME` holds a `.git` directory, because a checkout would have its tracked `docker-compose.prod.yml` replaced by the deploy. `COMPOSE_PROJECT_NAME` is honoured when set (the check of R20 uses it); the project name of the Compose file is `toki` (TOKI-084 R10), so the stack that the guide started in `$HOME/toki` and the one the script drives are one project. `status` prints the running tag, the previous tag and the state of the services (name, state, health), and nothing from `.env`. Every call of Compose names `--project-directory $TOKI_HOME` and `--env-file $TOKI_HOME/.env`, so the operator's `.env` is the one read even for the staged Compose file. The script ignores `SIGHUP` and `SIGPIPE`, writes each step line to `$TOKI_HOME/deploy.log` first and then to standard output, and ignores a failed write to standard output or error, so an SSH session that drops (a hang-up, or closed pipes that make the next write fail) does not stop a deploy half way. `deploy.log` (mode 600) is rotated at the start of a deploy when it is larger than 5 MiB (`TOKI_LOG_KB`), keeping the last 3 files. One run at a time: the script takes an exclusive lock on `$TOKI_HOME/.deploy.lock` and a second run exits 9 at once, saying that another deploy is running. Check: `toki-deploy.test.sh` (R20), with a fake `docker`, `curl` and `df` on `PATH`, a temporary `TOKI_HOME`, a temporary registry file and an injected `TOKI_SLEEP` (so no test waits on a timer): the four forms are accepted; `deploy sha-0123456789ab`, `deploy sha-0123456789ab ghcr.io/x/` (a registry in the request), `deploy sha-0123456789ab ghcr.io/x/; id`, `deploy latest`, `rollback now`, an empty request and `bash` exit 2 and the fake records no call; a registry file that is missing or malformed exits 3; a `TOKI_HOME` with a `.git` directory exits 3; a second run started while the first holds the lock exits 9 and changes nothing; a `SIGHUP` sent to the script by the fake `docker` in the middle of a deploy does not stop it, and neither does a run whose standard output and error are closed in the middle (the test closes the reading end of the pipes): each ends with exit 0 and the `live` line, and `deploy.log` holds the step lines; a `deploy.log` of 6 MiB is rotated.
- R8. What the script does with `.env`, and what it prints. The script never prints, copies or sends `.env`, never runs `docker compose config` without `-q` except in the one form of R22 (`--no-interpolate`, whose output holds no value of `.env` and goes into the validator, not to a log), and reads exactly four names from it: `APP_DOMAIN` and `HTTPS_PORT` (for the check of R11), and `TOKI_TAG` and `TOKI_REGISTRY` (it writes these two, and reads them back to record the running release when none is recorded, R12). It reads a name the way Compose does: a leading `export ` is ignored, one pair of surrounding quotes is removed, an unquoted ` #` starts a comment, and when a name appears twice the last line wins. It changes `.env` in one way only: every line of the name `TOKI_TAG` and of the name `TOKI_REGISTRY` (with or without `export`) gets the new value in its place, and the two lines are added at the end when missing (so a second `TOKI_TAG=` line cannot override the one the script wrote), through a new file in the same directory that keeps the owner and the mode, then renames it over `.env` (concern 5). The value of `TOKI_REGISTRY` it writes is the one of the registry file (R7), or, when it restores a release, the one recorded for that release (R12). Its standard output and standard error hold only step names, tags, container states, exit codes and the names of missing variables, because the run log of a public repository is public (concern 8): the output of `docker compose pull` and `up` (image and container names, no value) may pass; the output of the migration step and the logs of the services are written to `$TOKI_HOME/deploy.log` (mode 600) and never to the run log. Check: `toki-deploy.test.sh` with an `.env` that holds the marker values `SECRET-MARKER-DB`, `SECRET-MARKER-SMTP` and `SECRET-MARKER-VAPID`, whose fake `docker` writes the whole environment it was given and the content of `.env` to its own output when asked to run `migrate`: after a successful deploy and after a failed one, the markers are in neither standard stream of the script and not in `releases.log`; the migrate output, markers included, is in `deploy.log` and nowhere else outside `.env`; `.env` after the deploy differs from `.env` before it in the lines of the two names only (`diff` shows nothing else) and keeps its mode 600; every other line, comments and blank lines included, is byte-identical; a `.env` with `APP_DOMAIN=\"chat.example.com\"`, with `export TOKI_TAG=sha-aaaaaaaaaaaa` and with a second `TOKI_TAG=` line is read and rewritten correctly (the last value wins when read, and after the deploy every line of the name holds the new tag).
- R9. Before anything changes (the preflight). In this order, and each failure exits 3 with the reason and leaves the running release, `.env`, the installed Compose file and `releases.log` exactly as they were: (1) `$TOKI_HOME/.env` exists and its mode is 600, else the text names the file and the mode; (2) the registry file of R7 is valid; (3) the Compose file from standard input is read up to 256 KiB (`TOKI_MAX_TAR_KB`; a larger input is refused, so the sender cannot fill the disk) and is exactly one regular file named `docker-compose.prod.yml` (a tar with another name, a path with `..` or `/`, a link, a second entry or a size above the limit is refused) and is written to a staging directory; (4) the file passes the checks of R22 (what it may contain); (5) `docker compose -f <staged file> config -q`, run with `TOKI_TAG` of the request and `TOKI_REGISTRY` of the registry file, succeeds, so a name that the new release needs and `.env` lacks stops the deploy here with Compose's own message that names it (TOKI-084 R11); (6) the free space of the file system that holds Docker's data is at least 3 GiB (a starting value, one line to change, `TOKI_MIN_FREE_MB`); (7) `docker compose pull caddy server minio postgres` of the staged file succeeds, so a deploy never starts with an image missing (the Postgres image is pulled here too: a release that raises its tag would otherwise pull it during `run` or `up`, after the preflight) and the disk fills only by images that exist. A pull that the registry refuses (`denied` or `unauthorized`) adds the text that the package may still be private and that the owner makes it public once (R19, concern 6). Check: `toki-deploy.test.sh`: one case per step makes the fake fail at that step (for step (3): a tar with a bad name, with `..`, with a link, with two entries, and one above the size limit); each exits 3, the fake records no `up`, no `run` and no `rm`, and `.env`, `docker-compose.prod.yml` and `releases.log` are byte-identical to what they were; a fake pull that says `denied` gives the text about the package.
- R10. Migrations first, and alone. After the preflight and before any running container changes, the script runs the migration service of the new release once. Compose recreates a dependency whose configuration changed when it starts a service, so a plain `run migrate` of a release that changes the `postgres` image or limits would recreate the database before the switch; therefore the script (a) when the `postgres` container is not running (the first deploy of an empty machine), starts it alone with `docker compose -f <staged file> up -d --no-build --wait postgres`, and otherwise leaves it as it is, then (b) runs `docker compose -f <staged file> run --no-deps --no-build --rm --name toki-migrate-<tag> migrate` under `timeout` with a limit of 10 minutes (the queue schema step waits for at most 5 minutes by itself, TOKI-064 R3, and a migration needs time besides; a starting value, `TOKI_MIGRATE_MINUTES`); the old `server`, `worker` and `caddy` keep running, and a change of the `postgres` image or limits is applied by the switch (R11), with Postgres's own stop period. `timeout` ends the Compose client, not the container, so on a time-out the script runs `docker rm -f toki-migrate-<tag>`, checks that no container of that name is left, and only then exits 4; when the container cannot be removed it exits 4 with the text that a migration may still be running and that the operator must look at it before another deploy (a stale container of that name from an earlier crash is removed at the start of this step). A migration that fails or runs past the limit exits 4, names the step and says that the running release was not touched; the output is in `deploy.log` (R8). The database is as the Drizzle migrator leaves it, which the text does not call unchanged: the pending migrations run in one transaction, so a failure in that step changes nothing (TOKI-005 R7), but the queue schema step runs after that transaction, and a failure there leaves the new tables in place (TOKI-084 R13; it is idempotent, so the next `migrate` completes it). The migration step is not run twice for one request by this script; the service runs again, with nothing to do, when the switch brings the stack up (R11; TOKI-084 R13 expects exit 0). Check: `toki-deploy.test.sh`: a fake `migrate` that exits 1 gives exit 4, no `up`, no change in `.env`, in the installed Compose file or in `releases.log`; one that outlasts the limit (the fake returns the time-out status the script reads from `timeout`, no real wait) gives exit 4 with the same state, and the fake records `rm -f toki-migrate-<tag>` and shows no container of that name left; a fake whose removal fails gives exit 4 with the text about a migration that may still run; the fake records `--no-deps` on the `run`, and with `postgres` running records no `up` and no recreate of `postgres` before the switch; with `postgres` not running it records the one `up -d --wait postgres`; one that exits 0 is followed by the switch and the fake records the `run` before the first `up` of the switch. `tools/deploy/check.sh` (R20) deploys a release against a real database, then a release whose migration is broken and shows the running release unchanged and the database as the migrator leaves it.
- R11. The switch and the proof that it worked. After R10 the script (1) records the running release when none is recorded (R12, the baseline), (2) installs the staged Compose file (written as a new file and renamed, so `docker-compose.prod.yml` is never half written) and the staged copy under `releases/<new tag>/` together with a file `registry` that holds the registry of the release, (3) sets the two lines of R8, (4) runs `docker compose -f docker-compose.prod.yml up -d --no-build` in `$TOKI_HOME` under `timeout` (`TOKI_UP_SECONDS`, 240, a starting value: with `caddy` waiting for `server` to be healthy, `up -d` itself waits and exits non-zero when `server` becomes unhealthy) (Compose recreates the services whose image or values changed, and stops each with its own period, TOKI-084 R23; no `kill`, no `--timeout 0`, no `rm -f`, no `down`), then (5) checks, polling every 5 seconds for at most 180 seconds for the first, and 60 seconds for the last (the figure of TOKI-084 R22, one line each: `TOKI_HEALTH_SECONDS`, `TOKI_HTTPS_SECONDS`): the container of `server` is `healthy`; the containers of `server`, `worker` and `caddy` run the images `toki-server:<tag>` and `toki-web:<tag>` of the request (so a container that was not recreated does not count); `migrate` exited 0; `worker` is running and has restarted 0 times (it has no health check, TOKI-084 concern 10, so a worker that exits at start and is restarted by Compose is seen here); when the image holds `dist/cli/jobs-status.js`, `docker compose exec -T server node dist/cli/jobs-status.js` exits 0 (the queue can be read, TOKI-064 R20); and `GET https://<host>[:<port>]/` answers 200 with a `text/html` content type and a certificate that the server's own system trusts (so with a real domain the certificate of TOKI-084 R18 is proved). `APP_DOMAIN` may carry a port (TOKI-084 R22's `names.env` has `localhost:18443`): the script splits it, the host is the part before `:`, the port is `HTTPS_PORT` when set, else the port of `APP_DOMAIN`, else 443, and the port is written in the address only when it is not 443. The check is skipped, with a line that says so, when the host is `localhost` or ends in `.localhost` (Caddy then uses its own authority, which no system trusts, TOKI-084 R18). A failure or time-out of `up -d` in step (4) is a failed check of step (5). ## Design
### The flow
```
merge to main ─▶ CI (push) ──passes──▶ Release (workflow_run)                  Deploy (workflow_dispatch, a person)
                                        │ build + push toki-server, toki-web          │ tag? ─ "" = main head, sha-… = that commit, previous
                                        │ ghcr.io/<owner>/  tag sha-<12>               │ images exist in the registry?  (no ─▶ stop)
                                        └ toki-minio:<release> when new                │ ssh (forced command) ──▶ toki-deploy on the VPS
                                                                                        │      preflight ▶ migrate (alone) ▶ switch ▶ checks
                                                                                        │      not healthy ▶ running release back (exit 5)
```
On the server `$TOKI_HOME` (`$HOME/toki`, the run directory of the guide) holds: `.env` (the operator's, mode 600), `docker-compose.prod.yml` (the current release's), `releases/<tag>/docker-compose.prod.yml` and `releases/<tag>/registry` (one pair per release put on this server, a few kilobytes each, never pruned), `releases.log`, `deploy.log` (mode 600, rotated) and `.deploy.lock`. `toki-deploy.sh` is installed once as a root-owned file (R19) and changes rarely: its request grammar and exit codes are R7 and R13, and `deploy-remote.sh` checks the grammar number before it sends anything (R6), so a workflow that needs a newer script stops with a plain text.

### Why migrations run first and alone
`up -d` would run `migrate` too (TOKI-084 R13), but by then Compose may already have recreated the web container with the new image while the server is kept (a failed `migrate` stops `up` and leaves `server` and `worker`, not necessarily `caddy`), so the page and the API could be of two releases. Running `migrate` of the new image first, before anything is recreated, leaves the running containers as they are when it fails (R10), and the old release keeps serving while it runs. The database is as the migrator leaves it: the Drizzle step is one transaction and the queue schema step is not (TOKI-084 R13). The price is that the old server and worker run against the new schema for the length of the migration and the restart; the compatibility rule of TOKI-005 concern 10 is the one that allows it, and nothing yet checks it (concern 13).

### What the key can do
GitHub holds a private key that the runner uses to open an SSH session as the deploy user. The server's `authorized_keys` line limits that key to `toki-deploy.sh`, whose request grammar is four words (R7): no shell, no forwarding, no terminal. That does not make the key "the script and nothing else" in effect, because the script runs `docker compose` as a user who can use Docker, which is root-equivalent, with a Compose file that the sender supplies on standard input and a tag the sender names. A holder of the key needs no change to `main`: they can send a file with `privileged: true`, a bind mount of `/`, or an image of their own. Three things keep that from being true. The server holds what the sender must not choose: the registry is a root-owned file and is not in the request (R7), the script is root-owned (R7), and the staged Compose file is refused when it has a host mount, extra privileges or an image outside the registry (R22). What remains after that is stated in R22: a chosen `command` or `environment` inside the application's own containers. So a leaked key is worth the application, its secrets and its data, and the ability to stop the site, not a shell on the host (if the list is right) and not an image from anywhere. Who can use the key is then the boundary: the Environment `production` with a deployment branch rule `main` (required, R19), the review of changes to `main` and the workflows, the pinned actions. TOKI-091 is asked to review that boundary first (Plan changes). What the owner is asked to accept is in concern 5.

### Errors
- A run from a branch other than `main` -> exit 1 with the reason (R4).
- A tag that has no image -> exit 3 on the runner, no connection (R6).
- The script on the server does not match the workflow -> exit 3, "update toki-deploy on the server", nothing sent (R6).
- The server cannot be reached or its host key does not match -> exit 10 (R6).
- `.env` missing, with the wrong mode, or lacking a name the release needs; a Compose file that R22 refuses; a registry file missing -> exit 3, the message names the file, the name or the key, nothing changed (R9, R22).
- The pull fails (registry down, tag missing, package private, disk full) -> exit 3, nothing changed (R9).
- A migration fails or runs too long -> exit 4, the running release is untouched, the log is in `deploy.log` (R10).
- The new release is not healthy, or `up -d` fails or runs too long -> the release that was running is restored, exit 5, a red run (R11, R12).
- The SSH connection drops during a deploy -> the script ignores the hang-up and closed pipes and runs to its end (R7); the run in GitHub is red or lost, and `status` or the last line of `releases.log` says the result.
- Two deploys at once -> the second exits 9 (R7). GitHub's `concurrency` group queues one run and cancels an older pending run when a third arrives (R4), so a cancelled request is sent again by a person.
- GitHub unavailable -> the operator runs `toki-deploy.sh` by hand on the server; the images are in the registry or already on the machine (the last three releases, R15).

## Testing
- Tests are written first. `pnpm deploy:test` has no Docker, no network and no timer: shell tests with fakes on `PATH` for the three scripts that run commands, and one node test that reads the workflow files and `docs/deploy.md` (the YAML reader that the compose-shape tests of TOKI-084 use). Polling is counted in calls of the injected `TOKI_SLEEP`, not measured in seconds; no test of this work waits on a real clock (the rule of TOKI-008), and nothing in `apps/` is touched.
- Every requirement above names its check. The negative controls are part of the checks: a fixture workflow with a literal secret (R18), a fake `docker` that fails at each step of R9 to R12, a tar with a bad name or too large (R9), one refused Compose file for each rule of R22, a registry in the request (R7), a SHA with an upper-case letter (R2, R6), a migration that outlasts its limit (R10), closed pipes during a deploy (R7), a `.env` with quotes and a duplicate name (R8).
- `pnpm deploy:check` is the one check that needs Docker. It proves with real containers and a real registry (a local one) that a release is pulled, migrated and switched, that a rollback leaves the data, that a broken migration leaves the running release, and that the stop of `server` and `worker` is clean.
- Fake values only: no secret in a committed file (the secrets of `check.sh` are made at run time), `example.test` addresses, a registry on `localhost`. No real server, no real key and no real domain is used.
- Not proved here: the GitHub side (the `workflow_run` hand-off, the Environment and its deployment branch rule, the secrets and the variables, the runner reaching the server over the Internet, the packages on `ghcr.io` and their visibility), and a real certificate in the check of R11. The first real deploy to the VPS proves them (NFR-07, with TOKI-087): the Environment and its branch rule made, the first release of `main` after the settings of `docs/deploy.md` are made, the three packages made public after that first release, then the first deploy (a hand-installed machine gets its baseline), then a rollback, then a deploy during a test session with a page open (NFR-17, with TOKI-104).

## Data safety
- No secret is in a workflow, a script, an image or the repository (R8, R18). The `.env` stays on the server. GitHub holds one key, a host, a user and two non-secret values.
- The key opens one script, but that script runs Docker; a leaked key is as sensitive as the `.env` and the database, and the checks of R22 and the rules of the Environment (R19) are what limit it, not the `command=` option alone (Goal, concern 5).
- The run log of a public repository holds no value of `.env`, no service log and no migration output (R8, concern 8), and masks the host and the user (R5).
- A rollback and a failed deploy never touch the database, the stored files or `.env` beyond two lines (R14, R10); a failed migration may leave the queue tables of TOKI-084 R13.
- Nothing here backs up the volumes: a lost disk loses the data, as D-092 accepts for phase 1.

## Areas of concern
1. The trigger of a deploy. D-190 ("Is a deployment started automatically when a pull request is merged, or by hand?") is Open in the log, and the text after its arrow, "By hand in phase 1, with one command", is a proposal and is not used as a fact here. Not decided. What does not depend on it and is built either way: the build on merge (the technical design says a merge builds an image, R1), the whole deploy and rollback (R4 to R16), and the manual trigger, which a rollback needs in any case. The only part that depends on it is whether a merge also starts `Deploy`: if the owner says automatic, release.yml gets one more job after `images`, `uses: ./.github/workflows/deploy.yml`, with `deploy.yml` also taking `on: workflow_call` and the tag of the release just built, `ALLOWED_DEPLOY_TRIGGERS` in the test of R4 gets `workflow_call`, and the Environment `production` can hold a required reviewer so that a person still approves each run; if the owner says by hand, nothing is added. The repository rule of `CLAUDE.md` is "ask before every deploy". Under the by-hand proposal the rule is kept as it is: a deploy runs only when a person starts `Deploy` with `gh workflow run` (or `toki-deploy.sh` on the server), `Release` publishes images and deploys nothing, and `docs/deploy.md` says that an agent session asks before it runs either (R19). If the owner chooses automatic, nobody starts the run, so the rule needs one of two changes that the owner picks: the Environment's required reviewer becomes the \"ask\" (a person approves each run in GitHub), or the sentence of `CLAUDE.md` is reworded for the automatic deploy; the spec does not choose. Proposal, marked as one: by hand in phase 1 (the log's own text), started with `gh workflow run deploy.yml`, because one server with no zero-downtime update (TOKI-084 concern 12) means every deploy drops the open connections, and the person who merged knows whether this is a good moment. Needs the product owner. Owner: Thanh Truong.
2. The registry. The Blueprint names none (TOKI-084 hands the registry to this ticket). Decided in this spec: the GitHub Container Registry, `ghcr.io/<owner>/`, with the job's own `GITHUB_TOKEN` and no extra credential (R3); the server pins its own registry (R7, R22). Reason: the repository already lives on GitHub, the push needs no secret that must be stored and rotated, and the package can be public or private without a second account. Docker Hub or a registry on the server itself would add an account or a service to keep. Owner: Thanh Truong.
3. What triggers the build and what it waits for. Decided in this spec: the release is built when the `CI` run of a push to `main` has passed, not on the push itself (R1). Reason: the images are published only from a commit whose full checks passed, `stack` included, and a red `main` publishes nothing; the cost is that a release exists a few minutes after the merge, and a commit whose CI failed has none. Owner: Thanh Truong.
4. The tag, and who may run the script. Decided in this spec: `sha-<12 hex>` (R2), with no version number and no moving tag. Reason: phase 1 has one installation and one stream of releases, so a number carries nothing the commit does not, a moving tag cannot be rolled back to, and the tag shows in `docker ps` and in the log as the commit. The same script runs from the deploy user by hand with the same four requests (R7), so a missing GitHub is not a missing deploy. Owner: Thanh Truong.
5. How secrets and access reach the server, and what a leaked key is worth. Not decided: this part changes how the deploy is secured, the log is silent on it, and the owner is asked to accept it. Proposal, marked as one: (a) no application secret is stored in GitHub: `.env` is created and changed on the server and the deploy edits two non-secret lines of it (R8); (b) the workflow reaches the server by SSH with one ed25519 key stored as a secret of the Environment `production`, the host key pinned, limited by `restrict,command=` to `toki-deploy.sh` (R5); (c) the server pulls images itself, with no stored credential (concern 6); (d) the key is not \"the script and nothing else\": the script runs Docker with a Compose file the sender supplies, so an unchecked key is root on the machine, and with the checks of R22 and a root-owned registry file and script (R7) it is the means to stop the application and to read its secrets and data through a chosen `command` or `environment` of the application's own containers (R22, Goal); (e) the checks are the cheap protection and the Environment's deployment branch rule `main` is required, not optional (R19), because the `main` guard of R4 is only an error message that a branch can remove; (f) the SSH port must be reachable from GitHub's runners, which have no fixed addresses, so the firewall opens the SSH port (`DEPLOY_PORT`, default 22) as well as 80 and 443 (TOKI-087 R4 opens `22/tcp`; `docs/deploy.md` says what to add for another port), with key login only and no password (`PasswordAuthentication no` and `AllowUsers` for the deploy user, which TOKI-087 does not write and `docs/deploy.md` holds, R19): this changes the Blueprint's statement that only 80 and 443 are open, and the owner is asked to accept the change. Reasons: a copy of the `.env` in GitHub would be a second place for every secret and would need the secret values to pass through a public repository's runner; the deploy needs none of them. A self-hosted runner on the VPS would remove the open SSH port, but it would run workflow code on the production machine for a public repository, which is worse. A pull model (a timer on the server) would be the automatic deploy that D-190 leaves open. What the owner is asked to accept: (i) that the key is as sensitive as the `.env` and the database, and is kept, rotated and limited as such (R19); (ii) the residue that R22 states, which is a list that can have a gap; (iii) the open SSH port. If the owner does not want (ii) accepted, the way to remove it is to send no Compose file and let the server use the one it has (the release's Compose file would then be fetched by the server from the registry or the repository, a larger change outside this ticket). TOKI-091 reviews all of this; TOKI-087 writes the firewall step with `22/tcp`. Needs the product owner. Owner: Thanh Truong.
6. Who may pull the images. Decided in this spec: the server holds no registry credential, so the packages are public, which the owner sets once per package on GitHub after the first release has created them (`toki-server`, `toki-web` and `toki-minio`; a package made by a push is private by default). The images hold no secret and no sample data (TOKI-084 R5 to R7) and are built from a public repository; `toki-minio` is MinIO built from its public source, which is published with them. The images carry the label `org.opencontainers.image.source`, so the package is linked to the repository and the run token can push later versions (R3). The workflow checks the images with the run's token (R6), which also passes for a private package, so a package that is still private shows at the pull of R9 step (7), whose text says so. If the owner keeps them private, the operator runs `docker login ghcr.io` once on the server with a read-only token; that is a standing credential on the server, outside this work, and the runbook says so. Owner: Thanh Truong.
7. The order of a deploy and the retry. Decided in this spec: preflight, then the migration alone, then the switch (Design), with no automatic retry of any step. Reason: a retry hides a real fault behind a second run, and every step is safe to run again by running the same deploy (a second `migrate` finds nothing to do, TOKI-084 R13; the pull and the preflight change nothing); a migration that fails once on a refused connection and works the next time is a re-run by a person. The 10-minute limit of the migration and the other starting values (3 GiB of free space, 180 and 60 seconds, 240 for `up -d`, the last 3 releases, 256 KiB, 5 MiB) are one line each and follow the sizes of TOKI-084 and TOKI-064, as TOKI-084 concern 8 does for its limits; they are not product figures. Owner: Thanh Truong.
8. The run log is public. Decided in this spec: the run log shows step names, tags, states, exit codes and names of missing variables only (R8), with the host and the user masked (R5). Migration output and service logs stay in `deploy.log` on the server. Reason: a public repository's Actions log can be read by anyone, a log line of the server can hold an email address (a sign-in, TOKI-022) or a path of a person's file, and the migration output holds table names. The operator reads those on the server. Owner: Thanh Truong.
9. What a rollback undoes. Decided in this spec: the release pair, meaning the two Toki images and the Compose file of the same commit, which carries the versions of Postgres and MinIO that release named; never the database, the volumes or the `.env` (R14). The rule of TOKI-005 concern 10 (a migration stays compatible with the previous image) is what makes this enough, and nothing checks it yet (concern 13). Two cases break it and are not detected by the script: a raise of the queue library, whose newer schema an older library refuses (TOKI-064 R3 says the release notes name it), and a release that raises the Postgres major version or MinIO to a release that its own data format no longer lets an older one read. For those the rollback, and the automatic return of R12, fail their checks (exit 7) and the fix is a new release; the text of exit 5 and exit 7 says that the schema may have changed and the restored release may not start. A bad migration is also fixed by a new release (a new migration), never by a down migration (TOKI-005 concern 10). Owner: Thanh Truong.
10. The gap during a deploy. Decided in this spec: no zero-downtime update and no promise of one (TOKI-084 concern 12). A deploy stops `server` and `worker` and, when its image changed, `caddy`; open pages reconnect (TOKI-039) and the queue retries unfinished jobs (R16). The migration step, which can be the longest part, runs while the old release still serves (R10). Owner: Thanh Truong.
11. The release identifier and the update strip. D-107 and NFR-17 want an open app to show 'Update available · Reload' after a deploy and to force the reload only when the server says the page is too old. Decided in this spec, for this ticket's side: `release.sh` builds both images with the same `TOKI_BUILD_ID`, the commit SHA (R3), which is the build argument TOKI-104 R2 reads (TOKI-084 R10 already has it), and the tag `sha-<12 hex>` stays the operator's name for the release (R17). Reason: the build id names the code, the tag names the release, and one value for both images means a page and a server of one release never disagree; a rollback gives the older value back, which an app compares for difference. Not done here: the Dockerfile `ARG`, the `define` in the web build, the socket frame and the compare, which are TOKI-104's and TOKI-084's. Owner: Thanh Truong.
12. The MinIO image. Decided in this spec: the release also builds and pushes `toki-minio:<release tag of Dockerfile.minio>` when that tag is not in the registry (R3), so the server never compiles MinIO (a build from source takes about 3 GB of disk, TOKI-084 R28, which a 4 GB machine cannot afford beside the application). No public image of MinIO under that name exists, so the registry is the only source; the server cannot pull it from Docker Hub. This needs the Compose file of TOKI-084 R24 to name the image with `${TOKI_REGISTRY:-}`, as it does for the other two; as written there it is `toki-minio:<tag>` with no prefix and says that no image of MinIO is published. That is a change request to TOKI-084 (Plan changes) and a precondition of this ticket: R22 refuses a Compose file without the prefix with a text that names the cause, so a deploy never fails by a pull of a name that does not exist, and the first deploy fails at once and plainly when the change is missing. Owner: Thanh Truong.
13. Keeping a migration compatible with the previous release. Not decided. R12 makes the return automatic and R14 depends on the rule of TOKI-005 concern 10 (a migration is forward-only and stays compatible with the previous image), but the rule is a README sentence and a habit of people, and no ticket checks it; a release whose migration is not compatible fails its health, is \"restored\", and the restored release fails too (exit 7, the data already migrated). Proposal, marked as one, for a later ticket and not built here: a CI check that fails on `DROP`, `RENAME`, `SET NOT NULL` or a column type change in a new migration SQL file unless the file carries an explicit marker, and a line in `releases.log` that says whether `migrate` had work to do. This ticket adds only the text of exit 5 and exit 7 (concern 9). The owner decides whether either check is wanted and which ticket owns it; today none does. Owner: Thanh Truong.
