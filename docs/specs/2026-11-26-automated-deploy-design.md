# Automated deploy design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/automated-deploy.md (Thanh Truong)
Ticket: TOKI-085

## Goal
TOKI-084 makes one installable unit: two images and one Compose file. This work moves a release onto the machine and off it again. It builds and publishes the two images from a commit of `main` whose CI run passed, puts a chosen release on the server with a script that checks the release before it touches the running one, runs the migrations first and alone, switches, waits for the server to be healthy, and returns to the previous release by itself when the new one does not become healthy. A bad release found later is rolled back with one command. The repository is public, so none of this may need a secret value in a workflow file or print a person's data in a run log: the application's secrets stay in the `.env` on the server, and GitHub holds one key that can start the deploy script and nothing else.

## Scope
- In: `.github/workflows/release.yml` (build and publish); `.github/workflows/deploy.yml` (deploy and rollback); `tools/deploy/` (`release.sh`, `deploy-remote.sh`, `toki-deploy.sh` and their tests, the check of the whole flow `check.sh`); `docs/deploy.md`; the section "How secrets are kept, Production" and the "Supplied by" of two rows in `docs/environment-config.md`; one new CI job and one new name in `.github/scripts/changed.sh`; the root scripts `deploy:test` and `deploy:check`.
- Out (not now):
  - Whether a merge starts the deploy by itself: D-190, open (concern 1). Everything below is built and works with the deploy started by a person; the automatic start is one added job (concern 1).
  - The image, the Compose file, the Caddyfile, the health check, the migration service, the stop periods and the operator commands: TOKI-084. This work runs them and changes none.
  - Installing Docker, creating the user and the directory on a fresh server, DNS, the firewall: TOKI-087, which follows the facts fixed in `docs/deploy.md` (R19) and writes no second list.
  - A review of the key, the Docker group, the Actions permissions and the exposed SSH port: TOKI-091 (concern 5 lists what it receives).
  - Backup and restore of volumes or of `.env`: deferred (D-092). A rollback never restores data (R14).
  - Zero-downtime updates, several servers, blue-green or canary releases: not phase 1 (TOKI-084 concern 12; technical design).
  - The update strip and the server's "page too old" answer: TOKI-104 (R17, concern 11).
  - Signing or attesting images, scanning them for known flaws: TOKI-091.

## Requirements
- R1. The release workflow. `.github/workflows/release.yml` (name `Release`) has one trigger, `workflow_run` of the workflow named `CI` (`types: [completed]`), and its job `images` runs only when `github.event.workflow_run.conclusion == 'success'`, `github.event.workflow_run.head_branch == 'main'` and `github.event.workflow_run.event == 'push'`; so an image is built only from a commit of `main` whose whole CI run (the `stack` job of TOKI-084 R28 included, which a push to `main` always runs) passed. It checks out `github.event.workflow_run.head_sha`. `permissions` is `{}` at the top of the file and `contents: read` and `packages: write` on the job `images` only. The `concurrency` group is `release` with `cancel-in-progress: false`, so every commit of `main` gets its release. The workflow has no `pull_request`, `pull_request_target`, `issue_comment` or `workflow_dispatch` trigger (a failed release is started again with "Re-run" of its run). Check: `tools/deploy/workflows.test.mjs` (R20) reads the file and asserts each of these; it also asserts that the `name` of `ci.yml` is `CI`, so a rename of that workflow fails the test and does not silently stop releases.
- R2. The release tag. The tag of a release is `sha-` followed by the first 12 characters of the commit's SHA-1 in lower case, for example `sha-0123456789ab`. `tools/deploy/release.sh <sha>` prints it; a SHA that is not 40 hexadecimal characters exits 2 and prints nothing else. The server image and the web image of one commit carry the same tag (TOKI-084 concern 4). No tag is `latest` and no moving tag is written. A tag is immutable: when `toki-server` and `toki-web` both already exist in the registry under the tag, `release.sh` builds and pushes nothing and exits 0 saying so (a re-run of a finished release changes no image); when only one exists, it builds and pushes both. Check: `tools/deploy/release.test.sh` with a fake `docker` on `PATH`: the tag of a known SHA; a short SHA, an upper-case SHA and an empty argument exit 2; with both images present the fake records no `build` and no `push`; with one missing it records both pushes; no recorded call carries the tag `latest`.
- R3. What a release publishes. The registry is the GitHub Container Registry, `ghcr.io/<owner>/`, with `<owner>` the repository owner in lower case; that string, ending in `/`, is `TOKI_REGISTRY` (TOKI-084 R10 and R26) (concern 2). `release.sh` logs in with the job's own `GITHUB_TOKEN` (no other credential) and runs, with `TOKI_REGISTRY` and `TOKI_TAG` set in the environment of the command and `--env-file tools/stack/test.env` (the fake values of TOKI-084 R22, so Compose can read the whole file; no value of that file is written into an image, TOKI-084 R6 and R27), `docker compose -f docker-compose.prod.yml build caddy server` and `docker compose -f docker-compose.prod.yml push caddy server`: the same Compose file and the same build sections the server will run from, so the names cannot differ (TOKI-084 R10; the service `caddy` is the image `toki-web`, the service `server` is `toki-server`). The MinIO image of `Dockerfile.minio` is built and pushed too, as `toki-minio:<release tag of that file>` under `TOKI_REGISTRY`, only when that tag is not yet in the registry (the image is rebuilt only when MinIO's release changes, and the server never compiles it, concern 12). The login token is passed by `--password-stdin`, never as an argument. Check: `release.test.sh`: the recorded calls are the build and the push of the two services with the registry prefix and the tag, in that order, with the env file named; the login call has no password in its arguments; with the MinIO tag already present the fake records no MinIO build; a build that fails makes the script exit non-zero and records no push of the image it failed on.
- R4. The deploy workflow. `.github/workflows/deploy.yml` (name `Deploy`) has the trigger `workflow_dispatch` with one input `tag` (string, not required, default empty), and no other trigger (concern 1). Its job `deploy` has `environment: production`, `timeout-minutes: 30` and `permissions` of `contents: read` and `packages: read`; it runs only when `github.ref == 'refs/heads/main'` (a run started from another branch fails at once with that reason); its `concurrency` group is `deploy-production` with `cancel-in-progress: false`, because stopping a deploy half way is worse than waiting. The input reaches the shell only through `env:` (the workflow rules) and is validated by R6 before any use. Check: `workflows.test.mjs`: the trigger set is exactly `workflow_dispatch`; the three properties above; no `${{ github.event.inputs` or `${{ inputs` inside a `run:` value; the guard is present.
- R5. Only the key and three variables. The job reads the GitHub Environment `production`: one secret, `DEPLOY_SSH_KEY` (a private key made for this purpose only), and three variables that are not secrets, `DEPLOY_HOST`, `DEPLOY_USER` and `DEPLOY_KNOWN_HOSTS` (the host key line of the server). The other credential in the job is the `GITHUB_TOKEN` of the run. The runner writes the key to a file in `RUNNER_TEMP` created under `umask 077`, calls ssh with `-o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=<a file made from DEPLOY_KNOWN_HOSTS>` and `-o ServerAliveInterval=30` (no `ssh-keyscan` and no first-use trust, which would accept an attacker's server), and removes both files in a step with `if: always()`. The key's public half sits in the deploy user's `authorized_keys` with the options `restrict,command="<path of toki-deploy>"` (R9), so the key can start that script and nothing else: no shell, no port forwarding, no agent forwarding, no terminal. Check: `workflows.test.mjs`: every `secrets.` name in both workflows is `DEPLOY_SSH_KEY` or `GITHUB_TOKEN`, and every `vars.` name is one of the three; `deploy-remote.test.sh` with a fake `ssh`: the recorded arguments hold each option above, the key file has mode 600 when the fake runs and does not exist after the script ends (also when the fake fails), and the key text is in no output.
- R6. Which release a run deploys. `tools/deploy/deploy-remote.sh` is what the job runs; it takes the input as an argument. (a) Empty: the release of the head commit of `main` (its R2 tag). (b) `sha-` and 12 lower-case hexadecimal characters: that release; the commit is found in the checkout (`fetch-depth: 0`) and must be an ancestor of `main`'s head, so no unmerged work can be deployed. (c) `previous`: the previous release on the server (R14). Anything else exits 2 before any command is run. For (a) and (b) it logs in to the registry with the run's token, checks that `toki-server` and `toki-web` exist under the tag and fails with exit 3 and the text "no image for this release; the Release workflow has not finished or failed" when one is missing, all before it connects to the server. It then sends the server `deploy <tag> <registry>` with the file `docker-compose.prod.yml` of that same commit as a tar stream on standard input (a release is the pair of its images and its Compose file, so a release that adds a name or a service brings the file that goes with it). For (c) it sends `rollback` and nothing on standard input. Check: `deploy-remote.test.sh` with fake `git`, `docker` and `ssh`: the three forms send the right command and, for (a) and (b), a tar that holds exactly `docker-compose.prod.yml` of the right commit (the fake `git` serves two different files for two commits); a commit that is not an ancestor of `main`, a tag of the wrong shape, `sha-0123456789AB`, `sha-0123456789ab; id` and `latest` exit 2 with no `ssh` call; a missing image exits 3 with no `ssh` call.
- R7. The server script and its commands. `tools/deploy/toki-deploy.sh` runs on the server as the deploy user and is the forced command of R5. It reads its request from `SSH_ORIGINAL_COMMAND` when set and from its own arguments otherwise (so the operator can run it by hand, concern 4), and accepts exactly: `deploy <tag> <registry>`, `rollback`, and `status`. `<tag>` matches `^sha-[0-9a-f]{12}$` and `<registry>` matches `^[a-z0-9.-]+(:[0-9]+)?(/[a-z0-9._-]+)*/$` (it ends with `/`); the request is split into words and never passed to a shell for evaluation. A request that is anything else exits 2 before any other command runs. `TOKI_HOME` (default `$HOME/toki`) is the directory that holds `.env` and `docker-compose.prod.yml` (TOKI-084 R27); `COMPOSE_PROJECT_NAME` is honoured when set (the check of R20 uses it). `status` prints the current tag, the previous tag and the state of the services (name, state, health), and nothing from `.env`. Every call of Compose names `--project-directory $TOKI_HOME` and `--env-file $TOKI_HOME/.env`, so the operator's `.env` is the one read even for the staged Compose file. The script ignores `SIGHUP` and `SIGPIPE` and writes each step line to `$TOKI_HOME/deploy.log` as well as to standard output, so an SSH session that drops does not stop a deploy half way. One run at a time: the script takes an exclusive lock on `$TOKI_HOME/.deploy.lock` and a second run exits 9 at once, saying that another deploy is running. Check: `toki-deploy.test.sh` (R20), with a fake `docker`, `curl` and `df` on `PATH`, a temporary `TOKI_HOME` and an injected `TOKI_SLEEP` (so no test waits on a timer): the three forms are accepted; `deploy sha-0123456789ab`, `deploy sha-0123456789ab ghcr.io/x/; id`, `deploy latest ghcr.io/x/`, `rollback now`, an empty request and `bash` exit 2 and the fake records no call; a second run started while the first holds the lock exits 9 and changes nothing; a `SIGHUP` sent to the script by the fake `docker` in the middle of a deploy does not stop it: it ends with exit 0 and the `live` line, and `deploy.log` holds the step lines.
- R8. What the script does with `.env`, and what it prints. The script never prints, copies or sends `.env`, never runs `docker compose config` without `-q`, and reads exactly four names from it by exact name match: `APP_DOMAIN` and `HTTPS_PORT` (for the check of R12), and `TOKI_TAG` and `TOKI_REGISTRY` (it writes these two). It changes `.env` in one way only: it replaces the lines `TOKI_TAG=` and `TOKI_REGISTRY=` (adds them at the end when missing) through a new file in the same directory that keeps the owner and the mode, then renames it over `.env` (concern 5). Its standard output and standard error hold only step names, tags, container states, exit codes and the names of missing variables, because the run log of a public repository is public (concern 8): the output of `docker compose pull` and `up` (image and container names, no value) may pass; the output of the migration step and the logs of the services are written to `$TOKI_HOME/deploy.log` (mode 600) and never to the run log. Check: `toki-deploy.test.sh` with an `.env` that holds the marker values `SECRET-MARKER-DB`, `SECRET-MARKER-SMTP` and `SECRET-MARKER-VAPID`, whose fake `docker` writes the whole environment it was given and the content of `.env` to its own output when asked to run `migrate`: after a successful deploy and after a failed one, the markers are in neither standard stream of the script and not in `releases.log`; the migrate output, markers included, is in `deploy.log` and nowhere else outside `.env`; `.env` after the deploy differs from `.env` before it in the two named lines only (`diff` shows nothing else) and keeps its mode 600; every other line, comments and blank lines included, is byte-identical.
- R9. Before anything changes (the preflight). In this order, and each failure exits 3 with the reason and leaves the running release, `.env`, the installed Compose file and `releases.log` exactly as they were: (1) `$TOKI_HOME/.env` exists and its mode is 600, else the text names the file and the mode; (2) the Compose file from standard input is exactly one file named `docker-compose.prod.yml` (a tar with another name, a path with `..` or `/`, a link or a second entry is refused) and is written to a staging directory; (3) `docker compose -f <staged file> config -q`, run with `TOKI_TAG` and `TOKI_REGISTRY` of the request, succeeds, so a name that the new release needs and `.env` lacks stops the deploy here with Compose's own message that names it (TOKI-084 R11); (4) the free space of the file system that holds Docker's data is at least 3 GiB (a starting value, one line to change, `TOKI_MIN_FREE_MB`); (5) `docker compose pull caddy server minio` of the staged file succeeds, so a deploy never starts with an image missing and the disk fills only by images that exist. Check: `toki-deploy.test.sh`: one case per step makes the fake fail at that step; each exits 3, the fake records no `up`, no `run` and no `rm`, and `.env`, `docker-compose.prod.yml` and `releases.log` are byte-identical to what they were; the three malformed tars of step (2) are refused.
- R10. Migrations first, and alone. After the preflight and before any running container changes, the script runs the migration service of the new release once: `docker compose -f <staged file> run --rm migrate` (it starts only `postgres` as its dependency, TOKI-084 R13; the old `server`, `worker` and `caddy` keep running) with a limit of 10 minutes (the queue schema step waits for at most 5 minutes by itself, TOKI-064 R3, and a migration needs time besides; a starting value, `TOKI_MIGRATE_MINUTES`). A migration that fails or runs past the limit exits 4, names the step and says that the running release was not touched; the output is in `deploy.log` (R8). The database is as the Drizzle migrator leaves it: the pending migrations run in one transaction, so a failed run changes nothing (TOKI-005 R7); the queue schema step changes the library's own schema only when it can finish (TOKI-064 R3). The migration step is not run twice for one request by this script; the service runs again, with nothing to do, when the switch brings the stack up (R11; TOKI-084 R13 expects exit 0). Check: `toki-deploy.test.sh`: a fake `migrate` that exits 1 gives exit 4, no `up`, no change in `.env`, in the installed Compose file or in `releases.log`; one that outlasts the limit (the fake returns the time-out status the script reads from `timeout`, no real wait) gives exit 4 with the same state; one that exits 0 is followed by the switch and the fake records `run --rm migrate` before the first `up`. `tools/deploy/check.sh` (R20) deploys a release against a real database, then a release whose migration is broken and shows the database and the running release unchanged.
- R11. The switch and the proof that it worked. After R10 the script (1) records the current tag and installed Compose file under `$TOKI_HOME/releases/<current tag>/` when that directory is missing, (2) installs the staged Compose file (written as a new file and renamed, so `docker-compose.prod.yml` is never half written) and the staged copy under `releases/<new tag>/`, (3) sets the two lines of R8, (4) runs `docker compose -f docker-compose.prod.yml up -d` in `$TOKI_HOME` (Compose recreates the services whose image or values changed, and stops each with its own period, TOKI-084 R23; no `kill`, no `--timeout 0`, no `rm -f`, no `down`), then (5) checks, polling every 5 seconds for at most 180 seconds for the first, and 60 seconds for the last (the figure of TOKI-084 R22, one line each: `TOKI_HEALTH_SECONDS`, `TOKI_HTTPS_SECONDS`): the container of `server` is `healthy`; the containers of `server`, `worker` and `caddy` run the images `toki-server:<tag>` and `toki-web:<tag>` of the request (so a container that was not recreated does not count); `migrate` exited 0; `worker` is running and has restarted 0 times (it has no health check, TOKI-084 concern 10, so a worker that exits at start and is restarted by Compose is seen here); when the image holds `dist/cli/jobs-status.js`, `docker compose exec -T server node dist/cli/jobs-status.js` exits 0 (the queue can be read, TOKI-064 R20); and `GET https://<APP_DOMAIN>/` (the port `HTTPS_PORT` when it is not 443) answers 200 with a `text/html` content type and a certificate that the server's own system trusts (so with a real domain the certificate of TOKI-084 R18 is proved). The check is skipped, with a line that says so, when `APP_DOMAIN` is `localhost` or ends in `.localhost` (Caddy then uses its own authority, which no system trusts, TOKI-084 R18). When all hold, it appends `<UTC time> <tag> live` to `$TOKI_HOME/releases.log`, removes images by R15, prints `deployed <tag>` and exits 0. Check: `toki-deploy.test.sh` with fakes: the order of the recorded calls (preflight, `run --rm migrate`, install, `up -d`, the checks); the poll limits are counted in `TOKI_SLEEP` calls (36 and 12), not in time; a fake whose `server` never becomes healthy, one whose container runs the old image, one whose `worker` restarted once, one whose `jobs-status` exits 1 and one whose HTTPS answer is 502 each fail the step that names them; the installed Compose file is the staged one byte for byte and no temporary file is left in `$TOKI_HOME`.
- R12. A release that does not become healthy is replaced by the previous one. When a check of R11 fails after step (2), the script restores the previous release (the Compose file stored under `releases/<previous tag>/` and the two lines with the previous tag and registry), runs `up -d` and the same checks, appends `<time> <failed tag> failed` and `<time> <previous tag> live`, prints that the release failed and that the previous one was restored, and exits 5; a deploy is therefore a red run in GitHub even when the site is back on the previous release. When there is no previous release (the first one on this server) it leaves the stack as it is, appends `failed`, and exits 6. When the return itself fails its checks it exits 7 and prints `docker compose ps` (states only) so the operator knows to act by hand. The previous release is the latest `live` line of `releases.log` whose tag differs from the current tag, and the current one is the last `live` line. Check: `toki-deploy.test.sh`: a failure at each check of R11 with a previous release gives exit 5, the installed file, `.env` lines and `releases.log` match the previous release, and the fake records the second `up -d` with the previous tag; with no previous release exit 6 and nothing restored; a fake that also fails the return gives exit 7.
- R13. The exit codes are one table, which `docs/deploy.md` copies (R19): 0 deployed or rolled back; 1 an unexpected error of the script (no step of R9 to R12 was reached, or the script's own failure; its message says which step); 2 request refused; 3 preflight failed, nothing changed; 4 migration failed, nothing changed; 5 not healthy, previous release restored; 6 not healthy, no previous release; 7 not healthy and the return failed; 8 `rollback` with no previous release; 9 another deploy is running. `deploy-remote.sh` and the workflow pass the code through, so the run is green only for 0. Check: `toki-deploy.test.sh` reaches each code at least once; `workflows.test.mjs` asserts no `continue-on-error` and no `|| true` in either workflow; the test of R19 reads the table out of `toki-deploy.sh` and compares it with the one in `docs/deploy.md`.
- R14. Rollback: what it undoes. `toki-deploy.sh rollback` makes the previous release current again (the release pair of R12) and nothing else: it installs the Compose file kept under `releases/<previous tag>/`, sets the two lines of R8, runs `up -d` and the checks of R11, and appends `<time> <tag> live`. It never changes the database (no down migration exists, TOKI-005 concern 10; the older `migrate` finds nothing pending and changes nothing, TOKI-084 R13), the volumes (`postgres-data`, `minio-data`, `caddy-data`, `caddy-config`), or any line of `.env` except the two. The script's code holds no call of `docker volume`, `down`, `system prune`, `volume prune` or `exec` with `psql`. When no previous release exists it exits 8. A second `rollback` returns to the release that was rolled back from, because the previous release is by definition the latest other `live` one. A release that cannot be rolled back, because it changed the schema of the queue library or the data format of a service in a way the previous image refuses, is the case that TOKI-064 R3 and TOKI-005 concern 10 already put in that release's notes; the rollback then fails its checks and exits 7 (concern 9). Check: `toki-deploy.test.sh`: after two deploys `rollback` leaves the Compose file and tag lines of the first, `releases.log` shows the flip, and none of the forbidden calls was recorded (a search of the script's source and of the fake's record); `check.sh` proves it on a real stack with a marker row and a marker file kept through deploy, rollback and a second rollback.
- R15. Old images. After a release is `live` the script removes the images `toki-server` and `toki-web` of every tag that is not one of the last 3 distinct `live` tags of `releases.log`, and runs `docker image prune -f` (dangling images only); it removes no other image (`postgres`, MinIO and the base images stay) and no volume, so the 80 GB disk does not fill with releases while the previous release stays on the machine for a rollback that needs no registry. A removal that fails (an image in use) is reported and never fails the deploy. Check: `toki-deploy.test.sh`: five `live` lines give the removal of the two oldest tags of both images and none of the others; `docker image prune` is called without `-a`; the fake records no `rmi` of `postgres` or MinIO images.
- R16. Jobs and open pages during a deploy. The script adds nothing of its own: the worker is stopped by Compose with `stop_grace_period` 40 s after `SIGTERM`, stops taking jobs, waits up to 30 s for the running ones, and exits 0 (TOKI-064 R15, TOKI-084 R23); a job that did not finish is not marked complete and is retried after its `expireSeconds` by the queue (TOKI-064 R8), so a deploy loses no job and may run an unfinished one twice, which is the at-least-once rule of that module. The server stops with its 20 s period; open pages lose the WebSocket for the seconds the restart takes and recover through the reconnect flow (TOKI-084 concern 12, TOKI-039). During the migration of R10 the old server and the old worker still run against the new schema: that is the compatibility rule of TOKI-005 concern 10, which every migration already meets. Check: `check.sh` records `docker events` during a deploy of the real stack and finds, for each recreated `server` and `worker` container, a `die` event with `exitCode=0` before its `start` event of the new one; the script's calls hold no `kill` and no `--timeout`.
- R17. The release identifier. What a deploy changes, and what an open app can compare, is the release tag: `sha-<12 hex>` (R2), the same for the server and the web app of one release. It is set as `TOKI_TAG` for the Compose file (R8), so TOKI-084 can give it to the build as an argument and to the server as a value (concern 11). It has no order: a rollback sets it back to an older value, so a client of TOKI-104 compares for difference and never for "newer". Check: `check.sh`: after deploy B then rollback, `TOKI_TAG` in `.env` and the image names of the running `server` and `caddy` are release A's; `release.test.sh` pins the shape of the tag.
- R18. No secret in a file. No file of `.github/workflows/` and `tools/deploy/` holds a secret value: no private key block, no token, no password, no value of any name of `.env.example`, no address of a person. The names the workflows may read are the ones of R5. A value that a person must supply (the key, the host, the user) is read from the Environment and not written. Check: `workflows.test.mjs` fails on a line of the two workflows that matches `-----BEGIN`, `ghp_`, `github_pat_`, `AKIA`, a `password=` or `token=` with a literal value, an address that has the form of an email, or any name of `.env.example` (the workflows read none); it is shown to fail by a fixture workflow that carries each of them (a negative control). The same scan runs over the files of `tools/deploy/` that are not tests, where the only names of `.env.example` allowed are the four of R8 (`APP_DOMAIN`, `HTTPS_PORT`, `TOKI_TAG`, `TOKI_REGISTRY`); the fake and marker values live in the test files, which the scan skips by name.
- R19. The runbook. `docs/deploy.md` has these sections, and nothing else that TOKI-087's guide or `.env.example` already says: Setup once (the deploy user and its group, the directory `TOKI_HOME`, the line of `authorized_keys` of R5 with the path of the script, how `toki-deploy.sh` gets onto the server and is updated, that SSH must be reachable from GitHub's runners with a key and no password, the Environment `production` with its secret and three variables, the branch rule, and the visibility of the packages: concerns 2, 5 and 6, which settings are the owner's); Deploy (`gh workflow run deploy.yml`, with `-f tag=sha-<12 hex>` for another release); Roll back (`gh workflow run deploy.yml -f tag=previous`, and by hand on the server `toki-deploy.sh rollback`); Change a value of `.env` (edit the file on the server, then `docker compose -f docker-compose.prod.yml up -d` as TOKI-084's command table says; Compose recreates the services whose values changed); Rotate the key; What the run log shows and where the rest is (`$TOKI_HOME/deploy.log`, `docker compose logs`); the exit table of R13; what a rollback does not undo (R14). TOKI-087's guide links to it for these facts and does not repeat them. Check: `workflows.test.mjs` fails when the file lacks one of the sections, when a secret or variable name used by a workflow is not in the file, or when the exit table differs from R13's.
- R20. ## Design
### The flow
```
merge to main ─▶ CI (push) ──passes──▶ Release (workflow_run)                  Deploy (workflow_dispatch, a person)
                                        │ build + push toki-server, toki-web          │ tag? ─ "" = main head, sha-… = that commit, previous
                                        │ ghcr.io/<owner>/  tag sha-<12>               │ images exist in the registry?  (no ─▶ stop)
                                        └ toki-minio:<release> when new                │ ssh (forced command) ──▶ toki-deploy.sh on the VPS
                                                                                        │      preflight ▶ migrate (alone) ▶ switch ▶ checks
                                                                                        │      not healthy ▶ previous release back (exit 5)
```
On the server `$TOKI_HOME` holds: `.env` (the operator's, mode 600), `docker-compose.prod.yml` (the current release's), `releases/<tag>/docker-compose.prod.yml` (one per release put on this server, a few kilobytes each, never pruned), `releases.log`, `deploy.log` (mode 600) and `.deploy.lock`. `toki-deploy.sh` is installed once beside them (R19) and changes rarely: its request grammar and exit codes are R7 and R13, so a newer workflow works with an older script until the grammar changes.

### Why migrations run first and alone
`up -d` would run `migrate` too (TOKI-084 R13), but by then Compose may already have recreated the web container with the new image while the server is kept (a failed `migrate` stops `up` and leaves `server` and `worker`, not necessarily `caddy`), so the page and the API could be of two releases. Running `migrate` of the new image first, before anything is recreated, makes a failed migration change nothing at all (R10), and the old release keeps serving while it runs. The price is that the old server and worker run against the new schema for the length of the migration and the restart; the compatibility rule of TOKI-005 concern 10 is the one that allows it.

### What the key can do
GitHub holds a private key that the runner uses to open an SSH session as the deploy user. The server's `authorized_keys` line limits that key to `toki-deploy.sh`, whose request grammar is three words (R7). The deploy user must be able to run Docker, and a member of the `docker` group can start a container with the host's file system mounted, which is as good as root on that machine. The forced command therefore protects against a leaked key being used as a shell; it does not protect against someone who can change `toki-deploy.sh` or the Compose file the workflow sends, which is anyone who can change `main` and the workflows. That boundary (the Environment's branch rule, the reviewers of a change to `main`, the pinned actions) is the real protection and is the first item TOKI-091 reviews (concern 5).

### Files
```
.github/workflows/release.yml      R1
.github/workflows/deploy.yml       R4, R5
.github/workflows/ci.yml           job `deploy check` (R20)
.github/scripts/changed.sh         name `deploy` (R20), and its test
tools/deploy/release.sh            R2, R3
tools/deploy/deploy-remote.sh      R5, R6
tools/deploy/toki-deploy.sh        R7 to R15
tools/deploy/check.sh              R14, R16, R17, R20
tools/deploy/*.test.sh, workflows.test.mjs   R2 to R21
docs/deploy.md                     R19
docs/environment-config.md         R21
```
In both workflows each `uses:` of the job that holds the key or the registry login is pinned to a full commit SHA with the version in a comment (the jobs of `ci.yml` use version tags and hold no credential; these two do), and no step runs code from the repository's pull requests: both start from `main` only (R1, R4). The workflow steps are one line each, `bash tools/deploy/<script>.sh`, so the logic is testable without GitHub (the rule of TOKI-007 R10).

### Errors
- A tag that has no image -> exit 3 on the runner, no connection (R6).
- `.env` missing, with the wrong mode, or lacking a name the release needs -> exit 3, the message names the file or the name, nothing changed (R9).
- The pull fails (registry down, tag missing, disk full) -> exit 3, nothing changed (R9).
- A migration fails or runs too long -> exit 4, nothing changed, the log is in `deploy.log` (R10).
- The new release is not healthy -> the previous one is restored, exit 5, a red run (R12).
- The SSH connection drops during a deploy -> the script ignores the hang-up and runs to its end (R7); the run in GitHub is red or lost, and `status` or the last line of `releases.log` says the result.
- Two deploys at once -> the second exits 9 (R7); GitHub's own `concurrency` group also queues them (R4).
- GitHub unavailable -> the operator runs `toki-deploy.sh` by hand on the server; the images are in the registry or already on the machine (the last three releases, R15).

## Testing
- Tests are written first. `pnpm deploy:test` has no Docker, no network and no timer: shell tests with fakes on `PATH` for the two scripts that run commands, and one node test that reads the workflow files and `docs/deploy.md` (the YAML reader that the compose-shape tests of TOKI-084 use). Polling is counted in calls of the injected `TOKI_SLEEP`, not measured in seconds; no test of this work waits on a real clock (the rule of TOKI-008), and nothing in `apps/` is touched.
- Every requirement above names its check. The negative controls are part of the checks: a fixture workflow with a literal secret (R18), a fake `docker` that fails at each step of R9 to R12, a tar with a bad name (R9), a SHA with an upper-case letter (R2, R6).
- `pnpm deploy:check` is the one check that needs Docker. It proves with real containers and a real registry (a local one) that a release is pulled, migrated and switched, that a rollback leaves the data, that a broken migration changes nothing, and that the stop of `server` and `worker` is clean.
- Fake values only: throwaway passwords from `tools/stack/test.env`, `example.test` addresses, a registry on `localhost`. No real server, no real key and no real domain is used.
- Not proved here: the GitHub side (the `workflow_run` hand-off, the Environment, the secret and the variables, the runner reaching the server over the Internet, the packages on `ghcr.io`), and a real certificate in the check of R11. The first real deploy to the VPS proves them (NFR-07, with TOKI-087): the first release of `main` after the settings of `docs/deploy.md` are made, then a rollback, then a deploy during a test session with a page open (NFR-17, with TOKI-104).

## Data safety
- No secret is in a workflow, a script, an image or the repository (R8, R18). The `.env` stays on the server; GitHub holds one key that opens one script (R5).
- The run log of a public repository holds no value of `.env`, no service log and no migration output (R8, concern 8).
- A rollback and a failed deploy never touch the database, the stored files or `.env` beyond two lines (R14, R10).
- Nothing here backs up the volumes: a lost disk loses the data, as D-092 accepts for phase 1.

## Open questions from the intent
- Is a deployment started automatically when a pull request is merged, or by hand? Not answered: D-190 is open in the log; the spec builds the by-hand path and keeps the other as one added job, concern 1.
- Where are the images stored, and under which tags? Answered: the GitHub Container Registry, one tag `sha-<12 hex>` for the server and web images (R2, R3, concerns 2 and 3).
- How does the server get the `.env`, and how does the deploy reach the server without a secret in the repository? Answered: the operator creates `.env` on the server and changes it there; GitHub holds one key limited to one script over SSH; the deploy edits two lines of the file and reads two more (R5, R8, R21, concern 5).
- What exactly does a rollback undo? Answered: the images and the Compose file of the release, and nothing else (R14, concern 9).
- How does a deploy change the version that an open app compares? Answered for this ticket: it changes the release tag, which has no order; how the app and the server carry and compare it is TOKI-104's (R17, concern 11).

## Areas of concern
1. The trigger of a deploy. D-190 ("Is a deployment started automatically when a pull request is merged, or by hand?") is Open in the log, and the text after its arrow, "By hand in phase 1, with one command", is a proposal and is not used as a fact here. Not decided. What does not depend on it and is built either way: the build on merge (the technical design says a merge builds an image, R1), the whole deploy and rollback (R4 to R16), and the manual trigger, which a rollback needs in any case. The only part that depends on it is whether a merge also starts `Deploy`: if the product owner says automatic, release.yml gets one more job after `images`, `uses: ./.github/workflows/deploy.yml`, with `deploy.yml` also taking `on: workflow_call` and the tag of the release just built, and the Environment `production` can hold a required reviewer so that a person still approves each run; if he says by hand, nothing is added. Proposal, marked as one: by hand in phase 1 (the log's own text), started with `gh workflow run deploy.yml`, because one server with no zero-downtime update (TOKI-084 concern 12) means every deploy drops the open connections, and the person who merged knows whether this is a good moment. Needs the product owner. Owner: Thanh Truong.
2. The registry. The Blueprint names none (TOKI-084 hands the registry to this ticket). Decided in this spec: the GitHub Container Registry, `ghcr.io/<owner>/`, with the job's own `GITHUB_TOKEN` and no extra credential (R3). Reason: the repository already lives on GitHub, the push needs no secret that must be stored and rotated, and the package can be public or private without a second account. Docker Hub or a registry on the server itself would add an account or a service to keep. Owner: Thanh Truong.
3. What triggers the build and what it waits for. Decided in this spec: the release is built when the `CI` run of a push to `main` has passed, not on the push itself (R1). Reason: the images are published only from a commit whose full checks passed, `stack` included, and a red `main` publishes nothing; the cost is that a release exists a few minutes after the merge. Owner: Thanh Truong.
4. The tag, and who may run the script. Decided in this spec: `sha-<12 hex>` (R2), with no version number and no moving tag. Reason: phase 1 has one installation and one stream of releases, so a number carries nothing the commit does not, a moving tag cannot be rolled back to, and the tag shows in `docker ps` and in the log as the commit. The same script runs from the deploy user by hand with the same three requests (R7), so a missing GitHub is not a missing deploy. Owner: Thanh Truong.
5. How secrets and access reach the server. Decided in this spec: (a) no application secret is stored in GitHub: `.env` is created and changed on the server and the deploy edits two non-secret lines of it (R8); (b) the workflow reaches the server by SSH with one key stored as a secret of the Environment `production`, the host key pinned, limited by `restrict,command=` to `toki-deploy.sh` (R5); (c) the server pulls images itself, with no stored credential (concern 6). Reasons: a copy of the `.env` in GitHub would be a second place for every secret and would need the secret values to pass through a public repository's runner; the deploy needs none of them. A self-hosted runner on the VPS would remove the open SSH port, but it would run workflow code on the production machine for a public repository, which is worse. A pull model (a timer on the server) would be the automatic deploy that D-190 leaves open. Costs, stated: the server's SSH port must be reachable from GitHub's runners, which have no fixed addresses, so the firewall that TOKI-087 writes opens 22 as well as 80 and 443, with key login only and no password (the Blueprint says only Caddy is reachable from the Internet: that is true of the application, and this is a second door for the operator that the deploy also uses); and the key is as strong as root on that machine for whoever can change `main` (Design, "What the key can do"). TOKI-091 reviews both; TOKI-087 writes the firewall step; the settings of the GitHub Environment (a deployment branch rule `main`, a required reviewer, which is optional) are the owner's, listed in `docs/deploy.md`, and no file of this work depends on them: the `main` guard is also in the workflow (R4). Owner: Thanh Truong.
6. Who may pull the images. Decided in this spec: the server holds no registry credential, so the packages are public, which the owner sets once per package on GitHub (the images hold no secret and no sample data, TOKI-084 R5 to R7, and are built from a public repository). The workflow checks the images with the run's token (R6). If the owner keeps them private, the operator runs `docker login ghcr.io` once on the server with a read-only token; that is a standing credential on the server, outside this work, and the runbook says so. Owner: Thanh Truong.
7. The order of a deploy and the retry. Decided in this spec: preflight, then the migration alone, then the switch (Design), with no automatic retry of any step. Reason: a retry hides a real fault behind a second run, and every step is safe to run again by running the same deploy (a second `migrate` finds nothing to do, TOKI-084 R13; the pull and the preflight change nothing); a migration that fails once on a refused connection and works the next time is a re-run by a person. The 10-minute limit of the migration and the other starting values (3 GiB of free space, 180 and 60 seconds, the last 3 releases) are one line each and follow the sizes of TOKI-084 and TOKI-064, as TOKI-084 concern 8 does for its limits; they are not product figures. Owner: Thanh Truong.
8. The run log is public. Decided in this spec: the run log shows step names, tags, states, exit codes and names of missing variables only (R8). Migration output and service logs stay in `deploy.log` on the server. Reason: a public repository's Actions log can be read by anyone, a log line of the server can hold an email address (a sign-in, TOKI-022) or a path of a person's file, and the migration output holds table names. The operator reads those on the server. Owner: Thanh Truong.
9. What a rollback undoes. Decided in this spec: the release pair, meaning the two Toki images and the Compose file of the same commit, which carries the versions of Postgres and MinIO that release named; never the database, the volumes or the `.env` (R14). The rule of TOKI-005 concern 10 (a migration stays compatible with the previous image) is what makes this enough. Two cases break it and are not detected by the script: a raise of the queue library, whose newer schema an older library refuses (TOKI-064 R3 says the release notes name it), and a release that raises the Postgres major version or MinIO to a release that its own data format no longer lets an older one read. For those the rollback fails its checks (exit 7) and the fix is a new release. A bad migration is also fixed by a new release (a new migration), never by a down migration (TOKI-005 concern 10). Owner: Thanh Truong.
10. The gap during a deploy. Decided in this spec: no zero-downtime update and no promise of one (TOKI-084 concern 12). A deploy stops `server` and `worker` and, when its image changed, `caddy`; open pages reconnect (TOKI-039) and the queue retries unfinished jobs (R16). The migration step, which can be the longest part, runs while the old release still serves (R10). Owner: Thanh Truong.
11. The release identifier and the update strip. D-107 and NFR-17 want an open app to show 'Update available · Reload' after a deploy and to force the reload only when the server says the page is too old. Decided in this spec, for this ticket's side: the identifier is the release tag, the same for the web app and the server of one release, written into `.env` by R8 and so available to Compose as `TOKI_TAG`; it has no order, so the comparison is "different from mine" and a rollback is seen as an update to the older page (R17). Not done here: putting the value into the web bundle and the server, and the compare itself: TOKI-104, with a build argument in TOKI-084's Dockerfile (a name that is not an inventory name, because TOKI-084 R27 forbids an `ARG` with one). Owner: Thanh Truong.
12. The MinIO image. Decided in this spec: the release also builds and pushes `toki-minio:<release tag of Dockerfile.minio>` when that tag is not in the registry (R3), so the server never compiles MinIO. This needs the Compose file of TOKI-084 R24 to name the image with `${TOKI_REGISTRY:-}`, as it does for the other two; as written there it is `toki-minio:<tag>` with no prefix, so the pull of R9 step (5) would look for it on Docker Hub. This is a requested change to TOKI-084 (Plan changes), not made here. Owner: Thanh Truong.
