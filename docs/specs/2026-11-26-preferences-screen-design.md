## Goal
A person must be able to make Toki theirs from one page and find the same choices on every device. After this change the page at `/prefs` holds Look, Accent, Density, the three notification switches with the device's push block, Pause notifications, Language, "Your status", the person's Profile (display name, job title, time zone) and the list of signed-in devices that TOKI-099 built. Every choice is saved to the account and applied at once with no reload, on this device and on every other open device. "Match my device" follows each device's own light or dark setting. A person whose saved look differs from the device's setting sees the saved look from the first paint of a visit. The time zone a person sets is the one colleagues read their local time from and the one every screen's dates follow (the date context of TOKI-080).
This ticket draws the page, applies look, accent, density and language to the page, owns the first-paint look, and says what it needs from the server ticket "Profile and preferences (server)", which has no ticket number yet.

## Design
### How the choices reach the page
```
press (look, accent, density, language, "Switch look")
  --> ensureOnline? no: explanation, nothing changes
  --> pending = chosen value ; shown = held + pending ; AppearanceHost: applyAppearance + theme-color + device copy
  --> save (PATCH of the server ticket)
        answer: sync.patchOwnPreferences(values, number) -> held value = answer ; pending cleared
        failure: pending cleared -> shown = held ; one toast
other device saves --> user event --> held value changes --> AppearanceHost applies it, no press here
```
The held value is the only copy of the account's choices on the client. `AppearanceHost` is the only place that touches the page's attributes, the bar colour, the device's copy and the language of the page; the sections only press and read.

### What the page reads, section by section

### Decided in this spec
- One held value, a layer of pending values over it, and a flag that allows one save at a time (R2, R7). Reason: "at once" (AC-120, AC-122) cannot wait for a round trip, a failure must not leave a false success (D-079), and a second press during a save would race the first (D-111). The cost is a short moment in which a control is not operable; a 100 ms save is not noticed.
- Not operable is `aria-disabled` and a handler that returns, not `disabled` (R7, R11): a native `disabled` button drops the keyboard focus to the page, which would put the person back at the top of a long page after each press.
- The device's copy of the appearance is a JSON value under one key, written only by `writeAppearanceCopy`, read by the script and by `main.tsx` (R8). Reason: the platform spec gives `storage.device` for a copy that serves the first paint, and an inline script is the only code that runs before the first paint without a build change. A change of the copy's shape changes `v`, so an old script with a new copy does nothing.
- The language of the interface is the held value, else the device's copy, else English; the copy is written at every change (R10), so the sign-in page, which has no account, speaks the last language used on the device (TOKI-023 concern 3).
- The date context and its zone are TOKI-080's; this ticket saves the zone and the context reads it (R17). Reason: TOKI-080 R5 to R9 build one hook and a lint rule that rejects a second copy, so a ticket that built its own `usePersonTimeZone` would have to be removed by it.
- No leave-the-page guard on the Profile form: D-070 is about closing a form, and an unsaved change on a settings page is lost by navigating away like any other unsaved field. The form shows no "unsaved" state. The save is one request with only the changed fields (R16).
- The Pause section shows a row for each running period, Focus first, and the chips whenever no Pause runs (R12; concern 10).

## Areas of concern
1. What a new account's look and density start as. Not decided. The accent starts as teal (tokens concern 2). The log gives no look and no density for a new account; D-175 says only that they are saved to the account; the prototype starts with no look chosen, which is Match my device, and no density chosen, so each look shows its own. The tokens spec (concern 1) says this blocks the Preferences screen. Proposal, not a decision: a new account has `look` `device` and `density` null, as the prototype starts; the Look and Density controls then mark Match my device and the density of the look that applies (R3, R5). The page draws whatever the first load holds, so the answer is a default of the server ticket and changes no rule here. Owner: Thanh Truong (product owner).
2. The longest job title. Not decided. D-033 gives the display name 1 to 80 characters; no decision gives a job title a limit, and the People card and the profile panel must fit it. Proposal, not a decision: the same 80 code points as the display name. R14 reads the limit from one constant of `@toki/shared`, `JOB_TITLE_MAX`, that the server ticket offers, so the answer is one number and changes no rule here. Owner: Thanh Truong (product owner).
3. The starting time zone and a city. Not decided. D-144 says the local time shown on a profile comes from the time zone the person set, and the profile panel's concern 1 asks whether the row shows an offset or a city; Preferences lists "time zone" and no city in F35. For a person who has set none, the devices' zone is the interim zone for the person's own screens (TOKI-056 concern 1, TOKI-076 concern 8, TOKI-094 concern 2), and a colleague sees no local time for them (TOKI-057 R7); TOKI-080 concern 1 asks the same question for its date context and proposes the same device zone. Proposal, not a decision: a new account has no saved zone, and the page says so under the select (R15), so a person who wants colleagues to see their local time chooses a zone; the zone is chosen from the names of the zone database with their UTC offsets, and no city field exists, which is the profile panel's proposal. The alternative is to save the device's zone when the account is created or at the first sign-in, so the field is never empty. Owner: Thanh Truong (product owner).
4. What the command "Switch look" does. Not decided. F29 lists it with no target look; the prototype's command toggles between Calm and Focus (line 2181) and has no "Match my device" in it; the palette spec's concern 8 leaves the effect to this ticket and is itself open. Proposal, not a decision: it saves the one of Calm and Focus that is not the look in use now, and when the look is Match my device it uses the look that the device gives now, so the command always changes what the person sees and ends with a fixed look (R20). R20 builds that; another answer changes one function. Owner: Thanh Truong (product owner).
5. What this ticket needs from "Profile and preferences (server)". Decided in this spec. The merged accounts spec (TOKI-019 concern 8, decided by the product owner on 2026-11-18) places a server ticket with that name before TOKI-078 and TOKI-057; it has no number in the plan; TOKI-102 builds only the three switches. This screen needs, and that ticket must offer: (a) the own values `displayName`, `jobTitle`, `timeZone`, `look`, `accent`, `density` and `language` in the bootstrap answer (a key of its own, next to `notificationPreferences`, strict, with the fixtures changed in the same ticket as TOKI-031 R12 asks), held in the conversation store with a getter, cleared by `reset()`, and the `jobTitle` and `timeZone` of every person in `BootstrapPerson` for TOKI-057 and TOKI-079; (b) one request that saves any non-empty subset of the seven keys, strict, answering the values that apply and the number of the event it wrote or null, with the rules of TOKI-102 R5 and R6 for a save that changes nothing and for two saves that overlap; the display name is trimmed, 1 to 80 code points and not only spaces (D-033), one function in `@toki/shared` that the screen also calls; the job title at most `JOB_TITLE_MAX` or null; the time zone `null` or a name accepted by `isValidTimeZone` of TOKI-094; `look` one of `calm`, `focus`, `device`; `accent` one of the four; `density` one of the two or null; `language` `en` or `vi`; a body with no key, another key or a wrong value is 400 `validation_failed` and writes nothing; (c) a user-scope event that carries all seven values with its number, applied by the same order rule as TOKI-102 R10, so the person's other devices change at once (F35), and the change `person_patch` of TOKI-056 R12 with `displayName`, `jobTitle` and `timeZone` for colleagues; (d) the client side: `api.members.savePreferences(body, signal?)` and `sync.patchOwnPreferences(values, number)` in `client-core`, the names used by R2; (e) `users.language` is the column that sign-in reads for the language of the mail (D-180) and the session for the person's language (TOKI-022 R55), so a saved language is the language of the next sign-in mail. The names in (a) to (d) are this spec's assumption of that ticket's names: when its spec uses others, only `preferences/deps.ts` and the type `OwnPreferences` change. Until the plan owner gives the ticket its number and puts it before TOKI-078 (Plan changes), no screen can save these values. Owner: Thanh Truong, for the plan.
6. The first paint, and what it cannot do. Decided in this spec: a copy of the last look, accent, density and language is kept on the device and read by one inline script in `index.html` before the first paint (R8); the same copy serves the sign-in page (TOKI-023 concern 3). Reason: the saved look is in the account, which is unknown until the first load; TOKI-015 concern 10 and the tokens spec (concern 10) give this to this ticket and suggest exactly this.
