## Goal
A person must be able to make Toki theirs from one page and find the same choices on every device. After this change the page at `/prefs` holds Look, Accent, Density, the three notification switches with the device's push block, Pause notifications, Language, "Your status", the person's Profile (display name, job title, time zone) and the list of signed-in devices that TOKI-099 built. Every choice is saved to the account and applied at once with no reload, on this device and on every other open device. A colour scheme, Light, Dark or "Match my device", is chosen next to the look, and "Match my device" follows each device's own light or dark setting: it is the scheme option `device` and not a look (was: "Match my device" was a look; TOKI-142). A person whose saved look and scheme differ from the device's setting sees their own from the first paint of a visit. The time zone a person sets is the one colleagues read their local time from and the one every screen's dates follow (the date context of TOKI-080).
This ticket draws the page, applies look, scheme, accent, density and language to the page, owns the first-paint look and scheme, and proposes what it needs from the server ticket "Profile and preferences (server)", which has no ticket number yet.

### Decided in this spec
- One held value and a layer of pending values over it (R2, R7). Reason: "at once" (AC-120, AC-122) cannot wait for a round trip, and a failure must not leave a false success (D-079). The one-save-at-a-time flag and the way a control shows it are proposals (below, concern 16).
- The device's copy of the appearance is a JSON value under one key, written only by `writeAppearanceCopy`, read by the script and by `main.tsx` (R8). Reason: the platform spec gives `storage.device` for a copy that serves the first paint, and a blocking script in `<head>` is the only code that runs before the first paint. It is a same-origin file, not inline text, because the content security policy of TOKI-091 forbids inline scripts. A change of the copy's shape changes `v`, so an old script with a new copy does nothing.
- The language of the interface is the held value, else the device's copy, else English; the copy is written at every change (R10), so the sign-in page, which has no account, speaks the last language used on the device (TOKI-023 concern 3).
- The date context and its zone are TOKI-080's; this ticket saves the zone, reads it through `useDateContext()` and builds no hook (R15, R17). Reason: TOKI-080 R5 to R9 build one hook and a lint rule that rejects a second copy. TOKI-078 needs TOKI-080 one way (Plan changes).
- No leave-the-page guard on the Profile form: D-070 is about closing a form, and an unsaved change on a settings page is lost by navigating away like any other unsaved field. The form shows no "unsaved" state. The save is one request with only the changed fields (R16).

### Proposal to the server ticket
The ticket "Profile and preferences (server)" has no number and no spec. The merged accounts spec (TOKI-019 concern 8) fixes that it exists and comes before TOKI-078 and TOKI-057, and nothing more. What follows is what this screen would use. Every line is proposed, not decided; the author of that ticket's spec decides, and when the names differ only `preferences/deps.ts` and the type `OwnPreferences` change (concern 5).
- (a) Proposed, not decided: the own values `displayName`, `jobTitle`, `timeZone`, `look`, `scheme`, `accent`, `density` and `language` in the bootstrap answer (was: seven values without `scheme`; TOKI-142) (a key of its own next to `notificationPreferences`, strict, with the fixtures changed in the same ticket as TOKI-031 R12 asks), held in the conversation store with a getter and cleared by `reset()`, and the `jobTitle` and `timeZone` of every person in `BootstrapPerson` for TOKI-057 and TOKI-079.
- (b) Proposed, not decided: one request that saves any non-empty subset of the eight keys, strict, answering the values that apply and the number of the event it wrote or null; a save that changes nothing answers with number null and a repeat of the same request is ignored, as TOKI-102 R5 and R6 do for the switches (D-111's second half); the display name trimmed, 1 to 80 code points, not only spaces (D-033), one function in `@toki/shared` that the screen also calls; the job title at most `JOB_TITLE_MAX` or null; the time zone `null` or a name accepted by `isValidTimeZone` of TOKI-094; `look` one of `calm`, `focus`, `classic` and `scheme` one of `light`, `dark`, `device`, except that a write with no `scheme` may carry `look` `calm`, `focus` or `device`, which the server stores as the look and removes the stored `scheme` (R28; was: `look` one of `calm`, `focus`, `device`); `accent` one of the four; `density` one of the two or null; `language` `en` or `vi`; a body with no key, another key or a wrong value is 400 `validation_failed` and writes nothing.
- (c) Proposed, not decided: a user-scope event that carries all eight values with its number, applied by the same order rule as TOKI-102 R10, so the person's other devices change at once (F35). For colleagues, `displayName`, `jobTitle` and `timeZone` reach `people` through a change. The `person_patch` of TOKI-056 R12 is `{ id, statusText, statusClearAt, number }` with one number kept for each patched person, so adding the three keys to it would make a profile change and a status change of one person share one ordering number, and a status event numbered 11 would be dropped after a profile event numbered 12. The proposal is therefore a separate change with its own number (for example `person_profile_patch`), or a `person_patch` whose number is kept for each group of keys; this is a change request to TOKI-056 and TOKI-040 (Plan changes), not something this spec decides.
- (d) Proposed, not decided: the client side `api.members.savePreferences(body, signal?)` and `sync.patchOwnPreferences(values, number)` in `client-core`, the names used by R2; with `number` null the store sets the values on the held value and records no order number.
- (e) Proposed, not decided: `users.language` is the column that sign-in reads for the language of the mail (D-180) and the session for the person's language (TOKI-022 R55), so a saved language is the language of the next sign-in mail.
