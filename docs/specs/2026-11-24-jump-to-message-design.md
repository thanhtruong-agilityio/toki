Needs: TOKI-041 (the page's `onOpenMessage`, `selectMessagesTab`, `openAt` of the kind `jump`, `data-target`; pull request 218), TOKI-045 (the plain function `openThread` and the push and replace rule, R16, which its current text exports for this ticket; pull request 214). ## Goal
Every screen that points at one message opens it the same way. One hook, `useOpenMessage()`, returns one function: given a conversation, a message and the message's parent, it opens the conversation at the message and flashes it for 2 seconds, or, for a reply, opens the thread panel of the root with the reply in view. The callers (the attachment window, the Files section and tab, the command palette, the search inside a conversation, and later Activity, Later and toasts) build no jump of their own.
This ticket builds the hook, the small store that carries a jump to a page that does not exist yet (a message of another conversation), the flash, and the lines that the page, the list row, the archived history and the route body add to read them. It builds no screen, no server code and no text.

## Scope
- In:
  - The hook `useOpenMessage()` and its one signature (R1), the provider and store that hold a pending jump and the flash (R2, R9), the cases of a message of the list in another conversation and in the open one (R3 to R5), the reply (R6), and the cases where the conversation draws something other than its page (R7, R8).
  - The flash: when it starts, how long it lasts, one at a time, the CSS (R9 to R11).
  - Offline and failed loads, and a deleted message (R12), the single-hook rule and the naming (R13), the wiring and the edits to files of other tickets (R14), the browser test (R15).
- Out (not now):
  - The screens that call the hook: the palette (TOKI-071), the search inside a conversation (TOKI-072), the attachment window (TOKI-062), the Files section and tab (TOKI-063), Pinned (TOKI-048, which calls the page's own `onOpenMessage`, R4), Activity (TOKI-066 owns the press of an item; TOKI-065 is the server and calls no hook), Later (TOKI-067), toasts (TOKI-075), Web Push (TOKI-074, whose route `/open-message` and whose message from the service worker call `open`). Each builds its own press and calls the function. The specs of TOKI-066, 067, 074 and 075 are written and agree with the table in Design, "What each caller passes"; the spec of TOKI-083 is not written yet, so what this spec says of it is a hand-off.
  - How the list places itself, centres the row and loads around a message: TOKI-041 (R10, R11, R14). How the thread panel loads and brings a reply into view, and the thread address: TOKI-045 (R16, R18). The New divider: TOKI-054.
  - An address for one message to share as a link: concern 6. A push click has its own entry point in TOKI-074 (R23), which calls `open`.
  - Moving focus to the message and announcing the jump to a screen reader: TOKI-083 (accessibility pass); this ticket moves no focus.
  - Any text. The hook shows no message, toast or dialog (concern 7 asks whether one is wanted).

## Requirements
- R1. The hook and its one signature. `useOpenMessage()` (`apps/web/src/conversation/jump/useOpenMessage.ts`, exported by `apps/web/src/conversation/jump/index.ts`) returns `open`, a function `(target: OpenMessageTarget) => void` whose identity does not change between renders of one router, with `OpenMessageTarget = { conversationId: string; messageId: string; parentId: string | null }`. `parentId` is required: `null` for a message of the list, the id of the root for a reply (a message sent also to the channel has a `parentId` and is a reply here). The hook never returns `undefined`; it needs `JumpProvider` above it and throws without one. The type is exported as `OpenMessageTarget`, with `OpenMessage` for the function. `open` returns nothing, makes no request itself and shows no text. `JumpProvider` calls `useRouter()` once and keeps the router in a ref, so `open` is one `useCallback` with no dependency that changes and calls no hook inside the function (R6). Check: a type test (`expectTypeOf`) of the parameter and of the return; a call without `parentId` fails `pnpm typecheck` (a `// @ts-expect-error` line); a render test finds the same function after a re-render; the hook outside the provider throws; a type fixture (`tests/conversation/jump/callers.test-d.ts`) holds the calls that exist in the specs written, TOKI-062 R12, TOKI-063 R12, TOKI-066 R12, TOKI-067 R18, TOKI-071 R9 (d), TOKI-072 R12, TOKI-074 R23 and TOKI-075 R10, in the shape of the table in Design, "What each caller passes", and compiles against the type.
- R2. The jump store. `JumpProvider` (`apps/web/src/conversation/jump/JumpProvider.tsx`) holds, in a ref, one store made by `createJumpStore({ timers })` (`jump-store.ts`; `timers` is the `Timers` type of `@toki/client-core`, given by the provider from `apps/web/src/client.ts`, and a test gives a controllable one). The store has these members: (a) `request({ conversationId, messageId })`, which sets `pending = { conversationId, messageId, seq }` with `seq` a counter that grows by one at each request, replacing any earlier pending request (the last call wins, as the last press wins), and arms a life for it: `REQUEST_TTL_MS = 10_000` through `timers.after`, after which a request that is still pending is dropped (a request that no page has consumed in 10 seconds is not wanted any more: the store stayed `failed`, the navigation was blocked or never ended on that conversation). A new request cancels the earlier life. Decided in this spec (concern 2): the value is a design choice for the lifetime of a request, not a product rule; (b) `peek(conversationId)`, which returns `{ messageId, seq }` when `pending.conversationId` equals it and `null` otherwise, and changes nothing; (c) `consume(seq)`, which clears `pending` and its life only when its `seq` equals the argument (so a late consume of an old request does not drop a newer one); (d) `drop(conversationId)`, which clears `pending` when it is that conversation's and does nothing otherwise; it is what the route calls (R7) and it does not touch the flash; (e) `clear()`, the session reset: it empties `pending` and the flash and cancels every timer of the store; (f) `subscribe` and a snapshot for `useSyncExternalStore`, and the flash of R9. `JumpProvider` also subscribes to the router with `router.subscribe("onResolved", …)` (the event of `@tanstack/react-router` that fires when a navigation has settled) and, at each event, calls `drop` for the pending conversation when the location's path is not `/c/{that id}` (a navigation that was redirected, replaced by the fallback of `viewFallback` or ended elsewhere), and it cancels the subscription and calls `clear()` when it unmounts. `AppShellRoute` mounts `JumpProvider` inside `SessionSetsProvider` and above `AppShell`, so that everything the shell draws is inside it: the route outlet, the toast host of TOKI-075 (R8), the route `/open-message` and the subscription to the service worker's messages of TOKI-074 (R23). A component that calls `useOpenMessage()` is therefore a child of the shell and never `AppShellRoute` itself, which is above the provider and would throw. Also, `useStoreLife` calls `clear()` where it calls `sets.clear()`, so a request never outlives the person's session. Check: unit tests of the store with a fake `timers`: `request` then `peek` for the same and for another conversation; two requests keep the second and arm one life; `consume` with an old `seq` keeps a newer request; `drop` for another conversation keeps the request and `drop` for its own removes it and leaves a running flash alone; the request is gone after 10,000 ms and not at 9,999 ms; `clear` empties the request and the flash and leaves zero armed timers; `subscribe` is called once per change; with a memory router: a request for `b` followed by a navigation that is redirected to `/c/c` is dropped at `onResolved`, and one that ends on `/c/b` is kept; a render test of `AppShellRoute` finds the provider above the route outlet and above a child of the shell that calls `useOpenMessage()`; after the store reset of `useStoreLife` a pending request is gone; unmounting the provider leaves no timer and no subscription.
- R3. A message of the list in another conversation. When `parentId` is `null` and the open address is not that conversation's (the path read at the time of the call from `router.state.location.pathname`, matched with `^/c/([^/]+)`), `open` calls `request({ conversationId, messageId })` and then `router.navigate({ to: "/c/$conversationId", params: { conversationId } })`, a push and no `replace` (D-089), with no search and no `state`. The router comes from `useRouter()` of `@tanstack/react-router` and not from `router.tsx` (the module cycle that TOKI-045 R16 avoids). The request is made before the navigation, so the page that the navigation mounts finds it (R5). Check: with a memory router at `/c/a`, `open({ conversationId: "b", messageId: "m1", parentId: null })` leaves `peek("b")` equal `{ messageId: "m1", seq }` and the location `/c/b`, with one new history entry; the same from `/` and from `/c/a/t/r1` (the thread panel of another conversation is left, the entry is pushed); Back returns to the entry before and does not repeat the jump (the request was consumed, R5).
- R4. A message of the list in the open conversation. When `parentId` is `null` and the open address is that conversation's (`/c/{id}`, with or without a thread, `panel` or other search), `open` calls `request` and does not navigate: the address, the open thread panel and the open details panel stay. This ticket does not close a panel under 720 px, where a panel replaces the view (TOKI-045 R16): the list centres and flashes behind it; concern 14 asks whether the call should close the panel there. The page of that conversation reads the store with `useJumpRequests(conversationId, onOpenMessage)` (`apps/web/src/conversation/jump/useJumpRequests.ts`): a layout effect (so the list's second opening, below, is made before the browser paints) that, when `peek(conversationId)` is not `null` and its `seq` is not the `seq` of `initial` (R5), takes the pending `{ messageId, seq }`, calls `consume(seq)` and then `onOpenMessage(messageId)`, the page's own function of TOKI-041 R4 (it selects the Messages tab, gives the list a new `openAt` `{ messageId, kind: "jump" }`, under TOKI-054 R10 (a) drops the page's `newFromId`, and, by TOKI-072 R8, calls `closeSearch` of the conversation search first, so a jump that arrives while the search results show closes the search and the list mounts; the search context is provided by `ConversationRouteBody` above the page, which TOKI-072 R8 now says). A second call for the same message while the list is mounted gives a new `openAt` object and the list opens again, as TOKI-041 R14 says for a new object. The Pinned tab and the other panels that are given `onOpenMessage` by the page call that function directly, and it starts the flash the same way (R10): the hook is not needed inside the page. Check: a page test with a fake list: `open` for the open conversation calls `onOpenMessage` once with the id and the location does not change; with the Files tab selected the Messages tab becomes selected (TOKI-041 R4); with a thread panel open the panel stays; two calls give two `openAt` objects; a StrictMode render calls `onOpenMessage` once for one request; with a fake search context that is open, a request for the open conversation closes it before the list gets its `openAt` (TOKI-072 R8 holds the real check).
- R5. The first opening of a page that does not exist yet. `useJumpRequests` also returns `initial`, the `{ messageId, seq }` that `peek(conversationId)` held at the first render of the page, read once with `useState(() => peek(conversationId))` (the route keys `ConversationRouteBody` by the id, so a page is mounted for each conversation; Checks left for the build, (4)). The page builds its first state from it: `openAt` is `{ messageId: initial.messageId, kind: "jump" }` and the page's `newFromId` is `undefined` when `initial` is not `null`, so the list mounts once and calls `loadAround` for the message (TOKI-041 R10) without a first `loadLatest`. When `initial` is not `null` the page ignores the value of `useNewDivider` (TOKI-054 R7, which returns `ready: false` first and a value later) for as long as it shows that conversation, so a divider does not appear after the jump when the hook becomes ready (TOKI-054 R8 says the page's state starts as the hook's `new`; this is the case where it starts as the jump, as R10 (a) of TOKI-054 says for a fresh mount with a target). The layout effect of R4 then consumes the request: it compares the pending `seq` with `initial.seq`, and when they are equal it calls `consume` and does not call `onOpenMessage`; when a second request replaced the first between the first render and the effect (a different `seq`) it consumes that one and calls `onOpenMessage` for it. Nothing is kept for a request that no page consumed (R2, R7). This rests on TOKI-054 R10 (a), which is the proposal of its concern 6 ("the target wins and no divider is drawn"). If the owner chooses the other reading (the divider is drawn and the target is put in view), the only change here is that the page keeps the hook's `newFromId` in R5 and R4; the store, the flash and the other requirements do not change. The order rule for the edits of `ConversationPage.tsx` is the one of TOKI-040 R21: the ticket that is built second adds its lines to the first one's. Check: a page test with a fake store holding `peek` `{ messageId: "m9", seq: 1 }`: the first render passes `openAt` `{ messageId: "m9", kind: "jump" }` and no `newFromId` to the fake list, the list is mounted once (a mount counter) and `consume` is called once and `onOpenMessage` is not; a fake `useNewDivider` that is `ready: false` and then gives `m5` does not make the page pass `m5`; a second request with `seq` 2 made between the first render and the effect is consumed and `onOpenMessage` is called once with its id; with no request the page's state is TOKI-054's.
- R6. A reply. When `parentId` is not `null`, `open` calls the plain function `openThread(router, { conversationId, rootId: parentId, replyId: messageId })` and nothing else: no request, no `openAt`, no change of the Messages tab. `openThread` is TOKI-045's (its R16, pull request 214, now says so): `apps/web/src/conversation/openThread.ts` exports it as a function over the router (`router` has `navigate` and `state`, the two members of the router that `useRouter()` gives), builds the thread address with the optional `reply` key and applies the rule of R16, and `useOpenThread(conversationId)` becomes a hook that wraps it with `useRouter()`; the one helper that builds the address stays one, and the rule is the one R16 already states (the push with `state: { threadPushed: true }`, the replacement when the address already is a thread) and the case that this ticket needs, which R16 now has: the entry is replaced only when the open thread is in the same conversation. When the open address is another conversation's or none, `openThread` pushes `/c/{conversationId}` and then the thread address with `state: { threadPushed: true }`, so the panel's Close and Back (`history.back()`) end on `/c/{conversationId}` and Back again returns to where the person was. The `reply` key and the panel's own scroll to the reply are TOKI-045's. This ticket builds no address. `open` calls no hook (R1): it calls the plain function with the router it keeps in a ref. The reply of another conversation is the whole of what a jump to a reply across conversations does: no request is stored, because the address carries everything (`/c/{conversationId}/t/{rootId}?reply={replyId}`); the page of that conversation mounts, and its `ThreadPanel` is the one that reads the `reply` key (TOKI-045 R18) and brings the reply into view; the list behind it opens as it opens for any thread address (at the end, with the New divider when there is one). When the route draws another view for that conversation (R7) the panel is not drawn and nothing was stored, so there is nothing to drop. Check: a fake `openThread` is called once with the router and `{ conversationId, rootId: parentId, replyId: messageId }`, and `peek` is `null` afterwards; with the real router and the real function: from `/c/a` the location is `/c/a/t/{parentId}?reply={messageId}` with one pushed entry; from `/c/a/t/r1` for a reply of conversation `a` the entry is replaced and one Back closes the panel; from `/c/a/t/r1` for a reply of conversation `b` the history gets two entries, `/c/b` and the thread, the location is `/c/b/t/{parentId}?reply={messageId}`, the panel's Close ends on `/c/b` and Back from there returns to `/c/a/t/r1`; from `/` the same two entries.
- R7. A conversation that draws something other than its page. A request is dropped only when the route has drawn a view that cannot use it, and is kept while the route does not yet know. `ConversationRouteBody` of `apps/web/src/routes/conversation.tsx` calls `drop(conversationId)` of the store: (a) when it draws `NotFoundView` (the `notFound` state, which `onNotFound` sets after `readChannel` fails with 400, 403 or 404, and the `memberChecked` case, where `readChannel` said the person is a member and the store still holds neither the entry nor the archived detail after the refresh); (b) when `UnjoinedChannel` has finished its read and the person is not a member: the route gives `UnjoinedView` the optional prop `onChannel(channel: ChannelSummary)` that TOKI-033 R21 (pull request 251) and TOKI-034 R16 (pull request 268) define, and `UnjoinedChannel` calls it once for each finished read that ends in its case (a) (the name, the topic and Join, no message; D-116, F10) or (b) (an archived channel the person has not joined: the name and the label, no Join), with the summary it draws, and never for (c) (the person is a member), (d) (403 or 404), while loading or when the read fails; the route calls `drop` in it (this ticket does not add the prop to either file); (c) when the body draws nothing for the `wasSeen` case. It never drops because `UnjoinedView` is drawn or while `UnjoinedChannel` is loading, and never on the `onMember` path: after `readChannel` answers `isMember`, `onMember` refreshes the store and the body then draws the archived page (R8), whose history consumes the request; the request is also kept when the read `failed` (the Retry state), and the life of R2 ends it when nobody consumes. For `held` the body draws `ConversationPage`, which consumes (R4, R5). While the store is not `ready` the body draws nothing and keeps the request, so a call made before the first load (a cold start) is applied when the page appears. The person sees what the route already draws for that conversation: for a private channel the person is not in, the not-found view, which does not reveal the name; for a public channel not joined, the channel's name and topic with Join and no message (D-116, F10 cases); nothing of the target message. Check: route tests with a fake store: `held` false and not a member gives the not-found view and `peek` `null` afterwards; an unjoined public channel whose `readChannel` answers a channel with `isMember: false` gives the Join view and `peek` `null` (the same for an archived channel the person has not joined), and while `readChannel` is pending `peek` is still not `null`; a store with no entry and a `readChannel` that answers `isMember: true` with an archived detail keeps the request through `UnjoinedView`, `onMember` and the refresh, and `ArchivedHistory` (fake list) consumes it once; a `readChannel` that fails with a network error keeps it; a store `loading` keeps `peek`; a held conversation keeps it until the page consumes it.
- R8. An archived channel the person belongs to. `ArchivedHistory` (TOKI-101 R14, whose body TOKI-041 R3 turns into a `MessageList` with `archived`) reads `useJumpRequests` in the same way: its first state gives the list `openAt` `{ messageId: initial.messageId, kind: "jump" }` and no `newFromId` (the archived page has no divider), it consumes the request, and a request that arrives while it is mounted (a message of the same archived channel) gives the list a new `openAt` with no tab to select. It starts the flash as R10 does. The archived page has no tab row and no composer (TOKI-041 R3) and the history shows replies only as rows that were also sent to the channel; for a reply the thread address is not drawn on that page (concern 9). Archived channels are readable (F10, "An archived channel: readable"; concern 8). Check: a test of `ArchivedHistory` with a fake list and store: a pending request for its channel is the list's first `openAt`, is consumed once, and a second request moves the list again; one for another channel is untouched; the route test of R7 for the cold navigation that reaches it through `UnjoinedView`.
- R9. The flash store. The store of R2 holds `flash: { messageId, seq } | null` with `FLASH_MS = 2000` (F10: "flashes for 2 seconds"; Decided in this spec, concern 3), `startFlash(messageId)`, `useIsFlashed(messageId): boolean` and `clear()` of R2. `startFlash` sets `flash` to the message and cancels any earlier flash timer, then arms `timers.after(FLASH_MS, …)` that clears `flash` only when its `seq` is still the one it armed. At most one message flashes at any time: a call for another message replaces the earlier one. A call for the message that already flashes changes nothing, neither the timer nor the animation (the attribute stays as it is, so the CSS animation is not replayed, and the flash ends at its first end; Decided in this spec, concern 3). `useIsFlashed(messageId)` is a `useSyncExternalStore` selector whose value is `flash?.messageId === messageId`, so only the row that starts and the row that stops flashing render again, and it returns `false` outside the provider (a row test needs no provider). The timer is the `timers` given to the provider, never a global one, and the provider's unmount cancels it. Check: with a fake `timers`: `startFlash("m1")` makes `useIsFlashed("m1")` true and `useIsFlashed("m2")` false; after 1,999 ms it still is, after 2,000 ms it is false; `startFlash("m2")` at 1,000 ms replaces it and runs for 2,000 ms from then, and the first timer does not clear the second; `startFlash("m1")` again at 1,000 ms leaves the end at 2,000 ms; a render count shows that a third row does not render again; `clear()` and the unmount cancel the pending timer (the fake counts zero armed timers).
- R10. When the flash starts. The page's `onOpened` (TOKI-041 R14, which the page uses to drop `openAt`) calls `startFlash(openAt.messageId)` (the function of `useStartFlash()`) when the `openAt` that ended its opening is of the kind `jump`, in the same function and before it drops `openAt`; so the flash starts when the list has settled on the message, not when the call was made (a `loadAround` over a slow connection would otherwise use up the 2 seconds before the row is drawn). The row gives itself the target: the list's row wrapper `MessageRow` (TOKI-041) passes `target={useIsFlashed(item.id)}` to the message component, which draws `data-target="true"` (TOKI-042 R1), and the rule of R11 draws the flash (the change request to TOKI-041 R14 and R4 in Plan changes: `data-target` follows the flash and not the length of `openAt`; the page and the list are not given the id, so they do not render again at the start and the end of a flash). A jump whose message is hidden (TOKI-041 R5) or absent from the window flashes nothing that can be seen: the id matches no row. After a failed `loadAround` the list falls back to the latest page and still calls `onOpened` (R12), so the flash starts for an id that is on a row only if that row is among the latest ones; this is accepted (concern 3). A row that scrolls out of the virtual window and back during the 2 seconds mounts with the attribute and plays the animation again for the time that is left; accepted, the attribute is gone at 2 seconds. Check: a page test with a fake list: `onOpened` after a `jump` starts the flash with the message id, after a `new` opening it starts none; a test of `MessageRow` (TOKI-041) that a row with the same id gets `data-target="true"` and no other row does; with the fake clock the attribute is gone 2,000 ms after `onOpened`.
- R11. The look of the flash. `apps/web/src/conversation/jump/flash.css`, imported by `JumpProvider.tsx`, holds one rule and one keyframes block: `.message-outer[data-target="true"] > .message { animation: toki-flash 2s ease-out; }` and `@keyframes toki-flash { 0%, 40% { background-color: var(--accent-soft); } }`. The prototype's flash is `.msg.hl { animation: hl 2.2s ease-out }` with `@keyframes hl { 0%,40% { background: var(--accent-soft) } 100% { background: transparent } }` (lines 237 and 238 of `index.html`). F13 says the flashed message "has a yellow background"; the colour follows the prototype's token and not the word of the flow (Decided in this spec, concern 3). Two other differences, both Decided in this spec (concern 3): the length is the 2 seconds of F10 and not 2.2, and the block has no `100%` step, so the animation ends on the row's own background and a mentioned row (`.mentioned`, TOKI-042 R16) goes back to its tint without a flicker through transparent. The rule has no `transition`, no fill mode and no rule of its own for reduced motion: the global rule of `base.css` (TOKI-012, the prototype's line 575) cuts every animation to 0.01 ms, so under reduced motion the row is centred and the tint is not seen (concern 4 asks whether a still tint is wanted). The colour is a token, so both looks and every accent take it. Check: a test reads `flash.css` and finds exactly that rule, the keyframes with `var(--accent-soft)` and no `100%` step, no `transition`, and no colour value written as a literal; a browser test (R15) reads `getComputedStyle(row.querySelector(".message")).animationName` equal `toki-flash` and `animationDuration` `2s` while `data-target` is set and `none` after 2 s, in both looks; with `emulateMedia({ reducedMotion: "reduce" })` the duration is `0.01ms` (or `1e-05s`).
- R12. Offline, failures and a deleted message. `open` is not behind a connection check (D-079): it reads nothing from the server. For a message in a held window the list places itself with no request; for one that is not held the list calls `loadAround` and an offline failure is handled by TOKI-041 R11, which falls back to the latest page, so the person lands at the end of the conversation with no flash (the id is not on a row near the end unless it is also there, and then it flashes there). A deleted message is a row, not an error: TOKI-037 R14 keeps it in the list with no text, so `around` it answers 200. What the jump does depends on the row (F16, D-013, D-096; TOKI-041 R5, TOKI-042 R13, TOKI-047 R20): a message that the list hides (deleted by its author and with no replies) has no row, the list centres the next drawn row and nothing flashes; a message that is drawn as a line (deleted by its author and with replies, or deleted by an admin, which reads "Message deleted by an admin", D-049) is centred and the line flashes. The 404 is for an id that is not a row of the main list: a reply that was not sent to the channel, an unknown id, a message of another conversation; the list handles it as it handles an offline failure (the end of the conversation, no flash). The hook adds no toast and no text (concern 7). A reply opened offline opens the thread panel, whose own load fails or not by TOKI-045 R18. Check: with a fake store whose `loadAround` fails with a network error and then with 404 (a reply that is not in the list): `open` made no request of its own (a spy on the `api`), the list received one `openAt`, and the page shows the end; with a window that holds a hidden deleted message: `openAt` for it centres the next drawn row and `data-target` is on no row; with one drawn as a "Message deleted" line: the line is centred and gets `data-target`; with the connection check (`useIsOnline`) false the call still sets the request and navigates.

## Design
### Why a store and not the address, a context or a prop
A message of another conversation has to reach a page that is mounted only after the call, by the route, inside `ConversationRouteBody` and with its own state (TOKI-041: `openAt` and `newFromId` live in the page; TOKI-054 resets them when the conversation changes). Three ways were considered. (1) The address (`?message=`): it would give a link too, but Back would repeat the jump and the flash, the route's validator (TOKI-035 R8, TOKI-045 R16) would grow a key, and no decision says a message has an address (concern 6). (2) The router's `state` (as `threadPushed` and `fromList` do): the same repetition on Back and on a reload. (3) A store that holds one pending request until a page consumes it: the request is used once, Back does not repeat it, and a page that is already open reads it in the same way, so there is one path for the open conversation and for another. This is the choice, Decided in this spec (concern 2). It is a provider and not a module value, so a test gets a fresh store and the session reset empties it, as `SessionSetsProvider` does for `seen`. A request that the route cannot use is dropped (R7), one that nobody consumes ends with its life (R2), and a reply needs no request because its address carries it (R6).

### What the page does with it
```
open({ conversationId, messageId, parentId })
  parentId not null ----> openThread(router, { conversationId, rootId, replyId })   (TOKI-045 R16: push or replace)
  parentId null
    store.request({ conversationId, messageId })
    other conversation --> router.navigate("/c/$conversationId")  (push)  --> route body --> ConversationPage mounts
                                                                           first state: openAt jump, no newFromId (R5)
    open conversation  --> no navigation  --> page layout effect --> onOpenMessage(messageId)  (R4)
  list: loadAround if not held -> centres the row -> onOpened() -> page: startFlash(messageId) (R10)
        -> the row reads useIsFlashed(id) -> data-target for 2 s -> cleared
```

### Which signature, and why
TOKI-071 R9 (d) once typed `parentId` as optional; its current text and TOKI-072 R12, TOKI-062 and TOKI-063 say `string | null`; every caller passes it. Optional would let a caller forget it and open a reply as a message of the list, where the row does not exist, so the list would fall back to the latest page with no message shown. Required `string | null` makes the mistake a compile error and loses nothing. Decided in this spec (concern 1); TOKI-071 now says "required" in R9 (d).

### The flash, in one place
The row's own component draws nothing for a jump (TOKI-042 R19): it takes `target` and sets `data-target`. This ticket's CSS draws the flash from that attribute (R11), and the store decides which row is the target and for how long (R9, R10). One timer, one flashed id: a second jump while one flashes replaces it, and a repeat of the same one changes nothing. The animation starts when the attribute is set, which is when the list has settled (R10), and not at the call. The row reads the flashed id itself (`useIsFlashed`), so the page and the list do not render again for a flash.
