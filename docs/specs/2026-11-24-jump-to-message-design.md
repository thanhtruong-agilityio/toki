# Jump to message design

Date: 2026-11-24 · Status: draft for review
Intent: docs/intents/jump-to-message.md (Thanh Truong)
Ticket: TOKI-068
Needs: TOKI-041 (the page's `onOpenMessage`, `selectMessagesTab`, `openAt` of the kind `jump`, `data-target`; pull request 218), TOKI-045 (`useOpenThread(conversationId)(rootId, replyId?)`, the replace rule of its R16; pull request 214). Also read: TOKI-054 (a jump draws no New divider, R10 (a); pull request 238), TOKI-033 (the route body that draws the page, merged), TOKI-101 (the archived page and `ArchivedHistory`, merged), TOKI-008 (the controllable timers), TOKI-012 (`base.css` with the reduced-motion rule, merged). The plan's needs line is `TOKI-041` only; the change is in Plan changes.

## Goal
Every screen that points at one message opens it the same way. One hook, `useOpenMessage()`, returns one function: given a conversation, a message and the message's parent, it opens the conversation at the message and flashes it for 2 seconds, or, for a reply, opens the thread panel of the root with the reply in view. The callers (the attachment window, the Files section and tab, the command palette, the search inside a conversation, and later Activity, Later and toasts) build no jump of their own.
This ticket builds the hook, the small store that carries a jump to a page that does not exist yet (a message of another conversation), the flash, and the lines that the page, the archived history and the route body add to read them. It builds no screen, no server code and no text.

## Scope
- In:
  - The hook `useOpenMessage()` and its one signature (R1), the provider and store that hold a pending jump and the flash (R2, R9), the cases of a message of the list in another conversation and in the open one (R3 to R5), the reply (R6), and the cases where the conversation draws something other than its page (R7, R8).
  - The flash: when it starts, how long it lasts, one at a time, the CSS (R9 to R11).
  - Offline and failed loads (R12), the single-hook rule and the naming (R13), the wiring and the edits to files of other tickets (R14), the browser test (R15).
- Out (not now):
  - The screens that call the hook: the palette (TOKI-071), the search inside a conversation (TOKI-072), the attachment window (TOKI-062), the Files section and tab (TOKI-063), Pinned (TOKI-048, which calls the page's own `onOpenMessage`, R4), Activity (TOKI-066), Later (TOKI-067), toasts (TOKI-075), Web Push (TOKI-074). Each builds its own press and calls the function.
  - How the list places itself, centres the row and loads around a message: TOKI-041 (R10, R11, R14). How the thread panel loads and brings a reply into view, and the thread address with its push and replace rule: TOKI-045 (R16, R18). The New divider: TOKI-054.
  - An address for one message (a link, a push click): concern 6.
  - Moving focus to the message and announcing the jump to a screen reader: TOKI-083 (accessibility pass); this ticket moves no focus.
  - Any text. The hook shows no message, toast or dialog (concern 7 asks whether one is wanted).

## Requirements
- R1. The hook and its one signature. `useOpenMessage()` (`apps/web/src/conversation/jump/useOpenMessage.ts`, exported by `apps/web/src/conversation/jump/index.ts`) returns `open`, a function `(target: OpenMessageTarget) => void` whose identity does not change between renders of one router, with `OpenMessageTarget = { conversationId: string; messageId: string; parentId: string | null }`. `parentId` is required: `null` for a message of the list, the id of the root for a reply (a message sent also to the channel has a `parentId` and is a reply here). The hook never returns `undefined`; it needs `JumpProvider` above it and throws without one. The type is exported as `OpenMessageTarget`, with `OpenMessage` for the function. `open` returns nothing, makes no request itself and shows no text. Check: a type test (`expectTypeOf`) of the parameter and of the return; a call without `parentId` fails `pnpm typecheck` (a `// @ts-expect-error` line); a render test finds the same function after a re-render; the hook outside the provider throws; each of the eight callers' call shapes in the table of Design, "What each caller passes", compiles against the type.
- R2. The jump store. `JumpProvider` (`apps/web/src/conversation/jump/JumpProvider.tsx`) holds, in a ref, one store made by `createJumpStore({ timers })` (`jump-store.ts`; `timers` is the `Timers` type of `@toki/client-core`, given by the provider from `apps/web/src/client.ts`, and a test gives a controllable one). The store has `request({ conversationId, messageId })`, which sets `pending = { conversationId, messageId, seq }` with `seq` a counter that grows by one at each request, replacing any earlier pending request (the last call wins, as the last press wins); `peek(conversationId)`, which returns the pending `messageId` when `pending.conversationId` equals it and `null` otherwise, and changes nothing; `consume(seq)`, which clears `pending` only when its `seq` equals the argument (so a late consume of an old request does not drop a newer one); `clear()`; `subscribe` and a snapshot for `useSyncExternalStore`; and the flash of R9. `AppShellRoute` mounts `JumpProvider` inside `SessionSetsProvider`, and `useStoreLife` calls `clear()` where it calls `sets.clear()`, so a request never outlives the person's session. Check: unit tests of the store with a fake `timers`: `request` then `peek` for the same and for another conversation; two requests keep the second; `consume` with an old `seq` keeps a newer request; `clear` empties; `subscribe` is called once per change; a render test of `AppShellRoute` finds the provider above the route; after the store reset of `useStoreLife` a pending request is gone.
- R3. A message of the list in another conversation. When `parentId` is `null` and the open address is not that conversation's (the path read at the time of the call from `router.state.location.pathname`, matched with `^/c/([^/]+)`), `open` calls `request({ conversationId, messageId })` and then `router.navigate({ to: "/c/$conversationId", params: { conversationId } })`, a push and no `replace` (D-089), with no search and no `state`. The router comes from `useRouter()` of `@tanstack/react-router` and not from `router.tsx` (the module cycle that TOKI-045 R16 avoids for `useOpenThread`). The request is made before the navigation, so the page that the navigation mounts finds it (R5). Check: with a memory router at `/c/a`, `open({ conversationId: "b", messageId: "m1", parentId: null })` leaves `peek("b")` equal `"m1"` and the location `/c/b`, with one new history entry; the same from `/` and from `/c/a/t/r1` (the thread panel of another conversation is left, the entry is pushed); Back returns to the entry before and does not repeat the jump (the request was consumed, R5).
- R4. A message of the list in the open conversation. When `parentId` is `null` and the open address is that conversation's (`/c/{id}`, with or without a thread, `panel` or other search), `open` calls `request` and does not navigate: the address, the open thread panel and the open details panel stay. The page of that conversation reads the store with `useJumpRequests(conversationId, onOpenMessage)` (`apps/web/src/conversation/jump/useJumpRequests.ts`): an effect that, when `peek(conversationId)` is not `null`, takes the pending `seq`, calls `consume(seq)` and then `onOpenMessage(messageId)`, the page's own function of TOKI-041 R4 (it selects the Messages tab, gives the list a new `openAt` `{ messageId, kind: "jump" }` and, under TOKI-054 R10 (a), drops the page's `newFromId`). A second call for the same message while the list is mounted gives a new `openAt` object and the list opens again, as TOKI-041 R14 says for a new object. The Pinned tab and the other panels that are given `onOpenMessage` by the page call that function directly, and it starts the flash the same way (R10): the hook is not needed inside the page. Check: a page test with a fake list: `open` for the open conversation calls `onOpenMessage` once with the id and the location does not change; with the Files tab selected the Messages tab becomes selected (TOKI-041 R4); with a thread panel open the panel stays; two calls give two `openAt` objects; a StrictMode render calls `onOpenMessage` once for one request.
- R5. The first opening of a page that does not exist yet. `useJumpRequests` also returns `initial`, the `messageId` that `peek(conversationId)` held at the first render of the page, read once with `useState(() => peek(conversationId))`. The page builds its first state from it: `openAt` is `{ messageId: initial, kind: "jump" }` and `newFromId` is `undefined` when `initial` is not `null` (TOKI-054 R10 (a): a fresh mount with a target draws no divider), so the list mounts once and calls `loadAround` for the message (TOKI-041 R10) without a first `loadLatest`. The effect of R4 then consumes the request and does not call `onOpenMessage` again for it (it knows that `initial` came from the same `seq`). Nothing is kept for a request that no page consumed (R7). Check: a page test with a fake store holding `peek` `"m9"`: the first render passes `openAt` `{ messageId: "m9", kind: "jump" }` and no `newFromId` to the fake list, the list is mounted once (a mount counter) and `consume` is called once; with no request the page's state is TOKI-054's.
- R6. A reply. When `parentId` is not `null`, `open` calls `useOpenThread(conversationId)(parentId, messageId)` of TOKI-045 R16 and nothing else: no request, no `openAt`, no change of the Messages tab. The push with `state: { threadPushed: true }` or the replacement of the entry when the address already is a thread, the `reply` key and the panel's own scroll to the reply are TOKI-045's. The hook builds no address. Because `useOpenThread` takes a conversation id and returns a function, `open` holds one such function for each conversation it was called for (a map made when needed), so the identity of `open` does not change (R1). Check: a fake `useOpenThread` is called with the conversation id and then with `(parentId, messageId)`; `peek` is `null` afterwards; the location is `/c/{id}/t/{parentId}?reply={messageId}` with a pushed entry from a conversation address; from a thread address the entry is replaced and one Back closes the panel (TOKI-045 R16's check, repeated here only through the hook, with the real router).
- R7. A conversation that draws something other than its page. `ConversationRouteBody` of `apps/web/src/routes/conversation.tsx`, when the store is `ready` and the body draws the not-found view, `UnjoinedView` or nothing (the `wasSeen` case), calls the store's `clear()` for a pending request of that conversation (`peek(conversationId)` not `null`), so the request cannot fire later when the person opens the conversation by another way. While the store is not `ready` the body draws nothing and keeps the request, so a call made before the first load (a cold start) is applied when the page appears. - R8. An archived channel the person belongs to. `ArchivedHistory` (TOKI-101 R14, whose body TOKI-041 R3 turns into a `MessageList` with `archived`) reads `useJumpRequests` in the same way: its first state gives the list `openAt` `{ messageId: initial, kind: "jump" }` and no `newFromId` (the archived page has no divider), it consumes the request, and a request that arrives while it is mounted (a message of the same archived channel) gives the list a new `openAt` with no tab to select. It starts the flash as R10 does. The archived page has no tab row and no composer (TOKI-041 R3) and the history shows replies only as rows that were also sent to the channel; for a reply the thread address is not drawn on that page (concern 9). - R9. The flash store. The store of R2 holds `flash: { messageId, seq } | null` with `FLASH_MS = 2000` (F09: "flashes for 2 seconds"; Decided in this spec, concern 3), `startFlash(messageId)`, which sets `flash` to the message and cancels any earlier flash timer, then arms `timers.after(FLASH_MS, …)` that clears `flash` only when its `seq` is still the one it armed; `useFlashedId(): string | null` (a `useSyncExternalStore` selector, so a component re-renders only when the id changes); and `clear()` cancels the timer. At most one message flashes at any time: a new `startFlash` replaces the earlier one. The timer is the `timers` given to the provider, never a global one. Check: with a fake `timers`: `startFlash("m1")` gives `useFlashedId` `"m1"`; after 1,999 ms it still does, after 2,000 ms it is `null`; `startFlash("m2")` at 1,000 ms replaces it and runs for 2,000 ms from then, and the first timer does not clear the second; `clear()` cancels the pending timer (the fake counts zero armed timers).
- R10. When the flash starts. The page's `onOpened` (TOKI-041 R14, which the page uses to drop `openAt`) calls `startFlash(openAt.messageId)` when the `openAt` that ended its opening is of the kind `jump`, in the same function and before it drops `openAt`; so the flash starts when the list has settled on the message, not when the call was made (a `loadAround` over a slow connection would otherwise use up the 2 seconds before the row is drawn). The page gives the list `flashId = useFlashedId()` in its `messageList` object, and the list gives a row `target` true when the row's id equals `flashId` (the change request to TOKI-041 R14 and R4 in Plan changes: `data-target` follows `flashId`, not the length of `openAt`). The row component draws `data-target="true"` (TOKI-042 R1) and the rule of R11 draws the flash. A jump whose message is hidden (TOKI-041 R5) or absent from the window flashes nothing that can be seen: the id matches no row. Check: a page test with a fake list: `onOpened` after a `jump` starts the flash with the message id, after a `new` opening it starts none, and `flashId` reaches the list; a test of `rows`/`MessageRow` (TOKI-041) that a row with the same id gets `data-target="true"` and no other row does; with the fake clock the attribute is gone 2,000 ms after `onOpened`.
- R11. The look of the flash. `apps/web/src/conversation/jump/flash.css`, imported by `JumpProvider.tsx`, holds one rule and one keyframes block: `.message-outer[data-target="true"] > .message { animation: toki-flash 2s ease-out; }` and `@keyframes toki-flash { 0%, 40% { background-color: var(--accent-soft); } }`. ## Design
### Why a store and not the address, a context or a prop
A message of another conversation has to reach a page that is mounted only after the call, by the route, inside `ConversationRouteBody` and with its own state (TOKI-041: `openAt` and `newFromId` live in the page; TOKI-054 resets them when the conversation changes). Three ways were considered. (1) The address (`?message=`): it would give a link too, but Back would repeat the jump and the flash, the route's validator (TOKI-035 R8, TOKI-045 R16) would grow a key, and no decision says a message has an address (concern 6). (2) The router's `state` (as `threadPushed` and `fromList` do): the same repetition on Back and on a reload. (3) A store that holds one pending request until a page consumes it: the request is used once, Back does not repeat it, and a page that is already open reads it in the same way, so there is one path for the open conversation and for another. This is the choice, Decided in this spec (concern 2). It is a provider and not a module value, so a test gets a fresh store and the session reset empties it, as `SessionSetsProvider` does for `seen`.

### What the page does with it
```
open({ conversationId, messageId, parentId })
  parentId not null ----> useOpenThread(conversationId)(parentId, messageId)      (TOKI-045 R16: push or replace)
  parentId null
    store.request({ conversationId, messageId })
    other conversation --> router.navigate("/c/$conversationId")  (push)  --> route body --> ConversationPage mounts
                                                                           first state: openAt jump, no newFromId (R5)
    open conversation  --> no navigation  --> page effect --> onOpenMessage(messageId)  (R4)
  list: loadAround if not held -> centres the row -> onOpened() -> page: startFlash(messageId) (R10) -> 2 s -> clear
```

### What each caller passes
| Caller | Call | Spec |
| :---- | :---- | :---- |
| Attachment window, "Open in conversation" | `open({ conversationId: message.conversationId, messageId: message.id, parentId: message.parentId })`, after the dialog closes | TOKI-062 R12 |
| Files section and tab | `open({ conversationId: item.conversationId, messageId: item.messageId, parentId: item.parentId })` | TOKI-063 R12 |
| Command palette, a message result | the `conversationId`, `id` and `parentId` of the result | TOKI-071 R9 (d) |
| Search inside a conversation | `open({ conversationId, messageId: id, parentId })`, after `closeSearch` | TOKI-072 R12 |
| Pinned, the Messages list | the page's `onOpenMessage(messageId)`, not the hook (R4) | TOKI-048 R15, TOKI-041 R4 |
| Activity (a message item: mention, reaction, deleted by an admin) | `open` with the item's `conversationId`, `messageId` and `parentId`; a thread item calls `useOpenThread(conversationId)(rootId)` and an item with no message (added to a channel, role changed) navigates to `/c/{id}` or nothing | TOKI-066 (hand-off) |
| Later | `open` with the saved message's three values; a replacement row for a deleted source opens nothing | TOKI-067 (hand-off) |
| Toast "View", a Web Push click | `open` for a message of a conversation; a push click needs an address first (concern 6) | TOKI-075, TOKI-074 (hand-off) |

### Which signature, and why
TOKI-071 R9 (d) of its corrected text types `parentId` as optional and TOKI-072 R12 and TOKI-062, TOKI-063 ask for `string | null`; every caller passes it. Optional would let a caller forget it and open a reply as a message of the list, where the row does not exist, so the list would fall back to the latest page with no message shown. Required `string | null` makes the mistake a compile error and loses nothing. Decided in this spec (concern 1); the hand-off to TOKI-071 is that its R9 (d) says "required" and that its Plan changes line, which says "optional", is changed.

### The flash, in one place
The row's own component draws nothing for a jump (TOKI-042 R19): it takes `target` and sets `data-target`. This ticket's CSS draws the flash from that attribute (R11), and the store decides which row is the target and for how long (R9, R10). One timer, one flashed id: a second jump while one flashes replaces it. The animation starts when the attribute is set, which is when the list has settled (R10), and not at the call.

## Testing
- Written test-first. The store and the flash are tested as units with a fake `timers` (the controllable clock of TOKI-008); no test waits on a real timer, and the 2 seconds of R9 and R10 are advanced by the fake.
- The hook is tested with a memory router (`createMemoryHistory`) and the real `useOpenThread`; the page, the archived history and the route body with a fake list, a fake store of the conversation and fake `deps`, as TOKI-041 and TOKI-033 test theirs.
- The CSS test reads the file; the computed values are read in the browser test (R11, R15). A test that returns true for anything is not accepted: each check above names the value it compares.
- Browser test: R15, with the stubs of TOKI-041 R25 and a mode-`test` harness route. Fake data only: made-up names and sentences.
- Not tested here: the callers' presses (each caller's own test with a fake hook), the list's placement and `loadAround` (TOKI-041), the thread panel's scroll (TOKI-045).

## Data safety
- The store holds a conversation id and a message id in memory for one request and is emptied at the session reset (R2) and when the route draws a view that cannot use it (R7). Nothing is written to storage, the address or a log, and nothing is sent to the server by this ticket.
- A request for a conversation the person cannot read changes what is drawn by nothing: the route's own view appears and no content is shown, and the request is dropped, so no other view uses it (R7, D-116).

## How each constraint in the intent is met
| Constraint | Met by |

## Open questions from the intent
- What exactly does the hook take, and is `parentId` required, optional or `null`-able? Answered: `{ conversationId, messageId, parentId: string | null }`, all three required (R1, concern 1).
- A message of another conversation has no page yet when the call is made. How does the first opening at that message reach the page? Answered: a request held in a store above the route, read by the page for its first state and consumed once (R2, R3, R5, concern 2).
- Who draws the flash, for how long, and what does it do under reduced motion? Answered for the owner and the length (R9 to R11, concern 3); under reduced motion the global rule applies and a still tint is Not answered. Carried forward as concern 4.
- A reply: does the jump open the thread, and does the reply flash? Answered for the thread (R6, TOKI-045 R16); the flash on a reply is Not answered. Carried forward as concern 5.
- What does the person see when the message was deleted, the conversation is archived, or the person can no longer read it? Answered for a conversation that cannot be read and for an archived channel's messages (R7, R8, concern 8); Not answered for a message that cannot be shown, a reply in an archived channel and a Later row of a conversation no longer readable. Carried forward as concerns 7, 9 and 10.
- Does a message have an address of its own, for a link or a push click? Not answered. Carried forward as concern 6.
- What does a caller that is offline get? Answered: the same function, no gate (R12, concern 11).

## Areas of concern
1. The signature. Decided in this spec: `open(target: { conversationId: string; messageId: string; parentId: string | null })`, all three required, returned by `useOpenMessage()` that never returns `undefined` (R1). Reason: Design, "Which signature, and why". TOKI-071's corrected text types `parentId` as optional; TOKI-072, TOKI-062 and TOKI-063 ask for `string | null`; this resolves it for all of them, and the hand-off to TOKI-071 is to say "required" in R9 (d) and in its Plan changes. Owner: Thanh Truong.
2. How the first opening reaches the page of another conversation. Decided in this spec: a pending request held by `JumpProvider`, set before the push to `/c/{id}`, read by the page for its first `openAt` (kind `jump`, no `newFromId`) and consumed once; the same store serves the open conversation (R2 to R5). Reason: Design, "Why a store and not the address, a context or a prop". TOKI-041 R4 leaves this to this ticket and says the ticket adds what it needs to the page's state. Owner: Thanh Truong.
3. The flash: who draws it, how long, what it looks like. Decided in this spec: this ticket's `flash.css` draws it on the row that carries `data-target` (TOKI-042 R1, R19), for 2 seconds (F09, accepted as part of the baseline by D-091), one message at a time, starting when the list has settled (R9 to R11). The look is the prototype's `.msg.hl` (`--accent-soft` for the first 40 percent, then fading) with two differences: 2 s and not 2.2 s, and the fade ends on the row's own background and not on transparent, so a mentioned row keeps its tint. Reason: the journey gives 2 seconds; the prototype's end value would flash a mentioned row to blank. Owner: Thanh Truong.
4. The flash under reduced motion. Not decided. The prototype's global rule (line 575) cuts all animation to 0.01 ms, so its flash is not seen under reduced motion, and the log has no other rule; TOKI-083 owns the reduced-motion pass. Proposal, not a decision (R11): keep the prototype's behaviour (the row is centred and no tint is seen), because a movement-free tint for 2 s is a second look that nobody has asked for. The alternative is a still `--accent-soft` background for the same 2 seconds with no animation, which still shows where to look; it is one rule in `flash.css` inside `@media (prefers-reduced-motion: reduce)`. Owner: Thanh Truong (product owner), with TOKI-083.
5. A reply: does it flash? Not decided. F09 and F13 say the message flashes and the prototype opens the thread and flashes the root in the main list (`openConv(c, { msg: parent, thread: parent })`, line 2352); the merged and open specs (TOKI-045 R16, TOKI-071, TOKI-072) open the thread panel and do not move the list. Proposal, not a decision (R6): the hook opens the thread only (as built by TOKI-045) and the panel flashes the reply row: `ThreadPanel` calls `startFlash(replyId)` when it has brought the reply into view and gives that row `target` true while `useFlashedId()` is its id (TOKI-045 R18 gives `target` false today; one edit to `ThreadPanel.tsx` by this ticket and a change request to TOKI-045). The list stays where it is. If the owner wants the prototype's root flash too, `open` also calls `request` for the root. Owner: Thanh Truong (product owner).
6. An address for one message. Not decided. F09 has "Opened from a link to one message: it scrolls there and flashes for 2 seconds", TOKI-074 says a push click "opens Toki at that message" and TS-011 mentions "a link to a message in #launch", but D-089 lists conversations, threads and sections and no message address, and no spec defines one. Proposal, not a decision: a search key `message={id}` on `/c/$conversationId`, read by the route, which calls `request`, then replaces the entry with the address without the key (so Back and reload do not repeat the jump); the key is added to the validator of TOKI-035 R8 and the route calls the store the same way as `open`. Nothing of this is built here; a service worker can only open an address, so TOKI-074 needs it. Owner: Thanh Truong (product owner).
7. What the person sees when the message cannot be shown (deleted since the press, or not a row of the list). Not decided. The server answers 404 and TOKI-041 R11 falls back to the latest page, so the person sees the end of the conversation with no flash and no explanation; the log gives no wording and D-139 makes every wording a proposal. Proposal, not a decision: no text, as now; the alternative is a toast with a message such as "This message is no longer available", a proposal of wording for the owner to accept or change, shown by the hook when the fallback happens. Owner: Thanh Truong (product owner).
8. A conversation that cannot be opened, and an archived channel's messages. Decided in this spec: the route draws its own view and the request is dropped (R7): the not-found view for a private channel the person is not in and for an unknown id, the channel's name and topic with Join for a public channel not joined, no content in either (D-116, F09 cases); an archived channel the person belongs to is readable, so its history opens at the message and flashes it (R8; F09 case "An archived channel: readable"; the search returns messages of archived channels the person belongs to, TOKI-070). Reason: these views and their texts already exist (TOKI-033 R21, TOKI-101 R13); the jump adds no text. Owner: Thanh Truong.
9. A reply in an archived channel. Not decided. The archived page has no thread panel (TOKI-101, TOKI-041 R3), and `useOpenThread` would navigate to a thread address that the archived page does not draw. Proposal, not a decision: for a reply whose conversation is an archived channel the person belongs to, `open` makes a request for the root (`parentId`) so the history opens at the root and flashes it; this needs the hook to know that the channel is archived (`getChannelDetail`, `isArchivedMember`, as `ConversationRouteBody` does). Until it is decided the person sees the history at the end. Owner: Thanh Truong (product owner).
10. A Later row of a conversation the person can no longer read. Not decided. D-133 clears Activity items on leaving a channel and says nothing of Later (TOKI-067); pressing such a row would call `open` and the person would see the not-found view or Join (R7). Proposal, not a decision: nothing special; the route's view is what the person sees. Owner: Thanh Truong (product owner), with TOKI-067.
11. Offline. Decided in this spec: no gate on `open` and no text (R12). Reason: D-079 keeps loaded content readable and blocks only what needs the server; a held message is shown from the window, and a message that has to be loaded fails as TOKI-041 R11 says, ending at the end of the conversation. TOKI-062 R12 takes the same position for its button. Owner: Thanh Truong.
12. The name. Decided in this spec: `useOpenMessage` is the one hook (R13). TOKI-062 once defined a context and a hook of its own with two arguments and has dropped them; the page's `onOpenMessage(messageId)` of TOKI-041 and TOKI-048 is a prop that the page gives to the panel of its tabs and keeps its name. A grep test enforces one declaration. Reason: one way to open a message in the app, as TOKI-062, TOKI-063, TOKI-071 and TOKI-072 say. Owner: Thanh Truong.
13. The plan's needs line. Decided in this spec (Plan changes): `TOKI-068 needs: TOKI-041` becomes `TOKI-068 needs: TOKI-041, TOKI-045`, because `open` calls `useOpenThread` (R6); TOKI-054 is read for a rule and is not a need. The plan is a change request and is not edited here. Owner: Thanh Truong.
