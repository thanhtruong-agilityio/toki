## Goal
An Admin needs a way to create a channel. After TOKI-029 the server accepts the request and after TOKI-032 the store has a command for it, but no screen lets an Admin type a name and press Create. The prototype draws no such screen: its Browse channels dialog has no create control, and its Admin page has no "+" for channels (D-084, D-151).

After this change the Admin page can show a "+" beside its "Channels" list. It opens the Create channel dialog: Name, a Private switch (off by default), Topic (optional, up to 250 characters) and Add people (optional) (D-101). The name fixes itself as it is typed (a space becomes a hyphen, a capital becomes lowercase, D-127), errors show under the field and Create stays disabled until the form is valid (D-104), the server's refusal of a name in use is shown under the Name field (D-115), and the new channel opens at once (D-076; whether the list shows it under a filter is TOKI-033's, concern 6). The client also gets the generator of UUIDv7 ids that the server expects from it (TOKI-029 R4), in `packages/shared`, where message sending can reuse it.

## Requirements
Id generator
- R1. `packages/shared/src/ids/uuid-v7.ts` exports `createUuidV7Generator({ clock, randomBytes })` and `packages/shared/src/index.ts` re-exports it. `clock` is the `Clock` of TOKI-008 (`now()` in epoch milliseconds) and `randomBytes(length)` returns a `Uint8Array` of that length; the file reads neither the system time nor a random source itself (TOKI-008 R19, TOKI-002 rule 1: `crypto` is not on the allow list). The function it returns, called with no argument, returns a lower-case string of 36 characters in the form 8-4-4-4-12 that follows RFC 9562 section 5.7. The exact mapping, so that the output of a fixed input is one string: let `t = Math.floor(clock.now())` and let `r` be the first 10 bytes of `randomBytes(10)`; the 16 bytes of the id, numbered 0 to 15 from the left, are: bytes 0 to 5 the 48 bits of `t` (big-endian, byte 0 the most significant); byte 6 `0x70 | (r[0] & 0x0f)`; byte 7 `r[1]`; byte 8 `0x80 | (r[2] & 0x3f)`; bytes 9 to 15 `r[3]` to `r[9]`. Each byte is written as two lower-case hex digits and the groups hold 4, 2, 2, 2 and 6 bytes. A `t` that is not a finite number, is below 0 or is above 2^48 - 1 (checked after the floor, so a clock that returns a fraction is floored, never rejected) makes the function throw an `Error` before it asks for random bytes; a `randomBytes` that returns fewer than 10 bytes also makes it throw an `Error` instead of returning a short id. It asks `randomBytes` once per call. It does not promise that ids made in one millisecond sort in the order they were made (concern 8). Check, by exact output: with the clock at 1645557742000 and `r` equal to `0c c3 18 c4 dc 0c 0c 07 39 8f`, the result is exactly `017f22e2-79b0-7cc3-98c4-dc0c0c07398f` (the example of RFC 9562 appendix B.2: byte 6 is `0x70 | 0x0c`, byte 7 is `c3`, byte 8 is `0x80 | 0x18`); clock 0 with ten `ff` gives `00000000-0000-7fff-bfff-ffffffffffff`; clock 0 with ten `00` gives `00000000-0000-7000-8000-000000000000`; clock 2^48 - 1 with ten `00` gives `ffffffff-ffff-7000-8000-000000000000`; a clock of 1645557742000.9 gives the same id as 1645557742000. Check, by properties: 1000 ids made with a seeded source all match the pattern `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$` (the test holds its own copy, so this part does not wait for TOKI-029; the server's pattern is TOKI-029 R17 and R11 checks the sent `id` against it) and are all different; a clock of -1, 2^48, `NaN` and `Infinity` each throw an `Error` and `randomBytes` is not called; a `randomBytes` that returns 9 bytes throws an `Error`.
- R2. `apps/web/src/ids.ts` exports `newId`, made with `createUuidV7Generator` from the system clock of TOKI-008 and a `randomBytes` that fills a `Uint8Array` with `crypto.getRandomValues` (available also on a page served without HTTPS, unlike `crypto.randomUUID`, which needs a secure context; Toki is self-hosted, D-028). `ids.ts` is the one file of `apps/web/src` that touches a random source: every other file that needs a unique id imports `newId`. TOKI-025 does this for the `Idempotency-Key` of its mail routes (its R5: `adminApi.ts` calls `newId` and no function of `crypto`, and its own test checks that), so the scan below and the scan of TOKI-025 say the same thing. Check: a test reads the files of `apps/web/src` (test files excepted) and finds `crypto.`, `randomUUID` and `getRandomValues` only in `ids.ts`; the list of allowed files is one array at the top of that test, so a later ticket that needs `crypto` for something that is not an id adds its file there and says so in its own spec; `newId()` matches the pattern of R1; it is the same shape when the page has no `crypto.randomUUID`.

The button and the dialog

A press opens the dialog and gives it the pressed button as `returnFocusRef`. It also takes the optional prop `onCreated(id)` (R12). `useCreateChannelDialog({ onCreated? })` returns `{ open(options?: { returnFocusRef? }), element }`, where `element` is the dialog (or `null`) for a screen to render beside its own markup; `CreateChannelButton` is built on it, and `open` does nothing when the role is not `"admin"`. Check: a test with the role `admin` presses the button and finds the dialog, and Esc returns focus to the button; with `member`, with `null`, and with a role that changes from `admin` to `member` while the dialog is open (the dialog closes and sends nothing), the test finds no button and no dialog, and a call of `open` opens nothing.

It renders nothing when `useCurrentRole()` is not `"admin"` (R18). The body, in this order, inside one element that carries `trackFocus` (R16): (1) a `Field` of TOKI-012 (form (a), `variant="default"`) with `label` `t("createChannel.name.label")`, `autoComplete="off"`, `autoCapitalize="none"`, `spellCheck={false}`, the attribute `data-autofocus` and the `error` of R7, R13; (2) `div.ccrow` holding `span.grow` with `t("createChannel.private.label")` (its `id` names the switch) and a `Switch` of TOKI-012 with `labelledBy` that id and `checked` false when the dialog opens, then `p.cchint` with `t("createChannel.private.hint")`; (3) a `Field` with `label` `t("createChannel.topic.label")`, `autoComplete="off"` and the `error` of R8; (4) a `fieldset.ccpeople` with `aria-labelledby` the id of a `div.lbl` that holds `t("createChannel.people.label")`, and in it the `PeoplePicker` of TOKI-034 R18 (R9, R10). `PeoplePicker` carries `data-autofocus` too (TOKI-034 R18); the Name field wins because TOKI-014 R11 takes the first element in document order. The line is in the footer, not under the body, because the body scrolls and a line under a long list of people would be out of view when Create is pressed (TOKI-014 R29: the footer stays in view). Every time the dialog opens, every field, the chosen people, the errors and the attempt of R15 are cleared. When it opens, focus goes to the name input (`data-autofocus`, TOKI-014 R11); when it closes, focus goes to `returnFocusRef`, or else to the element that had focus when it opened (TOKI-014 R13). Check: component test of the markup and the order (the line is inside `div.ccfoot`, above the buttons, and not inside `div.mbd`); open, type, close, open again: empty; the first focus; Enter with `isComposing` true and with `keyCode` 229 in each of the two fields sends nothing, and a plain Enter sends one request.

Name and topic
- R6. The name field changes what is typed (D-127, concern 5). `normalizeChannelName(text)` in `channelName.ts` replaces every white-space character (`/\s/u`: space, tab, no-break space and the others, each one character for one hyphen) with `-` and then lower-cases the text with `toLowerCase()` (not the language-dependent form). It removes nothing else and trims nothing: a space typed at the end shows as a hyphen at the end. The input's `onChange` stores `normalizeChannelName` of what the browser holds and, when that differs from it, puts the caret back at the place where the person was typing (the text keeps its length in every case except the few letters whose lower case has more code units, where the caret goes to the end). A paste is normalised the same way. While an input method is composing (between `compositionstart` and `compositionend`, or an `onChange` whose `isComposing` is true) the input keeps the text as the browser holds it, so that the composition is not broken, and the state is normalised at `compositionend`; the verdict of R7 and the name sent are always `normalizeChannelName` of the state, so a capital typed during a composition never shows a message or reaches the server. The input has no `maxLength` (R7). Check: unit table: `"Q A"` gives `"q-a"`, `"  "` gives `"--"`, a tab and a no-break space give hyphens, `"ÉCOLE"` gives `"école"`, `"a&b"` stays `"a&b"`, an empty text stays empty; component test: typing a space and a capital into the field leaves the hyphen and the lower-case letter in the input's value; a composition of `"Q"` followed by `compositionend` leaves `"q"` and sends nothing in between; in the browser check (R21) the caret stays in place when a space is typed in the middle of a name.
- R7. Name validity and message. `validateChannelName(name)` returns `{ valid: true }` when `CHANNEL_NAME_PATTERN` of `@toki/shared` (TOKI-028 R15) matches the name, and otherwise `{ valid: false, message }`: for an empty name `message` is `null` (Create stays disabled and nothing is shown, so an untouched form shows no error, D-104); for a name with a character outside `a-z`, `0-9` and `-` it is `"invalid"`; otherwise (only allowed characters, more than `CHANNEL_NAME_MAX` = 80) it is `"tooLong"`. The field shows, under itself, `t("createChannel.name.error.invalid")` for `"invalid"` and `t("createChannel.error.tooLong", { count: 80 })` for `"tooLong"`, as the `error` of `Field` (TOKI-012 R17: one message, `role="alert"`, `aria-invalid`), at once while the person types, never as a toast. The verdict is the shared pattern's, so the screen and the server cannot disagree. Check: unit test over a table of names (`qa-team`, an 80-character name, an 81-character name, `Q&A Team!` after R6 as `q&a-team!`, `qa_team`, `-`, `0`, `école`, an emoji, the empty text) that compares `valid` with `CHANNEL_NAME_PATTERN.test(name)` for every row and checks each message; AC-049 and TS-075, TS-078 on the screen: an 80-character name enables Create, an 81-character name shows the message and disables it.
- R8. Topic. The topic is trimmed of white space at both ends before it is checked and sent (TOKI-029 R4). It is valid when it is empty or `isValidChannelTopic` of `@toki/shared` accepts it (1 to `CHANNEL_TOPIC_MAX` = 250 code points, counted with `Array.from`, not `.length`); a longer topic shows `t("createChannel.error.tooLong", { count: 250 })` under the field and disables Create. The input has no `maxLength` and no counter. Check: a topic of 250 characters and of 250 emoji enables Create; 251 characters and 251 emoji show the message and disable it; white space alone is valid and is sent as no topic (R11).
- R9. People. The picker's candidates are `usePeople()` whose `status` is `active` and whose id is not `useCurrentUserId()`, each with `hue` `personHue(id)`: a deactivated person is not offered (TOKI-029 R4 refuses them with `invalid_member`) and the Admin is not offered, because the server makes the Admin a member (TOKI-029 R3). No request lists people (TOKI-034 R21). `max` is `CHANNEL_MEMBERS_ADD_MAX` of `@toki/shared` (200, the length that TOKI-029 R4 allows in `memberIds`), `limitMessage` is `t("createChannel.people.limit", { count: 200 })`, `searchLabel` is `t("picker.search.label")`, `emptyText` is `t("picker.empty")` and `removeLabel(name)` is `t("picker.chip.remove", { name })` (the texts of TOKI-034 Table T; none is repeated in `createChannel`). The chosen ids are the dialog's state, in the order pressed. Check: with a store of 5 people (one deactivated) and the Admin, the picker lists 3; with 201 candidates, pressing a 201st person shows the limit message and adds nobody (the Admin is the 201st person of a workspace of about 200, NFR-04, so this is a safeguard).
- R10. The state of Create. `Create` has `disabled` and `aria-busy` as follows: it is `disabled` while the name is not valid (R7), while the topic is not valid (R8), while the name is the name that the server last refused (R13) and while a request runs (D-104, D-111); it has `aria-busy="true"` while a request runs. While a request runs, Cancel, the switch and the two fields (`readOnly`) are also disabled, and so is the whole people group: `fieldset.ccpeople` has `disabled`, which disables the search input, every row and every chip's remove button inside it without a prop of `PeoplePicker` (TOKI-034 R18 has none). So what was sent cannot change under the request. The Private switch counts for nothing in the validity of the form: it is a value, not a validity. Check: component test of every row: empty name, valid name, invalid name, long topic, a refused name, a request held open; in the last case a second press sends nothing (one request, D-111), the switch, the fields, the search input and a chip's remove button cannot be changed, and every one is enabled again after the answer.

Sending
- R11. Create. Pressing Create, or Enter in the Name or Topic field (R5) while Create is enabled, calls `submitCreateChannel(...)` of `submitCreateChannel.ts`, a plain function that calls no hook and takes `ensureOnline`, `createChannel` (the store's command), `newId`, the form values and the attempt of R15; the dialog binds them. In this order: (1) `ensureOnline()` of `useOnlineGate()` (TOKI-093 R17); when it returns `false` nothing is sent, the dialog and its fields stay, and the explanation toast of that helper is the only feedback (D-060, D-079: an admin action is blocked offline); (2) `body` is built: `{ name, isPrivate, topic?, memberIds? }` with `name` as shown, `isPrivate` the switch (always sent, `false` included), `topic` the trimmed topic and left out when it is empty, `memberIds` the chosen ids in the order pressed and left out when none are chosen; (3) the id of R15 for that `body`; (4) `conversations.createChannel({ id, ...body })` (TOKI-032 R15, `POST /api/v1/channels`); (5) it returns one of `{ kind: "created", id }`, `{ kind: "blocked" }`, `{ kind: "nameTaken" }`, `{ kind: "invalidMember" }` or `{ kind: "failed" }` (R13, R14). The screen sends no `createdBy`, no workspace and no role (TOKI-029 R3). Check: unit test of the function with a fake command and a fake gate: the body for each combination of the switch, an empty and a filled topic, and no, one and two people; the `id` of every body matches the pattern of TOKI-029 R17 (the server's check); offline sends nothing and does not call `newId`; the Admin's own id is never in `memberIds` (R9).
- R12. Success. When the command resolves with `{ id, created }` (a 201, or the 200 of a repeat, TOKI-029 R5; both are handled alike, with no other text), the store already holds the entry (TOKI-032 R13, R15). Then, in this order: `onCreated(id)` when given, `onClose()`, `onOpenConversation(id)`. No toast is shown (the log gives creation none; D-076: "the screen shows it", and the opened channel is the confirmation). The dialog closes through `onClose` without the guard (TOKI-093 R20: a form submitted successfully closes through the owner's code). If the dialog was unmounted before the answer, the store is still updated by the command and neither `onClose` nor `onOpenConversation` is called. `onCreated(id)` is called only while the component that owns the dialog (`CreateChannelButton`, or the screen that uses `useCreateChannelDialog`) is still mounted: `useCreateChannelDialog` keeps a mounted flag and hands the dialog a wrapper that checks it. So a list that is still on screen learns of the change, and a page that was left during the wait (the browser's Back) gets no call on a state that is gone; TOKI-025's `reload` needs no guard of its own. `CreateChannelButton` and `useCreateChannelDialog` give `onOpenConversation` as the router's navigation to `/c/{id}` (TOKI-033 R20, the router of TOKI-006); the dialog itself imports no router. After a creation the Admin's list of conversations shows the channel in the Channels group (TOKI-033 R29) because the command stored it; whether a filter, a search text or a collapsed group hides it is concern 6. Check: component test with a fake command that resolves for 201 and for 200: the three calls in order, once each, and no toast; with the dialog unmounted first (the button still mounted): only `onCreated`; with the button unmounted too: no call at all; the navigation test with a memory router: `/c/<id>` after a creation, from the Admin page.
- R13. A name in use. A 409 `channel_name_taken` (TOKI-029 R4, R5: any channel of the workspace with that name, public, private, archived or `general`, and also the loser of two simultaneous requests, D-115, D-128) gives `{ kind: "nameTaken" }`. The dialog remembers the refused name, shows `t("createChannel.name.error.taken")` as the `error` of the Name field, moves focus to the name input, keeps every other field and the chosen people, and enables nothing else: Create stays disabled while the name equals the refused one (R10) and is enabled again after the first edit that makes the name different, which also removes the message. The text does not say which kind of channel holds the name. The branch reads `status` and `code` of the `ApiError` (TOKI-032 R4) for this one code; every other answer goes through `classifyApiError` (R14). One case this message also covers: an earlier press of this dialog made the channel but its answer was lost, and the Admin changed the people or the topic before pressing again (R15 then makes a new id, and the server answers 409 for the name that the Admin's own first press took). The line says the name exists, and the channel is in the list of the Admin page. Check: a 409 with the code shows the message under the name, focus on the input, Create disabled; editing the name enables Create; typing the refused name again disables it; a 409 with another code does not show the message (R14).
- R14. Other answers (D-131, D-104). Three answers are read by their code: a 409 `channel_name_taken` (R13), a 400 `invalid_member` and a 409 `channel_id_in_use`. Every other failure goes through `classifyApiError` of TOKI-032 R8 (D-131: one behaviour for every feature), and the class decides: `unauthenticated` (the session state's, TOKI-032 R7, TOKI-023: the dialog adds nothing) and `ignore` (an aborted call) show no line and enable Create; every other class (`field`, `no_access`, `fresh_copy`, `wait`, `retry`, `unreadable`, `unknown`) gives `{ kind: "failed" }` and shows `t("common.error.actionFailed")`. This dialog shows the same plain line for all of them on purpose and says so: the shared page for 403 and 404, the wait text for a 429, the reload text for an unreadable answer and the error ID with Retry are TOKI-082's and no key for them exists yet (TOKI-034 R23 and concern 6 there do the same); a 400 `validation_failed` is not reachable from a correct screen, which validates first; and an `unreadable` answer keeps Create enabled, because the dialog has no Retry button of its own, a press is the form's own action, and the same id never makes a second channel (R15). A 400 `invalid_member` (a chosen person was deactivated since the list was read, TOKI-029 R4) gives `{ kind: "invalidMember" }`: the dialog waits for `conversations.refresh()` (TOKI-032 R10), then reads `getPeople()`, removes from the chosen ids every id that is no longer an active person, and shows `t("createChannel.error.invalidMember")` in the line of R5; if the refresh itself fails, the dialog shows `t("common.error.actionFailed")` and removes no chip (no id is known to be gone, and the line of `invalidMember` would tell the Admin to check a list that was not read); it keeps the other fields and nothing was created (the server refuses the whole request). A 409 `channel_id_in_use` (R15: not reachable from a correct screen) makes the dialog forget its attempt, so the next press makes a new id, and shows `t("common.error.actionFailed")` (TOKI-093 Table B). The line is `div.gerr` of TOKI-012 with `role="alert"` in `div.ccfoot` (R5), one line at a time, replaced by the next message and removed when the next press starts. After every answer that is not a success Create is enabled again, except for the name that the server refused (R13), and focus goes to the name input for `nameTaken` and to the Create button for every other answer (the pressed button was disabled during the wait and lost focus); pressing Create again is the Retry of D-126 and is safe (R15). Check: a table test of each answer (400 `invalid_member`, 409 `channel_id_in_use`, 400 `validation_failed`, 403, 404, 429, 500, `timeout`, `network`, `invalid_response`, an aborted call, a 401 with `session_ended`) for the message shown, the class used, the state of the buttons, where focus is and that the fields keep their content; the people tests: a refresh that deactivates one of two chosen people leaves one chip; a refresh that fails leaves both chips and shows the generic line.
- R15. Retry never makes two channels, and a changed form never reuses an id (D-111, TOKI-029 R5). The dialog keeps, while it is open, one attempt `{ id, body }`, empty when it opens, where `body` is the body of R11 without the `id`. `idFor(body)` returns the id of the attempt when `body` equals the attempt's body in every part (`name`, `isPrivate`, `topic` after the trim, and `memberIds` with the same ids in the same order), and otherwise makes a new id with `newId()`, stores the new attempt and returns it. So a retry of the same form after a failure, after no answer, or after the dialog's own error reuses the id, and the server answers 200 with the channel when the first request had in fact succeeded (the repeat of TOKI-029 R5); and a form whose name, switch, topic or people changed since the last press always gets a new id. This is stricter than the server needs: TOKI-029 R5 answers 200 for the same id, name and privacy whatever the topic and people, but says that a client that sends one id with other `memberIds` "gets the channel as it is and nobody is added", a client error; because the dialog stays editable after a failure, reusing the id there would make that case reachable and the Admin would be told of a success in which the people were not added. The cost is stated in R13: if the first press had made the channel and its answer was lost, and the Admin then edits the people or the topic, the second press gets 409 `channel_name_taken` for the name of the Admin's own channel. The attempt is forgotten when the dialog closes and by the 409 `channel_id_in_use` of R14. Check: two presses after a `network` failure with the same form send the same `id`; a change of the name, of the switch, of the topic, of the order of two people, and of one added or removed person between the two presses each send another `id`; after a close and an open the id is new; a fake command that answers the first press late and the second at once (the second press cannot happen while busy, R10) is covered by the unit test of `idFor` alone.

- R16. Form guard (D-070, FR-28, AC-074, AC-075). The dialog uses `useFormGuard` of TOKI-093 with `hasContent` equal to `hasFormContent({ name, topic, people: selected })`, `formName` `t("createChannel.title")` and `onClose` the dialog's close. 9. Closing during a request, and the id of a retry. Decided in this spec: a close request is ignored while the request runs and the header's close button is not drawn then (R17), and a retry reuses its id only while the whole form is unchanged (R15). Reasons: a dialog closed in flight leaves a channel the person was not shown; a new id for an unchanged retry could make two channels when the first answer was lost, and the server's repeat rule (TOKI-029 R5) exists for this case; a changed form gets a new id because the server's repeat answer does not add people or a topic that were not in the first request. The accepted cost is the 409 for the name after a lost answer and an edit (R13). Owner: Thanh Truong.
