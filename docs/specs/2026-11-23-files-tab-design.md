## Goal
Files, images and links are shared in conversations and then lost in the scroll. This ticket builds the two places that list them: the Files section of the app, which lists every file, image and link from the conversations the person can read, newest first, with a search by file name or sender, the chips All, Images, Documents and Links and a list or grid switch (FR-39, F30); and the Files & links tab of each conversation, which lists the same kind of items for that conversation only (FR-39, AC-105). Pressing an item opens the window of TOKI-062.
The hard rules are two. An item of a conversation the person cannot read never appears, whatever the filter or the search text, and a person who left a channel stops seeing its files while an archived channel's files stay (F30, AC-105, D-116, D-170). The search must reach every file the person can read, not only the ones the screen holds, so it is made by the server.
The ticket also adds the prototype's sample files and images to the seed data, so the two screens have content after `dev:seed`.

## Requirements
Shared shapes and the request
- R1. `packages/shared/src/files/shared-items.ts`, re-exported by the index of `files` and of the package, exports: `SHARED_ITEMS_PAGE_DEFAULT` = 50 and `SHARED_ITEMS_PAGE_MAX` = 100 (the 50 is the proposal of D-171, which is open; concern 4), `SHARED_ITEMS_QUERY_MAX` = 200 code points, `SHARED_ITEMS_CURSOR_MAX` = 512, `sharedItemKinds` (`file`, `image`, `link`); `SharedItemsQuery` (a strict Zod object: `conversationId` an optional lower-case UUID, `kind` an optional one of `sharedItemKinds`, `q` an optional string, `limit` an optional integer from 1 to `SHARED_ITEMS_PAGE_MAX`, `cursor` an optional non-empty string of at most `SHARED_ITEMS_CURSOR_MAX`); `SharedItem`, a strict union by `kind` with `Base = { id, conversationId, messageId, senderId, sharedAt (ISO 8601 UTC with Z: the time of the message that carries the item, R4), parentId: string | null }`, where `id` is the `attachments.id` for a `file` or an `image` and the id of the `message_link_previews` row for a `link` (it identifies the item and is not an order key, R4), and `parentId` is the root of the thread when the message that carries the item is a reply and `null` for a message of the main list (R5 (c)): `{ kind: "file" | "image", file: FileEntry }` (the `FileEntry` of TOKI-058 R3 with the `thumbnail` key of TOKI-060 R2) and `{ kind: "link", link: { href, siteName, title, description: string | null } }` (the fields of `LinkPreviewSchema` of TOKI-061 R15 without its `id`); and `SharedItemsResponse` `{ items: SharedItem[], nextCursor: string | null }`. The item holds no storage key and no address of a file. `q` is trimmed (`String.prototype.trim`) before the length test, an empty result is the same as no `q`, and `SHARED_ITEMS_QUERY_MAX` applies to the trimmed text. The package has no DOM global. - R2. - R3. Which items, and the filters. The set of conversations is `listConversationIdsOfUser(client, actor.id)` of TOKI-038 R8: every conversation the person has a member row in, an archived channel included, and no other (D-116: a conversation the person has not joined, a public one included, cannot be read; D-170: after leaving, the files leave the page, and an archived channel's files stay for its members). With `conversationId` the set is cut to that one id when it is in the set and is empty otherwise, and no further statement is made. `kind` keeps one kind and no `kind` keeps all three. The kinds are decided by one rule on the server: a file of the state `attached` is `image` when its `thumb_state` is `pending` or `ready` and `file` when it is `none` (the rule of `fileImage` of TOKI-062 R8 as TOKI-060 R15 fills it: the card and the chip never disagree; concern 5), and a link is `link`. `q` is applied to the name and to the sender together: an item is kept when the folded name contains the folded `q`, or when its sender is one of the people whose folded display name contains the folded `q`. The name is `files.name` for a file or an image and the `title` of the preview for a link. The fold is `foldText` of TOKI-050 R2 for the text typed and for the people (`listPeople(client, workspaceId)` gives every account, a deactivated one included, so a file of a person who left the company is still found by name) and the SQL expression `lower(replace(replace(regexp_replace(normalize(value, NFD), '[\u0300-\u036F]', '', 'g'), 'đ', 'd'), 'Đ', 'd'))` for the stored name, the same steps (concern 6). A fold that is empty after folding (a lone combining mark) matches nothing. The text is compared with `strpos` on the folded value, so `%` and `_` are plain characters; the fold is computed for each row of the person's conversations and no index serves it, which is acceptable at the size of the sample and not measured by TOKI-089, whose load has no files (Testing). A file of the state `pending`, `ready` or `removed` is never an item: an unsent file belongs to its uploader only (TOKI-058 R12), and a file of a deleted message is `removed` (TOKI-058 R17). A link row that is `failed`, removed by the sender (`removed_at` set) or in a deleted message (its rows are deleted, TOKI-061 R17) is never an item. The chip and the search apply together (AC-106). - R4. Order, paging and the cursor. `sharedAt` is the `created_at` of the message that carries the item, for all three kinds: for a file or an image it is `attachments.created_at`, which the send writes from the message's `created_at` (a change request to TOKI-058 and to the call site of TOKI-037, Plan changes), and for a link it is `message_link_previews.sent_at`, the message's `created_at` copied by the job (a change request to TOKI-061, Plan changes; the row's own `created_at` is the time the job ran and is never used here). Each is in whole milliseconds from the clock (TOKI-019 convention 3; no database default), so a file that waited in the composer for hours is placed by its send, and a card added by an edit or after a retry keeps the time of its message (concern 7). Items are in the order `sharedAt` descending, then `messageId` descending, then `rank` ascending, across files, images and links together. `rank` is the `position` (0 to 9) of a file or an image, and 10 plus the `position` of a link: inside one message the files come in their position order and the cards after them, as the message draws them (TOKI-062). The pair (`messageId`, `rank`) is unique, so the order is total and no id made at random decides it. The page has `limit` items (default `SHARED_ITEMS_PAGE_DEFAULT`). Each source is read with one more row than the page needs, the two lists are merged by the order above and cut to `limit`, and `nextCursor` is not null exactly when more items exist after the last one returned. `nextCursor` is opaque to the client: base64url of the JSON array `[sharedAtIso, messageId, rank]` of the last item returned, and the next page is the items after that triple in the same order (`(shared_at, message_id) < ($1, $2) or (shared_at = $1 and message_id = $2 and rank > $3)` on each source, with `rank` as the column `position` or `10 + position`). A cursor that is not base64url, not that JSON, of another shape, a `messageId` that is not a lower-case UUID, a `rank` that is not an integer from 0 to 32,767 or a time that is not ISO 8601 UTC with `Z` is 400 `validation_failed` with the path `cursor` and the code `invalid_cursor` (as TOKI-070 R8). A new item arriving between two pages is not repeated or skipped for the items already read, because the order key is fixed at the send. Check: 120 items of three kinds read with `limit` 50 give 50, 50 and 20 with no repeat and none missing and equal to the order of the whole set; two items of different messages with one `sharedAt` are in `messageId` order, and the two files of one message are in `position` order, with a page edge between them, and none is repeated or skipped; a link whose row was written an hour after its message is ordered and dated by the message (`sharedAt` equals the message's `created_at`); a cursor made for a page of `kind` `link` used with `kind` `file` still gives the items after the triple (the triple is the position); each bad cursor is 400; a file sent between two page reads shows only on the next first page; an item list of one source only (`kind=link`) reads no `files` row (a statement log).

The client
- R6. The call and the list hook. `apps/web/src/features/files/` holds `api.ts` (`listSharedItems(query, signal)`: the `GET` through `api.request` of `apps/web/src/client.ts`, parsed with `SharedItemsResponse`, an item that fails the schema fails the whole page as an error; no value of the item is stored outside the hook) and `useSharedItems({ conversationId?, kind?, q? })`, which returns `{ status: "loading" | "ready" | "failed", items, hasMore, isLoadingMore, isRefreshing, moreFailed, loadMore(), reload() }`. Rules, as the list of TOKI-025 R6 and TOKI-034: a first page, a change of `kind`, `q` or `conversationId` and a reload each start a generation; the answer of an earlier generation is dropped and its request is aborted; a reload keeps the rows on screen until the answer arrives and asks for as many rows as are shown (up to `SHARED_ITEMS_PAGE_MAX`, the next page after them by the cursor), so a person scrolled far down keeps the place; a failed reload keeps the rows and `status` stays `ready`; a failed first page is `failed`; a failed next page keeps the rows and sets `moreFailed` with a way to try again. The typed text reaches the hook after the person has stopped typing for 250 ms, measured with the `timers` object of `apps/web/src/client.ts` (the shape of `Timers` in `client-core`), never a global timer: 250 ms is a builder choice, no decision gives it (concern 9). `q` is sent trimmed; an empty text sends no `q`. The rows are held in memory only and dropped when the screen unmounts and on sign out (Data safety). `loadMore` is called by `useMoreOnScroll` of `apps/web/src/features/useMoreOnScroll.ts` when the end of the list is within 48 px or the focus enters the last row. Check: with a fake `api` and the `TestClock`, 50 rows then 20: `loadMore` once gives 70 and a second call with no more rows asks nothing; typing `a`, `ab` within 250 ms sends one request for `ab` and moving the clock sends it; a slow answer of an older generation is dropped (a deferred promise); a reload of 120 shown rows asks for 100 and then continues by the cursor; a failed reload keeps the rows; a failed first page is `failed` and `reload` retries; sign out clears the rows.
- R7. The list follows the data. `useSharedItems` registers, once while mounted, handlers with `registerEventHandler` of TOKI-040 R18 for the event kinds `message.created` (only when the message's `files` is not empty), `message.deleted`, `message.thumbnail_updated` (TOKI-060 R10), `message.link_previews_changed` (TOKI-061 R16), `member.joined`, `members.added`, `member.removed`, `member.left` and `conversation.left`, which change what the person may read or what an item is; for the member kinds and `conversation.left` only when the event is about the signed-in person, and for the others only when the conversation is the tab's own for the tab. Each such event calls `reload()` of R6. While a reload is running, further events set one flag, and one more reload runs when the first ends, so a burst makes at most two requests and the last state is read. The hook also reloads once when the connection comes back after it was down (`useIsOnline()` of `features/attachments/deps.ts` turns from false to true), because events may have been missed. The handlers are removed on unmount. Nothing is merged into the rows by hand: the server answer is the one source. Check: with a fake `registerEventHandler`, each kind triggers one reload and an unrelated kind (`message.edited`, `reaction.added`) none; a `message.created` of a message with no file triggers none; ten events during a reload make one extra reload, not ten; after unmount an event triggers nothing and the handlers are removed; the offline-to-online change triggers one reload; the new file of TS-165 is the first row after the event.

## Design
### How it fits
```
 Files section (/files)            Files & links tab (conversation page)
   FilesPage  --useSharedItems-->    FilesTab(conversationId) --useSharedItems-->
          \                                  /
           GET /api/v1/shared-items?kind&q&conversationId&limit&cursor   (R2)
                |  session -> canUseWorkspaceViews -> one READ ONLY transaction
                |  S1 listConversationIdsOfUser         (conversations)
                |  S2 listPeople (only with q)           (members)
                |  S3 listSharedFiles                    (files: attachments + files)
                |  S4 listSharedLinks                    (link-previews)
                |  merge by (sharedAt, id), cut to limit
                |  S5 listMessageParents                 (messages: parentId)
 press an item --> useFileDetails().open(details, { openInConversation })   (TOKI-062; the function calls useOpenMessage() of TOKI-068)
 events (message.created, ...thumbnail_updated, link_previews_changed, member.*) --> reload   (R7)
```

### Choices made here
- **A server list, not a client filter.** The client holds the messages of the conversations it opened, a page at a time, never every file of every conversation the person is in, and the search of TOKI-070 does not search by file name. A filter on the client would list only what was loaded and would answer "No files match" for a file that exists. The server reads the member rows once and the items from the two tables with indexes (concerns 1, 2).
- **A module with no table, in the pattern of search.** `file-list` combines four modules through their public entries, so no module reads another's table and no two import each other; the files and the links keep their own tables and the merge by one order key is made in code over two small pages. A SQL `UNION` across modules would break the boundary.
- **The kind is decided in one place.** The server computes `image` or `file` from the thumbnail state, the same rule `fileImage` applies to the card, and a test makes the two equal. So the Images chip never holds a file that draws as a file card (concern 5).
- **The order key is fixed at the send.** `sharedAt` is the message's time for every kind, written once, and the order ends with the message id and the position, so a page boundary cannot repeat or skip an item, a file uploaded early is placed where it was sent and a late card keeps its message's day (concern 7).
- **The server answer is the only source.** An event reloads the list instead of patching rows by hand: kind, order, search and access are all server rules and a second copy on the client would drift.
- **The window is the one of TOKI-062.** This ticket builds no dialog and no jump.

### Errors
- No session -> 401; a deactivated account -> 401 `account_deactivated`; a bad query -> 400 `validation_failed`; a bad cursor -> 400 with `invalid_cursor`; a `conversationId` that is not readable -> 200 with no items; any other failure -> 500 `internal_error` with no text of the query.
- The first page fails -> the failed state with Retry; a later page or reload fails -> the rows stay and Retry is shown for the page (R6, R11).
- An item whose file was deleted after the page was read -> the window opens on what the item held; Download then answers 404 in its new tab (TOKI-062); the next reload drops the item.

## Data safety
- The route returns items only of conversations the person has a member row in, from one snapshot, and the same body for a conversation that is not readable and one that has nothing (R2). A guest, an outsider, an Admin who is not a member and a person who left get no item of it (R5).
- An item holds no storage key and no address; the only address of a file is the route of TOKI-058 R12, which the window uses (TOKI-062). The text of a query is not logged and not in an address that is kept: the route is a `GET` with `q` in the query string, so the access log of the proxy must not log query strings (the request already made of TOKI-084 for the signed addresses; Plan changes), and `cache-control: no-store` keeps the answer out of the browser cache.
- File names, link titles and sender names are data: drawn as text, never as markup and never in an address or a log line.
- The sample's bytes are made by code, hold no real document and are written by the development seed only (TOKI-081 R21, D-031, D-147); the production image holds no sample (TOKI-084).

## Areas of concern

Reason: the client holds the messages of the conversations it has opened, a window at a time, so a filter on what it holds would miss files that the person can read; the search of TOKI-070 does not search by file name (its Scope names TOKI-063 for it). 2. Who owns the list. Decided in this spec: this ticket owns `GET /api/v1/shared-items`, the module `file-list` and the reads it adds to `files`, `link-previews`, `messages` and `conversations` (R2, R5). 3. What a link item is. Not decided. FR-39 and F30 say the section lists "every file, image and link", and TS-168 expects a message containing `https://example.com` to give a link item; the prototype's link item is a card with a title, a site and a description (`D.msgs` `att` of kind `link`).
