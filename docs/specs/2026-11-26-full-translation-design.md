# Full translation design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/full-translation.md (Thanh Truong)
Ticket: TOKI-080

## Goal
Every text a person reads must be in English (the default) and in Vietnamese, and every date and time must follow one format in the person's time zone (D-018, D-064, D-073, D-123, D-189). The i18n package (TOKI-017) already fails CI when a key lacks a language, and each screen ticket adds its keys in both languages. What is missing is the proof that no text escapes the catalog, the Vietnamese names of weekdays and months, one place that gives a formatter its context, a rule that keeps date formatting in `@toki/shared`, and a review of the Vietnamese drafts that the merged specs hand to this ticket. After this change a literal in a component, a date written outside the shared module and an English text on a Vietnamese screen each turn a CI check red, and the Vietnamese texts have one glossary and one written way of being sourced and reviewed.

## Scope
- In:
  - The Vietnamese weekday and month names in `packages/shared/src/datetime/names.ts` (R1 to R3).
  - One date context hook in `apps/web/src/date/`, which replaces the three copies on main and reads the person's time zone (R4 to R8).
  - Two lint rules: no date or number formatting by the browser (R9), no literal text in components (R10), and the moving of the literals that the second rule finds (R11).
  - A browser check that the Vietnamese interface shows no English catalog text, no `AM` or `PM` and no `Invalid Date` (R12 to R14).
  - A report command of `@toki/i18n` for the review, the glossary and its test (R15 to R17).
  - The written rule for sourcing and reviewing Vietnamese text, and the review itself (R18, R19).
- Out (not now):
  - The catalogs, the lookup, the provider, `formatNumber` and the missing-translation check: TOKI-017 (R4 to R17 of its spec). This ticket changes none of them. The check that fails CI on a missing text stays TOKI-017's `i18n` job (its R20); this ticket adds no second one (Design, "The CI checks").
  - The keys and English texts of each screen and of each server text: the ticket of that screen or module. This ticket changes Vietnamese values only, after the review, and moves the literals that R11 finds.
  - The language switch, saving the language to the account, the `lang` attribute of the page and the time zone field of Preferences: TOKI-078.
  - The column that stores a person's time zone and the request that changes it: the "Profile and preferences (server)" ticket that the accounts spec places before TOKI-078 (concern 5 of `2026-11-17-account-tables-design.md`; it has no number yet).
  - The formatting functions themselves (`formatTime`, `formatDate`, `formatDay`, `formatDateTime`, `formatCountdown`) and their rules: TOKI-094 (R1 to R8 of its spec). This ticket adds one language to the name table and calls them.
  - `formatFileSize` (TOKI-059, R4 of the composer-attachments spec). It is not on main yet. When built it writes a number through `formatNumber(language, value)` and the unit symbols `B`, `KB`, `MB`, `GB`, which are the same in both languages; this ticket adds nothing for it, and the rule of R9 keeps its number formatting in `@toki/i18n`.
  - Texts that are data, not interface: names of people, channels and files, the text of messages, the brand name `Toki`, the two language names `English` and `Tiếng Việt` (TOKI-017 R3), the UTC offset `UTC+7`, the unit symbols above, key names written as symbols.
  - The sort order of names (`Intl.Collator("vi")` in `apps/web/src/conversation/useChannelMembers.ts`): not changed.
  - A third language, loading a language on demand, right-to-left text.

## Design
### What exists on main (read before writing)
- `packages/i18n`: `src/messages/{en,vi}/` hold 16 namespace files today (`account`, `admin`, `archive`, `browse`, `common`, `conversation`, `conversationList`, `createChannel`, `emergency`, `join`, `mail`, `membership`, `nav`, `picker`, `sessionEnded`, `signIn`); each language has an `index.ts` that lists them. `src/check.ts` and `scripts/check.ts` are the missing-translation check (a key missing in one language, an empty text, different placeholders, a key that breaks the naming rule, a bad plural form); `src/format.ts` holds `formatNumber` only; the plural rule is English `one` and `other`, Vietnamese `other` (`src/translate.ts`, TOKI-017 R6). `formatFileSize` is not in the code: its spec (TOKI-059, composer-attachments) is merged and the build is later.
- Namespaces named by merged specs and not yet built, so that the review reads them when they land: `messageList`, `message`, `composer`, `thread`, `messageActions`, `pins`, `formatting`, `mentions`, `messageBar`, `presence`, `status`, `profile`, `files`, `linkPreview`, `attachments`, `activity`, `later`, `palette`, `quiet`, `notifications`, `push`, and the screens of TOKI-078, 079 and 082. This ticket is built after them (Plan changes).
- Dates: `@toki/shared` `datetime` writes every form (TOKI-094); its `names.ts` lists `en` only, with a comment that says so. The day words are the keys `common.today`, `common.tomorrow`, `common.yesterday` (they exist in both languages). Three places build the formatter context: `apps/web/src/account/use-date-context.ts`, `apps/web/src/admin/useDateContext.ts` and `apps/web/src/conversation/AboutSection.tsx`; each reads the zone with `Intl.DateTimeFormat().resolvedOptions().timeZone`. The zone of the person's profile is read by none, because no column stores it yet.
- Lint: `eslint.config.js` has three boundary rules and local rules under `tools/lint-rules/`, each with a test file listed in `test:lint-rules`. No rule on literal text or on date formatting exists. `apps/web` has one literal text (`NotFoundView`).
- `pnpm i18n:check` is the job `i18n` of `ci.yml`.

### The CI checks
Decided in this spec. The question of the intent is what the check for a missing translation covers beyond TOKI-017's. TOKI-017's check proves that every key has a text in both languages, with the same placeholders and a valid plural form. Three ways for a text to be missing remain, and each gets a check that fails by itself:
| A text can be missing because | The check | Where it runs |
| :---- | :---- | :---- |
| a component holds the text itself, so no key exists | `toki/no-literal-text` (R10) | `lint` job |
| a date or number is written by the browser, in a format and a language of the device | `toki/no-date-formatting` (R9) | `lint` job |
| a text is built outside JSX and rendered later, or a Vietnamese value is a copy of the English text, or a screen reads the wrong language | the browser check of R12 on the Vietnamese interface | `end-to-end` job |
| the weekday and month names, which are outside the catalogs | the name table test (R3) | `tests` job |
The check does not fail a Vietnamese text that equals the English one: TOKI-017 R18 says that `Email` and `Admin` are fine, a rule that finds copies without false alarms would need a list of exceptions that grows with every ticket, and the browser check already catches an English text that reaches the screen with a different Vietnamese value. R15 prints the list for the review. Reason for no new job: the failures are all found by jobs that exist, so one pull request shows one red entry that names its cause.

### The date context and the time zone
- The decided rule is that every time a person sees is shown in the time zone set in their profile (concern 2 of TOKI-094, option (a)). The hook of R5 applies it. Until the profile server ticket exists no person has a zone in the store, so the hook gives the device's zone; the choice for a person who never sets one is concern 1.
- `useDateContext` takes no argument. The old `timeZone` argument of the admin copy existed for tests; the test of R5 gives the zone through the store instead, so the production hook has one input path.
- The hook builds a new object on each render, as the three copies do (`now` changes). A caller that needs a stable object memoises it itself.

### The Vietnamese names
Decided in this spec: the names are a table in `names.ts`, not `Intl.DateTimeFormat('vi')`, for the reason TOKI-094 gives: the same text on the server, in the browser and in React Native. The order of the parts does not change with the language (concern 1 of TOKI-094, which the product owner kept when D-189 was answered). The wording is concern 2.

### The two rules
- `no-date-formatting` matches on member names and identifiers, as the existing rules do, because lint has no types: `x.toLocaleString()` is reported on any receiver, number or date. A caller that needs a number with a separator uses `formatNumber`. `Intl.Collator` is not reported (sort order is not a format).
- `no-literal-text` takes the attribute list and the word list from `eslint.config.js`. The list holds the props that `ui-web` components take for text (TOKI-012, TOKI-013 and the specs of the components: `label`, `text`, `heading`, `description`, `hint`) and the HTML attributes that a reader or a screen reader announces. A prop with another name that carries text (a new component with `caption`) is not seen: adding the name to the list is a one-line change in the ticket that adds the component, and R12 sees the text on the screen in the meantime.
- Both rules ignore test files, as the existing ones do, and use `noInlineConfig`, so no comment switches them off (`.claude/rules/packages.md`).

### The browser check
- The check reads what is on the page, so it also sees a text built in a constant (the limit of R10). It cannot see a state that no test opens; `STATES` is the list of what is covered, and R14 fails when a route has no state. A dialog or menu is covered only when a state opens it: the five of R12 are the first; the ticket that adds a screen adds its states in its own pull request, which is the rule of Layout below.
- The stubbed data of the states holds no text equal to a catalog text (the check would otherwise report data as untranslated); where a fixture word is also a catalog word the fixture changes, not the matcher.
- Texts that are data (names, messages, file names) are not matched because they are not in the catalogs.

### Namespaces written by more than one ticket
Decided in this spec. The i18n spec says a namespace belongs to the ticket whose spec lists its keys, and that when two tickets need the same keys the first built creates them and the other uses them. Two namespaces are written by two tickets with different keys:
- `notifications`: TOKI-102 R14 names it and its first key (`notifications.preferences.saveFailed`); TOKI-075 R13 adds the group `notifications.toast.*`. Owner of the namespace files: TOKI-102. Owner of the group `toast`: TOKI-075. Whichever is built second adds its group to the files the first wrote and says so in its pull request (both specs say this). The `i18n` check reads the merged files, so the order changes nothing for CI. TOKI-078 writes the switch labels of Preferences; the namespace it uses is its own spec's choice and, if it is `notifications`, its group is its own. Reason: 102 is the ticket that both specs name as the creator.
- `files`: TOKI-059 R18 creates `files.ts` and TOKI-063 R16 writes its own keys in it. Owner of the namespace files: TOKI-059. Owner of the groups of the Files tab: TOKI-063. Same rule for the order.
This ticket owns neither: it changes Vietnamese values of these files in the review (R19) after both are built, never a key and never an English text, so a pull request of 080 never conflicts with the owners on anything but a Vietnamese line, which the owner resolves by taking the reviewed wording.

### Sourcing and reviewing Vietnamese text
- Sourcing is as the merged specs say: the prototype's Vietnamese is 17 navigation labels (13 in `nav`); every other Vietnamese text is a draft written by the ticket that adds the key, with its English, and is a proposal (D-139).
- The review (R18, R19) is a reading by one reviewer of the printed table (R15) against the glossary (R17). What the repository can prove is that the text exists (TOKI-017), that no English reaches a Vietnamese screen (R12), and that the glossary terms are used (R17 covers the 13 terms of `nav`; a term added during the review is a row of the table and the test covers it). It cannot prove that a sentence reads as a Vietnamese speaker would write it. Who the reviewer is, whether a second reader is needed, and where the review is recorded are not decided (concern 3); R18 and R19 are written so that the answer changes only a name in the pull request.

### Layout
```
packages/shared/src/datetime/names.ts        + vi (R1)
packages/i18n/
  src/report.ts  scripts/report.ts            R15
  tests/report.test.ts  tests/glossary.test.ts
  README.md                                   + "Vietnamese texts" (R18)
docs/i18n/vi-glossary.md                      R17
apps/web/src/date/
  device-time-zone.ts  use-date-context.ts  index.ts   R4, R5
tools/lint-rules/
  no-date-formatting.js  no-date-formatting.test.mjs   R9
  no-literal-text.js     no-literal-text.test.mjs      R10
eslint.config.js                              both rules, attribute list, word list
package.json (root)                           script i18n:report; test:lint-rules lists the two tests
e2e/translation.spec.ts  e2e/support/translation.ts  e2e/support/translation.test.ts   R12 to R14
```
A ticket that adds a screen after this one adds its states to `STATES` in the same pull request (R12). That is a rule of review, not of a script; R14 only forces it for a new route.

### Errors
- A literal or a browser date call is found -> `pnpm lint` fails and names the file and the rule (R9, R10).
- An English catalog text is visible in a Vietnamese state -> the browser check names the state, the string and the key (R12).
- A person's zone is not a zone the runtime knows -> the hook uses the device zone, and the device zone, when unusable, is `UTC` (R4, R5).
- A formatter returns `null` (a bad instant): what the screen shows belongs to the screen (TOKI-094 R7); R13 fails if a visible string holds `Invalid Date`, `NaN` or `undefined`.

## Areas of concern
1. The time zone of a person who has set none. Not decided. Concern 2 of the date spec decides that every time is shown in the zone set in the profile; it says nothing about a person with no zone, and the profile panel spec (concern 2) asks the same question for the Local time row and is unanswered. Until the profile server ticket stores a zone nobody has one. R5 builds a proposal: the zone of the device, and `UTC` when the device gives none. Another reading is to ask the person for a zone at first sign-in, or to store the device's zone when the account is created; both need a screen or a server rule that no ticket has. Proposal, not a decision. Owner: Thanh Truong.
2. The wording of the Vietnamese weekday and month names. Not decided. D-189 says the names follow the interface language; the prototype has no Vietnamese weekday or month. R1 writes `CN`, `T2` to `T7` and `thg 1` to `thg 12`, the short forms that Vietnamese calendars commonly use; they are a proposal under D-139, and changing one is a value in `names.ts`. Owner: Thanh Truong.
3. Who reviews the Vietnamese drafts, and how the review is recorded. Not decided. The merged specs say "reviewed in TOKI-080" and name no person; the log has no reviewer. R18 and R19 describe the work (a printed table, a glossary, a list of namespaces with counts in the pull request). Proposal, not a decision: the product owner reads the table; whether a second reader who is a Vietnamese speaker is also needed, and whether the review is a block in the pull request or a file in the repository, are for the owner to say. This spec does not state that any review by a native speaker has happened or will. Owner: Thanh Truong.
4. Who builds the lint rule against date formatting. Not decided. Concern 6 of the date spec, decided by the product owner, gives it "its own small ticket, to be done before the screen tickets write date code"; the plan has no such ticket and three screens have since built their own date context with the device's zone. R9 builds it here because the rule can only pass when the three copies are moved (R7), which this ticket does anyway. Proposal, not a decision: build it here; if the owner prefers a small ticket, R8, R9 and R20 move to it, and this ticket (size M) keeps the other 19 requirements. Owner: Thanh Truong.
5. The CI checks that this ticket adds. Decided in this spec (technical choices the Blueprint leaves to the builder): the literal-text rule with the limits written in R10 and its Design section, the browser check on the Vietnamese interface, and no check that fails a Vietnamese text equal to the English one (R16). Reason: the first two find a text that has no key or reaches the screen untranslated and give no false alarm on `Email`; a copy-of-English rule needs an exception list that every ticket would grow. Cost: a Vietnamese value that is a copy of English is found by the review (R15 prints the list), not by CI, unless it also shows on a state of R12. Owner: Thanh Truong.
6. Where the known literal goes. Decided in this spec: `Page not found` in `NotFoundView.tsx` is moved to a key in the namespace of the screen that owns the not-found state. The extra-states ticket (TOKI-082) owns the wording and the screen of that state; if it is built first, the literal is already gone and R11 finds none there; if this ticket is built first it moves the existing text under the key that TOKI-082's spec names, or, when that spec names none, under `common.error.notFound`, and TOKI-082 changes the key in its own pull request. The English text stays `Page not found` (a proposal under D-139; the prototype has no such screen). Owner: Thanh Truong.
7. Ownership of namespaces that two tickets write. Decided in this spec (a technical choice about build order, not a product rule): the owners are named in "Namespaces written by more than one ticket" (`notifications`: TOKI-102 for the files, TOKI-075 for the group `toast`; `files`: TOKI-059 for the files, TOKI-063 for the Files-tab groups). Reason: the specs of 075 and 102 say the second built adds to the files of the first and do not say who owns them, and one name per file avoids two pull requests that each assume the other creates it. This ticket owns neither and changes Vietnamese values only. Owner: Thanh Truong.
8. What is not translated. Decided in this spec: data (names, messages, file names), the brand name `Toki`, the language names (TOKI-017 R3), the unit symbols of file sizes (TOKI-059 R4), the UTC offset of the profile (TOKI-057 R7) and symbols without letters. Reason: they are not sentences and read the same in both languages; each is already stated by the spec of the ticket that shows it. The rule of R10 reports a letter in JSX text, so a new brand word or abbreviation needs a line in the word list of `eslint.config.js`. Owner: Thanh Truong.
9. The size of the browser check. Decided in this spec: the check opens the states listed in R12 only and relies on each screen's own render tests in Vietnamese for the rest. Reason: a walk through every dialog and menu needs a stub for each, and each screen spec already requires a Vietnamese render of its own texts. A screen the list misses is covered by the rule of R10 and by those tests. Owner: Thanh Truong.
