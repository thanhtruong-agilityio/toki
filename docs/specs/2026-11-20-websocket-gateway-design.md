# WebSocket gateway design

Date: 2026-11-20 · Status: draft for review
Intent: docs/intents/websocket-gateway.md (Thanh Truong)
Ticket: TOKI-038

## Goal
A person with Toki open must see what happens in their conversations without reloading: a changed topic, a person added or removed, an archived channel, and (with the message API) every new message. Today the server only answers requests. This work adds the WebSocket address, the check that the connection belongs to a signed-in person and ends with the session, the in-memory map of who listens to which conversation, and the push of each event of the log to the people it concerns, once and in order. It also gives the channel changes their events, through the seam that the channel API left empty.

## Scope
- In:
  - The address `GET /ws`, its handshake, the session check and the Origin check (R1 to R6).
  - The first frame `ready`, the map of conversations each connected person listens to, and the rules that keep it right (R7 to R11).
  - The frames and event kinds written in `packages/shared`, the audience of each kind, the order and the once-only delivery (R12 to R19).
  - The events of every change that reaches `recordChange` (the nine channel changes, a sent message, the first message of a DM) and of a newly opened group, with their payloads (R20).
  - Closing a connection: an ended session, a dead connection, a slow one, a flood of frames, a person with too many connections, a server that stops (R21 to R26).
  - The live-only notice of a changed person (R17) and the way later tickets add a live notice or a client frame (R27).
  - The `/ws` entry of the web dev proxy and the change to the "no route outside `/api/v1`" rule (R1, R28).
  - Server tests, including tests with real connections.
- Out (not now):
  - The tables of the event log, `appendEvent`, `getLastEventNumber`, the numbering with no gap, the pruning after 7 days: TOKI-036 (the `realtime` module). This work calls `appendEvent` and reads the log; it changes none of them (R14).
  - The message API, the system lines, and hiding a new DM from the other person until its first message: TOKI-037. It calls `recordChange` with `message_created` and `direct_conversation_appeared` and adds its condition to the read of R8; this work turns those calls into events (R20). The shape of a message (`MessageEntry`) is TOKI-037's.
  - Everything on the client: opening the socket, the retry delays (1, 2, 5, 10, 30 seconds, D-129), answering `ping`, the offline banner, fetching what was missed, the reload after 7 days away and what to do on each close code: TOKI-039. Applying events to the cache and the optimistic send: TOKI-040. This work ships no client code.
  - The request that returns the events a client missed: TOKI-039. It uses the same audience rule (R15) and the same read of the log.
  - The typing signal and presence: TOKI-044 and TOKI-055. They use the mechanism of R27.
  - Activity items and push notifications: TOKI-065 and TOKI-074.
  - The production proxy rule for `/ws` (Caddy): TOKI-084. The measure of the 150 ms target (NFR-13): TOKI-089.
  - More than one server process. The design does not stand in its way (R14), but nothing is built or tested for it (D-009).

## Requirements
Handshake and authentication
- R1. `GET /ws` is registered by the gateway and is the only route outside `/api/v1` besides `/healthz`. The rule of `app.ts` that refuses a route outside the prefix and the route-list test of TOKI-004 R10 change from "only `/healthz`" to "exactly `/healthz` and `/ws`". Check: the app answers an upgrade at `/ws`; registering a route at `/outside` still throws; the route-list test lists `/ws` and fails on any other path outside `/api/v1`.
- R2. The connection is authenticated by the same check as a request: `checkSession` of the `auth` module (TOKI-022 R44), so a cookie session is accepted only from the cookie and a token session only from `Authorization: Bearer`, an ended session, an idle one and a deactivated account are refused with the codes of TOKI-022 R25 and R27, and a valid check sets `last_used_at` like any request. The connection keeps the account id and the session id. Check: a cookie session and a token session connect; a token sent as a cookie and a cookie sent as a header do not.
- R3. A request without a valid session still completes the upgrade, and the server then closes the connection at once with close code 4401 and, as the close reason, the code the REST answer would carry: `unauthenticated`, `session_ended` or `account_deactivated`. It sends no `ready` frame and no event, and the connection is never registered. Reason: a browser does not show the status of a refused upgrade, so a client could not tell a signed-out person from a network error (concern 2). Check: no session, an unknown secret, an ended session, an idle session and a deactivated account each give 4401 with the right reason and no frame.
- R4. A request whose `Origin` header is present and different from `appOrigin` is refused before the upgrade with status 403, the code `origin_not_allowed` and the error body of TOKI-004, and no connection opens. A request with no `Origin` (an app with a token) or with the app's own origin is accepted. Reason: a `GET` is exempt from the Origin rule of TOKI-022 R46, but a page of another site could open a socket with the person's cookie. Check: three requests, one of each case.
- R5. The route reads no query string for authentication: a request with `?token=<valid token>` and no header or cookie closes with 4401 `unauthenticated`. No log line holds a cookie, a token, a query string or an email address. The gateway writes one `info` line when a connection is accepted and one when it closes, each with the connection id, and the close line with the close code, the reason and the duration. Check: the captured log of a full test has no secret value, and holds one open and one close line per connection.
- R6. A plain `GET /ws` that is not an upgrade answers status 400 with the code `bad_request` in the error format of TOKI-004. Check: one request.

Connection start and the map of who listens
- R7. After a valid check the server sends exactly one `ready` frame, `{ "type": "ready", "eventNumber": N }`, before any other frame. `N` is the last event number that the connection's map already includes: every event with a number up to `N` is not sent on this connection (the client gets what it missed from its own number to `N` by the request of TOKI-039), and every event after `N` that concerns the person is sent on it, once, in order. Check: a test with a pause between the snapshot and the registration (the seam of the Design, "Connection start") writes three events, one before the snapshot, one between the snapshot and the registration and one after; the connection gets `ready` with `N` equal to the last number of the snapshot or higher, the events up to `N` are not sent, and every event above `N` is sent once.
- R8. The map of a person is the set of conversation ids from `listConversationIdsOfUser(client, userId)`, which this work adds to the `conversations` module (it is named in TOKI-028 R18 and Design and has no caller until now). It returns the id of every conversation of which the person has a member row, an archived channel included (its members keep hearing: the restore, F26, and the strip "This channel was just archived"), and no other. The set and the event number `N` of R7 are read in one transaction, `READ ONLY` at `REPEATABLE READ`, with `readEventNumber(tx, workspaceId)` of TOKI-036 R19 (`workspaceId` is the one of the account). A second connection of a person who already has a map reuses it and reads nothing from the database. The map of a person is dropped when their last connection closes. TOKI-037 adds to this read the condition that a DM is in the set of the person who did not open it only after its first message (F25, D-091), the same rule it adds to the bootstrap read; until then a DM is in both sets. Check: a person who is in a public channel, a private channel, a DM and an archived channel and not in a second public channel and a second private channel gets exactly the first four; a second connection runs no statement; the map is gone after both close.
- R9. The map follows the log, in number order, and an event changes the map before it is delivered. A conversation-scope event that gives people a conversation (`conversation.created`, `member.joined`, `members.added`) adds it to the map of each person named in its data, so the new member receives it; a user-scope event `conversation.appeared` adds `data.conversation.id` to the map of its person. A conversation-scope event that takes a person out (`member.left`, `member.removed`) removes the conversation from that person's map first, so the leaving person does not receive it, and the user-scope event `conversation.left` (R20) is what tells the leaving person: it is delivered to them and removes the conversation if it is still there. This is the rule of TOKI-036 ("Events": a conversation event goes to the members at the moment of delivery, and the person who has just left is addressed by a user event). Check: Lan is added to a private channel while connected: Lan receives `members.added` and every later event of the channel and none before it; Minh is removed: Minh receives `conversation.left` and no event of the channel after it, and the others receive `member.removed`; a map is the same as `listConversationIdsOfUser` for every connected person after each of the twelve channel routes of TOKI-029 (a test compares them).
- R10. A person has at most 20 open connections (several tabs and devices). The 21st is accepted and the oldest of that person is closed with code 4430 and the reason `too_many_connections`. Reason: a connection that died without a close (a closed laptop) is noticed only by R24, and a reconnect loop must not pile them up. The number is a technical choice of this spec (concern 5). Check: 21 connections of one person leave 20, the first one closed with 4430.
- R11. The registry of connections holds, for each connection, only: the connection id, the account id, the workspace id, the session id, the time of the last frame received, the time of the last `ping` sent, and the socket. It holds no cookie, token or secret. Check: a test reads every field of the registry and finds no value of the session secret.

Events and delivery
- R12. Frames are JSON text, one object each, with a `type`. The server sends `ready` (R7), `event`, `live` and `ping`; the client sends `pong` and the frames that later tickets register (R27). The schemas of every frame, the registry of event kinds and the schema of `data` for each kind are in `packages/shared/src/realtime/` (`frames.ts`, `events.ts`), used by the server to build and by the tests to check. An `event` frame is `{ "type": "event", "event": { "number", "kind", "conversationId", "createdAt", "data" } }`: `number` is the number of the log row, unchanged; `conversationId` is null for an event that has none; `createdAt` is ISO 8601. A `live` frame is `{ "type": "live", "kind", "data" }` and has no number. `ping` is `{ "type": "ping" }`. A client built earlier ignores a `type` or a `kind` it does not know, so adding one is allowed within a version. Check: every frame sent in every test is parsed with its schema; the `data` of each event kind of R20 is parsed with the schema of its kind; a test adds a kind to the registry and a test client ignores it.
- R13. The gateway sends an event only after the transaction that wrote it has committed, and never sends the event of a rolled-back transaction. Check: a change that writes an event and then rolls back sends no frame and leaves the gateway's position unchanged; the same change committed sends one.
- R14. The gateway finds new events by reading the log after its own position, not from a callback of the writer. Every event of this work is written by one function of the `realtime` module, `recordEvent(tx, input)`, which calls `appendEvent` of TOKI-036 (R15 there, unchanged) and then `SELECT pg_notify('toki_events', <workspaceId>)` in the same transaction, so the signal comes with the commit. This work adds `readEventsAfter(client, workspaceId, after, limit)` to the `realtime` module: the events with a number above `after`, in number order, at most `limit` (TOKI-036 has no such read; TOKI-039 reuses it). The gateway holds one `LISTEN toki_events` connection; on each signal, and after the listening connection is lost and restored, it drains the workspace of the signal (all workspaces with a connection after a restore): it reads in batches of 200, delivers each event in order, and moves the position of that workspace. The position of a workspace is made when its first connection starts, from `getLastEventNumber`, so nothing older is replayed. One drain runs at a time; a signal that arrives during a drain makes it run once more. A drain also runs from the sweep of R24 when 30 seconds passed since the last one, so a lost signal is repaired. No code outside the `realtime` module calls `appendEvent`. Check: events written by two transactions that commit in the opposite order of their start arrive in number order; the listening connection is ended from the database, an event is written, and it is delivered after the listener returns; with no signal, a sweep 30 seconds later delivers it; events written before the first connection are not sent; a search of `apps/server/src` outside tests and outside `modules/realtime` finds no call of `appendEvent`.
- R15. The audience of an event comes from its scope in the log (TOKI-036 R13: `workspace`, `conversation`, `user`): a conversation event goes to every connected person whose map holds the conversation (R8, R9); a user event goes to every connection of that person; a workspace event goes to every connection of that workspace. A connection receives an event at most once, and the events of one connection arrive in increasing number order. A person who is not in a conversation never receives a frame that holds its id, name, topic, description, members or any event of it, an Admin who is not a member included. Check: a scenario of the twelve channel routes and a DM with three connected people (a member, an Admin who is not a member, a person in another conversation); the frames of the two outsiders, recorded for the whole scenario, hold no id, name or topic of the private channel; an event is received once per connection (two tabs of one person get it once each).
- R16. A user-scope event is sent to every connection of that person and to nobody else. This work uses it for `settings.changed` (R20): a change of the person's own level, mute or star reaches their other tabs and devices (D-142, D-143: the values are the person's own and nobody else sees them). Check: Sam changes the star in one tab; Sam's second tab receives `settings.changed` and Lan, a member of the same channel, receives nothing.
- R17. When the `members` module reports a changed person through `onMemberChanged` (TOKI-024 R40: a role change, a deactivation, a reactivation), the gateway sends every connection one `live` frame of the kind `person.updated` with `data` `{ "userId", "role", "status" }` of the target after the change. The frame has no number and is not in the log, because the change is reported after its commit and not inside its transaction. A frame that is lost (a connection down at that moment) is repaired by the next load, as TOKI-024 concern 8 states: the server reads the role on every request. Check: an Admin changes a role; every connected person receives one `person.updated`; a connection opened after it receives none; the log has no new row.
- R18. The cost of one event does not grow with the number of people. Delivering an event runs no database statement: the audience comes from the memory of the gateway. The text of the frame is built once and the same string is sent to every recipient. Reading the log costs one statement per batch. Check: with 200 connected people in one channel (fake sockets that count their sends), one event gives 200 sends of one string, one call to the serialiser and, counted with the wrapper of TOKI-031 R14, exactly one statement for the read of the batch and none for delivery. There is no assertion about milliseconds: the 150 ms target is measured by TOKI-089 (concern 4).
- R19. The gateway never queues events for a slow connection. Before each send it reads the socket's buffered amount; when it is above 1 MiB the connection is closed with code 4408 and the reason `slow_consumer`, and the event is not sent. The other connections are not delayed by it. The client reconnects and reads what it missed from its own number (TOKI-039). Check: a socket whose buffered amount is above the limit is closed with 4408 and the next connection of another person receives the event; a socket under the limit is not closed.

Conversation events
- R20. The events of a change. This work adds one handler to the list of handlers that `recordChange` runs inside the caller's transaction (TOKI-037 R18; the handler of the system lines runs first and the event handler last). For each `Change` it is called with, it writes the events below through `recordEvent` (R14), after reading the current row of the conversation in the same transaction with `readConversationForEvents` (a read this work adds to the `conversations` module). A call that does not happen (a repeat, `changed` false, a refusal) writes no event. `appendEvent` is the last write of the transaction and takes no lock after the first one, as TOKI-036 R18 requires. The `type` of the log row is the `kind` of the frame and its `payload` is the `data`. In the order written:

  | Change | Events (kind, scope, `data`) |
  |---|---|
  | `channel_created` | `conversation.created`, conversation, `{ conversation, userIds }`: the first members, who start listening |
  | `member_joined` | `member.joined`, conversation, `{ userId, conversation }` |
  | `members_added` | `members.added`, conversation, `{ userIds, addedBy, conversation }` |
  | `member_left` | `member.left`, conversation, `{ userId }`; then `conversation.left`, user (the person), `{ conversationId, reason: "left" }` |
  | `member_removed` | `member.removed`, conversation, `{ userId, removedBy }`; then `conversation.left`, user (the person), `{ conversationId, reason: "removed" }` |
  | `details_changed` | `conversation.updated`, conversation, `{ topic?, description? }`: the current value of each field named in `change.fields` (both when absent) |
  | `channel_archived` | `conversation.archived`, conversation, `{}` |
  | `channel_restored` | `conversation.restored`, conversation, `{ conversation }` |
  | `settings_changed` | `settings.changed`, user (the actor), `{ conversationId, notificationLevel, isMuted, isStarred }`: the values that apply now (`notificationLevel` through `effectiveNotificationLevel`) |
  | `message_created` | `message.created`, conversation, `{ message }`: the `MessageEntry` of `change.message` (TOKI-037 R10) |
  | `direct_conversation_appeared` | `conversation.appeared`, user, once for each member of the conversation, the creator included, `{ conversation }`: the `DirectConversationEntry` with that person's own level, mute and star |
  | `direct_conversation_opened` (new, below) | the same `conversation.appeared`, for each member |

  Any change that also carries `change.message` (a system line written by TOKI-037 R16) writes one more event after those above, `message.created` with that line, so a client receives the line as a message of the conversation, and a person added by `members_added` receives their own "added" line. `conversation` in `conversation.created`, `member.joined`, `members.added` and `conversation.restored` is the entry of the bootstrap answer (`BootstrapChannelEntry`, `DirectConversationEntry`, TOKI-031 R7) without `notificationLevel`, `isMuted` and `isStarred`, which are the person's own; a client that adds the conversation applies the defaults of `effectiveNotificationLevel`, not muted, not starred, as for a new member row (TOKI-028 R14). A new group has no change today: `directRoutes` (TOKI-030) gets a `recordChange` dependency and calls it once with `direct_conversation_opened`, for the people of the group, only when the request creates the group row (not for a DM, which stays hidden until its first message, not for an existing group); this changes TOKI-030 R20 ("no event") for that one case (concern 6). Check: a spy shows one write per event of the table and none for a no-op; the leave that empties a private channel writes `member.left`, `conversation.left`, then `conversation.archived`; the restore by an Admin who is not a member writes `conversation.restored` then `member.joined`; a topic edit writes `conversation.updated` with `topic` only and then the line; the first message of a DM writes `message.created` then `conversation.appeared` for the two members (TOKI-037 R20 order: `message_created` then `direct_conversation_appeared`, so the numbers are in that order; the other person's map gains the DM at the second event and so that person does not receive the first message as an event: the entry carries `lastMessageAt` and the history is loaded from the message API when the DM is opened, concern 6); opening a new group writes `conversation.appeared` for each member and opening it again writes none; a rollback after the call leaves no event and no counter step; each `data` passes its schema of `packages/shared/src/realtime/events.ts`.

Ending a connection
- R21. The gateway registers a listener with `onSessionsEnded` (TOKI-022 R50). For each ended session id it closes every connection that holds that id, with code 4401 and a reason by the end reason: `deactivated` gives `account_deactivated`; `revoked` gives `session_ended`; `signed_out` gives `signed_out`; `replaced` gives `replaced`. The other connections of the same person, which have other sessions, stay open, and the tabs of one browser, which share one session, all close. A client treats `unauthenticated`, `session_ended` and `account_deactivated` as the 401 of a request (it calls `reportUnauthenticated`, sign-in screens R39); `signed_out` and `replaced` are ends that this browser asked for, so they raise no "Your session has ended" notice (TOKI-039 builds this client rule). The listener runs after the commit of the end (TOKI-022 R50). Check: `DELETE /api/v1/auth/session`, `DELETE /api/v1/auth/sessions` (R13 of TOKI-026), a deactivation (TOKI-024) and a sign-in that replaces the cookie session each close the right connections with the right reason, and the connection of a session that was not ended stays open and still receives events.
- R22. The map of a person is dropped when their last connection closes for any reason, so a deactivated person keeps no map. Check: after the deactivation of a connected person, the registry holds no connection and no map for them.
- R23. An open connection does not renew the session: only requests set `last_used_at` (TOKI-022 R25). The check of R2 runs at the handshake only. Reason and the accepted limit are in concern 3. Check: a connection kept open while the clock advances 31 days is not closed by the gateway on its own, and a new connection with that session gets `session_ended`.
- R24. Dead connections are found by the gateway, not by the browser. The server sends `{ "type": "ping" }` to a connection when 25 seconds passed since its last `ping`, and closes it with code 4410 and the reason `heartbeat_timeout` when 60 seconds passed since it last received any frame from the client. The client answers with `{ "type": "pong" }`; any frame from the client counts as a sign of life. A `sweep()` function does this work and the drain of R14; the application calls it every 5 seconds from one timer, and takes the time from the clock of TOKI-008 R19, so a test moves the `TestClock` and calls `sweep()` with no real timer. Check: at 25 seconds a `ping` arrives; a `pong` keeps the connection alive past 60 seconds; with no frame at 60 seconds the connection closes with 4410; the two numbers are constants of `packages/shared/src/realtime/limits.ts`.
- R25. A frame from the client is accepted only when it is at most 4,096 bytes (the library closes a larger one with 1009), is a JSON object with a string `type`, and arrives at a rate of at most 50 frames in 10 seconds. A frame that is not a JSON object closes the connection with code 4400 and the reason `bad_frame`; a rate above the limit closes it with 4429 and `rate_limited`; an unknown `type` is ignored. A frame received before `ready` was sent is ignored. A frame that names a conversation the person does not listen to is dropped with no answer, so it never tells a person that a conversation exists. Check: one case of each.
- R26. On shutdown (TOKI-004 R15) the gateway is closed by the app's close hook: it stops the listening connection, closes every socket with code 1001 and the reason `going_away`, and the process exits with code 0 with no connection of the gateway left open. Check: a test closes the app with open connections and receives 1001 on each; the process test of TOKI-004 still exits 0.

Extension and wiring
- R27. The `realtime` module exports `publishLive(audience, kind, data)` and `onClientFrame(type, handler)`, for the tickets that add a live notice or a client frame (typing, TOKI-044; presence, TOKI-055). `audience` is `{ conversationId }`, `{ userId }` or `{ workspace: true }`, resolved from the map and the registry of R8 and R11 like R15; `publishLive` writes nothing to the log. A handler gets the connection's account id and the frame, and `canListen(connection, conversationId)`, which is the check of R25. Check: a test registers a handler for a made-up type and a made-up live kind; the handler runs for a frame of a connection and not for an unknown type; `publishLive` with a conversation reaches the connections of its map only.
- R28. The dev proxy of `apps/web/vite.config.ts` has an entry for `/ws` with `ws: true` and the same target as `/api/v1` (web-skeleton spec concern 2). Check: a test of the config shows the entry, `ws` true and the equal target.
- R29. The gateway's code lives in `apps/server/src/modules/realtime/` (the module TOKI-036 creates) and is registered by `app.ts` when the database is given. `realtime` imports other modules only through their `index.ts` files: `checkSession` and `onSessionsEnded` of `auth` (the first is not exported now; this work exports it), `onMemberChanged` of `members`. It imports nothing of `conversations` or `messages`: `app.ts` passes the reads it needs as dependencies (`listConversationIdsOfUser`, `readConversationForEvents`, both added by this work to `conversations/index.ts`), builds the event handler of R20 with them, and adds it last to the handler list of `recordChange` (TOKI-037 R18). `createDb` returns a `listen(channel, onSignal, onReconnect)` next to `db` and `close`, built on the Postgres client, so the module makes no connection string of its own. Check: `pnpm lint` exits 0; the export-list tests of `auth`, `conversations` and `realtime` list the new names; no file of `realtime` imports a file of another module outside its `index.ts`, and none imports `conversations` or `messages` at all.

## Design
### The path of one event
1. A route changes something. Inside its transaction it calls `recordChange`; the event handler of R20 calls `recordEvent`, which calls `appendEvent` of TOKI-036 (it takes the next number under the lock of TOKI-036 and writes the row) and then `pg_notify` (R14).
2. The commit makes the row and the signal visible together.
3. The gateway wakes (or the sweep wakes it), reads the rows after its position in order, and for each row: resolves the audience (R15), applies the map change (R9), and sends one text frame to each recipient (R18, R19).

The gateway reads the log and does not receive the event from the writer (TOKI-036 notes that two pushes after a commit can reach a client in another order). Reasons: the order is the log's order whatever the order of the commits' callbacks; a crash between the commit and a callback loses nothing the log still holds; no module needs a post-commit call; and a second server process would work with the same code.

### Connection start
1. Upgrade: Origin check (R4). The handler adds its `message`, `close` and `error` listeners before its first `await`, so no frame is lost.
2. `checkSession` (R2); failure closes with 4401 (R3).
3. The gateway takes its drain lock, so no fan-out runs. If the person has no map: it opens the read-only `REPEATABLE READ` transaction and reads `listConversationIdsOfUser` and `readEventNumber(tx, workspaceId)`, giving the set and `M`; then, if its position for the workspace is lower than `M`, it drains the log up to `M` (the person is not registered yet, and the set already includes those events); a workspace with no position takes `M` as its position. If the person has a map: the answer is the position of the workspace.
4. It registers the connection, releases the lock, and sends `ready` with the position as `eventNumber`. Events after it are delivered by the next drain.
The lock is held for one transaction and the catch-up of a few events; fan-out resumes right after. A test seam (an optional function called after the snapshot, like TOKI-031 R10) lets a test commit events at that point (R7).

### Who hears what
| Scope in the log | Who receives it |
|---|---|
| conversation | the connected people whose map holds the conversation |
| user | every connection of that person |
| workspace | every connection |
| live (no log row) | as `publishLive` says |

Public channels are not announced to people who have not joined them: nobody previews a channel they are not in (D-116). The map is per person, not per connection, so a second tab costs no read.

Which kinds change a map is a table in `apps/server/src/modules/realtime/kinds.ts`: `conversation.created`, `member.joined` and `members.added` give the conversation to the people in `data.userIds` or `data.userId`; `conversation.appeared` gives it to its own person; `member.left` and `member.removed` take it from `data.userId` before delivery, and `conversation.left` takes it from its own person. A kind of a later ticket that needs this adds a row. A test checks that every kind of the shared registry has a row in this table and the reverse.

### Closing, codes and reasons
Close reasons are short ASCII strings (the 123-byte limit of the protocol).

| Code | Reason | When |
|---|---|---|
| 1001 | `going_away` | the server stops (R26) |
| 1009 | (library) | a client frame is too big (R25) |
| 4400 | `bad_frame` | a client frame is not a JSON object (R25) |
| 4401 | `unauthenticated`, `session_ended`, `account_deactivated`, `signed_out`, `replaced` | R3, R21 |
| 4408 | `slow_consumer` | R19 |
| 4410 | `heartbeat_timeout` | R24 |
| 4429 | `rate_limited` | R25 |
| 4430 | `too_many_connections` | R10 |

The codes and reasons are constants in `packages/shared/src/realtime/limits.ts`. A client reconnects after every code except 4401 with the reasons `unauthenticated`, `session_ended`, `account_deactivated` (the person must sign in again) and `signed_out` and `replaced` (this browser asked); that table of client behaviour belongs to TOKI-039.

### What the connection does not do
- It has no subscription step: the person hears every conversation in their map (technical design: "pushes that event to every open connection of the conversation's members").
- It carries no request and no answer. Every read and write stays on `/api/v1`; the socket pushes and takes the few client frames of R27.
- It does not renew the session (R23).

### Limits
Constants of `packages/shared/src/realtime/limits.ts`: `HEARTBEAT_PING_SECONDS` 25, `HEARTBEAT_TIMEOUT_SECONDS` 60, `SWEEP_SECONDS` 5, `SAFETY_DRAIN_SECONDS` 30, `MAX_CONNECTIONS_PER_PERSON` 20, `SOCKET_BUFFER_LIMIT_BYTES` 1,048,576, `CLIENT_FRAME_MAX_BYTES` 4,096, `CLIENT_FRAMES_MAX` 50 per `CLIENT_FRAMES_WINDOW_SECONDS` 10, `DRAIN_BATCH` 200. Decided in this spec; the log fixes none of them. Reasons: 25 seconds keeps a connection alive behind a proxy that closes a silent one after 30 seconds or more; 60 seconds is two missed pings and a margin; 1 MiB is about a hundred long messages; 20 connections is far more than one person has and still stops a loop; 4,096 bytes is much more than any frame of the tickets that add one. A product owner can change a number without a design change.

### Errors
- Not an upgrade -> 400 `bad_request`. Origin refused -> 403 `origin_not_allowed`. Both in the error format of TOKI-004.
- Session problem -> close 4401 with the reason (R3).
- A failure inside a drain (the database is down) is logged with the error and the drain is tried again by the next signal or the sweep. No connection is closed for it: the events stay in the log and the position does not move.
- A failure to send to one socket closes that socket and goes on with the others.

## Data safety
- A cookie, a token or a query string never reaches the log (R5). The registry holds no secret (R11).
- Events go only to the people whose map holds the conversation (R15); a frame of a private conversation, a DM or an unjoined channel never reaches anyone else. A client frame that names such a conversation is dropped silently (R25).
- The Origin of a browser connection is checked (R4), so another site cannot use a person's cookie to listen.
- The close reason names the kind of session end and nothing else.

## Open questions from the intent
- Where does a client learn why a connection was refused or closed? Answered: the upgrade completes and the server closes with 4401 and the reason, so the client reads it from the close event (R3, R21, the close table; concern 2).
- Who writes the events of a channel change, and when are they pushed? Answered: this work writes them inside the transaction through `recordChange`, as TOKI-029 concern 4 decided, and pushes them after the commit by reading the log (R14, R20; concern 1).
- How does the gateway know which conversations a person listens to? Answered: a map per connected person, read from the member rows at the first connection and then kept by the events in number order, with the DM condition added by TOKI-037 (R8, R9; concern 6).
- What happens to an open connection when its session ends, when a person is deactivated or a role changes? Answered: the connection is closed with a reason (R21, R22); a role change is a live notice (R17, concern 7); an open connection does not renew the session (R23, concern 3).
- What does the gateway do about a dead connection and a slow client? Answered: R24 and R19; the numbers are in concern 5.
- What is the line with TOKI-039, TOKI-040 and TOKI-044? Answered: Scope, the Design table of close codes, R7 and R27.

## Areas of concern
1. The event log belongs to TOKI-036 and the events of a change to this ticket (TOKI-029 concern 4, TOKI-036 concern 2, TOKI-037 concern 7). Decided in this spec: this work calls `appendEvent` and `getLastEventNumber` of TOKI-036 as they are and changes neither; it adds `recordEvent` (the write plus `pg_notify`) and `readEventsAfter` (TOKI-036 has no read after a number; TOKI-039 reuses it and adds its audience filter) to the `realtime` module, and the event types and payloads are its own, as TOKI-036 says. The no-gap rule (TOKI-036 R16) is a condition of the position of R14: if a number could be skipped the gateway would skip an event, and R14 tests two transactions that commit out of order. The notify is added in `recordEvent` and not in `appendEvent`, because TOKI-036 R15 fixes `appendEvent` at two statements and no push. Owner: Thanh Truong.
2. A browser does not show the status of a refused WebSocket upgrade, so a 401 at the handshake would look like a network error and the client would retry forever. Decided in this spec: complete the upgrade and close with 4401 and a reason that equals the REST error code (R3, R21). Reason: the client of TOKI-039 reads the close event and calls `reportUnauthenticated` as sign-in screens R39 says the realtime connection will. Owner: Thanh Truong.
3. An open connection does not renew the session, and the check runs at the handshake only (R23). A session that is idle for 30 days while a connection stays open, with no request at all, is not closed by the gateway. Decided in this spec: this is accepted, because every use of the app sends requests that renew the session, the end of a session by sign-out, revocation and deactivation closes the connection (R21), and the next connection is refused with `session_ended`. A periodic re-check would add a database read per connection for a case that does not occur in use. Owner: Thanh Truong.
4. The 150 ms target (NFR-13, D-113) cannot be asserted by a test that forbids real timers. Answered: this work keeps the path free of database statements and of per-recipient work and asserts that (R18); the measure with 200 people online is TOKI-089 in the plan ("Performance measurement"). TOKI-089 opens its 200 connections through `/ws` like any client and needs no special mode of this work. Owner: Thanh Truong.
5. The numbers of the heartbeat, the buffer, the client frames and the connections per person (the Limits section) are not in the log. Decided in this spec as technical choices, each with its reason, kept as constants so they can change without a design change. Owner: Thanh Truong.
6. A DM must not be heard by the other person before its first message (F25), and TOKI-037 owns that rule (TOKI-037 R19). Decided in this spec: the rule lives in one read, `listConversationIdsOfUser`, which mirrors the condition of TOKI-037 R19 (the creator, or a conversation with a message); the reveal is the event `conversation.appeared` of R20, written for each member when the first message is stored (TOKI-037 R20 calls `recordChange` with `message_created` and then `direct_conversation_appeared`, so the person who gains the DM does not receive the first message as an event, and loads the history when they open it; the order `appeared` then `message_created` would let them receive it, a change of TOKI-037 R20 that this spec asks for and does not make). A new group is not hidden (TOKI-037 concern 2), and no code announces it today (TOKI-030 R20: no event); decided in this spec: `directRoutes` calls `recordChange` once for a newly created group (R20), so its connected members learn of it at once. Until TOKI-037 a DM is in both maps from its creation. Owner: Thanh Truong.
7. A role change and a deactivation are reported after their commit (TOKI-024 R40), so they cannot be numbered events written in the change's transaction. Answered by TOKI-024 concern 8 (decided by the product owner on 2026-11-19): the gateway carries a live notice and the server reads the role on every request, so a reload repairs a lost one (R17). The client may refresh the people list after a reconnect (TOKI-039 decides). Owner: Thanh Truong.
8. The production proxy must pass `/ws` with the upgrade and must not close an idle connection before 30 seconds. Decided in this spec: the 25-second `ping` of R24 keeps the connection busy, and the rule of the Caddy file is TOKI-084's, which is named here so it is not forgotten. Owner: Thanh Truong.
9. The scope of the events that take a person out of a conversation. Decided in this spec, as TOKI-036 "Events" decides: the leaving person is addressed by a user-scope event, `conversation.left`, because on a replay they are no longer a member and a conversation event would not reach them; the members who stay get `member.left` or `member.removed` as conversation events. The live path applies the same rule (R9), so the live and the replayed streams agree. Owner: Thanh Truong.
