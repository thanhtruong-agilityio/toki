# First admin from environment variables design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/first-admin.md (Thanh Truong)
Ticket: TOKI-020

## Goal
A new installation has an empty database, so nobody can sign in and nobody can invite. The operator needs the server to create, once, the workspace, the first Admin and the #general channel from environment variables, and to leave a database that already has data alone. This work writes that start-up step: what it reads, when it runs, what it writes in one transaction, what it does on a second start, with two processes at once and when it fails, and what it logs.

## Scope
- In:
  - The configuration area of the three set-up values and their checks (the variables of the TOKI-096 inventory).
  - One start-up step, `ensureFirstAdmin`, in the `workspace` module, called from `main.ts` after the server listens.
  - The rows it writes: one `workspaces` row, one `users` row (an active Admin), the #general `conversations` row and the Admin's `conversation_members` row, in one transaction.
  - Three small public functions in the modules that own the other tables (Design, "Module boundaries").
  - The shared function that normalises and checks an email address (R16).
  - The log lines of the step, and its tests against the real Postgres of TOKI-008.
- Out (not now):
  - The tables: TOKI-019 (accounts) and TOKI-028 (conversations). This work writes rows and adds no table and no migration.
  - The inventory rows and `.env.example`: TOKI-096 owns the names, the Required flags and the development values. This work reads exactly those names.
  - Applying migrations: the `db:migrate` command of TOKI-005, run by the deploy (TOKI-085) and by `dev:reset:db`. The server does not migrate at start (Design, "Where it runs").
  - Sign-in of the first Admin: it is the code flow of TOKI-022 for an active account, and the mail is TOKI-021. This work creates no session, no code and sends no mail (R15). When mail cannot be sent, the one-time link of TOKI-026 (F43, D-159) works for the first Admin like for any active member; nothing here is special for them.
  - Inviting members and every later account change: TOKI-024. The invitation's member row in #general: TOKI-097. A leave request for #general is refused by TOKI-029 (D-034); this work only makes the row that rule protects.
  - The sample workspace of the development seed: TOKI-081. The installation guide that tells the operator which variables to set: TOKI-087.
  - What the first Admin sees on first entry (the line "This is the start of #general" and the card of three suggestions): a screen, not set-up. No ticket in the plan names it (concern 4).
  - The audit record of administrative actions (D-110): TOKI-024 decides its store (concern 7).

## Requirements
Variable names below are written `FIRST_ADMIN_EMAIL`, `FIRST_ADMIN_NAME` and `WORKSPACE_NAME`. They are working names: the code reads the names of the TOKI-096 inventory, and R2 checks that the three names it reads are in `.env.example` (concern 2). All text limits count code points, as the tables do.

- R1. The server configuration (TOKI-004 `config.ts`) gains one area for set-up with three values: the first admin email, the first admin name and the workspace name. The email and the workspace name are required; the name is optional. A required value that is missing, empty or only whitespace stops the server before it listens, as in TOKI-004 R3: exit code 1 and one line per failing variable with its name on standard error. This holds at every start, also when the database already has accounts (concern 1). Check: config tests with fake environments, each with one of the three required-or-optional cases (all valid; email missing; workspace name empty; workspace name whitespace only; name missing, which is valid); the process test of TOKI-004 started with the email missing exits 1 and prints its name.
- R2. The set-up area reads exactly the three names of the inventory and no other. Check: a test compares the three names the schema reads with the names in `.env.example` (the check of TOKI-004 R13); it fails when one is absent there.
- R3. The email value is trimmed and put in lower case, then must pass the shared check of R16. A value that fails stops the server as in R1 and prints the variable name and never the value (TOKI-004 R4). Check: config tests with `Minh@Example.com ` (accepted, stored form `minh@example.com`), `not-an-address`, `a b@example.com`, an address of 255 characters and one with a 65-character part before the @; each rejected one exits 1 with the name and the submitted value is absent from everything printed.
- R4. The workspace name is trimmed and must be 1 to 100 characters (the limit of `workspaces.name`, TOKI-005 R9). The first admin name, when it is given and not empty, is trimmed and must be 1 to 80 characters (D-033). An empty or whitespace-only first admin name counts as not given. A value outside its limit stops the server as in R3. Check: config tests with 100 and 101 characters for the workspace name, 80 and 81 for the name (counted in emoji too: 80 emoji pass, 81 fail), and an empty name (valid, not given).
- R5. When the database has no `workspaces` row and no `users` row, `ensureFirstAdmin` creates in one transaction, and returns `created`: (a) one workspace named with the workspace name; (b) one account in it with the email of R3, role `admin`, status `active`, the display name of R6 and language `en` (the table default, D-018, TOKI-019 R11), created at the time of the injected clock; (c) the #general conversation in it: kind `channel`, name `general`, public, `is_general` true, no topic, no description, no archive time, `created_by` the new account, created at the time of the clock (the shape that TOKI-028 R9 enforces); (d) the member row of that account in #general, with no notification level, not muted, not starred, created at the clock's time. Check: a database test calls it on empty tables with a test clock and reads back the four rows: one row in each table, every listed column as stated, and the creation times equal to the clock's instant (not `workspaces.created_at`, which keeps its database default, TOKI-019 concern 5).
- R6. The display name is the first admin name when it is given; otherwise the part of the email before the @, as D-150 does for a newcomer. The part before the @ is at most 64 characters (R16), so it always fits D-033. Check: two database tests, one with a name given (`Minh Tran`), one without (`minh@example.com` gives `minh`).
- R7. When the database already holds a `users` row or a `workspaces` row, `ensureFirstAdmin` creates nothing, changes nothing and returns `skipped`. It never writes a second workspace and never changes an existing account, workspace or conversation, whatever the variables say. Check: (a) set-up once, then call again with another email, another name and another workspace name: the result is `skipped` and every row of the four tables is identical to the first run, column by column; (b) a database with one account made by the table helper of TOKI-019 R26 (no #general): `skipped`, and no row added; (c) a database with a workspace and no account: `skipped`, no row added.
- R8. A start after a successful set-up changes nothing: restarting the server any number of times leaves the four tables as the first run left them (R7 (a)); a second run writes no row and no update. Check: the test of R7 (a) also counts the rows (1, 1, 1, 1) after three runs.
- R9. Two processes that start together create one set of rows. The step takes a transaction-scoped advisory lock before it counts anything, so the second process waits, then finds the database not empty and returns `skipped`. Check: a database test starts two calls from two clients made from the test connection; the first call carries a test hook (Design, "Test hooks") that pauses it inside the transaction after its count; the test waits, by reading `pg_locks`, until the second backend shows a lock of type `advisory` that is not granted (it fails after 5 seconds if none does), then releases the first call. Exactly one call returns `created`, the other `skipped`, and the tables hold 1, 1, 1, 1 rows. Without the lock the second call does not wait and the test fails.
- R10. The four writes are one transaction: when any step fails, no row of the other steps stays. Check: with the hook after the workspace insert, after the account insert and after the #general insert in turn throwing an error, each run returns `failed` and the four tables are empty; a run without a failing hook then returns `created`.
- R11. `ensureFirstAdmin` never throws. When the database cannot be reached, when a table does not exist (migrations not applied), or when a step fails, it returns `failed`, writes one error line (R13) and the server keeps running. Check: (a) a client for a loopback address where nothing listens: `failed`, no throw; (b) a throwaway database made by the TOKI-005 R13 rules with no migration applied: `failed`, no throw; (c) the hooks of R10.
- R12. In `main.ts` the step runs once per start, after `listen` has succeeded and with the database client the server built at start, the `config` set-up area, the system clock and the app logger. A start with an unreachable database still listens and `/healthz` answers ok (TOKI-004 R20, TOKI-005 R16). Check: the process test of TOKI-004 is extended: with the test database and a fake environment, the process listens, `/healthz` answers ok, and within 5 seconds the four tables hold the rows of R5; started a second time with the same database, they are unchanged; started with `DATABASE_URL` pointing to no Postgres, it listens, answers `/healthz` and logs the error of R13; SIGTERM still exits 0.
- R13. The step writes these log lines through the app logger and no others: `first_admin_created` (level info, fields `workspaceId`, `userId`, `conversationId`), `first_admin_skipped` (info, field `reason` with `database_not_empty`), `first_admin_workspace_without_account` (warn, when R7 (c) applies) and `first_admin_failed` (error, fields `code`, the Postgres error code or the Node error code, and `constraint` when there is one). No line holds the email, the display name, the workspace name, an error message, an error detail or a stack. Check: a test captures the log (the `logStream` of TOKI-004) over all the runs of R5 to R11, including a failure that Postgres words with the address in its detail (a second account with the same address inserted by the test hook gives a unique violation whose detail names it), and searches the captured text for the address, its part before the @, the display name and the workspace name: none is found; the lines found are exactly the four above with the fields above.
- R14. A table definition is not imported across modules. `ensureFirstAdmin` lives in `modules/workspace/`; it writes `workspaces` itself and reaches the other tables only through three new public functions: `countAccounts` and `createAccount` exported by `modules/members/index.ts`, and `createGeneralChannel` exported by `modules/conversations/index.ts`; `modules/workspace/index.ts` exports `ensureFirstAdmin` and its result and input types. Each of the three functions takes the open transaction as its first argument and writes with the caller's transaction. Check: `pnpm lint` exits 0; a test lists the exports of the three `index.ts` files and finds these names in them; the TOKI-028 test that lists the exports of the conversations module is changed in this PR to include `createGeneralChannel` (concern 10).
- R15. Set-up creates no session, no sign-in code and no device, and hands nothing to the mail layer. Check: after R5 the tables `sessions`, `login_codes` and `devices` are empty and a fake mail layer passed to the test has recorded no call.
- R16. One shared function, in `packages/shared`, normalises an email address (trim, lower case) and checks it: at most 254 characters, no whitespace, one @, a part before the @ of at most 64 characters, a well-formed address by the Zod email check. It is the check the first admin address passes (R3), and is the one rule the sign-in and the invitation code use for "well-formed" so that an address accepted here can always sign in (concern 11). Check: unit tests of the cases of R3, of an address that the `users` table accepts and one it refuses (`users_email_check`, `users_email_length_check`, TOKI-019 R7), and a database test that inserts every address the function accepts in its test list into `users` and succeeds.
- R17. After R5 the #general row is the one the tables protect: an update that sets `archived_at` on it is refused by the database (TOKI-028 R9), and the member row of the first Admin is in `conversation_members`, so #general is in their list with nothing to do. Check: a database test after R5 tries to set `archived_at` and the update is refused with the error TOKI-028 names; a read through `isConversationMember` of TOKI-028 returns true for the Admin and `getConversationFacts` reports `isGeneral` true.

## Design
### Where it runs
- `main.ts` (TOKI-004): load config (R1 to R4 stop the process here if a value is bad), build the app, listen, then `await ensureFirstAdmin(...)` once. It runs after `listen` because TOKI-004 R20 and TOKI-005 R16 say an unreachable or slow database must not stop the server or delay `/healthz`, and nothing in the first seconds needs the Admin: with no account, a sign-in request gets the same answer as for any unknown address (BR-04). A step that returns `failed` does not retry within the process: the error line is the signal and the next start tries again (concern 6).
- Migrations are not applied by the server. The `db:migrate` command (TOKI-005) runs before the server starts: by `dev:reset:db` in development and by the deploy in production (TOKI-085). So the tables exist when this step runs. When they do not, the step fails with the error line (R11) and the Postgres code `42P01` tells the operator why. Decided in this spec: the server stays free of migration logic, as TOKI-005 designed it.
- The step belongs to the `workspace` module, which owns the workspace and already offers the workspace name and id to sign-in (TOKI-022, "Module boundaries"). The server modules list has no `setup` module, and a new one would call the same three modules.

### What it does (inside one transaction)
1. Start a transaction and take `pg_advisory_xact_lock` with a fixed key for this step (R9). The key is a constant in the module; the lock is released by the commit or rollback.
2. Read the two counts: `workspaces` (own table) and, through `countAccounts`, `users`. Both zero: go on. Otherwise commit nothing, log `first_admin_skipped`, or `first_admin_workspace_without_account` when there is a workspace and no account (concern 5), and return `skipped`.
3. Insert the workspace; `createAccount` (role `admin`, status `active`, no language, so the default `en`); `createGeneralChannel` (the #general row and the member row of its creator). Commit; log `first_admin_created`; return `created`.
The times of the account, the conversation and the member row come from `clock.now()` (TOKI-008 R19); the step reads no system time.

### Module boundaries
- `members`: `countAccounts(tx)` returns the number of `users` rows; `createAccount(tx, { workspaceId, email, displayName, role, status, createdAt })` inserts one row (the language is left to the table default) and returns its id. TOKI-097 creates accounts too and may call the same function; TOKI-024 changes accounts by its own functions.
- `conversations`: `createGeneralChannel(tx, { workspaceId, createdBy, createdAt })` inserts the #general row and the member row of `createdBy`, and returns the conversation id. It owns the fixed values of #general (the name, the flag, public), so no other module writes them. TOKI-097 finds #general and adds its own member rows through a function it owns.
- The transaction type is exported by `src/db/client.ts` (TOKI-005). Decided in this spec: if TOKI-005 did not export a type for the Drizzle transaction, this ticket adds the alias in that file.

### Test hooks
`ensureFirstAdmin(deps, hooks?)` takes `deps` = `{ db, config, clock, logger }` and an optional `hooks` object with `afterCount`, `afterWorkspace`, `afterAccount` and `afterGeneral`, each an async function awaited inside the transaction after that step. `main.ts` passes none. Decided in this spec: tests need to pause the transaction (R9) and to fail it between steps (R10) deterministically, and a hook does this without a timer or a patched module.

### Errors
- A required value missing or empty, or a value that fails its check -> the server does not start, exit code 1, names only (R1, R3, R4).
- Database not empty -> nothing written; one info line (R7).
- Database unreachable, tables missing, any step fails -> rollback, one error line with codes only, server keeps running, no retry in the process (R10, R11).

### Layout
```
apps/server/src/
├─ config.ts                              gains the set-up area
├─ main.ts                                calls ensureFirstAdmin after listen
└─ modules/
   ├─ workspace/
   │  ├─ first-admin.ts                   ensureFirstAdmin, the lock key, the log lines
   │  ├─ first-admin.db.test.ts           R5 to R11, R13, R15, R17
   │  └─ index.ts                         exports ensureFirstAdmin and its types
   ├─ members/       accounts.ts          countAccounts, createAccount (exported by index.ts)
   └─ conversations/ general.ts           createGeneralChannel (exported by index.ts)
packages/shared/src/email.ts              normalizeEmail, the email schema (R16)
```

## Testing
- Written test-first. Database tests are `.db.test.ts` files in the database project of TOKI-008: Postgres is real, migrations are applied at the start of the run, each file starts with empty tables and runs alone. Between the cases of one file the test empties every table of the `public` schema except the migration journal in one `TRUNCATE`, the statement shape of TOKI-008 R6 and TOKI-028 R23. The clock is the test clock of TOKI-008. Fake data only: `@example.com` addresses.
- Config tests (R1 to R4) pass fake environment objects, like the TOKI-004 tests, and need no database. The process test (R12) is the TOKI-004 process test with the set-up values added to its fake environment.
- `first-admin.db.test.ts`: R5 and R6 (rows and display name), R7 and R8 (skip, run again with other values, counts), R9 (two clients, the hook, `pg_locks`), R10 and R11 (hooks that fail, a client with nothing listening, a database with no migration), R13 (captured log searched for the personal values), R15 and R17.
- R14 by `pnpm lint` and a test of the exports. R16: unit tests in `packages/shared` and one database test.
- Hand check once, output in the PR: start the server from `pnpm dev` after `dev:reset:db` with the development `.env`, sign in as the first Admin with the code from Mailpit, and open #general.

## Data safety
- The first admin address is personal data. It lives in `.env` (TOKI-096), reaches the database in the one transaction and is written to no log, error body or console (R13). A failure logs the error code and constraint name only, because a Postgres message can carry the value.
- A startup failure of the configuration prints names only (TOKI-004 R4).
- The step writes no credential: the account has no password (D-011), and no session or code is made (R15).
- Tests and fixtures use fake addresses only.

- 2. What name does the first Admin get? Answered: the first admin name when given, otherwise the part of the address before the @ (D-150) (R6). See concern 8.
- 3. What happens when the database is not empty, with two processes, and when set-up fails? Answered: R7 to R11, concerns 5, 6 and 12. Source: flow F01 ("nothing is created or changed").

- 5. What does the log hold? Answered: ids and codes, never the address, the name or an error message (R13). No decision of the log covers the address; this follows TOKI-004 R7 and the sign-in rule that its module writes no address to the log. See concern 7 for the record of D-110.

## Areas of concern
1. Whether the three values are checked at every start or only when the database is empty. Flow F01 says both that a missing required variable stops the server and that the setup variables are ignored once the database has accounts. Decided in this spec: they are checked at every start (R1), and ignored for writing once the database is not empty (R7). Reason: the configuration is read once, before the database is touched (TOKI-004 R2), and a server that starts without them today and fails at the next reset is worse than one that fails at the first deploy. The inventory marks them required for production. Cost: the operator keeps the three values in `.env` for the life of the installation. Owner: Thanh Truong.
2. The variable names. The Blueprint names none; TOKI-096 decided that the inventory names every phase 1 variable and that TOKI-020 reads exactly those names (TOKI-096 concern 7), but the inventory is built by that ticket and does not exist yet. Decided in this spec: the code reads the names of the inventory; `FIRST_ADMIN_EMAIL`, `FIRST_ADMIN_NAME` and `WORKSPACE_NAME` are working names, and R2 fails the build if the code reads a name that is not in `.env.example`. If the inventory chooses other names, this spec's requirements follow them unchanged. Whether the first admin name has Required = no in the inventory is this spec's choice (R1) and TOKI-096 follows it when it is built. Owner: Thanh Truong.
3. Whether #general starts with a topic or a description. Not decided. The log fixes the channel's name and its rules (D-034, D-040) and no text for it. The prototype's #general has the topic "Company-wide announcements and general chat" and a description, but they belong to the sample workspace, and D-147 calls sample content illustration; a stored text cannot be translated like interface text. This spec writes #general with no topic and no description (R5 (c)). Proposal, not a decision: keep it empty in phase 1; the Admin can edit the topic and description like any member (D-105). Owner: Thanh Truong, as product owner.
4. Who builds what the first Admin sees on first entry: the line "This is the start of #general" and the card suggesting three things (invite members, create a channel, set a status), from flow F01. Not decided. Flow F01 is the baseline (D-091) but no ticket in the plan names the empty-#general line or the card, and neither is in the prototype's markup that this spec could check. This work builds neither. Proposal, not a decision: the conversation screen tickets own the line and a ticket for the card is added to the plan. Owner: Thanh Truong, for the plan.
5. A database with a workspace and no account. Decided in this spec: nothing is written and a warning line is logged (R7 (c), R13). Reason: the step never writes into a database that is not empty, and guessing which workspace to reuse could hand the installation to the wrong rows. The tables cannot reach this state by themselves (an account needs a workspace, a workspace can exist alone, TOKI-005 R15), so it appears only after a manual change; the operator fixes it by `dev:reset:db` in development or by hand. Owner: Thanh Truong.
6. When the database cannot be reached or the step fails. Decided in this spec: the server stays up, logs one error line and does not retry in the process (R11, R12). Reason: TOKI-004 R20 and TOKI-005 R16 (decided by Thanh on 2026-11-16) keep the server up when Postgres is down, and the deploy runs the migrations and starts Postgres before the server (TOKI-085, TOKI-084). Cost: if the first start fails, the installation has no Admin until a restart. TOKI-085 and the installation guide (TOKI-087) own checking that the line `first_admin_created` appears after the first deploy. Owner: Thanh Truong.
7. The record of administrative actions (D-110, NFR-16: who, what, to whom, when). Not decided whether the creation of the first Admin counts. Nobody acts when the server does it, and TOKI-024 has not yet chosen the store (a table or the log, TOKI-019 concern 1). This work writes the info line `first_admin_created` with the ids and the log's own time (R13). Proposal, not a decision: that line is the record, and TOKI-024 writes its own records for what Admins do. Owner: Thanh Truong, with the owner of the TOKI-024 spec.
8. The first Admin's display name. Decided in this spec: the first admin name when given, otherwise the part before the @ (R6). Reason: D-150 gives that rule to a newcomer with no welcome step; the first Admin has no welcome step either (F01), and the inventory carries a name for them. The limit 1 to 80 is D-033; the part before the @ is at most 64 by R16, so it always fits. Owner: Thanh Truong.
9. The order with migrations at start-up. Decided in this spec: the server does not migrate; the step runs after `listen` and finds the tables because `db:migrate` ran first (Design, "Where it runs"). Reason: TOKI-005 made migration a command, run by the deploy and by `dev:reset:db`, and a server that migrates itself would need its own failure and lock rules. Owner: Thanh Truong.
10. Module boundaries and the TOKI-028 export list. Decided in this spec: the step lives in `workspace` and calls three new functions of the other two modules (R14). Reason: no module may write another module's table. Conflict to resolve: TOKI-028 R18 says the conversations module exports exactly six names and has a test of that list. This PR changes that test to include `createGeneralChannel`; the TOKI-028 spec is not edited here, and its owner should record the change. TOKI-020 needs TOKI-028 (the plan lists only TOKI-019). Owner: Thanh Truong, with the owner of the TOKI-028 spec.
11. One definition of a well-formed address. Decided in this spec: `packages/shared/src/email.ts` holds `normalizeEmail` and the Zod email schema (R16). Reason: the TOKI-022 spec trims, lower-cases and checks "well-formed" without saying how; if sign-in rejects an address that set-up accepted, the first Admin could never sign in. Whichever of TOKI-020 and TOKI-022 is built first creates the file; the other imports it. TOKI-022 and TOKI-097 are asked to use it. Owner: Thanh Truong, with the owners of the TOKI-022 and TOKI-097 specs.
12. Two processes starting together (a deploy that overlaps a restart). Decided in this spec: a transaction-scoped advisory lock taken before the counts, so one process creates the rows and the other skips (R9). Reason: no table constraint limits `workspaces` to one row (TOKI-005 R15), so without the lock two empty reads could each write a workspace. Owner: Thanh Truong.
13. The development seed. The sample workspace of TOKI-081 (Hugepig Studio, 8 people, #general with its members) is loaded into a database; if the server already ran set-up, the database is not empty. Decided in this spec: this ticket makes no rule for the seed, and its R7 never touches data that exists. TOKI-081 owns the order (wipe, then seed, then start, or reuse of `createAccount` and `createGeneralChannel`) and must not leave two #general rows (TOKI-028 R9 refuses a second one). Owner: Thanh Truong, with the owner of TOKI-081.
