# First admin from environment variables design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/first-admin.md (Thanh Truong)
Ticket: TOKI-020

## Goal
A new installation has an empty database, so nobody can sign in and nobody can invite. The operator needs the server to create, once, the workspace, the first Admin and the #general channel from environment variables, and to leave a database that already has data alone. This work writes that start-up step: what it reads, when it runs, what it writes in one transaction, what it does on a second start, with two processes at once and when it fails, and what it logs.

## Scope
- In:
  - The configuration area of the three set-up values and their checks (the variables of the TOKI-096 inventory).
  - One start-up step, `ensureFirstAdmin`, in the file `apps/server/src/first-admin.ts` (outside `modules/`), called from `main.ts` after the server listens, with a bounded retry (R18 to R20).
  - The rows it writes: one `workspaces` row, one `users` row (an active Admin), the #general `conversations` row and the Admin's `conversation_members` row, in one transaction.
  - Five small public functions in the modules that own the tables (Design, "Module boundaries"); `createGeneralChannel` is built and tested by TOKI-028 (its R18 and R25), with the arguments written here.
  - The shared function that normalises and checks an email address (R16).
  - The log lines of the step, its tests against the real Postgres of TOKI-008, and the new required variables in the fake environments and the CI file that start the server (R21).
- Out (not now):
  - The tables: TOKI-019 (accounts) and TOKI-028 (conversations). This work writes rows and adds no table and no migration.
  - The inventory rows and `.env.example`: TOKI-096 owns the names, the Required flags and the development values. This work reads exactly those names (TOKI-096 Scope, Out).
  - Applying migrations: the `db:migrate` command of TOKI-005. Which ticket runs it before the server starts is not settled: TOKI-085 (the plan: "deploy, run migrations") has no spec yet, and this work does not rely on the order (R18, concern 9).
  - Sign-in of the first Admin: it is the code flow of TOKI-022 for an active account, and the mail is TOKI-021. This work creates no session, no code and sends no mail (R15). When mail cannot be sent, the one-time link of TOKI-026 (F43, D-159; `pnpm --silent emergency:link <address>`, which prints the link alone on standard output, its R18 and R19) works for the first Admin like for any active member; nothing here is special for them.
  - Inviting members and every later account change, including the account made when an invitation is accepted: TOKI-024 inserts those accounts with its own function (concern 14). The invitation's member row in #general: TOKI-024 calls `addMemberToGeneral` of TOKI-028 (R26) inside `acceptInvitation` (its R20 step 8); TOKI-097 reaches it through TOKI-024. A leave request for #general is refused by TOKI-029 (D-034); this work only makes the row that rule protects.
  - The sample workspace of the development seed: TOKI-081. The installation guide that tells the operator which variables to set and that they are read once: TOKI-087.
  - What the first Admin sees on first entry (the line "This is the start of #general" and the card of three suggestions): a screen, not set-up. No ticket in the plan names it (concern 4).
  - The audit record of administrative actions (D-110): TOKI-024 keeps it in its table `admin_actions` (its R31, concern 7 there), which needs an acting account (concern 7 here).

## Requirements
Variable names below are written `FIRST_ADMIN_EMAIL`, `FIRST_ADMIN_NAME` and `WORKSPACE_NAME`. They are working names: the code reads the names of the TOKI-096 inventory, and R2 checks that the three names it reads are in `.env.example` (concern 2). All text limits count code points, as the tables do.

- R1. The server configuration (TOKI-004 `config.ts`) gains one area for set-up with three values: the first admin email, the first admin name and the workspace name. The email and the workspace name are required; the name is optional. A required value that is missing, empty or only whitespace stops the server before it listens, as in TOKI-004 R3: exit code 1 and one line per failing variable with its name on standard error. This holds at every start of the server, also when the database already has accounts (concern 1, a proposal that conflicts with flow F01). The set-up area is registered by the server entry only, as TOKI-004 concern 11 has each area loaded only by the process that uses it: a command-line tool that loads its own areas (the emergency command of TOKI-026 R22, `db:migrate`, `drizzle.config.ts`) is not stopped by a missing set-up value. Check: config tests with fake environments, each with one of the cases (all valid; email missing; workspace name empty; workspace name whitespace only; name missing, which is valid); the process test of TOKI-004 started with the email missing exits 1 and prints its name; `loadConfig` called with the database area only and none of the three values returns without error.
- R2. The set-up area reads exactly the three names of the inventory and no other. Check: a test compares the three names the schema reads with the names in `.env.example` (the check of TOKI-004 R13); it fails when one is absent there.
- R3. The email value is passed to `parseEmail` (R16): it is trimmed, put in lower case and checked. A value that fails stops the server as in R1 and prints the variable name and never the value (TOKI-004 R4). Check: config tests with `Minh@Example.com ` (accepted, stored form `minh@example.com`), `not-an-address`, `a b@example.com`, an address of 255 characters and one with a 65-character part before the @; each rejected one exits 1 with the name and the submitted value is absent from everything printed.
- R4. The workspace name is trimmed and must be 1 to 100 characters (the limit of `workspaces.name`, TOKI-005 R9). The first admin name, when it is given and not empty, is trimmed and must be 1 to 80 characters (D-033). An empty or whitespace-only first admin name counts as not given. A value outside its limit stops the server as in R3. Check: config tests with 100 and 101 characters for the workspace name, 80 and 81 for the name (counted in emoji too: 80 emoji pass, 81 fail), and an empty name (valid, not given).
- R5. When the database has no `workspaces` row and no `users` row, `ensureFirstAdmin` creates in one transaction, and returns `created`: (a) one workspace named with the workspace name; (b) one account in it with the email of R3, role `admin`, status `active`, the display name of R6 and language `en` (the table default, D-018, TOKI-019 R11), created at the time of the injected clock; (c) the #general conversation in it: kind `channel`, name `general`, public, `is_general` true, no topic, no description, no archive time, `created_by` the new account, created at the time of the clock (the shape that TOKI-028 R9 enforces); (d) the member row of that account in #general, with no notification level, not muted, not starred, created at the clock's time. Check: a database test calls it on empty tables with a test clock and reads back the four rows: one row in each table, every listed column as stated, and the creation times equal to the clock's instant (not `workspaces.created_at`, which keeps its database default, TOKI-019 concern 5).
- R6. The display name is the first admin name when it is given; otherwise the part of the email before the @, as D-150 does for a newcomer. The part before the @ is at most 64 characters (R16), so it always fits D-033. Check: two database tests, one with a name given (`Minh Tran`), one without (`minh@example.com` gives `minh`).
- R7. When the database already holds a `users` row, `ensureFirstAdmin` creates nothing, changes nothing and returns `skipped`. It never writes a second workspace and never changes an existing account, workspace or conversation, whatever the variables say. When the database holds exactly one `workspaces` row and no `users` row, the step adopts that workspace: it keeps the row and its name as they are, and writes the account, #general and the member row of R5 (b) to (d) in it, in the same transaction, and returns `created` (concern 5). When it holds several workspaces and no account, it returns `skipped`. Check: (a) set-up once, then call again with another email, another name and another workspace name: the result is `skipped` and every row of the four tables is identical to the first run, column by column; (b) a database with one account made by the table helper of TOKI-019 R26 (no #general): `skipped`, and no row added; (c) a database with one workspace made by the helper and no account: `created`, the workspace row unchanged (same id, same name even when `WORKSPACE_NAME` differs), one account, one #general, one member row, and the `first_admin_created` line carries `adopted` true; (d) two workspaces and no account: `skipped`, no row added, and the line `first_admin_workspace_without_account` is logged.
- R8. A start after a successful set-up changes nothing: restarting the server any number of times leaves the four tables as the first run left them (R7 (a)); a second run writes no row and no update. Check: the test of R7 (a) also counts the rows (1, 1, 1, 1) after three runs.
- R9. Two processes that start together create one set of rows. The step takes a transaction-scoped advisory lock before it counts anything, with the two-integer key of Design, "What it does", so the second process waits, then finds the database not empty and returns `skipped`. Check: a database test starts two calls from two clients made from the test connection; the first call carries the hook `afterCount` (Design, "Test hooks"), which pauses it inside the transaction after its count; the test waits, by reading `pg_locks`, until the second backend shows a lock of type `advisory` that is not granted (it fails after 5 seconds if none does), then releases the first call. Exactly one call returns `created`, the other `skipped`, and the tables hold 1, 1, 1, 1 rows. Without the lock the second call does not wait and the test fails.
- R10. The four writes are one transaction: when any step fails, no row of the other steps stays. Check: with the hooks `afterWorkspace`, `afterAccount` and `afterGeneral` in turn throwing an error that carries a code outside the retry list of R18, each run returns `failed` after one attempt and the four tables are empty; a run without a failing hook then returns `created`. A fourth case produces a real database failure: the hook `afterWorkspace` inserts, through its `tx` and with the `workspaceId` it receives, a `users` row with the configured email, so the account insert of the step violates the unique rule of TOKI-019 R7 on workspace and email; the run returns `failed` after one attempt, the log line carries code `23505` and the constraint name, and the four tables are empty.
- R11. `ensureFirstAdmin` never throws. When the database cannot be reached, when a table does not exist (migrations not applied), or when a step fails, it returns `failed` (after the retries of R18 where they apply), writes the error line of R13 for each attempt and the server keeps running. Check: (a) a client for a loopback address where nothing listens: `failed`, no throw, `MAX_ATTEMPTS` error lines; (b) a throwaway database made by the TOKI-005 R13 rules with no migration applied and a `sleep` that never lets the tables appear: `failed`, no throw, code `42P01` on every line; (c) the failing cases of R10.
- R12. In `main.ts` the step runs once per start, after `listen` has succeeded, with the database client the server built at start, the `config` set-up area, the system clock, the injected `sleep`, the abort signal of R20 and the app logger. A start with an unreachable database still listens and `/healthz` answers ok (TOKI-004 R20, TOKI-005 R16). Check, in two process tests. The database-free one is the process test of TOKI-004 (TOKI-008 R20: it runs in the database-free project and `pnpm --filter ./apps/server test:unit` passes with Postgres stopped) with the three set-up values added to its fake environment and one case added: with `DATABASE_URL` pointing to no Postgres the process listens, answers `/healthz`, logs a `first_admin_failed` line with `attempt` 1 and `retry` true within 5 seconds, and SIGTERM, sent while the step waits for its next attempt, exits 0 within 3 seconds. The second is a new file `first-admin.process.db.test.ts` in the database project: with the test database (empty at the start of the file, TOKI-008 R6) and a fake environment, the process listens, `/healthz` answers ok, and within 5 seconds the four tables hold the rows of R5; started a second time with the same database, they are unchanged.
- R13. The step writes these log lines through the app logger and no others: `first_admin_created` (level info, fields `workspaceId`, `userId`, `conversationId`, `adopted`), `first_admin_skipped` (info, field `reason` with `database_not_empty`), `first_admin_workspace_without_account` (warn, field `reason` with `several_workspaces`), `first_admin_failed` (error, fields `code`, the Postgres error code or the Node error code, `unknown` when there is none, `constraint` when there is one, `attempt` and `retry`, a boolean that says another attempt follows) and `first_admin_stopped` (info, field `attempt`, R20). No line holds the email, the display name, the workspace name, an error message, an error detail or a stack. Check: a test captures the log (the `logStream` of TOKI-004) over all the runs of R5 to R11 and R18 to R20, including the real unique violation of R10 whose Postgres detail names the address, and searches the captured text for the address, its part before the @, the display name and the workspace name: none is found; the lines found are exactly those above with the fields above.
- R14. A table definition is not imported across modules. `ensureFirstAdmin` lives in `apps/server/src/first-admin.ts`, outside `modules/`, and imports only the `index.ts` files of three modules (TOKI-002 R17), so the modules do not import each other for it (concern 15). The functions it calls, each taking the open transaction as its first argument and writing with the caller's transaction: `listWorkspaceIds(tx)` and `createWorkspace(tx, { name })` exported by `modules/workspace/index.ts` (the second returns the new id; `workspaces.created_at` keeps its default); `countAccounts(tx)` and `createFirstAdminAccount(tx, { workspaceId, email, displayName, createdAt })` exported by `modules/members/index.ts` (it writes the role `admin` and the status `active` itself, takes neither as an argument and returns the id; concern 14); `createGeneralChannel(tx, { workspaceId, createdBy, createdAt })` exported by `modules/conversations/index.ts`, which TOKI-028 builds and tests (its R18 and R25: the same arguments, it returns the conversation id, it opens no transaction). Check: `pnpm lint` exits 0 with TOKI-002's rules in force; a test checks that each of the four names of `workspace` and `members` is among the exports of its `index.ts` and that none is a table definition. `createGeneralChannel` is in the one list of exported names of the `conversations` module (`exports.test.ts` of TOKI-028 R18, a list every ticket extends), so this ticket adds nothing to that file; no ticket owns an export list for `workspace` or `members`, so the check here names the functions of this ticket and does not require that nothing else is exported.
- R15. Set-up creates no session, no sign-in code and no device, and has no way to send mail. Check: after R5 the tables `sessions`, `login_codes` and `devices` are empty; and a test reads the import lines of `apps/server/src/first-admin.ts` and fails when one names the mail layer (the mail module of TOKI-021 or any path with `mail`), and `ensureFirstAdmin` takes no mail dependency in `deps` (Design, "Test hooks"), so the file has no path to the mail layer.
- R16. One shared function, in `packages/shared/src/email.ts` and re-exported from `packages/shared/src/index.ts` (the package exports only `.`, TOKI-001 R4), `parseEmail(value: string): string | null`, returns the address trimmed and in lower case when it is well-formed and `null` when it is not. Well-formed (Decided in this spec, plain code with no Zod, so no Zod version decides it): after trimming, at most 254 characters, no whitespace, exactly one @, a part before the @ of 1 to 64 characters made of ASCII letters, digits and ``!#$%&'*+/=?^_`{|}~.-`` with no dot at its start or end and no two dots in a row, and a domain of at least two labels separated by dots, each label 1 to 63 ASCII letters, digits or hyphens that does not start or end with a hyphen. `EMAIL_MAX_LENGTH` (254) and `EMAIL_LOCAL_MAX_LENGTH` (64) are exported with it. The first admin address passes it (R3). TOKI-022 (R7), TOKI-024 (R10, R35), TOKI-026 (R18), the Admin page (TOKI-025 R22) and the sign-in screen (TOKI-023) already name this function and this file. Whichever of these tickets and this one is built first creates the file exactly as written here; the others import it. Check: unit tests with the accepted and refused cases of R3 plus: a trailing dot in the domain, a domain of one label, two @, a dot at the start of the part before the @, a label of 64 characters, a non-ASCII letter (all `null`), `A@B.co` (gives `a@b.co`); and a database test that inserts every address `parseEmail` accepts in the test list into `users` and succeeds, and one it refuses by `users_email_check` or `users_email_length_check` (TOKI-019 R7).
- R17. After R5 the #general row is the one the tables protect: an update that sets `archived_at` on it is refused by the database (TOKI-028 R9), and the member row of the first Admin is in `conversation_members`, so #general is in their list with nothing to do. Check: a database test after R5 tries to set `archived_at` and the update is refused with the error TOKI-028 names; a read through `isConversationMember` of TOKI-028 returns true for the Admin and `getConversationFacts` reports `isGeneral` true.
- R18. A failed attempt is retried, bounded, while the server keeps running. `ensureFirstAdmin` makes at most `MAX_ATTEMPTS` (10) attempts, with `RETRY_DELAY_MS` (15 000) between two attempts, waited with the injected `sleep`. An attempt that fails with a code on the retry list is followed by another; any other failure ends the step at once. The retry list: the Node codes `ECONNREFUSED`, `ECONNRESET`, `ETIMEDOUT`, `ENOTFOUND`, `EAI_AGAIN` and `EHOSTUNREACH`; the Postgres classes `08` (connection) and codes `57P01`, `57P02`, `57P03`, `53300`, `55P03` and `42P01` (the table does not exist yet); and the step's own `attempt_timeout` (R19). The code is read from the error, or from its `cause` when the error is a wrapper (the query layer wraps driver errors). Each failed attempt writes one `first_admin_failed` line with `attempt` and `retry`. An attempt that finds the database not empty returns `skipped` and ends the step, so a retry after a late commit of an abandoned attempt (R19) is safe. Check: database tests with a `sleep` that resolves at once for the retry delay and never for the attempt deadline: (a) the hook `afterWorkspace` throws an error with code `57P03` on the first two attempts and passes on the third: `created`, two delays of 15 000 recorded, the four tables hold 1, 1, 1, 1 rows, two `first_admin_failed` lines (`attempt` 1 and 2, `retry` true) and then one `first_admin_created`; (b) on a throwaway database with no migration, the `sleep` applies the migrations (`runMigrations` of TOKI-005) when it is first called: the first attempt fails with `42P01` and `retry` true, the second returns `created`, which is the deploy that runs its migrations after the container starts; (c) a failure with code `23505` ends after one attempt with `retry` false and no call of `sleep`; (d) the failures of R11 (a) give `MAX_ATTEMPTS` lines, the last with `retry` false, and nine delays.
- R19. One attempt is bounded. Inside its transaction the step first runs `SET LOCAL statement_timeout = '10s'` and `SET LOCAL lock_timeout = '10s'`, and the attempt as a whole races the injected `sleep(ATTEMPT_TIMEOUT_MS)` (10 000): when the sleep wins, the attempt counts as failed with the code `attempt_timeout`, which R18 retries. A late result of the abandoned attempt is discarded. Check: with a hook `afterCount` that never resolves and a `sleep` the test resolves by hand for the deadline, the attempt ends with `attempt_timeout`, `retry` true, and a later attempt on a free database returns `created`; with a second connection holding the advisory lock of R9 open, an attempt ends with code `55P03` within about 10 seconds of real time.
- R20. A shutdown is not blocked and does not leave a half-done step. `main.ts` registers a close hook (TOKI-004 R15) that aborts the `AbortSignal` the step received and waits for the attempt in progress, which R19 bounds at 10 seconds. The step checks the signal before each attempt and during the delay: when it is aborted, no new attempt starts, the step writes one `first_admin_stopped` line and returns `stopped`. An attempt already inside its transaction ends by commit or rollback before the close hook returns, so the connection pool is not closed under it. Check: (a) a database test aborts the signal while the step waits for its second attempt: `stopped`, no further attempt, one `first_admin_stopped` line; (b) the abort while the hook `afterCount` of the first attempt is paused: the test releases the hook, the attempt commits, and the result is `created`, not `stopped`; (c) the process test of R12 (SIGTERM during the wait).
- R21. The three set-up values are required at every start (R1), so every place that starts the real server or builds a fake environment for its configuration must provide them, or exits 1. This ticket adds them, with fake values on `@example.com` and a workspace name of `Test Workspace`, to: the fake environments of the config and process tests of TOKI-004 and of the TOKI-005 tests that build a configuration; the server start of the end-to-end test of TOKI-008 R23; the env block of the CI jobs that start the server (TOKI-007, TOKI-008; the repository holds no `.env` file there). The mail values that TOKI-021 makes required for the same process tests (its Hand-offs) are added by that ticket; this ticket adds only its three. Check: `pnpm test` and `pnpm test:e2e` pass at the root with Postgres running; a search of those files for the config of the server finds no fake environment without the three names.

## Design
### Where it runs
- `main.ts` (TOKI-004): load config (R1 to R4 stop the process here if a value is bad), build the app, listen, then start `ensureFirstAdmin(...)` once and keep its promise for the close hook of R20. It runs after `listen` because TOKI-004 R20 and TOKI-005 R16 say an unreachable or slow database must not stop the server or delay `/healthz`, and nothing in the first seconds needs the Admin: with no account, a sign-in request gets the same answer as for any unknown address (BR-04).
- A failure must not stay silent, and a server that exits on it would break TOKI-004 R20. So the server stays up and the step retries (R18): about two and a half minutes of attempts, an error line for each, and the last one with `retry` false. `/healthz` is liveness and stays ok (TOKI-004 R5); what shows an operator the failure is the error lines, at a level an operator reads. After the last attempt, the next start tries again. Proposal, not a decision (readiness is TOKI-004 concern 3, a later ticket): the future `/readyz` could report "not ready" while the step has failed for good; `main.ts` keeps the result for that.
- Migrations are not applied by the server. Who runs `db:migrate` before the server starts, and in which order with the container start, is not settled by any spec: `dev:reset:db` does it in development (TOKI-003, TOKI-005), and in production the plan gives it to TOKI-085 ("deploy, run migrations"), which has no spec yet and may run it after the new container starts. This spec therefore states a dependency and relies on nothing: TOKI-085 owns the order and the check that `first_admin_created` appears after the first deploy (Plan changes), and R18 makes the step survive both orders for about two and a half minutes (`42P01` is retried). Decided in this spec: the server stays free of migration logic, as TOKI-005 designed it.
- The step is a file of `apps/server/src/` and not of the `workspace` module: `members` already needs the workspace name from `workspace` (TOKI-024 R12) and `auth` reads the workspace id and name (TOKI-022), so a `workspace` that imports `members` and `conversations` would make `workspace` and `members` import each other (concern 15).

### What it does (one attempt)
1. Start a transaction, run the two `SET LOCAL` of R19, and take `pg_advisory_xact_lock(1414482761, 1)`: the first integer is the namespace (the four bytes of the ASCII text `TOKI`), the second is the key of this step. The keys are listed in one file, `apps/server/src/db/advisory-locks.ts`, where any later ticket that takes an advisory lock adds its own key under the same namespace. The lock is released by the commit or rollback (R9).
2. Read the workspace ids through `listWorkspaceIds` and the number of accounts through `countAccounts`. An account exists: log `first_admin_skipped` and return `skipped`. No account and several workspaces: log `first_admin_workspace_without_account` and return `skipped`. No account and one workspace: use its id (`adopted`). Nothing at all: go on.
3. Create the workspace when there is none (`createWorkspace`); `createFirstAdminAccount`; `createGeneralChannel` (the #general row and the member row of its creator). Commit; log `first_admin_created`; return `created`.
The times of the account, the conversation and the member row come from `clock.now()` (TOKI-008 R19); the step reads no system time.

### Module boundaries
- `workspace`: `listWorkspaceIds(tx)` returns the ids of all `workspaces` rows; `createWorkspace(tx, { name })` inserts one row and returns its id.
- `members`: `countAccounts(tx)` returns the number of `users` rows; `createFirstAdminAccount(tx, { workspaceId, email, displayName, createdAt })` inserts one active Admin (the language is left to the table default) and returns its id. It is narrow on purpose: no other module can use it to make an Admin through it, and the rules around the last Admin and invitations (TOKI-024) cannot be bypassed by it.
- `conversations`: `createGeneralChannel(tx, { workspaceId, createdBy, createdAt })` inserts the #general row and the member row of `createdBy` and returns the conversation id. It owns the fixed values of #general (the name, the flag, public), so no other module writes them. Adding a person to #general later is `addMemberToGeneral(tx, { workspaceId, userId, createdAt })`, built by TOKI-028 (its R26) and called by TOKI-024 in `acceptInvitation`.
- The transaction type is exported by `src/db/client.ts` (TOKI-005). Decided in this spec: if TOKI-005 did not export a type for the Drizzle transaction, this ticket adds the alias in that file.

### Test hooks
`ensureFirstAdmin(deps, hooks?)` takes `deps` = `{ db, config, clock, logger, sleep, signal }` (no mail layer) and an optional `hooks` object with `afterCount`, `afterWorkspace`, `afterAccount` and `afterGeneral`. Each is an async function awaited inside the transaction after that step, and it receives the open transaction and the ids made so far: `afterCount({ tx })`, `afterWorkspace({ tx, workspaceId })`, `afterAccount({ tx, workspaceId, userId })`, `afterGeneral({ tx, workspaceId, userId, conversationId })`. A hook therefore writes in the same transaction, with the real `workspaceId`, which is what the duplicate-address case of R10 needs, and an error it throws rolls the attempt back. `main.ts` passes none. `sleep(ms)` is a dependency like the clock: `main.ts` passes a real one that unrefs its timer, tests pass a fake. Decided in this spec: tests need to pause the transaction (R9), to fail it between steps (R10) and to run the retries (R18) without a timer or a patched module. TOKI-008 R19 asks that timers use the injected clock; its clock has `now()` only, so `sleep` is injected beside it, and the real `sleep` is the only global timer of this ticket (if the clock gains a `sleep`, `main.ts` uses it).

### Errors
- A required value missing or empty, or a value that fails its check -> the server does not start, exit code 1, names only (R1, R3, R4).
- Database not empty -> nothing written; one info line (R7).
- Database unreachable, tables missing, any step fails -> rollback, one error line per attempt with codes only, the server keeps running, bounded retry for the codes of R18, none for the others (R10, R11, R18).
- Shutdown during the step -> no new attempt, the attempt in progress ends first (R20).

### Layout
```
apps/server/src/
├─ config.ts                              gains the set-up area
├─ main.ts                                calls ensureFirstAdmin after listen, registers the close hook
├─ first-admin.ts                         ensureFirstAdmin, the retry constants, the log lines

packages/shared/src/email.ts              parseEmail, the two limits (R16), re-exported by index.ts
```

## Testing
- Written test-first. Database tests are `.db.test.ts` files in the database project of TOKI-008: Postgres is real, migrations are applied at the start of the run, each file starts with empty tables and runs alone. Between the cases of one file the test empties every table of the `public` schema except the migration journal in one `TRUNCATE`, the statement shape of TOKI-008 R6 and TOKI-028 R23. The clock is the test clock of TOKI-008, and `sleep` is a fake. Fake data only: `@example.com` addresses.
- Config tests (R1 to R4) pass fake environment objects, like the TOKI-004 tests, and need no database. The database-free process test (R12) is the TOKI-004 process test with the set-up values added; the database half of R12 is its own `.db.test.ts` file, so `test:unit` passes with Postgres stopped (TOKI-008 R20).
- `first-admin.db.test.ts`: R5 and R6 (rows and display name), R7 and R8 (skip, adopt, run again with other values, counts), R9 (two clients, the hook, `pg_locks`), R10 and R11 (hooks that fail, the real unique violation, a client with nothing listening, a database with no migration), R13 (captured log searched for the personal values), R15 and R17, R18 to R20 (retry, deadline, shutdown).
- R14 by `pnpm lint` and the export-name test. R16: unit tests in `packages/shared` and one database test. R21 by the root test commands.
- Hand check once, output in the PR: start the server from `pnpm dev` after `dev:reset:db` with the development `.env` and read back the four rows with `psql`. When TOKI-021 and TOKI-022 are merged, also sign in as the first Admin with the code from Mailpit and open #general.

## Data safety
- The first admin address is personal data. It lives in `.env` (TOKI-096), reaches the database in the one transaction and is written to no log, error body or console (R13). A failure logs the error code and constraint name only, because a Postgres message can carry the value. That no start-up log line holds the address is the intent's own rule: no decision of the log covers it (the intent says so).
- A startup failure of the configuration prints names only (TOKI-004 R4).
- The step writes no credential: the account has no password (D-011), and no session or code is made (R15).
- Tests and fixtures use fake addresses only.

## Areas of concern
1. Whether the three values are checked at every start or only when the database is empty. Not decided. Flow F01 (the baseline, D-091) says both that a missing required variable stops the server and that the setup variables are ignored once the database has accounts. R1 as written checks them at every start, which conflicts with "ignored": an operator who removes the first admin address from `.env` after set-up, which is reasonable for personal data, takes the server down at the next start. Reason for the proposal: the configuration is read once, before the database is touched (TOKI-004 R2), and a server that starts without them today and fails at the next reset is worse than one that fails at the first deploy. Proposal, not a decision: keep R1; the alternative is to make the two values optional at start and fail inside the step only when the database is empty, which turns a missing value into an error line (R18) and not an exit. Owner: Thanh Truong, as product owner, who must choose between the baseline text and R1.
2. The variable names. Not decided until TOKI-096 adopts them. The Blueprint names none; TOKI-096 says in its Scope that TOKI-020 reads exactly the names of its inventory, and its R2 asks for a row for "first admin email" and one for "first admin name", with no names and no Required flag; the inventory does not exist yet. `FIRST_ADMIN_EMAIL`, `FIRST_ADMIN_NAME` and `WORKSPACE_NAME` are working names; R2 fails the build if the code reads a name that is not in `.env.example`. If the inventory chooses other names, the requirements here follow them. The request to TOKI-096 (names and flags) is in "Plan changes and requests to other specs". Owner: Thanh Truong, with the owner of the TOKI-096 spec.
3. Whether #general starts with a topic or a description. Not decided. The log fixes the channel's name and its rules (D-034, D-040) and no text for it. The prototype's #general has the topic "Company-wide announcements and general chat" and a description, but they belong to the sample workspace, and D-147 calls sample content illustration; a stored text cannot be translated like interface text. This spec writes #general with no topic and no description (R5 (c)). Proposal, not a decision: keep it empty in phase 1; the Admin can edit the topic and description like any member (D-105). Owner: Thanh Truong, as product owner.
4. Who builds what the first Admin sees on first entry: the line "This is the start of #general" and the card suggesting three things (invite members, create a channel, set a status), from flow F01. Not decided. Flow F01 is the baseline (D-091) but no ticket in the plan names the empty-#general line or the card, and neither is in the prototype's markup that this spec could check. This work builds neither. Proposal, not a decision: the conversation screen tickets own the line and a ticket for the card is added to the plan. Owner: Thanh Truong, for the plan.
5. A database with a workspace and no account. Decided in this spec: with exactly one workspace and no account the step adopts the workspace and keeps its name; with several it writes nothing and logs a warning (R7 (c), (d), R13). Reason: such a workspace cannot hold a conversation or a member (conversations need `created_by`, TOKI-028 R16), so the single row has nothing that adopting could hand to the wrong place, and refusing it would leave a stray row (a failed manual change, a copied dump) as an installation that never gets an Admin and only warns; with several workspaces there is no single right one, and the warning is the signal. The cost: a workspace name in `.env` that differs from the adopted row is ignored. Owner: Thanh Truong.
6. When the database cannot be reached or the step fails. Decided in this spec: the server stays up and the step retries a bounded number of times, with an error line for each attempt (R11, R12, R18, R19, R20). Reason: TOKI-004 R20 and TOKI-005 R16 (decided by Thanh on 2026-11-16) keep the server up when Postgres is down; `/healthz` stays ok (liveness), so without a retry a first deploy that starts before Postgres or before the migrations ends with no Admin and nothing that shows it. Cost: after the last attempt (about two and a half minutes) the installation has no Admin until the next start, and what shows it is the last error line. Whether `/readyz` should report it is a proposal in Design, "Where it runs". Owner: Thanh Truong.
7. The record of administrative actions (D-110, NFR-16: who, what, to whom, when). Not decided whether the creation of the first Admin counts. Nobody acts when the server does it. TOKI-024 has chosen the store: the table `admin_actions` (its R31, concern 7), whose `actor_id` is required, so the server cannot write a row without an acting account; TOKI-024 itself does not record the account made when an invitation is accepted, since that is not an administrative action. This work writes the info line `first_admin_created` with the ids and the log's own time (R13). Proposal, not a decision: that line is the record, and TOKI-024 writes its own records for what Admins do; no row of `admin_actions` is written here. Owner: Thanh Truong, with the owner of the TOKI-024 spec.
8. The first Admin's display name. Decided in this spec: the first admin name when given, otherwise the part before the @ (R6). Reason: D-150 gives that rule to a newcomer with no welcome step; the first Admin has no welcome step either (F01), and the inventory carries a name for them. The limit 1 to 80 is D-033; the part before the @ is at most 64 by R16, so it always fits. Owner: Thanh Truong.
9. The order with migrations at start-up. Decided in this spec: the server does not migrate and does not rely on the order; the step retries `42P01` (R18). The order itself is TOKI-085's: its spec does not exist and the plan describes it as "deploy, run migrations", so nothing here says migrations run first; TOKI-084 (image and Compose) has no spec either. `dev:reset:db` migrates before development starts. Reason: TOKI-005 made migration a command, and a server that migrates itself would need its own failure and lock rules. Owner: Thanh Truong, with the owner of the TOKI-085 spec.
10. Module boundaries and the TOKI-028 export list. Settled by TOKI-028 (PR #66): its R18 lists `createGeneralChannel` and `addMemberToGeneral` among six exported names in one list that each ticket extends, and its R25 and R26 build both with the arguments of R14. This ticket adds no name to that list and edits no test of TOKI-028. Owner: Thanh Truong.
11. One definition of a well-formed address. Settled: R16 defines `parseEmail` in `packages/shared/src/email.ts` with its rule written out, and TOKI-022 R7, TOKI-024 R10 and R35, TOKI-026 R18 and the Admin page R22 take it by name and path; whichever ticket is built first creates the file (R16). Source: those requirements in the specs of #17, #74, #72 and #92. Owner: Thanh Truong.
12. Two processes starting together (a deploy that overlaps a restart). Decided in this spec: a transaction-scoped advisory lock taken before the counts, with the key (1414482761, 1) listed in `db/advisory-locks.ts`, so one process creates the rows and the other skips (R9). Reason: no table constraint limits `workspaces` to one row (TOKI-005 R15), so without the lock two empty reads could each write a workspace; the two-integer form keeps the keys of later tickets apart. Owner: Thanh Truong.
13. The development seed. The sample workspace of TOKI-081 (Hugepig Studio, 8 people, #general with its members) is loaded into a database; if the server already ran set-up, the database is not empty, and a seed that inserts a second #general fails on the unique name (TOKI-028 R9, R4). Decided in this spec: this ticket makes no rule for the seed, and its R7 never touches data that exists. TOKI-081 owns the order (wipe, then seed, then start) and needs TOKI-020 in the plan; an end-to-end run that seeds must empty the tables first. Owner: Thanh Truong, with the owner of TOKI-081.
14. Who inserts an account, and the path for the first Admin. Decided in this spec: `members` exports `createFirstAdminAccount`, which fixes the role `admin` and the status `active` and takes neither as an argument (R14); the account made by an accepted invitation is TOKI-024's own insert, with its last-Admin and invitation rules. Reason: a general `createAccount(role, status)` would let any module make an Admin around those rules, and the specs of TOKI-024 and TOKI-097 disagreed on who calls it; TOKI-024 R20 step 4 now inserts the account of an accepted invitation itself and says so (its concern 13 (h)). Owner: Thanh Truong.
15. Where the step lives. Decided in this spec: in `apps/server/src/first-admin.ts`, a file outside `modules/` that imports the `index.ts` of `workspace`, `members` and `conversations` (TOKI-002 R17 allows it; R7 forbids a module reaching into another's files). Reason: `members` already imports `workspace` for the workspace name (TOKI-024 R12) and `auth` reads the workspace (TOKI-022), so a step inside `workspace` that calls `members` would make a cycle, and an ES module cycle fails at start-up when an export is used while a module loads. Owner: Thanh Truong.
16. A mistyped first admin address. Not decided. The values are used once, when the database is empty, and the address is in no log, so after a typo the operator finds a live installation with an Admin nobody can sign in as; correcting `.env` only gives a `first_admin_skipped` line, and a code or a link sent to a wrong address reaches nobody. The emergency link of TOKI-026 (`pnpm --silent emergency:link <address>`, which prints the link on standard output) takes the address as stored, so the operator who knows the address written in `.env` can still enter as that Admin when the mistyped address is well-formed (R16); what the Admin can then change is for TOKI-024. Proposal, not a decision: the installation guide (TOKI-087) says that the values are used once and that the fix is to change the address of that one account in the database (or to reset an installation that holds nothing else); a server command that changes it is a later ticket if the owner wants one. Owner: Thanh Truong, as product owner, and the owner of TOKI-087.
