# Pins and the Pinned tab design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/pins.md (Thanh Truong)
Ticket: TOKI-048
Needs: TOKI-040 (the sync engine: `registerEventHandler`, `patchMessage`, `placeMessage`, the windows), TOKI-093 (the Undo helper and the rows `pinMessage` and `unpinMessage` of its table); and, as built before this ticket, the specs of TOKI-036 (tables and events), TOKI-037 (the message API) and TOKI-038 (the gateway).

## Goal
A member needs to mark a message that people should find again, and to see the marked messages of a conversation in one place. The server stores messages and numbered events (TOKI-036 to TOKI-038) and the client keeps them in windows (TOKI-040), but a message has no way to be pinned, the conversation has no list of pins, and nobody is told when one changes.
This ticket builds the pin as a row of its own table, the three requests (pin, unpin, list the pinned messages), the `pinned` key of the message entry, the grey system line that says who pinned a message, the two live events, the client store of the pinned lists, the hook that the message menu calls to pin and unpin with Undo, and the Pinned tab with its empty state.
The two rules that carry the design are these. A pin is its own row, so the message table of TOKI-036 does not change and an unpin is a plain delete (Design, "Where a pin is stored"). And a change of a pin is applied on the client by its server time, so an answer that arrives late cannot undo a newer change (R12).
Nothing here asks for a confirmation: a pin and an unpin are reversible, so they happen at once and offer Undo (D-061, D-069).

## Requirements
Data
- R1. The table `message_pins` of the `messages` module (defined in `modules/messages/schema.ts`) has exactly these columns: `message_id`, `workspace_id`, `conversation_id`, `pinned_by`, `pinned_at`. `message_id` is the primary key (`message_pins_pkey`), so a message has at most one pin. `pinned_at` is `timestamptz`, required, with no default: the server writes it from the clock of TOKI-008 (TOKI-036 R10, TOKI-019 convention 3). Every key refuses to delete the row it points to (`ON DELETE RESTRICT`): (`message_id`, `conversation_id`) references (`id`, `conversation_id`) of `messages` through `messages_id_conversation_id_key` (`message_pins_message_id_fkey`), so a pin cannot point to a message of another conversation; (`conversation_id`, `workspace_id`) references (`id`, `workspace_id`) of `conversations` through `conversations_id_workspace_id_key` (`message_pins_conversation_id_fkey`); `workspace_id` references `workspaces.id` (`message_pins_workspace_id_fkey`); `pinned_by` references `users.id` (`message_pins_pinned_by_fkey`). The keys that leave the module are written as SQL in the migration, the composite key to `messages` in the schema file (TOKI-036 R9). One index, `message_pins_conversation_idx`, on (`conversation_id`, `pinned_at` descending, `message_id` descending). Check: a test applies the migrations to a throwaway database and reads the columns, types, nullability, defaults, primary key and index from the catalog; it finds every key in `pg_constraint` with `ON DELETE RESTRICT`; an insert with a message of another conversation, an unknown workspace, a workspace that is not the conversation's, an unknown `pinned_by` and no `pinned_at` is refused, each by the name of its key or by the not-null error; a second insert for the same message is refused by `message_pins_pkey` and `ON CONFLICT (message_id) DO NOTHING` leaves one row, the first, unchanged.
- R2. What a pin may hold. A trigger before every insert (`message_pins_message_trg`) refuses a pin whose message is not of `kind` `user`, or is a reply that is not also sent to the channel (`parent_id` not null and `also_in_channel` false), or has `deleted_at` set. A trigger refuses every update of a pin (`message_pins_no_update_trg`): a pin is made or removed, never changed. A delete is allowed (an unpin). The rule is "a message of the main list" in the sense of the table (TOKI-036 R11; concern 3). The trigger looks at the message at the time of the insert only; a message deleted afterwards keeps its pin row and is left out of every read (R3, R8). Check: a pin of a user message of the main list is accepted; each of these is refused by `message_pins_message_trg`: a system line, a reply with `also_in_channel` false, a message with `deleted_at`; a reply with `also_in_channel` true is accepted; an update of each column is refused by `message_pins_no_update_trg` and the row is unchanged; a delete succeeds; a message that gets `deleted_at` after its pin was inserted keeps the row (the update of `messages` is not refused).
- R3. The key `pinned` of `MessageEntry` (TOKI-037 R15) is `null` or `{ by: string, at: string }`: `by` is the id of the person who pinned (`pinned_by`), `at` the time of the pin as ISO 8601 UTC. It is `null` for a message with no pin row and for a message with `deleted_at` set. The one function that makes an entry from a row (the mapper of TOKI-037) gets the key, and every read that builds entries adds `left join message_pins on message_pins.message_id = messages.id` to its one statement: the history of TOKI-037 R11 to R14, the answer of a repeated send (TOKI-037 R5), the pin answer (R6) and the list (R8). A new message and a system line are made with `pinned` `null` and no join. Adding the join does not change the predicate of the partial index nor add a statement: history is still one statement per page. Check: an unpinned and a pinned message come back from the history with `null` and with `{ by, at }`; a pinned message whose `deleted_at` is set comes back with `null`; the statement count of a history page and of a repeated send is the same as before the change (read through the wrapper of TOKI-031 R14); the `EXPLAIN` test of TOKI-036 R11, run with the join added to the three main-list queries, still names `messages_conversation_main_idx` and holds no `Sort` node; a schema test of the entry accepts both forms of `pinned` and refuses `{ by }` alone, an extra key and a non-ISO time.

Requests
- R4. All three routes need a valid session (TOKI-022 R24, 401) and run the first steps of TOKI-037 R1 in the same order: (1) the schemas of the path, the query and the body (400 `validation_failed`); (2) `getConversationFacts(db, actor.id, id)`: `null` is 404 `not_found`, and a private channel, a DM or a group the actor is not in is 404 `not_found` before any permission function runs (BR-09, BR-10, D-045); (3) `canReadConversation` (TOKI-027 R5): a person who is not a member of a public channel gets 403 `forbidden` (D-116). The routes live in the `messages` module, registered by `messageRoutes` (TOKI-037 R18) from a new file `pin-routes.ts`; they accept a direct message and a group like the routes of TOKI-037 do. No route compares a role. The refusals of `canPinMessage` (TOKI-027 R6) are answered by reason: `not_a_member` is 403 `forbidden`; `channel_archived` is 409 `channel_archived` (for pin and unpin, an Admin included); `fact_missing` and `unknown_role` are 500 `internal_error`. Check: a table test sends each case to each route and checks the status and the code: no session, an unknown conversation, a private channel, a DM and a group of which the caller is not a member (the same body as an unknown id), a public channel the caller has not joined, an archived channel, a malformed id; each refusal compares the tables `message_pins`, `messages` and `events` before and after.
- R5. Locks for pin and unpin. A pin and an unpin each run in one transaction at `READ COMMITTED` and take the locks of TOKI-037 R8 in the same order: the account row of the actor `FOR SHARE`, then the conversation row `FOR SHARE` (`FOR NO KEY UPDATE` for a `dm`), then the facts are read again and `canReadConversation` and `canPinMessage` are called with what the locks returned. The steps are the ones that the send uses and are written once: if TOKI-037 keeps them inline in `send.ts`, this ticket moves them to one function of `messages/locks.ts` that the send and the pin both call, with no change to the send. After them the transaction takes no lock that can wait, except the counter lock of the event handler, which comes last (TOKI-036 R18). The lock excludes a leave, an archive and a removal that commit first, so a pin is never stored in a conversation that was archived by an earlier commit or for a person who has left. Check, with two real connections, the second waiting and the result read after the first commits and never by sleeping: a pin and an archive at the same moment end either with the message pinned and then the channel archived, or with the pin refused 409 `channel_archived`; a pin and the leave of the same person end with a pin by a person who was still a member or with a refused request (404 or 403, as the facts say), never with a pin by a person who has no member row after both; two pins of different messages in one channel do not wait on each other; the isolation level read inside the transaction is `read committed`; a pin and a send in one channel finish with no deadlock (SQLSTATE `40P01`).
- R6. Pin: `PUT /api/v1/conversations/{id}/pins/{messageId}`, no body. After R4 and R5: (4) the read-only rule for a direct message with a deactivated person (concern 4); (5) the message is read with `where id = $messageId and conversation_id = $id`: no row, or `deleted_at` set, is 404 `not_found`; a system line, or a reply that is not also in the channel, is 409 `message_not_pinnable` (a code that this ticket adds, R10); (6) the time `at` is read once from the clock of TOKI-008, and `insert into message_pins (message_id, workspace_id, conversation_id, pinned_by, pinned_at) ... on conflict (message_id) do nothing returning *`. It answers 200 with `{ "message": MessageEntry, "changed": boolean }`, `message` being the entry with `pinned` filled. When the insert returned a row, `changed` is true, `pinned.by` is the actor and `pinned.at` is `at`, and the transaction calls `recordChange(tx, change)` once as its last statement, with `type` `message_pinned`, `actorId`, `conversationId`, `messageId`, `at` and `target` (the entry just returned), R9. When the message was already pinned, by the actor or by anyone, nothing is written: `changed` is false, `message.pinned` is the stored pin (the first one), and `recordChange` is called zero times, so a double press, a retry and two tabs make one pin, one line and one event. The pin of someone else's message and of one's own message are the same request (AC-096). Check: Sam pins Mai's message in a private channel and the answer is 200 with `changed` true and the entry's `pinned` equal to Sam and `at`; the same request again is 200 with `changed` false, the same `pinned`, one row, one system line and no second event; Mai pins the message Sam already pinned and gets Sam's pin back; a Member and an Admin who are members can pin, an Admin who is not a member of a private channel gets 404 and pins nothing (D-047); a 409 `message_not_pinnable` for a system line and for a reply with `also_in_channel` false; a 404 for a message of another conversation and for a deleted message; a rollback after the insert (a failing handler) leaves no pin, no line and no event; the statement log shows the lock statements before the lookup of the message and the lookup before the insert.
- R7. Unpin: `DELETE /api/v1/conversations/{id}/pins/{messageId}`. After R4 and R5 and the read-only rule: the message is read with `where id = $messageId and conversation_id = $id`; no row is 404 `not_found`; a deleted message is allowed (its pin row may still exist), so that the row can be removed. `delete from message_pins where message_id = $messageId returning *`. It answers 200 with `{ "messageId": string, "changed": boolean, "at": string }`, `at` being the time read from the clock once for the request, as ISO 8601. When a row was deleted, `changed` is true and the transaction calls `recordChange` once as its last statement with `type` `message_unpinned`, `actorId`, `conversationId`, `messageId` and `at`; when there was no pin, `changed` is false and `recordChange` is called zero times (an unpin of an unpinned message is a repeat, not an error). Any member can unpin any pin, the pinner's or another's (AC-096, TS-150). Check: Mai unpins Sam's pin and the answer is `changed` true, the row is gone and one event is recorded; the same request again is `changed` false and records nothing; an unpin of a message that was never pinned in an existing conversation is 200 `changed` false; an unpin of a deleted message that still has its row removes the row; a message of another conversation is 404; the refusals of R4 apply.
- R8. The list: `GET /api/v1/conversations/{id}/pins` takes `limit` (1 to `MESSAGE_PAGE_MAX`, default `MESSAGE_PAGE_DEFAULT`, the constants of TOKI-037 R22) and, together or not at all, `beforeAt` (ISO 8601 UTC) and `before` (a message id): the position after which the next page starts. One without the other, a bad value and a key other than these three are 400 `validation_failed`. It runs the steps of R4 only and takes no lock: reading is allowed for every member of every kind of conversation, an archived channel included (`canReadConversation`, TOKI-027 R5). It answers 200 with `{ "messages": MessageEntry[], "hasMore": boolean }`: the pinned messages of the conversation whose message has no `deleted_at`, each with `pinned` filled, ordered by (`pinned_at`, `message_id`) from the newest pin to the oldest, a page being the rows strictly after the position `(beforeAt, before)` compared as a pair, with `hasMore` read from one row more than the limit. One statement per page, using `message_pins_conversation_idx`. There is no limit on the number of pins of a conversation (D-164): the list is paged so that its size is not. Two pins with the same `pinned_at` are ordered by message id, newest id first; they can only be pinned within the same millisecond. Check: a conversation with 130 pins is read in pages with the pair of the last entry and returns every pin once, newest first, and a second walk gives the same order; a page with `hasMore` false at the end; three pins pinned in the order B, A, C come back C, A, B (TS-151 on the server); a deleted message is not listed and an unpinned one is not listed; an archived channel's list is readable by a member and refused for a non-member; `EXPLAIN` with `enable_seqscan` off names `message_pins_conversation_idx` and holds no `Sort` node for the first page and for a page with a position; the statement count of one page is 1; the body is parsed with the response schema of R10.

Changes, the line and the events
- R9. The two changes. `Change` of `conversations/changes.ts` (TOKI-037 R18) gains the types `message_pinned` and `message_unpinned` and the optional fields `messageId` and `target` (a `MessageEntry`); the route sets them as R6 and R7 say. The first handler of the list, the system-line handler of TOKI-037 R16, writes for `message_pinned` one row of `kind` `system`, `system_type` `message_pinned`, `author_id` the actor, `system_user_ids` empty and `created_at` equal to `at`, in the transaction of the change, and returns `{ message }`; it writes nothing for `message_unpinned` (D-165). The line holds no id of the pinned message: the journey gives a line that says who pinned a message and no link (F17). The last handler of the list, the event handler of TOKI-038 R20, gets two more rows, in `modules/realtime/` and typed with its own structural `EventChange`: `message_pinned` writes `message.pinned`, scope `conversation`, `data` `{ message: change.target }`; `message_unpinned` writes `message.unpinned`, scope `conversation`, `data` `{ conversationId, messageId }`. After the events of the change the handler writes, as TOKI-038 R20 says for every change that carries `change.message`, the `message.created` of the line, so a pin makes two events with consecutive numbers, `message.pinned` and then `message.created`, and an unpin makes one. Both kinds are added to the registry of TOKI-038 R12 with their `data` schemas, and to the table `kinds.ts` of TOKI-038 with a row that changes no map (the test that every registry kind has a row and the reverse stays true). The line is a `system` message: it raises no unread count and notifies nobody (D-100, D-165), by the rule on `kind` that TOKI-053 reads; this ticket counts and notifies nothing. No code of this ticket calls `recordEvent` or `appendEvent` (TOKI-036 R25). Check: a real pin leaves one line row with the type, author and `created_at` above and `system_user_ids` empty, and a recording handler after the line handler receives it as `change.message`; a real unpin leaves no line; with the real event handler the log holds `message.pinned` and then `message.created`, numbered one after the other, and `message.unpinned` for an unpin; `message.pinned.data.message.pinned` equals the stored pin; a repeat writes no line and no event; a rollback after the line leaves none of the three; a pin line is `kind` `system` and is not a message of `kind` `user`; the registry and `kinds.ts` tests pass with the two new kinds; a search of `apps/server/src` outside `modules/realtime/` finds no call of `recordEvent`.
- R10. `packages/shared` gains, in `src/messages/` and `src/realtime/`: the schema `PinInfoSchema` and the key `pinned` of `MessageEntry` (R3); `PinMessageResponseSchema` (R6), `UnpinMessageResponseSchema` (R7), `ListPinsQuerySchema` and `ListPinsResponseSchema` (R8); `message_pinned` in `SYSTEM_LINE_TYPES` (TOKI-037 R22); the event kinds `message.pinned` and `message.unpinned` with their `data` schemas (TOKI-038 R12); and the error code `messageNotPinnable` (`message_not_pinnable`, 409) in `ErrorCodes`. The server and its tests use the strict schemas; the client reads with the form that drops unknown keys (TOKI-032 R3). Check: schema tests accept a valid body and refuse a missing key, an added key, a non-ISO time and `beforeAt` without `before`; every 200 body of the route tests is parsed with its response schema; the registry has the new code with no duplicate; the two kinds parse a valid `data` and refuse one without `message` or without `messageId`; a type test imports every new name from `@toki/shared`.

Client
- R11. `createApiClient` gains `pins.list(conversationId, query?, signal?)`, `pins.pin(conversationId, messageId, signal?)` and `pins.unpin(conversationId, messageId, signal?)`, with the rules of TOKI-040 R2 (one request core, 10 seconds, no retry, a path part encoded, `signal` last, neither `headers` nor `timeoutMs`). `list` sends `limit`, `beforeAt` and `before` only when given and returns `{ messages, hasMore }`; `pin` sends `PUT` and returns `{ message, changed }`; `unpin` sends `DELETE` and returns `{ messageId, changed, at }`. Each answer is read with the response schema of R10 in the tolerant form. Check, with the fake `fetch` of the API tests: the method, the path with an encoded id, the query and the empty body of each; the answers parse; an unknown key in an answer is dropped; a 409 `channel_archived` and a 409 `message_not_pinnable` reach the caller as the `ApiError` of TOKI-032 R4 with the code.
- R12. The store of pinned lists: `createPinsStore({ conversations, api, sync })` of `packages/client-core/src/pins/`, exported from the package index with its types; `sync` is the engine of TOKI-040. It holds no text and uses no browser API, no `Date.now(` or `new Date()` and no timer (TOKI-008 R19). For each conversation it holds a `PinList`: `{ status, error, items, hasMore, isLoadingMore, isRefreshing }`, `status` being `idle` (never loaded), `loading` (the first load, no item held), `ready` or `failed` (only while no item is held); `items` is the pinned `MessageEntry` of the conversation, newest pin first; the list is replaced, never changed in place, so two reads with no change between return the same object. Methods: `getPins(id)` and `subscribePins(id, listener)` (one conversation's changes only); `loadPins(id)` requests the first page and replaces the held items with it, keeps the held items on screen while it runs (`isRefreshing`), and never rejects (the outcome is read from the list); `loadMorePins(id)` requests the page after the last held entry with `beforeAt` and `before`, does nothing when `hasMore` is false or a load runs, and adds the page; `pin(id, messageId)` and `unpin(id, messageId)` call the API and return its answer, reject with the `ApiError` on failure and apply the answer (below); `patchPinned(id, messageId, update)` and `removePinned(id, messageId)` change or drop one held entry, a no-op when it is not held, for the handlers of TOKI-046 and TOKI-047 (R13). The rule of last write by server time (decided in this spec): the store keeps, for each message it has seen change, `{ kind, at }` of the latest pin or unpin; a pin (an answer with `pinned.at`, or an event) is applied only when its time is not older than the held change of that message, and an unpin (an answer with `at`, or an event with its `createdAt`) likewise, so an answer that arrives after the event of a later change does not undo it. Applying a pin to a loaded list inserts the entry at the top; an unpin removes the entry; the answer changes the list only, and the window of TOKI-040 is changed by the events (R13). While `loadPins` runs, the events and answers of that conversation are kept aside and applied after its page, in the order they came, each by the same rule, so a change that committed after the page was read is not lost (the way TOKI-040 R5 treats a head load). A list that is `idle` takes no event and no answer (the next load brings the truth). The store resets, dropping every list and the held changes, when the conversation store of TOKI-032 goes back to `idle`. Check: with a fake `api` of deferred promises: the first load, the refresh that keeps the old items, the second page, `hasMore` false doing nothing; a pin answer puts the entry at the top and an unpin answer removes it, and changes no window; an unpin event with a later time than a pin answer that arrives after it leaves the message out; the same two the other way round leave it in; two events during a deferred `loadPins` are in the list after the page; an event for an `idle` list changes nothing; `pin` rejects with the error of a 409 and leaves the list; `reset` empties everything; two reads with no change give `===` objects and the listener of conversation `a` is not called for a change of `b`.
- R13. The events. The store registers, through `registerEventHandler` of TOKI-040 R18, one handler for `message.pinned` and one for `message.unpinned`; each runs after the engine's own effect (which is none for these kinds), gets the event with its `createdAt` as the time of the change, and applies it by the rule of R12 to the list, and to the window of the conversation through `tools.patchMessage` (a no-op when the window does not hold the message), which sets `pinned` from the event's `data` for a pin and to `null` for an unpin, only when the change passes the rule of R12. The two handlers are the only code that reads these kinds. A handler that fails to parse its `data` is skipped by the engine (TOKI-040 R13). The store gives the other tickets two seams and no more: `patchPinned` and `removePinned` (R12), which the handler of TOKI-047 for an edit and for a delete, and the handler of TOKI-046 for a reaction, call when the message is held in a list. A change of a message that nobody forwards shows when the tab is opened again (R15), because the server decides what the list holds. Known limit: a missed range that is too old makes the engine `reload` (TOKI-040 R19) and does not tell the store, so a Pinned tab that stays open through it shows the list as it was until the tab is opened again. Check: a `message.pinned` event inserts the entry at the top of a loaded list and sets `pinned` in the window that holds the message; a `message.unpinned` event removes it and clears `pinned`; an event with bad `data` changes nothing and calls no handler twice; `registerEventHandler` is called twice with these two kinds and the returned functions are kept by `dispose`; the same batch applied twice leaves the same state; a handler that throws does not stop the next event.

Web
- R14. `apps/web/src/features/pins/usePinActions.ts` exports `usePinActions()` returning `{ canPin, isPinned, labelKey, toggle }`. `canPin(facts: ConversationFacts)` is `canPinMessage` of `@toki/shared` with the signed-in person (the check is the server's too, R4; this one lets a menu leave the item out). `isPinned(message)` is `message.pinned !== null`. `labelKey(message)` is `pins.action.unpin` for a pinned message and `pins.action.pin` for the others (R17). `toggle(message)` pins an unpinned message and unpins a pinned one, through `useUndo().run` of TOKI-093 (R12 there), and returns its promise of `"done"`, `"failed"` or `"blocked"`. A pin is `run({ action: "pinMessage", text: t("pins.toast.pinned"), perform: () => store.pin(conversationId, id), undo: () => store.unpin(conversationId, id), key })`; an unpin is `run({ action: "unpinMessage", text: t("pins.toast.unpinned"), perform: () => store.unpin(...), undo: () => store.pin(...), key })`, with the same `key` `pin:<messageId>` for both, so that a pin followed by an unpin of the same message shows one toast (TOKI-093 R15). The request is made first and the toast comes after the server's answer, as `useUndo` does; nothing is changed on screen before the answer, and the answer and the event then show the label and the list. No confirmation is shown (D-069). Offline, `run` resolves `"blocked"` and calls nothing (the gate of TOKI-093 R17, which says that a connection is needed); a failed request shows the plain error toast of TOKI-093 R12 and no Undo. Undo is a second call (TOKI-093), so the undone state is the one the second call makes (concern 5). ## Design
### Where a pin is stored
Decided in this spec (concern 2): a table of its own, one row per pinned message, and not two columns on `messages`.
- The message table of TOKI-036 is "exactly these columns" in its own test and its trigger `messages_immutable_trg` lists the columns that may change; a pin on it would change both, and a pin is not a property of what was written but of how the conversation uses it.
- An unpin is a delete of a row; no column is set back to null, and nothing keeps a history of unpins (D-165 gives no line for it).
- The list is one index of the pin table, ordered by the time of the pin, and joins the message by its primary key; the main-list index of messages is untouched.
- Reactions are a table of their own for the same reason (technical design, table groups).
The cost is one left join on the primary key in the reads that build entries (R3), checked by `EXPLAIN`.

### API
All routes need a session (R4). Bodies are JSON; pin and unpin have none.

| Method | Path | Who | Purpose |
| :---- | :---- | :---- | :---- |
| PUT | `/api/v1/conversations/{id}/pins/{messageId}` | members of a conversation that is not archived | Pin; 200 with `changed` true or false (R6) |
| DELETE | `/api/v1/conversations/{id}/pins/{messageId}` | members of a conversation that is not archived | Unpin; 200 with `changed` true or false (R7) |
| GET | `/api/v1/conversations/{id}/pins` | members, any state | The pinned messages, newest pin first, paged (R8) |

| Status | `error.code` | When |
| :---- | :---- | :---- |
| 200 | none | Done, or nothing to do (`changed` false); a page of the list |
| 400 | `validation_failed` | A path, query or id fails its schema (R4, R8) |
| 401 | as TOKI-022 | No valid session, or the locked actor was deactivated |
| 403 | `forbidden` | A person who is not a member of a public channel (R4) |
| 404 | `not_found` | Unknown conversation; a private channel, DM or group the person is not in; a message that is not in the conversation, or is deleted (pin) (R4, R6, R7) |
| 409 | `channel_archived` | Pin or unpin in an archived channel (R4) |
| 409 | `conversation_read_only` | Pin or unpin in a DM with a deactivated person, as proposed in concern 4 |
| 409 | `message_not_pinnable` | A system line, or a reply that is not also in the channel (R6) |
| 500 | `internal_error` | A server failure, or `fact_missing` or `unknown_role` from a function |

A pin and an unpin are idempotent: `PUT` of a pinned message and `DELETE` of an unpinned one answer 200 and write nothing, so a retry after a lost answer is safe and needs no id from the client. A 409 means the screen was out of date; the client reloads the list (D-131).

### What a person sees, in order
A person opens the More menu of a message, which TOKI-052 draws with the item that `usePinActions` describes, and presses 'Pin to conversation'. The request goes to the server and nothing changes on screen yet. The answer arrives, the toast 'Pinned to conversation' with Undo shows for 5 seconds, the store puts the entry at the top of the list, and the event sets `pinned` on the message in the window, so the label appears. The same moment the server's events reach every member: `message.pinned` sets the label and the entry on their screens, and `message.created` brings the line "Sam pinned a message". Pressing Undo calls unpin, the label and the entry go, and no line is added for the unpin (D-165). The earlier line stays (concern 5).

### Reading the Pinned tab
The tab calls `loadPins` each time it is opened, so it starts from the server. While it is open the events keep it current, by the rule of last write by server time (R12), and an entry that is deleted or edited is changed by the handlers of TOKI-047 through the two seams (R13). Pressing an entry calls `onOpenMessage`; the row of TOKI-041 selects the Messages tab and opens the conversation at that message with `loadAround` of TOKI-040 (TOKI-037 R13).

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- A pin is a row of its own table (above, concern 2).
- Pin and unpin are idempotent `PUT` and `DELETE`, with `changed` in the answer, so a repeat writes no line and no event (R6, R7).
- The list is read by the position `(beforeAt, before)` as a pair, so unpinning the last entry between two pages does not break the next page (R8).
- Nothing is changed on screen before the server answers; the effect is "at once" in that there is no confirmation, as `useUndo` does it (R14, TOKI-093).
- Last write wins by server time, in the store (R12).
- The Pinned tab always starts from a request and is kept current by events while open (R15).

## Data safety
- A pin is visible to the members of its conversation only. A private channel, a DM and a group answer 404 to anyone else, with the same body as for an id that does not exist; a public channel answers 403 to a non-member and returns nothing of it (R4).

- Tests use made-up texts and generated ids.

5. What Undo does to the line and to the place. Not decided. AC-098 says Undo puts the message back in its earlier state; D-165 gives no line for an unpin, and TOKI-093 concern 9 leaves open whether an undone pin removes its line, adds a second one or leaves both. Undo is a second call (TOKI-093), so this ticket builds: Undo of a pin unpins and leaves the line it added; Undo of an unpin pins again, which takes a new time (the message goes to the top of the tab, not back to its old place) and adds a second line. Proposal, not a decision: Undo of a pin leaves the line, because the line is the record that a person pinned; Undo of an unpin restores the old pin time and adds no line, which needs a way to send the old time (a body on `PUT`) that this spec does not add. 9. Order inside one millisecond and a late answer.
