# Pins and the Pinned tab design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/pins.md (Thanh Truong)
Ticket: TOKI-048
Needs: TOKI-040 (the sync engine: `registerEventHandler` with several handlers for one kind, `patchMessage`, `placeMessage`, the windows and their journal of patches), TOKI-041 (`conversationTabs` in `apps/web/src/conversation/tabs.ts`, so the array exists when this ticket adds its entry), TOKI-042 (`messageExtensions` in `apps/web/src/conversation/message/extensions.ts`, where the Pinned label plugs in), TOKI-093 (the Undo helper and the rows `pinMessage` and `unpinMessage` of its table); and, as built before this ticket, the specs of TOKI-036 (tables and events), TOKI-037 (the message API and the one entry builder `buildMessageEntry`), TOKI-038 (the gateway) and TOKI-047 (the event kinds `message.edited` and `message.deleted`, `applyMessageChange`, which adopts the `isFresher` of TOKI-045).

## Goal
A member needs to mark a message that people should find again, and to see the marked messages of a conversation in one place. The server stores messages and numbered events (TOKI-036 to TOKI-038) and the client keeps them in windows (TOKI-040), but a message has no way to be pinned, the conversation has no list of pins, and nobody is told when one changes.
This ticket builds the pin as a row of its own table, the three requests (pin, unpin, list the pinned messages), the `pinned` key of the message entry, the grey system line that says who pinned a message, the two live events, the client store of the pinned lists, the hook that the message menu calls to pin and unpin with Undo, and the Pinned tab with its empty state.
The two rules that carry the design are these. A pin is its own row, so the message table of TOKI-036 does not change and an unpin is a plain delete (Design, "Where a pin is stored"). And a change of a pin is applied on the client by its server time, so an answer that arrives late cannot undo a newer change (R12).
Nothing here asks for a confirmation: a pin and an unpin are reversible, so they happen at once and offer Undo (D-061, D-069).

## Requirements
Data
- R1. The table `message_pins` of the `messages` module (defined in `modules/messages/schema.ts`) has exactly these columns: `message_id`, `workspace_id`, `conversation_id`, `pinned_by`, `pinned_at`. `message_id` is the primary key (`message_pins_pkey`), so a message has at most one pin. `pinned_at` is `timestamptz`, required, with no default: the server writes it from the clock of TOKI-008 (TOKI-036 R10, TOKI-019 convention 3). Every key refuses to delete the row it points to (`ON DELETE RESTRICT`): (`message_id`, `conversation_id`) references (`id`, `conversation_id`) of `messages` through `messages_id_conversation_id_key` (`message_pins_message_id_fkey`), so a pin cannot point to a message of another conversation; (`conversation_id`, `workspace_id`) references (`id`, `workspace_id`) of `conversations` through `conversations_id_workspace_id_key` (`message_pins_conversation_id_fkey`); `workspace_id` references `workspaces.id` (`message_pins_workspace_id_fkey`); `pinned_by` references `users.id` (`message_pins_pinned_by_fkey`). The keys that leave the module are written as SQL in the migration, the composite key to `messages` in the schema file (TOKI-036 R9). One index, `message_pins_conversation_idx`, on (`conversation_id`, `pinned_at` descending, `message_id` descending). Check: a test applies the migrations to a throwaway database and reads the columns, types, nullability, defaults, primary key and index from the catalog; it finds every key in `pg_constraint` with `ON DELETE RESTRICT`; an insert with a message of another conversation, an unknown workspace, a workspace that is not the conversation's, an unknown `pinned_by` and no `pinned_at` is refused, each by the name of its key or by the not-null error; a second insert for the same message is refused by `message_pins_pkey` and `ON CONFLICT (message_id) DO NOTHING` leaves one row, the first, unchanged.
- R2. What a pin may hold. A trigger before every insert (`message_pins_message_trg`) refuses a pin whose message is not of `kind` `user`, or is a reply that is not also sent to the channel (`parent_id` not null and `also_in_channel` false), or has `deleted_at` set. A trigger refuses every update of a pin (`message_pins_no_update_trg`): a pin is made or removed, never changed. A delete is allowed (an unpin). The rule is "a message of the main list" in the sense of the table (TOKI-036 R11; concern 3). The trigger looks at the message at the time of the insert only; a message deleted afterwards keeps its pin row and is left out of every read (R3, R8). Check: a pin of a user message of the main list is accepted; each of these is refused by `message_pins_message_trg`: a system line, a reply with `also_in_channel` false, a message with `deleted_at`; a reply with `also_in_channel` true is accepted; an update of each column is refused by `message_pins_no_update_trg` and the row is unchanged; a delete succeeds; a message that gets `deleted_at` after its pin was inserted keeps the row (the update of `messages` is not refused).
- R3. The key `pinned` of `MessageEntry` (TOKI-037 R15) is `null` or `{ by: string, at: string }`: `by` is the id of the person who pinned (`pinned_by`), `at` the time of the pin as ISO 8601 UTC. It is `null` for a message with no pin row and for a message with `deleted_at` set. The server builds every `MessageEntry` through one function, `buildMessageEntry(db, row, readers?)` and its list form `buildMessageEntries(db, rows, readers?)` of TOKI-037 (the contract of TOKI-045, "The entry builder"), which joins the thread summary, the reactions and the pin through readers that `app.ts` injects: `readers.listPinned(db, messageIds)`. This ticket supplies that reader: `listPinned` of `pin-list.ts`, exported from `messages`, runs one statement, `select p.message_id, p.pinned_by, p.pinned_at from message_pins p join messages m on m.id = p.message_id where p.message_id = any($1) and m.deleted_at is null`, and returns a map from message id to `{ by, at }`; the builder gives `null` to a message that is not in the map. Because history, the repeated send, the replies route and its `root` (TOKI-045 R6), the answers and the events of edit and delete (TOKI-047 R10), the pin answer and the list all build their entries through the builder, a pinned message keeps its label in each of them, and a key that a later ticket adds is filled everywhere at once. The builder calls the reader once for the ids of the non-deleted messages of `kind` `user` that it is given, and sets `pinned` `null` for a system line, for a deleted message, for a message that is not in the map and when no `listPinned` is given (so the tests of TOKI-037 stay valid). A new message is built with `pinned` `null` and the reader is not called for it. The schema of `MessageEntry` gives `pinned` the default `null` on read only, never on write, so a client that reads a page or an event of the retention window written before this ticket does not fail to parse it (the rule of TOKI-046 R9 for `reactions`); the server always writes the key. One call of the reader costs one statement for a page or an answer, never one for each message; with the readers of TOKI-046 and TOKI-050 given, a page makes one more statement for each reader. Check: an unpinned and a pinned message come back from the history, the replies route (reply and `root`), the answer of a repeated send, the pin answer and the list with `null` and with `{ by, at }`; a pinned message whose `deleted_at` is set comes back with `null`; the edit and the delete of a pinned message give an answer and a `message.edited` or `message.deleted` event whose `message.pinned` is the stored pin for the edit and `null` for the delete; a history page makes exactly one more statement than without the reader (read through the wrapper of TOKI-031 R14) and not one for each message; the `EXPLAIN` test of TOKI-036 R11 on the three main-list queries is unchanged (they do not join the pin table); a schema test of the entry accepts both forms of `pinned`, gives `null` to an entry read without the key, and refuses `{ by }` alone, an extra key and a non-ISO time.

Requests
- R4. All three routes need a valid session (TOKI-022 R24, 401) and run the first steps of TOKI-037 R1 in the same order: (1) the schemas of the path, the query and the body (400 `validation_failed`); (2) `getConversationFacts(db, actor.id, id)`: `null` is 404 `not_found`, and a private channel, a DM or a group the actor is not in is 404 `not_found` before any permission function runs (BR-09, BR-10, D-045); (3) `canReadConversation` (TOKI-027 R5): a person who is not a member of a public channel gets 403 `forbidden` (D-116). The routes live in the `messages` module, registered by `messageRoutes` (TOKI-037 R18) from a new file `pin-routes.ts`; they accept a direct message and a group like the routes of TOKI-037 do. No route compares a role. The refusals of `canPinMessage` (TOKI-027 R6) are answered by reason: `not_a_member` is 403 `forbidden`; `channel_archived` is 409 `channel_archived` (for pin and unpin, an Admin included); `fact_missing` and `unknown_role` are 500 `internal_error`. Check: a table test sends each case to each route and checks the status and the code: no session, an unknown conversation, a private channel, a DM and a group of which the caller is not a member (the same body as an unknown id), a public channel the caller has not joined, an archived channel, a malformed id; each refusal compares the tables `message_pins`, `messages` and `events` before and after.
- R5. Locks for pin and unpin. A pin and an unpin each run in one transaction at `READ COMMITTED` and follow the steps of TOKI-037 R8 in the same order, as TOKI-045, TOKI-046 and TOKI-047 do in their own routes: (1) the account rows `FOR SHARE`, in id order in one statement: the actor and, in a `dm`, the other person, so that the read-only rule of R6 step (4) reads a status that is locked; (2) the conversation row `FOR SHARE` (`FOR NO KEY UPDATE` for a `dm`); (3) the facts are read again and `canReadConversation` and `canPinMessage` are called with what the locks returned. The steps are written in `pins.ts`; this ticket moves no code out of the send and creates no shared lock file, and if TOKI-037 builds a function for them on `main` the pin calls it. For a pin, R6 adds one more lock, the message row, after these. After the locks the transaction takes no lock that can wait, except the counter lock of the event handler, which comes last (TOKI-036 R18), and, for two pins of one message, the wait of the second insert on the unique-index entry of the first, which ends when the first commits. The lock excludes a leave, an archive and a removal that commit first, so a pin is never stored in a conversation that was archived by an earlier commit or for a person who has left. The lock order of the four write routes is the same: account, conversation row, message row, counter. Check, with two real connections, the second waiting and the result read after the first commits and never by sleeping: a pin and an archive at the same moment end either with the message pinned and then the channel archived, or with the pin refused 409 `channel_archived`; a pin and the leave of the same person end with a pin by a person who was still a member or with a refused request (404 or 403, as the facts say), never with a pin by a person who has no member row after both; two pins of different messages in one channel do not wait on each other; two pins of one message end with one row and one `changed` true; the isolation level read inside the transaction is `read committed`; a pin and a send in one channel finish with no deadlock (SQLSTATE `40P01`); the statement log of a pin in a `dm` shows the account lock of both people in one statement.
- R6. Pin: `PUT /api/v1/conversations/{id}/pins/{messageId}`, no body. After R4 and R5: (4) the read-only rule for a direct message with a deactivated person (concern 4); (5) the message row is read with `where id = $messageId and conversation_id = $id for share` (a lock taken after the conversation row, as TOKI-046 R6 does, which excludes a delete of that message, `FOR NO KEY UPDATE` in TOKI-047 R9, and an edit, and does not exclude another pin or a reaction): no row, or `deleted_at` set, is 404 `not_found`; a system line, or a reply that is not also in the channel, is 409 `message_not_pinnable` (a code that this ticket adds, R10); (6) the time `at` is read once from the clock of TOKI-008, after the locks, and `insert into message_pins (message_id, workspace_id, conversation_id, pinned_by, pinned_at) ... on conflict (message_id) do nothing returning *`. Because the row is locked and its `deleted_at` was read under the lock, the trigger of R2 cannot see a deleted message here, and a pin of a message that is deleted in the same moment is either stored before the delete (and the delete then wins: the pin row stays and is left out of every read, R2) or refused 404. It answers 200 with `{ "message": MessageEntry, "changed": boolean }`, `message` being the entry built by the builder of R3 after the insert, with `pinned` filled. When the insert returned a row, `changed` is true, `pinned.by` is the actor and `pinned.at` is `at`, and the transaction calls `recordChange(tx, change)` once as its last statement, with `type` `message_pinned`, `actorId`, `conversationId`, `messageId`, `at` and `target` (the entry just returned), R9. When the message was already pinned, by the actor or by anyone, nothing is written: `changed` is false, `message.pinned` is the stored pin (the first one), and `recordChange` is called zero times, so a double press, a retry and two tabs make one pin, one line and one event. A pin answer therefore never has `changed` true and `pinned` null. The pin of someone else's message and of one's own message are the same request (AC-096). Check: Sam pins Mai's message in a private channel and the answer is 200 with `changed` true and the entry's `pinned` equal to Sam and `at`; the same request again is 200 with `changed` false, the same `pinned`, one row, one system line and no second event; Mai pins the message Sam already pinned and gets Sam's pin back; a Member and an Admin who are members can pin, an Admin who is not a member of a private channel gets 404 and pins nothing (D-047); a 409 `message_not_pinnable` for a system line and for a reply with `also_in_channel` false; a 404 for a message of another conversation and for a deleted message; a rollback after the insert (a failing handler) leaves no pin, no line and no event; the statement log shows the account lock, the conversation lock and the message lock before the insert; with two real connections, a pin and a delete of the same message end either with the message deleted and no pin answer of `changed` true that has `pinned` null, or with the pin refused 404, and in no run with a database error from the trigger of R2 or with a `message.pinned` event for a message whose delete committed first.
- R7. Unpin: `DELETE /api/v1/conversations/{id}/pins/{messageId}`. After R4 and R5 and the read-only rule: the message is read with `where id = $messageId and conversation_id = $id`; no row is 404 `not_found`; a deleted message is allowed (its pin row may still exist), so that the row can be removed. `delete from message_pins where message_id = $messageId returning *`. It answers 200 with `{ "messageId": string, "changed": boolean, "at": string }`, `at` being the time read from the clock once for the request, after the locks and the lookup, as ISO 8601. An unpin takes no lock on the message row: it removes a pin row only, and a deleted message must stay unpinnable. When a row was deleted, `changed` is true and the transaction calls `recordChange` once as its last statement with `type` `message_unpinned`, `actorId`, `conversationId`, `messageId` and `at`; when there was no pin, `changed` is false and `recordChange` is called zero times (an unpin of an unpinned message is a repeat, not an error). Any member can unpin any pin, the pinner's or another's (AC-096, TS-150). Check: Mai unpins Sam's pin and the answer is `changed` true, the row is gone and one event is recorded; the same request again is `changed` false and records nothing; an unpin of a message that was never pinned in an existing conversation is 200 `changed` false; an unpin of a deleted message that still has its row removes the row; a message of another conversation is 404; the refusals of R4 apply.
- R8. The list: `GET /api/v1/conversations/{id}/pins` takes `limit` (1 to `MESSAGE_PAGE_MAX`, default `MESSAGE_PAGE_DEFAULT`, the constants of TOKI-037 R22) and, together or not at all, `beforeAt` (ISO 8601 UTC) and `before` (a message id): the position after which the next page starts. One without the other, a bad value and a key other than these three are 400 `validation_failed`. It runs the steps of R4 only and takes no lock: reading is allowed for every member of every kind of conversation, an archived channel included (`canReadConversation`, TOKI-027 R5). It answers 200 with `{ "messages": MessageEntry[], "hasMore": boolean }`: the pinned messages of the conversation whose message has no `deleted_at`, each with `pinned` filled, ordered by (`pinned_at`, `message_id`) from the newest pin to the oldest, a page being the rows strictly after the position `(beforeAt, before)` compared as a pair, with `hasMore` read from one row more than the limit. The page of pin rows is one statement, using `message_pins_conversation_idx`, joined to `messages` for the text; the entries are then built by the builder of R3 (one more statement for the reader), so a page is two statements and not one for each message. There is no limit on the number of pins of a conversation (D-164): the list is paged so that its size is not. Two pins with the same `pinned_at` are ordered by message id, newest id first; they can only be pinned within the same millisecond. Check: a conversation with `2 * MESSAGE_PAGE_MAX + 1` pins (so that the paging is exercised whatever the constants are) is read in pages with the pair of the last entry and returns every pin once, newest first, and a second walk gives the same order, and a walk with `limit` 10 does the same; a page with `hasMore` false at the end; three pins pinned in the order B, A, C come back C, A, B (TS-151 on the server); a deleted message is not listed and an unpinned one is not listed; an archived channel's list is readable by a member and refused for a non-member; `EXPLAIN` with `enable_seqscan` off names `message_pins_conversation_idx` and holds no `Sort` node for the first page and for a page with a position; the statement count of one page is 2; the body is parsed with the response schema of R10.

Changes, the line and the events
- R9. The two changes. `Change` of `conversations/changes.ts` (TOKI-037 R18) gains the types `message_pinned` and `message_unpinned` and the optional fields `messageId` and `target` (a `MessageEntry`); the route sets them as R6 and R7 say. The first handler of the list, the system-line handler of TOKI-037 R16, writes for `message_pinned` one row of `kind` `system`, `system_type` `message_pinned`, `author_id` the actor, `system_user_ids` empty and `created_at` equal to `at`, in the transaction of the change, and returns `{ message }`; it writes nothing for `message_unpinned` (D-165). Both events are written with `at: change.at`, the time of R6 and R7, so the `createdAt` of the event, the `pinned.at` of the answer and the `created_at` of the line are the same value (TOKI-036 R15 gives `recordEvent` the time as `at`); R12 relies on it. The line holds no id of the pinned message: the journey gives a line that says who pinned a message and no link (F17). The last handler of the list, the event handler of TOKI-038 R20, gets two more rows, in `modules/realtime/` and typed with its own structural `EventChange`: `message_pinned` writes `message.pinned`, scope `conversation`, `data` `{ message: change.target }`; `message_unpinned` writes `message.unpinned`, scope `conversation`, `data` `{ conversationId, messageId }`. After the events of the change the handler writes, as TOKI-038 R20 says for every change that carries `change.message`, the `message.created` of the line, so a pin makes two events with consecutive numbers, `message.pinned` and then `message.created`, and an unpin makes one. Both kinds are added to the registry of TOKI-038 R12 with their `data` schemas, and to the table `kinds.ts` of TOKI-038 with a row that changes no map (the test that every registry kind has a row and the reverse stays true). The line is a `system` message: it raises no unread count and notifies nobody (D-100, D-165), by the rule on `kind` that TOKI-053 reads; this ticket counts and notifies nothing. No code of this ticket calls `recordEvent` or `appendEvent` (TOKI-036 R25). Check: a real pin leaves one line row with the type, author and `created_at` above and `system_user_ids` empty, and a recording handler after the line handler receives it as `change.message`; a real unpin leaves no line; with the real event handler the log holds `message.pinned` and then `message.created`, numbered one after the other, and `message.unpinned` for an unpin; `message.pinned.data.message.pinned` equals the stored pin; the `createdAt` of `message.pinned` and of `message.unpinned` equals the `at` of the answer of the same request; a repeat writes no line and no event; a rollback after the line leaves none of the three; a pin line is `kind` `system` and is not a message of `kind` `user`; the registry and `kinds.ts` tests pass with the two new kinds; a search of `apps/server/src` outside `modules/realtime/` finds no call of `recordEvent`.
- R10. `packages/shared` gains, in `src/messages/` and `src/realtime/`: the schema `PinInfoSchema` and the key `pinned` of `MessageEntry` (R3); `PinMessageResponseSchema` (R6), `UnpinMessageResponseSchema` (R7), `ListPinsQuerySchema` and `ListPinsResponseSchema` (R8); `message_pinned` in `SYSTEM_LINE_TYPES` (TOKI-037 R22); the event kinds `message.pinned` and `message.unpinned` with their `data` schemas (TOKI-038 R12); and the error code `messageNotPinnable` (`message_not_pinnable`, 409) in `ErrorCodes`. The server and its tests use the strict schemas; the client reads with the form that drops unknown keys (TOKI-032 R3). Check: schema tests accept a valid body and refuse a missing key, an added key, a non-ISO time and `beforeAt` without `before`; every 200 body of the route tests is parsed with its response schema; the registry has the new code with no duplicate; the two kinds parse a valid `data` and refuse one without `message` or without `messageId`; a type test imports every new name from `@toki/shared`.

Client
- R11. `createApiClient` gains `pins.list(conversationId, query?, signal?)`, `pins.pin(conversationId, messageId, signal?)` and `pins.unpin(conversationId, messageId, signal?)`, with the rules of TOKI-040 R2 (one request core, 10 seconds, no retry, a path part encoded, `signal` last, neither `headers` nor `timeoutMs`). `list` sends `limit`, `beforeAt` and `before` only when given and returns `{ messages, hasMore }`; `pin` sends `PUT` and returns `{ message, changed }`; `unpin` sends `DELETE` and returns `{ messageId, changed, at }`. Each answer is read with the response schema of R10 in the tolerant form. Check, with the fake `fetch` of the API tests: the method, the path with an encoded id, the query and the empty body of each; the answers parse; an unknown key in an answer is dropped; a 409 `channel_archived` and a 409 `message_not_pinnable` reach the caller as the `ApiError` of TOKI-032 R4 with the code.
- R12. The store of pinned lists: `createPinsStore({ conversations, api, sync })` of `packages/client-core/src/pins/`, exported from the package index with its types; `sync` is the engine of TOKI-040. It holds no text and uses no browser API, no `Date.now(` or `new Date()` and no timer (TOKI-008 R19). For each conversation it holds a `PinList`: `{ status, error, items, hasMore, isLoadingMore, isRefreshing }`, `status` being `idle` (never loaded), `loading` (the first load, no item held), `ready` or `failed` (only while no item is held); `items` is the pinned `MessageEntry` of the conversation, newest pin first, ordered like R8 by (`pinned.at`, `id`) descending; the list is replaced, never changed in place, so two reads with no change between return the same object. Methods: `getPins(id)` and `subscribePins(id, listener)` (one conversation's changes only); `loadPins(id)` requests the first page and replaces the held items with it, keeps the held items on screen while it runs (`isRefreshing`), and never rejects (the outcome is read from the list); `loadMorePins(id)` requests the page after the last held entry with `beforeAt` and `before`, does nothing when `hasMore` is false or a load runs, and adds the page; `pin(id, messageId)` and `unpin(id, messageId)` call the API and return its answer, reject with the `ApiError` on failure and apply the answer (below); `patchPinned(id, messageId, update)` and `removePinned(id, messageId)` change or drop one held entry, a no-op when it is not held; the store's own handlers (R13) call them and no other ticket does. The rule of last write by server time (decided in this spec). Every time in it is a server time and the same value for the answer and the event of one change (R9). ## Design
### Where a pin is stored
Decided in this spec (concern 2): a table of its own, one row per pinned message, and not two columns on `messages`.
- The message table of TOKI-036 is "exactly these columns" in its own test and its trigger `messages_immutable_trg` lists the columns that may change; a pin on it would change both, and a pin is not a property of what was written but of how the conversation uses it.
- An unpin is a delete of a row; no column is set back to null, and nothing keeps a history of unpins (D-165 gives no line for it).
- The list is one index of the pin table, ordered by the time of the pin, and joins the message by its primary key; the main-list index of messages is untouched.
- Reactions are a table of their own for the same reason (technical design, table groups).
The cost is one extra statement, the reader of R3, for a page or an answer; the main-list queries are untouched.

### API
All routes need a session (R4). Bodies are JSON; pin and unpin have none.

| Method | Path | Who | Purpose |
| :---- | :---- | :---- | :---- |
| PUT | `/api/v1/conversations/{id}/pins/{messageId}` | members of a conversation that is not archived | Pin; 200 with `changed` true or false (R6) |
| DELETE | `/api/v1/conversations/{id}/pins/{messageId}` | members of a conversation that is not archived | Unpin; 200 with `changed` true or false (R7) |
| GET | `/api/v1/conversations/{id}/pins` | members, any state | The pinned messages, newest pin first, paged (R8) |

| Status | `error.code` | When |
| :---- | :---- | :---- |
| 200 | none | Done, or nothing to do (`changed` false); a page of the list |
| 400 | `validation_failed` | A path, query or id fails its schema (R4, R8) |
| 401 | as TOKI-022 | No valid session, or the locked actor was deactivated |
| 403 | `forbidden` | A person who is not a member of a public channel (R4) |
| 404 | `not_found` | Unknown conversation; a private channel, DM or group the person is not in; a message that is not in the conversation, or is deleted (pin) (R4, R6, R7) |
| 409 | `channel_archived` | Pin or unpin in an archived channel (R4) |
| 409 | `conversation_read_only` | Pin or unpin in a DM with a deactivated person, as proposed in concern 4 |
| 409 | `message_not_pinnable` | A system line, or a reply that is not also in the channel (R6) |
| 500 | `internal_error` | A server failure, or `fact_missing` or `unknown_role` from a function |

A pin and an unpin are idempotent: `PUT` of a pinned message and `DELETE` of an unpinned one answer 200 and write nothing, so a retry after a lost answer is safe and needs no id from the client. A 409 means the screen was out of date; the client reloads the list (D-131).

### What a person sees, in order
A person opens the More menu of a message, which TOKI-052 draws with the item that `usePinActions` describes, and presses 'Pin to conversation'. The request goes to the server and nothing changes on screen yet. The answer arrives, the toast 'Pinned to conversation' with Undo shows for 5 seconds, the store puts the entry in its place in the list and sets `pinned` on the message in the window, so the label appears, and the event that follows changes nothing more. The same moment the server's events reach every member: `message.pinned` sets the label and the entry on their screens, and `message.created` brings the line "Sam pinned a message". Pressing Undo calls unpin, the label and the entry go, and no line is added for the unpin (D-165). The earlier line stays (concern 5).

### Reading the Pinned tab
The tab calls `loadPins` each time it is opened, so it starts from the server. While it is open the events keep it current, by the rule of last write by server time (R12), and an entry that is deleted or edited is changed by this store's own handlers for `message.edited` and `message.deleted` (R13). Pressing an entry calls `onOpenMessage`; the row of TOKI-041 selects the Messages tab and opens the conversation at that message with `loadAround` of TOKI-040 (TOKI-037 R13).

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- A pin is a row of its own table (above, concern 2).
- Pin and unpin are idempotent `PUT` and `DELETE`, with `changed` in the answer, so a repeat writes no line and no event (R6, R7).
- The list is read by the position `(beforeAt, before)` as a pair, so unpinning the last entry between two pages does not break the next page (R8).
- Nothing is changed on screen before the server answers; the effect is "at once" in that there is no confirmation, as `useUndo` does it (R14, TOKI-093).
- The log decides: events are always applied, and an answer only when its server time is later than the last change seen (R12).
- The Pinned tab always starts from a request and is kept current by events while open (R15).

## Data safety
- A pin is visible to the members of its conversation only. A private channel, a DM and a group answer 404 to anyone else, with the same body as for an id that does not exist; a public channel answers 403 to a non-member and returns nothing of it (R4).
- Every read goes through `getConversationFacts` and the permission function, never through a query on the pin table alone (R4).
- The log holds no text of a message, no name and no list of people (R20). The event `message.pinned` carries the message as the history does, and the log follows the retention of TOKI-036 R20.
- Tests use made-up texts and generated ids.

## Areas of concern
1. Who draws the tab row and the Pinned tab. Decided by the product owner in TOKI-035 concern 7 (2026-11-20): TOKI-041 draws the row with the Messages tab and the later tickets add theirs. Decided in this spec for this ticket: it draws the Pinned tab (its panel and its description, R15, R16) and adds `pinnedTab` to the array `conversationTabs`; the row is not part of it. Confirmed in TOKI-041 R4 (PR 218), which reads the form `{ id, labelKey, Panel }`, passes `onOpenMessage` and asks for the edge `TOKI-048 needs: TOKI-041`. The archived page: TOKI-041 R3 gives it no tab row (its concern 2, a reading: no decision puts the other tabs on it), so this ticket adds no Pinned tab there, though the server lists the pins of an archived channel to a member (R8). If the owner wants the tab on the archived page, TOKI-041 R3 changes and this ticket's `PinnedTab` needs no change. Owner: Thanh Truong.
2. Where a pin is stored. Decided in this spec: a table `message_pins` with one row per pinned message, not two columns on `messages`. Reason: the message table is fixed by its own tests and trigger, an unpin is a delete, and the list is one index (Design, "Where a pin is stored"). Owner: Thanh Truong.
3. What the pin may hold, for a message that is a root or a reply. Decided in this spec, reading D-166 ("only messages in the main list can be pinned", the reply inside a thread cannot) with the definition of the table (TOKI-036 R11, D-160): a root message and a reply that was also sent to the channel (D-160) can be pinned, and a reply that was not cannot (409 `message_not_pinnable`). Reason: a reply sent also to the channel is shown in the main list as a message. If the owner wants roots only, the trigger of R2 and R6 change. The system line is not part of this decision: concern 11. Owner: Thanh Truong.
4. A pin or an unpin in a direct message with a deactivated person. Not decided. F41 and D-091 make that direct message read-only and the log does not say whether a pin is a write that it blocks; `canPinMessage` (TOKI-027 R6) only knows archived channels. Proposal, not a decision: refuse both with 409 `conversation_read_only`, the code of TOKI-037 R7, because the conversation is read-only and the Pinned tab stays readable; the code of R6 and R7 builds this proposal until the owner answers, and the only places that change are step (4) of R6, the same step of R7 and the table of statuses. Owner: Thanh Truong (product owner).
5. What Undo does to the line and to the place. Not decided. AC-098 says Undo puts the message back in its earlier state; D-165 gives no line for an unpin, and TOKI-093 concern 9 leaves open whether an undone pin removes its line, adds a second one or leaves both. Undo is a second call (TOKI-093), so this ticket builds: Undo of a pin unpins and leaves the line it added; Undo of an unpin pins again, which takes a new time (the message goes to the top of the tab, not back to its old place) and adds a second line. Proposal, not a decision: Undo of a pin leaves the line, because the line is the record that a person pinned; Undo of an unpin restores the old pin time and adds no line, which needs a way to send the old time (a body on `PUT`) that this spec does not add. Owner: Thanh Truong (product owner).
6. The two-browser journeys and the menu. Decided in this spec: the tests of TS-149 to TS-153 are written at the level of requests, list and hook in this ticket, and the browser versions are written by TOKI-052 with the menu (Testing); the menu item and its place in the menu are TOKI-052's, and the hook is the contract between the two (R14). Owner: Thanh Truong.
7. What the line names. Decided in this spec: the line `message_pinned` holds the person who pinned and no id of the message, because F17 words the line as "who pinned a message" and gives it no link; a link would add a message id to a line that is stored as a type and people (TOKI-036 R3). The words of the line are TOKI-042's. Owner: Thanh Truong.
8. The size of a page of the list. Decided in this spec: the list uses the constants `MESSAGE_PAGE_DEFAULT` and `MESSAGE_PAGE_MAX` of TOKI-037, and its tests read the constants, not a number; their values are TOKI-037 concern 1 and are not set here. Owner: Thanh Truong.
9. Order inside one millisecond, a late answer and a page read before an event. Decided in this spec: pins are ordered by the server's `pinned_at` and then by message id (R8); the client applies every event, because the log is in commit order, and an answer only when its server time is later than the last change seen (R12), and it inserts by the same order as the server. Two pins of one conversation in the same millisecond are ordered by id, which no person sees. A `message.pinned` event, or an answer, that arrives while a page request of the window of TOKI-040 is running is not lost for the window: the engine journals every patch during a load and applies it again to the page before the merge (TOKI-040 R5 and its concern 10), which is why the updates of R12 are pure and repeatable; and an edit or a delete written into a held message by `applyMessageChange` (TOKI-047 R14) replaces only its own keys, so it cannot drop the label. Known limit, accepted as technical: the open Pinned tab is not told when the engine reloads after a missed range that is too old (R13). Owner: Thanh Truong.
10. Code of other tickets that this ticket changes. Decided in this spec: it edits no other spec; it adds the reader `listPinned` that the builder of TOKI-037 calls, `Change`, `SYSTEM_LINE_TYPES` and the system-line handler, the event handler and `kinds.ts` of TOKI-038, and one entry in the array of TOKI-041 (R3, R9, R16), each with its own tests. It does not move the locks of the send (R5). If a ticket that is built first has already made one of these in another shape, this ticket follows what is on `main`. Owner: Thanh Truong.
11. Whether a system line can be pinned. Not decided. D-166 says only a message of the main list can be pinned, and the main list of TOKI-036 R11 holds system lines too; no decision in the log says whether the grey line "Lan pinned a message" or "Sam joined" can carry a pin. Proposal, not a decision: it cannot (R2 and R6 refuse it with 409 `message_not_pinnable`), because a system line has no sender and no text to keep and the Pinned tab draws an author and a text; if the owner allows it, the trigger of R2, `isPinnable` (R14) and the entry of R15 change. Owner: Thanh Truong (product owner).
