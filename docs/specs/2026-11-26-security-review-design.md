# Security review design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/security-review.md (Thanh Truong)
Ticket: TOKI-091

## Goal
Toki goes onto the public internet for about 200 people. This work reads the security choices of the finished specs together, against the code on `main`, for four things: headers, cookies, rate limits and dependencies. It records what it finds in one file, builds what the findings call for (a Content-Security-Policy, limits for the routes that have none, a body size limit, an advisory check, pinned workflow actions) and adds tests so that routes and packages added later stay inside the same rules. Three findings need a product decision (the guessing budget, the text of a refusal, the shared office address) and are carried as concerns.

## Scope
- In:
  - The review: a checklist of items, each with its source, and the record of findings, `docs/security/review.md` (R1, R2).
  - Headers: the Content-Security-Policy, `Permissions-Policy` and `Cross-Origin-Opener-Policy` of the app host in `infra/Caddyfile`; the default `Cache-Control` of the API (R3, R4, R7); the proof of the policy in a real browser (R5).
  - Cookies and cross-site requests: the browser proof of the cookie (R6), the cross-site cases for every route that is not a `GET` (R16), and the proof that no `GET` route changes anything (R17).
  - Rate limits: one limiter for every limit, the address key, the three Join routes, failed sign-in checks, signed-in people by route class, the body size (R8 to R15), and the address that the proxy forwards (R18).
  - Dependencies: exact versions (the nine ranges of `apps/web/package.json` are pinned here), the advisory check, install scripts, pinned workflow actions (R19 to R22).
  - What the sibling specs hand to this review and nobody else takes: the deploy key, the Docker group, the Actions permissions, the Environment branch rule, the exposed SSH port and the public run log of TOKI-085 (rows D9, D10, H12), and the weighing of a storage host on the same site, which TOKI-084 concern 1 leaves here (row S8, concern 8). Out lists what is not taken, so TOKI-084, TOKI-085 and this spec draw the same line.
- Out (not now):
  - Authorization: who may read or change what, and the same answer for every outsider. That is TOKI-088 (its registry, its fixture and its refusals). This work asks how often and how much, and which headers and cookies; it never asks who is allowed. Where it reuses the registry of TOKI-088 it uses its requests and its route table and adds no authorization case (concern 5).
  - The content of the screens for a refused request: the text of `rate_limited` on sign-in and Join is open (concern 2); the screens belong to TOKI-023 and TOKI-097.
  - A virus scan (D-186), a quota on storage (NFR-15), a web application firewall, intrusion detection, a penetration test by a third party, and a vulnerability-disclosure page. Not asked by the log; each would be a new decision.
  - Signing or attesting the images, scanning them for known flaws (TOKI-085 hands both here), a scan of the operating-system packages inside the images and a licence review: not taken in this phase (concern 7). TOKI-085 is told in Plan changes.
  - The headers of TOKI-084 R20 and the Caddyfile outside the header block of this work; backup (D-092).
  - A limit shared by several processes or machines: the limits count in the memory of the one server process (concern 6).

## Requirements
### The review and its record
- R1. The record. `docs/security/review.md` holds one table with one row for each item of Table C (below), with the columns `id`, `area`, `checked`, `source`, `result` and `evidence`. `result` is one of `pass`, `fixed`, `accepted` and `open`. A `fixed` row names the requirement of this spec and the test that proves it; an `accepted` row names the decision that accepts the risk (a D-number, an NFR, or a concern of a merged spec); an `open` row names a concern of this spec or an issue of the repository. The file also holds the known findings F1 to F10 of Table D with the result and the reference written in that table, and one line at the top with the commit of `main` that the review read. The review is made against the built code, not only the specs: a row says what was read (a file and a line range, or a request that was sent). Check: R2.
- R2. The check of the record. `tools/security/findings.test.mjs` (Node test runner, run by `pnpm test`) reads `docs/security/review.md` and `Table C` of this spec and fails on: an item of Table C with no row; a row with a `result` that is not one of the four; a `fixed` row whose named test file does not exist; an `open` or `accepted` row with no reference; a `source` that names a path of the repository that does not exist; a known finding F1 to F10 with no row. Check: a fixture file with each of the six faults, each failing with its own message, and the real file passing.

### Headers
- R3. The Content-Security-Policy. The Caddyfile sets `Content-Security-Policy` on every answer of the app host that is not under `/api/*` or `/ws`: the classes (2) to (7) of TOKI-084 R16 and the 404s of them, that is the 404 of `/healthz`, the manifest, the icons, `/push-sw.js`, `/assets/*`, and `index.html` with the single-page fallback (`/`, `/c/<id>`, `/login`, `/emergency`), which is the document whose policy matters; and any other file copied from `public/`, such as `/first-paint.js` of TOKI-078 R8. It sits in the one header block that TOKI-084 R20 reserved. The value is the policy of the table "Content-Security-Policy" below, with `{$APP_DOMAIN}` and `{$STORAGE_DOMAIN}` taken from the environment of Caddy. It holds no `unsafe-inline`, no `unsafe-eval`, no `*` and no `http:`; `default-src` is `'none'`, so every kind of load that the table does not name is refused: the notification sound needs `media-src 'self'` because `default-src 'none'` would refuse every `play()` of it (TOKI-075 R1, R3; `packages/platform/src/web/sound.ts`). The answers of the API are not given the header, so the `sandbox` policy that the thumbnail route sets for itself (TOKI-060 R8) is never replaced. Check: `tools/security/csp.test.mjs` reads the value from the Caddyfile, parses it into directives (a name and a list of sources) and fails when a directive of the table is missing or differs, when a forbidden source is present, or when a directive not in the table is present; it reads the adapted configuration (`caddy adapt`, the command that TOKI-084 R16 already uses for its matcher test) and fails, naming the class, when the route that answers `index.html` and the single-page fallback (class 7) or any of the classes (2) to (6) has no `Content-Security-Policy`, so a policy on the manifest and the icons and none on the page cannot pass; a negative control feeds it a value with `'unsafe-inline'` in `script-src`, one with no `media-src`, and a Caddyfile whose header block skips the fallback, and expects the failure of each. The browser proof is R5.
- R4. Two more headers on the app host, on the same answers as R3: `Permissions-Policy: accelerometer=(), camera=(), geolocation=(), gyroscope=(), microphone=(), payment=(), usb=()` (the browser features Toki never uses) and `Cross-Origin-Opener-Policy: same-origin`. The storage host gets neither. Check: the same Caddyfile parse as R3; R5 reads both headers on `/`.
- R5. The policy in a real browser. `tools/stack/browser/security.mjs` (Playwright library, Chromium, run by `tools/stack/check.sh` of TOKI-084 after its own checks, one added line there) opens the production stack of TOKI-084 and signs in with the one-time link that TOKI-084 R25 prints, with the notification permission granted to the context. It then: (a) visits the screens of the web app (the first screen, the open conversation, Preferences, the Admin page, the people list, the search palette); (b) sends a message, picks a small PNG and sends it (the XHR to the storage host, the thumbnail from `/api/v1/files/<id>/thumbnail`, the download link) and keeps the WebSocket open; (c) presses once on the page, which unlocks the sound (TOKI-075 R3), and then a second signed-in member, in another context, posts in a conversation that the first does not have open, so a notice plays the sound; the check reads that the file `notification-*.wav` was answered 200 after the press and again after the notice; (d) registers `/push-sw.js` the way the app does when push is turned on (or, when the app registers it only at the subscription, by `navigator.serviceWorker.register("/push-sw.js")` in the page) and reads that `context.serviceWorkers()` holds it; the subscription to a push service is not proved, it needs the internet; (e) reads the manifest through the DevTools protocol (`Page.getAppManifest`) and finds no error; (f) runs the deny probes: the page inserts an `<iframe src="/">`, an `<object data="/x">`, a `<base href="https://other.test/">` and submits a form whose action is `https://other.test/`, and a page of another origin served by `page.route` embeds the app in a frame; each must be refused and produce a violation of its directive (`frame-src`, `object-src`, `base-uri`, `form-action`, `frame-ancestors`), recorded apart as expected. During the whole run a listener records each `securitypolicyviolation` event and each console message that names the policy. Pass means: none except the probes of (f), every directive of the table proved by something the run did or refused (script, style, image, font, connect to the API, the storage host and the socket, worker, manifest, media), and the headers of R3 and R4 on `/` as served, not as written. Negative controls, each the same run with the `Content-Security-Policy` of the document answer rewritten by `page.route`: without the storage host in `connect-src`, the upload records a violation; without `media-src`, the sound file records a `media-src` violation and no 200; with `worker-src 'none'`, the registration records a `worker-src` violation and `context.serviceWorkers()` is empty. So the listener is shown to see a violation of three different directives. The by-hand run in Firefox and Safari (concern 4) is recorded in the pull request.
- R7. The default `Cache-Control` of the API. One `onSend` hook on the root application, not in the `/api/v1` plugin (the not-found handler `setNotFoundHandler` of `errors.ts` and the auth hooks are on the root, so a hook inside the scope would not run for an unmatched `/api/v1/x`), applies when `isApiPath(url)` of `modules/auth/guards.ts` (the guard that `register.ts` already uses) is true, so `/healthz` and `/ws` are outside. It sets `Cache-Control: no-store` on every answer that has no `Cache-Control` of its own, errors and `404` included. Routes that set their own keep it: `private, no-store` of the download redirect (TOKI-058 R12), the validators of the thumbnail (TOKI-060 R8), `no-store` of `/bootstrap`. Reason: today only `/bootstrap` sets one (`apps/server/src/bootstrap/routes.ts`), so the answer of any other route is left to the browser's own rules. Check: a `GET`, a `POST`, a 401 and a 404 for an unmatched `/api/v1/x` carry `no-store`; `GET /healthz` is given none by this hook; the three routes named keep their own value.

### Cookies and cross-site requests
- R6. The cookie in a real browser. In the same run as R5, after the sign-in, `context.cookies()` holds exactly one cookie of the app host, named `__Host-toki_session`, with `httpOnly`, `secure`, `sameSite` `Lax`, path `/`, no `domain` attribute (a host-only cookie) and an expiry about 30 days ahead (TOKI-022 R21); `document.cookie` does not show it; the request that uploads to the storage host carries no `Cookie` header (`request.allHeaders()`); after sign-out the cookie is gone and the next `GET /api/v1/auth/session` answers 401. Check: the run; a negative control that adds a cookie with `domain` set through `context.addCookies` and expects the check to name it.
- R16. Cross-site requests, for every route. `apps/server/tests/security/csrf.db.test.ts` (the database project, TOKI-008) takes the route table of TOKI-088 R2 and, for every route whose method is not `GET`, `HEAD` or `OPTIONS` (the public routes included), sends the valid request of its entry in the registry of TOKI-088 R1 (`request(world, target)`) with the header `Origin: https://other.test`, and again with `Origin: https://storage.<the app domain>` (a sibling host of the same site, which `SameSite` does not separate from the app, so only the `Origin` rule does): the answer is 403 `origin_not_allowed` and the watch set of TOKI-088 R16 is unchanged; then with a valid `Origin` and `Content-Type: text/plain` on a route that has a body: 415 `unsupported_media_type` and the watch set unchanged. No answer of any route carries an `Access-Control-` header. Check: the test itself, with a control per case (the same request with the app's own origin and JSON succeeds or is refused for its own reason); a route that is not in the registry fails TOKI-088 R3 first.
- R17. No `GET` changes anything. `apps/server/tests/security/get-safe.db.test.ts` sends the valid request of each `GET` entry of the registry (and `GET /ws` without an upgrade) as its control person and compares the watch set of TOKI-088 R16, plus the columns of `users` and `sessions` other than `last_used_at` (the only write a request makes by design, TOKI-022 R25), before and after. All equal. Check: the test, and a negative control that registers a `GET` route which inserts a row and expects the test to fail on it.

### Rate limits and sizes
- R8. One limiter. `apps/server/src/modules/auth/limiter.ts` exports `createLimiter(clock, { max, windowSeconds, maxKeys })`, the one function that every limit of this spec and of TOKI-022 R56 and TOKI-026 R49 uses; `createAddressLimiter` becomes a call of it with `CODE_IP_REQUESTS_MAX`, `CODE_REQUESTS_WINDOW_SECONDS` and `LIMITER_MAX_KEYS`, and every existing test of R56 and R49 passes unchanged. `hit(key)` has the behaviour of R56: a request that reaches it is counted, a request it refuses leaves no entry, and the answer is `null` or the whole seconds to wait, at least 1. The limiter also has `clear()`, which a test calls to empty every counter (TOKI-090 R5 uses it, Plan changes). The map holds at most `maxKeys` keys (`LIMITER_MAX_KEYS`, 50,000): when a new key would pass it, expired keys are removed first and, if the map is still full, the key with the oldest last hit is removed. The new key is never refused (concern 12): a refusal would let anyone who sends one request from 50,000 different `/64` networks stop every real person from signing in, while an eviction costs the attacker 50,000 requests to push its own key out and reset a count of at most 20, and an attacker that owns 50,000 networks already holds 50,000 counters of its own (concern 1). 50,000 keys is about 80 times the keys that 200 people make (3 sign-in routes and 3 Join routes, a few addresses each) and is a size of memory (about 5 MB) and not a figure about people. Check: tests with the controllable clock of TOKI-008, no real timer: the Nth and the N+1th hit; the wait; a refused hit leaves no entry; the window slides; 50,001 distinct keys leave 50,000 and the one removed is the oldest; the attacker case: a key that has 20 hits, then 50,000 other keys, is evicted and its next hit counts as the first, and the 200 keys of real people that were hit after it are all still held; `clear()` empties the map.
- R9. The address that is counted. The key of every limit by network address is the address of `request.ip` reduced by `limitAddress(ip)`, which is in `packages/shared`: an IPv4 address is kept; an IPv4-mapped IPv6 address (`::ffff:a.b.c.d`) becomes the IPv4 address; any other IPv6 address becomes its first 64 bits written as four groups of lower-case hexadecimal, so all addresses of one `/64` count as one. Reason: one subscriber is given a whole `/64`, so a limit by full address is passed by changing the last 64 bits. TOKI-022 R56 and TOKI-026 R49 use this key; nothing else of them changes. Check: a table test (IPv4; mapped; two IPv6 addresses of one `/64` equal; two of different `/64` different; compressed and expanded forms of one address equal; upper case; the hex form of a mapped address `::ffff:102:304`, which becomes `1.2.3.4`; an address with a zone id `fe80::1%eth0`, which is read without the zone) and a limiter test where the 21st request from a second address of the same `/64` is refused.
- R10. The Join routes. `POST /api/v1/invitations/lookup`, `POST /api/v1/invitations/codes` and `POST /api/v1/invitations/sessions` (TOKI-097 R1, R6, R10) join the set of routes that the address limit counts, each with a counter of its own, checked first and counted as TOKI-022 R56 says. No requirement decides a figure for them: TOKI-022 R56 decided 20 per 15 minutes for the two sign-in routes only, and TOKI-026 R49 for the emergency route. This work proposes the same 20 for `codes` and `sessions` (`CODE_IP_REQUESTS_MAX`, a starting value: the same two actions as sign-in, with the same counts of codes and tries behind them) and 60 for `lookup` (`JOIN_LOOKUP_IP_REQUESTS_MAX`, a starting value, which sends no mail and writes nothing, because several people invited on the same day may open their links from one office); both are proposals, concern 3. The set is a table `LIMITED_ROUTES` of `route -> { max, windowSeconds }` in `modules/auth/`, replacing the `Set` of `register.ts`. Check: for each route the Nth request is answered by the route's own rule and the N+1th is 429 `rate_limited` with `details.retryAfterSeconds` and `Retry-After`, a valid token in the refused request is not used, the counters of the three routes are separate from each other and from the sign-in routes, and after 15 minutes of the test clock the same address is accepted.
- R11. Failed sign-in checks, by address. A request to a route that needs a session whose check finds no session at all (401 `unauthenticated`: no cookie or bearer secret, or one that matches no session), and a handshake of `GET /ws` whose check fails the same way (the upgrade completes and the connection is closed with 4401, TOKI-038 R3), is counted for its address. A 401 `session_ended` or `account_deactivated` is not counted: it is the answer to a real person whose session ended, who is then sent to sign in once, and counting it would let one colleague's ended session use up the count of the whole office. When an address has `FAILED_AUTH_MAX` (60, concern 3) counted failures in the last `FAILED_AUTH_WINDOW_SECONDS` (60), the next request to such a route is refused with 429 `rate_limited` before the session is read from the database, and the refused request is not counted. A handshake of `GET /ws` is refused with the HTTP status 429 before the upgrade: a browser reports that as a failed handshake with no close code (1006), and the close table of TOKI-039 R12 already treats a failed handshake that way, so the client retries with its backoff (1, 2, 5, 10, 30 seconds, D-129) and is accepted when the minute is over; nothing else of the client changes. Reason: today each request with an unknown cookie costs one database read at no price to the sender. A request that passes the check is never counted. The named cost (concern 3): while an address is over the count, a valid session from that address is refused too, so anyone on a shared address (the office, a carrier's NAT, one IPv6 `/64` under R9) who sends 60 requests with a bad cookie in a minute stops every colleague on that address from using the API until the minute ends, and can repeat it. The alternative, to let a valid session through, needs the session read that this limit exists to avoid (or a cache of valid sessions, which is new state), and is not taken. Check: 60 requests with an unknown cookie from one address are answered 401, the 61st is 429 and the fake database records no session read for it; a request with the cookie of an ended session or a deactivated account is answered 401 and adds nothing to the count; a second address is not limited; a valid session from the limited address is also refused for that minute (the named cost); after 60 seconds of the test clock the address is accepted; a handshake closed with 4401 `unauthenticated` counts in the same counter, and the 61st handshake is answered 429 with no upgrade.
- R12. Signed-in people, by class. After the session check, every request to a route that needs a session is counted for the account (`request.account.id`, not the address, because many people share an office address) in the class of its route, and when the class is full the request is refused with 429 `rate_limited`. The classes and their starting values (concern 3) are in the table "Limits by class" below and in `packages/shared/src/limits/classes.ts`, which exports `LIMIT_CLASSES` (`{ write, read, heavy }`, each `{ max, windowSeconds }`), the name that TOKI-089 R13 reads for its spacing. The class of a route is `write` for a method other than `GET` and `HEAD`, `read` for those two, and the route may name another in its definition with `config: { limitClass: "heavy" }`; no route may switch its limit off, and `/healthz` and `GET /ws` are outside the classes (the first needs no session; the second has the limits of TOKI-038 R10, R19, R24 and R25). A request is counted in one class only: a `heavy` request uses the `heavy` counter and not the `read` counter, so `/bootstrap` and a series of searches do not use up the 600 of `read`. The thumbnail and the download redirect are `read` requests, one for each image card or file opened: a person who scrolls fast through a channel of images can make about 10 a second, which is the 600 a minute; TOKI-089 is asked to include an image-heavy scroll in its 200-person run (Plan changes). Check: with the test clock, the Nth request of each class passes and the N+1th is 429; a request of another person is not affected; a `write` does not use up the `read` counter, a `heavy` request does not use it either and a `read` request does not use up `heavy`; after the window the same person is accepted; a refused request is not counted.
- R13. Every route has a class, and the overrides are a visible list. `apps/server/tests/security/limit-classes.test.ts` takes the route table of TOKI-088 R2, which keeps the whole `config` of each route (a change request to TOKI-088, Plan changes), resolves the class of each route that needs a session as R12 does (`config.limitClass` when present, else by the method), and fails when a route names a class that does not exist in `classes.ts` or when the set of routes that name a class themselves differs from the list written in the test (`heavy`: `GET /api/v1/bootstrap`, `GET /api/v1/search`, `GET /api/v1/conversations/:id/search`, `GET /api/v1/shared-items`; the list is closed, so a ticket that adds a `heavy` route edits it in its own change). A public route is checked by R10 and its row in `LIMITED_ROUTES`, not by a class: the test fails on a route with `config.public` true that has neither a `LIMITED_ROUTES` entry nor a `reason` in its TOKI-088 entry that says why it needs no limit. Check: the test, with a fixture route that names an unknown class, one that adds an override and one public route with no entry, each failing.
- R14. The size of a body, by class of route. Two constants in `packages/shared/src/limits/`: `BODY_LIMIT_BYTES` = 262,144 and `BODY_LIMIT_DRAFT_BYTES` = 1,201,024 (`DRAFT_TEXT_MAX * 12 + 1,024`; a test recomputes it from `DRAFT_TEXT_MAX`, so the two cannot drift). `buildApp` passes `bodyLimit: BODY_LIMIT_BYTES` to Fastify, and the route `PUT /api/v1/drafts/:kind/:id` (TOKI-051 R3) gives itself `bodyLimit: BODY_LIMIT_DRAFT_BYTES`. A body above the limit of its route is refused with 413 `payload_too_large` before the route runs, and writes nothing. The arithmetic, in bytes of the JSON text: a character written as it is takes 1 byte (ASCII), 2 or 3 (a Vietnamese letter with marks is 2 to 3) or 4 (an emoji outside the basic plane); a sender may also write each code point as `\u` escapes, 6 bytes for one and 12 for an emoji (a pair). Messages and every route that is not a draft: the largest text is a message of 10,000 code points (TOKI-037 R4), 40,000 bytes of literal emoji and 120,000 bytes escaped; an invitation batch is 50 addresses of at most 254 characters (D-134), 12,700 characters, 152,400 bytes at the worst; so 262,144 holds each with room. A draft takes `text` up to `DRAFT_TEXT_MAX` = 100,000 code points (TOKI-051 R2): 300,000 bytes in Vietnamese, 400,000 in literal emoji, 1,200,000 escaped, and 11 bytes of `{"text":""}` around it, so 1,200,011 at the worst and 1,201,024 allows it. Fastify's own default is 1 MiB (1,048,576), below that worst case, and was never set. Files are not a class here: a file goes to the storage host with the size rule of its upload ticket (TOKI-058 R7, 100 MB, D-014), and no route of the server receives its bytes. Reason: one 262,144 for all would refuse a long draft and the save would fail without a word on the client; 1.2 MB for all would let every route take a body 10 times its largest. Check: a message of 10,000 `😀` written as they are (40,000 bytes) and the same written as `\ud83d\ude00` pairs (120,000 bytes) are accepted; a draft of 100,000 `ệ` (300,000 bytes), one of 100,000 `😀` as they are (400,000 bytes) and one of 100,000 escaped pairs (1,200,011 bytes) are accepted; a body of 262,145 bytes to a message route and a body of 1,201,025 bytes to the draft route are each 413 `payload_too_large`, in the error format of TOKI-004, with no row written and no log line holding the body; a body of 300,000 bytes is 413 on a message route and accepted on the draft route; a draft of 100,001 code points under the byte limit is refused by its schema (400), not by this limit.
- R15. The answer of a limit. Every limit of this spec answers as TOKI-022 R42 and R56 do: status 429, code `rate_limited`, `details.retryAfterSeconds` (whole seconds, at least 1) and the header `Retry-After` with the same number, and the body of TOKI-004. A refusal writes one log line at `warn` with the fields `limit` (the class or route key), `route` (the matched url, not the path) and nothing else: no address, no account id, no query string. Check: the answer and the captured log of one refusal for each of R10, R11 and R12 searched for the address, the account id and a marker in the query string.
- R18. The address behind the proxy. `tools/stack/security-check.sh` (called from `tools/stack/check.sh` last, after R5 and R6) proves that the limit counts each client's own address and not the address of Caddy. It uses two source addresses, both required: A, the host, through the published port of Caddy (`https://localhost:<HTTPS_PORT>`); and B, a throwaway container started on the Compose network of the stack (a `curl` image at a pinned tag, written in row D7), which reaches Caddy by its address on that network (`--resolve`, `-k`: the check is about the address and the certificate is proved by R22 of TOKI-084). It prints the two addresses that Caddy sees and fails when they are equal. It first restarts `server` and waits for `healthy`, so the counters, which are in memory (concern 6), start empty. Every request is `POST /api/v1/auth/codes` with a body of its own, a different address of no member, `check-<n>@example.test`, so that `code_request_limit` and `code_resend_too_soon` (also 429) cannot be the cause, and the check reads the `code` of the error body and not the status. (1) A sends 20 requests, each with another forged `X-Forwarded-For`: none answers `rate_limited`, the 20th included, and the 21st answers 429 `rate_limited`: the forged header changed nothing, because Caddy gives the server the real address and the server trusts only Caddy (`TRUSTED_PROXY`, TOKI-084 R12); a server or a Caddy that took the forged value would let the 21st pass. (2) With A limited, B sends one request: it is not `rate_limited`, so the count is of each address and A's refusal does not reach B; B's 20th is accepted and its 21st is `rate_limited`. (3) Negative control: the same steps against `server` started with `TRUSTED_PROXY` unset in a throwaway Compose override (every request then seems to come from Caddy and everybody shares one counter): step (2) must fail, B's first request is `rate_limited`, and the check passes only when the control shows exactly that. Reason: a wrong value makes every person share one counter and locks everybody out after 20 requests; no test has so far proved the value Compose sets.

### Dependencies
- R19. Exact versions. `tools/security/pinned.test.mjs` reads every `package.json` of the workspace (root, `apps/*`, `packages/*`) and fails on a version in `dependencies`, `devDependencies`, `optionalDependencies`, `overrides` or `pnpm.overrides` of a `package.json`, and in `overrides` of `pnpm-workspace.yaml` (where pnpm 12 keeps them), that is a range (`^`, `~`, `>`, `<`, `*`, `x`, `latest`, a tag) or a git or URL source; an `npm:` alias is read at its own version; `workspace:*` is allowed. `peerDependencies` are outside the rule: a package that other packages load names the range of React it works with (`react@^19.0.0` in `packages/i18n` and `packages/ui-web`). ### Where the findings go (concern 9)
`docs/security/review.md` in the repository. A finding that this work fixes is `fixed` and points to the requirement and the test; a finding that needs a decision is `open` and points to a concern of this spec; a finding for work that this ticket does not own is `open` with the number of a repository issue that the builder opens (labelled as the tracker's pipeline labels allow) and the name of the owning ticket. ### Errors
- A limit is full -> 429 `rate_limited` with `Retry-After` (R15). The client treats any failed request by the rule of its own screen; the text for sign-in and Join is concern 2.
- A body above the limit of its route (256 KiB; 1.2 MB for a draft) -> 413 `payload_too_large` (R14).
- A policy violation in the browser -> the console of the browser; there is no report route.

## Areas of concern
1. The guessing budget of the sign-in code. The log decides a 6-digit code, 5 wrong tries per code, 5 code requests per address in 15 minutes and 20 requests per network address on each sign-in route (D-011, D-038, D-137; TOKI-022 R56). Together they allow 25 guesses per address in 15 minutes, 2,400 a day, which is about 0.24% a day for one address and about 38% a day for all 200 addresses of a workspace, if the sender has about 250 network addresses and knows the addresses of the members (TOKI-022 concern 3). TOKI-022 left "a cap on wrong tries across the codes of one address" and "a ceiling for the whole server" to this review. Not decided. The options, with their effect (a proposal, not a decision): (a) keep as it is; (b) count wrong tries per address across all its codes and, from `ADDRESS_WRONG_TRIES_MAX` in 15 minutes, answer `code_locked` for that address until the oldest counted try is 15 minutes old; with 10 the budget is 960 guesses a day (about 0.096% a day for one address, about 17% a day for 200), with 5 it is 480 (about 9%); the cost is that a sender who knows an address can block that member's sign-in for as long as they keep guessing, which they can already do by requesting codes (TOKI-022 concern 3 (b)); a member's own typing mistakes also count; (c) a ceiling on wrong tries for the whole server per hour that writes a log line at `error` for the operator to read, and refuses nothing; (d) (b) and (c) together. Two things the owner should weigh. First, the Join routes count the same rows: `POST /api/v1/invitations/sessions` and the invitation code share the counters of sign-in (TOKI-097 R50, R52: 5 code rows of either purpose in 15 minutes), so option (b) must count the wrong tries of invitation codes as well, or an invited address keeps a second budget. Second, the lock-out cost of (b) is wider than TOKI-022 concern 3 (b) names: a code request cancels the code that a member is typing (TOKI-022 R6; D-082 for "Resend code"), and (b) adds a block for the whole address after 5 or 10 wrong tries, which anyone who knows the address can cause on purpose. The arithmetic is TOKI-022's; a number for (b) and (c) is for the owner. Owner: Thanh Truong.
2. What a person sees when a limit refuses them. Sign-in and Join can now answer 429 `rate_limited` (TOKI-022 R56 already could, TOKI-097 now too through R10), and a signed-in person can meet it (R12). The sign-in and Join screens give a text for `code_request_limit` and `code_resend_too_soon` only; the emergency page has one (`emergency.rateLimited`, TOKI-026), and the other screens treat a failed request by their own rules. D-139 says a wording that the prototype does not contain is a proposal. Not decided. Proposal, not a decision: the sign-in and Join pages reuse the wording of `emergency.rateLimited` ("Too many attempts from this network. Try again in {minutes} minutes."), made by the screens' owners (TOKI-023, TOKI-097) with `details.retryAfterSeconds`; a signed-in request refused by R12 shows the failure state its screen already has, with no new text. This work adds no screen and no text. Owner: Thanh Truong.
3. The starting numbers of the limits by class and the failed-check count. Decided in this spec: the mechanism (R10 to R12) and the starting values of the table "Limits by class" (300, 600 and 60 a minute per person; 60 a minute of failed checks and 60 per 15 minutes for the Join `lookup` per address). The 20 per 15 minutes of Join `codes` and `sessions` copies the sign-in figure and is a proposal of this spec; TOKI-022 decided that figure for the two sign-in routes only. No decision of the log gives them; each is one constant in `packages/shared/src/limits/`, with its reason in the table, chosen above what the client does at its busiest (a draft save a second, a few requests per opened conversation) and below what would let one account load the server. TOKI-089's measure with 200 people sets the final numbers by reading its count of 429 answers; a number changes in one line and no test changes except the constant it reads. Reason for deciding here: a limit that waits for a product figure would leave the routes with none. The cost named: behind one office address, 60 failed checks a minute is not reached by normal use (only a request with no session at all counts, R11, and a person whose session ended is sent to sign in once). The denial case of R11 is also a named cost: anyone on a shared address who sends 60 requests with a bad cookie in a minute makes every colleague on that address refused until the minute ends, and can repeat it; it needs someone on the same network with that intent, and the way to remove it (a cache of valid sessions) is a new state that this phase does not add. Owner: Thanh Truong.
4. The Content-Security-Policy is enforced, not reported. Decided in this spec: the policy of the table is sent as `Content-Security-Policy` from the first release, with no `report-uri`, after the run of R5 in Chromium and the by-hand run in Firefox and Safari. Reason: a report-only phase needs a place that receives reports, which is a public route that stores text from anyone, and the policy comes from what the code does (each directive has its reason), not from a guess; a mistake is seen at once in the console and by R5. The policy allows no inline script, so the first-paint script cannot be inline in `apps/web/index.html`: it is a file, `apps/web/public/first-paint.js`, a classic script in `<head>` with a `src`, no `async` and no `defer`, so it still runs before the first paint. TOKI-078 R8 now says exactly that (PR 389, after its own review), so this spec asks nothing more of TOKI-078. A hash in the policy would have to be computed at build and written into the Caddyfile for every change of the script, which is why it is a file. The file is not hashed or immutable, and it is served as the class that TOKI-078 asks of TOKI-084 R16 (`Cache-Control: no-cache`). `dist-csp.test.mjs` fails on any inline script, so a later inline script cannot be forgotten. The directive `media-src 'self'` is in the policy for the notification sound (R3), and R5 plays it. `wss://{$APP_DOMAIN}` is named in `connect-src` even though `'self'` covers it in current browsers, so a browser that reads `'self'` for `wss:` the old way can open the WebSocket too. Owner: Thanh Truong.
5. The line with TOKI-088. Decided in this spec: TOKI-088 owns authorization: who may do an action, the refusals (401, 403, 404 with the same body for every outsider) and the canaries. This ticket owns abuse and exposure: how often (limits), how much (body size), which headers, which cookie, which outbound requests, and which packages. The two meet in two places, both stated here: R16 and R17 run over every route using the registry and the route table of TOKI-088, and add no authorization case; a route that is public is justified in TOKI-088 (its `reason`) and limited here (R10, table L2). A finding in one's area that belongs to the other goes into `docs/security/review.md` as `open` with the owner named. Owner: Thanh Truong.
6. The limits count in the memory of one process. Decided in this spec: the counters live in the server process and are emptied by a restart, as TOKI-022 R56 already accepts, because the server is one copy (NFR-04, TOKI-084 concern 12), the worker has no HTTP routes, and a table or Redis for counters would add a write to every request. The known cost: a deploy or a crash gives every address a fresh count, so an attacker who can make the server restart gains nothing the attacker does not already have by waiting. If a second copy of the server ever runs, the limiter is the one place to change (R8). Owner: Thanh Truong.
7. Images and base-image packages. Decided in this spec: no scan of the operating-system packages of the images and no licence review in this phase; the review records the base image tags and their release dates (D7) and the images follow the tag and are rebuilt with each deploy. Reason: the log asks for no scan, one operator would receive a second advisory source with no one on call, and the advisory check of R20 covers the packages that Toki itself chooses. TOKI-085 hands this ticket "signing or attesting images, scanning them for known flaws": they are not taken here either, for the same reasons (a signature or an attestation has no reader on one machine that pulls its own images, and a scan is the second advisory source above). A scan or a signature that fails a build is a later change to the stack job and to TOKI-085. What this ticket does take from TOKI-085 is the review of the way into the server (rows D9, D10, H12). Owner: Thanh Truong.
8. The cookie choice stays. Decided in this spec, as the result of the review of TOKI-022 concern 9: `SameSite=Lax`, `HttpOnly`, `Secure`, the `__Host-` name and a 30-day sliding life stay as built. `SameSite=Strict` would also work for the pages (the first request of a page needs no cookie, and later requests come from the page), but the `Origin` rule, the JSON-only rule and the absence of CORS already stop a cross-site request, a change would alter a merged decision for no extra protection against a request the server already refuses, and R16 proves the refusal for every route. The change that would matter is a `GET` route that writes, which R17 forbids and tests. A separate registrable domain for storage (TOKI-084 concern 1, row S8) is weighed and not needed: the storage host `storage.<domain>` is on the same site as the app, so `SameSite` gives no protection against a request that starts there, but nothing runs there (a file is an attachment with `sandbox` and `nosniff`, TOKI-058 R13, and never a page, D-095), the `__Host-` cookie never goes to it, and a request from a page of that host carries `Origin: https://storage.<domain>`, which the `Origin` rule refuses like any other (R16 sends that origin). A second domain would cost the operator a second domain name and DNS for protection against a page that cannot exist. Owner: Thanh Truong.
9. Where findings are recorded. Decided in this spec: in `docs/security/review.md`, in git, reviewed in the pull request of this ticket (R1, R2), with an issue only for work outside this ticket. Reason: a record outside the repository goes stale and cannot be checked by a test; one file shows the next reviewer what was read and when. The review is a point in time (the commit named at its top); the tests of R13, R16, R17, R19 and R20 keep the parts that can be kept true for later changes. Owner: Thanh Truong.
10. Permissions-Policy and Cross-Origin-Opener-Policy. Decided in this spec: both are set on the app host (R4), with the features Toki never uses switched off and `same-origin` for the opener. Reason: no sign-in goes through another site (TOKI-022) and a link only opens a new tab (TOKI-049); the review row H3 confirms that no code reads `window.opener`, and no screen uses the camera, microphone, location, payment or USB. The storage host gets neither because it serves downloads, not pages. If a later feature needs one of the switched-off features, it edits the one line. Owner: Thanh Truong.
11. The shared office address at the first sign-in (F10). TOKI-022 R56 gives this review "the figure 20 and the shared-address case", and the intent keeps the figure. 200 people behind one address each need one `codes` and one `sessions` request to sign in the first time, and a mistyped code or "Resend code" adds more. At 20 per 15 minutes per route about 20 people get in per window: 10 windows, about 2.5 hours for the company, longer with mistakes; the Join routes have the same shape on the first day (R10), and what the refused person sees is open (concern 2). Not decided. Options, proposals and not decisions: (a) keep 20 and have the installation guide (TOKI-087) ask the operator to bring people in groups of 15 each quarter of an hour; (b) a higher figure for the sign-in and Join routes, for example 200 per 15 minutes: the per-address and per-code limits already cap the guesses on the whole server at 200 members x 2,400 = 480,000 a day (concern 1), and what the network figure changes is how many addresses the sender needs to reach that cap, about 250 at 20 and about 25 at 200 (200 x 96 = 19,200 a day for one address), which is cheap for anyone with an IPv6 allocation; (c) a larger allowance only for an address that already holds sessions of many members, which needs the server to remember an address for each session (a new column of personal data in a table that TOKI-019 owns), so it is a new decision. Owner: Thanh Truong.
12. What the limiter does when its map is full. Decided in this spec: it removes expired keys and then the key with the oldest last hit, and never refuses the new key (R8). Reason: a refusal would let one request from each of 50,000 `/64` networks stop every real person from signing in; an eviction costs the attacker 50,000 requests to push its own key out and reset a count of at most 20, and an attacker with 50,000 networks already holds 50,000 counters (concern 1). 50,000 is a size of memory, about 80 times the keys that 200 people make. Owner: Thanh Truong.
