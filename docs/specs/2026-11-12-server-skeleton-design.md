# Server skeleton design

Date: 2026-11-12 · Status: draft for review
Intent: docs/intents/server-skeleton.md (Thanh Truong)
Ticket: TOKI-004

## Goal
The builder needs one basic Toki server that all later server work builds on. It settles in one place how the server reads configuration, logs, reports errors and where its API addresses live. Without it, TOKI-005 and later tickets cannot start, and each would decide these things for itself.

## Scope
- In: the Fastify app in `apps/server`; reading and checking the configuration values the server itself uses, at startup; `GET /healthz`; structured logs; one error handler for every error response, including errors Fastify raises itself; the `/api/v1` prefix for all API routes; the `apps/server/src/modules/` folder; one shutdown path; the error response schema in `packages/shared`; the `dev` and `test` scripts of `apps/server`; a minimal Vitest setup in `apps/server`; tests for the above.
- Out (not now):
  - Monorepo, packages and shared TypeScript config, and the root `pnpm dev` script: TOKI-001. This ticket does not edit the root script.
  - The inventory of environment variables, `.env.example` and how secrets are kept: TOKI-096. This spec only reads the values, under exactly the names in that inventory. It lists the kinds of value the server itself needs so the inventory can name them (concern 9).
  - ESLint, Prettier and the boundary rules: TOKI-002.
  - Postgres, MinIO and Mailpit for development, and the `dev:*` scripts: TOKI-003.
  - Postgres connection, Drizzle, migrations and any table: TOKI-005.
  - Web skeleton and the dev proxy to the server: TOKI-006.
  - CI: TOKI-007. Test harness (real Postgres, Playwright, controllable clock): TOKI-008.
  - Sending mail: TOKI-021. Background job queue and worker: TOKI-064. Production image and Compose, and the `build` and `start` of the server for production: TOKI-084 (concern 13).
  - A readiness check that reports the database state: a separate `/readyz`, added later by another ticket, not by TOKI-004 (concern 3).
  - WebSocket, sign-in, creating the first admin and workspace, and any business route: later tickets. The intent does not ask for them.

## Requirements
- R1. With a valid `.env` at the repository root, the `dev` script of `apps/server` starts the server and the server's log shows exactly one line with the address it listens on. The server binds to the one explicit address given by the bind-host value, `127.0.0.1` by default (R18), so Fastify does not log one line per resolved address.
- R2. Configuration is read and checked once, at startup, in one module. A search for `process.env` in `apps/server/src` finds it in that module only. The module checks only the values the server uses (concern 11); it holds one schema per area, and a later ticket adds its area to it.
- R3. When a required variable is missing, or is present but empty or only whitespace, the server does not start: the process exits with code 1 and writes to standard error one line per failing variable with its name. All failing variables are reported in one run.
- R4. When a variable is present but fails its check, the server does not start: the process exits with code 1 and writes the name of the variable to standard error, never its value. A test checks that the submitted value is absent from everything the process prints.
- R5. `GET /healthz` returns status 200 and the body `{ "status": "ok" }` while the server is running. It reports that the process is up and makes no database call, so it answers the same when Postgres is unreachable. A database readiness check is a separate `/readyz` added later by another ticket (concern 3).
- R6. Every line that the server's own logger writes to standard output parses as one JSON object. A startup failure (R3, R4) is not a logger line; it goes to standard error. R6 is checked on the process started directly with Node, not through pnpm, whose own lines are not JSON.
- R7. Fastify's built-in request logging is switched off. Each handled request writes exactly one completion line that holds the method, the path without its query string, the response status, the response time in milliseconds and the request id. A request to `/healthz` writes its line at level `debug`, so it is hidden at the default level. The log holds no other request data: the `authorization`, `cookie` and `set-cookie` headers, the query string and the request body never appear in any log line (concern 4).
- R8. Every error response has a body that passes the same single error schema from `packages/shared`: `{ "error": { "code": "<stable string>", "message": "<English text for developers>", "details": <optional> } }`. This covers five classes: an unknown path (404); a request that fails validation (400); a known error thrown by a route as an `AppError` with a status and a code; an error that Fastify raises with a 4xx status (malformed JSON body, body too large, unsupported media type), whose status is kept and whose code is mapped from it (concern 8); and anything else (500). It also covers paths that bypass the error handler: a malformed URL and a Node `clientError`. Tests check one case of each against the schema, including a malformed JSON body, a malformed URL and a `clientError`.
- R9. A response for an unexpected error has status 500, code `internal_error` and a fixed English message. Its body holds no stack trace and no internal error message, and `details` holds only `{ "requestId": "<id>" }`. The error, its stack and the request id go to the log. A test checks both parts.
- R10. A route registered through the API module answers under `/api/v1/` and returns 404 at the same path without the prefix. A test lists every route the app registers and fails on any path outside `/api/v1` other than `/healthz`.
- R11. The server tests run with the `test` script of `apps/server` (the root `test` script finds it), need no database and no network, and pass.
- R12. The server does not translate the `message` of an error body: the same failing request sent with `Accept-Language: vi` and with `Accept-Language: en` returns the same `code` and the same English `message`.
- R13. Every variable name that the configuration module reads is a name in the TOKI-096 inventory; the module reads no other name. A test checks that every name the schema reads appears in `.env.example`, which TOKI-096 keeps equal to the inventory.
- R14. `apps/server` has a `dev` script, and this ticket leaves the root `dev` script from TOKI-001 unchanged; root `pnpm dev` starts the server through the `apps/server` script. The `dev` script loads the root `.env` with Node's `--env-file=../../.env` flag; nothing loads a `.env` file in tests or in production (concern 13).
- R15. On SIGTERM or SIGINT the server stops accepting requests, runs the close hooks the app has registered and exits with code 0. Later tickets register what they close (connection pool, job worker, WebSocket gateway) as close hooks on the app. A test sends SIGTERM to the started process and checks the exit code.
- R16. `buildApp` takes `{ config, logStream?, registerRoutes? }`. The config is passed in and is never imported by modules; a module receives it from the app. `logStream` lets a test capture the log. `registerRoutes` runs inside the `/api/v1` scope before the app is ready, so a test route is registered under the prefix before the first `inject()` (concern 12).
- R17. The module folder is `apps/server/src/modules/<name>/` and the only public entry of a module is its `index.ts`. This ticket creates the `modules/` folder and registers no module in it.
- R18. The server area of the configuration has four values: the listen port (default `3000`), the bind host (default `127.0.0.1`; the container sets `0.0.0.0` through its environment), the environment name and the log level (default `info`). With none of them set, the server listens on `127.0.0.1:3000`. The names of the variables come from the TOKI-096 inventory (concern 9).
- R19. The database area of the configuration reads one variable only, the connection URL `DATABASE_URL`; tests use `TEST_DATABASE_URL`. No other variable describes the database connection (concern 11).
- R20. If Postgres is unreachable at start, the server still starts and `/healthz` returns `{ "status": "ok" }`. A database call made later fails with the 500 `internal_error` of R9 (concern 3).

## Design
### API
| Method | Path | Purpose |
|---|---|---|
| GET | `/healthz` | Process liveness: 200 and `{ "status": "ok" }`. It sits at the root, outside `/api/v1`, and is reached by the container health check inside the server's own network, not through Caddy (concern 3). |
| any | `/api/v1/*` | Prefix for all API routes. This ticket adds no business route. Within a version, fields are only added. |

### Errors
- Required variable missing or empty at startup -> the server does not start; the names go to standard error (Blueprint, flow F01 note; R3).
- Variable present but invalid at startup -> same behaviour (intent: the server "reads and checks its configuration values"; concern 7).
- Unknown path -> 404, code `not_found`.
- Request fails validation -> 400, code `validation_failed`, `details` as in concern 14. The status 400 matches the Blueprint mapping "400 field message" (D-131).
- Known error raised by a route or module -> the status and code of the `AppError` that was thrown.
- Error raised by Fastify with a 4xx status -> status kept, code mapped by status: 400 `bad_request`, 401 `unauthorized`, 403 `forbidden`, 404 `not_found`, 413 `payload_too_large`, 415 `unsupported_media_type`, 429 `too_many_requests`, any other 4xx `bad_request` (concern 19). The `FST_ERR_*` name never reaches the client.
- Malformed URL and Node `clientError` -> 400 `bad_request` in the one format (Fastify's `frameworkErrors` option and a `clientError` listener).
- Unexpected error -> 500, code `internal_error`, with no internal detail in the body and the request id in `details`. The Blueprint says a 5xx shows Retry with a short error ID (D-131); the request id is that ID.
- The one error format is `{ "error": { "code": "<stable string>", "message": "<English text for developers>", "details": <optional> } }` (concern 1). The HTTP status carries the class of error. The client translates to Vietnamese or English from `code`; the server does not translate `message`.
- All error bodies are built in one handler, so the format is set in one place. The schema lives in `packages/shared`, together with the registry of codes (concern 14). A later ticket raises a known error with `throw new AppError(status, code, message, details?)` from `errors.ts` and adds its code to the registry.

### Layout
Assumption: file names below are a proposal; the Blueprint fixes only `apps/server` and `packages/shared`. The `modules/` folder and `index.ts` entry are fixed by the TOKI-002 spec, concern 1.
```
apps/server/src/
├─ main.ts          load config, build the app, listen, handle SIGTERM and SIGINT
├─ app.ts           buildApp({ config, logStream?, registerRoutes? }), used by main and by tests
├─ config.ts        the only reader of process.env; one schema per area and the typed config
├─ errors.ts        AppError, the one error handler, the not-found handler, framework error mapping
├─ health.ts        GET /healthz
├─ api/index.ts     registers every module's routes under /api/v1
└─ modules/         one folder per module, public entry modules/<name>/index.ts (none yet)
packages/shared/    the error response schema and the registry of error codes (data contracts live here)
```
- Stack from the Blueprint: Fastify, Node 22, TypeScript, Zod. No version beyond these is fixed here.
- Assumption: the configuration schema is written with Zod, which is in the Blueprint stack; the Blueprint does not say which tool checks the environment. Requests are validated with Zod too (concern 14).
- The names of the variables that `config.ts` checks, which are required, and their defaults come from the TOKI-096 inventory, which is done first; this ticket invents no name (concerns 2, 9 and 11).
- `apps/server` gets its own `dev` script. The root `pnpm dev` script is made by TOKI-001 and runs the `dev` script of every workspace project that has one, so it picks this one up; this ticket does not edit the root script (concern 5).
- `api/index.ts` registers each module through `modules/<name>/index.ts`, so no module can leave the prefix; R10 enforces it with a route-list test.
- The placeholder `apps/server/src/index.ts` from TOKI-001 is removed: `main.ts` is the entry and nothing imports it.

## Testing
- Tests are written first. Most build the app with `buildApp` and send requests in memory; no port, no database, no network. The config is passed in, so no test reads the real environment and CI needs no `.env`.
- Config tests pass fake environment objects: all valid, one required value missing, one required value empty, one value whitespace only, one value invalid. The invalid-value test asserts that the value is not in the error text (R4). A schema-names test compares the names the schema reads with `.env.example` (R13). Config tests also check the defaults of R18 (nothing set gives `127.0.0.1:3000` and level `info`) and that the database area reads `DATABASE_URL` and no other name (R19).
- Error tests use a test route registered through `registerRoutes` that throws, one that throws an `AppError`, plus an unknown path, an invalid request, a malformed JSON body, an oversized body, an unsupported media type and a malformed URL. Each body is checked against the schema from `packages/shared` (R8, R9, R12).
- Log tests pass a `logStream` and check that every line is a JSON object (R6), that a request writes one completion line with only the fields of R7, and that a request sent with `authorization`, `cookie` and `set-cookie` headers, a query string and a body leaves none of those values anywhere in the captured log, and that the details of a 500 are in the log and not in the body (R9).
- A route-list test collects every registered route and fails on a path outside `/api/v1` other than `/healthz` (R10).
- One process test starts the real `main.ts` with a fake environment and port, checks the single listening line (R1), `GET /healthz` (R5), a raw malformed request (`clientError`, R8) and SIGTERM with exit code 0 (R15). It also starts with a `DATABASE_URL` that points to no running Postgres and checks that the server starts and `/healthz` returns ok (R20). It starts it again with a required value missing, an empty one and an invalid one, and checks exit code 1, the names on standard error and the absence of values (R3, R4). It does not go through pnpm.
- This ticket adds a minimal Vitest setup in `apps/server`, run by its `test` script (R11). TOKI-008 later extends it into the full harness (concern 6).
- Fake values only. No real secret appears in a test or a fixture.

## Data safety
- Secrets come from `.env`, which is never in git. This ticket adds no value to any committed file.
- A startup failure prints variable names only, never values (R4).
- Error bodies sent to clients hold no stack trace, no file path and no configuration value. The validation `details` hold field paths and codes, never the submitted values (concern 14).
- The log hides the `authorization`, `cookie` and `set-cookie` headers, the whole query string and the request body. The request line holds only the method, the path, the status, the duration and the request id, so a token, a code or an email address sent in a header, a query or a body does not reach the log (R7, concern 4).
