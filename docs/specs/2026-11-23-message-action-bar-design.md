# Message action bar design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/message-action-bar.md (Thanh Truong)
Ticket: TOKI-052
Needs: TOKI-042 (the message component, in its open pull request 221: `messageExtensions` with the `Actions` component and `useRow`), TOKI-045 (threads, PR 214: `canOpenThread`, `useOpenThread`), TOKI-046 (reactions, PR 215: `useReactionPicker`), TOKI-047 (edit and delete, PR 213: `useMessageActions`), TOKI-048 (pins, PR 216: `usePinActions`), TOKI-014 (`Menu`, merged), TOKI-018 (the platform package, merged) and TOKI-017 (i18n).

## Goal
A message is drawn in full by TOKI-042 and the work of TOKI-045 to TOKI-048 builds what a person can do to it, but nothing yet lets a person press anything: the place for the bar is empty. This work builds the bar and the menu behind its More button: the smile button, Reply in thread, More with Copy text, Pin or Unpin, Edit and Delete. It shows them on hover, on focus and, on narrow and touch screens, on a tap, so that no action is hover-only (D-067). It also gives copy a device clipboard, which the app reaches only through the platform package.

## Scope
- In:
  - The bar and its menu, in a new folder `apps/web/src/features/message-bar/` (R1 to R5, R10 to R16).
  - The active message and the tap on narrow and touch screens, the keyboard, the look at both widths and in both looks (R6 to R9, R21).
  - Who sees which action, from the permission functions of `@toki/shared` (R17, R18).
  - Copy text and the clipboard member of the platform package, with its lint pair (R14, R19).
  - Texts, tests (R20, R22, R23).
- Out (not now), each with its owner:
  - The picker of 8 emoji, the chips and the requests of reactions: TOKI-046. This work draws the smile button and calls `openFor` (R11).
  - The thread panel, its address and the reply line: TOKI-045. This work calls `useOpenThread` (R12).
  - The edit field, the delete confirmation and the rules of who may edit and delete: TOKI-047. This work draws the two menu entries from `useMessageActions` (R16).
  - The pin request, its Undo and the Pinned tab: TOKI-048. This work draws one menu entry from `usePinActions` (R15).
  - The place of the bar in the row, the tint, the grouped time and the narrow `flex-wrap` of the row: TOKI-042 (R17 of that spec). This work fills `Actions` and `useRow` of `messageExtensions` and adds no other change to the message folder.
  - Save for Later (the bookmark button) and Remind me about this: TOKI-067 (Later, phase 1). "Turn into task" belongs to Tasks (phase 2, no ticket in the plan yet). The bar and the menu are built so that each is one entry in one file (R10); this work draws none of them.
  - What the offline banner says and how a blocked action is worded: TOKI-082 and `useOnlineGate` of TOKI-093. This work adds no gate of its own (R18).
- Written in parallel: TOKI-049 (text formatting). It changes what is drawn in the text of a message and not the bar; the one point where the two meet is that Copy text copies the stored text (R14).

## Requirements
Structure
- R1. Layout and wiring. The work lives in `apps/web/src/features/message-bar/`: `MessageBar.tsx` (the `Actions` fill), `MoreMenu.tsx`, `entries.ts` (R10), `active-row.ts` and `useRow.ts` (R7), `tap-mode.ts` (R6), `surface.ts` (R24), `useConversationFacts.ts` (R17), `copy-text.ts` (R14), `deps.ts` (R2), `message-bar.css`, `index.ts` and a test file next to each source. The only change outside the folder in `apps/web` is in `apps/web/src/conversation/message/extensions.ts`: one import and two entries, `Actions: MessageBar` and `useRow`, which TOKI-042 R14 declares (rule (a) of that requirement); no other file of the message folder is edited and `Message.tsx` and `UserMessage.tsx` are not touched (rule (b)). The members are stable: the same component and the same hook between renders (rule (d)). Check: the files and exports exist; a test imports `messageExtensions` and finds `Actions` and `useRow` equal to the exports of this folder and every other member as TOKI-042 left it; a source search finds no import of `features/message-bar` in `conversation/message/` other than `extensions.ts`.
- R2. State and dependencies. `deps.ts` is the only file of the folder that imports `apps/web/src/client.ts`, the conversation store or `getPlatform`; it exports `useConversationEntry(conversationId)` and `useCurrentUserId()` (the selectors the other features of `apps/web` use over the store of TOKI-032), `clipboard` (`() => getPlatform().clipboard`, read at call time) and `tapMedia` (R6). The entry hooks of the neighbours (`usePinActions`, `useMessageActions`, `useOpenThread`, `useReactionPicker`) are imported where they are used, from their own folders. Tests of the folder replace `deps.ts` with `vi.mock`. Check: a test finds an import of `client`, the store or `@toki/platform` outside `deps.ts` and fails on it; a test finds no direct use of `navigator`, `window.matchMedia` or `localStorage` outside `deps.ts`.

What is drawn
- R3. When the bar is drawn. `MessageBar` is the component TOKI-042 renders for a user message and for a pending item (its R17). It renders the bar only for an item of `kind` `message` whose message has no `deletedAt`; for an item of `kind` `pending` (waiting, sending or failed) it renders `null` (the proposal of concern 1: a message with no server id has nothing to react to, reply to, pin, edit or delete). While the editor of TOKI-047 is open for the message (`useMessageActions(...).editing`) it renders `null` and stays mounted, because TOKI-042 R17 gives that state to the component that owns it; it draws the bar again when the editor closes. It renders `null` when the bar would hold no button (R10). Check: a table of item kinds and states (confirmed, waiting, sending, failed, editing, no button) with the expected presence; a test that the component stays mounted while it renders `null` for `editing` (a probe hook in it keeps its state).
- R4. The bar, as the prototype draws it (`.acts`, line 1371). One element with `role="toolbar"` and the accessible name `messageBar.label` ("Message actions"), the last child of the inner box `.message` of TOKI-042 (so its offsets are measured from the box, not from the outer wrapper), holding the buttons of R10 in order, each an `IconButton` of `@toki/ui-web` (the label is its only name; none has a `title`, because the prototype has no tooltip and every name is read from the `aria-label`). The numbers were measured in headless Chrome on the prototype at 1300 and 500 px wide, in both looks:

  | | Hover mode (1300 px, a pointer that hovers) | Tap mode (500 px, R6) |
  | :---- | :---- | :---- |
  | Position | `absolute`, `right: 12px` (8 px under 720 px), `top: -16px`, `z-index: 2` | in the flow of the box: `order: 3`, `flex-basis: 100%`, `position: static`, margin `6px 0 2px calc(var(--av) + 10px)`, no shadow |
  | Frame | 1 px `--line` border, radius `--radius-sm` (10 in Calm, 8 in Focus), `--surface` background, shadow `--pop`, padding 2 px, gap 0 | the same, without the shadow |
  | Button | 30 x 30 | 40 x 40 |
  | Four buttons (smile, reply, bookmark, more) | 126 x 36 | height 46; the bar spans the text column (407 px at 500 px in Calm, 413 in Focus) |
  | Distance from the top of the inner box | -16 | 6 px margin under the text, so the bar is below the message and never over its text |

  The bookmark of the measurement is the prototype's and belongs to TOKI-067; with the buttons of this work the bar has three (smile, reply, more) and is 96 x 36 in hover mode. The button states are the prototype's `.ib`: hover background `--hover`, and `.on` (the pressed look, `--accent-soft`) for a button with `aria-pressed`. The look is set by the existing tokens, so the component has no branch on the look. Check: in the browser test (R23) at 1300 and 500 px, in both looks, the sizes, offsets and margins above are read from the page within 1 px; a jsdom test checks the role, the name, the order and the absence of `title`.
- R5. When the bar shows on a pointer that hovers (hover mode). The bar is in the page for every message and `display: none` until one of these is true: the pointer is on the message (`:hover` of the inner box), focus is inside the message (`:focus-within`), or the message is the active row (R7, the class `act` that TOKI-042 sets from `useRow`). `display: none` takes the buttons out of the tab order and out of what a screen reader reads, so the buttons of a message that is not shown are not in the way (R9). The rule is CSS only: no script runs on a pointer move. Check: the browser test hovers a message and finds the bar visible with the sizes of R4, moves the pointer away and finds it `display: none`; focuses a button in the message (the name) and finds it visible; sets the class `act` and finds it visible.
- R6. Tap mode. "Tap mode" is a screen narrower than 720 px, or a screen whose primary pointer cannot hover, one media query: `TAP_MEDIA = "(max-width: 719.98px), (hover: none)"` (D-068 puts the line between 719 and 720 px; D-067 asks for touch screens, which concern 3 settles). `tap-mode.ts` exports the constant and `useTapMode()` (a `useSyncExternalStore` over `matchMedia(TAP_MEDIA)` given by `deps.ts`, `false` when `matchMedia` does not exist); `message-bar.css` uses the same text in its `@media` rule, and a test reads both and finds them equal, so the script and the stylesheet cannot disagree. In tap mode the bar is `display: none` unless the message is the active row or focus is inside it, and when it is shown it has the second column of R4's table (below the message, 40 px buttons: F38 asks for 40 px controls and the bar under the message "never over the text"). A hover does not show the bar in tap mode (the prototype's rule `.msg:not(.act) .acts{display:none}`). Check: a test reads `message-bar.css` and finds the media text equal to `TAP_MEDIA`; the browser test at 500 px finds the bar hidden on hover and shown below the message (its top at or below the bottom of the text, its left at the text column) after a tap, and, in a touch context (`isMobile`, `hasTouch`) at 1100 px, the same.
- R7. The active row and `useRow`. `active-row.ts` holds one value for the whole page, `{ tapped: string | null, held: string | null }`, with `subscribe`, a snapshot and these functions: `toggleTapped(id)` (sets `tapped` to the id, or to `null` when it already is that id: the prototype's `S.actMsg===id?null:id`, so a tap on another message moves the bar and a second tap on the same one hides it), `clearTapped()`, `hold(id)` (sets `held`; returns the function that clears it only if it still holds that id) and `isActive(id)` (`tapped === id || held === id`). `useRow(id)` is the hook TOKI-042 R14 declares: it returns `{ active, rootProps }` where `active` comes from `useSyncExternalStore` over `isActive(id)`, a boolean, so a change re-renders only the row that becomes active and the row that stops being, and never the others. `rootProps` is `{ onClick, onKeyDown, tabIndex: 0 }` made once per `id` (`useMemo`); `UserMessage` spreads it on the inner box (TOKI-042 R17). The row is cleared when it leaves the page: the cleanup of `useRow` calls `clearTapped()` when `tapped` is still its id, so a conversation change, a row that scrolls out of the window of the list (TOKI-041 R20) and a removed message each end the state, and a stale id is never kept. `held` is the row whose menu or picker is open (R13); it keeps the bar of a hover device in view while the pointer is over the menu, which is outside the row and would otherwise hide the bar (and its More button, the anchor of the menu) under it. Check: with a fake list of three rows, a tap on the first sets `act`, a tap on the second moves it, a second tap on the second clears it; a counting render shows that a tap re-renders two rows at most; unmounting the active row clears the state; `hold` keeps the row active and its release does not clear a hold made by another row; `useRow` returns a constant object when the id and the state do not change.
- R8. What a tap does. `onClick` of `rootProps` acts only in tap mode (a click on a hover device changes nothing: the bar there is the pointer's and the keyboard's). It does nothing when the click did not happen inside the row's own DOM (a `Menu`, the picker and the dialogs are portals: a React event from them reaches the row's handler through the React tree, so the handler first checks that `event.currentTarget.contains(event.target)`), and nothing when the target is inside a control: the closest ancestor of the target that matches `button, a, input, textarea, select, summary, [contenteditable], [role="menu"], [role="toolbar"], [data-no-tap]` (the prototype's list, with the toolbar and the menu made explicit). Otherwise it calls `toggleTapped(id)`. A press on a name, an avatar, a reaction chip, the thread link, a link in the text, a bar button or a menu item therefore never toggles the bar. Check: tap mode on, a click on the text toggles; a click on a `button`, on a link, inside the open menu (a portal) and inside the toolbar does not; tap mode off, a click on the text does not; a click that starts in the row and ends elsewhere is not a click and does nothing.
- R9. Keyboard. The inner box is focusable (`tabIndex: 0` from R7), so a person who uses the keyboard reaches a message with Tab, and `:focus-within` shows its bar (R5, R6) with the buttons after the text, the reactions and the thread link in the tab order. The toolbar also moves focus between its buttons with ArrowLeft and ArrowRight (wrapping is not done) and Home and End, though every button stays a tab stop. Escape, pressed in the row or in the toolbar when the bar is open by a tap or a hold, clears the tapped row and moves focus to the row; Escape in an open `Menu` is the menu's (TOKI-014) and does not reach this handler (the check of R8 again, and `defaultPrevented`). The row and every button have the visible focus ring of the design system. Check: a keyboard test with `user-event`: Tab reaches the row and the bar appears, Tab again reaches the buttons in order, the arrows and Home and End move focus, Escape on a tapped row clears it and focuses the row, Escape in the open menu closes the menu and leaves the bar.
- R10. The entries, in one file. `entries.ts` is the one place where an action is added, as TOKI-042 R14 makes `extensions.ts` the one place for a piece of a message. An action is described by a hook that returns a description or `null`: `type ActionSpec = { key: string; label: string; icon: IconName; onSelect: (anchor: RefObject<HTMLElement | null>) => void; pressed?: boolean; variant?: "default" | "danger" }` and `type ActionContext = { message: MessageEntry; conversationId: string; surface: "list" | "thread"; facts: ConversationFacts | null; editing: boolean }`. The file exports two hooks written by hand with a fixed order, `useBarSpecs(ctx)` (the smile, then Reply in thread; TOKI-067 adds Save for Later after them) and `useMenuSpecs(ctx)`, which returns `{ message: ActionSpec[], owner: ActionSpec[] }`: Copy text, then Pin to conversation or Unpin (TOKI-067 adds Remind me about this here) in `message`, and Edit, then Delete in `owner` (the prototype's order and its rule between the two groups). Each is a call to a hook with the same count of hooks on every render, so a list that is composed by hand never breaks the rules of hooks and a later ticket adds one line and one hook of its own. The More button is not an entry: it is drawn after the entries of the bar when `useMenuSpecs` returns at least one spec in either group, and it is the last button, as in the prototype. A bar with no button (no entry and no menu spec) is not drawn (R3). Check: a type test fixes the two types and the two hooks; a test renders each case of R11 to R16 and reads the order of the buttons and of the menu items from the DOM; a test adds a probe hook to `useBarSpecs` and `useMenuSpecs` with `vi.mock` of `entries.ts` and finds its button and its menu item in the right place; a menu with only the `owner` group has no separator and a menu with both has one `MenuSeparator` between them.
- R11. The smile button. Label `messageBar.react` ("Add reaction", the prototype's `aria-label`), icon `smile`, drawn when `canPostInConversation(me, facts)` of `@toki/shared` allows it (the function the server uses for reacting, TOKI-046 R4, R5; a person who may not react is not offered the button: archived channel, concern 8), for a message of kind `user`. It calls `useReactionPicker().openFor(message, anchorRef)` of TOKI-046 R20 with the button's own ref as the anchor, and sends no request and draws no picker: the picker, its Escape and the return of focus to the button are TOKI-046's. While the picker is open the row is held (R7): `openFor` takes the third argument `{ onClose }` that this work asks TOKI-046 for (Plan changes), and the hold is released from it. Check: with a fake `useReactionPicker`, a press calls `openFor` once with the message and the ref of the pressed button; a Member of a conversation that is not archived sees the button, an archived channel shows none; the row is held between the call and `onClose`; a test finds no `fetch` and no store write in the folder for a reaction.
- R12. Reply in thread. Label `messageBar.reply` ("Reply in thread", the prototype), icon `reply`, drawn when `canOpenThread(message)` of TOKI-045 R20 is true (a message of kind `user` with no `parentId`: a reply, a system line and a pending message have none, AC-087, TS-136), when `surface` is `"list"` (the prototype draws it for the main list only; the root in the panel already shows its thread) and when the person is a member who may read the conversation (`canReadConversation`). It calls `useOpenThread(conversationId)(message.id)`; in an archived channel it still opens the thread, which the panel draws read-only (TOKI-045 R19), because reading is allowed there. The More menu of a reply has no thread entry either (there is none to hide: no menu entry of this work opens a thread). Check: a root in the list shows the button and a press calls the opener with its id; a reply, the root in a thread surface, a pending item and a system line show none (the table of AC-087, TS-136 read on the bar and on the menu of a reply); an archived channel keeps the button.
- R13. The More button and its menu. Label `messageBar.more` ("More actions", the prototype), icon `more`. It is a button made with `useMenuTrigger` of `@toki/ui-web` (TOKI-014 R24), so a click or ArrowDown opens `Menu` with the first item focused, ArrowUp opens it with the last, and Escape, a choice, Tab and a press outside close it and return focus to the button. The menu has the accessible name `messageBar.more`, `align="end"` (its right edge on the button's, the prototype's `posMenu`), and holds `MenuItem`s from `useMenuSpecs` with the spec's icon and label, a `MenuSeparator` between the groups, and `variant="danger"` for Delete. While the menu is open the row is held (R7) and `held` is released when it closes, whatever the reason. A choice runs the spec's `onSelect` and then closes the menu (the `select` reason of `Menu`). If the row unmounts while the menu is open (a long scroll takes it out of the window of TOKI-041, its overscan being 10 rows) the menu goes with it and throws nothing (Known limits). Check: opening with click, ArrowDown and ArrowUp focuses the first and the last item; each close reason closes it and returns focus to the More button; the row has the class `act` while the menu is open and not after; unmounting the row with the menu open leaves no listener and no error; the separator and the `danger` variant as in R10.
- R14. Copy text. Label `messageBar.copy` ("Copy text", the prototype), icon `copy`; in the `message` group; drawn when the message has text (`message.text` is not empty after trimming: a message with only files, TOKI-058, has nothing to copy). It writes the stored text of the message, as it was sent (`message.text`, with the marks and the names as typed: the prototype copies `m.text`, and the server stores the text as sent, TOKI-037 R4), by `copyText(text)` of `copy-text.ts`, which calls `clipboard().writeText(text)` of the platform package (R19) and never `navigator.clipboard`. When it resolves `true` the toast of `useToasts().show` says `messageBar.copied` ("Copied text", the prototype's toast) with no button; when it resolves `false` the toast is `common.error.actionFailed`, so a person is never told that a copy happened when it did not. Copying reads the page and writes the device clipboard and sends no request, so it is not behind `useOnlineGate` and works offline (D-079 blocks what needs the server). Check: with a fake platform, a press passes exactly `message.text` (a text with `*bold*`, `@Lan` and a line break arrives unchanged) and shows "Copied text" on `true` and the failure toast on `false`; no `ensureOnline` call and the same result with the connection check set to false; a message with empty text has no Copy text item; the browser test (R23) grants the clipboard permission and reads the clipboard back after a press.
- R15. Pin or Unpin. In the `message` group, drawn only when `usePinActions().canPin(facts)` and `usePinActions().isPinnable(message)` are both true (TOKI-048 R14: a reply of the thread panel that was not also sent to the channel, a system line and a deleted message leave it out). The label is `t(usePinActions().labelKey(message))`: `pins.action.pin` "Pin to conversation" or `pins.action.unpin` "Unpin" (the prototype's two words, TOKI-048 R17), the icon is `pin`, and a press calls `toggle(message)`; the Undo toast, the request and the offline block are the hook's (`useUndo` of TOKI-093). This work reads no pin state of its own. Check: with a fake `usePinActions`, the item is absent when either function is false and present when both are true, with the label of the key for a pinned and an unpinned message; a press calls `toggle` with the message once.
- R16. Edit and Delete. In the `owner` group, from `useMessageActions(message, conversation)` of TOKI-047 R17, where `conversation` is `useConversationEntry(conversationId)`: Edit (`messageActions.menu.edit`, icon `edit`) when `canEdit`, calling `startEdit()`; Delete (`messageActions.menu.delete`, icon `trash`, `variant: "danger"`) when `canDelete`, calling `requestDelete()`. The two words are the prototype's. The author sees both, an Admin who is a member sees Delete on another person's message, and a person sees neither when the hook says `false` (an archived conversation included): this work compares no role (TOKI-027 R16). When the editor closes after Edit (the hook's `editing` goes from `true` to `false`), focus returns to the More button of that message, which TOKI-047 R18 asks for (the bar stays mounted while it renders nothing, R3, so the effect has a button to focus). Check: with a fake hook over the cases of TOKI-047 R17 (author, other Member, Admin member, Admin not a member, archived), the items present are the expected set; a press on Edit calls `startEdit`, on Delete `requestDelete`; the focus test: with a fake hook whose `editing` switches to `true` and back, focus is on the More button after the switch back and not before.

Who sees which action
- R17. The facts. `useConversationFacts(conversationId)` returns the `ConversationFacts` of `@toki/shared` (`kind`, `isGeneral`, `archived`, `isMember`) built the way the header spec builds them (TOKI-035 R15): `kind` and `isGeneral` from the held conversation entry, `isMember` true for a conversation the person has in their list, `archived` from the held detail for a channel and `false` for a direct message or a group; it returns `null` while a fact is missing, and every function of this work then denies (TOKI-027 R4: a missing fact denies), so no action is drawn from a guess. The signed-in person is `useCurrentUserId()` with the role from the held people. The same facts go to `canPostInConversation` (R11), `canReadConversation` (R12) and `canPin` (R15). Check: a table of entries (public channel, private channel, direct message, group, archived channel, missing detail) with the expected facts and the buttons that follow; a missing fact shows no smile, no Reply and no Pin.
- R18. The connection. The bar adds no gate and no `disabled` state of its own: no button of the bar or entry of the menu is disabled or hidden because the connection is down. Each action keeps the rule of its owner, which is how D-079 is met: a reaction goes through `toggle` behind `useOnlineGate` (TOKI-046 R20), a pin through `useUndo` (TOKI-048 R14), the edit save and the delete confirmation through TOKI-047 R18 and R21, a thread through the panel of TOKI-045, and Copy text needs no connection (R14). Check: with the connection check set to false the bar and the menu show the same buttons and items as with it true; no source file of the folder imports `useOnlineGate` or `isOnline`.

Texts, accessibility, platform, tests
- R19. The clipboard in the platform package. `Platform` of `packages/platform` gains the member `clipboard: { writeText(text: string): Promise<boolean> }` (the sixth member, as TOKI-099 added `tabs`; TOKI-018 R1 says later tickets add members and update its test). `createWebPlatform()` builds it with `createClipboard()` in `packages/platform/src/web/clipboard.ts`: `writeText` calls `navigator.clipboard.writeText(text)` inside the method (so creating the platform still starts nothing, TOKI-018 R5), resolves `true` when it resolves, and resolves `false` and never rejects when the browser has no `navigator.clipboard`, refuses (no permission, no user gesture, a page that is not secure) or throws. It reads nothing from the clipboard: the interface has no read method, so no part of the app can read what a person copied elsewhere. `eslint.config.js` adds the pair `["navigator", "clipboard"]` to `platformProperties` of rule 3, so `ui-web` cannot call it directly, and `tools/lint-rules/platform-boundary.test.mjs` gets the case. The tests that build a `Platform` object (`packages/platform/tests/current.test.ts`, `types.test.ts`) and any app test that does gain the member. A native clipboard is the native build's. Check: unit tests in jsdom with a fake `navigator.clipboard`: `true` on success, `false` on a rejection, on a throw and when the object is missing, `createWebPlatform()` calls nothing; the members test lists `clipboard`; the lint-rule test finds `navigator.clipboard` in `ui-web` reported and in `apps/web` not.
- R20. Texts. Every text goes through `@toki/i18n/react`: a new namespace `messageBar` in `messageBar.ts` of `en` and `vi`, with one import and one entry in each `index.ts`: `label` ("Message actions"), `react` ("Add reaction"), `reply` ("Reply in thread"), `more` ("More actions"), `copy` ("Copy text"), `copied` ("Copied text"). All six English texts are the prototype's, so none is a proposal (D-139); the Vietnamese texts are written by the builder and reviewed by TOKI-080, with no pronoun (D-188 is open). The words of Pin or Unpin, Edit and Delete are the keys of TOKI-048 and TOKI-047, and the failure text is `common.error.actionFailed`; this work duplicates none of them. No text is in a component or in `packages/ui-web`. Check: `pnpm i18n:check` exits 0; a test renders the bar and the menu in English and in Vietnamese; a search of the folder for a quoted English word finds none outside the catalogs and tests.
- R21. Accessibility. Every button of the bar is an `IconButton` with a name (the lint rule `toki/icon-only-button-name` passes); the toolbar has a name; the menu has a name and arrow keys (TOKI-014); a button that is a toggle in a later entry carries `aria-pressed` through `pressed`. The controls are 40 px by 40 px in tap mode (F38). Colour is not the only sign of a pressed button: `aria-pressed` is in the DOM. The row is focusable and has a focus ring (R9). The bar is `display: none` and so absent for a screen reader until the row is shown (R5), and shown for a screen reader user who focuses the row. This work adds no `transition` or `animation` to the bar, so `prefers-reduced-motion` needs no rule (the prototype's `.ib` transition is not kept: the same decision as TOKI-042 R19 on `.msg`). Check: roles and names by Testing Library; the lint rule over the folder; a test reads the rules of the bar's classes in `message-bar.css` and finds no `transition` or `animation`; the browser test reads the button sizes in tap mode.
- R22. Cost of a row. The bar is rendered for every message of the window, so it holds no timer, no `matchMedia` listener and no store subscription of its own for each row: `useTapMode()` shares one listener (one `matchMedia` object and one set of subscribers for the page), the active row is one store (R7), and the entry hooks read the same slices that the neighbours' hooks read. A change to one message re-renders the bar of that message only. ## Design
### How the bar is shown
```
UserMessage (TOKI-042) --- useRow(id) ---> { active, rootProps }  (R7)
   inner box .message  [ avatar | column ] [ MessageBar ]       (last child, R1)
MessageBar
   facts = useConversationFacts(...)           (R17)
   bar specs  = useBarSpecs(ctx)   smile, reply            (entries.ts, R10)
   menu specs = useMenuSpecs(ctx)  { message: copy, pin ; owner: edit, delete }
   <div role="toolbar"> IconButton ... [More -> Menu] </div>
CSS: hover mode: shown by :hover, :focus-within, .act        (R5)
     tap mode  : shown by :focus-within, .act, below the text (R6)
```
- Everything that decides whether a button is drawn is a function of the message, the facts and the hooks of the neighbours; the bar keeps no copy of any of it.
- The tap is a click handler on the row's own box, and the show and hide is CSS: the script writes one value (`tapped`) and TOKI-042 turns it into the class `act`. On a hover device no script runs for the bar at all.
- `useRow` is the one hook the row calls (TOKI-042 R14 rule (g)): it is called first on every render of `UserMessage`, so a pending item that confirms keeps its row and its hooks.

### Why the entries are hooks in one file
The neighbours already give a hook each (`usePinActions`, `useMessageActions`, `useReactionPicker`, `useOpenThread`), and later work (Later) adds two more. A table of components would hide from the bar whether the menu is empty; a table of functions could not call hooks. Two hand-written hooks in one file keep the count of hooks fixed, let the bar know whether it has any button or menu item, and make a later ticket's change one hook and one line, which is the rule of TOKI-041 R4 and TOKI-042 R14 applied to this place.

### What the prototype does and this work changes
The prototype shows the bar for a pending message and for every ctx but `x`; here a pending item gets none (concern 1). Its bar shows on hover only on a wide window and by a tap only when the app is 720 px or less wide, which leaves a touch tablet with no way; here tap mode is also any screen that cannot hover (concern 3). Its bar buttons cannot be reached by the keyboard when the row has no focusable control, and a focused bar button of a row the pointer left disappears; here the row is focusable and `:focus-within` shows the bar (concern 4). It keeps the tapped message until the conversation changes; here Escape, a second tap, another message and the row leaving the page also clear it (concern 2). It copies with `navigator.clipboard` directly; here through the platform package (concern 6). Its menu holds Turn into task and Remind me about this, which are Tasks (phase 2) and Later (TOKI-067).

### Known limits
- A More menu open on a row that is scrolled far enough to leave the window of the list closes with the row; the list keeps only the row that holds focus, and focus is in the menu. A short scroll keeps the row (the overscan is 10 rows) and the menu follows its button (TOKI-014 R23).
- The bar overlaps the last 16 px of the message above (9 px of them over a message that starts a group, which has 7 px of padding above it); that is the prototype's look, and it is in front because it comes later in the page.
- A hybrid device with a mouse and a touch screen reports a primary pointer that hovers, so it gets hover mode; a tap there shows the bar through the hover the browser emulates.

## Data safety
- Copy text writes to the clipboard what the person already sees, on their own press; the platform interface has no read method, so the app cannot read the clipboard (R19). The text is not logged and not sent anywhere.
- The bar sends no request itself; every request is the neighbour's and carries the checks of the server, which decides who may react, pin, edit and delete. The bar only leaves out what the permission functions refuse (R17), so a menu that was open when the person lost the right gets the server's refusal from the owner of the action.
- The active row holds a message id in memory only; nothing is stored.

## Areas of concern
1. What a waiting or a failed message offers. Not decided. The prototype draws the bar for a waiting message and its Reply, reaction, pin and edit buttons would act on a message that has no id on the server; the log gives a failed message only Retry and Delete beside the time (D-087, F11) and says nothing of a bar. TOKI-042 R17 leaves the question to this ticket. Proposal, not a decision: no bar for a waiting, a sending or a failed message (R3), because every action but one needs the server's message. The one that could apply is Copy text: a person whose message failed may want the text before they press Delete, which discards it; the other way is a bar with only More, holding only Copy text, for a failed message. A different answer changes `MessageBar` and the table of R3, and nothing else. Owner: Thanh Truong (product owner).
2. When the active row stops being active. Decided in this spec (the Blueprint leaves it to the builder): a second tap on the same message and a tap on another one clear or move it, as the prototype does; the conversation changing, the row leaving the page and Escape clear it as well (R7, R9). Reason: the prototype clears the state only when a conversation opens, so a keyboard user or a person who scrolls would keep a bar open with no way to dismiss it; the three additions cost one line each and keep one active row for the page. Owner: Thanh Truong.
3. Touch screens wider than 720 px. Decided in this spec: tap mode is a screen under 720 px or a screen whose primary pointer cannot hover (R6). Reason: D-067 and NFR-02 ask for every action on touch screens, F38 and F39 give the tap only for under 720 px, and the prototype tests the width alone, so a touch tablet in landscape would have a bar that only a hover can show. The buttons are 40 px there too, the size of F38, on the same grounds. Owner: Thanh Truong.
4. How the keyboard reaches the bar. Decided in this spec: the message is focusable and its bar is shown by `:focus-within`, with arrow keys between the buttons and Escape to leave (R5, R9). Reason: D-075 and NFR-03 ask for names and for arrow keys in menus but say nothing of reaching a message's actions; the prototype's bar is hidden with `display: none` and its buttons cannot be focused unless the row already holds focus. A row that is a tab stop costs one stop for each message of the window. Owner: Thanh Truong.
5. What Copy text copies. Decided in this spec: the stored text of the message, as sent, with its marks and names (R14). Reason: the prototype copies `m.text` and the server stores the text as sent (TOKI-037 R4); copying the drawn text would make a second rule that TOKI-049 and TOKI-050 would each have to keep in step. The words of the toast are the prototype's. Owner: Thanh Truong.
6. The clipboard in the platform package. Decided in this spec: `Platform` gets `clipboard.writeText` and nothing that reads (R19), and rule 3 of lint bans `navigator.clipboard` in `ui-web`. Reason: the technical design says components reach the device's features through the platform package, and the lint rule today lists notifications, storage, the service worker and audio only, so a direct `navigator.clipboard` would pass lint but break the design; TOKI-018 R1 and TOKI-099 already show the way to add a member. A write-only interface keeps the app from reading what a person copied elsewhere. Owner: Thanh Truong.
7. Where Later and Tasks add their actions. Decided in this spec: the two hooks of `entries.ts` (R10); Save for Later is TOKI-067's and "Turn into task" waits for Tasks (phase 2), and this work draws neither. Reason: Later is in phase 1 and Tasks is not (the scope of phase 1 lists Later and lists Tasks as a later phase), and the prototype's menu holds both. Owner: Thanh Truong.
8. Which actions an archived channel shows. Decided in this spec: the buttons follow the permission functions, so an archived channel shows no smile, no Pin, Edit or Delete, and keeps Reply in thread (it opens the thread read-only) and Copy text (R11, R12, R15, R16, R17). Reason: the functions of TOKI-027 are what the server enforces, and TOKI-047 R17 and TOKI-048 R14 already leave a refused entry out instead of drawing it disabled; reading a thread and copying text are reads. The direct message with a deactivated person follows the functions too; whether it is read-only for reactions and pins is concern 1 of TOKI-046 and concern 4 of TOKI-048, and the bar follows their answers with no change here. Owner: Thanh Truong.
