# Message action bar design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/message-action-bar.md (Thanh Truong)
Ticket: TOKI-052
Needs: TOKI-042 (the message component, in its open pull request 221: `messageExtensions` with the `Actions` component and `useRow`), TOKI-045 (threads, PR 214: `canOpenThread`, `useOpenThread`), TOKI-046 (reactions, PR 215: `useReactionPicker`), TOKI-047 (edit and delete, PR 213: `useMessageActions`), TOKI-048 (pins, PR 216: `usePinActions`), TOKI-014 (`Menu`, merged), TOKI-018 (the platform package, merged) and TOKI-017 (i18n).

## Goal
A message is drawn in full by TOKI-042 and the work of TOKI-045 to TOKI-048 builds what a person can do to it, but nothing yet lets a person press anything: the place for the bar is empty. This work builds the bar and the menu behind its More button: the smile button, Reply in thread, More with Copy text, Pin or Unpin, Edit and Delete. It shows them on hover, on focus and, on narrow and touch screens, on a tap, so that no action is hover-only (D-067). It also gives copy a device clipboard, which the app reaches only through the platform package.

What is drawn
- R3. When the bar is drawn. `MessageBar` is the component TOKI-042 renders for a user message and for a pending item (its R17). It renders the bar only for an item of `kind` `message` whose message has no `deletedAt`; for an item of `kind` `pending` (waiting, sending or failed) it renders `null` (the proposal of concern 1: a message with no server id has nothing to react to, reply to, pin, edit or delete). While the editor of TOKI-047 is open for the message (`useMessageActions(...).editing`) it renders `null` and stays mounted, because TOKI-042 R17 gives that state to the component that owns it; it draws the bar again when the editor closes. It renders `null` when the bar would hold no button (R10). Check: a table of item kinds and states (confirmed, waiting, sending, failed, editing, no button) with the expected presence; a test that the component stays mounted while it renders `null` for `editing` (a probe hook in it keeps its state); a row of a pending item also has no active state (R7).
- R4. The bar, as the prototype draws it (`.acts`, line 1371). One element with `role="toolbar"` and the accessible name `messageBar.label` ("Message actions"), the last child of the inner box `.message` of TOKI-042 (so its offsets are measured from the box, not from the outer wrapper), holding the buttons of R10 in order, each an `IconButton` of `@toki/ui-web` (the label is its only name; none has a `title`, because the prototype has no tooltip and every name is read from the `aria-label`). The numbers were measured in headless Chrome on the prototype at 1300 and 500 px wide, in both looks:

  | | Hover mode (1300 px, a pointer that hovers) | Tap mode (500 px, R6) |
  | :---- | :---- | :---- |
  | Position | `absolute`, `right: 12px`, `top: -16px`, `z-index: 2` | in the flow of the box, which this work's stylesheet makes `flex-wrap: wrap` in tap mode (R6): `order: 3`, `flex-basis: 100%`, `position: static`, margin `6px 0 2px calc(var(--av) + var(--gap))`, no shadow |
  | Frame | 1 px `--line` border, radius `--radius-sm` (10 in Calm, 8 in Focus), `--surface` background, shadow `--pop`, padding 2 px, gap 0 | the same, without the shadow |
  | Button | 30 x 30 | 40 x 40 |
  | Four buttons (smile, reply, bookmark, more) | 126 x 36 | height 46; the bar spans the text column (407 px at 500 px in Calm, 413 in Focus) |
  | Distance from the top of the inner box | -16 | 6 px margin under the text, so the bar is below the message and never over its text |

  The bookmark of the measurement is the prototype's and belongs to TOKI-067; the bar is `30 * n + 6` px wide and 36 px high in hover mode for `n` buttons: with the buttons of this work it has three (smile, reply, more) and is 96 x 36, and with the bookmark that TOKI-067 adds it has four and is 126 x 36. The browser test counts the buttons of the toolbar in the page and checks the width from that count, so an entry that a later ticket adds to `entries.ts` needs no change to the test. Tap mode has no `right` offset: the bar is in the flow, so there is no 8 px variant. The button states are the prototype's `.ib`: hover background `--hover`, and `.on` (the pressed look, `--accent-soft`) for a button with `aria-pressed`. The look is set by the existing tokens, so the component has no branch on the look. Check: in the browser test (R23) at 1300 and 500 px, and in a touch context at 1100 px, in the three looks (was both looks), the sizes, offsets and margins above are read from the page within 1 px; a jsdom test checks the role, the name, the order and the absence of `title`.
- R5. When the bar shows on a pointer that hovers (hover mode). The bar is in the page for every message and `display: none` until one of these is true: the pointer is on the message (`:hover` of the inner box), keyboard focus is inside the message (`.message:focus-visible` or `.message:has(:focus-visible)`, never `:focus-within`), or the message is the active row (R7, the class `act` that TOKI-042 sets from `useRow`). `:focus-within` is not used because the row is focusable (R7, R9): a mouse click or a tap on the text focuses the row, `:focus-within` would then keep the bar visible after the pointer left (a stuck bar on the last clicked message) and after a second tap in tap mode (R6); `:focus-visible` matches only focus that came from the keyboard or from a script after a keyboard use, and a focus that does not match it is covered by the hold of R7. `display: none` takes the buttons out of the tab order and out of what a screen reader reads, so the buttons of a message that is not shown are not in the way (R9). The rule is CSS only: no script runs on a pointer move. Check: the browser test hovers a message and finds the bar visible with the sizes of R4, moves the pointer away and finds it `display: none`; clicks the text with the mouse, moves the pointer away and finds the bar `display: none` although the row is the active element; presses Tab to the row and finds the bar visible, and a button of it focused with Tab and visible; sets the class `act` and finds it visible.
- R6. Tap mode. "Tap mode" is a screen narrower than 720 px, or a screen whose primary pointer cannot hover, one media query: `TAP_MEDIA = "(max-width: 719px), (hover: none)"`. Its first condition is the text of the shell's narrow line (`useNarrow` of `@toki/ui-web`, TOKI-015 R16 and R29, which allows exactly four conditions), so a window of 719.5 px is the same for the shell and for the bar and there is no third text for 719 px; D-068 puts the line at 720 px, and D-067 asks for touch screens, which concern 3 settles. `tap-mode.ts` exports the constant, which TOKI-066 (Activity) imports for its own buttons so that the shell, the bar and that screen agree on what a touch screen is, and `useTapMode()` (a `useSyncExternalStore` over `matchMedia(TAP_MEDIA)` given by `deps.ts`, `false` when `matchMedia` does not exist); `message-bar.css` uses the same text in its `@media` rule, and a test reads both, and the first condition of `useNarrow.ts`, and finds them equal, so the script, the stylesheet and the shell cannot disagree. In tap mode the bar is `display: none` unless the message is the active row or keyboard focus is inside it (the `:focus-visible` selectors of R5), and when it is shown it has the second column of R4's table (below the message, 40 px buttons: F38 asks for 40 px controls and the bar under the message "never over the text"). The row wraps by this work's own rule inside the same `@media` block, `.message:has(> .message-bar) { flex-wrap: wrap }`, because TOKI-042 R17 makes the inner box wrap only under 720 px, and a touch screen of 1100 px has to put the bar below the text as well; the rule is scoped to a row that holds a bar, so a row with no bar is as TOKI-042 left it, and it makes no change to `message.css`. The margin is `calc(var(--av) + var(--gap))`, the avatar and the gap of the look, so the bar starts at the text column at every width (the prototype's fixed 10 px is its narrow gap). A hover does not show the bar in tap mode (the prototype's rule `.msg:not(.act) .acts{display:none}`, which has no focus term; the keyboard term added here is `:focus-visible`, R5). Check: a test reads `message-bar.css` and finds the media text equal to `TAP_MEDIA` and the wrap rule inside it; the browser test at 500 px finds the bar hidden on hover and shown below the message (its top at or below the bottom of the text, its left at the text column) after a tap, and, in a touch context (`isMobile`, `hasTouch`) at 1100 px, the same, with the bar's top at or below the bottom of the text and its left at the text column; a tap, then a second tap on the same message, hides the bar although the row keeps focus.
- R7. The active row and `useRow`. `active-row.ts` holds one value for the whole page, `{ tapped: string | null, held: string | null }`, with `subscribe`, a snapshot and these functions: `toggleTapped(id)` (sets `tapped` to the id, or to `null` when it already is that id: the prototype's `S.actMsg===id?null:id`, so a tap on another message moves the bar and a second tap on the same one hides it), `clearTapped()`, `hold(id)` (takes one hold on the id and sets `held`; returns the function that releases that hold, once, and clears `held` only when no hold on that id is left and `held` is still that id; two holds on one id, as when a menu entry opens a second menu, keep the row held until both are released), `settleHold(release)` (runs the settle rule below and then calls `release`; it is what a menu, a picker or an editor calls when it closes) and `isActive(id)` (`tapped === id || held === id`). `useRow(id)` is the hook TOKI-042 R14 declares: it returns `{ active, rootProps }` where `active` comes from `useSyncExternalStore` over `isActive(id)`, a boolean, so a change re-renders only the row that becomes active and the row that stops being, and never the others. `rootProps` is `{ onClick, onKeyDown, tabIndex: 0, role: "group", "aria-labelledby": headerId(id) }` made once per `id` (`useMemo`); `UserMessage` spreads it on the inner box (TOKI-042 R17), and TOKI-042 R4 gives the header line the id `message-header-<id>`, on the gutter time of a grouped row that has no header line. The handlers act only on a row whose outer wrapper has `data-delivery="confirmed"` (`event.currentTarget.closest("[data-delivery]")`): a waiting, sending or failed row draws no bar (R3), so a tap on it sets nothing and does not tint it; TOKI-042 R14 and R17 have `UserMessage` spread no `rootProps` and set no `act` on a pending item, so the waiting row is not a tab stop with nothing to show; the check of `data-delivery` here stays as a guard, so a handler never acts on a row that has no bar. The row is cleared when it leaves the page: the cleanup of `useRow` calls `clearTapped()` when `tapped` is still its id, so a conversation change, a row that scrolls out of the window of the list (TOKI-041 R20) and a removed message each end the state, and a stale id is never kept. `held` is the row whose menu or picker is open (R13, R11) or whose editor is open (R16); it keeps the bar of a hover device in view while the pointer is over the menu, which is outside the row and would otherwise hide the bar (and its More button, the anchor of the menu) under it, and it keeps the bar displayed while focus returns to a button inside it. The rule of the hold: it is taken before any of these focus calls (`hold(id)` on the press that opens the picker or the menu, and in `startEdit`'s call), and released only after focus has landed, never in the same step as the close: when the picker, the menu or the editor closes, the bar waits one microtask (`queueMicrotask`, no timer), then looks at `document.activeElement`; when it is inside the bar's toolbar the hold stays and is released by the first `focusout` of the toolbar to an element outside it; when it is not (a choice that moved focus elsewhere, a press outside) the hold is released at once. A button inside a bar that is `display: none` cannot take focus, so without this order the focus returned to the smile button, to More or, after an edit, to More would fall to `body`. Check: with a fake list of three rows, a tap on the first sets `act`, a tap on the second moves it, a second tap on the second clears it; a counting render shows that a tap re-renders two rows at most; unmounting the active row clears the state; `hold` keeps the row active and its release does not clear a hold made by another row; two holds on one id keep the row active until both are released; `settleHold` leaves the hold in place when focus is inside the toolbar after one microtask and releases it at once when it is not; `useRow` returns a constant object when the id and the state do not change; a click on a row whose wrapper has `data-delivery="waiting"` sets nothing; the hold: a fake picker that closes and returns focus to its anchor in the same task leaves the button focused and its bar displayed, and the hold is released on the `focusout` of the toolbar.
- R8. What a tap does. `onClick` of `rootProps` acts only in tap mode (a click on a hover device changes nothing: the bar there is the pointer's and the keyboard's). It does nothing when the click did not happen inside the row's own DOM (a `Menu`, the picker and the dialogs are portals: a React event from them reaches the row's handler through the React tree, so the handler first checks that `event.currentTarget.contains(event.target)`), and nothing when the target is inside a control: the closest ancestor of the target that matches `button, a, input, textarea, select, summary, [contenteditable], [role="menu"], [role="toolbar"], [data-no-tap]` (the prototype's list, with the toolbar and the menu made explicit). Otherwise it calls `toggleTapped(id)`; when that call has shown the bar, an effect calls `rowRef.current?.scrollIntoView({ block: "nearest" })` (guarded for a missing method), so a message tapped at the bottom edge of the scroller does not leave its bar below the fold (the proposal of concern 2; TOKI-041 R15 and R16 say what the list does at the bottom, and this is one scroll of the row's own bar). A press on a reaction chip, the thread link, a link in the text, a bar button or a menu item therefore never toggles the bar. The name and the avatar are plain text until TOKI-057 fills `openProfile` (TOKI-042 R7), so a tap on them toggles the bar; once they are buttons they are controls and do not, and TOKI-057 keeps that. Check: tap mode on, a click on the text toggles; a click on a `button`, on a link, inside the open menu (a portal) and inside the toolbar does not; tap mode off, a click on the text does not; a click that starts in the row and ends elsewhere is not a click and does nothing; a tapped row near the bottom edge calls `scrollIntoView` once with `block: "nearest"`, a hiding tap calls it never; a probe `openProfile` that makes the name a button is a control and does not toggle.
- R9. Keyboard. The inner box is focusable (`tabIndex: 0` from R7) and has a role and a name, so a screen reader does not land on an unnamed generic element: `role="group"` and `aria-labelledby` the header line of TOKI-042 (name and time), whose `id` TOKI-042 R4 sets (on the gutter time for a grouped row with no header line, so the name of such a row is its time). A person who uses the keyboard reaches a message with Tab, and `:focus-visible` shows its bar (R5, R6) with the buttons after the text, the reactions and the thread link in the tab order. A mouse click or a tap on the text focuses the row too but does not show the bar (R5). The row's `rowRef` (TOKI-042 R14) is what Escape focuses. The toolbar also moves focus between its buttons with ArrowLeft and ArrowRight (wrapping is not done) and Home and End, though every button stays a tab stop. Escape, pressed in the row or in the toolbar when the bar is open by a tap or a hold, clears the tapped row and moves focus to the row through `rowRef`; Escape in an open `Menu` is the menu's (TOKI-014) and does not reach this handler (the check of R8 again, and `defaultPrevented`). The row and every button have the visible focus ring of the design system. Cost: every message of the window (the visible rows plus 10 on each side, TOKI-041 R20) is a tab stop between the list and the composer, so a full window of about 35 messages takes about 35 Tab presses to cross, plus the buttons of the message the person is in (Known limits; concern 4 states the proposal and the alternative). Check: a keyboard test with `user-event`: Tab reaches the row and the bar appears, Tab again reaches the buttons in order, the arrows and Home and End move focus, Escape on a tapped row clears it and focuses the row, Escape in the open menu closes the menu and leaves the bar; the row has `role="group"` and a name; a list of 40 fake rows has one tab stop for each row and no more than the buttons of the focused one besides.
- R10. The entries, in one file. `entries.ts` is the one place where an action is added, as TOKI-042 R14 makes `extensions.ts` the one place for a piece of a message. An action is described by a hook that returns a description or `null`: `type ActionSpec = { key: string; label: string; icon: IconName; onSelect: (anchor: RefObject<HTMLElement | null>) => void; pressed?: boolean; variant?: "default" | "danger" }` and `type ActionContext = { message: MessageEntry; conversationId: string; surface: "list" | "thread"; facts: ConversationFacts | null; editing: boolean }`. The file exports two hooks written by hand with a fixed order, `useBarSpecs(ctx)` (the smile, then Reply in thread; TOKI-067 adds Save for Later after them) and `useMenuSpecs(ctx)`, which returns `{ message: ActionSpec[], owner: ActionSpec[] }`: Copy text, then Pin to conversation or Unpin (TOKI-067 adds Remind me about this here) in `message`, and Edit, then Delete in `owner` (the prototype's order and its rule between the two groups). Each is a call to a hook with the same count of hooks on every render, so a list that is composed by hand never breaks the rules of hooks and a later ticket adds one line and one hook of its own. An entry that opens a menu or a picker of its own (TOKI-067's reminder menu) calls `hold(message.id)` of `active-row.ts` in its `onSelect` before it opens it and `settleHold(release)` when it closes, so the bar stays displayed, and its anchor with it, while that menu is open; `ActionSpec` has no `onClose` for this, and the hold of the More menu that closes on the choice is a second hold on the same id (R7). The More button is not an entry: it is drawn after the entries of the bar when `useMenuSpecs` returns at least one spec in either group, and it is the last button, as in the prototype. A bar with no button (no entry and no menu spec) is not drawn (R3). Check: a type test fixes the two types and the two hooks; a test renders each case of R11 to R16 and reads the order of the buttons and of the menu items from the DOM; a test adds a probe hook to `useBarSpecs` and `useMenuSpecs` with `vi.mock` of `entries.ts` and finds its button and its menu item in the right place; a menu with only the `owner` group has no separator and a menu with both has one `MenuSeparator` between them.
- R11. The smile button. Label `messageBar.react` ("Add reaction", the prototype's `aria-label`), icon `smile`, drawn when `canPostInConversation(me, facts).allowed === true` of `@toki/shared` (the function the server uses for reacting, TOKI-046 R4 step 6 and R5; main has no `canReactToMessage`, and the functions return a `Decision`, not a boolean; a person who may not react is not offered the button: archived channel, concern 8), for a message of kind `user`. It calls `useReactionPicker().openFor(message, anchorRef, { onClose })` of TOKI-046 R20 with the button's own ref as the anchor, and sends no request; the picker, its Escape and the return of focus to the button are TOKI-046's (R19, R20 there), and the element is drawn from what the hook returns (TOKI-046 R20 returns `{ openFor, picker }`, `picker` being `null` while closed, and the bar renders it beside the toolbar, so the cost of R22 is one `null` for every closed bar; the hook calls `onClose` once on every close and puts focus on the anchor after every close). The row is held (R7) before `openFor` is called and released after the close by the settle rule of R7, because the picker returns focus to the smile button, which is inside the bar. - R12. Reply in thread. Label `messageBar.reply` ("Reply in thread", the prototype), icon `reply`, drawn when `canOpenThread(message)` of TOKI-045 R20 is true (a message of kind `user` with no `parentId`: a reply, a system line and a pending message have none, AC-087, TS-136), when `surface` is `"list"` (the prototype draws it for the main list only; the root in the panel already shows its thread) and when the person is a member who may read the conversation (`canReadConversation`). The More menu of a reply has no thread entry either (there is none to hide: no menu entry of this work opens a thread). - R13. The More button and its menu. Label `messageBar.more` ("More actions", the prototype), icon `more`. It is a button made with `useMenuTrigger` of `@toki/ui-web` (TOKI-014 R24), so a click or ArrowDown opens `Menu` with the first item focused, ArrowUp opens it with the last, and Escape, a choice, Tab and a press outside close it and return focus to the button. The menu has the accessible name `messageBar.more`, `align="end"` (its right edge on the button's, the prototype's `posMenu`), and holds `MenuItem`s from `useMenuSpecs` with the spec's icon and label, a `MenuSeparator` between the groups, and `variant="danger"` for Delete. While the menu is open the row is held (R7), taken before the menu opens, and released by the settle rule of R7 after it closes, whatever the reason, so the focus that returns to the More button lands on a displayed button. A choice runs the spec's `onSelect` and then closes the menu (the `select` reason of `Menu`). If the row unmounts while the menu is open (a long scroll takes it out of the window of TOKI-041, its overscan being 10 rows) the menu goes with it and throws nothing (Known limits). Check: opening with click, ArrowDown and ArrowUp focuses the first and the last item; each close reason closes it and returns focus to the More button; the row has the class `act` while the menu is open and, after a close by Escape with the pointer away from the row, the More button holds focus and is visible before the hold is released, and the row is not active after the toolbar loses focus; unmounting the row with the menu open leaves no listener and no error; the separator and the `danger` variant as in R10.
- R14. Copy text. Label `messageBar.copy` ("Copy text", the prototype), icon `copy`; in the `message` group; drawn when the message has text (`message.text` is not empty after trimming: a message with only files, TOKI-058, has nothing to copy). It writes the stored text of the message, as it was sent (`message.text`, with the marks and the names as typed: the prototype copies `m.text`, and the server stores the text as sent, TOKI-037 R4), by `copyText(text)` of `copy-text.ts`, which calls `clipboard().writeText(text)` of the platform package (R19) and never `navigator.clipboard`; `getPlatform()` throws when no platform is set, and `copyText` catches that and resolves `false`. ## Design
### How the bar is shown
```
UserMessage (TOKI-042) --- useRow(id) ---> { active, rootProps }  (R7)
   inner box .message  [ avatar | column ] [ MessageBar ]       (last child, R1)
MessageBar
   facts = useConversationFacts(...)           (R17)
   bar specs  = useBarSpecs(ctx)   smile, reply            (entries.ts, R10)
   menu specs = useMenuSpecs(ctx)  { message: copy, pin ; owner: edit, delete }
   <div role="toolbar"> IconButton ... [More -> Menu] </div>
CSS: hover mode: shown by :hover, :focus-visible, .act       (R5)
     tap mode  : shown by :focus-visible, .act, below the text (R6)
```
- Everything that decides whether a button is drawn is a function of the message, the facts and the hooks of the neighbours; the bar keeps no copy of any of it.
- The tap is a click handler on the row's own box, and the show and hide is CSS: the script writes one value (`tapped`) and TOKI-042 turns it into the class `act`. On a hover device no script runs for the bar at all.
- `useRow` is the one hook the row calls (TOKI-042 R14 rule (g)): it is called first on every render of `UserMessage`, so a pending item that confirms keeps its row and its hooks.

### Why the entries are hooks in one file
The neighbours already give a hook each (`usePinActions`, `useMessageActions`, `useReactionPicker`, `useOpenThread`), and later work (Later) adds two more. A table of components would hide from the bar whether the menu is empty; a table of functions could not call hooks. Two hand-written hooks in one file keep the count of hooks fixed, let the bar know whether it has any button or menu item, and make a later ticket's change one hook and one line, which is the rule of TOKI-041 R4 and TOKI-042 R14 applied to this place.

### What the prototype does and this work changes
The prototype shows the bar for a pending message and for every ctx but `x`; here a pending item gets none (concern 1). Its bar shows on hover only on a wide window and by a tap only when the app is 720 px or less wide, which leaves a touch tablet with no way; here tap mode is also any screen that cannot hover (concern 3), and the bar is also hidden for a mouse click that merely focused the row. Its bar buttons cannot be reached by the keyboard when the row has no focusable control; here the row is focusable and `:focus-visible` shows the bar (concern 4). It keeps the tapped message until the conversation changes; here Escape, a second tap, another message and the row leaving the page also clear it (concern 2). It copies with `navigator.clipboard` directly; here through the platform package (concern 6). Its menu holds Turn into task and Remind me about this, which are Tasks (phase 2) and Later (TOKI-067).

### Known limits
- A More menu open on a row that is scrolled far enough to leave the window of the list closes with the row; the list keeps only the row that holds focus, and focus is in the menu. A short scroll keeps the row (the overscan is 10 rows) and the menu follows its button (TOKI-014 R23).
- The bar overlaps the last 16 px of the message above (9 px of them over a message that starts a group, which has 7 px of padding above it); that is the prototype's look, and it is in front because it comes later in the page.
- Tab: every message of the window is a tab stop (R9), about 35 Tab presses to cross a full window. The alternative, one stop for the list with the arrow keys moving between messages, is not built (concern 4).
- A hybrid device with a mouse and a touch screen reports a primary pointer that hovers, so it gets hover mode; a tap there shows the bar through the hover the browser emulates.

## Data safety

4. How the keyboard reaches the bar. Not decided: D-075 and NFR-03 ask for names and for arrow keys in menus but say nothing of reaching a message's actions. Proposal, not a decision: the message is focusable with a role and a name, its bar is shown by `:focus-visible`, with arrow keys between the buttons and Escape to leave (R5, R9). Reason: D-067 (no feature is out of reach of the keyboard); the prototype's bar is `display: none` and its buttons cannot be focused unless the row already holds focus. The cost is one Tab stop for each message of the window (about 35 presses to cross a full window); the other way is one tab stop for the list with the arrow keys moving between messages (a roving `tabIndex`), which is more code and a second key model. The product owner may want to rule on it. A different answer changes R5 and R9 and their tests. Owner: Thanh Truong (product owner).
5. What Copy text copies. Decided in this spec: the stored text of the message, as sent, with its marks and names (R14). Reason: the prototype copies `m.text` and the server stores the text as sent (TOKI-037 R4); copying the drawn text would make a second rule that TOKI-049 and TOKI-050 would each have to keep in step. The words of the toast are the prototype's. Owner: Thanh Truong.
6. The clipboard in the platform package. Decided in this spec: `Platform` gets `clipboard.writeText` and nothing that reads (R19). Reason: the technical design says components reach the device's features through the platform package; TOKI-018 R1 and TOKI-099 already show the way to add a member. A write-only interface keeps the app from reading what a person copied elsewhere. No lint rule is added: rule 3 covers `ui-web` only and the clipboard is used from `apps/web`, so what keeps `apps/web` from `navigator.clipboard` is the source test of R2; a lint rule over `apps/web` would be a change to TOKI-002 and is not asked for. Owner: Thanh Truong.
7. Where Later and Tasks add their actions. Decided in this spec: the two hooks of `entries.ts` (R10); Save for Later is TOKI-067's and "Turn into task" waits for Tasks (phase 2), and this work draws neither. Reason: Later is in phase 1 and Tasks is not (the scope of phase 1 lists Later and lists Tasks as a later phase), and the prototype's menu holds both. Owner: Thanh Truong.
8. Which actions an archived channel shows. Decided in this spec: the buttons follow the permission functions, so an archived channel shows no smile, no Pin, Edit or Delete, and keeps Reply in thread (it opens the thread read-only) and Copy text (R11, R12, R15, R16, R17). Reason: the functions of TOKI-027 are what the server enforces, and TOKI-047 R17 and TOKI-048 R14 already leave a refused entry out instead of drawing it disabled; reading a thread and copying text are reads. The direct message with a deactivated person follows the functions too; whether it is read-only for reactions and pins is concern 1 of TOKI-046 and concern 4 of TOKI-048. If either is answered "read-only", the smile and Pin must leave out for that direct message, `ConversationFacts` has no fact for the other person's status, and R17, R11 and R15 change (a fifth fact, or a separate check); the owner of that fact is TOKI-027 (the type and the functions of `@toki/shared`). Owner: Thanh Truong.
