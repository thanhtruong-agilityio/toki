Date: 2026-11-23 · Status: draft for review (concerns 3, 8 and 12 are open for the product owner)

## Goal
The server will keep up to 10 files of any type, each up to 100 MB, for a message (TOKI-058), and the composer has a slot for cards and a gate on Send (TOKI-043). No screen lets a person use them. This work builds that screen: the attach button, drag and drop, paste of an image, one card for each file with its progress, a remove button and Retry, the refusal of a file over 100 MB and of an eleventh file, Send that waits until every file has uploaded, the reason shown when uploading is blocked offline or refused because the disk is full, and the send of a message with files and no text.
The bytes go from the browser straight to storage with the ticket of TOKI-058; this work builds the code that does it and reports progress. A draft restores text only (D-168), so the cards live and die with the composer that shows them.

## Requirements
Limits and calls
- R1. The numbers come from `@toki/shared` and are written nowhere else: `FILE_MAX_BYTES` (104,857,600), `FILE_NAME_MAX` (255), `FILE_UNSENT_MAX_PER_PERSON` (20) of TOKI-058 R3 and `MESSAGE_FILES_MAX` (10) of TOKI-037 R22 (D-042, D-014). The text "Over 100 MB" is made from `FILE_MAX_BYTES` through the size format of R4, not typed. Check: a search of the sources of this work for `104857600`, `100 * 1024`, `10_000_000`-style literals of the limit and for a bare `10` used as the file limit finds none outside tests; the boundary tests of R6 read the constants.
- R2. `createApiClient` (TOKI-032 R9: one request core, 10 seconds, no retry, a path part encoded, an optional `signal` last, no `headers` or `timeoutMs`) gets the group `api.files`: `start(body, signal?)` sends `POST /files` with `StartUploadRequest` and returns `{ status: 200 | 201, file, state, upload }` (TOKI-058 R6, R8); `complete(id, signal?)` sends `POST /files/{id}/complete` and returns `{ file, state, upload: null }` (R10); `drop(id, signal?)` sends `DELETE /files/{id}` and returns nothing, 204 being its answer (R11); `listUnsent(signal?)` sends `GET /files/unsent` and returns `{ files }` (R23). The answers are read with the response schemas that TOKI-058 R3 exports from `packages/shared`, in the form that drops unknown keys (so the key that TOKI-060 adds to `FileEntry` reaches the card). Check: with the fake `fetch` of the existing tests, each method sends the method, path and body as written, a good answer parses, a 204 of `drop` returns, an unknown key in `file` is kept, and an error answer ends as an `ApiError` of the existing kinds with the `code` of the body (`storage_full`, `too_many_unsent_files`, `file_id_in_use`, `upload_incomplete`, `file_rejected`, `file_attached`).
- R3. The upload to storage. `Platform["files"]` (`packages/platform/src/types.ts`) gains `upload(handle, ticket, options?): Promise<UploadResult>`, with `ticket: { url: string; fields: Record<string, string> }`, `options: { onProgress?(sent: number, total: number): void; signal?: AbortSignal }` and `UploadResult = { ok: true } | { ok: false; reason: "network" | "refused" | "aborted"; status: number | null }`. It never rejects for a network, storage or abort outcome. The types name no DOM type (rule 1 of the platform spec). The web implementation (`web/files.ts`) takes `handle` as the browser's `File` and sends one `XMLHttpRequest` `POST` to `ticket.url` with a `FormData` in this order: every entry of `ticket.fields` in the order given, then the field `file` last, with the file's name (TOKI-058 R7: "before the field `file`"); no header of its own, no credentials (`withCredentials` false), no timeout. `onProgress` is called from the `progress` event of `xhr.upload` when `lengthComputable` is true, with `loaded` and `total` of the whole form (so the last value may be a little under the file size and never over `total`). A status from 200 to 299 (storage answers 204) is `{ ok: true }`; any other status is `refused` with that status (an expired ticket and a size the policy refuses are 4xx); an `error` or `timeout` event is `network`; an abort through `signal`, also one that was already aborted before the call, is `aborted` and sends nothing. A handle that is not a `File` throws a `TypeError` (a programming error, not an outcome). XMLHttpRequest is used because `fetch` has no upload progress in browsers; it is the one use of it, in `platform`, which the boundary lint allows (the lint bans it in `ui-web` and `client-core`, and `apps/web/tests/conversation/boundary.test.ts` bans it in the conversation code). Check: a unit test with a fake `XMLHttpRequest` class: the form has the ticket fields in order and `file` last, `withCredentials` false, no `setRequestHeader`; progress events become `onProgress` calls and an event that is not `lengthComputable` calls none; 204 and 200 are ok, 403 and 400 are `refused` with the status, `error` and `timeout` are `network`; `abort` of the signal calls `xhr.abort` and the result is `aborted`, and an aborted signal at the call sends nothing; a non-`File` handle throws. A Playwright test (R20) shows that a real browser sends a multipart body whose parts are in that order and whose last part holds the bytes.
- R4. File sizes. `@toki/i18n` exports `formatFileSize(language, bytes)`: below 1,024 it is "N B"; from there it divides by 1,024 up to "GB"; the number has one decimal when it is under 10 and none otherwise (the prototype's "96 KB", "412 KB", "4 KB", "184 KB"; "1.5 MB"), written with `formatNumber` of the language (a comma decimal in Vietnamese); the unit symbols `B`, `KB`, `MB`, `GB` are symbols, the same in both languages, like a number format and not a sentence (Decided in this spec, concern 10). The base is 1,024 so that `FILE_MAX_BYTES` reads "100 MB" (TOKI-058 concern 2). Check: a table test: 0 gives "0 B", 1,023 "1,023 B", 1,024 "1 KB", 1,536 "1.5 KB", 98,304 "96 KB", 421,888 "412 KB", `FILE_MAX_BYTES` "100 MB", 104,857,601 "100 MB" (a card never shows it, R6), 1,073,741,824 "1 GB"; Vietnamese writes "1,5 KB"; no `.tsx` of `apps/web` or `ui-web` formats a size by hand.

The cards (`packages/client-core/src/files/`)
- R5. The set of cards. `createAttachmentSet(options)` returns the set of one composer: `options` are `api` (the methods of R2), `upload` (the function of R3, so a test passes a fake), `newId` (a UUID version 7, the generator of `apps/web/src/ids.ts`), `conversationId`, `isOnline(): boolean` (R12), `onNoAccess()` and `onStale()` (R8). The set has `getState()`, `subscribe(listener)` (the state is an object that is replaced and never changed, as the store state of client-core), `add(files)`, `remove(id)`, `retry(id)`, `readyIds()`, `readyFiles()`, `markSent()` and `dispose()`. `getState()` is `{ cards, hasFiles, blocked }`. A card is `{ id, name, size, contentType, status, progress, reason, retryable, file }`: `status` is `"uploading"`, `"ready"`, `"failed"` or `"too_big"`; `progress` is a number from 0 to 1 while `uploading` and `null` while it waits for a place or for the server (R7); `reason` is `null` or one of `"failed"`, `"storage_full"`, `"too_many_unsent"`, `"no_access"`, `"stale"`, `"invalid"` (R8); `retryable` is true for a `failed` card whose reason can change by trying again; `file` is the `FileEntry` of the answer once known. `hasFiles` is true when at least one card is `ready`; `blocked` is true when at least one card is not `ready` (R10). The package keeps its rules: no DOM or browser global, no text, no key of `@toki/i18n`, no `Date.now(` or `new Date()`, no timer of its own. `PickedFile` of `@toki/platform` is the input type of `add`, so a picked file, a dropped file and a pasted image enter the same way (R14, R15). Check: `pnpm lint` and the search script of TOKI-008 find nothing in `packages/client-core/src/files/`; a type test builds the set with only the required options; the state object is replaced for each change and the listener is called once for each, and not for a call that changes nothing.
- R6. What `add` does. It returns `{ added: number, refused: { offline: boolean, overLimit: number } }`. (a) When `isOnline()` is false it adds nothing and returns `offline: true` (R12). (b) The cards count toward `MESSAGE_FILES_MAX`, whatever their state, a red card included (concern 6): files beyond the free places are not added and counted in `overLimit` (an eleventh file is refused and the ten stay, AC-026, TS-041); a call with a list adds the first files that fit, in the order given. (c) A file whose `size` is over `FILE_MAX_BYTES` becomes a card with status `too_big` at once: no call is made for it, and its name is on the card (AC-027, TS-042); a file of exactly `FILE_MAX_BYTES`, and of 0 bytes, is accepted. (d) The name is cleaned, not rewritten: U+0000 and lone surrogates are removed (the rule of TOKI-037 R4 that TOKI-058 R3 applies to `name`); a name that is empty after that gets `"file"` plus the extension of a known image type (`image/png` gives `.png`, `image/jpeg` `.jpg`, `image/gif` `.gif`, `image/webp` `.webp`; no extension for another type), so a pasted image with no name is `file.png`; a name over `FILE_NAME_MAX` code points is shortened before its last dot and keeps its extension (and is cut at `FILE_NAME_MAX` when the extension alone is longer), because the server refuses it with a 400 that no retry cures (TOKI-058 R3). (e) Each other file gets `id = newId()` and starts at R7. A refused file is never a card, so nothing is left to remove. Check: a table test with the fake `api` and `upload`: 10 files add 10 cards and an 11th adds none with `overLimit` 1; one call with 12 files adds 10 and returns `overLimit` 2; with 9 cards a call with 3 files adds 1; a card that is `too_big` still counts; `FILE_MAX_BYTES` is accepted and one byte more is `too_big` with zero calls of the fake `api` and `upload`; 0 bytes is accepted; names: "a\u0000b" gives "ab", "\uD800.png" gives ".png" (the lone surrogate is removed), "" with `image/png` gives "file.png", "" with another type gives "file", a 300-letter name with ".pdf" gives 255 code points ending ".pdf"; offline returns `offline: true`, adds nothing and calls nothing.
- R7. The pipeline of one card. At most 3 cards run at the same time (`UPLOAD_PARALLEL`, concern 11); the others wait, with `progress` `null`, and start in card order as a place frees. A card that runs does, in this order: (1) `api.files.start({ id, conversationId, name, size, contentType })` (`contentType` only when `PickedFile.mimeType` is not empty); the answer 201 or 200 with `upload` null and state `ready` (a repeat of a file that is already stored) goes straight to the end; (2) `upload(handle, { url, fields }, { onProgress, signal })` with the ticket of the answer; `progress` is `sent / total`, rounded down to a whole percent, and the state is replaced only when the whole percent changes (at most 101 changes for one file and no timer); (3) `api.files.complete(id)`, during which `progress` is `null` again; (4) the card is `ready` with `file` the entry of the answer. The ticket is asked when a place is free and not before, so a card that waited does not hold a ticket that ages (TOKI-058 R3: 15 minutes). The transfer has no time limit of its own: storage checks the ticket only when a request starts, and a person on a slow line must not be cut at a number (concern 11). Check: with a fake `api` and a fake `upload` that the test resolves by hand: 5 files call `start` for 3 and for the 4th only when one ends, in order; `progress` is `null` before `start` answers and after the last byte, and the values in between follow the fake's events, with one state change for each whole percent (events of 0.001 apart change the state once); `complete` is called after the upload only; a `ready` answer with `upload` null never calls `upload`; a failure of one card does not stop the others; `start` is never called for a `too_big` card.
- R8. Failures and Retry. A failure of the pipeline makes the card `failed` and sets its reason by this table (the screen of D-131 for each status, read with `classifyApiError` of TOKI-032 R8 where it applies):

| What happened | `reason` | `retryable` | Also |
| :---- | :---- | :---- | :---- |
| `upload` gives `network` or `refused`; `ApiError` of kind `network` or `timeout`; any 5xx other than 507; 409 `upload_incomplete`; 409 `file_rejected` | `failed` | yes | |
| 507 `storage_full` (TOKI-103 R9) | `storage_full` | yes | the card shows `storage.refused` (TOKI-103 R17, D-106) |
| 409 `too_many_unsent_files` after the recovery of R11 | `too_many_unsent` | yes | |
| 403 or 404 | `no_access` | no | calls `onNoAccess()` for a 404 (TOKI-043 R7) |
| 409 `channel_archived` or `conversation_read_only` | `stale` | no | calls `onStale()` (the page asks the store for a fresh copy, as TOKI-043 R7) |
| 400, an answer that does not parse, any other status | `invalid` | no | |
| the call or the upload was aborted by the set itself (remove, dispose) | none: the card is gone | | |

`retry(id)` on a `failed` card with `retryable` true, and `isOnline()` true, makes it `uploading` again and runs R7 from step 1 with the same id (a stored file is answered 200 with a new ticket, or with `upload` null when it is already `ready`, TOKI-058 R8); a 409 `file_id_in_use` at step 1 (the row was removed by `file_rejected` or the cleanup) makes the set give the card a new id (`newId()`) and run step 1 once more, and a second `file_id_in_use` is `failed`. It returns `"started"`, `"offline"` (nothing changes, R12) or `"not_retryable"` (a card that is not `failed`, a reason with `retryable` false, an id that is not a card). A 401 is not handled here: the client core ends the session (TOKI-032). Check: a table test sends each row's cause through the fakes and reads status, reason, `retryable` and the calls of `onNoAccess` and `onStale`; `retry` after `upload_incomplete` calls `start` again with the same id and then `upload` again; after `file_rejected` the second `start` answers 409 `file_id_in_use`, the card gets a new id and a third call succeeds; `retry` offline returns `"offline"` and calls nothing; `retry` on a `no_access` card returns `"not_retryable"`; a retry that answers `ready` with `upload` null ends `ready` and never calls `upload`.
- R9. Remove and dispose. `remove(id)` takes the card out of the state at once (the person pressed ×) and then, in the background: aborts its running calls through its `AbortController`; and for a card that has reached `start` (it may hold a row) calls `api.files.drop(id)` once, whatever the state; a failure of `drop`, including 404, 409 `file_attached` and a network error, is ignored (D-130: the file is removed after 24 hours anyway; TOKI-058 R11). A `too_big` card and a card whose `start` never ran call nothing. `dispose()` is what the composer's unmount calls: it does `remove` for every card, so the running transfers stop and the unsent files are dropped, and it makes every later call of the set do nothing. After a send, `markSent()` empties the state without a `drop` (the files are attached) and aborts nothing that is running (there is none: Send waits, R10). A reload or a closed tab runs nothing: those files are removed by the cleanup of TOKI-058 R18 after 24 hours, and the cap of 20 of TOKI-058 R9 is what limits them (concern 8). Check: `remove` of a `ready` card calls `drop` once with its id, of an `uploading` card aborts the signal that the fake `upload` and `start` received and then calls `drop`, of a `too_big` card calls nothing; a `drop` that rejects or answers 404 changes no state and raises nothing; `dispose` with 3 cards calls `drop` 3 times and the state is empty; a call after `dispose` does nothing; `markSent` calls `drop` zero times; an `add` made while a `drop` of an earlier card is still running is not affected.
- R10. What Send takes. `readyIds()` returns the ids of the `ready` cards in card order, which is the order of `attachmentIds` of the send (TOKI-058 R14, `position`). `blocked` is true while any card is `uploading`, `failed` or `too_big`: Send waits until every file has finished uploading (F18), and a card that did not upload is not sent behind the person's back, so a red or failed card is taken out with × or retried before the message can go (concern 5). With no card `blocked` is false and `hasFiles` false. Check: states table: no cards, one `ready`, one `ready` and one `uploading`, one `ready` and one `failed`, one `ready` and one `too_big`, all `ready` give `blocked` false, false, true, true, true, false and `hasFiles` false, true, true, true, true, true; `readyIds()` follows the card order after one in the middle was removed.
- R11. The cap of unsent files. When `start` answers 409 `too_many_unsent_files` (TOKI-058 R9: 20 unsent files for the person, whichever tab or earlier visit holds them), the set does the recovery once for that card: it calls `api.files.listUnsent()`, calls `api.files.drop(id)` for each listed file that is not a card of this set, and runs `start` for the card once more. If that is again 409 `too_many_unsent_files`, or the list or a drop fails, the card is `failed` with reason `too_many_unsent`. The recovery is a proposal (concern 8): it can drop a `ready` file that another open tab of the same person is holding (that tab's send then fails with 400 `attachment_unavailable` and its message shows "Not sent"), and it runs only for a person who is already refused. Check: a fake `api` that answers 409 on the first `start`, a list of 3 files of which one is a card of the set, then 201: the two others are dropped, the own card is not, and the card ends `ready`; a second 409 ends `failed` with `too_many_unsent` and a list that fails does the same; no list call is made when `start` succeeds the first time; a person with 20 unsent files whose list has 20 entries gets all 20 dropped except the cards of the set, in a counted number of calls.

Offline and the block
- R12. Uploading is blocked while the connection is down (D-060, D-079: "uploading files" is always blocked offline, with an explanation, never a false success). The set reads `isOnline()` in `add` (R6) and in `retry` (R8); `apps/web` passes `() => connection.getState().status !== "offline"` of TOKI-039 R15 (`connecting`, `idle` and `stopped` count as online, as TOKI-040 R10 reads them: the request is made and a failure is shown on the card). The attach button, a drop and a paste, and Retry, when the answer is "offline", show the toast `files.offline` (Table B) and do nothing else: no file dialog opens (the button checks first, R16), no card is added, no request is made. A transfer that is already running when the connection drops is not cancelled by this work: it ends by itself, and a failure makes the card `failed` with Retry, which is blocked until the connection is back. Cards that are `ready` stay and the message can be sent: it waits like any message (D-079, TOKI-040 R10). The block is by the connection state alone; this work adds no browser `online` listener and no ping. Check: a page test with a fake connection store: at `offline` the attach button shows the toast, `platform.files.pick` is not called, a drop and a paste add nothing, `fetch` is never called, and Retry on a `failed` card shows the toast; at `online` the same actions work; `connecting` and `stopped` allow them; a `ready` card stays when the state goes `offline`, and Send is enabled.

The screen

- R14. The drop target (`FileDropZone`, same folder). `FileDropZone({ onFiles, active, veilText, children })` wraps the Messages panel of the conversation page (F18: "drag files onto the chat"). It reacts only to a drag whose `dataTransfer.types` contains `"Files"` (a dragged text or link does nothing). For every such drag over it, `dragover` and `drop` call `preventDefault`, whether `active` or not, so a file dropped on the page never makes the browser open it and leave the app. When `active` is true it shows the veil `div.dropveil` with `veilText` (the whole zone, `pointer-events: none`, so the drag keeps working; a counter of `dragenter` and `dragleave` hides it when the drag leaves and at `drop`); when false it shows none and `drop` does nothing. A `drop` calls `onFiles(files, { folders })`: `files` are the `File` objects of `dataTransfer.files` that are not folders, in the order given, and `folders` is the number of entries that are folders, found through `dataTransfer.items[i].webkitGetAsEntry()?.isDirectory`, because a browser lists a dropped folder as a `File` that cannot be read (a folder is never uploaded or added as a card). The component holds no text and reads no `File` content. `active` is true when a composer is mounted that takes files (R17). Check: Testing Library with created drag events: a drag of text (`types` `["text/plain"]`) shows no veil and is not default-prevented; a drag of files over an active zone shows the veil with the given text, and `dragleave` after two `dragenter` keeps it and the second hides it; `drop` calls `onFiles` with the files in order and `folders` 0; with two files and one folder entry `onFiles` gets the two files and `folders` 1; an inactive zone is default-prevented, shows no veil and calls nothing; the veil has `pointer-events: none` (CSS test).
- R15. Paste. The same `FileDropZone` handles `paste`, which bubbles from the field inside it. The paste takes files only when the clipboard has image files and no `text/plain`: then it calls `onFiles` with the images (`type` starting `image/`) and `preventDefault`; in every other case it does nothing and the paste goes to the field as before (concern 7: a copied spreadsheet range has text and an image, and its text is what the person wants). So a screenshot or a copied image is attached (F18: "paste an image from the clipboard"), and text, and a file copied in a file manager (which carries its name as text), paste as text. A pasted image has the name the browser gives it (`image.png` in Chromium), or none (R6 gives it one). The paste is handled only when `active` is true. Check: a `paste` event with one `image/png` file and no text calls `onFiles` with it and is default-prevented; one with an image and `text/plain` calls nothing and is not prevented; one with only `text/plain` calls nothing; one with a `application/pdf` file and no text calls nothing (concern 7); two images give both; an inactive zone does nothing; a paste into the field that bubbles from a `textarea` inside the zone is the case tested.

`client-core` holds the rules and no browser API; `platform` holds the one browser API that sends bytes, because the handle of a picked file is opaque (`unknown`) and only the platform that made it can read it, and the native build will make its own handle and its own `upload`; `ui-web` draws and reads drag and clipboard events, which are DOM events of the component (the platform spec says so); `apps/web` joins them.

### How a file goes (what is built here)
```
 paperclip / drop / paste ──▶ set.add ──▶ card (uploading)
                                 │ slot free (3 at a time)
   api.files.start ──────────────▶ ticket            (TOKI-058 R6)
   platform.files.upload ──▶ POST form to storage    (progress → card)
   api.files.complete ───────────▶ ready             (TOKI-058 R10)
 Send: sync.send(conversationId, text, { attachmentIds })   (TOKI-058 R14, TOKI-040)
 × or leaving the conversation: abort + api.files.drop      (TOKI-058 R11)
```

## Data safety
- A file name is personal to the sender and is never logged: no code of this work writes a name, a file id or an upload address to a log, and an `ApiError` carries none (TOKI-058 R19).
- The ticket (`url` and `fields`) is held in memory for the length of one request and is never stored, shown or logged; the card state holds no address and no storage key.
- The form post sends no cookie and no header of the app to the storage host (R3), so the session is never sent there.
- Nothing about files is written to the browser's storage: a draft is text only (D-168), the outbox holds only ids (TOKI-040 as changed), and a reload loses the cards by design.

## Open questions from the intent
- Where does the code that sends the bytes live, given that `client-core` may use no XMLHttpRequest, File, Blob or FormData? Answered in this spec: in `platform`, as `files.upload`, because the handle of a picked file is opaque and the native build will bring its own (R3, concern 9).
- How many files upload at the same time, and is there a time limit on an upload? Answered in this spec: 3 at a time, no limit of time (R7, concern 11).
- Does a card count toward the 10 when it is red, and can a message be sent while a card is red or failed? Answered: a red card counts (R6, concern 6); Send waits until every card has uploaded, so a red or failed card is removed or retried first (F18; R10, concern 5).
- What happens to the cards when the person leaves the conversation, switches to the Pinned tab, or reloads? Answered for leaving the conversation and for a reload: D-168 says files are not restored, so the cards go and the unsent files are dropped or left to the 24-hour cleanup (R9, concern 2). Not answered for the switch to the Pinned tab, which unmounts the composer (TOKI-043 R20): carried forward as concern 3.
- What exactly is pasted: only images, or any file on the clipboard? Answered in this spec: images, when there is no text on the clipboard (R15, concern 7).
- What does the composer do when the server says the person already holds too many unsent files? Not answered. The log has no rule for how a person recovers; the build follows the proposal of concern 8 (R11).
- What does a message with files and no text look like while it waits to send, and what if its files expire while it waits? Not answered. Carried forward as concern 12 (a message and the engine's list are TOKI-040 and TOKI-042).
- Which texts does the card show, and which of them does the prototype have? Answered: Table B lists each with its source; the prototype has "Attach a file" and "Remove {name}" only (concern 1).

3. The cards when the person switches to the Pinned tab. Not decided: the composer is part of the Messages tab only and a tab switch unmounts it (TOKI-043 R20), D-168 does not say whether leaving the tab is "return". Proposal, built here: a tab switch is leaving, the cards go and the files are dropped, as in concern 2 (a text comes back from the store, the cards do not). The alternative is to keep the set above the tab (the page holds it) so uploads continue and the cards are there on return; it costs a store that lives longer than the composer and changes R9 and R17 only. Owner: Thanh Truong.
4. Uploading while offline. Decided: D-060 and D-079 (Confirmed) block uploading files offline "with an explanation, never a false success" and let messages wait. The build: the attach button, a drop, a paste and Retry show the reason and do nothing (R12); "offline" is the `offline` status of TOKI-039 R15, which comes 3 seconds after the connection is lost (so a drop shorter than that is not blocked and a transfer that fails in it ends as a failed card with Retry); a transfer that is running is not cancelled; the button is not disabled, so it can say why. Owner: Thanh Truong.
5. Send with a card that did not upload. Decided: F18 (accepted as the baseline by D-091) says sending is possible once every file has finished uploading. A red or failed card has not, so Send stays disabled until the person removes it or retries it (R10, R17); a message is never sent without a file the person believes is attached. Owner: Thanh Truong.
6. Which cards count toward the 10. Decided in this spec: every card counts, a red one included, so the number on screen is the number the person can see; a person who wants room removes the red card (R6). Reason: counting only good cards would let an eleventh card appear next to a red one and then fail at Send. Owner: Thanh Truong.
7. Paste. Decided in this spec: only images are taken, and only when there is no text on the clipboard, because a spreadsheet range or a web page carries an image and text and its text is what the person means, and F18 says "paste an image"; a file copied in a file manager is attached by the button or by drop (R15). Owner: Thanh Truong.
8. Recovery from "too many unsent files". Not decided: TOKI-058 concern 6 gives the cap of 20 and the list route as proposals and leaves the rule for what the person does to this ticket. Proposal, built here: when a start is refused for the cap, the set lists the person's unsent files, drops those that are not cards of this page, and tries once more (R11); the card says the reason if it still fails. Risk: it can drop a `ready` file held by another open tab of the same person. Alternatives: show the list for the person to choose (more screen), or never drop and let the cap run out in 24 hours (a person who reloaded twice with 10 files each waits a day). Owner: Thanh Truong.
9. Where the upload code lives. Decided in this spec: `files.upload` in `platform`. Reason: `client-core` may not use XMLHttpRequest, File, Blob or FormData; the handle of `pick` is `unknown` and only the platform that made it can read it; the native build brings its own handle and its own upload; XMLHttpRequest is needed because `fetch` has no upload progress. The cost is a change to the platform interface (an addition, as its spec foresaw). Owner: Thanh Truong.
10. The size format. Decided in this spec: `formatFileSize` in `@toki/i18n`, base 1,024, unit symbols the same in both languages, one decimal under 10. Reason: the prototype's "96 KB" has no decimal and the 100 MB limit is 100 × 1,024 × 1,024 (TOKI-058 concern 2, itself a proposal to the owner: if the owner picks 100,000,000 bytes, only that constant and the base here change). Owner: Thanh Truong.
11. Three uploads at a time, no time limit. Decided in this spec: at most 3 cards run together and the others wait, with no limit of time on a transfer. Reason: with ten files at once every file ends late and a break of the line wastes all of them, while with three the first cards end early; a ticket is asked only when a card starts so it does not age in the queue (TOKI-058 R3); storage checks time only at the start of a request, so a time limit here would only cut a slow line. The number is the constant `UPLOAD_PARALLEL`. Owner: Thanh Truong.
12. A message with files while it waits. Not decided: a message with files and no text that waits offline, or after a reload, has no text and holds its files only as ids; the files may be 24 hours old and gone (D-130), so its Retry fails with 400 `attachment_unavailable` until the person deletes it. Who draws such a waiting message and with what is TOKI-042's and TOKI-040's, and the engine's rules for a message that never sends are TOKI-040's. Proposal: the waiting item carries the file entries from `readyFiles()` (Plan changes). This work only hands the ids over. Owner: Thanh Truong.
