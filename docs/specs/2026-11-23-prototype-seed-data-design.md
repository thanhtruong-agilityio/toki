# Prototype seed data design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/prototype-seed-data.md (Thanh Truong)
Ticket: TOKI-081

## Goal
After `pnpm dev:reset:db` the development database has tables and no row. The builder needs the prototype's sample workspace (Hugepig Studio: eight people, channels, direct messages, messages, a thread, reactions, a pin) loaded with one command, so that every screen of the message feed has something to show, and the end-to-end flows have a known starting point. A production installation must never get it.
This work writes the command, the data, the entries the modules expose for it, and the rules that keep it out of production and make a second run harmless.

## Scope
- In:
  - The root script `dev:seed` (`scripts/seed.sh`) and the command behind it, `apps/server/src/cli/seed.ts`.
  - The step `seedPrototypeWorkspace` in `apps/server/src/seed/` (outside `modules/`), with the sample data as one typed file.
  - One narrow seed file in each module that owns a table the seed fills: `members`, `conversations`, `messages` (messages, the thread summary, the pin) and `reactions`. The workspace and `#general` are written by the existing writers as they are (R5, R6); this ticket changes none of them.
  - The calls of `saveMentions` of TOKI-050 for the sample messages that name a person (R7).
  - The two guards that keep the command out of production, the empty-database rule and the idempotence rule.
  - The list of what the sample may not contain, with the reason for each.
  - A row in "Common commands" of `CLAUDE.md`.
- Out (not now):
  - Sample files and images: TOKI-063 adds them to the seed once file storage exists (plan). Attachments of the other kinds the prototype draws (poll, voice message, Meet card, approval card) are not built in phase 1; no ticket of the plan adds them to the seed. The link card of `l1` is left out for the reason in the next item.
  - Profile fields of a person (job title, time zone, city), the status, the read pointers and unread counts, drafts, notes, tasks, reminders, calendar events, automations and the mail of the prototype: the tables or columns do not exist yet. The ticket that adds a table or a column extends the seed in its own pull request (concern 1): the job title and time zone by the server ticket "Profile and preferences (server)", the status by TOKI-056, the read pointers by TOKI-053 (Hand-offs).
  - A card for the link in `l1`: the text of `l1` holds no address, so TOKI-061 would find no candidate and delete a seeded card at its first job; the sample shows no card and no ticket loads one (Hand-offs).
  - Wiring the seed into the end-to-end runs: TOKI-090 owns it. This ticket exports the function (R17) and the command.
  - Building the production image: TOKI-084 owns it. This ticket states what the image must leave out (Hand-offs); its guards (R2, R3) stop a run, they do not stop shipping.
  - A reset that also seeds: `dev:reset` stays a wipe (TOKI-003 R8). The order is `pnpm dev:reset:db`, `pnpm dev:seed`, then start the server (first-admin spec, concern 13).

## Requirements
In the checks below, "the seeded database" is a database that the migrations built and the harness emptied, after one call of `seedPrototypeWorkspace` with the clock of R9.

- R1. The root `package.json` gains one script, `dev:seed`, that runs `bash scripts/seed.sh`. `scripts/seed.sh` sources `scripts/lib.sh` and `scripts/guard.sh`, calls `guard_development "$ENV_FILE"` first (the guard of TOKI-003 R10: every source that sets `NODE_ENV`, the shell and the root `.env`, must say `development`, and a script refuses when they disagree or when none sets it), and only then runs `pnpm --filter @toki/server run seed`. `dev:reset` and the other `dev:*` scripts do not call it, and `dev:reset:db` still ends with tables and no row. With `--check` the script runs the guard and stops with exit 0 before it starts the command. `scripts/lib.sh` fixes `ENV_FILE` at `$REPO_ROOT/.env` with no override and this ticket does not change it (it is TOKI-003's). Check: `scripts/seed.test.sh` tests the function `guard_development` against a temporary env file, as `smoke.test.sh` does, in six cases as TOKI-003 R10 does (`production` in the file, an unknown value, removed from the file, `development` in the file with `production` exported, the other way round, removed from the file with `production` exported): each returns non-zero and prints a refusal that names `NODE_ENV`; with `development` in both it returns 0. A seventh check reads `scripts/seed.sh` and fails unless the call of `guard_development` comes before the line that runs `pnpm`, and unless `--check` exits before it. The test never reads or writes the real `.env`. `smoke.test.sh` is in neither the root `test` script nor CI; this ticket adds a root script `test:scripts` that runs `bash scripts/seed.test.sh` and adds it to the root `test` script, so CI runs it (it needs no Docker). `pnpm run` lists `dev:seed`; the `dev:reset` entry points contain no call of `seed`.
- R2. The command has its own guard, which runs before it opens a connection. `apps/server/src/cli/seed.ts` reads only `NODE_ENV` and `DATABASE_URL`, through a new `readSeedConfig` of `cli/config.ts`. The file imports no code of `src/config.ts`, because that file requires at every start the first-admin values and the mail values (TOKI-020 R21, TOKI-021), which the seed neither needs nor should demand, as `emergency:link` does (TOKI-026 R23). The command still loads the mail module's code through `members/index.ts`; that is accepted: it opens no mail connection and sends nothing (R13). It runs only when `NODE_ENV` is exactly `development`: a missing value, `production`, `test` and any other value exit 1 with a message that names `NODE_ENV` and no value, and write nothing. Check: a process test starts `src/cli/seed.ts` directly through `tsx`, not through the `seed` script (which loads `../../.env` and could bring back a `NODE_ENV` of a developer's file), with a cleared environment (`env -i` plus the named variables), with `NODE_ENV` set to `production`, to `test`, to an empty string and removed, each with a `DATABASE_URL` that no server answers on: each exits 1, the message names `NODE_ENV`, and none reports a connection error (no connection was tried).
- R3. Nothing starts the seed by itself. The server's `main.ts`, `app.ts`, every route and every module file except the four seed entry files (R4) import no name of `apps/server/src/seed/` and no `seed*` entry. Check: a test reads the import lines of every file under `apps/server/src/` and `apps/server/tests/` and fails when a file other than `src/seed/**`, `src/cli/seed.ts`, the four entry files, their `index.ts` re-exports and test files imports one of them; a test reads the `scripts` of the root and server `package.json` and finds `seed` only in `dev:seed` and the server `seed` script.
- R4. The seed writes through the public entries of the modules and reads no table. `apps/server/src/seed/` imports only the `index.ts` of `workspace`, `members`, `conversations`, `messages`, `reactions` and `mentions` (TOKI-050), and `packages/shared`. Four files add five entries, one for each kind of row, each narrow on purpose (it fixes what no caller of it may choose, as `createFirstAdminAccount` does, first-admin spec concern 14; `seedAccounts` takes the role as the closed type `"member" | "admin"` and fixes status `active` and language `en`, so it is not the general account writer that concern refused, and the import test of R3 is the guard that keeps it so): `seedAccounts(tx, input)` of `members`; `seedConversations(tx, input)` of `conversations`; `seedMessages(tx, input)` and `seedPins(tx, input)` of `messages`; `seedReactions(tx, input)` of `reactions`. Each takes the caller's transaction, opens none, takes the ids and times it is given, and writes the rows through the module's own table definition. `seedMessages` also takes the writer `saveMentions` as a parameter, the pattern of the injected readers and writers of TOKI-046, 048 and 050: `messages` imports nothing of `mentions`, and the step in `src/seed/` passes it (R7). No table is exported from any `index.ts`. Check: this ticket writes two tests, because none exists for this. An import-line test reads the import lines of `src/seed/**` and fails on any import other than the six `index.ts` files, `packages/shared` and its own files; the lint run (`pnpm lint`, `pnpm lint:boundaries`) exits 0 for the four entry files. An export test, `tests/seed/exports.test.ts`, imports the `index.ts` of the five modules, finds each of the five seed names as a function in its module, and finds no exported value that is a Drizzle table (the rule that no table leaves a module). It does not claim to list every name of a module: only `tests/conversations/exports.test.ts` lists names today, and this ticket adds its seed names to that list and to the export tests that TOKI-045, TOKI-046, TOKI-048 and TOKI-050 write for `messages`, `reactions` and `mentions` (their R13, R18 and R10 each say the export test lists the module's names), for those that exist when this ticket is built.

- R9. Time. The sample is placed relative to the moment of the run, with the prototype's own gaps. The prototype's clock stands at 10:42 on its "today" (a Tuesday, 10 November 2026), its "yesterday" is the day before, and its wall times are those of Ho Chi Minh City (UTC+07:00, the zone of 7 of the 8 people; the workspace has no time zone setting). `seedPrototypeWorkspace` takes the clock as a parameter; with `now` the clock's time, every instant `P` of the data (messages, channel creation, account creation, reactions, the pin) is stored as `P + (now - T)`, where `T` is 10 November 2026 10:42 at UTC+07:00. So with the clock set to `T` every message lands at the prototype's wall time on 9 and 10 November 2026, and with any other clock every gap is the same and the newest sample message (`l14`, 10:20) is 22 minutes before `now`, never after it. The command passes the system clock (TOKI-008 R19: no direct read of the system time in the step). The channels' creation dates are the prototype's ("Jan 8", "Sep 2", "Sep 14", "Sep 20", "Oct 1", "Mar 4", "Feb 3") at 09:00 UTC+07:00 of 2026 and `#general` and `random` carry "Jan 8"; the accounts are created at the creation time of `#general`; every time the seed chooses is a whole number of milliseconds (the clock gives whole milliseconds, `T` and every gap of the data are whole minutes, and no step adds a fraction), because TOKI-070 merges the lists of its message search by (`created_at`, `id`) and reads `created_at` as a `Date`, which holds milliseconds while the column holds microseconds; the workspace keeps the database's default time (R5), so it is not part of the shift and not part of the "never after `now`" check below; a direct message or the group is created one minute before its first message; a member row has the creation time of its conversation (these are sample values: the prototype has dates but no hours). Check, with the controllable clock of TOKI-008 set to `T`: the `created_at` of `g1` is 15:10 on 9 November UTC+07:00 and that of `l14` is 10:20 on 10 November; with the clock set to `T` plus 400 days every `created_at` is 400 days later; no `created_at`, `edited_at` or `pinned_at` of a row the seed writes (the workspace excepted) is after `now` in either run; every `created_at`, `edited_at` and `pinned_at` of a row the seed writes (the workspace excepted, whose time is the database's default and has microseconds) equals itself cut to milliseconds (`date_trunc('milliseconds', created_at) = created_at` holds for all rows, with a clock set to a time that has a fraction of a millisecond in the test, so a step that forgot to cut would fail); in the main list of each conversation (the roots) the order by (`created_at`, `id`) is the prototype's order (no two roots of one conversation share a minute), and the replies are ordered among themselves (`l6a`, `l6b`, `l6c`). The reply `l6c` (09:11) comes after the root `l7` (09:10) in time, although the prototype lists it before `l7` in its flat list; the history route returns roots only (R8), so the order of the main list is not affected.

## Design
### Where it lives
```
toki/
├─ package.json                          dev:seed -> bash scripts/seed.sh
├─ scripts/
│  ├─ seed.sh                            guard_development, --check, then the server script
│  └─ seed.test.sh                       the six guard cases (R1)
└─ apps/server/
   ├─ package.json                       script "seed": tsx --env-file-if-exists=../../.env src/cli/seed.ts
   └─ src/
      ├─ cli/seed.ts                     the command: NODE_ENV check, config, connection, one call, exit code
      ├─ cli/config.ts                   readSeedConfig (NODE_ENV and DATABASE_URL only)
      ├─ seed/
      │  ├─ index.ts                     seedPrototypeWorkspace, PROTOTYPE_SEED
      │  ├─ data.ts                      the sample, typed: people, conversations, messages, reactions, pin, mapping
      │  └─ time.ts                      P + (now - T), the 9 and 10 November anchors
      └─ modules/
         ├─ members/seed.ts              seedAccounts
         ├─ conversations/seed.ts        seedConversations
         ├─ messages/seed.ts             seedMessages, seedPins
         └─ reactions/seed.ts            seedReactions
```
- `seed/` sits outside `modules/` like `first-admin.ts`, for the same reason: a step inside one module that calls the others would make an import cycle, and it may import only the `index.ts` of each module (TOKI-002 R17).
- Each `modules/<name>/seed.ts` is re-exported from that module's `index.ts`. The five names are the only way the seed reaches a table. Nothing else imports them (R3).

### How it works
1. `pnpm dev:seed` runs the shell guard (R1), then the server script, which runs the command.
2. The command checks `NODE_ENV` (R2), reads `DATABASE_URL`, opens one connection and calls `seedPrototypeWorkspace` with the system clock (TOKI-008) and `node:crypto`'s `randomBytes`.
3. The step opens one transaction, takes the first-set-up lock, counts workspaces and users (R14) and, on an empty database, writes in this order: workspace, accounts, `#general` and the other conversations with their members, messages (roots, then replies), the thread summary, the mention rows (`saveMentions`, R7), reactions, the pin.
4. It commits and returns `loaded`. The command prints the result and exits 0 (`loaded`, `already_loaded`) or 1 (`not_empty`, a failure).

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- Method: module entries, in one transaction, not the HTTP routes and not SQL. The routes read the clock at the request, so they cannot place a message in the past (TOKI-037 R3), they need a session for each person and they write an event for every change; SQL would read tables of other modules. Entries keep the module rule and let the step choose times and ids.
- The five entries are narrow and named `seed*`, and a test fixes who imports them (R3), because a general "create account with any role" entry is what the first-admin spec refused (its concern 14).
- Times are shifted by `now - T`, so the sample always looks like "yesterday and today", the newest message is never in the future, and a test that fixes the clock to `T` gets the prototype's exact wall times (R9).
- `👋` becomes `🎉` (R11): both are greetings of welcome, the 8 emoji have no wave, and the welcome message has no `🎉` of its own. Dropping the chip would lose the only reaction of the welcome message.
- The guest, the guest's channel and the three messages with no text are left out whole, and the attachments of every kind are left out (Scope): a message needs a text and the tables hold no attachment.
- The pin and the thread summary: the pin is a row with no system line (R12); the summary is made by `recomputeThreadSummary` (R8).
- The workspace and `#general` are written by the existing writers as they are. A change to `createWorkspace` (an optional `createdAt`) and to `createGeneralChannel` (an optional `id`) would make the whole sample reproducible, but the first-admin R14 and TOKI-028 R25 fix their shape and the cost of living with it is small: the workspace time and the `#general` id are the only values the seed does not choose, and R10's comparison leaves them out. This spec asks for no change to them (Plan changes).
- The mention rows come from the injected writer `saveMentions` of TOKI-050, called by the step through a parameter of `seedMessages`, so `messages` imports nothing of `mentions` and the seed keeps no second copy of the matching rule (R7). The name in `l8` is the full display name under 050's rule, which is a proposal of that spec.
- The first-set-up lock is reused (R14). Reason: the two steps are the same event, the set-up of an empty installation, and one key means they can never both write.
- No events and no system lines: the sample is loaded before any client connects, so there is nobody to tell; and the event log is pruned after 7 days (TOKI-036), so seeded events would be gone in a week and a reconnecting client would be told things that never needed telling.

### Errors
- `NODE_ENV` is not `development` -> exit 1 before any connection (R2); the shell guard refuses earlier (R1).
- `DATABASE_URL` is missing or invalid -> exit 1, the message names the variable (the way `emergency:link` does).
- The database cannot be reached, or a table does not exist (migrations not applied) -> exit 1, nothing written.
- The database holds other data -> `not_empty`, exit 1, the message says what to run (R15).
- The sample is already there -> `already_loaded`, exit 0 (R15).
- A step fails -> the whole transaction rolls back and the command exits 1 (R16).

## Testing
- Shell: `scripts/seed.test.sh` for the guard function and the order of the script (R1). It runs without Docker, never reads or writes the real `.env`, and runs in `pnpm test` through the new root script `test:scripts`.
- Unit (no database): the typed data (R5 to R7, R11, R12: counts, authors in their conversations, no empty or over-long text, no emoji outside `REACTION_EMOJI` and the mapping), the time shift (R9, with the clock of TOKI-008), the id generator use and the grep for `Math.random` and `crypto.random` (R10), the import-line test and the export test that this ticket writes (R3, R4, R21), the call of `saveMentions` for each text with an `@` (R7), `readSeedConfig` and the NODE_ENV refusal (R2).
- Database (`*.db.test.ts`, the harness of TOKI-008 empties the tables): the three results and the lock (R14, R15), the counts and column-by-column equality (R5 to R9, R11, R12), the mention row of `l8` (R7), the empty tables (R13), the lock limit (R14), the rollback hooks (R16), the real read paths and sign-in (R18, R19).
- Process: the command started directly with a cleared environment for the guard, and run against the test database for the three states (R2, R15).
- Timing is never tested with a real timer: every check of R9 uses the controllable clock.
- Hand check once, output in the PR: `pnpm dev:reset:db`, `pnpm dev:seed`, `pnpm dev`, sign in as `lan@hugepig.example` with the code from Mailpit and open `project-launch`; run `pnpm dev:seed` again and read "already loaded".

## Data safety
- The sample holds no real address: the domain `hugepig.example` cannot receive mail (R5, R21).
- The command logs counts and a result only (R17); no email, name or text goes to a log.
- The seed makes no session, no code and no credential (R13).
- It writes nothing when the database holds other data (R14, R15), so pointing `DATABASE_URL` at a database in use cannot change it; the `NODE_ENV` guards stop it earlier (R1, R2).
