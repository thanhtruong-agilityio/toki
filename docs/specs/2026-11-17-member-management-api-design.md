# Member management API design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/member-management-api.md (Thanh Truong)
Ticket: TOKI-024

## Goal
An Admin needs to bring people into Toki and keep the member list in order: invite them with a role, resend or revoke an invitation, change a role, deactivate and reactivate a person, and read the list. Today the server has accounts and sign-in but none of this, so nobody but the first Admin can enter. This work adds the server operations, the table of invitations, the record of administrative actions, and the functions the accept-an-invitation work calls. It states in one place the rules that protect the workspace: the last Admin, nobody deactivating themselves, a Member refused on every admin request, a repeat ignored.

## Scope
- In:
  - Seven routes under `/api/v1`: read the member list; invite a batch of addresses; resend and revoke an invitation; change a role; deactivate and reactivate a person (Design, "API").
  - The table `invitations`, the table `admin_actions` (the record of D-110) and the table `member_requests` (the repeat rule of D-111), in one migration, in the `members` module.
  - The life of an invitation: created, resent, revoked, expired, used (R18); the Join link and its token (R11); the functions of the `members` module that the accept-an-invitation work calls (R19, R20).
  - The lock that makes "the last Admin" and "nobody deactivates themselves" hold when two requests arrive together (R27).
  - Calling the `auth` module (invitation codes, ending sessions, last use), the mail layer and the permission functions.
  - The request and response schemas, the limits (50, 7 days) and the address-list parser in `packages/shared`; the new error codes.
  - Server integration and database tests.
- Out (not now):
  - The Admin page and its modal, row menu and confirmations: TOKI-025. This work says what the list returns (R21 to R25).
  - Accepting an invitation: the page behind Join, its refusal pages, "Resend code" on that page, the sign-in after the code, adding the person to #general, the "Minh joined" line: TOKI-097. This work gives it the functions of R19 and R20 and nothing else of that flow.
  - The code rules and the session functions: TOKI-022. The mail layer and the three mail texts: TOKI-021. The first Admin: TOKI-020. Listing and ending a person's own sessions, and the emergency link: TOKI-026.
  - What other people see of a deactivated person: the "Deactivated" label, leaving People and mention suggestions, read-only DMs (F41). They read `users.status`; each is the work of the ticket that builds that screen or list. This work stores nothing for them and deletes no message.
  - The Activity item and the live update for the person whose role or status changed (F40, F41): not owned by any ticket (concern 8).
  - Changing a person's own display name or sign-in address (D-098). Permanent deletion of an account: none in phase 1 (BR-29).
  - A limit of invitations across batches, and a screen for the record of actions: not decided (concern 12) and not in phase 1 (D-110).

## Requirements
Access and errors
- R1. Every route of this work needs a valid session (TOKI-022 R24) and an Admin. A Member gets status 403 with the code `forbidden` on every route, and nothing is created, changed or sent. The server calls the permission functions of TOKI-027: `canOpenAdminPage` for the list, `canInviteMember` for an invitation, `canManageInvitations` for resend and revoke, `canChangeRole`, `canDeactivateAccount` and `canReactivateAccount` for the person routes (D-090). A result `fact_missing` or `unknown_role` is a server error (status 500, `internal_error`), as TOKI-027 asks. No route compares a role itself.
- R2. Errors use the format of TOKI-004: `{ "error": { "code", "message", "details"? } }`. This work adds to the registry in `packages/shared` the codes `forbidden` (403), `batch_too_large` (400), `invitation_not_found` (404), `invitation_used` (409), `invitation_revoked` (409), `last_admin` (409), `self_target` (409), `request_in_progress` (409) and `idempotency_key_reused` (409); the three `invitation_*` codes are the ones TOKI-097 uses for the same states, so there is one name for each. A body or parameter that fails its schema, a missing or malformed `Idempotency-Key`, or an id that is not a UUID gets 400 `validation_failed` (the code of TOKI-004). A person that does not exist, or belongs to another workspace, gets 404 `not_found`; an invitation that does not, 404 `invitation_not_found`.
- R3. Every route of this work that changes something is a `POST`. The only `GET` is the list, and it changes nothing. Reason: TOKI-022 R46 refuses a foreign `Origin` for `POST` and `DELETE` only, and R36 asks that no `GET` changes anything.

Invite a batch
- R4. `POST /api/v1/invitations` takes `{ "emails": string[], "role"?: "member" | "admin" }` and the header `Idempotency-Key` (R13). `role` is `member` when absent. `emails` holds 1 to 50 entries (D-134): 0 entries or an entry that is not a string is 400 `validation_failed`; 51 or more is 400 `batch_too_large` with `details.max` 50; exactly 50 is accepted. Any other `role` is 400 `validation_failed`.
- R5. The response is status 200 with `{ "results": [...] }`: one result for each distinct address, in the order of first appearance. An address is normalised with the shared function of TOKI-020 R16 (trim, lower case) before anything else, and an address that appears twice in the request is reported once (D-099). A result is `{ "email", "result", "invitation"? }` with `result` one of `invited`, `mail_not_sent`, `already_member`, `already_invited`, `invalid_email`. The status is 200 whatever the results, so a batch where mail fails halfway still answers 200 and the invitations already made stay (D-099). `invitation` is present for `invited`, `mail_not_sent` and `already_invited` and has the shape of R22.
- R6. `invited` and `mail_not_sent`: for an address with no account and no open invitation, one `invitations` row is created with the role, the acting Admin as inviter, `created_at` and `sent_at` now, `expires_at` 7 days after `sent_at` (R18) and `code_serial` 0; a code is made with `issueInvitationCode` (R19), which creates it through `createInvitationCode` of TOKI-022 R49; and one mail is handed to `sendInvitationMail` of TOKI-021 with the address, the 6 digits, the workspace name, the display name of the acting Admin and the Join address of R11. When the mail layer answers `ok: true` the row has `mail_status` `sent` and the result is `invited`. For any other answer of the mail layer the row stays, with `mail_status` `failed`, and the result is `mail_not_sent` (D-099, F02). The mail of one address never changes the result of another.
- R7. `already_invited`: an address with an open invitation (R18), expired or not, is reported with its invitation as it stands. Nothing is created, no mail is sent, the 7 days are not restarted. A Resend is the way to renew it (R14).
- R8. `already_member`: an address with an account whose status is `active` gets this result, creates no invitation and sends no mail (F02).
- R9. A deactivated account: an address with an account whose status is `deactivated` is invited like a new address (R6), and the new invitation holds that account's id as `user_id`. The account is not changed at this point (D-094). The role of the invitation is the role chosen in the request, not the role the account had (D-181).
- R10. `invalid_email`: an entry that does not pass the shared address check of TOKI-020 R16 (`packages/shared/src/email.ts`: trimmed, lower case, at most 254 characters, one `@`, no whitespace, at most 64 characters before the `@`), the rule that sign-in and set-up also use gets this result, creates nothing and sends nothing, and the other addresses are processed (F02). When two requests invite the same address at the same moment, exactly one open invitation exists afterwards, and the other request reports `already_invited` for it (concern 1).
- R11. The Join link. For each invitation and for each resend, a token of 32 random bytes from a cryptographic source, written as 43 characters of base64url, is made. The database stores only its SHA-256 as 64 lower-case hexadecimal characters (`token_hash`), never the token. The Join address is the app's own origin, then `/join#`, then the token: the token is in the fragment, as TOKI-097 R26 reads it, so it is not sent in a request line or a `Referer`. The origin is the value of the environment that TOKI-022 R46 reads for the `Origin` rule (its name is TOKI-096's); this work adds no variable. The secret bound to the invitation's code is the token, a colon and the invitation's `code_serial` as a decimal number (`<token>:<serial>`), so that each code of an invitation has its own secret and `request_hash` stays unique (TOKI-019 R14). The token alone signs nobody in (D-149): the code step needs the code of the mail.
- R12. The inviter named in the mail is the Admin who made the request, also on a resend (R14). The workspace name is read through the `workspace` module function that TOKI-022 uses for its name read. The mail language is English (D-180): this work passes no language.
- R13. The repeat rule (D-111). The batch route and the resend route need the header `Idempotency-Key`, 1 to 64 characters from `A-Za-z0-9_-`. The server keeps, for each person and key, the hash of the request (route, parameters and the body after the schema has parsed it) and the response. A second request with the same key and the same hash gets the stored status and body, and creates no row, sends no mail and records no action. The same key with another hash is 409 `idempotency_key_reused`. The same key while the first request is still running is 409 `request_in_progress`. A request that has been running for 60 seconds or more is counted as dead and the key is taken over by the new request. Stored responses are removed 24 hours after they were made: each new batch deletes up to 100 older rows. The key is in the `member_requests` table (Data model). The person routes do not need a key: repeating one is already harmless (R26, R29, R30, R16).

Resend and revoke
- R14. `POST /api/v1/invitations/{invitationId}/resend` with the header of R13 renews a pending or expired invitation, whether its mail arrived or not (D-182). In one transaction, with the invitation row locked, it makes a new token and replaces `token_hash`, sets `sent_at` now and `expires_at` 7 days after it, sets `mail_status` `failed`, and makes a new code with `issueInvitationCode` (R19), which cancels the earlier unused code (TOKI-022 R49). After the commit it hands the mail to `sendInvitationMail` and sets `mail_status` `sent` when it was delivered. The response is status 200 with `{ "result": "invited" | "mail_not_sent", "invitation": {...} }`, with the same rules as R6. The earlier token finds no invitation (R19), and the earlier code does not work.
- R15. Resend of an invitation that is used or revoked is 409 `invitation_used` or `invitation_revoked`; nothing changes and no mail is sent. Revoke of a used invitation is 409 `invitation_used`. An unknown id is 404 `invitation_not_found`.
- R16. `POST /api/v1/invitations/{invitationId}/revoke` sets `revoked_at` now and answers status 200 with `{ "invitation": {...} }` whose `state` is `revoked`. Afterwards the Join link of that invitation is found with `revoked_at` set (R19), and the address can be invited again (R6 creates a new invitation). Revoking an invitation that is already revoked answers 200 as the first time, changes nothing and records nothing. A revoked invitation is not in the list (R22). Revoke can be sent for an expired invitation.

Invitation life, and what the accept-an-invitation work calls
- R17. Revoking the invitation of a deactivated person changes nothing in the account: it stays `deactivated` with its role, name and member rows (D-094).
- R18. An invitation has one of four states, worked out from its columns, the first that applies in this order (the order of TOKI-097 R3): `used` when `used_at` is set; `revoked` when `revoked_at` is set; `expired` when the time is at or after `expires_at`; otherwise `pending`. An invitation that is neither used nor revoked, pending or expired, is called open below. An invitation is valid while the time is before `expires_at`: refused at exactly 7 days and after (the same boundary as TOKI-022 R14). `used_at` is also set when the person's account is brought back directly (R30), so the old Join link then leads to the normal sign-in page (D-081). An address has at most one invitation that is neither used nor revoked: the database refuses a second one (R38).
- R19. The `members` module exports three functions for TOKI-097 and for no one else; their shapes are the ones that spec asks for (its "What this ticket needs from TOKI-024"). (a) `findInvitationByToken(db, token)` returns `null` when no row has the hash of the token (a token replaced by a resend finds nothing), else `{ id, email, role, usedAt, revokedAt, expiresAt, codeSerial, codeIssuedAt, accountId }`; `accountId` is `user_id`. It writes nothing. (b) `issueInvitationCode(tx, invitation, token)` adds 1 to `code_serial`, sets `code_issued_at` now, calls `createInvitationCode(email, "<token>:<serial>")` of the `auth` module and returns the 6 digits; it runs in the caller's transaction, which has locked the invitation row. This work uses it for the first code and for a resend (R6, R14); TOKI-097 uses it for "Resend code" and applies the 60 seconds itself. (c) `markInvitationUsed(tx, id, userId)` is one conditional update: it sets `used_at` now and `used_by` to `userId` when `used_at` and `revoked_at` are empty and the time is before `expires_at`, and returns whether it changed a row. Two calls for one invitation change one row.
- R20. Accepting is TOKI-097's work and not this ticket's: it inserts or reactivates the account, adds the member row of #general and starts the session. This work gives it no function for that, so the account change has one author. What this work guarantees is that a reactivation by an Admin closes the invitation (R30), so TOKI-097 R16 (an account already active) is rare; and that no `members` function of this work changes an account at the moment of acceptance.

The list
- R21. `GET /api/v1/members` is for an Admin (R1). Query: `search` (text), `status` (`invited`, `expired`, `active` or `deactivated`), `limit` (1 to 100, default 50, D-109) and `cursor` (the opaque value of the last response). A value outside these is 400 `validation_failed`.
- R22. The response is status 200 with `{ "members": [...], "counts": {...}, "activeAdminCount": number, "nextCursor": string | null }`. A member row is `{ "kind": "account" | "invitation", "userId": string | null, "email", "displayName": string | null, "role", "status", "lastActiveAt": string | null, "invitation": Invitation | null }`. `kind` `account` rows come from accounts and have `status` `active` or `deactivated`, the account's role and `displayName`; `kind` `invitation` rows are people who have no account yet and have `status` `invited` (state `pending`) or `expired` (state `expired`), the invited role, `displayName` null and `userId` null. An invitation that is used or revoked is not a row. An `Invitation` is `{ "id", "state": "pending" | "expired", "role", "mailStatus": "sent" | "failed", "invitedBy": { "id", "displayName" }, "createdAt", "sentAt", "expiresAt" }`; times are ISO 8601 strings in UTC. An account row carries `invitation` when the account is deactivated and an open or expired invitation names it (R9): its `status` stays the account's status (concern 3). Every other account row has `invitation` null.
- R23. Order and pages. Rows are ordered by the display name, or the address for a row with no name, compared without regard to case, and then by id. The first page has `limit` rows (50 by default); `nextCursor` is null on the last page. Reading all pages one after the other, with no change in between, gives every row once and none twice.
- R24. `search` keeps the rows whose display name or address contains the text, without regard to case. `status` keeps the rows with that status. `counts` is `{ "invited", "expired", "active", "deactivated" }`: the number of rows with each status among the rows that match `search`, whatever `status` says, so that a chip equals the rows shown (D-074, D-109). `activeAdminCount` is the number of active Admins of the workspace, whatever the query, so the screen can call the permission functions (TOKI-027 R12) to lock an entry with its reason.
- R25. `lastActiveAt` is the latest `last_used_at` among the sessions of the account, ended or not, or null when it has none; it is null for a `kind` `invitation` row. It is read through one `auth` function, `getLastUsedAtByUser(userIds)`, which reads the `sessions` table in one grouped query for the ids of the page. It is the function that TOKI-026 R17 names among its exports (TOKI-019 concern 13); the one of the two tickets built first adds it, with that name, and the other uses it (concern 9).

People
- R26. `POST /api/v1/members/{userId}/role` takes `{ "role": "member" | "admin" }` and answers 200 with `{ "member": Account }`, where `Account` is `{ id, email, displayName, role, status }`. It follows R27. `canChangeRole` refuses demoting the last active Admin: 409 `last_admin`; an Admin may demote themselves when there are two or more active Admins (TOKI-027 R12). Setting the role the person already has answers 200, changes nothing and records nothing. The change is seen on the person's next request, because the server reads the role from the account on every request (TOKI-027).
- R27. The lock. Every person route (R26, R28, R30) runs in one transaction that first reads, with `SELECT ... FOR UPDATE` ordered by id, every `users` row of the workspace with `role` `admin` and `status` `active` together with the row of the target, then counts the active Admins from those rows, then calls the permission function with that count, then writes, then commits. The permission function is never called before the lock. A second request that needs the same rows waits and then reads the new state. Test: two Admins demote each other at the same moment, with exactly two Admins: one succeeds and the other is 409 `last_admin`; the workspace still has one Admin. Same for two Admins deactivating each other (TOKI-019 concern 7, TOKI-027 concern 5).
- R28. `POST /api/v1/members/{userId}/deactivate` answers 200 with `{ "member": Account }` whose `status` is `deactivated`. The actor deactivating themselves is 409 `self_target`; deactivating the last active Admin is 409 `last_admin`; deactivating a Member, or any Admin while two or more are active, succeeds (D-153). When the status change has committed and before it answers, the server ends every session of the person through `endSessionsOfUser` of TOKI-022 R30 with the reason `deactivated`. The person is refused from the moment the status is committed, because the session check looks at the account first (TOKI-022 R27); if ending the sessions fails the answer is 500 and the same request again ends them (R29). Afterwards a request with any of their sessions is refused with 401 `account_deactivated`. No message, member row, device row or account row is deleted (BR-29).
- R29. Deactivating a person who is already deactivated answers 200, changes nothing, records nothing, and ends any session of the person that is still live (R28).
- R30. `POST /api/v1/members/{userId}/reactivate` answers 200 with `{ "member": Account }` whose `status` is `active`. Before it sets the status it ends any session of the person that is still live, so an old session cannot come back to life. The role, the display name and the member rows stay as they were (F41). An invitation of that person that is open gets `used_at` now and `used_by` the person, so the Join link of the mail leads to the normal sign-in page (R18). The person signs in again with a code. Reactivating an active person answers 200 and changes nothing.

The record
- R31. Every action that changes something writes one row to `admin_actions` in the same transaction as the change, so the record and the change exist together or not at all (D-110, F02): `invitation_created` for each `invited` or `mail_not_sent` address, `invitation_resent`, `invitation_revoked`, `role_changed`, `account_deactivated`, `account_reactivated`. A row holds the acting Admin, the action, the account acted on or, for an invitation, the address, a `detail` object (the role, the earlier role, the invitation id) and the time from the clock of TOKI-008. A refused request, a repeat answered from the stored response, and a change that changed nothing write no row. The table refuses every `UPDATE` and `DELETE`. No route reads it (phase 1 has no screen).

Safety
- R32. The module writes no email address, token, code, Join address or `Idempotency-Key` to the log and puts none in an error body. The failure of a mail is logged once, by the mail layer (TOKI-021 R14); this module logs no line of its own for it.
- R33. Each batch calls `pruneInvitationCodes(db, olderThan, limit)` of the `auth` module with 8 days ago and 100, which deletes up to that many `invitation` rows of `login_codes` created before the time. Reason: TOKI-022 R48 removes only `sign_in` rows, and a code of an invitation cannot work 7 days and 10 minutes after its creation, so older rows hold an address for nothing. If TOKI-022 has not added it, this work adds it to `auth` and nothing else.
- R34. A session that no longer belongs to an Admin does not pass: because the role is read on every request, an Admin who was demoted gets 403 on the next request to any route of this work (R1), and a deactivated Admin gets 401 (R28).

Shared package and tables
- R35. `packages/shared/src/members/` exports the Zod schemas of every request and response of R4 to R30, the constants `INVITATION_BATCH_MAX` (50) and `INVITATION_LIFETIME_DAYS` (7), and `parseAddressList(text)` (the address check itself is the shared function of TOKI-020 R16, whichever of TOKI-020 and TOKI-022 is built first creates its file). The routes validate with the same schemas. `parseAddressList` splits the text at commas and line breaks (CR, LF or both, F02), trims every piece, drops empty pieces, puts every piece in lower case, drops a piece that repeats an earlier one, and does nothing else: a piece with a space inside, an angle bracket or a semicolon is kept as typed and is reported by the server as `invalid_email`. TOKI-021 R26 pins its text of "7 days" to `INVITATION_LIFETIME_DAYS`.
- R36. One migration, `<number>_member_management.sql` made with `pnpm db:generate --name member_management` (TOKI-019 convention 8), creates `invitations`, `admin_actions` and `member_requests` and no other table, with the checks, keys and indexes of Data model and the hand-written statements (foreign keys that leave the module, the partial unique index, the append-only trigger). It changes no existing table and inserts no row. The tables are defined in `modules/members/schema.ts` and are not exported from the module's `index.ts` (TOKI-019 R21).
- R37. The `members` read functions that TOKI-022 and TOKI-027 call (find an account by address, get an account by id) return a status of `active` or `deactivated` only. An address that has an invitation and no account returns no account. "Invited" is a state of an invitation (R18, R22) and is not read from `users` (TOKI-019 concern 2).
- R38. The database holds these rules itself (Data model): an invitation's address follows the rule of `users.email`; its role is `member` or `admin`; `token_hash` is 64 lower-case hexadecimal characters and unique; `used_at` and `revoked_at` are not both set; `expires_at` is later than `sent_at`; at most one invitation of an address is neither used nor revoked; `mail_status` is `sent` or `failed`; `admin_actions` allows only the six actions and refuses update and delete; `member_requests` is unique by person and key, and a `done` row has a status and a body.

## Design
### Data model
Conventions of TOKI-019 apply: UUIDv7 `id` made by the server, `workspace_id` required with a foreign key, times are `timestamptz` written by the server from the clock of TOKI-008 with no database default, closed lists are `text` with a named check, foreign keys are `ON DELETE RESTRICT` and named `<table>_<column>_fkey`. The migration is written with the foreign keys that leave the module (`workspace_id`) as SQL (TOKI-019 R22); the keys between `users` and the new tables are inside the `members` module and Drizzle writes them.

`invitations`, one row per invitation:
- `id`, `workspace_id`.
- `email`: required, lower case, no whitespace, at most 254 characters, as `users.email` (`invitations_email_check`, `invitations_email_length_check`).
- `role`: `member` or `admin`, required (`invitations_role_check`).
- `user_id`: nullable, the deactivated account this invitation brings back (R9); points to `users.id`.
- `invited_by`: required, the Admin who made it; points to `users.id`.
- `token_hash`: required, unique, 64 lower-case hexadecimal characters (`invitations_token_hash_key`, `invitations_token_hash_check`).
- `code_serial`: integer, required, 0 or more, 0 before the first code (`invitations_code_serial_check`); `code_issued_at`: required, the time of the latest code, so the 60 seconds of TOKI-097 can be read from it.
- `mail_status`: `sent` or `failed`, required (`invitations_mail_status_check`). Written `failed` with the row and `sent` once the mail layer said it delivered (R6), so a crash between the commit and the send leaves "Mail not sent" with Resend, never a false "Invited".
- `created_at`, `sent_at` (the latest send or resend), `expires_at`: required; `expires_at` is later than `sent_at` (`invitations_expires_at_check`).
- `used_at`, `used_by`, `revoked_at`: nullable; `used_by` points to `users.id` and is set with `used_at`; `used_at` and `revoked_at` are not both set (`invitations_closed_check`).
- Unique partial index `invitations_open_email_key` on (`workspace_id`, `email`) where `used_at` and `revoked_at` are both null: one open or expired invitation per address (R18, R10).
- The state is not stored: it is worked out from `used_at`, `revoked_at`, `expires_at` and the clock (R18), so the row never says "pending" after the time has passed and no job is needed to expire it.

`admin_actions`, append-only (R31): `id`, `workspace_id`, `actor_id` (required, `users.id`), `action` (six values, `admin_actions_action_check`), `target_user_id` (nullable, `users.id`), `target_email` (nullable, same rule as `invitations.email`), `detail` (jsonb, required, an object, `admin_actions_detail_check`), `created_at`. Trigger `admin_actions_append_only_trg` refuses `UPDATE` and `DELETE`; `TRUNCATE` is not blocked, so the test emptying step works (TOKI-028 R23). Decided in this spec: a table and not a log line (concern 7).

`member_requests`, the stored answer of R13: `id`, `workspace_id`, `user_id` (the actor, `users.id`), `request_key` (1 to 64 characters, pattern `^[A-Za-z0-9_-]{1,64}$`, `member_requests_request_key_check`), `action` (`invite` or `resend`), `request_hash` (64 lower-case hexadecimal), `state` (`pending` or `done`), `response_status` and `response_body` (jsonb), both null while pending and both set when done (`member_requests_done_check`), `created_at`, `completed_at`. Unique on (`user_id`, `request_key`) (`member_requests_user_id_request_key_key`). The stored body holds the invited addresses; it is personal data and is removed after 24 hours (R13).

All three tables need adding to the list of tables that the test emptying step (TOKI-008 R6) empties in one statement, or the step must be generic (TOKI-028 Plan changes).

### API
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/members` | Read the member list with counts (R21 to R25) |
| POST | `/api/v1/invitations` | Invite a batch of addresses (R4 to R13) |
| POST | `/api/v1/invitations/{invitationId}/resend` | Renew an invitation and send it again (R14) |
| POST | `/api/v1/invitations/{invitationId}/revoke` | Revoke an invitation (R16) |
| POST | `/api/v1/members/{userId}/role` | Change a role (R26) |
| POST | `/api/v1/members/{userId}/deactivate` | Deactivate a person (R28) |
| POST | `/api/v1/members/{userId}/reactivate` | Reactivate a person (R30) |

Every route needs an Admin session. Outcomes, by route (the error body is the format of TOKI-004). The 401 answers come from the session check of TOKI-022 and are the same for every route.

### How the parts run
How a batch runs:
1. Check the role and the body (R1, R4). Claim the key (R13); a repeat answers from the stored response.
2. For each distinct address in order, one transaction: classify the address (invalid, active account, open invitation, deactivated account or none), and for a new invitation insert the row (R6), create its code through `auth` and write the `admin_actions` row (R31). A database failure for one address is that address's error; the others go on. Two requests that insert the same address at once meet the partial unique index and the loser reports `already_invited` (R10).
3. After the transactions, hand the mails to the mail layer all together; the layer keeps at most 2 connections and bounds its queue and waiting (TOKI-021 R19, R25), so a batch of 50 to a dead mail server ends in about one connect limit and not in 50 sends one after another. Then set `mail_status` `sent` for each delivered mail.
4. Store the response under the key and answer 200.

How a person route runs: R27. For the role route the order is: lock, read the target and the count, call `canChangeRole`, write, record, commit. For deactivate the same with `canDeactivateAccount`; the sessions are ended after the commit (R28). The lock reads at most 200 rows (NFR-04: about 200 people), by the index of TOKI-019.

How the list is read: one query over accounts and not-yet-used, not-revoked invitations, as a union ordered by (lower-case name or address, id), with `search` and `status` as conditions and a keyset cursor, so a page costs the same at any depth. `counts` is a second grouped query over the same union with `search` only.

- This work owns the table and every change of an invitation. TOKI-097 never reads or writes `invitations`; it calls the three functions of R19. It writes the account, the member row of #general (`addMemberToGeneral`, which it adds to the `conversations` module) and the session itself (R20).

### Decided in this spec
These are technical choices the Blueprint leaves to the builder.
- Tables in the `members` module (concern 1), the record as a table (concern 7), the lock (concern 5), the repeat rule by a stored key (concern 6), the Join token and the code secret (concern 4).
- Every change is a `POST` (R3). Reason: the Origin rule of TOKI-022 covers `POST` and `DELETE`, not `PUT` or `PATCH`.
- Per-address results with status 200, and `invalid_email` as a result and not a 400 (R5, R10). Reason: D-099 says each row reports its own result, and one bad address must not stop the others.
- An expired invitation counts as already invited (R7). Reason: F02 says an already-invited address gets no duplicate, and an expired row keeps Resend, which is the one way to renew it.
- Resend replaces the token (R14). Reason: D-182 says the earlier mail stops working; the old link then finds no invitation, so its page reads as "not recognised" (D-081).
- The inviter in the mail is the Admin who sends it (R12). Reason: the original inviter may since have been deactivated, and the person who presses Resend is the one inviting now.
- `mail_status` is written `failed` first (Data model). Reason: a crash between commit and send must not show a false "Invited".
- The state of an invitation is worked out at read time (R18). Reason: no job exists before M4 (TOKI-064).
- The status of a row is the account's status for a deactivated person with an invitation (R22). Reason: the account is still deactivated until acceptance (D-094); the invitation is a field, so either choice of concern 3 needs no change of the API.
- Order by name, then id, and a keyset cursor (R23). Reason: D-109 asks for the first 50 and more on scroll; no decision fixes an order, and a stable order is needed for paging.
- `counts` follow the search and not the status filter (R24). Reason: D-074 says a chip count equals the rows shown.
- `limit` up to 100 (R21). Reason: D-109 fixes the first page at 50, not the largest page.
- Setting a state a person already has (same role, already deactivated or active) answers 200 and records nothing (R26, R29, R30). Reason: a repeat of the same request is ignored (D-111).
- A failed permission result `fact_missing` is a 500 (R1), and `last_admin` and `self_target` are 409 and not 403 (Outcomes). Reason: 403 sends the person to the "no access" page (D-131), which is wrong for a rule about the target.
- The new account is made with `createAccount` of TOKI-020 (R20). Reason: one insert path for accounts.

## Data safety
- An invitation holds the address of a person who is not a member, and `admin_actions` and `member_requests` hold addresses too. They stay for good in phase 1: invitations that are revoked or expired are kept so the Join link can say which it is (D-081), and nothing is deleted permanently (BR-29). Stored responses of R13 are removed after 24 hours. The `login_codes` rows of invitations are removed after 8 days (R33).
- Only the hash of a token is stored; a code is stored only as its hash by `auth`; none is logged (R11, R32). The mail carries the code and the link; the link alone signs nobody in (D-149).
- Only an Admin reads the list, which holds every person's address (R1). A Member gets nothing, not even a count.
- The record names the Admin for every action, so a mistake can be traced (D-110).
