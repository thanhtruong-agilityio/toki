# Member management API design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/member-management-api.md (Thanh Truong)
Ticket: TOKI-024

## Goal
An Admin needs to bring people into Toki and keep the member list in order: invite them with a role, resend or revoke an invitation, change a role, deactivate and reactivate a person, and read the list. Today the server has accounts and sign-in but none of this, so nobody but the first Admin can enter. This work adds the server operations, the table of invitations, the record of administrative actions, and the whole life of an invitation, including the moment it is accepted: the functions that the accept-an-invitation work calls, and the account that is created or brought back when it does. It states in one place the rules that protect the workspace: the last Admin, nobody deactivating themselves, a Member refused on every admin request, a repeat ignored.

## Scope
- In:
  - Seven routes under `/api/v1`: read the member list; invite a batch of addresses; resend and revoke an invitation; change a role; deactivate and reactivate a person (Design, "API").
  - The table `invitations`, the table `admin_actions` (the record of D-110) and the table `member_requests` (the repeat rule of D-111), in one migration, in the `members` module.
  - The life of an invitation: created, resent, revoked, expired, used (R18); the Join link and its token (R11); the four functions of the `members` module that the accept-an-invitation work calls, including the one that creates or brings back the account (R19, R20).
  - The locks that make "the last Admin" and "nobody deactivates themselves" hold when two requests arrive together, and the order in which every operation takes its locks (R27, R39).
  - Calling the `auth` module (invitation codes, ending sessions, last use), the mail layer, the permission functions and the `conversations` module (the member row of #general).
  - The request and response schemas, the limits (50, 7 days, 60 seconds) and the address-list parser in `packages/shared`; the new error codes.
  - Server integration and database tests.
- Out (not now):
  - The Admin page and its modal, row menu and confirmations: TOKI-025. This work says what the list returns (R21 to R25).
  - The page behind Join, its refusal pages, the three public routes (look up, send a new code, accept with the code), the check of the 6 digits, the session and the cookie after an accept, the "Minh joined" line: TOKI-097. This work gives it the four functions of R19, which do everything to the invitation and the account that the accept flow needs, and nothing else of that flow.
  - The code rules and the session functions: TOKI-022. The mail layer and the three mail texts: TOKI-021. The first Admin: TOKI-020. Listing and ending a person's own sessions, and the emergency link: TOKI-026.
  - What other people see of a deactivated person: the "Deactivated" label, leaving People and mention suggestions, read-only DMs (F41). They read `users.status`; each is the work of the ticket that builds that screen or list. This work stores nothing for them and deletes no message.
  - The Activity item and the live update for the person whose role or status changed (F40, F41): not owned by any ticket (concern 8).
  - Changing a person's own display name or sign-in address (D-098). Permanent deletion of an account: none in phase 1 (BR-29).
  - A limit of invitations across batches, and a screen for the record of actions: not decided (concern 12) and not in phase 1 (D-110).

## Requirements
Access and errors
- R1. Every route of this work needs a valid session (TOKI-022 R24) and an Admin. The checks run in this order on every route, and a Member never gets a 400 or a 404: (1) the session check of TOKI-022 (401); (2) `canOpenAdminPage`, a function that needs no body, query or id: a Member gets status 403 with the code `forbidden`, and nothing is created, changed or sent (D-090); (3) the schemas of the path, query, body and header (400, R2, R4); (4) the function of the route, with the actor of the session: `canInviteMember` for the batch, `canManageInvitations` for resend and revoke, `canChangeRole`, `canDeactivateAccount` and `canReactivateAccount` for the person routes (D-090); (5) inside every write transaction the actor is read again from its locked row and the function of step 4 is called again with it (R27, R39); a locked actor who is no longer an Admin gets 403 `forbidden`, and one who is deactivated gets 401 `account_deactivated`. A result `fact_missing` or `unknown_role` is a server error (status 500, `internal_error`), as TOKI-027 asks. Reason for the order: TOKI-027 R3 puts `unknown_role` before `role_not_allowed`, so a Member who sends `{ "role": "owner" }` would otherwise be answered 500 or 400 and not 403. No route compares a role itself.
- R2. Errors use the format of TOKI-004: `{ "error": { "code", "message", "details"? } }`. This work adds to the registry in `packages/shared` the codes `forbidden` (403), `batch_too_large` (400), `invitation_not_found` (404), `invitation_used` (409), `invitation_revoked` (409), `invitation_expired` (409), `last_admin` (409), `self_target` (409), `request_in_progress` (409) and `idempotency_key_reused` (409); the four `invitation_*` codes are the ones TOKI-097 uses for the same states, so there is one name for each. A body, query or parameter that fails its schema, a missing or malformed `Idempotency-Key`, or an id that is not a UUID gets 400 `validation_failed` (the code of TOKI-004, which TOKI-022 and TOKI-097 use too). A person that does not exist, or belongs to another workspace, gets 404 `not_found`; an invitation that does not, 404 `invitation_not_found`. Of the four `invitation_*` codes, the routes of this work answer `invitation_used` and `invitation_revoked` (R15); `invitation_expired` and `invitation_not_found` are also the refusals of the functions of R19.
- R3. Every route of this work that changes something is a `POST`. The only `GET` is the list, and it changes no row of `users`, `invitations`, `admin_actions` or `member_requests`; the one row it touches is the `last_used_at` of the caller's own session, which the session check sets for every request that passes (TOKI-022 R25). Reason for `POST`: the routes are actions on a person or an invitation (`resend`, `revoke`, `role`, `deactivate`, `reactivate`), not the creation or deletion of a resource, so no `DELETE`, `PUT` or `PATCH` is needed. TOKI-022 R46 refuses a foreign `Origin` for every method except `GET`, `HEAD` and `OPTIONS`, so every route here is covered by it as written, and a route with another verb would be too. TOKI-022 R36 (no `GET` creates or ends a session) holds.

Invite a batch
- R4. `POST /api/v1/invitations` takes `{ "emails": string[], "role"?: "member" | "admin" }` and the header `Idempotency-Key` (R13). `role` is `member` when absent. `emails` holds 1 to 50 entries (D-134), counted as sent, before any address is normalised: 0 entries or an entry that is not a string is 400 `validation_failed`; 51 or more is 400 `batch_too_large` with `details.max` 50; exactly 50 is accepted. Any other `role` is 400 `validation_failed`.
- R5. The response is status 200 with `{ "results": [...] }`: one result for each distinct address, in the order of first appearance. An entry is trimmed and put in lower case before anything else (the first two steps of `parseEmail` of TOKI-020 R16), and an address that appears twice in the request is reported once (D-099). An entry that is an empty string or only spaces is an address like any other: it is reported once as `{ "email": "", "result": "invalid_email" }`. A result is `{ "email", "result", "invitation"? }` with `result` one of `invited`, `mail_not_sent`, `already_member`, `already_invited`, `invalid_email`. The status is 200 whatever the results, so a batch where mail fails halfway still answers 200 and the invitations already made stay (D-099). `invitation` is present for `invited`, `mail_not_sent` and `already_invited` and has the shape of R22.
- R6. `invited` and `mail_not_sent`: for an address with no account and no unclosed invitation (R18), one transaction takes the lock of R39, inserts one `invitations` row with the role, the acting Admin as inviter, `created_at` and `sent_at` now, `expires_at` 7 days after `sent_at` (R18), `code_serial` 0 and `code_issued_at` now, makes the first code with the internal function behind `issueInvitationCode` (R19), which calls `createInvitationCode(tx, ...)` of TOKI-022 R49 in the same transaction (a function of `auth` that is given a transaction joins it, TOKI-022 R53), so a rolled-back invitation leaves no live code, and writes the `admin_actions` row (R31). After the commit one mail is handed to `sendInvitationMail({ to, code, workspaceName, inviterName, joinUrl })` of TOKI-021 R9 (`app.mail`) with the address, the 6 digits, the workspace name, the display name of the acting Admin and the Join address of R11. When the mail layer answers `ok: true` the row has `mail_status` `sent` and the result is `invited`. For any other answer of the mail layer the row stays, with `mail_status` `failed`, and the result is `mail_not_sent` (D-099, F02). The mail of one address never changes the result of another.
- R7. `already_invited`: an address with an unclosed invitation (R18), expired or not, is reported with its invitation as it stands. Nothing is created, no mail is sent, the 7 days are not restarted. A Resend is the way to renew it (R14). When two requests invite the same address at the same moment, exactly one unclosed invitation exists afterwards (the partial unique index of R38), and the other request reports `already_invited` for it (concern 1).
- R8. `already_member`: an address with an account whose status is `active` gets this result, creates no invitation and sends no mail (F02).
- R9. A deactivated account: an address with an account whose status is `deactivated` is invited like a new address (R6), and the new invitation holds that account's id as `user_id`. The account is not changed at this point (D-094). The role of the invitation is the role chosen in the request, not the role the account had (D-181).
- R10. `invalid_email`: an entry for which `parseEmail` of TOKI-020 R16 (`packages/shared/src/email.ts`) gives `null`, the rule that sign-in and set-up also use, gets this result, creates nothing and sends nothing, and the other addresses are processed (F02).
- R11. The Join link. For each invitation and for each resend, a token of 32 random bytes from a cryptographic source, written as 43 characters of base64url, is made. The database stores only its SHA-256, taken over the 43-character string, as 64 lower-case hexadecimal characters (`token_hash`), never the token. The Join address is the app's own origin, then `/join#`, then the token: `<origin>/join#<token>`. Decided in this spec: the token is in the URL fragment, which a browser sends neither in a request line nor in a `Referer`, so it reaches no access log, proxy log or other site; a token in the path would be logged by whatever serves the page and kept in the history. This is the form TOKI-026 uses for its emergency link (`/emergency#<token>`). TOKI-097 serves `/join` and reads the token from the fragment (the Contract below). The origin is the value of the environment that TOKI-022 R46 reads for the `Origin` rule (its name is TOKI-096's); this work adds no variable. It includes the scheme, so the Join address is absolute, as `sendInvitationMail` requires (TOKI-021 R9). The secret bound to the invitation's code is `codeSecret(token, serial)` of R19: the token, a colon and the invitation's `code_serial` as a decimal number, so that each code of an invitation has its own secret and `request_hash` stays unique (TOKI-019 R14). The token alone signs nobody in (D-149): the code step needs the code of the mail.
- R12. The inviter named in the mail is the Admin who made the request, also on a resend (R14). The workspace name is read through the `workspace` module function that TOKI-022 uses for its name read. The mail language is English (D-180): this work passes no language.
- R13. The repeat rule (D-111). The batch route and the resend route need the header `Idempotency-Key`, 1 to 64 characters from `A-Za-z0-9_-`. After the checks of R1 steps 1 to 4, the server claims the key: it keeps, for each person and key, the hash of the request (route, parameters and the body after the schema has parsed it), a `claim_id`, and the response. A second request with the same key and the same hash, when the first has finished with a 200, gets the stored status and body, and creates no row, sends no mail and records no action. The same key with another hash is 409 `idempotency_key_reused`. The same key while the first request is still running is 409 `request_in_progress`. A request that has been running for 5 minutes or more is counted as dead and the key is taken over by the new request, which writes a new `claim_id`. The time is longer than the longest live batch, which is bounded by the mail layer (30 seconds for a slot and 30 seconds for a send, TOKI-021 R15 and R25) plus the database time of 50 addresses. The first request is fenced: when it completes, it updates the row only `WHERE claim_id` is still its own; if that matches no row it has lost its claim, stores nothing and answers what it computed. A takeover finds the invitations that the dead request made, so it reports those addresses as `already_invited`, with their `mailStatus` as it stands (`failed` for a mail that was never handed over); the list shows the true state and Resend is the way on. Only a 200 answer is stored: an answer of any other status (a 5xx, or the 403 of R1 step 5) deletes the claim, so the same request again is processed again. A replay returns the stored body even when the invitations it describes have changed since (for example one has been revoked): this is the rule of D-111 and is intended; the Admin page reloads the list after a batch or a resend (TOKI-025). Stored responses are removed 24 hours after they were made: each batch and each resend deletes up to 100 older rows, so a quiet workspace keeps them longer than 24 hours until the next batch or resend (no job exists before TOKI-064). The longest live request is bounded by that same limit, about 60 seconds plus database time, so a client waits longer than that; TOKI-025 gives these two routes 75 seconds and no other route more than its default. A client makes one key for each press of "Send invitations" and for each invitation it resends, sends the same key again when the earlier attempt ended with a timeout, a network error, a 5xx or `request_in_progress` (and, for a batch, with the same text and role), and makes a new key after a 200 or `idempotency_key_reused` (TOKI-025 R20, R22). A retry after a timeout meets the stored 200 or `request_in_progress`; a retry after a 5xx is processed again, so a Resend whose changes had committed before the failure is made a second time (a new token and a second mail, and the first mail stops working, D-182). The key is in the `member_requests` table (Data model). The person routes do not need a key: repeating one is already harmless (R26, R29, R30, R16).

Resend and revoke
- R14. `POST /api/v1/invitations/{invitationId}/resend` with the header of R13 renews an invitation that is pending or expired, whether its mail arrived or not (D-182). In one transaction, with the lock of R39 (the actor, then the invitation row), it re-reads the state and then makes a new token and replaces `token_hash`, sets `sent_at` now and `expires_at` 7 days after it, sets `mail_status` `failed`, makes a new code with the internal function behind `issueInvitationCode` (R19), which cancels the earlier unused code (TOKI-022 R49), and writes the `admin_actions` row. The 60 seconds of R19 do not apply to an Admin's Resend. After the commit it hands the mail to `sendInvitationMail` and sets `mail_status` `sent` when it was delivered. The response is status 200 with `{ "result": "invited" | "mail_not_sent", "invitation": {...} }`, with the same rules as R6. The earlier token finds no invitation (R19), and the earlier code does not work.
- R15. Resend of an invitation that is used or revoked is 409 `invitation_used` or `invitation_revoked`; nothing changes and no mail is sent. Revoke of a used invitation is 409 `invitation_used`. An unknown id is 404 `invitation_not_found`.
- R16. `POST /api/v1/invitations/{invitationId}/revoke` sets `revoked_at` now and answers status 200 with `{ "invitation": {...} }` whose `state` is `revoked`. Afterwards the Join link of that invitation is found with the state `revoked` (R19), and the address can be invited again (R6 creates a new invitation). Revoking an invitation that is already revoked answers 200 as the first time, changes nothing and records nothing. A revoked invitation is not in the list (R22). Revoke can be sent for an expired invitation.

Invitation life, and what the accept-an-invitation work calls
- R17. Revoking the invitation of a deactivated person changes nothing in the account: it stays `deactivated` with its role, name and member rows (D-094).
- R18. An invitation has one of four states, worked out from its columns by one function of the `members` module, `invitationState(row, now)`, which every read, the list and every re-check under a lock use; the first that applies in this order: `used` when `used_at` is set; `revoked` when `revoked_at` is set; `expired` when the time is at or after `expires_at`; otherwise `pending`. An invitation that is neither used nor revoked, pending or expired, is called unclosed below. An invitation can be used to join only while it is `pending`: refused at exactly 7 days and after (the same boundary as TOKI-022 R14). `used_at` is also set when an Admin reactivates the person's account directly (R30), so the old Join link then leads to the normal sign-in page (D-081). An address has at most one unclosed invitation: the database refuses a second one (R38).
- R19. The `members` module exports four functions for TOKI-097 and for no one else. The table "Contract with the accept-an-invitation work" gives the name, the arguments, the result, the errors and the caller of each, and is the only place where the shapes are written. In short: `findInvitationByToken` reads an invitation and its state and writes nothing; `codeSecret` builds the secret of a code; `issueInvitationCode` makes the next code of a `pending` invitation, with the 60 seconds between two codes held under the lock of the invitation row; `acceptInvitation` makes the account and closes the invitation (R20). The Admin routes of this work use the same code-making step inside their own transactions, without the 60 seconds.
- R20. Accepting an invitation is the work of `acceptInvitation(tx, { token, now })`, called by TOKI-097 in its transaction after it has checked the 6 digits with `checkInvitationCode` (the function does not check a code and is never called without that check). This work, and not TOKI-097, creates or brings back the account, so the change has one author. In order, in the caller's transaction: (1) the invitation is found by the hash of the token; none is `invitation_not_found`; (2) the locks of R39: the account of the address, if there is one, then the invitation row, which is read again; (3) the state: `used` is `invitation_used`, `revoked` is `invitation_revoked`, `expired` is `invitation_expired`, and these three write nothing; (4) no account for the address: one is inserted by this function, in `members`, with an insert of its own (`createFirstAdminAccount` of TOKI-020 fixes the role `admin` and is not used here), with an id made by the server, the workspace of the invitation, `created_at` now, `status` `active`, `role` the invitation's role (D-153), `display_name` the part of the address before the `@` as stored (lower case, at most 64 characters, so within the 80 of D-033, D-150) and the default language `en`; (5) an account whose status is `deactivated`: it is the same account brought back (D-094, D-181): first every session of the account is ended through `endSessionsOfUser(tx, userId, { reason: "deactivated" })` of TOKI-022 R30 (given the caller's transaction it joins it and reports nothing, R53, R50), because a session row that was never ended would live again when the status flips to `active`; then `status` becomes `active` and `role` the invitation's role; the display name, the language and the member rows are not changed; no second account is created; one `admin_actions` row `account_reactivated` is written with the person as `actor_id` and the `detail` `{ "via": "invitation", "invitationId", "invitedBy", "role", "earlierRole" }`, because a status and a role change here with no Admin pressing a button at that moment (D-110); (6) an account whose status is `active` already: nothing in the account changes (not its role, name or memberships) and no session is made; the invitation is closed (`used_at` now, `used_by` the account) and the result is `account_active`, which the caller commits and maps to the answer for a used invitation (409 `invitation_used`; the person is sent to sign in). Reason: the address already belongs to an active member, because an Admin's reactivation raced the accept or another path made the account, and an old invitation must not change the role of an active member; (7) the invitation is marked used: `used_at` now and `used_by` the account, in the same conditional update that checked the state; (8) `addMemberToGeneral(tx, { workspaceId, userId, createdAt })` of the `conversations` module (the workspace of the invitation) adds the member row of #general when it is missing and does nothing when it exists (a reactivated person has it, because deactivation deletes no member row), and returns the id of #general; it is one new export of that module (change request to TOKI-028 R18, concern 13). The result carries the account (with its `language`), the id of #general and `endedSessionIds`, the ids that step 5 ended (empty in every other case): the caller calls `reportSessionsEnded(endedSessionIds, "deactivated")` of TOKI-022 R50 after its commit, so the listeners hear of a session only when it is really ended. Two accepts at the same moment wait on the same invitation row; the second reads `used` and gets `invitation_used`, so exactly one account change, one member row and one `account_reactivated` row result. If any step throws, the caller's transaction rolls back and nothing is written, the ending of the sessions of step 5 included. Creating the session and the cookie, the "Minh joined" line and every answer to the browser are TOKI-097's.

The list
- R21. `GET /api/v1/members` is for an Admin (R1). Query: `search` (text), `status` (`invited`, `expired`, `active` or `deactivated`), `limit` (1 to 100, default 50, D-109) and `cursor` (the opaque value of the last response). A value outside these is 400 `validation_failed`.
- R22. The response is status 200 with `{ "members": [...], "counts": {...}, "activeAdminCount": number, "nextCursor": string | null }`. A member row is `{ "kind": "account" | "invitation", "userId": string | null, "email", "displayName": string | null, "role", "status", "lastActiveAt": string | null, "invitation": Invitation | null }`. `kind` `account` rows come from accounts and have `status` `active` or `deactivated`, the account's role and `displayName`; `kind` `invitation` rows are people who have no account yet and have `status` `invited` (state `pending`) or `expired` (state `expired`), the invited role, `displayName` null and `userId` null. An invitation that is used or revoked is not a row. An `Invitation` is `{ "id", "state": "pending" | "expired", "role", "mailStatus": "sent" | "failed", "invitedBy": { "id", "displayName" }, "createdAt", "sentAt", "expiresAt" }`; times are ISO 8601 strings in UTC (the web client turns them into numbers at its own boundary, TOKI-025 R5). An account row carries `invitation` when the account is deactivated and an unclosed invitation names it (R9): its `status` stays the account's status (concern 3). Every other account row has `invitation` null.
- R23. Order and pages. Rows are ordered by the key `lower(display name, or the address for a row with no name)` compared with the collation `"C"` (byte order of the lower-cased text), and then by id. Decided in this spec: one order for accounts and invitations together, so a person invited is found where the name or address would put them and the chips of the Admin page only filter (F39); the byte order puts a name that starts with an accented letter after every name that starts with an unaccented one, and the order is the same in the test database and in production because it does not depend on the database's default collation. `lower()` itself follows the database's character classes, so the test of the order uses upper and lower case of ASCII letters and one accented name in lower case. Whether the order should follow Vietnamese rules is part of concern 11. The first page has `limit` rows (50 by default); `nextCursor` is null on the last page. Reading all pages one after the other, with no change in between, gives every row once and none twice.
- R24. `search` keeps the rows whose display name or address contains the text, without regard to case. `status` keeps the rows with that status. `counts` is `{ "invited", "expired", "active", "deactivated" }`: the number of rows with each status among the rows that match `search`, whatever `status` says, so that a chip equals the rows shown (D-074, D-109). `activeAdminCount` is the number of active Admins of the workspace, whatever the query, so the screen can call the permission functions (TOKI-027 R12) to lock an entry with its reason.
- R25. `lastActiveAt` is the latest `last_used_at` among the sessions of the account, ended or not, or null when it has none; it is null for a `kind` `invitation` row. It is read through one `auth` function, `getLastUsedAtByUser(userIds)`, which reads the `sessions` table in one grouped query for the ids of the page and returns the latest `last_used_at` for each id, or null for a person with no session. Decided in this spec: this ticket adds it to the `auth` module (TOKI-022 leaves it to this ticket, its Scope) and TOKI-026 R17 is dropped, so there is one function and one owner; the list is its only caller in phase 1.

People
- R26. `POST /api/v1/members/{userId}/role` takes `{ "role": "member" | "admin" }` and answers 200 with `{ "member": Account }`, where `Account` is `{ id, email, displayName, role, status }`. It follows R27. `canChangeRole` refuses demoting the last active Admin: 409 `last_admin`; an Admin may demote themselves when there are two or more active Admins (TOKI-027 R12). The route also changes the role of a deactivated person, as `canChangeRole` allows (it allows demoting a deactivated Admin whatever the count and promoting anyone); it records `role_changed` as for anyone else, and the role then stays through a reactivation (R30) and is replaced by the role of the invitation if the person is invited again (D-181). Decided in this spec: no extra rule for a deactivated row; the Admin page decides whether to lock the entry. Setting the role the person already has answers 200, changes nothing and records nothing. The change is seen on the person's next request, because the server reads the role from the account on every request (TOKI-027).
- R27. The lock. Every person route (R26, R28, R30) runs in one transaction that first reads, with `SELECT id, role, status FROM users WHERE workspace_id = $1 ORDER BY id FOR NO KEY UPDATE`, every `users` row of the workspace (at most 200, NFR-04), then builds the actor and the target and counts the active Admins from those locked rows and not from the session check or an earlier read, then repeats the checks of R1 steps 2 and 4 with the locked actor, then calls the permission function with the count, then writes, then commits. The permission function is never called before the lock. A second request that needs the same rows waits and then reads the new state. If the locked actor is no longer an Admin the answer is 403 `forbidden`; if the actor is deactivated, 401 `account_deactivated`; if the target is not among the rows, 404 `not_found`. All rows are locked, and not only the Admins and the target, because with `READ COMMITTED` a `SELECT ... FOR NO KEY UPDATE ... WHERE role = 'admin'` would not see a person who another request has just promoted and so would undercount. Tests, each with two real connections: two Admins demote each other at the same moment, with exactly two Admins: one succeeds, the other is 403 `forbidden` (it wakes up as a Member), and the workspace has one Admin; two Admins deactivate each other: one succeeds, the other is 401 `account_deactivated`; three Admins A, B and C, where A demotes B while B's request to deactivate C is already waiting: B's request is 403 and C stays active; one Admin demotes themselves: 409 `last_admin` (TOKI-019 concern 7, TOKI-027 concern 5).
- R28. `POST /api/v1/members/{userId}/deactivate` answers 200 with `{ "member": Account }` whose `status` is `deactivated`. The actor deactivating themselves is 409 `self_target`; deactivating the last active Admin is 409 `last_admin`; deactivating a Member, or any Admin while two or more are active, succeeds (D-153). In the same transaction, after it sets the status, the server ends every session of the person through `endSessionsOfUser(tx, personId, { reason: "deactivated" })` of TOKI-022 R30 and R53, which joins the transaction: the status, the ended sessions and the `admin_actions` row are committed together or not at all, so no committed state has a deactivated person with a session of theirs still live. After the commit the route calls `reportSessionsEnded(ids, "deactivated")` of TOKI-022 R50, so the open connections of the person are closed (TOKI-038). If the process dies between the commit and that call, the sessions are ended in the database and only the notice is lost; the person is refused at once because the session check looks at the account before the session (TOKI-022 R27), and the process that held their connections is the one that died. Afterwards a request with any of their sessions is refused with 401 `account_deactivated`. No message, member row, device row or account row is deleted (BR-29).
- R29. Deactivating a person who is already deactivated answers 200, changes nothing, records nothing, and ends any session of the person that is still live, with the call and the notice of R28 (none is expected, because R28 ends them with the status; this covers a session that a sign-in running at that moment may have made).
- R30. `POST /api/v1/members/{userId}/reactivate` answers 200 with `{ "member": Account }` whose `status` is `active`. When the person is deactivated, under the locks of R27 and R39, it first ends every session of the person that is still live through `endSessionsOfUser(tx, ...)` with the reason `deactivated` (in the transaction, noticed after the commit as in R28), so an old session cannot come back to life, then sets the status. The role, the display name and the member rows stay as they were (F41). An unclosed invitation of that person gets `used_at` now and `used_by` the person, so the Join link of the mail leads to the normal sign-in page (R18); the role of that invitation is dropped, the role of the account stays, and the id and the role of the closed invitation are in the `detail` of the `account_reactivated` row, so the record explains why the invitation is gone (concern 14). The person signs in again with a code. Reactivating an active person answers 200 and changes nothing, and ends no session.

The record
- R31. Every action that changes something writes one row to `admin_actions` in the same transaction as the change, so the record and the change exist together or not at all (D-110, F02): `invitation_created` for each `invited` or `mail_not_sent` address, `invitation_resent`, `invitation_revoked`, `role_changed`, `account_deactivated`, `account_reactivated`. A row holds the acting Admin, the action, the account acted on or, for an invitation, the address, a `detail` object (the role, the earlier role, the invitation id, and for a reactivation the closed invitation, R30) and the time from the clock of TOKI-008. `account_reactivated` is also written when an invitation brings a deactivated account back (R20), with the person as the actor. A refused request, a repeat answered from the stored response, and a change that changed nothing write no row. The table refuses every `UPDATE` and `DELETE`. No route reads it (phase 1 has no screen).

Safety
- R32. The module writes no email address, token, code, Join address or `Idempotency-Key` to the log and puts none in an error body. The failure of a mail is logged once, by the mail layer (TOKI-021 R14); this module logs no line of its own for it.
- R33. Each batch and each resend calls `pruneInvitationCodes(db, olderThan, limit)` of the `auth` module with 8 days ago and 100, which deletes up to that many `invitation` rows of `login_codes` created before the time. Reason: TOKI-022 R48 removes only `sign_in` rows, and a code of an invitation cannot work 7 days and 10 minutes after its creation, so older rows hold an address for nothing. This replaces the rule that TOKI-019 handed over (remove the `invitation` rows of an address when its invitation is used, revoked or expired): the age rule needs no per-invitation bookkeeping and covers all three cases at once, at the price that a used or revoked invitation's code row lives up to 8 days, and longer in a workspace that sends neither a batch nor a resend. The function is TOKI-022 R51; it never deletes a `sign_in` row.
- R34. A session that no longer belongs to an Admin does not pass: because the role is read on every request, an Admin who was demoted gets 403 on the next request to any route of this work (R1), and a deactivated Admin gets 401 (R28). A request that was already waiting on a lock when this happened is stopped by the re-check after the lock (R1 step 5, R27, R39).

Shared package and tables
- R35. `packages/shared/src/members/` exports the Zod schemas of every request and response of R4 to R30, the constants `INVITATION_BATCH_MAX` (50), `INVITATION_LIFETIME_DAYS` (7), `INVITATION_RESEND_SECONDS` (60, D-038, D-082) and `INVITATION_TOKEN_PATTERN` (43 characters of the base64url alphabet, the shape of R11, the one definition that TOKI-097 imports), and `parseAddressList(text)` (the address check itself is `parseEmail` of TOKI-020 R16 in `packages/shared/src/email.ts`, which this work imports and does not write; whichever of TOKI-020 and TOKI-022 is built first creates the file). The routes validate with the same schemas. `parseAddressList` splits the text at commas and line breaks (CR, LF or both, F02), trims every piece, drops empty pieces, puts every piece in lower case, drops a piece that repeats an earlier one, and does nothing else: a piece with a space inside, an angle bracket or a semicolon is kept as typed and is reported by the server as `invalid_email`. TOKI-021 R26 pins its text of "7 days" to `INVITATION_LIFETIME_DAYS`.
- R36. One migration, `<number>_member_management.sql` made with `pnpm db:generate --name member_management` (TOKI-019 convention 8), creates `invitations`, `admin_actions` and `member_requests` and no other table, with the checks, keys and indexes of Data model and the hand-written statements (foreign keys that leave the module, the partial unique index, the append-only trigger). It changes no existing table and inserts no row. The tables are defined in `modules/members/schema.ts` and are not exported from the module's `index.ts` (TOKI-019 R21).
- R37. The `members` read functions that TOKI-022 and TOKI-027 call (find an account by address, get an account by id) return a status of `active` or `deactivated` only. An address that has an invitation and no account returns no account. "Invited" is a state of an invitation (R18, R22) and is not read from `users` (TOKI-019 concern 2).
- R38. The database holds these rules itself (Data model): an invitation's address follows the rule of `users.email`; its role is `member` or `admin`; `token_hash` is 64 lower-case hexadecimal characters and unique; `used_at` and `revoked_at` are not both set; `expires_at` is later than `sent_at`; at most one invitation of an address is neither used nor revoked; `mail_status` is `sent` or `failed`; `admin_actions` allows only the six actions and refuses update and delete; `member_requests` is unique by person and key, and a `done` row has a status and a body.
- R39. Locks, their modes and their order. Decided in this spec. Every operation of this work and `acceptInvitation` take their row locks in one order, `users` rows (by id) first and the invitation row last, and in these modes: the person routes take `FOR NO KEY UPDATE` on every account row (R27) and, for a reactivation, `FOR NO KEY UPDATE` on the invitation row; the batch (each address), resend and revoke take `FOR SHARE` on the row of the acting Admin, read the actor's role and status from it and call the permission function with it (R1 step 5), then resend and revoke take `FOR NO KEY UPDATE` on the invitation row; `acceptInvitation` takes `FOR NO KEY UPDATE` on the address's account row, if any, then on the invitation row; `issueInvitationCode` takes `FOR NO KEY UPDATE` on the invitation row only. `FOR UPDATE` is not used. Reason: a transaction that inserts a row that points to a `users` row (an `invitations` row with `invited_by` or `user_id`, an `admin_actions` row with `actor_id` or `target_user_id`, a session) takes `FOR KEY SHARE` on that row for the foreign key. `FOR UPDATE` conflicts with `FOR KEY SHARE`, so a person route holding `FOR UPDATE` on rows in id order could wait on a batch that holds the lock of one row and wants a key share on another, and the batch on the person route: a deadlock that Postgres ends by aborting one request, and every sign-in that inserts a session for a locked person would stall. `FOR NO KEY UPDATE` does not conflict with `FOR KEY SHARE`, two of them still exclude each other, and `FOR SHARE` (the actor read of a batch) conflicts with it, so a demotion that holds the lock is waited for and the actor is read after it. A person route changes only `role` and `status`, which are in no unique index, so it needs nothing stronger. This rests on the lock-mode conflict table of the PostgreSQL documentation and has not been run against a database, so the two-connection tests of Testing (a batch and a deactivation of an invited person at the same moment; a reactivation and an accept at the same moment; every pair of the operations above) are what proves the claim when the work is built. If a batch's re-check finds that the actor is no longer an Admin partway through, the remaining addresses are not processed, the invitations already made stay and are recorded, and the answer is 403 `forbidden` (401 `account_deactivated`), which R13 does not store.

The order for the whole server, which TOKI-029 R15 and TOKI-030 R22 follow and TOKI-031 needs none of (it takes no lock): (1) `users` rows, in id order, in one statement; (2) the invitation row; (3) the `conversations` row; (4) rows that belong to a conversation (member rows, messages). A transaction takes its locks in this order and never takes one with a lower number than one it holds. Modes: on `users`, `FOR NO KEY UPDATE` for a write to that account (the person routes, `acceptInvitation`) and `FOR SHARE` for a transaction that needs the account to stay as it is (the actor of a batch, a resend and a revoke; the actor and the other people of a channel or direct-message write, through `getAccountsByIds(tx, ids, { lock: "share" })` of TOKI-029 R19); on an invitation and on a conversation, `FOR NO KEY UPDATE`; `FOR UPDATE` nowhere. A read-only request (the list, the bootstrap of TOKI-031) takes no lock. The member row of #general that `acceptInvitation` inserts (R20 step 8) comes after locks 1 and 2 and takes only the key-share locks of its foreign keys, which no mode in this list conflicts with, so it needs no place of its own. The claim of R13 is a short transaction of its own that holds no other lock.

## Design
### Data model
Conventions of TOKI-019 apply: UUIDv7 `id` made by the server, `workspace_id` required with a foreign key, times are `timestamptz` written by the server from the clock of TOKI-008 with no database default, closed lists are `text` with a named check, foreign keys are `ON DELETE RESTRICT` and named `<table>_<column>_fkey`. The migration is written with the foreign keys that leave the module (`workspace_id`) as SQL (TOKI-019 R22); the keys between `users` and the new tables are inside the `members` module and Drizzle writes them.

`invitations`, one row per invitation:
- `id`, `workspace_id`.
- `email`: required, lower case, no whitespace, at most 254 characters, as `users.email` (`invitations_email_check`, `invitations_email_length_check`).
- `role`: `member` or `admin`, required (`invitations_role_check`).
- `user_id`: nullable, the deactivated account this invitation brings back (R9); points to `users.id`.
- `invited_by`: required, the Admin who made it; points to `users.id`.
- `token_hash`: required, unique, 64 lower-case hexadecimal characters (`invitations_token_hash_key`, `invitations_token_hash_check`).
- `code_serial`: integer, required, 0 or more, 0 before the first code (`invitations_code_serial_check`); `code_issued_at`: required, the time of the latest code (the row's creation time until the first code is made in the same transaction), so the 60 seconds of R19 are read from it.
- `mail_status`: `sent` or `failed`, required (`invitations_mail_status_check`). Written `failed` with the row and `sent` once the mail layer said it delivered (R6), so a crash between the commit and the send leaves "Mail not sent" with Resend, never a false "Invited".
- `created_at`, `sent_at` (the latest send or resend), `expires_at`: required; `expires_at` is later than `sent_at` (`invitations_expires_at_check`).
- `used_at`, `used_by`, `revoked_at`: nullable; `used_by` points to `users.id` and is set with `used_at`; `used_at` and `revoked_at` are not both set (`invitations_closed_check`).
- Unique partial index `invitations_open_email_key` on (`workspace_id`, `email`) where `used_at` and `revoked_at` are both null: one unclosed invitation per address (R18, R7).
- The state is not stored: it is worked out from `used_at`, `revoked_at`, `expires_at` and the clock (R18), so the row never says "pending" after the time has passed and no job is needed to expire it.

`admin_actions`, append-only (R31): `id`, `workspace_id`, `actor_id` (required, `users.id`), `action` (six values, `admin_actions_action_check`), `target_user_id` (nullable, `users.id`), `target_email` (nullable, same rule as `invitations.email`), `detail` (jsonb, required, an object, `admin_actions_detail_check`), `created_at`. Trigger `admin_actions_append_only_trg` refuses `UPDATE` and `DELETE`; `TRUNCATE` is not blocked, so the test emptying step works (TOKI-028 R23). Decided in this spec: a table and not a log line (concern 7).

`member_requests`, the stored answer of R13: `id`, `workspace_id`, `user_id` (the actor, `users.id`), `request_key` (1 to 64 characters, pattern `^[A-Za-z0-9_-]{1,64}$`, `member_requests_request_key_check`), `action` (`invite` or `resend`), `request_hash` (64 lower-case hexadecimal), `state` (`pending` or `done`), `claim_id` (uuid, required, replaced when a dead request is taken over), `response_status` and `response_body` (jsonb), both null while pending and both set when done (`member_requests_done_check`), `created_at`, `claimed_at` (the time of the latest claim, from which the 5 minutes of R13 are counted), `completed_at`. Unique on (`user_id`, `request_key`) (`member_requests_user_id_request_key_key`). The stored body holds the invited addresses; it is personal data and is removed after 24 hours (R13).

All three tables need adding to the list of tables that the test emptying step (TOKI-008 R6) empties in one statement, or the step must be generic (TOKI-028 Plan changes).

### How the parts run
How a batch runs:
1. Check the role and the body in the order of R1 (steps 1 to 4). Claim the key (R13); a repeat answers from the stored response.
2. For each distinct address in order, one transaction: lock the actor and check the role again (R39), classify the address (invalid, active account, unclosed invitation, deactivated account or none), and for a new invitation insert the row (R6), create its code through `auth` in the same transaction and write the `admin_actions` row (R31). A database failure for one address is that address's error; the others go on. Two requests that insert the same address at once meet the partial unique index and the loser reports `already_invited` (R7).
3. After the transactions, hand the mails to the mail layer all together; the layer keeps at most 2 connections and bounds its queue and waiting (TOKI-021 R19, R25), so a batch of 50 to a dead mail server ends in about one connect limit and not in 50 sends one after another. Then set `mail_status` `sent` for each delivered mail. Prune old stored answers and old invitation codes (R13, R33).
4. Store the 200 response under the claim and answer.

How a person route runs: R27 and R39. For the role route the order is: lock every account row, read the actor, the target and the count, call `canChangeRole`, write, record, commit. For deactivate the same with `canDeactivateAccount`; the sessions are ended inside the transaction and noticed after the commit (R28). For reactivate the same with `canReactivateAccount`; the sessions are ended before the status is set, inside the transaction's lock, and the unclosed invitation is closed (R30). The lock reads at most 200 rows (NFR-04: about 200 people), by the index of TOKI-019.

How the list is read: one query over accounts and not-yet-used, not-revoked invitations, as a union ordered by (lower-case name or address with the collation `"C"`, id), with `search` and `status` as conditions and a keyset cursor, so a page costs the same at any depth. `counts` is a second grouped query over the same union with `search` only.

### Contract with the accept-an-invitation work (TOKI-097)
The four functions of R19, written once. `db` is the database client and `tx` an open transaction of TOKI-005; `now` is the time from the clock of TOKI-008 that the caller passes in.

| Function | Arguments | Result | Errors | Called by |
|---|---|---|---|---|
| `findInvitationByToken` | `(db, token, now)` | `null` when no invitation has the SHA-256 of the token (a token replaced by a Resend finds nothing, and a token that is not 43 base64url characters finds nothing without a query); else `{ id, email, role, state, accountId, codeSerial, codeIssuedAt, expiresAt }` with `state` one of `pending`, `expired`, `revoked`, `used` (R18) and `accountId` the `user_id` of the invitation or null | none; writes nothing | TOKI-097: look up, and the read before "Resend code" and before an accept |
| `codeSecret` | `(token, codeSerial)` | the string `<token>:<codeSerial>`, the secret of that code (R11); pure | none | TOKI-097: `checkInvitationCode(codeSecret(token, invitation.codeSerial), digits)` before an accept |
| `issueInvitationCode` | `(db, { token, now, minIntervalSeconds? })` | `{ ok: true, email, code }`: in its own transaction it locks the invitation row (R39), reads the state again, and when `minIntervalSeconds` is given and `now` minus `code_issued_at` is less than it, refuses; otherwise adds 1 to `code_serial`, sets `code_issued_at` to `now`, calls `createInvitationCode(tx, email, codeSecret(token, serial))` of TOKI-022 R49 (which cancels the earlier unused code), and returns the 6 digits. It sends no mail | `{ ok: false, error }` with `error` one of `invitation_not_found`, `invitation_used`, `invitation_revoked`, `invitation_expired` (only a `pending` invitation gets a code here; the Admin's Resend is what renews an expired one) or `resend_too_soon` with `retryAfterSeconds` (whole seconds, rounded up, at least 1; at exactly `minIntervalSeconds` the call is accepted) | TOKI-097: "Resend code", with `minIntervalSeconds` `INVITATION_RESEND_SECONDS` (60), then `sendInvitationCode` after it returns (TOKI-021 R24). Two presses at the same moment wait on the lock; the second sees the new `code_issued_at` and gets `resend_too_soon` |
| `acceptInvitation` | `(tx, { token, now })` | `{ ok: true, account: { id, email, displayName, role, status, language }, created: boolean, reactivated: boolean, generalConversationId, endedSessionIds }`, after R20 steps 1 to 8 | `{ ok: false, error }` with `error` one of `invitation_not_found`, `invitation_used`, `invitation_revoked`, `invitation_expired` (these write nothing) or `account_active` (the invitation is closed: the caller commits and answers as for `invitation_used`) | TOKI-097 "accept", in its transaction, after `checkInvitationCode` returned ok; it then creates the session after the commit and calls `reportSessionsEnded(endedSessionIds, "deactivated")` of TOKI-022 R50 |

How TOKI-097 maps the results to its answers: `invitation_not_found` is 404, `invitation_used`, `invitation_revoked` and `invitation_expired` are 409 with the same codes, `resend_too_soon` is 429 with `code_resend_too_soon`, and `account_active` is 409 `invitation_used`.

What stays as written:
- This work owns the table and every change of an invitation. TOKI-097 never reads or writes `invitations` or `users`; it calls the four functions above.
- The Join address is built here, in the one place that makes a token (R6, R14): `<origin>/join#<token>` (R11). TOKI-097 serves `/join` and reads the token from `location.hash`; it never sends the token in a path or a query string.
- The first code and the code of a resend are made here, in the transaction that makes the row or replaces the token, with the same step as `issueInvitationCode` without the 60 seconds. A new code after the person pressed Join is made by `issueInvitationCode` and sent by TOKI-097 with `sendInvitationCode` (TOKI-021 R24).
- The three public routes of TOKI-097 (`/api/v1/invitations/lookup`, `/codes`, `/sessions`) share the path prefix with the routes here and do not collide with them: the routes here have an invitation id between `invitations` and the verb, or are `POST /invitations` alone. The four `invitation_*` codes are one set (R2).
- A reactivation by an Admin closes the invitation as `used` (R30).
- The member row of #general is made by `addMemberToGeneral` of the `conversations` module, called from `acceptInvitation` (R20 step 8). TOKI-028 R18 lists the exports of that module and none writes; the change request is one export, owned by TOKI-028 (concern 13), so TOKI-097 no longer adds it.

### Decided in this spec
These are technical choices the Blueprint leaves to the builder.
- Tables in the `members` module (concern 1), the record as a table (concern 7), the locks (concern 5), the repeat rule by a stored key (concern 6), the Join token and the code secret (concern 4).
- This work creates or brings back the account when an invitation is accepted, and adds the member to #general (R20). Reason: `users` belongs to the `members` module, so TOKI-097 cannot write it, and one function in one transaction under the lock of the invitation is the only way two accepts at once leave one account change.
- The Join address carries the token in the fragment (R11). Reason: it reaches no log or `Referer`.
- The 60 seconds between two codes are held where the code is made, under the lock of the invitation row (R19). Reason: a rule applied outside the lock lets two presses at once both pass.
- Every change is a `POST` (R3). Reason: the routes are actions, not resources.
- Per-address results with status 200, and `invalid_email` as a result and not a 400 (R5, R10). Reason: D-099 says each row reports its own result, and one bad address must not stop the others.
- An expired invitation counts as already invited (R7). Reason: F02 says an already-invited address gets no duplicate, and an expired row keeps Resend, which is the one way to renew it.
- Resend replaces the token (R14). Reason: D-182 says the earlier mail stops working; the old link then finds no invitation, so its page reads as "not recognised" (D-081).
- The inviter in the mail is the Admin who sends it (R12). Reason: the original inviter may since have been deactivated, and the person who presses Resend is the one inviting now.
- `mail_status` is written `failed` first (Data model). Reason: a crash between commit and send must not show a false "Invited".
- The state of an invitation is worked out at read time (R18). Reason: no job exists before M4 (TOKI-064).
- The status of a row is the account's status for a deactivated person with an invitation (R22). Reason: the account is still deactivated until acceptance (D-094); the invitation is a field, so either choice of concern 3 needs no change of the API.
- Order by the lower-cased name or address in byte order, then id, and a keyset cursor (R23). Reason: D-109 asks for the first 50 and more on scroll; no decision fixes an order, and a stable order that does not depend on a database setting is needed for paging.
- `counts` follow the search and not the status filter (R24). Reason: D-074 says a chip count equals the rows shown.
- `limit` up to 100 (R21). Reason: D-109 fixes the first page at 50, not the largest page.

## Data safety
- An invitation holds the address of a person who is not a member, and `admin_actions` and `member_requests` hold addresses too. They stay for good in phase 1: invitations that are revoked or expired are kept so the Join link can say which it is (D-081), and nothing is deleted permanently (BR-29). Stored responses of R13 are removed after 24 hours by the next batch or resend, so they stay longer in a workspace that sends neither. The `login_codes` rows of invitations are removed after 8 days in the same way (R33).
- Only the hash of a token is stored; a code is stored only as its hash by `auth`; none is logged (R11, R32). The mail carries the code and the link; the link alone signs nobody in (D-149). The token is in the fragment of the Join address, so it is not sent in a request line, a log or a `Referer` (R11).
- Only an Admin reads the list, which holds every person's address (R1). A Member gets nothing, not even a count.
- The record names the Admin for every action, so a mistake can be traced (D-110).
