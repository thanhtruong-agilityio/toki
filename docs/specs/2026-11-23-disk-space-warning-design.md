# Disk-space warning and upload refusal design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/disk-space-warning.md (Thanh Truong)
Ticket: TOKI-103

## Goal
Toki has no storage quota (D-106), so the disk of the one server is the only limit. This work lets the server read how full that disk is, tells an Admin at the top of the Admin page when it is 80% full or more, and makes the server refuse every new upload, with its reason, when it is 95% full or more. Messages keep working in every case, so the people of the workspace can still talk while an Admin frees space.

## Scope
- In:
  - A pure rule that turns the numbers of a disk into a percentage and one of four states, `ok`, `warning`, `full`, `unknown` (R1, R2).
  - A measurer that reads the disk with `statfs` on a configured path, an injected seam for tests, and a service that never throws (R3, R4).
  - The variable `STORAGE_DISK_PATH`, its row in the inventory and its line in `.env.example`, and the check at start-up (R5, R6).
  - One read route for Admins, `GET /api/v1/storage/disk` (R7), and the shared response shape (R8).
  - The refusal: the error code `storage_full`, the function that raises it and the rule for where it is called (R9, R10, R11).
  - The notice region of the Admin page: the read, the refresh, the four displays and the failure cases (R12 to R15).
  - The texts, in English and a Vietnamese proposal, including the reason text that a refused uploader sees (R16, R17).
- Out (not now):
  - The upload routes, the signed addresses and the `files` tables: TOKI-058. This work gives it the function to call and the rule for where to call it (R10); it adds no upload route.
  - The attachment card in the composer that shows a refused file and its Retry: TOKI-059. It shows the reason text of R17 when the request fails with the code of R9.
  - Thumbnails and link previews, which workers write after a message is sent (TOKI-060, TOKI-061): they are not uploads by a person and are not refused (concern 6).
  - Any periodic job or stored measurement: none is needed (concern 4); TOKI-064 is not used.
  - A quota per person or per channel, a clean-up tool, a screen that lists large files, mail or push notice of a full disk. D-106 says no quota; the log asks for none of the rest.
  - Showing the warning anywhere besides the Admin page (concern 2).
  - The production Compose file and the way the measured path is mounted into the server container: TOKI-084. This work states what the path must be (R5).

## Requirements
- R1. `apps/server/src/modules/disk-space/classify.ts` exports two constants, `DISK_WARN_PERCENT = 80` and `DISK_FULL_PERCENT = 95` (D-106), the type `DiskStats` `{ blocks, free, available, blockSize }` (all non-negative integers, as `statfs` reports them) and the pure function `classifyDisk(stats)`. It computes `used = blocks - free` and `usedPercent = floor(100 * used / (used + available))`, the figure `df` prints; it returns `{ state, usedPercent }`. `state` is `full` when `used * 100 >= 95 * (used + available)`, else `warning` when `used * 100 >= 80 * (used + available)`, else `ok`; the comparison uses integers only, so no rounding decides a boundary. The two levels are inclusive: exactly 80% is `warning` and exactly 95% is `full` (concern 7). When `used + available` is 0, or a field is not a non-negative integer, the result is `{ state: "unknown", usedPercent: null }`. Check: a table test with exact boundaries (79.99%, 80%, 94.99%, 95%, 100%) at block counts where the float form would round the wrong way; a disk with `free > available` (root reserve) counts the reserve as used space, not as free space, as `df` does; zero blocks and a negative or fractional field give `unknown`.
- R2. The percentage in a reading is an integer from 0 to 100, rounded down, so a reading never shows 80 while the state is `ok`. Check: for 1,000 generated pairs of `used` and `available`, `state` is `warning` or `full` exactly when `usedPercent >= 80`.
- R3. The module exports `type DiskMeasurer = () => Promise<DiskStats>` and `statfsMeasurer(path)`, the only code of the server that calls `statfs`; it reads `fs.promises.statfs(path)` and returns `{ blocks, free: bfree, available: bavail, blockSize: bsize }`. A test uses a measurer that returns fixed numbers or throws; no test fills a disk. Check: the test of `statfsMeasurer` runs it on a temporary directory and finds positive `blocks` and `blockSize` and `available <= free <= blocks`; a lint or test scan finds `statfs` in no other file of `apps/server/src`.
- R4. `createDiskSpace({ measure, logger })` returns `{ read(): Promise<DiskReading> }` with `DiskReading` `{ state: "ok" | "warning" | "full" | "unknown"; usedPercent: number | null }`. Each `read()` calls `measure` once and keeps no value: there is no cache and no timer (concern 4). `read()` never rejects: when `measure` throws or rejects, or returns what R1 calls unreadable, it logs one `error` line that names the error kind and carries no path and no stack of the system, and returns `{ state: "unknown", usedPercent: null }`. Check: tests with fixed stats, a throwing measurer, a rejecting measurer and an unreadable result; two reads in a row call the measurer twice and the second reflects a changed measurer (a changed disk is seen at once); the log line holds no path.
- R5. The server reads a new variable `STORAGE_DISK_PATH`: the path of a directory on the filesystem that holds the file storage, that is, the volume of MinIO's data (D-191, concern 1). It is a new area `storageDisk` of `apps/server/src/config.ts` (`{ path }`), a non-empty string; unset or empty counts as missing, as for every variable. The inventory `docs/environment-config.md` gets one row in the File storage table: Required yes, Default none, Development value `.`, Supplied by "the operator of that installation", Secret no, Read by server; its Purpose says that in the standard one-server Compose installation any path on the disk that holds the MinIO volume gives the right figure, and that when MinIO's data is on its own disk the path must be a directory on that disk, mounted into the server container. `.env.example` gets the line `STORAGE_DISK_PATH=.`. `configVariableNames` lists the name so the existing check of names against `.env.example` passes. Every launcher that starts `apps/server/src/main.ts` (the real-launch scripts of the end-to-end suites) sets the variable. Check: `config.test.ts` accepts a path and reports the name, never a value, when it is missing or empty; the existing names-equal-`.env.example` test passes; the launchers start with the variable set.
- R6. At start `main.ts` loads the area `storageDisk` with the others and reads the disk once with `statfsMeasurer`. A path that cannot be read stops the start with one line on standard error, `STORAGE_DISK_PATH cannot be read`, and exit code 1, before the server listens; the line carries no path. Check: a test of the start-up function with a measurer that throws gets that line and the exit; with a working measurer it continues.
- R7. `GET /api/v1/storage/disk` answers 200 with `{ "state": ..., "usedPercent": ... }` (R8) and the header `Cache-Control: no-store`. It needs a session (401 as for every route). Its first step after the session is `refuse(canOpenAdminPage(actor))` of TOKI-027, as the member routes do, so a Member gets 403 `forbidden` whatever the query; only then does it call `read()` (D-090). It reads no table and takes no query parameter: a query string is ignored. Check: a table test with no session (401, `read` not called), a Member (403, `read` not called) and an Admin (200) for each of the four states from a injected `diskSpace`; the header is present; the body parses with the schema of R8.
- R8. `packages/shared` exports `DiskSpaceResponseSchema`, a strict Zod object with `state` (one of the four values) and `usedPercent` (an integer 0 to 100, or `null`), and the rule that `usedPercent` is `null` exactly when `state` is `unknown`. The response carries no byte count and no path: the page needs neither (concern 8). Check: a schema test accepts the four valid forms and refuses an added key, a percent of 101 or a fractional one, `unknown` with a number and a state with `null`.
- R9. `ErrorCodes` in `packages/shared/src/error.ts` gains `storageFull: "storage_full"`. A refused upload answers 507 with the standard error body, code `storage_full` and the fixed English developer message "Uploads are refused because the server's storage is full." (D-106, concern 3). The body carries no `details`, no percent and no path: a Member must not learn the disk figures. 507 is a status of 500 or more, so `classifyApiError` already returns `retry` for it, which is right: the same upload may succeed once an Admin has freed space. Check: the registry test lists the new code once and keeps the older codes; an error built by R10 serializes to exactly that status, code and message and has no `details`; `classifyApiError` gives `retry` for it.
- R10. The module exports `assertUploadsAllowed(diskSpace)`: it calls `read()`, throws `AppError(507, "storage_full", …)` when the state is `full`, and returns for `ok`, `warning` and `unknown` (concerns 5 and 7). `buildApp` takes an optional `diskSpace` and decorates the app with `app.diskSpace`; it builds the real service from `config.storageDisk` when no `diskSpace` is passed, and when neither is given (a test of another area) it decorates a service that always reads `ok`, as the mail layer does for tests. The rule for the upload routes of TOKI-058: every route that starts an upload, that is, every route that issues a signed address to write a file or creates the row for a file that is about to be written, calls `assertUploadsAllowed(app.diskSpace)` after its session, permission and body checks and before it signs anything or writes a row, so a refused request leaves no file row and no address. The size of the file is not added to the reading: the rule judges the disk as it is (concern 7). An upload already started with an address issued before the disk reached 95% is not stopped. Check: tests with an injected `diskSpace` for the four states (only `full` throws); a stand-in route that follows the rule is refused before its stand-in "sign" and "insert" steps run (spies not called) and passes through for the other three states; a scan test finds `assertUploadsAllowed` in no file of `apps/server/src` except the module, the routes that start an upload, and the tests. The test that the real upload route of TOKI-058 refuses at `full` with that code, and that an Admin and a Member are refused alike, is written by TOKI-058's change (R10 is the line between the two).

Messaging, reading and downloading never call R10 and never read the disk: sending, editing and deleting a message, reactions, history, the other `GET` routes and the signed address that reads a file are unchanged at every state. A message that carries files that were uploaded before the disk filled is still sent. Check: with `diskSpace` fixed at `full`, the member list, the channel routes and the bootstrap route answer as with `ok`; and with the same injection a send to `POST /api/v1/conversations/{id}/messages` answers 201 (written in this ticket's change when that route is on `main` at build time; otherwise in the change of whichever of TOKI-037's route and TOKI-058 lands second, which adds it with its own test).

## Design
### How the server measures (Decided in this spec)
The server calls `statfs` on the configured path from inside its own process. The server runs in a container on the one VPS (technical design), where MinIO and Postgres also run, and a container cannot read another container's volume. Two cases are covered by the one variable: (a) the standard installation, where every Docker volume lives on the single 80 GB disk of the VPS, and any path in the server container, including `/`, reports the figures of the filesystem that backs it, which is that disk; (b) a MinIO volume on its own disk, where the operator mounts a directory of that disk into the server container (read-only is enough, `statfs` writes nothing) and names it in `STORAGE_DISK_PATH`. `statfs` is one cheap system call that reads no file, so the server takes a new measurement for each use instead of keeping one (concern 4). The figure is `used / (used + available)` as `df` shows it, so the number an operator reads on the machine equals the number in the warning (R1).

### Where the reading is used
```
GET /api/v1/storage/disk   Admin only    Admin page notices (R12 to R15)
assertUploadsAllowed()     upload routes  refuse at 95% (R10; TOKI-058 calls it)
```
Both go through `app.diskSpace`, so a test injects the one measurer and sees both the page and the refusal change together.

### API
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/storage/disk` | The state and the percent used of the disk that holds the files; Admin only (R7). The name is fixed here (D-125). |

### Errors
- No session -> 401, as every route.
- A Member asks for the route -> 403 `forbidden`, before the disk is read.
- An upload starts at `full` -> 507 `storage_full`, no body details (R9).
- The disk cannot be read at run time -> the route answers 200 `unknown`; the uploads are allowed; one error line is logged (concern 5).
- The disk cannot be read at start -> the server does not start (R6).

### Layout
```
apps/server/src/modules/disk-space/
├─ classify.ts      constants, DiskStats, classifyDisk (R1, R2)
├─ measure.ts       DiskMeasurer, statfsMeasurer (R3)
├─ service.ts       createDiskSpace, assertUploadsAllowed (R4, R10)
├─ routes.ts        GET /storage/disk (R7)
└─ index.ts         the public surface
packages/shared/src/storage/disk-space.ts     DiskSpaceResponseSchema (R8)
apps/web/src/admin/notices.tsx, useDiskSpace.ts, admin.css (adm-notice rules)
```

### Screen
The notice sits in the `adm-notices` region above the members section (TOKI-025 R27). It is one block of text with an icon, full width of the page content, with the colour tokens of the existing warning and danger roles of `tokens` (no new token); it has no close button, because it disappears by itself when the disk is below 80% again.

## Data safety
- The route returns a state and a whole percent, never a path, a size or a file name; the refusal error carries no figure. A Member can learn only that uploads are refused (R9).
- The log line of a failed measurement names the error kind and no path (R4). The measured path is a value of `.env`, which is never in git; the inventory row and `.env.example` hold the development value `.`, which is not a secret.

## Open questions from the intent
- Which disk is measured, the volume that holds the files or the one that holds the database? Answered in this spec: the filesystem that holds the file storage, named by `STORAGE_DISK_PATH`; on the standard one-disk installation it is the same disk as the database's. D-191 is still Open in the log and proposes the same. See concern 1.
- Is the warning shown anywhere besides the Admin page? Not answered. Carried forward as concern 2.
- How often does the Admin page look at the disk, and does the server keep a measurement? Answered in this spec: the page reads on open and every 5 minutes, and the server measures at each use and keeps nothing (R4, R12). See concern 4.
- What status and code does a refused upload get, and what does it cover? Answered in this spec: 507 `storage_full`, covering the start of an upload only (R9, R10, R11). See concerns 3 and 6.
- What happens when the server cannot read the disk? Answered in this spec: uploads are allowed, the Admin sees an "unknown" notice, and the start-up refuses a path it cannot read (R6, R10, R13). See concern 5.
- Does the 95% rule count the size of the file being uploaded? Answered in this spec: no, it judges the disk as it is (R10). See concern 7.

## Areas of concern
1. Which disk is measured. D-106 says "the disk" and the log row D-191 asks which one; its status is Open and its text is only a proposal ("the volume that stores files"). Decided in this spec, as a technical choice of the builder: the filesystem that holds the file storage (MinIO's data), named by `STORAGE_DISK_PATH` (R5); in the standard one-VPS installation this is the same disk as the database, so one figure covers both. Reason: the files are what grows without a quota, and the refusal protects the database that shares the disk. The product owner can confirm or change the log row. Owner: Thanh Truong (product owner).
2. Is the warning shown anywhere besides the Admin page? The plan line and journey F39 name the Admin page; D-191 proposes "on the Admin page only" but is Open. Not decided. This work builds the Admin page only, as the plan line says, and adds no banner, mail, push or Activity item. A Member learns of a full disk only when an upload is refused (R9, R17). Proposal, not a decision: keep it so. Owner: Thanh Truong (product owner).
3. The error code and the status of a refused upload. The log gives no code. Decided in this spec: the code `storage_full` (names the cause, like `channel_archived`), status 507 (insufficient storage), no details. Reason: it is a server condition, not a mistake of the request, so 4xx would be wrong, and 507 maps to the `retry` screen of D-131, which suits a condition that an Admin can clear. Owner: Thanh Truong.
4. Refresh cadence and a stored measurement. The log gives none. Decided in this spec: no job, no cache, no stored value; the page reads on open, every 5 minutes while open and when it becomes visible again. Reason: `statfs` costs one call, a stored value would be stale for the very request that must refuse, and a job (TOKI-064) would add a moving part for nothing; five minutes suits a disk that fills over days. Owner: Thanh Truong.
5. A disk that cannot be read at run time. The log is silent. Decided in this spec: the refusal fails open (uploads allowed, one error line logged, the Admin sees the `unknown` notice), and the start-up refuses a path that cannot be read at all (R6). Reason: a broken measurement must not stop the whole workspace from sharing files, and the start-up check removes the usual cause (a wrong path). Owner: Thanh Truong.
6. What "uploads are refused" covers. D-106 says uploads. Decided in this spec: the start of any upload by a person, whatever their role, an Admin included (D-106 makes no exception): the routes that issue a signed address or create a file row (R10). It does not cover sending a message with files uploaded earlier, downloads, deleting, thumbnails or link previews, which are written by workers after a message exists (R11). Owner: Thanh Truong.
7. The edges of the rule. Decided in this spec: the levels are inclusive ("when the disk is 80% full" is read as reaching it); the percent is `df`'s, with the reserved blocks counted as used; the size of the incoming file is not added, so a 100 MB file may take the disk a little past 95% (on the planned 80 GB disk 100 MB is 0.125%). Reason: the same figure for the operator on the machine and in the page, and the rule stays what D-106 wrote. Owner: Thanh Truong.
8. What the page shows besides the percent. Decided in this spec: only the state and the percent (R8); no free bytes, because the log asks for none and a byte figure needs a size formatter that the page does not have. Owner: Thanh Truong.
9. A failed read of the disk on the Admin page. Decided in this spec: the page keeps the last good reading and shows no error (R14). Reason: a false "unknown" or a red error on a page that already reports its own errors helps no one, and the next read is 5 minutes away. Owner: Thanh Truong.
10. The lines with the neighbours. Decided in this spec: this work owns the module, the route, the code, the refusal function and the reason text; TOKI-058 owns calling the function in each upload-starting route and the test of that call (R10); TOKI-059 owns showing the reason text on the attachment card (R17); TOKI-025 owns the empty region that this work fills (R12); TOKI-084 owns how the production Compose mounts the measured path; TOKI-064 and TOKI-060 are not touched. Each of these is a request until the other ticket's spec says the same. Owner: Thanh Truong.
