# Disk-space warning and upload refusal design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/disk-space-warning.md (Thanh Truong)
Ticket: TOKI-103

## Goal
Toki has no storage quota (D-106), so the disk of the one server is the only limit. This work lets the server read how full that disk is, tells an Admin at the top of the Admin page when it is 80% full or more, and makes the server refuse every new upload, with its reason, when it is 95% full or more. Messages keep working in every case, so the people of the workspace can still talk while an Admin frees space.

## Scope
- In:
  - A pure rule that turns the numbers of a disk into a percentage and one of four states, `ok`, `warning`, `full`, `unknown` (R1, R2).
  - A measurer that reads the disk with `statfs` on a configured path, an injected seam for tests, and a service that never throws (R3, R4).
  - The variable `STORAGE_DISK_PATH`, its row in the inventory and its line in `.env.example`, and the check at start-up (R5, R6).
  - One read route for Admins, `GET /api/v1/storage/disk` (R7), and the shared response shape (R8).
  - The refusal: the error code `storage_full`, the function that raises it and the rule for where it is called (R9, R10, R11).
  - The notice region of the Admin page: the read, the refresh, the four displays and the failure cases (R12 to R15).
  - The texts, in English and a Vietnamese proposal, including the reason text that a refused uploader sees (R16, R17).
- Out (not now):
  - The upload routes, the signed addresses and the `files` tables: TOKI-058. This work gives it the function to call and the rule for where to call it (R10); it adds no upload route.
  - The attachment card in the composer that shows a refused file and its Retry: TOKI-059. It shows the reason text of R17 when the request fails with the code of R9.
  - Thumbnails and link previews, which workers write after a message is sent (TOKI-060, TOKI-061): they are not uploads by a person and are not refused (concern 6).
  - Any periodic job or stored measurement: none is needed (concern 4); TOKI-064 is not used.
  - A quota per person or per channel, a clean-up tool, a screen that lists large files, mail or push notice of a full disk. D-106 says no quota; the log asks for none of the rest.
  - Showing the warning anywhere besides the Admin page (concern 2).
  - The production Compose file and the way the measured path is mounted into the server container: TOKI-084. This work states what the path must be (R5).

## Requirements
- R1. `apps/server/src/modules/disk-space/classify.ts` exports two constants, `DISK_WARN_PERCENT = 80` and `DISK_FULL_PERCENT = 95` (D-106), the type `DiskStats` `{ blocks, free, available, blockSize }` (all non-negative integers, as `statfs` reports them) and the pure function `classifyDisk(stats)`. With `used = blocks - free` and `total = used + available` (the space a user can ever use; the root reserve is in neither), it returns `{ state, usedPercent }`: `usedPercent = floor(100 * used / total)`, computed as `Math.floor(used * 100 / total)` on integers (`used * 100` stays below 2^53 for any disk, so no float rounding decides). `state` is `full` when `used * 100 >= 95 * total`, else `warning` when `used * 100 >= 80 * total`, else `ok`. Both levels are inclusive: with `total` 1,000, `used` 800 is `warning` (80.0%) and 799 is `ok` (79.9%); `used` 950 is `full` (95.0%) and 949 is `warning` (94.9%); `used` 1,000 is `full` with percent 100. The result is `{ state: "unknown", usedPercent: null }` when `total` is 0, when a field is not a non-negative integer, or when the numbers contradict each other: `free > blocks` (it would make `used` negative) or `available > blocks`. The percent is rounded down; `df` rounds up, so on the machine `df` may print one more than the page (concern 7): `df` shows 94% where the page shows 93%. The page never shows 80 or more while the state is `ok`, and never 95 or more while the state is `warning`. Check: a table test with the exact rows above at `total` 1,000 and at a block count near 2^40 (a large disk), where a float form would round the wrong way; a disk with `free > available` (root reserve) counts the reserve as used space, as `df` does (`used` 397,437,288 and `available` 25,789,608, which `df` prints as 94%, give `usedPercent` 93 and `warning`); zero `total`, a negative field, a fractional field, `free > blocks` and `available > blocks` each give `unknown`.

## Design
### How the server measures (a proposal; concern 1)
The server calls `statfs` on the configured path from inside its own process. The server runs in a container on the one VPS (technical design), where MinIO and Postgres also run, and a container cannot read another container's volume. Two cases are covered by the one variable: (a) the standard installation, where every Docker volume lives on the single 80 GB disk of the VPS, and any path in the server container, including `/`, reports the figures of the filesystem that backs it, which is that disk; (b) a MinIO volume on its own disk, where the operator mounts a directory of that disk into the server container (read-only is enough, `statfs` writes nothing) and names it in `STORAGE_DISK_PATH`. `statfs` is one cheap system call that reads no file, so the server takes a new measurement for each use instead of keeping one (concern 4). The figure is `used / (used + available)`, the same quotient `df` uses, rounded down; `df` rounds up, so it may print one more than the page (R1, concern 7).

### Where the reading is used
```
GET /api/v1/storage/disk   Admin only    Admin page notices (R12 to R15)
assertUploadsAllowed()     upload routes  refuse at 95% (R10; TOKI-058 calls it)
```
Both go through `app.diskSpace`, so a test injects the one measurer and sees both the page and the refusal change together.

### API
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/storage/disk` | The state and the percent used of the disk that holds the files; Admin only (R7). The name is fixed here (D-125). |

### Errors
- No session -> 401, as every route.
- A Member asks for the route -> 403 `forbidden`, before the disk is read.
- An upload starts at `full` -> 507 `storage_full`, no body details (R9).
- The disk cannot be read at run time -> the route answers 200 `unknown`; the uploads are allowed; one error line is logged (concern 5).
- The disk cannot be read at start -> the server does not start (R6).

### Layout
```
apps/server/src/modules/disk-space/

├─ measure.ts       DiskMeasurer, statfsMeasurer (R3)
```

### Screen
The notice sits in the `adm-notices` region above the members section (TOKI-025 R27). It is one block of text, full width of the page content, with the existing `--mention-*` and `--danger*` tokens of `tokens` (no new token, no new icon; R13); it has no close button, because it disappears by itself when the disk is below 80% again.

## Data safety
- The route returns a state and a whole percent, never a path, a size or a file name; the refusal error carries no figure. A Member can learn only that uploads are refused (R9).
- The log line of a failed measurement names the error kind and no path (R4). The measured path is a value of `.env`, which is never in git; the inventory row and `.env.example` hold the development value `.`, which is not a secret.

## Areas of concern
1. Which disk is measured. D-106 says "the disk" and the log row D-191 asks which one; its status is Open and its text is only a proposal ("the volume that stores files"). Not decided. Proposal, not a decision: the filesystem that holds the file storage (MinIO's data), named by `STORAGE_DISK_PATH` (R5); in the standard one-VPS installation this is the same disk as the database, so one figure covers both. Reason: the files are what grow without a quota, and the refusal protects the database that shares the disk. The build follows the proposal until the owner answers D-191; if the answer is another disk, only the path in `STORAGE_DISK_PATH` changes. This is the first half of D-191; concern 2 is the other half. Owner: Thanh Truong (product owner).
2. Is the warning shown anywhere besides the Admin page? The plan line and journey F39 name the Admin page; D-191 proposes "on the Admin page only" but is Open (the second half of D-191, with concern 1). Not decided. This work builds the Admin page only, as the plan line says, and adds no banner, mail, push or Activity item. A Member learns of a full disk only when an upload is refused (R9, R17). Proposal, not a decision: keep it so. Owner: Thanh Truong (product owner).
3. The error code and the status of a refused upload. The log gives no code. Decided in this spec: the code `storage_full` (names the cause, like `channel_archived`), status 507 (insufficient storage), no details. Reason: it is a server condition, not a mistake of the request, so 4xx would be wrong, and 507 maps to the `retry` screen of D-131, which suits a condition that an Admin can clear. Owner: Thanh Truong.
4. Refresh cadence and a stored measurement. The log gives none. Decided in this spec: no job, no cache, no stored value; the page reads on open, every 5 minutes while open and when it becomes visible again. Reason: `statfs` costs one call, a stored value would be stale for the very request that must refuse, and a job (TOKI-064) would add a moving part for nothing; five minutes suits a disk that fills over days. Owner: Thanh Truong.
5. A disk that cannot be read at run time. The log is silent. Decided in this spec: the refusal fails open on a failing measurement (uploads allowed, one error line logged, the Admin sees the `unknown` notice naming the setting), and the start-up refuses a path that cannot be read at all (R6). A missing service is not a failing measurement: `buildApp` throws when it has neither `diskSpace` nor `config.storageDisk` (R10), so the open case cannot come from a wiring mistake. Reason: a broken measurement must not stop the whole workspace from sharing files, and the start-up check removes the usual cause (a wrong path). Owner: Thanh Truong.
6. What "uploads are refused" covers. D-106 says uploads. Decided in this spec: the start of any upload by a person, whatever their role, an Admin included (D-106 makes no exception): the routes that issue a signed address or create a file row (R10). It does not cover sending a message with files uploaded earlier, downloads, deleting, thumbnails or link previews, which are written by workers after a message exists (R11). Owner: Thanh Truong.
7. The edges of the rule. Decided in this spec: the levels are inclusive ("when the disk is 80% full" is read as reaching it, with integer arithmetic, R1); the percent is `used / (used + available)` rounded down, with the reserved blocks counted as used, so `df` (which rounds up) may print one more than the page, and the state never changes at a figure the page does not show; unreadable numbers (`free > blocks`, `available > blocks`) are `unknown`; the size of the incoming file is not added, so a 100 MB file may take the disk a little past 95% (on the planned 80 GB disk 100 MB is 0.125%). Reason: a notice never shows 80 while the state is `ok`, and the rule stays what D-106 wrote. Owner: Thanh Truong.
8. What the page shows besides the percent. Decided in this spec: only the state and the percent (R8); no free bytes, because the log asks for none and a byte figure needs a size formatter that the page does not have. Owner: Thanh Truong.
9. A failed read of the disk on the Admin page. Decided in this spec: the page keeps the last good reading and shows no error (R14). Reason: a false "unknown" or a red error on a page that already reports its own errors helps no one, and the next read is 5 minutes away. Owner: Thanh Truong.
10. The lines with the neighbours. Decided in this spec: this work owns the module, the route, the code, the refusal function and the reason text; TOKI-058 owns calling the function in each upload-starting route and the test of that call (R10), and the test of the message send at `full` (R11, a change request to its R14); TOKI-059 owns showing the reason text on the attachment card (R17); TOKI-025 owns the empty region that this work fills (R12); TOKI-084 owns how the production Compose mounts the measured path; TOKI-064 and TOKI-060 are not touched. Each of these is a request until the other ticket's spec says the same (see Plan changes). Owner: Thanh Truong.
