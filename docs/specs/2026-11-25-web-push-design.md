# Web Push design

Date: 2026-11-25 · Status: draft for review (concerns 1 to 3 and 14 are open for the product owner)
Intent: docs/intents/web-push.md (Thanh Truong)
Ticket: TOKI-074
Needs: TOKI-068, TOKI-073, TOKI-099, TOKI-022, TOKI-019, TOKI-096 (through TOKI-073 it also reaches TOKI-064, TOKI-065 and TOKI-102; see Plan changes)

## Goal
A person who has closed Toki, or left its tab hidden, must still learn that something needs them. TOKI-073 decides, for each person and cause, that a push is due, and hands over identifiers. This ticket makes the push real: the server's key pair, the registration of a person's devices, the job that sends the encrypted message to the browser's push service, the service worker that shows it, the click that opens Toki at the message, the card that asks the person on their first visit, the explanation of the iPhone rule, and the removal of a device's registration when its session ends.
Without it a person with Toki closed gets nothing, which is the situation F36 and FR-18 exist to prevent.

  - In the web app: `platform.push`, the iPhone rule, the click address and its handler, the registration kept in step with the browser, the first-visit card, the device block of Preferences, the removal at sign-out, the texts (R21 to R28).

## Requirements
Keys and configuration
- R1. The configuration gains two areas, read through the one reader of `apps/server/src/config.ts` (TOKI-004) and defined in `modules/notifications/web-push-config.ts`. `webPushPublic` holds `VAPID_PUBLIC_KEY` and is the only one the server process (`main.ts`) requires, because the server only hands the public key out (R5). `webPush` holds `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` and is required by the worker (`worker.ts` adds it to its list of areas, TOKI-064 R17), the only process that signs. The module's `index.ts` exports `webPushPublicConfigSchema`, `webPushConfigSchema` and `webPushVariableNames` (all three names), like `auth` and `mail`. The public key is base64url of 65 bytes starting with `0x04`; the private key is base64url of 32 bytes; the subject is `mailto:` and an address, or an `https://` address. In `webPush` the private key must be the one that gives the public key (checked with `node:crypto`'s P-256 curve). `buildApp` takes the area as optional, as for `auth`, so a test builds the app without it. A failure names the variable and never its value. Tests and CI get a valid pair from the helper `apps/server/test/support/vapid-pair.ts` (`makeVapidPair()`, `node:crypto`, a new pair at each call): no pair is written in a workflow file or a secret of the repository, so CI needs no new secret (the rule of environment-config R13 for throwaway values), and the process tests of TOKI-004 R15 that start the server and the worker with a fake environment put a pair from the helper in it. Check: tests of each schema rule, a valid pair accepted, a pair whose halves do not match refused in `webPush`, the server entry started with only the public key, a failure message holding no value; `loadProcessConfig(["server","database","webPushPublic"])` and `loadProcessConfig(["worker","database","webPush"])` with a variable missing throw a `ConfigError` with its name only.
- R2. `docs/environment-config.md` gets a section "Web Push" with three rows: `VAPID_PUBLIC_KEY` (not secret; used by the server and the worker), `VAPID_PRIVATE_KEY` (secret; the worker) and `VAPID_SUBJECT` (not secret; the worker), each required `yes`, default `none`, supplied by "the operator of that installation", and `.env.example` gets the three names (public and private empty, subject `mailto:admin@example.test`), so the test of TOKI-004 R13 passes. The subject is `yes` although `.env.example` holds a sample, because the worker cannot sign without one. The three names are added to `REQUIRED_NAMES` in `scripts/env-pull.sh`: the test `scripts/local-run.test.sh` (local-run R6) fails when that list and the `yes` rows differ, and it builds its fake Doppler output from the inventory, so it needs no edit of its own and is the check that the list was updated. The development pair is kept in the Doppler project `toki`, config `dev`, because `env:pull` replaces `.env` from that config: the builder makes a pair with `pnpm --silent vapid:keys` and adds the three values to Doppler `dev` before the pull request is merged, so that `pnpm env:pull` and `pnpm start:local` keep working for everyone; the pair is never written in the repository, the pull request or a chat. The script `vapid:keys` (root and `apps/server`, added to "Commands" of `CLAUDE.md`) prints exactly two lines on standard output, `VAPID_PUBLIC_KEY=<value>` and `VAPID_PRIVATE_KEY=<value>`, made with `node:crypto`, and nothing else; the form is `pnpm --silent vapid:keys`. An installation that already runs must add the three values before it starts this version: the server and the worker refuse to start and name the missing variable (R1); there is no data to migrate besides the index of R9. The environment document says that changing the pair stops every registered device until it registers again (R22). Check: the names test; `scripts/local-run.test.sh` passes with the three names in the script and the inventory and fails when one is left out of the script; the script's output parsed by R1's schema, two runs giving different pairs.
- R3. Sending goes through the library `web-push` at one exact version (the newest published at least two weeks before the build; the pull request names it and the check that it handles the `aes128gcm` encoding and VAPID), reached only from `modules/notifications/web-push-sender.ts`. That file exports `createWebPushSender({ config, isAllowedEndpoint })` (the second argument defaults to R7's function; only the sender's own test replaces it) and the type `WebPushSender`, `send(subscription, payload: string, options: { ttlSeconds: number; urgency: "normal"; timeoutMs: number }) => Promise<SendResult>`, with `SendResult` one of `{ kind: "sent" }`, `{ kind: "gone" }` (status 404 or 410), `{ kind: "retry" }` (status 429 or 5xx, or a network error or a timeout: the library or Node error whose code is `ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `EPIPE` or the timeout of `timeoutMs`) and `{ kind: "rejected", reason, status? }` with `reason` one of `status` (any other status, a 3xx and a 401 or 403 included), `payload_too_large`, `endpoint_not_allowed` and `invalid_subscription`. Any error of the library that is not an HTTP status and not one of the listed network codes is `rejected` with `invalid_subscription`, never `retry`, so a bad key or an oversize payload is not tried six times. Before any request the sender (a) refuses, with `endpoint_not_allowed`, an endpoint that fails the function of R7 (the rows of `devices` are the boundary the server posts to, so a row written before the list changed, by hand or by an earlier bug is checked again), and (b) refuses, with `payload_too_large`, a payload of more than `PUSH_PAYLOAD_MAX_BYTES` (4,000 bytes of UTF-8, under the library's 4,078 bytes of plaintext and the push services' limit of about 4 KB). It follows no redirect (the library does not, and a 3xx is `rejected` with `status`), and it sets no `proxy` and no `agent` option. No test reaches the network: the handler takes the sender from `deps`, and tests pass a fake. Check: a test of the mapping from status and error code to result with the library's own error type; an error of another kind gives `rejected`; a payload of 4,001 bytes and an endpoint off the list make no request (a spy on the library); a test with a loopback TLS server on `127.0.0.1` (the one place a socket is opened, with `isAllowedEndpoint` replaced) that answers 302 to another loopback address: one request arrives, none at the second address, and the result is `rejected`; a search of the other tests for `fetch` and `https` finds no real call.
- R4. `packages/shared/src/notifications/web-push.ts` (exported from the package index) holds: `WebPushSubscriptionSchema`, strict `{ endpoint, keys: { p256dh, auth } }` with `endpoint` a string of at most 2,048 characters, `p256dh` base64url of 65 bytes and `auth` base64url of 16 bytes; `RegisterDeviceBodySchema`, strict `{ subscription, sendTest }` with `sendTest` an optional boolean; `PushPayloadSchema`, strict `{ v: 1, kind, title, body, tag, data }` with `kind` one of `message`, `mention`, `reminder`, `test` and `data` either `null` or strict `{ conversationId, messageId, parentId }` (UUIDs, `parentId` UUID or `null`); `PushClickSchema`, strict `{ type: "toki.openMessage", conversationId, messageId, parentId }`; and the constants `PUSH_PREVIEW_MAX` equal to `NOTICE_PREVIEW_MAX` of TOKI-073 R1 (60 code points), `PUSH_TITLE_MAX` (80 code points) and `PUSH_NAME_MAX` (40 code points) of R15. The schemas check shape and length only; that `p256dh` is a point of the curve is checked on the server (R6). Check: schema tests for each valid object and for an added key, a missing key and a wrong length of each key.

Registration
- R5. `GET /api/v1/notifications/web-push/key` with a valid session returns status 200 and `{ publicKey }`, the configured public key. It returns nothing else and needs no table. Without a session it returns 401 `unauthenticated` of TOKI-022. Check: the two cases.
- R6. `PUT /api/v1/notifications/devices/current` with a valid session and a body of R4 stores the registration of the session that carries the request: one row of `devices` with `id` (from the id generator), `created_at` (from the clock of TOKI-008, since the column has no database default, TOKI-019 R6), `workspace_id`, `user_id` and `session_id` of the request, `push_channel` `web_push` and `push_address` `{ endpoint, p256dh, auth }`. Before anything is stored the endpoint passes R7 and `p256dh` must be a point of P-256 (`crypto.createECDH("prime256v1").computeSecret(key)` throws on an invalid point), otherwise the answer is 400 `validation_failed`. A session has at most one row (`devices_session_id_key`, TOKI-022 tables R20): when the session has one, the call replaces its address and returns 200; when it has none, the call inserts one and returns 201. The body of the answer is `{ registered: true }`. When `sendTest` is true the call also enqueues the job of R17 for that device, in the same transaction, whether the row is new or not, after cancelling a test job for that device that has not started (`jobs.cancelByKey`), so at most one test is waiting for a device; when it is absent or false it enqueues nothing. A body that fails R4 returns 400 `validation_failed`. A session that ended between the check of the request and the insert leaves a row that is never sent to (R14 skips rows of sessions that are not live and deletes them). Check: the 201, the 200, the replaced address, a 65-byte value that is not a point refused with nothing stored, the test job present only with `sendTest`, two `sendTest` calls leaving one waiting job, and a rollback (a failure after the insert) leaving neither row nor job.
- R7. The endpoint is checked before anything is stored, and again before each send (R3), because the server will post to it. The check is the function `isPushEndpoint(endpoint)` of `endpoints.ts`. It parses the string with `new URL`; refuses a string that does not parse; refuses it when the part between `//` and the next `/` holds `%` or `@`; and accepts it only when the protocol is `https:`, there is no user name or password, the port is empty or 443, and `hostname` (which the parser lower-cases and converts to punycode) equals one of `fcm.googleapis.com`, `push.services.mozilla.com`, `push.apple.com` and `notify.windows.com` or ends with `.` plus one of them, the push services of the browsers D-108 supports; a host with a trailing dot, an IPv4 or IPv6 literal, or a name that merely contains one of the four fails. The row stores `url.href`, so the host that was checked is the host that is posted to. Any other endpoint returns 400 `validation_failed` and stores nothing. The list is the constant `PUSH_SERVICE_HOSTS` in `endpoints.ts`, next to `web-push-sender.ts`, and adding a host is a change of this spec. Check: a table of accepted endpoints (one per service, an upper-case host stored in lower case) and refused ones (`http://`, a loopback address, `https://[::1]/`, `https://127.0.0.1/`, an address with a user name, `https://fcm.googleapis.com@evil.example/`, a port, a trailing dot, `https://fcm%2Egoogleapis.com/`, a look-alike host such as `evilfcm.googleapis.com.example.test`, a host that merely contains the name); the same function refusing a stored row in the sender (R3).
- R8. `DELETE /api/v1/notifications/devices/current` with a valid session removes the row of the session that carries the request and returns 204. With no row it returns 204 and changes nothing. It never touches a row of another session or person. Check: both cases, and a row of another session of the same person left in place.
- R9. One migration, `<number>_web_push_endpoint_index` (forward-only, TOKI-005 R11), creates the unique index `devices_push_endpoint_key` on `(push_address ->> 'endpoint')` of `devices`, and the same index is declared in `modules/notifications/schema.ts`, so that `db:generate` reports no change. In the transaction of R6, before the insert or update, the rows of any other session with the same endpoint are deleted, so a browser's endpoint belongs to the session that registered it last and the pushes of one person never reach the browser that another person signed in on. The statements always run in that order (delete the others' rows, then write one's own). Two registrations of one endpoint that overlap leave exactly one row: a unique violation (`23505`) or a deadlock (`40P01`) makes the call run its whole transaction once more, and a second failure answers the ordinary 500 with nothing stored, which the app repairs at its next page load (R22). Check: a test registers an endpoint for person A, then for person B: A has no row; two overlapping calls with two connections leave one row, and two calls for two sessions that delete each other's row end with one row or one 500 and never a hang; the migration folder holds one new migration and `db:generate` reports no change.
- R10. A registration lives as long as its session. (a) `modules/notifications` registers a listener with `onSessionsEnded` of TOKI-022 R50 (`app.ts` passes the function in; the module imports no other module). The listener is synchronous, as the hook is: for the ids it hears it starts one statement that deletes the rows with those `session_id` values, for any reason (`signed_out`, `revoked`, `replaced`, `deactivated`), attaches a catch to it, and logs the failure with the number of ids and nothing else (R11); a failed delete leaves the row to the job of (b) and to R14, which never sends to a session that is not live. (b) The scheduled job `notifications.prune-devices` (`defineJob` with `schedule: { cron: "17 3 * * *" }`, TOKI-064 R16) deletes the rows whose session is not live, asking the port `SessionLiveness.liveIds(client, ids)` that `app.ts` and `buildJobDeps` build from `getLiveSessionIds(client, ids)`. This ticket adds `getLiveSessionIds` to the `auth` module (`sessions.ts`, exported from its `index.ts`; it is the one read of `sessions` for this purpose, and the pull request lists the edit as it did for `getLastUsedAtByUser` of TOKI-024). A session is live when it has not ended and `now - lastUsedAt <= IDLE_MS` (30 days, the rule `sessions.ts` applies, TOKI-026 R2), so a session idle for exactly 30 days is live. The job reads the rows in pages of 500 and holds no session secret. Check: with real sessions, each of the four reasons removes the row and no other; a session idle for 30 days and one second is pruned and one idle for exactly 30 days is kept, with `TestClock`; a listener whose delete throws and one whose delete rejects do not stop the sign-out and raise no unhandled rejection (TOKI-022 R50).
- R11. The routes of R5, R6 and R8 need a valid session (TOKI-022 R24), the `PUT` and `DELETE` obey the `Origin` rule (TOKI-022 R46), and no route returns an endpoint, a key or a row of `devices`. No log line of this work holds an endpoint, a key, a payload or the text of a message: a line carries the user id, the kind and counts only. Check: a captured log of a registration, a send, a failure and a removal searched for the endpoint, both keys and the message text; the answers of the three routes compared with their schemas.

Sending
- R12. The job type `notifications.send-push` (`defineJob`, TOKI-064 R6; added to `job-types.ts`) has a strict payload of identifiers and booleans only: `userId`, `workspaceId`, `kind` (`message`, `mention`, `reminder`, `test`), `conversationId`, `messageId`, `parentId`, `actorId`, `itemId`, `deviceId` and `viaChannel`; a value that does not apply is an omitted key, not `null`. It uses the defaults of TOKI-064 R8 (five retries, backoff) with `concurrency` 4. Its key is `push:<userId>:<messageId>` (`push:<userId>:<itemId>` for a reminder, `push:<userId>:test:<deviceId>` for a test), the key TOKI-073 R8 fixed. Check: the walking test of TOKI-064 R7 passes for the type; a payload with a free-text property is refused.
- R13. `createPushPort(deps)` of `modules/notifications/push-port.ts` is the real `PushPort` of TOKI-073 R8; it replaces the stand-in and its name, and `app.ts` and `buildJobDeps` build it. `enqueue(tx, notice)` always enqueues one `notifications.send-push` job through `jobs.enqueue(..., { key, tx })`, with no read of `devices`, so a rollback leaves no job and the notification handler keeps the fixed number of statements of TOKI-073 R5 (one job insert for each person who gets a push, and nothing more). A person with no device gets a job that completes at once (R14). `cancel(tx, userId, messageId)` calls `jobs.cancelByKey(sendPush, "push:<userId>:<messageId>", { tx })`. A person is one job, not one per device. Check: with real queue and database, one job for a person with no device and for a person with three, and the job of the first sends nothing; a rolled-back transaction leaves none; `cancel` stops a job not started and one for another person is untouched; the statement count of the handler with the real port is the same for a channel of 5 and one of 200 (the wrapper of TOKI-031 R14, as TOKI-073 R5 counts); the port satisfies the type test of TOKI-073 R8 (identifiers and the kind only).
- R14. The handler (`createSendPushHandler(deps)`, `defineHandler`) works in this order. (1) It reads the person's `web_push` rows of `devices` (its own module's table); with none it completes, which is the case of a person who never allowed notifications (TS-070). (2) It asks `SessionLiveness.liveIds` once for the sessions of those rows, deletes the rows whose session is not live and ignores them, so a registration that overlapped a sign-out (R6) is never sent to; with no row left it completes. (3) On an attempt after the first (the retry count that the job gives the handler, TOKI-064 R8; if the handler context carries none, this ticket asks TOKI-064 for it, see Plan changes) it asks the `HoldPort` of TOKI-073 R10, `listHeld(client, [userId], clock.now())`, and completes with no send when the person is held, so a retry never crosses the start of Pause or Focus time (D-072, concern 13). (4) For `message`, `mention` and `reminder` it reads the person's `desktop` switch with `loadNotificationPreferencesFor(client, workspaceId, [userId])` of TOKI-102 R8, which the module reads itself, and completes with no send when it is off. (5) For the same three kinds it makes the send-time check through the port `PushSourcePort.read(client, data)`, which returns `{ live, language, senderName, conversation, text, parentId }` and holds only what crosses a module boundary; `app.ts` and `buildJobDeps` build it from the reads in the table below. `live` is false, and nothing is sent, when: for `message` and `mention`, the message is deleted (TOKI-047), whether it is a reply or a top-level message; for `mention`, the Activity item `itemId` no longer exists; for `reminder`, the Later item `itemId` no longer exists, is completed or removed, or its source message is deleted (concern 3: the last part is a proposal); or the person is no longer a member of the conversation (left, removed or the account deactivated). Pause and Focus are not read on the first attempt: TOKI-073 decided them when it handed the push over (R10 there). A kind `test` skips steps (3) to (5) (R17).

Where a read does not exist on main when this ticket is built, the ticket named in the table adds it; this ticket's pull request does not write a second copy. Check: a table over each case with real tables or fakes of the reads: each false case sends nothing and completes the job (no retry); the live case sends; a deleted reply and a deleted top-level message both send nothing; a row of a session that ended after the registration is deleted and not sent to; a retry for a person who is now held sends nothing; a person with the `desktop` switch off gets none; a reminder with a completed item, a removed item and a deleted message sends nothing.
- R15. The content, built in `modules/notifications/push-payload.ts` as a pure function of `{ kind, language, senderName, conversation, text, ids }` to a `PushPayload` of R4. The words come from `translate(language, key, params)` of `@toki/i18n`, with the person's saved language (`users.language`, D-018): the server writes the whole text and the service worker only shows it. D-044 gives the three parts; the layout is a proposal (D-139). For a channel the `title` is the conversation name with its `#` and the `body` is `"<sender>: <start>"`; for a direct message the `title` is the sender and the `body` is the start; for a group direct message the `title` is the other people's names joined with `push.group.joiner` and the `body` is `"<sender>: <start>"`; for a reminder the `title` is `push.reminder.title` with the conversation name (F28's toast reads "Reminder: ..."; proposal: "Reminder: #general") and the `body` is `"<sender>: <start>"`, with the same start. A name is cut to `PUSH_NAME_MAX` (40) code points and the `title` to `PUSH_TITLE_MAX` (80) code points, each with one `…` when cut (by code points, never inside one, and a group title is cut as a whole, not by dropping names). The start is the first `PUSH_PREVIEW_MAX` code points of the message text, line breaks and runs of white space made one space, with no formatting removed and no ellipsis added; it is empty when the message has no text (only files), and then the `body` holds the sender alone. `tag` is `msg:<messageId>` for `message` and `mention`, `item:<itemId>` for `reminder` and `test:<deviceId>` for `test`, so a send that is retried replaces the notification it already showed instead of adding a second. `data` holds the three ids, or `null` for `test`. The size is bounded by these caps and not by luck: the longest title is 80 code points, the longest body 40 + 2 + 60 code points, and with the JSON escapes of every character (six bytes at the worst) and four ids the payload stays far under `PUSH_PAYLOAD_MAX_BYTES` (4,000 bytes, R3). A payload that is still over it is not sent: the handler logs the kind and completes the job. Check: a table of the four kinds in both languages, a start of exactly 60, 61 and 0 code points, an emoji at the cut, a name of 80 four-byte characters (cut to 40 plus `…`), a group direct message of 8 people with 80-code-point names (title of 80 code points, payload under 4,000 bytes), a text with line breaks; the payload checked with `PushPayloadSchema`; the payload built from the longest allowed inputs measured in UTF-8 bytes against `PUSH_PAYLOAD_MAX_BYTES`.
- R16. One send. For each row the handler calls the sender (R3) with `ttlSeconds` 3,600, `urgency` `normal` and `timeoutMs` 10,000, all rows of the person together. The constants are `PUSH_TTL_SECONDS` and `PUSH_TIMEOUT_MS`. A `gone` result deletes that row. A `rejected` result (a status other than the ones above, a payload too large, an endpoint off the list, a key the library cannot use) is logged by reason, status and device id and is neither retried nor deleted. A `retry` result makes the handler throw after every row has been tried, so the job is tried again by TOKI-064 R8; a row that succeeded is sent again by that retry and the `tag` of R15 makes the browser replace the notification instead of showing two. The job completes when no row answered `retry`. After a rotation of the VAPID pair the push services answer 401 or 403 for every stored row: these are `rejected` and the rows stay (concern 11). Check: a table with a fake sender over `sent`, `gone`, `retry` and `rejected` (each reason) for one and for several devices, with the row deletions and the throw asserted; the retry through the real queue with `TestClock`; the arguments of the fake checked for the three constants.
- R17. The test notification. After `PUT` with `sendTest` true (R6) the job has `kind` `test` and the `deviceId`: it reads that one row, builds a payload with the title `push.test.title` and the body `push.test.body` in the person's language (proposal: "Toki" and "Notifications are on", F36), tag `test:<deviceId>`, `data` null, and sends it to that device only. It is not subject to the `desktop` switch, to Pause or Focus, or to the send-time check (steps (3) to (5) of R14), because it proves the registration and is the answer to a press of Turn on. Check: a registration with `sendTest` sends one payload to that device and none to the person's other devices; with the switch off the test is still sent; a registration without `sendTest` sends nothing.

## Design
The push has five parts in a line: the engine decides (TOKI-073), the port hands over (R13), the worker sends (R14 to R17), the push service carries, the service worker shows and reacts (R19, R20). The server writes the whole words; the worker shows what it receives. Reason: the saved language is known to the server (D-018), the service worker then needs no catalog, and a notification can never show a half-translated text.

```
decision (TOKI-073) -- PushPort.enqueue(tx) --> job notifications.send-push  (one per person)
                                                   |  worker: rows of devices -> send-time check -> payload (R15)
                                                   v
                              push service (FCM, Mozilla, Apple, Windows) -- encrypted payload --> browser
                                                                                                    |
                                                  push-sw.js: showNotification (always)  <----------+
                                                  click: focus window + postMessage  |  or openWindow /open-message
                                                                  |                                 |
                                         platform.push.onOpenMessage                  route /open-message (guard -> /login?next=)
                                                                  \______ useOpenMessage().open(...) (TOKI-068) ______/
```

### Data model
No new table. `devices` (TOKI-019 R20) is used as it is: one row per session, `push_channel` `web_push`, `push_address` `{ endpoint, p256dh, auth }`. One migration adds `devices_push_endpoint_key` (R9). The three VAPID values are configuration, not data.

### API
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/notifications/web-push/key` | the public key the browser subscribes with (R5) |
| PUT | `/api/v1/notifications/devices/current` | register or replace this session's device; optional test (R6) |
| DELETE | `/api/v1/notifications/devices/current` | remove this session's device (R8) |

### Errors
- 400 `validation_failed`: a body that fails R4, an endpoint that fails R7.
- 401 `unauthenticated` or `session_ended`: no valid session (TOKI-022).
- 403: a foreign `Origin` on `PUT` or `DELETE` (TOKI-022 R46).
- A failed send never changes the answer to the person's request; it is a job outcome (R16).

### Why these choices
- One job per person, not per device, and no read of `devices` when the job is handed over: TOKI-073 R8 fixed the key `push:<userId>:<messageId>` so a cancel needs no search, and TOKI-073 R5 fixes the number of statements of its handler, which one read for each person would break. The cost is a job that completes at once for a person with no device (R13, R14), and that a retry sends again to devices that already got it; the `tag` makes the browser replace, not add (R15, R16).
- An allow-list of push hosts (R7), checked at registration and again at each send, with no redirect followed and no proxy (R3): the endpoint is chosen by the client and the server posts to it, so an open list would let a signed-in person make the server call any address. The four hosts are those of the browsers D-108 supports; a new service is one constant and a change of this spec.
- The click address (R23) is a route that uses the hook and leaves, not a search key on the conversation: TOKI-068 concern 6 has not decided whether a message has an address. This route is an entry point for a click and nothing else; it is not offered as a link to share, and TOKI-068 concern 6 may replace it with its own address.
- Registration per session, not per browser: the table already says so (`session_id` is unique), so ending the session removes the registration with one rule (R10), and one endpoint belongs to one session (R9).
- No `pushsubscriptionchange` handler: R22 repairs a changed subscription at the next run of its routine (the next page load or sign-in). Until then the old endpoint answers 410 and its row is deleted (R16), so a person whose browser changed the subscription gets no push until they next open Toki (concern 11).
- The server process holds the public key only (R1): the private key is read by the worker, the one process that signs, so a secret is not placed where it is never used.

## Data safety
- A subscription (endpoint and keys) is stored in clear in `devices.push_address`, next to the user id, as the table's own design allows (TOKI-019 Data safety). Sending also needs the private VAPID key, which is a secret: never committed, never logged, never in a payload or an answer, and read only by the worker (R1, R2, R11). Decided in this spec: the object is not encrypted at rest in phase 1; reason: the key to encrypt it would be one more secret next to the database it protects, and the VAPID key already stops a stranger from sending.
- The payload holds the sender, the conversation and the start of the message. It is encrypted for the one browser (`aes128gcm`) and the push service cannot read it. Job payloads and logs hold identifiers only (R11, R12).
- Whether a person has a device is private: no route and no event gives it to another person (R11).
- The service worker shows whatever the server sent it; it reads no message, makes no request and stores nothing (R19).

Decided in this spec: the endpoint of a registration must be an `https` address on one of four hosts, checked at registration and again at each send, and the sender follows no redirect and uses no proxy (R3, R7). Reason: the server posts to the address a client gives; the four hosts are those of Chrome and Edge's services, Firefox, Safari and Windows. A push service on another host is one constant to add and a change of this spec. Owner: Thanh Truong.
8. When the test notification is sent. Decided in this spec: only when the registration asks for it, which the app does on a press of Turn on (R6, R24, R26), not on the silent registration at each sign-in (R22). Reason: F36 shows the test as the answer to approval; a test at every sign-in on every device would be noise. Owner: Thanh Truong.
9. The iPhone rule. Decided by D-108 and F36: on an iPhone, push is offered only from the Home Screen, and Preferences says so. The check also needs the browser's push features (R21), so a device that gains push without the Home Screen is not blocked by a list. Reason: D-108 and F36. The iPad is concern 14. Owner: Thanh Truong.
10. Bounds that are not product rules. Decided in this spec: the start of the message is 60 code points, the same as the toast (R4); the push service keeps an undelivered message for 3,600 seconds and a send is given 10 seconds (R16); the stale-registration job runs daily at 03:17 (R10); a group direct message is titled with the other people's names. Reason: a notification and a send need a size and a time; a push older than an hour reads as news while the badge and the Activity item already say what happened. They are constants and can change. Owner: Thanh Truong.
11. A changed subscription. Decided in this spec: no `pushsubscriptionchange` handler in the first version; the next run of the routine of R22 repairs it, and a rotated VAPID pair makes every device register again at its next page load (R2, R22). After a rotation the push services answer 401 or 403 for every stored row; R16 neither deletes nor retries these, so until its owner opens Toki each message logs one rejection for each stale device (a line of the kind and a count, R11), which is at most the number of the person's devices for each push. Reason: the event is rare, the service worker would need to make an authenticated request on its own, and the repair costs a person with a changed subscription only the pushes until they next open Toki. Owner: Thanh Truong.
12. Verifying on a real iPhone. Decided in this spec: this ticket builds the iPhone rule, its explanation and the registration, and tests them with fakes (R21, R26). Whether a push really reaches an iPhone Home Screen app depends on the manifest of TOKI-077, so the check on a real device, which the technical design asks for ("try on a real iPhone before the notification work starts", techDeps of FR-18), is recorded in the QA record of TOKI-077 and repeated for this ticket once the manifest exists. Reason: without a manifest with `display: standalone` there is no Home Screen app to test. Owner: Thanh Truong.
13. The Pause and Focus state at send time. Decided in this spec: the handler does not read Pause or Focus again on the first attempt, because TOKI-073 decided them when it enqueued the job, in the same transaction as the message, and a first attempt runs within seconds; on a retry (which can run about ten minutes later, TOKI-064 R8) it asks the `HoldPort` of TOKI-073 once and sends nothing when the person is held (R14). Reason: D-072 says everything is held until Pause or Focus ends, and a retry is the one send that can cross its start. Owner: Thanh Truong.
14. Does an iPad follow the iPhone rule? Not decided. D-108 names the iPhone only; iPadOS has the same limit and reports itself as a Mac, so it can be recognised by its touch points. The log has no iPad decision, so this is a device classification and a product question. Proposal, not a decision: an iPad follows the iPhone rule, by the same check (R21), so an iPad outside the Home Screen shows the explanation and no button. The check is one condition, so a different answer changes one line of R21. Owner: Thanh Truong (product owner).
15. Test notifications and repeated calls. Decided in this spec: a call with `sendTest` cancels a test job for that device that has not started and enqueues one, so at most one test waits for a device (R6); the Turn on button is disabled while its call is in flight (R24), so repeated presses are not repeated sends. No other limit is added. Reason: the call needs a valid session of the person and posts only to the person's own device on an allowed host; a one-per-minute limit would need state this ticket does not otherwise keep. Owner: Thanh Truong.
