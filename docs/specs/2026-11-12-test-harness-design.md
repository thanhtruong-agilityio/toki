# Test harness design

Date: 2026-11-12 · Status: draft for review
Intent: docs/intents/test-harness.md (Thanh Truong)
Ticket: TOKI-008

## Goal
The builder needs one working test setup, so later tickets can be written test-first and "CI is green" has real tests behind it. The setup runs server tests against a real Postgres, runs one browser end-to-end test against the web app, and lets a test control the time the code sees. Later tickets add tests to this setup and do not build their own.

## Scope
- In: Vitest configuration for unit and server integration tests, extending the minimal Vitest setup from TOKI-004; a test database that is separate from development data, created (dropped and created again at the start of every run) by this work as a second database on the development Postgres server; the safety guard for it; a controllable clock; Playwright configuration with one sample test; root scripts to run them; one sample test of each kind as proof; running the existing tests from TOKI-004 and TOKI-005 under the harness, with the files that need Postgres in a separate Vitest project (R20); the end-to-end job (`pnpm test:e2e`) and the browser install step in the CI workflow that TOKI-007 creates.
- Plan change: TOKI-008 now also needs TOKI-007 (decision of 2026-11-12); the Blueprint plan must be updated.
- Plan change (review of 2026-11-16): the `test` script of `apps/server` now also runs the database tests of TOKI-005 and TOKI-008, so TOKI-004 R11 ("the server tests need no database") holds for the new script `test:unit` of `apps/server`, which runs only the database-free project (R20). This agrees with the plan change already recorded in the TOKI-005 spec.
- Out (not now):
  - The Postgres, MinIO and Mailpit services and the `dev:*` start and reset scripts: TOKI-003.
  - The Postgres connection, the migration workflow and the `workspaces` table: TOKI-005. This work only calls them: TOKI-005 already takes the connection value as a parameter (`createDb(connection)`, `runMigrations(connection, folder)`), so this work changes no TOKI-005 code (R18).
  - The web skeleton, router and dev proxy: TOKI-006. The server skeleton and `/healthz`: TOKI-004.
  - The CI workflow file and its lint, type check, tests, build and bundle size jobs: TOKI-007. That file already holds the Postgres service for the tests check (TOKI-007). This work only adds the end-to-end job to it (see concern 2).
  - Lint and package boundary rules: TOKI-002.
  - The environment variable inventory and `.env.example`: TOKI-096. The test database connection variable is named there; this work uses that name and invents none (see concern 4).
  - Prototype seed data and `dev:seed`: TOKI-081. The 12 main end-to-end flows belong to the feature tickets that build them.
  - Shared date and time rules (formatting, time zones): TOKI-094. The clock here only supplies "now".
  - Tests for MinIO or Mailpit, component tests for `ui-web`, coverage thresholds: the intent does not ask for them.

## Requirements
- R1. `pnpm test` at the repository root runs Vitest for every workspace package that has tests and exits 0 when all pass.
- R2. A sample server integration test inserts a row into `workspaces` and reads it back through the Drizzle connection to a real Postgres; it passes with the development services up (`pnpm dev:up`).
- R3. At the start of every run that includes database tests, the harness drops the test database if it exists, creates it again and applies the TOKI-005 migrations to it with `runMigrations`, before the first server test. Check: on a server where the test database does not exist, and again after a leftover table was added to it by hand, the R2 test passes with no manual step and the leftover table is gone.
- R4. Server tests use a database other than the development database: after `pnpm test`, the row counts in the development database are unchanged.
- R5. The database test run refuses to start, before any statement is sent to the server, unless the test connection passes all of these checks: it is set; its host is a loopback address; its database name ends in `_test` and differs from the development database name; the environment name variable of TOKI-003 R10 is not `production`. After connecting and before any table is emptied, `select current_database()` must return that same name. On a refusal the run exits non-zero and names the failed check. The checks are decided on the name and host the connection reaches, not on a string comparison with the development value. Check: a unit test of the guard function covers `127.0.0.1` against `localhost` for the same database, the development value with `?sslmode=disable` added, a name without the `_test` suffix, a non-loopback host, and the production setting; each is refused, and a valid test value passes.
- R6. Each server test file starts with empty tables, and server test files run one at a time against the test database. Check: two sample test files each assert, as their first step, that `workspaces` holds zero rows, then insert one row and leave it; both pass in either order, and removing the emptying step makes the second file fail.
- R7. With Postgres stopped, `pnpm test` exits non-zero and prints that the test database cannot be reached; no database test is skipped or reported as passed. The tests that need no database still run (R20).
- R8. A clock interface with a `now()` function exists, with a system implementation and a test implementation; a test sets the test clock to a fixed instant and code that receives the clock reads exactly that instant.
- R9. Advancing the test clock by a given duration moves `now()` by exactly that duration; a sample unit test shows this.
- R10. `pnpm test:e2e` at the repository root starts the web app, runs the Playwright tests in `e2e/`, and exits 0 when all pass.
- R11. One sample Playwright test exists: it opens the web app's root page, checks that the element with `data-testid="app-root"` shows the text "Toki", and checks that no error appears in the browser console. The index page of TOKI-006 renders exactly that text (TOKI-006 R2 and Screens, item 1). This test takes over the browser check of TOKI-006 R2. Changing the expected text in the test makes `pnpm test:e2e` exit non-zero.
- R12. A unit test file added under any package's `src/` and an end-to-end file added under `e2e/` are picked up by `pnpm test` and `pnpm test:e2e` with no configuration change.
- R13. In CI the server tests run against the Postgres service that the TOKI-007 workflow already has and use the connection value that TOKI-007 R15 gives them. That value must pass the R5 guard, so its database name ends in `_test`; if the value written by TOKI-007 does not, this work changes it in the workflow file. The credentials are throwaway values written in the workflow file (TOKI-007 R11). The R3 step runs in CI as it does locally. Check: on a PR, the R2 test is reported as passed in CI, not skipped.
- R14. The CI workflow from TOKI-007 has an end-to-end job, added by this work, that runs `pnpm test:e2e`: on a PR where the R11 test fails, the CI run is red.
- R15. The existing tests from TOKI-004 and TOKI-005 run under the harness: `pnpm test` at the repository root reports them and exits non-zero when one of them fails. The TOKI-004 tests run in the database-free project; the TOKI-005 tests run in the database project (R20).
- R16. No automated test changes the development database, and no automated test calls `dev:reset:db`: after `pnpm test`, the development database holds no row and no schema change made by any test. The TOKI-005 tests already meet this: each runs on its own throwaway database under a generated name, and the one check that runs `dev:reset:db`, the TOKI-005 R12 check, is a hand check (TOKI-005 R12, R13). Under the harness they receive the test connection through R18, so their throwaway databases are made on the test server and never on the development database.
- R18. Code under test and the migration command reach the database only through the configuration module of TOKI-004. The harness sets the database connection value of that module to the test database connection before any server code is loaded, so application code and `migrate.ts` both use the test database during `pnpm test`. Check: a test reads the database name through the application's own client and gets the test database name, not the development one.
- R17. This work creates the test database as a second database, under another name, on the development Postgres server, in the R3 step, over a connection to the maintenance database `postgres` of the same server with the same host and credentials as the test connection (the name is replaced; no extra variable). That connection is opened only after the R5 name, host and environment checks pass, and the only statements sent over it are `DROP DATABASE ... WITH (FORCE)` and `CREATE DATABASE` for the name that passed. Check: on a server that has only the development database, `pnpm test` brings the R2 test to pass without a hand-written SQL step.
- R19. Application code takes the clock as a parameter and does not read the system time itself. Check: a search for `Date.now(` and `new Date()` in `apps/server/src` and `packages/client-core/src` finds only the system clock file `packages/shared/src/clock/clock.ts` and no other file (test files excepted). A later ticket may turn the search into a lint rule through TOKI-002.
- R20. The database-free tests and the database tests run as two Vitest projects. A server test file whose name ends in `.db.test.ts` is in the database project and gets the R3 to R7 setup; every other test file is in the database-free project and needs no Postgres. `apps/server` has the scripts `test` (both) and `test:unit` (database-free only). Check: with Postgres stopped, `pnpm --filter ./apps/server test:unit` exits 0, and `pnpm test` runs the same tests, reports the database tests as failed (R7) and exits non-zero. Files of the database project run one at a time.
- R21. The browser that Playwright needs is installed by one documented command, `pnpm exec playwright install --with-deps chromium` (without `--with-deps` on a developer machine that already has the system libraries), run locally once after clone and in the CI end-to-end job before `pnpm test:e2e`. Check: on a clean clone, after that command, `pnpm test:e2e` passes (R10); in CI, the job log shows the install step before the test step.

## Design
### Errors
- Postgres server unreachable -> the run fails before any database test, with a message naming the connection by host and database name only: no user, no password. This matches TOKI-005 R14, which prints the same two items. A test database that does not exist is not an error: R3 creates it.
- A guard check fails (R5), or the connection value is missing -> the run fails before any statement is sent and prints which check failed or which variable is missing.
- Migration fails on the test database -> the run fails and prints the migration error.
- Web app does not start within Playwright's start timeout -> `pnpm test:e2e` fails and prints that the web server did not start.

### Layout
```
toki/
├─ vitest.config.ts               test.projects: globs over apps/* and packages/*, plus the database project of apps/server
├─ playwright.config.ts           starts apps/web, points at e2e/
├─ package.json                   scripts: test, test:e2e
├─ apps/server/
│  ├─ vitest.config.ts            database-free project (TOKI-004 tests, R20)
│  ├─ vitest.db.config.ts         database project: *.db.test.ts, one file at a time, sets the connection (R18)
│  └─ test/
│     ├─ guard.ts                 the guard function (R5), pure, no I/O
│     ├─ guard.test.ts            unit test of the guard
│     ├─ global-setup-db.ts       guard, drop and create (R17), migrate (R3)
│     ├─ setup-file-db.ts         empty tables before each file (R6)
│     └─ workspaces.db.test.ts    sample integration test (R2)
├─ packages/shared/src/clock/
│  ├─ clock.ts                    Clock interface, system clock
│  ├─ test-clock.ts               set and advance
│  └─ clock.test.ts               sample unit test (R8, R9)
└─ e2e/
   └─ sample.spec.ts              sample Playwright test (R11)
```
- The test database is a second database, under another name, on the same development Postgres server from TOKI-003, not a second container. This work creates it (R17). `dev:reset:db` (TOKI-003) wipes only the development database; it never drops the server, the volume or the test database (TOKI-003 R5, R12). Decided, see concern 3.
- The test database is dropped and created again at the start of every run (R3), not kept between runs. A changed or regenerated migration, or a switch to a branch with other migrations, therefore never leaves a stale schema, and no separate create step or reset command is needed. `DROP DATABASE ... WITH (FORCE)` is used so an open `psql` session does not block it, as TOKI-003 R23 does for the development database. The cost is one drop, one create and one migration per run.
- The Vitest setup extends the minimal one that TOKI-004 added. The TOKI-004 and TOKI-005 tests stay where those tickets put them; only the files that need Postgres are renamed to end in `.db.test.ts` so that the database project picks them up (R20). The TOKI-005 tests are not moved to the shared test database: they make and drop their own throwaway database (TOKI-005 R13), which they need for the empty-database, apply-twice and broken-migration cases (R15, R16).
- The project list is a glob over `apps/*` and `packages/*`, not a hand-kept list, so a first test in a new package is picked up (R12). Assumption: the root file uses `test.projects`, which replaces the standalone workspace file deprecated in Vitest 3.2 and removed in Vitest 4; the builder confirms this against the pinned Vitest version.
- CI: this work edits the workflow file that TOKI-007 creates. It adds an end-to-end job that runs `pnpm test:e2e` (R14) and points the server tests at the Postgres service that TOKI-007 already added (R13). TOKI-007 itself contains no end-to-end step. Decided, see concern 2.
- How the test database is chosen: the config of the database project (`vitest.db.config.ts`, outside `apps/server/src`, so TOKI-004 R2 is not affected) reads the test connection variable (named in the TOKI-096 inventory), runs the R5 guard, and sets the application's database connection variable (the TOKI-005 name) to that value in the test process through Vitest's `test.env`, before any server code is loaded. The configuration module of TOKI-004 then reads it like any other value. `createDb(connection)` and `runMigrations(connection, folder)` of TOKI-005 take the value as a parameter (TOKI-005 Layout), so nothing in TOKI-005 changes (R18).
- Files of the database project run one at a time (`fileParallelism: false`) so that they can share the one test database (R6, R20). See concern 6.
- Assumption: the clock lives in `packages/shared` so the server and `client-core` can both take it. Code receives the clock as a parameter; it does not read a global (R19). See concern 1.
- The clock interface is `now(): number`, the instant in epoch milliseconds, as the date and time module expects (TOKI-094 Scope, Out: the clock, and concern 9). The test clock has `set(instant)` and `advance(milliseconds)`, both numbers. Before a test calls `set`, the test clock returns a fixed instant, 2026-01-01T00:00:00Z, the same on every run, so a test that forgets to set it is repeatable rather than random.
- Why not Vitest's fake time (`vi.setSystemTime`) or Playwright's `page.clock`: they replace the global time and also hide a direct `Date.now()` call, while the injected clock makes every use of time visible and checkable (R19). Fake timers can still be added by the first ticket that needs timers (concern 1). This choice is an assumption of this spec.
- Assumption: the sample Playwright test runs in Chromium only and needs the web app only, not the server. See concern 5.
- CI database layout: the `tests` check of TOKI-007 starts one Postgres 17 service and passes its connection value (TOKI-007 R15). The R5 guard compares against nothing in CI: it checks the name, host and environment of the value it is given, and the development database does not exist there. R3 creates the `_test` database on that service on every run. The end-to-end job has no Postgres (the sample needs none).
- Playwright's browser is installed by one command (R21), in the same way locally and in the end-to-end job.
- The clock controls time read by application code. It does not change time produced inside Postgres (for example a column default of the current time).

## Testing
- The harness is proved by its own sample tests: the integration test (R2, R3), the clock test (R8, R9) and the Playwright test (R11). Each is written first and seen to fail before the configuration makes it pass.
- Automated: R18 (a test reads the database name through the application's client and gets the test name), R5 (the unit test of the guard function, so a later change to the guard fails a test), R6 (the two sample files), R8 and R9 (clock test), R19 (the search, run as a script in the PR).
- By hand once, recorded in the PR: R4 and R16 (compare development row counts and schema before and after `pnpm test`), R7 and R20 (stop Postgres and run both scripts), R3 and R17 (a server with only the development database, then a leftover table added by hand), R21 (clean clone).
- R13 and R14 are proved the way TOKI-007 proves its checks, with throwaway PRs that carry one fault each: one that breaks the R2 test must show a red `tests` check, with the R2 test not skipped; one that changes the expected text of the R11 test must show a red end-to-end job; a PR with no fault shows both green. The results go in this PR.
- R15 is checked by running `pnpm test` and seeing the TOKI-004 and TOKI-005 tests in the report.
- Fake data only: the sample workspace row uses a made-up name. No seed data is used.

## Data safety
- On a developer machine the test database connection comes from `.env`, never from a value committed to git. In CI it points at the Postgres service of the workflow, whose local-only credentials are written in the workflow file by TOKI-007; they protect nothing outside the run and are not secrets. Its variable name is the one in the TOKI-096 inventory. Error messages print the host and database name only, never a user or password (TOKI-005 R14).
- Tests drop and empty tables, so the R5 guard must run before any statement is sent to the server, including the first `DROP DATABASE`.

## Areas of concern
1. The purpose and first use of the controllable clock are not stated in the intent or the Blueprint. This spec assumes an injected `now()` clock in `packages/shared`. If the first use needs timers, browser time in Playwright, or database time, the design changes. Answered in part: the clock is for the time-dependent rules of phase 1. The Blueprint states: a sign-in code is valid for 10 minutes; a session lasts 30 days; an invitation expires after 7 days (G4); at most 5 code requests in 15 minutes and resend after 60 seconds (G5); presence turns Away after 5 minutes (G3); a status clears on a timer (TOKI-056); reminders and snoozes fire on time (TOKI-066, TOKI-067; M5 exit check "reminders fire on time"). The first ticket by milestone order that needs it is TOKI-022 "Sign-in API" (M2). Evidence: Toki Blueprint (claude.ai/artifact/VVRByrWR4d1BYgp3JA5vTE), Requirements tab, Sign-in; assumptions G3, G4, G5; Plan tab, tickets TOKI-022, TOKI-056, TOKI-067 and milestone M5. Still open: whether an injected `now()` is enough once timers run in the job queue (TOKI-064, pg-boss) and in the browser. Owner: Thanh Truong.
2. The Blueprint Infrastructure section says CI runs end-to-end on every PR, but the TOKI-007 scope lists only lint, type check, tests, build and bundle size, and TOKI-007 does not need TOKI-008. Decided: the test database is a second database, under another name, on the same development Postgres server; `dev:reset:db` wipes only the development database and never drops the server, the volume or the test database; TOKI-008 still owns creating the test database (R17). Decided by Thanh Truong (lead, as product owner) on 2026-11-12. Owner: Thanh Truong.
