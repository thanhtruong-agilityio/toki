# Later design

Date: 2026-11-25 · Status: draft for review
Intent: docs/intents/later.md (Thanh Truong)
Ticket: TOKI-067
Needs: TOKI-064 (the job queue: `defineJob`, `JobDeps`, `enqueue` and `cancelByKey` with `tx`; spec on main), TOKI-068 (`useOpenMessage`; spec on main), TOKI-037 (the message rows, `getConversationFacts`), TOKI-070 (`buildMessageEntriesByIds`, R9 (b)), TOKI-047 (`deletedBy`, R8), TOKI-058 (`listFiles`, R15, for `fileName`), TOKI-066 (the time-choice labels, hook and menu body, concern 6), TOKI-038 (the event log writer and the `user` scope), TOKI-040 (`registerEventHandler`, the sync seams), TOKI-052 (the bar and menu entries, `entries.ts`), TOKI-094 (`quickTimeChoices`, `validateFutureInstant`, merged), TOKI-093 (`useUndo`, `useOnlineGate`, the action id `removeFromLater`, merged). Written at the same time: TOKI-065 (Activity, server) and TOKI-102 (notification preferences, server); read them at the end of the work (Plan changes).

## Goal
A person who sees a message they must deal with later has nowhere to put it. This ticket builds Later: a personal list of saved messages with two states, In progress and Completed, an optional reminder on each, a reminder that fires on time through the job queue, a badge on the Later item of the navigation that counts reminders that have come due, and the page, the bookmark and the reminder entry that use them. The server keeps the list, the web app shows it, and the same list and badge appear on every device of the person.

## Scope
- In:
  - The `later` module of `apps/server`: the table `later_items`, four routes (list, save, change, remove), the reminder job and its handler, the change `later_changed` and the event `later.changed`, the port through which a due reminder is announced (R1 to R14).
  - The schemas and constants in `packages/shared`, the API calls and the store of `packages/client-core` (R2, R15, R16).
  - The Later page at `/later`, its rows, the reminder menu, Undo on removal, the badge, the reminder toast and the texts (R17 to R24).
  - The two entries this ticket adds to the message bar: Save for Later (the bookmark button) and Remind me about this (R19).
- Out (not now), each with its owner:
  - Everything that decides whether a due reminder makes a toast, a push or a sound while Pause or Focus time is on, and Pause and Focus themselves: TOKI-076 (the data and the time of Pause and Focus) and TOKI-073 (the decision), behind the port of R11. This ticket says what a held reminder is and who fires it afterwards (R11, concern 3).
  - The push itself: TOKI-074. The in-app sound and the toast rules for notifications in general: TOKI-075. This ticket draws only the content of the reminder toast and shows it when it is not held (R22).
  - The Activity screen and its snooze: TOKI-066. The pure rule that makes the time choices is `quickTimeChoices` of TOKI-094; the labels, the hook and the menu that both screens use are TOKI-066's, and this ticket uses them (R23, concern 6).
  - The More sheet and the badge of its tab on a narrow screen: TOKI-092. This ticket exports the number it shows (R20).
  - The summary at the end of Pause or Focus: TOKI-076. This ticket exports the read it needs (R12).
  - The action bar and its menu as such: TOKI-052. This ticket adds one line in `useBarSpecs` and one in `useMenuSpecs` (R19).
  - How the list opens a message and flashes it: TOKI-068; this ticket calls `useOpenMessage` (R18).
  - Saving while offline (queued writes): a later phase (D-060 says phase 6 queues saves to Later). Offline, a write is blocked with an explanation (D-079, R21).
  - Phone and desktop push content, mail, Tasks ("Turn into task") and Send later: not this ticket.

## Requirements
Server: table and rules
- R1. The module and the table. `apps/server/src/modules/later/` holds the Drizzle table `later_items` (`schema.ts`, not exported from `index.ts`) and a migration written for it (TOKI-005). Columns: `id` uuid primary key (UUIDv7 made by the server), `workspace_id` uuid not null, `user_id` uuid not null, `message_id` uuid not null, `conversation_id` uuid not null (the conversation of the message, copied once at save: a message never changes conversation), `saved_at` timestamptz not null, `updated_at` timestamptz not null, `completed_at` timestamptz null, `remind_at` timestamptz null, `fired_at` timestamptz null, `due` boolean not null. Foreign keys are written in the SQL of the migration (workspace, user, message, conversation). One row for each person and message: a unique constraint on (`user_id`, `message_id`). Checks: `due` is true only when `fired_at` is not null; `remind_at` and `completed_at` are not both set (concern 1, proposal). An index on `user_id`. No time column has a database default; every time is read from the clock of TOKI-008 (TOKI-024 R6). The table holds no message text, no name and no title: it holds identifiers and times. `index.ts` is the only public entry and exports `laterRoutes`, `laterReminderJob`, `createFireReminderHandler`, `listRemindersFiredBetween` and `getLaterItemStatus` (R12), `LaterJobDeps` and `ReminderNotifier` (R11) and the types. Check: a database test reads the columns, the unique constraint, the two checks and the index from the catalog; two rows for one person and message are refused; `due` true with `fired_at` null is refused; `db:generate` reports no change; the export test of the module lists these names.
- R2. Shared schemas and constants. `packages/shared/src/later/` (exported from the package index) holds, as strict Zod objects: `LaterItemStateSchema` with `id`, `messageId`, `conversationId`, `savedAt`, `completedAt` (null or ISO 8601), `remindAt` (null or ISO 8601), `due` (boolean), `firedAt` (null or ISO 8601); `LaterSourceSchema`, a union on `state`: `available` with `authorId`, `parentId` (null or the root's id), `createdAt`, `snippet` (string) and `fileName` (null or string); `deleted` with `deletedBy` (`"author"` or `"admin"`); `unavailable` with nothing else; `LaterItemEntrySchema` = the state plus `source`; `SaveLaterBodySchema` `{ conversationId, messageId, remindAt?, completed? }`; `UpdateLaterBodySchema` `{ completed?, remindAt?, acknowledged? }` (R5); the answers `LaterListResponseSchema` `{ items, number }` and `LaterChangeResponseSchema` `{ item, number }`; `LATER_SNIPPET_MAX` = 140 (the prototype cuts the text of a row at 140 characters, `msgSnippet(m, 140)`); and the event schema of R13. Times are ISO 8601 UTC strings. `remindAt` in a body is an ISO 8601 string; the route parses it with `Date.parse` (R6). Check: a schema test accepts each shape and refuses an added key, a missing key, a `state` that is not listed, a non-ISO time, `due` as a string and a body with both `completed: true` and a `remindAt` that is not null; a type test imports every name from `@toki/shared`.
- R3. Save. `POST /api/v1/later` takes `SaveLaterBodySchema` and needs a valid session (401). Steps in order: (1) the body schema (400 `validation_failed`); (2) `getConversationFacts(db, actor.id, conversationId)` of TOKI-028: `null`, or a private channel, a DM or a group of which the actor is not a member, is 404 `not_found`; (3) `canReadConversation` of `@toki/shared`: a person who is not a member of a public channel is 403 `forbidden` (D-116); a channel archived is readable (concern 5, proposal); (4) `remindAt`, when given, passes `validateFutureInstant` of TOKI-094 R14 with the clock of the request (R6); (5) one statement reads the message with `buildMessageEntriesByIds(db, workspaceId, [conversationId], [messageId])` (TOKI-070 R9 (b)): no entry, an entry of `kind` `system`, or an entry with `deletedAt` set is 404 `not_found` with the same body as step 2, so a message that is not in that conversation is not confirmed; a reply (an entry with a `parentId`) is allowed (the prototype draws the bookmark in the thread panel too); (6) steps 6 to 9 run in one transaction, with the locks in the order of TOKI-024 R39 (member-management R39): the account row `FOR SHARE` (a deactivated account is 401 `account_deactivated`), then the insert `ON CONFLICT (user_id, message_id) DO NOTHING`; when a row was inserted it is the new item (`saved_at` and `updated_at` from the clock, `completed_at` set to the clock when the body has `completed: true`, `remind_at` from the body); when none was inserted the existing row is read `FOR UPDATE` and the body is applied to it by the rules of R4 (a body with no field changes nothing); (7) the timer of R7; (8) `recordChange` once, as the last write, when something changed (R13); (9) still inside the transaction, after `recordChange` and while its counter lock is held, `getLastEventNumber(tx, workspaceId)` of TOKI-036 R19 (given by `app.ts` as a dependency) is read and returned as `number`: with the lock held no other change of the workspace can take a number between the write and the read, so `number` is the number of this change's own event, as the status spec does (TOKI-056 R6 step 5); it is never read after the commit. The answer is 201 with `{ item, number }` for a new item, 200 for an existing one (`number` null and `item` unchanged when nothing changed: a double press changes nothing, D-111). The item in the answer holds its `source` (R9). A person saves only for themselves: no field names another person. Check: a table test of each refusal, with a positive case for a public, a private channel, a DM, a group and an archived channel; saving a system line and a deleted message is 404; saving a message under another conversation's id is 404 and the same body as an unknown conversation; the same body twice gives 201 then 200 with `number` null and one row, one `recordChange` call; a reply is saved; a person who is not a member of a public channel gets 403 and no row; a deactivated account gets 401; the statement log shows the account lock before the insert and `recordChange` as the last write; another person's Later list does not hold the message (AC-062, TS-097); a two-session test: the second session records an event between this request's commit and its answer, and `number` is still the number of this request's event, not the second session's.
- R4. Change. `PATCH /api/v1/later/{messageId}` takes `UpdateLaterBodySchema`, a strict object with at least one key (an empty object is 400), and changes the caller's own item for that message; a message that is not in the caller's list is 404 `not_found` (another person's item cannot be told from none). `completed: true` sets `completed_at` to the clock when it is null, and clears `remind_at` and `due` (concern 1, proposal); `completed: false` sets `completed_at` to null and changes nothing else. `remindAt` set to an ISO time sets `remind_at`, clears `due` and, when the item is completed, moves it back to In progress (concern 1, proposal); `remindAt: null` clears `remind_at` (and leaves `due` as it is). `acknowledged: true` clears `due` and changes nothing else (the person opened the row, as in the prototype); `acknowledged: false` is 400. Two of `completed: true` and a non-null `remindAt` in one body are 400. A body that changes nothing (a value equal to the stored one) writes nothing, calls `recordChange` zero times and answers 200 with `number` null. Otherwise 200 `{ item, number }` with `updated_at` from the clock. The steps are those of R3 from step 4 on (the future rule, the account lock, the item row `FOR UPDATE`, the timer of R7, `recordChange` last, then `number` read inside the transaction after `recordChange`, as R3 step 9 says). No read of the conversation is made: the person's own list stays editable after they lost access to the conversation (concern 2). Check: each key and each refusal; completing a row that has a reminder clears the reminder and the job (R7); setting a reminder on a completed row makes it In progress; `acknowledged` clears `due` only; the same body twice gives one event; another person's item is 404; the two-session test of R3 (an event from another session between the commit and the answer) leaves `number` as this request's own.
- R5. Remove. `DELETE /api/v1/later/{messageId}` deletes the caller's row and answers 200 `{ item: null, number }`; a message that is not in the list is 200 `{ item: null, number: null }`, writes nothing and calls `recordChange` zero times (a retry after a lost answer is safe). The pending job is cancelled (R7). `number` is read inside the transaction after `recordChange`, as R3 step 9 says. Check: a delete twice is 200 twice with one event; the job is gone after the delete; another person's row is not touched.
- R6. The time rule. A reminder time must be later than the clock of the request: `validateFutureInstant(remindAt, now)` of TOKI-094 R14, where `at <= now` is `past`. The route converts the ISO string of the body with `Date.parse` and passes the number to the rule (a string the schema of R2 already refuses never reaches it, so the `invalid` case of the rule cannot happen through the route and the route has no code for it). A `past` answer is 400 `validation_failed` with `details.field` `remindAt` and `details.reason` `past` (TOKI-094 leaves the code to the ticket that has the field), and nothing is written. The time of the clock is read once for the request. No upper bound is set (concern 4). Check, with the controllable clock: now, now minus one second and now minus one year are refused; now plus one second and now plus one minute are accepted (TS-098, TS-099); a refused request leaves the item as it was, its earlier reminder included; the instant stored in `remind_at` and the instant in the job payload and `startAfter` are the same (one test compares them).
- R7. The timer. Inside the transaction of R3, R4 and R5, after the row is written and before `recordChange`: `deps.jobs.cancelByKey(laterReminderJob, key, { tx })` with `key` = `later-reminder:` + the item id, then, when the row now has a `remind_at`, `deps.jobs.enqueue(laterReminderJob, { itemId, remindAt }, { startAfter: remindAt, key, tx })` (TOKI-064 R11, R12, R14), so a rollback leaves neither the row nor the job. The job type is `laterReminderJob = defineJob({ name: "later.fire-reminder", payload: z.strictObject({ itemId: uuid, remindAt: ISO date-time }) })`, declared in `modules/later` and exported from its `index.ts`; its type is added to `apps/server/src/job-types.ts` and the factory `createFireReminderHandler(deps: LaterJobDeps)` (R11) to `job-handlers.ts` (TOKI-064 R9). The payload holds an identifier and a time and never any text (TOKI-064 R7). `cancelByKey` stops only a job that has not started, so the handler checks the row (R8). Check, on a jobs database (`createJobsTestDb`, TOKI-064 R5): a save with a reminder leaves one job with `startAfter` equal to the reminder; changing the reminder leaves one job for the new time; completing, removing and clearing the reminder each leave none; a transaction that throws after the enqueue leaves no job and no row; a request made through the fake queue (`createFakeJobQueue`) records the calls in this order.
- R8. The handler. `createFireReminderHandler(deps)` returns `defineHandler(laterReminderJob, async (context, data) => ...)`. It first reads the item by id, with no lock, for its `userId` (an item that is gone: the handler writes nothing and completes) and asks `deps.reminderNotifier.isHeld(userId, now)` (R11). It then runs one transaction, with the locks in the same order as R3 and R4 (the account row before the item row, as member-management R39), so a deactivation, a PATCH and the handler cannot wait on one another in a cycle: (1) the account row `FOR SHARE`: for a deactivated account the handler does nothing and completes; (2) the row is read `where id = $1 and remind_at = $2 and completed_at is null for update` with the exact time of the job, so an item that was removed, completed, given another reminder, or already fired (a second delivery of the same job) matches nothing, and the handler writes nothing and completes; (3) the row is updated: `due` true, `fired_at` the time of `context.clock`, `remind_at` null, `updated_at` the same time; (4) `deps.recordChange` once, as the last write, with the change of R13, reason `reminder_due` and `held` the answer of `isHeld`. After the commit, when `held` is false, it calls `deps.reminderNotifier.notify(input)` (R11); the handler catches an error of `notify`, writes one `warn` line with the identifiers only through `context.log`, and completes the job; the due state is not undone (a push that failed is TOKI-074's to retry; a retry of this job would find no row). Retry and backoff are the defaults of TOKI-064 R8. The handler reads no clock to decide whether the time has come: the queue hands the job over at `remindAt` (TOKI-064 R14); with the poll of TOKI-064 R8 a reminder fires within 2 seconds after its time while the worker is running, and late but still after the worker was stopped (concern 7). Check, with the library's `TestClock` and `enableSpies` (TOKI-064 R19): a job for a row of a pending reminder, with the clock moved to one millisecond before the time, is not run, and moved 2 seconds past it, sets `due`, `fired_at`, clears `remind_at` and writes one event; the same job delivered twice writes one event; a job whose row was changed to another time, completed or removed writes nothing; a deactivated account writes nothing; with `isHeld` true the row is due and the change says `held: true` and `notify` is not called; with false `notify` is called once with identifiers and times only; a failing `notify` leaves the row due, completes the job and writes exactly one `warn` line through `context.log` that holds identifiers only (the test reads the line); a two-connection test of a deactivation, a PATCH and the handler started together ends without a deadlock error and with a consistent row; the statement log shows the account lock before the item lock and `recordChange` last.
- R9. The list and its sources. `GET /api/v1/later` needs a session and returns `{ items, number }`: `number` is `getLastEventNumber` read first, then one statement reads all the caller's rows, newest `saved_at` first (then `id`). The conversations the person may read are found by one statement over their member rows: this ticket adds `listReadableConversationIds(db, userId, conversationIds)` to the `conversations` module (exported by its `index.ts`, one statement, the person's own member rows only, archived channels included, so an Admin who is not a member has no extra right, D-047). For the rows of those conversations the entries are built with `buildMessageEntriesByIds` and one `listFiles` read of TOKI-058 R15 for the available messages (injected by `app.ts`; when it is not given `fileName` is null). The `source` of each row is: `available` when the conversation is readable and the entry is a message that is not deleted (`snippet` is the first `LATER_SNIPPET_MAX` code points of `text`, cut by code points and never in the middle of a pair, and `""` when the text is empty; `fileName` is the name of the first file or null; the snippet is the stored text as sent, with no rendering); `deleted` when the entry has `deletedAt` set (`deletedBy` from the entry; no text, no author); `unavailable` when the conversation is not readable by the person now (concern 2). The list holds no row of another person. A message is never removed from its table and the row has a foreign key to it, so every item has an entry; should the read find none, the build treats the item as `unavailable`, never as `deleted` (`deletedBy` has no value for it). The number of statements is the same for any number of items (one for the number, one for the rows, one for the conversations, one for the entries, one for the files). Check: a person with 120 saved messages in 12 conversations gets 120 items, the statement count equals that of a person with 3 (counting fake); each `source` state has a fixture (a text of 300 characters is cut at 140, with an emoji at the cut not split; a message deleted by its author, by an admin; a conversation the person left, by SQL); no item of another person appears; the 401 case.
- R10. Cost and limits of the list. The list is returned whole in one answer, because the counts of the chips must equal the rows (D-074, concern 4); no page parameter exists. Check: a request with a `limit` key is 400 (the query is strict); a list of 1,000 rows is answered in the statement count of R9.
- R11. The port for a due reminder. `modules/later` defines and exports, structurally, what its handler needs: `ReminderNotifier = { isHeld(userId: string, at: number): Promise<boolean>; notify(input: ReminderNotice): Promise<void> }`, `ReminderNotice = { userId, workspaceId, itemId, messageId, conversationId, firedAt: number }` (identifiers and a time, no text) and `LaterJobDeps = { clock, recordChange, reminderNotifier }`, as the status spec does with `StatusDeps` (TOKI-056 R6) and TOKI-102 R6 with `PreferencesDeps`; the composition file `job-deps.ts` imports these types, not the reverse (TOKI-064 R24). `JobDeps` (TOKI-064 R9, its table "Fields of `JobDeps`") gains one field from this ticket, `reminderNotifier`, of that type, built in `buildJobDeps` (TOKI-064 R9; no other configuration area is needed). Until TOKI-073 gives the real one, `buildJobDeps` builds the default `{ isHeld: async () => false, notify: async () => {} }`, so a reminder is never held and no push is sent; this is a stand-in and is named so in the code. The owners of what stands behind it: TOKI-076 knows whether Pause or Focus time covers a moment and gives that answer to TOKI-073; TOKI-073 builds the real `isHeld` (true while Pause or Focus time covers `at`, D-072) and the `notify` that decides push and sound (with TOKI-074 and TOKI-075 sending them). A reminder that is held is not a stored state: the item becomes due at its time exactly as an unheld one does (the row, the badge and the event, D-072: "badges still update"), and only the toast and the push are left out; the event carries `held: true` so the open clients draw no toast (R22). D-072 and F28 say that badges still update during Pause or Focus time and that when it ends one summary lists what arrived. This spec's own reading, which fits D-072, D-063 and F28, is that nothing fires a held reminder afterwards: the summary is TOKI-076's and reads the rows through R12 (concern 3). A Pause that starts between the `isHeld` read and the commit leaves a toast that the person did not want; the window is the length of one handler run and is accepted (concern 3). Check: a type test of `ReminderNotifier`; the default is used when none is given and never holds; a fake that returns true holds as R8 says; `LaterJobDeps` and `ReminderNotifier` are exported from `modules/later` and `job-deps.ts` imports them (a lint or import test shows no import from `modules/later` to a composition file); no file of `modules/later` imports a Pause or notification module.
- R12. Two reads for other tickets, exported by `index.ts`. (a) `listRemindersFiredBetween(client, userId, fromMs, toMs)`, where `client` is the database or a transaction (TOKI-076 calls it from inside its transaction), returns `{ itemId, messageId, conversationId, firedAt }[]` for the person's rows whose `fired_at` is at or after `fromMs` and before `toMs`, oldest first, identifiers and times only. It is the one thing TOKI-076 reads from Later to count "what arrived" while it was on (its `countRemindersFired` is the length of this list). A row that was removed since is not returned, and a row that was completed since is (it fired). (b) `getLaterItemStatus(client, userId, itemId)` returns `{ messageId, conversationId, completed } | null` for the person's own row with that id, in one statement: `null` when the row does not exist (it was removed) and `completed` true when `completed_at` is set. It is the read that the push of a reminder makes at send time (TOKI-074 R14, the table row "the reminder item exists and is in progress"): the push is sent only for a row that exists and is not completed; whether the source message is deleted is read from the message by TOKI-074 itself. It reads no text and no other person's row (a row of another `userId` gives `null`). Check: (a) three rows fired at three times, one removed, one completed: the bounds include the lower and exclude the upper; another person's rows are not returned; no text is in the result; the same call with a transaction gives the same rows. (b) a row in progress gives `completed` false, a completed row gives true, a removed row gives `null`, another person's row gives `null`, and the result holds no text.
- R13. The change and the event. `Change` of `conversations/changes.ts` gains a member, `LaterChange`: `{ type: "later_changed", workspaceId, userIds: [userId], actorId, at: Date, messageId, reason, item, held? }` (`actorId` is the person whose list it is, as `ConversationChange` and `MemberStatusChange` carry it; the sibling tickets TOKI-065 `ActivityChange`, TOKI-076 `QuietChange` and TOKI-102 `NotificationPreferencesChange` add their own members in their own changes, so no member is "the third") with `reason` one of `saved`, `updated`, `removed`, `reminder_due`, `item` the `LaterItemState` of R2 (null for `removed`) and `held` for `reminder_due` only (the same way `MemberStatusChange` of TOKI-056 R8 has no `conversationId`; a handler narrows on `change.type`). The event handler of TOKI-038 gets one row (R20 there, "Rows of later tickets"), and its `EventChange` gains the optional fields `messageId?`, `reason?`, `item?` and `held?` (as TOKI-056 does with `StatusEventChange`): `later_changed` becomes the event `later.changed`, scope `user` (the one person of `userIds`), with `data` `{ messageId, reason, item, held }` (`held` false when absent). The kind is added to the registry of `events.ts` with that schema and to `kinds.ts` (it changes no conversation map), and the test that every kind has a row there passes. The system-line handler writes nothing for this type. The event holds no message text, no name and no snippet, so the log (kept 7 days) never holds the person's saved text. Every effective change of R3, R4, R5 and R8 calls `recordChange` once; a request that changes nothing calls it zero times. Check: for each route a recording handler receives the change with the fields above; the real event handler writes one `later.changed` event of scope `user` and no other person's connection receives it (a second person's connection hears nothing); the registry and `kinds.ts` tests pass; a search of the event payload finds no text. The pull request of the build lists the edits that this ticket and the tickets written beside it (TOKI-065, TOKI-076 and TOKI-102) make to the `Change` union of `changes.ts`, each adding its own member.

## Design
### Data model
`later_items` (R1): one row for each person and saved message. The reminder has two states in the row and nothing else: pending (`remind_at` set, `due` false) and due (`remind_at` null, `due` true, `fired_at` set). A completed row has no pending reminder (concern 1, proposal). The saved text is never copied into the row: the list reads it from the message each time, so the server's answer to each read shows the current text, a deletion or a loss of access, and the log never holds it. On a client that read happens at `load()`, which the store makes at the events of R16 (c) that edit or delete a message or remove the person's access, so a row changes its snippet or becomes a replacement row when the event arrives, with the chip counts following. R1, R4, R7 and R8 depend on the proposal of concern 1, R9 and R24 on concern 2, R3 and R19 on concern 5 and R22 on concern 8; the migration of R1 and these requirements are written after the owner has answered, or change with the answer.

### API
All routes need a session. Bodies are JSON. The writes carry the `Origin` rule.
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/later` | The person's items with their sources and the event number (R9) |
| POST | `/api/v1/later` | Save a message, optionally with a reminder; 201 new, 200 existing (R3) |
| PATCH | `/api/v1/later/{messageId}` | Complete, reopen, set or clear a reminder, acknowledge a due row (R4) |
| DELETE | `/api/v1/later/{messageId}` | Remove from Later (R5) |

### Event
`later.changed`, scope `user`: `{ messageId, reason, item, held }`. Every connection of the person receives it, so the list and the badge follow on every device (D-142's rule for personal data, as `settings.changed`).

### The life of a reminder
```
POST/PATCH with remindAt --> row.remind_at set --> cancelByKey + enqueue(startAfter = remindAt)   (one transaction)
                                   ...  worker poll (<= 2 s late)
later.fire-reminder: isHeld? --> tx: row (remind_at = job time, not completed) --> due = true, fired_at = now
                                    --> recordChange(later_changed, reminder_due, held) --> commit
                                    --> held ? nothing : reminderNotifier.notify(...)   (push: TOKI-074 through TOKI-073)
clients: event --> store --> badge, due row on top --> LaterHost: toast unless held or old
Pause/Focus end: TOKI-076 reads listRemindersFiredBetween(from, to) for its one summary
```

### Errors
- No session -> 401 `unauthenticated`; a deactivated account -> 401 `account_deactivated`.
- Unknown conversation, a private conversation the person is not in, a message that is not in that conversation, a system line, a deleted message, another person's item -> 404 `not_found`, one body for all (R3, R4).
- A public channel the person has not joined -> 403 `forbidden` (R3).
- A reminder that is not later than the clock, or not an instant -> 400 `validation_failed` with `details.field` `remindAt` (R6).
- A body with an extra key, an empty PATCH, `acknowledged: false`, or `completed: true` with a reminder -> 400 `validation_failed` (R2, R4).
- The job queue unreachable when a reminder is set -> the transaction fails and the route answers `internal_error`; nothing is saved (R7).

## Data safety
- A saved message belongs to one person: the list, the badge, the event and the summary read only that person's rows (R3 to R5, R9, R12, R13).
- No job payload, no event, no log line and no error message holds a message's text or a name: the payload holds an identifier and a time (R7), the event holds state and identifiers (R13), the notifier input holds identifiers and a time (R11), the list reads the text from the message at each request (R9) and shows nothing of a message the person can no longer read (`unavailable`, R9).
- A person who loses access to a conversation keeps the row and sees no content of it (R9, concern 2). Nothing is written to browser storage by this ticket.

## Areas of concern
1. Completed items and reminders. Not decided. The prototype lets a completed row keep a reminder that never fires while it is completed, and fires at the next tick when the row is reopened (its `!l.done` test); F28 and the log say nothing about it. The spec needs one behavior so that a reminder cannot fire for a finished item or sit unseen. Proposal, not a decision (R1, R4): completing clears the pending reminder and the due mark; a reminder set on a completed row moves it back to In progress (the prototype does this for "Remind me about this", `remindmsgset`, and not for the row's own button); a completed row shows no reminder line. Alternative: keep the prototype, with the job doing nothing for a completed row and a reopen that sets no new job. Second part, also a proposal and not a decision (R20 (b)): completing and reopening a row has no Undo, as the prototype has none and TOKI-093 concern 10 proposes; D-061 and D-063 list mark done among the actions with Undo, so the alternative is a 5-second Undo on Complete. Owner: Thanh Truong (product owner).
2. A Later row whose conversation the person can no longer read. Not decided. D-133 clears Activity items on leaving a channel and the log says nothing of Later (TOKI-068 concern 10 carries the same question). D-116 forbids showing the content. Proposal, not a decision (R9, R24): the row stays, shows no name, no text and no link, reads "Message no longer available" (a proposal of wording, D-139), can be completed or removed, opens nothing, and comes back as a normal row if the person regains access. The press of such a row is part of this proposal (R18, R24): it opens nothing and, when the row is due, clears the due mark; the alternative of TOKI-068 concern 10, which is also not decided, is that the press calls `open` and the route shows its not-found view or Join. Alternative to the whole proposal: the row is removed when access is lost. Owner: Thanh Truong (product owner).
3. A reminder due during Pause or Focus time: who fires it afterwards. Decided (D-072, F28): at its time the item is due, the badge rises and the event is written; only the toast, push and sound are left out; when Pause or Focus ends one summary lists what arrived, and TOKI-076 reads it through `listRemindersFiredBetween` (R12). The reading that nothing else fires a held reminder afterwards is this spec's own and fits D-072, D-063 and F28. Decided in this spec (technical): a held reminder is not stored; it is a due row whose event carries `held: true`, and the owner of the answer to "is this person held" is TOKI-073 with the data of TOKI-076, behind `reminderNotifier` (R11); the owner of the summary is TOKI-076; this ticket owns the due state. The stand-in that never holds is replaced by TOKI-073. The short window between the `isHeld` read and the commit is accepted. Owner: Thanh Truong.
4. Limits. Not decided. No decision gives a maximum number of saved messages or a furthest reminder time, and no decision gives a page size for the list. Proposal, not a decision (R6, R10): none; the list is returned whole because the chip counts must equal the rows, and a reminder may be at any later time. If the owner wants a limit it is one constant in `packages/shared` and one check in R3. Owner: Thanh Truong (product owner).
5. Saving from an archived channel. Not decided. An archived channel is readable (F26) and Later is personal, so saving writes nothing in the channel; no decision says whether the bookmark is offered there. Proposal, not a decision (R3, R19): offered, because reading is the right it needs. Alternative: follow the smile button of TOKI-052 R11, which hides in an archived channel. Owner: Thanh Truong (product owner).
6. The time choices and their owner. Decided in this spec (technical): `quickTimeChoices` and `validateFutureInstant` are TOKI-094's and merged; the four labels are given to TOKI-066 by TOKI-094, and `useQuickTimeChoices` and the menu body `QuickTimeMenu` (with `onChoose` and the optional `children` after a separator) are TOKI-066's own claim, which its R22 builds and confirms; this ticket imports them from `apps/web/src/time-choices/` and builds none; if this ticket is built before TOKI-066, the builder adds exactly those four keys, that hook and that component in that folder and TOKI-066 reuses them, so a name is never added twice (the rule of TOKI-064 R9 for `JobDeps`). The plan's needs line for TOKI-067 gains TOKI-066 or the build order is chosen with that rule. The time zone in which "Today 15:00" is read is decided in TOKI-094 concern 2 (option (a), the profile zone, 2026-11-18); this ticket uses the date context of `apps/web/src/account/use-date-context.ts` (or `apps/web/src/date/use-date-context.ts` once TOKI-080 R7 has replaced it) and, until TOKI-078 gives the profile zone, that context holds the browser's zone, as TOKI-056 R14 says. Owner: Thanh Truong.
7. How a reminder is kept and how exact it is. Decided in this spec (technical): the reminder is a stored job with `startAfter` in the queue of TOKI-064, inside the transaction of the change, with the row as the source of truth and an exact-time re-check in the handler (R7, R8), so a restart, a double delivery, a changed time and a cancel that arrives late all end right. No decision of the log gives the tolerance of "on time"; the poll of TOKI-064 gives at most 2 seconds after the time while the worker runs (TOKI-064 concern 7), which is accepted here because the smallest choice is one hour. A reminder set for a time that passes while the worker is down fires when the worker starts. Owner: Thanh Truong.
8. Wording and a stale toast. Not decided. Two proposals: the sentence of a refused past time (`later.error.past`, "Choose a time that has not passed") and the unavailable row (concern 2) are not in the prototype or the log (D-139). The toast of a reminder that fell due while the tab was closed or offline: the replayed event is new to the store and would show a toast hours late. Proposal, not a decision (R22): no toast for an event the store applied while catching up after `ready` (`replayed`), the row and the badge being enough. This rule compares no two clocks, so a device clock that is wrong does not decide it (as TOKI-056 R18 does for the status expiry). Alternative: a maximum age in milliseconds of the event's `createdAt` against the page clock, which a device clock more than that apart from the server's would defeat. Owner: Thanh Truong (product owner).
9. How the list and the API are shaped, and where a row can be removed. Decided in this spec (technical): items are addressed by message id (one row for each person and message); the list is built on the server from the message and the person's membership, so the stored row holds no text; a change is announced by one event of scope `user` that carries state and no text, and the store orders changes by event number as TOKI-056 orders a status (R9, R13, R16). Reason: a saved snippet would go stale on an edit and would outlive a loss of access, and a text in the log breaks the rule of TOKI-064 R7. The prototype removes from Later only through the bookmark of the message; no decision adds a remove control to a row, so this ticket adds none (R20 (a)). Owner: Thanh Truong.
10. Opening a row, and the replacement row. Decided in this spec for the rows that are available or deleted: an available row opens its message through `useOpenMessage` and clears its due mark (the prototype's `openlater`); a deleted row opens nothing, as TOKI-068's table says, and clears its due mark by the press; a saved reply opens the thread panel at the reply (TOKI-068 R6). Not decided for an `unavailable` row: its press depends on concern 2 and on TOKI-068 concern 10, which is the same question and is not decided. Proposal, not a decision (R18, R24): opens nothing and clears the due mark. Alternative: the press calls `open` and the route shows its not-found view or Join. Owner: Thanh Truong (product owner).
11. Offline and the narrow screen. Decided (D-079, D-067, F38): writes are blocked with the explanation of TOKI-093, the list stays readable, nothing is faked; Later is a tab of the bottom bar and its buttons are always drawn. Queued saves while offline are phase 6 (D-060) and not built. Owner: Thanh Truong.
