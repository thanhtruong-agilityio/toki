# Admin page design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/admin-page.md (Thanh Truong)
Ticket: TOKI-025

## Goal
An Admin needs a screen to bring people into Toki and keep the member list in order: see who is a member, who is only invited, whose mail did not go out and who has been deactivated; invite people with a role; resend or revoke an invitation; change a role; deactivate and reactivate a person. A Member must see nothing of it. The server already does all of this (TOKI-024); this work builds the page that calls it: the `/admin` route, the member table with its search and status chips, the Invite members dialog, the row actions with their confirmations, the Channels list, and the "no access" view.

## Scope
- In:
  - The route `/admin` and its row in the shell's list of sections, for Admins only (R1, R2); the gate and the "no access" view (R3, R4).
  - The calls to the seven routes of TOKI-024, in a file of `apps/web` (R5).
  - The member table: columns, rows, search, status chips with totals, the first 50 and more on scroll, reload after a change (R6 to R14).
  - The row actions and their locks, with the reason: Resend and Revoke on an invitation; Change role, Deactivate and Reactivate on a person; the confirmations; the errors (R15 to R20).
  - The Invite members dialog and its per-address results (R21 to R24).
  - The Channels list with each channel's member count, its own list state, and the place where TOKI-098 puts its "+" (R25, R32).
  - The narrow-screen form of the page, the texts in English and Vietnamese, the dates, the checks (R26 to R31).
- Out (not now):
  - The "+" on the Channels list, the Create channel dialog and everything it does: TOKI-098. This work builds the section it sits in and places TOKI-098's `CreateChannelButton` in its heading (R25).
  - The disk-space warning (80% and 95%, D-106): TOKI-103. This work leaves it an empty file that the page renders above the sections (R27).
  - The server: routes, rules, the record of actions: TOKI-024. The permission functions: TOKI-027. The API client and the conversation store: TOKI-032, which this work does not change, except for the one change request of R5 (the optional `headers` and `timeoutMs` of `request`). The generator of UUIDv7 ids, `newId`: TOKI-098 R1 and R2, which this work only calls (R5, concern 14). The shell, `SectionPage` and the section list: TOKI-015. Confirmation, Undo and the form guard: TOKI-093. The Toast, the base components, Menu and Modal: TOKI-012, TOKI-013, TOKI-014.
  - The More sheet that reaches the page on a phone: TOKI-092. This work gives its row `more: true` (R2).
  - The shared "not found or no access" page and loading skeletons: TOKI-082. This work draws its own small view and loading line, and TOKI-082 replaces their bodies (R4, R7).
  - The People page, where the role label also changes (F40): TOKI-079.
  - Analytics and Automations tabs of the Admin page (phase 5), a screen for the record of administrative actions (D-110: none in phase 1), permanent deletion of an account (BR-29).
  - The Activity item "Lan changed your role to Admin" and the live update of the changed person's screen (concern 5).

## Requirements
Route, gate and no-access view
- R1. `apps/web/src/routes/admin.tsx` exports `adminRoute`, a route with the path `/admin`, the parent `appLayoutRoute` (TOKI-015 R30), no search parameter, whose component is `AdminRoute` (R3). `src/router.tsx` adds it to the children of `appLayoutRoute`; nothing else of the router changes. The page is drawn inside the shell's `SectionPage` (TOKI-015 R12) with the title `t("nav.admin")` and, as its `actions`, the "Invite members" button (R21).
- R2. `apps/web/src/shell/sections.ts` gains one row, placed after `people` and before `preferences` (TOKI-099 R21 also adds a row; the order is the prototype's `SECTIONS`, line 1199: people, admin, prefs, so the order does not depend on which ticket merges first; a test reads the order of `visibleSections("admin")` ids): `id: "admin"`, `icon: "shield"` (the prototype's icon for Admin, line 1199, in the icon set of TOKI-011), `labelKey: "nav.admin"`, `to: "/admin"`, `match: p => p === "/admin" || p.startsWith("/admin/")`, `roles: ["admin"]`, `more: true`, and neither `tab` nor `calmHidden`. `visibleSections("admin")` holds it and `visibleSections("member")` and `visibleSections(undefined)` do not (TOKI-015 R36; F08, F39, D-090). The row is the only change this work makes to the shell.
- R3. Gate. `AdminRoute` reads the signed-in person (`id`, `role`) from the session state of TOKI-023 through the one React binding that `AppShellRoute` uses (TOKI-015 R36); this work adds no second binding. It calls `canOpenAdminPage({ id, role })` of `@toki/shared` (TOKI-027 R10). When the result is `allowed: false` it draws the view of R4 and sends no request to the server: a test with a fake client finds no call at all. When the result is `allowed: true` it draws the page of R6 to R27. The check only shapes the screen; the server repeats it on every request (BR-09, D-090). The role of the gate is the session's. `CreateChannelButton` of R25 reads the role from the conversation store (TOKI-098 R3, `useCurrentRole()`), a second source; after a role change (concern 5) the two may differ for a moment, in which case the "+" hides itself or is missing, which does no harm because the server refuses a Member's request. The heading of R25 does not depend on the button being drawn and does not check the role itself.
- R4. The no-access view. `apps/web/src/admin/NoAccess.tsx` renders, in the shell's `SectionPage`, with the title `t("admin.noAccess.title")` ("You do not have access to this page", journey F39) and nothing else: no member, no count, no channel, no word that names the page's content, not even the page's own title. A Member who types `/admin` sees it (AC-064, TS-100); an Admin sees it too when any request of this page is answered 403, so a person demoted while the page is open loses the page at their next action (R19). One shared view serves 403 and 404 in the whole app (D-131); TOKI-082 builds it and then replaces the body of `NoAccess.tsx`, keeping the file and its props (none). Until then this view is the one. Whether the view is drawn inside the app frame is concern 6.

Calls to the server
- R5. `apps/web/src/admin/adminApi.ts` exports one function for each route of TOKI-024, each calling `api.request` of TOKI-032 (R2: the request core of the client in `apps/web/src/client.ts`; R9 lists only the typed methods) with the response schema that `packages/shared/src/members/` exports (TOKI-024 R35) and the shared constants: `listMembers({ search?, status?, limit?, cursor? }, signal)` (`GET /members`, R21 to R25 there), `inviteMembers({ emails, role }, key, signal)` (`POST /invitations`), `resendInvitation(id, key)`, `revokeInvitation(id)`, `changeRole(userId, role)`, `deactivateMember(userId)` and `reactivateMember(userId)`. An empty `search` and an unset `status` are left out of the query.
  Dates are converted here, at the API boundary, and nowhere else. TOKI-024 R22 answers `lastActiveAt` and `invitation.createdAt` as ISO 8601 strings, while `formatDate` and `formatDateTime` of TOKI-094 take an `Instant`, a number of milliseconds (TOKI-094 R7: a value that is not a finite number gives `null`). `listMembers` returns rows in which both fields are `Date.parse` of the string, or `null` when the string is `null` or the result is not finite. The hook, the rows and R12, R13 and R30 hold and read numbers only; no component reads an ISO string.
  Two changes of the request core are needed and the client of TOKI-032 has neither: `request` takes the optional fields `headers`, which it adds to the request and which can never replace `Accept`, `Content-Type` or the credentials mode, and `timeoutMs`, which replaces `requestTimeoutMs` (default 10 000, D-126) for that one call. The two routes that send mail need `Idempotency-Key` (TOKI-024 R13) and may run longer than 10 seconds: a batch of 50 can take up to 30 s for a mail slot and 30 s for a send (TOKI-024 R13, TOKI-021 R15, R25). `inviteMembers` and `resendInvitation` pass `timeoutMs` of 75 000, above that bound with the database time of 50 addresses; every other function keeps the default. This is a change request to TOKI-032, which is pending its owner (concern 7); this work's build waits for it.
  The key is `newId()` of `apps/web/src/ids.ts` (TOKI-098 R2), the UUIDv7 generator `createUuidV7Generator` of `packages/shared` (TOKI-098 R1) fed by `crypto.getRandomValues`; it is 36 characters of `A-Za-z0-9-`, inside the 1 to 64 of `A-Za-z0-9_-` that the server takes. `crypto.randomUUID` is not used: it exists only in secure contexts and Toki is self-hosted (D-028), so an Admin may reach it over plain http on a LAN address, where pressing Send invitations would throw. `adminApi.ts` calls `newId` and no function of `crypto`; this work builds none of the generator and names TOKI-098 as a dependency for it (concern 14). The file adds no method to the client or the store of TOKI-032 and holds no state.

The member list
- R6. `apps/web/src/admin/useMemberList.ts` is the hook that holds the list: `{ rows, counts, activeAdminCount, status, isRefreshing, error, loadMore, reload, query, setQuery }`. The query is `{ search, status }`. On mount it asks the first page with no `limit` (the server's 50, D-109). Every answer is kept with `counts` and `activeAdminCount` of TOKI-024 R22 and R24. `status` is `loading` until the first answer, `ready` while data is held, `failed` when there is none and the request failed (the rule of TOKI-032 R10, so a refresh never empties the table). A request is aborted through its `signal` when a newer one starts, and an answer that arrives from an earlier request or an earlier query is dropped, so the table never shows the rows of an old search. Ordering (decided in this spec): a first page, a reload (R10) and a change of query each start a new generation; a reload or a first page aborts a load-more in flight, and the answer of a load-more that began before the latest reload or query change is dropped, so its rows are never appended to rows that replaced them with a cursor that no longer matches; of two reloads started in quick succession the later one wins and the earlier is aborted.
- R7. Search. The search box is `Field` with `variant="search"`, `icon="search"` and `aria-label` from `admin.members.search.label`, and the placeholder `admin.members.search.placeholder` (TOKI-012 R15 (b)). Typing sets the displayed text at once and the query's `search` after 300 ms without a key (decided in this spec: one request for each key press would load the server and flicker the table; a test with the clock moved shows one request for five key presses inside 300 ms). The text sent is trimmed. The filtering is the server's (case-insensitive; TOKI-024 R24): the page filters nothing itself, so the rows, the counts and the chips cannot disagree. The search text is not put in the address and is not stored (Data safety). While the first answer for a new query is awaited, the old rows stay and the table has `aria-busy="true"`.
- R8. Status chips (D-074, F39). A `ChipGroup` with `aria-label` `admin.members.filter.label` holds five `Chip`s in this order: All, Active, Invited, Expired, Deactivated (`admin.filter.all`, `admin.status.active`, `admin.status.invited`, `admin.status.expired`, `admin.status.deactivated`), each with its total after the label: `counts.active`, `counts.invited`, `counts.expired`, `counts.deactivated`, and for All their sum. `pressed` is true for the chip of the query's `status` (All when there is none). Pressing a chip sets the query's `status` to its value (All clears it) and asks the first page again. The totals are those of the last answer, which follow the search text and not the chip (TOKI-024 R24), so with any search text and any chip, the number on the chip equals the number of rows that pressing it shows (a test with a fake server that applies the same rule to 120 rows). A chip with a total of 0 is shown and can be pressed; the table then shows R14. Decided in this spec: Expired has a chip of its own (concern 9).
- R9. More on scroll (D-109). A sentinel element after the last row is watched with an `IntersectionObserver`. `useLoadMore` finds the nearest ancestor of the sentinel whose computed `overflow-y` is `auto` or `scroll` (the scrolling area of the shell's `SectionPage`, without a reference to it or a hook into it) and passes it as `root` with a `rootMargin` of 48 px at the bottom, so that the next page is asked a little before the sentinel is reached; when no such ancestor exists, `root` is `null` (the viewport) with the same margin. A root margin does not reach past an intermediate scrolling container when `root` is `null`, which is why the scroller is passed. When it comes into view, `nextCursor` of the last answer is not null and no page is being asked, the next page is asked with that cursor. A page is never asked twice for one cursor; with `nextCursor` null nothing is asked; the sentinel is also reachable by a keyboard-only person, because focus entering the last row asks the page too (the same rule as TOKI-034 R8). The rows of all pages are shown in order and each row once (a row is the same row when `kind` and `userId`, or `invitation.id`, are the same). While a later page is asked the table has `aria-busy="true"`. A page that fails keeps the rows and shows R19's retry line under the table.
- R10. Reload after a change. After any change that succeeded, or answered 409 or 404 (R19), `reload()` asks one page with `limit` equal to the number of rows now shown, no less than 50 and no more than 100 (the server's largest, TOKI-024 R21), with the same query and no cursor, and replaces the rows, the counts and `activeAdminCount` and the cursor. The scroll position is not set by the page. Reason: the server orders by name (TOKI-024 R23), so a change of role or status moves no row, but a status change moves a row out of a filtered chip, and one request of the size shown keeps the table as long as it was without asking every page again. A person with more than 100 rows loaded gets the first 100 after a reload, so the table is shorter and the view may jump up; this is accepted (a builder choice) and the person scrolls to get the rest again. A reload that starts while a load-more is in flight follows the ordering rule of R6.

The table
- R11. The table is a `table` with the class `adm-table` and one `thead` row of five `th`: `admin.col.name`, `admin.col.role`, `admin.col.status`, `admin.col.lastActive` and, visually hidden, `admin.col.actions`. The `tbody` holds one `tr` for each row of R6 in the server's order; the page sorts nothing (TOKI-024 R23). Its accessible name is the section's heading `admin.members.title`.
- R12. Name cell. An `Avatar` of TOKI-013 with `name` the display name, or the address for an invitation, and `hue` from `personHue(userId ?? email)` of TOKI-033 R28; then the name, or for an invitation the address, in bold; then the address (account rows only) in the muted small text; a `Tag` with `admin.row.you` beside the name on the signed-in person's own row. An invitation row has a second muted line `t("admin.row.invitedBy", { name, date })` with `invitation.invitedBy.displayName` and `date` from `formatDate(invitation.createdAt, ctx)` (R30; `createdAt` is a number, R5), which is F02's "the date and who invited them". Nothing in the row is a link: no part of the page leads to a profile, a conversation or a message (F39: nothing on the Admin page leads to message content).
- R13. Role, status and last active. The status cell is the label of the row's `status` (`admin.status.invited`, `expired`, `active`, `deactivated`), except that an invitation row whose `invitation.state` is `pending` and `mailStatus` is `failed` reads `admin.row.mailNotSent` instead of "Invited" (D-099, AC-067: after a batch where the mail failed halfway, three rows read Invited and seven read Mail not sent, each with Resend). An expired invitation reads Expired whatever its `mailStatus`. The status cell carries a text and the colour is never the only sign (D-067). The role cell is `common.role.member` or `common.role.admin` from the row's `role` (R28). The last-active cell is `formatDateTime(lastActiveAt, ctx)` (R30; `lastActiveAt` is a number, R5) for an account, and the glyph "—" when `lastActiveAt` is null or for an invitation row.
- R14. Empty and failed states. With no row for the query, the table body is replaced by `EmptyState` (TOKI-013 R15) with the icon `users`, the title `admin.members.empty.title` ("Nobody matches", the prototype's People empty state, line 1635) and the description `admin.members.empty.hint` (the prototype's description there is "Try a name or a job title."; an Admin's search is by name or address, so the hint is a proposal), centred in the content area (D-074). While the first answer is awaited the section shows `admin.members.loading` as a `role="status"` line. When the first load failed the section shows `admin.members.error`, the "Error ID" line of `admin.error.id` when the error has a `requestId` (D-131) and a `Button` `admin.error.retry` that asks again; for a `classifyApiError` result of `unreadable` it shows `admin.error.unreadable` and no retry. The same views, with the `channels` texts, serve the Channels list (R25).

Row actions
- R15. An invitation row (state `pending` or `expired`) has, in the last cell, two `Button`s of size `sm`: `admin.action.resend` and `admin.action.revoke`, shown whenever `canManageInvitations(actor).allowed` (TOKI-027 R11), and each named for its row by `aria-describedby` on the name cell, so a screen reader hears "Resend, Invited by ...". Resend and Revoke are on the row and not in a menu, as F02 says ("An 'Invited' row has two buttons"). An account row has an `IconButton` with `icon="more"`, size `sm`, `label` `t("admin.action.menu", { name })` that opens a `Menu` (TOKI-014 R17) made with `useMenuTrigger`, `aria-label` the same text, `align="end"`. The button is always drawn, never on hover (D-067). A person with a deactivated account and a pending invitation is an account row (concern 1).
- R16. The menu of an account row, for the actor `{ id, role }`, the target `{ id: userId, role, status }` and `activeAdminCount` of the last answer, is built only from the permission functions of TOKI-027; the page compares no role itself. For an active person it holds a `MenuGroup` with the heading `admin.action.changeRole` and two items, `common.role.member` and `common.role.admin`, where the item of the person's current role is disabled with the line `admin.lock.current` and the other item calls `canChangeRole(actor, target, thatRole, activeAdminCount)`; then a `MenuSeparator` and one item `admin.action.deactivate` (variant `danger`) that calls `canDeactivateAccount(actor, target, activeAdminCount)`. For a deactivated person it holds one item `admin.action.reactivate`, shown when `canReactivateAccount(actor).allowed`; decided in this spec: no Change role for a deactivated person, because the person comes back with the role they had and an Admin changes it afterwards (TOKI-024 R26, R30; F41). An item whose function answers `allowed: true` is enabled. `last_admin` makes it disabled with the reason `admin.lock.lastAdmin` ("Make someone else an Admin first", F40), and `self_target` with `admin.lock.self`. Any other result, `fact_missing` and `unknown_role` included, leaves the item out: a refusal that the page cannot explain never shows a control (TOKI-027, "the reason lets a screen choose"). On the actor's own row Deactivate is locked by `self_target`, and Change role is locked by `last_admin` only when the actor is the last Admin (concern 4).
- R17. A locked item is a `MenuItem` with `disabled` (TOKI-014 R18: `aria-disabled`, focusable, a press does nothing) and its reason is drawn inside the item as a second line of muted small text, so that the reason is on the screen for a touch user and is read with the item by a screen reader (D-067; TOKI-014 R20 lets the arrow keys reach a disabled item for this). The reason is never a `title` and never shown only on hover.
- R18. Confirmations (D-061, D-069, F40, F41, F02). Choosing Change role's item, Deactivate or Reactivate, or pressing Revoke, opens `ConfirmAction` (TOKI-093 R18) with the action id of Table A of that spec, the `target` and the texts of "The texts":

  | Action id | Opened by | `target` | `variant` | Question and confirm button | Request |
  | :---- | :---- | :---- | :---- | :---- | :---- |
  | `changeRole` | a role item | the person's display name | `primary` | `admin.changeRole.title` with `admin.changeRole.toAdmin` or `admin.changeRole.toMember` as the description (the new role and what changes), `admin.changeRole.confirm` | `changeRole` |
  | `deactivateMember` | Deactivate | the display name | `danger` | `admin.deactivate.title`, `admin.deactivate.description` (they are signed out everywhere, cannot sign in again, messages stay), `admin.deactivate.confirm` | `deactivateMember` |
  | `reactivateMember` | Reactivate | the display name | `primary` | `admin.reactivate.title`, `admin.reactivate.description`, `admin.reactivate.confirm` | `reactivateMember` |
  | `revokeInvitation` | Revoke | the address | `danger` | `admin.revoke.title`, `admin.revoke.description`, `admin.revoke.confirm` | `revokeInvitation` |

  The dialog's `returnFocusRef` is the button that opened it (the row's menu button, or the Revoke button). Closing it with Cancel, Esc or an outside press changes nothing and sends nothing (F40 "Closing the confirmation changes nothing"). The confirm button calls the request with `busy` true while it runs (D-111: a second press cannot reach it; TOKI-093 R7). A confirmation has no Undo (D-069: never both). When the offline gate of TOKI-093 R17 answers false the dialog stays open and the explanation shows (D-060, D-079).
- R19. Results of an action, one rule for all of R18, R20 and R22. On 200 the dialog closes, `reload()` runs (R10) and one plain toast shows the text of `admin.toast.*` for that action (`roleChanged`, `deactivated`, `reactivated`, `revoked`); focus goes back to the button that opened the dialog, and when the row has gone (a revoked invitation, or a row that left the chip's filter) to the heading of the members section, which has `tabindex="-1"` (TOKI-093 concern 6 leaves this to the call site). On a 409 with the code `last_admin`, `self_target`, `invitation_used` or `invitation_revoked`, and on a 404 (`not_found`, `invitation_not_found`), the page was out of date: the dialog closes, `reload()` runs and one plain toast shows `admin.error.stale`. The 404 is a choice of this spec, not a reading of D-131: D-131 gives 403 and 404 one shared page and 409 and 410 a fresh copy, and `classifyApiError` of TOKI-032 R8 returns `no_access` for a 404; but a 404 of an action on one row means that the person or the invitation has vanished, not that the Admin lost access, so the page takes the stale path and a 404 of an action never draws the no-access view. On a 403 the person is no longer an Admin and the view of R4 shows. On a 401 the session modal of TOKI-023 shows and the page does nothing more. On a 409 `request_in_progress` (the same key is still running on the server, TOKI-024 R13) the dialog stays open, its button is enabled again, the key of that press is kept, and one plain toast shows `admin.error.inProgress` ("still sending, try again in a moment"); a retry with the same key then meets the stored answer or the running claim. On any other 409 (`idempotency_key_reused`, which the key rule of R22 and R20 prevents, and so replaces the key), a 400, a 5xx, a timeout or a network error the dialog stays open, its button is enabled again, and one plain toast shows `common.error.actionFailed`, followed on a 5xx by `admin.error.id` when the error has a `requestId` (D-131, D-126); the person retries by pressing the button again, and the request is sent once for each press and never repeated by itself (TOKI-032 R6).
- R20. Resend (D-182, F02). Pressing Resend asks no confirmation and shows no Undo: this is the proposal of concern 13, not a decision (journey F02, taken as the baseline by D-091, says nothing of a confirmation; TOKI-093 concern 10 leaves Resend unclassified and names TOKI-025 as the owner of the answer). It calls the offline gate, then `resendInvitation(id, key)`; the button is disabled while the request runs and for no longer (D-111). Key rule, the same as R22 and TOKI-024 concern 6: the page keeps, in memory, one key for each invitation id that has a Resend in doubt; the key is made at the first press, the same key is sent again by the next press of the same invitation's Resend when the earlier attempt ended with a timeout, a network error, a 5xx or a 409 `request_in_progress`, and it is dropped (the next press makes a new one) after a 200 or a 409 `idempotency_key_reused`. So a lost answer never turns the retry into a second Resend, which would make a second token, kill the Join button of the mail that did go out (D-182) and send a second mail (D-111). The keys are dropped when the page unmounts. On 200 with `result` `invited` a plain toast shows `admin.toast.resent` with the address; with `mail_not_sent` it shows `admin.toast.resentNoMail`; the list reloads (R10), so the row reads "Invited" or "Mail not sent" as the server says. A failure follows R19, without a dialog.

The Invite members dialog
- R21. The button `admin.invite.open` ("Invite members", F02, F39) in the page's `actions` opens a `Modal` with the title `admin.invite.title`, `closeLabel` `admin.invite.close`, `returnFocusRef` the button, and the form of F02: a multi-line `Field` with `label` `admin.invite.emails.label` and a line under it `admin.invite.emails.hint` (commas or new lines); a `Select` with `label` `admin.invite.role.label` and the options `common.role.member` and `common.role.admin`, `member` first and chosen (D-153; the role the server takes is `member` or `admin`); and, as the `footer`, `Button` `common.cancel` and `Button` `variant="primary"` `admin.invite.send`. The dialog is a form with content, so it goes through `useFormGuard` of TOKI-093 (R20 to R23 there) with `hasContent` from `hasFormContent({ emails })`: an outside press does nothing, the close button and Cancel ask "Discard what you typed?" when there is text, and close at once when there is none (D-070, BR-21, AC-074, AC-075). The choice of a role alone is not content (TOKI-093 R19). Esc follows `GUARD_ESCAPE` of that spec.
- R22. Validation and send (D-104, D-111, F02). The text is split with `parseAddressList` of `packages/shared` (TOKI-024 R35) and each piece is checked with the shared address check (`packages/shared/src/email.ts`, TOKI-020 R16), the same check that the server uses (TOKI-024 R10). The error shows under the field, as one message, and never in a toast: the first piece that fails gives `admin.invite.error.invalid` with the piece as `{address}`, and more than `INVITATION_BATCH_MAX` (50) addresses gives `admin.invite.error.tooMany` with `{count}` 50; the list sent is the parsed list, so a repeated address counts once (TOKI-024 R5). "Send invitations" is disabled while the list is empty, while any piece is invalid, while there are more than 50, and while a request runs (F02: disabled "until every address is valid"). The role sent is the chosen one. A press calls the offline gate, then `inviteMembers({ emails, role }, key)`; while it runs both buttons are disabled and the dialog does not close on any reason. Key rule (TOKI-024 concern 6): the key is made at the first press; the same key is sent again for a retry when the earlier attempt ended with a timeout, a network error, a 5xx or a 409 `request_in_progress` and neither the text nor the role has changed since; it is replaced by a new one after a 200 and after any change of the text or the role. The request has the longer timeout of R5, so a slow but healthy batch of 50 does not time out at 10 s; if the answer is lost nevertheless, the retry meets either the stored 200 (no second mail) or `request_in_progress`. A 409 `request_in_progress` keeps the dialog open with the form as typed and shows, under the field, `admin.error.inProgress`. A 5xx, a timeout or a network error keeps the dialog open with the form as typed and shows, under the field, `common.error.actionFailed` and, with a `requestId`, `admin.error.id`. A 403 is R19. ## Design
### Where each part lives
The page is feature code of `apps/web`: it uses the client, the session, the permission functions, the texts and the patterns of TOKI-093, so it is not a `ui-web` component (the same reason as TOKI-034's dialogs). Nothing is kept in the conversation store of TOKI-032: the member list is the Admin page's own and is dropped when the page unmounts, so no other screen holds every person's address (Data safety). The hooks `useMemberList` and `useChannelList` and the helper `useLoadMore` are plain React with `useReducer`; no data library is added.

### The permission map
| Control | Function (TOKI-027) | Allowed | `last_admin` | `self_target` | Any other result |
| :---- | :---- | :---- | :---- | :---- | :---- |
| The page | `canOpenAdminPage(actor)` | page (R3) | none | none | no-access view |
| Invite members | `canInviteMember(actor, { role })` | button and dialog | none | none | button left out |
| Resend, Revoke | `canManageInvitations(actor)` | two buttons | none | none | buttons left out |
| Change role item | `canChangeRole(actor, target, role, count)` | enabled | disabled, `admin.lock.lastAdmin` | none | item left out |
| Deactivate item | `canDeactivateAccount(actor, target, count)` | enabled | disabled, `admin.lock.lastAdmin` | disabled, `admin.lock.self` | item left out |
| Reactivate item | `canReactivateAccount(actor)` | enabled | none | none | item left out |

The server repeats every check on every request (TOKI-024 R1, R27), so a page that is a little out of date is corrected by a 409 and a reload (R19), never by a wrong change.

### The Invite dialog's states
Form (R21, R22) -> sending (both buttons disabled, `busy`) -> results (R23) -> closed. From sending, a failure returns to the form with the typed text and the same key for a retry. From the form, Cancel or the close button with text asks the question of TOKI-093; with no text it closes.

### Errors
| Condition | Behaviour |
| :---- | :---- |
| The person is a Member (client check) | no-access view, no request (R3, R4) |
| Any request answered 403 | no-access view (R19) |
| 401 | session modal of TOKI-023 |
| List 5xx, timeout, network | section error, error ID when there is one, Retry (R14) |

| Offline | action blocked with `common.offline.blocked` (R18, R20, R22) |

## Data safety
- The page holds every person's email address and every invited address. They are held in memory by `useMemberList` only, are dropped when the page unmounts, and are not put in the address, in `localStorage`, in the conversation store or in a log. The search text is not put in the address, so it reaches no history and no `Referer`.
- No `console` call in `apps/web/src/admin` holds an address, a name, a key or an answer body. An `ApiError` is shown only through its kind, status, code and `requestId` (TOKI-032 R4); the address of a failed invitation is never put in an error text.
- The `Idempotency-Key` of the invite dialog and the keys of Resend (one for each invitation id) live in memory and are not stored. The code and the token of an invitation are never sent to this page: the server answers none (TOKI-024 R22).
- A Member's browser never asks for the list: the gate comes before the first request (R3), and the server refuses it anyway (D-090).
- The page leads to no message content, and an Admin sees no private channel or DM they are not in (F39, D-047; concern 3 is about which private channels the list holds).
- Nothing is deleted from this page: deactivation keeps messages and rows (BR-29).
