# Activity screen design

Date: 2026-11-25 · Status: draft for review (concerns 1 to 5 are open for the product owner)
Intent: docs/intents/activity-screen.md (Thanh Truong)
Ticket: TOKI-066

## Goal
The Activity server (TOKI-065) keeps, for each person, the things that need their attention, and tells every open screen when they change. A person cannot see any of it: the navigation has an Activity entry with no page and no number. This ticket builds the screen: the page with its filter chips and rows, the press of an item, "Mark all read", Done with Undo, Snooze and Unsnooze, the number on the navigation, the client store that keeps all of it right while other people act and while the connection comes and goes, and the labels, the hook and the menu body of the time choices that Activity and Later share.
The rules that must hold on the screen are D-074 (a count on a chip equals the rows shown), D-069 (Done happens at once and offers Undo for 5 seconds), D-067 and D-053 (Done and Snooze work on a phone with no hover), D-114 (a past time choice is not offered; "In 3 hours" takes its place) and D-079 (writes are blocked with an explanation while disconnected). The server decides what an item is, who has it and when a snoozed item wakes; the screen decides how it reads, looks and responds.

## Scope
- In:
  - The route `/activity`, the section row, the page frame and the chip row (R1, R2, R7, R8).
  - The client store `createActivityStore` of `packages/client-core`, its API methods, its handling of events and notices, the read of an item that arrives while its message is on screen, and its wiring (R3 to R6).
  - The row: its parts, its sentence for each of the six kinds, its time, and its press (R9 to R12).
  - The actions: Done with Undo, Snooze, Unsnooze, Mark all read (R13 to R16).
  - Done and Snooze visible without hover on narrow and touch screens (R17), the empty state (R18), the number on the navigation (R19), the loading, failed and offline states (R20), more rows on scroll (R21).
  - The time-choice labels, hook and menu body (R22), the texts (R23), the boundaries, the shared `.item` and `.udot` stylesheet that Later also uses, and what does not change (R24, R25), the tests (R26).
- Out (not now):
  - Everything on the server: the items, the routes, the events, the jobs (TOKI-065). What this screen needs from it that it lacks is in Plan changes.
  - The toast, push and sound for a new item and the toast "Back from snooze": TOKI-073 decides (its R12 makes the `back_from_snooze` notice and holds it for Pause and Focus), TOKI-075 draws it and TOKI-074 sends the push (TOKI-065, "What the later tickets get"). This screen shows the label "Back from snooze" on the row and draws no toast for it.
  - Later (saved messages and reminders): TOKI-067. It uses the labels, the hook and the menu body of R22 and builds its own page, store and badge.
  - How a message is opened, flashed and placed: TOKI-068 (`useOpenMessage`) and the pieces it names (TOKI-041, TOKI-045). This screen calls them (R12).
  - The unread counts of conversations, the read pointer and the tab title: TOKI-053 and TOKI-054. This screen gives the shell the Activity number only (R19).
  - "Catch up on everything" (a later phase, D-053 note), the kinds that belong to later phases (an approval request), the More sheet (TOKI-092), loading placeholders and the shared "no access" page (TOKI-082).
  - The notification preferences: TOKI-102. Nothing on this screen depends on a preference (D-174).

- R3. The store. `createActivityStore(options)` of `packages/client-core/src/activity/`, exported from the package index with its types. `options`: `api` (the methods of R4), `sync` (the engine of TOKI-040: `registerEventHandler`, `registerLiveHandler`), `conversations` (the store of TOKI-032, read for its `user` and its `status`) and the optional `isOnScreen(item)` of R5 (h). It takes no `clock` and no `timers`: nothing in it depends on the time of day (the view follows the state the server sends, R8, so a wake that happens while the page is open arrives as an event), and a requirement that is not used is not declared. It uses no DOM or browser global, no `Date.now(` and no `new Date()` (TOKI-008 R19), no timer and no key of `@toki/i18n`. It holds this state, replaced and never changed in place, read with `getState()` and `subscribe(listener)` (the shape of the other stores of the package): `status` (`idle`, `loading`, `ready`, `failed`: the state of the list), `filter` (one of `ACTIVITY_FILTERS` of TOKI-065 R2, `all` at the start), `items` (the `ActivityItem` objects of the chosen filter that are held, in the order of R8), `nextCursor` (string or null), `isLoadingMore`, `error` (the `ApiError` of the last failed load, or null) and `summary` (`{ unread, counts }` or null before the first answer). It has `setFilter(filter)`, `load()`, `loadMore()`, `refresh()`, the actions of R12 to R16 (`markRead`, `markMessageRead`, `markAllRead`, `markDone`, `reopen`, `snooze`, `unsnooze`), `attachConnection(connection)` (R6) and `reset()`. The store follows the conversation store as the engine of TOKI-040 R19 does: when that store holds a `user` and is `ready` and this store is not started for that person, it starts (reads the summary of R4; the list is read when `load()` is called by the page); when the user changes or the state returns to `idle` it resets (state back to the start, requests in flight aborted and their answers ignored by a generation number, nothing kept). No caller starts or resets it by hand. Check: with fakes, the store becoming `ready` with a user makes one summary request and no list request; `load()` makes one list request for the chosen filter; a store `reset()` and a second person's start leave no item, no summary and no pending answer; a late answer after a reset changes nothing; a package test finds no DOM reference and no use of the clock functions named above, and that `options` has no `clock` or `timers`.
- R4. The API methods. `createApiClient` gains `api.activity` with `list(query?, signal?)`, `summary(signal?)`, `read(body, signal?)`, `done(id, signal?)`, `reopen(id, signal?)`, `snooze(id, until, signal?)` and `unsnooze(id, signal?)`, on the seven routes of TOKI-065 (`GET /activity` with `filter`, `limit` and `cursor` only when given; `GET /activity/summary`; `POST /activity/read` with exactly one of `{ itemIds }`, `{ messageId }`, `{ all: true }`; `POST /activity/{id}/done`, `/reopen`, `/snooze` with `{ until }`, `/unsnooze`), with the rules of TOKI-032 R9 (one request core, 10 seconds, no retry, the path part encoded, an optional `signal` last). TOKI-065 R2 names `ActivityListResponseSchema`, `ActivitySummarySchema` and `ActivityItemStateSchema` and no schema for the answers of the other five routes, so `client-core` builds the two wrappers itself from `ActivityItemStateSchema`: `{ states: ActivityItemState[] }` for `read` and `{ state: ActivityItemState }` for `done`, `reopen`, `snooze` and `unsnooze` (TOKI-065 R18 to R20). Every answer is read in the form that drops unknown keys (TOKI-032 R3). No change to TOKI-065 R2 is needed. The screen asks for the server's default page size (`ACTIVITY_PAGE_DEFAULT`). Check: with the fake `fetch` of the existing tests, each method sends the method, path, query and body as written and parses a good answer; the list request has no `limit` or `cursor` unless given; a body with two keys is not built by `read` (the type allows one); an answer with an added key keeps working, also inside a wrapper; an error answer ends as an `ApiError` of the existing kinds.
- R5. Events and notices. The store registers, in `createActivityStore` and through the seams of TOKI-040 R18, `registerEventHandler("activity.upserted", …)`, `registerEventHandler("activity.removed", …)` and `registerLiveHandler("activity.changed", …)` (TOKI-065 R14, R23). The store keeps a map of the held items and a memory of ids (at most 500, oldest first out, dropped at `reset()`): an id is remembered as removed with the event's number, or as done with a version (R13). Rules, applied in this order for each: (a) An item or a state is applied only when its `version` is higher than the held version of that id; an equal or lower one changes nothing, so an event and a notice arriving in either order give one result (TOKI-065 R23). (b) `activity.upserted` sets the item in the map and puts it in or takes it out of the chosen view by the rule of R8; an item of the chosen view that is not held and whose position is after the last held item while `nextCursor` is not null is not inserted (it comes with a later page). (c) `activity.removed` drops each id from the map and from the view and remembers it as removed with the event's number. (d) `activity.changed` applies each state to the held item: `done` true removes it from the view and the map; `unread`, `snoozedUntil` and `backFromSnooze` are set; the view is recomputed by R8. A state for an item that is not held makes the store call `refresh()` (the notice says "read the list again", TOKI-065 R23), unless the id is in the memory: remembered as removed, or as done by this tab, the state being `done` true or its version not higher than the remembered one. The notice of the person's own action reaches every connection of the person, this tab included (TOKI-065 R23), and R13 records the id as done at the moment of the action, so the echo of the person's own Done, and the answer to its request, are recognised and cause no `refresh()` and no loss of the rows loaded beyond the first page. (e) After any of the three, the store reads the summary again (R6, one request at a time). (f) A list or summary answer carries `asOf`: an item of an answer is dropped when its id is remembered as removed with a number above that `asOf`, or as done with a version equal to or above its own, so an answer read before an event does not bring back what the event removed; a held item whose version is higher than the answer's keeps its held copy. (g) The store never decides by the time of day that an item has come back. The server builds the returned form (TOKI-065 R15, R16: `snoozedUntil` null, `backFromSnooze` true, `occurredAt` the sort time) in every list and every event, so the wake arrives as an `activity.upserted` event that moves the item from the snoozed view to the top of the main view by R8, and a late wake job changes the screen no later than the server's own read would. (h) An item that arrives while its message is on screen is read at once (the hand-off of TOKI-065, "What the later tickets get", F13, taken here): when `activity.upserted` gives an item that is not held, with `unread` true, `backFromSnooze` false and `kind` `mention` or `thread`, and `options.isOnScreen(item)` is true, the store calls `markMessageRead(item.messageId)`, which sends `{ messageId }` (R12). `apps/web/src/client.ts` makes `isOnScreen` from the view state of TOKI-073 R19 (`get()`: `inUse`, `conversationId`, `threadRootId`, `atBottom`): the window is in use, the item's `conversationId` is the one on screen and, for an item with no `parentId`, the person is at the bottom, and for a reply `threadRootId` equals its `parentId`; with no such state built, `isOnScreen` is absent and the rule does nothing. Whether any other trigger reads an item is concern 3. Check: a table test with the reducer, for each of (a) to (h): an upsert with a lower version is ignored; an upsert for an unseen item at the top of the chosen view appears first; an upsert that arrives for an item older than the last held row with a cursor open is not inserted; a removal and then an older list answer leaves the item out; a state with `done` true removes the row; a state for an unknown item calls `refresh` once; the same notice applied twice leaves one result; Done, then the same notice and the answer: no `refresh` and the second page still held; a state for an unknown item that this tab did not make done calls `refresh`; every kind of change calls the summary read once however many events come together (R6); an item with `snoozedUntil` in the past by the test's own clock stays in the snoozed view until its wake event comes, and the event moves it to the top of the main view; a new mention with `isOnScreen` true sends `{ messageId }` once, with it false or absent sends nothing, and a `backFromSnooze` item or a reaction sends nothing.
- R6. The summary and keeping it right. The summary is `{ unread, counts }` of `ActivitySummarySchema` and is what the navigation badge and the "Snoozed · n" chip read. `counts[filter]` is the number of rows that the list of that filter holds when read to its end (TOKI-065 R17, D-074); a row that is read is still a row, so reading an item changes no count. `unread` is the number of unread rows of the main list (the badge, AC-108); snoozed and done items are not in it. The summary is read from the server: at the start (R3), after every event or notice of R5, when the connection's `status` becomes `online` after a time it was not (the first `online` after the page loaded is skipped, as TOKI-053 R17 does), and after a failed read at the next of these moments. At most one read is in flight and one queued, however many things ask. An answer replaces the held summary when its `asOf` is not lower than the held one; a lower one is ignored. At the same moments, when the list has been loaded, the store also calls `refresh()` after an `online` that follows a loss, because events of the lost time are replayed by TOKI-039 but a replay that was refused as expired ends in a reload of the engine, which gives no event; `refresh()` reads the first page of the chosen filter again and keeps the loaded rows until the answer comes. The store has its own `attachConnection(connection)` taking the object of TOKI-039 R15 (`getState()` with a `status`, `subscribe(listener)`) and returning a remover; the engine's `sync.attachConnection` offers no state getter, which is why TOKI-053 R17 has its own. Local changes move the numbers at once and the answer replaces them, by what the action does to the item: read (R12, R16) lowers `unread` by one for each unread item it reads and changes no count; Done (R13) takes the item out of `unread` when it was unread and lowers `counts.all` and the count of the filter of its kind by one; Undo puts the same numbers back; Snooze (R14) does what Done does and raises `counts.snoozed` by one; Unsnooze (R15) does the reverse and, the item returning unread, raises `unread` by one. The badge therefore falls when the person presses Done and not one round trip later, and a count never differs from the rows it names. Check, with a fake connection: going `offline` then `online` makes one summary read and one list `refresh`, and the first `online` after the start makes none; ten events together make one read and one queued; an answer with a lower `asOf` is ignored; pressing an unread row lowers `unread` and no count while the row stays; pressing Done on a held unread item lowers `unread`, `counts.all` and the count of its kind at once and the answer then replaces them; Snooze moves one from `counts.all` to `counts.snoozed`; a failed read changes nothing and the next moment repeats it.
- R7. The chips. The chip row is a `ChipGroup` of TOKI-012 with the accessible name `t("activity.filters")`, holding one `Chip` for each of `all`, `mentions`, `threads`, `reactions` and `other` in this order, with the texts `activity.chip.*` (R23), and, after them, `snoozed` with the text `t("activity.chip.snoozed", { count })` only while `summary.counts.snoozed` is above 0. The chosen chip has `aria-pressed="true"`, the others `"false"`; `all` is chosen when the page opens; the chosen filter is state of the page and not of the address (the prototype, `S.actFilter`). A press calls `setFilter`. When the chosen filter is `snoozed` and the count falls to 0, the filter becomes `all` and the chip is gone (the prototype's line 1550; AC-113). The five chips are drawn whatever the counts, so a kind with no item is still reachable (D-071, AC-110). The three kinds of `added_to_channel`, `role_changed` and `message_deleted` are under the chip `other` (`activityFilterOfKind` of TOKI-065 R2; F27, AC-110); its name is concern 1. The chips other than `snoozed` show no number (concern 2). Check: a render test finds the six chips in that order with and without a snoozed item (five without), `aria-pressed` on the chosen one only, the press calling `setFilter` with the id, and the fall back to `all` when the last snoozed item is unsnoozed; the chip texts come from the catalogue in both languages.
- R8. The view and its order. The store keeps one view, that of the chosen filter. `setFilter(filter)` makes the view empty and `loading` for the new filter and reads its first page with `api.activity.list({ filter })`; an answer for a filter that is no longer the chosen one is ignored. A held item belongs to the view of a filter by the state the server sends and by nothing else: for `all`, `mentions`, `threads`, `reactions` and `other`, it is not done, `snoozedUntil` is null and `activityFilterOfKind(kind)` is the filter (or the filter is `all`); for `snoozed`, it is not done and `snoozedUntil` is not null. The store reads no clock for this, so the rows and the counts, which the server computes with its own clock, cannot differ by the skew between two clocks (D-074). An item whose wake time passes while the page is open stays under "Snoozed", and the count of the chip stays, until the wake event of TOKI-065 R21 arrives (R5 (g)); a reconnect or a `refresh` reads the server's returned form at once. The order is the one of the server (TOKI-065 R16): for the main views `occurredAt`, which for a returned item is the server's sort time, newest first and then the id in code-point order, descending; for `snoozed`, `snoozedUntil` earliest first and then the id. A page is added after the held rows (`loadMore`, R21) and the answer replaces the first page on `refresh()`. Check: with a fixture of every kind and state, each view holds exactly the items the rule says, in the order said, for the six filters (the fixture has two items of one time, ids in both orders); a mention at 10:00 and a reaction at 10:01 give the reaction first (TS-170); the chip `other` holds the three kinds and no other (TS-174); a snoozed item is in `snoozed` and not in `all`; a returned item (`snoozedUntil` null, `backFromSnooze` true, `occurredAt` the wake time) is the first row of `all`; each count of the summary equals the length of the view read to its end, a read row counted (D-074); with a test clock that runs ahead of and behind the time in the fixture the views and the counts are the same.
- R9. The row. A row is a `div.item.activity-item` with `role="button"` and `tabindex="0"` (`.item` is the prototype's row, defined once in the shared stylesheet of R24 that the Later row of TOKI-067, `div.item.later-row`, also uses; `activity-item` carries what only Activity needs), with the class `un` while the item is unread and shown in the main list. In order: the unread dot with the accessible name `t("activity.row.unread")` or `t("activity.row.read")` (the dot is drawn transparent when read, the prototype's `.udot.off`); the `Avatar` of TOKI-013 of the actor (the name and `personHue` as the rest of the app); a block holding the sentence (R10) and under it the meta line `{conversation} · {time}` (R11), followed, in the snoozed view, by the clock icon and `t("activity.row.back", { when })` with `when` the `snoozedUntil` through `formatDateTime` of TOKI-094 R5 (the prototype's "back" text, `fmtAt`; Table A row 3 of TOKI-094), and, when `backFromSnooze` is true, by `t("activity.row.backFromSnooze")`; and, at the end, the buttons of R13 to R15. A row of the snoozed view draws no unread dot (the transparent one) and no `un` class, whatever its `unread`: an unread item that is snoozed keeps `read_at` null (TOKI-065 R20) and is not in the `unread` of the summary, and the prototype sets `unread` false when it snoozes (line 2418), so the dot would count something the badge does not. `{conversation}` is read from the conversation store: `getConversation(id)` gives the `kind`, and `getConversationName(id)` the bare name (`packages/client-core/src/conversations/names.ts`); the row writes `#` before the name for a `channel` (the prototype's `cname`) and the name alone for a direct message or group (the other person's or people's names). When the item has no `conversationId` (`role_changed`), or the store does not hold the conversation (left, archived: the name is `""`), the meta line is the time alone and the sentence is built without the conversation (R10). The actor's name is the `displayName` of `getPerson(actorId)`; a person the store does not hold gives the sentence with no name part and the avatar with no initials, and never throws. An unread row's name is drawn in the ink colour (the prototype's `.item.un b`). Enter and Space on the focused row do what a press does (R12); a press of a button of the row does not. Check: a render test of each part and of its order for an unread, a read, a snoozed and a returned item; a snoozed unread item has no dot and no `un` class; an item with an unknown actor renders; a channel shows `#name`, a direct-message conversation shows the other person's name; an item whose conversation is not held shows the time alone; `role_changed` shows no conversation; Enter and Space on the row call the press once and a click on Done calls only Done.
- R10. The sentence of each kind. The sentence is one translated text per kind and shape, with the actor's name in bold before it (the prototype's `<b>name</b> text`), built only from the item's data and the conversation store, never from text the server sends (TOKI-065 sends no wording). The i18n package picks a plural form by `count === 1` (`one`) and every other value (`other`), and Vietnamese has only `other` (TOKI-017 R6), so a text with three shapes is two keys, chosen by the code. `mention` with `viaChannel` false: `activity.sentence.mention` with `{ preview }`; `mention` with `viaChannel` true: `activity.sentence.mentionChannel`, no parameter, followed by the clause below (the prototype's item `a6`, line 1050, reads "mentioned the team and you in #general": the text, then " in #general"; D-139, concern 4); `thread`: `activity.sentence.thread` with `{ preview }`; `reaction`: with `actorCount` 1, `activity.sentence.reaction` with `{ emojis }`, and with `actorCount` above 1, `activity.sentence.reactionMore` with `{ emojis, count }` where `count` is `actorCount` minus 1 (at least 1, so `one` is "and 1 other" and `other` is "and N others"); `emojis` is the item's `reactions.emojis` joined with a space; `added_to_channel`: `activity.sentence.added` with `{ conversation }`; `role_changed`: `activity.sentence.role` with `{ role }`, the word `common.role.member` or `common.role.admin` from the item's `role`; `message_deleted`: `activity.sentence.deleted`, followed by the clause. The clause is `activity.sentence.in` with `{ conversation }` ("in #general"), joined by one space after `mentionChannel`, `reaction`, `reactionMore` and `deleted`, and left out when the conversation is not held (R9). `added_to_channel` with no conversation held uses `activity.sentence.addedNoConversation`. A `preview` that is `null` (the message could not be read, TOKI-065 R15) uses the key with the suffix `NoText` (`mentionNoText`, `threadNoText`) that has no quoted text; a channel mention quotes no text and needs none. A long preview is cut by the layout to two lines (`-webkit-line-clamp`), not by the code. The wordings are in R23; the ones the prototype draws (mention, thread, reaction with one person, and the channel mention) are its own words, and the others are proposals (concern 4). Check: a table test renders each kind and shape in `en` and `vi` and reads the text; a reaction with `actorCount` 1 uses `reaction`, with 2 uses `reactionMore` with `count` 1 and its `one` form in English ("and 1 other"), with 4 uses `count` 3 and its `other` form, and in Vietnamese both use the one `other` text; a null preview gives the `NoText` text; the channel mention reads "mentioned the team and you in #general" for the prototype's data; an item whose conversation is not held has no "in" clause and `added` reads the no-conversation text; no text comes from the item's own strings except the preview.
- R11. The time of a row. The time in the meta line is `formatTime(occurredAt, timeZone)` of TOKI-094 R1 (Table A row 1 gives "Activity item time" the 24-hour form) when `occurredAt` falls on today in the zone of the date context, and `formatDateTime` otherwise (concern 5, a proposal for the item of another day; the prototype's item `a6` shows "Yesterday"). The date context is `useDateContext()` of `apps/web/src/account/use-date-context.ts` (TOKI-099 R15, the file that TOKI-067 R23 also names; the two other copies, `admin/useDateContext.ts` and the inline one of TOKI-035, are not used here). Its `now` is the one clock of `apps/web/src/clock.ts` and its zone is the one the app gives (TOKI-094 concern 2; concern 10 here). `features/activity/deps.ts` re-exports it and `time-choices/` (R22), which is a folder of the app and not a feature, imports the file directly. The `<time>` element carries the ISO value in `dateTime`. No other code in the feature formats a date or a time (TOKI-094 concern 6). ### The store in one picture
```
server --activity.upserted / activity.removed (numbered events)--> sync.registerEventHandler --\
server --activity.changed (the person's own marks, unnumbered)---> sync.registerLiveHandler  ---+--> reducer (version rule) --> view + summary --> page, badge
page   --press, Done, Snooze, Unsnooze, Mark all read--> optimistic change at once --> api.activity.* --> state answer --> reducer
connection online again / a state for an unknown item --> refresh the first page, read the summary
```
Two ways in, one rule: every change is applied only when its `version` is higher than the held one (R5 (a)), so the numbered event that another person causes, the notice of the person's own mark from another tab or from this one, and the answer to the person's own request give the same result in any order. A summary is read again after any of them, one request at a time, and its counts are row counts, so the numbers on the chips equal the rows and the badge equals the unread rows (D-074). An action changes the screen first and the server second, as D-069 asks for Done ("at once"), and a failed request restores what it changed. The store reads no clock: a wake while the page is open arrives as an event (R5 (g)).

## Data safety
- The store holds items (ids, a preview of message text, times) in memory only, for the signed-in person, and drops them at `reset()` (R3): nothing is written to storage, the address or a log.
- No text of a message or a preview is written to a log or sent anywhere but the person's own screen; the item reaches the screen only from the person's own routes and events (scope `user`, TOKI-065 R14, R24).
- The press sends an item id or a message id to the server and nothing else; nobody sees who has read or marked an item (D-048).
