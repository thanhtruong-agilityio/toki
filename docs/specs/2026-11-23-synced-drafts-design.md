# Synced drafts design

Date: 2026-11-23 · Status: draft for review (concerns 1, 2 and 3 are open for the product owner)
Intent: docs/intents/synced-drafts.md (Thanh Truong)
Ticket: TOKI-051
Needs: TOKI-043 (the composer: `DraftStore`, the keys `conversation:<id>` and `thread:<rootId>`, the browser store with the person's id inside; PR 217).
Also uses, without them being in the plan line: TOKI-036 and TOKI-037 (the `messages` module, where the table and the routes of this work live, R1 and R6), TOKI-099 (`registerBeforeSignOut`, PR 207 line of `account-menu-devices`), TOKI-039 (the connection and its state; PR 210), TOKI-038 (`publishLive`, merged), TOKI-037 (the access steps of a conversation route and the revised `listConversationSummaries` of its R19, merged as a spec), TOKI-033 (the conversation list, merged), TOKI-032 (API client, `classifyApiError`, `Timers`), TOKI-018 (platform storage).

## Goal
The composer keeps what a person has typed and not sent, one text for each conversation and one for each thread, but only in the browser. Journeys F06, F07 and F11 and FR-38 say more: the text is saved to the person's account, is back on their other devices, survives a sign-out, is cleared when the message is sent, and the conversation list shows "Draft" on a conversation that has one and is not open.
This work builds the server copy and everything around it: the table and three requests (save, remove, list) in the `messages` module, one live notice to the person's other open devices, the client store that saves after a pause in typing, keeps a list of what is not yet saved, merges the server's drafts when the app starts and when the connection returns, applies the notice, saves before Sign out, and the "Draft" label in the list. The composer is not changed: TOKI-043 R18 made `DraftStore` the seam, and this work puts a store of the same type behind it.

  - The shared shapes and limits (R2).

  - The API methods (R8) and the synced store with its journal, saving, merging and live apply (R9 to R12).
  - The task before Sign out, the wiring and the person-change rules (R13, R14).
  - The "Draft" label of a conversation row: the data, the text, the style (R15).
  - Logging and size (R16), the contract (R17).
- Out (not now):
  - The browser store, the keys and what the composer does on send: TOKI-043 (R9, R10, R18). This work does not edit them; the only change to the controller is the one of R12, asked of TOKI-043 in Plan changes.
  - The thread panel and its box: TOKI-045. A thread has no "Draft" label of its own (concern 8). The one change to the controller that the composer and the thread box share is made here (R12).
  - Attached files in a draft: never kept (D-168). Mentions or formatting in a draft are plain characters of the text.
  - The refusal of a sign-out while offline and the 10 000 ms limit of the tasks: TOKI-099 (R7, R8).
  - Showing the offline state: TOKI-082. A failed or waiting save shows nothing (R9).
  - How long a draft is kept, who wins when two devices edit one draft, and what happens to a draft of a conversation the person left: concerns 1, 2 and 3. The build follows the proposals written there, in one place each.
  - Unread counts and the read pointer: TOKI-053. The bootstrap call: TOKI-031 (its R12 keeps drafts out of the answer, so the list of drafts is a request of its own, R5).

## Requirements
The server
- R1. The table `drafts` and its migration, made with `pnpm db:generate --name drafts` (TOKI-019 convention 8). The table is declared in `apps/server/src/modules/messages/schema.ts` with the other tables of the Messages group (the technical design lists `drafts` there with `messages`, `reactions` and `thread_followers`; the server has no 15th module). Columns, exactly these: `workspace_id` (uuid, not null), `user_id` (uuid, not null), `kind` (text, not null, `drafts_kind_check`: `'conversation'` or `'thread'`), `target_id` (uuid, not null: the conversation id for `conversation`, the root message id for `thread`), `conversation_id` (uuid, not null: the conversation of the draft, equal to `target_id` for `conversation`), `body` (text, not null, `drafts_body_check`: `char_length(body) between 1 and 100000`), `updated_at` (timestamptz, not null, written by the server, R3; no database default, TOKI-005 convention 3). Primary key `drafts_pkey` (`user_id`, `kind`, `target_id`): one draft for each person and place. Every key refuses to delete the row it points to (`ON DELETE RESTRICT`, as TOKI-036 R9 and TOKI-019), no key cascades, and each is named `<table>_<column>_fkey`: `drafts_workspace_id_fkey` to `workspaces.id`, `drafts_user_id_fkey` to `users.id`, and `drafts_conversation_id_workspace_id_fkey` from (`conversation_id`, `workspace_id`) to (`id`, `workspace_id`) of `conversations` through `conversations_id_workspace_id_key` of TOKI-028, so a draft cannot name a conversation of another workspace. The keys that leave the module are written as SQL in the migration (a schema file may not import another module's table, TOKI-019 convention 6; TOKI-036 R9 does the same). There is no foreign key to `messages`; the root of a thread is checked by R6. Conversations and users are never deleted (TOKI-036 R22 and the account tables), so no draft is deleted by a cascade; a draft goes by R4 only. The one-`TRUNCATE` test of TOKI-028 R23 names `drafts` in its list (Plan changes). Check: a database test applies the migration to an empty database; `information_schema` shows exactly the seven columns above with their types and nullability; it inserts a conversation draft and a thread draft; it refuses a second row with the same primary key, an empty `body`, a `body` of 100,001 characters, a `kind` of `"x"`, an unknown workspace, an unknown user, an unknown conversation and a conversation of another workspace, and each error names its key; `pg_constraint` shows every foreign key of the table with `ON DELETE RESTRICT` and the names above; a delete of a user who has a draft is refused; the one-`TRUNCATE` test of TOKI-028 R23 with `drafts` added passes.
- R2. `packages/shared/src/drafts/` (exported from the package index) holds: `DRAFT_TEXT_MAX` = 100000 (code points, counted with `Array.from(text).length`, never `.length`; the number is the cap of the browser store of TOKI-043 R9, which says "characters" and is asked to say code points and to use this name, concern 7); `DraftKeySchema`, a string that is `conversation:` or `thread:` followed by a lower-case UUID, with `parseDraftKey(key)` returning `{ kind, targetId }` or `null`; `DraftChangeSchema`, the strict object `{ key, text, updatedAt }` where `text` is a string or `null` (null means "removed") and `updatedAt` is an ISO 8601 time with milliseconds; `DRAFT_LIVE_TEXT_MAX` = 10000 (code points; R7) and `DraftNoticeSchema`, the strict object `{ key, updatedAt, text? }` where `text` is a string of at most `DRAFT_LIVE_TEXT_MAX` code points, `null`, or absent (absent means "changed, read it", R7, R12); `SaveDraftBodySchema` = strict `{ text }` where `text` is a string of 1 to `DRAFT_TEXT_MAX` code points (counted with `Array.from(text).length`, never `.length`), with at least one character that `String.prototype.trim` does not remove, without U+0000 and with `text.isWellFormed()` true (the reasons of TOKI-037 R4: the database cannot store the first, and the second would be stored as U+FFFD); `SaveDraftResponseSchema` = `{ draft: DraftChange }` with a string `text`; `RemoveDraftResponseSchema` = `{ draft: DraftChange }` with `text` null; `ListDraftsResponseSchema` = `{ drafts: DraftChange[] (text never null), readAt }`. The live frame schema `draftNoticeLiveFrameSchema` is in `packages/shared/src/realtime/drafts.ts` (R7). Check: schema tests for each; a text of 100,000 emoji outside the Basic Multilingual Plane is accepted and 100,001 refused; a text of only U+00A0 and tabs is refused; a key with an upper-case id, with another prefix or with extra text is refused.
- R3. `PUT /api/v1/drafts/{kind}/{id}` (`kind` is `conversation` or `thread`) takes `SaveDraftBodySchema` and answers 200 `SaveDraftResponseSchema`. It needs a valid session (TOKI-022 R24). After the access steps of R6 it reads the clock of TOKI-008 once, as the last step before the statement, and runs one statement, `insert ... on conflict (user_id, kind, target_id) do update set body = excluded.body, updated_at = greatest(excluded.updated_at, drafts.updated_at + interval '1 millisecond') returning body, updated_at`. The statements of one key queue on the row lock and the later statement sees the committed row, so the later statement is the later save and its time is always later than the time it replaced, even when the request that read the earlier clock commits second (two saves that read the clock at .100 and .200, the second committing first, leave the text of the second statement with a time after .200). The answer holds the stored text and time (concern 2). The same text sent again is stored again with a new time (no comparison). The text is stored as sent: no trim, no change of line breaks. After the statement has completed, and only then, the route calls R7. A blank text is 400 `validation_failed` (the client removes instead, R9). Check: a save returns the stored text and time and the row holds them column by column; a second save by the same person replaces the text and moves the time; with the controllable clock set back, a second save still gets a time later than the first; two saves held on two connections so that the one that read the earlier clock commits last store its text with a time later than the other's; a body key `updatedAt` is 400 because the body is strict; text with a trailing line break is stored whole; two saves by two people for the same conversation make two rows.
- R4. `DELETE /api/v1/drafts/{kind}/{id}` answers 200 `RemoveDraftResponseSchema` and deletes the person's row for that place. It is idempotent: when there is no row it still answers 200, with the time of the request. The statement is `delete ... returning updated_at` and the time of the answer is the later of the clock read just before it and the time of the deleted row plus 1 millisecond, so a removal is always later than the save it removes. A save and a removal of one draft made by two devices in the same millisecond can still leave them with different views until the next change of that draft; this is accepted. It runs the same access steps as R3 and calls R7 after the statement, also when no row existed (another device may hold the text). Check: removing an existing draft deletes the row; a second removal answers 200 and the row count stays at zero; a removal never touches another person's row for the same place.
- R5. `GET /api/v1/drafts` answers 200 `ListDraftsResponseSchema`: every draft of the signed-in person whose `conversation_id` is a conversation that the person is a member of and that is not archived, in any order, with `text` the stored body and `readAt` the time of the request from the clock. It is two reads in one request, with no lock: `listConversationSummaries(db, workspaceId, userId, { listLastMessageTimes })` of the `conversations` module in the form of the revised TOKI-037 R19 (the fourth argument is the `listLastMessageTimes` of this same `messages` module, so no wiring by `app.ts` is needed), then one statement on `drafts` with `user_id = $1 and conversation_id = any($2)`. A direct message that has no message yet is not returned to the person who did not create it (TOKI-037 R19), so a draft there is not returned either until its first message; the person cannot have opened it from the list before. There is no paging: a person has at most one draft for each conversation and each thread they started and the rows are small, and the answer is bounded by the 100,000-character limit of each body and by the number of places (concern 5). Check: a person with three drafts gets three; another person's draft is not returned; a draft of a private channel that the person has left, and of an archived channel, is not returned and its row stays (concern 3); a draft in a hidden direct message is not returned to the person who did not create it; a person with none gets an empty list and a `readAt`; a request with no session is 401 and reads nothing; the call passes four arguments to `listConversationSummaries`.
- R6. Access and refusals. The routes are in the `messages` module and reach the other modules only through their `index.ts` (TOKI-002 rules 2 and 17: `getConversationFacts`, `canReadConversation` and `listConversationSummaries` of `conversations`). Both mutations run, in order: (1) the schemas of the path and the body (400 `validation_failed`; a `kind` other than the two, an id that is not a lower-case UUID, an unknown key in the body); (2) for `conversation`, `getConversationFacts(db, actor.id, id)`; `null`, and a private channel, a `dm` or a `group_dm` of which the actor is not a member, are 404 `not_found` before anything else, so a private conversation is never confirmed (BR-10, D-051); for `thread`, the conversation of the root is found with `findThreadRoot(db, workspaceId, messageId)`, a function of this ticket in `modules/messages/drafts.ts` that is not exported (the module is the owner of the table of messages, so it reads it directly; no other module needs it, and the export test of `messages` gains only the route registration of R14): one statement, `select conversation_id, parent_id, kind from messages where id = $1 and workspace_id = $2`, returning `{ conversationId: string; parentId: string | null; kind: "user" | "system" }` or `null`; `null`, a message with a `parentId` (a reply is not a thread root) and a message whose `kind` is not `user` (a system line) are 404 `not_found`; a deleted root is accepted, as TOKI-045 R6 answers for one; then the facts of that conversation as for `conversation`; (3) `canReadConversation` (TOKI-027 R5): a person who has not joined a public channel is 403 `forbidden` (D-116). Nothing else is checked: a draft is the person's own text, the right to keep it is the right to read the place, and the composer decides when it is drawn (the read-only notice of a direct message, the missing composer of an archived channel); so a save into an archived channel or a read-only direct message is 200 (the client must never be left with an unsaved key that a 409 would block). The actor is always the account of the session; no route takes a user id. No role is compared (TOKI-027 R16). Check: a table test sends each case to each mutation and checks status and code, a positive case for each kind (a public channel, a private channel, a direct message, a group, a thread root), a person who is not in the private channel gets 404 whatever the body, a member of an archived channel saves 200, a reply id as the root is 404, a system line as the root is 404, an unknown root is 404, a root of another workspace is 404, a deleted root is 200, `findThreadRoot` returns the three keys and `null` for an unknown id, and a loader that always refuses fails the positive cases.
- R7. The live notice. After a save or a removal the route calls `publishLive({ userId }, "draft.changed", data)` of TOKI-038 R27 with `data` the `DraftNoticeSchema` of the change: `{ key, updatedAt, text }` with `text` the stored text, or `null` for a removal, and, when the text has more than `DRAFT_LIVE_TEXT_MAX` (10,000 code points, the size of a message, D-042) code points, with the key `text` left out, so that no frame is larger than about 40 KB of text and three long drafts in a few seconds do not reach the 1 MiB limit of a connection (TOKI-038 R19; the Limits note there counts about a hundred long messages); the other devices read such a draft with `refresh` (R12). It goes to every connection of the person, the one that made the request included, and to nobody else. It writes nothing to the event log and takes no event number (concern 4). A failure of `publishLive` is logged without the text and does not change the answer, because the row is already stored. `draft.changed` is a live kind, not an event kind: it is not added to the registry of event kinds of TOKI-038 R12 (that registry holds what the handler writes) and has no row in `modules/realtime/kinds.ts`, so the test that every kind of the registry has a row there is not touched. Its schema is `draftNoticeLiveFrameSchema` in `packages/shared/src/realtime/drafts.ts`, the schema of the `live` frame `{ type: "live", kind: "draft.changed", data }` as TOKI-044 R2 does for `typing`, exported from `packages/shared/src/realtime/index.ts`. `app.ts` passes the route its dependency: `messageRoutes` (TOKI-037 R25) gets a `publishLive` option, which is `publishLive` of the `realtime` module when the gateway exists (TOKI-038 R29 registers it when `db` and `listen` are given) and a function that does nothing when it does not (an app built without `listen` saves drafts and notifies nobody); `realtime` imports no module and the `messages` routes receive the function, never import `realtime`. Check: with two connections of one person and one of another, a save reaches the first two and not the third; a removal sends `text: null`; a text of 10,001 emoji sends a frame with no `text`, one of 10,000 sends it, and the biggest frame is under 64 KB; the log has no new row and `getLastEventNumber` does not move; a throwing `publishLive` leaves the answer 200 and the row stored; an app built without `listen` answers a save 200; the frame schema parses the frame, the registry of event kinds and `kinds.ts` are unchanged, and a search of the `messages` module for an import of `realtime` finds none.

The client
- R8. `createApiClient` gains `api.drafts` (the way TOKI-039 R17 and TOKI-040 R2 add their methods, same request core, 10 seconds, no retry, the 401 hook, a path part encoded, an optional `signal` last): `list(signal?)` sends `GET /drafts` and returns the `ListDraftsResponseSchema` answer; `save(key, text, signal?)` sends `PUT /drafts/{kind}/{id}` with `{ text }` for the key `conversation:<id>` or `thread:<id>` and returns the `DraftChange`; `remove(key, signal?)` sends `DELETE` and returns the `DraftChange`. A key that `parseDraftKey` refuses throws a plain error before any request. The answers are read with the schemas of R2 in the form that drops unknown keys. Check: each method sends the method and path as written; a path part is encoded; a bad key sends nothing; a bad answer is an `invalid_response` error.
- R9. `createSyncedDraftStore(options)` of `packages/client-core/src/composer/synced-drafts.ts` (exported from the package index) returns a `DraftStore` (TOKI-043 R9: `get`, `set`, `clear`, `has`, `subscribe`) that wraps the store of TOKI-043 and adds `flush`, `refresh`, `applyLive` and `attachConnection` (R11 to R13). `options` is `{ local: DraftStore, journal: { read(): string | null; write(value: string): boolean; remove(): void }, api: { drafts }, timers, getUserId, saveDelayMs?, retryDelayMs? }`. `get`, `has` and `subscribe` are those of `local`: the label and the composer read the browser at once and never wait for the server. `set(key, text)` calls `local.set` and then: when the text is blank (`local.has(key)` is false after the call) it behaves as `clear`; when its length in code points (`Array.from`) is over `DRAFT_TEXT_MAX` it cancels the timer of the key, marks the key clean and sends nothing, now or later: the longer text stays in the browser, like the cap of TOKI-043 R9, and the server keeps the last valid text, which the other devices see (concern 7); every send, the first and a follow-up, checks the length of the text it is about to send again and sends nothing when it is over; otherwise it marks the key dirty in the journal (R10) and starts or restarts the timer `timers.after(saveDelayMs, fn)` for the key, `saveDelayMs` = 1000 by default. `clear(key)` calls `local.clear`; when the key has an entry in the journal (it was typed, or it is known to be on the server) it marks the key dirty with no text and flushes it at once with no delay (pending removal), otherwise it sends nothing. A save or removal is one request for a key at a time: when the text changes while one is in flight, the answer is recorded and one more request follows with the latest text, so a key is never written by two requests that can arrive out of order from this device. Keys are independent and may run together. When the answer arrives: the key is clean only if the text it sent equals the text now held (otherwise it stays dirty and a new request follows); `updatedAt` of the answer becomes the key's known time (R10). A failure is read with `classifyApiError` (TOKI-032 R8), all nine kinds: `no_access` (403, 404: the person left or the root is gone) and `field` (400) end the attempt, mark the key clean and keep the local text; `unauthenticated` (the session ended) leaves the key dirty and starts no retry, because a retry against a dead session fails and the flush after the next sign-in or connection repeats it; `ignore` (an aborted request) leaves the key dirty with no retry; `unreadable` (`invalid_response`: a repeat fails the same way) leaves the key dirty with no retry timer; `retry` (5xx, `network`, `timeout`), `wait` (429), `fresh_copy` (409 and 410, which this API never sends) and `unknown` leave the key dirty and start one retry timer of `retryDelayMs`, 30 000 ms by default, the longest reconnect wait of D-129; a retry timer is started once for all dirty keys, and the retry also runs when the connection returns (R11). No save, failure or retry shows anything to the person (D-079 allows messages only to wait; the owner's answers of 2026-11-19 on the sign-in screens, concern 8, and the account menu, concern 10, say a draft that could not be saved stays in the browser, and nothing says a draft shows an error, concern 5). The timers belong to the store, not to the composer, so a text typed and left within the delay is still saved after the composer is gone. All waiting goes through `timers`, never `setTimeout` (TOKI-032 R25). Check: with a recording fake `timers` and a fake `api.drafts` (no real timer, no Vitest fake time, TOKI-008 R19): a `set` starts one timer of 1000 ms and no request; firing it sends one save with the text; two `set` calls in the same delay send one request with the second text; a `set` during a request sends one more request after the answer with the latest text and never two at once; a `set` of blank text sends a removal only when the key has an entry; `clear` of an unknown key sends nothing; a text of 100,001 code points (also 60,000 emoji, which are over 100,000 in `.length`) sends nothing, stays readable by `get` and leaves the key clean; a valid text, then an over-cap text before the timer fires, sends nothing when the timer would have fired (the timer is cancelled); a 403 and a 400 leave the text and no dirty key; a timeout, a 500, a 429 and an unknown status leave it dirty with one 30 000 ms timer, and firing it sends again; a 401, an abort and an `invalid_response` leave it dirty with no timer; the text is saved after the store of the composer was unmounted (the store is used with no composer).
- R10. The journal. The store keeps in `journal` one JSON text, `{ version: 1, userId, keys: { [key]: { dirty: boolean, at: string | null } } }` (the web cell is `composer.drafts.sync`, stored as `toki:composer.drafts.sync`, R14): `dirty` means the browser's text, or its absence, is not yet on the server; `at` is the `updatedAt` of the last server state this device applied or caused. The journal is written only when an entry changes its `dirty` or its `at` (a key press on a key that is already dirty writes nothing, so a key press costs the one read-parse-write of the store of TOKI-043 and not a second). A change that does write reads the text, changes only its key and writes it back, so two tabs of one browser keep each other's keys, as TOKI-043 R9 does for the drafts. The rules of TOKI-043 R9 for the person apply here, so a draft of the browser and its journal always belong to the same person: when `getUserId()` is `null` nothing is read, written or sent and the cell is left as it is (the same person who signs in again finds their unsaved drafts, journey F07); when the stored `userId` is not the signed-in person's, the cell is removed and nothing is restored (the owner's answers of 2026-11-19, by the pattern of D-132); when the person changes while the store lives, the memory is dropped and every timer of the store is cancelled; a text that is not JSON, has another `version` or a wrongly typed key is removed and ignored. An entry that is clean and whose local text is gone is removed from the cell, but the store keeps its `at` in memory for the life of the page, so a late notice older than a removal cannot bring the text back (R12). A `write` that returns false leaves the journal in memory only and shows nothing. Check: tests over a fake cell: after a `set` the cell holds the key as dirty and, after the answer, as clean with `at`; a reload (a new store over the same cell and the same local cell) with a dirty key sends it; another person's journal is removed; `null` person leaves it and sends nothing; the same person after `null` finds it and sends; bad JSON and another version are removed; a refusing `write` keeps the keys in memory; two stores over one cell keep each other's keys; 20 keys make one `read` and one `write` per change; ten key presses on one key make one journal `write`. Drafts that sit in the browser store before this work is built have no entry and are not uploaded until the person edits them: `DraftStore` has no list of keys, and the work of TOKI-043 and this one ship in the same milestone, so this is accepted; a key list in `DraftStore` would be a change of TOKI-043.
- R11. Loading and merging. `refresh()` calls `api.drafts.list()` once at a time (a call while one runs returns the same promise) and merges the answer; it returns a promise that never rejects and resolves `true` when the answer was merged and `false` otherwise. It never runs while `getUserId()` is `null`. For each draft of the answer: when the key is dirty it is skipped (the text this device typed after it will be saved and wins, concern 2); when the key's known `at` is later than the draft's `updatedAt` it is skipped; when the local text of the key is longer than `DRAFT_TEXT_MAX` it is skipped; otherwise `local.set(key, text)` is called when the text differs and the entry becomes clean with that `updatedAt`. The store keeps, for the request that runs, the set of keys touched since it started: a `set`, a `clear`, an answer of a save or a removal, or an applied notice for the key adds it. A touched key is skipped by the merge and by the next rule, whatever the answer holds (a read takes its snapshot when it starts, so an answer can miss a save that this device made and had confirmed after that). For each key of the journal that is clean, has an `at`, is not touched and is not in the answer, and whose `at` is earlier than `readAt`: the draft was removed on another device (its message was sent there, or the field was emptied), so `local.clear(key)` is called and the entry is removed, unless the local text is over `DRAFT_TEXT_MAX`. A key typed while the request ran is dirty and touched when the answer comes back and is left alone. `attachConnection(connection)` takes `{ getState(): { status }; subscribe(listener): () => void }` (the shape TOKI-040 gave `sync.attachConnection`), calls `refresh()` and `flush()` at each change of `status` to `online` from another status, and returns the function that stops it. The app also calls `refresh()` once when the conversation store becomes ready for a person (R14), so a person whose socket cannot open still gets their drafts. Check: a fake `api.drafts.list` and a fake connection: a server draft for a key with no local text appears in `get`; a dirty key keeps its local text; an older answer does not replace a newer known time; a key known as synced and missing from the answer is cleared locally, and a key never synced and missing is kept; a key typed while the request ran is kept; a key whose own save was answered after the request started and is missing from the answer is kept with its text (the race of a save that commits after the snapshot); a 100,001-code-point local text is neither replaced nor cleared; two `refresh` calls make one request; a `refresh` with no person makes none; each change of the fake connection to `online` makes one `refresh` and one `flush`, and a change from `online` to `online` none; the stop function ends it.
- R12. Applying the notice, and the open composer. `applyLive(frame)` takes the live frame of TOKI-039 R19 (c) and does nothing unless `kind` is `draft.changed` and `data` parses with `DraftNoticeSchema`. For a key that is dirty it does nothing (the person's newer typing wins). For a frame whose `updatedAt` is not later than the key's known time, held also for a removed key (R10), it does nothing: this is how the echo of this device's own save is ignored (its time equals the time of the answer; while the save is in flight the key is dirty); otherwise a text calls `local.set(key, text)`, a `null` calls `local.clear(key)`, and the known time becomes the frame's; a frame with no `text` (a draft over `DRAFT_LIVE_TEXT_MAX`, R7) calls `refresh()` instead. It never sends a request of its own and never throws.
  The open composer follows only while it is untouched (concern 2, a proposal). Today the composer reads the store once, when it mounts (TOKI-043 R10), so a draft that arrives later never reaches a field that is already open: on a device that starts inside the conversation (journey F07 returns the person to the conversation that was open, and the first `GET` has not finished), the field is empty, stays empty, and the first key press saves a text that replaces the server's. ## Design
### Where a draft lives and how the pieces meet
Two copies: the browser's (TOKI-043, written at every keystroke, read at once, held for the person whose id is in it) and the server's (this work, written after a pause, read when the app starts and when the connection returns, pushed to the person's other devices). The browser copy is always the one the screen reads, so nothing waits on the network and a lost request loses nothing. The journal says which keys differ from the server; it is the only thing that tells "typed here and not yet saved" from "saved here and removed there".

The flow of one change: key press -> the composer calls `drafts.set` (browser) -> the store marks the key dirty and starts a 1000 ms timer -> one `PUT` -> the server upserts and publishes `draft.changed` to the person's connections -> the other device's `applyLive` sets its browser copy -> its row shows "Draft" and its composer shows the text, at the next mount or at once when the open field is still untouched (R12). Sending: the composer calls `drafts.clear` after `sync.send` returned an id (TOKI-043 R6) -> one `DELETE` -> `draft.changed` with `text: null` -> the other device clears its copy and the label goes, and an open field that is still untouched empties (R12). Missed notices (the device was offline) are repaired by `refresh` when the connection is back (R11), which also drops a draft removed meanwhile.

The server does not remove a draft when a message is stored. The client clears it on send (TOKI-043 R6), and two ways of clearing would race with a new draft typed right after the send (concern 6).

### Data model
Table `drafts` (R1): one row for each person and place; `kind` `conversation` or `thread`; `target_id`; `conversation_id` (for the access filter of R5; every key RESTRICT, none cascades); `body`; `updated_at`. No row for blank text. No retention job in this work (concern 1).

### API
| Method | Path | Who | Purpose |
|---|---|---|---|
| GET | `/api/v1/drafts` | the person | Every draft of the person that they can still read (R5) |
| PUT | `/api/v1/drafts/{kind}/{id}` | a person who can read the place | Save the text of one draft (R3) |
| DELETE | `/api/v1/drafts/{kind}/{id}` | a person who can read the place | Remove one draft, idempotent (R4) |

Live frame, not in the log: `{ "type": "live", "kind": "draft.changed", "data": { "key", "text", "updatedAt" } }` to the person's connections (R7).

### Errors
- Not signed in -> 401 as every route (TOKI-022).
- Body not valid, blank text, a text over the limit, a bad `kind` or id -> 400 `validation_failed`.
- A private conversation, a direct message or group the person is not in, an unknown id, a thread root that is unknown or is a reply -> 404 `not_found`.
- A public channel the person has not joined -> 403 `forbidden`.
- `fact_missing` and any unknown refusal -> 500 `internal_error`, logged without the text.
- 410 and 409 do not occur: there is no stale-copy answer in this set.

## Data safety
- A draft is the person's own unsent text and is as private as a message. It is stored in plain text like `messages.body` (the technical design stores no field-level encryption for messages), is returned only to its owner and is never logged (R16).
- The browser keeps the text and its journal under the person's id and drops them when another person signs in on that browser (R10: the owner's answers of 2026-11-19, by the pattern of D-132, which covers a waiting message only).
- Nothing in a draft request carries a name, a conversation title or a member list.

## Areas of concern
1. How long a draft is kept. D-169 is Open in the log; its proposal is "kept until sent or emptied, with no expiry". Not decided. Proposal, not a decision: no expiry, no job that removes old rows; the draft goes when the message is sent (R4), when the field is emptied, or with its conversation. The build has no retention code, so nothing needs to change if the answer is the proposal; a limit (for example a number of days) would be one scheduled statement on `drafts.updated_at`. The cost the owner should see: with no expiry, the draft of a thread whose root is deleted, or of a person who stays away, keeps its row for ever. Owner: Thanh Truong.
2. Two devices edit one draft; a draft arrives while the person has the conversation open. D-169 (Open) proposes "the last save wins, as for topics (D-121)", and D-121 (Confirmed) says that for topics, status and tasks. Not decided for drafts. Proposal, not a decision, which R3, R4, R11 and R12 build: the last statement that reaches the server is the stored draft, with a time that the server makes always later than the one it replaces (not the device's clock); a device that has unsaved typing for a key keeps it and its next save replaces the server copy; a device with no unsaved typing takes the server's text. For a composer that is open: while the person has not typed in it since it was mounted (and has not sent), it follows the store, so a draft that arrives after the mount (the first `GET` has not finished, or the other device saved a moment ago) fills the field, and a removal, such as a send on the other device, empties it; once the person has typed in it, nothing from another device changes the field, so the person never loses text they are typing. The cost of the proposal: a field that the person touched and then left idle keeps its text on screen while another device saves a newer one, and the next key press there saves the whole old text over the newer one; if that other device had sent the message, the touched field still holds it, and a Send there sends it a second time. The alternatives for the owner: the field always follows (the person loses typing when two devices are open), or the field asks (a notice, which no spec draws). The owner decides; until then the build follows the proposal. Owner: Thanh Truong.
3. A draft of a conversation the person left, was removed from, or that is archived. Not decided; no decision names it (D-133 clears the unread count and the Activity items on leaving, not drafts). Proposal, not a decision, which R5 builds: the row is kept and not returned while the person cannot read the conversation (`GET` filters on membership and on not archived), so a person who is added back to a private channel, or an Admin who restores an archived channel, finds the text again; the browser copy of a key the server no longer returns is cleared on the next merge only if the device had it as synced (R11). This does not conflict with R6, which lets a save into an archived channel return 200 (a device that had the channel open when it was archived must not be left with an unsaved key): the composer is not drawn there, so a person cannot type into it, a save that did get through is stored, the next `GET` does not return it, and the device clears its synced copy. The alternative is to delete the row when the person leaves; it would be one statement in the leave and remove-member handlers of the `conversations` module, which this work does not edit. Owner: Thanh Truong.
4. The notice is a live frame and not an event of the log. Decided in this spec. Reason: a draft changes after every pause in typing; every event of the log takes the workspace's counter row lock until the commit (TOKI-036 R16 to R18), so a draft event would queue every person's save behind every other write and fill the 7-day log with texts, while a lost notice costs nothing, because the client reads all drafts again when the connection returns (R11). TOKI-038 R17 and R27 give the same route to `person.updated` and the typing line. Alternative refused: a `user`-scope event in the log, which would repair a gap by itself but adds the lock and the volume. Owner: Thanh Truong.
5. The numbers and the silence. Decided in this spec, as technical choices the Blueprint leaves to the builder: the save waits 1000 ms after the last change (one request for each pause, and a text typed just before leaving a conversation is still saved because the timer belongs to the store); a failed save is retried after 30 000 ms, the longest reconnect wait of D-129, and when the connection returns; the list has no paging because a person has at most one draft for each place (R5); a failed save shows nothing, because the composer's own store shows nothing for a refused storage (TOKI-043 R9) and D-079 asks for an explanation only for blocked actions, while a draft is never blocked. The person is protected by the browser copy and the journal, and by the flush before Sign out. Owner: Thanh Truong.
6. The server does not clear a draft when a message is stored. Decided in this spec. Reason: the composer already clears it when Send is pressed (TOKI-043 R6), the message route is TOKI-037's and gains no coupling, and a server-side clear could remove a draft that the person began typing for the next message between the press and the answer. A send that fails keeps its text in the waiting message and the draft is already gone; that is the behaviour of TOKI-043 R6 and TOKI-040, not changed here. Owner: Thanh Truong.
7. The size of a draft. Decided in this spec: up to 100,000 code points, ten times a message (D-042, 10,000), which is the cap that TOKI-043 R9 puts on the browser copy so a paste of a megabyte is not stored. A longer text stays in the browser and is not sent; the server keeps the older text and the other devices see that. The unit is code points in both specs: TOKI-043 R9 says "characters" and, if that is read as `.length`, a text of 60,000 emoji is refused by the browser cell and a text of 60,000 emoji is sent by this work; the same unit prevents it. Hand-off: TOKI-043 names `DRAFT_TEXT_MAX` of R2 in its R9 instead of the bare number and says "code points" (a change in its pull request, the same value). A live notice carries the text only up to `DRAFT_LIVE_TEXT_MAX` (10,000 code points, the message limit, D-042), above that the device reads the draft (R7). Owner: Thanh Truong.
8. The label reads the conversation's draft only.
