Also uses, without them being in the plan line: TOKI-099 (`registerBeforeSignOut`, PR 207 line of `account-menu-devices`), TOKI-039 (the connection and its state; PR 210), TOKI-038 (`publishLive`, merged), TOKI-037 (the access steps of a conversation route, merged), TOKI-033 (the conversation list, merged), TOKI-032 (API client, `classifyApiError`, `Timers`), TOKI-018 (platform storage).

## Goal
The composer keeps what a person has typed and not sent, one text for each conversation and one for each thread, but only in the browser. Journeys F06, F07 and F11 and FR-38 say more: the text is saved to the person's account, is back on their other devices, survives a sign-out, is cleared when the message is sent, and the conversation list shows "Draft" on a conversation that has one and is not open.
This work builds the server copy and everything around it: the table and three requests (save, remove, list), one live notice to the person's other open devices, the client store that saves after a pause in typing, keeps a list of what is not yet saved, merges the server's drafts when the app starts and when the connection returns, applies the notice, saves before Sign out, and the "Draft" label in the list. The composer is not changed: TOKI-043 R18 made `DraftStore` the seam, and this work puts a store of the same type behind it.

  - The thread panel and its box: TOKI-045. A thread has no "Draft" label of its own (concern 8).

  - Unread counts and the read pointer: TOKI-053. The bootstrap call: TOKI-031 (its R12 keeps drafts out of the answer, so the list of drafts is a request of its own, R5).

## Requirements
The server
- R1. The table `drafts` and its migration, made with `pnpm db:generate --name drafts` (TOKI-019 convention 8; the foreign keys that leave the module are written as SQL in the migration, as TOKI-028 R16 does). Columns: `workspace_id` (uuid, not null, references `workspaces`), `user_id` (uuid, not null, references `users`, on delete cascade), `kind` (text, not null, check in `'conversation'`, `'thread'`), `target_id` (uuid, not null: the conversation id for `conversation`, the root message id for `thread`), `conversation_id` (uuid, not null, references `conversations`, on delete cascade: the conversation of the draft, equal to `target_id` for `conversation`), `body` (text, not null, check `char_length(body) between 1 and 100000`), `updated_at` (timestamptz, not null, written by the server from the clock of TOKI-008, no database default, TOKI-005 convention 3). Primary key (`user_id`, `kind`, `target_id`): one draft for each person and place. There is no foreign key to `messages` (the tables of a module are not read by another, TOKI-036 R24); the root of a thread is checked by R6. Check: a database test applies the migration to an empty database, inserts a conversation draft and a thread draft, refuses a second row with the same primary key, an empty `body`, a `body` of 100,001 characters and a `kind` of `"x"`, and deletes the rows of a person's draft when the conversation is deleted.
- R2. `packages/shared/src/drafts/` (exported from the package index) holds: `DRAFT_TEXT_MAX` = 100000 (code points; the number is the cap of the browser store of TOKI-043 R9, "a text of more than 100,000 characters", which this work gives a name, concern 7); `DraftKeySchema`, a string that is `conversation:` or `thread:` followed by a lower-case UUID, with `parseDraftKey(key)` returning `{ kind, targetId }` or `null`; `DraftChangeSchema`, the strict object `{ key, text, updatedAt }` where `text` is a string or `null` (null means "removed") and `updatedAt` is an ISO 8601 time with milliseconds; `SaveDraftBodySchema` = strict `{ text }` where `text` is a string of 1 to `DRAFT_TEXT_MAX` code points (counted with `Array.from(text).length`, never `.length`), with at least one character that `String.prototype.trim` does not remove, without U+0000 and with `text.isWellFormed()` true (the reasons of TOKI-037 R4: the database cannot store the first, and the second would be stored as U+FFFD); `SaveDraftResponseSchema` = `{ draft: DraftChange }` with a string `text`; `RemoveDraftResponseSchema` = `{ draft: DraftChange }` with `text` null; `ListDraftsResponseSchema` = `{ drafts: DraftChange[] (text never null), readAt }`. Check: schema tests for each; a text of 100,000 emoji outside the Basic Multilingual Plane is accepted and 100,001 refused; a text of only U+00A0 and tabs is refused; a key with an upper-case id, with another prefix or with extra text is refused.
- R3. `PUT /api/v1/drafts/{kind}/{id}` (`kind` is `conversation` or `thread`) takes `SaveDraftBodySchema` and answers 200 `SaveDraftResponseSchema`. It needs a valid session (TOKI-022 R24). After the access steps of R6 it runs one statement, `insert ... on conflict (user_id, kind, target_id) do update set body = excluded.body, updated_at = excluded.updated_at`, with `updated_at` read once from the clock for the request, so the last request to reach the server is the last save (concern 2) and the answer holds the stored text and time. The same text sent again is stored again with a new time (no comparison). The text is stored as sent: no trim, no change of line breaks. After the statement has completed, and only then, the route calls R7. A blank text is 400 `validation_failed` (the client removes instead, R9). Check: a save returns the stored text and time and the row holds them column by column; a second save by the same person replaces the text and moves the time; a save with an old time of the request is impossible (the client sends none, and a body key `updatedAt` is 400 because the body is strict); text with a trailing line break is stored whole; two saves by two people for the same conversation make two rows.
- R4. `DELETE /api/v1/drafts/{kind}/{id}` answers 200 `RemoveDraftResponseSchema` and deletes the person's row for that place. It is idempotent: when there is no row it still answers 200, with the time of the request. It runs the same access steps as R3 and calls R7 after the statement, also when no row existed (another device may hold the text). Check: removing an existing draft deletes the row; a second removal answers 200 and the row count stays at zero; a removal never touches another person's row for the same place.
- R5. `GET /api/v1/drafts` answers 200 `ListDraftsResponseSchema`: every draft of the signed-in person, in one statement, whose `conversation_id` is a conversation that `listConversationSummaries(db, workspaceId, userId)` of the `conversations` module returns (the person is a member and the conversation is not archived), in any order, with `text` the stored body, and `readAt` the time of the request from the clock. There is no paging: a person has at most one draft for each conversation and each thread they started and the rows are small, and the answer is bounded by the 100,000-character limit of each body and by the number of places (concern 5). Check: a person with three drafts gets three; another person's draft is not returned; a draft of a private channel that the person has left, and of an archived channel, is not returned and its row stays (concern 3); a person with none gets an empty list and a `readAt`; a request with no session is 401 and reads nothing.
- R6. Access and refusals. The module imports the other modules only through their `index.ts` (TOKI-002 rules 2 and 17). Both mutations run, in order: (1) the schemas of the path and the body (400 `validation_failed`; a `kind` other than the two, an id that is not a lower-case UUID, an unknown key in the body); (2) for `conversation`, `getConversationFacts(db, actor.id, id)`; `null`, and a private channel, a `dm` or a `group_dm` of which the actor is not a member, are 404 `not_found` before anything else, so a private conversation is never confirmed (BR-10, D-051); for `thread`, the conversation of the root is found with a function of the `messages` module that returns `{ conversationId, parentId }` or `null` for a message id (the one TOKI-045 R6 uses for its replies route, or, when it is not yet exported, a small read added to the `messages` module and its `index.ts` by whichever of the two is built first and named in its pull request); `null`, or a message with a `parentId` (a reply is not a thread root), is 404 `not_found`; then the facts of that conversation as for `conversation`; (3) `canReadConversation` (TOKI-027 R5): a person who has not joined a public channel is 403 `forbidden` (D-116). Nothing else is checked: a draft is the person's own text, the right to keep it is the right to read the place, and the composer decides when it is drawn (the read-only notice of a direct message, the missing composer of an archived channel); so a save into an archived channel or a read-only direct message is 200 (the client must never be left with an unsaved key that a 409 would block). The actor is always the account of the session; no route takes a user id. No role is compared (TOKI-027 R16). Check: a table test sends each case to each mutation and checks status and code, a positive case for each kind (a public channel, a private channel, a direct message, a group, a thread root), a person who is not in the private channel gets 404 whatever the body, a member of an archived channel saves 200, a reply id as the root is 404, an unknown root is 404, and a loader that always refuses fails the positive cases.
- R7. The live notice. After a save or a removal the route calls `publishLive({ userId }, "draft.changed", change)` of TOKI-038 R27 with `change` the `DraftChange` of the answer (`text` null for a removal). It goes to every connection of the person, the one that made the request included, and to nobody else. It writes nothing to the event log and takes no event number (concern 4). A failure of `publishLive` is logged without the text and does not change the answer, because the row is already stored. `draft.changed` is added to the registry of live kinds of `packages/shared/src/realtime/` (TOKI-038 R12) with `DraftChangeSchema` as the schema of `data`. Check: with two connections of one person and one of another, a save reaches the first two and not the third; a removal sends `text: null`; the log has no new row and `getLastEventNumber` does not move; a throwing `publishLive` leaves the answer 200 and the row stored; the registry holds the kind and its schema parses the frame.

The client
- R8. `createApiClient` gains `api.drafts` (the way TOKI-039 R17 and TOKI-040 R2 add their methods, same request core, 10 seconds, no retry, the 401 hook, a path part encoded, an optional `signal` last): `list(signal?)` sends `GET /drafts` and returns the `ListDraftsResponseSchema` answer; `save(key, text, signal?)` sends `PUT /drafts/{kind}/{id}` with `{ text }` for the key `conversation:<id>` or `thread:<id>` and returns the `DraftChange`; `remove(key, signal?)` sends `DELETE` and returns the `DraftChange`. A key that `parseDraftKey` refuses throws a plain error before any request. The answers are read with the schemas of R2 in the form that drops unknown keys. Check: each method sends the method and path as written; a path part is encoded; a bad key sends nothing; a bad answer is an `invalid_response` error.
- R9. `createSyncedDraftStore(options)` of `packages/client-core/src/composer/synced-drafts.ts` (exported from the package index) returns a `DraftStore` (TOKI-043 R9: `get`, `set`, `clear`, `has`, `subscribe`) that wraps the store of TOKI-043 and adds `flush`, `refresh`, `applyLive` and `attachConnection` (R11 to R13). `options` is `{ local: DraftStore, journal: { read(): string | null; write(value: string): boolean; remove(): void }, api: { drafts }, timers, getUserId, saveDelayMs?, retryDelayMs? }`. `get`, `has` and `subscribe` are those of `local`: the label and the composer read the browser at once and never wait for the server. `set(key, text)` calls `local.set` and then: when the text is blank (`local.has(key)` is false after the call) it behaves as `clear`; when its length in code points is over `DRAFT_TEXT_MAX` it sends nothing and marks nothing (it stays in the browser, like the cap of TOKI-043 R9; the server keeps the older text, concern 7); otherwise it marks the key dirty in the journal (R10) and starts or restarts the timer `timers.after(saveDelayMs, ..., )` for the key, `saveDelayMs` = 1000 by default. `clear(key)` calls `local.clear`; when the key has an entry in the journal (it was typed, or it is known to be on the server) it marks the key dirty with no text and flushes it at once with no delay (pending removal), otherwise it sends nothing. A save or removal is one request for a key at a time: when the text changes while one is in flight, the answer is recorded and one more request follows with the latest text, so a key is never written by two requests that can arrive out of order from this device. Keys are independent and may run together. When the answer arrives: the key is clean only if the text it sent equals the text now held (otherwise it stays dirty and a new request follows); `updatedAt` of the answer becomes the key's known time (R10). A failure is read with `classifyApiError` (TOKI-032 R8): `no_access` (403, 404: the person left or the root is gone) and `field` (400) end the attempt, mark the key clean and keep the local text; every other kind (`network`, `timeout`, 5xx, 429, `invalid_response`) leaves the key dirty and starts one retry timer of `retryDelayMs`, 30 000 ms by default, the longest reconnect wait of D-129; a retry timer is started once for all dirty keys, and the retry also runs when the connection returns (R11). No save, failure or retry shows anything to the person (D-079 allows messages only to wait; nothing says a draft shows an error, concern 5). The timers belong to the store, not to the composer, so a text typed and left within the delay is still saved after the composer is gone. All waiting goes through `timers`, never `setTimeout` (TOKI-032 R25). Check: with a recording fake `timers` and a fake `api.drafts` (no real timer, no Vitest fake time, TOKI-008 R19): a `set` starts one timer of 1000 ms and no request; firing it sends one save with the text; two `set` calls in the same delay send one request with the second text; a `set` during a request sends one more request after the answer with the latest text and never two at once; a `set` of blank text sends a removal only when the key has an entry; `clear` of an unknown key sends nothing; a text of 100,001 characters sends nothing, stays readable by `get` and marks nothing; a 403 and a 400 leave the text and no dirty key; a timeout, a 500 and a 429 leave it dirty with one 30 000 ms timer, and firing it sends again; the text is saved after the store of the composer was unmounted (the store is used with no composer).
- R10. The journal. The store keeps in `journal` one JSON text, `{ version: 1, userId, keys: { [key]: { dirty: boolean, at: string | null } } }` (the web cell is `composer.drafts.sync`, stored as `toki:composer.drafts.sync`, R14): `dirty` means the browser's text, or its absence, is not yet on the server; `at` is the `updatedAt` of the last server state this device applied or caused. Each change reads the text, changes only its key and writes it back, so two tabs of one browser keep each other's keys, as TOKI-043 R9 does for the drafts. The rules of TOKI-043 R9 for the person apply here, so a draft of the browser and its journal always belong to the same person: when `getUserId()` is `null` nothing is read, written or sent and the cell is left as it is (the same person who signs in again finds their unsaved drafts, journey F07); when the stored `userId` is not the signed-in person's, the cell is removed and nothing is restored (D-132); when the person changes while the store lives, the memory is dropped and every timer of the store is cancelled; a text that is not JSON, has another `version` or a wrongly typed key is removed and ignored. An entry that is clean and whose local text is gone is removed from the cell, but the store keeps its `at` in memory for the life of the page, so a late notice older than a removal cannot bring the text back (R12). A `write` that returns false leaves the journal in memory only and shows nothing. Check: tests over a fake cell: after a `set` the cell holds the key as dirty and, after the answer, as clean with `at`; a reload (a new store over the same cell and the same local cell) with a dirty key sends it; another person's journal is removed; `null` person leaves it and sends nothing; the same person after `null` finds it and sends; bad JSON and another version are removed; a refusing `write` keeps the keys in memory; two stores over one cell keep each other's keys; 20 keys make one `read` and one `write` per change.
- R11. Loading and merging. `refresh()` calls `api.drafts.list()` once at a time (a call while one runs returns the same promise) and merges the answer; it returns a promise that never rejects and resolves `true` when the answer was merged and `false` otherwise. It never runs while `getUserId()` is `null`. For each draft of the answer: when the key is dirty it is skipped (the text this device typed after it will be saved and wins, concern 2); when the key's known `at` is later than the draft's `updatedAt` it is skipped; when the local text of the key is longer than `DRAFT_TEXT_MAX` it is skipped; otherwise `local.set(key, text)` is called when the text differs and the entry becomes clean with that `updatedAt`. For each key of the journal that is clean, has an `at` and is not in the answer, and whose `at` is earlier than `readAt`: the draft was removed on another device (its message was sent there, or the field was emptied), so `local.clear(key)` is called and the entry is removed, unless the local text is over `DRAFT_TEXT_MAX`. A key typed while the request ran is dirty when the answer comes back and is therefore left alone. `attachConnection(connection)` takes `{ getState(): { status }; subscribe(listener): () => void }` (the shape TOKI-040 gave `sync.attachConnection`), calls `refresh()` and `flush()` at each change of `status` to `online` from another status, and returns the function that stops it. The app also calls `refresh()` once when the conversation store becomes ready for a person (R14), so a person whose socket cannot open still gets their drafts. Check: a fake `api.drafts.list` and a fake connection: a server draft for a key with no local text appears in `get`; a dirty key keeps its local text; an older answer does not replace a newer known time; a key known as synced and missing from the answer is cleared locally, and a key never synced and missing is kept; a key typed while the request ran is kept; a 100,001-character local text is neither replaced nor cleared; two `refresh` calls make one request; a `refresh` with no person makes none; each change of the fake connection to `online` makes one `refresh` and one `flush`, and a change from `online` to `online` none; the stop function ends it.
- R12. Applying the notice. `applyLive(frame)` takes the live frame of TOKI-039 R19 (c) and does nothing unless `kind` is `draft.changed` and `data` parses with `DraftChangeSchema`. For a key that is dirty it does nothing (the person's newer typing wins; the echo of this device's own save is also ignored this way or by the next rule); for a frame whose `updatedAt` is earlier than the key's known time, held also for a removed key (R10), it does nothing; otherwise a text calls `local.set(key, text)` and a null calls `local.clear(key)`, and the known time becomes the frame's. It never sends a request and never throws. The composer of a conversation that is open is not changed by it, because the composer reads the store when it is mounted (TOKI-043 R10); the next mount, and the "Draft" label (R15), show the new state (concern 2). Check: a frame with a new text for an idle key sets it; the same frame again changes nothing and calls no listener twice; a frame older than the known time does nothing; a null frame clears; a frame for a dirty key does nothing; a frame of another kind, a bad `data` and a frame for a person who is not signed in do nothing; the echo of this device's own save changes nothing; a test that mounts the real composer of TOKI-043 with text, applies a frame for its key and finds the field text unchanged, then remounts it and finds the new text.

## Design
### Where a draft lives and how the pieces meet
Two copies: the browser's (TOKI-043, written at every keystroke, read at once, held for the person whose id is in it) and the server's (this work, written after a pause, read when the app starts and when the connection returns, pushed to the person's other devices). The browser copy is always the one the screen reads, so nothing waits on the network and a lost request loses nothing. The journal says which keys differ from the server; it is the only thing that tells "typed here and not yet saved" from "saved here and removed there".

The flow of one change: key press -> the composer calls `drafts.set` (browser) -> the store marks the key dirty and starts a 1000 ms timer -> one `PUT` -> the server upserts and publishes `draft.changed` to the person's connections -> the other device's `applyLive` sets its browser copy -> its row shows "Draft" and its composer shows the text when mounted. Sending: the composer calls `drafts.clear` after `sync.send` returned an id (TOKI-043 R6) -> one `DELETE` -> `draft.changed` with `text: null` -> the other device clears its copy and the label goes. Missed notices (the device was offline) are repaired by `refresh` when the connection is back (R11), which also drops a draft removed meanwhile.

The server does not remove a draft when a message is stored. The client clears it on send (TOKI-043 R6), and two ways of clearing would race with a new draft typed right after the send (concern 6).

### Data model
Table `drafts` (R1): one row for each person and place; `kind` `conversation` or `thread`; `target_id`; `conversation_id` (for the access filter of R5, cascade when a conversation goes); `body`; `updated_at`. No row for blank text. No retention job in this work (concern 1).

### API
| Method | Path | Who | Purpose |
|---|---|---|---|
| GET | `/api/v1/drafts` | the person | Every draft of the person that they can still read (R5) |
| PUT | `/api/v1/drafts/{kind}/{id}` | a person who can read the place | Save the text of one draft (R3) |
| DELETE | `/api/v1/drafts/{kind}/{id}` | a person who can read the place | Remove one draft, idempotent (R4) |

Live frame, not in the log: `{ "type": "live", "kind": "draft.changed", "data": { "key", "text", "updatedAt" } }` to the person's connections (R7).

### Errors
- Not signed in -> 401 as every route (TOKI-022).
- Body not valid, blank text, a text over the limit, a bad `kind` or id -> 400 `validation_failed`.
- A private conversation, a direct message or group the person is not in, an unknown id, a thread root that is unknown or is a reply -> 404 `not_found`.
- A public channel the person has not joined -> 403 `forbidden`.
- `fact_missing` and any unknown refusal -> 500 `internal_error`, logged without the text.
- 410 and 409 do not occur: there is no stale-copy answer in this set.

## Data safety
- A draft is the person's own unsent text and is as private as a message. It is stored in plain text like `messages.body` (the technical design stores no field-level encryption for messages), is returned only to its owner and is never logged (R16).
- The browser keeps the text and its journal under the person's id and drops them when another person signs in on that browser (R10, D-132).
- Nothing in a draft request carries a name, a conversation title or a member list.

## Areas of concern
1. How long a draft is kept. D-169 is Open in the log; its proposal is "kept until sent or emptied, with no expiry". Not decided. Proposal, not a decision: no expiry, no job that removes old rows; the draft goes when the message is sent (R4), when the field is emptied, or with its conversation. The build has no retention code, so nothing needs to change if the answer is the proposal; a limit (for example a number of days) would be one scheduled statement on `drafts.updated_at`. Owner: Thanh Truong.
2. Two devices edit one draft; a draft arrives while the person types. D-169 (Open) proposes "the last save wins, as for topics (D-121)", and D-121 (Confirmed) says that for topics, status and tasks. Not decided for drafts. Proposal, not a decision, which R3, R11 and R12 build: the last request that reaches the server is the stored draft (the server's time, not the device's clock); a device that has unsaved typing for a key keeps it and its next save replaces the server copy; a device with no unsaved typing takes the server's text; the composer that is open is not changed by a draft from another device (it reads the store when it is mounted), so the person never loses text they are typing, and the next time the conversation is opened the newest saved text is shown. The cost of the proposal: a device that has the conversation open and idle keeps its old text on screen until it is remounted, and a later edit there replaces the newer text of the other device. Owner: Thanh Truong.
3. A draft of a conversation the person left, was removed from, or that is archived. Not decided; no decision names it (D-133 clears the unread count and the Activity items on leaving, not drafts). Proposal, not a decision, which R5 builds: the row is kept and not returned while the person cannot read the conversation (`GET` filters on membership and on not archived), so a person who is added back to a private channel, or an Admin who restores an archived channel, finds the text again; the browser copy of a key the server no longer returns is cleared on the next merge only if the device had it as synced (R11). The alternative is to delete the row when the person leaves; it would be one statement in the leave and remove-member handlers of the `conversations` module, which this work does not edit. Owner: Thanh Truong.
4. The notice is a live frame and not an event of the log. Decided in this spec. Reason: a draft changes after every pause in typing; every event of the log takes the workspace's counter row lock until the commit (TOKI-036 R16 to R18), so a draft event would queue every person's save behind every other write and fill the 7-day log with texts, while a lost notice costs nothing, because the client reads all drafts again when the connection returns (R11). TOKI-038 R17 and R27 give the same route to `person.updated` and the typing line. Alternative refused: a `user`-scope event in the log, which would repair a gap by itself but adds the lock and the volume. Owner: Thanh Truong.
5. The numbers and the silence. Decided in this spec, as technical choices the Blueprint leaves to the builder: the save waits 1000 ms after the last change (one request for each pause, and a text typed just before leaving a conversation is still saved because the timer belongs to the store); a failed save is retried after 30 000 ms, the longest reconnect wait of D-129, and when the connection returns; the list has no paging because a person has at most one draft for each place (R5); a failed save shows nothing, because the composer's own store shows nothing for a refused storage (TOKI-043 R9) and D-079 asks for an explanation only for blocked actions, while a draft is never blocked. The person is protected by the browser copy and the journal, and by the flush before Sign out. Owner: Thanh Truong.
6. The server does not clear a draft when a message is stored. Decided in this spec. Reason: the composer already clears it when Send is pressed (TOKI-043 R6), the message route is TOKI-037's and gains no coupling, and a server-side clear could remove a draft that the person began typing for the next message between the press and the answer. A send that fails keeps its text in the waiting message and the draft is already gone; that is the behaviour of TOKI-043 R6 and TOKI-040, not changed here. Owner: Thanh Truong.
7. The size of a draft. Decided in this spec: up to 100,000 code points, ten times a message (D-042, 10,000), which is the cap that TOKI-043 R9 puts on the browser copy so a paste of a megabyte is not stored. A longer text stays in the browser and is not sent; the server keeps the older text and the other devices see that. Hand-off: TOKI-043 names `DRAFT_TEXT_MAX` of R2 in its R9 instead of the bare number when it is built second (a change in its pull request, the same value). Owner: Thanh Truong.
8. The label reads the conversation's draft only. Decided: FR-38 says "a conversation that has a draft" and AC-102 keeps the thread's draft separate; the prototype reads the draft of the conversation only (line 1249, `D.drafts['c:'+c.id]`). A thread has its own draft and no row. Source: FR-38, AC-102, prototype. Owner: Thanh Truong.
9. The texts. Decided: the English word is "Draft", the prototype's and FR-38's. The Vietnamese "Bản nháp" is a proposal under D-139 (D-188 on the form of address is Open); `@toki/i18n` owns the catalogue and its checks. Owner: Thanh Truong.
10. Plan changes and the lines with the neighbours. Decided in this spec: the plan line of TOKI-051 needs TOKI-043 only; it also needs TOKI-099 for `registerBeforeSignOut` (TOKI-099 concern 11 already asks for it), TOKI-039 for the connection (R11, R14), and TOKI-038 for `publishLive`; a build can leave out the lines of a ticket that is not built and the one built second adds them (R14). Owners named: the browser store, the keys, the controller, clearing on send: TOKI-043; the thread box and its key: TOKI-045; the list and `draftLabel`: TOKI-033 (this work adds the one binding and the style, R15); the task and its 10 000 ms: TOKI-099; the connection and `subscribeLive`: TOKI-039; `publishLive`: TOKI-038; the read of a message's conversation for a thread root: TOKI-045 or, if absent, the first of the two builds (R6). No other spec is edited here. Owner: Thanh Truong.
