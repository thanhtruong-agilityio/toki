# Notification preferences (server) design

Date: 2026-11-25 · Status: draft for review (concern 1 is open for the product owner)
Intent: docs/intents/notification-preferences-server.md (Thanh Truong)
Ticket: TOKI-102

## Goal
A person's three notification switches must be kept on the server, belong to the person and not to a device, and reach every device the person has open at once. This work builds the whole path: the stored switches, the request that saves a change, the event that tells the person's other devices, the value in the first load, the value held by the client, and the one function that the later notification code calls to read the switches of any person. It does not draw the switches and does not obey them.

## Scope
- In:
  - Shared definitions: the three names, the defaults, the request, the answer and the event payload, and one key of the bootstrap answer (R1 to R3).
  - The server: the table, the one route, the one write function, the change and the event, the read for the bootstrap and the read for other server code, and the fixtures and bounds of the bootstrap tests (R3, R4 to R9).
  - The client: the API method, the value in the conversation store, the event, the seam for the saving device, the hook that a screen reads and saves through, and the connection to the muted-row rule that TOKI-054 already built (R10 to R13).
  - The texts that this work needs, which are only its errors (R14).
- Out (not now):
  - The Notifications section of Preferences, its labels (the phone's "Push notifications" form included) and its layout: TOKI-078. This work gives it the hook (R12) and nothing else.
  - Who gets a toast, a push or a sound: TOKI-073 reads the switches through `loadNotificationPreferencesFor` (R8) and the held value (R10). The Web Push registration, the browser permission and the card that offers notifications: TOKI-074. Sound and in-app toasts: TOKI-075. Pause and Focus time: TOKI-076. None of them is built here.
  - Every other saved preference of a person (display name, job title, time zone, look, accent, density, language): the ticket "Profile and preferences (server)" that the merged accounts spec places before TOKI-078 and that has no number yet (concern 5). It owns the request that saves them. This work owns the three notification switches and their request only, and the two requests do not share a route or a table.
  - The switch "Email me about missed mentions": phase 5 (AC-123, D-016). The schemas refuse the key (R2).
  - What "Desktop notifications" means for the browser's permission, and one device's permission: TOKI-074 (D-142).
  - Guests (phase 5).

- R4. The table `notification_preferences` (a Drizzle table in `modules/notifications/schema.ts` beside `devices`, not exported from the module's `index.ts`, and one migration written for it, `<number>_notification_preferences`, forward-only, TOKI-005 R11): `user_id` uuid primary key with a foreign key to `users(id)`, `workspace_id` uuid not null with a foreign key to `workspaces(id)` (every table carries it, D-004; both keys are written as SQL in the migration because they cross a module boundary, TOKI-019 R22; `ON DELETE RESTRICT`), `desktop`, `sound` and `mentions_in_muted` boolean null, and `updated_at` timestamptz not null with no database default (the server writes the time from the clock, TOKI-019 R6). Check: a database test reads the columns, their types, the nullability and the two keys from the catalog; two rows for one user are refused; a row with a null in each of the three columns is accepted; `db:generate` reports no change. The test "R23: one TRUNCATE empties every table" in `apps/server/tests/conversation-tables.db.test.ts` names its tables in one `TRUNCATE` with no `CASCADE`, and Postgres refuses it when a table that points to a named table is not named, even when it is empty. - R5. The route `PATCH /api/v1/notifications/preferences` in the `/api/v1` scope, registered by `notifications` (a valid session, as every route that is not marked public, TOKI-022 R24; a request with a foreign `Origin` is refused by the rule that covers every `PATCH`, TOKI-022 R46). It takes `SaveNotificationPreferencesBodySchema` and answers 200 `SaveNotificationPreferencesResponseSchema`: the values that apply after the save (all three, defaults filled in) and `number`, the number of the event that the save wrote, or null when it wrote none. The person is always the signed-in one: no route names another person, and no route reads or writes another person's switches (the values are private, D-142). A body that fails the schema is 400 `validation_failed` and writes nothing. A deactivated account never reaches the route: the session check answers 401 `account_deactivated` first (TOKI-022 R27). A server fault is the `internal_error` of TOKI-004, and the answer and the log carry no stack. What a save writes depends on two comparisons (R6): the patch against the stored columns decides whether a row is written, and the patch against the values that apply decides whether an event is written. So a save has one of three results, all 200: (a) every key sent equals a value that is already stored: nothing is written, no row, no event, nothing published, `number` null; (b) a key is stored that was not stored before (the column was null) or that differs from the stored value, and no value that applies changes, for example a person who chooses `sound: false` while the default is `false`: the row is written so that the choice is kept when a default changes later (Design), no event is written and `number` is null; (c) a value that applies changes: the row and one event are written and `number` is the event's number. A retry after a lost answer is therefore safe: it finds the stored values and is a result (a) (as D-111 for a repeated press). A save never changes the switch for any reason other than its own body: the level or Mute of a conversation does not write it (D-088, AC-039). There is no `GET`: the first load (R3) and the event (R7) are how a client reads the values (Decided in this spec, Design). Check: with two sessions, a save by one changes the row of that person and no row of the other; each refused body is 400 `validation_failed` and the row is unchanged; no session is 401; a foreign `Origin` is 403 `origin_not_allowed`; a second save of the values already stored is 200 with `number` null and the row count, the event count and `updated_at` are unchanged; a first save of `{ sound: false }` while the default of `sound` is `false` is 200 with `number` null, one row with `sound` false and no event; the route list holds exactly one route for the prefix `/notifications/preferences` and no other method.
- R6. `saveNotificationPreferences(tx, deps, input)` in `modules/notifications/preferences.ts` is the one function that writes the table; the route of `preferences.routes.ts` in the same module calls it, so `index.ts` does not export it. `input` is `{ userId, workspaceId, patch }` with the `patch` of R2; `deps` is `PreferencesDeps` = `{ clock, recordChange, getLastEventNumber }`, given by `app.ts`. `notifications` imports no other module (R9), so it declares its own structural types for `recordChange` and for the change it passes, as `realtime` does with `EventChange` (TOKI-038), and `app.ts` passes the real `recordChange` of `conversations`, so the compiler checks that the two agree; `getLastEventNumber` of TOKI-036 R19 is passed in the same way, as `members` does for TOKI-056. Inside the caller's transaction, in this order: (1) one statement inserts a row of nulls for the person (`user_id`, `workspace_id`, `updated_at` from `clock.now()`, the three switch columns null) `on conflict (user_id) do nothing`, so the row exists and the next statement has a row to lock for a person who has never saved, and a second first save waits here on the unique index until the first commits; (2) the row is read `FOR UPDATE`: these are the stored columns, and the values that apply before the save are the stored columns resolved with the defaults of R1 (null gives the default); (3) a key of the `patch` is written when its stored column is null or differs from the sent value; when no key is written the function stops and returns `{ stored: false, changed: false, preferences, number: null }` (this can only happen for a row that existed before step 1, so the row of nulls of step 1 is never left empty); (4) otherwise one statement updates only the columns of the keys to write (so two saves of different switches that overlap keep both, and the second waits on the row lock of the first until it commits) and `updated_at` from `clock.now()`, returning the three stored columns, which are resolved with the defaults to the values that apply after the save; (5) when the values that apply after the save equal the values that apply before it, the function returns `{ stored: true, changed: false, preferences, number: null }` and writes no event; (6) otherwise `deps.recordChange(tx, change)` is called once, as the last write, with the change of R7 (`preferences` are the values that apply after the save, not the values that were read in step 2), so the counter lock of TOKI-036 R18 is the last lock taken; (7) `deps.getLastEventNumber(tx, workspaceId)` is read, which is the number of the event just written because this transaction holds the counter row until it ends, and the function returns `{ stored: true, changed: true, preferences, number }`. The function does not lock the account row: a deactivation holds `FOR NO KEY UPDATE` on it, which the key check of this table\'s insert does not conflict with, so the two never wait for each other, and a save that races a deactivation leaves a harmless row that the session check keeps nobody from reading (Decided in this spec, concern 7). Check: a transaction that calls the function and then throws leaves no row and no event; a first save of `{ sound: true }` while the default of `sound` is `false` writes one row with `sound` true and the other two columns null, one event, and returns the values with the defaults filled in; a second save of `{ desktop: false }` leaves one row with both columns set and one more event; with two connections, two overlapping saves of different keys end with both columns set and two events in commit order; with two connections, two first saves of the same key and value end with one row and one event, and the second returns `number` null; a save of the stored values writes nothing and returns `number` null; a first save of the value that equals the default (for each of the three keys) stores the column and writes no event; a test that chooses the default value, then changes the default constant (the test replaces the constant\'s value for the one case), still reads the chosen value from `loadNotificationPreferences` (R8); a save of a switch back to its default value is a change when the stored column was the other value and writes an event.

## Design
### The path of one change
1. On the laptop Sam turns "Play a sound" off in Preferences. The screen calls `save({ sound: false })` of R12.
2. The route (R5) calls `saveNotificationPreferences` in one transaction: it makes sure the person's row exists and locks it, compares the patch with the stored columns, updates only the named columns, calls `recordChange` last when a value that applies changed, and reads the number of the event (R6).
3. The event handler writes `preferences.changed` for Sam alone (R7). The gateway sends it to every connection of Sam; each one's sync engine applies it as `preferences_set` with the event's number (R10). The saving device applies the answer, which carries the same number, through the same rule, so whichever arrives second changes nothing.
4. Sam's phone, with Toki open, now holds `sound: false` and the code of TOKI-073 and TOKI-075 that reads the value obeys it. If `mentionsInMuted` changed, the muted-row rule of TOKI-054 redraws in the same render (R11).
5. A device that was closed reads the first load (R3) and then the events after its number. A device that was away longer than the log's retention (7 days, TOKI-036) reloads, and the first load holds the values.
6. Server-side, when a message is sent, the decision code reads `loadNotificationPreferencesFor` for the recipients (R8). It reads the committed row, so a save and a message are ordered by commit.

### Decided in this spec
- A table of its own, `notification_preferences`, not three columns of `users`. The accounts spec (TOKI-019 concern 8) says that TOKI-102 adds its own columns. A separate table keeps `users` (read by sign-in, the member list and the Admin page) untouched, lets the row be created on the first save, and gives the "Profile and preferences (server)" ticket the freedom to change its own columns without touching this one; the one account row is not locked by a save (R6).
- Nullable columns, not a stored copy of the defaults. A null means "not chosen", so a person who never touched a switch follows the default, and a change of the default of `desktop` or `sound` (concern 1) needs no backfill and does not silently overwrite what a person chose. A person who has chosen keeps the choice, even when the choice equals the default of the day: a save stores a key whose column is null (R6 step 3), and only the event depends on the values that apply (R6 step 5).
- A user event, not a workspace event. These values are the person's own and nobody else sees them (D-142), as with `settings.changed` (TOKI-038 R16). The payload carries all three values, so a client applies a whole state and never has to merge one key into an older state: the last event wins whatever the order of arrival, and the order is the number.
- The route is `PATCH /api/v1/notifications/preferences`, in the module that the later notification tickets will extend (`devices`, TOKI-074), not under `/members/me`, so the other-preferences request (concern 5) and this one never share a path or a body. A `PATCH` takes any subset of the keys, so a Preferences switch sends one key and cannot overwrite the others that another device has just changed.
- No `GET`. The first load carries the values and the event keeps them fresh; a second way to read the same value would need its own ordering rule. A client that lost an answer sends the save again, which is safe (R5).
- One `desktop` switch for desktop and phone. The prototype has one switch, `sw('desktop', ...)`, in the object `n:{desktop:true,sound:false,email:true,mentions:true}` (the third switch is the key `mentions`), and changes only the label on a phone ("Push notifications"); D-142 says one set of switches for the person. The label is TOKI-078's.
- A save that changes no value that applies is not an event. It would send an event that nobody needs, with a number that a client could mistake for a newer state. The answer is 200 with `number` null. Whether it writes a row depends on the stored columns, not on the values that apply (R5, R6).
- The row is created before it is locked (R6 step 1): `FOR UPDATE` locks nothing for a person with no row, so without it two first saves would both read "no row", and the second would write an event for an unchanged value.
- The conversation store holds the value (R10). It is the store that already holds `user`, the first load, the refresh and the reset, and TOKI-054 already built `mentionsInMuted` in it; a second store would need its own reset, refresh and ordering.

### Hand-offs
- TOKI-073 (decision engine): server side it calls `loadNotificationPreferencesFor` (R8); client side it reads `getNotificationPreferences()` of the store. It decides what the switches mean for a toast, a push and a sound: this work only stores them. Whether a mention in a muted conversation notifies is `mentionsInMuted` (D-088, AC-039); the level and Mute never change the switch: only a save of this work does (D-088, AC-039; R5). D-103 says what the level and Mute decide (toast, push, sound, badge, bold), not the switch.
- TOKI-074 (Web Push) and TOKI-075 (sound): read the value as TOKI-073 gives it; the browser's push permission and the registration of one device are theirs (D-142).
- TOKI-076 (Pause and Focus): separate. It holds every notification whatever the switches say (D-072) and stores its own state.
- TOKI-078 (Preferences screen): draws the three switches, labelled as FR-44 words them, with `useNotificationPreferences` (R12); it owns the layout and the phone's label.
- TOKI-065 (Activity, server): the Activity items are made from mentions, replies and reactions whatever the switches are (D-174 says the items are still created in a muted conversation, with no toast, push or sound). It reads nothing of this work unless its spec says an item depends on a switch.
- "Profile and preferences (server)" (no number): owns the saves of the other preferences (concern 5).
- TOKI-054: this work is the one caller of its setter, through `bindMentionsInMuted` (R11), and changes no rule of it. TOKI-078 does not call the setter.
