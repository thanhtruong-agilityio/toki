# Notification preferences (server) design

Date: 2026-11-25 · Status: draft for review (concern 1 is open for the product owner)
Intent: docs/intents/notification-preferences-server.md (Thanh Truong)
Ticket: TOKI-102

## Goal
A person's three notification switches must be kept on the server, belong to the person and not to a device, and reach every device the person has open at once. This work builds the whole path: the stored switches, the request that saves a change, the event that tells the person's other devices, the value in the first load, the value held by the client, and the one function that the later notification code calls to read the switches of any person. It does not draw the switches and does not obey them.

## Scope
- In:
  - Shared definitions: the three names, the defaults, the request, the answer and the event payload, and one key of the bootstrap answer (R1 to R3).
  - The server: the table, the one route, the one write function, the change and the event, the read for the bootstrap and the read for other server code (R4 to R9).
  - The client: the API method, the value in the conversation store, the event, the seam for the saving device, the hook that a screen reads and saves through, and the connection to the muted-row rule that TOKI-054 already built (R10 to R13).
  - The texts that this work needs, which are only its errors (R14).
- Out (not now):
  - The Notifications section of Preferences, its labels (the phone's "Push notifications" form included) and its layout: TOKI-078. This work gives it the hook (R12) and nothing else.
  - Who gets a toast, a push or a sound: TOKI-073 reads the switches through `getNotificationPreferencesFor` (R8) and the held value (R10). The Web Push registration, the browser permission and the card that offers notifications: TOKI-074. Sound and in-app toasts: TOKI-075. Pause and Focus time: TOKI-076. None of them is built here.
  - Every other saved preference of a person (display name, job title, time zone, look, accent, density, language): the ticket "Profile and preferences (server)" that the merged accounts spec places before TOKI-078 and that has no number yet (concern 5). It owns the request that saves them. This work owns the three notification switches and their request only, and the two requests do not share a route or a table.
  - The switch "Email me about missed mentions": phase 5 (AC-123, D-016). The schemas refuse the key (R2).
  - What "Desktop notifications" means for the browser's permission, and one device's permission: TOKI-074 (D-142).
  - Guests (phase 5).

The values of `desktop` and `sound` are whatever the product owner answers in concern 1 (D-176 is not decided); they are written in this one constant and nowhere else, and no other file in the repository holds a default of a switch. Check: a test reads the three keys in order; a test reads `mentionsInMuted` as `true`; the reads of R8, the bootstrap of R9 and the store of R10 each give exactly this constant for a person who never saved; every other test of this work builds its expected values from the constant, so none of them changes when concern 1 is answered.
- R2. The same file holds the schemas. `NotificationPreferencesSchema` is strict with the three booleans, all required. `SaveNotificationPreferencesBodySchema` is strict with the same three keys, each optional and a boolean, and at least one key must be present; a body with another key (among them `email`), a key that is not a boolean, `null` for a key, or no key at all is refused. `SaveNotificationPreferencesResponseSchema` is strict and is `{ notificationPreferences: NotificationPreferencesSchema, number: integer >= 1 or null }`. `NotificationPreferencesChangedDataSchema` is `NotificationPreferencesSchema`. Check: a parse test for each refused body (an empty object, `{ email: true }`, `{ sound: "yes" }`, `{ sound: null }`, `{ desktop: true, extra: 1 }`), for each accepted body (one key, two keys, three), for an answer with a missing key, and for an answer with `number` null.
- R3. The bootstrap answer carries the person's own values. `BootstrapResponse` of `packages/shared/src/bootstrap/schemas.ts` gains the required key `notificationPreferences: NotificationPreferencesSchema`, at the top level next to `user`, because the values belong to the signed-in person and to no member of the list. The rule of TOKI-031 R12 (a later ticket adds its field to the schemas, to the entry of the answer and to the tests of the bootstrap in its own change) is followed here. Check: the strict parse of the bootstrap answer fails when the key is missing and when it holds a fourth key; the fixture of the bootstrap tests has the key.

The server
- R4. The table `notification_preferences` (a Drizzle table in `modules/notifications/schema.ts` beside `devices`, not exported from the module's `index.ts`, and one migration written for it, `<number>_notification_preferences`, forward-only, TOKI-005 R11): `user_id` uuid primary key with a foreign key to `users(id)`, `workspace_id` uuid not null with a foreign key to `workspaces(id)` (every table carries it, D-004; both keys are written as SQL in the migration because they cross a module boundary, TOKI-019 R22; `ON DELETE RESTRICT`), `desktop`, `sound` and `mentions_in_muted` boolean null, and `updated_at` timestamptz not null with no database default (the server writes the time from the clock, TOKI-019 R6). A column that is null means "this person has not chosen": the value then is the default of R1. A person who never saved has no row. The row is changed only by `saveNotificationPreferences` (R6). Check: a database test reads the columns, their types, the nullability and the two keys from the catalog; two rows for one user are refused; a row with a null in each of the three columns is accepted; `db:generate` reports no change.
- R5. The route `PATCH /api/v1/notifications/preferences` in the `/api/v1` scope, registered by `notifications` (a valid session, as every route that is not marked public, TOKI-022 R24; a request with a foreign `Origin` is refused by the rule that covers every `PATCH`, TOKI-022 R46). It takes `SaveNotificationPreferencesBodySchema` and answers 200 `SaveNotificationPreferencesResponseSchema`: the values that apply after the save (all three, defaults filled in) and `number`, the number of the event that the save wrote. The person is always the signed-in one: no route names another person, and no route reads or writes another person's switches (the values are private, D-142). A body that fails the schema is 400 `validation_failed` and writes nothing. A deactivated account never reaches the route: the session check answers 401 `account_deactivated` first (TOKI-022 R27). A server fault is the `internal_error` of TOKI-004, and the answer and the log carry no stack. A save that changes no value (every key sent equals the value that applies now) is 200 with the values and `number: null`, writes no row, no event, and publishes nothing, so a retry after a lost answer is safe (D-111). There is no `GET`: the first load (R3) and the event (R7) are how a client reads the values (Decided in this spec, Design). Check: with two sessions, a save by one changes the row and the answer of the other person's own save is untouched; each refused body is 400 `validation_failed` and the row is unchanged; no session is 401; a foreign `Origin` is 403 `origin_not_allowed`; a save of the held values is 200 with `number` null and the table's row count, the event count and `updated_at` are unchanged; the route list holds exactly one route for the prefix `/notifications/preferences` and no other method.
- R6. `saveNotificationPreferences(tx, deps, input)` in `modules/notifications/preferences.ts`, exported from `index.ts`, is the one function that writes the table. `input` is `{ userId, workspaceId, patch }` with the `patch` of R2; `deps` is `PreferencesDeps` = `{ clock, recordChange, getLastEventNumber }`, given by `app.ts` (`notifications` imports no other module, so `getLastEventNumber` of TOKI-036 R19 is passed in, as `members` does for TOKI-056). Inside the caller's transaction, in this order: (1) the person's row is read `FOR UPDATE` (none is a row of nulls) and resolved with the defaults of R1 to the values that apply now; (2) when every key of the `patch` equals the value that applies now, the function stops and returns `{ changed: false, preferences, number: null }`, having written nothing; (3) otherwise one statement upserts the row: an insert with the keys of the `patch` and null for the others, `on conflict (user_id) do update` setting only the columns that the `patch` names (so two saves of different switches that overlap keep both, and the second waits on the row lock of the first until it commits) and `updated_at` from `clock.now()`, returning the three stored columns, which are resolved with the defaults to the values that apply after the save (the event and the answer carry these, not the values read in step 1); (4) `deps.recordChange(tx, change)` is called once, as the last write, with the change of R7, so the counter lock of TOKI-036 R18 is the last lock taken; (5) `deps.getLastEventNumber(tx, workspaceId)` is read, which is the number of the event just written because this transaction holds the counter row until it ends, and the function returns `{ changed: true, preferences, number }`. The function does not lock the account row: a deactivation holds `FOR NO KEY UPDATE` on it, which the key check of this table's insert does not conflict with, so the two never wait for each other, and a save that races a deactivation leaves a harmless row that the session check keeps nobody from reading (Decided in this spec, concern 7). Check: a transaction that calls the function and then throws leaves no row and no event; a first save of `{ sound: true }` writes one row with `sound` true and the other two columns null, one event, and returns the values with the defaults filled in; a second save of `{ desktop: false }` leaves one row with both columns set and one more event; with two connections, two overlapping saves of different keys end with both columns set and two events in commit order; a save equal to what applies (also when the stored column is null and the default equals the sent value) writes nothing and returns `number` null; a save of a switch back to its default value is a change when the stored column was the other value.
- R7. The change and the event. `Change` of `modules/conversations/changes.ts` gains a member (it is a union of the conversation change and the status change of TOKI-056 R8, and this work adds a third, so no existing reader sees a new field): `NotificationPreferencesChange` is `{ type: "notification_preferences_changed"; actorId: string; workspaceId: string; userIds: readonly [string]; at: Date; preferences: NotificationPreferences }`, with no `conversationId`; `actorId` and the one id in `userIds` are the person, `at` is `new Date(clock.now())`, and `preferences` holds the three values that apply after the save, not only the keys that were sent. The event handler of TOKI-038 R20 gets one row in its table: `notification_preferences_changed` writes the event `preferences.changed`, scope `user` (the person), payload `NotificationPreferencesChangedDataSchema`, with `recordEvent` (`workspaceId` and `userId` from the change, `at`, no `conversationId`) and no read of the database; its structural `EventChange` gains a member with the same fields. The registry of TOKI-038 R12 (`packages/shared/src/realtime/events.ts`) gains the kind `preferences.changed` with that schema, and the table `kinds.ts` gets a row saying that the kind changes nobody's map; its test that every kind has a row stays true. The system-line handler of TOKI-037 writes no line for this type, and the Activity handler of TOKI-065 reads nothing of it. A user-scope event goes to every connection of that person and to nobody else (TOKI-038 R16), and a device that was offline reads it again from the log, because a user-scope event is replayed to its person (TOKI-039). Check: with the fake gateway sockets of TOKI-038 R18, a save by Sam from tab 1 is received by Sam's tab 2 and by Sam's phone as one `preferences.changed` each, in number order, and a second person who is connected receives nothing (the check TOKI-038 R16 makes for `settings.changed`); the payload passes the schema and holds all three values when one key was sent; a transaction rolled back after the call writes no event; no event is written for a save that changes nothing; the registry test, the kinds test and the export-list tests pass; no `system` message exists after a save; `pnpm typecheck` passes with the handlers of TOKI-037 and TOKI-038 as they narrow the union.
- R8. What other server code reads. `getNotificationPreferences(client, userId)` and `getNotificationPreferencesFor(client, userIds)` of `modules/notifications/preferences.ts`, exported from `index.ts`. The first returns `NotificationPreferences` (defaults filled in; a person with no row gets the defaults). The second takes any number of ids, reads them in one statement (`where user_id = any(...)`) and returns a `ReadonlyMap<string, NotificationPreferences>` that holds an entry for every id given, defaults for the ids with no row, so the code that decides the recipients of a message in a channel of 5,000 people makes one read and never one for each person (TOKI-073 is the first reader, Hand-offs). Neither function checks an account's status: who may be notified at all is the caller's rule. Check: with rows for two of three people, the map has three entries, two stored (null columns resolved with the defaults) and one default; an empty list returns an empty map and sends no statement; a list of 1,000 ids is one statement (a spy on the client).
- R9. The bootstrap read and the wiring. `buildBootstrap` of `bootstrap/build.ts` calls `getNotificationPreferences(tx, user.id)` in its read-only transaction, for the signed-in person only, and puts the answer at the key of R3; the read is one more statement and the order and the content of the other keys are unchanged. `app.ts` registers the route, passes `recordChange`, the clock and `getLastEventNumber` to it, and `modules/notifications/index.ts` exports the route registrar, `saveNotificationPreferences` (for the one other caller that may need it, none is planned), and the two reads of R8; `main.ts` is not changed. The table is not exported. A log line of this work carries the user id and the words "preferences changed" and no value of a switch. Check: the bootstrap of a person with no row holds the defaults; of a person who saved `{ sound: true }` holds that value and the defaults for the others; of another person is not affected; the bootstrap of person A never holds B's values (a test with two people and different values); the route-list test lists the one route; a search of `modules/notifications/` for an import of another module finds none.

The client
- R10. The value in the conversation store. The `BootstrapResponse` that the store of TOKI-032 holds in `user`, `workspace` and `people` now also gives `notificationPreferences`, which the store keeps in its state as `notificationPreferences` (`NotificationPreferences`, `null` until the first load has filled it) with `getNotificationPreferences()` (a snapshot read: the same object while nothing changed). ## Design
### The path of one change
1. On the laptop Sam turns "Play a sound" off in Preferences. The screen calls `save({ sound: false })` of R12.
2. The route (R5) calls `saveNotificationPreferences` in one transaction: it reads the row and the values that apply, upserts only the named column, calls `recordChange` last, and reads the number of the event (R6).
3. The event handler writes `preferences.changed` for Sam alone (R7). The gateway sends it to every connection of Sam; each one's sync engine applies it as `preferences_set` with the event's number (R10). The saving device applies the answer, which carries the same number, through the same rule, so whichever arrives second changes nothing.
4. Sam's phone, with Toki open, now holds `sound: false` and the code of TOKI-073 and TOKI-075 that reads the value obeys it. If `mentionsInMuted` changed, the muted-row rule of TOKI-054 redraws in the same render (R11).
5. A device that was closed reads the first load (R3) and then the events after its number. A device that was away longer than the log's retention (7 days, TOKI-036) reloads, and the first load holds the values.
6. Server-side, when a message is sent, the decision code reads `getNotificationPreferencesFor` for the recipients (R8). It reads the committed row, so a save and a message are ordered by commit.

### Decided in this spec
- A table of its own, `notification_preferences`, not three columns of `users`. The accounts spec (TOKI-019 concern 8) says that TOKI-102 adds its own columns. A separate table keeps `users` (read by sign-in, the member list and the Admin page) untouched, lets the row be created on the first save, and gives the "Profile and preferences (server)" ticket the freedom to change its own columns without touching this one; the one account row is not locked by a save (R6).
- Nullable columns, not a stored copy of the defaults. A null means "not chosen", so a person who never touched a switch follows the default, and a change of the default of `desktop` or `sound` (concern 1) needs no backfill and does not silently overwrite what a person chose. A person who has chosen keeps the choice.
- A user event, not a workspace event. These values are the person's own and nobody else sees them (D-142), as with `settings.changed` (TOKI-038 R16). The payload carries all three values, so a client applies a whole state and never has to merge one key into an older state: the last event wins whatever the order of arrival, and the order is the number.
- The route is `PATCH /api/v1/notifications/preferences`, in the module that the later notification tickets will extend (`devices`, TOKI-074), not under `/members/me`, so the other-preferences request (concern 5) and this one never share a path or a body. A `PATCH` takes any subset of the keys, so a Preferences switch sends one key and cannot overwrite the others that another device has just changed.
- No `GET`. The first load carries the values and the event keeps them fresh; a second way to read the same value would need its own ordering rule. A client that lost an answer sends the save again, which is safe (R5).
- One `desktop` switch for desktop and phone. The prototype has one value, `n.desktop`, and changes only the label on a phone ("Push notifications"); D-142 says one set of switches for the person. The label is TOKI-078's.
- A save that changes nothing is not an event. It saves a row and an event that nobody needs, and a number that a client could mistake for a newer state. The answer is 200 with `number` null.
- The conversation store holds the value (R10). It is the store that already holds `user`, the first load, the refresh and the reset, and TOKI-054 already built `mentionsInMuted` in it; a second store would need its own reset, refresh and ordering.

### Hand-offs
- TOKI-073 (decision engine): server side it calls `getNotificationPreferencesFor` (R8); client side it reads `getNotificationPreferences()` of the store. It decides what the switches mean for a toast, a push and a sound: this work only stores them. Whether a mention in a muted conversation notifies is `mentionsInMuted` (D-088, AC-039); the level and Mute never change the switch (D-103).
- TOKI-074 (Web Push) and TOKI-075 (sound): read the value as TOKI-073 gives it; the browser's push permission and the registration of one device are theirs (D-142).
- TOKI-076 (Pause and Focus): separate. It holds every notification whatever the switches say (D-072) and stores its own state.
- TOKI-078 (Preferences screen): draws the three switches, labelled as FR-44 words them, with `useNotificationPreferences` (R12); it owns the layout and the phone's label.
- TOKI-065 (Activity, server): the Activity items are made from mentions, replies and reactions whatever the switches are (D-174 says the items are still created in a muted conversation, with no toast, push or sound). It reads nothing of this work unless its spec says an item depends on a switch.
- "Profile and preferences (server)" (no number): owns the saves of the other preferences (concern 5).
- TOKI-054: this work calls its setter (R11) and changes no rule of it.

## Data safety
- The switches are a person's own settings and are private: no route and no event gives them to another person, and the bootstrap holds only the signed-in person's.
- The log lines carry the user id and the words "preferences changed"; they never carry another person's data.
- Tests use made-up names and values.

## Open questions from the intent
- What are "Desktop notifications" and "Play a sound" set to for an account that has never changed them? Not answered. Carried forward as concern 1.
- Where are the switches stored, and how does a second device learn of a change at once? Answered: a table of its own with nullable columns, the user event `preferences.changed` with its number, and the first load (R4, R7, R9, R10; concerns 2 and 3).
- Who owns the request that saves the other preferences, and where is the line with this one? Answered: the ticket "Profile and preferences (server)", which has no number yet; this work keeps to the three switches (Scope; concern 5).
- What does a person get when they save the value they already have? Answered: 200 with the values and no event (R5, R6; concern 4).
- Do the switches affect anything other than toast, push and sound? Answered: the @ mark of a muted row, through the setter that TOKI-054 built (R11; the journey of the conversation list says the mark shows while the switch is on). Nothing else is decided; whether an Activity item depends on a switch is TOKI-065's (Hand-offs).

## Areas of concern
1. The defaults of "Desktop notifications" and "Play a sound". Not decided. D-088 decides only "Notify me for @mentions even in muted channels" (on), and D-176, the question about the other two, is Open. Proposal, not a decision: as the prototype starts (`n:{desktop:true,sound:false}`), Desktop notifications on and Play a sound off. Either value is one constant (R1) and no test depends on it, so the answer changes one line; until it is given, the ticket cannot set the two. Owner: Thanh Truong, as product owner.
2. Where the values are stored. Decided in this spec: a table `notification_preferences` with nullable columns and a row only after a first save (Design, "Decided in this spec"). Reason: no backfill, a default can change without overwriting a choice, and `users` is untouched. Owner: Thanh Truong.
3. How the other devices learn of a change. Decided in this spec: a user-scope event `preferences.changed` with all three values, ordered by its number, and the value in the first load, as `settings.changed` does for a person's level, mute and star. No workspace event, because the values are private (D-142). Owner: Thanh Truong.
4. A save that changes nothing. Decided in this spec: 200 with the values and `number` null, no row, no event (R5, R6). Reason: no empty event, and a retry after a lost answer is safe (D-111). Owner: Thanh Truong.
5. Who owns the Preferences page API. Decided: the merged accounts spec (TOKI-019 concern 8, decided by Thanh Truong as product owner on 2026-11-18) places a server ticket "Profile and preferences (server)", which has no number in the plan, before TOKI-078 and TOKI-057, for the display name, job title, time zone, look, accent, density and language, and says that TOKI-102 adds its own columns. This work builds the three notification switches and their request only, on `PATCH /api/v1/notifications/preferences`. The plan owner gives the other ticket its number. Owner: Thanh Truong, for the plan.
6. The wording of the one error text. Decided in this spec: the English is a proposal under D-139 because the prototype has no failure text; the Vietnamese is a draft for TOKI-080. Owner: Thanh Truong.
7. A save that races a deactivation. Decided in this spec: the save does not lock the account row (R6). Its cost is a harmless row for a person who is being deactivated, whose sessions end in the same moment and who can never read it; what a deactivated person is notified of is the decision code's rule (TOKI-073). Owner: Thanh Truong.
