# Status design

Date: 2026-11-23 · Status: draft for review (concern 2 is open for the product owner)
Intent: docs/intents/status.md (Thanh Truong)
Ticket: TOKI-056

## Goal
A person must be able to tell colleagues what they are doing with a short line, and the line must go away by itself. This work builds the whole path: the stored status and its time, the two routes that set and clear it, the job that clears it on time, the event that tells every device and every colleague at once, the person data on the client, the dialog that sets it, the entry in the account menu and the line on the account card. It also fixes the contract that Focus time (TOKI-076), the profile panel (TOKI-057), Preferences (TOKI-078) and People (TOKI-079) use.

## Scope
- In:
  - Shared definitions: the limits, the presets, the "Clear after" choices, the request and answer schemas, the event payload, and two fields on the bootstrap person (R1, R2).
  - The server: the table, the time rule, the routes, the one function that writes a status (`setMemberStatus`), the clearing job and its handler, the change and the event, the bootstrap read (R3 to R10).
  - The client: the API methods, the person data and the event, the hooks, the status dialog and its editor hook, the account menu entry, the account card line, the toasts, the texts, and the one screen that already has a place for the status (the DM header line and the status text in the mention list's row) (R11 to R19).
- Out (not now):
  - Starting, extending and ending Focus time and "restores the earlier status": TOKI-076. This work gives it `setMemberStatus` (R6) and nothing else; what the earlier status is, and what happens when a person sets another status during Focus, is TOKI-076's spec (Hand-offs).
  - Presence and the status text next to the dot: TOKI-055 owns the dot, the hooks and `getDmSubline`; this work gives it the status text for the DM line and the component `StatusText` for the mention row (R17).
  - The profile panel, its status row and its "Set status" button: TOKI-057, which reads R13 and calls R15. The People cards: TOKI-079, same.
  - The "Your status" section of Preferences: TOKI-078 places it on the page; this work gives it the editor hook (R14) and the texts (R19).
  - The More sheet: TOKI-092 draws the registered entry (R16). The command palette action "Set status": TOKI-071 calls `useOpenStatusDialog` (R15).
  - Guests (phase 5). Presence controls: none exist (F34).
  - The look of `Modal`, `Chip` and `Field` (TOKI-012 to TOKI-014); this work uses them.

## Requirements
Shared definitions
- R1. `packages/shared/src/status/` (exported from the package index) holds `limits.ts` with `STATUS_TEXT_MAX` (100), `STATUS_RESTORE_MAX_MS` (172,800,000, R2), the tuple `STATUS_PRESET_IDS` equal to `["meeting", "focusing", "lunch", "commuting", "remote"]` in the order of the prototype and of FR-45 (In a meeting, Focusing, Out for lunch, Commuting, Working remotely), the tuple `STATUS_CLEAR_AFTER` equal to `["never", "30m", "1h", "today"]` (Don't clear, 30 minutes, 1 hour, End of today, AC-127; the prototype's `demo` choice is not here, D-145), and the function `statusTextLength(text)`, which counts code points with `Array.from`, never `.length` (as `isNullOrWithin` of `conversations.ts` does). "Character" in D-172 is read as one code point, the count the repository already uses; a flag or a family emoji is 2 to 7 of them, and the product owner may change the reading by changing this one function. The words of the presets are not here: they are texts (R19). Check: a test reads the five ids and four choices in order; `statusTextLength("a😀")` is 2 and the flag `🇻🇳` is 2; the export-list test of `packages/shared` lists the names; no choice is named `demo`.
- R2. The same folder holds the schemas. `SetStatusBodySchema` is strict and has two shapes. The ordinary shape is `text`, `clearAfter` (one of `STATUS_CLEAR_AFTER`, default `never`) and `timeZone`, an optional string that is required when `clearAfter` is `today` and must pass `isValidTimeZone` of the date and time module (TOKI-094). The restore shape is `text` and `clearAt`, an ISO 8601 string, and is only for the Undo of R14: the server accepts it when the instant is later than now and at most `STATUS_RESTORE_MAX_MS` (a technical bound, two days, with no source in the log; no choice gives more than 25 hours) later, and otherwise answers 400 `validation_failed` on `clearAt`; a body with both `clearAfter` and `clearAt` is a failure. In both shapes `text` is a string that is trimmed and has 0 to `STATUS_TEXT_MAX` code points and no control character (`\p{Cc}`, so no line break and no tab inside); a text that holds only white space and invisible characters (`\p{Z}` and `\p{Cf}`, such as U+200B) counts as empty, and `\p{Cf}` is not refused in a text because the joiner of a family emoji belongs to it. An empty `text` means "clear" (R5). `StatusSchema` is `{ "text": string of 1 to 100 code points, "clearAt": ISO 8601 string or null }`; `SetStatusResponseSchema` is `{ "status": StatusSchema or null, "number": integer or null }`, `number` being the number of the event this request wrote (R6) and `null` when it wrote none. `StatusChangedDataSchema`, the payload of the event of R8, is `{ "userId", "text": string or null, "clearAt": string or null, "reason": "set" | "cleared" | "expired" }` with `text` and `clearAt` both null when `reason` is not `set`. `BootstrapPerson` of `bootstrap/schemas.ts` gains `statusText: string or null` and `statusClearAt: string or null` (R9); it stays strict, and the bootstrap rule that a ticket adds its fields to the schema and its own tests (TOKI-031 R12) is followed here. The name `status` is not used for the text because `status` of a person is already `active` or `deactivated`. Check: a table test of the body schema with `""`, spaces, a text of one U+200B, a text of 100 and of 101 code points, a text with 100 emoji, a text with `\n`, `today` with and without a time zone, `today` with `Mars/Phobos`, an unknown `clearAfter`, an extra key, the restore shape with a past instant, an instant now plus two days plus 1 ms, a good instant, and a body with both `clearAfter` and `clearAt`; the strict parse of the bootstrap answer fails on a person with an added key and passes with the two new ones; a test that the trimmed text is what the schema returns.

The server
- R3. The table `member_statuses` (a Drizzle table in `modules/members/schema.ts`, not exported from the module's `index.ts`, and a migration written for it, TOKI-005): `user_id` uuid primary key with a foreign key to `users(id)`, `workspace_id` uuid not null with a foreign key to `workspaces(id)` (every table carries it, D-004; the job of R7 reads it back to write the event), `text` text not null with a check `char_length(text) between 1 and 100` (the same count as R1, in code points), `clear_at` timestamptz null, `set_at` timestamptz not null. No time column has a database default; the server writes the time from the clock (TOKI-024 R6). A person with no status has no row. The row is changed only by `setMemberStatus` and by the handler of R7. Check: a database test of the migration reads the columns and the check from the catalog; a row of 101 characters and a row of 0 characters are refused by the database; two rows for one user are refused; `db:generate` reports no change.
- R4. The time rule, in `modules/members/status-time.ts`: `computeClearAt(clearAfter: StatusClearAfter, now: number, timeZone?: string): Date | null | "past"` returns `null` for `never`, `new Date(now + 1,800,000)` for `30m`, `new Date(now + 3,600,000)` for `1h`, and for `today` the instant `atLocalTime(now, timeZone, 0, "23:59")` of the date and time module (it returns a number of milliseconds or `null`; the prototype's rule: end of today is 23:59 in the person's zone, `clearAtFor` in `index.html`). `now` is `clock.now()`, a number. It returns `"past"` when that instant is null or not later than `now` (a person who asks at 23:59:30) and the route then answers 400 `validation_failed` with the field `clearAfter` (the rule of `validateFutureInstant`, TOKI-094 R14); the dialog stops this case before the request (R15). The clock is the one of TOKI-008 R19; the function reads no other time. Check, with the `TestClock`: 10:00 gives 10:30 and 11:00; `today` at 10:00 in `Asia/Ho_Chi_Minh` gives 23:59 of that day in the zone, and in `America/New_York` the same wall time of that zone; at 23:58:59 it gives 23:59:00, at 23:59:00 and at 23:59:30 it gives `"past"`; the day the clock is set forward (the zone of TOKI-094 R10) still gives a later instant; no `Date.now` in the file.
- R5. Two routes in the `/api/v1` scope, registered by `members` like the other member routes (a valid session, as everywhere there). `PUT /api/v1/members/me/status` takes `SetStatusBodySchema` and answers 200 `SetStatusResponseSchema`: with a non-empty text it writes the status (R6) and answers `{ status, number }`; with an empty text it clears it and answers `{ status: null, number }`. `DELETE /api/v1/members/me/status` clears it and answers 200 `{ status: null, number }`; a clear when there is no status is 200 `{ status: null, number: null }`, writes nothing and publishes nothing (a retry after a lost answer is safe, D-111). "me" is always the signed-in person: no route names another person's status. A deactivated account is refused with 401 `account_deactivated` (TOKI-022 R27; R6 holds the lock case); a body that fails the schema is 400 `validation_failed`; an offline server error is the `internal_error` of TOKI-004. Two saves of one person end with the later commit as the stored status and the later event as the last one the clients read (D-121, last save wins). Check: with two real sessions of one person, two `PUT` calls leave the second text and clear time and the second call's `number` is above the first's; `PUT` with `"   "` clears; `DELETE` twice is 200 twice with one event and the second answer has `number: null`; a request to `/members/<other id>/status` is 404 `not_found` from the router and a body with a `userId` key is 400 (the body is strict), and both change nothing; a deactivated account gets 401; no session gets 401. These route tests use `createFakeJobQueue()` (TOKI-064 R11); only R7 needs a jobs database.
- R6. `setMemberStatus(tx, deps, input)` in `modules/members/status.ts`, exported from `index.ts` with `getMemberStatus(client, userId)`, is the one function that writes a status; the routes and TOKI-076 call it. `input` is `{ userId, text: string | null, clearAt: Date | null, reason: "set" | "cleared" }` and the result is `{ changed: boolean, number: number | null }`. `deps` is of the type `StatusDeps` = `{ clock, jobs, recordChange, getLastEventNumber }`, given by `app.ts` (`getLastEventNumber` is `getLastEventNumber(client, workspaceId)` of TOKI-036 R19, passed in because `members` imports no other module); `JobDeps` (R7) has these four fields (`jobs` is a base field of TOKI-064 R9; `getLastEventNumber` is added here), so a handler passes its own `deps`. Inside the caller's transaction, in this order: (1) the account row is read `FOR SHARE` (the lock order of TOKI-024 R39: accounts first); when its status is `deactivated` the function throws the 401 `account_deactivated` and writes nothing, so a `PUT` that waited behind a deactivation (which holds `FOR NO KEY UPDATE`, TOKI-024 R39) sees the new status when it gets the lock, and a call from TOKI-076 on a deactivated person writes nothing; (2) the row of `member_statuses` is upserted, or deleted when `text` is null, with `set_at` from the clock and the workspace id of the account; (3) the timer is moved: `deps.jobs.cancelByKey(clearStatusJob, userId, { tx })`, and when `clearAt` is set `deps.jobs.enqueue(clearStatusJob, { userId, clearAt }, { startAfter: clearAt, key: userId, tx })` (TOKI-064 R11, R12, R14), so a rollback leaves neither the row nor the job; (4) `deps.recordChange(tx, change)` once with the change of R8, as the last write, so the counter lock of TOKI-036 R18 is the last lock; (5) `deps.getLastEventNumber(tx, workspaceId)` is read, which is the number of the event just written because this transaction holds the counter row until it ends, and is returned as `number`. A call that clears when there is no row writes and publishes nothing and returns `{ changed: false, number: null }`. Check: a transaction that calls the function and then throws leaves no row, no job and no event; a call with a text writes one row, one job whose `startAfter` is `clearAt` and key is the user id, one change, and returns the number of that event; a second call for the same person leaves one row, no job of the first (`cancelByKey` called, the library's job state `cancelled`) and one more change; a call with `clearAt` null leaves no job; a clear with a row removes it and the job; with two connections, a deactivation that holds its lock and a `PUT` that waits: after the commit the `PUT` is 401 and no row, job or event exists; a call for a deactivated person writes nothing.
- R7. The clearing job. `clearStatusJob = defineJob({ name: "members.clear-status", payload: z.strictObject({ userId: uuid, clearAt: ISO date-time }) })` is declared in `modules/members` and exported from its `index.ts`; its type is in `apps/server/src/job-types.ts` and its handler factory `createClearStatusHandler(deps: JobDeps)` in `job-handlers.ts` (TOKI-064 R9; the payload holds an identifier and a time only, R7 there, and never the text). `JobDeps` already carries `jobs` (the queue; the base of TOKI-064 R9 and its table of `JobDeps` fields, which lists `getLastEventNumber` for this ticket), and this work adds `getLastEventNumber` in `job-deps.ts` and builds it in `buildJobDeps`, so that TOKI-076, which ends Focus in a handler of the worker (TOKI-055 concern 11), can call `setMemberStatus`; `enqueue` and `cancelByKey` with `tx` are used by a worker-mode queue too, and a test of this work proves it. The factory returns `defineHandler(clearStatusJob, async (context, data) => ...)`, and the handler runs in one transaction, `context.db.transaction`: it deletes the row `where user_id = $1 and clear_at = $2 returning workspace_id` (the exact time of the job, so a status that was replaced or cleared since, and a second delivery of the same job, delete nothing); when a row was deleted it calls `deps.recordChange` once with the change of R8 and reason `expired`, as the last write; when none was deleted it does nothing and completes. It reads no clock to decide: the job is handed over at `clearAt` (TOKI-064 R14); `context.clock` gives only the `at` of the change. The retry defaults of TOKI-064 R8 apply; an error message holds the user id and a code, never the text (TOKI-064 R18). Check, on a jobs database (`createJobsTestDb`, TOKI-064 R5) with the library's `TestClock` at `DEFAULT_TEST_INSTANT`: a status with `30m` is present after the clock moves 29 minutes 59 seconds and gone after a further `pollingSeconds` (2), with one `expired` event; a status replaced by another with `1h` before the 30 minutes is still there at the old time (the old job is cancelled, and when a delivery of it is forced the handler deletes nothing); a status cleared by hand leaves no job; the same job run twice gives one event; the payload walk of TOKI-064 R7 passes for the new type; a handler that is given a row whose `clear_at` differs by 1 ms deletes nothing; `setMemberStatus` called with the `deps` of `buildJobDeps` on a worker-mode queue writes the row and the job.
- R8. The change and the event. The `Change` of `modules/conversations/changes.ts` becomes a union of two members, so no existing reader sees a new field: `ConversationChange` is the type as it is on main (`conversationId: string`, its nine `type` values), and `MemberStatusChange` is `{ type: "member_status_changed"; actorId: string; workspaceId: string; userIds: readonly [string]; at: Date; status: { text: string | null; clearAt: string | null; reason: "set" | "cleared" | "expired" } }`, with no `conversationId`; `Change = ConversationChange | MemberStatusChange`, and `RecordChange` is unchanged. `actorId` and the one id in `userIds` are the person, `workspaceId` is the one of the locked account (R6) or of the deleted row (R7), and `at` is `new Date(clock.now())`. A handler that switches on `change.type` and skips what it does not handle needs no change; one that reads `change.conversationId` before the switch gets a compile error and narrows first (Plan changes). The event handler of TOKI-038 R20 gets one row in its table: `member_status_changed` writes the event `status.changed`, scope `workspace`, payload `StatusChangedDataSchema` (`{ userId, text, clearAt, reason }`), with `recordEvent` (`workspaceId` from the change, `at`, no `conversationId`) and no read of the database; its structural `EventChange` becomes the union of its own and a `StatusEventChange` with the same fields as `MemberStatusChange`. The shared registry of TOKI-038 R12 (`packages/shared/src/realtime/events.ts`) gains the kind `status.changed` with that schema, and the table `kinds.ts` gets a row saying that the kind changes nobody's map; its test that every kind has a row stays true. The system-line handler of TOKI-037 writes no line for this type. The event is for everyone signed in to the workspace: it is a status, which FR-45 shows to all colleagues, and the workspace has one tenant (D-009). Check: with the fake gateway sockets of TOKI-038 R18, two connected people and one person with two devices all receive one `status.changed` after a `PUT`, in number order; the payload passes the schema; a transaction rolled back after the call writes no event; the registry test, the kinds test and the export-list tests pass; no `system` message exists after a status change; `pnpm typecheck` passes with the handlers of TOKI-037 and TOKI-038 as they narrow the union.
- R9. The bootstrap read. `listPeople(client, workspaceId, now)` of `modules/members/people.ts` (TOKI-031 R15) takes a third argument, `now: Date`, and also returns, for each person, `statusText` and `statusClearAt` by a left join on `member_statuses` that keeps only a row whose `clear_at` is null or later than `now` (an expired row that the job has not cleared yet, for instance while the worker is stopped, is never returned, concern 6); `Person` gains the two fields. `BootstrapDeps` of `bootstrap/build.ts` gains `clock?: Clock` (default the app's clock, which `routes.ts` passes), and `buildBootstrap` calls `listPeople(tx, workspaceId, new Date(clock.now()))`; the transaction stays read-only and SQL's `now()` is not used (TOKI-008 R19). Both fields are `null` for a person with no status; `statusClearAt` is an ISO 8601 string. The order and the other four fields are unchanged and the read is still one statement. Check: a fixture of five people, two with a status (one with a clear time, one without), one whose time has passed and one deactivated with a status: the answer has the two new keys on every person, the values for the two, `null` for the expired one, and the stored values for the deactivated one (what the screen shows is concern 2); the strict parse passes; the statement count of the bootstrap test is unchanged; with the `TestClock` set 1 ms before `clear_at` the status is returned and at `clear_at` it is not.
- R10. What the module logs and keeps. No log line, no job payload and no error message holds the status text, because it is the person's own words (TOKI-064 R18); lines carry the user id and the reason. The text is stored in the table and sent in the event, the bootstrap and the answer of R5 and nowhere else. `app.ts` registers the two routes, passes `recordChange`, `jobs`, the clock and `getLastEventNumber` to them, and `job-types.ts`, `job-deps.ts` and `job-handlers.ts` list the job, the one field `getLastEventNumber` and the handler (TOKI-064 R9); `main.ts` is not changed. Check: the captured log of a test that sets a status with the text `secret-status-text`, clears it and lets it expire holds no such text; the route-list test lists the two routes; `buildJobHandlers` with fake deps returns the handler for `members.clear-status`.

The client
- R11. `createApiClient` gains `api.members.setStatus(body, signal?)` (`PUT /members/me/status`) and `api.members.clearStatus(signal?)` (`DELETE /members/me/status`), each through the one request core (the 10-second rule of D-126, no retry, the 401 hook) reading the answer with `SetStatusResponseSchema`. Check: the method and path of each; a bad answer is an `invalid_response` error; a 401 reaches the hook.
- R12. The person data carries the status, and an older answer never overwrites a newer event. The `BootstrapPerson` held in the `people` of the conversation store (TOKI-032) now has `statusText` and `statusClearAt`, so the bootstrap and a refresh fill them with no new code. The rule of version is this ticket's own: the number of an event orders the changes of one person's status, and a change is applied only when its number is above the number last applied to that person and above the number of the answer that filled `people` (the bootstrap or the last refresh). TOKI-040 has no cursor and applies no event by its number (its R13), and the engine is the only caller of `applyRemote` (its R15), so this work does not call `applyRemote` and asks TOKI-040 and TOKI-032 for these exact names (Plan changes): (a) the change `person_patch` of `applyRemote`, `{ id, statusText, statusClearAt, number }`, which sets those two fields of that person in `people` and `peopleList` when the person is held and `number` passes the rule above, and otherwise changes nothing; the store keeps one number for each person it patched and drops them when `people` is replaced; (b) the row `status.changed` of the table of R14 of TOKI-040: `person_patch` with `statusText` and `statusClearAt` from `text` and `clearAt`, and `number` the event's number; a person who is not held makes a `refresh`, as the member events do; (c) `sync.patchPerson(id, { statusText, statusClearAt }, number)` and the same `patchPerson` in `tools` of R18 there, the seam for a caller that has no event (the editor, R14), which makes the same `person_patch` through the engine; (d) the change `person_set` (`id`, `role`, `status`) of R15 there merges only `role` and `status` into the held person and keeps every other field, so a role change or a deactivation does not erase `statusText` and `statusClearAt`. Check: a `status.changed` event with a text sets it on a held person and calls the listener once; the same event with `reason` `cleared` sets both to `null`; an event for an unknown person refreshes; the event of save 2 (number 12) first and then `patchPerson` with the answer of save 1 (number 11): the person shows save 2; the answer of save 1 first and then the event of save 2: save 2; an event whose number is not above the bootstrap's changes nothing and calls no listener; a `person_set` for a person with a status keeps the status; the reference of `getPeople()` is kept for a change that changes nothing.
- R13. `useStatusText(userId)` and `useOwnStatus()` in `apps/web/src/status/use-status.ts` read the conversation store with `useSyncExternalStore`. `useStatusText` returns the `statusText` of that person or `undefined` when there is none or no id; `useOwnStatus` returns `{ text, clearAt }` or `undefined` for the signed-in person (`clearAt` as a number of milliseconds). - R14. The editor. `useStatusEditor()` in `apps/web/src/status/use-status-editor.ts` is the one piece of logic of the form and returns `{ text, setText, clearAfter, setClearAfter, applyPreset(id), save(), clear(), busy, current }`. `setText` refuses an input that would take the text over `STATUS_TEXT_MAX` code points (it counts with `statusTextLength`, so a smiling face is one character and the 101st is refused, D-172; a flag counts as the 2 code points of R1; a `maxLength` attribute alone would count UTF-16 units and is not used). `applyPreset(id)` saves at once the text `t("status.preset." + id)` with the `clearAfter` of the form at that moment (concern 4), without waiting for Save. `save()` sends `api.members.setStatus({ text, clearAfter, timeZone })` where `timeZone` is the one that `useDateContext` gives (`Intl.DateTimeFormat().resolvedOptions().timeZone`, the browser's, until TOKI-078 gives the zone the person set, concern 1). Every send first calls `ensureOnline()` (TOKI-093 R17, D-079) and does nothing when it is `false`; while a send runs `busy` is true and a second call does nothing. On success the editor calls `sync.patchPerson(me.id, { statusText, statusClearAt }, number)` with the answer (R12), when the answer's `number` is not null, so the card is right before the event arrives and an older answer never overwrites a newer event, and shows the toast of R18; on failure it shows one plain toast `t("common.error.actionFailed")` and keeps the form, except that the 400 on `clearAfter` shows `t("status.error.todayOver")` (R15). `current` is `useOwnStatus()`. `save()` with an empty text after trimming sends the clear. `clear()` is a reversible action (D-069, concern 3): it runs through `useUndo().run({ action: "clearStatus", text: t("status.toast.cleared"), perform, undo, key: "status" })` of TOKI-093 R10 and R16, `perform` being `api.members.clearStatus()` and `undo` being `api.members.setStatus` with the text that was held and, when it had a clear time, that time as `clearAt` (the restore shape of R2) or `clearAfter: "never"` when it had none; a status whose clear time is not later than the client's `clock.now()` at that moment has no Undo, and its Clear is a plain call with the plain toast. Check: tests with a fake `api`: a text of 100 emoji is kept and a 101st is refused; `applyPreset("lunch")` sends the English preset text with the form's `clearAfter`; `save()` with `today` sends the browser's zone; `save()` with `"  "` calls `clearStatus`; a second call while one runs sends nothing; `ensureOnline` false sends nothing; a failed send keeps the text and shows the error toast; a success changes the store before any event; the answer of save 1 arriving after the event of save 2 leaves save 2 on the card; Clear shows "Status cleared" with Undo, and Undo sends the held text with the held `clearAt` (and with `never` when there was none); Clear of a status whose time has passed shows no Undo.
- R15. The dialog. `StatusDialog` (`apps/web/src/status/StatusDialog.tsx`) is a `Modal` of TOKI-014 titled `t("status.dialog.title")` ("Set your status", the prototype's words), open at every width (TOKI-014 keeps the prototype's centred dialog; the Sheet is only the More sheet). It holds, in this order: the five preset `Chip`s; a text `Field` with the label `t("status.field.custom")` ("Custom status"), focused when the dialog opens, holding the current text when there is one; the `Clear after` select (`t("status.field.clearAfter")`) with the four choices of `STATUS_CLEAR_AFTER`, whose texts are `t("status.clear.never")` "Don't clear", `t("status.clear.30m")` "30 minutes", `t("status.clear.1h")` "1 hour" and `t("status.clear.today")` "End of today", default Don't clear; and the footer with a `Clear` button, drawn only when `current` exists, and a primary `Save` button. The choice "End of today" is disabled when `atLocalTime(clock.now(), timeZone, 0, "23:59")` is null or not later than `clock.now()` (from 23:59 in the person's zone), so the 400 of R4 is not a thing the person meets; a 400 on `clearAfter` that still arrives (the client's clock is ahead) shows `t("status.error.todayOver")` and keeps the form. A preset closes the dialog after a successful save; Save closes it after a successful save; Clear closes it after a successful clear. The dialog has no control for Active, Away or Do not disturb (F34, AC-129). ## Design
### The path of one change
1. The person opens "Set status", chooses a preset or types a text and a "Clear after", and presses Save. The editor sends `PUT /api/v1/members/me/status` with the text, the choice and the browser's time zone.
2. The route works out `clearAt` (R4) and calls `setMemberStatus` in one transaction: it locks the account, writes the row, moves the job, calls `recordChange` last and reads the number of the event (R6).
3. The event handler writes `status.changed` for the workspace (R8). The gateway sends it to every connection; each client's sync engine applies it as `person_patch` with the event's number (R12). The editor of the saving device applies the answer, which carries the same number, through the same rule, so whichever arrives second changes nothing. The account card, the DM header, the mention list, the profile and People show the new text.
4. At `clearAt` the job queue hands the job to the worker within 2 seconds (TOKI-064 R14). The handler deletes the row if it still has that `clear_at`, and writes `status.changed` with `reason` `expired`. The owner's devices that still show the status show the toast (R18).
5. A client that connects or reloads reads the people in the bootstrap, which holds the status and no expired row (R9), then applies the events after its number.

### Decided in this spec
- A table of its own, not columns of `users`. One row per person with a status, deleted when it clears: the readers of `users` (sign-in, the member list, the Admin page) are not touched, a person with no status costs no row, and the lock of the account row is not held by status writes (the account is locked `FOR SHARE` only, R6).
- An event, not a live frame. A status is stored, survives a reload and must agree with the bootstrap's event number, so it belongs in the numbered log; presence, which is not stored, uses live frames (TOKI-055). A device that was offline replays the event; one that was away longer than the log's retention reads the bootstrap, which has the status.
- Last save wins by order of the log. The version is the event number: the PUT answer carries the number of its own event (R2, R6) and a change is applied only when its number is above the one last applied to that person (R12), so an older answer never overwrites a newer event (D-121, AC-128).
- The server computes the time. The client sends "30m", "1h" or "today" and, for "today", its time zone, so a wrong clock on the device cannot set a wrong time and the server's clock (TOKI-008) is the only one tested. The one exception is the Undo of a Clear (R14), which sends back the instant that the server computed and that the client holds, and which the server checks against a two-day bound (R2).
- The cancel is a saving, the equality check is the rule. `cancelByKey` stops a waiting job; the handler deletes only a row whose `clear_at` equals the job's time, so a late, repeated or uncancelled job does no harm (TOKI-064 R13, R14 and concern 7).
- Readers hide an expired row. If the worker is stopped, the bootstrap does not return a status whose time has passed (R9); the connected clients keep showing it until the worker runs again and the event arrives, which is at most the poll of 2 seconds after it starts (concern 6).
- The status text is a person's own words: no log, no job payload (R10), no formatting or link made from it (R17).

5. Storage and delivery. Decided in this spec: a table `member_statuses`, an event `status.changed` for the workspace, the people of the bootstrap carry the two fields, the time is computed by the server (Design). Reason: see "Decided in this spec". Owner: Thanh Truong.
6. The worker lag and an expired row. Decided in this spec: the clearing is handed over within the job queue's poll (2 seconds, TOKI-064 R14 and concern 7) after the time, while the worker runs; a status whose time has passed is never returned by the bootstrap even if the worker was stopped; connected clients may show it until the worker returns. TS-203 reads the card a minute after the time, so the lag does not affect it. A job that failed six times is in `jobs.dead` (TOKI-064 R10) and the operator sees it with `jobs:status`; the row stays hidden from the bootstrap. Owner: Thanh Truong.
7. The "Your status was cleared" toast. Accepted: it shows on each open device of the owner that still showed the status when the event was applied; AC-127 says "its owner sees the toast" and this narrows it by one case, a device that was away and read a fresh bootstrap, which shows no status and so no toast (R18). The narrowing has no source in the log and uses no number and no clock. Owner: Thanh Truong.
8. Focus time and the earlier status. Decided in this spec: TOKI-076 sets and restores the status through `setMemberStatus`, and keeps the earlier status itself (Hand-offs). Which status is restored when the person changed it during Focus is not in the log (F32 says "restores the earlier status") and is for TOKI-076's spec. Owner: Thanh Truong.
