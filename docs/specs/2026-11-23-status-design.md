# Status design

Date: 2026-11-23 · Status: draft for review (concerns 2 and 3 are open for the product owner)
Intent: docs/intents/status.md (Thanh Truong)
Ticket: TOKI-056

## Goal
A person must be able to tell colleagues what they are doing with a short line, and the line must go away by itself. This work builds the whole path: the stored status and its time, the two routes that set and clear it, the job that clears it on time, the event that tells every device and every colleague at once, the person data on the client, the dialog that sets it, the entry in the account menu and the line on the account card. It also fixes the contract that Focus time (TOKI-076), the profile panel (TOKI-057), Preferences (TOKI-078) and People (TOKI-079) use.

## Scope
- In:
  - Shared definitions: the limits, the presets, the "Clear after" choices, the request and answer schemas, the event payload, and two fields on the bootstrap person (R1, R2).
  - The server: the table, the time rule, the routes, the one function that writes a status (`setMemberStatus`), the clearing job and its handler, the change and the event, the bootstrap read (R3 to R10).
  - The client: the API methods, the person data and the event, the hooks, the status dialog and its editor hook, the account menu entry, the account card line, the toasts, the texts, the two screens that already have a place for the status (the DM header line and the mention list) (R11 to R19).
- Out (not now):
  - Starting, extending and ending Focus time and "restores the earlier status": TOKI-076. This work gives it `setMemberStatus` (R6) and nothing else; what the earlier status is, and what happens when a person sets another status during Focus, is TOKI-076's spec (Hand-offs).
  - Presence and the status text next to the dot: TOKI-055 owns the dot, the hooks and `getDmSubline`; this work gives it the status text (R17).
  - The profile panel, its status row and its "Set status" button: TOKI-057, which reads R14 and calls R15. The People cards: TOKI-079, same.
  - The "Your status" section of Preferences: TOKI-078 places it on the page; this work gives it the editor hook (R15) and the texts (R19).
  - The More sheet: TOKI-092 draws the registered entry (R16). The command palette action "Set status": TOKI-071 calls `useOpenStatusDialog` (R15).
  - Guests (phase 5). Presence controls: none exist (F34).
  - The look of `Modal`, `Chip` and `Field` (TOKI-012 to TOKI-014); this work uses them.

## Requirements
Shared definitions
- R1. `packages/shared/src/status/` (exported from the package index) holds `limits.ts` with `STATUS_TEXT_MAX` (100), the tuple `STATUS_PRESET_IDS` equal to `["meeting", "focusing", "lunch", "commuting", "remote"]` in the order of the prototype and of FR-45 (In a meeting, Focusing, Out for lunch, Commuting, Working remotely), the tuple `STATUS_CLEAR_AFTER` equal to `["never", "30m", "1h", "today"]` (Don't clear, 30 minutes, 1 hour, End of today, AC-127; the prototype's `demo` choice is not here, D-145), the number `STATUS_EXPIRED_TOAST_WINDOW_MS` (300,000, R18), and the function `statusTextLength(text)`, which counts code points with `Array.from`, never `.length` (as `isNullOrWithin` of `conversations.ts` does). The words of the presets are not here: they are texts (R19). Check: a test reads the five ids and four choices in order; `statusTextLength("a😀")` is 2; the export-list test of `packages/shared` lists the names; no choice is named `demo`.
- R2. The same folder holds the schemas. `SetStatusBodySchema` is strict: `text` a string that is trimmed and then has 0 to `STATUS_TEXT_MAX` code points and no control character (`\p{Cc}`, so no line break and no tab inside), `clearAfter` one of `STATUS_CLEAR_AFTER` (default `never`), and `timeZone`, an optional string that is required when `clearAfter` is `today` and must pass `isValidTimeZone` of the date and time module (TOKI-094); an extra key is a failure. An empty `text` after trimming means "clear" (R5). `StatusSchema` is `{ "text": string of 1 to 100 code points, "clearAt": ISO 8601 string or null }`; `SetStatusResponseSchema` is `{ "status": StatusSchema or null }`. `StatusChangedDataSchema`, the payload of the event of R8, is `{ "userId", "text": string or null, "clearAt": string or null, "reason": "set" | "cleared" | "expired" }` with `text` and `clearAt` both null when `reason` is not `set`. `BootstrapPerson` of `bootstrap/schemas.ts` gains `statusText: string or null` and `statusClearAt: string or null` (R9); it stays strict, and the bootstrap rule that a ticket adds its fields to the schema and its own tests (TOKI-031 R12) is followed here. The name `status` is not used for the text because `status` of a person is already `active` or `deactivated`. Check: a table test of the body schema with `""`, spaces, a text of 100 and of 101 code points, a text with 100 emoji, a text with `\n`, `today` with and without a time zone, `today` with `Mars/Phobos`, an unknown `clearAfter` and an extra key; the strict parse of the bootstrap answer fails on a person with an added key and passes with the two new ones; a test that the trimmed text is what the schema returns.

The server
- R3. The table `member_statuses` (a Drizzle table in `modules/members/schema.ts`, not exported from the module's `index.ts`, and a migration written for it, TOKI-005): `user_id` uuid primary key with a foreign key to `users(id)`, `text` text not null with a check `char_length(text) between 1 and 100` (the same count as R1, in code points), `clear_at` timestamptz null, `set_at` timestamptz not null. No time column has a database default; the server writes the time from the clock (TOKI-024 R6). A person with no status has no row. The row is changed only by `setMemberStatus` and by the handler of R7. Check: a database test of the migration reads the columns and the check from the catalog; a row of 101 characters and a row of 0 characters are refused by the database; two rows for one user are refused; `db:generate` reports no change.
- R4. The time rule, in `modules/members/status-time.ts`: `computeClearAt(clearAfter, now, timeZone)` returns `null` for `never`, `now + 1,800,000` for `30m`, `now + 3,600,000` for `1h`, and for `today` the instant `atLocalTime(now, timeZone, 0, "23:59")` of the date and time module (the prototype's rule: end of today is 23:59 in the person's zone, `clearAtFor` in `index.html`). It returns `"past"` when that instant is not later than `now` (a person who asks at 23:59:30) and the route then answers 400 `validation_failed` with the field `clearAfter` (the rule of `validateFutureInstant`, TOKI-094 R14). The clock is the one of TOKI-008 R19; the function reads no other time. Check, with the `TestClock`: 10:00 gives 10:30 and 11:00; `today` at 10:00 in `Asia/Ho_Chi_Minh` gives 23:59 of that day in the zone, and in `America/New_York` the same wall time of that zone; at 23:58:59 it gives 23:59:00, at 23:59:00 and at 23:59:30 it gives `"past"`; the day the clock is set forward (the zone of TOKI-094 R10) still gives a later instant; no `Date.now` in the file.
- R5. Two routes in the `/api/v1` scope, registered by `members` like the other member routes (a valid session, as everywhere there). `PUT /api/v1/members/me/status` takes `SetStatusBodySchema` and answers 200 `SetStatusResponseSchema`: with a non-empty text it writes the status (R6) and answers `{ status }`; with an empty text it clears it and answers `{ status: null }`. `DELETE /api/v1/members/me/status` clears it and answers 200 `{ status: null }`; a clear when there is no status is 200 `{ status: null }`, writes nothing and publishes nothing (a retry after a lost answer is safe, D-111). "me" is always the signed-in person: no request names another person's status. A deactivated account is refused as in TOKI-024 (401 `account_deactivated`); a body that fails the schema is 400 `validation_failed`; an offline server error is the `internal_error` of TOKI-004. Two saves of one person end with the later commit as the stored status and the later event as the last one the clients read (D-121, last save wins). Check: with two real sessions of one person, two `PUT` calls leave the second text and clear time; `PUT` with `"   "` clears; `DELETE` twice is 200 twice with one event; a request with another person's id in the path or the body is a 404 or a 400 and changes nothing; a deactivated account gets 401; no session gets 401.
- R6. `setMemberStatus(tx, deps, input)` in `modules/members/status.ts`, exported from `index.ts` with `getMemberStatus(client, userId)`, is the one function that writes a status; the routes and TOKI-076 call it. `input` is `{ userId, text: string | null, clearAt: Date | null, reason: "set" | "cleared" }`. Inside the caller's transaction, in this order: (1) the account row is read `FOR SHARE` (the lock order of TOKI-024 R39: accounts first); (2) the row of `member_statuses` is upserted, or deleted when `text` is null, with `set_at` from the clock; (3) the timer is moved: `deps.jobs.cancelByKey(clearStatusJob, userId, { tx })`, and when `clearAt` is set `deps.jobs.enqueue(clearStatusJob, { userId, clearAt }, { startAfter: clearAt, key: userId, tx })` (TOKI-064 R11, R12, R14), so a rollback leaves neither the row nor the job; (4) `deps.recordChange(tx, change)` once, as the last statement, so the counter lock of TOKI-036 R18 is the last lock. `deps` is `{ clock, jobs, recordChange }`, given by `app.ts`; `members` imports no other module and reads the queue only from the public entry of `jobs` (TOKI-064 R24). A call that clears when there is no row writes and publishes nothing and returns `false`; every other call returns `true`. Check: a transaction that calls the function and then throws leaves no row, no job and no event; a call with a text writes one row, one job whose `startAfter` is `clearAt` and key is the user id, and one change; a second call for the same person leaves one row, no job of the first (`cancelByKey` called, the library's job state `cancelled`) and one more change; a call with `clearAt` null leaves no job; a clear with a row removes it and the job.
- R7. The clearing job. `clearStatusJob = defineJob({ name: "members.clear-status", payload: z.strictObject({ userId: uuid, clearAt: ISO date-time }) })` is declared in `modules/members` and exported from its `index.ts`; its type is in `apps/server/src/job-types.ts` and its handler factory `createClearStatusHandler(deps: JobDeps)` in `job-handlers.ts` (TOKI-064 R9; the payload holds an identifier and a time only, R7 there, and never the text). The handler runs in one transaction: it deletes the row `where user_id = $1 and clear_at = $2 returning` (the exact time of the job, so a status that was replaced or cleared since, and a second delivery of the same job, delete nothing); when a row was deleted it calls `deps.recordChange` once with the change of R8 and reason `expired`, as the last statement; when none was deleted it does nothing and completes. It reads no clock to decide: the job is handed over at `clearAt` (TOKI-064 R14). The retry defaults of TOKI-064 R8 apply; an error message holds the user id and a code, never the text (TOKI-064 R18). Check, on a jobs database (`createJobsTestDb`, TOKI-064 R5) with the library's `TestClock` at `DEFAULT_TEST_INSTANT`: a status with `30m` is present after the clock moves 29 minutes 59 seconds and gone after a further `pollingSeconds` (2), with one `expired` event; a status replaced by another with `1h` before the 30 minutes is still there at the old time (the old job is cancelled, and when a delivery of it is forced the handler deletes nothing); a status cleared by hand leaves no job; the same job run twice gives one event; the payload walk of TOKI-064 R7 passes for the new type; a handler that is given a row whose `clear_at` differs by 1 ms deletes nothing.

## Design
### The path of one change
1. The person opens "Set status", chooses a preset or types a text and a "Clear after", and presses Save. The editor sends `PUT /api/v1/members/me/status` with the text, the choice and the browser's time zone.
2. The route works out `clearAt` (R4) and calls `setMemberStatus` in one transaction: it locks the account, writes the row, moves the job and calls `recordChange` last (R6).
3. The event handler writes `status.changed` for the workspace (R8). The gateway sends it to every connection; each client's sync engine applies it as `person_patch` (R12). The account card, the DM header, the mention list, the profile and People show the new text.
4. At `clearAt` the job queue hands the job to the worker within 2 seconds (TOKI-064 R14). The handler deletes the row if it still has that `clear_at`, and writes `status.changed` with `reason` `expired`. The owner's devices show the toast (R18).
5. A client that connects or reloads reads the people in the bootstrap, which holds the status and no expired row (R9), then applies the events after its number.

### Decided in this spec
- A table of its own, not columns of `users`. One row per person with a status, deleted when it clears: the readers of `users` (sign-in, the member list, the Admin page) are not touched, a person with no status costs no row, and the lock of the account row is not held by status writes (the account is locked `FOR SHARE` only, R6).
- An event, not a live frame. A status is stored, survives a reload and must agree with the bootstrap's event number, so it belongs in the numbered log; presence, which is not stored, uses live frames (TOKI-055). A device that was offline replays the event; one that was away longer than the log's retention reads the bootstrap, which has the status.
- Last save wins by order of the log. No version number: the event numbers decide (D-121, AC-128).
- The server computes the time. The client sends "30m", "1h" or "today" and, for "today", its time zone; it never sends an instant, so a wrong clock on the device cannot set a wrong time and the server's clock (TOKI-008) is the only one tested.
- The cancel is a saving, the equality check is the rule. `cancelByKey` stops a waiting job; the handler deletes only a row whose `clear_at` equals the job's time, so a late, repeated or uncancelled job does no harm (TOKI-064 R13, R14 and concern 7).
- Readers hide an expired row. If the worker is stopped, the bootstrap does not return a status whose time has passed (R9); the connected clients keep showing it until the worker runs again and the event arrives, which is at most the poll of 2 seconds after it starts (concern 6).
- The status text is a person's own words: no log, no job payload (R10), no formatting or link made from it (R17).

### Hand-offs
- TOKI-076 (Focus time): calls `setMemberStatus(tx, deps, { userId, text: "Focusing", clearAt: null, reason: "set" })` when Focus starts, in its own transaction, and when Focus ends calls it with the earlier text and its remaining `clearAt` if that is still in the future and with `text: null` otherwise (the prototype's `endFocus` rule). It keeps the earlier status itself, because it already stores the Focus period. The text "Focusing" is the preset text of the person's language, taken by TOKI-076 from the texts of R19 or sent by the client. What the earlier status is when the person sets a new one during Focus is not decided by the log and is TOKI-076's spec to settle; this work only guarantees that the last call wins (R5, R6).
- TOKI-055 (presence): `getDmSubline` takes the `status` this work supplies (R17); the `trailing` of the mention row is shared (R17 (b)); this work changes no presence code.
- TOKI-057 (profile panel) and TOKI-079 (People): read `useStatusText`; TOKI-057 calls `useOpenStatusDialog` from its own profile's "Set status" button (F31).
- TOKI-078 (Preferences): its "Your status" section uses `useStatusEditor`, `useOwnStatus` and the texts of R19; it owns the layout.
- TOKI-092 (More sheet) and TOKI-071 (command palette): the first reads the registry of R16; the second calls `useOpenStatusDialog`.
- TOKI-064 (job queue): the job `members.clear-status` follows its contract table (declare, handle, register, test with the library's clock).

## Areas of concern
1. What "End of today" means. Decided in this spec: 23:59 in the time zone that the web app already uses for the person's dates (`useDateContext`, the browser's zone), because the prototype's `clearAtFor('today')` is 23:59 of the current day and D-144 says the profile zone is the one the person set, which TOKI-078 builds later and can then replace the source of the zone with no change to the route; a request made at or after 23:59 is refused with a field error (R4). Owner: Thanh Truong.
2. The status of a deactivated person. Not decided. F41 labels a deactivated person "Deactivated" and removes them from People and the mention list; no decision says whether their old status, or a status that a reactivated person had, is shown. Proposal, not a decision: the screens show no status for a person whose account status is `deactivated`, the row is kept and returns when the person is reactivated while it still runs (the job clears it on time either way); `useStatusText` (R13) would return `undefined` for such a person. The other proposal is to delete the row at deactivation, which changes the member-management code of TOKI-024. Question for the product owner: hide it or delete it. Owner: Thanh Truong (product owner).
3. Undo after Clear. Not decided. D-061 gives a reversible action a toast with Undo for 5 seconds; the prototype's `clearstatus` shows the toast "Status cleared" with no Undo; no decision names this action and TOKI-093's table does not list it. Proposal, not a decision: no Undo, as in the prototype, because setting the same status again takes one press; R18 builds this as the interim and adding the Undo is one row in `actionPatterns` of TOKI-093 and the call of the editor. Question for the product owner: Clear with no Undo, or with Undo for 5 seconds. Owner: Thanh Truong (product owner).
4. A preset saves at once, with the form's "Clear after". Decided in this spec: TS-201 has the person choose "In a meeting" and then read it on other screens with no Save step, and the prototype saves a preset at once and closes the dialog (`presetstatus`); it reads the "Clear after" of the Preferences form, not of the modal, which is a fault of the sample, so this spec uses the choice shown in the form that the person is looking at. Owner: Thanh Truong.
5. Storage and delivery. Decided in this spec: a table `member_statuses`, an event `status.changed` for the workspace, the people of the bootstrap carry the two fields, the time is computed by the server (Design). Reason: see "Decided in this spec". Owner: Thanh Truong.
6. The worker lag and an expired row. Decided in this spec: the clearing is handed over within the job queue's poll (2 seconds, TOKI-064 R14 and concern 7) after the time, while the worker runs; a status whose time has passed is never returned by the bootstrap even if the worker was stopped; connected clients may show it until the worker returns. TS-203 reads the card a minute after the time, so the lag does not affect it. A job that failed six times is in `jobs.dead` (TOKI-064 R10) and the operator sees it with `jobs:status`; the row stays hidden from the bootstrap. Owner: Thanh Truong.
7. The "Your status was cleared" toast. Decided in this spec: it shows on each open device of the owner when the event is applied and is not older than 5 minutes (`STATUS_EXPIRED_TOAST_WINDOW_MS`, a technical number with no source in the log), so a device that replays an old event after a long absence stays quiet. Owner: Thanh Truong.
8. Focus time and the earlier status. Decided in this spec: TOKI-076 sets and restores the status through `setMemberStatus`, and keeps the earlier status itself (Hand-offs). Which status is restored when the person changed it during Focus is not in the log (F32 says "restores the earlier status") and is for TOKI-076's spec. Owner: Thanh Truong.
9. Who draws what. Decided in this spec: this work owns the data, the dialog, the editor hook, the menu entry, the card line, the DM header's status and the status in the mention row; the profile, People and Preferences screens are the hand-offs to TOKI-057, TOKI-079 and TOKI-078, and the `trailing` of the mention row is shared with TOKI-055 (R17). Owner: Thanh Truong.
10. The wording. Decided in this spec: the English words are the prototype's; the toast `Status saved · clears {when}` follows the prototype's form with the date and time rules of TOKI-094, where F32 says "clears at 14:00"; the Vietnamese words are a draft and a proposal under D-139, reviewed in TOKI-080 (D-188 on the form of address is open, and these words need no pronoun). Owner: Thanh Truong.
11. Things the build must check, because the code is not on main yet. Decided in this spec: (a) `Change.conversationId` may be made `string | null` without breaking the handlers of TOKI-037 and TOKI-038, which must skip a type they do not handle (R8); if they cannot, the change gets its own optional field instead; (b) `cancelByKey` and `enqueue` with `tx` behave as TOKI-064 R11 to R14 say; (c) `registerEventHandler` of TOKI-040 runs after the engine's effect for the kind (R18). Each is a test of this ticket. Owner: Thanh Truong.
