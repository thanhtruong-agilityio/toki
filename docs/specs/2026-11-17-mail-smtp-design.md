# Sending mail over SMTP design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/mail-smtp.md (Thanh Truong)
Ticket: TOKI-021

## Goal
Sign-in by emailed code and invitations by email both need the server to send mail, and nothing in the server can do it yet. This work adds one mail layer in `apps/server` that sends through an SMTP account named in the configuration, and the mails the first phase needs: the sign-in mail, the invitation mail and the mail that carries a new code for an invitation, in English and Vietnamese (the invitation mails are sent in English, D-180). Later server work calls the layer and writes no mail code of its own.

## Scope
- In:
  - A server module `mail` with three operations, one per mail (R6, R9, R24), and the result they return.
  - The `mail` area of the server configuration: the SMTP host, port, security mode and login, and the sender address and name. The module exports its schema and the root `config.ts` composes it (R1).
  - The three templates, each with a text part and an HTML part, English and Vietnamese, and their texts in the `i18n` package (namespace `mail`).
  - Timeouts, the connection limit, the waiting queue and its limits, the pause after a connection failure, the rule that the layer does not retry, what is logged and what never is.
  - Tests against a real SMTP server started by the test, and one check against Mailpit.
- Out (not now):
  - Choosing the production SMTP account, the sender address and the domain, and any mail-domain setup such as SPF or DKIM: external values of TOKI-096 (R6 of that spec), owner Thanh Truong. This work reads whatever account the configuration names (concern 2).
  - Deciding when a mail is sent, to whom and with which code, and the code rules: TOKI-022 for the sign-in mail; TOKI-024 for the invitation (creating it, the batch of up to 50, "Mail not sent" and Resend, the record of who invited whom); TOKI-097 for accepting it, the page behind Join and its "Resend code" (it creates the new code with `issueInvitationCode` of TOKI-024 R19 and calls `sendInvitationCode` of R24; decided in this spec, concern 11).
  - The Join link itself: TOKI-024 makes the token and builds the address `<origin>/join#<token>` (its R11); TOKI-097 serves the page. This work receives the finished absolute address and puts it in the mail.
  - What a person reads when a mail is not sent: TOKI-022 and TOKI-023 for sign-in, TOKI-024 for an invitation (concern 1).
  - The emergency sign-in link for when mail is down: TOKI-026.
  - A job queue, a worker and retries after a failure: TOKI-064. This layer makes one attempt (R17).
  - Receiving mail, bounce handling, the Mail section of the app, the email about missed mentions (phase 5), a mail service other than SMTP.

## Requirements
- R1. `apps/server/src/modules/mail/` exists, and its `index.ts` is the only entry other code imports. It exports `createMailLayer`, the type `MailLayer` with the three operations of R6, R9 and R24, the type `MailResult` of R6, and the mail configuration schema `mailConfigSchema` with its type `MailConfig`. The root `config.ts` of TOKI-004 composes that schema into the server's areas and imports it from `modules/mail/index.ts` only; `createMailLayer({ config })` takes the `MailConfig` type from the same entry. A search of `apps/server/src` finds no import of a file inside `modules/mail/` from outside it other than through `index.ts`, and no `nodemailer` import outside `modules/mail/`.
- R2. The server configuration of TOKI-004 gets a `mail` area with these variables, defined in "Configuration": `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM_ADDRESS`, `MAIL_FROM_NAME`. The area is registered by the server entry only (R21). Every name is a row of the TOKI-096 inventory and a line of `.env.example`; where the inventory already names a row for the same value, that name is used instead and this list is read with it. A test compares the names the area reads with `.env.example`, as TOKI-004 R13 does.
- R3. With a required variable of the `mail` area missing or empty, or a value that fails its check, the server does not start: it exits with code 1 and writes the variable name to standard error, never the value (TOKI-004 R3, R4). The checks: `SMTP_HOST` is not empty; `SMTP_PORT` is an integer from 1 to 65535; `SMTP_TLS` is one of `none`, `starttls`, `tls`; `MAIL_FROM_ADDRESS` is a well-formed address (R6); `SMTP_USER` and `SMTP_PASSWORD` are either both set or both unset; `MAIL_FROM_NAME` has no line break.
- R4. `SMTP_TLS` `none` is accepted only when the environment name of the server area (the row of the TOKI-096 inventory, TOKI-004 R18) is exactly `development`; with any other value, or none set, the server does not start and names `SMTP_TLS`, so a deployment that forgets the variable fails closed, as the reset scripts of TOKI-003 R10 do. `SMTP_TLS` `none` with `SMTP_USER` set is refused in every environment: a login is never sent in clear. With `starttls` the layer refuses to send when the server does not offer STARTTLS, and with `starttls` or `tls` it checks the server's certificate and its host name; no variable switches the certificate check off. Tests that need a certificate are in Testing; the keys they use are generated by the test run and none is committed.
- R5. Changing only the SMTP and sender variables changes where the mail goes and who it comes from, with no change of code (requirement NFR-12). Test: two test SMTP servers, one configuration for each, differing in host, port and sender; the same call delivers to the server its configuration names, with that sender.
- R6. `sendSignInMail({ to, code, language })` returns a promise of `MailResult` and never throws, never rejects. `MailResult` is `{ ok: true }` or `{ ok: false, reason }` with `reason` one of `invalid_input`, `recipient_rejected`, `auth_failed`, `unavailable`, `rejected` (R16). `language` is `en` or `vi` (the values of `users.language`, which defaults to `en`); any other value returns `invalid_input`. A `code` that is not exactly 6 ASCII digits, or a `to` that is not a well-formed address, returns `invalid_input` and opens no connection. A well-formed address is exactly one address of at most 254 characters: one `@` with text on both sides, and no whitespace, control character, comma, semicolon, angle bracket, quote, parenthesis, bracket or backslash. `to` and the sender are passed to the SMTP client as `{ name, address }` objects, never as one joined string, so `Name <a@b>, c@d` can never mean two recipients. Every operation takes the values above and an optional second argument `{ log }`, a logger of the caller (for example the request's logger, which carries the request id); the layer writes its one line of R14 to it, and to the app logger when it is absent.
- R7. The sign-in mail is addressed to `to`, from `MAIL_FROM_NAME` and `MAIL_FROM_ADDRESS`, with the subject of the key `mail.signIn.subject`. Its text part and its HTML part both hold the code as 6 digits in one piece, with no space or dash inside it, and the sentence that the code works for 10 minutes (D-136). The subject holds no code.
- R8. The sign-in mail holds no link and no button: neither part holds `href`, `<a`, `http://`, `https://`, `www.` or `<img`, and the HTML part has no `<form`, `<button` or `<script` (D-157). The language of the text and the HTML is `language`; an invitation has no language argument (R10).
- R9. `sendInvitationMail({ to, code, workspaceName, inviterName, joinUrl })` returns a `MailResult` as in R6. `joinUrl` is the finished Join address that TOKI-024 builds, `<origin>/join#<token>` (its R11), and the layer does not parse or change it: it must be an absolute `https://` address, or `http://` when the environment name is not `production`, else `invalid_input`; the layer is told the environment by `createMailLayer` (Design). The `#` and the token after it reach the `href` and the text part unchanged. `workspaceName` and `inviterName` must be non-empty after trimming and at most 200 characters, else `invalid_input`; in the subject each name is cut at 40 characters with `…`. The mail names the workspace and the inviter, holds a Join button, shows the 6-digit code in one piece, says that the code works for 10 minutes and that the invitation lasts 7 days (D-149, D-136, D-037).
- R10. The invitation mail is always in English (D-180). The HTML part has the Join button as a link to `joinUrl` with the visible label of the key `mail.invitation.join`, and the text part holds `joinUrl` in full on a line of its own, because a text part has no button. Nothing in either part signs a person in without the code: the HTML part has exactly one `<a>`, the Join button, and no other link tag; the text part holds `joinUrl` once. Names of people are put in as text and cannot be promised free of text that a mail client turns into a link (a name that holds an address or a phone number). `joinUrl` is escaped for an attribute in the HTML part (D-149).
- R11. Every mail is sent as multipart with a text part and an HTML part, in UTF-8, with the header `Auto-Submitted: auto-generated`. The HTML part loads nothing from outside: no image, no style sheet and no font from an address, no tracking pixel, and the only link in it is the one of R10, and the sign-in and new-code mails have none. Vietnamese letters and the subject arrive intact when read back from the receiving server.
- R12. A value that came from a person is never put into the mail as markup or as a header line. `workspaceName` and `inviterName` are escaped in the HTML part, `joinUrl` is escaped for an attribute (a `"` or `&` in it cannot end the attribute), and their line breaks and control characters are replaced by a space in the subject and every other header. Test: a workspace name with `<script>` and an inviter name with a line break followed by `Bcc: x@example.com` give a mail with no `<script>` tag, no `Bcc` header and the names visible as text; a `joinUrl` with `"` and `&` leaves the HTML part with one well-formed `href`; a `joinUrl` of the form `https://toki.example.com/join#<43 characters>` appears in the `href` and on its own line of the text part character for character.
- R13. The layer logs no code, no recipient address, no `joinUrl`, no message body and no SMTP password, on success and on failure, and the transport's own debug output is off. It never logs the message, response, command, rejected-recipient list or stack of an error from a send, because Nodemailer errors and many SMTP replies carry the address; only the fields of R14 are written. Test: with the server's log captured, standard output and standard error captured, and a test SMTP server that accepts, and again with one that refuses and whose reply text repeats the recipient address and the code, the sent code, the recipient address, the `joinUrl` and the password appear nowhere in what was captured.
- R14. Each send writes exactly one log line from the layer. On success: level `info`, the event `mail_sent`, the template name (`sign_in`, `invitation` or `invitation_code`), the duration. On failure: level `warn`, the event `mail_send_failed`, the template name, the `reason` of R6, a `cause` (one of `connect`, `dns`, `tls`, `timeout`, `reply`, `queue_full`, `queue_wait`, `cooldown`, `internal`), the SMTP reply code when there is one, the stage where it failed (one of `connect`, `auth`, `mail_from`, `rcpt_to`, `data`) and the duration. The reply code and the stage are how an operator tells a sender address the account may not use (a 5xx at `mail_from`) from a refused recipient. This line is the one log line of a failed send: a caller (TOKI-022 R8, TOKI-024) writes none of its own for it. A caller that gets `invalid_input` gets one `warn` line with the event `mail_invalid_input` and the template name.
- R15. A send is bounded in time, and the bound is real. The SMTP client is given a connection, greeting and DNS limit of 5 seconds and a socket limit of 10 seconds. A whole-send limit of 30 seconds, which Nodemailer does not have, is a timer of the layer that starts when the send takes one of the 2 slots of R19 and covers the connection, the login and the transfer. When it fires, the layer returns `unavailable` (cause `timeout`) and destroys the connection of that send by closing the transport and building a new one for the next send, so the message cannot be delivered after the caller was told it failed; sends running on that transport at that moment end as `unavailable` too. The limits are inputs of `createMailLayer` so a test can shorten them; the defaults are these. Tests: (a) a test SMTP server that accepts the connection and never answers gives `unavailable` within the greeting limit; (b) a server that answers every command after a delay shorter than the socket limit, so that only the whole-send limit can end the send, gives `unavailable` within that limit, and after it the server shows the connection closed and no message received.
- R16. A failure is sorted into one reason: no connection, DNS failure, TLS failure, timeout and any SMTP 4xx reply -> `unavailable`; reply 530, 534, 535 or 538, or a login refused -> `auth_failed`; a 5xx reply to the recipient (550, 551, 553) -> `recipient_rejected`; any other 5xx reply, including one to `MAIL FROM` (a sender the account may not use) -> `rejected`, told from the others by its stage in the log (R14). Test: one test SMTP server per case answers with the reply and the result is checked.
- R17. The layer makes one attempt per call. A 4xx reply, a timeout or a lost connection is not retried; the same message is not sent twice. Test: a test SMTP server that answers 451 to the first message counts exactly one delivery attempt for one call.
- R18. The server starts and answers `GET /healthz` with the SMTP host unreachable: the layer opens no connection at startup and does not check the account (D-159: mail down must not stop the server). The first connection is made by the first send.
- R19. The layer sends over at most 2 connections: a gate of the layer lets 2 sends run at once, and the SMTP client's pool is set to 2 too. Test: 10 sends started together against a test SMTP server that counts open connections never show more than 2 at once, and all 10 mails arrive.
- R20. `createMailLayer` returns the layer and a `close` function that closes the pool. The app registers `close` as a close hook of TOKI-004 R15, so SIGTERM leaves no open connection. Test: after `app.close()`, the test SMTP server reports no open connection.
- R21. `buildApp` takes one more optional input, `mail`, a `MailLayer`. When it is absent the real layer is built from `config.mail` and the environment name of the server area; `config.mail` is optional in the configuration type, and when both are absent `buildApp` throws at once, naming `mail`. The layer is put on the app as `app.mail` with Fastify's `decorate`, before the routes are registered, and `close` is registered as a close hook. A test passes a fake layer that records its calls, so no test of another module needs an SMTP server or a mail configuration. The server entry registers the `mail` area, so the started server needs the three required variables; the tests of `buildApp` use a fake or a fixed fixture of mail values. This is the only change to `buildApp`.
- R22. Every visible word of every mail comes from `@toki/i18n` keys of the namespace `mail`, in English and in Vietnamese; the module holds no sentence, label or subject of its own. `pnpm --filter @toki/i18n check` passes with the new keys. Test: the render functions take the translate function as an argument; with one that returns `[[key]]` for every key, the visible text of each mail, with markup removed, holds only `[[key]]` markers, the code, the names, the `joinUrl` and punctuation.
- R23. In development the mail layer, run with the development values of `.env.example` and the services of TOKI-003 up, delivers one mail of each kind to Mailpit, readable in its inbox with the code and, for the invitation, the Join button. Check at build, by hand with `pnpm dev:up` and a script that calls the layer; this check is not part of `pnpm test` because it needs the service. It covers the three mails.
- R24. `sendInvitationCode({ to, code })` returns a `MailResult` as in R6 and sends the mail that carries a new code to a person who already has the invitation, always in English (D-180). Input rules as in R6 for `to` and `code`. The mail holds the code as 6 digits in one piece, the sentence that it works for 10 minutes (D-136) and a sentence that tells the person to enter it on the page they have open; it holds no link and no button, with the same absence list as R8 (D-149: the link alone signs nobody in). Its subject is the key `mail.invitationCode.subject` and holds no code. R7 (sender), R11, R12, R13, R14 and R22 apply to it as they do to the others.
- R25. The layer does not queue without limit and does not wait on a dead server one send after another. (a) At most 100 sends wait for a slot; the 101st returns `unavailable` at once (cause `queue_full`). (b) A send that has waited 30 seconds for a slot returns `unavailable` (cause `queue_wait`) and is removed from the queue, so a code is not kept in memory for a mail that will be late. (c) After a failure at the level of the connection (no connection, DNS, TLS or a connect or greeting timeout, not a reply of the server), the layer returns `unavailable` at once (cause `cooldown`) for every waiting send and every new send for 30 seconds, and opens no connection in that time; the next send after it tries the server. A batch of 50 to a dead server therefore ends in about one connect limit, not in 50 sends one after another. The numbers are inputs of `createMailLayer`. Tests, with shortened limits: 50 sends started together against a server that accepts and never answers all return `unavailable` within about one greeting limit, and the server saw at most 2 connections; with a queue limit of 3, 10 sends started together to a slow server leave 3 waiting and return `queue_full` for the rest; a waiting send past its wait limit returns `queue_wait` and is never delivered; after the cooldown a send to a server that is back is delivered.
- R26. The lifetimes in the mails, 10 minutes and 7 days, are not typed twice. Until TOKI-022 exists the layer holds them as constants of its own in one file of the module; once `CODE_TTL_SECONDS` (600) of TOKI-022 R38 in `packages/shared/src/auth/limits.ts` exists, the layer imports it, shows it as minutes, and a test compares what the mail says with that constant. The 7 days follow `INVITATION_LIFETIME_DAYS` of TOKI-024 R35 (`packages/shared/src/members/`) in the same way; until then the layer holds it and a test pins it to D-037. TOKI-024 R35 names this requirement as the one that pins to its constant.

## Design
### Configuration
The `mail` area is one more schema of the server configuration (TOKI-004 R2, concern 11). Decided in this spec: the schema is written in `modules/mail/config.ts`, exported through `modules/mail/index.ts` as `mailConfigSchema` and `MailConfig` (R1), and the root `config.ts` composes it with the other areas; the module is imported through its entry only, as the boundary rule of TOKI-002 requires, and the root `config.ts` stays the one place that reads the environment. The server entry registers the area and loads it; a command-line tool that does not send mail does not load it. Names, values and flags below are the rows this work adds to the TOKI-096 inventory (TOKI-096 R10, concern 10: a ticket that needs a missing variable adds the row and the `.env.example` line in its own pull request). Decided in this spec: the names, because the inventory names the category "Mail over SMTP" but fixes no variable.

| Name | Purpose | Required | Default | Development value | Secret |
| :---- | :---- | :---- | :---- | :---- | :---- |
| `SMTP_HOST` | SMTP server address | yes | none | `127.0.0.1` | no |
| `SMTP_PORT` | SMTP server port | yes | none | `1025`, Mailpit's own SMTP port | no |
| `SMTP_TLS` | `none`, `starttls` (upgrade required) or `tls` (TLS from the first byte) | no | `starttls` | `none` | no |
| `SMTP_USER` | Login; with `SMTP_PASSWORD`, both or neither | no | none | empty | no |
| `SMTP_PASSWORD` | Password of the login | no | none | empty | yes |
| `MAIL_FROM_ADDRESS` | Sender address | yes | none | `toki@example.com` | no |
| `MAIL_FROM_NAME` | Sender name | no | `Toki` | `Toki` | no |

The default of `SMTP_TLS` is `starttls`, so a server with the variable unset does not send in clear (R4). Mailpit takes no login and no TLS, so the development value is `none` with no login, which R4 allows because the environment name is `development`.

`SMTP_PORT` is the one row for this number: the Mailpit SMTP host port that TOKI-003 R25 publishes is read from the same variable, so `.env.example` holds it once. If the TOKI-096 inventory already carries a row for the Mailpit SMTP host port when this is built, `SMTP_PORT` takes that row's name (R2) and nothing is written twice.

### API
Server-internal functions, not HTTP routes.
| Operation | Input | Result |
|---|---|---|
| `sendSignInMail` | `to`, `code`, `language` (`en` or `vi`) | `MailResult` |
| `sendInvitationMail` | `to`, `code`, `workspaceName`, `inviterName`, `joinUrl` | `MailResult` |
| `sendInvitationCode` | `to`, `code` | `MailResult` |

The three operations take an optional `{ log }` as a second argument (R6).

The callers decide whether a failure matters. The layer only reports it and logs one line (R14); a caller does not log the failure again.

Every sentence and subject is a proposal (D-139): the prototype has no mail text, only the screen sentence "We sent a 6-digit code to … It works for 10 minutes." They are not sent in phase 1: invitations are in English (D-180, R10, R24). The render function takes a language so that the day D-180 changes, only the call changes.

The invitation mail's layout: the intro line, the Join button, the code intro, the code, the validity line, the lifetime line, the ignore line. The new-code mail's layout: the intro line, the code on its own line, the validity line. No logo image: the HTML part loads nothing from outside (R11).

### Layout
```
apps/server/src/modules/mail/
├─ index.ts        public entry: createMailLayer, MailLayer, MailResult, mailConfigSchema, MailConfig
├─ layer.ts        the three operations, the gate, the queue, the timeouts, the result and the log line
├─ render.ts       renderSignInMail, renderInvitationMail, renderInvitationCodeMail: pure functions that return subject, text and html
├─ classify.ts     sorts an SMTP or network error into a reason (R16)
└─ config.ts       the mail area schema; exported through index.ts and composed by the root config.ts of TOKI-004
packages/i18n/src/messages/{en,vi}/mail.ts    the keys of the table above
```
- Library: Nodemailer for the SMTP client, with its pool set to 2 connections. Decided in this spec: the Blueprint fixes SMTP and no library; Nodemailer is the usual Node client with STARTTLS, pooling and UTF-8 header encoding, so none of that is written here. It is used inside `modules/mail/` only (R1).
- `createMailLayer({ config, logger, production, limits?, tlsCa? })`. `buildApp` calls it with `config.mail`, the app's logger and `production` (the environment name is `production`) and registers `close` (R20, R21). `limits` holds the numbers of R15 and R25 so a test can shorten them. `tlsCa` is for tests only: it adds one trusted certificate authority to the client and leaves the certificate and host-name check on; no configuration variable reaches it (R4).
- Nodemailer settings that R4 relies on, Decided in this spec: `starttls` sets `requireTLS`, `tls` sets `secure`, `none` sets `ignoreTLS` (without it a `none` setting still upgrades when the server offers STARTTLS, and a development server with a self-signed certificate would fail), and `tls.rejectUnauthorized` is left at `true` in every case.
- Dependencies, named so the build does not guess: `nodemailer` and `@types/nodemailer` for the layer; `smtp-server`, `@types/smtp-server`, `mailparser`, `@types/mailparser` and `selfsigned` (it makes the test certificates when a test runs) as development dependencies of `apps/server`. Exact versions are chosen at build and held by the lockfile, and the build checks their licences against the repository's rule, if it has one, and writes the result in the pull request.
- Render functions are pure and take `t` (the translate function bound to a language, `createTranslator` of TOKI-017 R9) and the values; the server calls `translate` through `@toki/i18n` on the main entry that has no React (TOKI-017 R21).
- The HTML part is a small hand-written table layout with inline styles, as mail clients need, no script and no remote load. The text part is the same content with the Join address on its own line.
- Logging: the layer uses the app's logger and writes the fields of R14 only. Nodemailer's `logger` and `debug` options stay off, because with them on the message body, and so the code, reaches the log (R13).
- Decided in this spec: the layer writes no recipient address to the log, even though the address is not a secret. The sign-in API makes the same choice for its module (its R37), the address is personal data, and the callers already know which address they asked about.

### Errors
- Bad input to an operation -> `{ ok: false, reason: 'invalid_input' }` and no connection (R6, R9).
- Cannot connect, TLS or DNS failure, a timeout, a 4xx reply -> `unavailable` (R15, R16).
- Login refused (530, 534, 535, 538) -> `auth_failed`. A 5xx reply to the recipient -> `recipient_rejected`. Any other 5xx -> `rejected` (R16).
- The layer never throws and never rejects; a bug inside it that would throw is caught and returned as `unavailable` with cause `internal`; the log line holds the fields of R14 only, never the error's text or stack (R13).
- The queue is full, a send waited too long, or the server was just found unreachable -> `unavailable` at once (R25).
- Missing or invalid mail configuration -> the server does not start (R3, R4).

## Data safety
- The SMTP password is a secret of `.env`: `.env.example` holds it empty (TOKI-096 R9) and it is never logged, in a failure line either (R13).
- A code is a credential. It is in the mail and in memory for the send only (waiting in the queue for at most 30 seconds, R25); it is not in the log, not in the subject (a subject shows in notification lists and in the logs of mail servers) and not in an error (R7, R13, R14).
- A recipient address and the `joinUrl` are personal data or carry a token; neither is logged (R13).
- The mail travels over TLS whenever the environment is not `development`, and a login never travels in clear (R4). The certificate is checked and nothing switches the check off.
- The HTML part makes no request to an outside address, so opening the mail tells nobody that it was opened (R11).
- Text from a person (a workspace name, a display name) cannot become markup or a header (R12).

5. Decided in this spec: the layer makes one attempt and does not retry (R17), and the caller is told at once. Reason: a retry after a timeout can send the same code twice. One attempt alone does not keep a batch of 50 from waiting on a dead mail server, because TOKI-024 reports each row (D-099) and so waits for every result; that is bounded by R15 and R25: 2 slots, connect and greeting limits of 5 seconds, a pause after a connection failure that fails the rest at once, so the batch ends in about one connect limit, inside the 10 seconds after which a client counts a request as failed (D-126, Accepted Assumption). The person has Resend (D-082, D-099) and the operator has the emergency link (D-159). The retry count and delay of mail sent from the job queue belong to TOKI-064. A queue job keeps its payload in the database, and this layer keeps a code in memory for the send only, so a queued send will either store the code or carry a hash of it and call the layer from a handler that can read the code; TOKI-064 decides which and this spec does not constrain it. Owner: Thanh Truong.
