# Edit and delete messages design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/edit-delete-messages.md (Thanh Truong)
Ticket: TOKI-047

## Goal
A member needs to correct a message they sent and to take it back, and an Admin needs to remove another person's message in a conversation they belong to. The tables already hold `edited_at`, `deleted_at` and `deleted_by` (TOKI-036 R6), the permission functions `canEditMessage` and `canDeleteMessage` already decide who may (TOKI-027 R7), the send and history routes already return `editedAt` and `deletedAt` as `null` (TOKI-037 R15), and the confirmation helper already lists the two delete actions (TOKI-093, `deleteOwnMessage` and `deleteMemberMessage`). No route writes those columns and no screen offers the two actions.
After this change the author edits a message in place with no limit, a message edited shows "(edited)", a delete asks a confirmation that names its target and has no Undo, a deleted message with replies keeps its thread, a message deleted by an Admin always leaves a line that says so, and its author is told. The server refuses what the rules refuse, whatever the screen shows, and every open client shows the change through two new events.

## Requirements
Edit
- R1. `PATCH /api/v1/conversations/{id}/messages/{messageId}` takes `{ "text": string }` and answers 200 with `{ "message": MessageEntry, "changed": boolean }`. It needs a valid session (401). The steps and their order are those of TOKI-037 R1, for this route: (1) the schemas of the path and the body (400 `validation_failed`; the body is strict, so a key other than `text` is 400); (2) `getConversationFacts(db, actor.id, id)`: `null`, or a private channel, DM or group of which the actor is not a member, is 404 `not_found`; (3) `canReadConversation`: a person who is not a member of a public channel gets 403 `forbidden`; (4) the locks of R9, after which the facts are read again; (5) inside the locks, the lookup of the message (R2) and `canEditMessage`; (6) the update (R3, R4) and, for a changed text, the call of `saveMentions` (R9). The actor of steps 1 to 3 is the account of the session; no route compares a role. Check: a table test sends each case and checks status and code; a request with no session is 401 with no read of a message; the statement log shows the lock statements before the lookup of the message and the lookup before the update.
- R2. Who may edit, and which message. The message is the row of `messageId` in the conversation of the path with `kind` `user`. No row, a row of another conversation and a system line are each 404 `not_found` with the same body as for an unknown conversation. For a user message, `canEditMessage(actor, conv, { authorId })` decides (TOKI-027 R7): only the author, who is a member of a conversation that is not archived, a Member and an Admin alike. `not_author` is 403 `forbidden`, also for an Admin (F42: an Admin never edits another person's message); `not_a_member` of a public channel is 403 and of a private one 404 (step 2 of R1 has answered it); `channel_archived` is 409 `channel_archived`; `fact_missing` and `unknown_role` are 500 `internal_error`, logged at error level (TOKI-037 R2). A message with `deleted_at` set is 409 `message_deleted` (a new code, R8), the same for the author and for anyone else who passed the permission check; a person who failed it gets the refusal of the check, so that the deleted state is not told to a person who may not edit. The error body holds no text of a message. Check: a table test with the author, another Member and an Admin who is not the author, in a public channel, a private channel, a DM and a group, each as member and as non-member, in an archived and a live channel; each refusal leaves the row unchanged; the author succeeds in each kind (a positive case, so a loader that always refuses fails); a system line, an unknown id and an id of another conversation are 404; an edit of a deleted message by its author is 409 `message_deleted`; the stubbed `fact_missing` and `unknown_role` are 500.
- R3. The text of an edit follows the rules of the text of a send. TOKI-037 R4 states them and R22 exports the request schemas, not a separate text schema; the schema of the edit is built from the same pieces (`MESSAGE_TEXT_MAX` of TOKI-036 R22, the code-point count, the white-space and character rules), and Plan changes asks TOKI-037 to export its text schema so that this ticket imports it; until it does, this ticket builds the schema from the pieces and the test below runs the cases of TOKI-037 R4 against both. The rules: 1 to `MESSAGE_TEXT_MAX` (10,000) code points counted with `Array.from(text).length`, not only white space (what `trim` removes), no U+0000 and no lone surrogate, stored as sent with no trimming and no change of line breaks (the screen sends the text that `prepareOutgoing` of TOKI-043 returns, R18, so a person's edit is trimmed before it is sent, as a send is). A text that fails is 400 `validation_failed` and nothing is stored. When the text is equal to the stored text, nothing is written, `edited_at` does not change, `recordChange` and `saveMentions` are not called, and the answer is 200 with the stored message and `changed` `false`; the compare is on the exact string. Decided in this spec (concern 8). When TOKI-058 lets a message carry files and no text, it changes the rule of the text for both routes in its own change (concern 6). Check: each text case of TOKI-037 R4 on this route with the same expected result, and the same cases against the text schema of TOKI-037 (or the pieces) with the same result; the same text sent twice leaves `edited_at` as the first edit set it and calls `recordChange` zero times the second time; a text that differs only by a trailing space is a change.
- R4. What an edit writes. An edit of a message that passes R1 to R3 updates `body` and `edited_at` of that row and no other column: `edited_at` is read once from the clock of TOKI-008 for the request, so the client sends no time. There is no time limit: a message of any age is edited (D-013, FR-11, AC-030). No earlier text is kept anywhere (F16: no edit history). The thread, the replies, the reactions, the pin, the saved copies in Later, the file links and `created_at` are not touched, so the message keeps its place in the list. A second edit sets `edited_at` again (it is the time of the last edit, TOKI-036 R6). Editing a reply, or a message sent with "Also send to channel", edits the one row, so both places change (D-160). Check: a test edits a message made one year earlier with the controllable clock and finds the new text and `edited_at` equal to the clock; a row-by-row compare finds every other column and every other row unchanged; a message with a reply, a pin row and a reaction row inserted by SQL keeps them; a second edit moves `edited_at`; an edit of a reply leaves its parent unchanged.

Delete
- R5. `DELETE /api/v1/conversations/{id}/messages/{messageId}` takes no body (a body is ignored; a query string key is 400) and answers 200 with `{ "message": MessageEntry }`, the row as it stands after the delete. The steps are those of R1 with the deletion in step 6, and `canDeleteMessage(actor, conv, { authorId })` in step 5 in place of `canEditMessage`. The `Origin` rule and the media-type rule of TOKI-022 (R45, R46) cover this route and R1's: a foreign `Origin` is 403 `origin_not_allowed`. Check: the same table test as R2 for this route; a foreign `Origin` is 403; a request with a session and a good id is 200 for the author.
- R6. Who may delete. `canDeleteMessage` allows the author (`as: "author"`) and an Admin who is a member of the conversation (`as: "admin"`; an Admin who deletes their own message is the author) (TOKI-027 R7, BR-24, BR-26). A Member who is not the author gets `not_author`, 403 `forbidden` (TS-054). An Admin who is not a member of a private channel, a DM or a group gets 404 and has no extra right (D-047, TS-053); an Admin who is not a member of a public channel gets 403. An archived conversation is 409 `channel_archived` for the author and for an Admin (TOKI-027 concern 3). The function already allows an Admin in a DM or a group they belong to, as the capability table reads (TOKI-027 concern 2, which that spec's builder marked "Decided in this spec" as a risk for the owner to confirm, not an answer of the owner); this ticket follows it and carries the same risk (PR "Risk"). A message that is a system line, or is in no row of the conversation, is 404 as in R2. Check: a table test with Mai (Member, author), Sam (Member), Minh (Admin, member) and Lan (Admin, not a member), in a public channel, a private channel, a DM and a group; Sam deleting Mai's message is 403 and the row is unchanged (TS-054); Lan gets 404 in the private channel with no row changed and 403 in the public one (TS-053); Minh deleting Mai's message is 200 with `deletedBy` `"admin"`; Mai deleting her own is 200 with `"author"`; Minh deleting his own is `"author"`; the archived channel gives 409 for Mai and for Minh.
- R7. What a delete writes. A delete that passes R5 and R6 updates the row: `deleted_at` is the clock time of the request, `deleted_by` is the actor, and `body` becomes the empty string (decided in this spec, concern 5). The row is never removed (TOKI-036 R8) and its place never changes. The rows of its replies, reactions, pin and file links are left as they are: a delete removes none of them, and the entry hides them (R10); what each neighbour does with them is its own (Design, "What each neighbour does"). That the reaction, pin and file-link rows stay is decided here, so TOKI-046 needs no question about it (its R9 and concern 4). When the deleted row is a reply (`parent_id` not null), the same transaction also corrects the thread of its root: after the update of the reply row and before its first `recordChange` it calls `recomputeThreadSummary(tx, rootId)` of TOKI-045 R9 with `rootId` the `parent_id` of the reply, and keeps the `ThreadSummary` it returns for R10. The function locks the root row, counts the replies that are not deleted and raises `summaryVersion`, so the count of the root falls by one and the client applies it. This is done exactly when this request deleted a reply: not for a repeat, an edit, a delete of a root or a refusal. A delete of a message that is already deleted writes nothing, calls `recomputeThreadSummary` and `recordChange` zero times and answers 200 with the stored message as it stands, whoever the actor is among those who pass R6; so an Admin who deletes a message that its author deleted a moment before does not replace `deleted_by` (concern 8). History keeps returning the row as TOKI-037 R14 says, in its place, with `text` `null`. Check: after a delete the row has `deleted_at` equal to the clock, `deleted_by` equal to the actor and an empty `body`, and every other column of that row is as before; a message with 3 replies keeps the 3 replies, their text and their `parent_id`, and its own summary columns are unchanged; a delete of one of 3 replies gives the root `reply_count` 2 and `summary_version` one higher, and a delete of a root, a repeat and an edit leave the summary columns as they were; the reaction, pin and file-link rows of a deleted message are all still there; the history of the conversation still lists the row, in its place, with `text` `null`, and a page `around` it works; a second delete by the author, and one by an Admin after the author's, answer 200, change nothing and leave `deleted_by` as the first set it; an Admin's delete of a message with no reply still writes the row (the line is the client's, R19).

Entry, events, seams
- R8. In `packages/shared/src/messages/`: `MessageEntry` of TOKI-037 R15 gains the key `deletedBy`, `null` for a message that is not deleted and `"author"` or `"admin"` for one that is, `"admin"` only when `deleted_by` differs from `author_id`; the entry carries no person id of the deleter, because the line shows no name (D-049) and the author is told who by the Activity item (R11). `MessageEntry` stays one strict object, and the tests of TOKI-037 R15 are updated with the key. The entry of a deleted message has `text` `null`, `reactions` `[]`, `pinned` `null` and empty `mentions` (TOKI-046 R9, TOKI-048 R3, TOKI-050 R8): the single builder gives them for any row with `deleted_at` set, whatever the rows of reactions and pins hold (a request to TOKI-037, Plan changes). The package exports the schemas of the two requests and the two responses, and the registry of error codes gains `message_deleted` (409). `text` is `null` for a deleted message (TOKI-037 R15), so no response and no event of this ticket holds the text of a deleted message. Check: a schema test accepts an edited message, a deleted-by-author and a deleted-by-admin entry and refuses `deletedBy` `"other"`, a deleted entry with a text and an entry with `deletedAt` set and `deletedBy` `null`; the registry holds the code once; every 200 body of the route tests is parsed with the response schema.
- R9. Transaction and locks. Each route runs in one transaction in the order of TOKI-024 R39, as TOKI-037 R8 does: (1) `getAccountsByIds(tx, [actor.id], { lock: "share" })`, so a deactivated actor gets 401 `account_deactivated`; (2) the conversation row, in the mode of TOKI-037 R8 including its `dm` case: `FOR SHARE` for a channel and a group, so that an archive and a leave, which take `FOR NO KEY UPDATE` (TOKI-029 R15), cannot run between the check and the update, and edits and deletes of one channel do not wait on each other, and `FOR NO KEY UPDATE` for a `dm` as TOKI-037 concern 8 states, so the DM follows the one rule of the module (the other person's account is not locked, as no write here depends on it); (3) the facts are read again and `canReadConversation` is checked again; (4) the message row `FOR NO KEY UPDATE`, which serialises two edits or an edit and a delete of one message and does not conflict with the `FOR KEY SHARE` that a reply insert takes on its parent (decided in this spec, concern 9); (5) the lookup, the permission function and the update; (5a) for an edit that changed the text, the call of `saveMentions` (R10), after the update of the message row and before any statement that touches a root row or calls `recordChange`; (6) for the delete of a reply, `recomputeThreadSummary(tx, rootId)`, which takes the root row `FOR NO KEY UPDATE` as its first statement (TOKI-045 R9); (7) `recordChange` is the last statement (R10). The order is one order for both routes and the one of TOKI-045 R4 and R9: the conversation row, then the message row, then the row of the root of its thread, never the reverse, and the counter lock of the event handler last (TOKI-036 R18). A reaction (TOKI-046 R6) and a pin (TOKI-048 R6) take the conversation row and then the message row `FOR SHARE`, which waits for this ticket's `FOR NO KEY UPDATE` and never the reverse, so they close no cycle with an edit or a delete. Two edits of one message at the same time both succeed, one after the other, and the last to commit stands (D-121); an edit that waits behind a delete is 409 `message_deleted`; a delete that waits behind an edit deletes the edited row. This ticket adds no table, no column and no migration. It writes the row of the message and, for the delete of a reply, the four summary columns of the root through the function of TOKI-045 (the columns are TOKI-045's migration), and no other row, except that an edit that changed the text writes the rows of `message_mentions` of that message through the injected `saveMentions` (TOKI-050 R4, R7; the table is TOKI-050's migration), and with the default writer, which does nothing, it writes none. Check with two real connections, the second waiting and the result checked after the first commits, never by sleeping: two edits with two texts leave one of the two and `edited_at` of the later; an edit and a delete leave a deleted row, and the edit answers 409 when the delete came first; an edit and an archive end with the edit stored in the live channel or refused 409; a reply insert into the message while a delete holds its row finishes with no deadlock (SQLSTATE `40P01` never); the race of a reply insert (a send of TOKI-037 with `parentId`) and a reply delete under one root: both end applied, the root's `reply_count` equals the number of replies that are not deleted, `summary_version` has risen by 2, and no deadlock occurs, in both orders of arrival; two deletes of two replies of one root end with `reply_count` reduced by 2; the statement log of a reply delete shows the conversation lock, the message lock, the root lock and then the first `recordChange`, in that order, and no locking statement after it; the statement log of an edit shows the message lock, the update, the call of the writer and then `recordChange`; a reaction insert (a `FOR SHARE` on the message row set by SQL) that arrives while a delete holds the row finishes after the delete with no deadlock; in a `dm` the conversation lock statement is `FOR NO KEY UPDATE` and in a channel and a group `FOR SHARE`; a person deactivated while the request waits gets 401; the isolation level read back inside the transaction is `read committed`; the migration folder is unchanged and, for an edit with the default writer and for the delete of a root, the row counts of every table other than `messages` are unchanged (with a recording handler `events` and `event_counters` too).
- R10. The events. A route that wrote a row calls `recordChange(tx, change)` as the last statements of its transaction, after every lock and the update. An edit and the delete of a message that is not a reply call it once, with `type` `message_edited` or `message_deleted`, `actorId` the actor, `conversationId`, `userIds` empty, `at` the time written to the row and `message` the `MessageEntry` of the row after the update. The delete of a reply calls it twice, in this order: `message_deleted` as above, then `thread_updated` (TOKI-045 R8) with `conversationId`, `actorId` the actor, `at` the time of the delete and `thread` the `ThreadSummary` that `recomputeThreadSummary` returned; the event handler writes `message.deleted` and then `thread.updated` with consecutive numbers (TOKI-036 R18). The `thread_updated` change, its event, its schema and its row in `kinds.ts` are TOKI-045's; this ticket adds nothing for them. The entry is built by `buildMessageEntry` of TOKI-037 (its one function that makes every entry), the same one the history, the send and the reaction and pin routes use, with the same injected readers `listReactions` (TOKI-046 R10), `listPinned` (TOKI-048 R3) and `listMentions` (TOKI-050 R8): `app.ts` gives the two routes of this ticket the same dependencies as the send route, and the edit route also the writer `saveMentions`, so the event payload equals the 200 body with every key of the wave (the keys of TOKI-045 R7, `reactions`, `pinned`, `mentions`, `deletedBy`). In an edit the readers run inside the edit's transaction after the message row lock and after the call of `saveMentions`, so the entry holds the reactions committed before the edit and the mentions of the new text; a reaction that commits later is a later event (TOKI-046 R10). `message_edited` also carries `mentionDelta`, the delta that `saveMentions` returned (TOKI-050 R9), set by every edit that changed the text and empty when nobody is named or the default writer is used; `Change` gets that field from TOKI-050 and this ticket defines nothing for it. `Change` of `conversations/changes.ts` gains the two types and the optional fields of R11. A repeat of R7, an unchanged edit (R3) and every refusal call it zero times. This ticket writes no event: the event handler of TOKI-038 writes `message.edited` and `message.deleted`, scope `conversation`, payload `{ message }`, one event for each call; this ticket adds the two kinds and their schemas to the registry of `packages/shared/src/realtime/` and the two cases and the two rows of `kinds.ts` (no change of any map) to the handler, which is a small change to code of TOKI-038 (Plan changes). The line handler of TOKI-037 R16 does nothing for these two types, and the rule of TOKI-038 that writes an extra `message.created` for a message that a change "did not bring itself" does not apply to them: their message is their own and they write only their own event. The gateway sends each event to the people whose map holds the conversation, after the commit, in number order (TOKI-038 R13 to R15), so the author's other tabs and every member hear it, and a person outside the conversation never does. Check, with a recording handler as the only handler: one call for an edit and for the delete of a root, and two in order (`message_deleted`, `thread_updated`) for the delete of a reply, with the fields above, a `message` equal to the 200 body and a `thread` whose `replyCount` is the count after the delete; none for a repeat, an unchanged edit and a refusal; a statement log shows no write after the last call; a handler that throws leaves the old row and the old summary and the answer is 500; an edit of a message that holds two reactions and a pin returns, in the 200 body and in the change, its `reactions` and its `pinned`, and a delete of the same message returns `text` `null`, `reactions` `[]` and `pinned` `null`, with the reaction and pin rows still in the tables; with the real handler (an integration test of the two together): the edit of a message in a channel with three connected members and an Admin outside gives one `message.edited` frame to each of the three, none to the outsider, and a payload equal to the 200 body; the delete gives one `message.deleted` whose `message.text` is `null`; the delete of a reply gives `message.deleted` then `thread.updated` with consecutive numbers and the payload of the second parses with its schema; the registry test finds the two kinds, each with a row in `kinds.ts`.
- R11. What the changes carry for the work that follows. `message_edited` carries `previousText`, the text before the edit, and `message_deleted` carries `authorId` (the author of the row), `deletedAs` (`"author"` or `"admin"`) and `deletedById` (the actor). These fields are for handlers that run in the same transaction, before the event handler; they are not stored and not in any event payload or response, so no earlier text is kept (F16) and the identity of an Admin is told only where TOKI-065 chooses to tell it. This ticket registers no handler for them, and no ticket waits on another for them. The owners, each in its own change: TOKI-050 keeps the mentions of the new text through `saveMentions` and hands the result on as `mentionDelta` (R10), whose `removed` lists only the people whose name was edited out, so it does not use `previousText`; TOKI-065 creates the item of each person in `added`, removes the earlier item of each person in `removed` and may compare `previousText` with the new text (F16, F13; the actor is never notified, D-071); TOKI-065 creates the item "message deleted by an admin" for the author when `deletedAs` is `"admin"` (F42, D-049) and removes the Activity items whose source is the deleted message (F13); TOKI-069 updates and clears its search entry; TOKI-067 keeps the count and the rows of Later in step when a saved message is deleted. Pins: the pin row stays (R7), and TOKI-048 registers its own client handlers for `message.edited` and `message.deleted` with `registerEventHandler` (which allows several handlers for a kind, run in the order registered), one that patches the held pinned message and one that takes the message out of the Pinned tab (D-166), through its own store; this ticket calls none of its seams and its handlers do not wait for 048's. Any of these that takes a lock goes before the event handler (TOKI-036 R18). The line for the author in TS-052 is tested here only through `deletedAs` on the change; the notice itself is TOKI-065's, as the file part of TS-051 is TOKI-058's. Check: a recording handler receives `previousText` for an edit and `authorId`, `deletedAs`, `deletedById` for a delete, equal to the values of the test; the 200 body and the event payload of each have none of the three keys (a schema test); the test of R10 finds the same change in the same transaction.
- R12. The files of a deleted message. TOKI-058 owns the tables of files and the storage, and does not exist before this ticket, so this ticket cannot remove a file; the requirement of D-043 and AC-033 (after a delete the files can no longer be opened and are not in Files) is split as follows, decided in this spec (concern 6). This ticket makes the delete a change that a handler can act on inside its transaction (R10, R11: `message_deleted` with the message id and the conversation) and states the rule; TOKI-058 registers a change handler before the event handler that, for `message_deleted`, removes the links of the message's files so that the signed addresses are refused and the files are not listed in Files, and queues the removal of the stored objects through the job queue of TOKI-064; the test of AC-033 and TS-051 is TOKI-058's. This ticket's own test proves the seam: a recording handler registered before the event handler receives the change of a delete inside the delete's transaction and can write a row that is rolled back with it. Check: that test; a handler that throws rolls the delete back and the answer is 500.

Client
- R13. Two methods of `createApiClient` (TOKI-032 R9 and TOKI-040 R2, same rules: one request core, 10 seconds, no retry, a path part encoded, an optional `signal` last, neither `headers` nor `timeoutMs`). `api.messages.edit(conversationId, messageId, text, signal?)` sends the `PATCH` of R1 with the body `{ text }` and returns `{ message, changed }`; `api.messages.remove(conversationId, messageId, signal?)` sends the `DELETE` of R5 with no body and returns `{ message }`. ## Design
### API
| Method | Path | Who | Purpose |
|---|---|---|---|
| PATCH | `/api/v1/conversations/{id}/messages/{messageId}` | the author, a member, not archived | Edit the text; 200 `{ message, changed }` (R1 to R4) |
| DELETE | `/api/v1/conversations/{id}/messages/{messageId}` | the author; an Admin who is a member | Soft delete; 200 `{ message }` (R5 to R7) |

| Status | `error.code` | When |
|---|---|---|
| 200 | none | Stored; also an unchanged edit (`changed` false) and a repeated delete (R3, R7) |
| 400 | `validation_failed` | Path or body fails its schema; the text rules of R3 |
| 401 | as TOKI-022 | No valid session; a deactivated actor (`account_deactivated`) |
| 403 | `forbidden` | Not the author (edit), not the author and not an Admin member (delete), or not a member of a public channel |
| 403 | `origin_not_allowed` | A foreign `Origin` |
| 404 | `not_found` | Unknown conversation; a private conversation the person is not in; no such user message in the conversation |
| 409 | `channel_archived` | The conversation is an archived channel |
| 409 | `message_deleted` | An edit of a message that is deleted |
| 500 | `internal_error` | A server failure, `fact_missing` or `unknown_role` |

A 409 means the screen was out of date (D-131).

### Lines with TOKI-036, TOKI-037 and TOKI-038
- TOKI-036: `body`, `edited_at`, `deleted_at` and `deleted_by` are the editable columns and the immutable-columns trigger leaves them open (R7 there); `messages_deleted_check` wants `deleted_at` and `deleted_by` set together, and `body` may be the empty string (R4 there), so a deleted row with an empty body passes every check. The delete is an `UPDATE`, because a trigger refuses every `DELETE`.
- TOKI-037: the routes live in its module and use its one entry function `buildMessageEntry` with the injected readers, the pieces of its text rules and its lock rule (R3, R9, R10); the entry already carries `editedAt` and `deletedAt` and `text` `null` for a deleted row (R15), and history already returns a deleted row in place (R14). A repeat of a send that arrives after an edit or a delete returns the row as it stands (R5 there), which this ticket makes true.
- TOKI-045: `recomputeThreadSummary(tx, rootId)`, `ThreadSummary` with `summaryVersion`, the change `thread_updated` and `isFresher` are its (its R8, R9, R12 and its contract table); the delete of a reply calls the function and sends the change (R7, R10).
- TOKI-038: the two new kinds are added to its registry in `packages/shared/src/realtime/` and its event handler gets two cases; the handler of the system line does nothing for them. Its rule that a change which carries a `message` it did not bring itself also writes a `message.created` is for the changes that the line handler served, and is stated here not to apply (R10).
- TOKI-040: the handlers use `registerEventHandler` (several per kind) and `patchMessage`; `applyMessage` with its parent routing is the one addition, asked together with TOKI-045 (R14). `message.created` never replaces a held message (R4 there), so a replayed creation cannot undo an edit; `isFresher` of TOKI-045 makes the two new events safe to replay in the same way.

An Admin may delete another person's message in a 1:1 DM or a group that they belong to, because the capability table says "where a member" and the permission function follows it (TOKI-027 concern 2, a choice of that spec's builder that its owner has still to confirm); an Admin does not read or delete in a conversation they are not in (D-047).

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- The routes are `PATCH` and `DELETE` of `/conversations/{id}/messages/{messageId}`, under the conversation as the send and history routes are, so the conversation facts and the membership rules are the same steps.
- An edit of an unchanged text writes nothing; a repeated delete answers 200 and writes nothing (concern 8).
- A delete empties `body` (concern 5).
- The entry says `deletedBy` as `"author"` or `"admin"`, not a person (R8).
- The files are removed by TOKI-058's handler, not here (concern 6).
- The message row lock is `FOR NO KEY UPDATE`, the conversation row lock follows TOKI-037 R8 (concern 9).
- A delete leaves the reaction, pin and file-link rows (R7).
- One rule, `isFresher` of TOKI-045, decides which copy wins, and an edit or a delete writes only its own keys (R14, concern 11).
- Focus after a delete goes to the list region (concern 10).

2. A dialog or the line under the message for the delete confirmation. Not decided. Owner: Thanh Truong (product owner).
4. What "has replies" counts for a deleted message. Not decided. F16 says a message with replies becomes a "Message deleted" line and a message with none disappears. Nothing says what happens when every reply of a deleted root is deleted afterwards: the line stays if deleted replies count, and disappears if they do not. This is the same question as TOKI-045 concern 2 (what a deleted reply does to the count and to the thread), seen from the root: the answer is given once, there, and this concern depends on it and it on this one for the words "hidden" and "deleted" of R20. The count is TOKI-045's key (`replyCount`, which its R9 builds from the replies that are not deleted); R20 takes a number from it. Proposal, not a decision, the same as TOKI-045 concern 2: the count holds only replies that are not deleted, so a thread that has nothing readable left stops showing the line, and a deleted reply is hidden. Owner: Thanh Truong (product owner).
5. What a delete does to `body`. Decided in this spec: the text is emptied in the same update. Reason: the person asked for the message to be gone, no feature reads the text of a deleted message (the entry gives `text` `null`, TOKI-037 R15, and Activity, Later and search drop their items), an edit keeps no earlier text (F16), and the table allows an empty body (TOKI-036 R4); keeping the text would leave in the database what the product says is deleted. The cost: an Admin's delete cannot be undone or audited from the table; if the owner wants an audit copy it is a new column and a migration. TOKI-036 R6 leaves this to this ticket. This is a product trade-off as well as a technical choice, and it is named under "Risk" in the pull request for the owner to see. Owner: Thanh Truong.
6. Which ticket removes the files of a deleted message. Decided in this spec: TOKI-058, through a change handler registered before the event handler; this ticket ships the delete as a change and the seam test (R12). Reason: the tables and the storage of files do not exist until TOKI-058, which needs only TOKI-036, so this ticket cannot test a removal and TOKI-058 can. The plan line of TOKI-047 names the files; its "files leave storage" part is carried out by TOKI-058 and tested by AC-033 there. This moves the part of the plan line of TOKI-047 that says "files leave storage" (D-043, AC-033) to TOKI-058, which is a change of scope for the owner to see; it is named under "Risk" in the pull request. Owner: Thanh Truong.
7. The entry and the events of an edit and a delete. Decided in this spec: `deletedBy` is `"author"`, `"admin"` or `null` and carries no person (R8); the events are `message.edited` and `message.deleted` with `{ message }`, the same shape as the list, so one parser serves both (R10); the earlier text and the identity of the deleter travel only on the change, inside the transaction (R11). Reason: the line shows no name (D-049), a payload that held the earlier text would copy to every client what F16 says is not kept, and TOKI-050 and TOKI-065 need the earlier text only on the server. Owner: Thanh Truong.
8. Repeats. Decided in this spec: an unchanged edit answers 200 with `changed` `false` and writes nothing; a delete of a deleted message answers 200 and writes nothing, so `deleted_by` stays the first deleter. Reason: a double press and a retry must be safe (D-111, D-132) and must not show "(edited)" for no change or turn an author's delete into an Admin's line. The permission check runs before this answer, so a person who may not act still gets the refusal. Owner: Thanh Truong.
9. The locks. Decided in this spec: the account `FOR SHARE`, the conversation row in the mode of TOKI-037 R8 (`FOR SHARE` for a channel and a group, `FOR NO KEY UPDATE` for a `dm`), then the message row `FOR NO KEY UPDATE`, then, for a reply, the root through `recomputeThreadSummary` (R9). Reason: the conversation lock keeps an archive and a leave out of the window between the check and the update (TOKI-037 R8), and the `dm` follows the one rule of the module; `FOR NO KEY UPDATE` on the message row serialises two writes of one message and does not conflict with the `FOR KEY SHARE` that a reply insert takes on its parent, so a delete never deadlocks with a reply; the root is locked after the message, the order of TOKI-045 R4 and R9, and the event handler's counter lock stays last (TOKI-036 R18). This rests on the lock-mode table of PostgreSQL; the two-connection tests prove it when built. Owner: Thanh Truong.
10. Where focus goes after a delete. Decided in this spec: to the list region of the conversation that held the message. Reason: the message and its menu are gone or changed into a line, and TOKI-014 returns focus only to an opener that is still in the document (TOKI-093 concern 6 leaves this to the call site). Owner: Thanh Truong.
11. Which copy of a message wins. Decided in this spec: `isFresher` of TOKI-045 (R14): a deleted message is never replaced, a delete always wins over an undeleted copy, and of two edits the later `editedAt` wins; an edit or a delete writes only its own keys (`applyMessageChange`), so it never drops a newer reaction, pin or reply count; the answer of the person's own request is applied at once and the event that follows changes nothing. Reason: events can arrive twice or after a newer answer (a catch-up, TOKI-040 R13), and `message.created` already never replaces a held message (TOKI-040 R4); D-121 says the last save wins. Owner: Thanh Truong.
12. The edit field. Decided in this spec: one message is edited at a time in a window, and starting another ends the first without saving (the prototype has one editing message); a save of white space sends nothing and closes the field with the message unchanged (the prototype's `saveedit` ignores an empty text); no unsaved-form dialog, because F16 says Esc cancels (these three follow the prototype or the journey). The builder's choices, where neither speaks: the edit sends `prepareOutgoing(text).text`, as a send does; above the limit Save is disabled; on any error the field stays open with the text, so a text is never lost; and when the message turns deleted while the field is open, the field closes and its text is dropped, because the message no longer exists for an edit. Reason: the prototype and the journey give the first part, and the safe choice is made where neither speaks. Owner: Thanh Truong.
