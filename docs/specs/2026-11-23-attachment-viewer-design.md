## Goal
A message that carries files, images or links shows nothing of them today. This ticket draws them under the text of a message, as the prototype does: one card for each file, a thumbnail for each image, a card for each link preview. It also builds the details window that opens when a person presses a file or an image: sender, conversation, date, size, and the buttons Open in conversation, Copy link and Download.
The hard rules are two. A file is always downloaded and never run or drawn from its own bytes in the browser (D-095). A link to a file opens only for people who can read its conversation (F18, AC-029); the server decides that (TOKI-058 R12), and this ticket copies the link that the server decides on and never builds another.
The cards and the window are built once and are the ones the Files tab and the Files page (TOKI-063) reuse.

## Scope
- In:
  - The classes `.card` and `.fic`, which the base components spec assigned to this ticket, as `ui-web` components: the icon box, the file card, the image card and the link card (R2 to R5), `ButtonLink` for the Download anchor (R6), and `.imgph` and `.att`, which the prototype uses for them and no table assigns (concern 12).
  - The place under the text of a message (`messageExtensions.Files` of TOKI-042 R14): which card each file and each link gets, and their order (R7).
  - The two seams this ticket owns: `image.ts`, whose body TOKI-060 replaces, and the link-card seam (`link-cards.tsx`, `LinkCards`, `hasLinkCards`, the `action` slot of `LinkCard`, `.card`, the `.att` block and the grouping rule), which TOKI-061 uses (R8).
  - The details window: its data, its content, Open in conversation, Copy link, Download, and the one place it is opened from (R9 to R14).
  - The rule that a file is never run or drawn from its own bytes by the client (R15).
  - The rule that a message with files is not grouped (R16), the texts (R17), the styles (R18), the accessibility (R19) and the preview examples (R20).
- Out (not now):
  - Storing, signing and opening files, the entry key `files` and the rule of who can open a file: TOKI-058. This ticket calls its open route and reads its `FileEntry`.
  - The thumbnail itself, its size, its address and the key that carries them: TOKI-060. The link preview data, the worker, and the control that removes a link card (F12): TOKI-061. This ticket draws the image card and the link card from the values they give.
  - The composer's card of a file being uploaded (`.fchip`), progress, Retry and the over-100-MB card: TOKI-059.
  - The Files tab, the Files page, their lists, filters, search and grid, and the jump from them to a message in another conversation: TOKI-063, and TOKI-068 for the jump and its flash. They open the window of R10 with their own data.
  - Page counts such as "6 pages" on a file card (concern 11), previews of PDFs or documents, a zoom or a gallery over several images, and any viewer that shows the bytes of a file other than an image thumbnail.
  - The file size text: `formatFileSize` of TOKI-059, in `@toki/i18n`; this ticket imports it (concern 8).
  - Blocking file types and virus scanning: not built (D-095, D-186).

## Design
### How it fits
```
 message list (041)
   Message (042) -- messageExtensions.Files --> MessageFiles (R7)
        |                                          |-- FileCard / ImageCard  (ui-web)   --press--> useFileDetails().open (R9)
        |                                          |-- fileImage(file)  <- seam, TOKI-060 (R8)
        |                                          `-- LinkCards(message) <- seam, TOKI-061 (R8)
 app layout --> FileDetailsProvider --> FileDetailsModal (Modal, TOKI-014)
                   Open in conversation -> options.openInConversation (R12)
                   Copy link            -> clipboard().writeText(origin + /api/v1/files/<id>/download) (R13, proposal)
                   Download             -> <a href="/api/v1/files/<id>/download" target="_blank"> (R14)
                                              |-> 302 signed address, attachment (TOKI-058 R12, R13)
```

### Choices made here
- **One window for the whole app, opened with data.** The window takes a `FileDetails` value and not a message, so the Files tab and the Files page (TOKI-063), which list files and not messages, open the same window with values they build from their rows. It is mounted once in the layout, so a card never owns a dialog and a list row stays light.
- **The seams are files, not props.** `image.ts` and `link-cards.tsx` are the only places TOKI-060 and TOKI-061 edit, with defaults that draw a placeholder and nothing; this ticket is complete and testable without them, and neither ticket edits a card or the message component (the rule of TOKI-042 R14).
- **The original is never drawn.** The image in the window is the same thumbnail the card uses: TOKI-060 produces one rendition, 1040 px on the long side, for both. The original arrives only by Download (concern 1).
- **Copy link never copies a signed address.** The signed address lives 60 seconds (TOKI-058 R3), so a copied one would be dead before it is pasted; the route is stable and checks access each time it is opened (TOKI-058 R12). Whether the shared link is the route or an app page is open (concern 3).
- **Download is an anchor.** A redirect to another origin cannot be read with `fetch` without storage allowing the app's origin and without holding the bytes in memory; an anchor lets the browser follow the redirect and save the file with the name the server set, and holds no address. A new tab keeps the page when the route answers an error (a file whose message was deleted is 404), at the cost of a tab that opens and closes for a download.
- **The window has no state of its own about the file.** It shows what the message entry held when the card was pressed, a placeholder included. A message deleted or edited afterwards changes nothing in it; Download then answers 404 (TOKI-058 R12) in the new tab, and the person closes the window.

### Errors
- The route answers 404 for a file that was deleted or that the person may no longer read -> the new tab shows the not-found body of the server; the window stays as it was.
- The clipboard is refused or missing -> the failure toast (R13); nothing is copied.
- A thumbnail fails to load -> the placeholder (R4).
- A name that is 255 code points long, or has line breaks -> shown as text, cut on one line in the card and wrapped in the window (R19).
- A message with 10 files and 3 link cards -> 13 cards in the column; the list measures the row (TOKI-041 R20).

## Data safety
- The only address the client holds for a file is its route (`/api/v1/files/<id>/download`, no query), which carries no secret and opens only for people who can read the conversation (TOKI-058 R12). No signed address is read, stored, copied or logged by this ticket.
- File names and link texts are data: they are drawn as text, never as markup, never in an address and never in a log line. A link's `href` is drawn only when `TextLink` accepts it (`http` or `https`, TOKI-049 R8).
- The client draws nothing from the bytes of an uploaded file other than the server-made thumbnail (R15), so an HTML or SVG file cannot run in the page.
- The clipboard is written, never read (TOKI-052 R19).
- The rule that an HTML or SVG file never runs rests on the server: TOKI-058 R13 (layers 1 and 2) and TOKI-084, and on the storage host not sharing the app's origin (a hand-off to TOKI-058 and TOKI-084 in Plan changes). The client adds one more layer, R15 and the guard of R4, and the browser test of R21 proves only that a browser saves an answer that is an `attachment`.

8. The size text. Decided in this spec (a technical choice): the formatter is `formatFileSize(language, bytes)` of TOKI-059 in `@toki/i18n`, and this ticket has none of its own. Reason: two formatters of the same wave would disagree on the place, the argument order and the rounding; TOKI-059 is the earlier and `@toki/i18n` already holds `formatNumber`. The prototype's sizes (`212 KB`, `4.2 MB`, `1.8 MB`) follow the rule of TOKI-059 (KB with no decimal, MB and GB with at most one decimal), and the Plan changes line for TOKI-059 lists the values this ticket reads. The base of 1024 and the unit of the 100 MB limit are TOKI-059 and TOKI-058 concern 2; nothing in this ticket changes with them. Owner: Thanh Truong.
9. Which file is an image card. Decided in this spec (a technical choice, replaced by TOKI-060): until TOKI-060 says otherwise, a file is an image card when its declared type starts with `image/` and is not `image/svg+xml` (R8). Reason: F18 says images show as thumbnails and other files as cards; the declared type is the only data the entry has, and TOKI-058 keeps it as data and never as a rule for serving. SVG is left as a file card because a vector file has no thumbnail unless TOKI-060 makes one. A declared type is not proof of content, so the rule only chooses a card; a file that is not really an image shows a placeholder or its thumbnail error and still downloads. Owner: Thanh Truong.
10. The download opens a tab. Decided in this spec (a technical choice): the anchor uses `target="_blank"` (R14). Reason: the route answers 404 for a file that was deleted or is no longer readable, and an answer shown in the app's own tab would replace the page; in a new tab the person only loses that tab. The cost is a tab that flashes open and closes for a download in some browsers. Owner: Thanh Truong.
11. The page count on a file card. Not decided. The prototype's card reads `6 pages · 212 KB` for a PDF (line 1378), and the build has no page count: the server never reads the bytes of an upload (TOKI-058 Data safety, D-186) and `FileEntry` has `id`, `name`, `size` and `contentType`. Proposal, not a decision: the card shows the size only (R7); a page count would need a worker that reads the file, a later ticket. Owner: Thanh Truong (product owner).
12. Classes the tables do not assign. Decided in this spec: this ticket carries `.card`, `.imgph` and `.att` (used by the file, image and link cards, prototype lines 275 and 282 to 287; TOKI-061 reuses `.card` and `.att` through the seam of R8) and keeps the window's rows in its own file as `.file-details-row` with the values of the prototype's `.setrow` (padding 10 px 0, a line under it, a gap of 12 px), because `.setrow` is also a row of the preferences screens and no table assigns it; a later ticket that builds a shared row may replace it. Reason: the base components spec says a class that is in no table is carried over by the ticket that draws it. Owner: Thanh Truong.
13. One window mounted in the layout. Decided in this spec (a technical choice): `FileDetailsProvider` in `app-layout.tsx` (R10). Reason: the Files page and the message list are both under that layout, one window means one focus return and at most one dialog, and a card that owned a dialog would mount one for every file in a list of thousands. Owner: Thanh Truong.
