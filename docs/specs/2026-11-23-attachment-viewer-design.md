# Attachment cards and viewer modal design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/attachment-viewer.md (Thanh Truong)
Ticket: TOKI-062
Needs: TOKI-049 (`TextLink`, class `.lnk`, pull request 225), TOKI-058 (file storage, pull request 233: `FileEntry`, `GET /api/v1/files/{id}/download`), TOKI-042 (message component, pull request 221: `messageExtensions.Files`), TOKI-014 (`Modal`), TOKI-017 (i18n), TOKI-094 (`formatDay`), TOKI-052 (pull request 226: the `clipboard` member of the platform package). Reads, does not need: TOKI-060 (image thumbnails) and TOKI-061 (link previews), written in parallel; each fills one seam of this ticket (R8).

## Goal
A message that carries files, images or links shows nothing of them today. This ticket draws them under the text of a message, as the prototype does: one card for each file, a thumbnail for each image, a card for each link preview. It also builds the details window that opens when a person presses a file or an image: sender, conversation, date, size, and the buttons Open in conversation, Copy link and Download.
The hard rules are two. A file is always downloaded and never run or drawn from its own bytes in the browser (D-095). A link to a file opens only for people who can read its conversation (F18, AC-029); the server decides that (TOKI-058 R12), and this ticket copies the link that the server decides on and never builds another.
The cards and the window are built once and are the ones the Files tab and the Files page (TOKI-063) reuse.

## Scope
- In:
  - The classes `.card` and `.fic`, which the base components spec assigned to this ticket, as `ui-web` components: the icon box, the file card, the image card and the link card (R2 to R5), and `.imgph` and `.att`, which the prototype uses for them and no table assigns (concern 12).
  - The place under the text of a message (`messageExtensions.Files` of TOKI-042 R14): which card each file and each link gets, and their order (R7).
  - The two seams where the thumbnails of TOKI-060 and the link previews of TOKI-061 plug in (R8).
  - The details window: its data, its content, Open in conversation, Copy link, Download, and the one place it is opened from (R9 to R14).
  - The rule that a file is never run or drawn from its own bytes by the client (R15).
  - The file size text (R6), the rule that a message with files is not grouped (R16), the texts (R17), the styles (R18), the accessibility (R19) and the preview examples (R20).
- Out (not now):
  - Storing, signing and opening files, the entry key `files` and the rule of who can open a file: TOKI-058. This ticket calls its open route and reads its `FileEntry`.
  - The thumbnail itself, its size, its address and the key that carries them: TOKI-060. The link preview data, the worker, and the control that removes a link card (F12): TOKI-061. This ticket draws the image card and the link card from the values they give.
  - The composer's card of a file being uploaded (`.fchip`), progress, Retry and the over-100-MB card: TOKI-059.
  - The Files tab, the Files page, their lists, filters, search and grid, and the jump from them to a message in another conversation: TOKI-063, and TOKI-068 for the jump and its flash. They open the window of R10 with their own data.
  - Page counts such as "6 pages" on a file card (concern 11), previews of PDFs or documents, a zoom or a gallery over several images, and any viewer that shows the bytes of a file other than an image thumbnail.
  - Blocking file types and virus scanning: not built (D-095, D-186).

## Design
### How it fits
```
 message list (041)
   Message (042) -- messageExtensions.Files --> MessageFiles (R7)
        |                                          |-- FileCard / ImageCard  (ui-web)   --press--> useFileDetails().open (R9)
        |                                          |-- fileImage(file)  <- seam, TOKI-060 (R8)
        |                                          `-- LinkCards(message) <- seam, TOKI-061 (R8)
 app layout --> FileDetailsProvider --> FileDetailsModal (Modal, TOKI-014)
                   Open in conversation -> options.openInConversation (R12)
                   Copy link            -> clipboard().writeText(origin + /api/v1/files/<id>/download) (R13)
                   Download             -> <a href="/api/v1/files/<id>/download" target="_blank"> (R14)
                                              |-> 302 signed address, attachment (TOKI-058 R12, R13)
```

### Choices made here
- **One window for the whole app, opened with data.** The window takes a `FileDetails` value and not a message, so the Files tab and the Files page (TOKI-063), which list files and not messages, open the same window with values they build from their rows. It is mounted once in the layout, so a card never owns a dialog and a list row stays light.
- **The seams are files, not props.** `image.ts` and `link-cards.tsx` are the only places TOKI-060 and TOKI-061 edit, with defaults that draw a placeholder and nothing; this ticket is complete and testable without them, and neither ticket edits a card or the message component (the rule of TOKI-042 R14).
- **The original is never drawn.** The image in the window is the same thumbnail the card uses, at the size TOKI-060 gives it. The original arrives only by Download (concern 1).
- **Copy link copies the route, not the address.** The signed address lives 60 seconds (TOKI-058 R3), so a copied one would be dead before it is pasted; the route is stable and checks access each time it is opened (TOKI-058 R12).
- **Download is an anchor.** A redirect to another origin cannot be read with `fetch` without storage allowing the app's origin and without holding the bytes in memory; an anchor lets the browser follow the redirect and save the file with the name the server set, and holds no address. A new tab keeps the page when the route answers an error (a file whose message was deleted is 404), at the cost of a tab that opens and closes for a download.
- **The window has no state of its own about the file.** It shows what the message entry held when the card was pressed. A message deleted or edited afterwards changes nothing in it; Download then answers 404 (TOKI-058 R12) in the new tab, and the person closes the window.

### Errors
- The route answers 404 for a file that was deleted or that the person may no longer read -> the new tab shows the not-found body of the server; the window stays as it was.
- The clipboard is refused or missing -> the failure toast (R13); nothing is copied.
- A thumbnail fails to load -> the placeholder (R4).
- A name that is 255 code points long, or has line breaks -> shown as text, cut on one line in the card and wrapped in the window (R19).
- A message with 10 files and 3 link cards -> 13 cards in the column; the list measures the row (TOKI-041 R20).

## Data safety
- The only address the client holds for a file is its route (`/api/v1/files/<id>/download`, no query), which carries no secret and opens only for people who can read the conversation (TOKI-058 R12). No signed address is read, stored, copied or logged by this ticket.
- File names and link texts are data: they are drawn as text, never as markup, never in an address and never in a log line. A link's `href` is drawn only when `TextLink` accepts it (`http` or `https`, TOKI-049 R8).
- The client draws nothing from the bytes of an uploaded file other than the server-made thumbnail (R15), so an HTML or SVG file cannot run in the page.
- The clipboard is written, never read (TOKI-052 R19).

## Areas of concern
1. The image in the window. Decided in this spec (a technical choice that TOKI-058 R13 hands to this ticket): the window draws the thumbnail that TOKI-060 gives and never the original (R11, R15). Reason: the original is served with `nosniff` and the type `application/octet-stream`, and browsers may refuse to draw such an answer in an `img`; TOKI-058 does not claim it works and asks for a trial in Chrome and Safari before relying on it. Choosing the thumbnail needs no trial and cannot break for one browser. The cost: "opens large" (F18) is as large as the thumbnail. What this ticket asks of TOKI-060, which owns the size: its preview is at least 1040 px on the long edge (twice the 520 px width of the window, prototype line 287), so the window is sharp on a screen at 2x. If TOKI-060 keeps one small size, the window shows a small picture and the person downloads the original. Owner: Thanh Truong.
2. Copy link copies the route. Decided in this spec (the hand-off of TOKI-058 R12 and Plan changes): the text is the page's origin plus `/api/v1/files/<id>/download`, never a signed address (R13). Reason: the signed address ends in 60 seconds (TOKI-058 R3); the route is stable and is checked on every open (AC-029). The prototype copies `https://toki.hugepig.example/f/<id>`, a page that does not exist in the build; this is the departure. Owner: Thanh Truong.
3. A signed-out person who opens a copied link. Not decided. The route answers 401 to a request with no session (TOKI-058 R12), which a browser tab shows as the error body of the API, and the person is not taken to sign-in and back. The log has no rule for a link opened signed out. Proposal, not a decision: a page route that is a plain address of the app (for example `/files/<id>`), which sends a signed-out person to sign-in and, after sign-in, opens the file; Copy link would copy that address and not the API path. It needs a return-after-sign-in rule and a route that this ticket does not build; as written, the copied link is the API path and a signed-out person sees the 401 body. Owner: Thanh Truong (product owner).
4. Who opens a message from the window. Decided in this spec: this ticket builds the button and the in-conversation jump through the context of R12 and `ConversationPage`'s `onOpenMessage` (TOKI-041 R4); the Files page and tab supply their own function and TOKI-068 owns the jump from other places and the flash. Reason: the button is part of the window the plan gives this ticket (AC-107 step 3), and the page already owns the jump, so a context is the smallest bridge; the button is not drawn where nothing supplies a function. Owner: Thanh Truong.
5. A message with files is not grouped. Decided in this spec: R16 adds the prototype's rule `!(m.att||[]).length` to TOKI-041 R7, looking at the message itself. The TOKI-042 table gave the edit to TOKI-058, which draws nothing, so it is placed here with the cards it concerns. The log has no rule of its own for it; the prototype is the source (line 1351). Owner: Thanh Truong.

The prototype opens the window for a link from the Files page (line 1583, the `link` kind) with the title as the name, the value `Link` in the `Size` row, the buttons Open in conversation and Copy link, and Copy link copies a made-up file address; F18 and FR-39 describe the window for a file and say nothing about a link. Proposal, not a decision: the window supports a link item for the Files page of TOKI-063, with no `Size` row, no Download, and Copy link copying the link's own address (R11, R13, R14). Whether the link opens in the window at all is TOKI-063's list rule and the log's FR-39 ("every file, image and link"). Owner: Thanh Truong (product owner).
