# Update-available strip design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/update-available-strip.md (Thanh Truong)
Ticket: TOKI-104

## Goal
A deploy replaces the server and the web files at once. A person whose app stays open keeps the old page, and nothing tells them. This work gives the page a way to learn that a different version is running on the server, a strip that says "Update available" with a Reload button, and a forced reload for the one case where staying is not safe: the server says the page is too old for it (D-107, NFR-17).
After this change a person who keeps Toki open sees the strip soon after a deploy and reloads when it suits them; a page that the server no longer accepts reloads by itself.

## Scope
- In:
  - The version of a build (R2, R3) and the numbers that say how old a page may be (R1).
  - The server's word: a request from a page that is too old is refused (R4); the first frame of the socket carries the version and the oldest accepted page (R5, R6).
  - The client: it sends its number (R7), the update store (R8), the strip (R9), the reload (R10), the forced reload and its guard (R11, R12), a web file that cannot be fetched (R13), the texts (R14) and the browser test (R15).
  - The edit of the built gateway, `frames.ts` and the connection (R5, R6): they exist when this ticket is built, because it needs TOKI-082, which needs TOKI-039, which needs TOKI-038, so the edit is this ticket's.
- Out (not now):
  - The component `Strip` and its class `.strip`: built by TOKI-076 or TOKI-082 (see "Line with the strip tickets"). This work adds no file to `packages/ui-web/src/components/Strip/` and no example file: the `Strip` examples of that ticket already show the default tone.
  - The offline strip and the first-load retry: TOKI-082. The Pause and Focus strip: TOKI-076.
  - The Dockerfile, the Compose file, the Caddyfile, the headers of `index.html` (`no-store`), the tags: TOKI-084, which also owns the `ARG TOKI_BUILD_ID`, the Compose `args`, the function `define(buildId)` of `build.mjs` and the stack-check strings that R2 and R3 rely on. The build and the deploy on merge, and the value given to the build: TOKI-085 (R2 says what it must pass).
  - A service worker, a cache and an update flow for an installed copy: not built (D-030, NFR-06; TOKI-077 Scope).
  - Telling a person what changed in the new version.
  - A dismiss button for the strip (concern 2).

## Requirements
The shared numbers
- R1. `packages/shared/src/build.ts`, exported from the package index, holds: `CLIENT_COMPAT` (an integer, 1), the number that this commit's web app sends; `MIN_CLIENT_COMPAT` (an integer, 1), the oldest number that this commit's server accepts; `CLIENT_COMPAT_HEADER` (`"x-toki-client"`); `parseClientCompat(value: unknown): number | null`; and `isClientTooOld(compat: unknown, min: number): boolean`. `parseClientCompat` returns the integer for a number that is a safe integer of 0 or more, or for a text made only of digits with no sign, no space and no leading zero (`"0"` is read as 0, because a header is text, and at most 16 digits), and `null` for everything else (`"-1"`, `" 1"`, `"01"`, `"1e0"`, `"1.5"`, `""`, `"abc"`, a value above `Number.MAX_SAFE_INTEGER`, `undefined`, an array). `isClientTooOld` is true only when `parseClientCompat(compat)` is an integer below `min`. The rule for the two numbers is one step: a change that makes the server refuse what an older page sends sets both numbers to the same new integer (`MIN_CLIENT_COMPAT = CLIENT_COMPAT = N + 1`) in its own pull request; within `/api/v1` fields are only added (technical design), so a normal deploy raises neither. The author of that change makes the step; the check below keeps the pair consistent, and concern 4 says what is and is not checked. Check: a test table for `parseClientCompat` and `isClientTooOld` over the values above and over 0 and 1 against 1 and 2; and a test that `MIN_CLIENT_COMPAT <= CLIENT_COMPAT`, which fails when the minimum is raised without the number the web app of the same commit sends (that web app would be refused by its own server).

The server's word
- R4. A request under `/api/v1/` whose header `x-toki-client` holds an integer below the minimum is refused with status 426 and the error body of TOKI-004 (R8 there) with the code `client_too_old` (added to `ErrorCodes` in `packages/shared/src/error.ts`, which says a code is never renamed or removed) and a message that names no person and no internal. The hook is one app-level `onRequest` hook in `apps/server/src/app.ts`, not a hook of the `/api/v1` scope. It tests the path of `request.url` (before `?`) for the prefix `/api/v1/`, so a path that has no route is covered too (Fastify runs app-level `onRequest` hooks for the not-found handler) and `/healthz` (TOKI-004 R10) is never refused. The socket handshake of the browser carries no custom header, so it is never refused by this hook; the socket learns through the `ready` frame (R5). It is registered first in `buildApp`, before `registerAuthHooks` and the Origin rule (R46 of the sign-in API), so a signed-out page that is too old gets the 426 and reloads, not the 401 that sends it to the sign-in screen. The minimum comes from a new `buildApp` option `minClientCompat?: number`, default `MIN_CLIENT_COMPAT` (so `main.ts` passes nothing); a test passes it. The option sits next to `config`, `logStream` and `registerRoutes` (TOKI-004 R16). The value is read with `isClientTooOld` (R1): only a header made of digits is read; a header with no value, a sign, a space, a leading zero, a decimal, an exponent, a value above `Number.MAX_SAFE_INTEGER`, or a repeated header (Node joins repeated values with a comma, so the text is not digits) is not an integer and is not refused. The header is sent only by the web app, and a script, a test or a phone app of a later phase is not blocked by it. Status. 426 is chosen on purpose: it is the one status that `classifyApiError` of TOKI-032 R8 does not already send to a screen (400 is `field`, 403 and 404 are `no_access`, 409 and 410 are `fresh_copy`, 429 is `wait`, 5xx is `retry`), and the TOKI-004 format carries the class in the status and the meaning in `code`. RFC 9110 says a 426 response must carry an `Upgrade` header; this response does not, and that is a stated deviation: the header is connection-specific, HTTP/2 forbids it, Caddy serves HTTP/2 to browsers (TOKI-084), and no protocol token could name what the page must become. The page acts on the `code`, never on the header. Accepted in this spec (a technical choice, concern 4). The refusal is not rate limited and writes no row. Check: with the app built by `buildApp` and fake config and `minClientCompat` 1: a request with `x-toki-client: 0` answers 426 with the code, also when it has no session on a route that answers 401 to a signed-out request (the order against the auth and Origin hooks);a request with `1`, with no header and with `abc`, `-1`, ` 1`, `01`, `1e0`, a value above the safe integer and a repeated header is routed as before; a path under `/api/v1/` that does not exist answers 426 for a too-old header and 404 for none; `/healthz` with a too-old header answers as before; the response has no `Upgrade` header; no log line holds the header's value.
- R5. The first frame of the socket carries the server's word. The `ready` frame of TOKI-038 R7 becomes `{ "type": "ready", "eventNumber": N, "build": BUILD_ID, "minClient": MIN_CLIENT_COMPAT }`, with `build` a string and `minClient` an integer: the gateway always sends both and the schema in `packages/shared/src/realtime/frames.ts` declares both `optional`, so a client built for an older server still reads the frame and the client of R8 does nothing for a frame that lacks them. The extension is allowed by analogy, not by the text: TOKI-038 R7 writes the frame as exactly two fields and R12 allows a new `type` or `kind` within a version, not a field of a known frame; nothing forbids a field (no test of TOKI-038 asserts the whole object) and the rule that `/api/v1` only adds fields applies. The client reads the frame leniently: unknown keys are ignored (TOKI-032 R3). This ticket edits the built gateway and `frames.ts`; the existing tests of TOKI-038 R7 and TOKI-039 R9 stay unchanged because the fields are optional. Check: a gateway test reads the `ready` frame and finds the two fields with the values of the build; a schema test reads a frame with and without them and with an unknown extra key.
- R6. The connection reports the server's word. The connection of TOKI-039 (`createConnection`) gets one option, `onServerInfo({ build, minClient })`, called on every `ready` frame that holds both fields, before the catch-up of TOKI-039 R9 starts; it changes no other behaviour of the connection. Check: a connection test with a fake socket: `onServerInfo` is called once for each `ready` with both fields, with the values, before the first `catchUp` request is made, and not for a frame without them or with only one; every existing test of the connection passes unchanged.

The client
- R7. The API client sends its number. `createApiClient` (TOKI-032) gets the option `clientCompat?: number` and, for symmetry with `setOnUnauthenticated`, the setter `setOnClientTooOld(callback)`. When `clientCompat` is given, every request carries the header `x-toki-client` with that number; a caller's header of that name is ignored (its name joins `OWN_HEADERS`). A response with status 426 and the error code `client_too_old` calls the callback once per response and ends as the `ApiError` the client already makes for an HTTP error (`classifyApiError` sorts it as it sorts any status it does not list: it is a failure, never a field error); it is not retried (the request core has no retry, TOKI-032 R9). `apps/web/src/client.ts` makes the client with `clientCompat: CLIENT_COMPAT`, makes the update store (R8) after it, and calls `api.setOnClientTooOld(() => updates.observeTooOld())`; the setter is used because the client is made first in that file and the store needs no client. `client-core` imports no text and no `apps/web` file. The screen of TOKI-032 R8 for an `invalid_response` (`unreadable`, which asks for a reload because the page may be too old, NFR-17) does not call `forceReload`: an unreadable answer has other causes (a server fault) and would loop; the exact signals are the 426 and the `ready` frame, so the two do not give different answers to the same state. Check: with the fake `fetch` of the client tests: the header is on a GET and a POST, is absent when the option is absent, and a caller's value is dropped; a 426 with the code calls the callback once and rejects with an `ApiError` of `kind` `http`, `status` 426, code `client_too_old`; a 426 with another code, and a 409, call nothing.
- R8. The update store. `apps/web/src/update/update-store.ts` exports `createUpdateStore({ buildId, compat, reload, storage, clock })`, where `storage` is a function `() => StorageArea` and the app passes `() => getPlatform().storage.tab`; it is read at the first forced reload, because `client.ts` is imported (through `router`) before `main.tsx` runs `setPlatform(...)`, and `getPlatform()` before that throws (platform R2). The app makes one store in `client.ts` (like the stores of TOKI-076 R16: nothing in it imports the seams at load). `getState()` is `{ available: boolean }`, a new object at each change, with `subscribe(listener)` (returns the remover). Its commands, each safe to call any number of times, are: `observeServer({ build, minClient })` (the argument of R6), which calls `forceReload()` (R11) when `isClientTooOld(compat, minClient)` is true, and otherwise makes `available` true when `build` is not equal to `buildId` (when `build` equals `buildId`, `available` is not changed: a strip once shown stays, so a rollback to the version of the open page does not take back a Reload the person may already be about to press); `observeTooOld()` (from R7), which calls `forceReload()`; `observeStaleFile()` (R13), which makes `available` true; and `forceReload()` (R11). Nothing else changes `available`; there is no command that makes it false: it ends when the page is reloaded, which makes a new store. `useUpdateAvailable()` in `apps/web/src/update/` returns `available`. Check: a table over the commands with a fake `reload`, `storage` and `clock`: the same build id and a `minClient` not above `compat` leave `available` false and call nothing; a different build id sets it true and calls nothing; the same id after a different one leaves it true; `observeServer` with a `minClient` above `compat` calls `reload` and does not set `available`; `observeTooOld` calls `reload`; `observeStaleFile` sets it true; the listener is called once for the first change to true and not again; `getState()` returns a new object only when the value changed; the store is made without calling `storage` (a `storage` that throws does not fail the creation). `realtime.ts` passes `onServerInfo: updates.observeServer`; a test with a fake connection proves the wiring.
- R9. The strip. `apps/web/src/update/UpdateStrip.tsx` always draws a container with `role="status"` (a live region exists before its content changes, so it is announced when the text appears; it is empty and adds no height when nothing shows), and inside it, when `useUpdateAvailable()` is true, the `Strip` of `@toki/ui-web` with the tone `default` (no tone given), the icon `refresh` (the prototype's icon of that name), the text `t("update.strip.text")` in the `span.grow`, and the `action`, a `Button` with `t("update.strip.reload")`, which calls `reload()` (R10). TOKI-082 R5 gives `role="status"` to its offline strip only when it is `live`; this strip is mounted in the main area only, so it has the role always. `routes/app-layout.tsx` draws it in `main`, after the Pause and Focus strip of TOKI-076 and before `<Outlet />`, which is the order that TOKI-082 states (the offline strip, the Pause or Focus strip, the update strip, the page). The component holds no text and adds no file to `Strip/`. The strip appears in the main area only; the list screen of a phone is concern 6. Check: a render test of the layout route with a fake store: an empty `role="status"` container with `available` false; with true, one strip with the text, the icon and one button inside it, after the Pause strip when one shows; a press on the button calls the fake `reload` once; a source search of `apps/web/src/update/` and of `packages/ui-web/src` for the quoted text "Update available" finds none outside the test.
- R10. The reload. `apps/web/src/update/reload.ts` exports `reloadPage(location = window.location)`, which calls `location.reload()` and nothing else; the app gives it to the store as `reload`. The press does not ask for confirmation and does not wait: what a person has typed is already kept (the synced drafts of TOKI-051 and the waiting messages kept in the browser by TOKI-040), which is the reason no question is asked, and what a reload does to the stores is TOKI-040's. Check: a unit test with a fake `location`; the browser test of R15 shows the page loading again after the press.
- R11. The forced reload and its guard. `forceReload()` of the store reloads the page at once, with no strip, and at most once in 60 seconds. It reads `update.forcedAt` from `storage().get(...)`: the text is read as a time only when it is made of digits and is not above `clock.now()`; an absent, empty, non-numeric or future value (the clock was moved back) counts as absent. When the key is absent or `clock.now() - forcedAt >= 60_000`, it writes the current time first and, only if `set` returned true, calls `reload()`; otherwise (the key is fresh, or the write failed, R12) it makes `available` true and does not reload. Decided in this spec (concern 4): a page that is still too old right after a reload (a cached `index.html` somewhere between the browser and the server, or a deploy that is half done) would otherwise reload without end; the strip is then the honest state, because the page is old and the person can press Reload. The key is per tab and goes with the tab. Two signals in one tick (`observeTooOld` from a request and `observeServer` from the socket): the write is synchronous and comes before `reload()`, so the second call finds the fresh key and shows the strip. Check: with the fake clock of TOKI-008 and a fake storage: the first call reloads and writes the time; a second call at 59,999 ms later shows the strip and does not reload; one at 60,000 ms reloads; the values `"abc"`, `""` and a time ahead of the clock count as absent and reload; two calls in the same tick reload once; the key is read through `platform.storage.tab` and a source search of `apps/web/src/update/` for `localStorage`, `sessionStorage`, `setTimeout` and `Date.now` finds none.
- R12. The guard when storage fails. When `set` returns false (blocked site data, private mode), `forceReload()` does not reload: it makes `available` true, so the person sees the strip and decides. A memory copy of the time is not used: a reload destroys the page and its memory, so the new page would start with no copy and the loop would not be prevented. The cost is accepted: on a browser that blocks storage a page that is too old gets the strip and not the automatic reload; it is rare, and the strip is the state of the other case of R11. Check: with a fake storage whose `set` returns false: the first call shows the strip and does not call `reload`; a test of two page lives (a second store made over the same failing storage, as after a reload) calls `reload` zero times in total.
- R13. A web file that cannot be fetched. `apps/web/src/update/watch-stale-files.ts` listens, once, for the `vite:preloadError` event of `window` (Vite fires it when the file of a lazy part of the app cannot be fetched or parsed) and calls `updates.observeStaleFile()`. It does not call `preventDefault()`, so Vite's own rethrow reaches the code that asked for the part; the strip says why and what to do, and nothing else is shown by this ticket (no spec gives an error boundary for a failed part, and `LoadFailed` of TOKI-082 R10 takes an `ApiError`, which a failed file is not). The event also fires when the person is offline or the network failed, not only after a deploy (a 404 for a hashed file the new image no longer holds, TOKI-084 R16): the strip then shows for a cause that is not an update. Accepted: Reload fetches the page again, which is the right step in both cases, and the offline strip of TOKI-082 tells the other half. When it applies: `apps/web/src` has no dynamic import today (web-skeleton R10 excludes dynamic imports only from the first-load measure), so this listener has no live path until the first lazy part is added by a later ticket; it is installed now so that the first one is covered. The first load of the entry script is covered by the server (404 for a missing hashed file, TOKI-084 R16) and by R4. The listener is added by `main.tsx` in its body (not as an import, so the rule that `join/capture-on-load` is the first import that is not a style sheet holds), after `setPlatform(...)` and before the first render, and removed by nothing (the page's life). Check: dispatching a `vite:preloadError` event on a fake window sets `available`; the event is not cancelled (`defaultPrevented` is false); two events set the state once; a test that installs the listener twice (hot reload) adds one listener. A case with a real dynamic import is added to the browser test by the first ticket that adds one.

## Design
### How the page learns
```
deploy: new server + new web files (one build id)
  server restarts --> sockets close (1001) --> client reconnects (TOKI-039, 1 to 30 s)
     --> ready { build, minClient } --> onServerInfo (R6) --> update store
          build differs ................. available --> UpdateStrip "Update available" + Reload
          minClient > page's number ..... forceReload (once in 60 s; the strip when the guard or the storage says no)
  any request with x-toki-client < minClient --> 426 client_too_old --> setOnClientTooOld --> forceReload
  a lazy file 404 (old page, new files) ----------> vite:preloadError --> available (no lazy file yet, R13)
```
- Why the first frame: a deploy restarts the server, so every open page loses its socket and reconnects within about 30 seconds (TOKI-039 R11); the `ready` frame is the first thing it receives, and it arrives with no request. A page that makes no request for hours still learns. A page whose socket is stopped for another reason (TOKI-039 R12) learns at its next request only if it is too old (R4).
- Why two numbers and an id: the id says "different", never "older", so it only ever produces the strip. The numbers say "too old" and are chosen by a person, in the pull request that breaks compatibility (R1), so the forced reload is rare and deliberate; concern 4 says that this is a review rule and what a forgotten step costs.
- A page that is too old for the server, and also cannot parse a new `ready` frame, is covered by R4 on its first request, and by the strictness rule: client schemas ignore unknown keys (TOKI-032 R3), so an added field is never the thing that breaks a page.

### Version of a deploy
The build id is the commit hash, given by TOKI-085 when it builds the images; a build by hand without it holds `dev` in both images and never shows a strip. The tag `TOKI_TAG` (TOKI-084) names a release for the operator; the id names the code. They can differ: a rollback sets `TOKI_TAG` to an older tag, which holds an older id, so open pages see a different id and show the strip. That is the right behaviour: the open page is not the version that the server runs, and Reload makes it so. Running the same deploy again (same commit, same id) changes nothing and shows no strip.
Constraint on TOKI-085: it builds both images in one step with one `TOKI_BUILD_ID`. If it builds them separately with different values, every page would see a different version for ever; the stack check of TOKI-084 (R22 there) proves one build holds one value.

### Line with the strip tickets
- `Strip`: this ticket uses `Strip` with the default tone and builds none of it, as TOKI-082 R1 says. Who builds the folder (TOKI-076 as it proposes, or TOKI-082) is their open question; this ticket needs whichever ticket does, and the shape is the one TOKI-076 R18 and TOKI-082 R1 both state, so nothing here changes with the answer. The plan's "needs TOKI-082" holds; if the folder is built by TOKI-076, TOKI-076 (on main) comes first. If this ticket is built before either, it cannot be, and the ticket waits (concern 5).
- The order in `main` is TOKI-082's "Where the strips sit": `app-layout.tsx` holds it; this work adds one line.
- TOKI-084 owns the headers: `index.html` is `no-store` (R16 there), so a reload always fetches the new page. This work relies on it and adds no header.

### Errors
- A 426 `client_too_old` on a request: the page reloads (R11); the request itself is not repeated, the new page makes its own.
- A reload that does not help (a stale `index.html` upstream): the guard of R11 shows the strip after the first forced reload, and a second forced signal within 60 seconds does not loop; when the storage cannot keep the time the strip shows and nothing reloads (R12).
- A `ready` frame with no `build` or no `minClient`: nothing happens (an older server).

## Testing
- Tests are written first. Shared: R1 as a table and the guard that the minimum never exceeds the number sent. Server: R3's `define` through esbuild, R4 with `buildApp`, R5 in the gateway tests. Client: R6 with a fake socket, R7 with the fake `fetch`, R8 as a table with the fake clock and storage, R9 with a layout render, R10 to R13 as listed, R14 with the key check. One browser test (R15). R2 is a build test of the web configuration.
- Every requirement has its check in its own text: R1 table and consistency test; R2 and R3 `define` tests; R4 hook cases; R5 gateway and schema tests; R6 connection test; R7 client tests; R8 store table; R9 render; R10 unit test; R11 and R12 guard tests with the fake clock and storage; R13 event tests; R14 key check; R15 browser test.
- Time is never tested with a real timer: the 60 seconds of R11 use the controllable clock of TOKI-008, and the browser test uses `page.clock` (R15 names why).
- The stack check that one build holds one value in both images is TOKI-084 R22; this ticket adds no Docker test.
- Negative controls: a store that reloads without reading the guard fails the 59,999 ms case; a store that reloads when `set` fails fails the two-page-lives case; an `isClientTooOld` that returns true for a missing header fails the table; a hook that runs after the auth hook fails the signed-out case.

## Data safety
- The build id is a commit hash: public in the web bundle, no secret, no person. The header `x-toki-client` holds one integer. Neither is logged with a value (R3). The storage key holds a time only.

## Open questions from the intent
- How does the server say that a page is too old? Answered: Design, "How the page learns", R1, R4, R5. No signal existed in the specs of TOKI-038 or TOKI-039 or in the code; this work adds one (Decided in this spec, a technical choice, concern 4). The existing client-side signal, the `unreadable` screen of TOKI-032 R8, is left as it is (R7).
- Where does the version come from, and who gives it to the build? Answered: R2, R3 and "Version of a deploy" (a build argument that TOKI-084 declares; TOKI-085 passes the commit hash). Decided in this spec (a technical choice, concern 3).
- Can the person dismiss the strip? Not answered: D-107 gives a strip and a Reload and says nothing about dismissal. Carried forward as concern 2, with a proposal of no dismiss button.
- Does the strip show on a phone while the conversation list is the whole screen? Not answered. Carried forward as concern 6.

## Areas of concern
1. The split of the words "Update available · Reload" into a text and a button. D-107 gives the words; it does not give the split. The prototype has no such strip (its Focus strip writes ` · ` inside the text, line 1270, and has a button of the `.strip .btn` rule, line 226). Proposal, not a decision: the text "Update available" and the button "Reload", the dot dropped because the two are separate (R9, R14); keeping the dot as text is the other choice. Vietnamese is a proposal that TOKI-080 reviews (D-139). Not decided. Owner: Thanh Truong (product owner).
2. A dismiss button. D-107 gives a strip with Reload and says nothing about dismissal, so "no dismiss" is a reading of its silence, not a decision. Proposal, not a decision: none is built and the strip stays until the page is reloaded; a dismiss button would be a new requirement with a place to keep the choice. Not decided. Owner: Thanh Truong (product owner).
3. The version source. Decided in this spec (a technical choice): a build argument `TOKI_BUILD_ID`, the commit hash, baked into both bundles by `define`. Reason: the server and the web files are built from one commit and one tag (TOKI-084 concern 4); a value in `.env` would have to be set by hand and could differ between the two images; a hash of `index.html` would be known only to the web build. Cost: TOKI-084's Dockerfile, Compose file, `define` function and stack check carry the lines (they are TOKI-084's, which accepted the request), and TOKI-085 must pass one value (Plan changes). Owner: Thanh Truong.
4. How the server says "too old". Decided in this spec (a technical choice): two integers in `packages/shared` (R1), a header on every request from the web app (R4, R7) and two fields on the `ready` frame (R5); a missing header is never refused. It adds a code to the error registry and a header and two fields to contracts of merged specs (TOKI-004, TOKI-032, TOKI-038, TOKI-039). Reasons: no signal exists; a compare of build ids could only say "different", which would force a reload after every deploy and defeat D-107. The alternative, a socket close code for a too-old page, would need the client's number at the handshake (a query string, which TOKI-038 R5 keeps out of authentication) and is not built. The loop guard of R11 and R12 is also decided here. What is checked and what is not: the test of R1 keeps the pair consistent, but nothing detects a breaking change whose author forgot to raise the numbers; that is a review rule, backed by one line in `docs/definition-of-done.md` ("a change that the server refuses from an older page sets `MIN_CLIENT_COMPAT` and `CLIENT_COMPAT` to the same new integer"). The cost of a forgotten step is that an old page keeps running and its requests fail with an unreadable answer (TOKI-032 R8, the `unreadable` screen), and it is never reloaded by itself; a snapshot test of the error-code registry and the response schemas was considered and not built, because most breaks are in behaviour that no snapshot sees. Owner: Thanh Truong.
5. Who builds `Strip`. Decided in this spec (a technical choice) for this ticket only: it uses the component and builds none of it, and needs the ticket that builds it. The owner question itself is concern 1 of TOKI-082 and of TOKI-076 and stays theirs. Owner: Thanh Truong.
6. The phone's list screen. Not decided. D-107 says "an open app" and the log gives no place; the Pause and Focus strip is drawn in the main area only (TOKI-076 R18), and so is this strip (R9), but on a phone the list is the whole screen when no conversation is open, so a person there sees no strip until they open a conversation. Proposal, not a decision: also draw it as the `notice` of the conversation list as TOKI-082 R5 does for the offline strip. Owner: Thanh Truong (product owner).
