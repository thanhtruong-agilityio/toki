# Update-available strip design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/update-available-strip.md (Thanh Truong)
Ticket: TOKI-104

## Goal
A deploy replaces the server and the web files at once. A person whose app stays open keeps the old page, and nothing tells them. This work gives the page a way to learn that a different version is running on the server, a strip that says so with a Reload button, and a forced reload for the one case where staying is not safe: the server says the page is too old for it (D-107, NFR-17).
After this change a person who keeps Toki open sees "Update available · Reload" soon after a deploy and reloads when it suits them; a page that the server no longer accepts reloads by itself.

## Scope
- In:
  - The version of a build (R2) and the numbers that say how old a page may be (R1).
  - The server's word: the first frame of the socket carries the version and the oldest accepted page (R4); a request from a page that is too old is refused (R3).
  - The client: it sends its number (R5), the update store (R6), the strip (R7), the reload (R8), the forced reload and its guard (R9), a web file that cannot be fetched (R10), the texts (R11), the examples and the browser test (R12, R13).
- Out (not now):
  - The component `Strip` and its class `.strip`: built by TOKI-076 or TOKI-082 (see "Line with the strip tickets"). This work adds no file to `packages/ui-web/src/components/Strip/`.
  - The offline strip and the first-load retry: TOKI-082. The Pause and Focus strip: TOKI-076.
  - The Dockerfile, the Compose file, the Caddyfile, the headers of `index.html` (`no-store`), the tags: TOKI-084. The build and the deploy on merge, and the value given to the build: TOKI-085 (R2 says what it must pass).
  - A service worker, a cache and an update flow for an installed copy: not built (D-030, NFR-06; TOKI-077 Scope).
  - Telling a person what changed in the new version.
  - A dismiss button for the strip (concern 2).

## Requirements
The shared numbers
- R1. `packages/shared/src/build.ts`, exported from the package index, holds: `CLIENT_COMPAT` (an integer, 1), the number that this commit's web app sends; `MIN_CLIENT_COMPAT` (an integer, 1), the oldest number that this commit's server accepts; `CLIENT_COMPAT_HEADER` (`"x-toki-client"`); and `isClientTooOld(compat: unknown, min: number): boolean`, which is true only when `compat` is an integer below `min` (a missing, empty or non-numeric value is not too old). A change that makes the server refuse what an older page sends raises `MIN_CLIENT_COMPAT` in its own pull request; within `/api/v1` fields are only added (technical design), so a normal deploy never raises it. Check: a test table for `isClientTooOld` (0 and 1 against 1 and 2, `undefined`, `""`, `"x"`, `1.5`; the text `"0"` is read as the integer 0 because a header is text); and a test that `MIN_CLIENT_COMPAT <= CLIENT_COMPAT`, which fails when someone raises the minimum above the number the web app of the same commit sends (that web app would be refused by its own server).

The version of a build
- R2. A build has one version string, the build id, `TOKI_BUILD_ID`, given once when the two images are built. `apps/web` reads it in `vite.config.ts` from `process.env.TOKI_BUILD_ID` (default `dev`) and defines the global `__TOKI_BUILD_ID__` with `define`; `apps/web/src/update/build-id.ts` exports `BUILD_ID = typeof __TOKI_BUILD_ID__ !== "undefined" ? __TOKI_BUILD_ID__ : "dev"`. `apps/server` does the same: the `define` map is made by one function exported from `apps/server/scripts/build.mjs` (TOKI-084 R4) and `apps/server/src/build-id.ts` exports `BUILD_ID` the same way (under `tsx` in development there is no define, so it is `dev`). The id is a build-time constant: no environment variable of the server or the worker, no row of `.env`, no value in `.env.example`. The `Dockerfile` of TOKI-084 declares `ARG TOKI_BUILD_ID=dev` in the `build` stage, just before the two `RUN` lines that build `apps/web` and `apps/server` (so the layer that installs dependencies stays cached), and the `build` section of every service of `docker-compose.prod.yml` that builds a target passes `args: TOKI_BUILD_ID: ${TOKI_BUILD_ID:-dev}`; the one value reaches both images (TOKI-084 R1: one commit, one tag). TOKI-085 passes the commit hash (`TOKI_BUILD_ID=<full commit sha>`) once for both images (Design, "Version of a deploy"). Decided in this spec (concern 3). Check: a test of the `define` function (the same one the build calls) builds `build-id.ts` with the id `abc` through esbuild and the exported value is `abc`, and is `dev` without a define; a text test of the `Dockerfile` and of the Compose file finds the `ARG` before the two build steps and the `args` line in each build section; after `docker compose build` with `TOKI_BUILD_ID=check` (the stack check of TOKI-084 R22), the string `check` is in the built `apps/web/dist/assets/*.js` that holds `BUILD_ID` and in the server image's `dist/main.js`, and a build without the variable holds `dev` in both.

The server's word
- R3. A request under `/api/v1` whose header `x-toki-client` holds an integer below `MIN_CLIENT_COMPAT` is refused before routing with status 426 and the error body of TOKI-004 with the code `client_too_old` (added to `ErrorCodes` in `packages/shared/src/error.ts`, which says a code is never renamed or removed) and a message that names no person and no internal. It is one `onRequest` hook in `apps/server/src/app.ts`, registered before the routes, that calls `isClientTooOld` (R1). A request with no such header, or a value that is not an integer, is not refused: the header is sent only by the web app, and a script, a test or a phone app of a later phase is not blocked by it. The refusal is not rate limited and writes no row. Check: with the app built by `buildApp` and fake config, a request with `x-toki-client: 0` (the minimum set to 1 by the test through the hook's option) answers 426 with the code, a request with `1`, with no header and with `abc` is routed as before, a route that does not exist answers 426 for a too-old header and 404 for none, and no log line holds the header's value.
- R4. The first frame of the socket carries the server's word. The `ready` frame of TOKI-038 R7 becomes `{ "type": "ready", "eventNumber": N, "build": BUILD_ID, "minClient": MIN_CLIENT_COMPAT }`, with `build` a string and `minClient` an integer; both are always sent. The schema of the frame in `packages/shared/src/realtime/frames.ts` declares them `optional`, so a client built for an older server still reads the frame, and the client of R6 does nothing for a frame that lacks them. The connection of TOKI-039 gets one option, `onServerInfo({ build, minClient })`, called on every `ready` frame that holds both, before the catch-up of TOKI-039 R9 starts; it changes no other behaviour of the connection. Whichever of TOKI-038 or TOKI-039 is built later adds its half (the fields in the frame and its schema; the option); the other ticket's spec gets a plan change from this one (Plan changes). Check: a gateway test reads the `ready` frame and finds the two fields with the values of the build; a schema test reads a frame with and without them; a connection test with a fake socket: `onServerInfo` is called once for each `ready` with both fields, with the values, before the first `catchUp` request is made, and not for a frame without them; every existing test of the connection passes unchanged.

The client
- R5. The API client sends its number. `createApiClient` (TOKI-032) gets the option `clientCompat?: number` and the option `onClientTooOld?: () => void`. When `clientCompat` is given, every request carries the header `x-toki-client` with that number; a caller's header of that name is ignored (its name joins `OWN_HEADERS`). A response with status 426 and the error code `client_too_old` calls `onClientTooOld` once per response and ends as the `ApiError` the client already makes for an HTTP error (`classifyApiError` sorts it as before: it is a failure, never a field error); it is not retried (the request core has no retry, TOKI-032 R9). `apps/web/src/client.ts` passes `clientCompat: CLIENT_COMPAT` and an `onClientTooOld` that calls `updates.observeTooOld()` (R6); `client-core` imports no text and no `apps/web` file. Check: with the fake `fetch` of the client tests: the header is on a GET and a POST, is absent when the option is absent, and a caller's value is dropped; a 426 with the code calls the callback once and rejects with an `ApiError` of `kind` `http`, `status` 426, code `client_too_old`; a 426 with another code, and a 409, call nothing.
- R6. The update store. `apps/web/src/update/update-store.ts` exports `createUpdateStore({ buildId, compat, reload, storage, clock })` and the app makes one in `client.ts` (like the stores of TOKI-076 R16: nothing in it imports the seams). `getState()` is `{ available: boolean }`, a new object at each change, with `subscribe(listener)` (returns the remover). Its commands, each safe to call any number of times, are: `observeServer({ build, minClient })` (the argument of R4), which calls `forceReload()` (R9) when `isClientTooOld(compat, minClient)` is true, and otherwise makes `available` true when `build` is not equal to `buildId` (when `build` equals `buildId`, `available` is not changed: a strip once shown stays, so a rollback to the version of the open page does not take back a Reload the person may already be about to press); `observeTooOld()` (from R5), which calls `forceReload()`; `observeStaleFile()` (R10), which makes `available` true; and `forceReload()` (R9). Nothing else changes `available`; there is no command that makes it false: it ends when the page is reloaded, which makes a new store. `useUpdateAvailable()` in `apps/web/src/update/` returns `available`. Check: a table over the commands with a fake `reload`, `storage` and `clock`: the same build id and a lower `minClient` than `compat` leave `available` false and call nothing; a different build id sets it true and calls nothing; the same id after a different one leaves it true; `observeServer` with a `minClient` above `compat` calls `reload` and does not set `available`; `observeTooOld` calls `reload`; `observeStaleFile` sets it true; the listener is called once for the first change to true and not again; `getState()` returns a new object only when the value changed. `realtime.ts` passes `onServerInfo: updates.observeServer`; a test with a fake connection proves the wiring.
- R7. The strip. `apps/web/src/update/UpdateStrip.tsx` draws, when `useUpdateAvailable()` is true, the `Strip` of `@toki/ui-web` with the tone `default` (no tone given), the icon `refresh` (the prototype's icon of that name), the text `t("update.strip.text")` in the `span.grow`, and the `action`, a `Button` with `t("update.strip.reload")`, which calls `reload()` (R8). It has `role="status"` and draws nothing when `available` is false. `routes/app-layout.tsx` draws it in `main`, after the Pause and Focus strip of TOKI-076 and before `<Outlet />`, which is the order that TOKI-082 states (the offline strip, the Pause or Focus strip, the update strip, the page). The component holds no text and adds no file to `Strip/`. The strip appears in the main area only; the list screen of a phone is concern 3. Check: a render test of the layout route with a fake store: nothing with `available` false; with true, one `role="status"` strip with the text, the icon and one button, as the first child of `main` when no other strip shows and after the Pause strip when one does; a press on the button calls the fake `reload` once; a source search of `apps/web/src/update/` and of `packages/ui-web/src` for the quoted text "Update available" finds none outside the test and the examples.
- R8. The reload. `apps/web/src/update/reload.ts` exports `reloadPage(location = window.location)`, which calls `location.reload()` and nothing else; the app gives it to the store as `reload`. The press does not ask for confirmation and does not wait: what a person has typed is already kept (the synced drafts of TOKI-051 and the waiting messages kept in the browser by TOKI-040), which is the reason no question is asked, and what a reload does to the stores is TOKI-040's. Check: a unit test with a fake `location`; the browser test of R13 shows the page loading again after the press.
- R9. The forced reload and its guard. `forceReload()` of the store reloads the page at once, with no strip, and at most once in 60 seconds: it reads `update.forcedAt` from `platform.storage.tab` (a number of milliseconds, written as text), and when the key is absent or `clock.now() - forcedAt >= 60_000` it writes the current time first and then calls `reload()`; otherwise it makes `available` true and does not reload. Decided in this spec (concern 4): a page that is still too old right after a reload (a cached `index.html` somewhere between the browser and the server, or a deploy that is half done) would otherwise reload without end; the strip is then the honest state, because the page is old and the person can try the Reload button. The key is per tab and goes with the tab. A storage that fails (`set` returns false, private mode) counts as "no key": the reload goes ahead once per call, and the store's own state remembers the time of the last forced reload in memory, so a page that stays alive does not loop either. Check: with the fake clock of TOKI-008 and a fake storage: the first call reloads and writes the time; a second call at 59,999 ms later shows the strip and does not reload; one at 60,000 ms reloads; a storage whose `set` fails still reloads once and the second call within 60 seconds does not (the memory copy); the key is read through `platform.storage.tab` and a source search of `apps/web/src/update/` for `localStorage`, `sessionStorage`, `setTimeout` and `Date.now` finds none.
- R10. A web file that cannot be fetched. `apps/web/src/update/watch-stale-files.ts` listens, once, for the `vite:preloadError` event of `window` (Vite fires it when the file of a lazy part of the app cannot be fetched or parsed) and calls `updates.observeStaleFile()`. It does not call `preventDefault()`: the screen that asked for the part still shows its own failure (the shared Retry of TOKI-082 R10), and the strip says why and what to do. This is the case TOKI-084 names (an open page asks for a hashed file that the new image no longer holds and gets 404, TOKI-084 R16 and Errors). The listener is added by `main.tsx` before the first render and removed by nothing (the page's life). Check: dispatching a `vite:preloadError` event on a fake window sets `available`; the event is not cancelled (`defaultPrevented` is false); two events set the state once; a test that installs the listener twice (hot reload) adds one listener.

- R12. The example. This work adds no component, so it adds no example file; the `Strip` examples of TOKI-076 or TOKI-082 already show the default tone. Check: the component preview (TOKI-016) is unchanged by this work.
- R13. The proof in a browser. One test, `e2e/update.spec.ts`, built like `e2e/quiet.spec.ts` of TOKI-076 (the stubs of TOKI-041 R25, `routeWebSocket`, `page.clock`): (a) the first `ready` frame carries the page's own build id and `minClient` 1: no strip; (b) the socket is closed and reopened and the new `ready` carries another build id: the strip "Update available" with "Reload" shows in the main area, the page was not reloaded (the count of requests for `/` is still 1); (c) a third `ready` carrying the first id again leaves the strip; (d) pressing Reload loads the page again (the count is 2) and the strip is gone; (e) in a new page, a `ready` with `minClient` 2 reloads at once with no strip (count 2), and a second one within the 60 seconds, after `page.clock` moved 59 seconds, shows the strip and does not reload; after 61 seconds a third reloads; (f) a request to `/api/v1/...` answered with 426 and the code `client_too_old` by the stub reloads the page. The build id of the page in this test is the one the dev build holds, `dev`, and the stub sends `dev` and `other`. Check: that test.

## Design
### How the page learns
```
deploy: new server + new web files (one build id)
  server restarts --> sockets close (1001) --> client reconnects (TOKI-039, 1 to 30 s)
     --> ready { build, minClient } --> onServerInfo --> update store
          build differs ................. available --> UpdateStrip "Update available · Reload"
          minClient > page's number ..... forceReload (once in 60 s) or the strip
  any request with x-toki-client < minClient --> 426 client_too_old --> onClientTooOld --> forceReload
  a lazy file 404 (old page, new files) ----------> vite:preloadError --> available
```
- Why the first frame: a deploy restarts the server, so every open page loses its socket and reconnects within about 30 seconds (TOKI-039 R11); the `ready` frame is the first thing it receives, and it arrives with no request. A page that makes no request for hours still learns. A page whose socket is stopped for another reason (TOKI-039 R12) learns at its next request only if it is too old (R3).
- Why two numbers and an id: the id says "different", never "older", so it only ever produces the strip. The numbers say "too old" and are chosen by a person, in the pull request that breaks compatibility (R1), so the forced reload is rare and deliberate.
- A page that is too old for the server, and also cannot parse a new `ready` frame, is covered by R3 on its first request, and by the strictness rule: client schemas ignore unknown keys (TOKI-032 R3), so an added field is never the thing that breaks a page.

### Version of a deploy
The build id is the commit hash, given by TOKI-085 when it builds the images; a build by hand without it holds `dev` in both images and never shows a strip. The tag `TOKI_TAG` (TOKI-084) names a release for the operator; the id names the code. They can differ: a rollback sets `TOKI_TAG` to an older tag, which holds an older id, so open pages see a different id and show the strip. That is the right behaviour: the open page is not the version that the server runs, and Reload makes it so. Running the same deploy again (same commit, same id) changes nothing and shows no strip.
Constraint on TOKI-085: it builds both images in one step with one `TOKI_BUILD_ID`. If it builds them separately with different values, every page would see a different version for ever; the stack check of TOKI-084 (R2 above) proves one build holds one value.

### Line with the strip tickets
- `Strip`: this ticket uses `Strip` with the default tone and builds none of it, as TOKI-082 R1 says. Who builds the folder (TOKI-076 as it proposes, or TOKI-082) is their open question; this ticket needs whichever ticket does, and the shape is the one TOKI-076 R18 and TOKI-082 R1 both state, so nothing here changes with the answer. The plan's "needs TOKI-082" holds; if the folder is built by TOKI-076, TOKI-076 (on main) comes first. If this ticket is built before either, it cannot be, and the ticket waits (concern 5).
- The order in `main` is TOKI-082's "Where the strips sit": `app-layout.tsx` holds it; this work adds one line.
- TOKI-084 owns the headers: `index.html` is `no-store` (R16 there), so a reload always fetches the new page. This work relies on it and adds no header.

### Errors
- A 426 `client_too_old` on a request: the page reloads (R9); the request itself is not repeated, the new page makes its own.
- A reload that does not help (a stale `index.html` upstream): the guard of R9 shows the strip after the first forced reload, and a second forced signal within 60 seconds does not loop.
- A `ready` frame with no `build`: nothing happens (an older server).

## Testing
- Tests are written first. Shared: R1 as a table and the guard that the minimum never exceeds the number sent. Server: R2's define through esbuild, R3 with `buildApp`, R4 in the gateway tests. Client: R5 with the fake `fetch`, R6 as a table with the fake clock and storage, R7 with a layout render, R8 to R10 as listed, R11 with the key check. One browser test (R13). One stack check extension (R2).
- Time is never tested with a real timer: the 60 seconds of R9 use the controllable clock of TOKI-008 and `page.clock`.
- Negative controls: a store that reloads without reading the guard fails the 59,999 ms case; a `isClientTooOld` that returns true for a missing header fails the table; a build with a different id for the server fails the stack check.

## Data safety
- The build id is a commit hash: public in the web bundle, no secret, no person. The header `x-toki-client` holds one integer. Neither is logged with a value (R3). The storage key holds a time only.

## Areas of concern
1. The split of the words "Update available · Reload" into a text and a button. Decided by D-107 for the words; the prototype has no such strip, so the split follows the Pause and Focus strip of the prototype (a text in the strip and a button of the `.strip .btn` rule, line 226): the text "Update available", the button "Reload", the dot of D-107 dropped because the two are separate. Vietnamese is a proposal that TOKI-080 reviews (D-139). Owner: Thanh Truong (product owner).
2. A dismiss button. Decided by D-107: the log gives a strip with Reload and nothing else, so none is built; the strip stays until the page is reloaded. If the product owner wants one, it is a new requirement with a place to keep the choice. Owner: Thanh Truong (product owner).
3. The version source. Decided in this spec: a build argument `TOKI_BUILD_ID`, the commit hash, baked into both bundles by `define`. Reason: the server and the web files are built from one commit and one tag (TOKI-084 concern 4); a value in `.env` would have to be set by hand and could differ between the two images; a hash of `index.html` would be known only to the web build. Cost: TOKI-084's Dockerfile and Compose file gain the lines of R2, and TOKI-085 must pass one value (Plan changes). Owner: Thanh Truong.
4. How the server says "too old". Decided in this spec: two integers in `packages/shared` that a person raises (R1), a header on every request from the web app (R3, R5) and two fields on the `ready` frame (R4); a missing header is never refused. Reasons: no signal exists; a compare of build ids could only say "different", which would force a reload after every deploy and defeat D-107; the integers make the forced reload a decision in a pull request. The alternative, a socket close code for a too-old page, would need the client's number at the handshake (a query string, which TOKI-038 R5 keeps out of authentication) and is not built. The loop guard of R9 (one forced reload in 60 seconds) is also decided here. Owner: Thanh Truong.
5. Who builds `Strip`. Decided in this spec for this ticket only: it uses the component and builds none of it, and needs the ticket that builds it. The owner question itself is concern 1 of TOKI-082 and of TOKI-076 and stays theirs. Owner: Thanh Truong.
6. The phone's list screen. Not decided. D-107 says "an open app" and the log gives no place; the Pause and Focus strip is drawn in the main area only (TOKI-076 R18), and so is this strip (R7), but on a phone the list is the whole screen when no conversation is open, so a person there sees no strip until they open a conversation. Proposal, not a decision: also draw it as the `notice` of the conversation list as TOKI-082 R5 does for the offline strip. Owner: Thanh Truong (product owner).
