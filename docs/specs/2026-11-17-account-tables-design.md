# Account tables design

Date: 2026-11-17 · Status: draft for review
Intent: docs/intents/account-tables.md (Thanh Truong)
Ticket: TOKI-019

## Goal
The builder (Thanh working with Claude) needs the database to hold accounts: who a person is, their role and status, the sign-in codes that were issued, the sessions that are open and the devices that registered for push. Sign-in, the first Admin, member management, sessions and the permission rules all read and write these records, and every conversation table points to the account table. This work adds the four tables in one migration, with the rules of each column kept in the table itself, and states once the conventions that every later server table follows.

## Scope
- In:
  - The tables `users`, `login_codes`, `sessions` and `devices`, their constraints and indexes, and the one migration that creates them after `workspaces`.
  - Their definitions in the server modules that own them (Layout).
  - The conventions for server tables: ids, timestamps, names, soft deactivation, foreign keys, migration names (Design, "Conventions for server tables"), recorded in `apps/server/src/db/README.md` from TOKI-005.
  - Database tests of the tables, and one test-only helper that inserts valid rows (R26).
- Out (not now):
  - Everything that reads or writes the tables: the sign-in rules and routes (TOKI-022), the first Admin and the first workspace row (TOKI-020), invitations and member changes (TOKI-024), the list of sessions and the emergency link (TOKI-026), accepting an invitation (TOKI-097), device registration for push (TOKI-074), the permission functions (TOKI-027).
  - The table of invitations: TOKI-024 owns it (concern 1). This work stores no invitation.
  - Columns of features that have their own ticket: job title, time zone, status text, Pause and Focus, look, accent, density and notification switches. Each of those tickets adds its columns in its own migration (concern 8).
  - Seed data. The tables are created empty.
  - The conversation tables (TOKI-028) and every later table. This spec describes and tests its own four tables and their columns only. It never says that they are the only tables, so it stays true when later tickets add tables. TOKI-028 and later tickets follow the conventions below, keep their own tests for their own tables, and do not edit the tests of this ticket. For TOKI-028 this means: a join table may have a composite key (convention 1), the migration slug is written with underscores (`conversation_tables`, convention 8), and its tests use the row helper of R26.

## Requirements
All times are `timestamptz`. All text limits are counted in code points (Postgres `char_length`), not in UTF-16 units. Every check below is a database test (Testing) that sends SQL to a throwaway database made by the TOKI-005 R13 rules, unless it says otherwise.

- R1. One new migration creates `users`, `login_codes`, `sessions` and `devices`, in that order, and no other table. It applies on an empty database after the `workspaces` migration, and on a database that already holds `workspaces` rows without changing them. Check: a test reads the migration file and finds four `CREATE TABLE` statements, with these four names and no other; apply all migrations to an empty database and find the four tables by name (the test does not say that no other table exists); insert a `workspaces` row, apply again; the row is still there.
- R2. The columns of each table are exactly the ones listed in Data model, with their types and null rules. Check: a test reads `information_schema.columns` for the four tables and compares name, type and `is_nullable` with the list; one missing, extra or different column fails the test.
- R3. Every table has `id`, of type `uuid`, as primary key. The table definition gives it a default that makes a UUIDv7 with the generator chosen in TOKI-005 (R8 of that spec). Check: for each table, a test in its module inserts a row through the server database client without an id (its parent rows come from the helper of R26); the 13th hex digit of the stored id is `7`. SQL inserts of the other tests pass an id (R26).
- R4. Every table has `workspace_id`, required, with a foreign key to `workspaces.id`. Check: an insert with a `workspace_id` that is not in `workspaces` fails with a foreign-key error on each table; an insert that gives an id, every time column and every other required column but no `workspace_id` fails with a not-null error naming `workspace_id`.
- R5. Every foreign key in these tables refuses to delete the row it points to (`ON DELETE RESTRICT`); no row is deleted by cascade. Check: a test reads `pg_constraint` and finds every foreign key of the four tables with `confdeltype = 'r'`; deleting a `users` row that a `sessions` row points to fails.
- R6. The server writes every time column; the database sets none. No time column has a default. Check: a test reads `information_schema.columns`; every `timestamptz` column of the four tables has a null `column_default`, and an insert that gives an id and every other required column but omits `created_at` fails with a not-null error naming the column. A search of the three module `schema.ts` files finds no `defaultNow` and no `now()`.
- R7. `users.email` is required, at most 254 characters (counted in code points), equal to its own `lower()` form, and holds no whitespace character; the table rejects anything else. Two rows of one workspace cannot have the same `email`. A whitespace character is any character that the class `[[:space:]]` matches, so a leading or trailing space, tab or line break is refused, as TOKI-022 R7 trims all whitespace. The database `lower()` and the JavaScript lower-casing agree for the characters of a real address; for an address they disagree on (a rare Unicode capital) the table refuses the row and the writer reports it. Check: tests insert (a) `Minh@Example.com` and get the check-constraint error `users_email_check`, (b) ` minh@example.com` with a space and (b2) the same address with a tab at the end, with the same error, (c) a 255-character address and get `users_email_length_check`, (d) a 254-character lower-case address and succeed, (d2) an address of 254 characters that each take two UTF-16 units and succeed, because the count is in code points, (e) the same address twice in one workspace and get a unique violation on `users_workspace_id_email_key`, (f) the same address in a second workspace and succeed.
- R8. `users.display_name` is required, 1 to 80 characters, counted in code points (D-033). The table enforces the length only: whether a name made of spaces is a name is for the shared validator of the writers (TOKI-020, TOKI-078, TOKI-097), which counts in code points too, so a name of 80 emoji passes in the table and in the validator alike. Check: tests insert an empty name and an 81-character name and get `users_display_name_length_check`, and an 80-character name, one of 80 emoji and a one-character name and succeed. The part of an address before the @ is at most 64 characters by the mail standard, so a name made from it (D-150) always fits; making it is TOKI-020 and TOKI-097.
- R9. `users.role` is `member` or `admin`, required, with no default (D-152, D-090). Check: tests insert `owner`, `guest` and an empty value and get `users_role_check`, insert `member` and `admin` and succeed, and insert no role and get a not-null error.
- R10. `users.status` is `active` or `deactivated`, required, with no default. There is no status `invited` (concern 2). Check: tests insert `invited` and `Active` and get `users_status_check`, insert `active` and `deactivated` and succeed.
- R11. `users.language` is `en` or `vi`, required, and `en` when the insert gives none (D-018). Check: an insert without it stores `en`; an insert of `fr` gets `users_language_check`; `vi` succeeds.
- R12. A deactivated account stays a row: `status` can be set to `deactivated` and back to `active` on the same row, and no key deletes or cascades when it does (D-094). What deactivation and reactivation do to the role, the sessions and the invitation is the work of TOKI-024 and TOKI-097, not of the table. Check: a test sets `status` to `deactivated` and back to `active` on a row that has a session and a device; both updates succeed and the session and the device rows are still there.
- R13. `login_codes` stores one row per accepted code request with the columns of Data model. `purpose` is `sign_in` or `invitation`, `email` is required and follows the rule of R7 (same checks, same limit), and `user_id` may be empty and, when set, points to `users.id`. Check: tests insert a purpose `other`, an email with capitals, and a `user_id` that is not in `users`, and get `login_codes_purpose_check`, `login_codes_email_check` and a foreign-key error on `login_codes_user_id_fkey`; a 255-character address gets `login_codes_email_length_check`; they insert a row with an empty `user_id` and succeed. The 254 limit is the table's own; the rule that refuses a longer address with `validation_error` before any insert belongs to TOKI-022 (Design, "Hand-offs").
- R14. `login_codes.request_hash` and `code_hash` are required and are 64 lower-case hexadecimal characters; `request_hash` is unique across the table. No column holds a code or a request value in clear. Check: tests insert a 63-character value, a value with an upper-case letter and a value with a `g` and get `login_codes_request_hash_check` or `login_codes_code_hash_check`; a second row with the same `request_hash` gets a unique violation on `login_codes_request_hash_key`; the column list (R2) has no column other than the hash columns that could hold a code.
- R15. `login_codes.wrong_tries` is required, starts at 0 and is between 0 and 5 (D-137). The table refuses a sixth try with a check error; it does not stop it before: the update that adds a try must carry the condition `wrong_tries < 5` (TOKI-022, Design, "Hand-offs"). `expires_at` is required and later than `created_at`. `used_at` and `cancelled_at` may be empty. Check: an insert without `wrong_tries` stores 0; 6 and -1 get `login_codes_wrong_tries_check`; 5 succeeds; an `expires_at` equal to `created_at` gets `login_codes_expires_at_check`.
- R16. `sessions` stores one row per sign-in with the columns of Data model. `user_id` is required and points to `users.id`. `secret_hash` is required, 64 lower-case hexadecimal characters and unique. `kind` is `cookie` or `token`. `user_agent` may be empty and is at most 512 characters. `last_used_at` is required. Check: tests insert a `kind` of `bearer`, a 65-character hash, a duplicate `secret_hash`, a 513-character `user_agent` and a missing `user_id`, and get `sessions_kind_check`, `sessions_secret_hash_check`, a unique violation on `sessions_secret_hash_key`, `sessions_user_agent_length_check` and a not-null error; a row with no `user_agent` succeeds.
- R17. A session is ended, not deleted: `ended_at` and `ended_reason` are both empty or both set, and `ended_reason` is `signed_out`, `replaced`, `revoked` or `deactivated` (D-158). Check: tests insert `ended_at` without a reason, a reason without `ended_at`, and the reason `expired`, and get `sessions_ended_check` for the first two and `sessions_ended_reason_check` for the third; each of the four reasons with an `ended_at` succeeds.
- R18. A partial index on `sessions (user_id)` for rows with an empty `ended_at` exists, so the list of a person's live sessions and the end of all of them (TOKI-026, TOKI-024) read by person. The index is `sessions_user_id_live_idx`. Check: a test finds it in `pg_indexes` with its `WHERE ended_at IS NULL` condition.
- R19. Two partial indexes on `login_codes` for rows with purpose `sign_in` exist: one on `(email, created_at)`, for the counts of 5 in 15 minutes and 60 seconds, and one on `(created_at)`, for the removal of old rows (TOKI-022 R4, R5, R48). They are `login_codes_sign_in_email_created_at_idx` and `login_codes_sign_in_created_at_idx`. Check: a test finds both in `pg_indexes` with the `WHERE purpose = 'sign_in'` condition.
- R20. `devices` stores one push registration of a signed-in device with the columns of Data model. `user_id` and `session_id` are required and point to `users.id` and `sessions.id`; `session_id` is unique, so a session has at most one registration. `push_channel` is `web_push`, `apns` or `fcm`: the service that delivers the push, not the platform of the device. A browser, including Toki added to the Home Screen of an iPhone (D-108), uses `web_push`. `push_address` is required and is a JSON object. Check: tests insert a `push_channel` of `desktop`, a second row with the same `session_id`, a `push_address` that is a JSON string, and a `session_id` that is not in `sessions`, and get `devices_push_channel_check`, a unique violation on `devices_session_id_key`, `devices_push_address_check` and a foreign-key error on `devices_session_id_fkey`; a row with `push_channel` `web_push` and an object succeeds.
- R21. The table definitions are in the module that owns each table and are not exported from the module's `index.ts`: `users` in `modules/members/schema.ts`, `login_codes` and `sessions` in `modules/auth/schema.ts`, `devices` in `modules/notifications/schema.ts`. No schema file imports another module's file. Check: `pnpm lint` exits 0 with the files in place; a test or script lists the four table names exported by the three `index.ts` files and finds none; a search of the three `schema.ts` files finds no import that leaves its module folder except `drizzle-orm` and the shared database helpers of `src/db/`.
- R22. The foreign keys that cross a module boundary (R4, `login_codes.user_id`, `sessions.user_id`, `devices.user_id`, `devices.session_id`) are written as SQL in the migration file, with the names `<table>_<column>_fkey`, because a schema file may not import another module's table. Check: a test finds all of them in `pg_constraint` by those names (R4, R5), and `pnpm db:generate` run again after the migration is applied makes no new file.
- R23. The migration is named `<number>_account_tables` and is the only migration of this ticket; the whole `apps/server/migrations/` change, SQL and `meta/` files, is committed (TOKI-005 R3, R11). Check: `git status` after `pnpm db:generate --name account_tables` shows one new SQL file named so and updated `meta/` files; the migration folder in the PR has nothing else new.
- R24. `apps/server/src/db/README.md` gains a section "Table conventions" with the rules of "Conventions for server tables" below. Check: the section exists and lists each of them.
- R25. The tables are created empty: the migration inserts no row. Check: after the migration is applied to an empty database, each of the four tables holds no row.
- R26. One test-only helper, `apps/server/src/db/test-rows.ts`, inserts valid rows by SQL, so the tests of any module create parent rows without importing another module's table (TOKI-002 R7, R17). It has one function for each of `workspaces`, `users`, `login_codes`, `sessions` and `devices`. Each takes the database client and optional column values, gives every required column a valid value (a UUID for `id`, a fixed date for every time column, the parent ids passed in), and returns the new row's `id`. The tests of TOKI-027 and TOKI-028 use it for their fixtures. Check: for each function, a call with no values inserts a row, and a call with one value overridden stores that value; a search finds no import of the helper outside `*.test.ts` files.
- R27. `devices` has an index on `(user_id)`, named `devices_user_id_idx`, because the push sender reads a person's registrations. Check: a test finds it in `pg_indexes`. No index on `login_codes.user_id` is made: nothing reads codes by person.

## Design
### Conventions for server tables
Stated once here; TOKI-028 and later tickets follow them. A sibling ticket that needs another rule says so in its own spec.
1. Ids: `uuid`, primary key, UUIDv7 made in the server by the default on the column (TOKI-005 R8). A table that only joins two others (for example the members of a conversation) may use the pair of keys as its composite primary key instead of an `id`. Every table has a required `workspace_id` that points to `workspaces.id` (D-004).
2. Names: tables are plural `snake_case` nouns; columns are `snake_case`; a reference to another table is `<singular>_id`; a time is `<event>_at`; a flag that is a time (used, cancelled, ended) is a nullable `<event>_at`, not a boolean. Drizzle properties are `camelCase`, mapped to the column names by explicit name. Constraints and indexes are named `<table>_<column or purpose>_<kind>` where kind is `pkey`, `check`, `key`, `fkey` or `idx`; the names of these four tables are listed under "Constraint and index names".
3. Time: `timestamptz`. The server writes every time from the clock of TOKI-008 (R19 of that spec), so tests can move the clock. A new table does not give a time column a database default. `workspaces.created_at` keeps the database default that TOKI-005 R15 gave it; the table is not changed here.
4. Closed lists of values are `text` with a named check constraint, not a Postgres enum: adding a value is a one-line migration, and a table test names every allowed value.
5. Soft deactivation: an account is never deleted, and a session is ended, not deleted. A person is deactivated by `users.status`; a session is ended by `ended_at`; no foreign key cascades a delete (R5). Two kinds of row are removed by the tickets that own them: old `sign_in` rows of `login_codes` (TOKI-022 R48) and the `devices` row of a session that ended (TOKI-074). Phase 1 has no erasure of an account and no pruning of ended sessions (F41, BR-29); a later ticket that adds either writes its own rule for the foreign keys.
6. Foreign keys: `ON DELETE RESTRICT`. A key that crosses a module boundary is written as SQL in the migration (R22); inside one module Drizzle writes it.
7. Hashes: stored as 64 lower-case hexadecimal characters of a SHA-256 or an HMAC-SHA-256 (concern 6).
8. Migrations: one migration per ticket that changes the structure, created with `pnpm db:generate --name <slug>`, so the file is `<number>_<slug>.sql`; forward-only (TOKI-005 R11). The slug is lower case with underscores (`account_tables`, `conversation_tables`), so the file name is exactly `<number>_<slug>.sql`. Two branches that each add a migration both take the next number; the one that merges second runs `db:generate` again after rebasing, so the numbers and the `meta/` files follow merge order.

### Data model
`users`, one row per person who has an account, defined in `modules/members/schema.ts` (the `members` module owns `users`, as the technical design lists it):
- `id` (R3), `workspace_id` (R4).
- `email`: text, required, lower case, no whitespace, at most 254 characters (R7). 254 is the longest address the mail standard allows; this limit is Decided in this spec (concern 13). Unique with `workspace_id` (`users_workspace_id_email_key`). The unique index also serves the lookup by address that sign-in makes.
- `display_name`: text, required, 1 to 80 characters (R8, D-033).
- `role`: text, required, `member` or `admin` (R9). Guest is a phase 5 role (D-152); adding it is a later migration.
- `status`: text, required, `active` or `deactivated` (R10).
- `language`: text, required, `en` or `vi`, default `en` (R11). Sign-in needs it to choose the language of the mail (TOKI-022 `User.language`); Preferences (TOKI-078) writes it.
- `created_at`: timestamptz, required (R6).
Not stored: last active (the Admin table of TOKI-025 gets it from a function of `auth` that returns the latest `sessions.last_used_at` of each person; TOKI-026 builds it, concern 13), who invited the person (the invitation records it, concern 1), the inviter's name, and any password (D-011).

`login_codes`, one row per accepted request for a code, in `modules/auth/schema.ts`:
- `id`, `workspace_id`, `created_at`.
- `purpose`: text, required, `sign_in` or `invitation` (R13).
- `email`: text, required, same rule and same 254 limit as `users.email` (R7, no uniqueness). It holds the address of people who are not members too (concern 13).
- `user_id`: uuid, nullable, points to `users.id`; empty when the address has no account yet.
- `request_hash`: text, required, unique, 64 hex characters (R14).
- `code_hash`: text, required, 64 hex characters (R14).
- `expires_at`: timestamptz, required, later than `created_at` (R15). The 10 minutes are set by TOKI-022 (D-136).
- `wrong_tries`: integer, required, default 0, 0 to 5 (R15, D-137).
- `used_at`, `cancelled_at`: timestamptz, nullable.
- Indexes: R19.
These are the columns TOKI-022 lists under its Data model, one for one.

`sessions`, one row per sign-in, in `modules/auth/schema.ts`:
- `id`, `workspace_id`, `created_at`.
- `user_id`: uuid, required, points to `users.id`.
- `secret_hash`: text, required, unique, 64 hex characters (R16). The secret itself is never stored.
- `kind`: text, required, `cookie` or `token` (R16).
- `user_agent`: text, nullable, at most 512 characters (R16).
- `last_used_at`: timestamptz, required.
- `ended_at`, `ended_reason`: nullable together (R17).
- Index: R18.
These are the columns TOKI-022 lists. The 30-day rule is not stored: a session is live while it is not ended and was used less than 30 days ago (TOKI-022).

`devices`, one row per push registration of a signed-in device, in `modules/notifications/schema.ts`:
- `id`, `workspace_id`, `created_at`.
- `user_id`: uuid, required, points to `users.id`.
- `session_id`: uuid, required, unique, points to `sessions.id` (R20). Ending the session lets TOKI-074 remove the registration of that session (F06); TOKI-074 also owns the registrations of sessions that ran out of time, which no listener reports (concern 13).
- `push_channel`: text, required, `web_push`, `apns` or `fcm` (R20). The technical design names Web Push for phase 1 and APNs and FCM later ("Multi-channel push"); the three values name the channels, so an iPhone that runs Toki from the Home Screen is `web_push`. Adding a channel is a one-line migration (convention 4).
- `push_address`: jsonb, required, a JSON object (R20): what the channel needs to deliver to the device. For `web_push` it is the subscription the browser gives. Its fields are checked by TOKI-074, which owns registration; the table only keeps an object (Decided in this spec, concern 3).
The signed-in devices list of F06 (device kind, browser, last use) is not read from this table: it is read from `sessions`, which has `user_agent` and `last_used_at` for every signed-in device, push or not (concern 3). `sessions.kind` (cookie or token) is how the session is carried, not the kind of device.
- Index: R27.

### Constraint and index names
Primary keys are `<table>_pkey`, foreign keys `<table>_<column>_fkey`. The tests (Testing) and the code that turns a database error into its own error use these names.
| Table | Names |
| :---- | :---- |
| `users` | `users_workspace_id_email_key` (unique); checks `users_email_check` (lower case, no whitespace), `users_email_length_check`, `users_display_name_length_check`, `users_role_check`, `users_status_check`, `users_language_check`; foreign key `users_workspace_id_fkey` |
| `login_codes` | `login_codes_request_hash_key` (unique); checks `login_codes_purpose_check`, `login_codes_email_check`, `login_codes_email_length_check`, `login_codes_request_hash_check`, `login_codes_code_hash_check`, `login_codes_wrong_tries_check`, `login_codes_expires_at_check`; foreign keys `login_codes_workspace_id_fkey`, `login_codes_user_id_fkey`; indexes `login_codes_sign_in_email_created_at_idx`, `login_codes_sign_in_created_at_idx` |
| `sessions` | `sessions_secret_hash_key` (unique); checks `sessions_secret_hash_check`, `sessions_kind_check`, `sessions_user_agent_length_check`, `sessions_ended_check` (both empty or both set), `sessions_ended_reason_check`; foreign keys `sessions_workspace_id_fkey`, `sessions_user_id_fkey`; index `sessions_user_id_live_idx` |
| `devices` | `devices_session_id_key` (unique); checks `devices_push_channel_check`, `devices_push_address_check`; foreign keys `devices_workspace_id_fkey`, `devices_user_id_fkey`, `devices_session_id_fkey`; index `devices_user_id_idx` |

### Hand-offs
What the tables give, and the ticket that owns the rest. This ticket does not edit the specs of those tickets; each item is a change those specs need or a rule they state (concern 13).
- TOKI-022 (Sign-in API): refuses an address longer than 254 characters with `validation_error` in its R7, before any row is written. The table refuses it too, with `login_codes_email_length_check`; until R7 says so, such an address reaches the table and fails as an internal error. It also carries `wrong_tries < 5` in the update that adds a try (the table gives only the check of R15), gives each invitation code a new secret so that `request_hash` stays unique when a code is resent (R14), and exports a function that removes the `invitation` rows of an address.
- TOKI-024 (Members): creates `invitations` (concern 1); decides whether an administrative action is recorded in a table or in the log (D-110); calls the `auth` function that removes the `invitation` rows of an address when its invitation is used, revoked or expired, because TOKI-022 R48 removes only `sign_in` rows; locks the Admin rows before it counts them (concern 7).
- TOKI-026 (Sessions): exports the function that returns the last use per account, for TOKI-025, and turns `user_agent` into a device kind and a browser (concern 3).
- TOKI-074 (Web Push): removes the `devices` row of an ended session and of a session idle for 30 days, through the listener and the session check of TOKI-022.
- TOKI-022 and TOKI-027: the account status they read is `active` or `deactivated`; the state Invited is not in `users` (concern 11).

### Errors
- A row that breaks a rule is refused by the database with the Postgres error of the named constraint; the code that writes turns it into its own error (TOKI-004 format). No server code needs to repeat a rule for the table to hold.

### Layout
```
apps/server/
├─ migrations/
│  ├─ NNNN_account_tables.sql      the four tables, checks, indexes and cross-module foreign keys; meta/ updated
├─ src/
│  ├─ db/
│  │  ├─ README.md                 gains "Table conventions"
│  │  ├─ test-rows.ts              test-only SQL helper that inserts valid rows (R26)
│  │  └─ account-tables.db.test.ts constraint, index and key tests in plain SQL (R1, R2, R4 to R20, R22, R25 to R27)
│  └─ modules/
│     ├─ members/    schema.ts (users), schema.db.test.ts (R3, R6, R12 for users), index.ts
│     ├─ auth/       schema.ts (login_codes, sessions), schema.db.test.ts (R3, R6), index.ts
│     └─ notifications/ schema.ts (devices), schema.db.test.ts (R3, R6), index.ts
```
- A module that does not exist yet gets its folder, `schema.ts` and an `index.ts` that exports nothing; the ticket that builds the module fills `index.ts`.
- `drizzle.config.ts` already reads `src/modules/*/schema.ts` (TOKI-005), so the three files are found without a change.
- The constraint tests use SQL text, not the Drizzle objects, so they prove what the database enforces whatever the definitions say, and no test file imports another module's table (TOKI-002 R7, R17). The id and time tests (R3, R6) use the module's own table object, because the id default is made by Drizzle in the server; every raw SQL insert passes an id and every time column, and parent rows come from the helper of R26.

## Testing
- Written test-first, as the Blueprint asks for backend work. Database tests only; fake data only (`@example.com` addresses, fake hashes made of repeated hex digits).
- Files that end in `.db.test.ts` run in the database project of TOKI-008, one at a time, against the test database; each starts with empty tables (TOKI-008 R6). They apply migrations through `runMigrations` (TOKI-005). Nothing touches the development database (TOKI-005 R13).

Every "must fail" case asserts the constraint name in the Postgres error, so a failure for another reason (a missing parent, a missing column) does not pass; the "must succeed" cases next to each prove the data was valid otherwise.

R23 and R24 are checked by hand once and the output goes in the PR: run `pnpm db:generate --name account_tables`, look at `git status`, run it again and see no new file (R22); read the README section.

## Data safety
- No code, secret or session value is stored in clear: only hashes (R14, R16). No test uses a real address; fake data only.
- `user_agent` can hold a long header; it is cut by the writer (TOKI-022) and limited by the table (R16).
- `push_address` holds the subscription of a device: its endpoint and, for Web Push, the keys of the browser (`auth` and `p256dh`), in clear next to the user id. Sending needs the server's own key as well, so the endpoint alone does not let a stranger send; the keys are still private. It is never logged, no route returns it to another person, and TOKI-074 may encrypt the object.
- Ended sessions and their `user_agent` stay for good in phase 1 (convention 5).

## Open questions from the intent

- Does this ticket also create the table of invitations, or does the ticket that manages invitations? Answered: TOKI-024. The plan names four tables for this ticket and puts the invitation behaviour (7 days, once, resend, revoke, who invited, the role) in TOKI-024. See concern 1.

## Areas of concern
1. Who owns the table of invitations, the record of administrative actions and the storage of the emergency link. Decided in this spec: TOKI-024 creates and owns `invitations` in its own migration, in the `members` module. Reason: the plan gives this ticket four tables and lists no invitation among them; TOKI-024 holds the invitation rules (D-037, D-099, D-094, D-111, D-110) and TOKI-097 and TOKI-025 read it through the `members` module. D-110 asks that every administrative action is recorded on the server (who, what, to whom, when); this ticket adds no table for it, and TOKI-024 decides whether the record is a table or a log line and adds it by its own migration. The emergency link of TOKI-026 (D-159) needs storage too; this ticket adds none, and TOKI-026 adds what it needs by its own migration (a new `purpose` value, which is a one-line migration by convention 4, or a table of its own). This ticket keeps the account side ready: `login_codes.purpose` has the value `invitation` (R13), and `users` allows a deactivated row to be reused (R12). Owner: Thanh Truong.
2. Where "Invited" is stored. Decided in this spec: not in `users`. A person who has only been invited has no `users` row; the row appears when the invitation is accepted (TOKI-097), and for a deactivated person the invitation points to the existing row, which stays `deactivated` and unable to sign in until acceptance (D-094). So `users.status` is `active` or `deactivated` (R10), and "Invited" and "Expired" on the Admin page come from the invitation (TOKI-024, TOKI-025). Reason: a row with status `invited` would need a display name and a role before the person has chosen to join, and a deactivated person could not be both deactivated and invited. What the TOKI-022 and TOKI-027 specs say about Invited is concern 11. Owner: Thanh Truong.
3. What `devices` holds and where the devices list comes from. Decided in this spec: `devices` holds the push registration of a signed-in device (`push_channel`, `push_address`, its session), as the technical design describes it ("several devices per person, each with a kind and a push address"). The signed-in devices list of F06 and AC-133 (device kind, browser, last use) is read from `sessions`, which already stores `user_agent` and `last_used_at` for every sign-in (TOKI-022 R35), because a device that never turned on push must appear in the list, and a copy of those values on `devices` would have to be kept in step. No column for kind or browser is added: the user agent is kept for every session, ended or not, so the list can be rebuilt from it at any time, and a stored column would have to be decided now for a parser that does not exist yet. TOKI-026 owns the parser that turns `user_agent` into a device kind and a browser, and the list; `sessions.kind` (cookie or token) is not the device kind. What the list shows when the user agent says nothing useful is concern 12. `push_address` is one JSON object because the three channels differ (a browser subscription, an APNs token, an FCM token); TOKI-074 defines its content for `web_push`. Owner: Thanh Truong.
4. Foreign keys across modules. Decided in this spec: they are written as SQL in the migration (R22). Reason: TOKI-002 rule 2 and R17 forbid a schema file from importing another module's table, and Drizzle needs the table to describe a key. Cost: the Drizzle snapshot does not know these keys, so a later `db:generate` neither shows nor drops them; R22 checks that a second generate makes no file and that the keys exist. Owner: Thanh Truong.
5. Timestamps and the clock. Decided in this spec: the server writes the time columns of these tables from the injected clock and the database has no default for them (R6, convention 3), as TOKI-022 requires ("never by a database default"). `workspaces.created_at` keeps its database default from TOKI-005 R15: changing an existing table is outside this ticket and nothing needs it, so two conventions exist in the schema until a ticket moves that column. Owner: Thanh Truong.
6. How hashes are stored. Decided in this spec: 64 lower-case hexadecimal characters in a `text` column with a check (R14, R16, convention 7). Reason: the TOKI-022 spec names SHA-256 and HMAC-SHA-256 without a form for the stored value; hexadecimal is readable in a database tool and compares as plain text. Hand-off: TOKI-022 writes and compares that form. Owner: Thanh Truong.
7. The last Admin and self-deactivation. Decided in this spec: the table does not enforce them (R9). The rule needs a count of active Admins and the person who acts, so TOKI-024 checks it inside one transaction that first locks the active Admin rows of the workspace with `SELECT ... FOR UPDATE` (D-153, D-090); a trigger would hide the rule from the code that must show "Make someone else an Admin first". What this ticket gives for the lock is the `users` rows themselves: the rows with `role = 'admin'` and `status = 'active'` are the lock target, found through the `users_workspace_id_email_key` index; no extra column or index is made. Without the lock two Admins who demote each other at once both read a count of 2 under the default isolation and the workspace ends with no Admin. The owner of the locking read is TOKI-024, and the permission functions (TOKI-027) assume it. The table does not hold these two rules, so a writer that does not go through TOKI-024 (TOKI-020, a script) must keep them itself. Owner: Thanh Truong.
8. Who adds the columns for profile and preferences. Not decided. This ticket creates no column for the display-name change, job title, time zone (D-144), status text, Pause and Focus (D-072), look, accent, density (D-175) or the notification switches (D-142, D-088); `language` is the exception because sign-in reads it (R11). The plan's tickets that name these are screens (TOKI-078 Preferences screen, TOKI-057 Profile panel, TOKI-099, TOKI-092); the server tickets are only TOKI-076 (Pause and Focus) and TOKI-102 (notification switches), which add their own columns. No ticket in the plan owns the migration and the endpoint that save the profile fields and the look, accent, density and language to the account (D-175 says they are saved to the account). Proposal, not a decision: add a server ticket "Profile and preferences (server)" before TOKI-078 and TOKI-057, which adds those columns by its own migration; until it exists no ticket may assume the columns are there, and R11 says only that Preferences writes `language`. The intent no longer promises that later tickets start from these tables without any change. Owner: Thanh Truong, for the plan.
9. Migration numbering. Decided in this spec: the next free number, named by `--name` (convention 8). TOKI-028 adds a migration at the same time; the one that merges second regenerates its migration after rebasing. This is a process rule, not a table rule. Owner: Thanh Truong.
10. Which module owns which table. Decided in this spec: `users` in `members`, `login_codes` and `sessions` in `auth` (as TOKI-022's module boundaries say), `devices` in `notifications` (it holds push channels, and the worker that sends push is that module). Ending a session reaches `devices` through the listener that TOKI-022 exports (R50 of that spec), not through a join. Owner: Thanh Truong.
11. The hand-off of "Invited" and the state of a deactivated person with an invitation. Not decided. The TOKI-022 spec (Module boundaries) has the `members` read functions return a status of Invited, Active or Deactivated, and the TOKI-027 spec lists "account status (active, invited, deactivated)" in its scope; but Invited can only be read from the invitations table of TOKI-024, which needs TOKI-022 and TOKI-027 in the plan, so at their build time the function cannot return it, and `users` has no such value (concern 2). Proposal, not a decision: those two specs change to the two statuses of `users` (`active`, `deactivated`); TOKI-022 treats an address with no `users` row as no account, which its R1 and R2 already do for an invited person; TOKI-024 adds the reading of Invited for TOKI-025 and TOKI-097. Also not decided: when a deactivated person has a pending invitation, which state the Admin row (F02, TOKI-025) and the counts of the status chips (D-109) show. Proposal, not a decision: Deactivated until the invitation is used, because the account stays deactivated until then (D-094). Owner: Thanh Truong, with the owners of the TOKI-022, TOKI-027, TOKI-024 and TOKI-025 specs.
12. What the signed-in devices list shows when the user agent says nothing useful (no browser name, an app with a token session, an empty value). Not decided. The decision log fixes the three items of the list (device kind, browser, last use; F06, D-158) and gives no text or category for an unknown one. Proposal, not a decision: the list shows a generic device label and a generic browser label in the wording that the TOKI-026 and TOKI-078 specs choose; the table stores nothing more. The wording is a proposal until the prototype or the log gives it (D-139). Owner: Thanh Truong, with the owner of the TOKI-026 spec.
13. Work the tables hand to other tickets. Decided in this spec: each has the owner named under Design, "Hand-offs". (a) The 254 limit of `login_codes.email` stays on the table: the table also keeps the address of people who are not members, so an unbounded value is not acceptable there. TOKI-022 R7 asks only for a well-formed address and R41 inserts a row for every accepted request, so a 300-character address would reach the table and fail as an internal error; the length rule is for TOKI-022 to state, and this is the change request for its spec: refuse more than 254 characters with `validation_error` before any insert. The change request is not made in this PR, which edits no other spec. Meanwhile the table refuses the row with `login_codes_email_length_check`. (b) The cap of 5 on `wrong_tries` is a check on the table; it cannot stop the sixth try before the update. The guard `wrong_tries < 5` in the update that adds a try is TOKI-022's. (c) A code resent for an invitation must have a new secret, because `request_hash` is unique and for an invitation it is the hash of the secret the caller supplies; TOKI-022 R49 and TOKI-097 own that. (d) Invitation rows keep an address of a non-member and TOKI-022 R48 prunes only `sign_in` rows; TOKI-024 owns the removal, when its invitation is used, revoked or expired, through an `auth` function that TOKI-022 exports. (e) The last use per person for the Admin table: TOKI-026 exports it from `auth`, because sessions belong to `auth` and TOKI-026 is the sessions ticket; the plan then needs TOKI-025 to depend on TOKI-026. (f) A session that expires without being ended is not reported to listeners (TOKI-022, Module boundaries), so its `devices` row would stay and push would go on; TOKI-074 owns skipping and removing the registrations of ended or 30-day idle sessions. Owner: Thanh Truong.
