# End-to-end flows design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/end-to-end-flows.md (Thanh Truong)
Ticket: TOKI-090

## Goal
Every ticket so far proves its own piece, and most browser tests stub the server's answers. Before the first release the team needs 12 browser tests that run the real web app, the real server, a real Postgres, real mail and real file storage, as the people of the prototype's sample workspace, and that fail when the feature they cover is broken. Each flow is complete at a desktop width and at a phone width (D-053).

This work chooses the 12 flows from the phase-1 journeys accepted on 13 Nov 2026 (D-091), writes them, and builds the small amount of setup they need that no other ticket owns: a Playwright config and a CI job for the flows, a launcher that seeds and starts the server with a clock a test can move, a reset between flows, and the helpers that sign people in, pass time and read texts.

## Scope
- In:
  - The 12 flows, `e2e/flows/*.spec.ts`, and the table that says which journeys, which people and which feature tickets each one has (R9 to R22).
  - `playwright.flows.config.ts`, the script `test:e2e:flows`, the launcher `apps/server/tests/e2e-flows-launch.ts` that also runs the job queue's worker, and its control server (R1 to R5).
  - The helpers in `e2e/support/flows/` (R6 to R9), one small change to `signInByApi` of `e2e/support/real-server.ts` (R6) and one option added to `expectFits` of `e2e/support/layout.ts` (R23).
  - The extraction of the server's start into a function that takes a clock, `apps/server/src/start.ts`, and of the worker's start into `apps/server/src/start-worker.ts` (R3). `main.ts` and `worker.ts` keep their behaviour.
  - A CI job for the flows (R25) and the documents: a row in `CLAUDE.md` and the README of the flows (R26).
- Out (not now):
  - The behaviour of any feature: each belongs to the ticket named in the table. A flow that fails is fixed in the ticket that owns the feature.
  - The exhaustive access matrix (every endpoint, every role): TOKI-088. A flow makes the direct requests that prove its own claim, not the matrix.
  - The 6 performance targets: TOKI-089. The production image and Compose: TOKI-084; the flows run against the development build of the server and the Vite server, not the image.
  - Firefox and WebKit, and the Vietnamese interface: not run (TOKI-008 concern 5; the flows run in English, the default). The parity of look with the prototype: TOKI-109.
  - Journeys that are not among the 12: listed in "Journeys left out", with their owner.
  - The stubbed browser tests of each screen ticket stay where they are; this ticket changes none of them.

## Requirements
In the checks below, "the flows run" means `pnpm test:e2e:flows` with Postgres, Mailpit and MinIO up (R25 gives the CI values).

Setup
- R1. The flows have their own config and command. `playwright.flows.config.ts` at the root runs `e2e/flows/` and nothing else, with `fullyParallel: false` and `workers: 1`, `retries: 0`, `timeout` 90,000 ms for a test and `expect: { timeout: 10_000 }`, `trace`, `screenshot` and `video` on, and its own `outputDir` (`e2e/assets/flows`, as the other configs keep one folder each). The root `package.json` gains `test:e2e:flows`: `playwright test -c playwright.flows.config.ts`. `playwright.config.ts` adds `flows/**` to `testIgnore`, so `pnpm test:e2e` runs the same tests as before. The two limits are set so that the work of the machine (several sign-ins, many pages, a reconnect with its own delay) fits; they are not waits for a delay that a journey names, which R7 passes by moving the clocks. The config also sets `process.env.FLOWS_CONTROL_TOKEN` to a random value when it is unset (R4), before any worker starts, so the launcher and the tests share it. It has two projects, both Chromium: `desktop` with the viewport 1280 by 800 and `phone` with the viewport 390 by 844, `isMobile` and `hasTouch` true. The two sizes are exported from `e2e/support/flows/widths.ts`, the one place that names them. Check: `pnpm test:e2e:flows --list` shows each flow under both projects and no test of another folder; a unit test of `e2e/support/flows` compares the two sizes with the `wide` and `narrow` widths of `e2e/parity/` (1280 by 800 and 390 by 844, TOKI-109 R6); the list of `pnpm test:e2e` is the same before and after this change.
- R2. The launcher `apps/server/tests/e2e-flows-launch.ts` makes the state a run starts from, in this order. (1) The guard, before any statement: the checks of TOKI-008 R5 and R22 on `E2E_DATABASE_URL` (a loopback host; the name of the database it will make, `toki_e2e_flows_test`, ends in `_test`), a loopback `STORAGE_ENDPOINT` and a `STORAGE_BUCKET` that ends in `-test` (TOKI-058 R20 (b)); it refuses to run when `NODE_ENV` is `production`. (2) It drops and creates the database, applies the migrations (`runMigrations`) and then `installJobsSchema` (TOKI-064 R3: the schema `pgboss` is made by that call, not by `runMigrations`), makes the flows' bucket when it is missing and empties it. (3) It opens its own connection (`createDb`) and calls `seedPrototypeWorkspace` (TOKI-081 R17) on the empty database with the test clock of R4, a fixed random source and, when TOKI-063 is built, the store; its result must be `loaded`, otherwise the launcher drops the database and exits 1 with the reason. The seed comes before the server on purpose: it writes only into an empty database (TOKI-081 R14, R15), and the first set-up that `startServer` runs after it listens (TOKI-020) would create a workspace and an Admin first and make the seed answer `not_empty`. (4) It starts the server with `startServer` and the worker with `startWorker` (R3), both on the clock of R4; the first set-up then finds the accounts and skips (TOKI-020 R7). (5) It builds the configuration in code with `loadProcessConfig`, never from the root `.env`: the mail and storage values come from `E2E_SMTP_*`, `E2E_MAILPIT_URL` and `STORAGE_*`; the `FIRST_ADMIN_EMAIL`, `FIRST_ADMIN_NAME` and the secrets of the `auth` area are made by the launcher at run time (an address on `example.com` with a random part, a fixed name, random bytes), kept in memory and written nowhere; `WORKSPACE_NAME` is `Hugepig Studio`, the name the seed makes. They are only there because the configuration requires them: the first set-up is skipped. (6) `startServer` throws when it cannot listen and leaves `process.exit` to `main.ts` (R3), so the launcher can close the server and the worker, drop the database and then exit 1. The run ends by dropping the database. Check: a unit test of the guard has one case for each refusal; a launch whose seed answers `not_empty` exits 1 and leaves no `toki_e2e_flows_test`; the first screen of E01 shows `Hugepig Studio`, which proves that the seed ran before the first set-up; after a run, the development database holds the same rows and tables as before it (the by-hand check of TOKI-008 R22), and `toki_e2e_flows_test` does not exist; `dev:reset:db` and `dev:seed` are called by no file of the flows.
- R3. The server start and the worker start are functions that take a clock. `apps/server/src/start.ts` exports `startServer({ config, clock })`, which holds what `main.ts` does after reading the configuration: create the connection, the job queue as a producer (TOKI-064 R17) on the clock, `buildApp` with `clock` and the queue, the first set-up, the one close hook (gateway, then `jobs.stop()`, then the connection, TOKI-064 R15) and listening; it returns `{ app, db }`, it throws when listening fails and it never calls `process.exit`. `apps/server/src/start-worker.ts` exports `startWorker({ config, clock })`, which holds what `worker.ts` does after reading the configuration (open the database, `createWorker` with `handlers: (jobs) => buildJobHandlers(buildJobDeps(config, db, jobs))`, start) and returns `{ stop }`. `main.ts` and `worker.ts` read the configuration, call these with `systemClock`, and keep the shutdown signals and the exit codes they have. The `config` has the shape `loadProcessConfig` gives for the areas of each entry (the list that TOKI-084 R11 calls `entryAreas`), so an area that a later ticket adds to an entry reaches the launcher. Any later ticket that adds a step to either start adds it to the function. No other code of `apps/server/src` imports these two files. Check: the tests of `main.ts`, `worker.ts` and `app.ts` pass unchanged; a test reads the import lines of `apps/server/src` and finds `start.ts` imported only by `main.ts` and `start-worker.ts` only by `worker.ts`; the launcher and the server started by `main.ts` answer `/healthz` the same way; `startServer` on a port that is taken throws and leaves the process running.
- R4. A control server for the test, in the launcher process and nowhere else. It listens on `127.0.0.1` at the port of the config (3201) and answers three requests, each with a JSON body: `GET /now` returns the test clock's time in epoch milliseconds; `POST /advance` with `{ ms }` (a whole number, 1 to 86,400,000) moves the test clock of TOKI-008 R8 forward by exactly that and returns the new time; `POST /reset` makes the state of R5 and returns `{ now }`. Every request must carry the header `x-flows-token` equal to `FLOWS_CONTROL_TOKEN` (R1) or it gets 401, and a `POST` must have `Content-Type: application/json` or it gets 415 (a page open in the builder's own browser can send neither with a plain form or a no-cors request); anything else is 404. It is a file of `apps/server/tests/`, imported by nothing in `apps/server/src`, so the production server has no such route and no surface: `start.ts` takes a clock and nothing else, `src` does not import the control file, and TOKI-084 bundles from its entries only. The clock is one object the launcher makes: it holds the `TestClock` that `startServer` gave `buildApp` (so the sign-in codes, the sessions and the mail of TOKI-022 see the move) and the clock of the library of the job queue (TOKI-064 R19) that `startServer` and `startWorker` received, and `POST /advance` moves both by the same amount in one call, so the timed jobs (the end of a status, the end of Focus time, reminders) see the move too. No flow of the 12 waits for a timed job; the move of the second clock keeps a later flow from meeting a job that is late for no reason. Check: `GET /now` after `POST /advance { ms: 60000 }` is 60,000 more; a request with no token or a wrong one is 401 and changes nothing; a `POST` with `Content-Type: text/plain` is 415; a request to the server's own port for `/advance` is 404; a test reads the import lines of `apps/server/src` and finds no import of the control file; with the clock advanced by 60 s, a second code request for one address that answered 429 `code_resend_too_soon` now answers 200 (TOKI-022 R5); a job added with a start 60 s ahead is not run before `POST /advance { ms: 61000 }` and is run after it.
- R5. Every flow starts from the same state. `POST /reset`, in one call: stops the worker (`stop` of R3, which waits for the handlers now running, TOKI-064 R15), truncates every table of the application schema except the migration journal and deletes every row of the job tables of the schema `pgboss` (waiting, retry, running, dead and finished jobs; the tables of the queues, the schedules and the version stay, and the builder reads the table names from the installed version), sets the test clock to the system time, calls `seedPrototypeWorkspace` again with that clock (so the sample lands at "yesterday and today" as TOKI-081 R9 says; the result must be `loaded`), empties the file bucket, writes the manifest of R6 again, and starts the worker again (`startWorker`, on the clock at the new time). So a job queued by one flow never runs against the tables of the next. The state that a truncate does not clear and the flows meet: (a) the code rows are in the database, so the limits on code requests per address (5 in 15 minutes and one in 60 seconds, TOKI-022 R4, R5) start again with each flow; (b) the limit per network address (20 requests in 15 minutes for each route, `modules/auth/limiter.ts`) is kept in the server's memory and `/reset` cannot clear it, and does not need to: `flow()` gives every browser context a network address that no other context of the run has (R9), so no key is used twice, and entries of earlier flows, made at the advanced time, are never read again. The same holds for the limits that TOKI-091 adds (R8 to R11 there: the Join routes, and the failed sign-in checks of 60 in a minute by address): `/reset` does not call the `clear()` of 091 R8, because the limiters are made inside `buildApp` and `startServer` returns only `{ app, db }`, and because a key that no context shares is never full. No context of a flow makes more than a dozen counted requests (E01 is the busiest, about 8 code and session requests and 3 requests with no session), far under 20 and 60, and a flow that needed more would be split; (c) the open connections of the gateway belong to pages of the flow that is over, which `flow()` closes before the test ends (R9). Check: after a flow that changed every kind of data (a channel, a message, a role), a reset leaves 1 workspace, 8 accounts and the counts of conversations, members, messages, reactions and pins that TOKI-081 R5 to R12 give, and no row in `sessions`, `login_codes`, `events`; a job added with a start in the future, then a reset and an advance past that start, never runs; after two resets the answer of `GET /api/v1/bootstrap` for Lan lists the 11 conversations of TOKI-081 R18 both times (a server that kept state of the first run in memory would fail here); a flow that leaves a page open and a draft saving is followed by a flow whose database holds none of its writes; the flows run in any order and any one of them runs alone (`--grep E07`).
- R6. The manifest and the sign-in helper. The manifest is a JSON file at `e2e/assets/flows-run/manifest.json` (a folder that is not an `outputDir`, so Playwright does not empty it; named by the environment variable `FLOWS_MANIFEST`), written by the launcher from `PROTOTYPE_SEED` of TOKI-081 and the ids the database holds, at the start and again at every `/reset`. It has `workspace` (`name`), `people` (key, id, email, display name, role), `conversations` (key, id, name, kind) and `messages` (id, key, conversation key, author key, text). Every reset makes new ids (the seed makes new UUIDs, TOKI-081 R10), so `readManifest()` in `e2e/support/flows/people.ts` reads the file each time `flow()` starts a test and never at import; a test that needs the id of the root message of the thread (E09) or the name of the workspace (E01) reads it from there. No file of the flows or of `e2e/support/flows` writes a sample address or a sample text (TOKI-081 R21, Hand-offs). `signInAs(page, ip, key)` in the same file signs the person in through the real routes: it calls `signInByApi` of `e2e/support/real-server.ts` (a code request and a session request, the code read from the mail that Mailpit received), in the browser context of `page`, so the cookie is the one the server set. One change is made to `signInByApi`: it counts the mails to the address before it asks (`mailCount`) and waits for one more (`codeFromMail(address, count)`), so a mail of an earlier run to the same sample address, still in Mailpit, is never read. The `ip` is the network address that `flow()` gave the context (R9); the server runs with `TRUSTED_PROXY`, so it is the address the server counts. Check: with a mail to `lan` already in Mailpit from an earlier run, the helper still signs in with the new code; each of the 8 people signs in; two sign-ins of one address in one flow with no time passed fail with 429 (the 60 s limit), and pass after `advanceTime(60_000)` (R4, R7).
- R7. Time is passed, never waited for. `advanceTime(ms)`, given to the body of a flow by `flow()` (R9) and written in `e2e/support/flows/time.ts`, moves the server's test clock (`POST /advance`) once and the browser clock (`page.clock.fastForward(ms)`) of every page the flow has open, so no context falls behind the server; a page opened later has `startClock(page)` install its clock at the server's `GET /now` before it loads. A delay that a journey names (the 60 s before "Resend code", the 5 s of an Undo, the 5 s of a toast, the 10 minutes of a code) is passed with `advanceTime`; a flow that asserts a delay never lets real time pass for it. The gateway's sweep (TOKI-038 R24) reads the same server clock and closes a connection with 4410 `heartbeat_timeout` when 60 s have passed without a frame from the client; it runs every 5 real seconds. So a big move of the clock would close every open realtime connection of the flow at the next sweep, and the choice here is that it never happens: (a) a move of more than 20 s is made only while no page of the flow is signed in and open, that is on a sign-in page, in a context that is signed in by API and has not opened a page yet, or after the page was closed; `advanceTime` throws when asked for more while such a page is open; (b) while a connection is open, the moves of a flow add up to at most 20 s (the 5 s of a toast or of an Undo, a few times), below the 25 s after which the server pings and the page answers; `advanceTime` adds them up and throws above 20 s. E01 passes its 60 s on the sign-in page; E02 and E04 pass theirs when no page is open (R12, R14). No file of `e2e/flows` or `e2e/support/flows` uses `waitForTimeout`, `setTimeout`, `setInterval`, `Date.now(` or `new Date(`; the waiting of Playwright's own assertions (retrying until a screen shows, up to the limit of R1) is allowed. Check: a unit test scans those folders and fails on each of those names (and passes on today's files); a unit test of `advanceTime` has it throw for 60 s while a signed-in page is open and for a total above 20 s, and pass for 60 s with none open; a flow that needs 60 s passes in the time of its own steps, which the report of the run shows; E01 passes only if the resend button is disabled before `advanceTime(60_000)` and enabled after it.
- R8. Texts come from the catalogs, and the locators are by role. A flow finds a control by its role and its accessible name, taken with `text(key, values)` of `e2e/support/flows/texts.ts` from the English catalog of `@toki/i18n` (as `e2e/support/sign-in.ts` does for its texts; a plural key takes `{ count }`); no flow holds a sentence of the journeys as a literal, because the wording of states the prototype does not draw is a proposal (D-139). The keys the flows name were checked against the catalog when this spec was written: `signIn.error.wrongCode` (E01, with `count` 4: five tries, one used, TOKI-023 R16), `account.devices.title`, `account.devices.thisDevice` and `account.devices.signOutLabel` with `{ device }` (E02), `account.entry.signOut` (E02), `sessionEnded.title` and `sessionEnded.signInAgain` (E02, E04), `sessionEnded.deactivated` (E04), `states.notFound.title` of TOKI-082 R9 (E04 and E06: the shared page that `NoAccess` of TOKI-025 now draws, so `admin.noAccess.title` is no longer on screen), `states.offline.banner` of TOKI-082 R5 and R14 (E12) and, for the phone runs, `nav.search`, `nav.preferences` and `nav.admin`, the row names of the More sheet (TOKI-092 R13). A key the builder needs and this list does not have is looked up in the catalog the same way. `data-testid` is used only where the spec of the screen names one. A key the catalog does not have fails the flow with the key's name. Check: a unit test reads every `text("…")` key of the flows and finds each in the catalog; a rename of a catalog text changes what the flow looks for and the flow still passes; the flows use no `getByText` with a quoted sentence of more than one word.
- R9. A flow is declared with `flow({ id, journeys, features }, body)` in `e2e/support/flows/flow.ts`, which registers one Playwright test for the project that runs, titled `E07 · F10 F11 · …`, calls `POST /reset` first, and gives the body `{ person, advanceTime }`: `person(key)` opens a new browser context, signs that person in, and starts its clock (R6, R7); the context carries the header `x-forwarded-for` with a network address made for it, one that no other context of the run has (a counter over the run, as `nextIp` of `real-server.ts` does, and that file's `test` fixture is not used; each address is IPv4, because TOKI-091 R9 counts an IPv6 address by its first 64 bits and two such addresses made by a counter would share one key), so the limit per network address of R5 never meets two flows. `flow()` closes every context it opened when the test ends, passed or failed (a fixture teardown), so no page keeps a realtime connection, a draft save or a retry running into the next flow's database. The 12 flows are exactly E01 to E12 of "The 12 flows": a unit test lists the declarations and fails unless there are 12, with ids E01 to E12 each used once, each naming at least one journey that is in the written journeys and at least one ticket that is in the plan. The two projects run every flow: a flow that is skipped at one width fails the unit test of R1 that compares the two lists. In CI no flow is skipped (R25); on a machine without the services a run lists every flow as skipped with the reason, as `playwright.sign-in.config.ts` does. Check: a unit test of `flow()` finds no network address used by two contexts of two flows and every address an IPv4 address; the check of R5 with a page left open passes.
- R10. What makes each flow a proof and not a smoke test. Every flow: (a) begins by asserting something that only the seeded workspace has (a named conversation in the person's list, the text of a seeded message), so a page that renders and nothing else fails at step 1; (b) proves each result in two places, on the screen of the person who acts and in what the server answers to a person it concerns (another person's screen in a second browser context, or that person's own request to the server through `page.request` with their cookie); (c) for each claim of the form "nobody else can" asks the server directly as that person and expects the refusal named in the flow, so a screen that only hides a control passes nothing; (d) ends by reading the state through a route, not through the screen the flow just used. Each flow row below ends with the fault that must turn it red (R11 to R22), and Testing says how that is tried.

The flows. In each, "page of X" is a browser context signed in as X (R9). Common to all flows
- R23. Every page a flow opens at the phone width is checked once, after it settles, with `expectFits` of `e2e/support/layout.ts`; at the desktop width the same call is made on the last page of each flow. That function was built for the sign-in card (TOKI-023 R29): it walks every element of its scope, requires 40 px height under 720 px and "not covered" of every `button, input, a[href]`. So the scope is named for each kind of page and a small option is added: `expectFits(page, label, scope, { exempt })`, where `exempt` is a CSS selector whose elements and their descendants are left out of the height and the "covered" rules (the width and clipping rules still hold for them). ### How a run works
1. Playwright starts two web servers: the launcher and the Vite dev server, which proxies `/api` to the server (the way the other configs do).
2. The launcher checks the database (R2), makes and migrates `toki_e2e_flows_test` and installs the job schema, seeds with its own connection, starts the server and the worker on one test clock, writes the manifest and opens the control port. Playwright waits for `/healthz`.
3. Each test calls `POST /reset`, then opens the pages it needs, each context with its own network address. `signInAs` goes through the real sign-in routes, with the mail read from Mailpit (R6). The test ends by closing its contexts (R9).
4. A delay is passed by `advanceTime` on both clocks (R7). Nothing sleeps.
5. At the end the launcher is stopped and drops the database.

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- Own config and job, not a folder of `pnpm test:e2e`. Reason: the flows need Postgres, Mailpit, MinIO and a seeded database, which the stubbed `e2e` run does not, and TOKI-008 R22 asks for a seeded flow to have its own config and database; `playwright.sign-in.config.ts` set the pattern. A flows run that fails must not hide the faster stubbed run.
- One server and one worker for the whole run, reset between flows, not a database and a server for each flow. Reason: a server start and a migration for each of 24 runs costs more than a truncate and a seed, and the sample loads in one transaction (TOKI-081 R14). The risk is state that survives a truncate in the server's memory; R5 has a check for it, and a module that keeps such state must clear it on reset by its own spec.
- Real sign-in for every person in every flow, through the routes, and no route that makes a session for a test. Reason: a route that mints a session is a way into the app that production must never have; the real path is the one the people use, so every flow proves it a little; and because the reset deletes the code rows, the limits that count rows never stop a flow, and the limit per network address, which is in memory, is met by giving each context its own address (R5, R9).
- The clocks. The server gets its clock through `startServer` and the worker through `startWorker` (R3), the browser through Playwright's `page.clock`; `advanceTime` moves them together (R4, R7). Reason: a code that is valid for 10 minutes and a button that enables after 60 seconds depend on the server's time and the page's time together, so moving one breaks the flow. A move of more than 20 s is made only when no signed-in page is open, because the gateway's sweep would close the connection of every open page (R7). Alternative refused: changing `created_at` of code rows in the database, which needs the tests to know every table that stores a time.
- The manifest instead of importing `PROTOTYPE_SEED` into the test process. Reason: the import would load server modules into the Playwright runner, and the ids of the sample are made when it is seeded (TOKI-081 R10), so only the database knows them; they change at every reset, so the manifest is read for each flow (R6). The launcher writes the manifest from `PROTOTYPE_SEED` and the ids it reads back.
- Widths: desktop 1280 by 800 and phone 390 by 844, the `wide` and `narrow` widths of TOKI-109 R6; the middle band (900) is not run, because D-053 names desktop and phone. Concern 3.
- Texts from the catalogs and role-based locators (R8). Reason: the wording of many states is a proposal that the design may change (D-139); a flow that quotes it breaks for a change that is not a bug.
- Proposed, not decided: MinIO in the flows job (concern 5). Reason: E11 would be a stub otherwise, and TOKI-059 and TOKI-062 say that nothing in CI yet proves a real browser against a real MinIO ("a later automated run against MinIO is a change of the `e2e` job"). The steps and the CORS setting are in R25.
- The look: every flow runs in the look the app starts with and never changes it, nor the accent, density or language; those are tested by the screens and by TOKI-109.

### Errors
- A service is not reachable and the run is not in CI: every flow is listed as skipped with the reason (R9). In CI: the job fails.
- The seed returns `not_empty` or fails: the launcher closes what it started, drops the database, exits 1 and prints the reason; Playwright reports the web server as not started.
- A reset fails: the test fails at its first step with the control server's message; no later flow depends on it.
