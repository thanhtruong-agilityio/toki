# End-to-end flows design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/end-to-end-flows.md (Thanh Truong)
Ticket: TOKI-090

## Goal
Every ticket so far proves its own piece, and most browser tests stub the server's answers. Before the first release the team needs 12 browser tests that run the real web app, the real server, a real Postgres, real mail and real file storage, as the people of the prototype's sample workspace, and that fail when the feature they cover is broken. Each flow is complete at a desktop width and at a phone width (D-053).

This work chooses the 12 flows from the phase-1 journeys accepted on 13 Nov 2026 (D-091), writes them, and builds the small amount of setup they need that no other ticket owns: a Playwright config and a CI job for the flows, a launcher that seeds and starts the server with a clock a test can move, a reset between flows, and the helpers that sign people in, pass time and read texts.

## Scope
- In:
  - The 12 flows, `e2e/flows/*.spec.ts`, and the table that says which journeys, which people and which feature tickets each one has (R9 to R21).
  - `playwright.flows.config.ts`, the script `test:e2e:flows`, the launcher `apps/server/tests/e2e-flows-launch.ts` and its control server (R1 to R5).
  - The helpers in `e2e/support/flows/` (R6 to R8), and one small change to `signInByApi` of `e2e/support/real-server.ts` (R6).
  - The extraction of the server's start into a function that takes a clock: `apps/server/src/start.ts` (R3). `main.ts` keeps its behaviour.
  - A CI job for the flows (R22) and a row in `CLAUDE.md` (R23).
- Out (not now):
  - The behaviour of any feature: each belongs to the ticket named in the table. A flow that fails is fixed in the ticket that owns the feature.
  - The exhaustive access matrix (every endpoint, every role): TOKI-088. A flow makes the direct requests that prove its own claim, not the matrix.
  - The 6 performance targets: TOKI-089. The production image and Compose: TOKI-084; the flows run against the development build of the server and the Vite server, not the image.
  - Firefox and WebKit, and the Vietnamese interface: not run (TOKI-008 concern 5; the flows run in English, the default). The parity of look with the prototype: TOKI-109.
  - Journeys that are not among the 12: listed in "Journeys left out", with their owner.
  - The stubbed browser tests of each screen ticket stay where they are; this ticket changes none of them.

How the 12 were chosen (Decided in this spec, concern 1). First, the four the plan names: an Admin creates the channel (E05, D-084, D-151), there is no Owner (E04, D-152; also the role list of E03), a channel not joined shows no messages (E06, D-116), Sign out (E02, D-158). Then one rule for the rest: a journey is a flow when a release that broke it would leave people unable to do the main job of a chat (get in, bring someone in, find and join a channel, talk, be told, act on a message, share a file, survive a bad network), and when it crosses the server and a second person's screen, so that a stubbed browser test cannot prove it. Every group of the written journeys that phase 1 builds has at least one flow: Account and sign-in (E01 to E03), Home and conversations (E07 to E10), Channels and direct messages (E05, E06), Keeping track (E08, E11), Status and personal settings (E12), Administration (E04).

## Requirements
In the checks below, "the flows run" means `pnpm test:e2e:flows` with Postgres, Mailpit and MinIO up (R22 gives the CI values).

Setup
- R1. The flows have their own config and command. `playwright.flows.config.ts` at the root runs `e2e/flows/` and nothing else, with `fullyParallel: false` and `workers: 1`, `retries: 0`, `trace`, `screenshot` and `video` on, and its own `outputDir` (`e2e/assets/flows`, as the other configs keep one folder each). The root `package.json` gains `test:e2e:flows`: `playwright test -c playwright.flows.config.ts`. `playwright.config.ts` adds `flows/**` to `testIgnore`, so `pnpm test:e2e` runs the same tests as before. It has two projects, both Chromium: `desktop` with the viewport 1280 by 800 and `phone` with the viewport 390 by 844, `isMobile` and `hasTouch` true. The two sizes are exported from `e2e/support/flows/widths.ts`, the one place that names them. Check: `pnpm test:e2e:flows --list` shows each flow under both projects and no test of another folder; a unit test of `e2e/support/flows` compares the two sizes with the `wide` and `narrow` widths of `e2e/parity/` (1280 by 800 and 390 by 844, TOKI-109 R6); the list of `pnpm test:e2e` is the same before and after this change.
- R2. The launcher `apps/server/tests/e2e-flows-launch.ts` makes the state a run starts from. Before any statement it applies the checks of TOKI-008 R5 and R22 to `E2E_DATABASE_URL`: a loopback host, and the name of the database it will make, `toki_e2e_flows_test`, ends in `_test`; it refuses to run when `NODE_ENV` is `production`. It then drops and creates that database and applies the migrations (`runMigrations`), empties the flows' file bucket when `STORAGE_*` is set (the bucket name must end in `-test`, as in TOKI-058 R20), and starts the server through `startServer` (R3) with the test clock of R4. The seed of TOKI-081 is loaded before the server accepts a request: `seedPrototypeWorkspace` (R17 there) is called with the test clock, a fixed random source and, when TOKI-063 is built, the store, on the empty database; its result must be `loaded`, otherwise the launcher exits 1 with the reason. The run ends by dropping the database. Check: a unit test of the guard has one case for each refusal; after a run, the development database holds the same rows and tables as before it (the by-hand check of TOKI-008 R22), and `toki_e2e_flows_test` does not exist; `dev:reset:db` and `dev:seed` are called by no file of the flows.
- R3. The server start is one function that takes a clock. `apps/server/src/start.ts` exports `startServer({ config, clock })`, which holds what `main.ts` does after reading the configuration (create the connection, `buildApp` with `clock`, the first set-up, the close hook, listening) and returns `{ app, db }`; `main.ts` reads the configuration, calls it with `systemClock` and keeps the shutdown signals and the exit codes it has. Any later ticket that adds a step to the start adds it to `startServer`. No other code of `apps/server/src` imports `start.ts`. Check: the tests of `main.ts` and `app.ts` pass unchanged; a test reads the import lines of `apps/server/src` and finds `start.ts` imported only by `main.ts`; the launcher and the server started by `main.ts` answer `/healthz` the same way.
- R4. A control server for the test, in the launcher process and nowhere else. It listens on `127.0.0.1` at the port of the config (3201) and answers three requests, each a JSON body: `GET /now` returns the test clock's time in epoch milliseconds; `POST /advance` with `{ ms }` (a whole number, 1 to 86,400,000) moves the test clock of TOKI-008 R8 forward by exactly that and returns the new time; `POST /reset` makes the state of R5 and returns `{ now }`. It answers 404 to anything else and 403 to a caller whose address is not loopback. It is a file of `apps/server/tests/`, imported by nothing in `apps/server/src`, so the production server has no such route. The same clock is the one `startServer` gave `buildApp`, so code and mail that read time through it (the sign-in codes, the sessions, TOKI-022) see the move. Check: `GET /now` after `POST /advance { ms: 60000 }` is 60,000 more; a request to the server's own port for `/advance` is 404; a test reads the import lines of `apps/server/src` and finds no import of the control file; with the clock advanced by 60 s, a second code request for one address that answered 429 `code_resend_too_soon` now answers 200 (TOKI-022 R5).
- R5. Every flow starts from the same state. `POST /reset`, in one call: truncates every table of the schema except the migration journal, sets the test clock to the system time, calls `seedPrototypeWorkspace` again with that clock (so the sample lands at "yesterday and today" as TOKI-081 R9 says), empties the file bucket, and writes the manifest of R6 again. The `flow()` helper of R9 calls it before each test. Because the code rows are in the database, the limits on code requests (5 in 15 minutes and one in 60 seconds for an address, TOKI-022 R4, R5) start again with each flow. Check: after a flow that changed every kind of data (a channel, a message, a role), a reset leaves 1 workspace, 8 accounts and the counts of conversations, members, messages, reactions and pins that TOKI-081 R5 to R12 give, and no row in `sessions`, `login_codes`, `events`; after two resets the answer of `GET /api/v1/bootstrap` for Lan lists the 11 conversations of TOKI-081 R18 both times (a server that kept state of the first run in memory would fail here); the flows run in any order and any one of them runs alone (`--grep E07`).
- R6. The manifest and the sign-in helper. The manifest is a JSON file at `e2e/assets/flows-run/manifest.json` (a folder that is not an `outputDir`, so Playwright does not empty it; named by the environment variable `FLOWS_MANIFEST`), written by the launcher from `PROTOTYPE_SEED` of TOKI-081 and the ids the database holds. It has `people` (key, id, email, display name, role), `conversations` (key, id, name, kind) and `messages` (key, conversation key, author key, text). Helpers read it; no file of the flows or of `e2e/support/flows` writes a sample address or a sample text (TOKI-081 R21, Hand-offs). `signInAs(page, ip, key)` in `e2e/support/flows/people.ts` signs the person in through the real routes: it calls `signInByApi` of `e2e/support/real-server.ts` (a code request and a session request, the code read from the mail that Mailpit received), in the browser context of `page`, so the cookie is the one the server set. One change is made to `signInByApi`: it counts the mails to the address before it asks (`mailCount`) and waits for one more (`codeFromMail(address, count)`), so a mail of an earlier run to the same sample address, still in Mailpit, is never read. The helper uses the per-test network address of the `test` fixture of that file (the server runs with `TRUSTED_PROXY`). Check: with a mail to `lan` already in Mailpit from an earlier run, the helper still signs in with the new code; each of the 8 people signs in; a sign-in with the 60 s limit reached (two requests for one address in one flow) fails with 429 unless the clock is advanced (R4).
- R7. Time is passed, never waited for. `advanceTime(page, ms)` in `e2e/support/flows/time.ts` moves the server's test clock (`POST /advance`) and the browser's clock (`page.clock.fastForward(ms)`) by the same amount; `startClock(page)` installs the page clock at the server's `GET /now` before the page opens, so both read the same instant. A delay that a journey names (the 60 s before "Resend code", the 5 s of an Undo, the 5 s of a toast, the 10 minutes of a code) is passed with `advanceTime`; a flow that asserts a delay never lets real time pass for it. No file of `e2e/flows` or `e2e/support/flows` uses `waitForTimeout`, `setTimeout`, `setInterval`, `Date.now(` or `new Date(`; the waiting of Playwright's own assertions (retrying until a screen shows) is allowed. Check: a unit test scans those folders and fails on each of those names (and passes on today's files); a flow that needs 60 s passes in the time of its own steps, which the report of the run shows; E01 passes only if the resend button is disabled before `advanceTime(60_000)` and enabled after it.
- R8. Texts come from the catalogs, and the locators are by role. A flow finds a control by its role and its accessible name, taken with `text(key, values)` of `e2e/support/flows/texts.ts` from the English catalog of `@toki/i18n` (as `e2e/support/sign-in.ts` does for its texts); no flow holds a sentence of the journeys as a literal, because the wording of states the prototype does not draw is a proposal (D-139). `data-testid` is used only where the spec of the screen names one. A key the catalog does not have fails the flow with the key's name. Check: a unit test reads every `text("…")` key of the flows and finds each in the catalog; a rename of a catalog text changes what the flow looks for and the flow still passes; the flows use no `getByText` with a quoted sentence of more than one word.
- R9. A flow is declared with `flow({ id, journeys, features }, body)` in `e2e/support/flows/flow.ts`, which registers one Playwright test for the project that runs, titled `E07 · F10 F11 · …`, calls `POST /reset` first, and gives the body a page factory (`person(key)` opens a new browser context, signs that person in, and starts its clock, R6, R7). The 12 flows are exactly E01 to E12 of "The 12 flows": a unit test lists the declarations and fails unless there are 12, with ids E01 to E12 each used once, each naming at least one journey that is in the written journeys and at least one ticket that is in the plan. The two projects run every flow: a flow that is skipped at one width fails the unit test of R1 that compares the two lists. In CI no flow is skipped (R22); on a machine without the services a run lists every flow as skipped with the reason, as `playwright.sign-in.config.ts` does.
- R10. What makes each flow a proof and not a smoke test. Every flow: (a) begins by asserting something that only the seeded workspace has (a named conversation in the person's list, the text of a seeded message), so a page that renders and nothing else fails at step 1; (b) proves each result in two places, on the screen of the person who acts and in what the server answers to a person it concerns (another person's screen in a second browser context, or that person's own request to the server through `page.request` with their cookie); (c) for each claim of the form "nobody else can" asks the server directly as that person and expects the refusal named in the flow, so a screen that only hides a control passes nothing; (d) ends by reading the state through a route, not through the screen the flow just used. Each flow row below ends with the fault that must turn it red (R11 to R21), and Testing says how that is tried.

## Design
### Where it lives
```
toki/
├─ playwright.flows.config.ts       two projects, webServer: launcher + Vite (ports 3200, 3201, 5175)
├─ package.json                     test:e2e:flows
├─ apps/server/
│  ├─ src/start.ts                  startServer({ config, clock }) (R3); main.ts calls it
│  └─ tests/
│     ├─ e2e-flows-launch.ts        guard, database, seed, startServer, control server (R2, R4)
│     └─ e2e-flows-control.ts       GET /now, POST /advance, POST /reset (R4, R5)
└─ e2e/
   ├─ flows/
   │  ├─ README.md                  the 12 flows (R26)
   │  └─ e01-sign-in.spec.ts … e12-connection.spec.ts
   └─ support/flows/
      ├─ flow.ts                    flow(), the reset, the page factory (R9)
      ├─ people.ts                  manifest reader, signInAs (R6)
      ├─ time.ts                    startClock, advanceTime (R7)
      ├─ texts.ts                   text(key, values) from the English catalog (R8)
      ├─ widths.ts                  the two sizes (R1)
      ├─ control.ts                 the client of the control server
      └─ *.test.ts                  the unit tests of R1, R2, R7, R8, R9 (Vitest, `e2e/vitest.config.ts`)
```

### How a run works
1. Playwright starts two web servers: the launcher and the Vite dev server, which proxies `/api` to the server (the way the other configs do).
2. The launcher checks the database (R2), makes and migrates `toki_e2e_flows_test`, starts the server with the test clock, seeds, writes the manifest and opens the control port. Playwright waits for `/healthz`.
3. Each test calls `POST /reset`, then opens the pages it needs. `signInAs` goes through the real sign-in routes, with the mail read from Mailpit (R6).
4. A delay is passed by `advanceTime` on both clocks (R7). Nothing sleeps.
5. At the end the launcher is stopped and drops the database.

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- Own config and job, not a folder of `pnpm test:e2e`. Reason: the flows need Postgres, Mailpit, MinIO and a seeded database, which the stubbed `e2e` run does not, and TOKI-008 R22 asks for a seeded flow to have its own config and database; `playwright.sign-in.config.ts` set the pattern. A flows run that fails must not hide the faster stubbed run.
- One server for the whole run, reset between flows, not a database and a server for each flow. Reason: a server start and a migration for each of 24 runs costs more than a truncate and a seed, and the sample loads in one transaction (TOKI-081 R14). The risk is state that survives a truncate in the server's memory; R5 has a check for it, and a module that keeps such state must clear it on reset by its own spec.
- Real sign-in for every person in every flow, through the routes, and no route that makes a session for a test. Reason: a route that mints a session is a way into the app that production must never have; the real path is the one the people use, so every flow proves it a little; and because the reset deletes the code rows, the limits on code requests (which count rows) never stop a flow.
- The clocks. The server gets its clock through `startServer` (R3) and the browser through Playwright's `page.clock`; `advanceTime` moves both. Reason: a code that is valid for 10 minutes and a button that enables after 60 seconds depend on the server's time and the page's time together, so moving one breaks the flow. Alternative refused: changing `created_at` of code rows in the database, which needs the tests to know every table that stores a time.
- The manifest instead of importing `PROTOTYPE_SEED` into the test process. Reason: the import would load server modules into the Playwright runner, and the ids of the sample are made when it is seeded (TOKI-081 R10), so only the database knows them. The launcher writes the manifest from `PROTOTYPE_SEED` and the ids it reads back.
- Widths: desktop 1280 by 800 and phone 390 by 844, the `wide` and `narrow` widths of TOKI-109 R6; the middle band (900) is not run, because D-053 names desktop and phone. Concern 3.
- Texts from the catalogs and role-based locators (R8). Reason: the wording of many states is a proposal that the design may change (D-139); a flow that quotes it breaks for a change that is not a bug.
- MinIO in the flows job. Reason: E11 would be a stub otherwise, and TOKI-059 and TOKI-062 say that nothing in CI yet proves a real browser against a real MinIO ("a later automated run against MinIO is a change of the `e2e` job"). The cross-origin request of the browser to storage must be allowed for the web origin of the run by MinIO's own setting (checked by hand at the first run, Testing); this spec does not claim to know that setting.
- The look: every flow runs in the look the app starts with and never changes it, nor the accent, density or language; those are tested by the screens and by TOKI-109.

### Errors
- A service is not reachable and the run is not in CI: every flow is listed as skipped with the reason (R9). In CI: the job fails.
- The seed returns `not_empty` or fails: the launcher exits 1 and prints the reason; Playwright reports the web server as not started.
- A reset fails: the test fails at its first step with the control server's message; no later flow depends on it.
