# Vietnamese search index design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/search-index.md (Thanh Truong)
Ticket: TOKI-069

## Goal
Ctrl+K has to find messages, and a Vietnamese text typed without diacritics has to find the text with them. This ticket builds what the database needs for that and nothing above it: one column of `messages` that holds the searchable words of a message with case and diacritics removed, a GIN index over it, the function that turns what a person typed into the query for that column, and one server function that returns the ids of the messages that match.
The hard rule is that the stored words and the typed words go through the same fold. The database computes the column from the text of the row (a generated column), so a send, an edit and a delete cannot leave it wrong, and a test over every Vietnamese letter, on a database made with `lc_ctype = C` and on one made with `en_US.UTF-8`, checks that the shared function that folds the typed text gives the same words as the database's fold for Latin letters, digits, Vietnamese letters and the separators of R2 step 5 (R3). For text outside that set the two folds are not claimed equal.
The 200 ms budget of D-113 (p95, 1,000,000 messages) is met for ordinary terms: a rare two-word query ran in under 10 ms on 1,000,000 rows. It is not met for a very common short prefix: `n:*` took 335 ms measured on 1,000,000 rows, and `ha`, `ng` or `nh` can also go over. This ticket fixes the shape of the query (one index probe plus a sort) and does not promise 200 ms for such a prefix; the options and the owner's choice are left open in R11 and concern 11.
No extension is installed and the send path gets no new statement. Nothing on screen changes and no request is added: the search API (TOKI-070), the command palette (TOKI-071) and the search inside a conversation (TOKI-072) are built on this.

## Scope
- In:
  - The column `messages.search_vector`, its generation rule (what is indexed and what is folded) and the GIN index `messages_search_idx`, in one migration (R1 to R5, R8).
  - The shared rule for the typed text: `searchWords` and `buildSearchTsQuery` in `packages/shared/src/search/` (R6), and the matching rule they give (R7).
  - `searchMessageIds` in `apps/server/src/modules/messages/` (R9): the one statement that reads the column.
  - The change of the test of the columns of `messages` (R10) and the plan and budget tests (R11).
- Out (not now):
  - The search request, the permission rule (which conversations a person may search), 20 results per kind and more on request, the 2-character minimum, the text of a result and its highlight: TOKI-070. This ticket's function takes the conversation ids it must search and trusts them.
  - The palette and its screens: TOKI-071. The search field of one conversation, which also matches the sender's name: TOKI-072 (it may call `searchMessageIds` with one conversation id).
  - The folding of names (conversations, people), which is `foldText`, owned by TOKI-050 (R6, concern 10), and the search of files by name (TOKI-063).
  - What the text of a deleted message becomes in the row, and the edit request: TOKI-047. The send: TOKI-037. Both are unchanged here (R5, concern 7).
  - The measurement with a million messages on a real server: TOKI-089 (R11).

## Requirements
- R1. `messages` gains one column, `search_vector`, of type `tsvector`, not null, generated and stored (`GENERATED ALWAYS AS (...) STORED`), and no other column. It has no default (a generated column cannot have one) and no caller writes it: an insert that names it and an update that sets it are refused by Postgres. The generation rule is R2. Check: a test applies the migrations to a throwaway database and reads `pg_attribute`: the column exists, `atttypid` is `tsvector`, `attnotnull` is true, `attgenerated` is `s` (stored); the expression is proved by what it computes (the lexeme lists of R2), not by its text, because `pg_get_expr` returns a normalised form (`'simple'::regconfig`, `NORMALIZE(body, NFD)`) that cannot be compared with the migration word for word; if a text check is wanted, the test builds a reference generated column from the same expression constant in a scratch table and compares the two `pg_get_expr` outputs; an insert that sets `search_vector` fails; an update of it fails; the other columns of the table are as TOKI-036 R1 and TOKI-045 R1 left them (the test of R10).
- R2. What is indexed. The column is `to_tsvector('simple', words)` where `words` is: the empty string when `kind` is not `user` or `deleted_at` is not null; otherwise the text `body` folded and cleaned in this order: (1) `normalize(body, NFD)`; (2) every combining mark `U+0300` to `U+036F` removed; (3) `đ` and `Đ` replaced by `d`; (4) lower case with `lower`; (5) every run of the following characters replaced by one space: white space (`\s`), ASCII punctuation and symbols (`!` to `/`, `:` to `@`, `[` to the backtick, `{` to `~`) and these separators, listed in the expression so that no database setting decides them: no-break space `U+00A0`, `¡ « · » ¿`, general punctuation `U+2000` to `U+206F` (curly quotes, dashes, the ellipsis, zero-width characters), currency signs `U+20A0` to `U+20CF` (`₫`), arrows `U+2190` to `U+21FF`, symbols and dingbats `U+2600` to `U+2775` (`✓`, `★`), the ideographic space `U+3000`, the variation selectors `U+FE00` to `U+FE0F` and the emoji planes `U+1F000` to `U+1FAFF`. The expression, which the migration holds word for word: `to_tsvector('simple', CASE WHEN "kind" = 'user' AND "deleted_at" IS NULL THEN regexp_replace(lower(replace(replace(regexp_replace(normalize("body", NFD), '[\u0300-\u036F]', '', 'g'), 'đ', 'd'), 'Đ', 'd')), '[\s!-/:-@\[-`{-~\u00A0\u00A1\u00AB\u00B7\u00BB\u00BF\u2000-\u206F\u20A0-\u20CF\u2190-\u21FF\u2600-\u2775\u3000\uFE00-\uFE0F\U0001F000-\U0001FAFF]+', ' ', 'g') ELSE '' END)`. Why the list is explicit: what is left after step 5 is split into words by the Postgres parser, and the parser's idea of a letter depends on the `lc_ctype` of the database. On a database with `lc_ctype = C` (also UTF8) a text such as `chào…bạn`, a word between curly quotes or `x😀y` is not split by the parser, while on `en_US.UTF-8` it is; the list makes both give the same words. The fold itself needs no locale for Vietnamese: after steps 1 to 3 every Vietnamese capital is an ASCII capital, so `lower` works under `C`. A character that is in neither the list nor the Vietnamese and ASCII sets (another script) is tokenised by the parser and so does depend on the locale ("Locale and other scripts"). This rule has not been run on PostgreSQL 14 or 17 by the author of this spec; the regular-expression classes are checked when the work is built (R12 cases 8 and 13 on both databases). Steps 1 to 4 are the steps of `foldText` (TOKI-032 R19) and of the SQL fold of member management R24; step 5 is added so that the text is only words: without it the Postgres parser would keep a web address, an e-mail address or a number such as `2.1` as one token and "example" would not find `https://example.com`. The check of step 5 is repeated on a database made with `lc_ctype = C` (R3, R12). The text is the body as stored (TOKI-037 R4 stores it as sent, no markup removed), so the name in `@Lan Nguyễn` is searchable like any word and the marks `*`, `_` and the backtick of TOKI-049 vanish with step 5. System lines have an empty body and are empty here by the `kind` test; a deleted message is empty by the `deleted_at` test, so it is not found even before TOKI-047 empties its text (R5). Check: with SQL inserts, the vector of `Xin chào, các bạn!` holds the lexemes `ban`, `cac`, `chao`, `xin`; of `Đà Nẵng http://example.com/a?b=1` holds `a`, `b`, `1`, `com`, `da`, `example`, `http`, `nang`; of `Deploy v2.1 tonight` holds `1`, `deploy`, `tonight`, `v2`; of `*in đậm* và _nghiêng_` holds `dam`, `in`, `nghieng`, `va`; of `@Lan Nguyễn` holds `lan`, `nguyen`; a system line (an empty body) and a user message with an empty body hold no lexeme; a user message with `deleted_at` and `deleted_by` set (SQL) and a non-empty body holds none, and the same row before the delete held its words.
- R3. The database fold and the shared fold follow the same rule. `searchWords(text)` of R6 returns the words the column would hold for that text, when the text is made only of Latin letters, digits, Vietnamese letters and the separators of R2 step 5; for any other script or character the two are not claimed equal (the Postgres parser decides them by the locale), and TOKI-070 must not rely on equality there. Check: a test inserts, for each of 12 base vowels (`a ă â e ê i o ô ơ u ư y`) in lower and upper case with each of the six tones (none, grave, acute, hook, tilde, dot below), plus `đ` and `Đ`, one message per letter, in the precomposed form (NFC) and in the decomposed form (NFD), each inside the word `x<letter>y` (about 300 rows), reads `tsvector_to_array(search_vector)` and compares it, row by row, with `searchWords` of the same text: the two give the same set of words, every letter is reduced to its base letter (`đ` to `d`), and the NFC and NFD rows of one letter give one lexeme. The same comparison is made for every fixture of R12 whose text has no character outside Latin letters, digits, the Vietnamese letters and the separators of R2 step 5 (a character that Unicode counts as a letter or a digit but step 5 does not list, such as an enclosed digit, is not used in these fixtures), and the whole test runs twice: on a throwaway database made with `TEMPLATE template0 LC_CTYPE 'C' LC_COLLATE 'C'` and on one made with `en_US.UTF-8`, so the result does not depend on the locale; if the second locale is missing in the image the test is skipped with a stated reason and the `C` run still stands. A table test of the shared function alone covers the same letters with no database. This test is what keeps the two implementations from drifting apart; it fails if either changes alone.
- R4. The index `messages_search_idx` is a GIN index on `search_vector` with the storage parameter `fastupdate = off`, so that a send updates the index directly and never pays for the flush of a pending list (concern 9). It is a full index, not a partial one: a row that is deleted or a system line holds an empty vector, which adds no entry. Check: `pg_indexes` and `pg_class.reloptions` show the index, the method `gin` and `fastupdate=off`; the plan test of R11.
- R5. The column is right after every write, with no code of this ticket in the write. `search_vector` is computed by Postgres from `kind`, `deleted_at` and `body` of the same row, so: a send (an insert) stores the words of its text (TOKI-037 changes nothing); an edit (an update of `body` and `edited_at`, TOKI-047 R4) replaces them; a delete (an update of `deleted_at`, `deleted_by` and `body`, which TOKI-047 R7 sets to the empty string) empties them. The owner of this rule is TOKI-069 (the rule and its tests); TOKI-047 and TOKI-037 add no step and no column write, and no handler of `recordChange` touches the column (concern 7). Because the generated expression reads `deleted_at`, a message deleted by SQL with its text left in place (which TOKI-036 R6 allows) is also not found. `messages_immutable_trg` (TOKI-036 R7) is not changed: it lists neither `body` nor the new column. Check: insert a message with `Xin chào các bạn`; `search_vector @@ to_tsquery('simple','chao:*')` is true; update `body` to `Tạm biệt` and the old word no longer matches while `tam:*` does and `edited_at` can be set in the same update; update `deleted_at` and `deleted_by` with the text left in place and nothing matches; the same with the text set to the empty string; an update of other columns (`edited_at` alone) leaves the vector as it was; a rolled back edit leaves the old words; the row count and `created_at` are unchanged by all of it; one test sends a message through the send function of TOKI-037 and finds it (this is what the dependency on TOKI-037 is for, with the entries read through `buildMessageEntry` in the tests of R9); another updates the summary columns of a thread root as TOKI-045 R4 does, once per reply, and checks that the vector is unchanged and, as a build-time check, whether the GIN index gains entries (it should not).
- R6. `packages/shared/src/search/` holds the rule for the typed text, pure and with no DOM global, exported from the package index. `searchWords(text: string): string[]` returns the distinct words of a text in order of first appearance: `foldText(text)` (R2 steps 1 to 4, from `packages/shared/src/text/fold.ts`, owned by TOKI-050 R2), then split on every run of characters that are not a letter, a mark or a digit (`/[^\p{L}\p{M}\p{N}]+/u`), empty pieces dropped. The words match what the column holds only for text made of Latin letters, digits, Vietnamese letters and the separators of R2 step 5 (R3); TOKI-070 does not rely on it for other scripts. It never throws, also for a lone surrogate or an empty string. `buildSearchTsQuery(text: string): string | null` returns the argument of `to_tsquery('simple', $1)`: the first `SEARCH_MAX_TERMS` (8) words of `searchWords(text)`, each cut to `SEARCH_TERM_MAX_LENGTH` (64) code points, each followed by `:*` (a word prefix) and joined with ` & `; `null` when there is no word. A word holds only letters, marks and digits, so no character of the query language (`& | ! ( ) : * ' \ <`) can reach the query: the text of a person is never put into the query as syntax. The constants `SEARCH_MAX_TERMS` and `SEARCH_TERM_MAX_LENGTH` (builder choices: a longer query never helps a person and costs the database; no decision gives them). The 2-character minimum of the palette (F29) is not applied here: it is TOKI-070's and TOKI-071's, which decide when to call. The names `foldText`, `searchWords` and `buildSearchTsQuery` are the contract for TOKI-070, TOKI-071 and TOKI-072. `foldText` is TOKI-050's (R2 of its spec: one fold in `packages/shared`, `foldSearchText` of `client-core` re-exports it); if this ticket is built first, it adds `text/fold.ts` exactly as that requirement describes, with its test, and TOKI-050 finds it present and adds nothing (concern 10). Check: table tests: `"Hà Nội"`, `"ha noi"`, `"HÀ NỘI"` and the decomposed form give `["ha","noi"]`; `"  tiếng   Việt, "` gives `["tieng","viet"]`; `"đạt"` and `"Đạt"` give `["dat"]`; `"a.b/c"` gives `["a","b","c"]`; `""`, `"   "`, `"!!!"` and `"😀"` give `[]`; a lone surrogate and 100,000 characters do not throw; `buildSearchTsQuery("Hà Nội")` is `ha:* & noi:*`; `buildSearchTsQuery("a & b | !c (d) 'e' f:* \\g")` is `a:* & b:* & c:* & d:* & e:* & f:* & g:*`; 9 words give the first 8; a 100-letter word is cut to 64; `""` and `"!!!"` give `null`; a database test passes the result of every query of this list to `to_tsquery('simple', $1)` and none raises a syntax error. The shared package has no DOM global (lint rule `toki/client-core-globals`).
- R7. The match rule that follows, stated once for the tickets above. It is a proposal, not a decision (concern 4): the log decides Postgres full-text search that ignores diacritics (D-015) and nothing about word prefixes, order or the inside of a word, and it departs from the prototype, whose message search (`paletteItems`, line 2178 of `index.html`) keeps a message when its lower-cased text contains the whole query as one substring (`includes(q)`), so a part inside a word and a phrase match there. With the proposal a message is found by a text when every word of `searchWords(text)` is the start of some word of the message (a word prefix, case and diacritics ignored, in any order and at any distance, not as a phrase). As proposed, `ha noi` finds `Hà Nội` and `Nội thành Hà Nội`, and finds `noi chuyen o ha` (both words are there); `tieng v` finds `tiếng Việt`; `ieng` does not find `tiếng` (no match inside a word); `viet` finds `Việt` and `việt`; no word is stemmed (the `simple` configuration). Folding removes tones, so `ma` finds `má`, `mà`, `mả`, `mã` and `mạ` alike: that is what "ignoring diacritics" (D-015) says, and a person who types the marks still finds the same set. Check: the cases above as database tests with the function of R9 and with `to_tsquery` on the column; the tone case with all six forms of `ma` stored and `ma` and `má` as queries, both finding all six. If the owner chooses the prototype's rule (a substring of the whole query), the column and the index stay and the query changes, but a substring match inside a word needs another index (concern 4).

One migration, `<number>_message_search_index.sql`, made with `pnpm db:generate --name message_search_index` (TOKI-019 convention 8; the whole `apps/server/migrations/` change is committed, `meta/` included). The generated column and the storage parameter are written into the generated file by hand if the generator does not write them, as the migration of TOKI-036 does for what it cannot. DROP COLUMN`, which is a quick catalog change); nothing reads the column before TOKI-070, so the way back loses no feature. The schema file (`modules/messages/schema.ts`) declares the column with a `tsvector` custom type, `generatedAlwaysAs` the same expression, and the index with `.using("gin", ...)` and `fastupdate: off`, so `pnpm db:generate` run again reports no change. Check: the migration test of TOKI-005 passes with the file; a test finds one `ADD COLUMN` and one `CREATE INDEX` and no `CREATE TABLE` in it; a test of the backfill applies all earlier migrations, inserts rows with SQL (an accented text, an NFD text, a system line, a deleted row), applies this migration and reads the vectors: every row already holds its words; `pnpm db:generate` reports no change.
- R9. `searchMessageIds(client, input)` of `apps/server/src/modules/messages/search.ts`, exported by the module's `index.ts` (no table is exported), is the one read of `search_vector`. `client` is a `DbClient`; `input` is `{ workspaceId: string; tsQuery: string; conversationIds: string[]; limit: number; before?: { createdAt: Date; id: string } }`. It runs one statement: `select id, conversation_id, created_at from messages where workspace_id = $1 and conversation_id = any($3) and search_vector @@ to_tsquery('simple', $2) [and (created_at, id) < ($5, $6)] order by created_at desc, id desc limit $4` and returns `{ id, conversationId, createdAt }[]`. The order, newest first by (`created_at`, `id`) as TOKI-036 R12 orders messages, is a proposal until concern 5 is answered; it is the one `order by` of the statement. `limit` is an integer from 1 to 50 and `conversationIds` has 0 to 1,000 distinct ids, and `tsQuery` is not empty; anything else throws before a statement is sent (an empty list of conversations returns `[]` with no statement). A caller that has more than 1,000 conversation ids calls the function once for each group of 1,000 and merges the results by (`createdAt`, `id`) itself (TOKI-070 R7); the function does not group. `before.createdAt` is a JavaScript `Date`, which holds whole milliseconds, while `created_at` holds microseconds: for rows written by the application (whole milliseconds, TOKI-037 R3) the cursor loses nothing, and for a row written by SQL, an import or a seed with microseconds a page boundary can skip or repeat a row; the seed of TOKI-081 therefore writes whole milliseconds. The function does not decide which conversations a person may search: the caller gives the ids it has already checked (TOKI-070; the rule of D-116 and D-051 is its rule), and the function adds no condition of its own about archived channels, direct messages or threads, so the history of an archived channel is found (Blueprint context) and so is a reply. It returns no text and no author: the caller reads the entries through the builder of TOKI-037 (`buildMessageEntry`), so a result has the same shape and the same hiding rules as a message in a list. `tsQuery` must come from `buildSearchTsQuery`; a string that is not a valid query makes Postgres raise a syntax error, which propagates (the caller passes only what R6 built). Check: with rows in three conversations of one workspace and one of another: only the given conversations and the given workspace come back; the order is newest first and equal times break by id; `limit` 2 with `before` set to the last row of the previous page walks 7 matches in pages of 2, 2, 2, 1 with every match once and no repeat; a deleted message, a system line and a message with no match are never returned; a message in an archived conversation is returned; a reply is returned; a `limit` of 0 and 51, 1,001 ids and an empty `tsQuery` throw with no statement sent (the test counts the statements on the connection); `conversationIds` empty returns `[]` and sends none; the statement count is one; the export test of the module lists `searchMessageIds` and no table.

- R11. The index is used, and the cost is bounded. (a) Plan test: on a throwaway database holding 20,000 messages over 40 conversations with Vietnamese-like text (a fixed seed; about 10% with a deleted flag), the test runs `EXPLAIN (FORMAT JSON)` of the statement of R9 with `enable_seqscan` off for: a one-word query (`nguoi:*`), a two-word query (`ha:* & noi:*`), a 1-letter-prefix query (`n:*`), with 1 and with 30 conversation ids, and with a `before` cursor; with 30 conversation ids and with a cursor, each plan contains a `Bitmap Index Scan` on `messages_search_idx` and no `Seq Scan` on `messages`; with 1 conversation id the planner may walk the btree index of TOKI-036 on (conversation, `created_at`, `id`) and filter, so that case accepts either index and the test does not assert one (it is kept only to prove there is no `Seq Scan`). The plan has a sort of the matches (the index holds no time), which is allowed and is the cost the budget below limits. (b) Budget. D-113 asks for under 200 ms at p95 over 1,000,000 messages. The design meets it for ordinary terms and does not meet it for a very common short prefix (335 ms measured for `n:*`); the options and the owner's choice are left open in concern 11. Stated plainly: the cost follows the number of matches of the words in the whole workspace, not the conversations searched, because the GIN index holds no conversation and no time (the matches are read, filtered by conversation and sorted). The reviewer ran 1,000,000 synthetic rows on PostgreSQL 14 (1,000 conversations, 30 searched, top 21 newest first): a rare two-word query ran in under 10 ms, but `n:*`, which matches every row, took 335 ms (1,000,000 rows from the index, 970,000 removed by the conversation filter, 41,667 heap blocks), over the budget. A short common prefix (`ha`, `ng`, `nh`) can therefore exceed 200 ms, and the 2-character minimum of TOKI-070 does not prevent it. This ticket promises the shape: one index probe plus a sort of the matches with a limit of at most 50 rows returned, the index the only structure it needs; it does not promise 200 ms for a common 1 or 2-letter prefix (concern 11). The measurement on the real server with a million messages, 200 people online and the permission join of TOKI-070 is TOKI-089's, and the plan of TOKI-070 must read this paragraph. For reference, the design was tried on a laptop with PostgreSQL 14 (the same functions) on 1,000,000 synthetic Vietnamese messages, 30 conversations of 1,000 searched, a top-21 query newest first: the three shapes above answered in 90 to 150 ms with a skewed word list that makes the first word match 16% of the rows; the table was 308 MB and the index 29 MB, and building the index took 2.5 s (the reviewer's text had longer words: 326 MB and 65 MB). These figures are not a test and not a promise of this ticket (a test with real time is not written, the rule of the repository); the budget is reachable for selective queries, and the builder repeats the measure on the target image, with a common prefix among the queries, and writes it in the pull request. (c) The send path: the column is computed inside the insert, with no extra statement and no call to another system; with `fastupdate = off` a send updates the index in the same transaction (R4). TOKI-089 measures the 150 ms send target (NFR-13) with it in place. If the measure fails, the options that keep the contract are a partial index, `btree_gin` for the conversation, a cap on the matches read for a one-letter or two-letter prefix, or a longer minimum prefix in TOKI-070; none is built now (concerns 9 and 11). Check: the plan test; a unit check that the statement has one `limit` and no `offset`; the statement count of R9.

## Design
### Data model
`messages.search_vector` (module `messages`; the "search column" of the technical design's Messages group): `tsvector`, not null, generated and stored from `kind`, `deleted_at` and `body` (R1, R2). `messages_search_idx`: GIN on it, `fastupdate = off` (R4). Nothing else.

### Why a generated column, and no extension
Decided in this spec (concerns 1 and 2); the alternatives were tried against the facts of the repository:
- `unaccent`: not used. It is an extension (`CREATE EXTENSION` needs a privilege on the database that the application's role and the throwaway test databases do not have today, and the development compose file and CI start the stock `postgres` images with no setup script), its function is not marked immutable so it cannot be used in a generated column or an index expression without a wrapper function, and its rules are a file of the server install, so the result could change with the image. The fold of `foldText` needs only five steps that Postgres has built in, and the Admin list already uses them as one SQL expression (member management R24).
- `pg_trgm`: not used. D-015 names Postgres full-text search and does not forbid a trigram index; the reasons are ours: it is an extension to install, which the images and the throwaway databases do not do today; a trigram index is several times the size of the text and slow to update; a 1 or 2-letter query makes no full trigram; and fuzzy matching is a proposal that no decision accepts (D-187 is open). It is what a match inside a word would need (concern 4).
- A trigger that sets an ordinary column: not used. A trigger is code that every later change of the table must keep in mind, and a column set by a trigger can be written around by a caller; a generated column cannot be written at all.
- A column computed by the server code (`foldText` in TypeScript, written with the text): not used. Every writer of `body` would have to remember it (the send, the edit, the delete, the seed of TOKI-081, a future import), and a missed writer leaves a message that cannot be found with no error. It would give one fold in one language, which R3 gives anyway by a test.
The price of a generated column: the fold exists twice (in SQL and in `foldText`), and changing the rule means a new migration that rewrites the table (about 28 s of waiting writes on 1,000,000 rows, R8). R3 turns the first into a test that fails when they differ; the second is accepted because the rule is decided (D-015, TOKI-032 R19) and rarely changes.

### What is indexed
The words of `body` as stored, for `user` messages that are not deleted (R2). Not indexed: system lines (they have no text, TOKI-036 R3), deleted messages, the names of attached files (TOKI-058; the Files section searches them, TOKI-063), the sender's name (TOKI-072 matches it on the people list), the topic of a conversation. A mention is stored as the name typed in the text (TOKI-050 proposal, concern 1 of that spec), so `lan` finds a message that mentions Lan. If that spec stores mentions another way, this column is unchanged: it reads the body and nothing else.

### The query
`buildSearchTsQuery` (R6) gives `ha:* & noi:*`; `searchMessageIds` (R9) filters by workspace and by the conversations it is given, then by `search_vector @@ to_tsquery('simple', $2)`. The GIN index cannot hold the conversation, so Postgres reads the matches of the words from the index and filters them by conversation; for words that are in most of the messages the number of matches is large, and the cost is the sort of them. This is why the query has a minimum length in the palette (TOKI-070) and a limit of 50 here. A composite index with `btree_gin` is the option if the measure of TOKI-089 asks for it (R11).

### Locale and other scripts
The configuration is `simple` (no stop words, no stemming), so every word is searchable and the same for Vietnamese and English. Vietnamese text folds to the 26 ASCII letters, and the separators that matter in chat (curly quotes, dashes, the ellipsis, no-break space, currency signs, emoji) are listed in the expression (R2 step 5), so for Vietnamese and English text the column is the same on a database with `lc_ctype = C` and on one with `en_US.UTF-8`; the tests run on both (R3). This is a choice: the other way would be to require that `lc_ctype` is not `C` and to test it in the migration test. Text in another script (Cyrillic, Chinese) or a separator that is not in the list is tokenised by the database's character rules, so it does depend on the locale (and under `C`, `lower` does not lower-case non-ASCII capitals); this is not tested and not a requirement, because the product is English and Vietnamese (D-018). `lower` and `toLowerCase` may differ for a few letters of other scripts (for example the Turkish dotted capital I), which can only make a word of such a text not found.

## Data safety
- `search_vector` holds the words of the content of conversations, folded. It is stored in the same table as the text, so it has the same readers; it is not logged and not returned. A result carries ids, so the text goes through the builder of TOKI-037 and its hiding rules.
- Private channels and direct messages are searchable by their members only. That rule is applied by TOKI-070 before it calls `searchMessageIds`; this function does not check it and says so (R9), and the access-control suite of TOKI-088 covers search ("also through search").
- The text of a person is never put into the query as syntax (R6). The statement takes the query and the ids as parameters.

## Areas of concern
1. Which extension. Decided in this spec: none; the fold is built from `normalize`, `regexp_replace`, `replace` and `lower`, all built in and all immutable. Reason: `unaccent` is an extension whose function is not immutable, `pg_trgm` is an extension too, and the repository's images and the throwaway test databases are set up with no extension (see "Why a generated column, and no extension"; D-015 does not rule `pg_trgm` out). Checked on PostgreSQL 14 only: the functions were run as a generated column and a GIN index on 1,000,000 rows; the target is `postgres:17.12`, where `normalize` exists since 13, but 17 has not been run. Owner: Thanh Truong.
2. Where the column is computed. Decided in this spec: a generated stored column. Reason and alternatives (trigger, server code): "Why a generated column, and no extension". The cost is a second copy of the fold, held equal to `foldText` by R3. Owner: Thanh Truong.
3. Which text is indexed. Decided in this spec: the `body` as stored of `user` messages that are not deleted, with every run of white space and ASCII punctuation as a separator (R2). A mention is the name in the text and is searchable. System lines, deleted messages, file names and the topic are not in the column. Reason: a deleted message is shown as "Message deleted" with no text (D-013, D-049), so finding it would show text the screen hides; the other items have their own searches. Owner: Thanh Truong.
4. How a typed text matches. Not decided: no entry of the log gives the rule. D-015 decides Postgres full-text search that ignores diacritics and respects permissions; D-112 gives 20 results per kind; nothing says word prefix, any order, or no match inside a word, and the prototype's message search is a plain substring of the whole query (`includes(q)`, line 2178 of `index.html`), so the proposal below departs from it. Proposal, not a decision (R7): every typed word is the start of some word of the message, in any order, with no match inside a word, no stemming and no fuzzy match. Reason for the proposal: it is what a full-text index answers fast (D-015, D-113); the flows speak of messages "containing the words" (F29 and the search inside a conversation); a match inside a word needs a trigram index (concern 1), which costs size and write time; fuzzy matching is a proposal that no decision accepts (D-187). Folding makes the six tones of a syllable equal, which is what "ignoring diacritics" says. If the owner wants the prototype's rule, R7 and R6 change and a trigram index becomes the question. The ranking of results is not a matter of this column. Evidence for the owner: the prototype line above and R7's examples (`ieng` does not find `tiếng`; a phrase finds words in another order). Owner: Thanh Truong (product owner).
5. The order of the messages of a search. Not decided. The log orders names ("exact matches first", "names that start with the text, then names that contain it") in D-187, which is itself open and is about names; nothing orders messages, and the 20 results per kind of D-112 need one. Proposal, not a decision: newest first by (`created_at`, `id`), so a person sees the latest talk about the words first and a page after a cursor is stable; the other candidates are the best match first (`ts_rank`), which a prefix query does not rank well, and the conversations of the person first. R9 and its plan test use the proposal; if the owner answers otherwise only the `order by` and the cursor of R9 and their checks change. Evidence for the owner: F29 (the palette lists messages last, 20 per group, more on request); the same question belongs to TOKI-070, whose spec should state it the same way, and the cursor of R9 works only for the newest-first order. Owner: Thanh Truong (product owner).
6. Who owns the migration and the test of the columns. Decided in this spec: this ticket, with one migration of its own (TOKI-019 convention 8, TOKI-036 concern 7), and it edits the test of TOKI-036 R1 in the same change into an allow-list (R10), because a test that counts the columns of the table would fail once for every ticket that adds one, in an order that depends on which branch merges first. Owner: Thanh Truong.
7. Who keeps the column right when a message is edited or deleted. Decided in this spec: the database; TOKI-069 owns the rule and the tests that prove it (R5). The edit of TOKI-047 updates `body`, the delete sets `deleted_at` and empties `body` (its R4, R7), and the column follows without a line of their code. Reason: a column that every writer must remember is missed once; a generated column cannot be missed. A future writer of `body` (an import, the seed of TOKI-081) gets the same result. The one thing the builders of TOKI-047 and TOKI-037 must not do is write a copy of the words by themselves; R13 has a test for it. Owner: Thanh Truong.
8. Backfill and the rewrite. Decided in this spec: adding a generated stored column makes Postgres compute it for every existing row while it rewrites the table, so the migration is the backfill (R8); it holds a lock that stops reads and writes of `messages` until it ends, and the index build then stops writes. The migration is run before the people use the server (the table holds only the seed of TOKI-081 and the first messages), so the stop is short on the first deploy; the reviewer's run on 1,000,000 rows on PostgreSQL 14 was 20.7 s for the column (exclusive lock) and 6.9 s for the index (R8), and the builder measures it on the target and writes it in the pull request. Risk and way back: R8 (a new migration that drops the index and the column; nothing reads the column before TOKI-070). If a later change to the fold has to run on a busy table, it needs its own plan (a new column, a batched fill, `CREATE INDEX CONCURRENTLY`), and that is out of this ticket. Owner: Thanh Truong.
9. The index settings and the budget. Decided in this spec: GIN, `fastupdate = off`, the `simple` configuration, no composite index. Reason: a send is rare (200 people) and its latency is the one that counts (NFR-13), so the index is updated in the send transaction and no later insert pays for a flush of a pending list; the search budget is D-113 and the plan test is R11. The cost is slower inserts than with the default; TOKI-089 measures the send with it in place, and its result may reopen this one setting (not the contract). The search budget is a separate matter (concern 11). Owner: Thanh Truong.
10. Where `foldText` lives. Decided: TOKI-050 owns `packages/shared/src/text/fold.ts` (its R2, which moves the rule of TOKI-032 R19 there because the server may not import `client-core`). This ticket needs the same function; whichever ticket is built first adds the file exactly as TOKI-050 R2 describes it and with its tests, and the other imports it, so there is one function and no copy. Owner: Thanh Truong.
11. The budget for a very common short prefix. Not decided. D-113 asks for under 200 ms at p95 over a million messages; the reviewer measured 335 ms for `n:*` on 1,000,000 rows on PostgreSQL 14 (R11), and the 2-character minimum of TOKI-070 does not prevent it for `ha`, `ng` or `nh`. Proposal, not a decision: build as R11 says, measure at TOKI-089 with common prefixes among the queries, and if the budget fails take one of the options of R11 (a cap on the matches read for a short prefix, a minimum prefix of 3 letters in TOKI-070, `btree_gin` for the conversation). Which option is a product matter (a 3-letter minimum changes F29). Owner: Thanh Truong (product owner).
