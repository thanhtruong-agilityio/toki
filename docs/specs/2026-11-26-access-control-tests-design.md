# Access-control test suite design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/access-control-tests.md (Thanh Truong)
Ticket: TOKI-088

## Goal
The owner needs proof, for every endpoint of the server, that a person without access is refused, and that the proof cannot rot: a new endpoint must not be able to join the application without a refusal test. This ticket builds one test suite, driven by a registry of endpoints that is checked against the routes the application really registers.
The suite looks at the server from the side of the person who must be refused: signed out, a Member asking for Admin things, an Admin outside a private channel or a direct message, a person who has not joined a public channel, and a person who reaches the same data through search, a file list, a file address, a jump to a message or the live stream.
This ticket adds tests only. It changes no route and no permission function.

## Scope
- In:
  - The route table of the real application, read while it is built (R2), and the registry of endpoints with one entry for each route (R1, R3).
  - The check that fails when a route has no entry, when an entry has no route, or when an entry says less than its route needs (R3).
  - The fixture of people, conversations and hidden content (R5) and the cases that every class of endpoint must pass (R4, R6 to R15).
  - The scan that looks for hidden content in every answer (R13, R14).
  - The ledger that proves every required case ran (R4, R17).
- Out (not now):
  - The tests of each feature's own rules (validation, locks, limits, repeats). They stay with the ticket that owns the route. This suite adds the refusal side for all of them and does not copy those cases.
  - Guests. Phase 5 adds the role, its rows and the guest suite of D-050; the registry is built so that one more actor class is one more row of Table A (concern 3).
  - The browser flows with a signed-in person at desktop and phone widths: TOKI-090. The shared "no access" page and what it says: TOKI-082.
  - The wording and looks of any refusal on screen. The suite checks status, code and body of the server only.
  - The headers, cookies, rate limits and dependencies review: TOKI-091.
  - Speed. The suite has no time limit of its own; the measurement of the six targets is TOKI-089.

## Requirements
- R1. The registry. `apps/server/tests/access/registry.ts` exports `accessRegistry`, a list of entries, built from one file for each module in `apps/server/tests/access/entries/` (`auth.ts`, `members.ts`, `channels.ts`, `direct.ts`, `bootstrap.ts`, `messages.ts`, `threads.ts`, `reactions.ts`, `pins.ts`, `read.ts`, `files.ts`, `link-previews.ts`, `search.ts`, `shared-items.ts`, `activity.ts`, `later.ts`, `quiet.ts`, `notifications.ts`, `drafts.ts`, `status.ts`, `presence.ts`, `storage.ts`, `realtime.ts`; a ticket that adds a module adds its file and one line in `registry.ts`). An entry has: `route` (the method and the url exactly as Fastify registers it, for example `POST /api/v1/channels/:id/join`), `access` (one of `public`, `signed-in`, `admin`, `conversation`, `owned`; Table A), `request(world, target)` (returns the url, the body and the headers of a valid request for that target), `control` (who must succeed with that request, a person of the world), `destructive` (true when a success changes the target, so each case gets a fresh one, R5), `source` (the spec requirement that gives the route its rule), and the fields of its class: `open` for a `conversation` entry (R10), `ownedBy` for an `owned` entry or a route that takes someone's id (R12), and `target` for a route that takes a conversation id in a body or a path with an owned id (R3 e). A `public` entry has `reason`, a sentence that says why no session is needed, and a source id. Check: a unit test of the registry shape builds every entry's request once and fails on an entry with a missing field, a duplicate `route`, or a `public` entry with no `reason`.
- R2. The route table. `apps/server/tests/access/route-table.ts` builds the full application once, with every option that registers a route switched on (the database, the gateway, presence, the storage client, the push key, and every option a later ticket adds for the same purpose), adds an `onRoute` hook to the application before it is ready, and returns one record for each route: method, url as registered, and `config.public`. The automatic `HEAD` route that Fastify adds for a `GET` is left out; every other method counts, and `/healthz` and `GET /ws` count (they are the two routes outside the `/api/v1` scope, TOKI-038 R1). The table has a floor: it holds at least every route of the code that was on `main` when this spec was written (the channel, direct, member, sign-in and bootstrap routes) or the test fails, so an `onRoute` hook that sees nothing cannot make the check pass. Check: the floor test, and a test that builds the application twice and gets the same table.
- R3. The coverage check. A test compares the route table (R2) with `accessRegistry` (R1) and fails on each of these, naming the route and the file to edit: (a) a registered route with no entry: "POST /api/v1/x has no access entry; add one in apps/server/tests/access/entries/<module>.ts"; (b) an entry whose route is not registered; (c) two entries for one route; (d) a route registered with `config.public` true whose entry is not `public`, and a `public` entry whose route needs a session; (e) a url with a path parameter whose entry is `signed-in` or `admin` with no `ownedBy` or `target` field (a route that takes an id must say whose id and be tried with someone else's, R12); (f) a url under `/channels/:id` or `/conversations/:id` whose entry is not `conversation`. There is no list of exempt routes: `/healthz` and the sign-in routes are `public` entries with a reason like any other. Check: the coverage test runs against the real table, and a second test feeds it a table with one invented route, one removed route and one route with the wrong class, and expects the three failures with these messages.
- R4. Cases follow the class. `apps/server/tests/access/cases.ts` holds the required cases of each class (Table B). The runner makes them from the entry; an entry cannot remove or soften a case. A case is a request, the person who makes it, the expected status and code, and a state check (R15). The runner writes one line to the ledger for each case it ran (`route`, `case`, `status`). One final test builds the list of required cases from the registry and fails unless the ledger holds exactly those lines, so a case that is skipped, a file that is not run or an entry whose cases did not run fails. The suite contains no `it.skip`, `it.todo`, `it.only`, `describe.skip` or `test.skip`: a source test over `apps/server/tests/access/` fails on one.
- R5. The fixture. `apps/server/tests/access/world.ts` builds one world once for each test file, on the real database, through the real routes and the helpers of the sign-in and channel tests (`createHarness`, `person`, `send`), the fake mail layer, the fake storage client and the test clock of TOKI-008. People: `admin1` (Admin, member of the private channel), `member1` (Member, member of it), `admin2` (Admin, in no private conversation), `member2` (Member, in none), `left1` (a Member who was in the private channel and left it), `gone1` (a Member whose account is deactivated after signing in, so its cookie is still a real one). Conversations: `#general`, a public channel both Members joined (`joined`), a public channel `member2` and `admin2` have not joined (`open`), a private channel `secret` (`admin1`, `member1`, `left1` before leaving), a direct message of `member1` and `admin1`, a group direct message of `member1`, `admin1` and `left1`, an archived private channel. Content in each of `secret`, the direct message, the group, `open` and the archived channel: a message, a thread reply, a pin, a reaction, a file with a thumbnail, a message with a link preview, and a mention of `member1` (which gives Activity and Later items to `member1`). Every piece carries a canary: a word that exists nowhere else (R13). `world.fresh(shape)` makes another conversation of the same shape, with the same people and content, for a destructive case. Check: a test of the world lists every conversation and every canary and reads them back as their members.
- R6. Signed out, on every route that is not `public`. For each of: no cookie; a cookie that was never issued; the cookie of a session that was ended by `DELETE /api/v1/auth/session`; a request whose cookie belongs to a session ended by the sign-out of all other devices; the answer is 401 with the code `unauthenticated` (no cookie, unknown cookie) or `session_ended` (an ended one), and the same error body for every route. The cookie of `gone1` gets 401 `account_deactivated`. The request is a valid request of the entry (R1), so the refusal is the session check and not a 400; a foreign `Origin` and a wrong media type are not tried here (TOKI-022 R45, R46). For the socket route `GET /ws`, the upgrade completes and the server closes the connection with code 4401 and the reason of the REST answer, with no `ready` frame and no event (TOKI-038 R3). Check: the cases of Table B, class by class; the state check of R15 after each.
- R7. Public routes. For each `public` entry, a request with no session does not answer 401, and the answer of a conversation-less route holds none of the canaries of R5. For the sign-in routes the cases are the ones of TOKI-022 and TOKI-097 for their own rules; this ticket adds only that the entry exists, that the reason is given, and that nothing a conversation holds is in the answer. Check: the `public` cases of Table B.
- R8. Admin requests. For each `admin` entry, `member1` and `member2` get 403 `forbidden` for a valid request, for a request with an invalid body or query, for an id that does not exist and for an id of another person: never a 400, 404 or 500 (D-090, TOKI-024 R1 step 2, TOKI-027 R10). `POST /api/v1/channels` is one of these entries: a Member gets 403 whatever the body (D-084), no channel is created and no event is recorded. Each of these entries also has its `control`: `admin1` succeeds with the same request, so the 403 is the role and not a broken request. Check: Table B, class `admin`, with the control.
- R9. Hidden conversations. For each `conversation` entry, `member2`, `admin2` and `left1` (after leaving `secret`) make the valid request of the entry against `secret`, the archived private channel, the direct message and the group. The answer is 404 `not_found`, and its status, its code and its whole body are equal, byte for byte, to the answer for a conversation id that does not exist, made by the same person to the same route (D-051, D-047, D-131, BR-10). An Admin gets nothing more than a Member (D-047). The answer holds no name, topic, description, member or count of the hidden conversation. Check: the byte comparison; the `control` of the entry (a member of `secret`) succeeds with the same request.
- R10. A channel that was not joined. For each `conversation` entry, `member2` and `admin2` make the valid request against `open`. The answer is the one the entry names in `open` (R1, Table B), and the entry may name only a status that a merged spec gives: 403 `forbidden` for every route that needs membership, the messages of the channel, its replies, its pins, its search and its members first among them (D-116, TOKI-037 R2); 200 with the summary only for the detail route (TOKI-029 R4); the join route succeeds for a person who may join. In no answer is there a message, a reply, a pin, a file or a member list of `open` (the canaries of R13). `left1` gets, for `secret`, what a stranger gets (R9): leaving ends access (D-116, TOKI-029). A person who joins `open` then reads the whole history. Check: the table of answers, one row for each entry, and the history read after the join.
- R11. Admin without membership. `admin2` against `open`, `secret` and the group: the delete of another person's message, the removal of a member, the archive and the restore, the pin, the edit of the details and the add of people are refused as in R9 and R10, and the state check of R15 shows no message deleted, no member removed and no channel archived (D-047, TOKI-027 R7, R9). The same request by `admin1`, who is a member, succeeds. Check: the six requests, each with its control.
- R12. Another person's thing. An `owned` entry is a route that takes the id of something a person owns (a file, an Activity item, a Later row by message id, a draft place, a session id, the device of a session). `member2` makes the valid request with an id owned by `member1`; the answer is status, code and body equal to the answer for an id that does not exist, and the row of `member1` is as it was (D-131, TOKI-058 R12, TOKI-065 R19, TOKI-067 R4, TOKI-026 R7). A file or a draft place that belongs to a conversation `member2` cannot read answers as R9 says. Check: the equality, the row read back as `member1`, the control as `member1`.
- R13. The canary scan. Every canary of the fixture (R5) is a unique string of lower-case letters that no other text of the fixture contains (so a substring found in an answer is a leak and nothing else). A canary exists for the text of each message and reply, the name, topic and description of `secret`, the group and the archived channel, the name of each file, the title of each link preview and the text of each mention. For every `GET` entry, and for every response of `POST` that carries data, each outsider of the hidden content (R9, R10) makes the valid request, and the body, the headers and, for the socket, every frame must contain no canary and no id of a conversation, message or file of the hidden content. `open` hides its messages, replies, pins and files and not its name and topic (F29, D-116): the canary of `open`'s name is allowed in `GET /api/v1/channels`, `GET /api/v1/channels/:id` and `GET /api/v1/search` and in no other answer. Check: the scan reads the real answers; a test of the scan feeds it a body that holds a canary and expects the failure, so a scan that reads nothing cannot pass.
- R14. Search, file lists, direct links, jumps and the stream. The scan of R13 is run with these requests too, for each outsider: `GET /api/v1/search` with each canary word, with the name of `secret`, and with each `kind`; `GET /api/v1/conversations/:id/search` on every hidden conversation (R9, R10); `GET /api/v1/shared-items` with each `kind`, with the word of a hidden file name and with `conversationId` of each hidden conversation (200 with no item, TOKI-063 R2); `GET /api/v1/files/:id/download` and `GET /api/v1/files/:id/thumbnail` for the files of every hidden conversation, a removed file, an unsent file of `member1` and an unknown id (404 `not_found`, one body for all, TOKI-058 R12, TOKI-060); `GET /api/v1/conversations/:id/messages` with `before`, `after` and `around` a message of a hidden conversation (R9, R10); `GET /api/v1/activity`, `GET /api/v1/later`, `GET /api/v1/bootstrap`, `GET /api/v1/unread`, `GET /api/v1/drafts` and `GET /api/v1/events?after=0`; and, for the socket, a connection of the outsider that is open while `member1` posts, replies, reacts and pins in the hidden conversations (the audience rule of TOKI-038). The people found are the ones the Members may see; a deactivated person is not listed (TOKI-070 R4). Check: each request runs for `member2`, `admin2` and `left1`; the same request for `member1` finds the canaries (a control, so the scan is not passing on an empty fixture).
- R15. Nothing changes and nothing is sent. After every refused case the runner reads a watch set and compares it with the set read before: the row counts of `messages`, `conversation_members`, `reactions`, `pins`, `files`, `attachments`, `activity_items`, `later_items`, `drafts`, `devices`, `sessions` and `events`, the highest event number, the columns `archived`, `topic`, `description`, `role` and `status` of the people and conversations of the world, and the calls recorded by the fake mail layer, the fake storage client and the push sender. All are equal (R8 to R12). Check: the comparison after each case; a test makes a change on purpose through a route that is not refused and expects the comparison to see it.
- R16. Controls. Each refused case is paired with a control: the same request made by the person named in the entry's `control`, which must answer 2xx. A control that fails fails the case, so a refusal can never come from a request that is wrong for another reason. A destructive request is made against a fresh target (`world.fresh`, R5) for each case. Check: a test makes an entry whose request is invalid and expects the control to fail.
- R17. Real setup, no real time. The test file is `apps/server/tests/access/access.db.test.ts`, in the database project of `vitest.db.config.ts`, so they run one at a time against the throwaway test database and are skipped by nothing (TOKI-008 R3, R5, R6, R20). Time moves only through the test clock; no test sleeps, waits on a timer or reads the system time (TOKI-008 R19). The suite sends no mail, makes no network call and uses no real storage or push service. `pnpm test` runs it and CI runs `pnpm test`, so a pull request that adds a route without an entry is red (R3). Check: run `pnpm test`; the ledger test (R4) passes; run it once with one entry removed and see the red run.
- R18. One owner for an entry. A ticket that adds a route adds its entry in the same pull request; the entry names the spec requirement that gives the route its rule (`source`). The pull request template and the definition of done already ask for tests, so this ticket adds one line to `docs/definition-of-done.md`: "A new route has an entry in `apps/server/tests/access/entries/`." Check: the line is in the file; the coverage test is the proof for the code.

## Design
### Why a registry checked against the route table
A hand-written list of "routes to test" rots: nobody notices a route that is not in it. The routes the application registers are the only list that cannot be forgotten, so the suite reads it (R2) and demands one entry for each route (R3). An entry is the one thing a human must write; the cases come from its class (Table B), so an entry cannot lower the bar.
Decided in this spec: the route table comes from an `onRoute` hook on the application built for the test, not from a printed route tree and not from the OpenAPI-like list in this spec. Reason: `onRoute` gives the method, the exact url and `config.public` of every route as the server will serve it, including routes that a module registers conditionally. The `onRoute` hook already exists in `apps/server/src/app.ts` for the `/api/v1` rule, so the mechanism is known to work before `ready`. The cost: the test application must switch on every option that registers a route, and a ticket that adds such an option adds it to the test application too (R2); the floor of R2 and the count in the failure message make a forgotten option visible.

### Table A. The classes of endpoint
| Class | What it is | Examples |
| :---- | :---- | :---- |
| `public` | No session needed, with a reason | `GET /healthz`, `POST /api/v1/auth/codes`, `POST /api/v1/auth/sessions`, `POST /api/v1/auth/emergency-sessions`, `DELETE /api/v1/auth/session`, `GET /api/v1/auth/workspace`, `POST /api/v1/invitations/lookup`, `/codes`, `/sessions` |
| `signed-in` | A session; every person has it; it works on the person's own data | `GET /api/v1/bootstrap`, `GET /api/v1/unread`, `GET /api/v1/activity`, `GET /api/v1/later`, `GET /api/v1/quiet`, `PATCH /api/v1/notifications/preferences`, `PUT /api/v1/members/me/status`, `GET /api/v1/search`, `GET /api/v1/shared-items`, `GET /api/v1/channels` (browse), `POST /api/v1/direct-conversations`, `GET /ws`, `POST /api/v1/files` |
| `admin` | A session and the role Admin | `GET /api/v1/members`, `POST /api/v1/invitations`, `POST /api/v1/invitations/:invitationId/resend` and `/revoke`, `POST /api/v1/members/:userId/role`, `/deactivate`, `/reactivate`, `GET /api/v1/storage/disk`, `POST /api/v1/channels` |
| `conversation` | A session and a conversation id in the path or the body | everything under `/api/v1/channels/:id`, `/api/v1/conversations/:id` (messages, replies, reactions, pins, read, search, settings, link previews), `GET /api/v1/quiet/dm/:conversationId`, `PUT` and `DELETE /api/v1/drafts/:kind/:id` |
| `owned` | A session and an id of something a person owns | `GET /api/v1/files/:id/download`, `GET /api/v1/files/:id/thumbnail`, `POST /api/v1/files/:id/complete`, `DELETE /api/v1/files/:id`, `POST /api/v1/activity/:id/done`, `/reopen`, `/snooze`, `/unsnooze`, `PATCH` and `DELETE /api/v1/later/:messageId`, `DELETE /api/v1/auth/sessions/:sessionId` |

This table is the starting point from the specs on `main`; the registry is the truth once built, and the coverage check (R3) says when the two differ. A route with both a conversation and an owned id (a file in a conversation) is `owned` and also gets the conversation cases through its `target` field (R3 e).

### Table B. The cases of each class
Persons: S0 no session; S1 an ended session; S2 `gone1`; M `member2`; A `admin2`; L `left1`; C the control of the entry.
| Class | Case | Request by | Expected | Requirement |
| :---- | :---- | :---- | :---- | :---- |
| `public` | reachable | S0 | not 401; no canary in the body | R7 |
| `signed-in`, `admin`, `conversation`, `owned` | no session | S0, with a never-issued cookie | 401 `unauthenticated`, one body | R6 |
| the same | ended session | S1 | 401 `session_ended` | R6 |
| the same | deactivated | S2 | 401 `account_deactivated` | R6 |
| `signed-in` | control | C | 2xx | R16 |
| `signed-in` with `ownedBy` | another person's id | M | equal to the unknown id's answer; the row unchanged | R12 |
| `admin` | Member, valid request | M | 403 `forbidden` | R8 |
| `admin` | Member, invalid body, unknown id, another's id | M | 403 `forbidden` | R8 |
| `admin` | control | C (an Admin) | 2xx | R8, R16 |
| `conversation` | hidden: `secret`, archived private, direct message, group | M, A, L | 404 `not_found`, body equal to the unknown id's | R9 |
| `conversation` | not joined: `open` | M, A | the entry's `open` answer (403 or the summary) | R10 |
| `conversation` | admin without membership | A | as R9 and R10 | R11 |
| `conversation` | control | C (a member) | 2xx | R16 |
| `owned` | another person's id | M | equal to the unknown id's | R12 |
| `owned` | an id of a hidden conversation | M, A | equal to the unknown id's | R12, R14 |
| `owned` | control | C (the owner) | 2xx | R16 |
| every class | scan | the outsiders | no canary | R13 |
| every class | state | after each refusal | the watch set is equal | R15 |

An entry's `open` field is one of `forbidden` (403 `forbidden`), `summary` (200, with no canary but the name and topic of `open`), `allowed` (the request is one a person who has not joined may make, like `join`), and a `source` (the spec requirement). The runner refuses any other value, so no entry can say 200 with content.

### What the suite compares
A refusal and the answer for a missing id are compared as `{ status, code, body }` after the request id is removed, and the headers `content-type`, `cache-control` and `www-authenticate` are compared too. A hidden conversation that answers 404 with a different message from an unknown one is a leak (it confirms that the thing exists); a test string is not compared, the whole parsed body is.

### The routes with a different shape
- The socket `GET /ws` has no status: the case reads the close code and the frames (R6, R14), through the socket helper of the gateway tests.
- A route of the Admin page that has a repeat key (`Idempotency-Key`, TOKI-024 R13) gets a fresh key for each case.
- `GET /api/v1/files/:id/download` answers 302 for a person who may open the file and 404 for everyone else; the control checks the 302 and does not follow it (TOKI-058 R12).

### Layout
```
apps/server/tests/access/
  registry.ts          accessRegistry, the entry type, the classes
  entries/<module>.ts  one file for each module that registers routes
  route-table.ts       the full application and its onRoute hook
  world.ts             people, conversations, content, canaries, fresh()
  cases.ts             Table B as code, the runner and the ledger
  scan.ts              the canary scan and its own test helpers
  access.db.test.ts    calls the groups below in order; its last `it` is the ledger test (R4)
  groups/coverage.ts   R2, R3
  groups/signed-out.ts R6, R7
  groups/roles.ts      R8, R11
  groups/hidden.ts     R9, R10, R12
  groups/leaks.ts      R13, R14
  groups/state.ts      R15, R16
```
The ledger test must run after the others. Decided in this spec: one test file, `access.db.test.ts`, calls the groups in order and the ledger test is its last `it`. Reason: Vitest does not promise the order of files, and the ledger must see every case.

## Testing
- Each requirement has the Check it names. The suite is its own test, and these tests prove it is not passing for nothing: the failing registry (R3), the scan fed a canary (R13), the watch set fed a change (R15), the control fed a broken request (R16), and the floor of the route table (R2).
- The fixture is built through the routes, so a change of the real behaviour changes the fixture and not a copy of it.
- Fake data only: addresses at `example.com`, words made for the canaries, no real person.
- No test depends on the number of routes: a new route is a new entry, never a changed number.
- Before the build starts, the build lists the specs of the Depends-on list whose routes are not on `main` (concern 4); a route that is missing then is a blocker of the ticket, and the entry is not written against a spec alone.

## Data safety
- The canaries are words made for the tests and exist only in the test database, which the guard of TOKI-008 R5 allows only on a loopback host with a name ending in `_test`.
- A failure message names the route and the case and never prints a body, a cookie or a session secret.

## How each constraint in the intent is met
| Constraint | Met by |
| :---- | :---- |
| Signed-out requests refused on every route that is not public (TOKI-022 R24, D-125) | R6, R7, R3 (d) |
| A Member is refused on Admin requests and on creating a channel (D-090, D-084) | R8 |
| An Admin has no extra reach into private channels or direct messages (D-047) | R9, R11 |
| No content of a channel not joined; no preview (D-116) | R10, R13 |
| No access answered like not found (BR-10, D-131, D-051) | R9, R12, R14; "What the suite compares" |
| The same through search, file lists, direct links and the live stream (AC-083, AC-029, TS-129, TS-045) | R14 |
| A new endpoint without an access test fails a check | R2, R3, R4, R17, R18; "Why a registry checked against the route table" |
| Real PostgreSQL and the controllable clock of TOKI-008, no real timers | R5, R17 |
| Server modules reach each other's data through public interfaces only | The suite reads through HTTP and through the shared test helpers; it imports no module internals except `buildApp` |
| Milestone M6, size M, needs TOKI-070 and the data routes | Scope; concern 4 |

## Open questions from the intent
- How does a new endpoint without an access test fail a check? Answered: the route table of the built application is compared with the registry (R2, R3, concern 2).
- A person who has not joined a public channel: is the answer 403 or 404? Answered: 403 for the routes that need membership, as TOKI-037 R2 decided, and 404 for private channels, direct messages and ids that do not exist (concern 1).
- Does a group direct message that has no message yet count as hidden from the other members? Not answered. Carried forward as concern 5.
- What does a Later row show for a message the person can no longer read? Not answered. Carried forward as concern 6.
- Do the tests call the routes over HTTP or call the permission functions? Answered: over HTTP, on the real application and the real database (R5, R17, concern 8).
- Does the suite cover Guests? Answered: no, phase 5 (concern 3).
- What happens to routes of tickets that are not built when this ticket starts? Answered: the ticket does not start until they are built (concern 4).

## Areas of concern
1. 403 or 404 for a public channel that was not joined. Decided in this spec: the suite pins what the merged specs say: 403 `forbidden` for a request that needs membership (TOKI-037 R2, TOKI-047, TOKI-048, TOKI-045), the summary for the detail route (TOKI-029 R4), and 404 with one body for a private channel, a direct message, a group, a file and an id that does not exist. Reason: a public channel is listed in Browse and found by search (F29), so its existence is not a secret; D-116 forbids the content, and D-131 maps 403 and 404 to one page on the screen, so a person sees the same page for both. The plan line says "answered like not found"; that holds where existence is secret. If the owner wants 404 for a public channel too, it is a change in each route's own spec and in the `open` field of the entries (R10), not in this suite's design. Owner: Thanh Truong.
2. Where the list of endpoints comes from. Decided in this spec: the application's own routes, read by an `onRoute` hook (Design, "Why a registry checked against the route table"). Reason: it cannot be forgotten and it is exact; the alternatives (a printed route tree, a list in a spec, a scan of the source for `scope.get(`) all miss conditional or generated routes. Owner: Thanh Truong.
3. Guests. Decided in this spec: not in phase 1. Reason: D-090 and D-152 leave Guest to phase 5 and D-050 gives it its own suite; the actor list of the world and Table A take one more row then. Owner: Thanh Truong.
4. Routes of tickets not built when this ticket starts. Decided in this spec: the ticket starts when every route listed under its dependencies (070, 069, 071, 072, 063, 008, 037, 045, 046, 048, the channel and member routes, 058, 062, 061, 065, 067, 102, 074, 076, 068) is on `main`; the entry for a route that is not there fails R3 (b), and the entry is never written for a route that does not exist. Reason: an entry for a route that is not built would be a guess about its url and its answer. If one is late, the ticket waits or the route is named a blocker. Owner: Thanh Truong.
5. Whether a new group stays out of the other people's lists until its first message. Not decided: it is concern 2 of TOKI-037 and F25 names the direct message only. The suite pins the answer of a group that has a message (R5 builds the group with one) and does not pin the case of a group with no message, where the answer to the other members is open. If the owner decides that it is hidden, one case is added to R9. Owner: Thanh Truong.
6. What Later shows when the person can no longer read the conversation of a saved message. Not decided: it is concern 2 of TOKI-067. The suite checks only that the answer holds no canary and no name of the conversation (R13, R14); the shape of the replacement row is not checked until the owner decides. Owner: Thanh Truong.
7. Who writes an entry. Decided in this spec: the ticket that adds a route, in the same pull request (R18). Reason: the author knows the rule the route must give and the spec requirement that says so; the coverage check makes it impossible to skip. This suite does not write entries for routes of tickets built after it. Owner: Thanh Truong.
8. Over HTTP, not over the permission functions. Decided in this spec: the suite calls the routes of the built application. Reason: the permission functions are already proved by their matrix (TOKI-027 R14), and the risk this ticket covers is a route that forgets to call them or calls them in the wrong order. Owner: Thanh Truong.
