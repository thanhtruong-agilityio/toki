# Access-control test suite design

Date: 2026-11-26 · Status: draft for review
Intent: docs/intents/access-control-tests.md (Thanh Truong)
Ticket: TOKI-088

## Goal
The owner needs proof, for every endpoint of the server, that a person without access is refused, and that the proof cannot rot: a new endpoint must not be able to join the application without a refusal test. This ticket builds one test suite, driven by a registry of endpoints that is checked against the routes the application really registers.
The suite looks at the server from the side of the person who must be refused: signed out, a Member asking for Admin things, an Admin outside a private channel or a direct message, a person who has not joined a public channel, and a person who reaches the same data through search, a file list, a file address, a jump to a message or the live stream.
This ticket adds tests and one test option in `buildApp` (R2) that lets the suite see every route. It changes no route and no permission function.

## Scope
- In:
  - The route table of the real application, read while it is built through one test option of `buildApp` (R2), and the registry of endpoints with one entry for each route (R1, R3).
  - The check that fails when a route has no entry, when an entry has no route, or when an entry says less than its route needs (R3).
  - The fixture of people, conversations and hidden content (R5) and the cases that every class of endpoint must pass (R4, R6 to R17).
  - The scan that looks for hidden content in every answer (R14, R15).
  - The ledger that proves every required case ran (R4, R18).
- Out (not now):
  - The tests of each feature's own rules (validation, locks, limits, repeats). They stay with the ticket that owns the route. This suite adds the refusal side for all of them and does not copy those cases.
  - Guests. Phase 5 adds the role, its rows and the guest suite of D-050; the registry is built so that one more actor class is one more row of Table A (concern 3).
  - The browser flows with a signed-in person at desktop and phone widths: TOKI-090. The shared "no access" page and what it says: TOKI-082.
  - The wording and looks of any refusal on screen. The suite checks status, code and body of the server only.
  - The headers, cookies, rate limits and dependencies review: TOKI-091.
  - Speed. The suite has no time limit of its own; the measurement of the six targets is TOKI-089.
  - Any change to `docs/definition-of-done.md` or the pull request template (concern 7).

## Requirements
- R1. The registry. `apps/server/tests/access/registry.ts` exports `accessRegistry`, a list of entries, built from one file for each module in `apps/server/tests/access/entries/` (`auth.ts`, `members.ts`, `channels.ts`, `direct.ts`, `bootstrap.ts`, `messages.ts`, `threads.ts`, `reactions.ts`, `pins.ts`, `read.ts`, `files.ts`, `link-previews.ts`, `search.ts`, `shared-items.ts`, `activity.ts`, `later.ts`, `quiet.ts`, `notifications.ts`, `drafts.ts`, `status.ts`, `presence.ts`, `storage.ts`, `realtime.ts`; Table D names the ticket that owns the routes of each file; a ticket that adds a module adds its file and one line in `registry.ts`). An entry has: (a) `route`: the method and the url exactly as Fastify registers it, for example `POST /api/v1/channels/:id/join`; (b) `access`: one of `public`, `signed-in`, `admin`, `conversation`, `owned` (Table A); (c) `request(world, target, variant?)`: returns the url, the body and the headers of a valid request for that target (the `variant` of an `admin` entry is `valid`, `invalid`, `unknown-id` or `other-id`, R8); (d) `ids`: every id the request carries, in the path, the query or the body, as `{ in, name, of }` where `of` is `conversation`, `message`, `file`, `user`, `draft`, `session`, `activity`, `invitation` or `other`; `ids: []` says there is none. The field is required on every entry that is not `public`, so a route that takes an id in a body, like `POST /api/v1/later` (`conversationId` and `messageId`, TOKI-067 R3), must say so; (e) `control`: who must succeed with that request, a person of the world, and `controlTarget` when the control is not made against the target of the case (the control of `POST /api/v1/channels/:id/join` is `member2` against a fresh `open`, because a member of `secret` gets 404 `private_channel` from join, TOKI-029 R2); (f) `destructive`: true when a success changes the target, so each case gets a fresh one (R5); (g) `returnsData`: true when the answer or a frame carries data of conversations (R14); (h) `source`: the spec requirement that gives the route its rule; (i) and the fields of its class: `open` for a `conversation` entry (R10), `adminOnly` for a `conversation` entry whose action a Member of the conversation may not do (R11), `ownedBy` for an `owned` entry or any entry with an id of something a person owns (R13), and `target` for a route that takes the id of a conversation, a message or a file in a body or a query, or in a path whose id is owned (R3 e). A `public` entry has `reason`, a sentence that says why no session is needed, and a source id. Check: a unit test of the registry shape builds every entry's request once and fails on an entry with a missing field (`ids` included), a duplicate `route`, a `public` entry with no `reason`, or a request that carries a key ending in `Id` or `Ids` that `ids` does not list.
- R2. The route table. `apps/server/tests/access/route-table.ts` builds the full application once, with every option that registers a route switched on (the database, the gateway, presence, the storage client, the push key, and every option a later ticket adds for the same purpose), and returns one record for each route: method, url as registered, and `config.public`. The records come from a test option of `buildApp`: `BuildAppOptions` gains `routeObserver?: (route: RouteOptions) => void`, commented "Only a test passes it" like `joinHooks` and `bootstrapDeps`, and `buildApp` installs it as an `onRoute` hook before anything else is registered. This is needed because `buildApp` registers `GET /healthz` (`registerHealth(app)`) before it returns, and `GET /ws` the same way (TOKI-038 R1); a hook added to the application after `buildApp` returns sees only the routes loaded later, so it would miss both and R3 could not hold. Owner of the edit: this ticket, in its own pull request: about five lines in `apps/server/src/app.ts` and one test that the observer sees `/healthz`; no route and no permission function changes. Not chosen: reading the two root-level routes with `app.hasRoute`, which finds only routes someone already knows, so a new root-level route (the hook of `app.ts` already admits `/healthz`, and TOKI-038 R1 adds `/ws`) would escape the check. A route registered for several methods arrives with `method` as an array and is split into one record for each method. The automatic `HEAD` route that Fastify adds for a `GET` is left out; every other method counts. The table has a floor: `apps/server/tests/access/floor.ts` lists the routes of the code on `main` when this spec was written (the 34 of "The floor"), and the test fails unless the table holds every one, so an observer that sees nothing cannot make the check pass. The floor is a second, hand-written list, kept on purpose small: a route that is renamed or removed edits it in the same pull request, and a route that is added does not need to. Check: the floor test, a test that builds the application twice and gets the same table, and the test that the observer sees `/healthz` and `/ws`.
- R3. The coverage check. A test compares the route table (R2) with `accessRegistry` (R1) and fails on each of these, naming the route and the file to edit: (a) a registered route with no entry: "POST /api/v1/x has no access entry; add one in apps/server/tests/access/entries/<module>.ts"; (b) an entry whose route is not registered; (c) two entries for one route; (d) a route registered with `config.public` true whose entry is not `public`, and a `public` entry whose route needs a session; (e) a url with a path parameter that the entry's `ids` does not list, and an entry that has an id of a conversation, a message or a file, or of something a person owns, in `ids` and has neither `ownedBy` nor `target` (a route that takes an id must say whose id and be tried with someone else's, R13; R1 makes `ids` required, so a route with an id in the body cannot be left as a bare `signed-in`); (f) a url under `/channels/:id` or `/conversations/:id` whose entry is not `conversation`. There is no list of exempt routes: `/healthz` and the sign-in routes are `public` entries with a reason like any other. A limit that the suite states and does not hide: the routes of `main` validate the body inside the handler, so the hook cannot read which keys a body takes; `ids` is written by the author of the entry and checked only against the entry's own valid request (R1) and against the url. Check: the coverage test runs against the real table, and a second test feeds it a table with one invented route, one removed route, one route with the wrong class and one route whose entry has a body id with no `target`, and expects the four failures with these messages.
- R4. Cases follow the class. `apps/server/tests/access/cases.ts` holds the required cases of each class (Table B). The runner makes them from the entry; an entry cannot remove or soften a case. A case is a request, the person who makes it, the expected status and code, and a state check (R16). The runner writes one line to the ledger for each case it ran (`route`, `case`, `status`). The ledger test (R18) fails unless the ledger holds exactly the expected lines. The expected number of cases does not come from `cases.ts`: the test holds the number of cases of each class as constants copied from the "Cases" column of Table B (a case added or dropped in `cases.ts` changes the ledger and not the constants, so the test fails until both are edited on purpose), multiplies them by the entries of the registry and its flags (`adminOnly`, `ownedBy`, `target`, `returnsData`), and compares that total, and the count of lines for each route, with the ledger. A line that appears twice fails too. The suite contains no `it.skip`, `it.todo`, `it.only`, `describe.skip` or `test.skip`: a source test over `apps/server/tests/access/` fails on one.
- R5. The fixture. `apps/server/tests/access/world.ts` builds one world once for each test file, on the real database, through the real routes and the helpers of the sign-in and channel tests (`createHarness`, `person`, `send`), the fake mail layer, the fake storage client and the test clock of TOKI-008. People: `admin1` (Admin), `member1` (Member), `admin2` (Admin, in no private conversation), `member2` (Member, in none), `left1` (a Member who is in `secret` and leaves it, and stays a member of the group), `gone1` (a Member whose account is deactivated after signing in, so its cookie is still a real one). Everyone is a member of `#general`. Conversations: `joined`, a public channel `admin1`, `member1` and `member2` joined; `open`, a public channel of `admin1` and `member1` that `member2` and `admin2` have not joined; `secret`, a private channel of `admin1`, `member1` and `left1`; a direct message of `member1` and `admin1`; a group direct message of `member1`, `admin1` and `left1`; an archived private channel of `admin1` and `member1`. The archived channel is private, because the restore of an archived public channel by an Admin who is not a member succeeds by design (TOKI-029 R14) and is not a refusal. Order: the world writes one message in `secret` while `left1` is a member, then `left1` leaves `secret` (`POST /channels/:id/leave`), and then it writes all the other content of `secret`; so what `left1` could once read, and what came after, are both hidden from `left1` (D-116), and the scan can tell a leak from what `left1` saw before. Content in each of `secret`, the direct message, the group, `open` and the archived channel: a message by `admin1`, a message by `admin1` that mentions `@member1` (which makes the Activity item of TOKI-065 for `member1` through the message route), a thread reply, a pin, a reaction, a file with a thumbnail, and a message with a link preview; `joined` holds one message by `admin1` (the target of the delete of R11). `member1` then saves one message of each of these conversations through `POST /api/v1/later` (TOKI-067), which makes the Later rows; a mention does not make one. Every piece carries a canary and every conversation, message and file has an id canary (R14). `world.fresh(shape)` makes another conversation of the same shape, with the same people and content, for a destructive case. Check: a test of the world lists every conversation and every canary and reads them back as their members.
- R6. Signed out, on every route that is not `public`. For each of: no cookie; a cookie that was never issued; the cookie of a session that was ended by `DELETE /api/v1/auth/session`; the cookie of a session ended by the sign-out of all other devices; the answer is 401 with the code `unauthenticated` (no cookie, unknown cookie) or `session_ended` (an ended one), and the same error body for every route. The cookie of `gone1` gets 401 `account_deactivated`. That is 5 cases for each such entry. The request is a valid request of the entry (R1), so the refusal is the session check and not a 400; a foreign `Origin` and a wrong media type are not tried here (TOKI-022 R45, R46). For the socket route `GET /ws`, the upgrade completes and the server closes the connection with code 4401 and the reason of the REST answer, with no `ready` frame and no event (TOKI-038 R3). Check: the cases of Table B, class by class; the state check of R16 after each.
- R7. Public routes. For each `public` entry, a request with no session does not answer 401, and the answer of a conversation-less route holds none of the canaries of R5. For the sign-in routes the cases are the ones of TOKI-022 and TOKI-097 for their own rules; this ticket adds only that the entry exists, that the reason is given, and that nothing a conversation holds is in the answer. Check: the `public` cases of Table B.
- R8. Admin requests. For each `admin` entry, `member1` and `member2` get 403 `forbidden` for each of four variants of the request: a valid one, one with an invalid body or query, one with an id that does not exist and one with an id of another person (when the route has no such part, the entry returns the valid request for that variant and the 403 must still hold): never a 400, 404 or 500 (D-090, TOKI-024 R1 step 2, TOKI-027 R10). `POST /api/v1/channels` is one of these entries: a Member gets 403 whatever the body (D-084), no channel is created and no event is recorded. Each of these entries also has its `control`: `admin1` succeeds with the same request, so the 403 is the role and not a broken request. Check: Table B, class `admin`, with the control.
- R9. Hidden conversations. For each `conversation` entry, `member2` and `admin2` make the valid request of the entry against `secret`, the archived private channel, the direct message and the group; `left1` makes it against `secret`, the archived private channel and the direct message. `left1` is not tried against the group: `left1` is a member of it (R5) and gets what a member gets. The answer is 404 `not_found`, and its status, its code and its whole body are equal to the answer for a conversation id that does not exist, made by the same person to the same route (the rule is BR-09 and BR-10, as the merged specs apply it: TOKI-029 R1 step 3, TOKI-037 R1 step 2, TOKI-048 R4; the comparison is "What the suite compares"). An Admin gets nothing more than a Member (D-047). The answer holds no name, topic, description, member or count of the hidden conversation. A route under `/channels/:id` answers 404 for a direct message and a group to everyone, a member included (TOKI-029 R1 step 3), so the control of such an entry is always asked against `secret` or against `controlTarget`. Check: the equality; the `control` of the entry (a member of `secret`, or the person and target named by `controlTarget`) succeeds with the same request.
- R10. A channel that was not joined. For each `conversation` entry, `member2` and `admin2` make the valid request against `open`. The answer is the one the entry names in `open` (Table B), and the entry may name only a value that a merged spec gives: (a) `forbidden`: 403 `forbidden`, for every route that needs membership: the messages and the history of the channel (TOKI-037 R2), its replies (TOKI-045), its pins (TOKI-048 R4), the reactions (TOKI-046 R4), the read pointer (TOKI-053 R3), the conversation search (TOKI-072 R1), its members, the edit of its details, the add and the removal of people and the archive (TOKI-029 R2, R8, R9, R11, R13, R14), the settings (TOKI-029 R22), the draft place (TOKI-051 R6) and the save to Later with its `conversationId` (TOKI-067 R3). The status is the one of the merged specs; the log gives none (concern 1); (b) `summary`: 200 with the summary only, no description, creator or message, for the detail route (TOKI-029 R7); (c) `allowed`: the request is one a person who has not joined may make: `join` (TOKI-029 R10); (d) `no-op`: 200 with `changed` false and nothing written: `leave` by a person who is not a member of a public channel (TOKI-029 R12), and `restore` of a channel that is not archived (TOKI-029 R14); (e) `not-found`: 404 `not_found`, equal to the unknown id's answer: the files of `open`, which the file routes answer as a file that is not there (TOKI-058 R12, TOKI-060 R8). The runner refuses any other value, so no entry can say 200 with content. In no answer is there a message, a reply, a pin, a file or a member list of `open` (the canaries of R14). `left1` gets, for `secret`, what a stranger gets (R9): leaving ends access (D-116, TOKI-029 R12). A person who joins `open` then reads the whole history. Check: the table of answers, one row for each entry, and the history read after the join.
- R11. A Member inside a conversation, on an admin-only action. For each `conversation` entry with `adminOnly` true (the archive and the restore of a channel, TOKI-029 R14; the removal of a member, TOKI-029 R13; the delete of another person's message, TOKI-047 R6), `member1`, a Member who is a member of `secret` and of `joined`, makes the request against each of them and gets 403 `forbidden` (the role comes before the state of the channel in the order of TOKI-027 R3, so the restore is refused although `secret` is not archived). The delete targets a message of `admin1`. The state check shows no channel archived or restored, no member removed and no message deleted. The control is `admin1`, who is a member and an Admin, on a fresh target. This is the "Member on Admin requests" of the intent for the case where the Member is inside the conversation; R8 is the case of the page. Check: Table B, the `adminOnly` rows, with the control.
- R12. Admin without membership. `admin2` is an Admin and is in none of these. The seven requests of the table are made by `admin2`; the answer is the one in the table, the state check of R16 shows no message deleted, no member removed, no channel archived and no member row added, and the same request by `admin1`, who is a member, succeeds (D-047, TOKI-029 R13, R14, TOKI-047 R6, TOKI-048 R4).

  | Request | `secret` | the group | `open` |
  | :---- | :---- | :---- | :---- |
  | delete another person's message | 404 | 404 | 403 |
  | remove a member | 404 | 404 | 403 |
  | archive | 404 | 404 | 403 |
  | restore | 404 (the archived private channel) | not asked | 200 `changed` false, no member row (`open` is not archived, TOKI-029 R14) |
  | pin | 404 | 404 | 403 |
  | edit the details | 404 | 404 | 403 |
  | add people | 404 | 404 | 403 |

  The group row for the requests of `/channels/:id` is 404 for everyone (TOKI-029 R1 step 3), so the control of those is made against `secret`. Check: the seven requests, each with its control.
- R13. Another person's thing. An `owned` entry is a route that takes the id of something a person owns (a file, an Activity item, a Later row by message id, a draft place, a session id, the device of a session). `member2` makes the valid request with an id owned by `member1`; the answer is status, code and body equal to the answer for an id that does not exist, and the row of `member1` is as it was (TOKI-058 R12, TOKI-065 R19, TOKI-067 R4, TOKI-026 R7). A file that belongs to a conversation `member2` cannot read answers 404 `not_found` as the unknown id does, a file of `open` included (TOKI-058 R12; not the 403 of R10). A draft place of a conversation `member2` cannot read answers as R9 and R10 say (TOKI-051 R6). Check: the equality, the row read back as `member1`, the control as `member1`.
- R14. The canary scan. There are two kinds of canary. A text canary is a unique string of lower-case letters that no other text of the fixture contains (so a substring found in an answer is a leak and nothing else): the text of each message, reply and mention, the name, topic and description of `secret`, the group and the archived channel, the name of each file and the title of each link preview. An id canary is the id of a conversation, a message or a file of the hidden content, matched as a whole string. For every entry with `returnsData` (every `GET`, and a `POST` or `PUT` whose answer carries data), each outsider of the hidden content (R9, R10) makes the valid request, and the body (keys and values), the headers and, for the socket, every frame must contain no canary of the content hidden from that person. What is hidden from whom: from `member2` and `admin2`, the content of `secret`, the archived channel, the direct message, the group and, except its name and topic, `open`; from `left1`, the content of `secret` (all of it, before the leave and after, D-116), the archived channel, the direct message and `open`, and not the group, whose content `left1` reads as a member. The only places where a hidden thing may show are in Table C; everything else is a hit. The id that the outsider put in the request is the request's own and is dealt with by the comparison of "What the suite compares"; the id of the request (`X-Request-Id`) is not an id of the world and is not scanned. Check: the scan reads the real answers; a test of the scan feeds it a body that holds a canary and expects the failure, and feeds it each allowed place of Table C and expects a pass, so a scan that reads nothing, or that fails a correct server, cannot pass.
- R15. Search, file lists, direct links, jumps and the stream. The scan of R14 is run with these requests too, for each outsider: `GET /api/v1/search` with each canary word, with the name of `secret`, and with each `kind` (it never answers 403 or 404 about data and shows only what the person may read, TOKI-070 R11); `GET /api/v1/conversations/:id/search` on every hidden conversation (R9, R10); `GET /api/v1/shared-items` with each `kind`, with the word of a hidden file name and with `conversationId` of each hidden conversation (200 with no item, TOKI-063 R2); `GET /api/v1/files/:id/download` and `GET /api/v1/files/:id/thumbnail` for the files of every hidden conversation and of `open`, a removed file, an unsent file of `member1` and an unknown id (404 `not_found`, one body for all, TOKI-058 R12, TOKI-060 R8); `GET /api/v1/conversations/:id/messages` with `before`, `after` and `around` a message of a hidden conversation (R9, R10); `GET /api/v1/activity`, `GET /api/v1/later`, `GET /api/v1/bootstrap`, `GET /api/v1/unread`, `GET /api/v1/drafts` and `GET /api/v1/events?after=0`; and, for the socket, the case below. The people found are the ones the Members may see; a deactivated person is not listed (TOKI-070 R4). The socket case waits without a timer, by a barrier: (1) the outsider opens `GET /ws` and the test waits for its `ready` frame; (2) `member1` posts, replies, reacts and pins in each hidden conversation; (3) `member1` then posts one message in `#general`, which the outsider is allowed to see, with a text that holds no canary; (4) the test waits, through the frame helper of the gateway tests, until the event of that message reaches the outsider. The gateway delivers one connection's events once and in number order (TOKI-038 R14, R15), so every frame that was ever going to carry a hidden event has arrived before the barrier frame; the scan then reads the frames up to it. A barrier that never arrives fails the case through the helper's own frame wait, not through a sleep (R18). Check: each request runs for `member2`, `admin2` and `left1`; the same request for `member1` finds the canaries (a control, so the scan is not passing on an empty fixture); a test of the socket case with a gateway that sends a hidden event expects a hit.
- R16. Nothing changes and nothing is sent. After every refused case the runner reads a watch set and compares it with the set read before: the row counts of `messages`, `conversation_members`, `reactions`, `pins`, `files`, `attachments`, `activity_items`, `later_items`, `drafts`, `devices`, `sessions` and `events`, the highest event number, the columns `archived`, `topic`, `description`, `role` and `status` of the people and conversations of the world, and the calls recorded by the fake mail layer, the fake storage client and the push sender. All are equal (R8 to R13). A case whose expected answer is a `no-op` (R10) is compared the same way. Check: the comparison after each case; a test makes a change on purpose through a route that is not refused and expects the comparison to see it.
- R17. Controls. Each refused case is paired with a control: the same request made by the person named in the entry's `control` (against `controlTarget` when it is set), which must answer 2xx. A control that fails fails the case, so a refusal can never come from a request that is wrong for another reason. A destructive request is made against a fresh target (`world.fresh`, R5) for each case. Check: a test makes an entry whose request is invalid and expects the control to fail.
- R18. Real setup, no real time. The test file is `apps/server/tests/access/access.db.test.ts`, in the database project of `vitest.db.config.ts`, so they run one at a time against the throwaway test database and are skipped by nothing (TOKI-008 R3, R5, R6, R20). Time moves only through the test clock; no test sleeps, waits on a timer or reads the system time (TOKI-008 R19). The suite sends no mail, makes no network call and uses no real storage or push service. `pnpm test` runs it and CI runs `pnpm test`, so a pull request that adds a route without an entry is red (R3). Check: run `pnpm test`; the ledger test (R4) passes; run it once with one entry removed and see the red run.

## Design
### Why a registry checked against the route table
A hand-written list of "routes to test" rots: nobody notices a route that is not in it. The routes the application registers are the only list that cannot be forgotten, so the suite reads it (R2) and demands one entry for each route (R3). An entry is the one thing a human must write; the cases come from its class (Table B), so an entry cannot lower the bar.
Decided in this spec: the route table comes from an `onRoute` hook that `buildApp` installs first, through the test option `routeObserver` (R2), not from a hook added after `buildApp` returns, not from a printed route tree and not from the list in this spec. Reason: the hook gives the method, the exact url and `config.public` of every route as the server will serve it, including routes that a module registers conditionally, and, installed first, it sees `/healthz` and `/ws`, which `buildApp` registers itself. The cost: the test application must switch on every option that registers a route, and a ticket that adds such an option adds it to the test application too (R2); the floor of R2 and the count in the failure message make a forgotten option visible.

### Table A. The classes of endpoint
| Class | What it is | Examples |
| :---- | :---- | :---- |
| `public` | No session needed, with a reason | `GET /healthz`, `POST /api/v1/auth/codes`, `POST /api/v1/auth/sessions`, `POST /api/v1/auth/emergency-sessions`, `DELETE /api/v1/auth/session`, `GET /api/v1/auth/workspace`, `POST /api/v1/invitations/lookup`, `/codes`, `/sessions` |

### What the suite compares
A refusal and the answer for a missing id are compared as `{ status, code, body }` after the request id is removed and the id of the request, in the url or the body, is replaced by one fixed word in both, and the headers `content-type`, `cache-control` and `www-authenticate` are compared too. A hidden conversation that answers 404 with a different message from an unknown one is a leak (it confirms that the thing exists); a test string is not compared, the whole parsed body is.

## Testing
- Each requirement has the Check it names. The suite is its own test, and these tests prove it is not passing for nothing: the failing registry (R3), the scan fed a canary and fed every allowed place (R14), the socket case fed a hidden event (R15), the watch set fed a change (R16), the control fed a broken request (R17), the floor and the observer of the route table (R2), and the ledger count that comes from constants and not from the runner (R4).
- R1 to R4: the shape test, the floor test, the coverage test with its four invented failures, and the ledger test. R5: the test of the world. R6, R7: the signed-out and `public` cases. R8: Table B, class `admin`. R9, R10: the hidden and not-joined cases with their equality. R11, R12: the `adminOnly` rows and the seven requests, each with its control. R13: the owned cases. R14, R15: the scan and the socket barrier. R16, R17: the watch set and the controls. R18: `pnpm test`, and a red run with one entry removed.
- The fixture is built through the routes, so a change of the real behaviour changes the fixture and not a copy of it.
- Fake data only: addresses at `example.com`, words made for the canaries, no real person.
- No test depends on the number of routes: a new route is a new entry, never a changed number. The two hand-written lists (the floor of R2 and the case counts of R4) change only when a route is renamed or a case is changed on purpose.
- Before the build starts, the person who starts it checks that the tickets of Table D are on `main` (concern 4); a route that is missing then is a blocker of the ticket, and the entry is not written against a spec alone.

## Data safety
- The canaries are words made for the tests and exist only in the test database, which the guard of TOKI-008 R5 allows only on a loopback host with a name ending in `_test`.
- A failure message names the route and the case and never prints a body, a cookie or a session secret.

## Areas of concern
1. 403 or 404 for a public channel that was not joined. Decided in this spec: the suite pins what the merged specs say: 403 `forbidden` for a request that needs membership (TOKI-037 R2, TOKI-029 R2, TOKI-045, TOKI-046 R4, TOKI-048 R4), the summary for the detail route (TOKI-029 R7), and 404 with one body for a private channel, a direct message, a group, a file and an id that does not exist. Reason: the status is the merged specs', not the log's. D-116 forbids the content and says nothing of the status, and D-131 maps 403 and 404 to one page on the screen, so a person sees the same page for both. A public channel is listed in Browse and found by search (F29), so its existence is not a secret. TOKI-058 R12 is a deliberate second answer for the same channel: a file of a channel not joined is 404, because the id of a file is not something a person can browse. The plan line says "answered like not found"; that holds where existence is secret and for files. If the owner wants 404 for a public channel too, it is a change in each route's own spec and in the `open` field of the entries (R10), not in this suite's design. Owner: Thanh Truong.
2. Where the list of endpoints comes from. Decided in this spec: the application's own routes, read by an `onRoute` hook that `buildApp` installs first through the test option `routeObserver` (R2; Design, "Why a registry checked against the route table"). Reason: it cannot be forgotten and it is exact; a hook added after `buildApp` returns misses `/healthz` and `/ws`, and the alternatives (a printed route tree, a list in a spec, a scan of the source for `scope.get(`, a look at the two root-level routes with `hasRoute`) all miss conditional, generated or new root-level routes. The edit of `apps/server/src/app.ts` is the only code change of this ticket and is owned by it; it follows the other test options of `BuildAppOptions` (`joinHooks`, `bootstrapDeps`). Owner: Thanh Truong.
3. Guests. Decided in this spec: not in phase 1. Reason: D-090 and D-152 leave Guest to phase 5 and D-050 gives it its own suite; the actor list of the world and Table A take one more row then. Owner: Thanh Truong.
4. Routes of tickets not built when this ticket starts. Decided in this spec: the ticket starts when every ticket of Table D is on `main`, and the entry for a route that is not there fails R3 (b); an entry is never written for a route that does not exist. The plan gives TOKI-088 only `needs: TOKI-070`, so the tracker can start it early; "Plan changes" asks for the longer line, and until it is changed the person who starts the build checks Table D. Reason: an entry for a route that is not built would be a guess about its url and its answer. If one is late, the ticket waits or the route is named a blocker. Owner: Thanh Truong.
5. Whether a new group stays out of the other people's lists until its first message. Not decided: it is concern 2 of TOKI-037 and F25 names the direct message only. Proposal, not a decision: the suite pins the answer of a group that has a message (R5 builds the group with one) and does not pin the case of a group with no message, where the answer to the other members is open; the suite does not depend on the answer. If the owner decides that it is hidden, one case is added to R9. Owner: Thanh Truong.
6. What Later shows when the person can no longer read the conversation of a saved message. Not decided: it is concern 2 of TOKI-067. Proposal, not a decision: the suite checks only that the answer holds no canary and no name of the conversation (R14, R15); the shape of the replacement row is not checked until the owner decides. Owner: Thanh Truong.
7. Who writes an entry, and the definition of done. Decided in this spec: the ticket that adds a route writes its entry in the same pull request. Reason: the author knows the rule the route must give and the spec requirement that says so (`source`); the coverage check makes it impossible to skip, because the pull request is red without it (R3). This suite does not write entries for routes of tickets built after it. This spec does not edit `docs/definition-of-done.md` or the pull request template, because the intent asks for tests only and the check in CI already enforces the rule. A line such as "A new route has an entry in `apps/server/tests/access/entries/`." in the pull request template is a proposal for the owner and a later ticket, not part of this one. Owner: Thanh Truong.
8. Over HTTP, not over the permission functions. Decided in this spec: the suite calls the routes of the built application. Reason: the permission functions are already proved by their matrix (TOKI-027 R14), and the risk this ticket covers is a route that forgets to call them or calls them in the wrong order. Owner: Thanh Truong.
