## Requirements
- R1. A GitHub Actions workflow file exists under `.github/workflows/` and its triggers are `pull_request` and `push` to the `main` branch. Check: open a pull request; a CI run appears on it without any manual step; merge it; a CI run appears for the new commit on `main`. GitHub starts no run on a pull request that has a merge conflict with its base; the run starts once the conflict is resolved (see Errors).
- R2. The lint check runs the two root scripts of TOKI-002: `pnpm lint` and `pnpm format:check`. Check: a pull request that adds an ESLint error shows a failed lint check; so does one that adds a badly formatted file.
- R3. CI enforces the package boundary rules of TOKI-002 through the same lint check. Check: a pull request where `client-core` imports a DOM API shows a failed lint check. The other boundary rules are enforced the same way. Removing or lowering a boundary rule is not caught by CI; TOKI-002 concern 13 accepts that and leaves it to the review of `eslint.config.js`.
- R4. CI runs the TypeScript type check for the whole workspace. Check: a pull request that adds a type error shows a failed type check.
- R5. CI runs the test suite through the root `test` script. The tests check passes when the repository holds no test yet (the root script runs the `test` script of every project that has one and succeeds when there is none), and runs every test once tests exist. Check: a pull request that adds a failing test shows a failed test check.
- R6. CI runs the build of every app and package that has a `build` script, through the root `build` script, which skips every project that has no `build` script (`pnpm -r --if-present run build`). The build check passes when none has one yet. Check: once a `build` script exists, a pull request that breaks that build shows a failed build check.
- R7. CI runs a bundle size check against one limit stored in a file in the repository. The limit is 200,000 bytes (200 KB, with 1 KB = 1000 bytes), measured with gzip by a script written in this repository that reads `apps/web/dist/` (no bundle size tool is added as a dependency), on the JavaScript that `apps/web` loads on first page load: every script and every `modulepreload` link in `apps/web/dist/index.html`, plus the chunks they import statically; chunks reached only by a dynamic `import()` do not count. The check fails when the measured size is greater than or equal to the limit and prints the measured gzip size, the limit and the difference. The bundle size check passes, and says that there is no bundle to measure, while `apps/web` has no `build` script. The `size` root script builds `apps/web` itself and then measures it, so it runs the same way on a clean clone and in CI. Check: the limit file holds 200,000; once the bundle exists, lower the limit below the current size in a pull request; the bundle size check fails and prints the three values.
- R8. Each of the seven checks is reported under its own fixed name (`lint`, `type check`, `tests`, `end-to-end`, `build`, `bundle size`, `i18n`) on the pull request and on the `main` commit; these are the names Thanh Truong requires in branch protection on `main`, so they are not renamed without telling him. Check: the pull request checks list shows lint, type check, tests, end-to-end, build, bundle size and i18n as separate entries, each with pass or fail.
- R9. The run is not green when any of the seven checks fails. Check: in each failing case of R2 to R7, the overall result on the pull request is red.
- R10. Every check can be run locally with one root command. Check: the root `package.json` has one script per check, and the workflow calls those scripts and holds no check logic of its own.
- R11. The workflow uses no repository or organisation secret, declares `permissions: contents: read`, and the repository holds no `.env` file. The local-only credentials of the Postgres service container in R15 are written in the workflow file; they protect nothing outside the run and are not secrets. Check: `grep -rnE "^[^#]*(secrets\.|secrets\[|secrets:)" .github/workflows/` prints nothing, `grep -rn "contents: read" .github/workflows/` prints a line, and `git ls-files | grep -E '(^|/)\.env(\.|$)' | grep -vE '\.env\.example$'` prints nothing.
- R12. CI uses the toolchain that TOKI-001 pins and keeps no second copy of it: Node from `.nvmrc` (`node-version-file`) and pnpm from the `packageManager` field of the root `package.json`. Check: the workflow holds no literal Node or pnpm version, the log prints a Node 22 version line, and the pnpm version in the log equals the `packageManager` value.
- R13. On a pull request with no fault, all seven checks pass, whichever of the other foundation tickets are already merged: a check with nothing to run yet passes (R5, R6, R7). Check: the first pull request after this work shows a green run. This is the "CI is green" part of the M1 exit check.
- R14. The workflow as delivered by this ticket held no end-to-end step; TOKI-008 added the end-to-end job later (and TOKI-017 the i18n job), so the `grep` below applied when this ticket was delivered and no longer holds on `main`. Check: `.github/workflows/` holds at least one workflow file, and when this ticket was done `grep -rniE "e2e|playwright" .github/workflows/` prints nothing.
- R15. The workflow starts a Postgres 17 service for the tests check and gives the tests its connection value as `TEST_DATABASE_URL`, one URL written directly in the workflow with a throwaway password and no repository secret (R11). The database name in the URL ends in `_test`, so the test guard of TOKI-008 accepts it. The service is throwaway: it exists for one run and holds no real data. Check: the workflow holds `TEST_DATABASE_URL` with a database name ending in `_test`; on a pull request made after TOKI-005 is merged, the database tests of TOKI-005 are reported as passed in the tests check, not skipped.
- R16. Each of the seven checks is its own job, with its own checkout, toolchain setup and `pnpm install --frozen-lockfile`, and no job depends on another, so a failure in one never cancels or skips another. No step uses `continue-on-error`. Check: one throwaway pull request with a lint error and a failing test shows both checks red and the other checks reported (pass or fail), no job skipped or cancelled; the pull request changes a `.ts` file under `apps/web` (to fail lint) and a test file under `packages/` (to fail a test), so every check starts. A check that has nothing to check (R19) still starts and is reported as passed, with its steps skipped; it is not left out of the run.
- R17. A pull request whose lockfile is out of date shows all seven checks red, each failing at its install step. Check: a throwaway pull request that changes a dependency in `package.json` without updating `pnpm-lock.yaml`.
- R18. A newer push to the same pull request cancels the run still in progress for it (`concurrency` group per pull request with `cancel-in-progress`; runs on `main` are not cancelled, so every commit on `main` gets its own result), and every job caches the pnpm store (`cache: pnpm` of the Node setup step). Check: two pushes in a row show the first run as cancelled; the second run's install step log reports a cache hit.
- R19. A check runs its steps only when the pull request changes a file it depends on; otherwise its steps are skipped and the job passes, so every check is still reported and the seven required checks can merge a pull request that changes documents only. The rule is one script, `.github/scripts/changed.sh`, that reads the files changed since the base commit: a change only in `docs/`, `.claude/` or `.md` files at the repository root starts no end-to-end, test, type check, build, size or i18n step; everything under `apps/` or `packages/`, an `.md` file there included, counts as code and starts the checks that read it; the lock file, the root `package.json`, the TypeScript and workspace configuration, `ci.yml` and the script start every check; `lint` always runs, because `pnpm format:check` also reads the documents; a push to `main` runs every check. The workflow has no `paths` or `paths-ignore` filter. Check: `bash .github/scripts/changed.test.sh` passes; a throwaway pull request that changes only a root `.md` file shows `lint` run and the other six checks passed with their steps skipped; one that changes only an `.md` file under `apps/web` or `packages/` shows end-to-end, tests, type check, build and bundle size run too; one that changes `apps/web` shows end-to-end, tests, type check, build and bundle size run.

## Design
### Errors
- A check fails -> its entry on the pull request is red, the overall run is red, and the log shows the failing command output.
- Bundle size at or over the limit (R7) -> the bundle size check fails and prints what R7 lists.
- Dependency install fails (lockfile out of date) -> each job fails at its own install step, so all seven checks are red and the log names the install step (R17).
- One check fails -> the other checks still run, because the jobs are independent (R16), so the builder sees every failure in one run.
- A pull request has a merge conflict with its base -> GitHub starts no run on a `pull_request` trigger, so the pull request shows no check at all until the conflict is resolved. This is GitHub behaviour, not changed here; it is not green. Evidence: GitHub Actions documentation, `pull_request` event (the run uses the merge commit of the pull request).
- A check has nothing to run yet (no test, no `build` script, no web bundle) -> the check passes and its log says what was missing.

### Layout
```
toki/
├─ .github/
│  └─ workflows/
│     └─ ci.yml          the only workflow in this ticket; triggers: pull_request and push to main; seven independent jobs (R16)
├─ package.json          root scripts, one per check (R10)
└─ <bundle limit file>   holds the limit value for R7 (200 KB gzip)
```
- Assumption: the workflow file is named `ci.yml`.
- Assumption: the root script names are `lint`, `typecheck`, `test`, `build` and `size`. Scripts that TOKI-001 or TOKI-002 already added are reused, not renamed. The root `build` script is `pnpm -r --if-present run build` (R6).
- The limit and how it is measured are stated once, in R7, including the self-written measuring script. The Blueprint names no bundle size tool and no limit file. See concern 3.
- TOKI-008 later added the end-to-end job (`pnpm test:e2e`) to `ci.yml` and TOKI-017 the i18n job; this ticket did not (R14).
- The Postgres service is part of this ticket (R15), so the database tests of TOKI-005 run in CI as soon as both tickets are merged, in either order.
- The root `test` script: TOKI-004 adds the first tests and TOKI-008 R1 owns the full `pnpm test` (Vitest for every package that has tests). This ticket creates the root `test` script only if it does not exist yet, as `pnpm -r --if-present run test`, which exits 0 when no project has a `test` script. When TOKI-008 merges, its script replaces this one; the CI job keeps calling `pnpm test`.
- The `size` job does not wait for the `build` job (R16). The `size` script builds `apps/web` itself (R7), so the bundle is built twice per run; this is accepted for the small phase 1 web app, to keep every check runnable alone with one command (R10). Passing the build output as an artifact is the alternative if the build time grows.
- Toolchain: `actions/setup-node` with `node-version-file: .nvmrc` and `cache: pnpm`, and a pnpm setup step that reads `packageManager` (R12, R18). Evidence: TOKI-001 spec R8 (`.nvmrc` holds `22`, `engines.node` is `22.x`) and R9 (`packageManager` is `pnpm@<exact version>`); TOKI-001 sets no `engine-strict`.

## Testing
- R2 to R7 are proven on GitHub with a throwaway pull request that carries one fault each (lint error, format error, switched-off boundary rule, boundary violation, type error, failing test, broken build, lowered size limit); R16 and R17 with the two-fault and stale-lockfile pull requests; R1, R8, R11, R12, R14 and R18 by the checks written in them. The `main` trigger of R1 is shown by the run on the merge commit of the first pull request. Required checks on `main` are set by hand by Thanh Truong after merge and are not tested here; the check names of R8 must match what he selects. Each must show red on the matching check. The failing-test, broken-build and size faults can only be shown once a test, a `build` script and the web bundle exist; until then R5, R6 and R7 are checked by the passing case and by the local scripts.
- One clean pull request must show all seven checks green (R13).
- Size script: with a built `apps/web`, run it at a limit below, equal to and above the measured size; it fails below and at, passes above, and prints size, limit and difference. Check that `pnpm build` exits 0 when no project has a `build` script.
- Local check first: run each root script and confirm it exits non-zero on the same faults.
- Fake data only. No real credential is used in any test pull request.

## Data safety
- Secrets live in `.env`, never in git. The workflow in this ticket needs no secret.
- Logs must not print environment values. The checks in scope read none.
