# Reconnect design

Date: 2026-11-23 · Status: draft for review (concern 7 is open for the product owner)
Intent: docs/intents/reconnect-recovery.md (Thanh Truong)
Ticket: TOKI-039

## Goal
A person who leaves Toki open must find it right again after the connection comes back, with nothing for them to do: every event that concerns them and happened while the client was not connected is applied, once and in order, and a client that was away longer than the server keeps events starts again from a fresh load. Today the gateway (TOKI-038) pushes events to a connected client only, and the client has no socket.
This work builds the client side of the connection (open, wait and try again, answer the heartbeat, know what each close code means), the number the client has applied up to, the request that returns the events a client missed (client and server halves), and the hand-off of those events, in order, to the code that applies them (TOKI-040). It also publishes the connection state that the offline banner and the waiting messages follow, and shows nothing itself.

## Scope
- In:
  - The connection in `packages/client-core`: open, the answer to `ping`, the silence check, the retry delays, the close table, `start`, `stop` and `retryNow` (R7 to R14, R18).
  - The number the client has applied up to and the rule that no event is applied twice (R8, R10).
  - The catch-up after `ready`: the request, the pages, the live events that arrive meanwhile (R9, R10), and the full reload when the number is no longer kept (R16).
  - The new route `GET /api/v1/events` of the `realtime` module, its audience rule, its pages and its refusal for an expired number (R1 to R6), and the new request method of the API client (R17).
  - The connection state (R15), the hand-off of live frames and of client frames (R19), and the wiring in `apps/web`: the address of the socket, start and stop with the session, the browser's `online` signal (R20).
  - Tests with a fake socket, the fake timers and a real database (Testing).
- Out (not now):
  - The gateway, its close codes, its `ready` frame and its frames: TOKI-038 (this work reads them as TOKI-038 R7, R12, R21 to R25 and the Design table of codes say). The log and its reads, `readEventsAfter`, `getOldestEventNumber`, the pruning after 7 days: TOKI-036.
  - Applying an event to the cache, the optimistic send, the queue of waiting messages and the single automatic try after the connection returns, and what "everything" is when a full reload is needed (the message caches): TOKI-040. This work hands it the events and the reload trigger (R19, R16).
  - The offline banner, the blocking of writes while disconnected and the call of `setConnectionCheck`: TOKI-082 (TOKI-093 R17 says the same). This work gives it the state (R15).
  - The typing signal, its frames and its timing: TOKI-044. This work gives it a way to send a frame and to receive live frames (R19).
  - Presence (TOKI-055), the production proxy rule for `/ws` (TOKI-084), the measure of the 150 ms target (TOKI-089).
  - A saved cache for offline reading across a reload (Phase 6, D-060); the strip that offers a new version of the app (TOKI-082).
  - The text of any banner or notice: no text is written here (R21).

## Requirements
Server: the events a client missed
- R1. `GET /api/v1/events?after=<n>&limit=<m>` is a route of the `realtime` module, registered by `app.ts` inside the `/api/v1` scope, so it needs a valid session like every route there (TOKI-022 R24: no session is 401, an ended session or a deactivated account is the 401 of TOKI-022 R25 and R27). `after` is required, an integer from 0 to 9,007,199,254,740,991 (the range of `events_number_check`, TOKI-036 R13). `limit` is optional, an integer from 1 to `CATCH_UP_LIMIT_MAX` (500), and defaults to `CATCH_UP_LIMIT_DEFAULT` (200). A missing, repeated or non-integer `after`, a `limit` out of range and any other query key are 400 `validation_failed`, in the error format of TOKI-004. The route writes nothing, takes no lock and sets no cache header other than `Cache-Control: no-store`. Check: no session, an ended session and a deactivated account give the 401 of their code; `after` missing, `-1`, `1.5`, `abc` and `after=1&after=2`, `limit` 0 and 501 and a key `x=1` give 400; `after=0` and `limit` 500 give 200; the response has `Cache-Control: no-store`; the route list of TOKI-004 R10 lists `/api/v1/events`.
- R2. The answer is `{ "events": EventObject[], "through": number, "hasMore": boolean }`, written as a Zod object in `packages/shared/src/realtime/catch-up.ts`. `EventObject` is the `event` object of an `event` frame of TOKI-038 R12 (`number`, `kind`, `conversationId`, `createdAt`, `data`), built by the same function of the gateway that builds the live frame (TOKI-038 R12 says only one function maps a log row to it; this work asks for it to be exported from `realtime/index.ts`, Plan changes), so a live event and a missed event of the same row are the same object. Check: the shared schema parses the answer of every test; for one log row, the object in the answer equals the `event` of the frame the gateway sends for it (one test with both).
- R3. The reads run in one `READ ONLY` transaction at `REPEATABLE READ` (the one the gateway uses for its snapshot, TOKI-038 R8, and the bootstrap build uses, TOKI-031 R10; `app.ts` passes it in), so the three reads see one state: `M`, the number of the last event, with `readEventNumber(tx, workspaceId)` (TOKI-036 R19); the set of conversations of the person, with the same function and the same DM condition as the gateway's map (TOKI-038 R8, which `app.ts` builds once and passes to both); and the raw events, with `readEventsAfter(tx, workspaceId, after, limit)` (TOKI-036 R26), the one read of the log. The route reads the workspace id of the account as the bootstrap build does. It adds no second read of `events` and no index. Check: counted with the wrapper of TOKI-031 R14, a request runs a fixed number of statements (the number is written in the test) whatever the number of events or conversations; a spy shows that `readEventsAfter` is the only function that reads `events`; a source search finds no `from events` in this ticket's files.
- R4. The audience of an event of the page is the audience of TOKI-038 R15, read from the set of R3: an event with scope `conversation` is kept when its conversation is in the set of the person; an event with scope `user` is kept when it is addressed to the person; an event with scope `workspace` is kept. Every other raw event is dropped. A conversation that the person has left, or never joined, is not in the set, so none of its events is returned, and the person who left is told by the `conversation.left` event of scope `user` (TOKI-038 R9, R20). A conversation that the person joined after `after` is in the set, so its events inside the page are returned, those before the joining included; this shows the person nothing they could not read through the history route, which gives every message of a conversation they belong to (TOKI-037 R14). Check: the scenario of TOKI-038 R15 (a member, an Admin who is not a member, a person in another conversation, the twelve channel routes and a DM): the answers for the two outsiders, searched whole, hold no id, name, topic or message of the private channel and of the DM; the member's answer holds every event of the scenario in number order; a person added in the middle of the range gets the events of the conversation from before the adding; a person removed in the middle gets `conversation.left` and no `member.removed` or later event of that conversation; the first message of a DM reaches the other person together with its `conversation.appeared`; an event is returned at most once.
- R5. Paging. `events` holds the kept events of the raw page in increasing number order. When the raw page holds fewer than `limit` events, `through` is `M` and `hasMore` is false. When it holds `limit` events, `through` is the number of the last raw event, kept or not, and `hasMore` is true when `through` is below `M`. So a client that sets its number to `through` after each page moves forward even over a page where every event was for someone else, and never returns to a number it passed. A page may hold fewer events than `limit`, or none, with `hasMore` true. Check: with 450 events of which one in three concerns the person and `limit` 200, three requests give `through` 200, 400 and `M`, `hasMore` true, true and false, and the kept events of the three pages are all the person's events once; a request with `after` equal to `M` gives no events, `through` equal to `M` and `hasMore` false; a page of 200 raw events none of which is the person's gives `events` empty, `through` 200 and `hasMore` true; `M` is read in the same snapshot, so an event committed during the request is in no page of it and is returned by the next request.
- R6. An `after` that the log can no longer serve is refused with status 410 and the code `events_expired` (added to `ErrorCodes` in `packages/shared/src/error.ts` and to the codes the API client knows), in the error format of TOKI-004, and no event is returned. The rule, read in the same snapshot with `getOldestEventNumber(tx, workspaceId)` (TOKI-036 R20): when the log holds events, `after` is expired when `after + 1` is below the oldest kept number, or when `after` is above `M` (the client holds a number that this log never reached); when the log holds none, `after` is expired when it is not equal to `M`. The rule does not read a clock: pruning (TOKI-036 R21, `EVENT_RETENTION_DAYS` 7) is what decides what is kept. Check: with events 1 to 10 and 1 to 5 pruned, `after` 4 is served, `after` 3 is 410, `after` 11 is 410, and `after` 10 gives no events with 200; with the log empty after a prune of everything and `M` 10, `after` 10 gives 200 and `after` 9 is 410; with the `TestClock` moved 8 days and `pruneEvents` run, an `after` from before the oldest kept event is 410 and the number just before the oldest is served; the 410 body has the code `events_expired`.

Client: the connection
- R7. `packages/client-core/src/realtime/` exports `createConnection(options)` and its types. `options` has `url` (the address of the socket, given by the app), `timers` (the `Timers` of the API client, `after(ms, fn)`), `random` (a function that returns a number from 0 up to but not including 1), `catchUp` (a function `(after: number, signal?: AbortSignal) => Promise<CatchUpAnswer>`, the method of R17), `onEvents`, `reload` (R19) and `onUnauthenticated` (a function `(code: string) => void`, which the app gives as `reportUnauthenticated` of the session store), and optionally `createSocket` (a function that opens a socket from `url` and returns a `SocketLike`: `send`, `close(code, reason)` and the four handlers `onopen`, `onmessage`, `onclose`, `onerror`; it defaults to `new WebSocket(url)`, a global that the allow list of boundary rule 1 has). The package reads no clock, no `window`, no `document`, no `navigator` and no `location`, and writes no text a person reads. The connection has `start(number)`, `stop()`, `retryNow()`, `send(frame)`, `subscribeLive(listener)`, `subscribe(listener)` and `getState()` (R15, R19). Check: a type test calls every member; a search of the package for `window`, `document`, `navigator`, `location`, `Date.now(` and `new Date(` finds none; `pnpm lint` exits 0 (boundary rule 1); with no `createSocket`, a test with a stub global `WebSocket` shows `new WebSocket(url)` is called with the `url`.
- R8. `start(number)` takes the number of the last event the client has applied (after the first load it is `getEventNumber()` of the conversation store, which is the `eventNumber` of the bootstrap answer, TOKI-031 R11) and opens a socket. `number` is the connection's cursor: the highest event number the client has applied. The cursor never decreases except through R16, and no event with a number at or below it is applied (R10). A `start` while the connection runs stops the earlier socket first, as `stop()` does, and drops its queue. The connection does not open before `start` and does not call `catchUp` or `reload` before the `ready` frame. Check: with a fake socket, nothing is opened before `start`; two starts leave one open socket, the first closed with code 1000; no call of `catchUp` before `ready`.
- R9. On the `ready` frame `{ "type": "ready", "eventNumber": N }` (TOKI-038 R7), with `c` the cursor: when `N` is below `c`, the server's log is behind the client and R16 runs; when `N` is equal to `c`, nothing was missed and no request is made; when `N` is above `c`, the connection calls `catchUp(c)` and, while `hasMore` is true, calls it again with the `through` of the answer. After each answer it hands the answer's `events` to `onEvents` (one call per answer, none for an empty one), waits for the call to end, and sets the cursor to `through`. When `hasMore` is false the catch-up is over. `N` is not compared with the numbers of the events, because the numbers a person receives are not consecutive: an event for someone else leaves a hole in them, so a hole is never a sign of loss. Why this is enough: the gateway sends on this connection every event above `N` that concerns the person (TOKI-038 R7), and the request returns the events up to the number it read, which is not below `N` (it is read after `ready`; R5). Check: with a fake socket and a fake `catchUp`, `ready` with `N` below, equal to and above the cursor give the reload, no request, and a request from the cursor; three pages call `catchUp` with the cursor, the first `through` and the second `through`, `onEvents` receives the two non-empty answers in order and not the empty one, and the cursor ends at the last `through`; the answer of a request that is made when events have a hole in their numbers (1, 4, 9) is applied and the cursor ends at `through`, with no second request.
- R10. Live events. An `event` frame is parsed with the schema of TOKI-038 R12; a text that is not JSON, a frame with an unknown `type` and an event frame of a `kind` that no code knows are not errors (an event of an unknown kind is handed to `onEvents` like any other, TOKI-040 ignores a kind it does not know). An `event` frame whose envelope is not valid (`number`, `kind`, `conversationId`, `createdAt` or `data` of the wrong type) is a failure of the stream: the connection drops the socket and goes on as for a lost connection (R11), so the next catch-up starts from the cursor. Events are applied one batch at a time, in number order: a live event that arrives while a catch-up or an `onEvents` call is running waits in a queue (at most `CATCH_UP_QUEUE_MAX`, 2,000 events; past that the connection drops the socket as for an invalid envelope, because the catch-up that follows is cheaper than an unbounded queue); when the running work ends, the queue is applied, skipping every event whose number is at or below the cursor (an event the catch-up already returned), and the cursor moves to the number of each applied event. An event is never handed to `onEvents` twice and never after an event with a higher number. Check: a live event with a number below the cursor is not applied; events that arrive during a catch-up wait for it and are applied after it in number order; an event that the catch-up already returned and that arrives live afterwards is applied once; a frame with invalid JSON, an unknown type and an event of kind `x.y` give no failure and the third reaches `onEvents`; an invalid envelope drops the socket and a new socket is opened after the first delay; the 2,001st queued event drops the socket.
- R11. Retry. After a socket is lost for a reason that R12 says to retry, the connection waits and opens a new socket. The wait for the attempt `k` (counted from 0 since the connection last held, below) is `RECONNECT_DELAYS_SECONDS[min(k, 4)]` seconds, where the list is 1, 2, 5, 10, 30 (D-129), multiplied by `1 - J + 2 * J * random()` with `J` equal to `RECONNECT_JITTER` (0.2). Decided in this spec: the log says "a little randomness" and no amount, so the amount is a technical choice, with its reason (a client that returns at 24 seconds and one at 36 do not meet at 30). The wait is a call of `timers.after`. `k` goes back to 0 once a socket has been open for `RECONNECT_STABLE_SECONDS` (10) after its `ready` (a timer started at `ready` and cancelled by the loss), so that a server that accepts and closes at once does not keep the delay at 1 second. `retryNow()` cancels a wait that is pending and opens a socket at once; it does not change `k`, and it does nothing when a socket is open, when the connection is not started or when it has stopped itself (R12). A socket that opens but sends no `ready` within `READY_TIMEOUT_SECONDS` (10) is dropped as a lost socket. Check, with the fake timers and a fake `random`: the delays asked of `timers.after` after eight losses in a row are 1, 2, 5, 10, 30, 30, 30, 30 seconds for `random` returning 0.5; with `random` returning 0 they are 0.8 times and with `random` just under 1 they are just under 1.2 times those values; a socket that held 10 seconds (the stable timer fired) and then closed waits 1 second; one that closed after 9 seconds and one that closed at once do not reset; `retryNow` with a pending wait opens a socket without waiting and the old wait is cancelled; with an open socket it opens nothing; a socket with no `ready` is dropped after 10 seconds.
- R12. What the connection does for each close. It reads the code and the reason of the close event and follows this table; the codes and reasons are those of TOKI-038 (Design, "Closing, codes and reasons"), constants of `packages/shared/src/realtime/limits.ts`:

  | Close | Action |
  |---|---|
  | 4401 with the reason `unauthenticated`, `session_ended` or `account_deactivated` | stop and do not retry; call `onUnauthenticated(reason)` (this is the 401 of a request: the session state shows 'Your session has ended', sign-in screens R24 and R39); `stoppedBy` is the reason |
  | 4401 with the reason `signed_out` or `replaced` | stop and do not retry; call nothing (this browser asked for the end, TOKI-038 R21: no notice); `stoppedBy` is the reason |
  | 4401 with any other reason or none | stop and do not retry; call `onUnauthenticated("unauthenticated")`; `stoppedBy` is `unauthenticated` |
  | 4430 `too_many_connections` | stop and do not retry (TOKI-038 R10); `stoppedBy` is `too_many_connections`; the tab stays as it is until it is reloaded (concern 7) |
  | every other code and the loss of the connection with no close (1000, 1001 `going_away`, 1006, 1009, 1011 `server_error`, 4400, 4408, 4410, 4429, a failed handshake such as the 403 of TOKI-038 R4 which a browser shows as 1006, and a code that this table does not know) | retry with the delay of R11 |

  A connection that has stopped itself stays stopped: only `start` (R8) opens it again. `onUnauthenticated` is called at most once for a stop. Check: one case for each row, with the fake socket closing with that code and reason: the rows that retry ask `timers.after` for a delay and open a socket when it fires; the others open nothing, `getState().stoppedBy` is the reason, `onUnauthenticated` is called with the right argument or not at all, and `retryNow()` opens nothing; the session store of `client-core` (the real one) goes to `ended` for `session_ended` and `account_deactivated` with the codes of the table and stays `signedIn` for `signed_out`, `replaced` and `too_many_connections`.
- R13. Heartbeat. A `ping` frame (`{ "type": "ping" }`, TOKI-038 R24) is answered at once with `{ "type": "pong" }`. The connection also checks the server: a timer of `HEARTBEAT_TIMEOUT_SECONDS` (60, the constant of TOKI-038) is started at the open of the socket and restarted at every frame received; when it fires the connection drops the socket and goes on as for a lost connection. It does not wait for the close event: a browser may take a long time to report a socket whose network is gone, so the connection removes its handlers, calls `close(4000, "heartbeat_timeout")` and opens a new one after the delay of R11. Decided in this spec: 60 seconds, the number the server uses for the client, which is two missed pings (25 seconds apart) and a margin. Check: a `ping` gets a `pong` as the next sent frame; with the fake timers, no frame for 60 seconds drops the socket, a frame at 59 seconds restarts the count, a `ping` counts as a frame; the handlers of the dropped socket are removed, so a late `message` or `close` of it changes nothing; the new socket opens after the delay of R11.
- R14. A frame the client sends is a JSON text. `send(frame)` sends `JSON.stringify(frame)` and returns true when the socket is open and the `ready` frame has been received, and false otherwise; it never throws. Check: false before `start`, before `ready` and after a close; true after `ready`; a frame of the typing ticket reaches the fake socket as text.

Client: state, reload, wiring
- R15. The connection state `getState()` is `{ status, catchingUp, stoppedBy, cursor }`, an object that is replaced and never changed (as the store state, client-core R12), with `subscribe(listener)` (returns the function that removes it; the listener gets no argument). `status` is `idle` (before `start`, and after `stop()`), `connecting`, `online` or `offline`. It is `online` from the `ready` frame until the socket is lost, and `catchingUp` is true from `ready` until the catch-up or the reload is over. It is `connecting` from `start` and from a loss, and becomes `offline` when `OFFLINE_GRACE_SECONDS` (3) have passed since the start or the loss without a `ready` (a timer of `timers.after`), or at once when the connection stops itself (R12). A `ready` before the three seconds have passed means `offline` was never shown. Why: the journey of F37 says a drop of under 3 seconds shows no strip, D-091 accepts it as the baseline of the phase-1 journeys, and D-102 and D-140 say the banner stays the whole time the connection is down, with no reconnecting state and no toast when it returns; `connecting` is internal, nothing draws it. TOKI-082 shows the banner when `status` is `offline` and hides it when it is `online`; TOKI-040 resends the waiting messages when `status` becomes `online`. `cursor` is the cursor of R8. The listeners are called once for each change of the object and not for a change that gives an equal state. Check: with the fake timers, a loss followed by `ready` before the grace timer gives `connecting` then `online` and never `offline`; a loss with no `ready` gives `offline` when the 3-second timer fires, and `online` at the next `ready`, with no state in between; `start` with a server that never answers gives `offline` after 3 seconds; a stop by 4401 gives `offline` with `stoppedBy` at once; `stop()` gives `idle`; `catchingUp` is true during a catch-up and false after; the state object is the same one until a change; a listener is called once per change.
- R16. The full reload. When the server answers `catchUp` with the status 410 and the code `events_expired` (R6), or `N` is below the cursor (R9), the connection calls `reload()`, which the app gives and which returns a promise of the number of the new first load (R19). It waits for it, sets the cursor to that number, drops from the queue every live event at or below it, and carries on as for a `ready` with the same `N`: when `N` is above the new cursor it makes the catch-up of R9, otherwise none. A `reload()` that rejects, a second 410 in the same connection after a reload, and an exception of `onEvents` are failures of the connection: it drops the socket and goes on as for a lost connection (R11) with the next delay; the exception is not swallowed. Decided in this spec: the reload is a reload of the data the app shows (a new bootstrap and the message caches), not a reload of the page, because a page reload would lose the text the person is typing and make the screen flash; the waiting messages are kept in the browser either way (D-132); what is dropped and reloaded is TOKI-040's (R19). Check: with a fake `catchUp` that rejects with the 410, `reload` is called once, the cursor is its result, a live event at or below it is not applied and one above it is, and the catch-up that follows asks from the new cursor when `N` is higher; `N` below the cursor calls `reload` and no `catchUp`; a rejected `reload` and a second 410 drop the socket and the next socket opens after the delay; an `onEvents` that throws does the same and `reload` is then called by the next connection only if the server says so.
- R17. `packages/client-core/src/api/methods.ts` gets one method, `events.after(after, options?)`, which sends `GET /events?after=<n>` (with `limit` when `options.limit` is given) through the one request core (the 10-second rule of D-126, no retry, the 401 hook of TOKI-032 R7), reads the answer with the schema of R2 and takes an optional `signal` last, like the other methods (TOKI-032 R9). A 410 `events_expired` ends as the `ApiError` of kind `http` with that status and code, which `classifyApiError` already sends to `fresh_copy` (TOKI-032 R8). When `catchUp` fails for any other reason (`network`, `timeout`, 5xx, `invalid_response`) the connection drops the socket and goes on as for a lost connection (R11); when it fails with a 401 of a session code, the connection stops (R12 row 1, `stoppedBy` `session_ended`), because the hook has already reported it and a retry would only repeat it. A request that is still running when the socket is dropped or `stop()` is called is aborted with its `signal`, and its answer is ignored. Check: the method sends the path and the query as written and parses the answer; a 410 gives the `ApiError` with the code; a fake `catchUp` that rejects with `network`, with `timeout` and with `invalid_response` each drops the socket and retries; a 401 `session_ended` stops with no retry and does not call `onUnauthenticated` a second time (the hook of the API client does); a drop while a request runs aborts it and an answer that arrives later changes nothing.
- R18. `stop()` closes the socket with code 1000, cancels every timer and every request of the connection, empties the queue, sets `status` to `idle` and leaves the cursor as it is. It is called by the app when the session stops being signed in or another person signs in (R20), so the connection of one person is never used for another: a `start` after it takes the number of the new first load. A call of `stop()` that finds the connection idle does nothing. Check: after `stop()` no timer of the connection is pending (the fake timers show every one cancelled), the fake socket got 1000, a late `message` of the closed socket changes nothing, and a second `stop()` changes nothing.
- R19. The hand-offs. (a) `onEvents(events)` is a function that returns nothing or a promise; it gets the events of R2 in number order, one batch at a time (R9, R10), and applies them to the cache: that is TOKI-040's work, and this work applies nothing to a store. Until TOKI-040 is built, the app passes a function that does nothing. (b) `reload()` returns a promise of a number; TOKI-040 makes it drop the message caches and run the bootstrap again; until then the app's `reload` is `conversations.refresh()` followed by the store's `getEventNumber()`, and it rejects when the refresh left an error in the store state. (c) `subscribeLive(listener)` calls `listener(frame)` for every `live` frame (`{ type: "live", kind, data }`, TOKI-038 R12) as it arrives, at once, never queued and never after a stop; the connection does not read `kind`. TOKI-044 and TOKI-040 (`person.updated`) are its readers. (d) `send(frame)` (R14) is the way TOKI-044 sends its frame. A listener that throws does not stop the other listeners or the connection. Check: a live frame reaches two listeners at once, also during a catch-up; a listener that throws leaves the second one called and the connection open; with no `onEvents` supplied by a test of the app wiring, the default does nothing and the cursor still moves.
- R20. Wiring in `apps/web`. A new file `apps/web/src/realtime.ts` creates the one connection of the app with `createConnection`, `timers` from `apps/web/src/client.ts`, `random` as `Math.random`, `catchUp` as `api.events.after`, `onUnauthenticated` as `reportUnauthenticated`, `onEvents` and `reload` of R19 and a `url` built from the page's address (`ws` for `http` and `wss` for `https`, the same host, the path `/ws`; the Vite dev server forwards it, TOKI-038 R28). It exports `connection` and `bindRealtime()`, and `main.tsx` calls `bindRealtime()` once before the app is mounted. `bindRealtime` follows two states: it calls `connection.start(conversations.getEventNumber())` when the session is `signedIn` and the conversation store has `status` `ready` and the connection is `idle`; it calls `connection.stop()` when the session is not `signedIn` or the store goes back to `idle` (a `reset()`, a change of person; TOKI-033 R32 and TOKI-097 R33 empty the store). It connects the typing indicator as TOKI-044 R17 and its Scope say this ticket does: `connection.subscribeLive` hands each live frame to `typing.receive`, and `typingSender.setSend` gets `connection.send` (and `null` when the connection stops). It also calls `connection.retryNow()` when the browser fires `online` on the window. The file is the only one in `apps/web` that creates a connection (a search finds one `createConnection(`). Decided in this spec: the `online` signal is a browser event, so it is read here and not in `client-core` (boundary rule 1); it shortens a wait and starts no second socket. ## Design
### The path of a reconnect
1. The socket is lost (a close, a silence of 60 seconds, a failed catch-up). The state is `connecting`; after 3 seconds without a `ready` it is `offline` and the banner of TOKI-082 shows (D-102).
2. The connection waits 1, 2, 5, 10, 30 seconds (with the jitter), or less if the browser says `online`, and opens a new socket to `/ws` with the cookie. The gateway checks the session and answers `ready` with `N`.
3. The client compares `N` with its cursor `c`. Nothing was missed when they are equal. Otherwise it asks `GET /api/v1/events?after=c` and applies each page before it asks for the next. A number that the server no longer keeps is a 410, and the app reloads what it shows.
4. Live events that arrive during step 3 wait in a queue and are applied after it, skipping what the pages already gave.
5. The state is `online`, with no toast (D-102). TOKI-040 sends the waiting messages.

### Why the numbers are not consecutive and what that allows
The log numbers every event of the workspace, and a person receives only the events of their audience (TOKI-038 R15), so the numbers a client holds have holes. A client therefore cannot tell a lost event from an event for someone else by looking at numbers. The protocol does not need it: the server tells the client where the live stream starts (`N`), the request returns everything up to a number that is not below `N`, and everything above `N` comes live on the same connection, in order. A connection that fails starts again from the cursor. Duplicates are told by number only (R10), and the message itself is told by its id when TOKI-040 applies it, so a message sent while the connection flaps is stored once by the server (TOKI-037 R5) and shown once.

### The cursor
The cursor is the highest event number applied. It starts as the `eventNumber` of the bootstrap (TOKI-031 R11) and moves after each applied batch to the number of its last event, and after each catch-up page to its `through` (a number that is at least the last returned event and may be higher: R5). It lives in memory only. A page reload starts from a bootstrap and a new cursor, so the 7 days matter only to a tab that stays open: a laptop that sleeps for 8 days. The expiry rule reads the log, not a clock (R6): the log is what says whether the events are still there.

### Audience of the catch-up (decided in this spec)
The route uses the set of conversations of the person now, not the set at each event. A set at each event would need the history of membership, and the log holds it only as events. Using the set now is safe: a person never gets an event of a conversation they are not in (R4), and what they get from before they joined is readable by them anyway. It also gives them what they need: a conversation they joined during the absence has its `conversation.created`, `member.joined` or `members.added` event in the range (scope `conversation`, the conversation is in the set), and one they left has its `conversation.left` (scope `user`). Two consequences, both for TOKI-040: a `conversation.left` for a conversation the client never held must change nothing, and the events of one conversation inside a catch-up may begin with events from before the person was added, which only add messages the history route would give.

### Close codes (summary)
The table of R12. The codes are TOKI-038's. A client that is told to stop by 4401 `signed_out` or `replaced` raises no notice, because this browser asked for the end; its next request is refused with a 401, which is the notice, if there is one to give.

### Limits
`RECONNECT_DELAYS_SECONDS` 1, 2, 5, 10, 30 (D-129); `RECONNECT_JITTER` 0.2; `RECONNECT_STABLE_SECONDS` 10; `READY_TIMEOUT_SECONDS` 10 (the same as the 10 seconds a request may wait, D-126); `OFFLINE_GRACE_SECONDS` 3 (F37); `CATCH_UP_LIMIT_DEFAULT` 200 (the gateway's batch, TOKI-038 Limits) and `CATCH_UP_LIMIT_MAX` 500 (below the 1,000 that `readEventsAfter` accepts); `CATCH_UP_QUEUE_MAX` 2,000. Only the delays, the grace and the 7 days are in the log; the others are decided in this spec as technical choices, each with its reason above or in the line, and are constants so they can change without a design change.

### Errors
- The route: 401 of a session code; 400 `validation_failed`; 410 `events_expired`; 500 `internal_error` for a failure of a read, with no event and no number in the log line (the log holds no payload).
- The client: a lost socket retries; a stop is final until `start`; a failed request, a rejected `reload` and a throwing `onEvents` drop the socket and retry (R16, R17). Nothing is shown by this work.

## Data safety
- The route returns only what the audience rule gives (R4): no event of a private channel, a DM or an unjoined channel reaches a person outside it, an Admin who is not a member included. The test of R4 searches the answers of the outsiders.
- A page holds the payloads of events; the log line of the route holds the method, the path without its query and the status, as every request (TOKI-004 R7), and no payload and no number list.
- The client keeps the cursor in memory only and writes nothing to storage; `stop()` is called when another person signs in, so one person's cursor and queue are never used for another.
- The close reasons are the short words of TOKI-038; the client sends nothing to the server about why it closed.

## Areas of concern
1. Who builds the request for missed events. TOKI-038 leaves it to this ticket (its Scope, "The request that returns the events a client missed: TOKI-039"), and TOKI-036 names this ticket as the user of `readEventsAfter` and `getOldestEventNumber` (its "What the later tickets get"). Decided in this spec: this ticket builds `GET /api/v1/events` in the `realtime` module with the reads of TOKI-036 and the audience rule of TOKI-038 R15, adds the error code `events_expired`, and adds no read of the log of its own (R1 to R6). The answer reuses the gateway's one mapping function, so TOKI-038 exports it (Plan changes). Owner: Thanh Truong.
2. The audience of a catch-up. Decided in this spec (a technical choice): the set of conversations of the person now, in the snapshot of the request, not the set at each event (Design, "Audience of the catch-up"). Reason: a set at each event needs the history of membership; a person never gets an event of a conversation they are not in, and what they get from before they joined is readable by them through the history route (TOKI-037 R14, D-116 is about people who are not members). The cost, two rules for TOKI-040, is in the Design. Owner: Thanh Truong.
3. The numbers a client holds are not consecutive, so a hole is not a sign of a lost event, and the first load, a reconnect and a reload all start from the cursor. Decided in this spec (a technical consequence of TOKI-036 R16 and TOKI-038 R15): the client compares only the `ready` number with its cursor, asks for the range once, and applies live events above it (R9, R10). TOKI-036's remark that the client asks for a missing number is read as this request. Owner: Thanh Truong.
4. What "a long absence" means and what a reload is. Decided in this spec: the server says it, by the oldest number it keeps (R6), not a clock in the client; with the retention of 7 days (TOKI-036 R22) this is an absence of about 7 days and more; and the reload is a reload of the data the app shows, not of the page (R16), so that the text the person is typing stays and the waiting messages, which are kept in the browser (D-132), are not touched. A new version of the web code is the update strip of TOKI-082, not this work. Owner: Thanh Truong.
5. The numbers of the client are not all in the log. Decided in this spec as technical choices, each with its reason in the requirement or in Limits: the amount of jitter, 20 percent (R11); the reset of the delay after 10 seconds of a held connection (R11); the 10 seconds to receive `ready` (R11); the 60 seconds of silence, equal to the server's own timeout (R13); the 3 seconds of grace come from journey F37 (concern 6); the page sizes and the queue limit (Limits). Owner: Thanh Truong.
6. The 3-second rule for a short drop. Decided: journey F37 states that a drop of under 3 seconds shows no strip, and D-091 accepts the phase-1 journeys as the baseline; D-102 and D-140 say the banner stays the whole time the connection is down. R15 follows both: `offline` begins after 3 seconds and lasts until `ready`. Per D-091 the behaviour is accepted, not the wording of the journey. Owner: Thanh Truong (product owner).
7. What a person sees in a tab that was closed with 4430. Not decided. The gateway closes the oldest connection of a person who opens a 21st (TOKI-038 R10) and the client does not reconnect (R12), so the tab stays disconnected until it is reloaded; by D-102 a disconnected tab shows 'Offline: showing saved messages', and by D-079 the messages it sends wait and nothing else is written, so in that tab a person who is on a good network sees an offline banner and cannot write until they reload, and no text in the log says why. Proposal, not a decision: show the same banner and give no separate text. Alternative: a text that tells the person to reload this tab, or a reconnect that ends the oldest of the others. Question for the product owner: what the person must see and be able to do in that tab. Owner: Thanh Truong (product owner).
8. A close that this table does not know. Decided in this spec: a 4401 with an unknown reason stops the connection and is reported as `unauthenticated`, so the session state decides (it shows the modal when the person was signed in); any other unknown code retries with the delay, because a stop with no notice would leave the tab dead without a reason and a retry costs one request at most every 30 seconds (R12). Owner: Thanh Truong.
9. The line with the sync engine and the cache. Decided in this spec: this ticket owns the socket, the retry, the cursor, the request and the order and uniqueness of the events handed over; TOKI-040 owns what an event does to the cache, the messages that wait, and what a reload drops (R19, Plan changes). Until TOKI-040 is built the app's consumer does nothing and its reload is a new bootstrap, so a build with this ticket alone shows no new message. Owner: Thanh Truong.
10. The `online` event and the sleeping laptop. Decided in this spec: the browser's `online` event shortens a wait through `retryNow` (R20); a laptop that wakes with a dead socket is found by the 60-second silence (R13) or by the `online` event, whichever comes first; the page's visibility is not used (a hidden tab keeps its connection, and a browser may delay a timer of a hidden tab, which only delays the check). Owner: Thanh Truong.
