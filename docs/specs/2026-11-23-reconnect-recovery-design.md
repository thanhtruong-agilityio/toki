# Reconnect design

Date: 2026-11-23 · Status: draft for review (concern 7 is open for the product owner)
Intent: docs/intents/reconnect-recovery.md (Thanh Truong)
Ticket: TOKI-039

## Goal
A person who leaves Toki open must find it right again after the connection comes back, with nothing for them to do: every event that concerns them and happened while the client was not connected is applied, once and in order, and a client that was away longer than the server keeps events starts again from a fresh load. Today the gateway (TOKI-038) pushes events to a connected client only, and the client has no socket.
This work builds the client side of the connection (open, wait and try again, answer the heartbeat, know what each close code means), the number the client has applied up to, the request that returns the events a client missed (client and server halves), and the hand-off of those events, in order, to the code that applies them (TOKI-040). It also publishes the connection state that the offline banner and the waiting messages follow, and shows nothing itself.

TOKI-038 does not build this route (its Scope leaves it to this ticket), so this ticket owns it in full.
  - The connection state (R15), the hand-off of live frames and of client frames (R19), the contract table of the connection (Design), and the wiring in `apps/web`: the address of the socket, start and stop with the session, the recovery of a tab that was stopped by `replaced`, the browser's `online` and `offline` signals (R20).

## Requirements
Server: the events a client missed
- R1. `GET /api/v1/events?after=<n>&limit=<m>` is a route of the `realtime` module (`events-route.ts`), registered by `app.ts` inside the `/api/v1` scope, so it needs a valid session like every route there (TOKI-022 R24: no session is 401, an ended session or a deactivated account is the 401 of TOKI-022 R25 and R27). The query is one Zod object in `packages/shared/src/realtime/catch-up.ts`: `after` is required, an integer from 0 to 9,007,199,254,740,991 (the range of `events_number_check`, TOKI-036 R13); `limit` is optional, an integer from 1 to `CATCH_UP_LIMIT_MAX` (500), and defaults to `CATCH_UP_LIMIT_DEFAULT` (200). A missing, repeated or non-integer `after`, a `limit` out of range and any other query key are 400 `validation_failed`, in the error format of TOKI-004. The route writes nothing, takes no lock and sets `Cache-Control: no-store` and no other cache header. It is a `GET`, so the Origin rule of TOKI-022 R46 (which lists `GET` as exempt) does not apply; it adds no CORS header, so a page of another origin cannot read the answer, and it changes nothing, so a cross-origin request has nothing to forge. Check: no session, an ended session and a deactivated account give the 401 of their code; `after` missing, `-1`, `1.5`, `abc` and `after=1&after=2`, `limit` 0 and 501 and a key `x=1` give 400 `validation_failed`; `after=0` and `limit` 500 give 200; the response has `Cache-Control: no-store` and no `Access-Control-Allow-Origin`; a request with a foreign `Origin` header is answered as any `GET` is; the route list of TOKI-004 R10 lists `/api/v1/events`.
- R2. The answer is `{ "events": EventObject[], "through": number, "hasMore": boolean }`, the Zod object `catchUpAnswerSchema` of `packages/shared/src/realtime/catch-up.ts`. `EventObject` is the `event` object of an `event` frame of TOKI-038 R12 and checks the envelope only: `number` an integer, `kind` any string, `conversationId` a string or null, `createdAt` an ISO 8601 string, `data` an object. It is the schema `eventObjectSchema` that `frames.ts` exports on its own and the `event` frame is built from; it does not check `data` for each known kind (that registry serves the server that builds an event and the tests, TOKI-038 R12). Reason: a client older than the server must take an event of a kind it does not know (R10), so one new kind must not make a whole page `invalid_response`, drop the socket and retry for ever. The object is built by `toEventObject(row)`, the one function that maps a log row to an event object; TOKI-038 R12 says only one function does it, so the route and the gateway call the same one, which TOKI-038 puts in `realtime/event-object.ts` and exports from `realtime/index.ts` (the change request in Plan changes names both, and says what this ticket's build does if TOKI-038 was built without it). A live event and a missed event of the same row are the same object. Check: the shared schema parses the answer of every test; for one log row, the object in the answer equals the `event` of the frame the gateway sends for it (one test with both); a page with an event of kind `x.y` and `data` `{}` parses; a page with an event whose `number` is a string does not.
- R3. The route reads in one `READ ONLY` transaction at `REPEATABLE READ` (the one the gateway uses for its snapshot, TOKI-038 R8, and the bootstrap build uses, TOKI-031 R10; `app.ts` opens it and passes it in), so the four reads see one state: `M`, the number of the last event, with `getLastEventNumber(tx, workspaceId)` (TOKI-036 R19; `realtime` has its own, and may not import the bootstrap's `readEventNumber`); the set of conversations of the person, with the same function `listConversationIdsOfUser` and the same DM condition as the gateway's map (TOKI-038 R8; `app.ts` passes the one function to both); the oldest kept number, with `getOldestEventNumber(tx, workspaceId)` (TOKI-036 R20); and the raw events, with `readEventsAfter(tx, workspaceId, after, limit)` (TOKI-036 R26), the one read of the log. The route reads the workspace id of the account as the bootstrap build does. It adds no other read of `events` and no index. Check: counted with the wrapper of TOKI-031 R14, a request runs a fixed number of statements (the number is written in the test) whatever the number of events or conversations; a spy shows that no statement reads `events` except those of `readEventsAfter` and `getOldestEventNumber`, and none reads the counter except `getLastEventNumber`; a source search finds no `from events` in this ticket's files.
- R4. The audience of an event of the page is the audience of TOKI-038 R15, read from the set of R3: an event with scope `conversation` is kept when its conversation is in the set of the person; an event with scope `user` is kept when it is addressed to the person; an event with scope `workspace` is kept. Every other raw event is dropped. A conversation that the person has left, or never joined, is not in the set, so none of its events is returned, and the person who left is told by the `conversation.left` event of scope `user` (TOKI-038 R9, R20). A conversation that the person joined after `after` is in the set, so its events inside the page are returned, those before the joining included; this shows the person nothing they could not read through the history route, which gives every message of a conversation they belong to (TOKI-037 R14). Check: the scenario of TOKI-038 R15 (a member, an Admin who is not a member, a person in another conversation, the twelve channel routes and a DM): the answers for the two outsiders, searched whole, hold no id, name, topic or message of the private channel and of the DM; the member's answer holds every event of the scenario in number order; a person added in the middle of the range gets the events of the conversation from before the adding; a person removed in the middle gets `conversation.left` and no `member.removed` or later event of that conversation; the first message of a DM reaches the other person together with its `conversation.appeared`; an event is returned at most once.
- R5. Paging. `events` holds the kept events of the raw page in increasing number order. When the raw page holds fewer than `limit` events, `through` is `M` and `hasMore` is false. When it holds `limit` events, `through` is the number of the last raw event, kept or not, and `hasMore` is true when `through` is below `M`. So a client that sets its number to `through` after each page moves forward even over a page where every event was for someone else, and never returns to a number it passed. A page may hold fewer events than `limit`, or none, with `hasMore` true. Check: with 450 events of which one in three concerns the person and `limit` 200, three requests give `through` 200, 400 and `M`, `hasMore` true, true and false, and the kept events of the three pages are all the person's events once; a request with `after` equal to `M` gives no events, `through` equal to `M` and `hasMore` false; a page of 200 raw events none of which is the person's gives `events` empty, `through` 200 and `hasMore` true; `M` is read in the same snapshot (R3), so an event committed during the request is in no page of it and is returned by the next request.
- R6. An `after` that the log can no longer serve, or that costs more than a reload, is refused with status 410 and the code `events_expired` (added to `ErrorCodes` in `packages/shared/src/error.ts` and to the codes the API client knows), in the error format of TOKI-004, and no event is returned. With `M` and `oldest` (`getOldestEventNumber`, null when the log holds no event) read in the same snapshot, `after` is expired when any of these holds: `after` is above `M` (the client holds a number that this log never reached); `oldest` is null and `after` is not equal to `M`; `oldest` is not null and `after + 1` is below `oldest` (the first event the client needs, `after + 1`, was pruned); or `M - after` is above `CATCH_UP_GAP_MAX` (5,000). The last rule bounds the work after a long absence in a busy workspace: the client asks for pages of `CATCH_UP_LIMIT_MAX` (500, R17), so a served catch-up is at most 10 requests, and a longer gap is cheaper as a reload (R16); the gap counts every event of the workspace, not only the person's, so it is a bound on rows read. The rule does not read a clock: pruning (TOKI-036 R21, `EVENT_RETENTION_DAYS` 7) decides what is kept. Check: with events 1 to 10 and 1 to 5 pruned (`oldest` 6), `after` 5 is served, `after` 4 is 410, `after` 11 is 410, and `after` 10 gives no events with 200; with the log empty after a prune of everything and `M` 10, `after` 10 gives 200 and `after` 9 is 410; with `M` 6,000 and no prune, `after` 1,000 is served and `after` 999 is 410; with the `TestClock` moved 8 days and `pruneEvents` run, an `after` whose `after + 1` is below the oldest kept number is 410 and the number just before the oldest kept number is served; the 410 body has the code `events_expired`.

Client: the connection
- R7. `packages/client-core/src/realtime/` exports `createConnection(options)` and its types. `options` has `url` (the address of the socket, given by the app), `timers` (the `Timers` of the API client: `after(ms, fn, label?)`; TOKI-032's type gets the optional third argument, which `createTimers` of the web app ignores and the test fakes record, Testing), `random` (a function that returns a number from 0 up to but not including 1), `catchUp` (a function `(after: number, signal?: AbortSignal) => Promise<CatchUpAnswer>`, which the app builds on the method of R17 with the limit), `onEvents`, `reload` (R19) and `onUnauthenticated` (a function `(code: string) => void`, which the app gives as `reportUnauthenticated` of the session store), and optionally `createSocket` (a function that opens a socket from `url` and returns a `SocketLike`: `send`, `close(code, reason)` and the four handlers `onopen`, `onmessage`, `onclose`, `onerror`; it defaults to `new WebSocket(url)`, a global that the allow list of boundary rule 1 has). The package reads no clock, no `window`, no `document`, no `navigator` and no `location`, and writes no text a person reads. The connection has `start(number)`, `stop()`, `retryNow()`, `suspect()`, `send(frame)`, `subscribeLive(listener)`, `subscribe(listener)` and `getState()` (R8 to R15, R19; the contract table in the Design lists every shape). Every timer it asks for has a label: `retry`, `heartbeat`, `ready-timeout`, `stable`, `grace`. Check: a type test calls every member; a search of the package for `window`, `document`, `navigator`, `location`, `Date.now(` and `new Date(` finds none; `pnpm lint` exits 0 (boundary rule 1); with no `createSocket`, a test with a stub global `WebSocket` shows `new WebSocket(url)` is called with the `url`; each timer of the connection carries its label.
- R8. `start(number)` takes the number of the last event the client has applied (after the first load it is `getEventNumber()` of the conversation store, which is the `eventNumber` of the bootstrap answer, TOKI-031 R11) and opens a socket. `number` is the connection's cursor: the highest event number the client has applied. The cursor never decreases except through R16, and no event with a number at or below it is applied (R10). A `start` while the connection runs stops the earlier socket first, as `stop()` does, and drops its queue; a `start` after a stop that the connection made itself (R12) opens it again. The connection does not open before `start` and does not call `catchUp` or `reload` before the `ready` frame. Check: with a fake socket, nothing is opened before `start`; two starts leave one open socket, the first closed with code 1000; no call of `catchUp` before `ready`; a `start` after a 4430 opens a socket.
- R9. On the `ready` frame `{ "type": "ready", "eventNumber": N }` (TOKI-038 R7), with `c` the cursor: when `N` is equal to `c`, nothing was missed and no request is made; when `N` is not equal to `c`, the connection calls `catchUp(c)` and, while `hasMore` is true, calls it again with the `through` of the answer. After each answer it hands the answer's `events` to `onEvents` (one call per answer, none for an empty one), waits for the call to end, and sets the cursor to `through`. When `hasMore` is false the catch-up is over. A 410 ends in R16. `N` below `c` is not an error and not a reload: `N` is where the gateway's live stream for this connection starts, it can trail the log by a drain, and `c` can come from the `M` of an earlier request, so a quick reconnect often sees `N` below `c`; the stream then resends events at or below `c`, which R10 skips, and every event above `c` still comes live. The request is made anyway for one reason: it answers 410 when `c` is above the last number of the log (a log that was restored or reset), a case in which live events would carry numbers the client has already applied and be skipped by mistake. `N` is not compared with the numbers of the events, because the numbers a person receives are not consecutive: an event for someone else leaves a hole in them, so a hole is never a sign of loss. Why this is enough: the gateway sends on this connection every event above `N` that concerns the person (TOKI-038 R7), and the request returns the events up to the number it read, which is not below `N` (it is read after `ready`; R5). Check: with a fake socket and a fake `catchUp`, `ready` with `N` equal to the cursor makes no request, with `N` above and with `N` below it makes a request from the cursor; a fake `catchUp` that answers no events and `hasMore` false for `N` below the cursor leaves the cursor and the stores as they were and calls no `reload`; three pages call `catchUp` with the cursor, the first `through` and the second `through`, `onEvents` receives the two non-empty answers in order and not the empty one, and the cursor ends at the last `through`; the answer of a request that is made when events have a hole in their numbers (1, 4, 9) is applied and the cursor ends at `through`, with no second request.
- R10. Live events. An `event` frame is parsed with the envelope schema of R2 (TOKI-038 R12); a text that is not JSON, a frame with an unknown `type` and an event frame of a `kind` that no code knows are not errors (an event of an unknown kind is handed to `onEvents` like any other, TOKI-040 ignores a kind it does not know). An `event` frame whose envelope is not valid (`number`, `kind`, `conversationId`, `createdAt` or `data` of the wrong type) is a failure of the stream: the connection drops the socket (R11) and goes on as for a lost connection, so the next catch-up starts from the cursor; it counts for R16. Events are applied one batch at a time, in number order: a live event that arrives while a catch-up or an `onEvents` call is running waits in a queue; when the running work ends, the queue is applied, skipping every event whose number is at or below the cursor (an event the catch-up already returned), and the cursor moves to the number of each applied event. An event is never handed to `onEvents` twice and never after an event with a higher number. The queue holds at most `CATCH_UP_QUEUE_MAX` (2,000) events. When it is full, the connection keeps the queue, sets the flag `overflowed` and discards every further live event; the socket stays open. When the queue has been applied it makes one catch-up from the cursor as in R9, clearing the flag at the moment it sends the first request: an event discarded before that moment was committed before the request reads its snapshot, so the request returns it, and an event that arrives after that moment is queued and told from the pages by number. Reason: the stream has a hole after the first discarded event, and the catch-up from the cursor is the only thing that fills it; dropping the socket instead would restart from the same cursor and overflow again on a long catch-up. Check: a live event with a number below the cursor is not applied; events that arrive during a catch-up wait for it and are applied after it in number order; an event that the catch-up already returned and that arrives live afterwards is applied once; a frame with invalid JSON, an unknown type and an event of kind `x.y` give no failure and the third reaches `onEvents`; an invalid envelope drops the socket and a new socket is opened after the first delay; with 2,001 events queued during a catch-up the socket stays open, the 2,000 are applied in order, a follow-up `catchUp` runs from the last applied number, an event that arrives while the flag is set is discarded and one that arrives after the request is sent is applied once, and the cursor ends at the last number.
- R11. Retry. After a socket is lost for a reason that R12 says to retry, the connection waits and opens a new socket. The wait for the attempt `k` (counted from 0 since the connection last held, below) is `RECONNECT_DELAYS_SECONDS[min(k, 4)]` seconds, where the list is 1, 2, 5, 10, 30 (D-129), multiplied by `1 - J + 2 * J * random()` with `J` equal to `RECONNECT_JITTER` (0.2). Decided in this spec: the log says "a little randomness" and no amount, so the amount is a technical choice, with its reason (a client that returns at 24 seconds and one at 36 do not meet at 30). The wait is a call of `timers.after` with the label `retry`. To drop a socket is to remove its handlers, call `close(4000, reason)` on it, and go on as for a lost socket: this one definition is used by R10, R13, R16, R17 and `suspect()` (R13). `k` goes back to 0 once a socket has been open for `RECONNECT_STABLE_SECONDS` (10) after its `ready` (a timer with the label `stable`, started at `ready` and cancelled by the loss), so that a server that accepts and closes at once does not keep the delay at 1 second. `retryNow()` cancels a wait that is pending and opens a socket at once; it does not change `k`, and it does nothing when a socket is open, when the connection is not started or when it has stopped itself (R12). A socket that opens but sends no `ready` within `READY_TIMEOUT_SECONDS` (10) is dropped as a lost socket (a timer with the label `ready-timeout`, cancelled by `ready`). Check, with the fake timers and a fake `random`: the delays asked with the label `retry` after eight losses in a row are 1, 2, 5, 10, 30, 30, 30, 30 seconds for `random` returning 0.5; with `random` returning 0 they are 0.8 times and with `random` just under 1 they are just under 1.2 times those values; a socket that held 10 seconds (the stable timer fired) and then closed waits 1 second; one that closed after 9 seconds and one that closed at once do not reset; `retryNow` with a pending wait opens a socket without waiting and the old wait is cancelled; with an open socket it opens nothing; a socket with no `ready` is dropped after 10 seconds.
- R12. What the connection does for each close. It reads the code and the reason of the close event and follows this table; the codes and reasons are those of TOKI-038 (Design, "Closing, codes and reasons"), constants of `packages/shared/src/realtime/limits.ts`:

  | Close | Action |
  |---|---|
  | 4401 with the reason `unauthenticated`, `session_ended` or `account_deactivated` | stop and do not retry; call `onUnauthenticated(reason)` (this is the 401 of a request: the session state shows 'Your session has ended', sign-in screens R24 and R39); `stoppedBy` is the reason |
  | 4401 with the reason `signed_out` | stop and do not retry; call nothing (this browser asked for the end, TOKI-038 R21: no notice; the cookie session is ended, so the next request is refused with a 401, which is the notice); `stoppedBy` is `signed_out` |
  | 4401 with the reason `replaced` | stop and do not retry; call nothing (a sign-in in this browser replaced the cookie session, TOKI-038 R21: no notice); `stoppedBy` is `replaced`; the cookie now holds a valid session, so no 401 will come and the tab does not stay dead: the app recovers it (R20, concern 12) |
  | 4401 with any other reason or none | stop and do not retry; call `onUnauthenticated("unauthenticated")`; `stoppedBy` is `unauthenticated` |
  | 4430 `too_many_connections` | stop and do not retry (TOKI-038 R10); `stoppedBy` is `too_many_connections`; `status` is `stopped`, which says nothing about what is shown: what a person sees in that tab is concern 7 and is not decided |
  | every other code and the loss of the connection with no close (1000, 1001 `going_away`, 1006, 1009, 1011 `server_error`, 4400, 4408, 4410, 4429, a failed handshake such as the 403 of TOKI-038 R4 which a browser shows as 1006, and a code that this table does not know) | retry with the delay of R11 |

  A connection that has stopped itself stays stopped (`status` `stopped`, R15): only `start` (R8) opens it again. `onUnauthenticated` is called at most once for a stop. Check: one case for each row, with the fake socket closing with that code and reason: the rows that retry ask `timers.after` for a delay and open a socket when it fires; the others open nothing, `getState().stoppedBy` is the reason, `onUnauthenticated` is called with the right argument or not at all, and `retryNow()` opens nothing; the session store of `client-core` (the real one) goes to `ended` for `session_ended` and `account_deactivated` with the codes of the table and stays `signedIn` for `signed_out`, `replaced` and `too_many_connections`; `status` is `stopped` for every stop of the table.
- R13. Heartbeat. A `ping` frame (`{ "type": "ping" }`, TOKI-038 R24) is answered at once with `{ "type": "pong" }`. The connection also checks the server: a timer with the label `heartbeat` and `HEARTBEAT_TIMEOUT_SECONDS` (60, the constant of TOKI-038) is started at the open of the socket and restarted at every frame received; when it fires the connection drops the socket (R11, reason `heartbeat_timeout`) and opens a new one after the delay of R11. It does not wait for the close event: a browser may take a long time to report a socket whose network is gone. `suspect()` does the same at once, with the reason `offline`: the app calls it when the browser says the network is gone (R20), so the banner of a laptop that lost its wifi does not wait up to 63 seconds (concern 10); it does nothing when no socket is open. Decided in this spec: 60 seconds, the number the server uses for the client, which is two missed pings (25 seconds apart) and a margin. Check: a `ping` gets a `pong` as the next sent frame; with the fake timers, no frame for 60 seconds drops the socket, a frame at 59 seconds restarts the count, a `ping` counts as a frame; the handlers of the dropped socket are removed, so a late `message` or `close` of it changes nothing; the new socket opens after the delay of R11; `suspect()` with an open socket gives `connecting` and a new socket after the first delay, with no `heartbeat` timer pending for the old one, and with no socket does nothing.
- R14. A frame the client sends is a JSON text. `send(frame)` sends `JSON.stringify(frame)` and returns true when the socket is open and the `ready` frame has been received, and false otherwise; it never throws. Check: false before `start`, before `ready` and after a close; true after `ready`; a frame of the typing ticket reaches the fake socket as text.

Client: state, reload, wiring
- R15. The connection state `getState()` is `{ status, catchingUp, stoppedBy, cursor }`, an object that is replaced and never changed (as the store state, client-core R12), with `subscribe(listener)` (returns the function that removes it; the listener gets no argument). `status` is `idle` (before `start`, and after `stop()`), `connecting`, `online`, `offline` or `stopped`. It is `online` from the `ready` frame until the socket is lost, and `catchingUp` is true from `ready` until the catch-up or the reload is over. It is `connecting` from `start` and from a loss, and becomes `offline` when `OFFLINE_GRACE_SECONDS` (3) have passed since the start or the loss without a `ready` (a timer with the label `grace`). A `ready` before the three seconds have passed means `offline` was never shown. When the connection stops itself (R12) `status` is `stopped` at once and `stoppedBy` holds the reason; `stopped` is not `offline`: it is set for a session that ended (a modal is shown by the session state), for `signed_out`, for `replaced` and for 4430, and it does not say what is drawn, so the proposal of concern 7 is not built into it. `stoppedBy` is null in every other status. Why `offline` follows a loss: the journey of F37 says a drop of under 3 seconds shows no strip, D-091 accepts it as the baseline of the phase-1 journeys, and D-102 and D-140 say the banner stays the whole time the connection is down, with no reconnecting state and no toast when it returns; `connecting` is internal, nothing draws it. TOKI-082 shows the banner when `status` is `offline` and hides it when it is `online`; TOKI-040 resends the waiting messages when `status` becomes `online`. `cursor` is the cursor of R8. The listeners are called once for each change of the object and not for a change that gives an equal state. Check: with the fake timers, a loss followed by `ready` before the grace timer gives `connecting` then `online` and never `offline`; a loss with no `ready` gives `offline` when the `grace` timer fires, and `online` at the next `ready`, with no state in between; `start` with a server that never answers gives `offline` after 3 seconds; a stop by 4401 or 4430 gives `stopped` with `stoppedBy` at once and never `offline`; `stop()` gives `idle`; `catchingUp` is true during a catch-up and false after; the state object is the same one until a change; a listener is called once per change.

## Design
### The path of a reconnect
1. The socket is lost (a close, a silence of 60 seconds, the browser's `offline` event, a failed catch-up). The state is `connecting`; after 3 seconds without a `ready` it is `offline` and the banner of TOKI-082 shows (D-102).
2. The connection waits 1, 2, 5, 10, 30 seconds (with the jitter), or less if the browser says `online`, and opens a new socket to `/ws` with the cookie. The gateway checks the session and answers `ready` with `N`.
3. The client compares `N` with its cursor `c`. Nothing was missed when they are equal. Otherwise it asks `GET /api/v1/events?after=c&limit=500` and applies each page before it asks for the next. A number that the server no longer keeps, or a gap of more than 5,000 events, is a 410, and the app reloads what it shows through TOKI-040's `reload`.
4. Live events that arrive during step 3 wait in a queue and are applied after it, skipping what the pages already gave.
5. The state is `online`, with no toast (D-102). TOKI-040 sends the waiting messages.

### Why the numbers are not consecutive and what that allows
The log numbers every event of the workspace, and a person receives only the events of their audience (TOKI-038 R15), so the numbers a client holds have holes. A client therefore cannot tell a lost event from an event for someone else by looking at numbers. The protocol does not need it: the server tells the client where the live stream starts (`N`), the request returns everything up to a number that is not below `N`, and everything above `N` comes live on the same connection, in order. A connection that fails starts again from the cursor. Duplicates are told by number only (R10), and the message itself is told by its id when TOKI-040 applies it, so a message sent while the connection flaps is stored once by the server (TOKI-037 R5) and shown once.

### The cursor
The cursor is the highest event number applied. It starts as the `eventNumber` of the bootstrap (TOKI-031 R11) and moves after each applied batch to the number of its last event, and after each catch-up page to its `through` (a number that is at least the last returned event and may be higher: R5). It lives in memory only (a `replaced` tab keeps it, R20). A page reload starts from a bootstrap and a new cursor, so the 7 days matter only to a tab that stays open: a laptop that sleeps for 8 days. The expiry rule reads the log, not a clock (R6): the log is what says whether the events are still there.

### Audience of the catch-up (decided in this spec)
The route uses the set of conversations of the person now, not the set at each event. A set at each event would need the history of membership, and the log holds it only as events. Using the set now is safe: a person never gets an event of a conversation they are not in (R4), and what they get from before they joined is readable by them anyway. It also gives them what they need: a conversation they joined during the absence has its `conversation.created`, `member.joined` or `members.added` event in the range (scope `conversation`, the conversation is in the set), and one they left has its `conversation.left` (scope `user`). Two consequences, both for TOKI-040: a `conversation.left` for a conversation the client never held must change nothing, and the events of one conversation inside a catch-up may begin with events from before the person was added, which only add messages the history route would give.

### Close codes (summary)
The table of R12. The codes are TOKI-038's. A tab that is told to stop by 4401 `signed_out` raises no notice, because this browser asked for the end; its next request is refused with a 401, which is the notice, if there is one to give. A tab told `replaced` is different: the cookie now holds a valid session, so no 401 will come, and the tab would stay `stopped` with a good session. So the app reads the session and either starts again from the kept cursor (the same person) or resets the tab as for a change of person (another person), R20 and concern 12.

## Data safety
- The route returns only what the audience rule gives (R4): no event of a private channel, a DM or an unjoined channel reaches a person outside it, an Admin who is not a member included. The test of R4 searches the answers of the outsiders.

## Open questions from the intent
- What does the client do after each close code of the gateway, in particular 4401 and 4430? Answered: the table of R12. 4401 stops the connection, with a notice for the three session reasons and none for `signed_out`; `replaced` stops it with no notice and the app recovers the tab (concern 12); 4430 stops it with no notice; everything else retries. What the person sees in a tab closed by 4430 is not answered: it is concern 7.
- Who asks the server for the missed events, with what request, and what does the server return for a number that is no longer kept? Answered: the client, with `GET /api/v1/events?after=<n>`, built here (R1 to R6, R9, R17); a number the log no longer holds, or a gap above 5,000 events, is a 410 `events_expired` and a reload (R6, R16; concerns 1 and 4).
- Who applies the events to the cache? Answered: TOKI-040; this work hands it the events in order and the reload trigger (R19, concern 9).
- What does the person see while the connection is down and when it returns, and is a short drop shown? Answered: the banner of D-102 for the whole time `status` is `offline`, none for a drop of under 3 seconds, no toast on return (R15, concern 6).
- What does the person see in a tab that the server closed because the person has too many tabs open? Not answered. Carried forward as concern 7.

## Areas of concern
1. Who builds the request for missed events. TOKI-038 leaves it to this ticket (its Scope, "The request that returns the events a client missed: TOKI-039"), and TOKI-036 names this ticket as the user of `readEventsAfter` and `getOldestEventNumber` (its "What the later tickets get"). Decided in this spec: this ticket builds `GET /api/v1/events` in the `realtime` module with the reads of TOKI-036 and the audience rule of TOKI-038 R15, adds the error code `events_expired`, and adds no read of the log of its own (R1 to R6). The answer reuses the gateway's one mapping function and one event schema, which TOKI-038 does not export today; the change request (name, file, export) is in Plan changes, with what this build does if TOKI-038 was built without it. Owner: Thanh Truong.
2. The audience of a catch-up. Decided in this spec (a technical choice): the set of conversations of the person now, in the snapshot of the request, not the set at each event (Design, "Audience of the catch-up"). Reason: a set at each event needs the history of membership; a person never gets an event of a conversation they are not in, and what they get from before they joined is readable by them through the history route (TOKI-037 R14, D-116 is about people who are not members). The cost, two rules for TOKI-040, is in the Design. Owner: Thanh Truong.
3. The numbers a client holds are not consecutive, so a hole is not a sign of a lost event, and the first load, a reconnect and a reload all start from the cursor. Decided in this spec (a technical consequence of TOKI-036 R16 and TOKI-038 R15): the client compares only the `ready` number with its cursor, asks for the range once, and applies live events above it (R9, R10). TOKI-036's remark that the client asks for a missing number is read as this request. Owner: Thanh Truong.
4. What "a long absence" means and what a reload is. Decided in this spec: the server says it, by the oldest number it keeps and by a bound on the gap (R6), not a clock in the client; with the retention of 7 days (TOKI-036 R22) this is an absence of about 7 days and more, or a gap of more than 5,000 events sooner; and the reload is TOKI-040's `reload()` (R16, R19): it keeps the windows on screen and the waiting messages (D-132), marks the windows stale and refreshes the list, and it is not a reload of the page, so the typed text stays. This work calls it with no argument and drops nothing. A new version of the web code is the update strip of TOKI-082, not this work. Owner: Thanh Truong.
5. The numbers of the client are not all in the log. Decided in this spec as technical choices, each with its reason in the requirement or in Limits: the amount of jitter, 20 percent (R11); the reset of the delay after 10 seconds of a held connection (R11); the 10 seconds to receive `ready` (R11); the 60 seconds of silence, equal to the server's own timeout (R13); the 3 seconds of grace come from journey F37 (concern 6); the page sizes, the 5,000-event gap, the queue limit and the two repeated failures (Limits, R6, R10, R16). Owner: Thanh Truong.
6. The 3-second rule for a short drop. Decided: journey F37 states that a drop of under 3 seconds shows no strip, and D-091 accepts the phase-1 journeys as the baseline; D-102 and D-140 say the banner stays the whole time the connection is down. R15 follows both: `offline` begins after 3 seconds and lasts until `ready`. Per D-091 the behaviour is accepted, not the wording of the journey. No decision states the 3 seconds: the number is in the journey F37 only, and this spec reads it as the rule; the owner can overrule it, and it is one constant (`OFFLINE_GRACE_SECONDS`). Owner: Thanh Truong (product owner).
7. What a person sees in a tab that was closed with 4430. Not decided. The gateway closes the oldest connection of a person who opens a 21st (TOKI-038 R10) and the client does not reconnect (R12), so the tab stays disconnected until it is reloaded; its `status` is `stopped` (R15), which does not say what is shown. By D-102 a disconnected tab shows 'Offline: showing saved messages', and by D-079 the messages it sends wait and nothing else is written, so if the same banner were shown, a person who is on a good network would see an offline banner and could not write until they reload, and no text in the log says why. Proposal, not a decision: show the same banner and give no separate text. Alternative: a text that tells the person to reload this tab, or a reconnect that ends the oldest of the others. Nothing in R12, R15, the contract table or TOKI-082's line builds the proposal in; they say what is shown is this concern. Question for the product owner: what the person must see and be able to do in that tab. Owner: Thanh Truong (product owner).
8. A close that this table does not know. Decided in this spec: a 4401 with an unknown reason stops the connection and is reported as `unauthenticated`, so the session state decides (it shows the modal when the person was signed in); any other unknown code retries with the delay, because a stop with no notice would leave the tab dead without a reason and a retry costs one request at most every 30 seconds (R12). Owner: Thanh Truong.
9. The line with the sync engine and the cache. Decided in this spec: this ticket owns the socket, the retry, the cursor, the request and the order and uniqueness of the events handed over; TOKI-040 owns what an event does to the stores, the messages that wait, and what a reload does (R19, Plan changes, the contract table). Until TOKI-040 is built the app's consumer does nothing and its reload is a new bootstrap, so a build with this ticket alone shows no new message. Owner: Thanh Truong.
10. The `online` and `offline` events and the sleeping laptop. Decided in this spec: the browser's `online` event shortens a wait through `retryNow` and its `offline` event drops the socket through `suspect()` (R13, R20), so the banner of a laptop that loses its wifi shows after the 3 seconds of grace and not after the 60 seconds of silence (F37: the banner stays the whole time); a false `offline` costs one reconnect; a laptop that wakes with a dead socket is found by the 60-second silence (R13) or by the `online` event, whichever comes first; the page's visibility is not used (a hidden tab keeps its connection, and a browser may delay a timer of a hidden tab, which only delays the check). Owner: Thanh Truong.

11. The volume of a catch-up. Decided in this spec (a technical choice): the client asks for pages of 500 and the server answers 410 for a gap above 5,000 events (R6), so a long absence in a busy workspace is at most 10 requests, each one a snapshot read, and a longer one is a reload; the gap counts the events of the whole workspace, so it bounds the rows read, not the person's events. Reason: the raw page is filtered after the read, so the number of requests depends on the workspace and not on the person; without a bound a person away for days in a busy workspace would make hundreds of requests. Owner: Thanh Truong.
12. A tab stopped by `replaced`. Decided in this spec (a technical choice): TOKI-038 R21 sends `replaced` to every tab of a browser when a sign-in replaces the cookie session; the cookie then holds a valid session, so no 401 comes, and the tab would be `stopped` for ever. The app reads the session (R20): for the same person it starts again from the kept cursor, so the catch-up repairs what was missed; for another person it signs that person in to the session store and the tab resets as for any change of person; with a 401 the session state shows its own notice; with a network failure it reads again after 30 seconds and at the next `online`. `signed_out` keeps the 401 as its notice, because the cookie session is ended. Owner: Thanh Truong.
13. A first load that fails. Decided in this spec (a technical choice about owners): the connection starts only when the conversation store is `ready` (R20), so a person who opens the app with no network has a `failed` store, an `idle` connection and no `offline` state. The banner and the retry of that load belong to TOKI-082 with the list screen (TOKI-033), which read the store's `failed` status as well as `status`; this ticket adds nothing for it and names the owner in Scope and in Plan changes. Owner: Thanh Truong.
14. How the connection reaches the engine and the typing store. Decided in this spec (a technical choice): one wiring file, `apps/web/src/realtime.ts`, which imports `client.ts`; `client.ts` imports nothing from it; the engine takes the connection through `sync.attachConnection` and not as a creation option, to avoid the cycle; each sibling ticket that builds second adds its own lines in that file (R20, the contract table). Owner: Thanh Truong.
