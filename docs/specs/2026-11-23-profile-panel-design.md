# Profile panel design

Date: 2026-11-23 · Status: draft for review (concerns 1, 2 and 3 are open for the product owner)
Intent: docs/intents/profile-panel.md (Thanh Truong)
Ticket: TOKI-057

## Goal
A person who sees a name, an avatar or a member row needs to learn who that is, and to message them from there. The pieces exist but are not joined: the message component draws a name and has a place for a profile to open (TOKI-042 R14), the Details panel draws member rows that are not pressable and a bare "Person" row for a direct message (TOKI-035 R13), presence has a hook and the three words (TOKI-055 R17, R19), and the date rules return a time and a UTC offset for any zone (TOKI-094 R1, R9). Nothing draws the profile.
This work builds the Profile panel: initials on a colour, name, job title, presence in words, status, local time and time zone, the Message button, the own-profile buttons and the "Deactivated" label. It builds its address, its Back (D-089), the press targets that open it (message name and avatar, member rows) and the profile card of a direct message's Details panel. The panel is one component that the People screen and the command palette mount with their own address.

## Scope
- In:
  - The panel and its card: the frame, the identity block, the presence row, the status, the two time rows, the buttons (R1 to R10).
  - Opening and closing: the route `/c/$conversationId/p/$personId`, the history rule, the single shell-panel call of the conversation page, Back (R11 to R13).
  - The press targets: the member rows and the group's rows of the Details panel, the avatar and name of a message, the profile card in the Details panel of a direct message, and the job title in the direct message header's second line (R14 to R16).
  - The reuse by other screens (R17), the texts (R18), the layout (R19) and what the panel does not have (R20).
- Out (not now):
  - Presence data, the dot and the three words: TOKI-055. This work reads them.
  - Status: setting it, the modal, its timer and its text: TOKI-056. This work shows the text and offers the entry to it.
  - The columns and the requests that store a person's job title, time zone and status text, and Preferences where they are changed: the accounts server ticket named in concern 5, TOKI-056 for the status text, and TOKI-078 for the form. This work adds no column, no request and no migration.
  - The People screen and its cards, which open this panel: TOKI-079. The command palette and its choice of a person: TOKI-071. The address each of them gives the panel is theirs (R17).
  - "Start a Meet" (phase 4) and the Guest role (phase 5, no Message button on a guest's profile, D-050): not drawn.
  - A picture, an email address and a "last seen" time: none is shown (R20).
  - Live changes of a person's fields (job title, time zone, status) arriving from another device: the sync engine of TOKI-040 applies the events to the store; the panel redraws from the store and adds nothing.
  - The shell's slot, the panel frame and its widths: TOKI-015 and TOKI-033.

## Design

### The view and where each field comes from
```
store person (TOKI-032 getPerson)        id, displayName, role, status          exists today
  + jobTitle, timeZone                   accounts server ticket (concern 5)
  + statusText                           TOKI-056 (R12, useStatusText)
presence hook (TOKI-055)                 state, word                            from the snapshot
clock + timers (apps/web)                now, minute redraw
```
`useProfile` is a plain mapping of these into the `ProfileView` of R2, with no request of its own. The bootstrap call carries none of the three added fields today and its strict schema rejects them (TOKI-031 R12); the ticket that adds each field adds it to that schema and to the store's person in its own change, so this work reads an optional key and needs no change to the call. The store holds every person of the workspace, deactivated ones included (TOKI-031 R5), so a profile opened from an old message has its data.

### How the panel opens, in order
1. A person presses a name or avatar on a message, a member row or (in a later ticket) a card. The press calls `open(personId)` (R11).
2. The router goes to `/c/{conversationId}/p/{personId}` with the history rule of R11. `profileRoute`'s `beforeLoad` drops a stray `panel` (R13).
3. `ConversationPage` computes its one shell-panel choice: the profile when `personId` is set, otherwise the thread, otherwise Details, otherwise nothing (R13).
4. `ProfilePanel` reads `useProfile(personId)`, draws the card, and calls `onClose` for Back, Close and Escape (R12).

### Decided in this spec
- The address. A path child `/c/$conversationId/p/$personId` and not a search parameter. The thread is a path child already (TOKI-045 R16), the panels are one slot, and a search key would add a second validator rule to the merged `validatePanelSearch` of TOKI-035 and a second key that the thread route has to drop. A path segment needs none of that and shows the person in the address, so a copied link opens the same profile (D-089: every place has an address).
- The history rule. A profile opened over Details or over another profile replaces the entry; one opened over a thread or over no panel pushes one. This is TOKI-035 R8 and TOKI-045 R16 read together with D-089 ("Back closes the side panel first, then returns to the previous place"): the panel that Back closes is the profile and everything above the conversation with it. The prototype's `closepanel` also closes the whole panel.
- The hook, not a plain function, in the message component. TOKI-042 R14 types `openProfile` as a plain function, but opening needs the router, and a module that the message component imports cannot import the router module (the cycle that TOKI-045 R16 avoids). A hook that takes `conversationId` and returns a stable function has no subscription, so a row still re-renders only for its own parts (TOKI-041 R21). The change request is in Plan changes.
- Edit profile leads to Preferences. Preferences is where display name, job title and time zone are changed (flow of Preferences, FR-43 and the plan line of TOKI-078), so an editor on the profile would duplicate it. Edit profile navigates to `/prefs`, which TOKI-099 R21 built; TOKI-078 owns the page. If the product owner wants the fields edited in place, this requirement and TOKI-078 change together.
- The UTC offset text. `UTC+7`, `UTC+5:30`, `UTC-3:30` and `UTC` for 0: the shortest form that reads without a leading zero, with minutes only when they exist. The date rules hand the choice to this ticket (TOKI-094 Scope); the log gives none.
- The minute redraw. At the next UTC minute, then each minute, because every zone's offset is a whole number of minutes. A redraw each second, or at the start of each person's minute, would cost more and show nothing more.
- Presence before a snapshot. No row and no dot, as TOKI-055 R17 draws none, so the panel never says "Away" for a person whose state is not known.
- No Message button in a direct message's own card, and none for oneself (TS-190); a press would only navigate to the conversation that is open.
- A group's rows and a channel's rows open the same panel; a group has no card because it has more than one other person.
- The job title in a row is one muted line under the name, as the prototype's `mrow` is. The Admin tag is drawn on the profile and not on the rows (flow F40 names the profile; the rows have no tag in the prototype).

## Areas of concern
1. The Time zone row: UTC offset or a city. Not decided. D-144 (an assumption the product owner accepted) reads "Profile: local time and a city"; the plan line of TOKI-057 and flow F31 say "time zone as a UTC offset"; the prototype shows the city name (`city`, for example "Manchester") and no offset; Preferences lists display name, job title and time zone, with no field for a city. A city would need a field that no ticket adds, or a name worked out from the IANA zone (`Asia/Ho_Chi_Minh` gives "Ho Chi Minh", not the prototype's "Ho Chi Minh City"). Proposal, not a decision: the row shows the UTC offset only (R7), because the offset is what the plan and the flow ask for and needs no new field. Question for the product owner: offset only, or offset and a city, and if a city, where it comes from. Owner: Thanh Truong (product owner).
2. A person with no time zone. Not decided. No decision gives a default time zone and the accounts spec adds the column without one; a new account's zone is not set by any flow (Preferences has the field). D-144 covers only a zone that was set. Proposal, not a decision: with no zone the Local time and Time zone rows are not drawn (R6, R7) and nothing is guessed from the viewer's device. Question for the product owner: should a new account get a zone (for example the browser's at first sign-in), and what does a profile show until one is set. Owner: Thanh Truong (product owner).
3. The profile of a deactivated person. Not decided. Flows F31 and F41 give the label and the missing Message button; the log does not say whether the profile still shows presence, the status or the local time. The server gives `away` to every deactivated person, so a presence row would say "Away" for someone who cannot sign in (the same question as concern 2 of TOKI-055, about the dot). A status text may be stale, and a local time still tells where the person was. The status has the same question in concern 2 of TOKI-056, and the dot in concern 2 of TOKI-055. Proposal, not a decision, built as written in R4, R5 and R10 and the same as the proposals of those two: no presence row and no status block; job title, local time and time zone stay. Question for the product owner: confirm these, or hide the time rows too. Owner: Thanh Truong (product owner).
4. The history rule for a profile opened over Details or over another profile. Decided in this spec: it replaces the entry (R11), so one Back ends on the conversation. The alternative, a pushed entry, would make Back return to the Details panel, which reads D-089 as "close the panel I am looking at" and not "close the side panel". The prototype closes the whole panel. If the product owner prefers a step back to Details, only R11 and R12 change. Owner: Thanh Truong.
5. Who adds job title and time zone, and how they reach the screen. Decided: not this work. The merged accounts spec (concern 8 of `docs/specs/2026-11-17-account-tables-design.md`, decided by Thanh Truong as product owner) places a server ticket "Profile and preferences (server)" before TOKI-078 and TOKI-057 that adds the columns for display name, job title, time zone and status text with the request that saves them; the bootstrap spec (R12) makes each such ticket add its field to the strict schema and the store's person. The plan has no such ticket, and the seed-data spec (concern 1) says TOKI-057 and TOKI-078 add the columns, which this spec does not. Decided in this spec: the panel reads three optional keys `jobTitle`, `timeZone` and `statusText` of the store's person (the names that the bootstrap test already lists as "keys that other tickets add later"), and shows nothing for a missing one. If that ticket names a field differently, only `use-profile.ts` changes. The plan needs the ticket added before TOKI-057 (Plan changes). Owner: Thanh Truong.
6. How other screens open the panel. Decided in this spec: `ProfilePanel` takes `personId` and `onClose` and no route (R17); TOKI-079 and TOKI-071 give it their own address and use `useOpenProfileAt`. The log gives the profile no address of its own beyond D-089's "each has an address", and the technical design's list of paths has none for it. Owner: Thanh Truong.
7. The change to the message component's extension. Decided in this spec: a hook, `useOpenProfile(conversationId)`, replaces the plain function `openProfile` (R11, Plan changes), because the router cannot be imported where the message component is. The request is made while TOKI-042 is still a pull request. If TOKI-042 is built first with the plain function, this work changes the one member and its test. Owner: Thanh Truong.
8. The Vietnamese words of R18 and the text of the unknown person. Decided in this spec: they are drafts and a proposal under D-139, reviewed in TOKI-080; the keys are what the code reads. Owner: Thanh Truong.
