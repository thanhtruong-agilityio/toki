# client-core: sync engine design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/client-sync-engine.md (Thanh Truong)
Ticket: TOKI-040
Needs: TOKI-037 (message API: `MessageEntry`, the send and history routes, `lastMessageAt`) and TOKI-038 (the events and live frames and their schemas in `packages/shared/src/realtime/`), as revised in their open pull requests; TOKI-036 (event numbers and retention); TOKI-032 (the conversation store this work extends). It is used by TOKI-039, which hands it the events; see Lines with the neighbouring work.

## Goal
The server stores messages and pushes numbered events, but the client keeps nothing of them. The conversation store of TOKI-032 never changes after its first load, there is no place that holds the messages of a conversation, and a message cannot be sent so that it shows at once. This work builds, in `packages/client-core`, the sync engine: the cache of the messages of each conversation (ordered, without duplicates), the rules that apply each event and live notice to the conversation store and to that cache, and the optimistic send with its three states, its single automatic try and its kept-in-the-browser queue. It holds no text and uses no browser API: the browser pieces (the storage of the waiting messages, the socket) are given to it.

## Scope
- In:
  - Two typed methods of the API client: send a message, read history (R2).
  - The message windows: the state a screen reads, order, duplicates, the four loads, what a switch of conversation keeps (R3 to R6).
  - The optimistic send: the client-made id, the states `sending`, `waiting`, `failed`, the queue, the confirmation by answer or by event, Retry and Delete, the single automatic try, the kept-in-the-browser queue through a storage port (R7 to R12).
  - The entry points the connection calls: `onEvents`, `reload`, `applyLive`; what every event kind of TOKI-038 does to the conversation store and to the windows (R13 to R17).
  - The additions to the conversation store that the effects need (R15), the seams that later tickets use (R18), the life of the engine (R19), cost and stability (R20), the wiring in `apps/web` (R21) and the contract (R22).
- Out (not now):
  - The socket, the retry delays, the heartbeat, the cursor, the request for missed events, the offline state and what a close code means: TOKI-039. The engine only reads the connection state it publishes and is handed the events it returns.
  - Drawing: the list of messages (TOKI-041), the message and its states (TOKI-042), the composer, its limits and its draft (TOKI-043), the offline banner and the blocking of other actions (TOKI-082).
  - Threads, reactions, edit, delete, pins (TOKI-045 to TOKI-048): they add their keys to `MessageEntry` and register their event kinds through R18.
  - Unread counts and the read pointer (TOKI-053): it reads the events through R18 and calls `setUnread` and `clearUnread` of TOKI-032.
  - The typing signal (TOKI-044); this work only calls its `clear` (R16).
  - Keeping the message cache across a reload (concern 2).

## Requirements
Package and requests
- R1. The engine is `createSyncEngine(options)` of `packages/client-core/src/sync/`, exported from the package index with its types. `options`: `conversations` (the store of TOKI-032 with the additions of R15), `api` (the methods of R2), `newId` (a function that returns a new UUID version 7; the app gives the generator of `apps/web/src/ids.ts`), `clock` (`Clock` of `@toki/shared`, read only for `localTime` of R7), `outbox` (the storage port of R12), optional `connection` (`{ getState(): { status }, subscribe(listener): () => void }`, the state object of TOKI-039 R15) and optional `typing` (`{ clear(conversationId, userId): void }`, TOKI-044 R12). The package keeps its rules: no DOM or browser global, no text a person reads, no key of `@toki/i18n`, no `Date.now(` and no `new Date()` (TOKI-008 R19), no timer of its own. Check: `pnpm lint` and the search script of TOKI-008 find nothing in `packages/client-core/src/sync/`; a type test builds the engine with only the required options.
- R2. Two methods of `createApiClient` (TOKI-032 R9, same rules: one request core, 10 seconds, no retry, a path part encoded, an optional `signal` last, neither `headers` nor `timeoutMs`). `api.messages.send(conversationId, { id, text }, signal?)` sends `POST /conversations/{id}/messages` with exactly that body and returns `{ status, message }`, `status` being 201 or 200 (TOKI-037 R3, R5) and `message` a `MessageEntry`. `api.messages.history(conversationId, query?, signal?)` sends `GET /conversations/{id}/messages` with `limit`, `before`, `after` or `around` only when given (never two of the three positions) and returns `{ messages, hasOlder, hasNewer }` (TOKI-037 R11). Both read the answer with the response schemas that TOKI-037 R22 exports from `packages/shared`, in the form that drops unknown keys (TOKI-032 R3), so a key that TOKI-045 to TOKI-058 add reaches the cache. The engine sends no `limit`, so the page size is the server's default (TOKI-037 concern 1 is open and does not touch this work). Check: with the fake `fetch` of the existing tests, each method sends the method, path, query and body as written and parses a good answer; a send with an extra key in the answer keeps it; the history request has no `limit` unless given; an error answer ends as an `ApiError` of the existing kinds.

The windows
- R3. State a screen reads. `getMessages(conversationId)` returns a `MessageWindow`: `{ status, error, items, hasOlder, hasNewer, isLoadingOlder, isLoadingNewer, stale }`. `status` is `idle` (nothing loaded), `loading` (the first load of a window that holds no confirmed message), `ready` or `failed` (only while no confirmed message is held); `error` is the `ApiError` of the last failed load or null; `stale` is true after `reload` (R19) until the next latest load. `items` holds first the confirmed messages and then the waiting ones (R4). For a conversation never touched `getMessages` returns one frozen empty window, the same object for every such id. `subscribeMessages(conversationId, listener)` returns the function that removes it; the listener is called once for each change of that conversation's window and never for a change of another conversation's. A window is replaced and never changed in place, so two calls with no change in between return the same object (`useSyncExternalStore`). Check: two calls give `===` objects; a change in conversation `a` calls the listener of `a` and not that of `b`; a snapshot kept before a change is not altered by it.
- R4. Order and duplicates. A confirmed message is placed by the pair (`Date.parse(createdAt)`, `id`), the time first and then the id in code-point order, which is the order of TOKI-037 R9 and R12; a message is never placed after one that follows it in that order, and a message whose `id` is already in the window is not added again (the held one is replaced by the one that arrives, because a later one is the fresher: TOKI-047 and TOKI-046 change a message in place). The waiting messages follow all confirmed ones, in the order they were pressed. A message placed in the middle (a page that fills a hole, a message of an earlier time) takes its place by that pair. Check: five messages given in a shuffled order, two with one time and ids in both orders, land in the pair order; the same message twice (a page and an event, a send answer and an event) leaves one; a waiting message stays after a confirmed message that arrives later.
- R5. The four loads. `loadLatest(id)`, `loadOlder(id)`, `loadNewer(id)` and `loadAround(id, messageId)` call `api.messages.history` with no position, `before` the oldest confirmed message, `after` the newest confirmed message, and `around` the message. Each returns a promise that never rejects: the outcome is read from the window (`status`, `error`, `isLoadingOlder`, `isLoadingNewer`). `loadOlder` and `loadNewer` do nothing (no request) when `hasOlder` or `hasNewer` is false, when the window holds no confirmed message, or when the same load is already running. The answer is merged as follows, and `hasOlder` and `hasNewer` are taken from it as it applies to the side the load extends:

  | Load | Merge | Flags |
  | :---- | :---- | :---- |
  | latest | the page is merged with the held messages when they share an id or the held newest is in the page; otherwise it replaces them (the held window was a place far from the end) | both from the page when it replaced; otherwise `hasOlder` of the held window or the page's, whichever says there is more, and `hasNewer` false |
  | older | added before the held oldest | `hasOlder` from the answer |
  | newer | added after the held newest | `hasNewer` from the answer |
  | around | replaces the held messages unless the page shares an id with them, then merged | both from the answer when it replaced |

  A failed load changes no message, sets `error`, leaves `status` `ready` when messages are held and sets `failed` when none is held. A load that was begun before `reset` (R19) or before the person left the conversation is ignored when its answer comes. A 403 or 404 answer for a conversation the engine holds does nothing else (the store's entry is changed by events, R14). Check: a fake `api` with 120 messages in pages of 20 gives, from `loadLatest` and six `loadOlder`, every message once, in order, with `hasOlder` false at the end; `loadNewer` after an `around` window reaches the end with `hasNewer` false; a latest load over a far window replaces it; a second `loadOlder` while one runs sends one request; a failed `loadOlder` keeps the messages and sets `error`; `loadOlder` with `hasOlder` false sends none.
- R6. What a switch keeps. The windows stay in memory when the screen shows another conversation, so switching back shows the held messages at once (NFR-13: under 100 ms). `loadLatest` on a window that is `ready`, not `stale` and has `hasNewer` false sends no request, because the events keep such a window current (R16). A window is dropped only by `reset`, by the removal of the conversation from the person (R14) or by nothing else; there is no size limit (the memory is bounded by what the person scrolled, and is freed by `reset`). Check: after a load, a second `loadLatest` sends no request and `getMessages` is the same object; a `stale` window sends one; a window with `hasNewer` true sends one.

Sending
- R7. Optimistic send. `send(conversationId, text)` returns at once, with no wait on the network, a new id made by `options.newId()`, and puts a waiting-list item for it into the window of that conversation, so the message shows at the end of `items` before any request is answered. The item is `{ kind: "pending", id, conversationId, text, authorId, delivery, error, localTime }`: `authorId` is the id of the signed-in person, `localTime` is `clock.now()` at the call (it is shown beside the message only until the server's `createdAt` replaces it), `delivery` is `sending`, `waiting` or `failed` (R10), `error` is the `ApiError` of the last failure or null. The text is kept as given (no trim, no change). `send` returns `null` and queues nothing when no signed-in person is held or when the text holds no character that `String.prototype.trim` of JavaScript does not remove (the rule of TOKI-037 R4: nothing is sent that the server would refuse as white space); the composer (TOKI-043) owns the 10,000 code points rule and the counter, and the engine does not repeat it. Check: the item is in `items` synchronously, before the fake `api` answers, with `delivery` `sending`; the id is the one `newId` returned; `send("c", "   ")` returns null and makes no item and no request; the text is unchanged.
- R8. The queue. Waiting messages are sent in the order they were pressed, one request at a time for each conversation, and the next one of that conversation is sent when the earlier one has ended (answered, failed or put back to waiting), because the server orders by the time it handles the send (TOKI-037 concern 4); different conversations send in parallel. A message of `failed` state does not hold back the messages after it. The request is `api.messages.send(conversationId, { id, text })`, with the id of the item, and has a signal that `reset` aborts. Check: three sends to one conversation call the fake `api` once, the second after the first answers; two conversations call it twice at once; a failed first message does not stop the second.
- R9. Confirmation. A send answer (201 or 200, the same body, TOKI-037 R5) replaces the item by the `MessageEntry` of the answer: the item disappears from the waiting list and the message is placed by R4. An event `message.created` whose `message.id` is the id of an item does the same (R16), so the message becomes solid by whichever comes first, and the one that comes second changes nothing: the answer after the event finds no item and no message is added twice, the event after the answer finds the message and replaces it by an equal one. Both leave exactly one message with that id. For a `dm` or `group_dm`, a confirmed send also sets `lastMessageAt` of the conversation's entry to the message's `createdAt` when it is newer than the held value, so the list order of F09 follows the person's own send without waiting for the event (TOKI-037 R21). Check: answer before the event and event before the answer each leave one message and no item; a replay of the same event leaves one; a DM entry with `lastMessageAt` null has the time of the confirmed message; a channel entry gets no such key.
- R10. Offline, failure and the single automatic try. This is the reading of D-079, D-097, D-087, D-126 and the journey F11 (decided in this spec, concern 5). Let `status` be the `status` of `options.connection.getState()` (TOKI-039 R15); with no `connection`, or `idle`, the engine behaves as `online`.
  (a) A message pressed while `status` is `offline` is not sent: `delivery` is `waiting`. When `status` becomes `online`, every waiting message is sent once, by the queue of R8 (the one automatic try of D-097). A message pressed when `status` is `online`, `idle` or `connecting` is sent at once with `delivery` `sending`.
  (b) A send that ends with an `ApiError` of kind `network` or `timeout` (a request with no answer after 10 seconds is the `timeout`, D-126) while `status` is `offline` or `connecting` goes back to `waiting` and does not count as the try; while `status` is `online` or `idle` it is `failed`.
  (c) Every other error answer (a 4xx or 5xx status, `invalid_response`) makes the message `failed` at once, with the `ApiError` kept in `error`, for example 409 `channel_archived`, 409 `conversation_read_only`, 403 or 404 (a screen reads the reason with `classifyApiError`, D-131). The engine makes no other automatic try: a message has one try after a wait and none after a failure.
  (d) A `failed` message shows "Not sent" with Retry and Delete (D-087, TOKI-042); the engine only holds the state.
  Check, with the fake connection whose `status` the test sets and a fake `api` that answers or rejects as told: offline press waits and no request is made; `online` sends once and, on success, confirms; a `timeout` while `online` gives `failed`; a `timeout` while `offline` gives `waiting` and `online` sends again; a 409 gives `failed` with that error and no second request; the statuses `connecting` and `idle` send; the end-to-end test of R22 runs the real `createApiClient` with fake timers and a `fetch` that never answers, moves the timers by 10,000 ms and finds the message `failed`.
- R11. Retry and Delete. `retry(id)` puts a `failed` item back in the queue as `sending` (or `waiting` when `status` is `offline`), with the same id, so a message that the server stored before the answer was lost is answered by the repeat rule (TOKI-037 R5, status 200) and appears once. `discard(id)` removes a `waiting` or `failed` item at once and from the storage (R12), with no confirmation (D-087); it does nothing for a `sending` item and for an id that is not an item, and both return `true` when they acted and `false` otherwise. A deleted message that the server had in fact stored (the answer was lost) shows when its event or its page arrives, as the real message it is; the engine does not try to cancel it (Design, "Known limits"). Check: `retry` of a `failed` item sends again with the same id and the fake `api` that answers 200 gives one message; `discard` of `failed` and `waiting` removes the item and the stored copy; `discard` of `sending` returns false and changes nothing.
- R12. A waiting message survives a reload. `options.outbox` is `{ read(): string | null; write(value: string): boolean; remove(): void }`; the web app gives an adapter over `platform.storage.device` (R21). The engine writes one JSON text, `{ version: 1, userId, items: [{ id, conversationId, text, seq, localTime }] }`, each time the set of kept items changes, and removes it when the set is empty. The kept items are those in `sending` and `waiting` (a `sending` item is kept as waiting, because after a reload nobody knows whether the server got it; the repeat rule makes the second send safe), in press order. Whether a `failed` item is kept is concern 1 and the proposal there is not built. When the engine starts for a person (R19) it reads the text, validates it with a Zod schema of its own (an unreadable or unknown text is removed and ignored), and: when its `userId` is not the signed-in person's the whole text is removed and nothing is restored (D-132); otherwise each item becomes a `waiting` item and is sent by R10, as the connection allows. `write` returning false (the browser refused storage, TOKI-018 R9) changes nothing else: the items stay in memory. Check: a waiting message is in the fake `outbox` as written; a new engine with the same `outbox` and the same person restores it as `waiting` and sends it once, and a second reload before the answer restores it again; another person's text is removed and not restored; a text that is not JSON, one with another `version` and one with a missing key are removed; a `write` that returns false leaves the item in the window; a confirmed or discarded message leaves no item in the text.

Events
- R13. The entry points. The connection of TOKI-039 hands the engine the events of the missed range and of the stream through `onEvents(events)`, and the engine has `reload()` (R19) and `applyLive(frame)` (R17); the app connects them (R21). `onEvents(events)` takes events in number order, each `{ number, kind, conversationId, createdAt, data }` (TOKI-038 R12, TOKI-039 R2), returns nothing, applies the events in order and never throws: an event that fails to apply is skipped and the next is applied. The connection tells duplicates by number (TOKI-039 R10) and the numbers have holes (TOKI-039 R9), so the engine neither requires consecutive numbers nor keeps a cursor; it tells repeats by what they change: a message by its id (R4), the conversation state by the rule of R15. An event of a kind it does not know (and no handler of R18 knows) changes nothing. `data` is parsed with the schema of its kind in the registry of TOKI-038 R12 (`packages/shared/src/realtime/`); an event whose `data` fails it, or whose `conversationId` differs from the one in the `data`, is skipped, and the engine asks the store for `refresh()` (one call at a time, R10 of TOKI-032) so the state is repaired from the server, and marks the window of that conversation `stale`. Check: a batch of events from numbers 3, 9, 10 is applied in order with no complaint about the holes; an unknown kind changes nothing and does not throw; an event with bad `data` is skipped, the next one is applied and `refresh` is called once; the same batch applied twice leaves the same state and the same messages.
- R14. What each event does to the conversation store. "Entry" is the entry of the list, "detail" the `details` of TOKI-032 R14. Every row is made of the changes of R15, in one commit for the event, and uses the merge rule of TOKI-032 R13 (held level, mute and star, or the defaults for an id not held). `me` is the signed-in person.

  | Event kind (scope) | Effect |
  | :---- | :---- |
  | `conversation.created` (conversation) | when `me` is in `userIds`: the channel entry from `conversation`, defaults for a new id (a second tab of the creator, or a person made a first member); other people in `userIds` that are not in `people` make a `refresh` (see below) |
  | `member.joined` | when `userId` is `me`: the entry from `conversation`, detail `isMember` true when a detail is held; when the channel's detail is held, the member count is re-read (below); a `userId` not in `people` makes a `refresh` |
  | `members.added` | as `member.joined` for each id in `userIds` |
  | `member.left`, `member.removed` | when a detail of the channel is held, the member count is re-read; no change to the list. The event of `me` is not received (the gateway took the conversation from the map first, TOKI-038 R9) |
  | `conversation.left` (user) | for `conversationId` held: the entry is removed and the detail dropped, the window of that conversation is dropped (a person who is not a member reads nothing, D-116) while its waiting messages stay and fail when tried (R10); for one not held: no change at all (TOKI-039 Design) |
  | `conversation.updated` | `topic`, when present, to the entry and to a held detail; `description`, when present, to a held detail only (the entry has no description); a key that is absent changes nothing |
  | `conversation.archived` | the entry is removed (an archived channel is not in the list, TOKI-031 R17) and a held detail gets `archived` true; with no detail held, the engine reads the channel once (`readChannel`) so a screen that has it open can show that it is archived (F26). The window stays: a member reads an archived channel |
  | `conversation.restored` | the entry from `conversation` with defaults and a held detail gets `archived` false; the person's own level, mute and star are those of a member row that the event does not carry, so the engine asks the store for `refresh()` (as `restoreChannel` does, TOKI-032 R15) |
  | `settings.changed` (user) | the entry's three values are set to the event's, for an entry that is held and when no `saveSettings` for that id is in flight (its answer carries the truth); an id not held changes nothing |
  | `conversation.appeared` (user) | the direct entry is stored as it is, as `openDirect` stores its answer (TOKI-032 R13), with its own settings and its `lastMessageAt`; for a group too, whatever TOKI-038 concern 11 decides |
  | `message.created` | R16 |

  Why a re-read and a refresh: the payloads carry ids and an entry, not a member count and not a person's name. A count that is added or taken away by the engine would be wrong when the detail was read after the change but before its event arrived, so the engine reads the detail again (a request, only for a held detail, one at a time for each channel, an answer that fails changes nothing) and the count is the server's. A person who is not in `people` (a newcomer) has no `displayName` yet, which the names of direct conversations and the lists need, and only the bootstrap carries it, so `refresh()` runs. Check: each row has a test that starts from a fixture store and applies a fixture event; `conversation.left` for a conversation never held changes nothing and calls no listener; `conversation.updated` with `description` only leaves the entry as it was and changes the held detail; the same event applied twice calls no listener the second time; `settings.changed` while a `saveSettings` of that id runs changes nothing, after it ends applies; `conversation.archived` with no detail held calls `readChannel` once; `members.added` with an unknown person calls `refresh` once and a known person none; `member.joined` with a held detail calls `readChannel` and with none does not.
- R15. Additions to the conversation store. The store of TOKI-032 gets `applyRemote({ number, changes })` (the engine is its only caller), where `changes` is a list of these changes: `channel_upsert` (an entry without level, mute and star, merged by R13), `direct_upsert` (an entry, stored as it is), `entry_remove` (`id`, also drops the detail), `entry_patch` (`id`, optional `topic`, optional `lastMessageAt`; `lastMessageAt` is applied only when it is later than the held value or the held value is null), `detail_patch` (`id`, optional `topic`, `description`, `archived`, applied only to a held detail), `settings_set` (`id` and the three values), `person_set` (`id`, `role`, `status`: replaces that person in `people` and `peopleList` when held, and `user.role` and `user.status` when the id is the signed-in person's). It applies the list in one `commit` (one call of each listener, and none when nothing changes: TOKI-032 R12), and raises `eventNumber` to `number` only when the event changed the state, so a message event that touches only the windows does not replace the conversation state (R20). A change of a held entry that is equal to the held one changes nothing. For the stale answers of TOKI-032 R26: an applied change notes its id (an add for `channel_upsert`, `direct_upsert` and `detail_patch` of a held detail, a remove for `entry_remove`, settings for `settings_set`) with the event's number, so (a) a `readChannel` that was begun before it does not apply its answer to that id, like a command, and (b) a `refresh` that was begun before it keeps what the event left over the answer's entry for that id only when the event's number is above the `eventNumber` of the answer: an event at or below it is already in the answer, which is the fresher. Check: each change type has a test; a list of three changes is one listener call; an event that changes nothing calls no listener and leaves `eventNumber` as it was; a `refresh` begun before a `conversation.left` whose number is above the answer's `eventNumber` leaves the channel out, and one whose number is at or below it takes the answer; a `readChannel` begun before a `conversation.updated` does not overwrite its topic; `reset()` empties everything the engine added, as before.
- R16. Message events. `message.created` with `data.message` (a `MessageEntry`) acts on the window of `message.conversationId` and on the entry, in this order: (1) when the author is a person whose typing line is held, `typing.clear(conversationId, authorId)` is called first, so the line goes before the message shows (TOKI-044 R12); (2) a waiting item with the id of the message is replaced by it (R9); (3) a message of the main list (`parentId` null) is placed in the window by R4 when the window exists, is `ready`, and has `hasNewer` false; when the window is `loading` the message is kept aside and merged when the load ends, so a message that committed after the page was read is not lost (TOKI-037 R12); when `hasNewer` is true or no window exists the message is not placed (it comes with the next `loadNewer` or `loadLatest`); (4) a message of kind `user` with `parentId` null sets `lastMessageAt` of a `dm` or `group_dm` entry (R15); a system line (`kind` `system`) never does (D-100, TOKI-037 R19). A message with a `parentId` is not placed and does not set `lastMessageAt`: placing a reply that was also sent to the channel needs the key that TOKI-045 adds to the entry, and TOKI-045 registers its handler for it through R18 (concern 9). An event whose conversation is not held in the store is applied to the window only when one exists, and calls no request. A message event makes no request. Check: the fake `typing` is called before the window changes; a message of another person in a `ready` window with `hasNewer` false is appended; the same with `hasNewer` true is not; during a `loadLatest` whose page lacks it, the message is in the window after the load; a system line leaves `lastMessageAt` as it was; a `user` message in a DM raises it and an older one does not lower it; a reply with a `parentId` changes nothing and reaches the handlers of R18; the number of `api` calls is zero.
- R17. Live frames. `applyLive({ type: "live", kind, data })` (TOKI-038 R12) acts on `person.updated` with `data` `{ userId, role, status }`, parsed with its schema: a `person_set` change (R15). A frame of another kind is handed to the handlers of R18 and otherwise ignored; a frame that fails its schema is ignored. A frame is not stored and has no number. Check: a role change and a deactivation of a held person change `people` and the reference of `getPeople()`; the same of the signed-in person changes `getUser()`; an unknown person changes nothing; an unknown kind and a bad `data` change nothing and do not throw.
- R18. Seams for the tickets that follow. `registerEventHandler(kind, handler)` and `registerLiveHandler(kind, handler)` each return the function that removes the handler. A handler runs after the engine's own effect for that kind, with `(event, tools)` for an event (and `(frame, tools)` for a live frame), where `tools` has `patchMessage(conversationId, id, update)` (replaces one confirmed message of a window by `update(held)`, no-op when it is not held), `placeMessage(conversationId, message)` (R4) and `removeMessage(conversationId, id)`; a handler that throws does not stop the others or the next event. `subscribeEvents(listener)` calls `listener({ event, changed })` after each event of `onEvents` was applied (`changed` is true when the engine changed the conversation store or a window), so TOKI-053 can count and the member list of TOKI-035 can reload. Check: a handler registered for a made-up kind runs for an event of that kind and not for another; `patchMessage` changes one message and calls the listener of that window once; a throwing handler leaves the second one called; `subscribeEvents` is called once for each event, in order, also for an event that changed nothing; an unsubscribed function is not called.

Life of the engine
- R19. Life, reset and reload. The engine follows the conversation store: when its state holds a `user` and `status` `ready` and the engine is not started for that person, it starts for them (R12: restores the kept messages); when the user changes or the state returns to `idle` (a `reset()` of the store), it resets: every window and every waiting item in memory is dropped, every request in flight is aborted and its answer ignored (a generation number, as TOKI-032 R11), and the storage text is left as it is for the same person (D-132 drops it only when another person starts). No caller starts or resets it by hand. `reload()` is what the connection calls after a missed range that is too old (TOKI-039 R16): it marks every window `stale` (messages stay on screen), keeps the waiting items, calls `conversations.refresh()` and returns a promise of `conversations.getEventNumber()`; it rejects with the store's `ApiError` when the refresh left an error. A screen that has a `stale` window calls `loadLatest`. When `connection` is given, the engine subscribes to it and, when `status` becomes `online`, sends the waiting messages (R10). Check: the store becoming `ready` with a user starts the engine, `reset()` of the store resets it, a second person's start removes the first person's stored text; an answer that arrives after a reset is ignored (a send, a history page); `reload()` leaves windows and items in place, marks `stale`, calls `refresh` once and resolves with the new number, and rejects when the fake `api` of the refresh fails; the engine sends nothing before the store is `ready`.
- R20. Cost and stable results. Applying a `message.created` makes no request, replaces one window and no other state, and does not replace the conversation state unless it sets `lastMessageAt` (so the list does not draw again for a message in a channel, and a message of a conversation that is not on screen costs one array copy of its window). Placing a message at the end is made without sorting the window; one in the middle finds its place by search. `getMessages`, the lookups of TOKI-032 R23 and `getList` keep returning the same object when nothing they read changed (TOKI-032 R22). Check: a counter on the fake `api` shows zero calls for 100 message events; the listener of the conversation store is not called for 100 channel messages and is called for a DM message that raises `lastMessageAt`; applying 1,000 messages in order leaves a window whose items are the same objects as given (no copy of a message); the window of an unrelated conversation is `===` before and after.

## Design
### Where the code lives
```
packages/client-core/src/sync/
├─ engine.ts        createSyncEngine, the entry points, the life (R1, R13, R19)
├─ windows.ts       the windows, order, merge, loads (R3 to R6)
├─ outgoing.ts      the queue, the states, Retry and Delete (R7 to R11)
├─ outbox.ts        the stored text and its schema (R12)
├─ effects.ts       the table of R14, message events R16, live R17
├─ handlers.ts      the seams of R18
└─ *.test.ts
packages/client-core/src/api/methods.ts            messages.send, messages.history (R2)
packages/client-core/src/conversations/store.ts    applyRemote and its journal (R15)
packages/client-core/src/conversations/types.ts    the change types (R15)
packages/client-core/src/index.ts                  exports
apps/web/src/client.ts, outbox.ts, realtime.ts     the wiring (R21)
```
The engine is a second store beside the conversation store and not a part of its state, on purpose: a message event changes a window many times a second in a busy channel, and if it replaced `ConversationState` every list row would be offered to React again. The windows are one record by conversation id inside the engine, each replaced when it changes, with listeners by id (R3).

### Lines with the neighbouring work
- TOKI-039 owns the socket, the retry, the heartbeat, the cursor (the highest number applied), the request for the missed range, the `online` or `offline` state and the drop of duplicates by number. It hands this engine `onEvents(events)` (one batch at a time, in number order, TOKI-039 R19), `reload()` (R16 there) and every live frame; the engine reads the connection state only to decide `waiting`, and sends the waiting messages when it becomes `online` (TOKI-039 R15 says so). This work owns what an event does to the stores and what a reload drops. The numbers of the events have holes because a person receives only their own events (TOKI-039 R9), so the engine does not look for gaps by number: the connection's catch-up covers what was missed, and the engine tells a repeat by id or by the rule of R15.
- TOKI-044 owns the typing store and `clear`; this work calls `clear` when a message of the typing person is applied (R16). The typing frames go from the connection to `typing.receive` (TOKI-039 R20), not through this engine.
- TOKI-041, TOKI-042, TOKI-043 read `getMessages` and call the loads, `retry`, `discard` and `send`; TOKI-043 owns the limit and the draft; TOKI-082 draws the offline banner from the connection state.
- TOKI-053 reads the events through `subscribeEvents` (R18) to count unread messages and calls `setUnread` and `clearUnread`; the engine writes no count and a system line is never counted (D-100).
- TOKI-045 to TOKI-048 add keys to `MessageEntry` and register handlers (R18) that call `patchMessage` or `placeMessage`; TOKI-045 also decides how a reply sent to the channel reaches the window and the list time (R16).
- TOKI-035's member list reloads on the member events it reads through `subscribeEvents`; that change is made in `useChannelMembers` by this work when the hook exists, and by TOKI-035 when it is built later, as listed in Plan changes.

### Known limits
- Two tabs of one browser with waiting messages at the same time write one stored text each: the last write wins, so after a reload of both a message of the other tab can be missing. A message that two tabs both restore is sent twice with one id and stored once (TOKI-037 R5). This is accepted for phase 1 (concern 6).
- Delete of a failed or waiting message whose first request in fact reached the server removes only the local copy; the message shows when its event or its page arrives.
- A description changed in the instant between a detail read and its answer is overwritten by the older answer until the next read of the channel; the topic is not affected (R15 (a), the entry carries it).
- Between a `conversation.restored` and the refresh that follows, the entry shows the defaults of a new member for the level, mute and star.

### Errors
- A history or send failure ends as the `ApiError` of TOKI-032 R4, held in the window (`error`) or in the item (`error`); nothing is thrown to a caller of the loads, `onEvents`, `applyLive`, `send`, `retry` or `discard`; `reload` rejects only as R19 says.
- 401 with a session code reaches the hook of the API client as for any request (TOKI-032 R7).
- A storage that refuses a write is silent (R12).

## Data safety
- The text of a waiting message is kept in `localStorage` through the platform (R12) until it is sent or deleted, and remains after a sign-out of the same person, as D-132 decides; it is removed when another person signs in on that browser. It holds the person's id, the conversation id and the text, no name and no address. A shared computer therefore keeps the unsent text of the last person until someone signs in; a `discard` removes it.
- The conversation store and the windows hold every person's messages in memory only; `reset()` empties them (TOKI-032 R11) and nothing of an earlier person stays in memory.
- A person who leaves or is removed has the window dropped (R14).
- The engine logs nothing and holds no secret; an event, a message and an error are kept as data and are never turned into markup.

## Open questions from the intent
- Where is the line with reconnect (TOKI-039)? Answered: TOKI-039 owns the socket, the retry, the cursor, the missed-range request and the repeat-by-number rule; this work owns what an event does and what a reload drops (R13, R19, Lines with the neighbouring work, concern 4).
- Is a message that ended as "Not sent" kept through a reload, or only a waiting one? Not answered. D-132 names the waiting message only. Carried forward as concern 1.
- Does the cache of messages survive a reload, so that a person who opens the app without a connection can read it? Not answered. Carried forward as concern 2.
- What does the engine do when an event is out of date, repeated, or about a conversation it does not hold? Answered: R13 (repeats and unknown kinds change nothing), R14 (`conversation.left` of a conversation not held changes nothing), R15 (the stale-answer rule), R16 (a message for a conversation with no window is not kept).
- When is a send "offline" and when is it a failed request, given D-097? Answered: R10, by the state of the connection of TOKI-039 (concern 5).

## Areas of concern
1. Whether a message that ended as "Not sent" is kept in the browser through a reload. Not decided. D-132 says that a waiting message survives a reload and is dropped when someone else signs in; it does not say what happens to a message that is already "Not sent" when the page is reloaded. If it is not kept, the text is lost, which the reason of D-132 ("nothing lost") argues against. Proposal, not a decision: keep it, as a `failed` item that the person can Retry or Delete after the reload; the change is one condition in R12 (the kept items would be all unconfirmed ones) and one more case in its test. Until it is answered R12 keeps the waiting messages only. Owner: Thanh Truong (product owner).
2. Whether the messages already loaded are kept in the browser across a reload. Not decided. The offline banner of the prototype reads "Offline: showing saved messages" (D-102, D-140) and the journey says that with no connection at open the banner shows and the app retries on its own, but no decision says that messages are stored in the browser; the log decides storing the waiting messages only (D-132), and the NFR "with the network off no stale page is served from a cache" is about pages. Proposal, not a decision: phase 1 keeps the messages in memory only, so a person who opens the app with no connection sees the banner and an empty list until the connection returns, and the banner is true for the messages loaded before the connection dropped; storing the windows would need a storage choice (the 5 MB of `localStorage` is too small, IndexedDB is not in `platform`) and a rule for what to keep, and is a ticket of its own. Owner: Thanh Truong (product owner).
3. Where the messages live: in a second store beside the conversation store. Decided in this spec (a technical choice): a message event changes a window often and should not make the conversation list draw again (R20, Design). Reason: one store would give every list row a new state on every message. Owner: Thanh Truong.
4. How the engine and the connection of TOKI-039 divide the work. Decided in this spec: the connection owns the cursor and tells repeats by number; the engine tells repeats by id and by the rule of R15, applies the events it is given in order and never throws, and owns `reload`. Reason: TOKI-039 R9 and R10 fix the cursor and the order, and the numbers have holes, so only the engine can know what an event changed. The conversation effects of an event are skipped only by the rule of R15 (an event at or below the `eventNumber` of a newer bootstrap), never by a cursor of the engine. Owner: Thanh Truong.
5. What "offline" means for a send. Decided in this spec: the state `offline` of the connection (TOKI-039 R15), and `connecting` for a failed request, decide `waiting`; the one automatic try is the send after the wait; a failure while the connection is `online` or `idle` is "Not sent" at once. Reason: D-097 gives one automatic try after a wait; the journey F11 gives "Not sent" for a failed send; TOKI-037's text on 10 seconds mentions one resend with the same id, and the same id makes it safe, but the log gives no second try for a message pressed while online, so none is made. If the owner wants one more automatic try, it is one counter in R10. Owner: Thanh Truong.
6. Two tabs and the stored text. Decided in this spec: one stored text for the browser, the last write wins, a message restored by two tabs is stored once by the server (Known limits). Reason: the platform storage has no list of keys and no lock; a per-tab key could not be found again after a reload. Owner: Thanh Truong.
7. Refreshing a count or the people after an event, instead of counting. Decided in this spec (R14): a held detail is read again after a member event and the bootstrap is read again when a person is unknown. Reason: the payloads carry ids and no counts or names, and a count kept by adding one is wrong when a read overlaps its event. The cost is a request on a member event for a channel whose detail is held. Owner: Thanh Truong.
8. Delete of a message that the server may have stored. Decided in this spec: Delete removes the local copy and asks nothing (D-087); a message that was in fact stored appears when its event or page arrives. Reason: the engine cannot know whether an answer was lost and cannot withdraw a stored message (deleting a sent message is TOKI-047, and it is not Delete of D-087). Owner: Thanh Truong.
9. Replies and the main list. Decided in this spec: a message with a `parentId` is neither placed nor counted for `lastMessageAt` by the engine, which cannot tell a reply that was also sent to the channel from one that was not; TOKI-045 adds the key that tells them apart and registers its handler (R18, R16). Reason: placing a thread reply in the channel by mistake would show it twice. Owner: Thanh Truong.
