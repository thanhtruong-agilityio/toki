# client-core: sync engine design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/client-sync-engine.md (Thanh Truong)
Ticket: TOKI-040
Needs: TOKI-037 (message API: `MessageEntry`, the send and history routes, `lastMessageAt`) and TOKI-038 (the events and live frames and their schemas in `packages/shared/src/realtime/`), as revised in their open pull requests; TOKI-036 (event numbers and retention); TOKI-032 (the conversation store this work extends). It is used by TOKI-039, which hands it the events; see Lines with the neighbouring work.

## Goal
The server stores messages and pushes numbered events, but the client keeps nothing of them. The conversation store of TOKI-032 never changes after its first load, there is no place that holds the messages of a conversation, and a message cannot be sent so that it shows at once. This work builds, in `packages/client-core`, the sync engine: the cache of the messages of each conversation (ordered, without duplicates), the rules that apply each event and live notice to the conversation store and to that cache, and the optimistic send with its three states, its single automatic try and its kept-in-the-browser queue. It holds no text and uses no browser API: the browser pieces (the storage of the waiting messages, the socket) are given to it.

## Scope
- In:
  - Two typed methods of the API client: send a message (with the ids of attached files, R2), read history (R2).
  - The message windows: the state a screen reads, order, duplicates, the four loads, what a switch of conversation keeps (R3 to R6).
  - The optimistic send: the client-made id, the ids of attached files, the states `sending`, `waiting`, `failed`, the queue, the confirmation by answer or by event, Retry and Delete, the single automatic try, the kept-in-the-browser queue through a storage port (R7 to R12).
  - The entry points the connection calls: `onEvents`, `reload`, `applyLive`, and `attachConnection` that gives the engine the connection; what every event kind of TOKI-038 does to the conversation store and to the windows (R13 to R17).
  - The additions to the conversation store that the effects need (R15), the seams that later tickets use (R18), the life of the engine (R19), cost and stability (R20), the wiring in `apps/web` (R21) and the contract (R22).
- Out (not now):
  - The socket, the retry delays, the heartbeat, the cursor, the request for missed events, the offline state and what a close code means: TOKI-039. The engine only reads the connection state it publishes and is handed the events it returns.
  - Drawing: the list of messages (TOKI-041), the message and its states (TOKI-042), the composer, its limits and its draft (TOKI-043), the offline banner and the blocking of other actions (TOKI-082).
  - Threads, reactions, edit, delete, pins (TOKI-045 to TOKI-048): they add their keys to `MessageEntry` and register their event kinds through R18.
  - Unread counts and the read pointer (TOKI-053): it reads the events through R18 and calls `setUnread` and `clearUnread` of TOKI-032.
  - The typing signal (TOKI-044); this work only calls its `clear` (R16).
  - Keeping the message cache across a reload (concern 2).

## Requirements
Package and requests
- R1. The engine is `createSyncEngine(options)` of `packages/client-core/src/sync/`, exported from the package index with its types. `options`: `conversations` (the store of TOKI-032 with the additions of R15), `api` (the methods of R2), `newId` (a function that returns a new UUID version 7; the app gives the generator of `apps/web/src/ids.ts`), `clock` (`Clock` of `@toki/shared`, read only for `localTime` of R7), `outbox` (the storage port of R12) optional `typing` (`{ clear(conversationId, userId): void }`, TOKI-044 R12) and optional `mergeMessage` (`(held, incoming) => MessageEntry`, the rule that `applyMessage` of R18 uses; it defaults to the incoming message). The connection is not an option: it is made in a file that imports the file that makes the engine, so it is given afterwards through `attachConnection` (R19, R21). The package keeps its rules: no DOM or browser global, no text a person reads, no key of `@toki/i18n`, no `Date.now(` and no `new Date()` (TOKI-008 R19), no timer of its own. Check: `pnpm lint` and the search script of TOKI-008 find nothing in `packages/client-core/src/sync/`; a type test builds the engine with only the required options and calls `attachConnection` with a plain object of the shape of R19.
- R2. Two methods of `createApiClient` (TOKI-032 R9, same rules: one request core, 10 seconds, no retry, a path part encoded, an optional `signal` last, neither `headers` nor `timeoutMs`). `api.messages.send(conversationId, { id, text, attachmentIds? }, signal?)` sends `POST /conversations/{id}/messages` with exactly that body (the key `attachmentIds` only when the array is given and not empty, so the body of a message with no file is as before; TOKI-058 R14 adds the key and lets the text be empty when it is set) and returns `{ status, message }`, `status` being 201 or 200 (TOKI-037 R3, R5) and `message` a `MessageEntry`. `api.messages.history(conversationId, query?, signal?)` sends `GET /conversations/{id}/messages` with `limit`, `before`, `after` or `around` only when given (never two of the three positions) and returns `{ messages, hasOlder, hasNewer }` (TOKI-037 R11). Both read the answer with the response schemas that TOKI-037 R22 exports from `packages/shared`, in the form that drops unknown keys (TOKI-032 R3), so a key that TOKI-045 to TOKI-061 add (`files`, `linkPreviews`) reaches the cache. The engine sends no `limit`, so the page size is the server's default (TOKI-037 concern 1 is open and does not touch this work). Check: with the fake `fetch` of the existing tests, each method sends the method, path, query and body as written and parses a good answer; a send with an extra key in the answer keeps it; a send with `attachmentIds` has the key in the body, one with none or an empty array has no such key; the history request has no `limit` unless given; an error answer ends as an `ApiError` of the existing kinds.

The windows
- R3. State a screen reads. `getMessages(conversationId)` returns a `MessageWindow`: `{ status, error, items, hasOlder, hasNewer, isLoadingOlder, isLoadingNewer, stale }`. `status` is `idle` (nothing loaded), `loading` (the first load of a window that holds no confirmed message), `ready` or `failed` (only while no confirmed message is held); `error` is the `ApiError` of the last failed load or null; `stale` is true after `reload` (R19) until the next latest load. A window is one contiguous range of the conversation's main list: between its oldest and its newest confirmed message no message that the server holds is missing, as of the time the window was read, and nothing is placed that would leave a hole (R5, R16). `items` holds first the confirmed messages and then the waiting ones (R4). For a conversation never touched `getMessages` returns one frozen empty window, the same object for every such id. `subscribeMessages(conversationId, listener)` returns the function that removes it; the listener is called once for each change of that conversation's window and never for a change of another conversation's. A window is replaced and never changed in place, so two calls with no change in between return the same object (`useSyncExternalStore`). Check: two calls give `===` objects; a change in conversation `a` calls the listener of `a` and not that of `b`; a snapshot kept before a change is not altered by it; the model test of R5 checks the contiguous range after every step.
- R4. Order, duplicates and identity. A confirmed message is placed by the pair (`Date.parse(createdAt)`, `id`), the time first and then the id in code-point order, which is the order of TOKI-037 R9 and R12; a message is never placed after one that follows it in that order, and a message whose `id` is already in the window is not added again. Which source may replace the held one: a page merge (R5) and a handler of R18 (`patchMessage`, `applyMessage`, `placeMessage`) replace it, because a page and a handler are fresher (TOKI-047 and TOKI-046 change a message in place), and a page that was read before a change gets that change put back first (R5); a send answer never replaces a held message, it only fills the place of its waiting item (R9); an event `message.created` never replaces a held message, because an event is the state at creation and a replay after a catch-up must not undo an edit that a page already holds. It fills a place that is empty, and it replaces a waiting item of its id (R9). The waiting messages follow all confirmed ones, in the order they were pressed. A message placed in the middle (a page that fills a hole, a message of an earlier time) takes its place by that pair. Identity: `item.message` is the very object that the API client or the event gave (the engine never copies a message), and when a window is replaced the item of a confirmed message whose `message` is the same object is the same item object, so TOKI-041 and TOKI-042 can memoise rows by item. Placing at the end costs one comparison with the held newest; placing in the middle is a binary search. Every window keeps an index of its confirmed messages by id, so a message is found by id with no scan, and a held message is replaced at the place that its pair gives. Check: a lookup of a held id by `patchMessage` visits no other message; five messages given in a shuffled order, two with one time and ids in both orders, land in the pair order; the same message twice (a page and an event, a send answer and an event) leaves one; an event for an id that is held leaves the held message as it was (`===`) while a page with a changed copy replaces it; a waiting message stays after a confirmed message that arrives later; `item.message` is `===` the given message; after a page merge the items of the messages that did not change are `===` their earlier items; 1,000 messages given in order cost at most 1,000 comparisons (the windows module takes the comparison function as an argument that defaults to `compareMessages`, and the test passes one that counts).
- R5. The four loads. `loadLatest(id)`, `loadOlder(id)`, `loadNewer(id)` and `loadAround(id, messageId)` call `api.messages.history` with no position, `before` the oldest confirmed message, `after` the newest confirmed message, and `around` the message. Each returns a promise that never rejects: the outcome is read from the window (`status`, `error`, `isLoadingOlder`, `isLoadingNewer`). `loadLatest` and `loadAround` are "head loads": while one runs for a conversation, the message events of that conversation are kept aside (R16) and put in order after its page, so none is lost. `loadOlder` and `loadNewer` do nothing (no request) when `hasOlder` or `hasNewer` is false, when the window holds no confirmed message, or when the same load is already running; a `loadLatest` that is already running for the conversation is not started again and its promise is returned. Patches during a load: while any of the four loads of a conversation runs, the engine writes every `patchMessage`, `applyMessage` and `removeMessage` of R18 for that conversation into a journal, in order, whether or not the message is held; when the answer comes, the entries written since that load began are applied, in order, to the messages of the page and to the aside messages (R16) before they are merged (an `update` to the copy of its id, a removal drops it), so a page that was read before a change does not bring back the older copy and a change to a message that the window does not hold yet is not lost (concern 10). The journal is emptied when no load of the conversation is running. The answer is merged as follows. When a page is merged with held messages, `hasOlder` comes from whichever of the two ranges has the older oldest message and `hasNewer` from whichever has the newer newest (the page when they are equal), so the union keeps one contiguous range:

  | Load | Merge | Flags |
  | :---- | :---- | :---- |
  | latest | merged with the held messages only when the page shares an id with them (two contiguous ranges that overlap give one contiguous range); otherwise it replaces them (the held window was a place far from the end, or a stale one whose end is unknown), so a hole is never kept; it clears `stale` | both from the page when it replaced; otherwise as said above (`hasNewer` is false, the page reaches the end) |
  | older | added before the held oldest | `hasOlder` from the answer |
  | newer | added after the held newest | `hasNewer` from the answer |
  | around | replaces the held messages unless the page shares an id with them and the window is not `stale`; then merged. A `stale` window is always replaced | both from the answer when it replaced; otherwise as said above. It leaves `stale` as it was unless it replaced |

  A failed load changes no message, sets `error`, never clears `stale`, leaves `status` `ready` when messages are held and sets `failed` when none is held. A load that was begun before `reset` (R19) or before the person left the conversation is ignored when its answer comes. A 403 or 404 answer for a conversation the engine holds does nothing else (the store's entry is changed by events, R14). Check: a fake `api` with 120 messages in pages of 20 gives, from `loadLatest` and six `loadOlder`, every message once, in order, with `hasOlder` false at the end; `loadNewer` after an `around` window reaches the end with `hasNewer` false; a latest load over a far window replaces it; a second `loadOlder` while one runs sends one request, and so does a second `loadLatest`; a failed `loadOlder` keeps the messages and sets `error`; `loadOlder` with `hasOlder` false sends none; with a deferred page, a `message.created` that arrives between the request and the answer, whatever the window status (`ready`, `stale`, `loading`), is in the window after the page (a page read before a commit must not drop it); a window `stale` with messages 1 to 50 and a `loadLatest` that returns 61 to 110 is replaced and not merged, so no hole stays; a test handler that patches a message during a deferred `loadOlder`, `loadNewer` and `loadLatest` whose page holds that message leaves the patched copy after the merge (the page is the older copy); a patch to an id that the window does not hold and that the page then brings is applied to it; a `removeMessage` during a load drops that message from the page; a patch to a message that came as an aside event is applied to it; the journal is empty when no load runs; one model test runs a fake server list and random sequences of events, `reload`, the four loads and delayed pages, and after every step the confirmed messages of the window are a contiguous run of the server's list.
- R6. What a switch keeps. The windows stay in memory when the screen shows another conversation, so switching back shows the held messages at once (NFR-13: under 100 ms). `loadLatest` on a window that is `ready`, not `stale` and has `hasNewer` false sends no request, because the events keep such a window current (R16). A window is dropped only by `reset`, by the removal of the conversation from the person (R14) or by nothing else; there is no size limit (the memory is bounded by what the person scrolled, and is freed by `reset`). Check: after a load, a second `loadLatest` sends no request and `getMessages` is the same object; a `stale` window sends one; a window with `hasNewer` true sends one.

Sending
- R7. Optimistic send. `send(conversationId, text, options?)` (`options` is `{ attachmentIds?: readonly string[] }`, the ids of the files that the person attached, TOKI-058 R14; TOKI-045 adds its own keys to the same object) returns at once, with no wait on the network, a new id made by `options.newId()`, and puts a waiting-list item for it into the window of that conversation, so the message shows at the end of `items` before any request is answered. The item is `{ kind: "pending", id, conversationId, text, attachmentIds, authorId, delivery, error, localTime }`: `attachmentIds` is the array given (a copy), empty when none; `authorId` is the id of the signed-in person, `localTime` is `clock.now()` at the call (it is shown beside the message only until the server's `createdAt` replaces it), `delivery` is `sending`, `waiting` or `failed` (R10), `error` is the `ApiError` of the last failure or null. The text is kept as given (no trim, no change), except that with files a text of only white space is queued as the empty string (below). When the window of the conversation is `stale` or has `hasNewer` true, `send` also starts `loadLatest` for it (one at a time), because a person who sends goes to the end of the conversation and a message cannot be placed after a hole (R9, R16). `send` returns `null` and queues nothing when no signed-in person is held or when there is no file and the text holds no character that `String.prototype.trim` of JavaScript does not remove (the rule of TOKI-037 R4: nothing is sent that the server would refuse as white space). With at least one id in `attachmentIds` a message with no text is allowed (TOKI-058 R14): an empty text is queued, and a text of only white space is queued as the empty string, because the server refuses a given text that is only white space (400) and a person who typed a space and attached a file has no text to lose. The engine does not check the ids (their number, repeats, whether the files are still there): the server answers 400 and the message is `failed` by R10 (e). The composer (TOKI-043) owns the 10,000 code points rule and the counter, and the engine does not repeat it. Check: the item is in `items` synchronously, before the fake `api` answers, with `delivery` `sending`; the id is the one `newId` returned; `send("c", "   ")` returns null and makes no item and no request; `send("c", "", { attachmentIds: ["f1"] })` returns an id and queues an item with the empty text and `attachmentIds` `["f1"]`, `send("c", "  ", { attachmentIds: ["f1"] })` queues the empty text, and `send("c", "", { attachmentIds: [] })` returns null; the text is unchanged; `send` on a `stale` window and on one with `hasNewer` true starts one `loadLatest`, and on a `ready` window with `hasNewer` false starts none.
- R8. The queue. Waiting messages are sent in the order they were pressed, one request at a time for each conversation, and the next one of that conversation is sent when the earlier one has ended (answered, failed or put back to waiting), because the server orders by the time it handles the send (TOKI-037 concern 4); different conversations send in parallel. A message of `failed` state does not hold back the messages after it. The request is `api.messages.send(conversationId, { id, text, attachmentIds }, signal)`, with the id and the `attachmentIds` of the item (the empty array is left out by R2), and has a signal that `reset` aborts. Check: three sends to one conversation call the fake `api` once, the second after the first answers; two conversations call it twice at once; a failed first message does not stop the second; the request of an item with files carries its `attachmentIds`.
- R9. Confirmation. A send answer (201 or 200, the same body, TOKI-037 R5) replaces the item by the `MessageEntry` of the answer: the item disappears from the waiting list and the message is placed by R4, under the placement rule of R16 step 3 (a window that is `stale` or has `hasNewer` true cannot take it: then the item stays as it was while the `loadLatest` that `send` started (R7) runs, and the message comes with that page or from the aside list of R16; if that load fails the item is removed, the message is stored and comes with the next `loadLatest`). An event `message.created` whose `message.id` is the id of an item does the same (R16), so the message becomes solid by whichever comes first, and the one that comes second changes nothing: the answer after the event finds no item and no message is added twice, the event after the answer finds the message and, by R4, leaves it as it is. Both leave exactly one message with that id. For a `dm` or `group_dm`, a confirmed send also sets `lastMessageAt` of the conversation's entry to the message's `createdAt` when it is newer than the held value, so the list order of F09 follows the person's own send without waiting for the event (TOKI-037 R21). Check: answer before the event and event before the answer each leave one message and no item; a replay of the same event leaves one; a DM entry with `lastMessageAt` null has the time of the confirmed message; a channel entry gets no such key; a send from a window with `hasNewer` true leaves the item until the `loadLatest` ends and then one message, in the window, at the end.
- R10. Offline, failure and the single automatic try. This is the reading of D-079, D-097, D-087, D-126 and the journey F11 (decided in this spec, concern 5). Let `status` be the `status` of the connection given by `attachConnection` (R19; the state object of TOKI-039 R15). The engine reads `online` and `offline` as they are, `stopped` with `stoppedBy` `too_many_connections` as `offline` (a tab that the server closed for good: TOKI-039 concern 7), and `connecting`, `idle` and every other `stopped` as `idle`: it sends, and a failed request is "Not sent" at once. With no connection attached the engine behaves as `idle`.
  (a) A message pressed while `status` is `offline` is not sent: `delivery` is `waiting`. When `status` becomes `online`, every waiting message is sent once, by the queue of R8 (the one automatic try of D-097). A message pressed when `status` is `online` or `idle` is sent at once with `delivery` `sending`.
  (b) A send that ends with an `ApiError` of kind `network` or `timeout` (a request with no answer after 10 seconds is the `timeout`, D-126) while `status` is `offline` goes back to `waiting` and does not count as the try.
  (c) A `timeout` while `status` is `online` or `idle` is `failed` at once (D-126 says a request with no answer after 10 seconds shows Retry).
  (d) A `network` error while `status` is `online`: the socket may be dead although the connection has not noticed yet (it notices only after its silence check of TOKI-039 R13, up to about a minute, and its 3 seconds of grace), and D-079 says a message pressed with no connection waits. So the message goes to `waiting` once, and the engine calls `suspect()` of the attached connection when it has one (TOKI-039 R13: it drops the socket at once, so `status` follows). The message is then sent when `status` is `online` again, as in (a); a `network` error of that send, or a `network` error when the attached connection has no `suspect`, is `failed`. A message has this one extra wait only once.
  (e) Every other error answer (a 4xx or 5xx status, `invalid_response`) makes the message `failed` at once, with the `ApiError` kept in `error`, for example 409 `channel_archived`, 409 `conversation_read_only`, 403 or 404 (a screen reads the reason with `classifyApiError`, D-131). The engine makes no other automatic try: a message has one try after a wait and none after a failure.
  (f) A `failed` message shows "Not sent" with Retry and Delete (D-087, TOKI-042); the engine only holds the state.
  Check, with the fake connection whose `status` the test sets and a fake `api` that answers or rejects as told: offline press waits and no request is made; `online` sends once and, on success, confirms; a `timeout` while `online` gives `failed`; a `timeout` while `offline` gives `waiting` and `online` sends again; a `network` error while `online` gives `waiting` and one call of `suspect`, then `online` sends again, and a second `network` error gives `failed`; with no `suspect` a `network` error while `online` gives `failed`; a 409 gives `failed` with that error and no second request; the statuses `connecting`, `idle` and `stopped` send, and `stopped` with `stoppedBy` `too_many_connections` makes the item `waiting` and sends nothing; the end-to-end test of R22 runs the real `createApiClient` with the injected `timers` of the test and a `fetch` that never answers, fires the 10-second timer and finds the message `failed`.
- R11. Retry and Delete. `retry(id)` puts a `failed` item back in the queue as `sending` (or `waiting` when `status` is `offline`), with the same id and the same `attachmentIds`, so a message that the server stored before the answer was lost is answered by the repeat rule (TOKI-037 R5, status 200) and appears once. `discard(id)` removes a `waiting` or `failed` item at once and from the storage (R12), with no confirmation (D-087); it does nothing for a `sending` item and for an id that is not an item, and both return `true` when they acted and `false` otherwise. A deleted message that the server had in fact stored (the answer was lost) shows when its event or its page arrives, as the real message it is; the engine does not try to cancel it (Design, "Known limits"). Check: `retry` of a `failed` item sends again with the same id and the fake `api` that answers 200 gives one message; `discard` of `failed` and `waiting` removes the item and the stored copy; `discard` of `sending` returns false and changes nothing.
- R12. A waiting message survives a reload. `options.outbox` is `{ read(): string | null; write(value: string): boolean; remove(): void }`; the web app gives an adapter over `platform.storage.device` (R21). The stored text is one JSON text for the browser, `{ version: 1, userId, items: [{ id, conversationId, text, attachmentIds, seq, localTime, tabId }] }`, where `attachmentIds` is an array of strings that defaults to `[]` when the key is missing, so a text written before this key existed stays readable with `version` 1 and nothing but ids of files is kept, no name and no size, and it is shared by every tab of that browser, so a write must not drop what another tab kept. Each engine has a `tabId` (`newId()` at its start). Each time the set of its own kept items changes, the engine reads the stored text and writes it back with its own items replaced by the current ones and the items of other tabs kept as they are (an item whose id this engine has confirmed or discarded is removed whoever owns it); it removes the text when no item is left. The kept items of a tab are those in `sending` and `waiting` (a `sending` item is kept as waiting, because after a reload nobody knows whether the server got it; the repeat rule makes the second send safe), in press order. Whether a `failed` item is kept is concern 1 and the proposal there is not built. When the engine starts for a person (R19) it reads the text, validates it with a Zod schema of its own that drops unknown keys, in the text and in each item (an unreadable text, one with another `version` or one with a missing key is removed and ignored; an extra key is not an error, so a tab of an older or newer build does not make the text unreadable and does not remove the waiting messages of the other tabs), and: when its `userId` is not the signed-in person's the whole text is removed and nothing is restored (D-132); otherwise each item, whichever tab wrote it, becomes a `waiting` item of this engine (its `tabId` becomes this engine's) and is sent by R10, as the connection allows. Two tabs that both restore one item send it twice with one id, and the server stores it once (TOKI-037 R5). `write` returning false (the browser refused storage, TOKI-018 R9) changes nothing else: the items stay in memory. A read for a caller that has no event: `heldFileIds()` (also `sync.heldFileIds`) returns a new `ReadonlySet<string>` with the ids in `attachmentIds` of every `sending`, `waiting` and `failed` item of this engine and of every item of the other tabs in the stored text (read and validated as above, read-only: it writes and removes nothing); it is for a caller that must not drop a file that a message is about to send (TOKI-059 R11). Check: a waiting message is in the fake `outbox` as written; a new engine with the same `outbox` and the same person restores it as `waiting` and sends it once, and a second reload before the answer restores it again; another person's text is removed and not restored; a text that is not JSON, one with another `version` and one with a missing key are removed, and one with an extra key in the text or in an item is read with the key dropped; a `write` that returns false leaves the item in the window; a confirmed or discarded message leaves no item in the text; two engines over one fake outbox (two tabs) that each hold a waiting message leave both items in the text, whichever wrote last, and a tab that discards its item leaves the other's; an item with files is in the text with its `attachmentIds` and is restored with them; a stored item with no `attachmentIds` key is restored with `[]`; `heldFileIds()` holds the ids of a `sending`, a `waiting` and a `failed` item, those of an item of another tab in the stored text, and not those of a confirmed or discarded item, and a call changes neither the window nor the stored text.

Events
- R13. The entry points. The connection of TOKI-039 hands the engine the events of the missed range and of the stream through `onEvents(events)`, and the engine has `reload()` (R19) and `applyLive(frame)` (R17); the app connects them (R21). `onEvents(events)` takes events in number order, each `{ number, kind, conversationId, createdAt, data }` (TOKI-038 R12, TOKI-039 R2), returns nothing, applies the events in order and never throws: an event that fails to apply is skipped and the next is applied. The connection tells duplicates by number (TOKI-039 R10) and the numbers have holes (TOKI-039 R9), so the engine neither requires consecutive numbers nor keeps a cursor; it tells repeats by what they change: a message by its id (R4), the conversation state by the rule of R15, a person's status by the number that the store keeps for that person (R15, `person_patch`), the person's notification switches by the two numbers that the store keeps for that value (R15, `preferences_set`). An event of a kind it does not know (and no handler of R18 knows) changes nothing. `data` is parsed with the schema of its kind in the registry of TOKI-038 R12 (`packages/shared/src/realtime/`); an event whose `data` fails it, or whose `conversationId` differs from the one in the `data`, is skipped, and the engine asks the store for `refresh()` (one call at a time, R10 of TOKI-032, and at most once for each call of `onEvents`, so a burst of bad events makes one) so the state is repaired from the server, and marks the window of that conversation `stale`. The engine reads `data` with the form of each schema that drops unknown keys (the form of TOKI-032 R3), so a server that adds a key to a payload does not make every event of that kind a bad one. Life of the engine
- R19. Life, reset and reload. The engine follows the conversation store: when its state holds a `user` and `status` `ready` and the engine is not started for that person, it starts for them (R12: restores the kept messages); when the user changes or the state returns to `idle` (a `reset()` of the store), it resets: every window and every waiting item in memory is dropped, every request in flight is aborted and its answer ignored (a generation number, as TOKI-032 R11), and the storage text is left as it is for the same person (D-132 drops it only when another person starts). No caller starts or resets it by hand. `reload()` is what the connection calls after a missed range that is too old (TOKI-039 R16, which calls it with no argument and drops nothing itself, so what a reload does is decided here): it marks every window `stale` (messages stay on screen), keeps the waiting items, calls `conversations.refresh()` and returns a promise of `conversations.getEventNumber()`; it rejects with the store's `ApiError` when the refresh left an error. A screen that has a `stale` window calls `loadLatest` (TOKI-041), and a `send` on a stale window starts it (R7); a stale window takes no event (R16). `attachConnection(connection)` gives the engine the connection once the app has made it: `connection` is `{ getState(): { status }, subscribe(listener): () => void, suspect?(): void }` (the object of TOKI-039 R15 and R13 has this shape), it returns the function that detaches it, and a second call detaches the first. The engine subscribes to it and, when `status` becomes `online` (and at the attach when it is `online` and the engine holds waiting items), sends the waiting messages (R10). A `reset` of the engine does not detach the connection. The engine gives no read of the connection's state and holds one connection only: a piece that needs the status (the unread tracker of TOKI-053, the drafts of TOKI-051, presence) has its own `attachConnection` and subscribes itself, from the same line in `realtime.ts` (R21). Check: the store becoming `ready` with a user starts the engine, `reset()` of the store resets it, a second person's start removes the first person's stored text; an answer that arrives after a reset is ignored (a send, a history page); `reload()` leaves windows and items in place, marks `stale`, calls `refresh` once and resolves with the new number, and rejects when the fake `api` of the refresh fails; an event for a `stale` window is not placed; `attachConnection` with a fake connection whose `status` is `online` sends a waiting message, a second `attachConnection` unsubscribes the first connection, and the returned function detaches; the engine sends nothing before the store is `ready`.
- R20. Cost and stable results. Applying a `message.created` makes no request, replaces one window and no other state, and does not replace the conversation state unless it sets `lastMessageAt` (so the list does not draw again for a message in a channel, and a message of a conversation that is not on screen costs one array copy of its window). Placing a message at the end is made without sorting the window (one comparison, R4); one in the middle finds its place by search. `getMessages`, the lookups of TOKI-032 R23 and `getList` keep returning the same object when nothing they read changed (TOKI-032 R22). Check: a counter on the fake `api` shows zero calls for 100 message events; the listener of the conversation store is not called for 100 channel messages and is called for a DM message that raises `lastMessageAt`; applying 1,000 messages in order leaves a window whose `item.message` objects are the same as given (no copy of a message) and costs at most 1,000 comparisons (the counting comparison of R4); the window of an unrelated conversation is `===` before and after.

The engine is a second store beside the conversation store and not a part of its state, on purpose: a message event changes a window many times a second in a busy channel, and if it replaced `ConversationState` every list row would be offered to React again. The windows are one record by conversation id inside the engine, each replaced when it changes, with listeners by id (R3). `windows.ts` takes the key of a window and the function that loads a page and knows nothing of conversations, so a later ticket can keep a second family of windows (TOKI-045's thread windows) with the same code and not a copy; the journal of R5 and the id index of R4 are part of it.

### Known limits
- Two tabs of one browser share one stored text, and each write keeps the items of the other tab (R12), so no waiting message is lost. A message that two tabs both restore is sent twice with one id and stored once (TOKI-037 R5). An item of a tab that was closed stays in the text until a tab starts and restores it (concern 6).
- A waiting message with files holds only the ids of its files; the files may be gone after 24 hours (D-130), and its Retry then ends `failed` with 400 `attachment_unavailable` until it is deleted. Showing the file cards of such a message is not decided (the composer spec's concern 12; the proposal there would keep the file entries on the item, which this spec does not do).
- Delete of a failed or waiting message whose first request in fact reached the server removes only the local copy; the message shows when its event or its page arrives (concern 8, not decided).
- A description changed in the instant between a detail read and its answer is overwritten by the older answer until the next read of the channel; the topic is not affected (R15 (a), the entry carries it).
- Between a `conversation.restored` and the refresh that follows, the entry shows the defaults of a new member for the level, mute and star.

### Errors
- A history or send failure ends as the `ApiError` of TOKI-032 R4, held in the window (`error`) or in the item (`error`); nothing is thrown to a caller of the loads, `onEvents`, `applyLive`, `send`, `retry` or `discard`; `reload` rejects only as R19 says.
- 401 with a session code reaches the hook of the API client as for any request (TOKI-032 R7).
- A storage that refuses a write is silent (R12).

## Data safety
- The text of a waiting message is kept in `localStorage` through the platform (R12) until it is sent or deleted, and remains after a sign-out of the same person, as D-132 decides; it is removed when another person signs in on that browser. It holds the person's id, the conversation id, the text and the ids of the attached files, no name and no address. A shared computer therefore keeps the unsent text of the last person until someone signs in; a `discard` removes it.
- The conversation store and the windows hold every person's messages in memory only; `reset()` empties them (TOKI-032 R11) and nothing of an earlier person stays in memory.
- A person who leaves or is removed has the window dropped (R14).
- The engine logs nothing and holds no secret; an event, a message and an error are kept as data and are never turned into markup.

## Areas of concern
1. Whether a message that ended as "Not sent" is kept in the browser through a reload. Not decided. D-132 says that a waiting message survives a reload and is dropped when someone else signs in; it does not say what happens to a message that is already "Not sent" when the page is reloaded. If it is not kept, the text is lost, which the reason of D-132 ("nothing lost") argues against. Proposal, not a decision: keep it, as a `failed` item that the person can Retry or Delete after the reload; the change is one condition in R12 (the kept items would be all unconfirmed ones) and one more case in its test. Until it is answered R12 keeps the waiting messages only. Owner: Thanh Truong (product owner).
2. Whether the messages already loaded are kept in the browser across a reload. Not decided. The offline banner of the prototype reads "Offline: showing saved messages" (D-102, D-140) and the journey says that with no connection at open the banner shows and the app retries on its own, but no decision says that messages are stored in the browser; the log decides storing the waiting messages only (D-132), and the NFR "with the network off no stale page is served from a cache" is about pages. The merged client-core spec (Scope, and Data safety) gives the saved cache for offline use to TOKI-040, and D-102 and D-140 keep the banner "Offline: showing saved messages", so leaving it out takes work away from this ticket and the banner is true only for messages loaded before the connection dropped; D-060 puts an offline mode in Phase 6. Proposal, not a decision: phase 1 keeps the messages in memory only, so a person who opens the app with no connection sees the banner and an empty list until the connection returns, and the banner is true for the messages loaded before the connection dropped; storing the windows would need a storage choice (the 5 MB of `localStorage` is too small, IndexedDB is not in `platform`) and a rule for what to keep, and is a ticket of its own. If the answer is "keep", the ticket that would carry it is a new Phase 6 ticket for the saved cache (no key exists yet; it needs its own intent), which the engine would read through a port like the outbox. Owner: Thanh Truong (product owner).
3. Where the messages live: in a second store beside the conversation store. Decided in this spec (a technical choice): a message event changes a window often and should not make the conversation list draw again (R20, Design). Reason: one store would give every list row a new state on every message. Owner: Thanh Truong.
4. How the engine and the connection of TOKI-039 divide the work. Decided in this spec: the connection owns the cursor and tells repeats by number; the engine tells repeats by id and by the rule of R15, applies the events it is given in order and never throws, and owns `reload`. Reason: TOKI-039 R9 and R10 fix the cursor and the order, and the numbers have holes, so only the engine can know what an event changed. The conversation effects of an event are skipped only by the rule of R15 (an event at or below the `eventNumber` of a newer bootstrap), never by a cursor of the engine; the uses of an event's number are the order of a person's status changes (R15, `person_patch`), kept by the store for each person, and the order of the person's notification switches (R15, `preferences_set`), kept by the store in two numbers of its own. Owner: Thanh Truong.
5. What "offline" means for a send. Decided in this spec: the state `offline` of the connection (TOKI-039 R15) decides `waiting`, and `connecting`, `idle` and `stopped` are read as `idle` (a `stopped` for `too_many_connections` as `offline`, TOKI-039 concern 7, decided 2026-11-27); the one automatic try is the send after the wait; a `timeout` while the connection is `online` or `idle` is "Not sent" at once (D-126), and a `network` error while it is `online` waits once and asks the connection to check, because the connection may not yet know that it is down (R10 (d)). Reason: D-097 gives one automatic try after a wait; the journey F11 gives "Not sent" for a failed send; D-079 says a message pressed with no connection waits, and the connection notices a dead socket late. 6. Two tabs and the stored text. Decided in this spec (a technical choice): one stored text for the browser, shared by the tabs; each tab has a `tabId` and each write keeps the items of the other tabs and replaces only its own (R12), so no waiting message is lost; a message restored by two tabs is stored once by the server. Reason: the platform storage has no list of keys and no lock, so a key for each tab could not be found again after a reload, and the last write would drop the other tab's items against D-132 ("nothing lost"). The cost: an item of a closed tab stays until a tab starts. Owner: Thanh Truong.
7. Refreshing a count or the people after an event, instead of counting. Decided in this spec (R14): a held detail is read again after a member event and the bootstrap is read again when a person is unknown. Reason: the payloads carry ids and no counts or names, and a count kept by adding one is wrong when a read overlaps its event. The cost is a request on a member event for a channel whose detail is held. Owner: Thanh Truong.
8. Delete of a message that the server may have stored. Not decided. D-087 says Delete asks nothing, and it does not say what happens when the first request had reached the server and only its answer was lost: the message that the person deleted shows later, as sent, when its event or its page arrives. The engine cannot know whether an answer was lost and cannot withdraw a stored message (deleting a sent message is TOKI-047, and it is not Delete of D-087). Proposal, not a decision: keep it as it is in R11 (Delete removes the local copy and asks nothing); the cases are a lost answer, which is rare, followed by a Delete, which is rarer. The alternative is that Delete of an item whose last error was a `timeout` or `network` also asks the server to delete the message by id once TOKI-047 exists, at the cost of a request and a rule for a 404. Owner: Thanh Truong (product owner).
9. Replies and the main list. Decided in this spec: a message with a `parentId` is neither placed nor counted for `lastMessageAt` by the engine, which cannot tell a reply that was also sent to the channel from one that was not; TOKI-045 adds the key that tells them apart, registers its handler (R18, R16) and calls `setLastMessageAt` for a reply sent also to the channel, so the list time agrees with TOKI-037 R19 and R21. Reason: placing a thread reply in the channel by mistake would show it twice, and the one place that knows the key is TOKI-045. Owner: Thanh Truong.
10. Patches that arrive while a page is being read. Decided in this spec (a technical choice): while a load of a conversation runs, the engine journals every `patchMessage`, `applyMessage` and `removeMessage` and applies them again, in order, to the page and to the aside messages before the merge (R5). Reason: a page read before a commit and merged after its event would replace the held message with the older copy, and an event for a message that the page brings but the window does not hold yet would be lost; the requests of TOKI-046 (concern 3), TOKI-047 and TOKI-048 (concern 9) name both cases for edits, deletes, reactions and pins, and one rule in the engine covers every kind of patch and needs no rule of its own in the page merge. The cost: an `update` must be pure and give the same result twice (R18), and the journal lives only while a load runs. Not done: a send answer is not journaled, since it never replaces a held message (R4). Owner: Thanh Truong.
