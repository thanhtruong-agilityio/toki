# Background job queue design

Date: 2026-11-23 · Status: draft for review
Intent: docs/intents/job-queue.md (Thanh Truong)
Ticket: TOKI-064

## Goal
The builder needs one way to run work later, or away from a request, and to try it again when it fails. Status timers, thumbnails, link previews, reminders and Pause and Focus all need it, and the merged specs of the mail layer, the invitations and the event log already defer to it. This ticket builds the queue on Postgres (pg-boss), the worker process that runs the jobs, and the rules every job follows, so the tickets that come after write only a job and its handler.

## Scope
- In:
  - the `jobs` module of `apps/server` and the pg-boss dependency;
  - the creation and upgrade of the queue's own database schema by `db:migrate`, and the test helper that gives a test a database with that schema;
  - the declaration of a job (name, data shape, retry, timing), the handler, the adding of a job (also inside a database transaction), cancelling a job by key, jobs that start at a time and jobs that recur on a cron schedule;
  - the worker entry `apps/server/src/worker.ts`, its `dev:worker` script, the change of the root `dev` script, the shutdown path of the worker and of the server's queue connection;
  - the retry defaults, the dead-letter queue, the log lines, the `jobs:status` command;
  - the first scheduled job, `realtime.prune-events`, which replaces the in-process pruning timer of TOKI-036.
- Out (not now):
  - Every job of a feature: status expiry (TOKI-056), thumbnails (TOKI-060), link previews (TOKI-061), reminders (TOKI-067), Pause and Focus (TOKI-076), the deletion of files never sent (TOKI-058), Web Push (TOKI-074). Each declares its own job and handler with the tools of this ticket.
  - Any mail job. The mail layer and its callers stay as TOKI-021 and TOKI-024 built them (concern 6).
  - The production image, the Compose service for the worker and its stop grace period: TOKI-084 (concern 12). The automated deploy that runs `db:migrate`: TOKI-085.
  - A screen or API route that shows jobs to an Admin. The operator reads the log and the `jobs:status` command.
  - Any new environment variable (R2).

## Requirements
- R1. The dependency and the module. `apps/server` depends on `pg-boss` at one exact version of major 12, which needs Node 22.12 or later, and has the module `apps/server/src/modules/jobs/`. Its `index.ts` is its only public entry and exports `defineJob`, `defineHandler`, `createJobQueue`, `createWorker`, `installJobsSchema`, `PermanentJobError`, `JobQueueUnavailable`, `JOBS_SCHEMA`, `DEAD_LETTER_QUEUE` and the types of these. The names `pg-boss` and `pg` are imported only by files of `modules/jobs/` and by tests. The module adds no Drizzle table. Check: the export test of the module lists these names; a search of `apps/server/src` for an import of `pg-boss` finds files under `modules/jobs/` only; `pnpm --filter ./apps/server run db:generate` after the change creates no migration.
- R2. No new variable. The queue reads the connection through the existing `database` area of the configuration (`DATABASE_URL`). The schema name is the constant `JOBS_SCHEMA = "pgboss"`. The jobs code adds no row to `docs/environment-config.md` and no line to `.env.example`. Check: the test of TOKI-004 R13 (names read by the schema against `.env.example`) passes unchanged; a search of `modules/jobs/` and `worker.ts` finds no `process.env`.
- R3. The schema is made by pg-boss, in the migrate step. `installJobsSchema(connection, { sleep })` starts a pg-boss instance with `migrate` on, `supervise` and `schedule` off and no instance registration, which creates the schema `pgboss` when it is missing and upgrades it when the installed version is older than the one the library needs. It then waits, calling `sleep(500)` between reads, until the library's background index builds (`getBamStatus`) show no `pending` and no `in_progress` row, for at most 5 minutes, and stops the instance. It returns the schema version it found. A second call changes nothing. `db:migrate` (`src/db/migrate-cli.ts`) calls it after the Drizzle migrations, with the real `sleep`; `runMigrations` of TOKI-005 is not changed. A failure prints what `db:migrate` prints for the Drizzle step (the variable name, or the host and database name when Postgres is unreachable, or the error text; never the password or the whole URL) and exits 1. Check, on a throwaway database: the first call creates the schema `pgboss` and a version row; the second returns the same version and the table list is unchanged; the schema is absent on a database that only had `runMigrations`. A test of `migrate-cli` with Postgres unreachable checks the message and the exit code.
- R4. Drizzle and the queue schema stay apart. Drizzle's migrator and `db:generate` never read, create or drop objects in the schema `pgboss`, and `installJobsSchema` never touches the schema of the application. Check: after `installJobsSchema`, `runMigrations` run again succeeds and `db:generate` reports no change; after `runMigrations` on a database that already has `pgboss`, the schema `pgboss` is unchanged.
- R5. The test database. `tests/jobs-db.ts` exports `createJobsTestDb()`, which makes a throwaway migrated database (as `createMigratedDb` of TOKI-005 does), runs `installJobsSchema` on it with a `sleep` that resolves at once, and returns the migrated database object with its `drop`. The shared test database of TOKI-008 does not get the schema: `global-setup-db.ts` and `setup-file-db.ts` are not changed, so the one-TRUNCATE rule of TOKI-028 R23 does not see `pgboss`. A test that needs a real queue uses `createJobsTestDb()`; a test of another module that only needs to know that a job was added uses the fake queue of R10. Check: a test creates two jobs databases, adds a job in one, and the other holds none; the shared test database has no schema `pgboss` after the global setup.
- R6. Declaring a job. `defineJob({ name, payload, retry?, expireSeconds?, concurrency?, pollingSeconds?, schedule? })` returns a job type. `name` is `<module>.<verb>`, matching `^[a-z][a-z0-9-]*\.[a-z][a-z0-9-]*$`, and is the name of the queue. `payload` is a Zod object schema (R7). `retry`, `expireSeconds`, `concurrency` and `pollingSeconds` override the defaults of R8 within the bounds `retryLimit` 0 to 10, `retryDelay` 1 to 3,600 seconds, `expireSeconds` 10 to 3,600, `concurrency` 1 to 10, `pollingSeconds` 0.5 to 60. `schedule` is `{ cron }` with a five-field cron expression (R16). A value outside a bound, a bad name, or a cron the library cannot read makes `defineJob` throw at once. A job type is declared in the module that owns the work, with its handler beside it, and is exported from that module's `index.ts`. Check: tests of each rule, including a name with an upper-case letter, a name with no dot, `retryLimit` 11, `concurrency` 0 and the cron `61 * * * *`.
- R7. The shape of the data. The payload of a job holds identifiers and numbers, never content. Every property of a payload schema is one of: a string with the `uuid` format, an integer or number, a boolean, a string from a fixed list (`enum`), or a string with the `date-time` format; the schema is `strict` (no other keys). A test walks the JSON Schema (`z.toJSONSchema`) of every job type of the registry (R9) and fails on any property of another kind, so a body, an email address, a code, a token or a link cannot be put in a payload by a free-text property. A handler reads the content it needs from the database by the identifier. Check: the walking test passes for every job of the registry; a test with a payload that has a free string property fails the walk; a payload with an extra key is refused by `enqueue` (R11).
- R8. Defaults. A job with no override has: `retryLimit` 5 (six attempts in all), `retryDelay` 10 seconds, exponential backoff with `retryDelayMax` 300 seconds, `expireSeconds` 300 (the time a handler may run before the library counts it as lost and tries again), `concurrency` 2 (handlers of that job at one time in one worker), `pollingSeconds` 2, completed and failed jobs of the queue kept 86,400 seconds (`deleteAfterSeconds`), and `retentionSeconds` of the library's default. The library's backoff after the n-th failure (n from 0) waits between `retryDelay` × 2^n and `retryDelay` × 2^(n+1) seconds, at most `retryDelayMax`; with these defaults the five waits are 10 to 20, 20 to 40, 40 to 80, 80 to 160 and 160 to 300 seconds, so a job that never succeeds ends in about ten minutes at most. Check: with a handler that always throws and the clock of R19, after each failure the job is not fetched when the clock is moved to the lower bound minus one second and is fetched when it is moved to the upper bound; after the sixth failure it is in the dead-letter queue (R10); a test reads the stored queue options and compares them with these figures.
- R9. The registry. `apps/server/src/job-types.ts` lists every job type of every module (`export const jobTypes = [...]`) and `apps/server/src/job-handlers.ts` lists every handler. A name used twice makes `createJobQueue` and `createWorker` throw at start. A handler whose job type is not in `jobTypes` makes `createWorker` throw. A job type with no handler is allowed in the server process (it only adds jobs) and a worker started with a job type that has no handler logs a warning with the name. A module that adds a job adds its type and its handler to these two files in its own change. Check: tests for the duplicate name, the unknown handler and the missing handler.
- R10. Queues and the dead-letter queue. Both processes ensure, once at start, that every job type of the registry has a queue with the options of R8 and the job's overrides: a missing queue is created; in the worker an existing queue whose options differ is updated to match the registry, so changing a default in the code takes effect at the next start. A second queue, `jobs.dead` (`DEAD_LETTER_QUEUE`), exists for every installation and is the `deadLetter` of every job queue; its completed and failed jobs are kept 14 days (1,209,600 seconds). A job moves to `jobs.dead` when its last attempt fails, when its handler throws `PermanentJobError`, or when its data fails the schema (R13); the stored job keeps its source queue name and its error. Check: tests on a jobs database: queues exist with the expected options after the first start and after a second start; a changed option is updated by the worker and left alone by the server process; each of the three ways ends with one job in `jobs.dead` carrying `sourceName`.
- R11. Adding a job. `createJobQueue({ connection, types, clock?, logger, mode })` returns `{ enqueue, cancelByKey, stop }`. `enqueue(jobType, data, { startAfter?, key?, tx? })` checks `data` against the job's schema (a mismatch throws a `ZodError`, nothing is stored), adds one job and resolves with its id. `startAfter` is a `Date`; `key` is a string of 1 to 128 characters stored as the job's `singletonKey`, and two jobs may carry the same key. The module `jobs` is the only one that calls the library. A fake with the same type, `createFakeJobQueue()` of `tests/jobs-fake.ts`, records `enqueue` and `cancelByKey` calls and runs nothing; the app takes the queue as the option `jobs` of `buildApp` (decorated as `app.jobs` like `app.mail`), and `main.ts` passes the real one. Check: tests that a valid job is stored with its data, its key and its start time; that a bad data object, an unknown job type and a key of 129 characters are refused and store nothing; the fake records calls in order.
- R12. Adding a job inside a transaction. With `tx` (a Drizzle transaction or database of TOKI-005, the `DbClient` type), the job is inserted through that transaction (the library's Drizzle adapter), so a rollback leaves no job and a commit leaves exactly one. Check, with real connections: a transaction that enqueues and then throws leaves no job; one that commits leaves one; a job enqueued in a transaction is not visible to a second connection before the commit.
- R13. Handlers and outcomes. `defineHandler(jobType, async (context, data) => void)` returns a handler. `context` is `{ db, log, clock, signal, attempt }`: the application database, a logger carrying the job name and id, the clock of R19, an `AbortSignal` that aborts when the handler's time (`expireSeconds`) is over or the worker is being stopped past its grace (R15), and the attempt number from 1. The worker checks the data with the job's schema before calling the handler. The outcome is: the handler resolves, the job is completed; it throws any other error, the job is failed and tried again by R8; it throws `PermanentJobError`, or the data fail the schema, the job goes to `jobs.dead` at once with no retry. The queue delivers a job at least once, so every handler must be safe to run twice for the same job, and a handler of a timed job reads the row it acts on again before acting (R14). Check: tests with a real queue for success, a throw that succeeds on the third attempt (the job completes with `retryCount` 2), `PermanentJobError`, invalid data written by a direct insert, and a handler that waits for its signal and sees it abort after `expireSeconds` of clock time.
- R14. A job at a time, and cancelling it. A job added with `startAfter` is not handed to a handler before that time and is handed to one within `pollingSeconds` after it while the worker is running; the default is 2 seconds. `cancelByKey(jobType, key, { tx? })` cancels every job of that type with that key that has not started (created or waiting for a retry) and returns how many it cancelled; a job already running is left to finish, and none of this ticket's code treats a cancel as a guarantee: the handler of a timed job checks that the thing it was set for still holds (for example that the status still has that end time). Check, with the clock of R19: a job with `startAfter` 60 seconds ahead is not run after the clock is moved 59 seconds and 999 milliseconds and runs after it is moved a further 2 seconds; `cancelByKey` stops a waiting job, returns 1, and returns 0 for a running or finished one, and for a key nobody used.
- R15. Shutdown. `createWorker` returns `{ start, stop }`. On `SIGTERM` or `SIGINT`, `worker.ts` calls `stop`, which stops fetching new jobs, waits for the handlers now running for at most 30 seconds (`GRACE_MS = 30000`), aborts the signals of those still running when the time is over, closes the queue's connections, then `worker.ts` closes the application database and exits with code 0. A job whose handler did not finish is not marked completed; the library retries it after its `expireSeconds`. The server process stops its queue (`jobs.stop()`) in the `onClose` hook of the app, before `connection.close()`. Check: a test in which a handler waits on a promise the test controls: `stop` does not resolve before the promise resolves, and the job is completed; a test that `stop` passes `timeout: 30000` to the library; a process test that starts the real `worker.ts` against a jobs database, sends `SIGTERM`, and checks exit code 0 and no further output; a process test of `main.ts` (TOKI-004 R15) still ends with 0.
- R16. Recurring jobs. A job type with `schedule` is created in the library's schedule table by the worker at start, with the job's data `{}` (so its schema has no property) and the library's default `skip` for runs missed while the worker was down. At start the worker also removes from the schedule table every schedule that no job type of the registry declares (a job was renamed or dropped). Only the worker schedules and supervises (maintenance, expiry of lost jobs); the server process does neither. Check: after a worker start the schedule table holds exactly the declared schedules; removing a job type from the registry and starting again removes its schedule; a scheduled job runs when the clock reaches its time (hourly `0 * * * *` at the next full hour) and does not run twice in that hour when two workers are started on the same database.
- R17. Two entries, one codebase. `src/main.ts` stays the API and WebSocket process: it builds the queue with `mode: "producer"` (no handler is registered, no schedule, no supervision) and passes it to `buildApp`. `src/worker.ts` is the worker: it loads the configuration areas `server` and `database` (a feature ticket that adds a handler needing another area adds that area to the list in `worker.ts`), starts the queue with `mode: "worker"` and the handlers of `job-handlers.ts`, opens no HTTP port and handles `SIGTERM` and `SIGINT` (R15). The producer opens no connection until the first `enqueue` or `cancelByKey` without `tx`, so the server starts and `/healthz` answers while Postgres is unreachable (TOKI-004 R20). When Postgres is unreachable, `enqueue` rejects with `JobQueueUnavailable` (carrying no URL), and the next call tries to start again. At start the worker retries the connection up to 10 times, with the library's waits of 1 second doubling to 30 seconds, then logs one error line and exits with code 1. The pool of the producer is 2 connections and the pool of the worker is 4; each connection reports the name `toki-api` or `toki-worker` as its `application_name` (concern 11). Check: a server built with a producer queue never runs a handler even when a job exists; a queue pointed at a loopback port where nothing listens is built without throwing, `enqueue` rejects with `JobQueueUnavailable`, and after the database is available the same instance enqueues; the process test of R15 for the exit code; the worker started with no database exits 1 after its attempts (the test passes a `sleep` that resolves at once); `pg_stat_activity` shows the two `application_name` values.
- R18. Log lines. Every line the queue writes is a JSON object of the server's logger. A handler run writes one line when it ends with the fields `job` (the queue name), `jobId`, `attempt`, `durationMs` and `outcome` (`completed`, `failed`, `dead` or `aborted`); a failure line, at level `warn` while a retry remains and `error` when the job goes to `jobs.dead`, also holds `errorName` and `errorMessage`. No line holds the data of a job. The library's `error` events are logged at `error` and its `warning` events at `warn`; a worker never exits because of them. The module's rule for handlers: an error message holds identifiers and codes, never a message body, an address, a code or a token, because the message is also stored on the job for 14 days. Check: a captured log (as TOKI-004 R6 does) of a success, a retry and a dead job holds these fields and no value of the data; a test that makes the library emit an `error` event sees one `error` line and a live worker.
- R19. The clock. No file of `modules/jobs/` and no file of the handlers written by this ticket calls `Date.now()`, `new Date()` or the global timer functions (TOKI-008 R19). Time reaches the code through the `clock` of `createJobQueue` and `createWorker`, which is the clock of the library: the system clock by default, and in a test the library's `TestClock`, which moves the time of the library's timers and the time Postgres uses for the queue together. The handler's `context.clock` reads the same clock (`now()` only). A test waits for a job with the library's spy (`getSpy(name).waitForJobWithId(id, "completed")`, enabled only by the test option `spies`) and moves time with `clock.tick(ms)`; no test waits with a real timer. Check: the source search above; every test of this ticket that involves time uses `TestClock` and no `setTimeout` or `sleep` with a real delay; the first test creates the clock at the instant `DEFAULT_TEST_INSTANT` of TOKI-008.
- R20. `jobs:status`. `pnpm jobs:status` (root script; the script `jobs:status` of `apps/server`, which loads `.env` like `db:migrate`) prints one line per queue: name, jobs waiting, waiting for a retry, running, failed, and the age in seconds of the oldest job that is ready, then one line for `jobs.dead` with its count and the names of the queues its jobs came from. It reads through the library without starting the worker and writes nothing. It exits 0 when it could read, 1 when the variable is missing or Postgres is unreachable (the messages of `db:migrate`), and prints no job data. Check: a test on a jobs database with three jobs in different states and one dead job compares the printed counts; the two failure messages.
- R21. Pruning becomes the first job. A job type `realtime.prune-events` is declared in the `realtime` module (TOKI-036) with `schedule: { cron: "0 * * * *" }`, an empty payload and `expireSeconds` 600; its handler calls `pruneEvents(db, { before })` with `before = clock.now()` minus `EVENT_RETENTION_DAYS` days, and logs the count removed (an error is logged by R18 and retried by R8). `startEventPruning`, `EVENT_PRUNE_INTERVAL_MS`, the `setInterval` schedule built in `main.ts` and the stop of the pruning in its `onClose` hook are removed, with their tests (`realtime/prune-start.test.ts`, the pruning part of `main.test.ts`); `pruneEvents` and its tests do not change. The hourly period is the one TOKI-036 R21 set. Check: the handler test on a jobs database with events at six times removes the same rows as the `pruneEvents` test of TOKI-036; the schedule test of R16 holds `realtime.prune-events`; a search finds no `startEventPruning` in `apps/server/src`; `pnpm --filter ./apps/server test` passes with the removed tests gone.
- R22. Development commands. `apps/server` gains `dev:worker` (`tsx watch --env-file=../../.env src/worker.ts`) and `jobs:status`. The root `dev` script becomes `pnpm -r --parallel --if-present run "/^dev(:worker)?$/"`, so `pnpm dev` starts the server and the worker together with the web app, and no other script of the workspace is matched; the root gets `jobs:status` and the "Common commands" of `CLAUDE.md` and the rule file of the server area list the two new commands. Check, by hand once and recorded in the pull request: `pnpm dev` starts both processes and the worker logs its start line; a job added through a test route is run by the worker; stopping `pnpm dev` ends both with no error line.
- R23. No mail job here. This ticket adds no job that sends mail, and the payload rule R7 makes it impossible to queue a one-time code or an address. Mail that carries a one-time code (sign-in, invitation, resend) stays sent at once by its caller, which reports the result (TOKI-021 R17, TOKI-024). Check: the walking test of R7 over the registry; a search of `modules/mail/` finds no import of `modules/jobs/`.
- R24. Boundaries and commands. No file of `modules/jobs/` imports another module except through its `index.ts`, and none imports `@toki/client-core`, `@toki/ui-web` or a browser API; a feature module imports the queue only from `modules/jobs/index.ts`. Check: `pnpm lint` passes; the export test of R1.

## Design
### Data model
No table of the application. The library creates and owns the schema `pgboss` (version table, queue table, the job table and its partitions, schedule, subscription, instance and warning tables) in the application's database. Nothing of the application points to it, and it holds only the job data of R7. It is not covered by `dev:reset:db` of TOKI-003 beyond what that script already does (it wipes the whole database and then calls `db:migrate`, which now also creates the queue schema again).

### Queues and names
| Name | Purpose |
|---|---|
| `<module>.<verb>` | One queue per job type, for example `realtime.prune-events` |
| `jobs.dead` | Dead-letter queue shared by all job queues; each stored job keeps its source queue and its error |

### Process model
```
 main.ts   (API + WebSocket)  --- producer: enqueue, cancelByKey --->  pgboss.* tables  <---  worker.ts (handlers,
 apps/server, `server`/`database`/...                                 same Postgres                  schedules, maintenance)
```
One image and one codebase, two commands. The technical design draws the app and the worker as two boxes that both use Postgres; this follows it.

### Layout
```
apps/server/src/
├─ main.ts                    builds the producer queue, passes it to buildApp, stops it in onClose
├─ worker.ts                  worker entry: config, createWorker, signals, exit codes
├─ job-types.ts               every job type of every module (R9)
├─ job-handlers.ts            every handler of every module (R9)
├─ cli/jobs-status.ts         pnpm jobs:status (R20)
├─ db/migrate-cli.ts          also calls installJobsSchema (R3)
└─ modules/jobs/
   ├─ define.ts               defineJob, defineHandler, PermanentJobError, bounds (R6, R7, R13)
   ├─ defaults.ts             the constants of R8 and GRACE_MS
   ├─ install.ts              installJobsSchema (R3)
   ├─ queue.ts                createJobQueue: lazy start, queues, enqueue, cancelByKey (R10 to R12, R14, R17)
   ├─ worker.ts               createWorker: handlers, schedules, shutdown (R13, R15, R16)
   ├─ log.ts                  the log lines (R18)
   └─ index.ts                the public entry (R1)
apps/server/tests/
├─ jobs-db.ts                 createJobsTestDb (R5)
├─ jobs-fake.ts               createFakeJobQueue (R11)
└─ jobs/*.db.test.ts, jobs/*.test.ts
```

### Errors
- Data that do not match the job's schema when adding -> `ZodError` from `enqueue`, nothing stored (R11).
- Postgres unreachable when adding -> `JobQueueUnavailable`; in a request it becomes the `internal_error` of TOKI-004 (R17).
- The handler throws -> retry with backoff, then `jobs.dead` (R8, R10, R13).
- The handler throws `PermanentJobError`, or the data fail the schema in the worker -> `jobs.dead` at once (R13).
- The schema `pgboss` is missing when a process starts -> the library refuses to start; the process logs that `db:migrate` has not run and the worker exits 1 after its attempts; the server process answers `JobQueueUnavailable` to an `enqueue` (R17). Neither process creates the schema.

## Testing
- Written test-first. Unit tests need no database: `defineJob` bounds and names (R6), the walk of R7, the registry rules (R9), the fake queue (R11), the source searches (R1, R2, R19, R23, R24).
- Tests with a real queue use `createJobsTestDb()` (R5), one database per test file, and run in the database project of TOKI-008 (`*.db.test.ts`). Each builds its queue with the library's `TestClock` and the option `spies`, and waits for a job with the spy and moves time with `tick`, never with a real delay (R19). Backoff checks use the bounds of R8, not a fixed delay, because the library adds a random part.
- Real connections are used for the transaction tests (R12) and for the two-workers test (R16); they wait on the state of the database, not on time, as the concurrency tests of TOKI-036 do.
- Process tests start the real `worker.ts` and `main.ts` with a fake environment, as TOKI-004's process test does, and check exit codes (R15, R17).
- The pruning handler test (R21) reuses the event rows helpers of TOKI-036's tests and checks the same expected rows; fake data only.
- R22 is checked by hand once on the builder's machine and its output goes in the pull request; it starts the real services.

## Data safety
- A job's data are identifiers and numbers only (R7): the payload is stored in Postgres for up to 24 hours after completion, and 14 days in `jobs.dead` with the error. No message body, address, code or token is ever stored there.
- No log line holds job data (R18). The error message of a handler is stored and logged, so a handler's errors carry identifiers and codes only (R18).
- The queue connection reuses `DATABASE_URL`; it is never written to a log or an error (R3, R17).
- A job that is run twice must do no harm (R13); a duplicate message, push or file deletion is a bug of the handler, and each feature ticket tests its handler twice.

## How each constraint in the intent is met
| Constraint | Met by |
| :---- | :---- |
| The queue is pg-boss on Postgres; no Redis | R1, R3; concern 2 |
| One modular monolith in Node 22; the worker is a separate process on the same database | R17, concern 1; the dependency needs Node 22.12 (R1, concern 12) |
| One server, up to about 200 people | Defaults of R8 and the pool sizes of R17 (concern 11) are small; no clustering is built |
| The queue holds the jobs of the technical design | R6 to R16 give every one of them its tools: timed jobs (R14), recurring jobs (R16), retries (R8), the transaction (R12); the feature jobs are out of scope and listed with their owners (concern 10) |
| A failed job is retried | R8, R10, R13 |
| Test-first, timers with the controllable clock | R19 and Testing |
| Migrations forward-only, applied by command, not at server start | R3, R4; neither process creates the schema (Errors) |
| Messages and mail never in a log | R7, R18, R23 |
| The server starts and answers `/healthz` while Postgres is unreachable | R17 (lazy start) |
| Milestone M4, size M, needs TOKI-005 | Scope; the one added need, TOKI-036, is concern 9 |

## Open questions from the intent
- Does the worker run inside the server process or as its own process? Answered in this spec: its own process, `worker.ts`, one image (concern 1).
- Who creates the queue library's own database schema, and how does a test get it? Answered in this spec: `installJobsSchema`, called by `db:migrate`; a test gets it from `createJobsTestDb` (concerns 2 and 3).
- How many times, and with what waits, is a failed job tried again? Answered in this spec: five retries, 10 seconds doubling to at most 300 (R8, concern 5).
- Does the job queue take over the pruning of old events from TOKI-036? Answered in this spec: yes, R21 (concern 9).
- Can a job that carries a one-time code be queued? Answered in this spec: no, and no payload can hold one (R7, R23, concern 6).
- How exactly does a job that starts at a given time keep its time, and how does it stop when the reason for it is gone? Answered in this spec: R14 (concern 7).
- How does an operator see that jobs are failing? Answered in this spec: log lines, `jobs.dead` and `jobs:status` (R18, R20, concern 8).

## Areas of concern
1. Where the worker runs. Decided in this spec: a second process, `apps/server/src/worker.ts`, from the same codebase and image as the server, started with its own command; the server process only adds jobs. Reason: the technical design draws the worker as its own box beside the app; thumbnails and link previews do slow and CPU-heavy work that must not block the event loop that carries the WebSocket; the worker can restart without dropping connections. Alternatives refused: running the handlers in the server process (simpler to start, but a slow handler delays the messages that must reach another person in 150 ms, NFR-13); a separate package or app for the worker (the handlers use the modules of the server, so a second app would copy or export them). Cost accepted: one more process to start in development (R22) and one more service in Compose (TOKI-084, concern 12). Owner: Thanh Truong.
2. The schema name and who owns its migrations. Decided in this spec: the schema is `pgboss`, the library's default, in the application's database; the library creates and upgrades it, and `db:migrate` triggers that (R3). Drizzle never manages it (R4). Reason: the library versions its own schema and ships its own upgrades; copying its SQL into a Drizzle migration would fix one version of it and break at the first library upgrade, and Drizzle could not roll the library's later changes into its journal. Alternatives refused: the SQL of the library's construction plan inside a Drizzle migration (stale at the next upgrade); letting each process create the schema at its start (two processes would race, migrations would run outside the deploy step, and TOKI-005 says migrations are applied by command only). Owner: Thanh Truong.
3. How a test gets the schema (TOKI-008). Decided in this spec: `createJobsTestDb()` makes a throwaway database and installs the schema; the shared test database does not get it (R5). Reason: the shared database is emptied by one TRUNCATE of the application's tables between files; leaving jobs behind in a schema that script does not know would make files depend on each other, and a throwaway database per file cannot. A test of another module that only needs to know a job was added uses the fake queue. Owner: Thanh Truong.
4. The registry, the typing and the queue names. Decided in this spec: a job is a typed object, `defineJob`, with a Zod data schema; its handler is a typed function bound to it; the two lists `job-types.ts` and `job-handlers.ts` hold all of them; the name is `<module>.<verb>` and is the queue name (R6, R9). Reason: the data type then flows from the schema to `enqueue` and to the handler without a cast; the module name in the queue name shows who owns a job in the log and in `jobs:status`; two lists outside the modules keep modules from importing each other. The library's `publish` and `subscribe` fan-out, its workflow `flow` and its group concurrency are not used in this ticket; a later ticket may, with a spec of its own. Owner: Thanh Truong.
5. Retry and backoff defaults. Decided in this spec: five retries, a first wait of 10 seconds that doubles with the library's random spread up to 300 seconds, a run limit of 300 seconds, two handlers at a time, completed jobs kept 24 hours (R8). No decision of the product fixes these figures. Reason: a failure caused by a restart or a network gap clears in under a minute, so the early retries are quick; a failure that lasts ten minutes will not be cured by waiting, and a thumbnail, preview or status clear that arrives later than that is of little use to the person, so the job then goes to `jobs.dead` for the operator. A job with other needs overrides within the bounds of R6. Owner: Thanh Truong.
6. What may be in a payload, and mail. Decided in this spec: a payload holds only identifiers, numbers, booleans, fixed words and timestamps (R7); mail that carries a one-time code is not queued (R23). This is the answer to TOKI-021 concern 5. Reason: a payload is stored; a code would be stored in clear, and a hash cannot be turned back into a code by a handler; a rule the test can check (R7) is stronger than a rule in prose. A future mail job with no secret (for example a digest) reads the address and the text from the database by identifier and is its own ticket's work; the retry defaults of R8 apply to it. Owner: Thanh Truong.
7. Time-based jobs and their cancel. Decided in this spec: a timed job is a job with `startAfter`; the worker's poll every 2 seconds (`pollingSeconds`) is the precision, so an end of status or a reminder fires within 2 seconds after its time while the worker runs, and late, but still, after a stop of the worker (R14). A cancel by key removes a job that has not started; the handler re-checks the row, so a job that already started, or a cancel that failed, does no harm. Reason: the cancel is a saving of work, not the rule; the rule in the data is what makes a timer correct after a crash or a double run. A job that must fire at a minute second-accurate would need LISTEN/NOTIFY or a shorter poll, and the technical design asks for neither. The product rules about what a timer does, such as holding a reminder during Pause or Focus (TOKI-067, D-072), are those tickets'. Owner: Thanh Truong.
8. Observability. Decided in this spec: JSON log lines for every run (R18), the dead-letter queue as the record of what failed for good, and `pnpm jobs:status` for counts (R20); no screen and no route. The worker has no HTTP port; whether Compose checks it, and how, is TOKI-084's (concern 12). Reason: one VPS and one operator (D-004, NFR-07); the Admin page of the product has no jobs area in any decision, so adding one would be a product decision. The library's OpenTelemetry output is left off (no collector exists). Owner: Thanh Truong.
9. Pruning and the plan. Decided in this spec: this ticket takes over event pruning from TOKI-036 (R21), which TOKI-036 concern 11 allowed. Reason: the log is then pruned by one job, once an hour for the whole installation, instead of by a timer in every copy of the server; a failure is logged and retried; the first scheduled job proves the recurring path end to end. One consequence is a plan change for the product owner to confirm: TOKI-064 now also needs TOKI-036 (it removes code that TOKI-036 adds). The plan places TOKI-036 in M3 and TOKI-064 at the start of M4, so the order already holds. If TOKI-036 is not built when this ticket is built, R21 is built with TOKI-036's pruning in place of the removal and nothing else changes. Owner: Thanh Truong.
10. Who registers which job, and the lines with the neighbouring tickets. Decided in this spec: a job belongs to the module that owns the work and is declared and handled there; this ticket declares only `realtime.prune-events`. TOKI-058 (file storage) declares the job that deletes a file uploaded and never sent after 24 hours (D-130), as a recurring job in its `files` module, with its own handler, using R6, R9 and R16; this ticket does not delete files. TOKI-069 (search index) adds a column and an index and writes the column in the message write; it needs no job from this ticket. TOKI-053 (read pointer) and TOKI-055 (presence) need none: presence works on the live WebSocket connections and changes within a second, and a job's 2-second poll is no fit for that. TOKI-103 (disk-space warning) measures the disk when asked; if it decides to measure on a schedule it declares a recurring job of its own. TOKI-056, 060, 061, 067, 074 and 076 each declare theirs. A feature ticket changes `job-types.ts` and `job-handlers.ts`, and `worker.ts` when its handler needs another configuration area (R17). Owner: Thanh Truong.
11. Pools, connections and the clock. Decided in this spec: the producer has a pool of 2 connections and the worker a pool of 4, besides the 10 connections of the application's own pool in each process (the default of the Postgres client of TOKI-005); about 26 connections in all against Postgres's default limit of 100. `application_name` tells them apart in `pg_stat_activity`. The queue library keeps its own connection pool because it uses another Postgres client; a job is added in a caller's transaction through the library's adapter (R12), so a job and the change it belongs to commit together. The clock of the queue is the library's, because the library moves the time of Postgres with it (R19); the `Clock` of `@toki/shared` has only `now()` and cannot move a timer, so handlers read it through `context.clock` and tests use the library's `TestClock`, started at `DEFAULT_TEST_INSTANT`. Owner: Thanh Truong.
12. Hand-offs to the production image and the deploy (TOKI-084, TOKI-085). Decided in this spec, from this ticket's side: Compose runs two services from one image, `server` with the command that runs `main.ts` and `worker` with the command that runs `worker.ts`; the image's Node must be 22.12 or later (the library needs it); the worker's stop grace period must be longer than `GRACE_MS` (30 seconds), for example 40 seconds, or Compose kills it while it drains; `db:migrate` runs before either service starts, and now also creates the queue schema (R3), so the deploy step needs no second command; `worker.ts` and `jobs-status.ts` are named entries in the image like the other commands. TOKI-084 decides the worker's health check and its restart policy; the worker exits 1 only when it cannot start (R17), so a restart policy of "on failure" restarts it correctly. Owner: Thanh Truong.
