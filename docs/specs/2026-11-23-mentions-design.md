## Goal
A person writes `@` and a name to call someone, and today nothing happens: no list of people, no record of who was named, no tint on the message of the person who was named. This work builds mentions end to end: the list that opens in the composer, the rule that finds the names in a text, the table that keeps who was mentioned in which message, the confirmation for `@channel` in a big channel, the offer to add a person who is not in the conversation, the effect of an edit, and the key `mentions` that every copy of a message carries so that the tint, the chip, the `@` dot and the Activity items can be built from it. It creates no Activity item, no toast, no push and no unread flag: those read what this work stores (Hand-offs).

## Requirements
The rule in the text
- R1. `packages/shared/src/mentions/find.ts` exports `findMentions(text, people, options)`, a pure function with no DOM global, where `people` is `{ id: string; displayName: string }[]` and `options` is `{ channel: boolean }`. It returns the spans it finds in the order they appear: `{ start: number; end: number; kind: "user" | "channel"; userId: string | null }`, `start` and `end` being offsets in the code units of the text it was given (`end` is exclusive), `start` at the `@`. Spans never overlap. A name is compared after the folding of R2: the text and the name are folded one code point at a time, so a letter with its mark compares equal to the letter without it, and the offsets still point into the original text. A span for a person covers `@` and the display name as the text has it; the combining marks (U+0300 to U+036F) that follow the last letter belong to the name. `findMentions` never throws for any string, including a lone surrogate, an `@` at the end and an empty list. Check: a table test: "hi @Lan Nguyễn," with a person "Lan Nguyễn" gives one span from 3 to 14, and the same with "@lan nguyen" and with the name typed in decomposed form (the letters followed by combining marks) gives the same person and the span of the text as written; "@Lan" with only a person "Lan Nguyễn" gives none (concern 1); "" and "@" and "a@" give none; a lone surrogate after `@` gives none and does not throw; two mentions of the same person give two spans (R5 keeps one person once).
- R2. Which `@` counts, and which person it names. (a) An `@` opens a mention only at the start of the text, after white space, or after one of `*`, `_`, a backtick, `(`, `[`, `{`, `"` or `'` (so `*@Lan*` after a bold mark is a mention and `a.b@lan` is not). (b) The folding is: Unicode form NFD, the combining marks U+0300 to U+036F removed, `đ` and `Đ` turned into `d`, lower case: the rule of `foldSearchText` of TOKI-032 R19; `packages/shared/src/text/fold.ts` exports it as `foldText`, and `foldSearchText` of `client-core` becomes a re-export of it (the server needs the same rule and may not import `client-core`; same name, same behaviour, its tests stay valid). (c) A name matches when the folded text after the `@` starts with the whole folded display name (trimmed) and the character after it in the original text is not a letter or a digit (`\p{L}`, `\p{N}`) or is the end of the text. (d) The longest matching name wins ("Lan Nguyễn" over "Lan"). (e) When two people with different ids have the same folded name and it is the longest match, none of them is named (concern 2). (f) `@channel` is the word `channel`, compared folded and with the boundary of (c); it counts only when `options.channel` is true, and it wins over a person whose name is "channel". `@here`, `@everyone` and every other word is plain text (D-017). (g) The text is read as a plain string: a mention inside a code mark counts like any other (concern 6). Check: each letter of (a) as a preceding character and an email address; the boundary of (c) with "@Lan.", "@Lan," and "@Lanx"; (d) with the two names; (e) with two people "An" and "An" (none named) and with "An" and "Án" (folded alike, none named); (f) with `options.channel` true and false, upper case "@CHANNEL", "@channels" (no span) and a person named "channel"; "@here" and "@everyone" give none.
- R3. `packages/shared/src/mentions/` also exports `MessageMentionsSchema`, a strict object `{ userIds: string[], channel: boolean }` with its type `MessageMentions` (the ids are distinct and in ascending order), the constant `EMPTY_MENTIONS`, `MentionDeltaSchema` and its type `MentionDelta` (`{ mentions: MessageMentions, added: string[], removed: string[], channelAdded: boolean, channelRemoved: boolean }`) and `CHANNEL_MENTION_CONFIRM_FROM`, 20 (D-041, FR-17). `MessageEntry` of TOKI-037 R15 gains the key `mentions` (a `MessageMentions`, as that spec allows later work to add keys), always present, `EMPTY_MENTIONS` for a system line, a deleted message and a message that names nobody. Check: schema tests accept the empty value and one with two ids and refuse an added key, a missing key, a repeated id, ids out of order and a non-boolean `channel`; every entry the other tests parse carries the key (their fixtures are updated in this change); a type test imports each name from `@toki/shared`.

The server
- R4. The table `message_mentions`, in `apps/server/src/modules/mentions/schema.ts` (a table of its own: this work adds no column to `messages`, TOKI-036 concern 7), with a migration made by `pnpm db:generate --name message_mentions` (TOKI-019 convention 8; the whole `apps/server/migrations/` change is committed). Columns: `message_id` (`uuid`, not null), `user_id` (`uuid`, null) and `is_channel` (`boolean`, not null, default false). The check `message_mentions_target_check` says `(user_id is null) = is_channel`: a row names one person or is the `@channel` row, never both and never neither. A unique index on (`message_id`, `user_id`) where `user_id is not null` and one on (`message_id`) where `is_channel`, so a message names a person once and `@channel` once. An index `message_mentions_user_idx` on (`user_id`, `message_id`) where `user_id is not null` serves the question "which messages mention this person" that TOKI-053, TOKI-054 and TOKI-065 ask. The foreign keys to `messages(id)` and to `users(id)` cross a module boundary, so they are written as SQL in the migration with the names `message_mentions_message_id_fkey` and `message_mentions_user_id_fkey` (TOKI-019 R22; a schema file may not import another module's table). A row is never deleted when its message is deleted (R11) and never updated. Check: the migration test lists the table, the check, the three indexes and the two foreign keys by those names in `pg_constraint` and `pg_indexes`; a row with both columns set, one with neither, a second row for the same person and a second `@channel` row each fail with the name of the constraint; one SQL file is new in the migration folder.
- R5. Who can be mentioned, and what is stored. `resolveMentions(tx, input)` in `apps/server/src/modules/mentions/resolve.ts` takes the conversation (`id` and the facts of TOKI-028), the actor and the text, and returns a `MessageMentions`. The candidates are the people with a member row in that conversation whose status is `active`, without the author: a person outside the conversation, a person who left, a deactivated person (F41) and the author (AC-037) are never stored, and the text that names them stays plain text (D-058, D-135). `channel` is true when the text holds `@channel` (R2 (f)) and `canUseAtChannel(actor, conv)` of TOKI-027 R6 allows (a member of a channel that is not archived): in a direct message or a group `@channel` is plain text and no error. A person named twice is stored once (AC-036: one mention, one item). A text that holds no `@` makes no read at all. A mention never makes a send or an edit fail: no name, however wrong, gives a 400, a 403 or a 404. The members are read with `listMemberIds` of `conversations` and the new `getPeopleByIds(db, ids)` of `members` (`{ id, displayName, status }[]`, one statement), both through their `index.ts`; no lock is taken, because the send already holds the conversation row `FOR SHARE` and a person who is deactivated at the same moment is at worst mentioned once more (the actor's own lock order is TOKI-037 R8, unchanged). Check: with a fixture of a channel with five members, one deactivated, one who left, and a person outside it: a text naming each of the six gives the active members only; a self-mention gives none; "@Lan @Lan" gives one id; `@channel` in a public channel, a private channel, a direct message and a group gives `true`, `true`, `false`, `false`; a text with no `@` is a statement log with no read of members; an unknown name returns `EMPTY_MENTIONS` and the route answers 201.
- R6. A new message keeps its mentions. `saveMentions(tx, input)` of `modules/mentions/write.ts` (`input`: the conversation facts, the actor, the id of the message and its text) calls `resolveMentions`, inserts the rows with `ON CONFLICT DO NOTHING` in one statement and returns a `MentionDelta` with `added` all the people, `removed` empty and `channelAdded` the flag. The send route of TOKI-037 calls it inside its transaction, for a stored message only, after the insert of the message and before it builds the entry and before any call of `recordChange`; the reply of TOKI-045, which is the same route, gets the same call. A repeat (TOKI-037 R5) and every refusal call it zero times, so a repeat stores no second set. The route receives it as the dependency `saveMentions` that `app.ts` gives it (R10); the default does nothing and returns an empty delta, so the tests of TOKI-037 and TOKI-045 that do not pass one stay valid. Check: a send of "hi @Mai" in a channel with Mai leaves one row `(message, Mai)` and an entry whose `mentions.userIds` is `[Mai]`; the same send twice leaves one row and the second answer (200) carries the same `mentions`; a refused send (archived channel, non-member) leaves no row; a rollback after the call leaves no row; a reply with a mention leaves the row for the reply's id; a statement log shows the insert after the message insert and before the `recordChange` call, and no statement for a text with no `@`.
- R7. An edit recomputes. The edit route of TOKI-047 calls `saveMentions` with `isEdit: true`, inside its transaction, after the message row is locked and updated and before it builds the entry and calls `recordChange`, for an edit that changed the text. It reads the rows the message has, computes the new set from the new text (R5), deletes the rows that are no longer named, inserts the new ones, and returns a `MentionDelta`: `mentions` the new set, `added` the people named now and not before, `removed` the people named before and not now, `channelAdded` and `channelRemoved` likewise. A person named before and after is in neither list, so an edit never tells again a person who was told (F16: only the newly mentioned person is notified). A text with no `@` and a message with no rows makes no statement beyond the read of the rows. An edit that changes nothing (TOKI-047 R3) does not call it. Check: "hi @Mai" edited to "hi @Mai and @Sam" gives `added` `[Sam]`, `removed` empty, rows Mai and Sam; edited to "hi" gives `removed` `[Mai, Sam]`; edited to "hello @Mai" gives both lists empty; `@channel` added and removed gives `channelAdded` then `channelRemoved` and the `is_channel` row follows; a person who was deactivated after the first text and is still named in the new text is not stored again and is in `removed` (R5 stores active people only); a rollback leaves the old rows.
- R8. The entry carries the mentions. `listMentionsOfMessages(client, messageIds): Promise<Map<string, MessageMentions>>` is exported from `modules/mentions/index.ts`: one statement, `where message_id = any($1)`, grouped in code, ids in ascending order, `channel` from the `is_channel` row, a message with none has no key in the map. The `messages` module imports nothing of `mentions`: `app.ts` passes the function as `readers.listMentions` to `buildMessageEntry` and `buildMessageEntries` (TOKI-045, "The entry builder"; the shape of `listReactions` of TOKI-046 R10), which call it once for the ids of the messages of `kind` `user` that are not deleted and set `mentions` from the map, `EMPTY_MENTIONS` when absent, for a system line, for a deleted message and when the reader is not given. Every place that returns or sends an entry goes through the builder, so the history, the replies, the send answer, the answer and the event of an edit, and every event carry `mentions`; the `message.created` and `message.edited` events of TOKI-038 and TOKI-047 carry the new set with no change to the event code. Check: a page of 20 messages calls the reader once; a deleted message and a system line (rows inserted by SQL) have `EMPTY_MENTIONS`; the entry of a send, the entry of an edit and the `message` of the recording handler's `change` equal the 200 body, `mentions` included.
- R9. What the changes carry for Activity and notifications. `Change` of `conversations/changes.ts` gains the optional field `mentionDelta` (a `MentionDelta`, imported as a type from `@toki/shared`). The send sets it on `message_created` (R6), and the edit sets it on `message_edited` (R7). It is always set by these two routes, empty when nobody is named. TOKI-065 reads `change.mentionDelta` to create the items (`added`, `channelAdded`) and to remove them (`removed`, `channelRemoved`, F13), and `change.message.mentions` for the full set; TOKI-045 and TOKI-065 read `mentions.userIds` for the follow rule of threads; TOKI-073 reads the same to decide who is told. This work writes no event and calls `recordChange` no extra time. Check: with a recording handler, the send and the edit each leave one `message_created` or `message_edited` call whose `mentionDelta` equals the delta of R6 or R7; a repeat and a refusal leave none; a type test checks the optional field.
- R10. The module and its wiring. `apps/server/src/modules/mentions/` holds `schema.ts` (not exported), `resolve.ts`, `write.ts`, `read.ts` and `index.ts`, which exports `saveMentions`, `listMentionsOfMessages` and no table. `mentions` imports `conversations` (`listMemberIds`, the facts types) and `members` (`getPeopleByIds`) through their `index.ts` and imports `messages` nothing; `messages` imports `mentions` nothing; neither `conversations` nor `members` imports `mentions` (the lint rule `toki/module-entry` checks the paths). `apps/server/src/app.ts` gives `saveMentions` to `messageRoutes` and to the edit routes and `listMentionsOfMessages` to the builder, as it does for reactions. The export tests of the three modules list the new names. Check: `pnpm lint` and `pnpm lint:boundaries` exit 0; a test starts the app with `buildApp` and sends a message that mentions a member through the real wiring and reads it back with its `mentions`; a search finds no import of another module's `schema.ts`.
- R11. A delete keeps the rows. A deleted message's rows stay (TOKI-036: a message row is never removed and nothing here takes a row away on a delete); every read of mentions ignores a deleted message (R8: its entry says `EMPTY_MENTIONS`), and a later read that joins `messages` for an unread flag or a list filters `deleted_at is null` (Hand-offs). The Activity items of a deleted message are removed by TOKI-065 (F13). Check: a message with a mention row deleted by SQL has `EMPTY_MENTIONS` in the page and in the entry of its delete; the row is still in the table.

The list in the composer
- R12. The people the list offers. `useMentionCandidates(conversationId)` in `apps/web/src/conversation/mentions/` returns `{ candidates, status, ensureLoaded }`. `candidates` is the people with a member row in the conversation, as `{ id, displayName }`, in the order of the member list, without the signed-in person and without a person whose `status` is `deactivated` (F41, context states; the display name and status come from the people of the bootstrap call). For a direct message or a group the member ids are the entry's `memberIds`; for a channel they are read with `api.channels.members(id)` of TOKI-032 in pages of 100 (the largest page of TOKI-029 R8) until `nextCursor` is `null`, once for each conversation, started by `ensureLoaded` (called when the first `@` is typed and by the offer of R18) and kept in a module-level store that the member events of the sync engine (`member.joined`, `member.left`, `member.removed`, `registerEventHandler` of TOKI-040 R18) and the person's own add (R18) invalidate for that conversation. While the read runs `status` is `loading` and the list shows only `@channel` where it applies; a failed read leaves `candidates` empty and `status` `failed`, with no message and no retry button (the list simply has no people; the next `@` starts a new read). Check: a hook test with a fake API: a channel of 230 members makes three requests (100, 100, 30) and one for the second `@`; the signed-in person and a deactivated person are not in `candidates`; a `member.removed` event for the channel makes the next `@` read again and one for another channel does not; a direct message reads no request; a failed page leaves `candidates` empty and does not throw.
- R13. The list: trigger, filter and order. `findTrigger(value, caret)` of `packages/client-core/src/mentions/trigger.ts` is pure: it looks at the text before the caret and returns `{ start, query }` when it ends with an `@` that follows the start of the text or white space and then at most characters that are neither white space nor `@` (the prototype's `(^|\s)@([A-Za-zÀ-ỹ]*)$`, widened from letters to any character but white space and `@`, because a display name starts as the part of the address before the `@`, such as `hoa.tran`, FR-06), and `null` otherwise. `rankCandidates(candidates, query, { channel })` returns the rows: the `@channel` row first when `channel` is true and `channel` matches the folded query as a prefix (or the query is empty), then the people whose folded display name, or whose folded display name from the start of any word of it, starts with the folded query ("nguyen" finds "Lan Nguyễn", the journey's "with or without diacritics"), in the order of the candidates. An empty result closes the list (the prototype hides it when nothing matches). The list shows every matching row; whether it stops at 50 and loads more on scroll is concern 5. The list opens when `findTrigger` gives a result after a change from the person (source `input` or `tool`) or after a caret move, and never for a restored draft (source `restore`, TOKI-043 R16), so a draft that ends with `@Mai` does not open a list on a page load. It closes when the trigger no longer holds, when the field loses focus or a press lands outside the list and the field (a `focusin` or `pointerdown` listener of the hook; the composer has no blur prop), and after an insert. Check: pure tests of `findTrigger` ("@", "hi @ma", "a@b", "x @a b" at the caret after "a", "@hoa.tran", a caret in the middle of a word); of `rankCandidates` (the empty query, "ng" finding "Lan Nguyễn" and "Ngọc", "nguyen", the order, `channel` false hides the row, "chan" finds only the row, a person named "Chan" is listed after it); a component test: typing "@" opens, a draft restored with "@Mai" does not, a press elsewhere closes it, moving the caret out closes it.
- R14. Keys and insert. The hook passes one function in `keyInterceptors` (TOKI-043 R16); while the list is open it consumes: `ArrowDown` and `ArrowUp` move the choice, wrapping at both ends (the prototype); `Enter` and `Tab` insert the chosen row; `Escape` closes only the list (the function also calls `stopPropagation`, so that no panel or dialog behind it closes on the same key, as the prototype's order of Esc puts the list before them). While the list is closed it consumes nothing, so Enter sends as TOKI-043 R2 says; while it is open Enter never sends, and a key of an input-method composition never reaches it (TOKI-043 R16). The first row is chosen when the list opens, and the choice stays on the same row (clamped to the list) while the person keeps typing. A press on a row inserts it; the press keeps the focus in the field. An insert replaces the text from the `@` to the caret with `@` plus the display name of the person plus one space, through `replaceRange(start, caretEnd, text, caret)` with the caret after the space (the prototype inserts `@First ` with a space; Toki has one display name, not a first name (FR-06), so the whole name is inserted, which also is what R2 reads); for `@channel` it inserts `@channel ` (the word does not depend on the language of the screen). The change reaches `onChange` with source `"tool"` and the draft and the counter follow it (TOKI-043 R16). Check: a component test with the real `Composer`: ArrowDown wraps, Enter inserts "@Lan Nguyễn " and sends nothing, Tab inserts, Escape closes the list and a `keydown` listener on `document` does not see that Escape, a click inserts, the caret is after the space; with the list closed Enter sends; during a composition nothing is consumed; `onChange` gets `"tool"`.
- R15. The button. `composerTools.mention` of TOKI-043 R17 (`apps/web/src/conversation/composer-tools.ts`) is `MentionTool`, which returns one `IconButton` (size `sm`) with the icon `at` and the accessible name `t("mentions.tool.label")` ("Mention someone", the prototype's `aria-label`). A press puts an `@` at the caret, with one space before it when the character before the caret exists and is not white space (the prototype checks the end of the value; the caret is the place of the insert, so the caret is checked), through `replaceRange`, opens the list and keeps the focus in the field; it is `disabled` as the composer is. Check: a test presses it on an empty field (value "@", list open), after "hi" (value "hi @"), after "hi " (value "hi @"), with the caret between the two letters of "ab" (value "a @b"), and with `disabled` (nothing); `composerTools` lists the six ids in the order of TOKI-043 R17 and the test that lists it is updated for this entry.
- R16. The look and the roles. `MentionPopup` is a component of `packages/ui-web/src/components/MentionPopup/` (`MentionPopup.tsx`, `MentionPopup.css`, `MentionPopup.test.tsx`, `MentionPopup.examples.tsx`, `index.ts`, one line in `components/index.ts` and one entry in `componentExamples`, TOKI-012 R31). Props: `items: { key: string; label: string; leading: ReactNode; trailing?: ReactNode }[]`, `activeIndex`, `onPick(index)`, `label` (the accessible name) and `className`; it holds no text of its own and imports no other package. It renders `div.mpop` with `role="listbox"`, `aria-label` the label, and one `button.mrow-pick` for each item with `role="option"` and `aria-selected` (true for the active one), holding `leading` (an `Avatar` of size 24 for a person, the icon `at` in a tile of the same size for `@channel`), `span` with the label, and `trailing` (empty here: TOKI-055 and TOKI-056 put the presence dot and the status there, F12). It is the first child of the box, placed by the `popup` slot (TOKI-043 R17, the prototype's `.mslot`). The CSS is Table A. The field keeps the focus: the popup has no tab stop of its own. Check: a render test with three items finds the roles, the one `aria-selected`, no text outside the props (empty labels give an empty `textContent` but for the leading nodes), and no colour literal in the CSS; the browser test at 1280 and 360 px finds the popup above the field with its left edge at 34 px and at 12 px (the container narrower than 720 px) and inside the viewport.
- R17. `@channel` asks first. When the text to send holds an `@channel` that counts (R2 (f), with `channel` true for a channel that is not archived, TOKI-027 R6) and the channel has `CHANNEL_MENTION_CONFIRM_FROM` (20) or more members (D-041, AC-044: 19 sends at once, 20 asks), the composer opens `ConfirmAction` of TOKI-093 with the id `notifyChannel` (Table A of that spec: "names the number") before it sends. The member count is `getMemberCount(id)` of TOKI-035 R13, the count the header shows. Cancel, Esc and an outside press send nothing, notify nobody and leave the text in the field (TS-068); the confirm button sends once. `useComposerController` of TOKI-043 R18 gains one optional field, `beforeSend(prepared): boolean | Promise<boolean>`, called after the checks of its R2 and R6 and before `send`; `false` does nothing (the text stays) and `true` goes on; while a promise is pending, another press of Send or Enter does nothing, so one dialog is open at most. The composer's `send` stays synchronous, as TOKI-043 R6 has it. The question is asked once, at the press: a message that waits offline or is retried is not asked again, and the server does not ask (the rule is the screen's, as the permission functions say, TOKI-027 "Limits that are not permissions"). The rule that finds a mention is one pure function in `packages/shared`, used by the server to decide who is mentioned and by the client to draw the chip, to ask for the confirmation and to find the people outside the conversation, so the three can never disagree about what a text says. The server alone decides who is stored; the client never sends who it thinks it mentioned.

### How a mention is written and stored (Decided in this spec)
- The text carries the name as the person sees it: `@Lan Nguyễn`. No id, no markup and no new key in the body of a send or an edit: the server reads the names in the text and finds the people among the members of the conversation (R5). Reasons: the body of the send of TOKI-037 R4 is strict (`id` and `text`, and TOKI-045 adds two keys); the edit of TOKI-047 R11 hands `previousText` to the later work so that a mention can be compared; a person who types a full name by hand is mentioned like one who picked it, which is what D-135 describes ("a name typed for someone outside the conversation"); a text that holds an `@` and a name is read the same everywhere. The cost is that two people with the same name cannot be told apart (concern 2) and that a first name typed alone names nobody (concern 1).
- What is stored is who, not where: the people and a flag for `@channel` (R4). The place in the text is found again when it is drawn (R19), from the people the message names, so an edit needs no offsets and a rename costs only the chip.
- `@channel` is a flag, not a list of people: who is a member now is read when the notification is made (TOKI-065, TOKI-073), so a person who joined after the message is not told for an old message and nothing here grows with the size of a channel.
- The confirmation is the screen's: the server stores `@channel` for any member of a channel (TOKI-027 R6) and never asks.

### What the prototype does, and where this work follows or differs
- Follows: the list opens on an `@` that follows the start of the text or white space; a row is an avatar of 24 px and the name; ArrowDown and ArrowUp wrap, Enter and Tab insert, Esc closes before anything else; the insert leaves the name and a space, with the caret after it; the list hides when nothing matches; the chip and the tint (Table A); the mention button with the icon `at` and the label "Mention someone".
- Differs, with the reason: the prototype matches the start of a first name and inserts the first name because its data has one; Toki has one display name (FR-06), so it matches the start of the name or of any word of it and inserts the whole name (R13, R14). The prototype's list shows no `@channel` row and its tint is found by a regex on the first name; the product has `@channel` (D-017) and the tint follows stored ids (R19). The prototype lists every person but the signed-in one, members or not; the product lists members only (D-058, R12). The prototype tints on a text match, in any message, in any conversation; the product tints only messages that the server stored a mention for.

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder.
- The text carries the name and the server reads it; no id and no new key in a request (above).
- A table `message_mentions` of its own, with a flag row for `@channel`, and no column on `messages` (R4).
- The rule that finds a mention is one shared function, with the character rules and the folding of R2 (a `@` is opened after the start, white space or a text mark; the boundary after a name; the longest name wins).
- The self-mention, the deactivated person and the person outside the conversation are never stored (R5), a mention never fails a request (R5), and `@channel` is plain text in a direct message or a group (TOKI-027 R6).
- The writer is one function called by the send, the reply and the edit, and the entry reads the mentions through the builder (R6 to R8).
- The confirmation is the screen's and the server never asks (R17); `beforeSend` is added to the controller of TOKI-043.
- The list matches the start of the display name or of any word of it, inserts the whole name, and puts `@channel` first (R13, R14).

## Data safety
- Only a member of the conversation can be mentioned, and the server decides: a client cannot name a person outside the conversation, a deactivated person or a name that is not in the text (R5). A mention never reveals who exists: a name that is not a member is plain text and the answer is the same as for any other text, and the offer to add a person is built on the client from the people list that every member already has.
- The list of members of a channel is read through the member route, which refuses a non-member of a private channel with the same body as for an unknown channel (TOKI-029), so the list never opens a private channel to an outsider.
- The text is stored as sent and drawn as text (R23); no name becomes markup.
- No log line holds a text, a name or a list of ids (R23). Tests use made-up names.

## Open questions from the intent
- How is a mention written in the text, and how does the server know whom it names? Answered in part: the log gives the visible form (`@` and a name, the prototype); this spec decides that the server reads the full display name in the text (R2, Design). Whether a name typed in part, such as a first name, counts is not answered: concern 1; two people with one name: concern 2.
- Which people does the list show, and are there `@here` and `@everyone`? Answered: the members of the conversation, without the deactivated, plus `@channel` (D-058, F12, F41); no `@here` and no `@everyone` in phase 1 (D-017). The row details the log leaves open (order, the number of rows, the look of the `@channel` row) are concern 5.
- Who may use `@channel`, and what does the confirmation say? Answered in part: any member of a channel, and from 20 members a confirmation that names the number (D-041, AC-044, Table A of TOKI-093); the number it names and its wording are not answered: concern 4. Whether an edit that adds `@channel` asks is not answered: concern 3.
- What happens to a name typed for someone outside the conversation? Answered in part: nobody is notified and the sender is offered "Add them" (D-135, D-058). Where, when and in which words the offer is made, and what the added person gets for the old message, are not answered: concern 3.
- What does a deactivated person do to a mention? Answered: a deactivated person is not suggested and not stored (F41, R5); the name of one that was mentioned before keeps its tint (R19).
- What does an edit do to the mentions of a message? Answered: the set is recomputed; the newly named are told, the removed lose their item (F16, F13, R7, R9). A mention list inside the edit field: not answered, concern 5.
- Which ticket draws the chip and the tint? Answered in this spec: the chip (the element `Mention` and its stage of the text pipeline) and the functions are this work's; the row, the class and the tint's CSS are TOKI-042's, and the stage that runs before the chip is TOKI-049's (R19, Hand-offs).

## Areas of concern
1. A name typed by hand that is not the full display name. Not decided. The log says a typed name for someone outside the conversation notifies nobody (D-135) and the prototype tints any `@First` it finds, but Toki has one display name of 1 to 80 characters, not a first name, and the log does not say whether `@Lan` typed alone names "Lan Nguyễn". Proposal, not a decision: only the full display name names a person (R2), the list is the way to get it, and a part of a name is plain text; the other way is to let a first word name a person when only one member has it, which is one more rule in `findMentions`. R1, R2 and the check of R1 read as this proposal until it is answered. Owner: Thanh Truong (product owner).
2. Two members with the same display name. Not decided. A display name need not be unique (it starts as the part of the address before the `@` and can be changed). Proposal, not a decision: when two members share the longest matching name, nobody is named and nobody is notified (R2 (e)), and the list shows both rows with the same name; the other way is to show something that tells them apart (the job title) and to store the choice, which needs an id in the text. Owner: Thanh Truong (product owner).
3. The offer "Add them" and the confirmation of an edit. Not decided. D-135 and F12 give the offer and its two words, and say nothing of where it appears, when, what it names, or what the added person gets for the message that named them. The same journey gives no rule for an edit that adds `@channel` in a big channel. Proposal, not a decision: one toast with the button after the send, naming the people, 5 seconds (R18); the person added gets no notification for that message and no mention is stored for them; an edit that adds `@channel` asks the same question, through `needsChannelConfirm` (R17). Other ways: the offer in the composer before the send, or a line under the sent message; no question on an edit. Owner: Thanh Truong (product owner).
4. What the confirmation names. Not decided. The journey says "Notify 34 people?" and D-041 says "a channel of 20 or more people"; the log does not say whether the number is the member count, the member count without the sender (who gets no notification, D-071), or without deactivated people, and whether the threshold counts the same people. The tests TS-067 and TS-068 fix only that 19 sends at once and 20 asks. Proposal, not a decision: the threshold and the number are the member count the header shows (R17); the dialog's words are Table B. Owner: Thanh Truong (product owner).
5. The details of the list. Not decided. The log gives its content (members, `@channel`, avatar, name, presence dot and status in F12) and its keys, not the order of `@channel`, the number of rows, the look of the `@channel` row, or whether the edit field has the list. D-109 gives "first 50, more on scroll" for member lists and people pickers. Proposal, not a decision: `@channel` first, the first 50 matches and more on scroll with a maximum height set when it is built, a tile with the icon `at` as the `@channel` avatar and the hint of Table B, and no list in the edit field of TOKI-047 in this ticket. R13 and R16 show every match and the tile until it is answered. Owner: Thanh Truong (product owner).
6. A mention inside a code mark, a bold mark or a link. Not decided. The prototype tints a name in any place of the text, a code mark included, but the log does not say whether a name inside code, inside a mark or inside the address of a link is a mention, and the spec of TOKI-042 (R15) has the chip stage skip the elements that formatting makes. Proposal, not a decision: the server and the chip agree on one rule; the simplest is that a name inside a code mark is plain text for both (the server would need the grammar of TOKI-049 to skip it), and that a name inside a bold or italic mark is a mention for both (the stage reads inside those elements). R2 (g) and R19 read as the first proposal's opposite (the server reads the plain string, the chip skips elements) until it is answered, so a name in code is stored and tinted but has no chip. Owner: Thanh Truong (product owner).
7. How a screen reader is told that the list is open. Not decided. The log has no accessibility rule for the list beyond the keys. Proposal, not a decision: the popup has the roles `listbox` and `option` (R16) and the field gets the combobox attributes through the change request to TOKI-043; until that is built the popup is usable by keyboard and not announced. Owner: Thanh Truong (product owner).
