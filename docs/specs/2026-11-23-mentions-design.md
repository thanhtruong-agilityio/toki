## Goal
A person writes `@` and a name to call someone, and today nothing happens: no list of people, no record of who was named, no tint on the message of the person who was named. This work builds mentions end to end: the list that opens in the composer, the rule that finds the names in a text, the table that keeps who was mentioned in which message, the confirmation for `@channel` in a big channel, the offer to add a person who is not in the conversation, the effect of an edit, and the key `mentions` that every copy of a message carries so that the tint, the chip, the `@` dot and the Activity items can be built from it. It creates no Activity item, no toast, no push and no unread flag: those read what this work stores (Hand-offs).

## Requirements
The rule in the text
- R1. `packages/shared/src/mentions/find.ts` exports `findMentions(text, people, options)`, a pure function with no DOM global, where `people` is `{ id: string; displayName: string }[]` and `options` is `{ channel: boolean }`. It returns the spans it finds in the order they appear: `{ start: number; end: number; kind: "user" | "channel"; userId: string | null }`, `start` and `end` being offsets in the code units of the text it was given (`end` is exclusive), `start` at the `@`. Spans never overlap. The rule of R2 follows the proposal of concerns 1 and 2 until the owner answers them. A name is compared after the folding of R2: the text and the name are folded one code point at a time, so a letter with its mark compares equal to the letter without it, and the offsets still point into the original text. A span for a person covers `@` and the display name as the text has it; the combining marks (U+0300 to U+036F) that follow the last letter belong to the name. `findMentions` never throws for any string, including a lone surrogate, an `@` at the end and an empty list. Check: a table test: "hi @Lan Nguyễn," with a person "Lan Nguyễn" gives one span from 3 to 14, and the same with "@lan nguyen" and with the name typed in decomposed form (the letters followed by combining marks) gives the same person and the span of the text as written; "@Lan" with only a person "Lan Nguyễn" gives none (concern 1); "" and "@" and "a@" give none; a lone surrogate after `@` gives none and does not throw; two mentions of the same person give two spans (R5 keeps one person once).
- R2. Which `@` counts, and which person it names. (a) An `@` opens a mention only at the start of the text, after white space, or after one of `*`, `_`, a backtick, `(`, `[`, `{`, `"` or `'` (so `*@Lan*` after a bold mark is a mention and `a.b@lan` is not). The marks `*`, `_` and the backtick are the three marks of TOKI-049 (its R2, R4 and R5, from the prototype's `rich()`); this list is a superset of them, as TOKI-049 R12 says, so it needs no change. (b) The folding is: Unicode form NFD, the combining marks U+0300 to U+036F removed, `đ` and `Đ` turned into `d`, lower case: the rule of `foldSearchText` of TOKI-032 R19; `packages/shared/src/text/fold.ts` exports it as `foldText`, and `foldSearchText` of `client-core` becomes a re-export of it (the server needs the same rule and may not import `client-core`; same name, same behaviour, its tests stay valid). (c) Proposal of concern 1: a name matches only when the folded text after the `@` starts with the whole folded display name (trimmed) and the character after it in the original text is not a letter or a digit (`\p{L}`, `\p{N}`) or is the end of the text. (d) The longest matching name wins ("Lan Nguyễn" over "Lan"). (e) Proposal of concern 2: when two people with different ids have the same folded name and it is the longest match, none of them is named. (f) `@channel` is the word `channel`, compared folded and with the boundary of (c); it counts only when `options.channel` is true, and it wins over a person whose name is "channel". `@here`, `@everyone` and every other word is plain text (D-017). (g) The text is read as a plain string: a mention inside a code mark counts like any other (concern 6). TOKI-049 exports `parseMarks` and `findLinks` from `packages/shared` with the ranges of code and links (its R12 (d)), so the server could skip them if the owner decides so; this spec does not use them. Check: each letter of (a) as a preceding character and an email address; the boundary of (c) with "@Lan.", "@Lan," and "@Lanx"; (d) with the two names; (e) with two people "An" and "An" (none named) and with "An" and "Án" (folded alike, none named); (f) with `options.channel` true and false, upper case "@CHANNEL", "@channels" (no span) and a person named "channel"; "@here" and "@everyone" give none.
- R3. `packages/shared/src/mentions/` also exports `MessageMentionsSchema`, a strict object `{ userIds: string[], channel: boolean }` with its type `MessageMentions` (the ids are distinct and in ascending order), the constant `EMPTY_MENTIONS`, `MentionDeltaSchema` and its type `MentionDelta` (`{ mentions: MessageMentions, added: string[], removed: string[], channelAdded: boolean, channelRemoved: boolean }`) and `CHANNEL_MENTION_CONFIRM_FROM`, 20 (D-041, FR-17). `MessageEntry` of TOKI-037 R15 gains the key `mentions` (a `MessageMentions`, as that spec allows later work to add keys), always present, `EMPTY_MENTIONS` for a system line, a deleted message and a message that names nobody. Check: schema tests accept the empty value and one with two ids and refuse an added key, a missing key, a repeated id, ids out of order and a non-boolean `channel`; every entry the other tests parse carries the key (their fixtures are updated in this change); a type test imports each name from `@toki/shared`.

The server
- R4. The table `message_mentions`, in `apps/server/src/modules/mentions/schema.ts` (a table of its own: this work adds no column to `messages`, TOKI-036 concern 7), with one migration made by `pnpm db:generate --name message_mentions` (TOKI-019 convention 8; the whole `apps/server/migrations/` change is committed). It follows the conventions of TOKI-019 and the shape of `message_reactions` (TOKI-046 R1, R2). Exactly these columns: `id` (`uuid`, not null, UUIDv7 by the default of the column, primary key `message_mentions_pkey`), `workspace_id` (`uuid`, not null), `conversation_id` (`uuid`, not null), `message_id` (`uuid`, not null), `user_id` (`uuid`, null), `is_channel` (`boolean`, not null, default false) and `created_at` (`timestamptz`, not null, written by the server from the clock of TOKI-008, no database default, convention 3). The check `message_mentions_target_check` says `(user_id is null) = is_channel`: a row names one person or is the `@channel` row, never both and never neither. Two unique indexes, both named: `message_mentions_message_id_user_id_key` on (`message_id`, `user_id`) where `user_id is not null`, and `message_mentions_message_id_channel_key` on (`message_id`) where `is_channel`, so a message names a person once and `@channel` once. The index `message_mentions_user_id_idx` on (`user_id`, `message_id`) where `user_id is not null` serves the question "which messages mention this person". Every foreign key is `ON DELETE RESTRICT` (convention 6) and is written as SQL in the migration, because a schema file may not import another module's table (TOKI-019 R22): (`message_id`, `conversation_id`) references (`id`, `conversation_id`) of `messages` through `messages_id_conversation_id_key` of TOKI-036 (`message_mentions_message_id_fkey`), so a row carries the conversation of its message; (`conversation_id`, `workspace_id`) references (`id`, `workspace_id`) of `conversations` through `conversations_id_workspace_id_key` (`message_mentions_conversation_id_fkey`); `workspace_id` references `workspaces.id` (`message_mentions_workspace_id_fkey`); `user_id` references `users.id` (`message_mentions_user_id_fkey`). A trigger refuses every update of a row (`message_mentions_no_update_trg`): a row is inserted or deleted, never changed. A delete of a message never removes a row (R11); a row is deleted only by an edit (R7). Check: an exact-columns test reads names, types, nullability and defaults from the catalog (the seven columns, no other) and counts zero rows; `pg_constraint` and `pg_indexes` list the primary key, the check, the two unique indexes, the user index and the four foreign keys by those names, with `ON DELETE RESTRICT` on the four; an insert with an unknown message, a conversation that is not the message's, a workspace that is not the conversation's and an unknown user is refused, each error naming its key; a row with both columns set, one with neither, a second row for the same person and a second `@channel` row each fail with the name of the constraint or index; an update of any column fails and names the trigger; a delete succeeds; a delete of the user, message or conversation row is refused while a row points to it; one SQL file is new in the migration folder.
- R5. Who can be mentioned, and what is stored. `resolveMentions(tx, input)` in `apps/server/src/modules/mentions/resolve.ts` takes the conversation (`id` and the facts of TOKI-028), the actor and the text, and returns a `MessageMentions`. The candidates are the people with a member row in that conversation whose status is `active`, without the author: a person outside the conversation, a person who left, a deactivated person and the author (AC-037) are never stored ("a deactivated person is not suggested" is F41; "not stored" is this spec's rule), and the text that names them stays plain text (D-058, D-135). `channel` is true when the text holds `@channel` (R2 (f)) and `canUseAtChannel(actor, conv)` of TOKI-027 R6 allows (a member of a channel that is not archived): in a direct message or a group `@channel` is plain text and no error. A person named twice is stored once (AC-036: one mention, one item). A text that holds no `@` makes no read at all. A mention never makes a send or an edit fail: no name, however wrong, gives a 400, a 403 or a 404. The members are read with `listMemberIds` of `conversations` and the new `getPeopleByIds(db, ids)` of `members` (`{ id, displayName, status }[]`, one statement), both through their `index.ts`; no lock is taken by this work, because the send already holds the conversation row `FOR SHARE` and a person who is deactivated at the same moment is at worst mentioned once more. The insert of R6 takes `FOR KEY SHARE` on the message row and on each `users` row through the foreign keys; that mode does not conflict with `FOR NO KEY UPDATE` of TOKI-037 R8 and TOKI-047 R9 nor with the `FOR SHARE` of a deactivation check, so the lock order of those specs is unchanged. Check: with a fixture of a channel with five members, one deactivated, one who left, and a person outside it: a text naming each of the six gives the active members only; a self-mention gives none; "@Lan @Lan" gives one id; `@channel` in a public channel, a private channel, a direct message and a group gives `true`, `true`, `false`, `false`; a text with no `@` is a statement log with no read of members; an unknown name returns `EMPTY_MENTIONS` and the route answers 201; with two connections, a deactivation of a mentioned person at the same time as the send neither blocks nor deadlocks it.
- R6. A new message keeps its mentions. `saveMentions(tx, input)` of `modules/mentions/write.ts` (`input`: the conversation facts, the actor, the id of the message and its text) calls `resolveMentions`, inserts the rows (with `workspace_id`, `conversation_id` of the message and `created_at` from the clock) with `ON CONFLICT DO NOTHING` in one statement and returns a `MentionDelta` with `added` all the people, `removed` empty and `channelAdded` the flag. Who calls it: the send handler of the `messages` module calls the writer that `app.ts` injects into `messageRoutes` as the option `saveMentions`, the pattern of the reactions reader (TOKI-046) and the pin reader (TOKI-048); `messages` imports nothing of `mentions`. The call is inside the transaction of the send, for a stored message only, after the insert of the message and before the entry is built and before any call of `recordChange`; the reply of TOKI-045 is the same route and gets the same call, after the insert of the reply and before the statement that updates the row of its root (TOKI-045 R4; the order of TOKI-045 and TOKI-047 is one order). A repeat (TOKI-037 R5) and every refusal call it zero times, so a repeat stores no second set. The default of the option does nothing and returns an empty delta, so the tests of TOKI-037 and TOKI-045 that pass none stay valid. The merged TOKI-037 says in R24 that the send "writes only rows of `messages`": the change request in Plan changes amends it, and this ticket's pull request adds the call to the route and to that test. Check: a send of "hi @Mai" in a channel with Mai leaves one row `(message, Mai)` and an entry whose `mentions.userIds` is `[Mai]`; the same send twice leaves one row and the second answer (200) carries the same `mentions`; a refused send (archived channel, non-member) leaves no row; a rollback after the call leaves no row; a reply with a mention leaves the row for the reply's id, and its statement log shows the call after the insert of the reply and before the update of the root; a statement log shows the insert after the message insert and before the `recordChange` call, and no statement for a text with no `@`; the row-count test of TOKI-037 R24 passes with the default writer and counts one `message_mentions` row with the real one.
- R7. An edit recomputes. The edit handler of the `messages` module (TOKI-047) calls the same injected `saveMentions` with `isEdit: true`, inside its transaction, after the message row is locked and updated, before the root row of a thread is touched, and before it builds the entry and calls `recordChange`, for an edit that changed the text. The writer reads the rows the message has, computes the new set from the new text (R5), deletes the rows whose person is no longer named, inserts the new ones, and returns a `MentionDelta`: `mentions` the new set, `added` the people named now and not before, `removed` the people named before and not now, `channelAdded` and `channelRemoved` likewise. A person who already has a row and is still named in the new text keeps the row, even when they have since left or been deactivated (the candidates for the new text are the active members and the people of the old rows), so `removed` lists only people whose name was edited out and TOKI-065 takes away only their item. A person named before and after is in neither list, so an edit never tells again a person who was told (F16: only the newly mentioned person is notified). A text with no `@` and a message with no rows makes no statement beyond the read of the rows. An edit that changes nothing (TOKI-047 R3) does not call it. `previousText` is not needed by this work: the rows say what was mentioned before. Check: "hi @Mai" edited to "hi @Mai and @Sam" gives `added` `[Sam]`, `removed` empty, rows Mai and Sam; edited to "hi" gives `removed` `[Mai, Sam]`; edited to "hello @Mai" gives both lists empty; `@channel` added and removed gives `channelAdded` then `channelRemoved` and the `is_channel` row follows; a person who was deactivated after the first text and is still named in the new text keeps the row and is in neither list; the same person named out of the text is in `removed`; a person who left after the first text and a new person added by the edit are both handled in one edit; a rollback leaves the old rows.
- R8. The entry carries the mentions. `listMentionsOfMessages(client, messageIds): Promise<Map<string, MessageMentions>>` is exported from `modules/mentions/index.ts`: one statement, `where message_id = any($1)`, grouped in code, ids in ascending order, `channel` from the `is_channel` row, a message with none has no key in the map. The `messages` module imports nothing of `mentions`: `app.ts` passes the function as a third key `listMentions` in `readers` of `buildMessageEntry(db, row, readers?)` and `buildMessageEntries(db, rows, readers?)`, the one builder that every entry goes through. The builder is TOKI-037's (TOKI-045 asks it there and TOKI-046 and TOKI-048 add their readers to it; the merged 037 does not hold it yet, Plan changes); this work adds `listMentions` to `readers`, which becomes `{ listReactions?, listPinned?, listMentions? }`. The builder calls it once for the ids of the messages of `kind` `user` that are not deleted and sets `mentions` from the map, `EMPTY_MENTIONS` when absent, for a system line, for a deleted message and when the reader is not given. Every place that returns or sends an entry goes through the builder, so the history, the replies, the send answer, the answer and the event of an edit, and every event carry `mentions`; the `message.created` and `message.edited` events of TOKI-038 and TOKI-047 carry the new set with no change to the event code. The schema of an entry read from an event or a page written before this change gives `mentions` the default `EMPTY_MENTIONS` on read, never on write, so a reconnecting client that reads an old event in the retention window does not fail to parse it (the same holds for the keys of TOKI-045, 046 and 048, Plan changes). Check: a page of 20 messages calls the reader once (one more statement for a page, as TOKI-046 R10 counts for each reader; the sentence "one statement per page" of TOKI-037 R8 is amended with it); a deleted message and a system line (rows inserted by SQL) have `EMPTY_MENTIONS`; the entry of a send, the entry of an edit and the `message` of the recording handler's `change` equal the 200 body, `mentions` included; an event payload without the key parses with `EMPTY_MENTIONS`.
- R9. What the changes carry for Activity and notifications. `Change` of `conversations/changes.ts` gains the optional field `mentionDelta` (a `MentionDelta`, imported as a type from `@toki/shared`). The send sets it on `message_created` (R6), and the edit sets it on `message_edited` (R7). It is always set by these two routes, empty when nobody is named. TOKI-065 reads `change.mentionDelta` to create the items (`added`, `channelAdded`) and to remove them (`removed`, `channelRemoved`, F13), and `change.message.mentions` for the full set; TOKI-045 and TOKI-065 read `mentions.userIds` for the follow rule of threads; TOKI-073 reads the same to decide who is told. This work writes no event and calls `recordChange` no extra time. Check: with a recording handler, the send and the edit each leave one `message_created` or `message_edited` call whose `mentionDelta` equals the delta of R6 or R7; a repeat and a refusal leave none; a type test checks the optional field.
- R10. The module and its wiring. `apps/server/src/modules/mentions/` holds `schema.ts` (not exported), `resolve.ts`, `write.ts`, `read.ts` and `index.ts`, which exports `saveMentions`, `listMentionsOfMessages` and no table. `mentions` imports `conversations` (`listMemberIds`, the facts types) and `members` (`getPeopleByIds`) through their `index.ts` and imports `messages` nothing; `messages` imports `mentions` nothing; neither `conversations` nor `members` imports `mentions` (the lint rule `toki/module-entry` checks the paths). `apps/server/src/app.ts` gives `saveMentions` to `messageRoutes` and to the edit routes and `listMentionsOfMessages` to the builder, as it does for reactions. - R11. A delete keeps the rows. A deleted message's rows stay (TOKI-036: a message row is never removed and nothing here takes a row away on a delete); every read of mentions ignores a deleted message (R8: its entry says `EMPTY_MENTIONS`), and a later read that joins `messages` for an unread flag or a list filters `deleted_at is null` (Hand-offs). The Activity items of a deleted message are removed by TOKI-065 (F13). The list in the composer
- R12. The people the list offers. `useMentionCandidates(conversationId)` in `apps/web/src/conversation/mentions/` returns `{ candidates, status, ensureLoaded }`. `candidates` is the people with a member row in the conversation, as `{ id, displayName }`, in the order of the member list, without the signed-in person and without a person whose `status` is `deactivated` (F41; the display name and status come from the people of the bootstrap call). For a direct message or a group the member ids are the entry's `memberIds`. For a channel the ids come from the loop of `useChannelMembers(id)` of TOKI-035 R13 (`api.channels.members(id, { limit: 100, cursor })` page after page, `getPerson` for each id, a cap of 10 requests), not from a second loop: that loop moves to one function of `client-core` that the hook and this work both call, with the one cap (Plan changes), so the two lists cannot disagree. This work keeps the result once for each conversation in a module-level store, started by `ensureLoaded` (called when the first `@` is typed and by the offer of R18), invalidated for that conversation by the member events of the sync engine (`member.joined`, `member.left`, `member.removed`, `registerEventHandler` of TOKI-040 R18) and by the person's own add (R18); the panel's `reload` and the store read the same function. For a channel of more than 1,000 people `candidates` holds the 1,000 the cap reads and no more: a person beyond them is not offered, but a full name typed by hand still names them (the server reads the text, R5). While the read runs `status` is `loading` and the list shows only `@channel` where it applies; a failed read leaves `candidates` empty and `status` `failed`, with no message and no retry button (the next `@` starts a new read). Check: a hook test with a fake API: a channel of 230 members makes three requests (100, 100, 30) and one for the second `@` makes none; a channel of 1,200 stops after 10 requests and holds 1,000; the signed-in person and a deactivated person are not in `candidates`; a `member.removed` event for the channel makes the next `@` read again and one for another channel does not; the panel's list and `candidates` hold the same ids after a `member.joined`; a direct message reads no request; a failed page leaves `candidates` empty and does not throw.
- R13. The list: trigger, filter and order. `findTrigger(value, caret)` of `packages/client-core/src/mentions/trigger.ts` is pure: it looks at the text before the caret and returns `{ start, query }` when it ends with an `@` that follows the start of the text or white space and then at most characters that are neither white space nor `@` (the prototype's `(^|\s)@([A-Za-zÀ-ỹ]*)$`, widened from letters to any character but white space and `@`, because a display name starts as the part of the address before the `@`, such as `hoa.tran`, FR-06), and `null` otherwise. `rankCandidates(candidates, query, { channel })` returns the rows: the `@channel` row first when `channel` is true and `channel` matches the folded query as a prefix (or the query is empty), then the people whose folded display name, or whose folded display name from the start of any word of it, starts with the folded query ("nguyen" finds "Lan Nguyễn", the journey's "with or without diacritics"), in the order of the candidates. An empty result closes the list (the prototype hides it when nothing matches). The list shows every matching row; whether it stops at 50 and loads more on scroll is concern 5. The list opens when `findTrigger` gives a result after a change from the person (source `input` or `tool`) or after a caret move, and never for a restored draft (source `restore`, TOKI-043 R16), so a draft that ends with `@Mai` does not open a list on a page load. It closes when the trigger no longer holds, when the field loses focus or a press lands outside the list and the field (a `focusin` or `pointerdown` listener of the hook; the composer has no blur prop), and after an insert. The rule that finds a mention is one pure function in `packages/shared`, used by the server to decide who is mentioned and by the client to draw the chip, to ask for the confirmation and to find the people outside the conversation, so the three can never disagree about what a text says. The server alone decides who is stored; the client never sends who it thinks it mentioned.

### How a mention is written and stored (proposed here, concerns 1 and 2)
The first bullet is a proposal, not a decision: the build follows it until the product owner answers concerns 1 and 2. The rest of this section is a technical choice.
- Proposal: the text carries the name as the person sees it: `@Lan Nguyễn`. No id, no markup and no new key in the body of a send or an edit: the server reads the names in the text and finds the people among the members of the conversation (R5). Reasons: the body of the send of TOKI-037 R4 is strict (`id` and `text`, and TOKI-045 adds two keys); the edit of TOKI-047 R11 hands `previousText` to the later work so that a mention can be compared; a person who types a full name by hand is mentioned like one who picked it, which is what D-135 describes ("a name typed for someone outside the conversation"); a text that holds an `@` and a name is read the same everywhere. The cost is that two people with the same name cannot be told apart (concern 2) and that a first name typed alone names nobody (concern 1); a name-only text is the choice that rules out the other answer of concern 2, which needs an id in the text.
- What is stored is who, not where: the people and a flag for `@channel` (R4). The place in the text is found again when it is drawn (R19), from the people the message names, so an edit needs no offsets and a rename costs only the chip.
- `@channel` is a flag, not a list of people: who is a member now is read when the notification is made (TOKI-065, TOKI-073), so a person who joined after the message is not told for an old message and nothing here grows with the size of a channel.
- The confirmation is the screen's: the server stores `@channel` for any member of a channel (TOKI-027 R6) and never asks.

### What the prototype does, and where this work follows or differs
- Follows: the list opens on an `@` that follows the start of the text or white space; a row is an avatar of 24 px and the name; ArrowDown and ArrowUp wrap, Enter and Tab insert, Esc closes before anything else; the insert leaves the name and a space, with the caret after it; the list hides when nothing matches; the chip and the tint (Table A); the mention button with the icon `at` and the label "Mention someone".
- Differs, with the reason: the prototype matches the start of a first name and inserts the first name because its data has one; Toki has one display name (FR-06), so it matches the start of the name or of any word of it and inserts the whole name (R13, R14). The prototype's list shows no `@channel` row and its tint is found by a regex on the first name; the product has `@channel` (D-017) and the tint follows stored ids (R19). The prototype lists every person but the signed-in one, members or not; the product lists members only (D-058, R12). The prototype tints on a text match, in any message, in any conversation; the product tints only messages that the server stored a mention for.

### Decided in this spec
These are technical choices that the Blueprint leaves to the builder; none touches concerns 1 to 7.
- A table `message_mentions` of its own, with a flag row for `@channel`, and no column on `messages` (R4).
- The rule that finds a mention is one shared function (the folding, the boundary after a name, the longest name wins); what it counts as a name is the proposal below.
- The self-mention, the deactivated person and the person outside the conversation are never stored (R5), a mention never fails a request (R5), and `@channel` is plain text in a direct message or a group (TOKI-027 R6).
- The writer is one function that the `messages` module calls through an injected option for the send, the reply and the edit, and the entry reads the mentions through the one builder (R6 to R8).
- The confirmation is the screen's and the server never asks (R17); `beforeSend` is added to the controller of TOKI-043; a confirmation cannot be confirmed offline (R17).
- The list matches the start of the display name or of any word of it and puts `@channel` first (R13, R14).

### Proposed here, not decided (concerns 1 to 7)
The build follows these until the product owner answers; each is marked in its requirement.
- The text carries the full display name and the server reads it; a part of a name is plain text; two members with one name name nobody (R1, R2, R14; concerns 1 and 2).
- The insert puts the whole display name (R14; concern 1).
- The offer "Add them", its place, timing and words, and the confirmation of an edit (R17, R18; concern 3).
- The number the confirmation names (R17; concern 4).
- The details of the list (concern 5), the reading of a name inside a mark (R2 (g); concern 6) and the screen reader's announcement (concern 7).

## Data safety
- Only a member of the conversation can be mentioned, and the server decides: a client cannot name a person outside the conversation, a deactivated person or a name that is not in the text (R5). A mention never reveals who exists: a name that is not a member is plain text and the answer is the same as for any other text, and the offer to add a person is built on the client from the people list that every member already has.
- The list of members of a channel is read through the member route, which refuses a non-member of a private channel with the same body as for an unknown channel (TOKI-029), so the list never opens a private channel to an outsider.
- The text is stored as sent and drawn as text (R23); no name becomes markup.
- No log line holds a text, a name or a list of ids (R23). Tests use made-up names.

## Open questions from the intent

- Which people does the list show, and are there `@here` and `@everyone`? Whether an edit that adds `@channel` asks is not answered: concern 3. A person who is offline cannot confirm the question (R17).

## Areas of concern
1. A name typed by hand that is not the full display name. Not decided. The log says a typed name for someone outside the conversation notifies nobody (D-135) and the prototype tints any `@First` it finds, but Toki has one display name of 1 to 80 characters, not a first name, and the log does not say whether `@Lan` typed alone names "Lan Nguyễn". Evidence for the owner: the journeys, TS-055, TS-056, F12 and F13 all write `@Lan`, and the prototype finds a first name (`@First\b`), while the seed (TOKI-081) gives the member the display name "Lan Nguyễn"; under the full-name rule that text names nobody, so the acceptance steps and the seed use the full name (Plan changes). Proposal, not a decision: only the full display name names a person (R2), the list is the way to get it, and a part of a name is plain text; the other way is to let a first word name a person when only one member has it, which is one more rule in `findMentions`. R1, R2, R14 and the check of R1 follow this proposal until it is answered. Owner: Thanh Truong (product owner).
2. Two members with the same display name. Not decided. A display name need not be unique (it starts as the part of the address before the `@` and can be changed). Proposal, not a decision: when two members share the longest matching name, nobody is named and nobody is notified (R2 (e)), and the list shows both rows with the same name; the other way is to show something that tells them apart (the job title) and to store the choice, which needs an id in the text (so the name-only text of the Design section rules that answer out until the owner chooses). Owner: Thanh Truong (product owner).
3. The offer "Add them" and the confirmation of an edit. Not decided. D-135 and F12 give the offer and its two words, and say nothing of where it appears, when, what it names, or what the added person gets for the message that named them. The same journey gives no rule for an edit that adds `@channel` in a big channel. Proposal, not a decision: one toast with the button after the send, naming the people, 5 seconds (R18); the person added gets no notification for that message and no mention is stored for them; an edit that adds `@channel` asks the same question, through `needsChannelConfirm` (R17). Other ways: the offer in the composer before the send, or a line under the sent message; no question on an edit. Owner: Thanh Truong (product owner).
4. What the confirmation names. Not decided. The journey says "Notify 34 people?" and D-041 says "a channel of 20 or more people"; the log does not say whether the number is the member count, the member count without the sender (who gets no notification, D-071), or without deactivated people, and whether the threshold counts the same people. The tests TS-067 and TS-068 fix only that 19 sends at once and 20 asks. Proposal, not a decision: the threshold and the number are the member count the header shows (R17); the dialog's words are Table B. Owner: Thanh Truong (product owner).
5. The details of the list. Not decided. The log gives its content (members, `@channel`, avatar, name, presence dot and status in F12) and its keys, not the order of `@channel`, the number of rows, the look of the `@channel` row, or whether the edit field has the list. D-109 gives "first 50, more on scroll" for member lists and people pickers. Proposal, not a decision: `@channel` first, the first 50 matches and more on scroll with a maximum height set when it is built, a tile with the icon `at` as the `@channel` avatar and the hint of Table B, and no list in the edit field of TOKI-047 in this ticket. R13 and R16 show every match and the tile until it is answered. Owner: Thanh Truong (product owner).
6. A mention inside a code mark, a bold mark or a link. Not decided. The prototype tints a name in any place of the text, a code mark included, but the log does not say whether a name inside code, inside a mark or inside the address of a link is a mention, and the stages of TOKI-042 (R15) skip the elements that formatting makes. TOKI-049 (concern 3 there, R12) is the same question from its side and leaves the way open: code and links are never given to a function, and the strings inside its bold and italic marks go through `mapText` when one is passed. Proposal, not a decision: the server and the chip agree on one rule; a name in bold or italic being a mention for both needs only that `mapText` of R19 is passed to `createFormattingStage` (no change to R15 of TOKI-042), and a name in code being plain text for the server needs the ranges of `parseMarks` and `findLinks` of TOKI-049; the simplest is that a name inside a code mark is plain text for both (the server would need the grammar of TOKI-049 to skip it), and that a name inside a bold or italic mark is a mention for both (the stage reads inside those elements). R2 (g) and R19 read as the first proposal's opposite (the server reads the plain string, `mapText` is not passed, the chip stage skips elements) until it is answered, together with concern 3 of TOKI-049, so a name in code is stored and tinted but has no chip. Owner: Thanh Truong (product owner).
7. How a screen reader is told that the list is open. Not decided. The log has no accessibility rule for the list beyond the keys. Proposal, not a decision: the popup has the roles `listbox` and `option` (R16) and the field gets the combobox attributes through `fieldProps` of `Composer` (TOKI-043 R16, which has the seam) that `useMentions` fills while the list is open (R20); until the owner answers, this is the build and the exact announcement is not checked beyond the attributes. Owner: Thanh Truong (product owner).
