## Result notes
- 14 rows are Pass, 1 is Fail (T10) and 1 is Blocked (T12) at `b304159`. Each output line is compared with Expected and the script gave the same lines on a second run. The last evidence line shows the script left the repository, its worktree list and status as they were, no process alive, no PostgreSQL left and its temporary folder removed.
- T10 Fail (`T10 3 2 0`): three of the files that the pull request changed hold a connection string with a password; they are the test files `apps/server/src/db/client.test.ts`, `apps/server/src/db/migrate-cli.test.ts` and `apps/server/src/test/throwaway-db.test.ts`, one match in each. The values are made-up credentials used as fixtures (for example a database that nothing listens on), not real ones, and no value is quoted here or in the evidence; the literal text of R10 says `git grep` finds nothing in the files of the change, so the row fails. The other two parts of the row pass: `.env.example` has the `DATABASE_URL` and `TEST_DATABASE_URL` rows and neither has a value. The BA decides whether a made-up password in a test counts as the "connection value that holds a password" that R10 forbids, and whether to amend the spec or reopen the ticket.
- T12 Blocked: `dev:reset:db` on a development database that holds data wipes it, so only the QA runs it, at the Version, in a checkout with their own `.env`; the Steps column says what to paste (exit code, table present, row count, no value). Until it is pasted the row is not Pass and no criterion that depends on it can be accepted.
- T7: the stock Drizzle migrator applied the valid and the broken migration in one transaction on this PostgreSQL: the run rejected with the Postgres syntax error and `workspaces` did not exist afterwards (the assumption of concern 11 of the spec of TOKI-005 holds on 14.24).
- The PostgreSQL is 14.24, not the 17 of Compose; no row's answer depended on the version (the catalog queries and the `uuid`, `timestamp with time zone` and check constraint types are the same).
- The Version is the ticket as delivered. Compared with `main` on 2026-11-25 (not judged here): `apps/server/migrations/` holds 5 SQL files instead of 1 and 5 modules have a `schema.ts`, added by later tickets (for example the users and sessions tables by TOKI-019), so R3 ("one new SQL file") and R15 (the columns of `workspaces`) would read against a bigger schema; the README still states the forward-only rule.
- For the acceptance of I01 (the `done` line: `pnpm dev` runs, CI is green, lint blocks a package-boundary violation), rows T2, T4, T6 and T16 show the server and the migration command run at the Version. Nothing here judges a criterion.
