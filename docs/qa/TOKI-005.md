## Result notes
- After the first verifier round of TOKI-116 the checks of T1, T10 and T13 were strengthened: T1 also names the test file that reads `DATABASE_URL` and shows with a counting listener that building a client opens no connection while the first query does; T13 also shows that the loopback guard refuses with its own error within 500 ms, which is the evidence that no connection to the host was attempted; T10 prints, for each match, the file and the host and port (never the credentials). T1 and T13 have a changed Expected, so the QA approved them again in chat on 2026-11-25 and Claude reran every row twice with identical lines; the first run is kept in the evidence file under its own heading.
- T10 Fail (`T10 3 2 0`): three of the files that the pull request changed hold a connection string with a password: `apps/server/src/db/client.test.ts`, `apps/server/src/db/migrate-cli.test.ts` and `apps/server/src/test/throwaway-db.test.ts`, one match in each. In two the host is a loopback address with a port taken from a variable and in the third it is the reserved `db.example.com` (the evidence lists host and port only; no credential is quoted here or in the evidence, and what the credentials are is for the BA to read in those files). The literal text of R10 says `git grep` finds nothing in the files of the change, so the row fails. The other two parts of the row pass: `.env.example` has the `DATABASE_URL` and `TEST_DATABASE_URL` rows and neither has a value. The BA decides whether a password in a test fixture counts as the "connection value that holds a password" that R10 forbids, and whether to amend the spec or reopen the ticket.
- T12 Blocked: `dev:reset:db` on a development database that holds data wipes it, so only the QA runs it, at the Version, in a checkout with their own `.env`; the Steps column says what to paste (exit code, table present, row count, no value). Until it is pasted the row is not Pass and no criterion that depends on it can be accepted.
- T7: the run of the server's own `runMigrations` on a folder with the valid migration and a deliberately broken one rejected with a Postgres syntax error and `workspaces` did not exist afterwards. That is what a single transaction would give; the transaction itself was not observed.
- Every row ran on PostgreSQL 14.24 only, none on the 17 of Compose, so the record does not say whether any answer depends on the version.
- The Version is the ticket as delivered. The evidence file lists four read-only commands run against `main` on 2026-11-25 (not judged here): 5 SQL files in `apps/server/migrations/`, 5 `schema.ts` files under `modules/`, the second migration added by the commit whose subject names TOKI-019, and 2 matches of `forward-only` in the README. R3, R15 and the table of R8 would read against a bigger schema.
