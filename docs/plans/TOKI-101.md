# TOKI-101 Archive and restore a channel - implementation plan

**Goal:** an Admin who is a member archives a channel from the Details panel (with a confirmation that names the channel and its member count); a member who opens an archived channel sees its header with an "Archived" label, a place for the history, and the notice "This channel has been archived" where the composer would be; an Admin restores an archived channel from Browse channels (with a confirmation). Nothing deletes a channel.

**Spec:** `docs/specs/2026-11-17-archive-restore-channel-design.md` (R1 to R22, all concerns decided; PR 189). Tier L. Ticket: issue 124. Branch `feat/toki-101-archive-restore-channel`. TOKI-029, 032, 033, 034, 035 and 093 are merged.

## Design

The design is the merged spec, sections "Design" (flows, Table T, Table A, Layout, Hand-offs). It is not repeated here. What the code on `main` changes, found while exploring:

1. **Two of the spec's additions already exist.** `BrowseRow` already takes `extra?: ReactNode` (line 69 draws it after the action button) and `BrowseChannelsDialog` already takes `rowExtra?: (channel, reset) => ReactNode` (passes `extra={rowExtra?.(channel, reset)}`). Nothing is added to those two files. `ConversationStarters.tsx` gets the one line `rowExtra={...}` its header comment promises (R18, R20). Their existing tests keep passing.
2. **The row count.** `actionPatterns` holds 19 rows today (R5 says it "then holds 19", written before TOKI-035 added its row). With `restoreChannel` it holds 20. `apps/web/tests/patterns/actions.test.ts` changes in the same step: the `tableA` tuple, the title and `toHaveLength(20)`. The `archiveChannel` row (`confirm`, owner TOKI-101) is used as it is.
3. **`canArchiveChannel` does not read `archived`**; `canOfferArchive` checks `archived === false` itself (R6). `canRestoreChannel` needs no `isMember` (R7).
4. **No `deps.ts` in `conversation/`.** It imports `../client` directly. `tests/conversation/boundary.test.ts` has an import whitelist (`ALLOWED_RELATIVE`); `DetailsPanel` importing `../channel-archive` needs one entry added there. `channel-archive/deps.ts` follows `features/deps.ts` (it is the only file of the folder that imports `../client` or `@toki/client-core`), with its own fake in `tests/channel-archive/fakeDeps.ts` and its own source-scan tests (copy of `tests/features/deps.test.ts` and `sources.test.ts`).
5. **`DetailsPanel` today.** Order: About, People, then (only when `entry !== undefined`) Notifications and Settings, then Leave (lines 50-74). `ArchiveSection` goes after the `entry !== undefined` block and before `LeaveSection`. It reads `entry` for `isPrivate`/`isGeneral` and the held detail for `archived`, so for an archived channel (no entry) it renders nothing. The archived page does not open the panel (concern 4), so this never comes up.
6. **The route today** (`routes/conversation.tsx`): `held` -> `ConversationPage`; `wasSeen` -> null; `notFound || memberChecked.has(id)` -> `NotFoundView`; else `UnjoinedView`. Case (c) effect runs when `ready && !held && wasSeen`. R13 adds, before all of these, a branch `ready && !held && isArchivedMember(getChannelDetail(id))` that draws `ArchivedChannelPage` with `<ArchivedHistory channelId={id} />`, and adds `!isArchivedMember(detail)` to the case (c) effect. The route selects `getChannelDetail(id)` through `useConversationSelector` so it redraws when `readChannel` puts the detail in the store.
7. **Error kinds.** `classifyApiError` (`packages/client-core/src/api/classify.ts:45-46`) gives `no_access` for 403/404 and `fresh_copy` for 409 and 410; `ignore` (aborted), `unauthenticated` (401 with a session code); every other answer is "other" (`retry`, `unreadable`, `field`, `wait`, `unknown`). The flows branch on `classifyApiError` from `./deps`; they do not copy `LeaveSection`'s `status === 409` (it would miss 410).
7a. **`readChannelOnce` already exists** in `conversation/useConversation.ts:24-36` (Map of promises; the header and panel use it). `channel-archive/deps.ts` re-exports it, so the page, the header and the panel share one read (R16's mechanism, no second Map). Its Map is module state: tests use a unique id each, or reset it.
7b. **`notFound`.** R2 and R16 say `throw notFound()`; the code's pattern is state plus `<NotFoundView />` and a quiet `refresh()` (`ConversationPage.tsx:25-30,46`). The new code follows the code; the PR records the deviation.
7c. **After a successful archive the panel is still mounted** for one render: `DetailsPanel.tsx:36-39` draws a panel for an archived channel with no entry, and the shell slot clears when `ConversationPage` unmounts. `ArchiveSection` calls every hook before it returns `null` and must not throw in that render; its dialog unmounts with nowhere to return focus, so R21's focus check applies to Cancel, Esc and the failure paths only.
7d. **The count (R9).** `readChannel` skips its store write when the id changed during the read (`store.ts:395-399`), so the flow uses the returned `channel.memberCount` and falls back to `getMemberCount` only when the read fails (as `LeaveSection.tsx:109` does). "Failed read and no held count" cannot happen through the component (a held detail has `memberCount`), so that branch is tested on `archiveFlow` directly.
7e. **A gap in R13 (ii), found in review.** `app-layout.tsx:103` puts every id the store held into `seen`. A member who had the channel in their list this session, and then presses "Open" in Browse after an Admin archived it, has `wasSeen` true, no detail, and `UnjoinedView` never mounts: nothing reads, and case (c) sends them to #general until a reload. Decided here (technical, inside the files this ticket already touches): for an archived row, `ConversationStarters`' open awaits `conversations.readChannel(id)` and then navigates. Test: id in `seen`, archived, opened from Browse -> the page. The PR notes it as a gap in the spec.
7f. **Tools.** There is no `lint:boundaries` script; the boundary check is part of `pnpm lint`. The browser test is Playwright (`e2e/`, `pnpm test:e2e`, the server faked in `e2e/support/fixtures.ts`), not a vitest project.
7g. **`restoreChannel` is slow to resolve.** It waits for any refresh in flight and then a full refresh (`store.ts:352-365`), so the Restore dialog stays busy for a bootstrap; its tests use a deferred bootstrap. `getConversation(id)` (for `isPrivate`/`isGeneral`, R8) is not in R2's list; `deps.ts` exports it and the fake provides it.
8. **Tests of other tickets that change** (R13, R18): the TOKI-033 route tests for (b) and (c) (new cases, no text change), the TOKI-034 tests that render `ConversationStarters` (mock `channel-archive/index.ts` with a stand-in `RestoreButton`; the R14 case through `ConversationStarters` gains "Restore").
9. **Pull request notes.** The change requests to TOKI-033/034/035/093/100 are in the spec's Hand-offs; the PR names them, edits no other spec.

## What can break / riskiest step

1. **Step 7, the route.** It changes behaviour TOKI-033 built. Two effects fight: the case (c) move to #general and the new page branch. The branch must come before (b) and (c) in the render and the effect must skip an archived-member detail, or an Admin who archives a channel is thrown to #general. `lastViewed` is written in case (a) only; the page writes none. The test is the memory-router test with both orders of (ii) and the two orders of (iv).
2. **Step 5, the archive press.** Irreversible for other people (the channel leaves every list). The count must come from a fresh read at the press; the confirmation never opens without a count; a double press and a double confirm each send one request; a confirmation never also offers Undo.
3. **Step 7 (ii), reload and unjoined path.** A member who opens an archived channel by address goes through `UnjoinedView`; the page must appear as soon as `readChannel` puts the detail in the store, and `UnjoinedView` must unmount without calling `onNotFound`.
4. **Step 8, stale Restore.** An Admin demoted meanwhile gets 403/404: toast and `onChanged` so the list shows what the server says. A resolved command is never read as a failure even if its refresh failed (TOKI-032 R15).
5. **Seams with other work.** TOKI-100 edits `DetailsPanel.tsx` in a different place (the `Controls` prop) and the later ticket rebases; TOKI-041 replaces the body of `ArchivedHistory` and keeps its file, props and test id. The page asks for no message and has no composer element.
6. **Not delivered here.** Readable history (AC-052, TS-082) passes only when TOKI-041 lands (concern 9); the strip "This channel was just archived" and live removal (TOKI-038/040/082).
